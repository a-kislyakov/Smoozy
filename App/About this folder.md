# App

This folder holds the actual application code, produced during the Build stage. It's organized by module.

Planning documents live in `Preparation/`, not here.

**Two folders here are not modules, and each one's own note says so.** `Shell measurement/` is the throwaway that filled the shell comparison sheet, kept for reproducibility. **`Release/` is the machinery one release runs** — it composes and signs a release over artifacts that already exist and checks a published one from the outside. Nothing in Smoozy depends on either. **`Scenarios/` is not a module either**: it is the scenarios played as tests, and the desk machine they play against, and its own note says so. **`Build a test copy.sh` is not a module either**: it builds the Creator's own test copy, *Smoozy Test*, from the newest commit on `main`. Its account is `Audits/Build/Step 10c/A test copy the Creator builds — what landed.md`.

**And nine modules are each in two folders.** *(Two until 2026-09-19, when step 10c piece 3 split seven more.)*

`Server protocol and transfers/` and `Server protocol and transfers — framing/`. One plan governs both. The framing folder holds what both ends of the connection speak — a request's frame, the two versions that travel with it, and the shapes a result carries — and it opens no connection; the folder beside it holds every act of connecting. **The reason is the program the rented machine runs**, which is the far end of an SSH connection and never opens one: while the module was one crate, that program carried the desktop's SSH client and that client's C cryptography. Split on 2026-09-06 at step 8a, and each folder's own note says which half it is.

`Rented-server runtime/` and `Rented-server runtime — program/`. One plan governs both. The first holds what the supervisor, the machine-local endpoint, the workers and the package transaction *are*; the second holds `smoozy-server`, the one program a rented machine runs, which was a binary inside the first until step 8b. **The reason is that a program has to be able to reach the work it drives.** Dependencies belong to a package rather than to a target, so a binary inside the first folder could reach only what that library reaches — and every crate holding machine-side work depends on that library, so reaching them from it would close a loop the build tool refuses. A package nothing depends on can depend on all of them. Split on 2026-09-06 at step 8b; the ruling is `Audits/Build/The machine program/Decisions record.md`.

`Servers/`, `Server Setup/`, `Job files and outputs/`, `Render Settings/`, `Dependency Upload & Remap/`, `Queue & History/` and `Rendering/`, each beside a folder of the same name ending `— machine` (`— values` for `Servers`). One plan governs each pair. The second folder holds the half the rented machine's own program may take, and opens no connection; the first holds every act of the desktop's and re-exports the second at the paths it always had. **The program takes all seven**, through the two that hold the machine-local queue and the render worker. **The reason is the same as the framing split's**: the machine's program must never carry the SSH client, and while these halves sat beside the acts, taking them meant taking it. Split on 2026-09-19 at step 10c piece 3; each folder's own note says which half it is.

**Every other folder is one module, named for the plan that governs it.** `The shape` gets no folder, and the reason changed on 2026-09-06 without the folder changing. It used to read *there is nothing in it to construct*. **The three executable classes it names are now constructed** — they are the three roles of the one machine-side program, built at step 8a and living in `Rented-server runtime — program/`, under the plan that owns what that program is. **So the reason is that `The shape` constructs nothing of its own, not that it names nothing constructable.**
