# Rented-server runtime

*How the server package is placed, committed, rolled back, repaired and replaced on a machine whose boot return is two arrangements rather than one; what the supervisor is, what restarts it, and what its machine-local endpoint is made of; how every worker is started, identified, arbitrated and stopped; how work waiting for a person is held on the machine, outside its line, indefinitely, and released by an answer arriving over a path Smoozy is not on; what holds reconciliation back while a setup is unfinished; how the Telegram role is hosted and which machine may ask for what the user sends; and how a render's two streams and its exit are captured, retained with explicit loss reporting, and presented so that *the render printed nothing* is a recorded fact rather than an absence.*

**Scope, from [The shape](The%20shape.md#6-rented-server-runtime):** the complete transactional placement, boot registration, health exchange, commit, rollback, repair, and replacement of the server package; durable package-phase record; previous-version selection; continuation-or-fresh-replacement retry rule; supervisor ownership; per-operation and role-worker lifecycles; recorded execution-group identities; per-kind termination ownership and signal targets; machine-local endpoint existence, lifecycle and access control; scheduling and exclusion for every worker class that can contend for machine resources, including preview and media; machine-held jobs and commands awaiting a person and their common answer-release path; machine-level setup-in-progress state that holds reconciliation back; stdout, stderr and exit capture; finite retention of both captured streams, with a stated ceiling above the control-state reserve and an explicit loss outcome where the ceiling is reached, the streams still drained; an explicit collection outcome distinguishing *the render printed nothing* from *nothing was collected*; release provenance, so a requested package version resolves through the signed manifest, exact artifact descriptor and digest rather than through a version label; one exclusive and recoverable transaction owner, so a second caller can neither terminalise another's attempt nor be locked out of a genuinely abandoned one; health readings; Telegram worker hosting; runtime upgrade and replacement, with the whole package commit blocked by live or held work and removal only as an internal step. Each owning feature document declares an operation's resource class, priority, cancellability, and atomic-or-partial boundary; Rented-server runtime owns the common arbitration mechanism. **Three things answered below, and one clause blocking the commit on a wider condition than the shape's own sentence, were departures from that list; §6 and both *Each rented server* sentences now name them, and [Section 16](#16-unresolved) items 21 and 22 record each closure and what stood before it.** This document implements `State, identity and recovery` over the protocol from `Server protocol and transfers`, places the package through that protocol's pre-package surface, runs work for `Server Setup`, `Render Settings`, `Dependency Upload & Remap`, `Rendering`, `Queue & History` and `Telegram`, and reads file rules from `Job files and outputs`.

**The boot return is two arrangements and a detection step, never one.** Fact 1's narrow clause is answered on both machine kinds by completely different mechanisms, and *"on a container every route a builder would reach for first is a silent no-op"* (same document, Fact 1's narrow clause). It must check for its own state, not for reachability."* (same, *Recycle*.) The installation identity of [State, identity and recovery](State,%20identity%20and%20recovery.md#23-the-machines-installation-identity) §2.3 is the only thing that tells a rental from an installation — no path, no host key and no directory's presence does. Fact 83 is the second independent argument for the same rule: a fresh rental on the same physical machine presented **byte-identical** keys while being a demonstrably different rental ([The host key](The%20host%20key%20—%20obtained%20without%20authenticating,%20and%20whose%20it%20turns%20out%20to%20be.md), Fact 83). **The mechanism this sentence used to give — that container images carry host keys baked in at build time — is withdrawn at its own source, corrected 2026-08-22.** A container's keys are the **host's**: [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md) Test 19 re-rented the same offer and got three identical keys, and a **different** machine on the **same** `ubuntu:22.04` image gave three different ones — *"the keys are neither the proxy's nor the image's: they are generated once on the host and reused by whatever the host rents out next"*. **The conclusion is strengthened rather than weakened**: the keys name hardware Smoozy does not rent and outlive every rental on it, so they name neither the rental nor the installation. **Nothing in this document is keyed on a host key, on reachability, or on a file's or directory's presence.**

**[State, identity and recovery](State,%20identity%20and%20recovery.md#13-rules-that-bind-every-store) §1.3 rule 5 binds every section below: nothing reads a file's presence, its name or its size as state.** The carve-out belonging to another document is `Job files and outputs`', for the re-run's already-there test.

**This document has two carve-outs of its own, and they are named here rather than left to be discovered in the code. Added 2026-09-12, out of the step 8b code round, which found this sentence claiming there were none.** The two machine-level on-or-off states — **the Telegram role's enabled-or-disabled desired state ([W7](#53-the-one-role-worker)) and the setup-in-progress state ([P1](#9-the-setup-in-progress-state))** — each write one of their two values by taking the record away, and read that absence back as that value. **The reason is that each holds one state with one meaning and there is no second record to disagree with it**: an absence is *disabled*, or *no setup in progress*, and nothing else. **Reading an absence as *unknown* instead would be worse rather than safer** — it would stop a machine no placement had ever written either record on from reconciling at all, and it would not close the case it is reached for, since a record lost some other way reads as absent whichever way the value is spelt. **Everywhere else the rule stands exactly as written.** That rule is what forces [11.1](#111-the-two-streams-are-captured-by-the-worker-into-sinks-the-supervisor-made)'s byte count to be Smoozy's own count rather than a reading of a sink, and [1.4](#14-what-a-registration-is-confirmed-by-and-it-is-never-presence)'s registration check to be a comparison of content rather than of existence.

**The shape forbids discovering or stopping a worker by executable name, command-line pattern or process search**, on Batch A's observation that a pattern *"matched **two** process ids"* and the intended worker went on working ([Batch A](Batch%20A%20—%20the%20shape%20throwaway.md), Fact 68). **Fact 91 completes that rather than contradicting it:** a recorded identifier alone is a pattern with extra steps, because identifiers are re-handed-out; the identifier **paired with the kernel-set start time** is not, because the later holder cannot present it and cannot forge it ([The host key](The%20host%20key%20—%20obtained%20without%20authenticating,%20and%20whose%20it%20turns%20out%20to%20be.md), Fact 91).

**The arrangement that makes work survive a reboot also undoes a deliberate stop.** Observed: two seconds after a clean stop, `Restart=always` started a fresh process and the work carried on ([Batch A](Batch%20A%20—%20the%20shape%20throwaway.md)). **Only the supervisor is boot-restarted; every worker outcome comes from durable state.** [3.2](#32-what-restarts-the-supervisor-and-it-differs-by-machine-kind) is that rule made concrete on both machine kinds.

**Fact 78's two-file half is answered and negative.** Replacing a file by rename is atomic **by the call's own definition rather than by a property of one filesystem, corrected 2026-08-20** — `rename(2)`, read 2026-08-20 at `https://man7.org/linux/man-pages/man2/rename.2.html`: *"If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing."*, unqualified by filesystem, and POSIX requires the same. `Facts.md`'s own Fact 78 entry already carried the general form and this document narrowed it when it copied it across. A symlink pointer switches atomically by the same means, **and no single operation updates two independent files atomically** — with one documented exception this document does not use, `RENAME_EXCHANGE`, which *"Atomically exchange oldpath and newpath"* and permits a non-empty directory on either side; `rename(2)` publishes filesystem-support lists for two of its flags and **none for that one**, and nothing establishes it on overlayfs, which is one of this project's three filesystems — *"the matching pointer-and-registration pair is a design obligation, built on single-rename atomicity plus ordering, not a filesystem primitive"* ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 78). [Section 16](#16-unresolved) item 3 carries what it does not close.

**Fact 80 gives a rule and takes away a signal.** Ubuntu's own reboot-required flag *"was never set on the machine that needed a restart most"*, so the rule that survives both machines is: run the check after installing and restart only if it fails — never unconditionally and never on the package manager's word. **Restart cost varied from 9 seconds to 90 across three machines**, so nothing here budgets a fixed wait for a machine to return.

**Fact 27 differs by machine kind, and both halves bind.** On a virtual-machine rental elevated access is ordinarily present and passwordless; **on a container a non-root login's elevation route demands a password Smoozy does not hold**, which is K11's own observation and is what this sentence used to overstate as no route at all (corrected 2026-08-20); and root inside a container is capability-limited. **Nothing downstream changes** — a password Smoozy does not have is as good as no route for the placement's purposes, which is why K11's conclusion stands either way. Restarting the machine is refused to an ordinary login — *"An SSH session is not a local seat"* (Fact 51). So [1.3](#13-on-a-container)'s registration is answerable only as *root installs the hook and the hook drops privilege*, and the elevation is `Server Setup`'s step.

A provider's stop is an orderly shutdown rather than a power cut, and **one provider answers no ping at all** while its connection works perfectly. **No health check in this document pings**, and nothing here infers a machine's state from a connection's.

## 1. The machine kind, and the boot return that is two arrangements

**Constraint:** [The shape](The%20shape.md#each-rented-server) — *"The machine's boot service facility starts it after a reboot and restarts the supervisor after an unexpected exit."* And Fact 1's narrow clause, answered on both machine kinds by two different arrangements, with the pair as the point.

### 1.1 Detection comes first, and is re-taken at every placement

**K1. Before any registration is chosen, the machine kind is detected, by `systemd-detect-virt` and by the presence of the container marker file, in that order.** That is the detection step the evidence names — *"**Tell them apart** with `systemd-detect-virt` and `/.dockerenv` before choosing"* ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 1's narrow clause). **The two readings select an arrangement by this closed table and by nothing else**, because a virtualization type is not a machine kind: the tool returned `docker` on the container and `kvm` on the virtual machine in this stage's own evidence, and on a machine that is neither it names none of them. **A near-miss on 2026-08-22 is why the table is closed rather than merely tidy.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md) met **a container running inside a VMware virtual machine**: bare `systemd-detect-virt` said `docker`, `/.dockerenv` was present, PID 1 was a shell — and **`systemd-detect-virt -v` said `vmware`**, with the DMI strings reading `VMware, Inc.` / `VMware Virtual Platform` and the processor carrying the hypervisor flag. **This table places it as a container and is right.** **A table that expected the two readings to agree, or that treated the virtual-machine form as authoritative, would place it as a virtual machine and choose a service-manager registration on a box that has no service manager.** The nesting was not on the record before.

| What the two readings give | Arrangement |
|---|---|
| the container marker file is present, **or** `systemd-detect-virt` names a container technology | [1.3](#13-on-a-container) |
| neither of those, **and** systemd is running as the machine's first process | [1.2](#12-on-a-systemd-machine) |
| anything else | K3's refusal |

**The second row is the bare-metal rented GPU server as well as the virtual machine**, and it is the machine the product's own first sentence names, so a reading that refused it would refuse the ordinary case.

**K2. The detected kind is a machine-derived value and is re-taken at every placement, never carried forward from the local record.** It carries the installation identity it was read under ([State, identity and recovery](State,%20identity%20and%20recovery.md#23-the-machines-installation-identity) §2.3), and a placement never reads a kind recorded under another installation. The recycle case is why: a recycled container is a new installation on the same address, and every machine-derived value held against that server row is disqualified by that document's own rule.

**K3. A machine K1's table does not place is a placement that does not happen.** The bootstrap-and-repair request answers that the machine is not one this package version can register a boot return on, and nothing is staged and nothing is committed. **No third arrangement is guessed at, and nothing but the two container readings K1's table names ever selects the container arrangement** — the systemd arrangement is selected by that table's second row and needs no further marker. The two arrangements below are the complete set this document carries.

### 1.2 On a systemd machine

**K4. The registration is a user unit under the supervisor login's own configuration directory, enabled, plus lingering granted to that login by name.** No elevated access is needed for either step. Observed: the service returned **6.71 seconds** into a new boot, as uid 1001, with nobody logged in, **resuming rather than starting over**, and the system side confirmed it was started by uid 0 at boot rather than by a login; Hyperstack reproduced it independently with the service started six seconds after boot and four heartbeats before any login.

**K18. The unit is written so that ending the supervisor does not end the workers it started, and that is a requirement of the registration rather than a detail of it.** The service manager's default takes the whole control group down with the main process, so **a unit written to K4 and nothing further destroys a running render on every supervisor restart** — including the restart S4 performs after an unexpected exit, and the one G25 performs during a package commit. Observed directly: with the default in force, killing the supervisor under a live render took the worker and Blender with it and reconciliation wrote *re-run once*; with the unit corrected, the same kill left both alive, the worker reparented to the user service manager, and **the render finished under a supervisor it never met** — disposition `resumed`, attempt count unchanged, output **byte-for-byte identical to the uninterrupted run**, no frame re-rendered ([The last two boxes](The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md) §3.3).

**The machine permits it two independent ways and both are available to an unprivileged login with no elevated access** — the unit's kill behaviour confined to the main process, or each worker started in a transient scope of its own — proved by three side-by-side probes on scratch units. **This document requires the first**, because it keeps K4's arrangement exactly as it stands and adds one directive, where the second changes how the supervisor starts every worker, which nothing here describes. **What the reduction must not do is exempt the supervisor from being ended**: G25's deliberate end and S4's restart both act on the supervisor's own process and are unaffected.

**Nothing equivalent is owed on a container**, because S5's keeper starts the supervisor as an ordinary process with no control group of its own to collapse, and the orphaning behaviour there is the machine's default rather than a directive.

**K5. Enabling alone is not the registration and its failure is silent.** With the unit still enabled and only lingering turned off, the program **did not come back** and *"no log line anywhere says why"*. **So the registration is not complete until lingering is read back and found granted** — the state and the linger flag are read for that login by name and compared, and a placement whose read-back does not show lingering granted fails before the commit. **The name in the grant and in the read-back alike is the machine's own, derived at execution, never a value Smoozy interpolates** — [Server protocol and transfers](Server%20protocol%20and%20transfers.md#11-what-the-surface-is-made-of-and-it-is-two-mechanisms-rather-than-one) §1.1's machine-self-derivation route, K6's mechanism — because the login name is a user- or provider-origin identifier and no such value rides a command string in either phase. **And what the read-back is worth is stated rather than overstated**: it is served by the machine's own login manager, so it catches a grant the image's policy refused or dropped — K8's per-image fact, and the silent failure this clause exists for — and defends against nothing the machine itself does; no read-back on a machine can exceed that machine's honesty ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#3-the-authentication-boundary) A6).

**K6. Lingering is requested by name and never as *self*, and the name is the machine's own, derived at execution.** The bare form failed — `Could not enable linger: No such device or address` — because *self* is derived from a session that does not exist under a provider that creates no login session; the tool's own page documents exactly that ground — it *"Takes one or more user names or numeric UIDs as argument. If no argument is specified, enables/disables lingering for the user of the session of the caller."* (`loginctl(1)`, read 2026-08-22; label: **documented**, citation in the sources companion). By name it succeeded, unprivileged. **The name is never carried by Smoozy.** The grant and K5's read-back are constant command strings under [Server protocol and transfers](Server%20protocol%20and%20transfers.md#11-what-the-surface-is-made-of-and-it-is-two-mechanisms-rather-than-one) §1.1's machine-self-derivation route: the login shell replaces a double-quoted substitution with `id`'s name for the invoking process's **effective** user — a value the process's own credentials answer, resting on no session, which is precisely the ground the bare form lacked (label: **documented**; the route's citations are that document's). **The connection's configured login name is not used, and the difference is deliberate rather than convenient**: what the grant must name is whatever the machine's own user database calls the effective user this connection's login maps to — the same database and identity the login manager consults — and the derivation asks the machine exactly that question, where a Smoozy-carried copy could differ from the machine's own mapping for the same uid. **The derived name is the machine's claim about itself and is trusted for exactly what the two commands need and nothing more**: it is consumed on the machine, in those commands, and is never read back as a value, never recorded, never correlated, and never evidence of which login Smoozy connected as; no rule anywhere keys on it. **What bounds a wrong or dishonest derivation is the machine's own refusal boundary plus K5**: on an honest machine the derivation names the one login the grant is permitted to name — the caller's own, any other being refused outright (*What binds this*; [The last two boxes](The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md) §10) — and a substitution that names no login the machine holds fails the grant and the read-back loudly, before the commit. **The composed constant form has been run on no machine**: the by-name grant and read-back are observed, the derivation is documented, and their composition rests on the same per-image ground every pre-hand-over command stands on; its failure is K5's loud one, never a silent registration. **[Section 16](#16-unresolved) item 32 carries it as permanently unresolved, added 2026-09-02** — running the composed form wants a rented machine and there will be none, so this sentence records a permanent state rather than a run that is coming.

**K7. Where the provider creates no login session, the runtime directory variable is exported by hand.** Observed on a provider that set the option turning login sessions off: no session is created, the per-user runtime directory does not exist, and the user-level control tool cannot reach a bus without it ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), the `UsePAM no` reading). **The exported value's carriage is declared, and it is K6's route again.** The value is a fixed literal prefix — the per-user runtime directory form the observation names, `/run/user/1001` on the observed box — completed by the login's **numeric effective user ID**, derived on the machine under [Server protocol and transfers](Server%20protocol%20and%20transfers.md#11-what-the-surface-is-made-of-and-it-is-two-mechanisms-rather-than-one) §1.1's machine-self-derivation route: `id`'s effective user ID, the same invoking-process credential as K6's name, in numeric form, so the route's citations are that document's. The assignment rides the constant command string as a variable-assignment prefix, which the shell exports *"for the execution environment of the command"* and no further (Shell Command Language §2.9.1, read 2026-08-22; label: **documented**, citation in the sources companion) — so the uid originates on the machine, reaches one command's environment, and never leaves the machine or crosses from Smoozy. **What the derived uid is and is not trusted for**: it is the machine's own number for the connection's effective login — on the observed box, the number its runtime directory sits under — consumed in that one environment value and nowhere else, never read back as a value, never recorded, never correlated, and never evidence of anything off the machine. **A wrong derivation or a wrong prefix fails loudly rather than silently**: the user-level control tool cannot reach a bus over a path that is not the runtime directory, the grant or the read-back errors, and K5 fails the placement before the commit. **The prefix's form stands on the observed box alone**, under the same one-or-two-boxes caveat every machine observation here carries.

**K7 corrected 2026-09-21, found at Build: the export names the runtime directory and does not make it, so on a provider that creates no login session the order of K4's two acts is part of the registration.** The second pass of step 10c on Sesterce, whose image sets `UsePAM no`, placed Smoozy with the enable first and the grant second, and the enable failed — *"Failed to connect to bus: No such file or directory"* — with `/run/user/1001` absent and `loginctl` answering that the user *"is not logged in or lingering"* (`Audits/Build/Step 10c/Piece 12, the second pass — Sesterce.md`, fault 1). **This clause was written from a box where the directory did exist when the enable ran**: the observation it rests on granted lingering by name first and enabled afterwards ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md)), and nothing here said the order mattered. **What makes the directory, documented**: `user@.service(5)` — *"`user@UID.service` is accompanied by the system unit `user-runtime-dir@UID.service`, which creates the user's runtime directory `/run/user/UID`"*; and the login manager's own handling of the grant, `src/login/logind-dbus.c` at systemd `v249` (Ubuntu 22.04's) and `v255` (Ubuntu 24.04's), `method_set_user_linger`, which on enabling writes the linger file and then *"`if (manager_add_user_by_uid(m, uid, &u) >= 0) user_start(u);`"*, where `user_start` in `src/login/logind-user.c` says of itself *"Start `user@UID.service`"* (all read 2026-09-21; label: **documented**, citations in the sources companion). **So a grant starts the user's service manager at once, with no session, and K6's grant is what gives K7's export something to name.** `loginctl(1)`'s own sentence says only *"a user manager is spawned for the user at boot and kept around after logouts"*, which is why the source is cited rather than the page. **The order is therefore: K6's grant, K5's read-back, then the user-level service manager asked until it answers, then the enable.** The source queues the manager's start rather than waiting for it, so **the enable waits for the manager to answer, inside the caller's own deadline** ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#46-per-waiter-deadlines) C16) — never a fixed wait, which K17 forbids — and a manager that does not answer inside it is a failure before the commit in the machine's own words. **Where a session did exist** — the Hyperstack image of the same pass — the manager answers the first time it is asked and nothing is waited for. **Not observed**: no machine has run this order since the correction; this desk has no Linux to run it on. What holds if the reading is wrong is the rule this document already has, loud failure before the commit.

**K8. The permission that grants lingering is a property of the image rather than of Linux.** The shipped policy that grants it to an unprivileged caller was read on one machine at one release, and both machines that posed it said the behaviour rather than the reading is what they agree on, with one calling it *"a per-image fact rather than a Linux one"* that should be re-read on each provider. **K5's read-back is what turns that from an assumption into a check**, and [Section 16](#16-unresolved) item 2 states what breaks where the permission is refused.

**K9. The one-shot boot entry is not an equal and is not used as the registration.** It launches once and forgets — no restart, no status, no supervision — and it carries its own trap, **whose mechanism is corrected here on 2026-08-23 against the page itself, this clause having said an entry containing the character *runs, does nothing, and is logged as a successful command***. `crontab(5)` as Debian ships it: *"The entire command portion of the line, up to a newline or % character, will be executed by /usr/bin/sh"*, and *"Percent-signs (%) in the command, unless escaped with backslash (\\), will be changed into newline characters, and all data after the first % will be sent to the command as standard input."* **So an unescaped `%` truncates the command at that point and hands the remainder to it as standard input.** The registration is not refused and nothing reports a fault: what runs is the truncated prefix, and its own ending is what cron records. **This is an additional reason to refuse the one-shot entry as the registration and never the reason** — the supervision grounds above are.

### 1.3 On a container

**K10. The registration is the provider's own boot hook and nothing else, and what the hook starts is [3.2](#32-what-restarts-the-supervisor-and-it-differs-by-machine-kind)'s keeper rather than the supervisor directly.** The hook ran on both container restarts — twelve seconds after the first request and five after the second — and launched a long-lived process running as the non-root login, which is the whole of what the registration has to do.

**K10a. Confirmed on a second seller and a second image, and the *nothing else* is now an absence rather than a preference. Added 2026-08-22.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md), on a stock `ubuntu:24.04` container: `systemctl is-system-running` returns **`offline`**; PID 1 is `/bin/sh -c while [ ! -e /.launch ]; do sleep 1; done; bash /.launch`; and **`cron`, `crontab` and `at` are not installed at all.** **So on that image the two routes K12 and K13 rule out are not merely ineffective — they are absent**, and the provider's hook is what is left rather than what was chosen. The chain matches this document's own reading: `/.launch` runs the container's provisioning and then `/root/onstart.sh`.

**K10b. What writes the hook is the rental request's own field, on the seller's control plane, and Smoozy has no route to it. Added 2026-08-22.** `/root/onstart.sh` is written from the `onstart` field of the create call. **Smoozy never rents a machine and never speaks to a seller's control plane**, so on a machine already rented the hook is a file Smoozy places over the connection at the path the seller runs — which is exactly what [K11](#13-on-a-container) and [K15](#13-on-a-container) do, and why K15's read-back is Smoozy's own content rather than a machine-set value ([K14](#13-on-a-container)). **The consequence stands unchanged and is stated once here:** a provider that runs no hook at that path is caught by nothing, because the content reads back exactly as written. [Section 16](#16-unresolved) item 16.

**K10c. Whatever the provider's hook already holds is kept, and Smoozy's part is placed within it rather than over it. Added 2026-09-21, found at Build, where it was built and no clause said it.** The hook is the provider's own file, written from the rental's own start-up field (K10b), and the provider's own instruction is to add to it, not to replace it — Vast's *"Add to `/root/onstart.sh` for persistence across restarts"*, which [Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md) already quotes. **So the placement reads the file's current content first, keeps every byte of it, and writes Smoozy's part between two marker lines of its own**; a later placement replaces Smoozy's part between those markers and never adds a second copy. **Smoozy's part goes near the top**, so that a provider command that never returns cannot keep it from running. **The record K16 holds is the whole resulting file by value**, so K15's read-back compares all of it, the provider's part included. **Why it is a clause and not a detail**: a placement that wrote Smoozy's hook over the file would remove whatever the user or the provider had put there to start their own work, which is a thing Smoozy was never asked to touch.

**K11. Installing the hook requires root, so the placement's registration step is an elevated step and `Server Setup` owns the elevation.** From the non-root account the hook's path and the traditional local start file are both `Permission denied`, and the elevation route demands a password. **The clause is answerable only as *root installs the hook, and the hook drops privilege*.** Every worker the hook's supervisor starts runs as that same non-root login, per `Job files and outputs` L13.

**K19. The root step must also leave the hook readable by the login that performs K15's read-back, and this is a second obligation rather than a restatement of the first.** K15 is performed by the non-root placement, and on the provider this arrangement was designed around **the directory the hook sits in is mode 0700 root-owned**, which the supervisor's login cannot traverse. Written as K11 alone, the placement **fails at K15 every time, before the commit**, with `container hook at /root/onstart.sh could not be read ([Errno 13] Permission denied)` — **and the failure is a permanent loop**, because the message sends the operator to run the root step they have just run. Observed on both sides of the root step: the read before it failed and the read after it failed identically, while the hook itself had been installed byte-perfectly ([The last two boxes](The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md) §2.1).

**Two routes satisfy it and both were established on the machine.** Making the containing directory traversable is enough — a named file inside it is then readable while listing the directory stays refused, so nothing else in it is exposed. Or the hook goes at the provider's **second** hook path, run by the same provider line, **whose directory is world-readable already and needs no permission change at all**. **K10 fixes which path**; where that path's directory is not readable by the supervisor's login, the root step makes it so.

**This is a property of the provider's chosen path rather than of containers**, so it is stated as an obligation on the root step rather than as a fixed permission: whatever path K10 names, the read-back must be able to reach it.

**K12. The service-manager enable is never the registration step on a container, and this is a prohibition rather than a preference.** Observed: `systemctl enable ssh` *"reports success, writes the symlink, exits 0 — and the unit will never run."*

**K12a. And the prohibition covers the third route a builder would reach for, which nothing here forbade until now. Added 2026-08-22.** **`/etc/rc.local` exists on the container image read on 2026-08-22 and nothing runs it** ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)). It is neither the service-manager enable K12 names nor the recurring entry K13 names, so a builder meeting both prohibitions would have found it untouched and taken it — and it would report success and do nothing, which is the exact shape K12 exists to close. **On a container, the boot registration is the provider's own hook at K10's path and no other file is written for the purpose**, whatever the image happens to carry. **Anything that appears to be a boot route on a machine with no init system is treated as absent until a read-back proves it ran**, which is K5's and K15's rule applied to a route rather than to a value.

**K13. The recurring boot entry did not fire on the container image that was read.** Three separate fresh starts of the daemon, including with a trivial job, gave zero, while an every-minute entry in the same table fired throughout. **This is a claim about that image and not about containers, corrected 2026-08-20**, because `crontab(5)` as Debian ships it documents the trigger as *"the time when the cron(8) daemon startup"* — which is what those three starts were — and names no condition a container would fail. The observation and the documentation disagree and neither is discarded: [Section 16](#16-unresolved) item 20 carries it, and item 16 rests on this rule by name. **On a second image the question cannot arise at all — added 2026-08-22.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md): on a stock `ubuntu:24.04` container **`cron`, `crontab` and `at` are none of them installed**, so the recurring route would need an elevated package install before it could even be attempted. **Two images, two different reasons, the same outcome** — one where the entry does not fire and one where there is nothing to enter it in. **That strengthens the rule on both images and settles nothing about containers in general**, which is what this clause already says of itself.

**K14. So on a container two routes a builder would try first report success and do nothing**, which is why K1's detection is a step rather than a courtesy, and why K5's and K15's read-backs are what separate a registration from a report of one. **But K15 does not reach as far on a container as K5 does on a systemd machine, and the difference is which side wrote the value being read.** K5 reads back a **machine-set** value — the linger flag, set by the machine and refused where the provider's policy refuses it — so a machine that will not grant the registration fails the placement loudly. K15 reads back **Smoozy's own content** against the record Smoozy wrote, so it catches the recycle case and **cannot catch a provider that runs no hook at the path K10 names**: the content reads back exactly as written, the registration is confirmed, and nothing ever runs it. That failure is separated by no read-back this document has; [Section 16](#16-unresolved) item 16.

### 1.4 What a registration is confirmed by, and it is never presence

**K15. A boot registration is confirmed by reading its own content back and comparing it against the boot-registration record Smoozy wrote.** The recycle observation forbids the other reading in the plainest terms: the hook *"was not deleted but replaced"* by an 82-byte provider default dated at the recycle moment, so *"a check for 'does my hook exist' passes while the hook does nothing Smoozy asked for"*. This is [Server protocol and transfers](Server%20protocol%20and%20transfers.md#5-the-bootstrap-and-repair-request-and-package-inspection) B4's *content, never presence* applied to the half of package inspection that is this document's.

**K15 is performed by the non-root placement on both machine kinds**, which is what makes K19 an obligation on the container's root step rather than an afterthought.

**K20. What K15 catches and what it does not, both observed.** It **refuses loudly when the registration's own bytes change** — `registration content differs from the record Smoozy wrote (246 bytes on the machine, 268 recorded)`, `failed before commit`. It **confirms happily when a supplementary configuration file changes what the registration does** while its own bytes are untouched: with a drop-in in force and the unit's effective behaviour changed, the read-back answered `content matches the record` ([The last two boxes](The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md) §3.4). **Both halves it compares are Smoozy's own**, so a change to the effective configuration made by anything but Smoozy is outside its reach. **This document adds no second read-back for it** and records the gap at [Section 16](#16-unresolved) item 18; what it does do is forbid any reader from taking a confirmed registration as a statement that the effective configuration is Smoozy's.

**K16. The boot-registration record is a record Smoozy wrote and holds the registration's content by value.** It is in the package area ([State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2), and nothing derives it from what is on the machine at the moment it is read.

**K16a. The record is written by the non-root placement on both machine kinds, and it holds on a container even though the registration itself is the root step's. Added 2026-09-06, found at Build, where the record had to be written and the document did not say whose it was.** The two halves of a container placement are split by privilege in a way that invites the wrong answer: K11 makes installing the hook the elevated step's, so a builder can read the record as the root step's too. **It is not.** K15's read-back is the non-root placement's on both kinds, which is what makes K19 an obligation on the root step rather than an afterthought, and G31a makes all three durable records the placement's own, this being one of the three. **So on a container the placement writes the record and leaves the hook to the root step**, which is a hand-over and not a refusal. A container placement that wrote no record would leave the recycle case caught by nothing at all, on the machine kind the recycle was actually observed on, K15 having nothing to compare against. **This adds no obligation to the root step**, whose two are K11's and K19's: the record is in the package area (K16) and no root step is asked to touch it.

**K16b. The record is written durably before the registration it describes, and the same order holds when a rollback restores the pair. Added 2026-09-06, found at Build beside K16a; G3 and G9 order other things and not these two.** It is [State, identity and recovery](State,%20identity%20and%20recovery.md#3-desired-state-and-observed-state) D1's *intent before acting*, the rule G3 already applies to every phase of this transaction, and the two orders are not equally safe. **Interrupted after the record and before the registration**, the record holds content the machine does not, which is exactly what K15 compares and it fails the placement before the commit; G17's continuation writes both again. **Interrupted the other way round**, Smoozy's own boot bytes are live on the machine with no record at all, which package inspection reads as the honest never-held answer (G31a) on a machine that is about to start Smoozy, and K15 has nothing to compare against — a true reading of the records and a false statement about the machine. **Nothing of the previous registration is lost by writing over the record**, which is what would otherwise argue for the other order: G4 has already carried the previous boot-registration content forward by value, and G14a is what restores from it.

**K17. Nothing budgets a fixed wait for a machine to come back.** Restart cost was measured at **9, 11 and 12 seconds** on one machine, **21, 22 and 28** on a second and **85 to 90** on a third (Fact 80), **49 and 55 on a fourth** ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md), 2026-08-22), and a container recycle returned in about 90 seconds against 15–20 for a reboot. **The same rule holds for a machine coming up for the first time, and there the spread is an order of magnitude. Added 2026-08-22, observed on three sellers the same day:** requested to reachable was about **40 seconds** on one, about **90** on another and about **seven minutes** on the third. **So anything that waits a fixed period for a machine to come up is wrong on at least one seller in three**, which is the same rule this clause already states for a machine coming back. A caller waits on its own deadline ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#46-per-waiter-deadlines) C16, C17) and resumes on [Server protocol and transfers](Server%20protocol%20and%20transfers.md#45-a-reconnection-is-gated-on-the-installation-identity-and-not-on-reachability) C14's gate, never on a timer that assumed a number.

## 2. The package transaction

**Constraint:** [The shape](The%20shape.md#each-rented-server) — *"`Rented-server runtime` responds by inspecting package health and version; staging and validating a complete versioned package beside the active package; staging boot-service registration; and placing, repairing, or replacing the package. Its durable phase record holds the previous-version selection, commit point, health exchange, rollback, and whether retry continues an interrupted attempt or starts a fresh replacement."* The request's carriage, framing and idempotency key are [Server protocol and transfers](Server%20protocol%20and%20transfers.md#5-the-bootstrap-and-repair-request-and-package-inspection) §5's and are not restated.

### 2.0 The trusted release and the exact artifact

**G26. A requested package version is not an artifact identity, and this document consumes rather than redefines the release evidence.** [Server protocol and transfers](Server%20protocol%20and%20transfers.md#5-the-bootstrap-and-repair-request-and-package-inspection) B8 to B10 own the signed manifest's canonical bytes, the offline-root and online-key transition and revocation rules, the exact artifact descriptor, and verification at the desktop before upload and at rest by the desktop's read-back through the pre-package surface (B10). A request that does not carry B10's verified release descriptor reaches *failed before commit* without any downloaded byte being made executable or invoked.

**G27. The phase record pins B1's exact verified release descriptor by value.** It carries the manifest format and verified release sequence, requested package version, manifest digest, selected artifact identity, artifact byte length and SHA-256 digest. A retry never substitutes another manifest or artifact behind that descriptor. B8's canonical manifest, target tuple, fixed entry point and exact sources remain evidence the desktop verified and selected before it formed B1; this document does not create a second wire copy with a different field set.

**G28. Artifact selection is B8's exact tuple match and never a best effort.** `Server Setup` supplies the detected rental tuple and the desktop selects the B1 descriptor from the verified manifest before this transaction begins. This clause neither narrows nor widens the supported-rental ruling and performs no second selection. **No generic Linux entry, closest processor, closest ABI, capability fallback, package-name guess or first entry is permitted.** No exact match is an unsupported machine reported before any package byte is executed.

**G29. Staging consumes B10's at-rest evidence.** The staged artifact's byte length and SHA-256 digest are compared with B1's verified release descriptor before it is made executable or any byte invoked — B10's read-back comparison, performed by the desktop through the surface where no verified runtime is alive, and free to be the live verified runtime's own comparison where one is. A mismatch records *failed before commit*, leaves the pointer and boot registration untouched, and is never repaired in place.

**G30. Trust and anti-rollback failures are inputs to the transaction, never readings made from staged material.** B9 and B10's accepted key-set generation, release sequence, manifest signature and digest are decided before this document acts. A version answer from the package, a matching filename, transport success or bytes self-consistent with an untrusted manifest cannot replace that evidence.

**G31. Package inspection and continuation expose and re-check the same evidence.** B4 returns the active pointer's release sequence, package version, manifest digest and artifact digest; the phase and retained-adapter intervals; and each adapter's declared current-plus-immediately-previous interval and request set. G19 re-checks G27's recorded descriptor before staged material is reused. The package phase becomes *staged and validated* only after those values and B10's at-rest comparison agree.

**G31a. Every value B4's inspection returns exists as a durable record the placement writes, because no program answers an inspection in either phase.** B4 is a composed file-transfer-subsystem reading of the installation's own durable records: the desktop composes the answer, a dead supervisor changes nothing, and on a machine that has never held a package every record is absent, which is the honest never-held answer. Three records carry the whole set — the boot-registration record (K16), the installation identity (G10), and the phase record (G2). Which of the phase record's two recorded descriptors is the active pointer's is decided by the pointer's own value against the recorded staging and previous locations, which is G17's *committing* rule already. **Two of B4's values had no durable home until 2026-08-22 and the phase record now holds both by value, because each was a value a program would have had to compute on demand — exactly what B4's composed reading forbids:**

- **the active package's complete descriptor across later attempts.** G2 held the previously active package's version, retained-adapter interval and location alone, so from the moment a later attempt rewrote the one phase record, the active package's release sequence, manifest digest and artifact digest existed nowhere durable and B4's active-pointer values could not be composed. G2 and G4 now capture the previous active package's complete verified descriptor by value.
- **each retained adapter's declared protocol interval and request set.** `Server protocol and transfers` [1.2](Server%20protocol%20and%20transfers.md#12-capability-negotiation-and-it-is-load-bearing-rather-than-a-courtesy) item 3's request-set declaration was otherwise only a running adapter's own answer. The placement writes it into the phase record by value, per retained adapter, taken from the staged package's own declaration after G29's at-rest comparison has passed and before the *staged and validated* phase is written; the runtime rewrites it the same way where it performs its own half of a replacement (B2). Inspection reads it as content and never asks a program.

### 2.1 The durable package-phase record

**G1. One phase record per machine, in the package area, written by whatever is carrying out the transaction, and it is the record B3 answers idempotency from.** [Server protocol and transfers](Server%20protocol%20and%20transfers.md#5-the-bootstrap-and-repair-request-and-package-inspection) B3 is exact about this and about why: the supervisor may not exist when the request arrives, so *"A builder must not look for an operation record for this request."*

**G1a. One kernel-held exclusive lock owns the whole package transaction wherever a machine-side program is performing it, and it is acquired before G1 is created, replaced or changed and before any phase act begins. Narrowed 2026-08-22 — see [G1b](#21-the-durable-package-phase-record), which owns the case this clause cannot reach.** The lock is at one fixed path in the package area — the same path G1b claims. Its holder opens it itself, holds the exclusive open-file-description lock for the whole inspection, staging, commit, health exchange, rollback and terminal write, marks the descriptor close-on-exec, and passes it to no child. **Documented** ([Sources](Sources/Rented-server%20runtime.sources.md)): Linux `flock(2)` says an exclusive lock admits only one holder and that locks are released when all file descriptors referring to the open file description have been closed. A process exit therefore makes a genuinely abandoned transaction claimable without a timer, while a live holder remains the owner. **That property belongs to a machine-side holder and to no other** — G1b states what stands in its place where the performer is the desktop. A claimant that cannot acquire the lock changes no phase, pointer, staging path or health result; it returns *package transaction in progress* with the recorded owner and phase. A claimant that acquires it after abandonment re-reads the phase and follows G17 or G18; it never takes over merely because a deadline or wall-clock age passed.

**G1b. Who is actually holding it, and before hand-over the answer is nobody — so the claim in that case is a different instrument. Added 2026-08-22, out of the third sanity sweep's verification round; G1a as it stood named an owner no phase of the bare machine could supply.**

**The case G1a reaches.** A verified runtime is alive and performs its own half of the transaction ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#5-the-bootstrap-and-repair-request-and-package-inspection) B2). That program opens the lock file itself and G1a stands exactly as written, its process exit releasing the claim without a timer.

**The case it does not.** Every bare machine, and every machine whose supervisor is dead — which is the whole case the bootstrap-and-repair request exists for. There the desktop performs the transaction through the surface (G29, G31a), and **the surface has no route to a kernel lock**: before hand-over there is no Smoozy program on the machine at all ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#11-what-the-surface-is-made-of-and-it-is-two-mechanisms-rather-than-one) §1.1), the command channel's invocations are per-invocation processes whose exit releases any lock they took, and the file-transfer subsystem's observed request set carries no lock operation of any kind.

**What claims it instead, and it is one operation rather than a mechanism.** The claim is the **exclusive create of the lock file itself**, through the subsystem's own `SSH_FXP_OPEN` with `SSH_FXF_CREAT` and `SSH_FXF_EXCL` — `draft-ietf-secsh-filexfer-02` §6.3, read 2026-08-22: *"Causes the request to fail if the named file already exists. SSH_FXF_CREAT MUST also be specified if this flag is used."* **Observed** on OpenSSH's own server subsystem driven over a pipe, macOS 26.6.2, `OpenSSH_10.3p1`, 2026-08-22, with a control either side: an exclusive create on an absent path returned a handle; the same request on the now-existing path returned status **4, `Failure`**; a plain create on that same path returned a handle, so the refusal is the flag rather than a permission; and the exclusive create succeeded again once the file was removed. **And it is observed on rented machines too, which is stronger than the ground this clause used to state — corrected 2026-08-23, where the evidence given was the caller's-end reading alone.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md) group 1, 2026-08-22, on **three machines across three sellers, two operating-system families, two machine kinds and three OpenSSH versions** — a Vast container on Ubuntu 24.04 (9.6p1), a Hyperstack virtual machine on Debian 12 (9.2p1) and a Sesterce virtual machine on Ubuntu 22.04 (8.9p1): *"Exclusive create over an existing path | **refused** (`Failure`)"*, with the same control on the same row — *"Plain create over the same path"* **succeeded** — and that batch names G1b as what was at stake. **What is left as an expectation is a server Smoozy has not met**, which is [Section 16](#16-unresolved) item 23's neighbour and is the standing `Server protocol and transfers` [Section 12](Server%20protocol%20and%20transfers.md#12-unresolved) item 3 gives the rest of the surface. **It costs no session beyond the reading channel already open** and needs no program on the machine, which is why it is this and not a held command invocation — that alternative would hold one of `Server protocol and transfers` T5's sessions for the transaction's whole length, and a machine whose learned cap is one has none to spare.

**What the claim file holds:** the claiming **installation identity** (G10) and G2's transaction-owner fields. It is removed at the terminal write, and by nothing else.

**A claimant that meets an existing claim does exactly what G1a says a failed acquisition does** — changes no phase, pointer, staging path or health result, and returns *package transaction in progress* with the recorded owner and phase.

**One take-over is permitted and it needs no timer: a claim naming the claimant's own installation identity.** [Desktop app and delivery](Desktop%20app%20and%20delivery.md#31-one-process-one-instance-and-two-short-lived-helpers) P2 admits one ordinary running instance per user, so a claim written by this installation cannot also be held by a live process of it; the desktop takes it back, re-reads the phase and follows G17 or G18. **A claim naming another installation is never taken over, whatever its age** — that is [Section 16](#16-unresolved) item 23's residual, and it is the price of refusing a deadline.

**Where both performers could meet, the claim file is the single point and the lock is the runtime's addition to it.** A live runtime takes the claim file first and then G1a's exclusive lock on that same file; a desktop performing through the surface takes the claim file and cannot take the lock. So neither can begin while the other holds the file, and G1a's release-on-exit remains what tells a later runtime that no live program is inside the transaction.

**The automatic repair route, every `Server Setup` package placement, and [Server Setup](Server%20Setup.md#9b-the-user-facing-fallback-re-run)'s fallback all acquire this same claim.** Two desktop application instances do not have two owners: one acquires it and the other receives the in-progress result. The same holds when automatic repair and a setup fallback arrive together. A waiter's deadline may stop that waiter; it does not release another process's lock and does not alter the transaction.

**G2. It holds, and holds nothing derived from what is on the machine at the moment it is read:**

- the **operation identity** of the attempt in hand, which is the request's idempotency key (B1);
- the **current transaction owner** — the invocation identity, route (`automatic repair`, `setup placement`, or `user fallback`), process identifier and kernel-set start time — written only while G1a's lock is held and distinct from the attempt's operation identity;
- the **phase**, from the closed set of G3;
- B1's **verified release descriptor** — manifest format and release sequence, requested package version, manifest digest, artifact identity, byte length and artifact digest — and the **previously active package's complete descriptor by value**, the same fields, with its retained-adapter interval and location, and the **previous boot-registration content by value** ([2.2](#22-previous-version-selection-is-captured-by-value-before-the-commit));
- **each retained adapter's declared protocol interval and request set, by value** (G31a) — the staged package's written before *staged and validated*, the previous version's carried with its retained-adapter record;
- the **staging location** of this attempt's material;
- the **machine kind** detected for this attempt (K2);
- the **outcome of the health exchange**, once there is one;
- the **reason a commit was deferred**, where one was.

**G3. The phase set is closed and each phase is written durably before the act it names.** That ordering is [State, identity and recovery](State,%20identity%20and%20recovery.md#3-desired-state-and-observed-state) D1's *intent before acting* applied to a transaction that has no supervisor to hold it. **What *durably* means is defined once, in [State, identity and recovery](State,%20identity%20and%20recovery.md#13-rules-that-bind-every-store) §1.3 rule 6, and every one of this document's uses of the word takes it from there** — added 2026-08-20, because until then neither document said what made a write durable and the whole of this ordering rested on the operating system's own flushing schedule. **The figure this sentence carried — *thirty-four uses* — is dropped 2026-08-29 rather than re-counted.** It was a count taken against the document of 2026-08-20 and the document holds 75 today; the count moves with every clause added, so re-counting it puts the same clause back on the same path, and *every one* does the sentence's work without a number.

| Phase | Written before | What a later reading of it means |
|---|---|---|
| *inspecting* | anything is staged | the machine is unchanged |
| *staging* | the first byte of material is placed | staged material may be incomplete; the active package is untouched |
| *staged and validated* | the registration content is written | the material is complete and validated by content; the active package is untouched |
| *committing* | the deciding write of [2.3](#23-the-commit-is-one-deciding-write) | the pointer may or may not have moved; nothing else about the machine has |
| *committed, unverified* | the running supervisor is ended (G25) and the health exchange is attempted | the pointer has moved; the previous package is still present; the supervisor answering may be either version's |
| *verified* | the previous package is removed | the transaction succeeded |
| *rolling back* | the pointer is restored | the machine is between two known states, both of which are recorded |
| *rolled back* | — | the machine is on the previous package |
| *failed before commit* | — | the machine is on the previous package and staged material is owed a sweep |
| *deferred* | — | the machine is on the previous package, the staged material is kept, and live or held work is blocking the commit ([2.6](#26-what-blocks-the-commit-and-removal-as-an-internal-step)) |

### 2.2 Previous-version selection is captured by value, before the commit

**G4. The previous active package's complete descriptor, its adapter's declared interval and request set, and the previous boot-registration content are carried forward from the outgoing phase record, by value, in the same durable write that records a fresh attempt — **one write, carrying the fresh attempt's identity, the carried-forward values and that attempt's first phase together**, never an attempt recorded first and a phase after it — there being no program that answers for them (G31a).** A rollback restores from that record and never from a second reading of the machine, because a rollback runs in exactly the case where what is on the machine is no longer trustworthy.

**G5. There is at most one previous version kept, and it is the one the phase record names.** A machine holds the active package and, between the *committing* and *verified* phases, its immediate predecessor. **Nothing accumulates, and it is two removals rather than one.** In the forward direction the removal of the **predecessor** is the last step of a verified commit, and a fresh replacement that begins with a predecessor still present removes it as its first act, recording that removal in the phase record. In the other direction the material a **rolled-back** attempt leaves behind is not a predecessor and neither removal reaches it: a committed package is still at the staging location the phase record names, so after G14 that material is this attempt's own staged material, and **G20's bounded sweep removes it on [Section 13](#13-retention-on-the-machine) R1's terms** when the transaction reaches *rolled back*. Nothing else removes it and no separate step is written for it.

**G6. A first placement has no previous version, and its phase record says so.** A rollback with no previous version to restore leaves no active pointer, which is the *absent* branch of the installation-identity check and is safe: nothing starts, nothing claims to be Smoozy's, and `Server Setup` owns what the user is offered.

### 2.3 The commit is one deciding write

**G7. The pair problem Fact 78 names is removed rather than solved.** That fact's answer is that **no single operation updates two independent files atomically**, so an arrangement whose commit is two writes has to recover deterministically to one matching pair. **This arrangement has one write: the boot registration is written to start whatever the active-package pointer names, rather than to name a package version.** So the registration's content does not change when the version does, and the commit is the single rename of the pointer, **which is atomic by `rename(2)`'s own words rather than by an ext4 observation** (corrected 2026-08-20; the observation stands and is not what the guarantee rests on) — *"the content became the whole new string"*, **the inode changed**, *"a whole-file swap that was never partial"*.

**G8. That is a requirement on every package version and not only on the commit.** A package version that cannot be started through the fixed path the registration names is a version this arrangement refuses at the *staged and validated* phase. The refusal is a failure before the commit and the machine is untouched.

**G9. The one case where the registration's own content must change is a placement whose registration shape differs from the one on the machine**, and it is ordered rather than made atomic: the registration is written and confirmed by K15's read-back **before** the *committing* phase is entered, in a form that starts whatever the pointer names, so it is correct for the active package as well as for the staged one. A crash between the two therefore leaves a registration that starts the package that is still active, which is the state the machine was already in.

**G10. The installation identity is written and made durable before the pointer switch, not after and not beside it.** [State, identity and recovery](State,%20identity%20and%20recovery.md#13-unresolved) §13 item 2 records the window this closes from one side: an interrupted first commit could leave a committed package with no installation identity, which that document's §7 step 1 would read as **absent** and act on by discarding what the local record holds. With this ordering a machine that has a pointer always has an identity, and the remaining window is the reverse one — an identity with no pointer — which reads as *present, and the supervisor did not answer*, whose own branch discards nothing and whose repair is the bootstrap-and-repair request. **The window is narrowed and not closed**; [Section 16](#16-unresolved) item 3.

**G11. Nothing about the commit is inferred from a directory or a file being there.** The active-package pointer's target is read as a value; the registration is read as content (K15); the installation identity is read from Smoozy's own state area and never from a path a provider also writes ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#45-a-reconnection-is-gated-on-the-installation-identity-and-not-on-reachability) C15).

**G25. The rename does not put the new supervisor in place, so the transaction does, and it is an ordered, phase-recorded step of its own between the deciding write and the health exchange.** A rename starts no process, and both restarters of [3.2](#32-what-restarts-the-supervisor-and-it-differs-by-machine-kind) act **after an exit**. Without this step, [2.4](#24-the-health-exchange-and-what-a-failure-restores)'s exchange would reach the previous package's supervisor on a replacement, and nothing at all on a first placement, and G13 would read both as a failed exchange — so every runtime upgrade would roll back. **The order is: the *committed, unverified* phase is written; the running supervisor is ended where there is one; the restarter of [3.2](#32-what-restarts-the-supervisor-and-it-differs-by-machine-kind) starts a supervisor — the user unit on a systemd machine, the keeper on a container — which under G7 is whatever the active-package pointer now names; and only then is G12's exchange attempted.** The ending is what Batch A recorded as a hazard for a worker and is correct here: a clean stop was followed by a fresh process two seconds later, which for the supervisor is the behaviour wanted. **What makes the ending safe is G21**, which has already established that no live or held work depends on the runtime before the *committing* phase was entered. **A first placement has no supervisor to end** and the step is the start alone. **On a container, the commit invokes the keeper itself as that start step, once** — the same keeper [S5](#s5) says the boot hook launches — **so there is exactly one restarter and [3.2](#32-what-restarts-the-supervisor-and-it-differs-by-machine-kind) is untouched.** Where the restarter produces no answering supervisor inside the caller's own deadline, that is G13's *did not answer* branch and nothing here softens it. *(**Added 2026-09-12 by the build runner**, out of step 8b's round on the desktop-side placement performer, must-do U-1. This clause could not keep its own promise on a container's first placement: S5 made the keeper the boot hook's to start, the hook has only just been written, the machine has not restarted since — so the start step started nothing, the health exchange reached nothing, and **every first container placement rolled back.** Routed to the runner rather than written by that round's implementer, whose brief barred it from this document while a second agent held it.)*

### 2.4 The health exchange, and what a failure restores

**G12. The health exchange is one request over the machine-local endpoint to the supervisor the commit has just activated, and it is framed like any other request.** [Security and licence](Security%20and%20licence.md#8-the-supervisors-machine-local-endpoint) §8 requirement 3 binds it: *"The endpoint is not a trusted channel that skips validation; it is a channel whose peer is known."* It asks for four things and takes nothing else as evidence: the **package version** the supervisor was built from, its **run identifier**, the **installation identity** it read from the state area, and the **phase** its own reading of the phase record gives.

**G13. The exchange succeeds only where all four agree with the phase record.** A supervisor that answers with a different package version, a different installation identity or a phase the record does not carry is a failed exchange, not a healthy machine. **A supervisor that does not answer at all is also a failed exchange**, and the caller does not distinguish the two: both restore.

**G14. A failed exchange restores the previous pointer from G4's recorded value, and the phase record moves to *rolling back* before it.** The previous package is present because G5 keeps it until *verified*, so the restore is the same single rename in the other direction. **The boot registration is restored only in G9's case**, where this placement changed its content; in every other case G7 has left it version-independent and there is nothing about it to restore, which is the whole reason the pointer is the one deciding write.

**G14a. The boot-registration record is restored with the registration, from the same recorded value and in the same case. Added 2026-09-06, found at Build; G14 as it stood named the registration's content and said nothing about the record that holds it.** K16's record holds that content by value and K15 compares what is on the machine against it, so a restore that puts the previous content back on the machine and leaves the record holding this placement's content makes **every later read-back answer *content differs*** — silently at the moment it happens, permanently afterwards, on a machine the plan calls correct. The previous content is already in the phase record by value (G4), which is what the registration itself is restored from, so the record is restored from that same value in the same act; the order of the two is K16b's, in this direction as in the other, and an interrupted restore is not a new state because G16 already holds the transaction at *rolling back* until the next request completes it. **Where G9's case does not arise there is nothing to restore on either half**, exactly as G14 already says of the registration alone. **It was derivable rather than contradictory**, which is why nothing was wrong in the app when it was found — no performer carries the restore out — and why the sentence belongs here and not in a comment beside the code.

**G15. The previous package is removed only after the exchange succeeds**, which is the shape's own rule and the reason G5 keeps exactly one.

**G15a. The machine's stores are upgraded to the new program's shapes only after *verified* is written, and never inside the transaction. Added 2026-09-28, outside any round, out of step 10c of Build. No auditor of this document has seen it.** `State, identity and recovery` §1.3 rule 7 gives every store on the machine one version and upgrades it step by step when a newer program first reads it. **The order is what keeps a rollback honest**: G14 puts the previous program back in front of the stores, and a previous program must never meet a store the newer one rewrote. **So a supervisor that starts on stores older than itself reads and writes none of them while the phase record is anything but *verified*** — it answers G12's four values, which come from the package area and the state area's identity and never from a versioned store, and refuses every other request as *not yet ready*. **Reconciliation does not run in that time** (`State, identity and recovery` §6 step 0a). Once the phase record reads *verified*, the first request the supervisor serves, or its next start, upgrades the stores step by step, then reconciles, then serves. **After *verified* there is no rollback to meet the upgraded stores**: G15 has removed the previous package. **G12 and G13 are unchanged**, and G25's activation starts a supervisor that does exactly this.

**G16. A rollback that cannot complete is not a silent one.** The phase record stays at *rolling back*, the request answers with that phase, and the next request under any identity reads the phase and completes the rollback before considering anything else. **Nothing starts a fresh transaction over an incomplete rollback.**

### 2.5 The retry rule: continuation or fresh replacement

**G17. After acquiring G1a's or G1b's ownership, a retry carrying the same operation identity is answered from the phase, and the branch is fixed by the phase rather than judged.** That is B3's idempotency, taken from the phase record because there is no operation record for this request. A same-identity request that meets a live owner receives the in-progress result and changes nothing.

| Phase found | What a retry with the same identity does |
|---|---|
| *inspecting*, *staging* | **continues** — the staged material is re-validated by content, the parts that match are kept and the rest is re-staged |
| *staged and validated* | **continues** from the registration step |
| *committing* | **completes** — it reads the pointer's current value. Where it names the **requested** version it proceeds to G25's activation and the health exchange; where it names the **previous** one it re-enters *committing*; where it names **neither**, which is the interrupted-rename state [Section 16](#16-unresolved) item 3 records rather than assumes away, the pointer is restored from G4's recorded previous value under the *rolling back* phase, exactly as G14 restores it after a failed exchange |
| *committed, unverified* | **completes** — it performs G25's activation and the health exchange and takes G14 or G15 |
| *rolling back* | **completes the rollback** (G16), and then answers as *rolled back* |
| *rolled back*, *failed before commit* | **starts a fresh replacement**, under the same identity, after sweeping the abandoned staging of the failed attempt |
| *verified* | **acts again on nothing** and returns the recorded outcome (`Server protocol and transfers` C4) |
| *deferred* | re-evaluates [2.6](#26-what-blocks-the-commit-and-removal-as-an-internal-step) and either proceeds or answers deferred again |

**G18. A different operation identity never replaces a live transaction owner and never rewrites an unfinished attempt as its own.** It first acquires the claim — G1a's lock where a machine-side program is performing the transaction, G1b's exclusive create where the desktop is. Where it cannot, it receives the in-progress result and acts on nothing. Where it can because the previous owner has genuinely ended, it drives the **recorded attempt under the recorded attempt identity** to a terminal phase — completing a commit, completing a rollback (G16), or sweeping failed staging (G20). Only after that terminal write may it replace the owner and attempt fields and begin a fresh replacement. This preserves the route out for an attempt whose identity is never re-sent without allowing two application instances, automatic repair and the setup fallback to terminalise one another's live work.

**The one carve-out is *deferred*, where B6 governs**: a request under a different identity that finds the phase record at *deferred* is answered with that phase and acts on nothing, because [Server protocol and transfers](Server%20protocol%20and%20transfers.md#5-the-bootstrap-and-repair-request-and-package-inspection) B6 and G22 are exact that a deferred result *"does not license a second attempt under a fresh identity"*. **The phase record alone still cannot tell an unfinished attempt from a live one** — G3 writes every phase before the act it names, so a record left at *staging* by a dead attempt reads identically to one held by a live attempt. The claim, not a time or a reading of the record, makes that distinction: failure to acquire means live ownership; acquisition permits the recorded attempt's recovery under G18. **Where the claim is G1b's, *live* is read one degree weaker and G1b says so** — an unacquirable claim naming another installation may be live or abandoned, and [Section 16](#16-unresolved) item 23 carries what that costs.

**G19. Staged material is validated by content and never by presence or version label.** A retry that finds staged material at the location the phase record names re-verifies G27's recorded release sequence, manifest digest, artifact identity, byte length and artifact digest through B10's at-rest read-back comparison before reusing or invoking a byte. A version answer from the staged program is a health check after provenance and cannot replace provenance.

**G20. Abandoned staging is swept, and the sweep is bounded to the locations the phase record names.** It is the same shape as [Server protocol and transfers](Server%20protocol%20and%20transfers.md#78-cleanup-and-the-five-ways-a-transfer-ends) S28 and it reaches nothing else on the machine.

### 2.6 What blocks the commit, and removal as an internal step

**G21. The whole commit is blocked while accepted work still depends on the current package or its immediately previous adapter**, which is [Server protocol and transfers](Server%20protocol%20and%20transfers.md#2-request-framing-and-versioning) P3 applied at the commit. Before *committing*, the transaction reads whether any operation accepted under either retained protocol version is live, held, has an uncollected result, or has a result not yet acknowledged. The retained previous adapter remains runnable for inspection, stop, release and collection throughout; an indefinite hold delays activation and never removes the control route.

**G22. A blocked commit is *deferred* and is not a failure.** The phase record records the reason, the staged material is kept, and the request answers with the deferred result [Server protocol and transfers](Server%20protocol%20and%20transfers.md#5-the-bootstrap-and-repair-request-and-package-inspection) B6 already carries — *"it is not a failure, it does not expire a waiter, and it does not license a second attempt under a fresh identity."*

**G23. A hold blocks a commit for as long as it stands, and an ended result blocks retirement until it is collected and acknowledged.** [8.6](#86-nothing-expires-a-hold) is why the first has no timer; P3 is why neither condition permits removing the last compatible adapter. Once no accepted operation depends on the immediately previous version, G15 may retire it after the candidate's health exchange succeeds.

**G24. Removal of the runtime is only an internal step of G15 and G20, and no user action reaches it.** The one machine-reaching server removal stops work, clears pending jobs and removes the Telegram role; the runtime remains. That is the shape's rule and this document exposes nothing else.

## 3. The supervisor

**Constraint:** [The shape](The%20shape.md#each-rented-server) — *"One long-lived service controls the machine-local queue, durable job state, event journal, worker identities, and local command endpoint"*, and *"The server supervisor is the only writer of the machine-local queue and job journal."*

### 3.1 One process, one writer, one run identifier

**S1. One supervisor per installation, and it is the only writer of every durable store in [State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2 except the staging areas and the captured streams, both of which are written under its control.** That serialization is what makes every rule below implementable as a rule rather than as a hope, and it is what answers Row 53's race at the point the shape puts it. **The captured streams are material rather than state and [11.1](#111-the-two-streams-are-captured-by-the-worker-into-sinks-the-supervisor-made) states why the writer is the worker;** [Section 16](#16-unresolved) item 5 records that §1.3 rule 1 names the staging areas and not them.

**S2. The supervisor writes a fresh run identifier at every start**, whatever caused the start ([State, identity and recovery](State,%20identity%20and%20recovery.md#52-what-a-recorded-execution-group-must-be-paired-with) §5.2). A recorded execution group carrying a previous run identifier is treated as gone unless it validates.

**S3. A second supervisor never runs.** Where a start's bind of the machine-local endpoint is refused because another process holds it (Z2), that start ends without touching a store and without signalling anything. **The bind is not the interlock, corrected 2026-08-20 — [Z12](#41-existence-and-lifecycle) is, and it always was.** A bind refusal carries no information about whether anything holds the endpoint: `unix(7)`, read 2026-08-20 at `https://man7.org/linux/man-pages/man7/unix.7.html`, gives **EADDRINUSE** as *"The specified local address is already in use **or the filesystem socket object already exists**"*, so a stale object left by a crashed run refuses a bind exactly as a live holder does. **All of the separating is done by Z12's connect probe**, and this sentence used to name the wrong act as the safety. What is read is still the operation's own result rather than a file's presence or a process listing; nothing here uses a lock file, a process search or a name.

### 3.2 What restarts the supervisor, and it differs by machine kind

**S4. On a systemd machine the user unit carries an unconditional restart directive, and that is correct for the supervisor and forbidden for a worker.** Batch A's constraint is exact about the distinction: the restart policy that recovered work also restarted it two seconds after a deliberate stop. **Only the supervisor is boot-restarted; every worker outcome is decided by the supervisor from durable desired state** ([State, identity and recovery](State,%20identity%20and%20recovery.md#3-desired-state-and-observed-state) D2). **That restart is the commonest reason [1.2](#12-on-a-systemd-machine) K18 exists**: without it, every restart this directive performs takes the running render down with the supervisor it is restarting.

**S5. On a container the boot hook starts a keeper, and the keeper's only job is to start the supervisor and start it again after an unexpected exit.** It is needed because the container's first process is a shell waiting on a marker file rather than an init system, so nothing else on that machine restarts anything. **The keeper holds no policy of its own**: it never starts, stops or restarts a worker, never reads a store, and never decides an outcome. It is the container's implementation of *boot-restarted* and nothing more. **The keeper is started by the boot hook or by [G25](#g25)'s start step, whichever comes first, and starting an already-running keeper is not a second restarter** — it is the same one reached by the other door. *(**Added 2026-09-12 by the build runner**, the matching half of G25's addition of the same date; see there for what it was found by and why the runner wrote it.)* **What makes that sentence true is a lock the keeper holds, and without it the sentence is false.** The keeper is a loop, and starting it a second time gives a second loop — so a failed first placement tried again, or a container restarted after its hook was installed, would otherwise leave two keepers each starting a supervisor at nearly the same moment, which is exactly the two starts [Z2b](#41-existence-and-lifecycle)'s race needs and exactly the second restarter Z2b says nothing in software bounds. **So: the keeper takes an exclusive open-file-description lock on one fixed file in the package area before it starts anything, and holds it for as long as it runs. A keeper that cannot take the lock ends at once and starts nothing.** The file is the keeper's own and **not** G1a's package-transaction lock file, which a keeper holding for its whole life would make every later transaction wait on. **This is not a reading of whether a file is there, which [State, identity and recovery](State,%20identity%20and%20recovery.md#13-rules-that-bind-every-store) §1.3 rule 5 forbids**: the file's presence, name and size decide nothing, and what decides is whether a live process holds the lock on it — the same footing as [Z12](#41-existence-and-lifecycle)'s connect probe, which asks whoever is live rather than looking at an object. **Documented** for the lock itself at [G1a](#21-the-durable-package-phase-record)'s source: `flock(2)` admits one exclusive holder and releases the lock when every descriptor on the open file description has closed, so a keeper that dies — including every keeper a container restart ends — leaves the lock free for the next without a timer. **The lock is not a store and reading it is not policy**: the keeper still decides nothing about any worker or outcome. **The command a shell loop takes the lock with is Build's to choose and to source at the site** under Rule 2, as the hook's own use of `su` already is. With the lock in place [G25](#g25)'s sentence stands as written: the commit starts the keeper on every container commit, and where one is already running the second ends at once and does no harm. *(**Added 2026-09-19 from the Gemini catch-up's code round on step 8b, Area 2, must-do U-1.** No auditor of this document has seen this text.)*

**S5a. That the keeper can outlive the connection that started it is observed on the container kind, at the promise level. Added 2026-08-22.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md), machine A: a process started `setsid nohup … </dev/null >/dev/null 2>&1 &` took **PID 855 as its own session leader** (`sid == pid`); the connection was closed; on a **new** connection it was still running, **reparented to PID 1**, still appending to its log, and `kill -TERM 855` was accepted — the process logged its own clean ending and exited within two seconds. **The negative would have been the program dying with the session on the container kind, which is where it was most likely**, and it did not. **What this does *not* establish is survival of a restart**: on the same batch the plain detached process was gone after a reboot while the service-manager registration came back, which is [K4](#12-on-a-systemd-machine) and [K18](#12-on-a-systemd-machine) behaving exactly as written and is why the boot hook is the registration rather than the detachment.

**S6. Neither restarter distinguishes a crash from a deliberate end, and that is what the package transaction uses.** The supervisor has exactly one deliberate end and it is [2.3](#23-the-commit-is-one-deciding-write) G25's: the transaction ends the running supervisor after the pointer has moved, and the restarter starts the one the pointer now names. **No user action reaches it** ([G24](#26-what-blocks-the-commit-and-removal-as-an-internal-step)), and nothing else on the machine ends it deliberately. What a start does with the work it finds is [3.3](#33-reconciliation-is-the-supervisors-and-it-runs-at-more-moments-than-a-start)'s and not the restarter's.

**S7. Crash return is answered on both machine kinds.** The supervisor returned after a real kernel panic on the virtual machine and after the provider-equivalent forcible restart on the container. **What remains is a genuine power cut**, which is [Section 16](#16-unresolved) item 13 and which no rental can pose.

### 3.3 Reconciliation is the supervisor's, and it runs at more moments than a start

**S8. Reconciliation is [State, identity and recovery](State,%20identity%20and%20recovery.md#6-reconciliation-on-the-machine) §6 entire, taken and not restated**, including Step 0, its four dispositions, its two prohibitions, and its requirement that a disposition is journalled every time it is written, **and its split of *should be stopped* by the recorded group: a stop whose group still validates after a restart is *resumed*, not closed, and its ending arrives by W12's report** (added 2026-10-01, from step 10c's pass before Vast on Sesterce).

**S9. It runs at every supervisor start, and it runs once more: at the moment the machine-level *setup in progress* state is cleared.** [Section 9](#9-the-setup-in-progress-state) is why that second moment is not optional.

**S10. Nothing else triggers it.** No timer, no free-space reading, no connection, and no reading of a job's output folder — the last is §6's own prohibition.

**S11. A disposition that ends a job carries the completeness statement, taken after the disposition is decided and written in the same act. Added 2026-08-21, closing `Queue & History` §18 item 17 and [Section 16](#16-unresolved) item 17's neighbouring half.** Two of §6's five dispositions end a job with no worker alive to have taken the ending step — ***left stopped*** written from a durable *should be stopped*, and ***given up*** at the second interruption. For those two, and only those two, the supervisor runs the reckoning of [Job files and outputs](Job%20files%20and%20outputs.md#10-completeness-already-there-the-last-frame-the-exit-status-and-the-stop) C1 and C7 — one walk of that job's output folder against the expected-output inventory for the map in force — and writes its statement (C27's four sets) with the recorded outcome, exactly as a worker's ending step carries one (`Rendering` K13). **A render's recorded outcome carries a second thing in that same act, on these two dispositions and on the ordinary ending alike: [V12](#12-health-readings)'s free-space reading against the job's own output folder.**

**S12. §1.3 rule 5 stands and is not weakened by S11, because nothing about state is decided from the walk.** The disposition is chosen from records alone — the desired state, the recorded execution group, the attempt count — precisely as §6's table has it, **before the walk is taken**. The walk supplies a measurement that rides with an outcome already decided; it can move no branch of that table, and reversing the order would be the thing rule 5 forbids. Downstream every reader reads the written statement and never the folder, which is the same standing rule 5 already gives the re-run's already-there test: *"a rule about what to render, never a reading of state."* **The measurement's own limits ride with it and are not softened here** — `Job files and outputs` C15, a file short but not empty still counts, and C29, a write that ran out of room counts as present.

**S13. Where the walk cannot be taken, the outcome is written without a statement and says so.** The job output folder gone, the mount absent, the walk raising — none of it holds up the disposition, which is decided and written whatever the walk does. **An outcome carrying no statement is not an outcome carrying an empty one**, and `Queue & History` H8 already turns on that difference: no drop is written against a missing reading. **The absence is recorded explicitly rather than left to be inferred from four empty sets.**

**S14. A durable write refused for want of room does not end the supervisor's run, and what could not be written is held and re-attempted until it lands — the route `Queue & History` P1b names beside the restart. Added 2026-08-22, scenario replays Pile 1 item R10; **observed end to end on 2026-08-25** ([Section 16](#16-unresolved) item 25).** Every disk-full clause in this stage was written about a supervisor that cannot start (`Queue & History` Q8, [Section 16](#16-unresolved) item 12); a supervisor already running when the state mount fills is past the directory entry that bars a start, and this clause is what it does. **On the container kind S14's hold-pending-and-re-attempt shape is now observed rather than required**: the arrangement ran through a fill to genuine zero without exiting, refused loudly, moved nothing, and accepted the pending write the instant space returned. **The bullets about a run that ends, about [V12](#12-health-readings)'s reading and about what is refused over a pending write are unexercised, and the systemd kind is unexercised entirely.** **Narrowed 2026-08-29**: this said *every bullet below is now observed rather than required*, which is wider than the run reaches and wider than the answer of record claims — [The Pile 3 batch](The%20Pile%203%20batch%20%E2%80%94%20a%20full%20mount%20under%20a%20running%20supervisor,%20an%20interrupted%20heavy%20frame,%20and%20an%20hour%20of%20silence.md) §2.5 says the hold-pending-and-re-attempt shape works exactly as written and no more, no render ran so no V12 reading was taken, nothing exercised the no-act-over-a-pending-write rule, and the run did not end, which is the finding rather than an observation of the ending case.

- **The run does not end for a refused write.** The refusal is the loud errno-28 one, observed leaving every read truthful and nothing moved behind it; the supervisor records the first reason once in its run's memory and goes on serving — the same conduct M5 already requires of the worker for a refused sink write. Whether anything **outside** Smoozy's own code ends a live supervisor when its mount fills has never been observed and is asserted nowhere here; [Section 16](#16-unresolved) item 25 carries it, and a run that does end — whatever ends it — is the case every bullet below is not: the machine is then the supervisor-unavailable condition and Q8's existing route is the repair.
- **What is held pending, exactly: the durable writes owed about work that has already happened.** A recorded outcome the wait returned ([State, identity and recovery](State,%20identity%20and%20recovery.md#53-the-deliberate-stop) §5.3 step 6) with everything that rides it — the completeness statement (S11), [V12](#12-health-readings)'s free-space reading, the collection outcomes (M13), the note's ending and the journal events for all of it — is held in the run's memory, in the order the writes were owed, and re-attempted **at every request the supervisor serves and at every worker report or reaped ending it takes** — occasions of its own that something else already caused, never a timer, a watcher, a schedule or a free-space reading, so S10 stands unqualified. Each re-attempt is a real write and its own test ([State, identity and recovery](State,%20identity%20and%20recovery.md#13-rules-that-bind-every-store) §1.3 rule 4); when it lands, the writes land in their owed order, the journal events take their sequence numbers at the landing — §4 E1's rule untouched, a reader learning late, which `Queue & History` N5 already states — and everything that rides the ending's write, its P1b's preview catch-up among it, rides the landing. On a machine where space returns with no request arriving and no worker ending, the pending writes land at the next request or the next supervisor start — a bounded delay, never a loss, and the user's own next connection is requests.
- **V12's reading is the first attempt's and is not re-taken at the landing.** A reading re-taken after space returned would read the freed mount and silence the very diagnosis route (b) exists for — the fault R11's repair closed, arriving again by this window — so the reading taken in the act's first attempt rides the pending outcome unchanged.
- **No act is taken over a pending write, and no new refusal kind exists.** A command whose conduct requires a durable record first is refused loudly, naming want of room — Q8's own conduct, from a supervisor that answers rather than from one that is down; the admission point starts nothing, because `Queue & History` Q4's trigger — the previous outcome **written** — has not occurred and a fresh operation record could not be written anyway; and no hold is placed, U6's rule already covering a hold that cannot be journalled.
- **Readings stay truthful and carry what the supervisor knows.** Reads answer as ever; the queue reading's answer for a job whose group has ended carries the pending recorded outcome as that job's state rather than *rendering* — the ending is classified from the operation record, the group's validation and the reaped status (M20), all of which the supervisor holds, only the durable write being owed — so the entry the user watches moves off *rendering* while the durable account catches up at the landing. The note keeps `Queue & History` N5's conduct meanwhile: the null ending standing is the truthful durable state, and nothing durable is guessed.
- **A run that ends before the landing loses the pending writes and nothing silent follows.** The operation record still carries no outcome, the group is gone, and the next start's reconciliation takes its ordinary branch — *re-run once* bounding the cost at one repeated attempt, the same price [State, identity and recovery](State,%20identity%20and%20recovery.md#6-reconciliation-on-the-machine) §6 already puts on any record that did not reach the disk.

**S14a. The rest of what is held pending rides the reading beside the state, and this answers a question S14 left silent. Added 2026-09-02, out of the disk-fill scenario replay's finding N-g.** S14's own list names five things held pending — the completeness statement (S11), [V12](#12-health-readings)'s free-space reading, the collection outcomes (M13), the note's ending and the journal events for all of it — and its readings bullet carried forward exactly one of them, the job's state. **The others are carried too**, on the same ground and by the same route: the supervisor holds every one of them in its run's memory, and withholding them would be withholding what the supervisor knows from a reader whose whole purpose is to ask it what it knows.

- **What it fixes.** Between the fill and the landing the user otherwise has a failed job and a correct diagnosis with nothing behind either — `Rendering` K18's *which frames were rendered* states nothing, and `Desktop app and delivery` M10's four collection outcomes have nothing to draw over a stream that is genuinely truncated.
- **How it is carried, and the boundary that keeps it honest.** Each rides the reading **as of the moment it was taken**, which is [V5](#12-health-readings)'s standing rule and no new one, and each is marked in the reading as **owed to the durable store rather than written to it**. **A reading is never evidence that a record landed.** Anything whose conduct turns on the write having landed reads the durable record and not the reading; [Section 16](#16-unresolved) item 26 already records the journal running ahead of the store, and this is the same window seen from the reading's side rather than a second one.
- **[V12](#12-health-readings)'s reading is unchanged by this.** It is still the first attempt's and is still not re-taken at the landing. Carrying it forward is what lets the disk-full diagnosis reach the user inside the window `Server protocol and transfers` F6a's route (b) exists for, instead of only after the landing.
- **The alternative was considered and refused.** Withholding all five until the landing would be defensible and is the honest silence; it was refused because the whole cost of the fill falls in exactly that window, and a reading that is truthful about its own moment is what this section already promises everywhere else.
- **One sentence this does not write, and it is another document's.** A capture record whose collection outcome is still pending must never present as *collected*. That is `Desktop app and delivery` §16.3's to write — this document supplies the outcome and does not present it — and it is routed rather than written here.

## 4. The machine-local endpoint

**Constraint:** [Security and licence](Security%20and%20licence.md#8-the-supervisors-machine-local-endpoint) §8 — *"`Rented-server runtime` owns its existence and lifecycle; what follows is the access boundary it must implement."* Taken as given from that document: the endpoint is a filesystem object in the machine's own namespace, it **binds no address**, and it is therefore outside the *no inbound listener* question entirely.

### 4.1 Existence and lifecycle

**Z1. The endpoint is created by the supervisor at every start and is never a store.** [State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2 lists it as volatile for exactly that reason. Nothing about the machine's state is read from it, and nothing survives across a supervisor run in it.

**Z2. Its path is fixed for the installation, does not vary with the package version, and is recorded in the package area at placement; the supervisor binds first and removes second.** **The stability across package versions is what puts both supervisors on one endpoint, which is what S3's interlock needs to act on at all — corrected 2026-08-22: this clause said the stability is what makes S3's *bind* an interlock, and S3 stopped saying the bind is the interlock on 2026-08-20** (Z12's connect probe is): two supervisors of two package versions binding two different objects would both succeed, and the machine would have two writers of the machine-local queue, the operation records, the event journal and the hold records at exactly the moment a runtime upgrade is in flight — which is the condition S1 says makes every rule below a rule rather than a hope. The supervisor attempts the bind at the recorded path; **where the bind is refused because another process holds the endpoint, S3 applies and this start ends**; where it is refused and nothing holds the endpoint, the supervisor removes the object at its own recorded path and binds again. **The interlock is the connect probe's own result and never a reading of whether an object was there**, which is what keeps this inside §1.3 rule 5 — **the bind's result cannot serve, corrected 2026-08-20**, because `unix(7)` gives the same EADDRINUSE for a live holder and for a stale object, and Z12 already said so.

**Z2b. The remove-and-rebind is racy between two starts, and nothing else in this document names it.** Each step is an ordinary operation: `unlink` of a **live** holder's path succeeds and leaves the holder listening; a second socket then binds that same path while the first is still listening; new callers reach the second while the first is alive and unreachable. **Run on the Creator's Mac — one MacBook Pro with an M1 Pro chip, macOS 26.6.2 build 25G83, Darwin 25.6.0, Python 3.14.3 — on 2026-08-23, as uid 501 with no elevation, and this is the record. Re-performed on that date because the run this clause used to cite as 2026-08-20 has no record anywhere under `Preparation/`; the record here is new rather than recovered, and the earlier date is withdrawn.** A caller reached the holder before the removal (`b'before-unlink'`). `unlink` of the live holder's path returned no error and the holder's own `getsockname()` still read `'/tmp/z2b.sock'` afterwards, while a caller on that path now failed with **`errno 2 No such file or directory`**. A second socket then bound the same path while the first was still listening, its `getsockname()` reading the same `'/tmp/z2b.sock'`. Three fresh callers were then accepted by the **second** socket (`b'after-rebind-0'`, `-1`, `-2`) and by neither the first, which was still listening on its own descriptor at the end with one accepted connection to its name. **What a negative would have looked like:** the `unlink` refused, or the second bind refused with the address already in use, or any one of the three fresh callers reaching the first socket. **Not covered:** this is macOS's `AF_UNIX`, and the documented ground for the arrangement on the machine kind Smoozy rents is `unix(7)`'s own sentence below rather than this run. `unix(7)` states the standing arrangement the race exploits — *"Binding to a socket with a filename creates a socket in the filesystem that must be deleted by the caller when it is no longer needed"* — the object is an ordinary filesystem entry, separate from the open socket. **So two starts running Z12 at once both bind, both are refused, both probe, both are refused, both conclude stale, the first removes and binds and is live, and the second then removes the first's live object and binds its own** — two supervisors, the condition S1 says makes every rule in this document a rule rather than a hope. Z12 makes the stale case the **ordinary** case after every crash, so this sits on the ordinary path rather than in a corner. **What bounds it is the restarters rather than anything here** — one unit on a systemd machine, one keeper on a container, and G25 ends before it starts — and this document establishes no bound. [Section 16](#16-unresolved) item 19. **Two standard arrangements would remove it and both carry a cost this document does not pay today**: an advisory lock, which releases on the holder's death with nothing left to clean up and which §1.3 rule 5 does not plainly forbid since it reads the kernel's lock table rather than a file's presence, name or size; and the abstract namespace, which has no object to go stale (`unix(7)`: *"Abstract sockets automatically disappear when all open references to the socket are closed"*) but is Linux-only and has no owner and no permission, which would take away `Security and licence` §8 requirement 1 and leave the whole boundary on Z6's peer credentials. **Neither is chosen here.**

**Z12. What separates the two refusals is an attempt to reach the endpoint as a caller, and it is never a reading of presence.** A stale object left by a crashed run and a live endpoint held by a running supervisor refuse a bind alike, and Z4 makes the stale case the ordinary one the next start must clear — so a start that treated every refusal as a live holder would never start a supervisor after a crash, and one that treated every refusal as stale would remove a live supervisor's endpoint and break S3. **So on a refused bind the supervisor connects to the endpoint at that path as an ordinary caller: a connection refused means nothing holds it and Z2's second branch applies; a connection accepted means S3 applies and this start ends without touching a store.** That is this document's decision; **the exact mechanism by which a connection is refused is Build's and is tentative here**, and nothing above rests on which errno it arrives as.

**Z3. Its containing directory is created by the placement, owned by the login the supervisor runs as, and permits that login alone** ([Security and licence](Security%20and%20licence.md#8-the-supervisors-machine-local-endpoint) §8 requirement 1). The endpoint object carries the same ownership and the same permission.

**Z4. It ends when the supervisor's run ends, and a run that ended without removing it leaves an object Z2's second attempt removes.** No sweep and no schedule is involved, and no reading of presence: what Z2 acts on is a refused bind, not an object it found.

**Z5. The endpoint is not a credential and its path is not a secret** ([Security and licence](Security%20and%20licence.md#8-the-supervisors-machine-local-endpoint) §8), so nothing here randomises it, hides it, or treats knowledge of it as authority.

### 4.2 The access boundary implemented

**Z6. The supervisor establishes the caller's local identity from the accepted connection itself, by peer credentials read from the kernel, and refuses any caller whose identity is not the login it runs as.** Fact 84 answers the mechanism on both machine kinds and both halves: a server was told `pid=1628 uid=1000 gid=1000` for a caller running as an ordinary login, unchanged under a container's reduced capability set and identically on a virtual machine, with the endpoint deliberately left world-writable so what was observed was credentials rather than file permissions.

**Z7. The endpoint cannot be lied to, and that is why the check is the second layer rather than a courtesy.** An unprivileged caller attaching a claim of the superuser's identity was **refused outright by the kernel** with `errno 1 Operation not permitted`, as was claiming another process's identifier, and a datagram attaching nothing still arrived carrying the caller's true identity.

**Z8. No request field names its caller, and any such field is ignored rather than checked** ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#3-the-authentication-boundary) A2, [Security and licence](Security%20and%20licence.md#8-the-supervisors-machine-local-endpoint) §8 requirement 2). Ignoring and checking are the same thing for security and only one of them is safe to write down.

**Z9. The refusal happens before the request is framed.** A refused caller receives nothing that describes the protocol, and the refusal is journalled as an event rather than answered as a request result.

**Z10. The recorded identifier the kernel reports is a stale handle the instant the caller finishes**, observed: by the time the server looked up the identifier it had just been told, the caller had exited and its entry was gone. **So nothing here reads anything further about a caller by its identifier**, and the identity established at Z6 is the whole of what is used.

**Z11. This boundary separates one login from another on a machine and does not separate Smoozy from the machine's owner.** [Security and licence](Security%20and%20licence.md#8-the-supervisors-machine-local-endpoint) §8 states the limit — *"Root ignores file permissions"*, and on some rentals the login Smoozy holds is root — and nothing here is built on top of it as though it were more.

### 5.2 Per-operation workers

**W3. Every worker is started against one durable operation record, written before the worker is started** ([State, identity and recovery](State,%20identity%20and%20recovery.md#51-the-durable-operation-record) §5.1). There is no worker with no operation record and no operation record whose worker was started before it was written.

**W4. The four outcomes and the four dispositions are that document's and are not restated.** What this document adds is that **a per-kind field of the operation record is the kind's document's**, which is where the capture record of [11.3](#113-the-explicit-collection-outcome) lives for a render and where a setup run's safe-boundary marker lives for a setup.

**W5. No worker has a restart policy of its own.** A worker that exits is an observation; what happens next comes from the operation record's desired state at the next reconciliation, and from nothing else.

**W6. A worker that outlives its supervisor is the case the *resumed* branch exists for.** Observed: a detached program outlived the connection and the shell that started it, *"Its parent is **1**"* ([Batch A](Batch%20A%20—%20the%20shape%20throwaway.md), Fact 1). A worker is started so that it survives the supervisor's own exit, because a render that died with a crashed supervisor would lose work the machine was paid for.

**W12. What makes that branch work rather than merely name it is that the worker's report survives the restart, and the route is the endpoint's recorded path.** [State, identity and recovery](State,%20identity%20and%20recovery.md#6-reconciliation-on-the-machine) §6 writes *resumed* *"before the supervisor re-attaches"*, and re-attaching is this: **a worker's report is re-attempted against the endpoint at Z2's recorded path — a path that does not vary with the package version and outlives any one supervisor run, though the object at it does not (Z1) — until it is accepted or the worker's own work is over; the report carries the run identifier the worker was started under (S2); and a supervisor that has written *resumed* accepts a report from a group recorded under an earlier run identifier while refusing a stale one.** Without it the counts, the exit and the end of stream have nowhere to arrive: M6 gives the worker one channel to the supervisor, Z1 and Z4 destroy the endpoint object with the run that made it, S1 forbids the worker writing the outcome itself and §1.3 rule 5 forbids the next supervisor reading it off the disk — so a finished render would leave an operation record with no recorded outcome, blocking every package commit under G21 and re-running on a paid machine at the next reconciliation. **S1 is untouched**: the worker reports and the supervisor writes. **The same route carries a stop a restart found outstanding**: where §6 writes *resumed* for a *should be stopped* record whose group validates, the ending arrives by this report and is recorded at [State, identity and recovery](State,%20identity%20and%20recovery.md#53-the-deliberate-stop) §5.3 step 7's boundary (added 2026-10-01, from step 10c's pass before Vast on Sesterce).

### 5.3 The one role worker

**W7. The Telegram worker is the only role worker, and it is started, restarted and stopped from a durable enabled-or-disabled desired state held at machine level** ([State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2). It takes none of the four operation outcomes and has no operation record.

**A role worker that outlives the run that started it is not reattached, and it ends itself. Added 2026-10-12, out of the Telegram worker's map (H1), on the build runner's ruling of that day.** W6 makes outliving the ordinary case for every worker, and W12 is what reattaches a render; the role worker leaves nothing durable for a new run to reattach (W7 gives it no operation record), so after a supervisor restart, crash or package update the old worker would go on beside the one the new run starts, reading the same journal and editing the same messages, and a *disabled* could not reach it. **So the supervisor answers the role worker's own requests — the ones only a role worker makes — only from the role worker this run started, and refuses every other caller of them; a role worker refused that way ends itself.** The old one therefore ends at its next request. **What marks the caller must single out that one worker and not merely this run**: the process the endpoint reads the caller from, matched against the group this run recorded, does; a run identifier alone does not, since two workers started under one run would both carry it. No auditor of this document has seen this paragraph.

**W8. `Server Setup` sets that desired state through the same command path as every other command, and never starts or stops the process.** That is the shape's rule and it is the mechanism **Row 91** needs: the second entry point puts the role's material on a machine prepared earlier and sets the state, and the supervisor does the rest.

**W9. A change of that desired state restarts nothing but the role worker.** The supervisor is not restarted, the machine is not restarted, and no per-operation worker is disturbed — which is Row 91's second promise, that *"a render already going on that machine is left alone"*. The mechanism is that the role worker is a child of the supervisor like any other and its start needs nothing the machine is not already running.

**W10. The supervisor restarts it for as long as it remains enabled, records and reports repeated failure rather than silently giving up, and never resurrects it after it is disabled.** That is the shape's own sentence and it is taken whole.

**The occasions it takes that look at, and the last of them is what makes the sentence true with nobody connected. Added 2026-09-12, out of the step 8b code round.** The supervisor's own start, W8's two acts on the desired state, and **each turn of the supervisor's own loop, including a turn no caller arrived for** — which the machine-local endpoint's own bounded wait for a caller already produces ([Section 4](#4-the-machine-local-endpoint)). **That fourth occasion is an occasion something else caused and not a schedule**, the same shape [S14](#33-reconciliation-is-the-supervisors-and-it-runs-at-more-moments-than-a-start) already uses for its re-attempt occasions, so [S10](#33-reconciliation-is-the-supervisors-and-it-runs-at-more-moments-than-a-start)'s *no timer* stands unqualified and no new mechanism, schedule or constant is added. *(From 2026-10-12 the pace below adds two values to the restart this occasion performs; the occasion itself still adds none, and S10's* no timer *still stands.)* **No store is read on an idle turn**: the turn takes the endings of the children the supervisor already holds a wait for ([X9a](#62-the-stop-sequence-on-this-side)), and the durable enabled-or-disabled state is read only where the role worker this run started has ended. **Without it the first three occasions all need somebody at the desk**, and the case W10 exists for is the user's laptop shut: a role worker that died two minutes after a six-hour render began would never be looked at again, and the phone stays silent while the machine is paid for.

**The pace of that restart on the turn. Added 2026-10-12, out of the Telegram worker's map (H2), on the build runner's ruling of that day.** A role worker that ends less than five minutes after its start ends *quickly*. **The first quick ending is started again at once, as every ending was; each further quick ending in a row waits on the turn twice as long as the one before, from two seconds up to five minutes, and stays at five minutes for as long as the role stays enabled.** A worker that ran five minutes or more starts the count afresh. **Only the fourth occasion is paced**: the supervisor's start, W8's two acts and §6 step 3 are caused by something other than the turn coming round, and each takes at once an ending the turn is still waiting on. The wait is held in the run's memory and read on the turn that comes round anyway — the shape `Server Setup` Y7's command-gap window already has — so nothing wakes the supervisor for it. **Why:** until this day a worker that ended the instant it began was started again on every turn, about four times a second, and W11 journalled each start; the journal's 32,768 entries filled within hours, and E6 then dropped events the desktop had not read — an overnight render's endings among them. **The role worker itself does not end on a condition it cannot fix** (`Telegram` F1, its paragraph of 2026-10-12), so on a working machine the pace is met only by a worker that crashed. No auditor of this document has seen this paragraph.

**W11. Repeated failure is reported through the event journal**, so a reader learns of it by reading forward from its own cursor rather than by comparing two readings ([State, identity and recovery](State,%20identity%20and%20recovery.md#4-the-event-journal-and-acknowledgement) §4).

**The first ending under a run, and then only a changed count. Added 2026-10-12, out of the Telegram worker's map (H2), on the build runner's ruling of that day.** W11 journals the first ending under a run, and after it an entry only where the count of endings under the run has moved — one entry per ending, written below the start it led to and carrying the count, never one per turn and never one per pass. With W10's pace, a worker that ends at once moves the count at most once every five minutes once its waits reach their cap: under 300 entries a day, against the four a second this journalled until this day. No auditor of this document has seen this paragraph.

## 6. The recorded execution group, and the stop

**Constraint:** [The shape](The%20shape.md#each-rented-server) — *"Its recorded runtime identity names the complete supervised execution group: the worker and every external process it starts for that operation. A worker is never discovered or stopped by executable name, command-line pattern, or process search."* And [State, identity and recovery](State,%20identity%20and%20recovery.md#52-what-a-recorded-execution-group-must-be-paired-with) §5.2, whose pairing requirement this section supplies the mechanism for.

### 6.1 What is recorded, and what it is paired with

**X1. The recorded execution group is the group leader's identity paired with its kernel-set start time, recorded together at the moment the worker is started, and held in the operation record.** **Only the leader is recorded**, and X9 reads a leader that is gone as a group that has ended. **That inference is sound only for a kind whose termination contract makes the worker outlive every member of its group**, which X12 states for the render, **which `Server Setup` [Section 11](Server%20Setup.md#11-declarations)'s termination-contract paragraph states for the setup kind** — *"the setup worker remains until every external process it started has exited, or is ended only after them"* — and which nothing states for file-inspection, preview, media or transfer-support — where a leader can exit first, a live member reads as a group that ended, and X6 forbids relaxing the failed validation, so reconciliation writes *re-run once* over work that is still running. *(Setup struck from that list 2026-08-29 at the stage-close gate repair: `Server Setup` §11 has stated the answer plainly, naming this clause while doing it, and this sentence had not caught up — a builder reading it was told the leader-gone reading is unsound for the one kind whose recovery refusal (`Server Setup` S5) and admission exception (A11a) both turn on it.)* **So it is the fourth thing every per-kind contract must name** (X11), and [Section 16](#16-unresolved) item 6 records that the kinds with no contract have no answer here either; [Section 16](#16-unresolved) item 29 records that item 6's own close may have made the three remaining names stale too. Fact 91 is answered: the start time is *"written by the kernel at fork, in clock ticks since boot"*, and **it cannot be chosen by the process it describes** — a write to it was refused with `errno 22 Invalid argument` on both machine kinds.

**X2. The pair is what separates a live group from a re-handed-out identifier, and it was forced rather than argued.** On a virtual machine a leader recorded as **(identifier 1493, start time 19186)** was killed, the identifier space was made to hand out that identifier again, and validating the recorded pair against the new, unrelated process gave **`exists=True matches=False`**. *"A later, unrelated process validating against the recorded pair would have been the negative result"*, and it did not happen.

**X3. The run identifier settles what the pair cannot.** Start time is in ticks since boot and is meaningful only within one boot, so a reboot, a container restart and a recycle are settled by the run identifier the supervisor writes at every start (S2) and never by the pair. That division is [State, identity and recovery](State,%20identity%20and%20recovery.md#52-what-a-recorded-execution-group-must-be-paired-with) §5.2's and is unchanged.

**X4. A container cannot pose the reuse demonstration and the mechanism reads identically there.** Three separate refusals — an identifier space of 4,194,304 making natural wrap untestable, the next-identifier control refused with `errno 30 Read-only file system`, and a namespace of one's own refused with `Operation not permitted`. **What is a kernel property is not re-derived per machine kind**, and [Section 16](#16-unresolved) item 4 records what that leaves open.

**X5. The group is the worker and every external process it starts for that operation, and the leader is the worker.** So a render's group is the render worker and the Blender it starts; a setup run's group is the setup worker and whatever it invokes. **The leader is what the pair identifies; which member receives a termination is [6.3](#63-per-kind-termination-and-signal-targets)'s and is not always the leader.**

**X6. Nothing anywhere in this document finds a worker by executable name, by command-line pattern, or by searching the machine's processes.** A pattern *"matched **two** process ids"*, the stop was handed a malformed argument, and the work carried on. **A validation that fails means the group is gone — never that the check should be relaxed.**

### 6.2 The stop sequence on this side

**X7. Stopping work the machine has taken is its own command with its own operation identity, naming the target's** ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#47-cancellation-and-there-are-two-of-them) C21). That document fixes the request; the sequence, the validation and the signal target are this document's, and C21 says so.

**X8. The sequence is [State, identity and recovery](State,%20identity%20and%20recovery.md#53-the-deliberate-stop) §5.3's seven steps, and what this document adds to each is only this:**

1. the stop's own command record is written by the supervisor before anything (`Server protocol and transfers` C4);
2. the target's desired state is written to *should be stopped*, durably, **before** the group is looked at, so a supervisor that dies between steps 2 and 4 leaves a stop reconciliation will honour;
3. **the pair of X1 is validated, and a pair that does not validate ends the sequence**: the group is gone, the recorded outcome is written from what the operation record and the reaped status say, and no signal is sent to anything;
4. the kind's own termination is issued to the member that kind's contract names ([6.3](#63-per-kind-termination-and-signal-targets));
5. nothing infers completion from delivery — the stop took effect *"on the program's next cycle, about 2.3 seconds against a three-second cycle"*, and *"A check made two seconds after sending the signal reported the program still running and would have been wrong"*;
6. the outcome **left stopped** is recorded when the group has ended, and the event is journalled;
7. where the worker ended on its own **before step 4's termination was issued** — the pair failing validation at step 3, or the ending already reaped before anything was issued — the recorded outcome is that ending and not *left stopped* (D3); **an ending step 6 takes past the issuance is *left stopped***. The boundary is [State, identity and recovery](State,%20identity%20and%20recovery.md#53-the-deliberate-stop) §5.3 step 7's one boundary — the issuance, the only one the supervisor holds a record of its own about — cited rather than re-decided *(fixed 2026-08-22, scenario replays Pile 1 item R6: this said "between steps 2 and 6", a window holding the ordinary successful stop, so a render that honoured the interrupt would have been recorded as its own ending and shown failed against the spec's marked as stopped)*.

**X9. The group is confirmed ended by the same pair, and by nothing else.** A group whose leader's pair no longer validates has ended. Nothing reads a process listing, a name, or the absence of an output file to decide it.

**X9a. The pair is the *gone* test and the wait is the *ended* test, and the supervisor performs the wait. Added 2026-08-22 at the Architecture seam close, routed by the runner from [Server Setup](Server%20Setup.md#13-unresolved) §13 item 16.** **The supervisor waits on every worker it starts and takes the ending from the wait status**, which [State, identity and recovery](State,%20identity%20and%20recovery.md#53-the-deliberate-stop) §5.3 step 6 already requires of it and which [Section 16](#16-unresolved) item 4 had carried as a Build-side fix. **So the defunct-entry hole is closed here rather than left to Build**: without the wait a worker that ended still validates at X9, a termination is absorbed by a defunct entry, and *when the group has ended* never arrives — which on a setup machine leaves `Server Setup` S5 refusing for ever with no act inside the app that clears it. **X9 itself is unchanged and keeps its job**, which is the safe-direction check that a group is gone; what the wait adds is the positive that it has ended. §3.2's one-restarter rule is untouched — a wait is not a restart.

**X10. A stop issued by something on the machine with nobody connected takes exactly this sequence.** Fact 68's success was *"Redone against the identity the service manager itself holds"*; here that identity is X1's pair, and the caller is the supervisor rather than a script.

### 6.3 Per-kind termination and signal targets

**X11. Each contract names four things and is owned by the document that defines the kind (W1):** which member of the recorded execution group receives the termination; whether the kind may be terminated at any moment or only at a recorded safe boundary; what cleanup is owed afterwards; and **whether the worker outlives every member of its group**, which is what X1's recording of the leader alone and X9's reading of leader-gone as group-gone both rest on. **No contract is universal and none is inherited from another kind.**

**X12. For a render, the target is the recorded render process and not the worker, and not a shell around it.** The shape fixes the signal and `Job files and outputs` C36 fixes the reason: *"A render had to be started detached to survive the connection at all, so the thing that must be reached is by construction not the thing the connection started."* **The render worker remains until its external processes have exited, or is terminated only after them** — which is the shape's rule and is what makes [11.1](#111-the-two-streams-are-captured-by-the-worker-into-sinks-the-supervisor-made)'s capture survive the stop.

**X13. Nothing here matches an ending on its number.** The number a polite terminate ends with is recorded as `-15` by one topic and `143` by three others, and anything matching an ending on its number accepts both.

**X14. For transfer-support, termination is staging and cleanup rather than a signal** ([Server protocol and transfers](Server%20protocol%20and%20transfers.md#47-cancellation-and-there-are-two-of-them) C22), so X8 step 4 issues no signal for that kind and the sequence completes on the cleanup's own confirmation.

**X15. For a setup run, termination is at, or recovery from, a recorded safe boundary**, and the boundary marker is the per-kind field of that operation record (W4). Its meaning is `Server Setup`'s.

**X16. A stop reaching another login's process is refused by the machine, and that is the observed reason L13's one-login requirement is a requirement.** From a second ordinary login both a polite and a forceful stop were refused with `Operation not permitted` (Fact 60). **Under one login the case does not arise**, and this document does not build a route around it.

## 7. The common arbitration mechanism

**Constraint:** the scope line — *"Each owning feature document declares an operation's resource class, priority, cancellability, and atomic-or-partial boundary; Rented-server runtime owns the common arbitration mechanism."* (**Corrected 2026-09-02**: this quotation carried backticks around the document's name that [The shape](The%20shape.md#6-rented-server-runtime)'s own scope line does not carry.) And `Job files and outputs` [8.4](Job%20files%20and%20outputs.md#84-the-derivatives-one-set-made-once-on-the-machine) B24, which declares a derivative worker **low priority, cancellable, never blocking a render**, against this mechanism.

### 7.1 What each owning document declares

**A1. 1. **Resource class** — which of the machine's contended resources the operation takes, and whether it takes each **exclusively** or **shared**. The contended resources are the cards, the processors, and the machine's memory. 2. **Priority**, as a rank against the other kinds.
3. **Cancellable or not**, and where cancellable, whether at any moment or only at a recorded safe boundary (X11).
4. **Atomic or partial**, against [State, identity and recovery](State,%20identity%20and%20recovery.md#9-the-atomic-or-partial-boundary) §9.

**A7. Where the holder is not cancellable, the higher-priority operation waits at the admission point.** It is not started and then blocked, so nothing that has been started is ever holding a resource it cannot use.

**A8. **A9. The one exception to A8 is exclusion, and it is not starvation.** While a render holds the cards exclusively, another render is not admitted however long it waits. That is the allotment promise working, not a scheduling fault, and the ordering of what waits is `Queue & History`'s.

**A10. A held job is not at the admission point at all.** [8.2](#82-where-a-hold-sits-and-why-it-takes-no-place-in-the-line) is why: a hold is not a low-priority admission, it is an absence from the line.

**A11. While the machine-level *setup in progress* state is set, nothing is admitted** ([Section 9](#9-the-setup-in-progress-state)). That is an exclusion at machine level rather than a priority.

**A11a. One thing is admitted under it, and exactly one. ### 7.3 What is not measured, and it is stated here rather than in a footnote

**A12. **A13. So the mechanism above is built to be tightened rather than to be right.** A2's declaration lets a derivative run beside a render today and lets it be excluded tomorrow by one change to that declaration, with nothing in this section moving. **What would be unfixable is a design in which the render and the derivative are not both arbitrated at one point**, and that is what A4 exists for.

## 8. Machine-held work awaiting a person, and the one answer-release path

**Constraint:** the scope line — *"machine-held jobs and commands awaiting a person and their common answer-release path"* — and the seven rows in four documents that cite it: `Rendering`'s Rows 4 and 23, `Queue & History`'s Rows 52 and 53, `Job files and outputs`' Row 123, and `Telegram`'s Rows 275 and 276. **`Job files and outputs` H3 states outright that no second waiting mechanism is to be invented.** None is.

### 8.1 One hold record, two origins

**U1. There is one hold record and one release path, and every place in this project where the machine waits for a person uses them.** The two origins are different moments and the same machinery, which `Queue & History`'s Row 52 states in as many words: *"Two kinds, one arrangement."*

- **Placed at submission.** The first-frame check's second job arrives on the machine already held; the user's yes only releases it. `Rendering`'s Row 4: *"The second job is already on the machine from the first act; the answer only releases it."*
- **Placed at the start of a render.** The render worker loads the file, evaluates the three conditions `Job files and outputs` [9.1](Job%20files%20and%20outputs.md#91-the-three-conditions-and-where-each-is-established) H1 names, and where one holds it places the hold **after the file is loaded and before the render begins** (H4).

**Both origins are jobs, and no document today places a hold whose subject is a command.** The scope line's *"machine-held jobs **and commands** awaiting a person"* is answered by the record carrying the **subject kind** (U2), so a command hold can be added by the document that wants one without a second waiting mechanism and without a change here — rather than by this document building a case nobody has asked for. Until one is placed, the two origins above are the whole of what fills the record.

**U2. A hold record is a durable store of this document's, in the package area, one per hold, and it holds:**

- the **hold identity**, issued by the supervisor when the hold is placed, opaque and never reused ([State, identity and recovery](State,%20identity%20and%20recovery.md#21-the-rules-that-bind-every-identity) §2.1 binds it entire);
- the **subject** it holds **and the kind of subject it is** — a job identity, or the operation identity of a command awaiting a person, of which only the first is placed by any document today (U1);
- the **reason**, from the closed set the placing document declares; this document carries the reason and never interprets it;
- the **origin**, submission or render start;
- the **dependency**, where the hold has one: the identity of the work whose ending drops it, and the **release predicate** the placing document declared ([8.5](#85-the-dependency-that-drops-a-hold));
- the **release outcome**, written once and never rewritten: *released*, *stopped*, or *dropped*, with the answer or the ending that produced it and the moment on the machine's clock.

**U3. That is a machine store kind [State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2's inventory does not name.** It is a seam and not a licence to extend that inventory here — its one home is §1.2 and a second copy would give a fact two homes. **It is one of a run of such findings across this stage, and the tally's one home is [Open Threads](../Groundwork/Open%20Threads.md)** rather than any document's own count; it is recorded the same way here, at [Section 16](#16-unresolved) item 5. *(This clause said fifth in five; the number is withdrawn to that one home, 2026-08-19, and nothing else about the seam changes.)*

**U4. The waiting state has one home and it is this record.** `Telegram`'s Row 276 says the spec is emphatic that the approval is a feature of the product rather than of the bot, *"which makes a single home for the state a requirement rather than a preference"*. **The home is the machine that holds the work**, because that is the only place both answer routes can reach with Smoozy closed, and because the supervisor is the single writer that makes two callers unable to change one job independently. `Telegram` carries the tap and holds no waiting state of its own.

### 8.2 Where a hold sits, and why it takes no place in the line

**U5. An unreleased hold removes its subject from the admission point entirely.** It is not queued at low priority, not deferred, and not ordered behind anything: [7.2](#72-admission-exclusion-and-cancellation) A10 means the arbitration mechanism never considers it. That is `Queue & History`'s Row 52 — *"held outside its machine's line while it waits, so it takes no place there and is not reordered"* — kept by the subject not being in the line rather than by a rule about how it is ordered within it.

**U6. A hold placed at the start of a render ends that attempt without rendering, and the machine is released.** **The render worker reports the hold and the reading it was computed from; the supervisor issues the hold identity, writes the hold record and journals it** (U2, U26, S1, M6); the worker writes the attempt's record, which is `Job files and outputs`' own record in the job-record area (M8) and not one of the machine stores S1 governs, and exits. The attempt ends with the render kind's own recorded outcome for an attempt that placed a hold, which `Rendering` names, and no render was started. **Where the supervisor is not answering at that moment the attempt places no hold at all**: it ends as an interrupted attempt and reconciliation takes it ([State, identity and recovery](State,%20identity%20and%20recovery.md#6-reconciliation-on-the-machine) §6), because a hold record written without a supervisor-issued identity and without a journal entry is a hold no reader on either cursor ever learns of, and U22 gives it no ending. **It does not stay alive waiting**, because a Blender with the scene loaded holds the machine's memory and its cards, and Row 52 requires that the machine start the next job.

**U7. Release starts a fresh attempt, and that attempt is an attempt like any other.** `Job files and outputs` R12's fresh four-value check of the file is taken at its start, before the map is applied, exactly as it is for a first attempt. **Where the file is unchanged, nothing is recomputed**: the recorded reading is the map in force per that document's [4.3](Job%20files%20and%20outputs.md#43-the-rule-runs-once-per-job-and-the-side-that-ran-it-writes-the-map) and R14, and the folders the user was shown are the folders written into. **Where the values differ, R13 governs** — the manifest's map is not applied, the worker takes a fresh reading, composes a fresh map and records that the file changed — and this document adds nothing to it. **What the release does not do is put the question to the user again.**

**U8. The released subject rejoins the line in the ordinary way, behind whatever is waiting at the moment the answer comes.** How it is ordered there is `Queue & History`'s; what this document supplies is that it enters the line at the moment the release outcome is written and not before.

### 8.3 The release command, and both routes are one path

**U9. An answer is an ordinary command with its own operation identity, naming the hold identity and carrying the answer.** It is subject to [Server protocol and transfers](Server%20protocol%20and%20transfers.md#42-idempotent-submission) C4 like any other: **the supervisor records the identity durably before acting on it, and a repeat of that identity never acts again.**

**U10. Both routes arrive at the same command path, and there is no second one.** The desk's answer arrives over SSH through the command adapter and the machine-local endpoint; the phone's answer arrives at the Telegram role worker, which *"submits phone actions to the same supervisor command path used by the SSH adapter"* and *"never signals a render directly"* ([The shape](The%20shape.md#each-rented-server)). **The two routes differ in how they reach the machine and in nothing after that.**

**The phone's answer arrives at whichever machine holds the listening slot, which need not be the machine holding the hold, and the carriage between them is stated rather than assumed.** Where the Telegram worker that receives the answer is not on the machine holding the hold record, the listener proposes the answer under its operation identity to [Telegram](Telegram.md#32-the-write-protocol-and-how-an-instruction-crosses-machines)'s bounded board. It is accepted only after the slot holder appends the complete entry and reads the board back exactly; from then until acknowledgement the board, outside every rental, is its authoritative durable home. The holding machine reads it there, records the identity durably before acting, applies it once and submits it to the **holding** machine's supervisor command path. No listener-local or former-sender record is authority for survival or redelivery. **A listening machine's own supervisor holds no hold record and releases nothing**, so it is never the addressee of an answer it merely received.

**U11. The answer's arrival needs no connection Smoozy holds.** Row 4's own words: *"nothing needs Smoozy to be running for it"*. The route that satisfies that is the phone's, and [Section 10](#10-the-telegram-role-worker-the-listening-slot-and-the-bounded-board) is what makes it available on a machine that is not the one listening: `Telegram` B1 to B15 keep the board and its accepted instructions alive across listener hand-over, and U10 ends the instruction at the machine holding the hold.

**U12. The supervisor applies the answer by writing the release outcome, once.** The write is what releases the subject; nothing else does. A worker is started afterwards by the ordinary admission point (A4) and never by the answering caller.

**U12a. A *no* removes its subject, in the same act that writes its release. Added 2026-09-30 by the build stage, step 10c's eleventh-pass fix piece 8b, on the build runner's ruling of that day.** The supervisor writes the release outcome *stopped* (U12) and journals it (U26); then it removes the subject's job record exactly as [Queue & History](Queue%20&%20History.md#4-acting-on-the-line) L1 and L5 remove a held job's. The record's removal is the deciding write, after which the job cannot start. The removal is journalled, so the desktop takes its local record (`Queue & History` L2). The hold record goes with its subject (U22's third ending; [Section 13](#13-retention-on-the-machine)), the job's material follows by L1's enumeration, and where another hold names the removed job as its dependency, `Queue & History` H9 fires. **The answer's result says the job is gone**, in the cancel's own outcome field and word — `Queue & History` L2's *removed* — so a caller sends no cancel after it. **One rule for both routes** (U10) **and both origins** (U1): a hold placed at a render's start ended that attempt without rendering (U6), so its subject has rendered nothing either.

**Why.** `Specs/Queue & History`: *"Saying no leaves nothing behind … Cancelling it and saying no are one act, not two."* `Specs/Telegram`: *"Saying no leaves nothing running and nothing waiting."* Until this clause a *no* wrote *stopped* and nothing removed the subject, so a *no* from a phone left the job held on the machine for ever, in every queue reading. The desk had kept the promise by sending a cancel after its own *no*, which made it true on one route only.

- **A removal the store refuses leaves the *no* in hand.** The release stands *stopped*, the job stays held and cannot start (U5), and the result carries what the store said. **A *no* that finds the release already *stopped* and its subject still standing removes the subject** — the same *no* asked again, or another. So a removal refused once is finished by the next *no*, and a machine whose older program wrote *stopped* and removed nothing is emptied the first time a *no* reaches it.
- **A repeat of the *no*'s own identity is answered from its command record** (`Server protocol and transfers` C4, C8). The hold record has gone with its subject, so the answer is read from the command's recorded outcome, *removed*, and acts on nothing. That repeat carries no release moment, the record that held it being gone.
- **What U14 can no longer tell.** An answer that arrives after a *no* removed its subject — a *yes* at the desk after a *no* from a phone — finds no hold record, as it already did after a drop (U20) or a cancel (`Queue & History` L5). It is told the machine holds no such hold, not which answer was applied. The user meets a job that is gone, which is the ending [Section 17](#17-moments-that-reached-the-creator)'s check of the race already describes.
- **U15 is untouched**: a *no* that finds *released* removes nothing and is told which answer was applied.

### 8.4 Two answers to one hold

**U13. The first answer to be recorded wins, and the second acts on nothing.** That is `Server protocol and transfers` C4 with no addition: the second answer carries its own operation identity, the supervisor records it, finds the hold's release outcome already written, and acts again on nothing. **The serialization is on the machine that holds the hold record**, because that is where both routes end — the desk's over SSH, the phone's carried there by U10's instruction where it arrived elsewhere — so first-recorded-wins is true of both routes rather than of one. **This is the race Row 53 says nobody has decided, and it is settled by the serialization the shape already put in place** — *"The server supervisor is the only writer of the machine-local queue and job journal … This serialization boundary prevents two callers from independently changing the same job and answers Row 53's race."*

**U14. The one that lost is told, and it is told what happened rather than that it failed.** The command's result carries the hold's recorded release outcome: which answer was applied, and the moment on the machine's clock. **A second answer is not an error** — it is [Server protocol and transfers](Server%20protocol%20and%20transfers.md#43-atomic-acknowledgement-and-what-an-acknowledgement-is-not) C8's *recorded outcome* answer, which is one of the three closed answers a machine can give about an identity.

**U15. A *no* that arrives after a *yes* is not converted into a stop.** The hold is gone and there is nothing to answer; what remains available is the ordinary stop, which `Rendering` owns and which both the desk and the phone already offer. **Nothing here invents a second way to end work that has started**, and the caller is told plainly that the hold was already answered, by which answer, and when. *(Added 2026-10-16 by the build runner, from the Telegram worker's piece 4: the other order is narrower — an answer arriving after a* no *finds no hold, the* no *having removed its record, and is answered as an expired button; the phone has already been told the* no *off the journal.)*

**U16. Neither route is privileged over the other, and the order is whatever the machine recorded.** There is no arrangement in which a *no* wins over a *yes* regardless of order, because that would need a window in which a *yes* does not release the job, and Row 52 promises that saying yes puts the job in line.

### 8.5 The dependency that drops a hold

**U17. A hold may name a dependency, and the ending of that dependency drops the hold without any answer.** `Telegram`'s Row 275 carries the negative case: where the first-frame job fails or is stopped, the waiting job is dropped and the user is told why — **done by the machine with nobody connected**.

**U18. The predicate is declared by the document that placed the hold and evaluated by the supervisor; this document does not decide what counts as the dependency having ended badly.** For the first-frame case the test is `Queue & History`'s Row 54, which reads the output folder rather than the exit status, and the reading it reads is `Job files and outputs`' completeness statement. **This document supplies the evaluation moment and the record; it answers neither row.**

**U19. The predicate is evaluated at exactly one moment: when the dependency's recorded outcome is written.** Not on a timer, not at every reconciliation, and not on a connection. That is the only moment at which the answer can change, and evaluating it anywhere else would be a poll.

**U19a. A second moment, for a dependency that ends without ever running. Added 2026-08-22 at the Architecture seam close, routed by the runner from [Queue & History](Queue%20&%20History.md#18-unresolved) §18 item 12.** **The removal of a job record a standing hold names as its dependency** is also a moment at which the predicate is evaluated, and the waiting job is dropped. It is not a poll — it is one durable act, the removal, exactly as U19's moment is one durable act. **Why it is owed:** a first-frame job cancelled before it ever ran has no operation record and therefore no recorded outcome, so U19 never fires and U21 as it stood held the waiter for ever — while the spec's own list of endings names *"or it is cancelled before it ever runs"* among them. `Queue & History` H9 supplies the moment from that side. **The removal is the deciding write** (that document's L1), so this evaluation rides it and never precedes it.

**U30. When the answer can change and when the reading can be taken are two different questions, and the reading is produced by the dependency's own ending.** U18's predicate reads the output folder, which the supervisor may not read — §1.3 rule 5 is restated at the head of this document with `Job files and outputs`' re-run test named as the single carve-out. **So the reading the predicate is evaluated against is taken by the dependency job's own worker as a step of that job's ending, and carried with the outcome the worker reports** — a step of a worker rather than a poll, and the same discipline M4's count is taken under. **The predicate is evaluated at U19's moment against that reading and never against a lookup at the supervisor and never against a reading taken before the dependency ran.** Which reading it is, and what it must contain, is `Queue & History`'s Row 54 and `Job files and outputs` [Section 10](Job%20files%20and%20outputs.md#10-completeness-already-there-the-last-frame-the-exit-status-and-the-stop)'s; **this document writes neither** and records the seam at [Section 16](#16-unresolved) item 17.

**U20. A drop writes the release outcome *dropped*, with the dependency's ending as the reason, and journals it.** The subject leaves the line and never enters it. What the user is told and where is `Queue & History`'s and `Telegram`'s; [8.7](#87-what-reaches-a-person-who-is-not-connected) supplies how it reaches them. **The journalled release of a drop carries what the user is told from. Added 2026-10-16, out of the Telegram worker's piece 3 (its reading 4), on the build runner's ruling of that day, and built at its piece 4.** Ahead of the words every release says, so the outcome stays the last thing it says, the event carries the reason, the held job's count of frames, the first frame's number and a bounded rendering of the held job's label (`Job files and outputs` N3). **Why**: the drop removes the held job's record, its material and its hold record in the same act (`Queue & History` H11), so a reader that did not read the hold's placing — a Telegram worker started between the placing and the drop — has nothing else to tell the user from. Like `Queue & History` L22's drop, it names no record and carries no path, and it sits inside `State, identity and recovery` E6a's per-entry budget. A part that cannot be read at the drop is left empty, never made up. No auditor of this document has seen this text.

**U21. A dependency whose ending is never recorded never drops the hold, save for the one moment U19a names. Corrected 2026-08-22 at the Architecture seam close.** Where the dependency's own operation was *given up* by reconciliation, that is a recorded outcome and U19 fires on it. Where the machine is destroyed, nothing fires and nothing is recorded, which is `Queue & History`'s own answer for a machine that went away.

### 8.6 Nothing expires a hold

**U22. The waiting ends in exactly one of three ways and there is no fourth**: an answer is recorded — *released*, or *stopped*, which removes its subject in the same act (U12, U12a) — its dependency's ending drops it (U20), or its subject is removed and the record goes with it. **No age, no cap, no sweep, no schedule, and nothing that reaches out to a machine to look** — the same closed list and the same reason as [State, identity and recovery](State,%20identity%20and%20recovery.md#88-when-a-failure-record-ends) §8.8. **The hold record's own lifetime is a different question and is [Section 13](#13-retention-on-the-machine)'s:** a released or dropped hold's record stays until its subject's machine-side record ends, so nothing is written twice about what the answer was.

**U23. That is the spec's promise and not a choice made here.** Row 52: *"**It waits with no time limit.** Nothing expires it and nothing decides for the user."*

**U24. A hold survives every restart the machine can have.** It is durable, it is read by reconciliation at every supervisor start, and reconciliation starts nothing whose hold is unreleased. A reboot, a supervisor crash and a container restart all leave the hold exactly as it was.

**U25. A hold blocks a package commit for as long as it stands** ([2.6](#26-what-blocks-the-commit-and-removal-as-an-internal-step) G23). That is the shape's rule and U23 is why it can last indefinitely; the caller is told the upgrade is deferred and why.

### 8.7 What reaches a person who is not connected

**U26. Every hold placed, every release and every drop is journalled as an event when it is written** ([State, identity and recovery](State,%20identity%20and%20recovery.md#4-the-event-journal-and-acknowledgement) §4 E1), so a reader learns of it by reading forward from its own durable cursor. **Nothing polls and nothing is pushed to the desktop.** **The desktop reader's read-forward recurs while it is connected, on `Desktop app and delivery` [3.3](Desktop%20app%20and%20delivery.md#33-ui-event-delivery) P10d's bounded live-reading sequence — added 2026-08-22, scenario replays Pile 1 item R1**: each pass is that reader reading forward from its own durable cursor, which is this clause's stated route. What *nothing polls and nothing is pushed* forbids is a machine-side watcher and a push, and that sequence is neither; nothing on this machine holds a schedule for it.

**U27. There are exactly two readers of that journal and the Telegram worker is one of them** ([State, identity and recovery](State,%20identity%20and%20recovery.md#4-the-event-journal-and-acknowledgement) E2). That is what lets a machine tell a person something with nobody connected: the role worker reads the event and sends it. **What it sends, and how it is paced, is `Telegram`'s.**

**U28. A cursor advances after the work the event asked for is done, never on receipt** (§4 E3), so a role worker that takes an event and dies before sending destroys nothing.

**U29. The hold record carries no notion of having been presented, and the journal carries none either** (§4 E7). A single flag cannot serve two independent readers, and an event the role worker presented would read as presented to the desktop.

## 9. The setup-in-progress state

**Constraint:** [The shape](The%20shape.md#each-rented-server) — *"`Rented-server runtime` owns a machine-level durable *setup in progress* state that holds reconciliation back; Server Setup sets and clears it through the same command path."* And [State, identity and recovery](State,%20identity%20and%20recovery.md#6-reconciliation-on-the-machine) §6's Step 0, which is that state. **Row 110** is what needs it.

**P1. One machine-level durable state, in the package area, holding whether a setup is in progress and the operation identity of the setup run that set it.** The identity is what lets a later reading say which run it belongs to; nothing infers the state from a setup worker being present or absent.

**P2. While it is set, reconciliation does not run and nothing is admitted but A11a's one exception** (§6 Step 0, and A11). Not the interrupted job, not a re-run, not a derivative, not a role worker's work — the exclusion is at machine level. **The exception is the worker start of the setup run the state names**, added 2026-08-22 at the Architecture seam close; reconciliation is not excepted and still does not run.

**P3. `Server Setup` sets it and clears it through the ordinary command path, and the supervisor never sets or clears it itself.** In particular no timer clears it, and the supervisor does not clear it because a setup worker has gone: a setup interrupted by a restart is precisely the case where the state must survive with no worker behind it.

**P4. Setting it is durable before the restart a setup step causes.** That is the whole of what Row 110 needs from this side: the machine that comes back on its own comes back with the state still set, so **the interrupted job is not started before the setup finishes** even though *"the machine re-runs without waiting for Smoozy or anyone else"*.

**P5. Clearing it runs reconciliation.** Without that, a machine whose setup finished would start nothing until its next supervisor start, and Row 110's *"the interrupted job is re-run after it"* would not happen. **So the clear is two acts in one durable write: the state goes, and reconciliation runs immediately afterwards** — which is the second of the two moments S9 names.

**P6. Ordering is what keeps Row 110's promise and it is stated as an ordering rather than as a coordination.** The setup and the queue do not talk to each other; the state is the only thing between them, and it is held by the machine rather than by Smoozy, so it works with nobody connected. **Smoozy is not required to be running at any moment of it.**

**P7. Nothing clears the state on the strength of time passing or of Smoozy reconnecting.** A machine whose setup was abandoned holds the state until a setup run clears it — either by completing, or by `Server Setup`'s recovery from its recorded safe boundary on a re-run. **The state is reported on every health answer** ([Section 12](#12-health-readings)), so the first thing a reconnecting Smoozy learns is that a setup is unfinished, and `Server Setup` owns what the user is offered. [Section 17](#17-moments-that-reached-the-creator) records the check on that.

**P8. A setup run that finds the state already set and naming a different run does not clear it.** It reports the state and its identity, and what happens next is `Server Setup`'s safe re-run.

## 10. The Telegram role worker, the listening slot and the bounded board

**Constraint:** the scope line's *"Telegram worker hosting"* and [Telegram](Telegram.md#3-the-slot-and-the-board) §3's confirmed bounded board. **[Section 8](#8-machine-held-work-awaiting-a-person-and-the-one-answer-release-path)'s answer-release path consumes that board**, because Rows 53 and 276 turn on where a phone's answer can arrive and how it survives until the owning machine acknowledges it.

**The observations behind the board were established against a real bot on 2026-08-12.** The rule they required is no longer missing: `Telegram` §3 owns it, and this document consumes it.

### 10.1 Hosting

**T1. The role worker is hosted exactly as [5.3](#53-the-one-role-worker) says and gets nothing of its own.** It reads the bot token at start from the file `Security and licence` §10 places, never passes it to a child as an argument or an environment value, submits every action to the same supervisor command path as the SSH adapter, and never signals a render directly.

**T2. It is a reader of the event journal with its own durable cursor in the machine's state area** ([State, identity and recovery](State,%20identity%20and%20recovery.md#4-the-event-journal-and-acknowledgement) E2), and it advances that cursor after the work is done and never on receipt (§4 E3). The observed reason is the same mechanism: three updates taken and deliberately not confirmed came back *"identical, same ids"* on the next ask, so *"a machine that grabs an update and dies before acting on it destroys nothing."*

**T3. It binds no inbound endpoint in the ordinary case**, and the one exception — the machine currently holding a registered webhook, where a provider permits one — is [Security and licence](Security%20and%20licence.md#13-the-inbound-boundary-at-a-rented-server) §1.3's and **nothing here hardens that boundary in either direction**.

### 10.2 Which machine asks

**T4 to T14 consume `Telegram` B1 to B15 and own no competing slot, heartbeat, board-capacity or instruction-survival rule.** Where the webhook route of [Security and licence](Security%20and%20licence.md#13-the-inbound-boundary-at-a-rented-server) §1.3 is in force, `Telegram` J1 to J4 own the registration-held form and stale-registration removal. **T3's promise to harden that boundary in neither direction stands.**

**T4. A machine asks for what the user sends only while it holds the slot, and a machine that is refused for conflict stands down rather than retrying.** That single rule removes the observed disaster: three machines all polling for a minute gave **61 attempts, 60 conflicts and one success, with nobody listening about 92% of the time**, and the cause is that the newest request always wins, so **two machines that both retry destroy each other**. A machine that stands down leaves the newest asker holding the slot cleanly.

**T5. Standing down is not giving up, and the board's heartbeat is tested without subtracting across clocks.** `Telegram` B4 and B5 own the exact rule: a stood-down machine asks again only after completed reads show no change in the opaque heartbeat value continuously for the stated renewal interval measured on the reader's own clock. A failed read advances and resets nothing. This replaces an age comparison against the holder's clock.

**T6. The board's holder and roster are hints; the slot's authority is Telegram's own exclusivity.** If two stood-down machines ask together, the accepted asker becomes holder and the refused one stands down. `Telegram` B3 makes a hand-over preserve the complete accepted instruction list before the reported pin moves; a claim never evicts or rewrites an accepted instruction.

**T7. A machine that has died releases the slot by not asking again**, which is the free half of the observation and needs no mechanism. The heartbeat going stale is what the others read.

**T8. Nothing in this arrangement requires a machine to reach another machine.** A rented server never holds another's connection identity and never opens a connection to another ([The shape](The%20shape.md#each-rented-server)); the conversation is the only channel and this rule uses only reads and writes of it.

### 10.3 The bounded-board write rule

**T9. The observed failure is exact and it is what the rule exists for.** Two machines wrote different instructions to the same pinned message **ten milliseconds apart**; Telegram told both they had succeeded, and a third machine reading every 1.5 seconds only ever saw the later one — *"The earlier instruction was gone with nothing anywhere to show it had existed."* Everything else about the note is sound and observed: any holder can read it without disturbing the listener, any holder can edit any message the bot sent, two machines editing the same message were never refused, and pinning is a stack so an older pin is hidden rather than destroyed.

**T10. One writer per message remains the primitive.** The slot holder writes the board it created; every other machine proposes instructions and returns acknowledgements through its own machinery message. No machine edits another machine's message. `Telegram` B1, B10 and B15 own the exact conduct.

**T11. The bounded board is written only by the slot holder and composed whole.** It has one canonical versioned serialization, admits no rendered candidate over Telegram's 4,096-character bound, and evicts no existing entry to make a new instruction fit. A refused admission is reported; it is never mistaken for an accepted instruction.

**T12. A board write is accepted only after exact read-back.** Telegram reports success for a write that may be overwritten, and nothing observed offers a conditional write, so an unconfirmed candidate is not a delivered instruction and does not advance the causal Telegram-update cursor.

**T13. An accepted instruction's authoritative durable home before acknowledgement is the confirmed board entry, outside every rental.** The board carries the complete request and operation identity; its current holder re-presents every unacknowledged identity, and B3 carries the complete list across holder replacement. The addressee records the identity durably before acting (`Server protocol and transfers` C4), acts once and acknowledges through its machinery message; a repeat acts on nothing. **No sender-local outstanding record, sender resend loop or sender lifetime is part of the survival proof.**

**T14. An instruction stays on the board until its acknowledgement is observed, and a missed acknowledgement is reported rather than assumed delivered.** Whichever holder owns the board at the entry's reporting deadline tells the user that the addressee has not confirmed. It does not infer that the requested work failed, and it removes nothing without the acknowledgement. **The one exception is `Telegram`'s context-resolution entry** (its B8 and B12), which is a question addressed to one machine rather than an accepted action: it is completed by being replaced with the full instruction, and expires under that owner's own deadline rule where it never is. **An accepted action instruction still never expires.** Returned by `Telegram` under T17 rather than written from this side.

**T15. Nothing here is timed against the user's own reading.** The end-to-end chain was observed to work — a tap reached the right one of two machines in 1.4 seconds and of three machines in 0.9 and 0.7 — and this rule adds a read-back to the machine-to-machine half only.

### 10.4 What is `Telegram`'s and is not answered here

**T16. Rows 257, 258, 259 and 260 are `Telegram`'s and none of them is answered here.** This document consumes that owner's bounded-board result only for the machine-held answer-release path. **`Telegram` owns the conversation's conduct and authority**: the board's contents and capacity, how a tap is shaped, how instructions are accepted and retained, which message is pinned and what the user sees.

**T17. [The shape](The%20shape.md#18-telegram) assigns the single receiving slot and pinned-message write serialization to `Telegram`, and that owner has now answered both through its bounded board.** T4 to T14 are the runtime consequences of that answer, not a second authority.

## 11. Captured streams, the exit, and the explicit collection outcome

**Constraint:** Row 286, quoted at the head of this document, and the scope line's *"stdout, stderr and exit capture; finite retention of both captured streams, with a stated ceiling above the control-state reserve and an explicit loss outcome where the ceiling is reached, the streams still drained; an explicit collection outcome distinguishing *the render printed nothing* from *nothing was collected*"*. **The raw record is this document's and nothing edits it** — [Security and licence](Security%20and%20licence.md#13-logging-redaction) §13's own boundary: *"Nothing in these rules edits it — Smoozy does not alter what the machine said."*

### 11.1 The two streams are captured by the worker into sinks the supervisor made

**M1. The supervisor creates two sinks per attempt inside the package area, keyed to the job identity and the attempt, before the worker is started, and records their paths in the operation record's per-kind field.** That is where the captured streams already live — [State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2 lists them as a machine store inside the server package's own state area, and `Job files and outputs` L6 puts them in the same area — and the job-record area is that document's to own. They are outside every job output folder, so nothing the user browses, downloads or renders reaches them (`Job files and outputs` L7). **When they end is [Section 13](#13-retention-on-the-machine) R1's**, which names it by the job's machine-side record rather than by a sweep.

**M2. No probe byte is written into a sink to confirm its placement.** [State, identity and recovery](State,%20identity%20and%20recovery.md#13-rules-that-bind-every-store) §1.3 rule 4's real-write confirmation is performed once for the whole root at hand-over (`Job files and outputs` L11) and is not repeated per stream, because a byte written to confirm a placement would be a byte in the raw record that the machine did not print.

**M3. The worker holds both of the render's streams and copies them to the sinks itself.** It does not hand the render a descriptor onto a file and it does not pipe them through the supervisor. **Two things force that and both are observed.** The supervisor may die while the render lives — a detached program outlived the shell that started it, *"Its parent is **1**"* — so a capture that ran in the supervisor would stop mid-render in exactly the case the *resumed* branch exists for. And the worker is already the process that remains until its external processes have exited (X12), so it is alive for the whole of the render by construction.

**M4. The worker counts the bytes it writes to each sink, and the count is Smoozy's own count.** It is never a reading of a sink's size: §1.3 rule 5 forbids reading a file's size as state, and the reason is the same one that defeats every other size reading in this project — a zero-byte file *"is indistinguishable between 'still being written', 'the disk filled' and 'the render wrote nothing'"* (Fact 28). **This is the same discipline [Server protocol and transfers](Server%20protocol%20and%20transfers.md#82-the-enforcement-point-is-smoozys-own-byte-loop-and-the-evidence-forced-it) R12 applies to a transfer's progress and S22 to its digest: the count is taken at Smoozy's own loop and never asked of anything else.**

**M4a. The pair of sinks receives one finite capture ceiling when M1 creates it.** The supervisor reads the bytes available to its login on the state area's recorded mount through V7's free-space route and subtracts a **64 MiB control-state reserve**; the non-negative remainder is the attempt's capture ceiling, recorded by value before the worker starts. Existing retained streams are already absent from that available-byte reading and are not subtracted a second time. The two streams draw from one remaining-byte counter at M4's loop: a write is offered no more than the remainder, only bytes successfully retained decrement it, and once it is zero neither sink receives another durable write. **No later free-space reading raises it, and a lower reading clears nothing**: the ceiling limits only new stream bytes and does not age, trim or remove any byte already retained. Where the remainder is zero, the capture record and empty sinks are still established from the control-state reserve, the worker starts, and every stream byte is drained and discarded under M5 with *collection incomplete* recorded.

**The reserve protects the state mount from Smoozy's own stream capture and claims no protection from the user's outputs or another process filling that mount.** What keeps a render's own outputs off this mount at all, where anything does, is placement rather than this reserve: `Job files and outputs` L4a puts the package area on a mount chosen apart from the job area's where the machine offers more than one, and that document's §14 item 21 states what still breaks where it does not — added 2026-08-22, scenario replays Pile 1 R12. **Narrowed 2026-10-04: that placement keeps the outputs off this mount only for a job whose output folder is in the job area**, which from that date is `Job files and outputs` 6.6 P19's fallback alone; a job whose folder sits where its file points writes on whatever mount that folder is on, this one included (P22), and nothing but this reserve stands between it and the control state. *Narrowed again later on 2026-10-04: a fallback job whose output folder is in the server's chosen fallback folder (`Job files and outputs` P23) is in the same position as one where its file points, so the job area holds only the fallbacks that found no chosen folder they could use.* It exists so the worker and supervisor can still write the refused-write fact, the two collection outcomes and the job ending after capture reaches its ceiling. A placement that cannot establish the reserve does not admit a render; it reports that the machine has no room for control state. The `64 MiB` value is a Build constant at one declaration point and not a user setting.

**M28. At that same loop, and on the ordinary stream, the worker records two further observations of its own: whether the launch material's marker passed, and whether anything followed it.** They are observations of Smoozy's own act on bytes Smoozy is copying, exactly as the count is, and neither is a reading of a sink or an arithmetic comparison against the marker's length — the marker names the job identity and each destination it set (M9), so its length varies by job and nothing here compares against it. **The complaints stream carries no marker and takes neither observation** (M16). What the two are for is M13's ordinary-stream rows.

**M5. Reaching M4a's ceiling, or a sink write being refused first, ends durable writes for that stream and never ends its read.** The worker records the first reason once, keeps reading that child pipe to end of stream, counts the bytes it discards, and writes none of them anywhere. It continues the other stream independently until that stream reaches the shared ceiling or its own sink refuses. **Documented** ([Sources](Sources/Rented-server%20runtime.sources.md)): POSIX `write()` requires a broken-pipe outcome where a pipe has no reader and permits a pipe writer to wait where capacity is unavailable; closing the reader or leaving it present but undrained can therefore change or stop the child rather than merely shorten Smoozy's record. Draining and discarding keeps the collection failure from changing the render. On a full filesystem every sink write is refused with `No space left on device` and errno 28, uniformly (Fact 28). **Smoozy does not stop a render because it can no longer durably record what the render is saying**, and [11.3](#113-the-explicit-collection-outcome) says exactly which prefix was retained and why the rest was lost.

**M6. The worker reports its retained and discarded counts, the first loss reason per stream, M28's two observations and the exit it reaped to the supervisor, which writes them into the operation record.** Workers report observations and the supervisor is the only writer of state (S1); **the sinks are material written under the supervisor's control, in the same sense the staging areas are.** **A report that crosses a supervisor restart is the case this channel is written for, and [5.2](#52-per-operation-workers) W12 states how it survives one**: the report is re-attempted against the endpoint's recorded path, carries the run identifier the worker was started under, and is accepted by a supervisor that has written *resumed* for that group.

### 11.2 The streams are kept apart, and every retained byte is verbatim

**M7. The two streams are two sinks and are never merged.** The reason is Blender's own and is already settled: in 4.5 the line naming what did the work is reached only through a debugging switch writing to the complaints stream, while from 5.0 it is on the ordinary output (`Rendering`'s Row 10), and the complaints stream also carries the failure text shown to the user. **Anything mixing the two into one record loses which one a line came from**, which Row 286's own constraints name.

**M8. Nothing edits any byte retained from either stream — not a redaction, not a filter, not a prefix, not a trim.** [Security and licence](Security%20and%20licence.md#13-logging-redaction) §13's protection is *never emitted* rather than *filtered before display*, and its rules 1 and 2 keep secrets out of the machine's reach in the first place: no secret is ever a process argument or an environment value, and the machine's own environment is never captured into any record Smoozy keeps. **M5's post-ceiling bytes are not retained and are represented only by the discarded-byte count and loss reason; Smoozy never presents the retained prefix as the whole stream.**

**M9. The launch material's marker is part of the raw record and is not an edit of it.** `Job files and outputs` D16 has the material's first act print a marker on the render's own output naming the job identity and each destination it set. **That is the render printing, through material Smoozy handed it, and it is what [11.3](#113-the-explicit-collection-outcome) leans on.**

**M10. Both streams are read back with nobody connected, and searched.** Fact 70's plain half is answered: a program printing to both and ending at status 3, started detached, had both streams kept separate, the ending recorded, and the kept output searchable for a line ([Batch A](Batch%20A%20—%20the%20shape%20throwaway.md), Fact 70). **The paths worth searching for are `Job files and outputs`' completeness statement's** ([10.6](Job%20files%20and%20outputs.md#106-the-completeness-reading-and-the-one-signal-a-lost-write-leaves) C28); whether anything searches them is that document's and `Desktop app and delivery`'s.

**M11. What is retained is read back whole or not at all.** A read of the retained prefix that did not complete is not a reading — the same rule and the same evidence as `Job files and outputs` C9, where *"Partial output is delivered before the connection dies"* ([One box with Blender on it](One%20box%20with%20Blender%20on%20it%20—%20the%20reading,%20the%20listing,%20and%20the%20names%20that%20do%20not%20come%20back.md) §5.6) and a truncated listing and a genuinely short one were separable only by exit status. **Completing this read proves only that the retained prefix arrived whole; M13's outcome says whether that prefix is the whole stream.**

### 11.3 The explicit collection outcome

**M12. The collection outcome is a recorded fact about the collection, written by Smoozy about its own act, and it is what turns an absence into something that can be reported.** Row 286 says the plain sentence must say the render ended without printing anything **rather than leaving the user to work out whether Smoozy failed to collect the words or there were none** — and an absence cannot prove itself. **What can be recorded is what Smoozy did**, and this is that record.

**M13. One outcome per stream per attempt, from a closed set of four.**

| Outcome | Written when | What it says |
|---|---|---|
| **collected** | the worker reported an end of stream and a non-zero count — and on the **ordinary** stream, observed the marker and observed something after it (M28) | the record is the whole of what was printed on that stream |
| **collected, and the stream was empty** | on the **ordinary** stream: the worker reported an end of stream, observed the marker, and observed nothing after it. On the **complaints** stream, which has no marker (M16): an end of stream and a count of zero | **the render printed nothing on that stream**, and this is a recorded fact rather than an inference from an empty file |
| **collection incomplete** | the worker did not report an end of stream; or M4a's ceiling was reached; or a sink write was refused (M5) | the retained bytes are a verbatim prefix and may be empty; nothing says they are all of it; retained and discarded counts and the first loss reason are recorded |
| **never established** | no capture record exists for the attempt; or, on the **ordinary** stream, the worker reported an end of stream and never observed the marker; or, defensively, where a worker was started before its sinks were made, which [Section 14](#14-atomic-or-partial--this-documents-declarations) forbids | **nothing of the render's own printing was established** — a run that ended before it reached the launch material, or an attempt with no capture record at all — and Smoozy says so rather than showing an empty panel |

**M14. The two that Row 286 exists to separate are separated by two different records, not by two readings of one thing.** *Collected and empty* rests on an end Smoozy observed and on what Smoozy observed passing its own loop — the count on the complaints stream, the marker and what followed it on the ordinary one (M28). *Never established* rests on the absence of a capture record the supervisor writes before the worker starts, or on that marker never having passed at all. **Neither is derived from the sink**, and both are Smoozy's own record of its own act.

**M15. The marker is the positive signal that makes *collected and empty* believable on the ordinary stream.** `Job files and outputs` D16 puts the marker first, before anything of Blender's, printed by Smoozy's own material. **So an ordinary stream holding the marker and nothing after it is a render that printed nothing, and an ordinary stream with no marker at all is a run that did not reach the material** — which D17 already forbids anyone treating as a loud failure, and which M13 now takes by name: the first is *collected, and the stream was empty*, the second is *never established*. **Neither is read off the stream afterwards**; both are M28's observations, taken as the bytes passed.

**M16. There is no equivalent marker on the complaints stream and this document does not add one.** D16 is `Job files and outputs`' and prints on the render's own output; **adding a second marker would be a change to another document's launch material**, so what stands for the complaints stream is M13's own four outcomes and no more. [Section 16](#16-unresolved) item 9.

**M17. Reconciliation writes *collection incomplete* for any attempt whose capture record was established and whose worker never reported an end.** That is the case a reboot, a container restart and a worker's own death all produce, and it is written at the reconciliation that finds the operation record's group gone (§6 step 2). **Without that step an interrupted capture would be indistinguishable from an empty one**, which is exactly the confusion Row 286 forbids.

**M18. The outcome is written once per stream per attempt and is never rewritten.** It is a subject outcome in [State, identity and recovery](State,%20identity%20and%20recovery.md#81-two-kinds-and-the-kind-is-declared) §8.1's sense: immutable, and not the user's to clear.

**M19. A re-run is a new attempt with its own two sinks and its own two outcomes.** Nothing appends to a previous attempt's record and nothing merges two attempts' streams.

### 11.4 The ending is never read from what was printed

**M20. A job's state comes from the operation record, the execution group's validation and the reaped exit status, and never from either stream.** That is Row 286's third clause and it is kept by the streams being material that nothing reads as state (§1.3 rule 5).

**M21. Where the group is gone and no exit status was reaped, the outcome is recorded as an ending with no status, and an ending with no status is failed.** *"A job that stops with nothing to read is failed, not still rendering."* **Nothing stays in a running state because nothing was printed**, and no absence of output ever extends a job's life.

**M22. A successful exit status is never read as *everything was written*.** Blender's own research counts twelve endings that report success, and this stage's own evidence from outside Blender adds three conditions that all end at **0** — a full disk, a purged driver and a mismatched driver. **Three conditions, one ending, and neither figure is added to the other.** **This document reads the exit status for one thing only:** it is recorded, verbatim as a number, in the capture record, and it is handed on. What completeness is read off is `Job files and outputs` [Section 10](Job%20files%20and%20outputs.md#10-completeness-already-there-the-last-frame-the-exit-status-and-the-stop)'s and is not this document's.

**M23. Nothing here matches an ending on its number** (X13), and nothing reads the machine's own system log for a job's ending. Fact 55 is why: *"The system log records only that it sent a termination signal to remaining processes, naming neither Blender nor the render nor its output."*

**M24. Nothing mines either stream for a cause.** [Security and licence](Security%20and%20licence.md#13-logging-redaction) §13 rule 5 — *"A tool's own output is captured whole or not at all, and is never mined for a cause"* — and `Job files and outputs` C26, which records four different wordings for one failure across versions and operating systems.

### 11.5 What the arrangement does not close

**M25. Fact 70's second half is not closed by this section and this section does not claim to close it.** What is written here is the arrangement; whether it delivers the distinction on a real render on a real machine was Batch E's, and it is the whole difficulty Row 286 names. **Batch E posed it on 2026-08-18 and the arrangement delivers**: all four outcomes came back distinguishable on both machine kinds, read with nobody connected, with every count agreeing exactly with what the sinks held, *collected and empty* never written where the worker was killed, and *never established* plainly distinct from it. **Nothing in this section changed**; what changed is that it is observed. **M26's residual stands unaltered** — a worker that died can still leave bytes its count never reached.

**M26. The residual is named exactly.** A worker that died can leave bytes in a sink that its count never reached, so a *collection incomplete* stream can hold content while the count says none. **That is why *collection incomplete* is its own outcome and never collapses into *collected and empty***, and why the raw record is still offered for an incomplete stream, marked as incomplete.

**M27. `Job files and outputs` [Section 14](Job%20files%20and%20outputs.md#14-unresolved) item 5 states what breaks without the fact**: C28's route from an absent path to the line naming it, which is Row 136's only signal. **What holds without it is that document's completeness statement**, which is produced from the inventory and one walk and needs no stream at all.

## 12. Health readings

**Constraint:** the scope line's *"health readings"*, and [State, identity and recovery](State,%20identity%20and%20recovery.md#83-the-condition-identity-and-who-supplies-each-observed-value) §8.3, whose table names `Rented-server runtime` as the supplier of the *supervisor unavailable while SSH is live* condition's observed value. **And, for [V12](#12-health-readings) alone, [Server protocol and transfers](Server%20protocol%20and%20transfers.md#92-the-two-routes-to-the-cause-and-the-moment-each-is-fixed-at) F6a, which leaves the machine-side act of Row 287's route (b) to this document.** That one is not a health reading and the section holds it because V7 holds the free-space mechanism this document uses. **And, for [V13](#12-health-readings) alone, the architecture runner's ruling of 2026-09-02 under the Creator's delegation of that date. Added 2026-09-02 with V13, this constraint having read *for V12 alone* while the section held two clauses that are not health readings.** That one is not a health reading either; it is the architecture half of the runaway rental, and it is written here because both of its grounds are properties of the machine.

**V1. *Health exchange* and *health readings* are two different things and are not one word.** The health exchange is the package commit's verification step ([2.4](#24-the-health-exchange-and-what-a-failure-restores)) and happens once per transaction. Health readings are what the machine reports about itself on request.

**V2. Every health reading is taken on request and never on a schedule, with one named exception.** Nothing here polls, nothing watches, and no reading is taken to keep a message fresh.

**The exception, and it has one beneficiary and no others: the `Telegram` role worker's status reading.** It is taken by that worker on its own machine, about that machine, on that machine's own clock, at the cadence [Telegram](Telegram.md#10-the-clock-the-status-message-and-report-pacing) §10 C2 states; it is used for the status message and for the gather's reply and for nothing else; it is **never sent to the desktop and never written durably**. Everything outside those words stays on request: **nothing else polls, nothing else watches, and no other reading anywhere is taken to keep a message fresh.** This is an exception with a named beneficiary rather than a general loosening, and V3's *no health check pings* is untouched by it.

**The desktop's live-reading sequence carries no health reading and neither uses nor widens this exception. Added 2026-08-22, scenario replays Pile 1 item R1.** `Desktop app and delivery` [3.3](Desktop%20app%20and%20delivery.md#33-ui-event-delivery) P10d's set is closed — the journal read-forward, the queue reading, the commentary read — and this section's readings are named out of it, so no health reading recurs for it and every one stays on request as this rule says.

**The citation this rule used to carry now narrows.** [State, identity and recovery](State,%20identity%20and%20recovery.md#84-nothing-is-polled-to-withdraw-a-record) §8.4 is the **desktop-side** rule of the same shape — nothing is polled to withdraw a record, no condition gets a watcher of its own, no failure record reaches out to a machine — and it stands word for word; the exception above is this document's alone and reaches nothing on the user's computer. **Applied, 2026-08-19, on the Creator's ruling, outside this document's own rounds; no auditor of this document has seen it** — the decisions record carries the line.

**V3. No health check pings.** Fact 57: *"one provider answers no ping at all"* while its connection works perfectly, **so any ping-based health check would report it dead.**

**V4. The observed value of the *supervisor unavailable* condition is one thing: whether the supervisor answered a request on the command path.** It is not a reading of a process, not a reading of a file, and not a reading of the connection. `Servers` supplies the connection's own condition and the two are never inferred from one another.

**V5. Every health reading carries the moment it was taken and the clock it was taken on, and it is period-held** ([State, identity and recovery](State,%20identity%20and%20recovery.md#3-desired-state-and-observed-state) D5, [§11.1](State,%20identity%20and%20recovery.md#111-five-classes-and-the-reason-there-is-no-sixth)). **Nothing durable is written from a health reading, and no health reading is ever journalled or written into a job record** — that half holds for the readings this section is about, everywhere and without exception. **And no promise rests on a health reading, with the single exception V2 names**: the status message's statement of what the machine is using rests on a reading, and its statement of how long the machine has been up rests on one only on the machine kinds where [Telegram](Telegram.md#10-the-clock-the-status-message-and-report-pacing) C1 makes that statement — C1 holds that half conditional on the detected kind (K1) and states it as unavailable on the kind where the figure is not the machine's own, so nothing rests on a reading there. **Conditioned 2026-08-23**: this carried the uptime half unconditionally and read as though the statement is always made. Whichever statement is made is shown with the moment it was taken and is never a durable fact. The ruling that made the exception needs the reading **shown, not stored**. **Applied, 2026-08-19, on the Creator's ruling, outside this document's own rounds; no auditor of this document has seen it.**

**Narrowed to the health readings 2026-08-22, scenario replays Pile 1 item R11: this said *every* reading and *nothing durable is written from one*, and two figures in this document already contradicted it.** M4a's capture ceiling is derived through V7's free-space route and *"recorded by value before the worker starts"*, and V12's free-space reading is carried with a render's recorded outcome. **What separates both from a health reading is what is being recorded.** A health reading is a live value with a lifetime — what the machine is using now — so writing one down puts a claim about the present into a record that cannot be refreshed, which is the fault this rule exists to prevent. Those two are figures about the moment they were taken, written once into a record nothing rewrites ([State, identity and recovery](State,%20identity%20and%20recovery.md#81-two-kinds-and-the-kind-is-declared) §8.1's *ending* kind for V12's, [§8.6](State,%20identity%20and%20recovery.md#86-the-subject-outcome-is-durable-and-immutable); M4a's own *"no later free-space reading raises it, and a lower reading clears nothing"* for the ceiling), and neither is refreshed, re-read or withdrawn. **The one promise that rests on a reading of this second sort is Row 287's route (b)**, which rests on V12's and never on a health reading, and which is a statement about the place at that moment rather than about the present (`Server protocol and transfers` F14, F15).

**V6. Which mechanism a reading is taken by is chosen by the detected machine kind (K1), and getting that wrong is silent.** Three of Fact 48's and Fact 46's consequences bind:

- **On a container the machine's own memory and processor readings are wrong** — `nproc` said 4 and the memory file said 15.57 GiB while the real allocations were 3.84 processors and 14.95 GiB, and on a second host on 2026-08-22 a **20-core** slice reported `nproc` **40** and the host's **64 GiB**. **The cgroup's figures are the ones to take**, falling back to the machine's own only where the cgroup reads the literal unlimited value. On a one-of-eight rental the machine's own figure would overstate memory eightfold. **Both cgroup generations are read and neither is assumed, and there is a third outcome — corrected 2026-08-22.** The reading is attempted at `cpu.max` and `memory.max` **and** at `cpu.cfs_quota_us` with `cpu.cfs_period_us` and `memory.limit_in_bytes`, whichever answers. **Where neither answers, the allocation is not established and the machine's own figure is not substituted for it** — a stated absence, carried as such. **Keyed on the machine kind, 2026-09-21, ruled R12 by the build runner under the Creator's standing delegation of 2026-08-31; no auditor has seen this change.** That sentence is about a container and always sat inside this bullet, but `Servers` H9a's table read it as covering every machine, and on a plain virtual machine neither file exists at the root of the control-group tree — observed on a rental that day — so every virtual machine and bare-metal server showed its memory as unreadable. **On a machine K1's table places at its second row — no container marker, the tool's container-only form finding no container, systemd the first process — no route means nothing caps it and the machine's own figure is its memory.** On a container, and on a machine K1 does not place, the absence stands exactly as written. **The container-only form is what tells a systemd-booted system container apart**: the tool documents it as detecting *"shared kernel virtualization"* and names `lxc`, `lxc-libvirt`, `systemd-nspawn` and `openvz` among its containers (`Servers` [Sources](Sources/Servers.sources.md) 11.11). **A container of a technology the tool does not name is not told apart** and is [§16](#16-unresolved) item 33. That case is observed rather than hypothetical: on the box above *"`cpu.cfs_quota_us` and `memory.limit_in_bytes` both empty — the host is on cgroup v2 and the v1 paths do not exist"*, so a rule written on the older pair alone fell through to the host's answer while believing it had the rental's, which is the eightfold error arriving by the route the rule was meant to close. `Servers` H9a holds the same rule from the reading side and the two must stay identical ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)).
- **On a container the card readings inherited from the host lie, and the newer case is quieter than the old one. Strengthened 2026-08-22.** `/proc/driver/nvidia` and the PCI sysfs scan *"are inherited from the host kernel"* and reported two NVIDIA devices in a container that could touch neither. **So card presence is read from the driver's own answer and never from either of those on a container.** **The observed case used to be a container holding none of the host's cards, where the reading is obviously wrong. It is now also a container holding *some* of them, where it is not** — two hosts of four cards each, rented as two-card slices, on which the driver's own query returned **2** and `/proc/driver/nvidia/gpus` returned **4**, two of the UUIDs belonging to another tenant ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)). **A count taken there is two too many and looks entirely reasonable.** And on the same boxes **`lspci` was absent from the image altogether**, so the scan does not lie there — it does not run; `Servers` H11's fifth row is the rule for that. **The device-node route is forbidden too**: four nodes appeared for one two-card rental and two for the other, and on the second the kernel's `Device Minor` values for our own cards were **2** and **0**, unrelated to the query's index 0 and 1.
- **The count is read as a count and never as a parsed total.** A per-card query returns the value once per card, so a caller parsing the whole output as an integer gets `22` on a two-card machine. **It passes every test ever written on a one-card machine.**

**V7. Free space is a choice of mount and never a reading of the machine.** [State, identity and recovery](State,%20identity%20and%20recovery.md#13-rules-that-bind-every-store) §1.3 rule 3 and [Server protocol and transfers](Server%20protocol%20and%20transfers.md#91-a-reading-is-a-choice-of-mount-and-the-mount-is-the-one-the-write-was-attempted-on) §9.1 own the mechanism. **What this document adds is the mount it names for its own state**: the state area's mount is recorded at placement and every free-space claim about state writes names that mount. **The only other free-space reading this document takes is V12's**, which is about a job's own output folder rather than about state and names that path's mount instead.

**V12. A render's recorded outcome carries a free-space reading against that job's own output folder, taken in the same act that writes the outcome. Added 2026-08-22, scenario replays Pile 1 item R11.** [Server protocol and transfers](Server%20protocol%20and%20transfers.md#92-the-two-routes-to-the-cause-and-the-moment-each-is-fixed-at) F6a states the disk-full carve-out's route (b) from the desktop's side and leaves the machine-side act here. **It is neither of V1's two things, and neither V2 nor V5 reaches it**: it is taken once, in one act, and nothing schedules it, refreshes it or re-reads it.

- **The act.** The same durable write that records the render operation's outcome ([State, identity and recovery](State,%20identity%20and%20recovery.md#51-the-durable-operation-record) §5.1) — the ordinary ending the supervisor takes from the wait status ([X9a](#62-the-stop-sequence-on-this-side), [State, identity and recovery](State,%20identity%20and%20recovery.md#53-the-deliberate-stop) §5.3 step 6), and equally the ending reconciliation writes for a group that is gone ([S11](#33-reconciliation-is-the-supervisors-and-it-runs-at-more-moments-than-a-start), [M17](#113-the-explicit-collection-outcome)). Whichever act writes the outcome is the reading's moment. **Only the render kind takes it**, and no other kind's ending is given one.
- **What is read.** [Server protocol and transfers](Server%20protocol%20and%20transfers.md#91-a-reading-is-a-choice-of-mount-and-the-mount-is-the-one-the-write-was-attempted-on) F1's per-path reading against **that job's own output folder** and nothing wider — that document's F3 available figure, never its F4 subtraction, never its F5 writability test, and never widened into a statement about the machine (its F16). **One reading covers the job output folder and every write place the redirect brings under it** (`Job files and outputs` P7, D20), which is what makes a single per-path reading the right one; **it says nothing about the one residue the redirect does not reach** (that document's D21) and is never widened to stand for it. The mechanism is V7's: the mount is the one that path resolves to, which is the job area's rather than the state area's wherever `Job files and outputs` L4a placed them apart.
- **What it needs.** No announced extension and no program on the machine beyond the supervisor itself. After hand-over the supervisor is Smoozy's own code and takes the filesystem call directly — the route Fact 28 answered on a rental, *"both through `df` and through the filesystem call underneath it"* ([Two more boxes](Two%20more%20boxes%20—%20the%20volume,%20the%20full%20disk,%20and%20a%20day%20left%20running.md)) — so this reading is not one of the two `Server protocol and transfers` F2 negotiates, and neither of those routes going unannounced withdraws it.
- **What it rides.** The write that records the outcome, so it needs no durability the ending does not already need and reaches a reader by the route the ending does. **On a mount the render has filled, that write is refused and both it and this reading ride the pending outcome under [S14](#33-reconciliation-is-the-supervisors-and-it-runs-at-more-moments-than-a-start)** — the ending is late rather than guaranteed, and S14's hold-and-re-attempt is the whole of what saves the case. **M4a's control-state reserve is not what leaves room for it**: M4a says in terms that the reserve protects the state mount from Smoozy's own stream capture and *"claims no protection from the user's outputs or another process filling that mount"*, `Job files and outputs` L4a says the separation is placement and not protection, and that document's §14 item 21 states what breaks on a machine with one writable mount. **Corrected 2026-09-01**, scenario replay *The server disk fills up during render* finding N-d: this said the reserve is what leaves room for the write, which those three clauses contradict on the machine that scenario describes, and **a builder who took it at face value had no reason to build S14's pending queue at all.**
- **What it carries.** The moment it was taken, on the machine's own clock ([State, identity and recovery](State,%20identity%20and%20recovery.md#3-desired-state-and-observed-state) D5), and it is immutable with the outcome it rides ([State, identity and recovery](State,%20identity%20and%20recovery.md#86-the-subject-outcome-is-durable-and-immutable) §8.6). It is a statement about a past moment rather than about the present.
- **Where it cannot be taken.** The job output folder gone, the mount absent, the call refusing — none of it holds up the outcome, which is decided and written whatever the reading does. **An outcome carrying no reading is not an outcome carrying a zero**, exactly as [S13](#33-reconciliation-is-the-supervisors-and-it-runs-at-more-moments-than-a-start)'s outcome carrying no completeness statement is not one carrying an empty statement: the absence is recorded explicitly, route (b) does not fire on it, nothing is re-read afterwards to supply one, and nothing infers a full disk from it (`Server protocol and transfers` F6a item 6).
- **What it is not.** It is never a supplier of the live disk-full condition, which keeps [State, identity and recovery](State,%20identity%20and%20recovery.md#83-the-condition-identity-and-who-supplies-each-observed-value) §8.3's own two current suppliers (`Server protocol and transfers` F11a); it is not V4's observed value; and it never becomes a statement about why the render ended (`Server protocol and transfers` F14). **What the user meets is `Desktop app and delivery` [16.4](Desktop%20app%20and%20delivery.md#164-row-287-presented-the-disk-full-carve-out) M15's presentation of Row 287 and nothing new from here.**
- **Where the outcome's own write is refused for want of room, the reading is the first attempt's and rides the pending outcome unchanged** ([S14](#33-reconciliation-is-the-supervisors-and-it-runs-at-more-moments-than-a-start); added with it, 2026-08-22): re-taken at the landing it would read the freed mount and silence the diagnosis — the fault R11's repair closed, arriving again by that window.

**V8. A writability test is not a health reading and is not a signal.** On a full filesystem the writability test returns writable and creating an empty file succeeds; only writing at least one byte fails (§1.3 rule 4).

**V9. The machine-level *setup in progress* state and its setup run's identity are reported with every health answer** (P7), so the state is learned on the first request rather than discovered by a machine doing nothing.

**V11. A machine's clock is its own and readings taken on different clocks are never subtracted** (D5). **A container has no clock of its own** — the reading is the host kernel's and nothing inside can discipline it. [Section 16](#16-unresolved) item 10. **Struck 2026-08-29**: this opened *Fact 92 is not answered and*, which has been wrong since Batch E — the register carries Fact 92 as answered 2026-08-18 and [Section 16](#16-unresolved) item 10 records that answer here in the same words. Nothing in V11 rested on the label; the pointer to item 10 is where the answer and its qualifier live and it stays. **A fifth reading of that, on a second seller, 2026-08-22** ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)): no time daemon of any kind present (`chronyd`, `ntpd`, `systemd-timesyncd` all absent), `timedatectl` unusable because there is no service manager, and the clock nonetheless correct to the second against the caller, clocksource `tsc`. **The new detail is the second half rather than the first: nothing inside can correct it either**, so a container whose host clock is wrong stays wrong for the whole rental and no step of this document can act on it. **The virtual machine of the same batch was the opposite** — `systemd-timesyncd` active, synchronised, and still correct across a reboot.

**V13. Nothing this document places on a machine can end that machine's rental or cap its life, and Smoozy builds nothing that tries. Added 2026-09-02, on the runner's ruling of that date under the Creator's delegation of the same date.** This is the architecture half of the runaway rental. It is written here because both of its grounds are properties of the machine and of what runs on it, which is this document's subject; **the half the user meets is not this document's and is named at [Section 18](#18-what-this-document-does-not-own)**.

- **The provider publishes no way to cap a rental's life, and this was read rather than assumed.** Vast's create-instance reference, `https://docs.vast.ai/api/create-instance`, read 2026-08-20, lists the request body in full and carries no duration field at all; a duration exists only as a read-only number of seconds on the instance, per `https://docs.vast.ai/api-reference/instances/show-instance`. Its Instances FAQ, `https://docs.vast.ai/documentation/reference/faq/instances`, read 2026-08-20, under *"What does "Lifetime" mean on my instance?"*: *"This rental end date is locked when you rent and cannot be changed by the host. When the rental end date is reached, the rental contract expires and the instance is stopped."* **A cap was asked for on creation and again on the running instance; both returned `{"success": true}` and changed nothing**, which is what an ignored unknown field looks like ([Two more boxes](Two%20more%20boxes%20—%20the%20volume,%20the%20full%20disk,%20and%20a%20day%20left%20running.md)).
- **A watchdog inside a container cannot end the container either, and that is a kernel rule rather than a provider's choice.** `pid_namespaces(7)`, `https://man7.org/linux/man-pages/man7/pid_namespaces.7.html`, read 2026-08-20: *"Only signals for which the "init" process has established a signal handler can be sent to the "init" process by other members of the PID namespace."* and *"SIGKILL or SIGSTOP are treated exceptionally: these signals are forcibly delivered when sent from an ancestor PID namespace. Neither of these signals can be caught by the "init" process."* SIGKILL can never be caught, so no handler for it can ever exist, so it can never reach the namespace's init from inside; the forcible route runs from an ancestor namespace, which is the provider's side. **Every worker class of [Section 5](#5-worker-classes-and-their-lifecycles), and the supervisor itself, is inside that namespace.** The observed attempt is recorded: a watchdog written to kill PID 1 at a chosen hour did not end the box, and the outcome had been written in the future tense and never checked ([Two more boxes](Two%20more%20boxes%20—%20the%20volume,%20the%20full%20disk,%20and%20a%20day%20left%20running.md)).
- **So the only thing that ends the charge is a person destroying the rental by hand.** This document places nothing on a machine that could do it, and no clause here is to be read as licence to add one.
- **No automatic destruction is built, and that is a ruling rather than an omission.** A rescue that destroyed a machine would destroy the work on it, and that is the worse of the two failures. There is no timer here that reaches a provider, no condition that ends a rental, and no *give up and destroy* branch anywhere in [Section 2](#2-the-package-transaction), [Section 3](#3-the-supervisor) or [Section 5](#5-worker-classes-and-their-lifecycles). **[Section 17](#17-moments-that-reached-the-creator) stays empty and is not owed an entry**: the spec already says the machine is the user's and is *"never rented, billed, powered on or off by Smoozy"*, so building nothing here costs the user nothing the spec did not already promise them — which is a narrowing stated rather than an escalation.
- **The second half — how long the machine has been running — is a reading, and it is conditional on the machine kind.** On a systemd rental the uptime reading is the machine's own. **On a container it is the host's and would lie** — 8.2 days reported on a container created that morning ([The last two boxes](The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md)) — so it is not a figure about the rental at all, and the ruled conduct of 2026-08-23 stands unchanged: where the reading would not be the machine's own, the line says it is unavailable rather than showing the host's (`Telegram` §21 item 21, and `What Build inherits`). **[Section 16](#16-unresolved) item 31 carries what that costs**, and this document opens no second route to the figure. **Who makes the request is `Servers` [W41a](Servers.md#118-the-machine-runs-and-bills-until-it-is-destroyed-by-hand)'s, added there 2026-09-02** out of the scenario replay *The machine is destroyed* — one request per primary connection, at that document's Q1 step 7 where the supervisor is reachable, on the confirmed branch only. **V2 is untouched by it**: a reading taken once when a connection is made is taken on request, it is not in `Desktop app and delivery` P10d's closed set and does not join it, and nothing re-reads it to keep a screen fresh. **Where the request is not made or is not answered, no figure stands and none is inferred** — the stated absence, never a zero and never a held figure carried forward as current.
- **What this clause supplies to whatever surface tells the user, and what it refuses to supply.** The statement — that a rented machine runs and bills until it is destroyed by hand — is **true on every machine kind, needs no reading, and must never be made conditional on one**; the machine that cannot report its running time is exactly the machine the statement matters most on. This document supplies the two negatives above and the kind-conditional reading and nothing else. **Which surface says it, when, and in what words is not decided here** ([Section 18](#18-what-this-document-does-not-own)).
