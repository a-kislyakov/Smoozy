## 1. The record — Row 178

**Eight promises across five sections of the spec read this record, and it is the only place the artist's file's remap lives.** Because the artist's file is never written to, losing this record costs the user every decision they made by hand, and nothing anywhere holds a copy — the spec says both outright.

### 1.1 Where it lives, and what it is

**K1. Every durable fact this module keeps on the user's side is a record kind inside the local record** ([State, identity and recovery](State,%20identity%20and%20recovery.md) §1.1). There are five kinds and the list is closed: the **located-answer record** (K3), the **placement record** (K7), the **fixing record** (K8), the **check standing** (7.3 V10), and the **shift record** (K6). The per-job resolved set of K9 is a field of the job's own local record rather than a sixth kind.

**K2. Nothing about this record is ever written on a rented machine, with exactly two machine-side exceptions, both material rather than state:** the remap material of 6.4, and the fixed copies of 6.5. Both are derived from the record and can be re-derived from it; neither is ever read back as state. The machine dying costs neither a located answer nor a user decision — which is the spec's split: the resolution record outlives the machine, the fixing dies with it.

### 1.2 The located answer — keyed with no machine in it

**K3. One located-answer record per (holding file, reference as the file records it), and the reference key is the recorded location's exact bytes, capitals included.** Two references reading `METallic.png` and `metallic.png` are two records with two answers — the spec states the comparison is exact and why: compared any other way they collapse, and the second reference silently inherits the first one's file. The **holding file** is identified by its source location on the user's own computer, as stored on disk (4.3 F12): for the file the user points at, the source path `File Browser` hands over; for a linked file below it, the source location its own resolution recorded. **No machine and no installation identity is any part of this key**, which is what makes the answer travel: the same file checked on a machine it has never been on gets every match the user made by hand.

**K4. What a located answer holds:** what the reference resolved to — a whole location on the user's computer, as stored on disk, or a folder for a set row (3.6); how it was resolved — the recorded location itself, the search (and from which searched folder, and whether the pick was arbitrary and among which candidates), a shift (naming the shift record), or the user's own hand; a **set-aside** mark, remembered beyond the sitting; and a **rejected guess** — a proposal the user turned down, kept so it is not put forward again by itself and can be reinstated. Each write of a located answer is one durable write made at the moment the user acts or the search resolves, never batched to the end of a sitting — a connection lost mid-check loses nothing already decided (3.4 G17). **It also holds what the check read the reference as — every data-block kind and every setting that holds the location (M4) under which the latest reading of the holding file carried those bytes, once each, in the reading's order. Added 2026-09-29, out of step 10c's dependency wave piece 7b, on the build runner's ruling.** M4 puts a kind and a setting in every pair and M10 composes the pairs from the record at submission, where the spec forbids reading the file; with neither kept here the pairs could be composed only in the run that did the check, and after a restart a checked and sent file was submitted with none. Each reading of the holding file writes them afresh, and a decision the user takes carries them unchanged. Where one holding file records the same bytes under more than one kind or setting, the one answer keeps each and each gives its own pair, since a pair is a kind and a setting (M8). They say what the check read and never what the file holds now (K11): a file edited since reads differently at the render, and M8's *not applied* already covers that. An answer that no reading has written them into holds none and gives no pair until the file is checked again. Label: Smoozy's decision.

**K5. A file that was already on the machine with no known local origin is the one degenerate case.** Its references still get located-answer records, keyed by the holding file's machine location under the machine's installation identity — and those answers do not travel, because there is no user-side file for them to travel with. A relative location inside such a file resolves against its machine folder and nothing else, which is the spec's own limit. **The case is reached by the user's own act as well as met below a root — stated 2026-08-22, scenario replays Pile 1 R23**: `File Browser` N7a's **Check dependencies…** on a file its N6 lookup finds nothing for starts the check in this reduced form — a file whose request record the user tidied away (its N8) arrives here exactly as one that never crossed by Smoozy at all. What the user is told at such a start is this clause's limit in as many words — the answers will stay with this machine, and a relative location resolves against the machine folder alone — wording `File Browser`'s and Design's.

**K6. A shift record is written when a hand-locate teaches a shift** (4.4): the old root, the new root, and the moment. Every located answer a shift produced names its shift record, which is what makes the one-action undo of 4.4 F20 a lookup rather than a search. Shift records are keyed inside the local record; they are record keys rather than identities in [State, identity and recovery](State,%20identity%20and%20recovery.md) §2.2's register — no identity anywhere is derived from one, and none of §2.1's rules is touched. The same is true of K3's keys: the reference bytes and the source location are lookup keys the spec itself fixes, not issued identities, and nothing parses, sorts by, or derives anything from them. **The scope of that closing sentence is stated 2026-08-25, per Row 498, which found it read as a flat bar on any ordering.** Its verbs are [State, identity and recovery](State,%20identity%20and%20recovery.md) §2.1 rule 2's — the opacity rule that binds *identities* — and its subject is the register this paragraph is about: the keys are not issued identities, no identity anywhere is derived from them, and none of §2.1's rules is touched, which is the whole of the sentence's load. It was never a bar on this document's own declared clauses reading the same value in its other roles — F16 was already deriving the shift from the recorded location's whole segments when the sentence was written, and [G11a](#33-one-row-per-thing-and-the-check-staying-finite--row-161) now orders the panel's rows by the same bytes — each a declared reading that issues no identity and enters nothing in §2.2. What it bars is unchanged where it was ever load-bearing: nothing derives an identity from a key, and no key is one.

### 1.3 The machine-keyed records — what was sent where, placed, and fixed

**K7. One placement record per (machine, mirrored location), keyed under the server row and the installation identity it was placed under.** It holds: the mirrored location (5.2); the source location the upload came from — without which a relative location cannot be resolved after the file has moved, and the shift has nothing to shift from; the **content identity** of what was placed (Section 2: size and digest, taken from the transfer's own pass-through digest at publication); the four-value identity of the published file read at publication (size, inode, modification time, change time — the same shape as [Server protocol and transfers](Server%20protocol%20and%20transfers.md) S13 and [Job files and outputs](Job%20files%20and%20outputs.md) R10, one shape rather than three); and whether a later confirmation has re-established it (2.3 Q7). A placement record carrying a superseded installation identity is **disqualified rather than ended** ([State, identity and recovery](State,%20identity%20and%20recovery.md) §11.1) — a recycled machine answers on the same address with everything gone, and the installation identity is the only thing that tells ([State, identity and recovery](State,%20identity%20and%20recovery.md) §2.3).

**K8. One fixing record per (machine, fixed copy), same keying.** It holds: which linked `.blend` the fixed copy was made from (the **machine location** of the copy it was derived from — the mirror where this module placed the file, and the file's own machine location where it is there by another route — and that copy's content identity), where the fixed copy sits (5.1 A3), and **what the fixing points at** — the list of (reference bytes → machine location) pairs written into it, which is also the list M16's second replacement trigger compares against the current located answers. The fixing itself lives in the fixed copy on the machine and dies with the machine; the fixing record is what lets the three warnings of 7.1 answer *what did Smoozy place and fix here, and what points at what* **at the moment a destination is named, before any write, without touching the machine** — which Row 172 requires because all three warnings are shown before a write.

**K9. Each submitted job's local record carries the job's resolved set as composed at submission:** the machine locations its remap material names — mirrors and fixed copies — beside the manifest's `.blend`, **and the remap material's own machine location** (6.4 M10). The material is in the set because the whole of Row 177's chain runs through it and it is otherwise the one link in that chain no reading names: with it in the set, the points-at reading of 7.1 V2, the live-job rule of V6 and the delete warning of V3 reach it with no new mechanism, and it is on U1's never-removed list beside the assets. [Job files and outputs](Job%20files%20and%20outputs.md) R15 states the division — *"Which files a live job depends on is the manifest's `.blend` and the resolved set `Dependency Upload & Remap` keeps."* That document supplies the first with its identity and staleness rule; the second is this field. It is written when the remap material is composed (6.4 M9), it is immutable for the life of the job's record, and `File Browser`'s live-job warning and `Queue & History` read it (Section 11).

### 1.4 What the record survives

**K10. The app closing, a connection lost mid-check, and the machine being destroyed — in that order: trivially, by K4's write-as-it-happens, and by construction.** Located answers and shift records carry no machine key and survive the machine outright. **A check standing does not, and is keyed exactly as 7.3 V10 keys it** — one per (root file's machine path, machine under its installation identity) — because a check describes one file on one machine and says nothing about a newly rented or recycled one. Placement records, fixing records and check standings all describe a machine and are disqualified with its installation identity; they are **subject-held** on their server row ([State, identity and recovery](State,%20identity%20and%20recovery.md) §11.1), which is the same list U3 keeps. Located answers, shift records and the search-folder list are **user-held**. Nothing here has an age, a cap, or an elapsed-time lifetime.

**K11. The record answers *where did this live* and *what did the user decide*; it never answers *what does this file need now*.** Only the check answers that, and the check reads the file every time it runs — the spec's own division, kept structurally: no path anywhere below reads a located answer as a statement about the file's current contents.

## 2. Telling two files apart by what is inside them — Row 168

**Four different questions are put to one mechanism, and the mechanism is one content identity compared at whichever end holds the bytes.** *Already on the machine* as a row state; the overwrite warning; the second reference to a file already up; and confirming a *sent before, not confirmed* row. How Smoozy does the comparing is stated by the spec to be Architecture's, Creator-stated 2026-07-28.

**Q1. The content identity is the pair (size in bytes, digest), and the digest function is the one [Server protocol and transfers](Server%20protocol%20and%20transfers.md) S23 fixes per protocol version, so that one reading serves both purposes.** A transfer's pass-through digest, computed in Smoozy's own byte loop as the bytes pass (S22), **is** the content identity of what was published — no second read of a file that just crossed the wire is ever taken. Equality of the pair is this module's definition of *the same file*; the size is compared beside the digest, and a partial can never satisfy it, because a partial's contents are not the whole file's contents. **That is the sentence that closes Row 170's central hazard**: nothing on the machine distinguishes a part-arrived file from a whole one (Fact 18), and nothing here ever asks the machine to — equality of contents is the test, and a hybrid or a truncation fails it.

**Q2. On the user's computer the digest is computed by the application reading the file through.** Observed on a real 669,966,622-byte `.blend` on the Creator's Mac: **md5 at 1.26 s and sha256 at 2.22 s** ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 15). **Corrected 2026-08-23: this clause used to give those two numbers as a range *"depending on the implementation"*, and they are two digest functions rather than two implementations of one.** Q1 fixes the function to the single one [Server protocol and transfers](Server%20protocol%20and%20transfers.md) S23 fixes per protocol version, so **one of those two figures is the cost and the other is not, and which one follows from S23** — there is no range here. Fact 15 measures a five-fold implementation gap **on the machine** (`openssl dgst -sha256` 0.46 s against `sha256sum`'s 2.24 s, Q3) and asserts a gap in the same direction on the Mac without recording figures for it, so **no observation bounds what a particular desktop implementation costs**. Nothing rests on either number: Q4 is that no rate is promised anywhere.

**Q3. On the machine the digest is computed by Smoozy's own package code, running as a per-operation worker, and never by a tool found on the machine.** Fact 15 measured `openssl dgst -sha256` at 0.46 s against `sha256sum`'s 2.24 s on the same box and the same file — but which programs an arbitrary rental carries is established nowhere, and the package removes the question: the digest is the package's own code, driven through the supervisor's command path. Section 9 declares the operation.

**Q4. The cost is processor rather than disk, and no rate is promised anywhere.** Fact 15's own clause: an end-to-end check at about a gigabyte a second is available *"on processors with the instructions that make it fast, which both ends here had and a rental may not."* Every promise below is written as *reading both files through, at both ends, on each machine rather than between them* — the spec's wording — and none names a duration. Section 12 item 6.

### 2.1 Already on the machine

**Q5. A row is *already on the machine* when the contents of the file at the resolved machine location are established equal to the contents of the local file the row resolved to — established by record or by reading, never by presence.** Two routes, tried in order:

1. **The record fast path.** A placement record (K7) ~~or a published transfer record ([Server protocol and transfers](Server%20protocol%20and%20transfers.md) S9 — `File Browser`'s hand-uploads carry one too)~~ names that machine location with a content identity, under the current installation identity. **Corrected 2026-09-29, out of step 10c's dependency wave piece 4, on the build runner's ruling: a published transfer record is not a route.** [Server protocol and transfers](Server%20protocol%20and%20transfers.md) S9 says that record *"holds no copy of any byte and no observed value the machine still holds"*, so it carries no four values to compare and can never answer this path. A file that came up by `File Browser`'s hand-upload therefore meets route 2, and where route 2 cannot run it is simply not established here — the cost is one redundant send, never wrongness. The machine copy's four values are read and compared against the four recorded at publication. Where all four match, the copy is bit-for-bit what was published (Fact 21 answered *"yes, from size, inode, modification time and change time together"*; a save-by-rename changes the inode; a hand-restored modification time still moves the change time, which cannot be set back), and the recorded digest stands for its contents with no read. The row is *already on the machine* exactly where that digest equals the local candidate's.

**Which channel that read runs on is named here for the first time, 2026-08-21, because it was named nowhere and only one of the two channels can answer it — the command channel.** The file-transfer surface cannot. **Revision 3 is the revision in play, on two grounds and no longer on a third.** Documented: OpenSSH's own `PROTOCOL` file, read **2026-08-23** at `https://raw.githubusercontent.com/openssh/openssh-portable/master/PROTOCOL`, says *"Note that OpenSSH's sftp and sftp-server implement revision 3 of the SSH filexfer protocol described in:"*. Observed: **protocol version 3 was the version announced by every rental posed — four boxes across three sellers** ([One box with Blender on it](One%20box%20with%20Blender%20on%20it%20—%20the%20reading,%20the%20listing,%20and%20the%20names%20that%20do%20not%20come%20back.md) §3.1, 2026-08-17; [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md) group 1, 2026-08-22). **Withdrawn 2026-08-23: this clause used to add that a session against this project's own shipped server negotiated `Remote version: 3`.** No document under `Preparation/` records that session — no machine, no end, no client, no date — so it is not an observation this project holds and it is struck rather than relabelled. `Server protocol and transfers` §7.4 carries the same unrecorded session in its own words and is **routed rather than edited here** (Section 11).

**What revision 3 defines, quoted from the specification as published** — `draft-ietf-secsh-filexfer-02`, section 5 *File Attributes*, read **2026-08-23**: *"A new compound data type is defined for encoding file attributes"*, whose fields are *"uint32   flags"*, *"uint64   size"*, *"uint32   uid"*, *"uint32   gid"*, *"uint32   permissions"*, *"uint32   atime"*, *"uint32   mtime"*, *"uint32   extended_count"*, *"string   extended_type"*, *"string   extended_data"*, with *"The `flags' specify which of the fields are present."* and *"The `atime' and `mtime' contain the access and modification times of the files, respectively. They are represented as seconds from Jan 1, 1970 in UTC."* **So: no inode. No file identifier. No change time. And `mtime` is a `uint32` count of seconds, so no sub-second granularity either.** **Read against what this document carried, the specification agrees with it — 2026-08-23**; what it did not have until now was quoted words, which is why it is quoted rather than described.

Two of the four values are absent from that surface, and **the one the design leans on hardest is one of them** — the change time, whose whole point in Fact 21 is that a hand-restored modification time still moves it and it cannot be set back. **So a builder reaching for the ordinary listing would silently get two of the four and a coarser clock on one of those.** **This read is a command-channel reading**, which puts it on [`File Browser`](File%20Browser.md#13-unresolved) Section 13 item 9's unestablished ground — which programs answer such a reading on an arbitrary rental, and whether their formatted output holds — and it is carried there rather than repeated. **Section 9's operation table names three machine-side shapes and none of them is this one**; that shortfall is recorded at [Section 12](#12-unresolved) item 19 rather than repaired here, because naming a program would be inventing a fact. **Nothing below moves:** where the reading is unavailable, the fast path simply does not fire and the ordinary contents route runs, which is the same shape as every other missing capability.

**After hand-over that read goes through Smoozy's own installed program, and many files share one ask. Added 2026-10-03, out of step 10c's slow send (`Audits/Build/Step 10c/After the Vast fixes, the whole desk, four rulings and the slow send — what landed.md`, part 3), ruled by the build runner; no auditor of this document has seen it.** The read is [Server protocol and transfers](Server%20protocol%20and%20transfers.md) §1.1's request *the four values of files on the machine*, answered by the entry point. It is still a command-channel reading — the entry point is reached by a command — so everything above about revision 3 stands; what it no longer leans on is a machine program's output format, because the entry point makes the filesystem call itself. **Every four-value read this document takes after hand-over rides it, and the reads are gathered:** the send's pre-flight asks once for every file whose mirror a placement record names; Q7's *Confirm* asks once for every placement the row covers; and the read at publication that K7's record waits on goes in the next ask, together with every other publication on that server still waiting for its read when that ask starts. Nothing waits on purpose to gather more. A placement record is written when its file's answer lands; a publication whose answer never lands gets no record, and a later check sends the file again, as before. **Where the server's program does not declare the request**, the read stays on the command route above, one file at a time. **Why gathered:** the entry point is itself reached through a planted link, so one ask per file would cost what the command route costs; the saving is one link and one command shared by many files.
2. **The read-through.** Where no record names the location, or the four values moved, the machine copy is read through by the digest worker and compared against the local candidate's digest. Equal → *already on the machine*, and a confirmation is recorded (Q7). Unequal → the row is not already there, and where the location is occupied by a different file the overwrite warning of Q8 fires before anything is sent.

**Q5's two routes are written for one file, and a set row's located answer is a folder (K4, 3.6), so a set row carries its own contents test on top of them: a set row is *already on the machine* only where the mirrored folder's membership — enumerated on the machine and matched by the same pattern rule G22 applies to the user's own folder — equals the local set member for member, *and* each member's contents are established equal by the two routes above.** The membership half is what the file-by-file test cannot see. It is a listing on the transfer surface ([Server protocol and transfers](Server%20protocol%20and%20transfers.md) 1.1) read with N15's discipline, and like Q5's own two routes it is a deliberate comparison rather than a reading of state (Q6): it can only **withhold** confirmation, never grant it, since every member still has to have its contents established. Nothing ever removes a member from the machine (Section 8), so a set's machine-side membership only grows: a tile the artist deleted locally and re-checked would leave every remaining member satisfying Q5, the row confirmed, nothing sent — and M4's pair would point the reference at a mirrored folder holding a tile the project no longer has, with the pattern intact. **How Blender decides a set's membership at render is exactly what G22 says is uncovered by the research and deliberately not modelled here**, so nothing in this document can say the surplus member is left out — and a surplus member drawn into a render is real content the user's project does not hold, which is worse than a member missing and is the harm Row 168's *"That is what stops an old job's texture being silently reused for a new one"* exists against. **Where the membership differs the row is simply not confirmed** — a state the spec already has — and what the row then shows, and any offer to remove the surplus, is `File Browser`'s wording and Design's. What this document supplies is the reading.

**Q6. The four-value read and the read-through are deliberate comparisons the spec orders, not readings of state.** They are the same shape as [Job files and outputs](Job%20files%20and%20outputs.md) 4.4's change test and [Server protocol and transfers](Server%20protocol%20and%20transfers.md) S13's resume test — a rule about what to send, never a fact inferred from a file being there. A file found at a location no record names, and not read through, is **never** *already on the machine*.

### 2.2 Sent before, not confirmed

**Q7. Confirmation of a *sent before, not confirmed* row is Q5 run against the record's own entry.** The state exists where the record says a file was sent for this reference to this machine and the local original is no longer there to compare — the spec's case of a file the user moved or deleted locally. Confirmation: the four-value fast path against the placement record; where it holds, *already on the machine*; where the file is absent, back to *not found* and the placement record is marked gone; where the file is present but the values moved, the read-through — against the **recorded** content identity, since there is no local original. The confirmation's outcome is written into the placement record with the moment it was taken.

### 2.3 The overwrite warning and the second reference

**Q8. The overwrite warning is Q5's route 2 finding a different file at the landing place — and its scope is this module's own row sends, reaching no plain `File Browser` upload. **Q9. The second-reference question — *have I seen these contents anywhere on this machine* — is a lookup by content identity across the machine's placement ~~and published-transfer~~ records.** **Corrected 2026-09-29, with Q5 route 1 and for the same reason: a published transfer record holds nothing this lookup can match** ([Server protocol and transfers](Server%20protocol%20and%20transfers.md) S9), so the lookup reads placement records alone, and a copy that came up by `File Browser`'s hand-upload is missed like any copy Smoozy did not place. A hit means the reference is pointed at the copy already there rather than uploaded again — the spec's rule that the layout mirrors where a file **first** came from. A file the user placed twice by routes Smoozy did not perform has no record and the lookup misses it; the cost is one redundant mirror copy, which is bandwidth and disk, never wrongness. **A hit on a linked `.blend` saves the upload and nothing else.** A `.blend` is remapped in place and what a render reads is Smoozy's fixed copy of it (6.5), so the reference is never pointed at the copy already there: that copy is what the fixed copy is produced from, the fixed copy is addressed off its machine path (A3), and the library pair names the fixed copy. *Already on the machine* means the file does not need sending, never that it does not need fixing — the spec's own sentence.

### 2.4 What the comparison never does — Row 170's half

**Q10. Nothing in this module ever marks a row *already on the machine*, *sent before, not confirmed*, or anything else from a file's presence, name or size.** A part-arrived file carries all three convincingly (Fact 18) and carries nothing else; every state above comes from a record Smoozy wrote or a contents comparison Smoozy ran.

**Q11. **G6a. A linked file that is there while the named thing inside it is gone is said as a statement, not as a row. Added 2026-08-22 on the Creator's ruling of Row 410.**

**The case, which is not the one the rest of this section covers.** A reference into another file names the thing it wants, and **the name is the whole identity**: rename that thing inside the library, or delete it, and the reference breaks — reported in the same words either way, *"with only a count of missing libraries telling a lost file from a lost item inside a file that loaded"*, and **what is left behind keeps the name and the library and holds nothing, and the render still writes a frame** (*Dependencies 8, 11*, through the joined answer [What has to travel with a file](../Blender%20Research/Across%20topics/What%20has%20to%20travel%20with%20a%20file.md)). **So nothing is missing at the file level.** The library resolved, the search has nothing to look for, and every route this section has — the enumeration of recorded locations, the search, the located answers — produces nothing at all. Left alone, the job renders to a **successful** ending with an empty stand-in where the artist's chair or rig used to be, and the user is told nothing.

**Why it cannot be a row, and this is the spec's own rule rather than a preference.** A row would be **none of the seven states** — nothing failed to resolve and the file is there — **none of the four qualifiers**, and would carry **no action**, because there is no file to find and nothing to point at. The spec's *a row that cannot be acted on is a control that does nothing* rules exactly that out. **The ruling does not overturn that rule; it declines the premise that the panel can only speak in rows.**

**What it is instead.** **A statement of the check's own, standing with the statements the panel already carries and not with its rows** — *could not be read* with the version named (G3), a sitting said plainly to be incomplete (G16), the search's per-folder report (F7, F1a). Those are already established as **statements of what happened rather than things to act on**, and [V3a](#71-what-smoozy-knows-about-a-machine-answerable-before-a-write--row-172) already declares that none of them is a warning and none is dismissible. This joins them and inherits all of it: **not a row, not a warning, no action, no suppression, no switch-off**. It says that a linked item was not found inside its file, and it names the library file, which is the one thing that is always known. **It does not name the item**, because Blender's signal never does, and the statement says that rather than implying the name was withheld.

**What it changes about the check's standing: nothing.** [V11](#73-the-check-standing--row-179)'s stop rule counts rows, and this produces no row, so a check that is otherwise complete still stops the warning. **That is deliberate.** The alternative — letting an unnameable, unactionable finding hold the ready-to-render signal open forever — would give the user a file they can never make Smoozy happy about, which is the same *control that does nothing* in a different costume. **The user is told, and is left able to proceed**, which is the whole of what the ruling buys.

### 3.3 One row per thing, and the check staying finite — Row 161

**G10. A row stands for the thing pointed at; a located-answer record stands for one reference.** References are grouped into one row where they resolve to the same file, and the row says that more than one reference led to it. The record beneath stays per reference (K3), which is what keeps `METallic.png` and `metallic.png` two answers even when they turn out to be one file on the user's folding disk.

**G11. Before resolution, references group by their tidied resolved location text; after resolution, by the resolved file.** Blender's own one-library rule is the constraint (observed, all four versions, both machines, *Dependencies 19* through the spec): two recordings differing only in how the path is written — relative, full, or a detour to the same place — are one library, because Blender tidies the writing before it decides; two recordings reaching one file by two names on disk are a separate library each, because the tidying stops at the text. **The remap consequence is the load-bearing half**: a remap that gives two ordinary library entries the same location merges them at the next read. So two references resolve to one row — and one remap target — exactly where they resolved to the same file on the user's computer (same stored whole location, 4.3 F12), and never on a name match alone. Two references resolved to two different files keep two rows and two mirror locations, and the mirror rule of 5.2 keeps those locations distinct — **except where Q9 points a second reference at a copy already on the machine, which fires only on equality of contents, so a merge produced that way merges two files that are the same file by this module's own definition (Q1)**. That is the whole of the guarantee, and it is the argument that actually holds: mirror locations are distinct by 5.2, and the one route that lands two references on one machine location lands them there because the bytes are identical. From 5.0, packing linked data deliberately leaves two entries with one recorded location (***Dependencies 19*** again, which carries packing as the deliberate exception to its own one-library rule; **route added 2026-08-23, this clause having named none for the packing half**); the check reads them as what they are and manufactures no second row.

**G11a. The within-group ordering: the recorded location's own bytes, compared whole segment by whole segment, a location standing at its final segment before one still descending. Added 2026-08-25, per Row 498.** [Design](../Design/Dependency%20Upload%20&%20Remap.md) sorts rows inside a group *"by the location the file records"*, so that *"the folders of a project stay together and a shift's effect reads as a block rather than as scattered rows"*; the spec hands the layout to Design without a value to lay it out by, and no clause here produced an ordering key.

- **The value ordered is G3a's byte object and never the drawable form.** The comparison is over the recorded location's own bytes, the object carried once from the reading — the drawable form may draw two distinct byte values identically (G3a: the value is bytes and is not required to be text), so an order over it is not deterministic without the bytes as its tie-break, and the bytes alone are. G3a's own lists are untouched: the ordering is one more comparison over the bytes, and the drawable form still reaches nothing.
- **The comparison is segment by segment because the design's sentence promises an outcome, not merely an order.** The value splits at the separator byte into whole segments — the same unit F16's suffix rule compares — each segment compared as exact bytes, no folding, no normalising and no canonicalising (F9's discipline, held for ordering as for matching). At the first level where two locations differ, one standing at its final segment sorts before one with segments still to come; only where both stand or both descend do the segment's bytes decide. That is what makes a folder read as its own files in one run and then each subfolder as one block — under a whole-value byte order, a subfolder's block falls between its own folder's files wherever the subfolder's name, or the separator byte itself, sorts between two file names, and *the folders of a project stay together* is then not delivered. A subtree is contiguous under either comparison; only this one keeps a folder's own files together as well, and it is also what makes a shift's effect one block: every row whose recorded location sits under the old root is one contiguous run.
- **The key is the location as recorded, never as resolved and never tidied.** The column being ordered is *what the file records*, so relative and absolute writings sort under their own forms rather than being shuffled against the very value the user is reading; G11's tidied grouping text stays a grouping rule and supplies no order. A location carrying no separator byte is one segment and compares whole — an odd order for that row and never a wrong one; what separator a location written on a Windows computer carries rides [Section 12](#12-unresolved) item 3 with the rest of Windows.
- **A many-reference row's key is the least of its references' recorded locations under this same ordering.** G10 keeps the record per reference and the row per thing, so a row may hold several byte objects where the design's key is singular; the least member is deterministic, derived from values the row already holds, and needs nothing kept. Which of the several the column draws is Design's; a drawn member other than the key costs a reading oddity in that one row, never a wrongness.
- **The ordering is a run-held comparison made at drawing and derives nothing.** No record is written, no identity is issued, and nothing durable holds it — the footing F22 gives the selection. That is what keeps it outside K6's closing clause, whose scope is stated in K6 itself this day: the bar there is the register's, not a bar on a declared reading of the value.

**G12. Capitals decide the library case differently at the two ends and the answer leans on neither.** On the rented Linux machine a wrongly capitalised library location is not a file and the link fails outright; on the Creator's Mac it quietly succeeds and leaves two libraries where one was meant — settled for those two machines and not for the kind (***Dependencies 19***, which carries that pair in those words and says plainly that it settles those two machines and not the kind; the general rule that capitals are the disk's decision rather than Blender's is ***Dependencies 8***. **Routes added 2026-08-23, this clause having named none for the Mac half.**) The mirror and the remap write exact stored bytes (4.3, 5.2), so neither end's folding is ever relied on. **The machine end is now three machines across three sellers rather than one — 2026-08-22** ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)): both rented filesystems were **case-sensitive by both routes**, with `casefile.txt` and `CASEFILE.TXT` holding different contents and listing as two entries, and `stat` on a mixed-case form returning not-found. **So a wrongly capitalised library location is not a file and the link fails outright, on three machines instead of one.** **What that widens is this clause's first half only, and the batch settles nothing about folding:** its own words are that *"a folding directory returning the name it was given was not posed, because no folding directory was found to pose it on"*. That question was settled for ext4 by the kernel's own documentation on 2026-08-21 and by nothing rented.

**G13. Finiteness is a visited set, not a depth limit.** A file already read in this sitting is not walked again, keyed by its resolved machine location; a chain that comes back round stops there. A chain is recorded to at least nineteen libraries deep and no depth cap is imposed (***Dependencies 13***, which the spec's own sources file names for both the nineteen levels and a location inside a library being measured from that library; **route added 2026-08-23**). What was not covered by the round — a library relocated onto a file another library already records — is not leaned on anywhere here.

### 3.4 The loop, and the sitting surviving the connection — Row 162

**G14. The check is a desktop-driven loop of single-file readings, not one long machine-side operation.** Pass one reads the file the user pointed at. No auditor has seen it.* Blender 5.2 alone can be asked for one level of an unopened file's own links, which shortens the loop by a step and does not remove it (***Reading a file 8*** again, which records that the 5.2 listing still needs the file to be there); **all three routes added 2026-08-23, this clause having named none**; the loop is written for all four versions and 5.2's shortcut is an optimisation Build may take, not a mechanism anything rests on.

**G15. Each reading is one operation with its own operation identity, admitted through arbitration on its own.** There is no unbounded machine-side loop to stop: stopping the check is the desktop ceasing to issue readings, cancelling the in-flight one under Section 9's contract, and letting in-flight transfers end under S26. **G16. **G17. Nothing carries on by itself when the connection comes back.** The loop is driven by the user's sitting; a fresh check starts from what is already known — the record supplies every located answer by K3's keying and the reading re-reads every file, because the record never answers *what does this file need now* (K11).

**G18. A check sitting is partial across files; one reading is atomic.** Declared in Section 10.

### 3.7 The Blender application's own recorded location — Row 171

**G25. **The mark.** The path arrives on an ordinary datablock as a **`library_weak_reference`** — read through `library_weak_reference.filepath`, with `library_weak_reference.id_name` beside it — **and has no datablock in any path-carrying collection.** Observed in both **4.5.12** and **5.2.0**, on a file saved from each Blender's own factory startup touching nothing: `bpy.utils.blend_paths()` returned **two entries**, both the same path into the application's own datafiles (`…/4.5/datafiles/assets/brushes/essentials_brushes-gp_draw.blend` and the 5.2 equivalent), each carried by a Material — `Dots Stroke` and `Material`, with `id_name` `MADots Stroke` and `MAMaterial`. **`bpy.data.libraries` was empty**, and nothing in `images`, `sounds`, `fonts`, `movieclips`, `cache_files`, `volumes` or `texts` carried the path ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)).

- **Whether more than one can exist:** **yes.** Two were present in both versions, **one per datablock, both naming the same file.** **So a deduplicating reader sees one path and a per-datablock reader sees two**, and the exclusion must be written to remove every occurrence rather than one.

Added 2026-09-05, out of round 1 of the code audit of this module.** F9 to F15 are written about a file's name, and no clause here said a directory entry may be a candidate for anything — while [G6](#32-what-the-reading-enumerates--rows-159-and-160)'s folder-shaped kinds and [G24](#36-one-row-standing-for-many-files--row-164)'s sets both need one.

- **A reference whose recorded location names a folder** — G6's folder-shaped kinds — is matched on the **final named segment** of its recorded location, any trailing separator dropped, against a directory entry's own name. A folder has a name, so F9's byte equality and F10's fold apply to it unchanged: a capitals-only difference is *not found* plus a proposal, exactly as for a file. **The walk goes on descending into the entry either way** (F3).
- **A set row's answer is the folder holding at least one entry matching the pattern**, which is [G22](#36-one-row-standing-for-many-files--row-164)'s rule named here as the search's own answer rather than as an expansion taken after one. The pattern's own characters are never a wanted name: nothing on any disk is called by them.
- **K4 does not move.** *"A whole location on the user's computer, as stored on disk"* covers a folder-shaped reference's answer and *"or a folder for a set row"* covers the set's; the narrowing was never this section's.
- **Everything else reads a folder answer as it reads a file's.** F4's first-folder rule, F5's arbitrary pick among candidates, F7's failing folder, and [F18](#44-the-shift--row-167)'s look at the shifted location — which resolves a folder-shaped row where a directory stands there, on the same stored-name reading.

### 4.4 The shift — Row 167

**F16. A shift is derived from one hand-locate: the longest common suffix of whole segments, compared in exact bytes, between the reference's old location and the located file's new location.** Old location `work/project1/assets/textures/metallic.png` and new location `Archive/project1/assets/textures/metallic.png` share the suffix `project1/assets/textures/metallic.png`; what is left is the shift — old root `work`, new root `Archive`. **The root two locations share is that suffix's complement, and a shift reaches exactly the references whose old location sits under the old root** — sibling folders at any depth included, which is the promise; nothing outside the old root, which is *a shift moves what shares a root, not everything*. Where the located file's name differs from the reference's — the user pointed at a renamed file, which the spec allows — there is no common suffix and no shift: locating taught that one answer and nothing more. **The derivation is refused in a second case, on the same terms: where the common suffix is the reference's old location entire and the old root comes out empty.** That is the ordinary shape of a backup or an archive keeping the original tree under a new prefix — old location `/Users/alice/proj/tex/x.png` located at `/Volumes/Backup/Users/alice/proj/tex/x.png`, old root empty, new root `/Volumes/Backup`. An empty old root is one every absolute reference sits under, so the shift would reach all of them and the bound this clause states would be vacuous rather than true: F18 would probe every outstanding reference under the new root, and references belonging to projects the user never archived would resolve to whatever old copies the backup happens to hold, marked as from this shift. So no shift is derived and the locate teaches that one answer and nothing more. **The cost is stated rather than hidden**: a user who archived a whole disk under a new prefix locates once per project root instead of once for the disk, which is F21's ordinary case rather than a new one.

**F17. A shift needs an old location written out in full, so it applies where the recorded location is full, or where the holding file's placement record names where its upload came from** — the relative location is resolved against that source folder and is then full. That is why the shift depends on the record rather than only on the file (K7's source location), and why a file with no known origin (K5) contributes nothing to a shift.

**F18. A shift resolves rows by looking, not by assuming.** Each candidate — old root swapped for new — is checked for a file at the shifted location with the stored-name reading of F12; found exactly → the row resolves, marked as from this shift; found as a case near-miss → offered as a proposal exactly as the search offers one; found not at all → the row stays as it was. The check is over enumerated stored bytes like everything else.

**F19. Every row a shift resolved names the shift record (K6), and the shift is shown as the move it is** — the old location and the new one.

**F20. One action returns every row the shift produced to *not found*.** The undo enumerates by the shift record's key, which every answer it produced carries; a shift application stopped part-way leaves only answers carrying that key, so the undo is complete whether or not the application ran to its end. Declared partial across rows in Section 10, with the shift record as the enumeration.

**F21. A project spread over several roots takes one locate per root, and shifts do not chain** — a later locate derives its own shift from its own pair, never from an earlier shift's output.

### 4.5 An act taken over a selection of rows — Row 427

**F22. An act taken over a selection is N independent acts of that same act, one per row, and never one action with an outcome of its own.** The partition unit is one row and the act inside one row is the single-row act unchanged; Section 10 declares it. Three things follow, and each is a constraint rather than a preference.

- **The write stays per row and stays immediate.** K4 requires each located answer's durable write *"at the moment the user acts, never batched to the end of a sitting"*, and G16 makes the sitting durable as it happens. One write per row as the act reaches it keeps both; one write for the set would break both, for as many rows as the user selected at once.
- **The selection is held nowhere durable.** It is a sitting's own state, run-held as F7's per-folder search outcome is, and it is not a record kind: K1's five kinds are closed and nothing in this subsection adds a sixth.
- **No §9.4 outcome record is written for a selection act, and the reason is that no unit is ever owed.** [State, identity and recovery](State,%20identity%20and%20recovery.md) §9.4 gives an outcome record to an action whose partition unit is smaller than the action, so that *"an interruption cannot lose the fact that a unit was owed"* — the shape `Queue & History` X3's machine-side erase is in, where an unreached unit is a debt standing against a machine. A selection act leaves no debt: a row the act did not reach is a row nothing promised anything about, and its state is exactly what it was. A durable enumeration written before the first row would add a user-held record none of the spec's or Design's promises needs, which is F7's own argument on the same terms.

**The precedent is `Queue & History` L18 and L19, and it is the same answer to the same question.** There is no group store and a group act is member acts under one command; there is no selection store and a selection act is row acts under one command. In both, what has to survive is the members' own records and nothing else.

**F23. A selection act stopped part-way leaves every row it reached decided and durable, every row it did not exactly as it was, and no bulk outcome to show.** No row is ever half-acted, because the single-row act is already atomic (Section 10, *one reference's resolution*). A row whose own act failed names its own reason and holds up nothing — Section 10's sentence for the upload set, and the same rule here. What the panel shows after a stopped selection act is what it shows at any other moment: each row's own state, read from the record. The failures that exist are the single-row act's own — for a proposal accepted or a row located, F12's stored-name reading is taken per row at the moment that row is resolved, so a candidate that moved between the search and the act fails that row alone.

**F24. A capitals-only match is accepted per row and never once for a set.** *(This is Row 427 seen a second time and not a second requirement.)* A bulk accept writes one located answer per selected row that carries a proposal, each naming that row's own candidate; a selected row carrying none is untouched. **No selection act ever changes what counts as a match.** F9's byte equality decides what is found whatever the size of the selection, and F10's fold decides only what is offered — so accepting many proposals is many acceptances of many pairs, never a rule that folds, which would be 4.3's wrong-file harm arriving by the one door that reaches two hundred rows at a time. What is recorded is unchanged: K4's *how it was resolved*, per row, exactly as a singly accepted proposal records it — and K4's rejected guess, kept so it is not put forward again by itself and can be reinstated, is written per row in the same way when a guess is undone over a selection.

**F25. No selection act has a record of its own and none is undone in one action; F20's undo is not the precedent it looks like.** The shift's undo needs a record because **a shift resolves rows the user never picked** — every reference whose old location sits under the old root, sibling folders at any depth included (F16) — so the shift record's key is the only thing that can enumerate them. A selection act reaches exactly the rows the user picked, so the enumeration is the selection itself, and every act in the set has an inverse the spec already grants: bring back against set aside and set aside against bring back, K4's rejected guess reinstated, and a located answer replaced by locating again. Taking the inverse over the same selection is one act by F22 and needs no new record. **What the inverse is not is a restoration of what stood before**: the record holds a mark rather than a history, so a row already set aside before a bulk set-aside is brought back with the rest. The mark is on the row and the panel reads it; no history is kept and none is promised.

**F26. Three acts are not selection acts, and two of the three are already declared.**

- **Locate… has no per-row bulk form, and its reach across rows is the shift.** Pointing many references at one file resolves each of them to a file it does not mean. One hand-locate derives the shift (F16) and F18 resolves every other row under the old root **by looking** — which is the two-hundred-textures case the promise names, taken once. Where a locate is offered over a selection at all, the only reading that points no reference at a file it does not mean is a locate at a **folder**, each selected row resolved inside it by F18's own rule — found exactly resolves the row, a case near-miss is offered as a proposal, found not at all leaves the row as it was — and **no shift is derived**, because the user named a folder and not an old-and-new pair for F16 to take a common suffix from. What is offered is Design's; the resolution is F18's either way. A set row's Locate… points the whole row at a folder and is one row's act (G23).
- **The acts that touch the machine are the per-row acts issued more than once.** A confirmation is Q7 run per row; a *could not be sent* retry is A11's new transfer per row; a *could not be fixed* retry is M16a's own production per row — each with its own operation identity, each a new action rather than a retry inside one ([State, identity and recovery](State,%20identity%20and%20recovery.md) §9.5), each admitted per server (A9). None of them becomes a set. **The one act over many rows that is already declared is the upload set after a check** — Section 10's third row, partition unit one row, partial across rows — and nothing here changes it.
- **Nothing here caps how many rows an act may reach**, because nothing accumulates: N rows is N record writes, or N transfers already bounded by the per-server admission point. How many the panel lets the user select at once is Design's, and the spec parks it.

## 5. The asset area and the landing — Rows 169 and 170

### 5.1 The area and its three subtrees

**A1. The asset area is the sibling area [Job files and outputs](Job%20files%20and%20outputs.md) 1.2 L6 assigns, under the one root, outside every job folder, its contents this document's.** It survives what the root survives: the mount is chosen once for its available space (that document's 1.1), the whole root is handed to the login the supervisor runs as before hand-over (its 1.3, on Fact 6's observation that a rental's second place to write arrives `root:root 755` and refuses the non-root login until a setup step hands it over), and both disks of the volume case survived a stop and a start ([Two more boxes](Two%20more%20boxes%20—%20the%20volume,%20the%20full%20disk,%20and%20a%20day%20left%20running.md), Fact 6).

**A2. Three fixed segments sit directly under the asset area, and their names are constants of this document, deliberately short against the byte budget:** `files` — the mirrored copies; `fixed` — the fixed copies of 6.5; `remaps` — the per-job remap material of 6.4. Keeping the mirrors one segment down is what stops a user path's own first segment ever colliding with a name this document needs for itself.

**A3. A fixed copy is addressed off the machine location of the linked `.blend` it was made from, and never off a mirror location**: the `fixed` segment joined to that file's own machine path taken from the root downward. For the ordinary case — a linked `.blend` this module mirrored — that reads `fixed/<the asset area's own segment>/files/<location>`, so the fixed tree still repeats the mirror tree's shape, one level further down. For a linked `.blend` that is on the machine by any other route — uploaded by hand through `File Browser`, which the spec calls the ordinary way a linked file arrives; pointed at by Q9; or already there with no known local origin (K5) — the same join off its own machine path gives it an address too. **Keying on the machine path rather than on the mirror is what makes every linked `.blend` on the machine fixable, and it is unique by construction**, since two files cannot share one machine path. One fixed copy per linked `.blend` on the machine, shared by every project and job that links it — correct for all of them because the fixing is derived from that file's own references, which are per file and not per project.

**A fixed copy's address passes A5's two byte checks unchanged, and it is the longer address of the two.** Every segment against 255 and the whole path against 4095, in bytes, by Smoozy's own arithmetic before anything is written — and because the address carries two segments more than the mirror does, a linked `.blend` whose mirror fits can have a fixed copy that does not. Where the address will not fit, the row fails as **could not be fixed** with the reason named, on the same terms A5 fails a mirror that cannot fit; nothing is truncated, folded or renamed to make one fit.

### 5.2 The mirror rule — Row 169

**A4. An asset lands at the mirrored copy of its own whole location: the `files` segment joined to the whole location the file came from on the user's computer, from the top of the user's disk downward, as stored on disk (F12), byte for byte.** Creator-stated (2026-07-28) in the spec; what this document adds is the spelling — the stored name, not the reference's — and the prefix. The disk name is whatever the operating system puts in the absolute location: on macOS the location as the system writes it, `/Volumes/<name>` included where the file sits on a named volume; a location from a Windows computer is **permanently unresolved** with the rest of Windows, and Section 12 item 3 carries it. **Corrected 2026-09-02: this clause cited *the spec's own `[PENDING]`* and that marker is gone.** The spec settled it on 2026-09-02 — *"Windows is permanently unresolved… The machine that could have answered it was destroyed on 2026-08-26, and the Creator ruled on 2026-08-31 that there will be no further rental, so it will not now be answered"* — and names this clause and item 3 as where it is carried. **This is not a pending item and must not be read as one, and no reader may leave a space in the code or the record for the answer.**

**A5. The rented machine takes the bytes and refuses only length, and the length check is Smoozy's own arithmetic, run before any byte is sent.** A colon, an asterisk, a question mark, a pipe, a semicolon, letters outside the Latin alphabet, an emoji, a newline, a tab, a leading dash and a trailing space all reached disk unaltered ([Job files and outputs](Job%20files%20and%20outputs.md) N13, which owns this claim); a name over 255 bytes and a whole path over 4095 are refused at open with `Bad message` ([One box with Blender on it](One%20box%20with%20Blender%20on%20it%20—%20the%20reading,%20the%20listing,%20and%20the%20names%20that%20do%20not%20come%20back.md) §7; Fact 29). Names written outside the Latin alphabet survive the crossing whole in all four versions (the spec's answered deal-breaker). Two checks per landing, both in bytes: every single segment against 255, and the whole mirrored path — root, area segment, `files`, then the source location — against 4095. **Both can genuinely fail**: macOS accepts a name of 255 UTF-16 code units, which reached 765 bytes in the one measured case (**Fact 24** — the reading batch of 2026-08-18, [The user's own computer](The%20user's%20own%20computer%20—%20where%20a%20download%20lands,%20what%20it%20will%20take,%20what%20it%20will%20show,%20and%20how%20the%20app%20replaces%20itself.md) §3; **corrected 2026-08-23 from *"Fact 16's batch"*, which named the right batch and the wrong fact — `Download` §15 item 8 and `Desktop app and delivery` C5 both file the figure under Fact 24**), so a legal Mac name can exceed the machine's name budget. A row whose mirrored location cannot fit is **could not be sent**, with the reason named, before any transfer is arranged. Smoozy never truncates, folds or renames to make one fit — a made-up name would break the very thing that keeps two same-named textures apart.

**A6. The assumption the rule rests on — two files on one computer cannot sit at the same whole location — is weighed here and the promise does not fall with it.** The sources file records it as having no source in this project; if it were simply trusted and wrong, two different files would land on one name and the module's central promise would fail silently. It is not simply trusted. At one moment on one computer the assumption is what a path means; every way it is stressed in practice — the same location holding a *different* file at a later time, or a second computer of the user's carrying a different file at the same location and uploading to the same machine — lands on a mirror location that is already occupied, and Q5's comparison reads the difference and Q8's warning fires before the write. So where the assumption holds the rule is clean, and where time or a second computer breaks it the contents comparison catches the collision before it becomes a silent replacement. Checked against Method's escalations and not one: no promise fails and nothing new reaches the user. Section 13 records the check.

**A7. Mirror directories are created with the plain create-directory form, segment by segment, and an already-standing segment is the ordinary case rather than a fault.** N9's rule is kept — never the make-parents form, whose silent success against an existing folder is the recorded collision path. Unlike a job folder (N10), a mirror folder is *meant* to be shared by every asset beneath it, so a refusal of the plain form is resolved by one follow-up attribute read: where the path now exists as a directory, the landing proceeds; anything else fails the row as *could not be sent*. The refusal-then-read is safe against Smoozy's own concurrency because this module never removes a mirror directory (Section 8), so a directory seen standing stays standing.

**A8. Every machine-side path this module touches travels as protocol fields, never through a shell line.** The one-space-in-a-folder-name breakage — three tools broken three different ways on one box ([The rented machine](The%20rented%20machine.md)) — was tool- and quoting-level; mirrored user paths carry spaces, newlines and quotes as a matter of course, so file operations go through the file-transfer subsystem's length-prefixed fields or the package's own request fields, and nothing composes a command line with a user path spliced into it.

### 5.6 The handed unit from `File Browser` — the entry point

**A18. The occupied landing path is what the offer was made about, and it is never the act's destination.** A4 is this module's one landing rule and the act takes no second one: the destination is the mirror of the crossed source path, whatever the walk found occupied. The two name one source location in the case the offer is made in — the user's own copy re-sent over its own mirror — and where they do not, the file lands at its own mirror and the occupied file keeps the contents and the records it had; nothing about it is made silently wrong, and V3's warning and the collision question's own Replace are the routes to it that already exist. **For a unit of class *fixed* the two never coincide, and that is right rather than a miss:** a fixed copy's address begins at the `fixed` segment and no transfer of this module's ever publishes to one — a fixed copy is only ever produced by M14 (A3, M13) — so an occupied fixed copy is replaced by step 3's rename, which reaches that same address exactly where the crossed source path is the source location the copy at that address was derived from.

### 6.1 What is already decided, and what is left

### 6.2 What the remap material says

**M4. The remap material for a job is a list of pairs, each pair naming a reference of the top file and the machine location it is to read from.** A pair carries: the data-block kind and the setting that holds the location; the recorded location's **expected bytes**, exactly as the check read them, **and the pair's match text, derived from those bytes by [M4a](#62-what-the-remap-material-says)'s one rule** — the bytes are what the record holds and what everything else on the desktop compares (G3a), the match text is what the pair is matched on and nothing else uses it; and the new location — the mirror location of the resolved asset (5.2), or the **fixed copy's** location where the reference is a linked `.blend` (6.5), or the machine location of a file already up that the reference was pointed at (Q9). Pairs cover the top file's direct references only: everything below the top was fixed where it sits, which is what keeps the depth manageable — nothing is arranged per level at render start. **A library pair never names a copy that has not been fixed.** Where the reference is a linked `.blend`, the new location is that file's fixed copy (A3, 6.5) whichever route the file arrived by — mirrored, uploaded by hand, or already on the machine and pointed at under Q9; the third alternative above is for ordinary assets and never for a `.blend`.

**M4a. A pair is composed and matched on path text alone — never on the file's bytes and never on a checksum — and the text is compared with separators normalised to forward slashes. Added 2026-08-31 on Fact 128, answered 2026-08-30; label: observed in a test.**

- **The rule, exactly.** The match text of a value is that value with **every backslash — byte `0x5C` — replaced by a forward slash, byte `0x2F`**. That is the whole of it. **Nothing else is changed and everything else is compared verbatim**: the leading `//` blend-file shorthand stays, a doubled separator stays doubled, a `..` step stays, letter case stays as recorded, a trailing space stays, and no Unicode form is normalised, no path is resolved or tidied, no folding of any kind is applied (F9's discipline, held here as everywhere). The pair's match text is derived once, at composition, from the expected bytes the check read. At render (M8) the same replacement is applied to the value the data-block's setting currently holds, and the two match texts are compared **byte for byte**; equal is a match and anything else is not.
- **Why the separator has to go.** **Opening a `.blend` re-spells the separators in a recorded place toward the opening machine's own convention, and a plain save then writes that re-spelling into the file** — on Mac and on Linux a backslash becomes a forward slash, and **on Windows it runs the other way and is much larger: every forward slash in a recorded place becomes a backslash, with only a handful of places spared.** Nothing else in the recorded text moves. **So a user checking a file on Windows and a rented Linux machine rendering it read the same recorded place differently.** Composed and matched on the expected bytes exactly as read, **every pair of such a file misses at once**, every one is reported *not applied*, the render finishes and reports success — the silent wrong render this module exists to prevent, and now established rather than feared.
- **What the normalisation costs, said rather than smoothed.** A backslash is a legal character in a file name on Mac and on Linux, so this rule cannot tell such a name from a Windows separator. **Blender's own re-spelling already destroys that distinction** — the same open that would carry the name re-spells it — so the rule gives up nothing that was reliable, and it gives it up in one named place instead of in whichever place a builder happened to compare.

**M5. Every pair is applied by the per-setting route, in every version, and no bulk route and no one-pass route is used for any part of it.** The per-setting route is the one route proved to reach every recorded location in the fixture, write locations included, in all three exercised versions, read back off disk by a separate process (Fact 77). The one-pass route is absent in 4.5.9 outright, and in 5.0.1 and 5.2.0 it rewrote the images, the text and the library and **silently left every write location alone** — nothing raised, nothing printed, the save succeeding. It reaches the read locations this module remaps in 5.x, but one route across all four versions is one mechanism to be wrong about instead of two, and the route that is silently partial for the redirect is not given a second chance here.

**M6. The material is composed per version and names the version it was composed for**, exactly as the redirect's half is (D7, D8) — the property carrying a File Output node's folder is `base_path` in 4.5.9 and `directory` in 5.0.1 and 5.2.0, and the same discipline is assumed for every setting the remap writes: the setting names are resolved per version at composition, never guessed at run time. 5.1 is inferred across the version boundary and not observed (G4).

**M7. A pair whose target setting holds a curly-brace template is never composed** — templates live only in the render output path and the File Output node, both write places outside this module's pairs — and no pair is ever composed for a path held in a custom property, because the check never finds one (G7).

### 6.3 How the pairs take effect in the running Blender

**M8. The material applies each pair whose match text is found, reloads what needs reloading, reports every pair in the marker, and fails nothing quietly.** **A pair names a kind and a setting, which is a property path rather than an instance, so it is applied to every data-block of that kind whose named setting currently matches the pair's match text under [M4a](#62-what-the-remap-material-says)'s rule — not to one.** That is the reading, and K3's keying is what makes it safe: two references inside one holding file recording identical bytes are one located answer and one row, so they are one pair and want one answer. The marker reports how many data-blocks each pair was applied to.

In order, for each pair: the current value of the named setting is read in the running Blender, on every data-block of the pair's kind; **each one whose value, put through M4a's separator rule, equals the pair's match text** is assigned the new location; **for a library, the assignment is followed by the reload, because assigning a library's path changes what is recorded at once and leaves the old data in place until the library is reloaded** — observed in all four versions, on the rented Linux machine alone, with the relocate command doing both in one act as the alternative form, which is the form Blender's own repair path uses on a broken library. **What that observation is of, exactly, is a library that loaded and was then re-pointed** — *old data in place* is data that resolved — and the case this module is in is the opposite one: at launch the load resolves the top file's own recorded values, the library path names the artist's computer, nothing loads, and the material then re-points what the load did not resolve (Section 11). **Whether assignment plus reload populates a library that never loaded is ANSWERED, positively, in both versions — 2026-08-22, Fact 101 ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)), and Section 12 item 17 closes.** At load the library was genuinely unresolved — `Warning: Unable to open '…/orig/lib.blend': No such file or directory`, `Info: Cannot find lib`, `LIB: Object: 'LinkedThing' missing`, `is_missing=True`, and the linked object present as an `EMPTY` with `data = None`, **which is the state a remapped file is in and not a working library being re-pointed**. **After assigning the path with no reload: `('LinkedThing', None, -1, -1)` — still nothing.** **After `library.reload()`: `('LinkedThing', 'Cone', 4, 4)` and `is_missing=False`**, and the mesh is the alternate library's cone rather than the original's plane. **So the reload is required for a library and it works on one that never loaded** — and the image kind needs no reload at all ([M9](#63-how-the-pairs-take-effect-in-the-running-blender)), which is the per-kind difference this pair of questions was written to find. Where no data-block of the kind matches — the file was edited and re-uploaded with a reference re-pointed — the pair is **not applied and is reported in the marker as not applied**: the reference now records a different location, the remembered answer no longer belongs to it, and the spec's own rule is that such an edit is an addition the next check has to resolve, covered by the submission warning rather than by a guess here. A reference matching no pair is left exactly as recorded. The marker (D16) carries every pair's outcome — applied and to how many data-blocks, or not applied with the value found — on the render's own captured stream, so what the remap did is readable after the fact with nobody connected. **That is also what makes *not applied* honest**: it means zero data-blocks of the kind matched, a countable fact, rather than an unidentified miss.

**M8a. What an ordinary save does to a reference the artist never touched is now established, it moves the recorded place in two ways, and neither is announced. Added 2026-08-31 — Fact 128, answered 2026-08-30, ***Dependencies 20***; label: observed in a test. This clause replaces the assumption M8 used to close on, which said an ordinary save leaves an untouched reference's recorded bytes alone and that this was not established. It is established, and it is false.** A plain save over the same file with nothing touched writes almost every recorded place back character for character — a `//` shorthand, a full path, a `..` step, a doubled separator, the wrong letter case, a name outside the Latin alphabet, a name with a space, a trailing space, a place pointing at nothing — and **two things move.**

- **The separator, which M4a's rule is written for.** The re-spelling happens when the file is *opened* and the plain save writes it in: backslash to forward slash on Mac and Linux, and on Windows every forward slash to a backslash but for a handful of places. **Matched on M4a's match text, a pair survives it**, in either direction and on any of the three machines.
- **A data-block nobody is using is dropped at the save, taking its recorded place with it — a second shape, and a different one.** An image with no users and no fake user disappears at a plain save in every version on all three machines, and the weak reference beside it goes too; a fake user preserves it. **That removes the place outright rather than re-spelling it**, so no normalisation can rescue it: the pair for that reference finds **zero data-blocks of its kind at all**, and it is reported *not applied* exactly as M8 already provides. **So *not applied* now has a known and benign cause**, and a builder must not read every *not applied* as a re-pointed reference: it means the pair matched nothing, which covers an edited reference, a dropped unused data-block, and nothing else that has been established. The user's own file is unharmed either way — the render is missing what the artist had already stopped using.
- **What a builder must not reach for: a whole-file comparison, or a checksum, says nothing about whether a recorded place moved.** The separator re-spelling and the dropped data-block both move the file's bytes while the places the pairs care about may be untouched, and both leave places moved while other bytes stand still. **The two questions are independent and only the path text answers the second one** — which is why M4a matches on text and why nothing anywhere in this module decides a pair's fate from a digest. The digest comparisons of Section 2 answer *is this the same file*, which is a different question and stays theirs.

**M9. Answered for the image kind and unanswered for five others, and the per-kind difference the question was written to find is real. Corrected 2026-08-22; this clause used to say the whole of it was untried.**

**The image kind: assignment alone is enough, in both versions, proved by render rather than by a flag.** Fact 99 ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)). The fixture was built so that **its recorded locations were absent at load** — the folder they name was renamed away — which is the state every remapped file is in and the case item 1's own recipe insists on; the original texture is pure red and the alternate, which exists, is pure green; everything but the textured plane was hidden, because an occluding object returns black and makes every reading meaningless, **which happened on the first attempt**.

| | 4.5.12 and 5.2.0 |
|---|---|
| as loaded, original absent | `[0.741, 0.400, 0.745]` — **the missing-texture colour** |
| **after assigning the new path, no reload** | `[0.145, 0.557, 0.000]` — **green** |
| after `image.reload()` | `[0.145, 0.557, 0.000]` — unchanged |
| control: a freshly loaded datablock in the same slot | `[0.145, 0.557, 0.000]` |

**So for an image the material assigns and does not reload**, and the control proves the colour is what a correct read looks like rather than a coincidence.

**M9a. And one flag must never be read as the test of whether the remap worked. Added 2026-08-22, and it is sharp.** **`image.has_data` reported `False` throughout** — before the assignment, after it, and after the reload — **while the render was reading the file correctly.** **Anything that gates on it, or reports from it, will call a working remap broken.** The marker reports what was assigned ([M8](#63-how-the-pairs-take-effect-in-the-running-blender)) and never what a flag says about it.

**M9b. Five kinds are not posed and are not claimed.** **Cache file** — the datablock had no user after the import and was dropped on save, so it was not present at load to be tested. **Sound** — assigned and read back correctly, but a sound has no render to observe, so *is it in force for the render* cannot be asked of it at all. **Font**, **movie clip** and **volume** — not posed; Blender's default font is built-in and carries no path, and no external font, movie or volume fixture was built. **Nothing above extends to them**, and item 1 stays open on their account.

**M9c. What is left of this clause, for the kinds nothing has answered.** The spec's own sources file states it: *for anything but a library, whether a write is enough on its own is still untried*. The proven observations bracket it from one side only: a rewrite in the running Blender shows in the running Blender (D5's ground), and a **saved** rewritten copy rendered with its rewritten **write** locations in force — ten files under the new folder and the artist's folder tree never built (Fact 77's render check) — **but that check reports nothing about a read reference resolving, and no observation anywhere renders from an in-session rewrite of a non-library read location.** **What breaks if the assignment alone is not enough for some kind**: that kind's reference still reads the artist's location, finds nothing, and the render finishes at success with the thing missing — the silent wrong picture this module exists to prevent. **What holds**: the library case *for a library that loaded and was re-pointed*, which is what was observed and is not the case a remapped file is in (M8, Section 12 item 17); that the assignment is recorded at once, which the marker reads back; the mechanism's shape, which **takes a per-kind reload step by one edit if a builder ever learns a kind needs one** — a property of the shape, and **not a space kept for an answer, because no per-kind answer is coming** (Section 12 item 1, permanently unresolved on the Creator's ruling of 2026-08-31; corrected 2026-09-02, where this read *the moment the per-kind answer exists*); and the marker, which records what was assigned — and now, per applied pair, whether assignment alone is established for that pair's kind ([M9d](#63-how-the-pairs-take-effect-in-the-running-blender)). The fact is described for the runner in Section 12 item 1, and this document does not close it by assertion.

**M9d. The marker names, per applied pair, whether assignment alone is established for that pair's kind. Added 2026-09-02, and it costs no reading of its own.** The marker (D16) already carries every pair's outcome — applied and to how many data-blocks, or not applied with the value found ([M8](#63-how-the-pairs-take-effect-in-the-running-blender)) — on the render's own captured stream, readable afterwards with nobody connected. It now carries one further field on each pair that **was** applied: **established** for the image kind (Fact 99 — assignment alone, proved by render and not by a flag, [M9](#63-how-the-pairs-take-effect-in-the-running-blender)) and for the library kind with its reload (Fact 101, M8); **not established for every other kind** — the five [M9b](#63-how-the-pairs-take-effect-in-the-running-blender) names, cache file, sound, font, movie clip and volume, and the further kinds whose rewrite is inferred rather than watched ([Section 12](#12-unresolved) item 2). The field is composed from the pair's kind alone, so a kind nobody has posed reads *not established* by construction rather than by omission.

**What the field claims:** that the assignment was made, and that its sufficiency for that kind was never observed. **What it does not claim:** that the render read the wrong file, or that anything failed — an applied pair of an unestablished kind may well have worked, and nothing here declares a fault. **No second reporting channel is opened**: it is a field of the marker M8 already writes, exactly as the applied/not-applied outcome is, and where the kind is established nothing extra is said at all. **So a finished render that is wrong because a kind silently needed a reload becomes readable after the fact instead of silent**, which is what the fact itself can no longer be made to do — the answer for those kinds being permanently unresolved ([Section 12](#12-unresolved) item 1). **[M9a](#63-how-the-pairs-take-effect-in-the-running-blender)'s rule stands over it**: the field reports from the pair's kind and from what was assigned, never from `image.has_data` or from any flag of the kind.

### 6.4 Where the remap is kept, and Smoozy going away — Rows 174 and 177

**M10. One remap-material document per job, immutable, in the asset area at `remaps/<job identity's textual form>`, placed through the transfer contract — staged, integrity-checked, published by one rename — before the job's submission material is published.** The manifest carries the reference to it ([Job files and outputs](Job%20files%20and%20outputs.md) M1) and a re-run reads the manifest, so the chain at a restart with nobody connected is: manifest → remap reference → remap material on the machine's own disk → launch material composed on the machine. Nothing in that chain needs a connection, which is Row 177's requirement met by placement rather than by hope. Composition happens on the desktop, from the record, at submission — the located answers and the landing rule give the pairs.

**M11. The placement and the submission are one ordered unit**: the material is placed first, and where the placement fails the submission is **not attempted**, naming the material as the unit that stopped it ([State, identity and recovery](State,%20identity%20and%20recovery.md) §9.3). A job therefore never exists with its remap material missing, and `Rendering`'s Row 2 whole-or-nothing is joined rather than weakened. Immutability mirrors the manifest's: a later check, a later upload and a later sitting change nothing in a submitted job's material; the next submission composes the next document.

**M12. What Row 177 inherits and does not repair**: the re-run itself is the machine's, and on a full state mount the supervisor cannot start; after space is freed, the container heals by itself while the systemd unit did not recover merely because space was freed — Fact 1's disk-full form, answered no ([The last two boxes](The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md)). Where the supervisor cannot run, no re-run happens and the remap material sits unread; `Rented-server runtime` carries the condition. The reboot and crash halves are answered yes on both machine kinds, so the material's survival story is the disk's — which is 5.4 A13's, shared with every asset.

### 6.5 The two copies of a linked `.blend` — Row 175

**M13. Every linked `.blend` the check resolves gets a fixed copy — whichever route put it on the machine — and the render is made to read the fixed copy; the copy the user sent up survives untouched where it lies.** The two halves of the row pull against each other — the fixing is written into the file, and the file the user uploaded is never written — and two copies is the only arrangement that satisfies both. **Whichever route** means all of them: mirrored by this module, uploaded by hand through `File Browser` before any check was run, pointed at under Q9, or on the machine with no known local origin (K5). A3's address covers each of those because it is taken off the file's own machine path. The top file's library pair (M4) points at the fixed copy's address; a fixed copy's own library references point at other fixed copies; every other reference in a fixed copy points at mirrors. So the whole tree below the top file reads Smoozy's versions, and every user copy stays byte-identical to what was uploaded.

**M14. A fixed copy is produced on the machine, by a worker driving the job's Blender, from the machine copy of the linked `.blend`, and published by one rename.** The machine copy is the mirror where this module placed the file and the file's own machine location where it is on the machine by any other route — the same copy A3's address is taken off. The steps: **open the machine file headless**; rewrite each resolved reference by the per-setting route to its mirror or fixed-copy location; **save the result to a staging path as a copy, with the save-time relative-remapping turned off**

**REPAIRED 2026-09-04, by the builder writing this document's acting half at Build step 7, and the struck words are the whole of what changed. They read: *"copy the machine file to a staging path; open the copy headless; rewrite …; save …"*.** **The step that is gone is the copy, and it could not be built.** A copy of a file from one place on a rented machine to another is a machine-side act, and this stage establishes no route to one: the file-transfer surface has no copy operation, so a copy taken through it reads the whole `.blend` down to the desktop and writes it back up — two crossings of the connection for a file the spec's own measured case is 669,966,622 bytes ([Q2](#2-telling-two-files-apart-by-what-is-inside-them--row-168)) — and a copy taken by naming a program on the command channel rests on **which programs an arbitrary rental carries**, which is [`File Browser`](File%20Browser.md#13-unresolved) Section 13 item 9's unestablished ground and the widest such ground in the stage. **Neither is a route, and inventing the second one would be inventing a fact.**

**What replaces it needs no copy and no program.** Blender's own save takes the file to write as an argument and takes a flag that leaves the opened file alone — *"Save Copy, Save a copy of the actual working state but does not make saved file active"* (`bpy.ops.wm.save_as_mainfile`'s `copy` argument, Blender's own published Python API reference, read 2026-09-04). So the worker opens the machine file, rewrites in the running Blender, and **writes the fixed copy straight to the staging path**; the rename then publishes it exactly as before.

**Three things this changes and each is stated rather than left to be noticed.** **M2's never-written promise is kept the same way and is not weakened**: nothing saves over the machine file, the rewrite lives in the running Blender and reaches no file on disk unless something saves it (D5), and the one save this act performs names a different path. **The relative-remapping flag matters more rather than less**: the save's own documented condition is *"Remap Relative, Remap relative paths when saving to a different directory"*, and writing the copy to a staging path **is** saving to a different directory, so the trap this clause was already written against is the ordinary case here and turning the flag off is what stops it. **And the atomicity of [Section 10](#10-atomic-or-partial--this-documents-declarations) is untouched** — staged, saved, published by one rename, or nothing — because what changes is which act writes the staged file and not that the staged file is published by one rename.

*(The struck wording follows for the record: **copy the machine file to a staging path; open the copy headless**; rewrite each resolved reference by the per-setting route to its mirror or fixed-copy location; **save with the save-time relative-remapping turned off**)* — saving remaps paths relative by default, and a save that was allowed to do so would silently rewrite locations nobody asked to change (Fact 77's first recorded trap; the second — from 5.0, adding an output to a File Output node rebuilds its socket list — is recorded for anything that composes node values, though the fixing adds no output); digest the result; publish by rename into the address A3 gives it. The fixing record (K8) is written at publication with what the fixing points at.

**M15. Uniformity is deliberate: every linked `.blend` gets a fixed copy even where its references all resolved to *nothing to change*.** One rule, no conditional targets, and the top file's library pairs never have to know which case they are in.

**M16. A changed linked `.blend` replaces its fixed copy only after being checked, and the old copy stands until the new one is published.** The new version arrives through this module (the spec's rule), is checked as any file is, its fixed copy is produced staged, and one rename replaces the old — the old copy readable to the last moment, the replacement whole or not at all. Rename-boundary behaviour is answered on ext4, xfs and overlayfs with no part-arrived bytes at a final name at any boundary (Fact 78, the interruption boundaries, 2026-08-18).

**There are three replacement triggers, and the second is the file standing still while its own references move.** The first is the one above; the third is [M16b](#65-the-two-copies-of-a-linked-blend--row-175)'s, added 2026-08-23. The second: **a fixed copy is re-produced whenever the located answers for its holding file differ from the list of (reference bytes → machine location) pairs the fixing record (K8) holds for it** — the record's list is the comparison, and the comparison is made whenever a check runs over a file whose tree holds that `.blend`. A reference located by hand in a later sitting, one a shift resolved, a rejected guess reinstated, a reference re-pointed at another copy: none of them changes a byte of the linked `.blend`, so the first trigger cannot fire, and without the second the fixed copy the render reads would still record the artist's own locations for everything resolved after it was produced — a render that finds Smoozy's versions for the references resolved early and the artist's computer for the ones resolved late, at success, silently. The production is the same act with the same atomicity as the first trigger's — staged, saved, published by one rename (Section 10) — and the fixing record is rewritten at publication. **V11 leans on this**: a row inside a linked `.blend` is confirmed only where that file's fixing record matches the current located answers.

**M16a. A *could not be fixed* row is tried again on its own, and the retry is M14's production run once more for that one file — no check re-run, nothing re-sent. Added 2026-08-21, per Row 405.** [Design](../Design/Dependency%20Upload%20&%20Remap.md) puts a Retry on that row and requires it *"without re-running the check or re-sending what already arrived"*, which the spec grants both failure states. **5.3 A11 is written for transfers and does not reach this**: a *could not be fixed* row is a fixed copy that could not be produced, not a file that did not cross.

- **The retry needs nothing the sitting holds.** M14's inputs are all durable and all already in place: the machine copy the fixed copy is derived from — the mirror this module placed, or the file's own machine location where it arrived by another route (A3) — the located answers in the record (K3, K4), the address A3 computes, and the pair list the fixing record holds (K8). **None of them is a product of the check**, so the retry re-reads no `.blend`, arranges no transfer, and asks nothing of the desktop but the record.
- **Running it again is safe because the production is atomic and the old copy stands.** [Section 10](#10-atomic-or-partial--this-documents-declarations) declares producing or replacing a fixed copy atomic — staged, saved, published by one rename — so a retry either publishes a whole fixed copy or leaves what was there; a production that did not reach publication leaves no fixing record and nothing at the address.
- **It is one operation and it holds up nothing.** The fixing is [Section 9](#9-machine-side-operations--declarations-and-termination)'s third shape, admitted on its own with its own operation identity, and Section 10 declares the set after a check partial across rows: *"A row's failure names the row and holds up nothing"*.
- **A retry that fails again leaves the row as it was, and the reason it names does not have to change.** The row's state comes from the fixing record and the publication, never from an attempt, so it can never be quietly turned into a success — A11's sentence, on this side of the split. Two reasons are stable by construction and a retry reproduces them exactly: an address that will not fit A5's two byte checks (A3), which is the same arithmetic over the same bytes; and a machine copy no longer at the location the fixed copy is derived from, where the production has nothing to open. **Neither is turned into a different row state by the retry.** It is the next check, not the retry, that re-establishes what is on the machine and turns such a row back into one to send.
- **The retry is M16's act rather than a fourth mechanism.** It publishes by the same rename and rewrites the fixing record at publication, so V11 reads its result exactly as it reads a replacement: a row inside that `.blend` is confirmed only where the fixing record matches the current located answers.

**M16b. The third replacement trigger: the machine copy a fixed copy was derived from is published over. Added 2026-08-23, routed out of Row 428.** M16's first trigger is a changed linked `.blend` arriving **through this module**; its second is the located answers moving while the file stands still. **Neither reaches a `.blend` that is on the machine by another route being published over** — uploaded by hand through `File Browser`, or there with no known local origin (K5, A3, M13) — because the file changed and the located answers did not; and V3's plain-upload warning does not fire on it either, its trigger being *placed or fixed* and that copy being neither. - **The trigger.** A fixed copy is **owed a re-production** whenever the content identity last published at the machine location K8 records it as derived from differs from the content identity K8 records for that copy. **Both values are already in the local record** — K8's own, and the publishing act's, which is a placement record's (K7) or a published transfer record's ([Server protocol and transfers](Server%20protocol%20and%20transfers.md) S9, which `File Browser`'s hand-uploads carry) — so the comparison is a record against a record, made by the module that published at the moment it published, on exactly the footing V13's replaced-since-check mark is already written on. **Nothing reads the machine and nothing is inferred from a file's presence, name or size** (V15, Q10). **Every publication has a content identity to compare**: it is the transfer's own pass-through digest taken as the bytes pass, beside the size (Q1, S22), so there is no publication this comparison cannot be made against.

It is a row of the check the disturbance mark sends the user back to, like any other. **Warning at the upload instead is refused**: it would put a warning in front of the user about a file this module did not place, which no spec grants, and `File Browser`'s W1a has already declined the class.
- **V11 reads this trigger with the other two.** A row inside a linked `.blend` is confirmed only where that file's fixing record matches the current located answers **and** no M16 trigger has left its re-production owed.

**M17. The fixed copy remains what *other* files' renders read through their library references.
