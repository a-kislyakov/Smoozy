## Deployment shape

Smoozy has two deployment trust domains: the user’s computer and each rented server.

### The user's computer

One desktop application contains every feature module and the shared desktop services they call. Its responsibilities are:

- the UI and the application process;
- the durable local record, including saved servers, history, settings, suppressed warnings, transfer arrangements, and the server state the specs explicitly allow it to remember;
- **the diary — the rolling plain-text record a bug report is cut from. Added 2026-08-29 at the stage close: this list had no line for it, so the placement was decided in [Reporting a problem](#19-reporting-a-problem) R2 instead, and that clause is cited here rather than re-taken.** It is a fifth durable **non-state** thing on this side, beside `Desktop app and delivery` L2's four, and not a row inside the local record; the diary service is its one writer.
- operating-system adapters for files, secure secret storage, notifications, menus, updates, and application identity;
- SSH connection control, reconnect policy, transfer scheduling, and the client side of the server protocol;

There is no always-running local daemon. Work that must continue with the desktop application closed runs on the rented server. The updater may use a short-lived helper when the running application cannot replace itself; its platform-specific lifecycle belongs to [Desktop app and delivery](#7-desktop-app-and-delivery). **Fact 74 is answered on all three systems, by three different mechanisms.** macOS replaces the **complete signed `.app` bundle at the installed path** and never a member inside it, on Apple's own sealing rule ([Desktop app and delivery](#7-desktop-app-and-delivery) Z5). Windows installs the new build side by side and stops then relaunches. Linux installs a **signed, dependency-declaring package through the distribution's own package mechanism**; a raw executable copied over an old path is not a Linux release or update route ([Desktop app and delivery](#7-desktop-app-and-delivery) E4 and Z10). **The macOS and Linux clauses were narrowed on 2026-08-22, and the register paragraph carrying both is `Facts.md` Fact 79's narrowing paragraph — corrected 2026-08-29 at the stage close, where this read *`Facts.md` Fact 74 carries both narrowings*.** Fact 74's own entry carries the macOS half only and points onward with *"the same correction is recorded at Fact 79's narrowing paragraph"*; its Linux paragraph is unnarrowed and still argues the update route from `rename(2)`, which is the route this document stopped taking. Fact 79's `rename(2)` answer underwrites ordinary data publication on Linux rather than the arrival of a new version. Row 280 breaks only if the user must independently discover, fetch, or initiate the update, or must remember to perform it later. A prompt during an update the app initiated is Design's, bounded by the platform fact and the security rules.

The desktop application reaches a rented server through SSH. It does not expose a listener to the server and does not require the rented server to call the user's computer.

The same surface carries one narrow, versioned bootstrap-and-repair request independent of the supervisor's machine-local endpoint. The whole commit is blocked while any work accepted under either retained protocol version is live, held, uncollected or unacknowledged, and the caller is told that the upgrade is deferred for that reason.

After hand-over, the versioned SSH command adapter and supervisor control every queue, job, and worker command. Transfer data moves on its own SSH channels; the supervisor controls the staging area, publication step, and cleanup through a transfer-support worker. `Server protocol and transfers` defines one transfer staging-and-publication contract in both directions for the whole of the machine's life: part-arrived bytes never sit at the final name; integrity and resume are measured against staged material; publication is the last step; and abandoned staging is cleaned up. The pre-package surface performs that contract before hand-over, the transfer-support worker performs it afterwards, and the contract does not change at hand-over. If the supervisor does not answer while SSH is live, command callers report the supervisor as unavailable without marking the server connection down, inspect the package, and the desktop application automatically invokes the bootstrap-and-repair request under the same commit and rollback rules. Server Setup's user-facing re-run is the fallback if automatic repair fails. Browsing, file operations, readings, and transfers remain available; the pre-package surface carries transfers through publication and cleanup under the same contract while the supervisor is unavailable.

The supervisor-unavailable state is a failure condition under the [whole-app failure rules](../Specs/Whole%20app.md#concerns-that-span-the-whole-product). `Rented-server runtime` supplies the condition and `Desktop app and delivery` presents it against the server, clearing it when the supervisor answers again. The server connection remains up.

`Server protocol and transfers` owns the pre-package surface, hand-over, and the versioned bootstrap-and-repair request. `Rented-server runtime` owns the complete package placement, boot-registration, health, commit, rollback, repair, and replacement transaction. `Server Setup` owns the user-facing fallback re-run.

Server Setup installs the core Smoozy server package containing three executable classes or roles, plus a separately enabled Telegram role whose material placement belongs to Server Setup under Row 91:

1. **Server supervisor.** One long-lived service controls the machine-local queue, durable job state, event journal, worker identities, and local command endpoint. The machine's boot service facility starts it after a reboot and restarts the supervisor after an unexpected exit. The endpoint is reachable only by the login Smoozy holds; the supervisor rejects a request from any other local identity. **Fact 84 answers the mechanism on both machine kinds:** peer credentials read from the kernel on the accepted connection of an `AF_UNIX` stream socket, which the caller cannot forge. `Security and licence` owns this local access boundary, and `Rented-server runtime` implements it as owner of the endpoint.
2. **SSH command adapter.** A short-lived command invoked through SSH authenticates by the SSH connection, frames one versioned request, passes it to the supervisor over a machine-local endpoint, and returns the correlated result. The supervisor does not expose a second remote control port.
3. **Operation workers.** The supervisor starts render, file-inspection, setup, transfer-support, preview, and media workers as separate child processes. Every worker is attached to one recorded operation or job identity. Its recorded runtime identity names the complete supervised execution group: the worker and every external process it starts for that operation. A worker is never discovered or stopped by executable name, command-line pattern, or process search.
4. **Telegram worker.** This is a supervisor-hosted role worker. The supervisor starts, restarts, and stops it from durable enabled-or-disabled desired state. Server Setup has two entry points for the separately enabled role: preparation installs its material when Telegram is on; the dedicated Telegram entry point makes the role available on a machine prepared earlier. Both set the durable desired state requested by Telegram, enabled or disabled, and neither starts or stops the process directly. The second does not re-run the rest of setup, restart the machine, or disturb a running render. Whether the role's material was placed during the earlier setup and is only enabled later, or is placed by the second entry point, belongs to Server Setup under Row 91. The worker sends that machine's reports and submits phone actions to the same supervisor command path used by the SSH adapter. It never signals a render directly. `Telegram` settles the single receiving slot and cross-machine routing on the receiving call, which answers everything that module needs on any rental; no licence-service responsibility is added to make that routing work. A rented server never holds another rented server's connection identity and never opens a connection to another rented server. The Telegram conversation is the only channel between machines, and cross-machine routing is settled inside that limit.

No rented-server component binds an inbound listener except under the Telegram webhook route, which `Telegram` J1 makes an optional path that nothing in that document needs. The receiving route is a per-bot choice, not a rental requirement. The webhook route is available only where a machine can host the endpoint; where none can, the exclusive receiving slot remains the route, and no rental becomes ineligible for Telegram or for Smoozy. Under the webhook route, only the machine currently holding the registered webhook binds the endpoint. No other prepared server binds a listener. The endpoint belongs only to the Telegram worker, authenticates every request, reaches the supervisor command path only through the worker's existing command route, and is an additional exposed machine boundary owned by `Security and licence`. **Fact 63 closed provider-shaped rather than against the route.** Telegram's page constrains the URL to ports 80, 88, 443 and 8443, and a rental whose ports its provider's own allocator assigns cannot name its own mapped port in one — so on such a rental nothing binds an inbound listener and the receiving slot is the route. **No conflict with the receiving-slot fallback arose and nothing returned to Specs:** the asking route works on every rental, so no rental became ineligible. **Fact 63's remainder is one item rather than three — corrected 2026-09-02, this line having named all three as uncovered.** The webhook POST wrapper and the `X-Telegram-Bot-Api-Secret-Token` header were **answered by reading** Telegram's own *Bot API* page that day, so the one exceptional inbound endpoint carries a documented authentication and neither was ever a rental question. **The retry cadence against a failing endpoint is the third and it stands open**: the same page gives no interval, no count and no window, and Telegram's webhook guide says nothing about retries at all, so **no reading will ever close it**. **It is not swept in with the permanently unresolved items and this is deliberate** — what settles it is a run against an address that answers nothing, needing no rental, no provider and no certificate of this project's own, so its route is open even though nobody schedules it. It blocks only the optional route, which no build takes until it closes (`Telegram` §21 item 5), and it blocks nothing on this map, the receiving slot being the route on every rental.

The server supervisor is the only writer of the machine-local queue and job journal. Workers report observations to it; the desktop application and Telegram worker submit commands to it. This serialization boundary prevents two callers from independently changing the same job and answers Row 53's race between a desktop answer and a phone answer.

The supervisor persists intent before acting. Every deliberate stop records durable desired state first, then validates that the complete recorded execution group still belongs to the intended operation before issuing its worker-kind termination. Reconciliation after a supervisor crash or machine reboot may resume only work whose durable desired state still permits it. `Rented-server runtime` owns a machine-level durable *setup in progress* state that holds reconciliation back; Server Setup sets and clears it through the same command path. Per-operation workers use the four operation outcomes: resumed, re-run once, left stopped, or given up. Role workers instead use durable enabled-or-disabled desired state. The Telegram worker is the only role worker; the supervisor restarts it for as long as it remains enabled, records and reports repeated failure rather than silently giving up, and never resurrects it after it is disabled. A per-worker restart policy remains forbidden: only the supervisor is boot-restarted, and it decides every worker outcome from durable state.

Termination and cleanup are per-worker-kind contracts owned by the document that defines the worker. Each contract names which member of the recorded execution group receives its signal. Rendering owns `SIGINT` delivered to the recorded render process rather than to the render worker. The render worker remains until its external processes have exited, or is terminated only after them. Server protocol and transfers owns transfer-support termination through staging and cleanup. Server Setup owns setup termination at, or recovery from, a recorded safe boundary. No signal or cleanup contract is universal across worker kinds.

Each command has an operation identity. Each caller waiting for a state transition has its own deadline and reports expiry without changing the operation's durable state. There is no shared assumption that a successful signal means the worker has already ended.

The server package and its state live outside every job folder. Each job has an immutable submission manifest and a distinct working folder. Exact paths, commits, atomic publication, output redirection, remap material, and cleanup belong to [Job files and outputs](#5-job-files-and-outputs).

Every viewable derivative is produced once on the rented server. The preview worker produces the still copies; the media worker produces the moving picture and contact sheet. Queue & History fetches and holds the copies used on the user's computer and produces none of its own; Telegram reads the same derivatives. They are throwaway material, and Job files and outputs owns when both the machine-side derivatives and fetched copies are cleared under the local lifetimes State, identity and recovery defines.

No user action removes the server runtime. The only machine-reaching server removal stops work, clears pending jobs, and removes Telegram's role under the Servers and Telegram specs; the runtime remains. Runtime removal is only an internal step of package upgrade or replacement and exposes no user action. The complete package commit, including pointer switch, boot-registration activation, health exchange, rollback, and old-package removal, is blocked while any work accepted under either retained protocol version is live, held, uncollected or unacknowledged.

## Constraints established by the shape throwaway

The feasibility evidence and its limits have one home: [Batch A — the shape throwaway](Batch%20A%20%E2%80%94%20the%20shape%20throwaway.md).

- **Observed on the Batch A machine:** detached work survived the SSH disconnect, durable queue state was read from a later connection, and a boot-registered service resumed after reboot.
- **Observed on the Batch A machine:** a later connection and a process on the same machine could each issue `SIGINT` to a recorded target.
- **Observed constraint:** the restart policy that recovered work also restarted it after a deliberate stop. The architecture therefore boot-restarts the supervisor and lets durable desired state control workers; it never gives a render worker an unconditional restart policy.
- **Observed constraint:** pattern matching selected more than one process and failed to stop the intended worker. Every stop therefore uses the runtime identity recorded when that worker was started and validates that it still belongs to the intended operation.
- **Observed constraint:** the stop took effect on the worker's next cycle. Every waiter therefore has a deadline; no caller infers completion from signal delivery.
- **Observed at promise level under Fact 1, on both machine kinds:** the supervisor returned after reboot and crash and reconciled the durable held-job, running-job and role-worker state. **The disk-full form is answered no:** the supervisor cannot start on a full state mount; the container heals when space returns, while the systemd unit requires a plain start after space is freed.
- **Observed at promise level under Fact 2, on both machine kinds:** every tested stop reached Blender itself rather than a shell or the worker, and nothing restarted the render.

[Facts](Facts.md) records Facts 1 and 2 as answered at promise level; no Batch E re-run remains pending.
