**Three observations run through everything below and none is softened.**

- **The danger is never the machine going away; it is the caller's own connection failing.** Observed — a machine closing politely and a machine powered off from a provider's console were both announced **in the same second**, keepalives making no difference, while the caller's own line pulled was detected in **56 seconds** with keepalives on and **not detected at all for 21 minutes 45 seconds** with them off ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 57). **The machine had not learnt within the five minutes it was watched** — it held the socket open with the job still running. **Corrected 2026-08-21: this said *never learns at all*, and that is wrong by the manual of the software being observed.** The box ran `tcpkeepalive yes`, and `sshd_config(5)` (macOS 26.5 man page dated 2025-10-04, read on the Creator's Mac 2026-08-20) states *"The default is yes (to send TCP keepalive messages), and the server will notice if the network goes down or the client host crashes."* It would have noticed on the kernel's own defaults — kernel.org `ip-sysctl`, read 2026-08-20: `tcp_keepalive_time` *"Default: 2hours"*, then `tcp_keepalive_probes` 9 at `tcp_keepalive_intvl` 75 s, *"connection will be aborted after ~11 minutes of retries"*; and where the machine has anything to send, `tcp_retries2` *"yields a hypothetical timeout of 924.6 seconds and is a lower bound"*. The observation ran 5 min 10 s ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), *findings-hyperstack*), so it measured nothing about that ceiling. **Nothing below changes**: two hours, or fifteen minutes, is no use to a caller either.
- **The machine sends no application-level keepalive of its own, and that is OpenSSH's shipped default rather than this provider's choice.** Observed — `clientaliveinterval 0`, `clientalivecountmax 3`, `tcpkeepalive yes`; the box's own file carried `#ClientAliveInterval 0`, commented out. `sshd_config(5)`, read 2026-08-20: *"The default is 0, indicating that these messages will not be sent to the client."* The TCP keepalive above **is** on and is two hours slow. *"So keeping an idle connection open is still the caller's job, and the reason is the one that is off rather than a machine that sends nothing at all"* ([The rented machine](The%20rented%20machine.md) §5). **Corrected 2026-08-21**, following its source `The rented machine.md` §5, which had flattened both keepalives into *switched off* and was itself corrected on 2026-08-20.
- **A container rental's recycle destroys everything Smoozy installed and comes back on the same address and port with nothing in the connection to reveal it**, in about 90 seconds against 15–20 for a reboot, and *"A Smoozy that reconnects and finds its address answering has no signal that its whole installation is gone. It must check for its own state, not for reachability"* ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), *Recycle*).

## 1. The connected period

**Constraint:** Row 29, quoted at the head of this document, and [State, identity and recovery](State,%20identity%20and%20recovery.md#3-desired-state-and-observed-state) §3's D1 — *"Every controllable thing has exactly one durable desired state, written by exactly one writer, and separately zero or more observed readings. They are never one field"* — whose own table already names the connection: desired state is *"the connected period on the desktop (`Servers`)"*, observed is *"connected, reconnecting, disconnected"*.

### 1.1 The period and the connection are two things

**S1. A connected period is the desired state for one server's connection, and the live connection is an observed value of it.** They are never one field, and no reading of the connection ever writes the period. That is D1 and D2 applied, and D2 is the whole of why a drop does not end a period: *"No desired state is ever inferred from an observed reading."*

**S2. A period is per server, and one server's period touches no other's.** Connecting or disconnecting one server changes nothing about another, and several periods stand at once. Nothing anywhere holds a count of periods, a global connection state, or a shared connection.

**S3. A period is held in process memory for the life of the application run and is written nowhere durable.** That is what Row 25's *every server starts disconnected* requires ([6.6](#66-every-server-starts-disconnected-by-construction)), and it is consistent with [State, identity and recovery](State,%20identity%20and%20recovery.md#3-desired-state-and-observed-state) §3's D6, which makes a crash and a clean close leave the same durable state: there is no durable connection state for either to leave.

**S4. A period holds, and holds nothing else:** the local server identifier it belongs to; the moment and the act that opened it; the *restarting, caused by Smoozy* mark where `Server Setup` has set one ([4.1](#41-the-mark-taken-rather-than-decided)); the current observed value and the repair state below; and the connections open under it ([1.4](#14-the-additional-connection-and-it-is-the-only-one-a-period-may-hold)). Every other thing that lives for a period's length is **period-held** under [State, identity and recovery](State,%20identity%20and%20recovery.md#111-five-classes-and-the-reason-there-is-no-sixth) §11.1 and is that section's, not a field of the period.

### 1.2 The closed list: two period-opening acts, two replacements, one additional connection, six endings

**S5. A period begins at exactly two moments and the list is closed. A period begins at the act.** It begins the moment the act is taken and never when the connection becomes live, whatever that connection then does. That is D2 applied — a period begun on a live connection would be a desired state inferred from an observed reading, which is the one inference D2 forbids — and it is why a period whose opening connection never becomes live is ended by item 5 of [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) rather than never having begun.

| # | The act | What begins |
|---|---|---|
| **O1** | **The user's connect action** on a saved server, including a connect carrying a remembered setup ([Section 7](#7-the-remembered-setup-bit-row-26)) | one period, and one connection under it |
| **O2** | **An add with a setup option ticked**, which the spec makes connect right away to carry the setup out | one period, and one connection under it. When the setup ends the server stays connected, so the period stands until the user disconnects or the run ends |

**S6. A connection under a standing period is replaced at exactly two moments and the list is closed.**

| # | The act | The period |
|---|---|---|
| **R1** | **Repair after an unintended drop** ([Section 3](#3-repair-rows-30-and-31)) | stands throughout, including while the drop is unrepaired |
| **R2** | **The return after a restart `Server Setup` caused** ([Section 4](#4-the-restart-server-setup-caused-row-32)) | stands throughout, carrying the restart mark |

**S7. R1 and R2 are the two the spec names, and the additional connection is not a third of that kind: it is a list of its own, of one.** Row 29 says Smoozy may replace the connection underneath the period *"in two cases, and only these two"*, and the table above is that kept literally. The additional connection replaces nothing: it opens a second connection beside the primary one to the same machine inside a period the user already opened, because a machine permitting too few sessions leaves **no other route this project chose** to a transfer channel — **corrected 2026-08-22: this said *no other route*, and one exists.** Several transfers can share one subsystem channel, which [Server protocol and transfers](Server%20protocol%20and%20transfers.md#61-a-transfer-is-a-channel-and-the-channel-is-independent-of-the-command-channel) T1 established on 2026-08-21 and names as the fallback where a cap is too low for one channel per transfer; isolation is that document's declared route rather than a necessity, and the additional connection is what buys it here. It is an **addition inside a standing period** and never a replacement and never a period-opening act, and it is bounded in [1.4](#14-the-additional-connection-and-it-is-the-only-one-a-period-may-hold).

| # | The act | The period |
|---|---|---|
| **R3** | **The additional connection at a low session cap** ([1.4](#14-the-additional-connection-and-it-is-the-only-one-a-period-may-hold)) | stands; this adds a connection under it and replaces none |

**S8. The edit put-back is not in any of the three lists, and [Section 5](#5-the-edit-put-back-row-39) is why.** The edit's save disconnects the server, which ends the period; the put-back is O1 performed by Smoozy as part of the user's own act of saving. So the replacement list stays exactly two, and a failed put-back leaves no period to repair — which is what makes the spec's *"the server is left disconnected with the new details saved"* true by construction rather than by an exception in the repair.

**S9. The acts of the three tables above are the ones that reach a machine — O1 and O2, R1 and R2, and the additional connection R3 — and nothing else reaches one. Two cases are named because they are where the rule does real work.** **A removal of a disconnected server never starts a connection and never asks for a passphrase** ([6.5](#65-what-a-removal-reaches-row-41)). **Nothing watches keys in the background** ([9.3](#93-at-the-list-row-46)) — the usability check is a local read taken when the list is drawn, and it never reaches a machine, so it is not an open at all.

**S10. A period ends at exactly six moments and the list is closed.**

1. **The user disconnects**, which is available for as long as a period stands, including while the server reads as reconnecting or as disconnected between runs of attempts. Taking it stops the repair.
2. **The application run ends**, however it ends.
3. **The edit's save on a server whose period stands** ([5.1](#51-the-edits-disconnect-ends-the-period-and-the-put-back-opens-a-new-one)).
4. **A break is declared while the server's key is not usable** ([9.2](#92-during-a-connection-row-34)), because the repair Row 33 forbids could never run and a period whose repair cannot run promises what Smoozy cannot deliver.
5. **The connection the opening act was to make never became live.** S5 begins the period at the act, so where the connection that act was to make never becomes live, the period ends there — including where the attempt was abandoned by a step of [Q1](#10-the-first-connection-in-order-rows-36-and-35)'s sequence, and including where [P3](#91-before-a-connection-row-33) meant no attempt was made at all. **This ending is written against the opening act's own connection and reaches no replacement**: a repair attempt that fails and a return after a restart that fails are both attempts under a period that already stands, and neither is this.
6. **The server row is removed**, at the moment the removal's **local forget** is performed and not at the moment it is asked for. **Added 2026-08-22, scenario replays Pile 1 item R21.** [W25](#115-stop-and-clear-and-what-it-says-when-it-only-partly-worked-row-42) makes the local forget the removal's last unit, *"atomic entire … and only on the user's word"*, so on the machine-reaching removal the period must stand through the clear-and-stop pair and Telegram's role off, both of which reach the machine over the connection it holds; on a removal that reaches no machine the forget is the whole act ([Section 14](#14-declarations--atomic-or-partial)) and the period ends with it. **Nothing ends on the request**: [W21](#115-stop-and-clear-and-what-it-says-when-it-only-partly-worked-row-42)'s *try again* and *try the remainder again* leave the row standing, and a period ended at the request could carry neither.

**And the removal must end it, which is the argument for the sixth item.** [N13](#33-the-three-places-repair-does-not-run-at-all) makes repair a property of a standing period and of nothing else, so a period left standing after its row is gone goes on opening connections at [N2](#31-a-run-and-the-two-figures-in-it)'s cadence for the rest of the run, to a machine the user has just told Smoozy to forget — and [D19](#65-what-a-removal-reaches-row-41)'s *"Removing a disconnected server never starts a connection"* would then be broken by the repair rather than by the removal.

**A failed run of attempts is not on that list**, and that is Row 31's *repair does not stop for good* kept by construction: nothing ends a period on a count.

### 1.3 What the period holds and what ends with it

**S11. Every period-held thing ends the moment the period ends, however it ends.** [State, identity and recovery](State,%20identity%20and%20recovery.md#111-five-classes-and-the-reason-there-is-no-sixth) §11.1 names them: the last-known queue reading, every live reading, and the machine password held for a connection. §11.2 already fixes that the application run ending is one way a period ends and not the only one, so a period ended by a disconnect or by an edit drops them then. **Two inputs class the third of them differently and both are cited here rather than one:** §11.1 puts *"the machine password held for a connection"* in the period-held class, while `Security and licence` [§2](Security%20and%20licence.md#2-the-five-held-things) item 3b writes it against *"the connection, not the connected period"*. [S12](#13-what-the-period-holds-and-what-ends-with-it) follows §2 item 3b, and [Section 16](#16-unresolved) item 17 records the seam with both sentences quoted.

**S11a. So ending a period by hand while a repair is running drops the last-known queue reading with it, and with that the removal warning's source. Added 2026-08-22, scenario replays Pile 1 item R30.** A **repairing** server takes the connected menu whose first slot reads *disconnect* ([K8a](#22-the-three-observed-values-and-what-servers-supplies)), and taking it is [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 1 — the period ends, the repair stops, and S11 drops the last-known queue reading and every live reading. **The consequence is stated rather than left to be met**: the server moves out of [W19](#115-stop-and-clear-and-what-it-says-when-it-only-partly-worked-row-42)'s third row and into its last, so a removal taken afterwards warns about nothing and offers a plain confirmation. [Section 16](#16-unresolved) item 18 is the same consequence read from the other side.

**Nothing is said to the user before the act, and nothing here supplies a fact for saying one.** `Preparation/Specs/Servers.md` grants the disconnect during a repair as *"the ordinary disconnect"* with *"No separate action is needed for it"*, so a statement before it would be a new thing in front of the user rather than this document's answer. [Section 17](#17-moments-that-reached-the-creator) records the check.

**S12. A drop does not end a period, so nothing period-held is dropped by one — except the machine password held for a connection, which is connection-held under `Security and licence` [§2](Security%20and%20licence.md#2-the-five-held-things) item 3b and does not survive the connection that took it.** That is the rule `Queue & History` [C6](Queue%20&%20History.md#11-one-job-two-records-two-lifetimes) reads from the other side — the last-known queue reading is *"gone when the period ends — and the period is `Servers`' connected period, which runs until the user disconnects or the application closes, standing through a drop"* — and it is what lets a dropped-connection server go on showing last-known entries for the rest of the run. **The exception reaches the password and nothing else**: the connection that took it has ended, so it is asked for again where it is next needed, which is `Security and licence` §2's arrangement and the same one [E4](#51-the-edits-disconnect-ends-the-period-and-the-put-back-opens-a-new-one) states on the edit path.

**S13. Nothing durable is written from anything period-held**, which is D4. The three exceptions D4 names are not this section's to widen, and the one that belongs to this document — the remembered server state the spec names — is [Section 8](#8-the-hardware-reading-rows-27-and-28)'s and carries its installation identity.

### 1.4 The additional connection, and it is the only one a period may hold

**Constraint:** `Server protocol and transfers` [T2](Server%20protocol%20and%20transfers.md#61-a-transfer-is-a-channel-and-the-channel-is-independent-of-the-command-channel) and [T5](Server%20protocol%20and%20transfers.md#62-concurrency-and-one-admission-point-rather-than-one-per-server). `MaxSessions` is per connection and may be one — documented at [T2](Server%20protocol%20and%20transfers.md#61-a-transfer-is-a-channel-and-the-channel-is-independent-of-the-command-channel), `sshd_config(5)`, macOS 26.5 man page dated October 4, 2025, read 2026-08-17. At that learned cap, **the primary connection carries one alternating lease: its reading subsystem closes after the current framed reply when a command waits, the command takes the one session, and reading reopens afterwards; no transfer can take that lease. Every transfer uses an additional authenticated connection that remains transfer-only for its life.** `Servers` owns opening and replacing those connections and consumes that division unchanged.

**S14. Decided: a connected period may hold one additional connection to the same server, opened for transfer channels alone.** Its conditions are exact and it fires nowhere else.

**At `MaxSessions 1`, the primary and additional connections have different permanent roles.** The primary alternates its sole session between browsing readings and command invocations under `Server protocol and transfers` T5; a queued command prevents another reading from beginning and takes the session as soon as the current framed reading reply completes. The additional connection never alternates: it carries transfer channels only, and no command, package inspection, installation-identity read, queue read or browser reading can be admitted on it.

1. **It is opened only on a refused channel admission**, and only where the per-server admission point `Server protocol and transfers` [T5](Server%20protocol%20and%20transfers.md#62-concurrency-and-one-admission-point-rather-than-one-per-server) has learned that the primary cannot seat a transfer without consuming its reading/command lease. A machine at the documented default of 10 never reaches this rule; a machine at `MaxSessions 1` reaches it at the first transfer.
2. **It carries the same four connection details, the same key and the same host-trust decision.** The host key comparison of [10.1](#101-host-trust-comes-first-and-the-scan-decides-row-36) is per attempt and the remembered identity is per server, so both connections are compared against the one record and neither can be trusted on terms the other was not.
3. **It is a connection Smoozy makes on its own, so [9.1](#91-before-a-connection-row-33) binds it entire**: where the key is not usable, or needs a passphrase Smoozy is not holding, it is not attempted, and the transfer is reported as unavailable on this connection rather than failed.
4. **It carries no command channel and no reading channel, and it is never used for a request.** Correlation, the installation identity, the queue reading and every command stay on the primary connection.
5. **It is opened at the first refused admission and closed when the last transfer on it ends.** It is never held idle.
6. **The connection condition of [2.2](#22-the-three-observed-values-and-what-servers-supplies) is derived from the primary connection alone.** Losing the additional connection is a transfer interruption under `Server protocol and transfers` [S26](Server%20protocol%20and%20transfers.md#78-cleanup-and-the-five-ways-a-transfer-ends) and never a connection break; losing the primary connection ends both, and the repair rebuilds the primary first.
7. **One is the cap, and the reason is that the rule is a remedy rather than a pool.** Two connections give two session pools; a third would be Smoozy tuning throughput by opening connections, which Fact 25's measurements already say buys nothing — *"a whole second rented machine bought about 20%, not 100%"* — and which nothing in any spec grants.

**S15. Where the cap is 0, no session of any kind is permitted and Smoozy has no route to the machine at all.** The connection is reported as one Smoozy could not use, with no claim about why. This is a machine Smoozy cannot work on and it is not a case this rule covers. **What the server is left reading as follows from [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 5**: a connection Smoozy has no route on never became live, so the period the opening act began ends there and the server reads **disconnected**.

## 2. Holding the connection up, and learning it has ended

**Constraint:** Row 29's *"nothing in between may let it lapse unremarked"* and *"How the connection is held open, and what keeps it alive, is Architecture's to work out"*; Row 30's *"Smoozy has to learn of the drop by itself"*; and [State, identity and recovery](State,%20identity%20and%20recovery.md#85-the-connection-condition-needs-a-break-reported-without-using-the-connection) §8.5, which is a requirement on this document and not a decision it retakes: *"the connection's observed value must come from a mechanism that reports a break without the caller having to use the connection first."*

### 2.1 The break-reporting mechanism

**K1. The connection is held by the SSH transport Smoozy itself drives, and that transport is the supplier of the connection's observed value.** It is the same transport `Server protocol and transfers` [R5](Server%20protocol%20and%20transfers.md#82-the-enforcement-point-is-smoozys-own-byte-loop-and-the-evidence-forced-it) puts the byte loop inside, so the mechanism below is Smoozy's own and not a flag handed to a tool.

**K1a. No command-line SSH client is invoked for this connection, so no option handed to one governs it. Ruled 2026-09-02 by the architecture runner, against `Security and licence` [§4](Security%20and%20licence.md#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it).** [K1](#21-the-break-reporting-mechanism) says the mechanism is *"not a flag handed to a tool"* and leaves what that excludes to be inferred; this clause states it. **Smoozy opens, authenticates, holds up and tears down this connection inside its own process, on the SSH transport it drives** — the same transport `Server protocol and transfers` [R5](Server%20protocol%20and%20transfers.md#82-the-enforcement-point-is-smoozys-own-byte-loop-and-the-evidence-forced-it) puts the byte loop inside, S15 drives the rename extension over and T5 counts `MaxSessions` against, and the same one [1.4](#14-the-additional-connection-and-it-is-the-only-one-a-period-may-hold)'s second connection and [K3](#21-the-break-reporting-mechanism)'s keepalive are properties of. **No `ssh`, `sftp` or `scp` process is run for it at any moment.** So `IdentityFile`, `BatchMode`, `SSH_ASKPASS_REQUIRE`, `ServerAliveInterval` and every other client option are not mechanisms of this document: each configures a program this architecture does not run, and a builder reaching for one has found this clause rather than a gap. **What the connection is given instead is a value on a call** — the private key file's path at authentication (`Security and licence` [§6](Security%20and%20licence.md#6-the-private-half-of-an-ssh-key) P1's *holds a path and a fingerprint*, which is a value handed to the transport here and not a flag), and K3's interval and count as figures of Smoozy's own driving.

- **What this does not reach.** `Keys`' local readings genuinely do run `ssh-keygen` as a subprocess and their flags are that document's (`Keys` [Section 1](Keys.md#1-what-binds-this-before-anything-is-decided)); nothing here touches them, and nothing here says a tool is never run — only that none is run to make **this** connection.
- **[Section 16](#16-unresolved) item 3's answer stands as a fact and stops being a mechanism of this document.** Batch mode suppressing a private-key passphrase prompt is a property of the command-line client, so the second line of defence that item named is not available here — and it is not needed. A transport Smoozy drives asks nobody anything: there is no terminal, no helper and no prompt route in the process at all. **[P1](#91-before-a-connection-row-33) to [P3](#91-before-a-connection-row-33)'s *the attempt is never made* is the whole defence**, which is what that item already says the promise rests on.
- **What was owed elsewhere, and it was paid the same day.** `Security and licence` §4 R3 **prescribed** this same connection's construction as *"no controlling terminal, `SSH_ASKPASS_REQUIRE=never`, and `BatchMode=yes`"*, and R2 **routed** a key passphrase to *"the SSH client"* through askpass — both describing the command-line client rather than the transport this document drives. **That document's R0, R2 and R3 were corrected on 2026-09-02 to follow K1, and the correction is made.** R3 now reads *"The construction is the transport itself, and the promise is structural rather than configured"* and states that *"nothing in this stage now sets `BatchMode`"*; R2 splits the passphrase's consumer by connection against local read; R2a states the four rules bounding the in-process unlock and what it costs. [Section 16](#16-unresolved) item 25 records the closure. *(Past-tensed 2026-09-02 at the stage-close gate repair: this bullet went on stating as live a prescription its own ruling had ended hours earlier in the same document.)*

**K2. Two things report a break and neither requires the caller to have work to do.**

- **An announced ending.** The far end closing the connection, or its own service closing the socket as it shuts down, arrives on the transport as a close. Observed — a machine closing politely and a machine powered off from a provider's console were **both told to the caller in the same second**, *"keepalives making no difference"*, because *"A provider's stop is an orderly shutdown, not a power cut"* (Fact 57).
- **A caller-side keepalive that goes unanswered.** The transport sends its own keepalive request on the connection at a fixed interval and counts the unanswered ones. This is what covers the case the announced ending does not, and it is the case that matters: **the caller's own line failing**. Observed — the same event was detected in **56 seconds** with keepalives on and **not detected at all for 21 minutes 45 seconds** with them off (Fact 57). The machine will not do it: *"clientaliveinterval 0 … Keeping an idle connection open is the caller's job"* ([The rented machine](The%20rented%20machine.md)).

**K3. The figures, and what they are derived from.** The keepalive interval is **15 seconds** and the unanswered count is **3**, and **the break is declared when three consecutive keepalive requests have gone unanswered and one further interval has elapsed** — so the declaration lands **between 45 and 60 seconds** after a break that fell anywhere in an interval. The third thing is stated because the two figures alone do not fix the bound: without it, whether the elapsed time since the break is 30-to-45 seconds or 45-to-60 turns on a timing rule nobody wrote down. It is this document's rule to state and it is stated here.

Three constraints fix them and none is any one machine's measured cost.

- **It must be far below the silent case's cost.** Twenty-one minutes and forty-five seconds of a caller believing a dead connection is a slow one is the harm §8.5 exists to prevent, and one minute is not it.
- **It must be far above what one exchange on the user's own line costs.** Observed — [Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 25, 2026-08-15/16, in that document's own words: *"most of the gain is hiding a flat 1.0–1.4 s connection setup rather than adding bandwidth."* **Connection setup is the upper bound and it contains a round trip rather than being one**, so a keepalive exchange on that line costs less than 1.4 s, which is more than ten times inside a 15-second interval. Three unanswered requests fifteen seconds apart cannot be produced by ordinary latency there. **Struck 2026-08-23, and the constraint stands without what was struck.** This bullet gave a round-trip figure in milliseconds and quoted three verbatim strings for it, all attributed to a file named `findings-connection.md`, 2026-08-15/16. **No such file exists under `Preparation/`**, Fact 25's own home carries throughput, concurrency and sharing figures and no round-trip latency at all, and every one of those strings occurred in this document and nowhere else in the project. **They are struck rather than repeated; the struck words are kept in `Preparation/Architecture/Sources/Servers.sources.md` §3.1 with what went and why.** **What is lost is the round-trip number and the hundredfold margin it claimed.** **What holds is the constraint, on the setup figure above** — which is the figure this bullet cited before **2026-08-21**, when it was corrected for being called a round trip. It is not a round trip and it is not called one here. **Nothing in K3 is derived from either**, which is what this list's own opening sentence already says.
- **It must not be so tight that a busy connection declares a break under its own traffic.** The count of three is what absorbs a single lost keepalive on a link carrying a transfer at the negotiated maximum write of 261,120 bytes per operation.

**K3a. The count is kept even where the transport cannot send its keepalive. Added 2026-10-02 by Build, step 10c's check-before-0.1.7 fix piece 1.** K3 assumes a keepalive request goes out at each interval. **On a line that goes silent under an upload it does not**: the transport sends from the same loop that keeps the count, that loop waits until the socket takes everything it was given, and a silent line never takes it — so no request is sent, none is counted, and K3's window never closes. Observed in a test at the desk, through OpenSSH's own server, in five silences of six; and on the Hyperstack check before 0.1.7, where the row read *connected* over a connection that was gone. **So the break is also declared where the line has carried nothing either way for the whole of K3's window — the interval times one more than the count, measured from the last thing carried** — which is the moment the transport's own count declares at when it is free. **Carried means a byte read from the machine, or a byte the socket took from the transport**: a full socket taking bytes is the machine acknowledging them. It is the same break, with K2's second bullet's name; the figures do not move, and nothing is sent to learn it (K10, `Server protocol and transfers` C18).

**K4. A keepalive is a request on the connection and never a ping.** `Server protocol and transfers` [C18](Server%20protocol%20and%20transfers.md#46-per-waiter-deadlines) is exact — *"no health check in this document pings"* — and Fact 57 is why: *"one provider answers no ping at all"* while its connection works perfectly, **so any ping-based health check would report it dead**. The keepalive here rides inside the connection Smoozy holds and is answered by the same transport that carries the work, so a machine that answers no ping is unaffected.

**K5. A break declared is a break, and the connection under it is torn down rather than kept for later.** Observed — a ten-minute silent gap left a connection **unrecoverable even after the path was restored**, almost certainly because the provider's address translation forgets faster than the protocol does, *"though the actual timeout was not established"* (Fact 57). So the repair of [Section 3](#3-repair-rows-30-and-31) always **builds a new connection** and never resurrects one, and nothing anywhere waits on an old connection coming back to life. **Tearing down a connection already known to be dead — by the repair, or by the user's disconnect — sends nothing on it, not even Smoozy's own disconnect message: nothing at the far end would hear it, and a message queued behind a stalled transport can wait for good.** Added 2026-10-02, ruled by the build runner; no auditor of this document has seen it.

**K5a. And the address the new connection is built to survives an hour of complete silence, which is the half K5 could not speak to. Added 2026-08-25, the scenario replays' unchecked fact U2.** **Observed** ([The Pile 3 batch](The%20Pile%203%20batch%20%E2%80%94%20a%20full%20mount%20under%20a%20running%20supervisor,%20an%20interrupted%20heavy%20frame,%20and%20an%20hour%20of%20silence.md) §4): a rental left running and touched by nothing at all for **3623 seconds** answered on the same host and the same port on the first packet, and it was the same machine — the marker written before the silence, the boot identifier unchanged, and a process started before the silence still alive with an unbroken heartbeat. **The two observations are about different things and do not disagree.** K5's ten minutes is about **one held connection** dying and not coming back; this is about **the provider's address mapping** still routing a fresh connection to the same machine. So N6's *runs continue for as long as the period stands* has a real address to build to for at least an hour of silence, where before nothing said it did. **The bound is exactly one hour, on one provider, on one rental.** It sets no upper limit, says nothing about a rental that stops and restarts, and does not touch [Section 16](#16-unresolved) item 5's remaining half — whether a seller later hands the same address to a **different** machine. Label: **observed in a test**.

### 2.2 The three observed values, and what Servers supplies

**K6. The connection's observed value has exactly three values and the set is closed:** **connected**, **reconnecting**, **disconnected**. They are what [State, identity and recovery](State,%20identity%20and%20recovery.md#83-the-condition-identity-and-who-supplies-each-observed-value) §8.3's table already names against this document, and this document does not add a fourth.

| Value | When |
|---|---|
| **connected** | a period stands and its primary connection is live |
| **reconnecting** | a period stands, its primary connection is not live, and an attempt is in flight — including while a connection is being opened or closed by hand |
| **disconnected** | no period stands; or a period stands with **no run of attempts in flight**, which is the stretch between one run and the next |

**K6a. This table's second value has been read wrongly once and promised wrongly once, and both are recorded here because the same sentence caused both.**

- **The misreading, corrected 2026-08-21 per Row 347, and the correction was one word.** The *disconnected* row read *"no attempt in flight"* and then glossed itself *"the stretch between one run of attempts and the next"*, and **those two are not the same stretch** — the 15-second pause inside a run has no attempt in flight and is not between runs. [N7](#32-the-standing-repair-which-never-ends-while-the-app-is-open) had already ruled it the other way in plain words, so **a run is in flight for its whole length, its in-run pauses included**, and the table says so. Nothing else moved: the set is still three, the transitions are still the transport's, and no presentation changed.
- **The promise, corrected in the spec 2026-08-22 on the Creator's ruling, and this table did not move for it.** `Preparation/Specs/Servers.md` used to promise the user a **two-state flicker** — *disconnected* between one run of attempts and the next, *reconnecting* again the next time Smoozy tries — which is this table read as though it were a label. **It is not a label.** These three values are the **connection condition's**, supplied under [K7](#22-the-three-observed-values-and-what-servers-supplies) and drawn by nobody; what a repairing server shows the user is [K8a](#22-the-three-observed-values-and-what-servers-supplies)'s steady *repairing* presentation and `Desktop app and delivery` [M29](Desktop%20app%20and%20delivery.md#167-row-347-presented-a-repair-that-says-when-it-next-tries)'s steady *Reconnecting…*. **The two documents are no longer each declaring their own answer**: the spec was changed to say what the app shows, and the flicker the retired sentence described exists only as this value moving where nothing reads it. **Nothing in this table, in the set of three, or in the transitions changed**, and T13's could-not-restore notification still fires on the value reaching *disconnected* after a failed run — which is what the ruling deliberately kept.

**K6b. The observed value lags a break by the declaration bound, and no presentation may claim a currency a reading's own moment does not support. Added 2026-08-22, scenario replays Pile 1 item R2.** [K3](#21-the-break-reporting-mechanism) declares a break between 45 and 60 seconds after it fell, so a server can read **connected** for up to one interval-and-count over a connection that is already dead. Nothing shortens that — tightening the figures is what K3's own constraints forbid — and nothing anywhere reads the value as a statement about a reading's freshness: a reading's currency comes from its own moment ([H2](#81-three-states-and-the-cheap-implementation-has-two), H2a; `Queue & History` [C7](Queue%20&%20History.md#11-one-job-two-records-two-lifetimes)), never from the observed value standing beside it. **And the spec concedes a lag rather than forbidding one, which is the whole of the reconciliation.** `Preparation/Specs/Servers.md`'s [*Connecting*](../Specs/Servers.md#connecting) section, detection paragraph, label **settled at Architecture** (2026-08-23), records that a failed line is learned of only by asking — so that spec's true-state sentence is a claim about what the list shows and never a claim of instantaneous knowledge, and a Build-stage reading of it against this clause finds a lag the spec itself grants, not a shortfall. **Corrected 2026-08-29: this sentence, added the same day, rested on that paragraph's number instead of its mechanism**, calling *"in under a minute"* the spec's *settled figure* and the lag *inside the spec's own bound*. **That figure is not a bound**: it is Fact 57's single measurement, one rental, 2026-08-16, with the keepalive interval and count behind it never recorded, and [Section 16](#16-unresolved) item 11, [K3](#21-the-break-reporting-mechanism)'s own *"Three constraints fix them and none is any one machine's measured cost"* and `Preparation/Architecture/Sources/Servers.sources.md` §3.1's *"no figure in K3 is derived from these numbers"* all refuse it as a standard. **The containment was false at its endpoint besides** — K3's window closes at exactly sixty seconds, which is not under a minute. **Nothing moves with the correction**: the mechanism half is what the reconciliation always rested on, and the figure is dropped rather than replaced, because nothing here needs one.

**K7. Servers supplies that value and the transitions, and presents neither.** The condition record is [State, identity and recovery](State,%20identity%20and%20recovery.md#82-a-condition-record-is-a-derivation-never-a-copy) §8.2's derivation; it holds over *disconnected* and *reconnecting* and is withdrawn on *connected*. `Desktop app and delivery` [T13](Desktop%20app%20and%20delivery.md#133-the-four-kinds-and-what-composes-each) presents it and raises the could-not-restore notification **from that record and not from a request failing**, which this document keeps by supplying a value that moves on the transport's own report rather than on any request's outcome.

**K8. *restarting* is a fourth presentation and not a fourth observed value.** `Server Setup` [T6](Server%20Setup.md#8-the-restart) supplies it *"as a state, not a wording"*. It is composed from the period's restart mark standing while the observed value is *reconnecting* or *disconnected*, so §8.3's table stays exactly as written. [4.3](#43-no-condition-record-stands-while-the-mark-does) settles what happens to the condition record under it.

**K8a. *repairing* is a fifth presentation on the same footing as K8's fourth, and it is supplied rather than inferred. Added 2026-08-21, per Rows 348 and 347.** [K6](#22-the-three-observed-values-and-what-servers-supplies)'s *disconnected* covers two situations a screen must tell apart — **no period stands**, and **a period stands with no run of attempts in flight** — and they take opposite first slots in the menu the row is given. **So this document supplies, beside the observed value, whether a connected period stands.** It is one boolean per server row, run-held, taken from the period itself and derived from nothing.

- **The composition is K8's exactly, and that is the argument for it.** K8 already composes a presentation out of the period's restart mark standing beside the observed value; **a period standing beside the observed value is the same shape**, and it is what was missing.
- **What it makes tellable.** A **repairing** server is one whose period stands while the observed value is *reconnecting* or *disconnected*, and it takes the connected menu whose first slot reads *disconnect* — which is [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 1's promise, available for as long as a period stands. A server whose period does not stand is repaired by nothing ([N13](#33-the-three-places-repair-does-not-run-at-all)) and takes the disconnected menu.
- **It adds no observed value and K6's set is still three.** Nothing here is a fourth; the condition record, its transitions and T13's notification are untouched.
- **The precedence between the two presentations is stated so nobody derives it.** Where the restart mark stands, K8's *restarting* wins and [4.3](#43-no-condition-record-stands-while-the-mark-does) governs; *repairing* is what a standing period reads as when no mark stands.
- **What each presentation is called on screen is Design's**, exactly as K8 leaves *restarting*'s wording to `Server Setup` and Design.

**K9. *connected* and *needing a new key* are two independent readings of one server and never one state machine.** The first is this section's; the second is [9.3](#93-at-the-list-row-46)'s, computed at each list draw from a local read. Both can be true at once, which is what Row 34 requires.

### 2.3 What is never used for this

**K10. No request is made to learn whether the connection is alive.** §8.5's constraint forbids a mechanism that needs the caller to use the connection first, and a request made to find out is exactly that.

**K11. A stalled transfer channel is never read as a broken connection**, which is `Server protocol and transfers` [G8](Server%20protocol%20and%20transfers.md#103-a-slow-thing-and-a-stopped-one)'s rule from the other side, and Fact 57 is its reason.

**K12. A supervisor that does not answer is never read as a broken connection.** `Desktop app and delivery` [V1](Desktop%20app%20and%20delivery.md#12-the-automatic-supervisor-unavailable-repair-trigger) states it: the supervisor-unavailable condition's observed value *"is whether the supervisor answered a request on the command path, and is nothing else"*, and *"the two are never inferred from one another"*. The server connection stays up.

**K13. Nothing about the connection is inferred from a machine being reachable by any other route.** Reachability is not the check; §2.3's installation identity is, and it is a check about Smoozy's own state rather than about the connection.

## 3. Repair (Rows 30 and 31)

**Constraint:** Row 31's two clauses, quoted at the head of this document; the Creator's ruling of 2026-08-08 that repair does not stop for good; `Server Setup` [T6](Server%20Setup.md#8-the-restart)'s constraint that **no figure may be derived from any one machine's observed return cost**, against a measured spread of **9 to 90 seconds across three machines and a container recycle at about 90**; and Fact 57's ten-minute finding, which forbids resurrecting a connection.

### 3.1 A run, and the two figures in it

**N1. Repair starts the moment a break is declared inside a standing period, with the user doing nothing**, and every attempt belongs to the period the user opened rather than starting a new one.

**N2. A run is eight attempts.** Between one attempt and the next the pause is **15 seconds**, measured from the **end** of the previous attempt and never from its start. Each attempt carries its own connect deadline of **20 seconds**, which is a waiter's deadline under `Server protocol and transfers` [C16](Server%20protocol%20and%20transfers.md#46-per-waiter-deadlines) and changes no durable state when it expires.

**N2a. And a run's span is fixed at 105 seconds, so a run's failure lands at a moment nobody has to compute from what its attempts happened to cost. Added 2026-08-22, scenario replays Pile 1 item R32.** No attempt begins once 105 seconds have elapsed from the run's start, and an attempt still in flight at that moment is abandoned there — abandonment is that attempt's own waiter deadline arriving early and changes no durable state, exactly as `Server protocol and transfers` [C16](Server%20protocol%20and%20transfers.md#46-per-waiter-deadlines)'s expiry does not. **With every attempt refused at once the eight attempts fill the span exactly** (7 × 15 = 105), which is the shape [N2](#31-a-run-and-the-two-figures-in-it) already had; with attempts running to their 20-second deadline, fewer fall inside it.

**What forced the bound.** [N5](#31-a-run-and-the-two-figures-in-it) raises the connection condition when a run fails, `Desktop app and delivery` [T13](Desktop%20app%20and%20delivery.md#133-the-four-kinds-and-what-composes-each) posts the could-not-restore notification from that record, and `Preparation/Specs/Servers.md` fixes the moment in the Creator's ruling of 2026-08-22 — the message *"still arrives when a run fails."* **Unbounded, run 1 fails anywhere between 105 and 265 seconds**, on how a failed attempt against that particular machine happens to fail: a figure nothing in this project has observed and nobody chose. For one and the same three-minute outage Smoozy would then either notify the user shortly before the machine came back or reconnect silently, with nothing written down deciding which. **Bounded, the outcome is one comparison**: a break repaired within 105 seconds of its declaration raises nothing, and one that is not raises the condition at 105 seconds, which is [K3](#21-the-break-reporting-mechanism)'s 45-to-60-second declaration window and nothing else added to it.

**Nothing else moves.** N2's three figures are unchanged, [N3](#31-a-run-and-the-two-figures-in-it)'s rule that a pause is measured from the end of the previous attempt is unchanged, and [N4](#31-a-run-and-the-two-figures-in-it)'s derivation is the same one — 105 seconds clears the 90-second top of the observed return spread, now exactly rather than as a floor. **The alternative shapes were rejected for what they cost**: pacing attempts from a fixed slot start is what [N3](#31-a-run-and-the-two-figures-in-it) forbids, and holding every attempt open to its full 20-second deadline puts 35 seconds between two attempts against a machine that refused the first one at once, which spends the fast case to fix the slow one.

**One consequence is named rather than hidden: *eight* is the count in the refused-at-once case and an upper bound in every other.** Where attempts run to their deadline, fewer than eight fall inside the span. `Preparation/Specs/Servers.md` carries the figure as a settled-at-Architecture sentence and **already carries the bound**: *"a run is **up to** eight attempts with a pause of fifteen seconds between them, and after a failed run a further run begins after a standing pause of a minute, for as long as the app is open."* **The word was brought there by the runner at the Part 6.3 re-sweep**, so the two records agree and nothing is owed. *(Corrected 2026-09-02 at the stage-close gate repair. This quoted the spec without* up to *and then said that sentence* now says one word more than this document does *and* is not edited from here *— the opposite of the record on both counts, the quotation being of a sentence the spec had not carried for weeks.)*

**N3. Measuring the pause from the end of the previous attempt is the load-bearing half of that shape.** An attempt against an unreachable machine takes time to fail, and a cadence measured from the start would put attempts in flight against a connection nobody has declared dead yet. Fact 57's own numbers are why the two cannot be separated: **the detection of a break is itself tens of seconds**, so a fresh attempt made before the previous one has failed is an attempt made in the dark.

**N4. What the numbers are derived from, and it is a spread and a floor rather than any machine's cost.**

- **The pause is at or above the shortest observed return.** The spread's floor is **9 seconds**; a pause under it spends attempts before the fastest machine on record could have answered. Fifteen seconds sits above it, and it is the Creator's own rough shape, stated as such and not as a settled number.
- **A run's span sits above the spread's top.** Eight attempts and seven pauses of 15 seconds are **105 seconds**, and the top of the observed spread is **90 seconds**, a container recycle. So a machine returning at the slowest cost anyone has watched is still inside its first run. **Corrected 2026-08-22, scenario replays Pile 1 item R32.** This used to add that with every attempt running to its deadline the run spans 265 seconds, *"so the floor is the number the derivation rests on and the ceiling is not a promise"* — [N2a](#31-a-run-and-the-two-figures-in-it) now bounds the span at 105 seconds, so 105 is the run's length rather than its floor and there is no ceiling left to disclaim.
- **No figure above is any one machine's measurement.** 15 is a rough shape bounded below by the spread's floor; 8 is chosen so that 7 × 15 clears the spread's top; 105 is that same product taken as the run's bound; 20 is a waiter's own limit and not a return cost.

**N5. Where a run fails, the server is left disconnected, carrying what Smoozy said about the run that failed, and Smoozy says so.** The failure record is [State, identity and recovery](State,%20identity%20and%20recovery.md#81-two-kinds-and-the-kind-is-declared) §8's, of kind **condition** — the connection condition, which is live and can stop being true — and it says only that the connection is down. **It carries no claim about why**, because Smoozy cannot tell a network problem from a machine switched off from a machine that no longer exists. **The record is raised at the run's failure and not at the break declaration**, which [N2a](#31-a-run-and-the-two-figures-in-it) puts at a determinate 105 seconds after the declaration; `Desktop app and delivery` [T13](Desktop%20app%20and%20delivery.md#133-the-four-kinds-and-what-composes-each) posts the could-not-restore notification from that raise, and [K6a](#22-the-three-observed-values-and-what-servers-supplies) is the ruling it keeps.

### 3.2 The standing repair, which never ends while the app is open

**N6. A failed run is not the end of it.** After a run fails, the period stands, the server reads **disconnected**, and a further run begins after a **standing pause of 60 seconds**. Runs continue for as long as the period stands, which is for as long as the app is open unless the user disconnects.

**N7. So the observed value moves between two of [K6](#22-the-three-observed-values-and-what-servers-supplies)'s three across a standing repair, and nothing shows that movement to the user.** It is **reconnecting** while a run is in flight and **disconnected** between runs. A machine that becomes reachable again is picked up on the next attempt, with the user doing nothing.

**N7a. Corrected 2026-08-22, on the Creator's ruling of that date.** N7 used to read *"So the server flickers between two readings, and that is the promise rather than an artefact"*, and said the alternation was *"what the spec describes in its own words"*. **The spec no longer describes it and the promise has gone the other way**: `Preparation/Specs/Servers.md` now says the server reads as **reconnecting** for the whole repair, in-run pauses and between-run pauses alike, because a word changing every fifteen seconds cannot be read. **Nothing built here moves** — the value, its two states across a repair, N5's record and `Desktop app and delivery` [T13](Desktop%20app%20and%20delivery.md#133-the-four-kinds-and-what-composes-each)'s could-not-restore notification are all exactly as they were, and the cost the ruling accepted is that the user cannot tell from the label whether an attempt is in flight at this second.

**N7b. So which vocabulary these three words are in is fixed for the whole of this document. Added 2026-08-22, with N7a.** Wherever this document says a server *reads* or *is left* **connected**, **reconnecting** or **disconnected** — [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 1, [N5](#31-a-run-and-the-two-figures-in-it), [N6](#32-the-standing-repair-which-never-ends-while-the-app-is-open), [N8b](#32-the-standing-repair-which-never-ends-while-the-app-is-open) and [Q17](#102-the-three-paths-and-the-two-reads-that-close-the-gap-between-them) among them — **it names K6's observed value and never a word on a screen.** **[W19](#115-stop-and-clear-and-what-it-says-when-it-only-partly-worked-row-42)'s table was in that list until 2026-08-22 and is not any more**: it is keyed on whether a period stands and whether the primary connection is live, and uses none of the three words. K7 already says this document presents none of them; this says which vocabulary the sentences are written in, so that no builder reads one of them as the label a row carries.

**N8. Nothing escalates, backs off further, or gives up.** There is no growing pause, no attempt ceiling and no terminal state. *"An hour with the user's own line down costs them that hour"* — with a 60-second standing pause and a 105-second run ([N2a](#31-a-run-and-the-two-figures-in-it)), a machine that returns is picked up within about three minutes of returning, and the hour costs the hour and nothing more.

**N8b. One refusal is permanent and the repair stops on it rather than retrying for ever. Added 2026-08-21, per Row 315 and `Keys` [S11](Keys.md#84-a-protected-key-on-a-computer-with-nowhere-to-remember-row-315).** Where [P1](#91-before-a-connection-row-33)'s second answer is *no* because `Security and licence` §3.3's store standing reads *never answered* and the row's key is protected, no run of attempts can ever change it — the answer is a property of the installation and not of the moment. **The server is left disconnected and marked with the permanent condition; the standing pause does not restart for it.** N8's *no terminal state* is untouched for every other cause, and a user-started connect still works and still asks (P4). **The refusal stops being permanent the moment the standing does**, so nothing is written that would have to be cleared by hand.

**N9. Every attempt is a fresh connection.** K5's finding forbids anything else, and it is also what makes a repair capable of meeting a changed identity ([10.2](#102-the-three-paths-and-the-two-reads-that-close-the-gap-between-them)) and a key that has gone away ([9.1](#91-before-a-connection-row-33)) — both of which are checked at every attempt and not once at the start of the repair.

**N10. A repair that succeeds asks nothing of the user and does not need their connect action again.** The condition record is withdrawn by the observed value reaching *connected*, which is §8.2's derivation and needs no act of this document's.

**N10a. The repair publishes one further reading and it is *the moment the next attempt is due*. Added 2026-08-21, per Row 347.** [Design](../Design/Servers.md) draws *Reconnecting…* with when the next attempt falls, and nothing here produced that value.

- **What it is.** One moment on the desktop's own clock, and nothing else — no attempt count, no run number, no schedule. There is exactly one such value per server row.
- **When it is written, and it cannot be written earlier.** At the instant an attempt ends. **N2's rule is what forces that**: the pause is measured from the **end** of the previous attempt, and an attempt carries a 20-second connect deadline, so **the moment the next attempt falls is unknown until the current one has failed.** A value published when an attempt began would be wrong for that attempt's whole life.
- **What it reads while an attempt is in flight: absent.** There is no next attempt due while one is running, and *absent* is a value rather than a gap.
- **It covers both pauses and does not distinguish them.** N2's 15 seconds inside a run and N6's 60 seconds between runs are both *when the next attempt falls*, and the reading is the same reading. Whoever draws it never learns which pause it came from, and does not need to.
- **Where it lives: run-held, beside the condition record and never inside it.** [State, identity and recovery](State,%20identity%20and%20recovery.md#82-a-condition-record-is-a-derivation-never-a-copy) §8.2 fixes what a condition record holds — the condition identity and the set of observed values it was raised over — and **a moment is neither**, so putting it there would widen a closed document's record shape for one drawing. It is process memory for the life of the run, in §11.1's run-held class, exactly as the last-known queue reading is (S12). **Nothing durable is written from it** (D4, S13), and a fresh launch knows nothing until a break is declared again.
- **It is a reading and not an outcome**, so `Desktop app and delivery` P7's write-then-post rule has nothing to bind here: there is no durable state behind it to write first.
- **The marked period's policy publishes the same value.** [4.2](#42-the-reconnect-policy-for-a-marked-period)'s four runs and ten-minute wait are pauses of the same kind, so a restart-marked period publishes *the moment the next attempt is due* on the same reading. **What it does not publish is a moment for giving up**, because M7's giving up is an event rather than a schedule the user is shown.
- **N8b's permanent refusal publishes nothing.** Where the repair has stopped for good, there is no next attempt, so the reading is absent and stays absent — which is the correct answer and not a missing one.

### 3.3 The three places repair does not run at all

**N11. Where the period carries the restart mark**, the ordinary repair is suppressed and [4.2](#42-the-reconnect-policy-for-a-marked-period)'s policy runs instead. `Server Setup` §12 requires the suppression and this document performs it.

**N12. Where the server's key is not usable**, no attempt is made — Row 33 — and [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 4 ends the period.

**N13. Where no period stands.** A server the user has not connected, a server whose put-back failed, and a server the user disconnected are all repaired by nothing, because repair is a property of a standing period and of nothing else.

## 4. The restart `Server Setup` caused (Row 32)

**Constraint:** `Server Setup` [§12](Server%20Setup.md#12-what-this-document-supplies-and-to-which-document) and [T4 to T6](Server%20Setup.md#8-the-restart), taken whole; Fact 51 answered yes; Fact 57's same-second detection of both announced endings.

### 4.1 The mark, taken rather than decided

**M1. The mark is `Server Setup`'s and this document takes it.** *Restarting, caused by Smoozy* sits on the connected period, is **set before the restart command leaves**, and is cleared **by exactly two things and nothing else: the machine answering, or this document's reconnect policy for a restart-marked period giving up.** A user who stops waiting **clears nothing** — the mark and the machine-level state both stand and the reconnect policy goes on running.

**M2. *This drop is mine* is a state set before the act and never a reading taken after it.** That is T4's own sentence and Fact 57 is its reason: a machine closing politely and a machine powered off are detected in the same second, so nothing in the moment tells a restart from a destruction. Smoozy knows because it caused it.

**M3. While the mark stands, the dropped-connection repair and the could-not-restore notification are suppressed**, and the server reads as **restarting** ([K8](#22-the-three-observed-values-and-what-servers-supplies)).

### 4.2 The reconnect policy for a marked period

**M4. The policy is four runs of [3.1](#31-a-run-and-the-two-figures-in-it)'s shape, and then it gives up.** Eight attempts per run, 15-second pauses, a 20-second connect deadline, [N2a](#31-a-run-and-the-two-figures-in-it)'s 105-second run span, and a 60-second standing pause between runs. Its wait is therefore exactly **4 × 105 + 3 × 60 = 600 seconds — ten minutes.** **It was a floor until 2026-08-22**, when N2a bounded the run's span and made it a length.

**M5. Ten minutes is derived from the spread and not from any machine.** `Server Setup` T6 measured return at **9 to 90 seconds across three machines and about 90 for a container recycle**, and says outright that *"anything budgeting a fixed wait is wrong on most machines"*. Ten minutes is **more than six times the top of that spread**, so a machine merely slow to return is never declared gone, and it is the run structure of [3.1](#31-a-run-and-the-two-figures-in-it) repeated rather than a fresh constant. **No figure is any one machine's observed cost**, which is T6's requirement on this document.

**M6. The three ways the wait ends, and only two clear the mark.** This is T6's closed set, performed.

1. **The machine answers.** The mark clears, the period's observed value reaches *connected*, and `Server Setup`'s recovery run takes the setup over from the recorded boundary.
2. **The user stops waiting.** The mark does **not** clear, this policy goes on running, and the machine-level state stands. What ends is the user's waiting and nothing else.
3. **This policy gives up.** The mark clears. `Server Setup` reports the setup cut off part-way, and Smoozy says only what it knows — the connection is down and could not be restored — **with no claim to know why, because a machine still starting cannot be told from one that will never answer.**

**M7. Giving up hands the period back to the ordinary repair rather than ending it.** The spec's own sentence is *"Only if the machine never comes back does it become an ordinary failure, reported as one"*, and an ordinary failure is one the standing repair of [3.2](#32-the-standing-repair-which-never-ends-while-the-app-is-open) goes on working at for as long as the app is open. So the period stands, the suppressions lift, and the machine comes back on its own if it ever does.

### 4.3 No condition record stands while the mark does

**M8. While the mark stands, no connection condition record is raised at all.** The observed value still moves — Smoozy knows perfectly well the connection is down, because it took it down — but the record `Desktop app and delivery` T13 raises the could-not-restore notification from is not raised. **That is the suppression `Server Setup` requires, expressed in the one mechanism that presents it**, rather than a second suppression rule sitting beside the record.

**M9. So the two clearing events land differently and both land correctly.** Where the machine answers, the observed value reaches *connected* and there was never a record to withdraw. Where the policy gives up, **the condition is raised at that moment** and the notification fires then, which is the first moment Smoozy has anything to tell the user that it did not already cause.

## 5. The edit put-back (Row 39)

**Constraint:** Row 39, quoted at the head of this document, and its own dependency on Row 29's closed replacement list.

### 5.1 The edit's disconnect ends the period, and the put-back opens a new one

**E1. Saving an edit to a connected server's host, port, username or key ends the period.** The spec's own verb is the reason — the save *"disconnects a live server so the change can be applied"* — and a disconnect is how a period ends. The user's act of saving is what ends it, exactly as their disconnect would.

**E2. The put-back is O1 performed by Smoozy as part of that same act.** It opens a new period on the new details. Three things follow and each is a promise kept by construction rather than by an exception:

- **A failed put-back is left alone.** There is no period, so [3.3](#33-the-three-places-repair-does-not-run-at-all) N13 applies and no repair runs. The server is left disconnected with the new details saved and Smoozy says so — the spec's own outcome, delivered without carving the repair out for this one case.
- **The replacement list stays exactly two.** Row 29's *"in two cases, and only these two"* is kept literally.
- **Editing a disconnected server leaves it disconnected**, because there was no period to end and none is opened.

**E3. A renaming changes no connection detail, so it ends no period and opens nothing.** Neither does a colour change. *Nor, from 2026-10-04, does a change to the chosen fallback folder (D3), which reaches no machine and carries no warning.*

**E4. What the ended period drops is what [1.3](#13-what-the-period-holds-and-what-ends-with-it) says it drops**: the last-known queue reading, every live reading, and any machine password held for the connection. The last two are re-taken on the new period; the machine password held for a connection is the user's own choice and is asked for again where it is needed, which is `Security and licence` §2's arrangement and not a new cost.

**E5. Transfers are not period-held and do not go with it.** Their durable record is `Server protocol and transfers` [S9](Server%20protocol%20and%20transfers.md#73-the-progress-record-is-on-the-desktop-side-in-both-directions)'s, in the local record and keyed to the server row and the installation identity. A transfer whose channel ends at the edit's disconnect ends as **interrupted**, never as *stopped* — Smoozy did not stop the user's transfer, it replaced the machine underneath it — so the staged material is kept and the user is told it is there. What becomes of it on the new period is [12.2](#122-the-label-every-connection-carries)'s label and `Server protocol and transfers` [C14](Server%20protocol%20and%20transfers.md#45-a-reconnection-is-gated-on-the-installation-identity-and-not-on-reachability)'s gate: on a host or port edit the installation identity read on the new connection is absent or different, and every transfer record held against the row is disqualified, which is correct — the entry now points at a different machine.

### 5.2 The two interruptions on one path, and they are not the same kind

**E6. The put-back may meet a changed identity, and it may never meet a passphrase.** These are two different kinds of interruption on one automatic path and the document tells them apart:

- **A changed identity puts a question on screen and that is permitted.** It arises on a username or key edit, where the remembered identity is kept rather than started over ([6.4](#64-what-an-edit-throws-away-and-it-is-four-rules-on-two-fields-row-38)), and the machine's identity may have changed for its own reasons in the meantime. The user decides; declining leaves the server disconnected with the new details saved, which is the same outcome as any failed put-back.
- **A key passphrase never does.** Row 33 binds every connection Smoozy makes on its own, and the put-back is one. Where the new key needs a passphrase Smoozy is not holding, **the put-back is not attempted at all**: the server is left disconnected with the new details saved and marked with what is wrong.

**E7. The difference between them is what each question is about.** The changed-identity question is about the machine and only the user can answer it, and it is a question the spec puts on screen by name. The passphrase question is about a secret, and putting one on screen at a moment the user is looking elsewhere is what the promise forbids outright.

**E8. A put-back never carries a remembered setup.** A setup is remembered only where the connection failed, so a server holding one has never been reached and is disconnected — and editing a disconnected server leaves it disconnected, so there is no put-back to carry one. [Section 7](#7-the-remembered-setup-bit-row-26) is the mechanism that makes this true rather than merely stated.

## 6. The store (Rows 25, 28, 37, 38 and 41)

**Constraint:** [State, identity and recovery](State,%20identity%20and%20recovery.md#11-on-the-users-computer) §1.1 — the local record is the only durable store on the user's side, and *"A builder that needs a second state store has found a fault in this section rather than a case it does not cover"*; §11.1's five lifetime classes; `Security and licence` §3's secret store and §7's placement of the remembered identity; `Desktop app and delivery` [§9](Desktop%20app%20and%20delivery.md#9-the-secret-adapter-and-its-helper)'s secret adapter, which means no module here holds a secret value.

### 6.1 One durable store, and one row per server

**D1. Everything durable Smoozy holds about a server is in the local record, and it is either a field of the server row or a record keyed by the row's local server identifier.** There is no second store, no per-server file, and nothing written into the user's own SSH configuration — `Security and licence` §7 is exact about that last one, and *"Nothing Smoozy does modifies the user's own SSH configuration."*

**D2. The one thing not in the local record is a secret's value**, which sits in the operating system's secret store under a (kind, subject) pair, reached only through `Desktop app and delivery`'s secret adapter. What the server row holds is the **subject reference**, which carries no value and, per `Security and licence` §3.0 rule 1, carries nothing about the user — never a host, a port, a username, a file path or a fingerprint.

**D3. The server row, in full.**

| Field | Kind | Carries an installation identity? | Ends at |
|---|---|---|---|
| **local server identifier** | identity, issued by the local record ([§2.2](State,%20identity%20and%20recovery.md#22-the-register-of-identities)) | — | the removal |
| **host**, **port**, **username** | the connection identity ([Section 13](#13-the-connection-identity-row-24)) | no | the removal |
| **key reference** — a local key identifier — and the **key fingerprint** beside it | `Keys`' reference and Row 46's match value | no | the removal |

**D5. History records are keyed by the job identity and never by the server row**, which is why a removal leaves them exactly where they are. That is `Queue & History`'s rule and this document performs nothing about it.

### 6.2 The enumeration, and it is the thing a removal walks

**D6. The table in D3 and the list in D4 together are one enumeration, and it is the only route by which anything about a server is reached.** Nothing about a server is reachable only by the path that wrote it. That is Row 41's real requirement — five separate things are named, they do not live in one place, and the promise is that a removal reaches all five — and it is met by making the enumeration the structure rather than a list a builder keeps in step by hand.

**D7. Finding one is finding D5 working, not a fault.

### 6.3 The remembered host key (Row 37)

**Constraint:** `Security and licence` [§7](Security%20and%20licence.md#7-host-trust), which owns it and is not retaken: *"The remembered identity lives in the local record against the saved server, and nowhere else. Not in `~/.ssh/known_hosts`."* And Row 37's two constraints — it is per server and started over by an address edit or an accept, and **nothing may put it in front of the user**.

**D8. It is one field of the server row, holding the host key value the last accepted comparison approved.** Per server, rewritable one entry at a time, readable and writable at the moment a connection is attempted, and started over by an address edit or an accept by being overwritten or cleared. A single shared file gives none of that, which is §7's own argument.

**D9. It is never shown, never logged, and never handed to any other module.** `Security and licence` §7's closing sentence is the rule — *"nothing here reaches the user's eyes. No fingerprint at a first connection, none at a changed one, none in the warning, and none in any log"* — and §13's redaction covers the rest.

**D10. It carries no installation identity, and that is deliberate rather than an omission.** [§2.3](State,%20identity%20and%20recovery.md#23-the-machines-installation-identity) requires every durably remembered machine-derived value to carry the installation identity it was read under. This one cannot and must not:

- **It is read before any connection that presents Smoozy's credential** (`Server protocol and transfers` A5), and the installation identity is read over such a connection. There is no identity in hand at the moment the host key is recorded.
- **It is recorded on machines where no installation exists at all** — a plain add's first connection, before anything is installed — so the absent branch of §2.3 is the ordinary case for it rather than the exceptional one.
- **It is a statement about the machine at that address and not about Smoozy's installation on it.** §2.3 says so itself: *"This does not rest on the machine's remembered identity, and deliberately so."*

**So the remembered host key is outside §2.3's carrying rule**, its lifetime is D3's row, and [Section 16](#16-unresolved) item 9 records the seam.

**D11. Nothing in this document, and nothing this document supplies, is keyed on the remembered host key.** `Server protocol and transfers` [A5](Server%20protocol%20and%20transfers.md#3-the-authentication-boundary) states it for its own scope and the reason binds here too: **Fact 83 is answered negatively** — a fresh container rental on the same physical machine presented **byte-identical** host keys while being a demonstrably different container with everything Smoozy installed destroyed. What tells one installation from another is §2.3's installation identity, and [10.2](#102-the-three-paths-and-the-two-reads-that-close-the-gap-between-them) records what that costs Row 36's promise.

### 6.4 What an edit throws away, and it is four rules on two fields (Row 38)

**D12. The rules are cut on the field that changed, not on *the connection details changed*.** An answer that treats the edit as one event gets three of the four wrong.

| What changed | Remembered hardware, cursor, confirmed installation identity | Remembered host key | Remembered machine password | Remembered setup |
|---|---|---|---|---|
| **host or port** | **dropped** | **started over** — the field is cleared, so the next connection is a first connection and trusts silently | kept | **kept** |
| **username** | kept | kept | **cleared, without asking** | **kept** |
| **the key** | kept | kept | kept | **kept** |
| **the label or the colour** | kept | kept | kept | **kept** |

**D13. Host and port together name what Smoozy is reaching**, so changing either points the entry at a different machine. The hardware read from the old one is the wrong answer, the event cursor was taken against a journal on the old one, the confirmed installation identity belonged to it, and **the machine's root was chosen on it**. All four go in the same write, **and the driver's missed OptiX bar (D3) with them**, for the same reason — *added 2026-10-11, the fourth piece of the OptiX and driver work, Rule 7; no auditor has seen it*. *(Repaired at Build, 2026-09-03, where a builder stood on this clause. It read "All three go in the same write" and named three values, because D3's table did not carry the root — a field [Job files and outputs](Job%20files%20and%20outputs.md#11-one-root-one-mount-chosen-once) **L1** requires against this row and which D7 makes a fault to hold outside D6's enumeration. **The rule does not move**: the reason this clause gives reaches the root exactly as it reaches the other three.)*

**D14. Changing the username clears the remembered machine password without asking, because a password belongs to a login and the login has changed.** Label: **Creator-stated** (2026-08-10). The clearing is an erase through the secret adapter against the row's subject reference, and where the store does not confirm the erase, the **recorded debt** of `Security and licence` §5.1 is written and the sweep clears it later. **This is the one place a stored secret is destroyed without being asked about**, so a miss leaves a password behind against a login that no longer exists — which is why it is an enumerated step of the edit's own write and not a side effect of anything.

**D15. Changing the key clears nothing.** The row's key reference and fingerprint change, and that is all. In particular it does not touch the remembered host key, since a key change does not change which machine is reached.

**D16. The whole write is one durable write**, made before the put-back of [Section 5](#5-the-edit-put-back-row-39) is attempted.

### 6.5 What a removal reaches (Row 41)

**D17. A removal walks the enumeration of [6.2](#62-the-enumeration-and-it-is-the-thing-a-removal-walks) and removes everything in it.** The five things the spec names are all inside it: the details (D3's first three fields), the connection (**the period, which ends with the local forget** — [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 6, **corrected 2026-08-22, scenario replays Pile 1 item R21**; this said *ended first*, which cannot hold on the one removal that reaches a machine), the machine's remembered identity, any remembered setup, and any machine password. **What the walk never reaches is a history record: a confirmed job record is not in the enumeration ([D4](#61-one-durable-store-and-one-row-per-server), narrowed 2026-08-22, scenario replays Pile 1 item R4), and [D21](#65-what-a-removal-reaches-row-41) is the same fact from the spec's side** — the entry for the animation the user just rendered survives the row that submitted it.

**D18. The machine password's value is erased through the secret adapter, and an erase the store does not confirm is a recorded debt rather than a forgotten one.** `Desktop app and delivery` [S10](Desktop%20app%20and%20delivery.md#9-the-secret-adapter-and-its-helper) is exact about what confirmation means per system, and §5.1's mark is what carries an unconfirmed erase forward. **A leftover here is a remembered secret against a machine the user believes Smoozy has forgotten, and nothing afterwards would ever show it** — the debt is what makes that impossible rather than unlikely.

**D19. It happens without reaching the machine, in every case but one.** Nothing in a removal is a clean-up performed on the server. **Removing a disconnected server never starts a connection and never asks for a passphrase**, which is one of the two places [S9](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings)'s closed list does real work. The one exception is *stop and clear first*, which is [11.5](#115-stop-and-clear-and-what-it-says-when-it-only-partly-worked-row-42) and is not a clean-up either — it is two commands the user asked for.

**D20. Staged download material held against the row is `Server protocol and transfers` [S28](Server%20protocol%20and%20transfers.md#78-cleanup-and-the-five-ways-a-transfer-ends)'s third bullet and is cited rather than performed here**: it is removed with the row or recorded as an owed cleanup, because §11.1 makes values held against a removed server row subject-held and the record that named the material goes with the row.

**D21. History is untouched.** Removing a server does nothing to any history record, which is `Queue & History`'s rule and the spec's own.

### 6.6 Every server starts disconnected, by construction

**D22. Nothing durable records that a server was connected**, so on a fresh launch there is no period, every server's observed value is *disconnected*, and reopening the app connects to nothing on its own. There is no clearing step at start-up, which means there is no clearing step to fail.

**D23. A server stays in the list until the user removes it**, because the row is **user-held** under §11.1 — *"the user removes it, and never otherwise"*. Nothing ages it, caps it, sweeps it, or drops it because a machine stopped answering. [§7](State,%20identity%20and%20recovery.md#7-reconciliation-on-the-desktop) step 2's own rule is the general form: *the machine will not come back* is not a state anything here may reach.

## 7. The remembered setup bit (Row 26)

**Constraint:** Row 26, quoted at the head of this document, and its dependency on Row 32 — the rule turns on **reached the machine or not**, and a restart mid-setup filed on the wrong side either forgets a setup it should keep or keeps one it should forget.

### 7.1 One moment writes the bit, and nothing else ever does

**B1. The bit is written at exactly one moment: an add carrying a ticked setup option whose period never gets a live connection.** It records which options were ticked, and it is written as part of the same durable write that saves the server.

**B2. *Reached the machine* is a single instant and it is named exactly: the moment the SSH transport reports the connection authenticated and usable.** Before that instant the connection failed and the bit is written. From that instant on, **the bit is not written, whatever happens next** — not by a setup step failing, not by a drop mid-setup, not by a restart Smoozy caused, and not by a half-finished add where one option succeeded and the other did not.

**B3. So a restart is filed on the *reached* side and the question never arises for it.** A restart is not a case for this bit at all: the connection was established, the setup is not abandoned, and `Server Setup`'s recovery run carries it on from its recorded boundary. The bit exists only for a setup that **never started**.

**B4. The instant is after step 3 of the first-connection sequence and before steps 4 to 8** ([Q1](#10-the-first-connection-in-order-rows-36-and-35)), so a machine that authenticates and is then found not to be Linux is on the *reached* side. The user is told plainly it is not a Linux machine and nothing about the setup is remembered, which is right — a remembered setup would only run again on the same machine and fail the same way.

### 7.2 What clears it

**B5. Three things clear it and the list is closed.**

1. **A connection to that server is established**, whatever the setup then does. **The bit is cleared in the same durable write as the moment [B2](#71-one-moment-writes-the-bit-and-nothing-else-ever-does) names** — the transport reporting the connection authenticated and usable — **and the remembered options are handed to `Server Setup` from what that write carried**, so the clearing does not depend on the hand-over happening and no path that is established and then goes no further leaves the bit standing. The setup runs exactly once from the bit and the bit is gone whether the setup succeeds, partly succeeds or fails. That is the spec's rule kept literally: *"Once Smoozy has reached the machine, nothing about the setup is remembered."*
2. **The user drops it** without carrying it out.
3. **The server is removed.**

**B6. The connect action carries it.** A server holding the bit reads as needing both, and its connect action says it will do both. What that action is called is Design's.

**B7. It survives every edit** ([6.4](#64-what-an-edit-throws-away-and-it-is-four-rules-on-two-fields-row-38)), which is what it is for: an add whose connection failed on a wrong address is put right by editing the address and connecting.

### 7.3 It is not a machine-derived value

**B8. The bit is the user's own instruction and nothing was read from a machine to produce it**, so it carries no installation identity and no installation-identity branch disqualifies it. §11.1 puts *"a server's remembered setup state"* in the **subject-held** class beside machine-derived values, and this clause is what tells the two apart inside that class. [Section 16](#16-unresolved) item 9 carries it with the host key's.

## 8. The hardware reading (Rows 27 and 28)

**Constraint:** Rows 27 and 28, quoted at the head of this document; `Rendering` [§8](Rendering.md#8-what-this-document-supplies-and-to-which-document)'s requirement that *"the hardware reading must carry each card's make as a value L23's table can be keyed on, never a wording to be parsed"*; `Queue & History` [G1 and G2](Queue%20&%20History.md#7-readings-taken-from-the-machine), which split the card capacity to this document and the live usage to that one; [State, identity and recovery](State,%20identity%20and%20recovery.md#23-the-machines-installation-identity) §2.3 and §3's D4 and D5.

### 8.1 Three states, and the cheap implementation has two

**H1. A server's hardware has three states and the set is closed: never read, last seen, live.**

| State | When | What is shown |
|---|---|---|
| **never read** | no reading Smoozy may show is held against this row | **that there is nothing to show**, rather than an empty row. A server that has never been connected is in this state, and so is one whose held reading has been disqualified ([8.4](#84-the-installation-identity-over-all-of-it)) |
| **last seen** | a reading is held, and the *live* row's condition does not hold | the reading, marked as what was last seen, with the moment it was taken |
| **live** | the held reading was taken on the period's primary connection and that connection is live now | the reading |

**H1a. The *live* row is keyed on the connection the reading was taken on, never on the period alone. Re-keyed 2026-08-22, scenario replays Pile 1 item R2.** As it stood, *live* read *"a reading was taken in the period that stands now"* and *last seen* read *"no reading was taken in a standing period"* — and [S12](#13-what-the-period-holds-and-what-ends-with-it)'s *a drop does not end a period* then kept a destroyed machine's row in the *live* state: its cards, its memory and its free disk stated as present facts, unqualified, beside an observed value flickering *reconnecting*. Three things fix the key:

- **The spec keys the mark on the connection**: `Preparation/Specs/Servers.md` keeps what was read on the last connection and shows it *"for a server that is not connected, saying it is what was last seen."*
- **A reading is taken once per primary connection ([H15](#83-where-the-reading-is-taken-and-why-no-blender-is-in-it)) and nothing re-reads it inside the connected stretch**, so the one reading that may stand unmarked is the live connection's own. Every other held reading falls to *last seen* — a period standing over a declared break ([K3](#21-the-break-reporting-mechanism), K5), and a live connection still on [H18](#84-the-installation-identity-over-all-of-it)'s fourth branch, whose held reading is an earlier connection's and is that table's own *shown as last seen*. **The consolidation's suggested condition — *taken in the period that stands now and the primary connection is live* — was tested and not taken**: on the fourth branch it calls an earlier connection's reading *live* the moment the repair's connection comes up, which is exactly what H18 and [H21](#84-the-installation-identity-over-all-of-it) forbid.
- **The mark's moment is [H2a](#81-three-states-and-the-cheap-implementation-has-two)'s desktop moment**, already supplied; and `Queue & History` [C7](Queue%20&%20History.md#11-one-job-two-records-two-lifetimes) now states the same connection-keyed trigger for the queue reading, so the two documents no longer key the one mark two ways.

The three states stay presentation over one held record ([H4](#81-three-states-and-the-cheap-implementation-has-two)); no store, no field and no reading moved.

**H2. The moment and the clock travel with the reading and are never subtracted from anything.** D5 binds it: the reading carries the moment it was taken **and the machine's own clock it was taken on**, and no duration is computed by subtracting it from the desktop's clock. What the *last seen* mark is worded as is Design's.

**H2a. The reading carries a second moment, and it is that one the *last seen* mark is drawn from. Added 2026-08-21, per Row 349.** H2 leaves the wording to Design and Design words it in three granularities — *last seen 11:04*, *last seen 3 Aug 18:12*, *last seen 28 Jul* — **and choosing between them is a comparison against now, which H2's machine-clock moment cannot supply without the subtraction D5 forbids.**

- **So the record holds two moments: the machine's own moment on the machine's clock (H2), and the desktop's own moment at which the reading was received, on the desktop's clock.** The second is written when the reading lands and is never computed from the first.
- ***last seen* is the desktop's moment, and the mark therefore means *when Smoozy last had a reading*** rather than *when the machine took one*. That is the honest reading of a mark on the user's screen, and it is the only one that can be compared with the user's own now.
- **D5 permits this in its own words** — *"the desktop's clock is used for presentation and for nothing a promise rests on"* — and **nothing here rests on it**: the granularity of a mark is presentation entire. **The machine's moment goes on being the one no duration about work is ever taken from**, and H2 is unchanged.
- **The two are never subtracted from each other**, and neither is ever shown as a duration on this record. **Where the desktop's clock has moved backwards**, a mark can read as in the future; it is drawn as it stands and nothing is corrected, because correcting it would be arithmetic across an undefended clock ([Security and licence](Security%20and%20licence.md#123-the-clock-defence-comes-from-the-service-not-from-the-computer) §12.3).
- **Which of the three granularities is chosen, and at what boundaries, is Design's** — this document supplies the moment they are chosen against and chooses nothing.

**H3. Free disk is in the same record on the same terms, and is explicitly allowed to be wrong.** A job left running writes files, so a held figure is only what was true when the reading was taken. The remembered figure is never shown as current: the same last-seen mark covers it — coherent now that [H1](#81-three-states-and-the-cheap-implementation-has-two) keys *live* on the reading's own connection, so every reading this sentence covers is in the *last seen* state and the mark exists to cover it (**corrected 2026-08-22, scenario replays Pile 1 item R2**: as H1 stood, a reading held inside a standing period over a dead connection was in the *live* state, and this sentence had no mark to point at). In the *live* state the figure is the live connection's opening reading ([H15](#83-where-the-reading-is-taken-and-why-no-blender-is-in-it)), carrying its moment (H2, [H2a](#81-three-states-and-the-cheap-implementation-has-two)), and [K6b](#22-the-three-observed-values-and-what-servers-supplies)'s rule holds of it — no presentation claims a currency the reading's own moment does not support. Label: **Creator-stated** (2026-08-13).

**H4. There is one durable last-seen record per server row and a reading replaces it whole.** Nothing merges a fresh reading into an old one, and no part of a record outlives the reading it came from — a half-updated record would show one machine's cards beside another machine's disk.

### 8.2 What the reading is made of, and every part of it is a trap closed

**H5. The card count is read as a count and never as a parsed total.** `Queue & History` [G1](Queue%20&%20History.md#7-readings-taken-from-the-machine) carries the trap and Fact 46 is the observation: the driver's own count query **returns the value once per card**, so *"A caller reading the first line is right by luck; one parsing the whole output as an integer gets `22`"* on a two-card box, and *"It passes every test ever written on a one-card machine."* **The count is the number of rows of a per-card query, and nothing else is read as a count.**

**H5a. And on a slice of a multi-card host, that rule is the only one that counts the cards the rental actually holds. Added 2026-08-22, observed.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md): two different hosts, each holding **four** cards, each rented as a **two-card** slice. `nvidia-smi -L` and `nvidia-smi --query-gpu=index` returned **2** on both — ours. **`/proc/driver/nvidia/gpus` returned 4 on both**, the extra two UUIDs belonging to another tenant. **So a count taken below the driver's own query counts the host's cards, not the rental's**, and the error is quiet: the reading is not obviously wrong, it is two too many. **This project's own earlier probe used `ls /proc/driver/nvidia/gpus | wc -l` and agreed only because that box had one card and one tenant.** **Reading the kernel's per-card directory as a count is forbidden**, and so is any arithmetic — an allotment, a memory total, a price-per-card — built on it.

**H5b. Identifying or keying a card by its device node is forbidden too, and the numbering is not the query's. Added 2026-08-22, observed.** On the same two boxes, `/dev/nvidia*` exposed **four** nodes on one two-card rental and **two** on the other, and on the second the kernel's `Device Minor` values for **our own** cards were **2** and **0** — no relationship to `nvidia-smi`'s index 0 and 1. **So node *n* is not index *n*, the node count is not a card count, and neither is stable between hosts.** This is H13's prohibition widened from device class to device node: the only card identity is H6's.

**H6. Each card carries an identity that survives two identical cards, and a make that is a keyable value.** Observed — both cards on the two-card box were the same model, so *"the UUID and bus location are what tell them apart"*, and on that box the bus listing gave them *"without a model name"* (Fact 46). **The reason is corrected here to the source's own, 2026-08-20; the design does not move.** That listing names a card out of a `pci.ids` database shipped in the image, and **that image's database was older than the card** — the same lookup resolved the vendor half to *NVIDIA Corporation* on the same run, and the PCI ID Repository gives that vendor and device as *"AD102 [GeForce RTX 4090]"*. **So it is not a property of the tool and it must not be read as one.** What follows is unchanged and is the right way round regardless: identity comes from the driver's own query, presence from the bus scan. So per card the reading carries: the card's **unique identifier**, its **bus location**, its **make** as a value, and its **total memory**. **Vindicated on a rented multi-card slice, 2026-08-22** — the identifier and the bus location are what named the two cards that were ours on a four-card host, and [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md) records that this pair *"turns out to be the only pair that survives this"*. **A card's index, UUID and bus location also survive a restart unchanged**, observed across a reboot on a virtual machine — **on one card, which is the observation's own scope and is stated here from 2026-08-23.** The negative would have been the ordering changing, and it did not; **but an ordering can only move on a multi-card box, and no multi-card box was restarted.** So what holds across a restart is the identity of a card, and **whether an ordering is stable across a restart is unposed** — which costs nothing above, because nothing here is keyed on the index.

**H7. The make is a value `Rendering` L23's table can be keyed on, never a wording to be parsed.** That is `Rendering` §8's requirement by name, because the card technology named at launch is looked up from it. **A reading returning no card at all and a make with no row in that table are one case**, and that case is `Rendering`'s to answer — no submission is withheld anywhere and the attempt ends on the machine before the render instruction with the reason recorded.

**H7a. Nothing here reads a card's live memory use, and one reading of it is on the record with a limit that matters more than the number. Added 2026-08-22.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md) read used memory three times at ten-second intervals on two two-card slices with nothing running: **steady at 1 MiB on both cards of one box and 2 MiB on both of the other**, with the compute-application list empty on both. **A negative would have been used memory moving while Smoozy was doing nothing**, and it did not. **The limit is what makes this weak, and it is stated rather than glossed:** the cards the driver's own query shows are the two we hold, so a neighbouring tenant's work on the host's **other** two cards could not have appeared in the reading whether it existed or not. **What is established is that the two cards we held reported only our own use. Whether a card can ever be shared under us was not posed and this test could not pose it.** Nothing above depends on either answer — this reading is not taken by any clause of this document — and it is recorded so nobody reads the steady figures as evidence of exclusivity.

**H8. Per-card memory has exactly one route and where that route is absent the count and the identity survive and the memory does not.** Observed — the kernel's own per-card information *"gives model, UUID and bus location and no memory figure at all"* (Fact 46). A reading with cards and no per-card memory is a complete reading with a stated absence and never a failed one.

**H9. The machine's own memory reading is the container's allocation where there is one.** Observed — a container reported 4 processors and 15.57 GiB against real allocations of **3.84 processors and 14.95 GiB**, and *"On a 1-of-8 rental, `/proc/meminfo` would overstate usable memory eightfold. The reading Smoozy must take on a container is the cgroup's, falling back to `/proc` only when it reads the literal `max`"* (Fact 46). The fallback's trigger is the literal `max` and nothing else — observed on the reproduction, *"the high-water reading answers the literal `max`, so a reader taking that instead falls back to the wrong figure."*

**H9a. The reading has two shapes and three outcomes, not one shape and two. Corrected 2026-08-22, and as it stood the rule fell through to nothing on a host that is not on the older kind.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md): on a two-card slice of a four-card host, **the older pair answered nothing** — *"`cpu.cfs_quota_us` and `memory.limit_in_bytes` both empty — the host is on cgroup v2 and the v1 paths do not exist."* The rental was sold as a **20-core** slice; `nproc` reported **40**, `/proc/cpuinfo` listed 40 processors, and `free` reported the host's **64 GiB**. **So on that box H9 as written had no input, and the fallback's stated trigger — the literal `max` — never fired, because there was no file to read it from.** **The scope of that observation, corrected 2026-08-23:** this said *the cgroup answered nothing at all*, and the batch records no reading of the **newer** paths — `cpu.max` and `memory.max` — on either machine. **What was observed is that the older pair was empty and absent on a host running the newer kind, and that no quota was readable by the route this document had.** Whether the newer pair would have answered on those boxes is unposed.

**Both path pairs are named, and the older is not assumed.** The reading is attempted at the newer paths — **`cpu.max` and `memory.max`** — and at the older — **`cpu.cfs_quota_us` with `cpu.cfs_period_us`, and `memory.limit_in_bytes`**. Whichever answers is the reading.

**And the third outcome is named rather than left to fall through.** Three cases, and only the first two existed before:

| What the cgroup reading gives | The reading says |
|---|---|
| a figure | that figure — the rental's allocation |
| the literal `max` | the `/proc` figure, which is the whole machine and is right, because nothing is capping it |
| **no route at all — neither pair present or both empty — on a machine `Rented-server runtime` K1's table places as a container, or does not place at all** | **the allocation could not be established**, carried as a stated absence, and the `/proc` figure is **not** substituted for it |
| **no route at all, on a machine K1's table places at its second row** — no container marker, the tool's container-only form finding no container, and systemd the first process | **the `/proc` figure, which is the machine's own**: the machine runs its own kernel and no control group caps it |

**The third row is the correction.** The `/proc` figure on a slice is the host's, and a reader that reaches it because the cgroup was silent gets the host's answer while believing it got the rental's — the eightfold overstatement H9 was written to prevent, arriving by a route H9 did not cover. **A stated absence is the only honest answer there**, and it is the same shape H8 already uses for missing per-card memory and H12 for the card scan on a container.

**And the third row's own footing is stated rather than borrowed from the observation above it. Added 2026-08-23.** **No box on record has been read at both path pairs and answered at neither.** The batch read the older pair on a host running the newer kind and found it absent; it did not read the newer pair, so its result is consistent with all three rows and demonstrates none of them. **The third row is therefore this document's own construction against a case nothing has posed**, and it is kept because it errs in the one safe direction — a stated absence never substitutes the host's figure, and the row it replaces would have. Label: **this document's rule**, not an observation.

**The third row is keyed on the machine kind, and the row as it stood caught every virtual machine and bare-metal server. Ruled R12, 2026-09-21, by the build runner under the Creator's standing delegation of 2026-08-31; no auditor has seen this change.** On a plain virtual machine rented on 2026-09-21, at the root of the control-group tree, **neither memory file exists** — label: **observed**, one machine on one seller (`Audits/Build/Step 10c/The first pass's walls, the placement — what was done.md`, outcome 6). **So the row written for a container slice put the ordinary machine into *could not be established*, and every screen said Smoozy could not read its memory when it had read it and nothing capped it.** That is the row saying something false, which is what Rule 8 forbids, in the direction the row was chosen to avoid.

- **The kind is the reading's own, taken first, and it is K1's table**: the container marker file, then `systemd-detect-virt --container`, then whether systemd is the machine's first process. **The first two are the ones this document already takes for [H12](#82-what-the-reading-is-made-of-and-every-part-of-it-is-a-trap-closed)**; the third is read from the first process's command name, the same reading `Server Setup` takes for K1's second row, so the two documents place one machine the same way. **A machine K1 would refuse is not a machine with its own kernel** and stays in the absence row.
- **Whether this tells a systemd-booted system container apart — it does, by the tool's own test, for every container technology the tool names.** `systemd-detect-virt(1)` documents `--container` as *"Only detects container virtualization (i.e. shared kernel virtualization)"* and names, among its container identifiers, `lxc`, `lxc-libvirt`, `systemd-nspawn` and `openvz`. Label: **documented** ([Sources](Sources/Servers.sources.md) 11.11). **So a system container of any of those kinds answers *container* whether or not it booted systemd, and keeps the absence row.** The option asks whether the kernel is shared, not how the guest started, which is exactly the question this row turns on.
- **What it does not tell apart, and the row does not rescue it.** A container of a technology the tool does not name, with no marker file and systemd as its first process, reads as its own kernel and would show the host's figure. **Nothing in the reading can see that case**, so it cannot be kept in the absence row by any rule here. It is carried as `Rented-server runtime` [§16](Rented-server%20runtime.md#16-unresolved) item 33, with what breaks.
- **The container and cgroup rows do not move.** A figure is still the allocation on any kind, and the literal `max` still takes the whole-machine figure on any kind. **Only the absence row is split.** `Rented-server runtime` V6 carries the same rule from the machine's side and the two stay identical.

**H10. Free space is a choice of mount and the reading names the path it was taken against.** Observed — a plain reading on one container returned **51 filesystems, 48 of them memory-backed**, and of the three that were not, one was *"the host's own 32 GiB disk bind-mounted in to deliver the driver files, showing 20 GiB free that the rental may not use"* (Fact 28). So the reading is `Server protocol and transfers` [F1 to F3](Server%20protocol%20and%20transfers.md#91-a-reading-is-a-choice-of-mount-and-the-mount-is-the-one-the-write-was-attempted-on)'s per-path reading, taking the **available** figure and never the free figure, and it is taken against **the path a job's folders sit under** — the same path `Queue & History` [G4](Queue%20&%20History.md#7-readings-taken-from-the-machine) reads, so the server list and a queue entry never disagree about one machine. Where that path does not exist yet, the reading is taken against its deepest existing ancestor and the record names the path it was actually taken against. **A figure derived from a filesystem list is forbidden**, and so is widening a per-path answer into a per-machine one.

**H11. Four card states exist, not two, and the discrimination is by the bus scan wherever there is one. Corrected 2026-08-22 — this said *three* and *by the bus scan alone*, and the table below now has a row for the case where the scan has no route at all.** Observed (Fact 46): a card present with no driver makes the driver's tool **simply absent, byte-identical to what a cardless machine gives**; a driver with no card gives `No devices were found`, exit 6. *"Anything concluding "this machine has no GPU" from `nvidia-smi` failing will misclassify a perfectly good rented A6000 as cardless — and on two of these three providers that is not a corner case, it is what they shipped."* So:

| Bus scan for the card vendor | Driver's own answer | The reading says |
|---|---|---|
| populated, **or the scan has no route** | answers | the cards, in full |
| populated | absent | **cards are present and cannot be read**, naming that the driver is absent |
| populated | `No devices were found` | the same, naming that the driver answered with none |
| empty | absent or none | **no card** |
| **the scan has no route** | **absent, or `No devices were found`** | **the cards could not be established**, naming that the scan is unavailable |

**The fifth row is a correction of 2026-08-22, and without it the table has no input on a whole machine kind rather than a lying one.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md): **`lspci` is absent on every Vast container in the batch — A, E and F** — and present on the Hyperstack virtual machine. `pciutils` is not in the image, and installing it is a package operation the pre-package reading of H14 is taken before. **So on that kind the scan does not return `empty`; it does not run.** Those two must never be collapsed, because `empty` is the one row that concludes *no card*.

**The fifth row is keyed on the driver's answer as well as on the scan, and that is a correction of 2026-08-23.** As written it read *anything* in the driver column, so a container on which the driver's own query answers honestly with the rental's cards was still ruled *the cards could not be established* — discarding a good reading on precisely the boxes the row was added for. [Section 16](#16-unresolved) item 2 records that **`nvidia-smi` was honest on both** of those hosts. **The scan is only ever a discriminator where the driver does not answer**: its whole job is to separate *no card* from *cards present and unreadable*, which is a question that does not arise once the cards are in hand. So a driver that answers is the reading, whatever the scan's state, and the first row now says so. **What does not change is the prohibition either way** — a missing scan never concludes *no card*, and a missing driver never concludes it either.

**H11b. Where the driver answers, the reading also carries the driver's version and the CUDA version the driver reports, and where that driver is below Blender's OptiX bar and Smoozy cannot change it, the user is told from the first connection. ### 8.3 Where the reading is taken, and why no Blender is in it

**H14. The reading is taken over the pre-package surface, under the login Smoozy holds, before anything is installed.** [The shape](The%20shape.md#each-rented-server) already places the reading on the pre-package surface — *"Readiness and package inspection, directory listing, file operations, free-space and hardware readings, and file transfer in both directions use it whether or not the server package is installed"* — and **that the reading is taken under the login Smoozy holds is this document's own clause**, not a quotation of that one. Together they are what make the promise reach a server the user has just added. *(Corrected 2026-09-02 at the stage-close gate repair: this presented as a quotation of `The shape` the string* "free-space and hardware readings are taken under the login Smoozy holds and before anything is installed"*, which is nowhere in that document. The nearest real sentence is quoted above and the login half is stated as what it is.)*

**H15. It is taken once per primary connection, on the three branches [H18](#84-the-installation-identity-over-all-of-it) names, in the first-connection sequence of [Section 10](#10-the-first-connection-in-order-rows-36-and-35)**, after the not-Linux check and after the installation identity is read, and never on a schedule. Nothing polls it and nothing re-reads it to keep a screen fresh — [State, identity and recovery](State,%20identity%20and%20recovery.md#84-nothing-is-polled-to-withdraw-a-record) §8.4 forbids the watcher and this document does not want one. **And it is not in `Desktop app and delivery` [3.3](Desktop%20app%20and%20delivery.md#33-ui-event-delivery) P10d's live-reading sequence** — that sequence's set is closed and names this reading out of it — so nothing re-reads hardware within a connected stretch either.

**H16. No Blender is in it, and that is a decision rather than an oversight.** A Blender already on a machine can be asked which cards it sees and can count them, with no window and on a machine with no display server. It is not used here for two reasons: **the promise covers any connected server, including one with no Blender on it** — which is the ordinary case at the moment a server is added — and **card memory has never been seen except through Blender's window, never with more than one card**, so the route answers less than the driver's own query does. The machine's own memory is not a Blender question at all. The route is recorded as considered and declined so a later reader does not take its absence for a gap. **A third reason arrived on 2026-08-22 and it is stronger than either.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md): from `--factory-startup` on a rented multi-card box, in both Blender versions, `compute_device_type` arrives as **`NONE`** while **every individual device in the list arrives with `use = True`**. **So Blender's own device list read as it comes is not a statement about what the machine has, nor about what Blender will use** — it shows every card enabled on a build that will render on the processor. A hardware reading taken through it would be right about the cards and wrong about everything a reader would infer. `Rendering` L21 owns the launch-side consequence.

**A fourth reason arrived on 2026-09-02, and it is the strongest of the four because it defeats the reading on a machine that has cards.** The repaired Blender research records Cycles' own card list coming back **empty** on a factory-fresh Blender in all four versions — untouched settings folder, and again started at factory settings — filling only once a refresh has been asked for, the preferences panel has been drawn, or a preferences file saved earlier is read. Label: **observed in a test** — `Preparation/Blender Research/Across topics/Running Blender with nobody there.md`, *The machine 5* (see [Sources](Sources/Servers.sources.md)). **So a machine asked cold gives the same answer as a cardless one, and this document's whole job at [H11](#82-what-the-reading-is-made-of-and-every-part-of-it-is-a-trap-closed) is telling those two apart** — the route would have fed the one row of that table that concludes *no card*. **The decline stands for all four reasons and nothing in the table moves.** **Where the third reason and the fourth disagree, they are not reconciled here**: the batch says the devices arrive switched on, the research says the list arrives empty, the batch's own record does not say whether its script called a refresh, and [Section 16](#16-unresolved) item 24 carries it.

### 8.4 The installation identity over all of it

**H17. Every held reading carries the installation identity present on the machine when it was taken, or the explicit absence of one.** §2.3 requires the carrying; the explicit absence is what makes the rule work for the ordinary case of a machine Smoozy has not prepared.

**H18. What each of §2.3's four branches does to a held reading, and the fresh reading is taken on three of them.**

| Branch | The held reading | The fresh reading |
|---|---|---|
| **present and equal, confirmed** | current; may be shown | taken and written under that identity, replacing the held one |
| **absent** | **disqualified** — the row returns to *never read* | taken and written under an explicit absence |
| **present and different** | **disqualified** — the row returns to *never read* | taken and written under the identity now on the machine |
| **present, supervisor did not answer** | **nothing is discarded**; it stays as it is and is shown as last seen | **none is taken** — nothing is read and nothing is written, so the held record stays exactly as it is |

**H19. It is a reading of the machine in front of Smoozy rather than a use of state Smoozy holds, which is exactly what a newly added, never-prepared server needs.

**H20. A container recycle is the case this exists for.** *"nothing in the connection distinguishes a recycled machine from a rebooted one"* — same address, same port, back in 90 seconds — so a remembered reading shown against a recycled machine would be a reading of a different machine. The disqualification is the one act that covers it, and it is a single act because the carrying rule is a single rule.

**H21. H19's argument does not reach the fourth branch, and nothing is taken there.** §2.3's requirement on that branch is not that the held value go unused but that it be **unchanged** — *"every machine-derived value held against this server row stays exactly as it is, neither used as current nor thrown away"* — and [H4](#81-three-states-and-the-cheap-implementation-has-two)'s *a reading replaces it whole* is exactly what a fresh reading would do to it. **H21a. That row's *none is taken* is about the hardware reading and about nothing else. Added 2026-08-22, scenario replays Pile 1 item R19.** [Q19](#10-the-first-connection-in-order-rows-36-and-35) re-takes step 5's **identity** read while the fourth branch stands, and takes no reading of this section's. ### 9.3 At the list (Row 46)

**P12. The check runs when the server list is drawn, once per server, over every server on it.** It runs for a connected server too, since *connected* and *needing a new key* can both be true. **Nothing polls in the background.**

**P13. **P16. The row holds the fingerprint of the key it uses and matches against it.** That is what lets a key be recognised as the one this server wants after it left Smoozy entirely and was pointed at again later. **The recognition is `Keys`'** — what a fingerprint is, and whether two keys can share one, is Fact 76 and that document's — and **Servers' half is that the row holds the fingerprint it needs and hands it over to be matched.** [Section 16](#16-unresolved) item 4 names the collision clause as `Keys`' residual.

### 10.1 Host trust comes first, and the scan decides (Row 36)

**Q3. The policy is settled and is not this document's to retake.** Silent first trust plus a user-decided replacement of a **changed** identity is Smoozy's own policy, Creator-stated 2026-07-17. It is **neither** SSH's own default, which asks before recording a new identity, **nor** the documented setting that accepts new identities without asking while still refusing changed ones — that setting does not deliver the accept path. **Carrying it out is this document's.**

**Q4. The offered host key is obtained by a scan that presents no credential, and the scan is what the decision is taken from.** Observed (Fact 82), in the observation's own words — the scan *"exited 0, wrote nothing to stderr"* and returned every key type the machine offers, and *"No identity file was supplied and none was asked for"*; and *"Two independent scans, minutes apart, returned byte-identical key material."* **The quotation is restored to the source's words 2026-08-23**, this having carried a one-line condensation of all three stated as a quotation of the fact; nothing it said went beyond what was observed. So the trust decision happens **before a connection presenting Smoozy's credential exists**, which is A5's requirement and the whole reason the accept-a-change path can be honoured at all.

**Q5. The comparison is against the value in the local record and never against a diagnostic string.** `Security and licence` §7 is exact and Fact 37 is why: **no OpenSSH manual documents a single one of the diagnostic strings the tools emit**, and a changed host key is observable at default log level only through a banner whose text is undocumented. **Nothing here parses a message.**

### 10.2 The three paths, and the two reads that close the gap between them

**Q6. The three paths are `Security and licence` §7's and are performed here.**

- **Nothing remembered.** The scanned key is recorded against the server and the connection proceeds. Nothing is asked and nothing is shown.
- **It matches.** The connection proceeds. Nothing is said.
- **It differs.** **The attempt stops before anything else happens.** The changed-identity warning is raised and the user decides. **Accepting** replaces the recorded value and repeats the first-connection path, and the attempt goes ahead. **Declining** keeps the old record, leaves the server disconnected, and the same warning returns on the next attempt until the user accepts or the machine answers with the identity Smoozy remembers.

**Q17. On a repair attempt the user did not start, the changed-identity warning is bounded to the declared break and not to the attempt.** Q6's *It differs* path is literal for a connect the user started and for the edit put-back, where [E6](#52-the-two-interruptions-on-one-path-and-they-are-not-the-same-kind) and [E7](#52-the-two-interruptions-on-one-path-and-they-are-not-the-same-kind) settle that the question is permitted because the user is standing in front of the act that raised it. Under the standing repair of [3.2](#32-the-standing-repair-which-never-ends-while-the-app-is-open) the next attempt is Smoozy's, fifteen seconds later, for as long as the app is open — so the bound is stated here.

- **The warning is raised once**, on the first attempt of the repair that meets a differing identity.
- **The run goes on** at [3.1](#31-a-run-and-the-two-figures-in-it) and [3.2](#32-the-standing-repair-which-never-ends-while-the-app-is-open)'s cadence, with the identity comparison still made at every attempt ([N9](#32-the-standing-repair-which-never-ends-while-the-app-is-open)) and **no further warning raised while the question stands**. Nothing stops the clock and nothing loops: [N2a](#31-a-run-and-the-two-figures-in-it)'s 105-second run span and [M4](#42-the-reconnect-policy-for-a-marked-period)'s 600-second wait are untouched by it.
- **Accepting** replaces the recorded value and the next attempt goes ahead. **Declining** leaves the record as it is and the standing repair goes on failing at step 1, the server reading *reconnecting* while a run is in flight and *disconnected* between runs, exactly as [N7](#32-the-standing-repair-which-never-ends-while-the-app-is-open) describes.

**Q7. The scan and the connection are two reads of the host key, and the throwaway file is what closes the gap between them.** Each connection attempt is given a throwaway known-hosts file holding **that server's approved entry and nothing else**, with the user's own configuration excluded, and the client is configured so that it can **neither ask nor accept on its own**. So the connection either presents Smoozy's credential to the machine whose key the comparison approved, or it does not connect at all. Where the file is written, that it is never written into `~/.ssh` or into any directory Smoozy scans for keys, that it is discarded when the attempt ends, and that any left behind by a process that exited first is swept at application start before any connection is attempted, are all `Security and licence` §7's and are performed rather than re-decided.

**Q8. Accepting is a choice to trust the machine and not a check that has been passed.** No fingerprint is shown at a first connection, at a changed one, in the warning, or in any log. There is nothing here for the user to check the machine against, which is silent first trust holding at the second connection as well as the first.

**Q9. A scan that gets no answer is not a changed identity.** It is a connection that could not be made, reported as one, with no claim about the machine's identity.

**Q10. What the promise does not catch, and it is observed rather than supposed. Re-decided 2026-08-22 on corrected evidence, and it catches less than this clause used to claim.**

**What this clause used to say, and the half of it that was wrong:** it read that container images *carry host keys baked in at build time*, and that the promise a change can be caught *reaches a virtual machine, which "generated its own host keys at first boot"*. **Both halves of that mechanism are now disproved.** The keys a container presents are **the host's**, not the image's — the same offer re-rented gave three byte-identical keys and a different machine on the same image gave three different ones ([The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md) Test 19). And a **virtual machine** was found to be **shipped** its keys in the image, not to generate them: files dated `2025-11-06 20:55:50` to the nanosecond, byte-identical after a recycle that destroyed everything else on the box ([The last two boxes](The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md) §17). The *generated at first boot* reading was an inference from cloud-init printing fingerprints, and [The host key](The%20host%20key%20—%20obtained%20without%20authenticating,%20and%20whose%20it%20turns%20out%20to%20be.md) now carries that correction in place.

**What the promise catches, stated on the true mechanism.** **Fact 83 is still answered negatively, and more widely than before.** A host key identifies **neither the rental nor the machine** — on a container it identifies the host, which outlives the rental and rents itself out again; on the machine kind observed it identifies the **image**, which every rental of that image shares. **So a replacement under one address raises no changed-identity warning on either kind**, and the promise that a change can be caught is not carried by the host key on any rented machine this project has seen. **A changed key still means something happened** — nothing here reads it as noise — but an **unchanged** key means nothing at all.

**What covers it instead is the installation identity of [§2.3](State,%20identity%20and%20recovery.md#23-the-machines-installation-identity)**, which is why nothing in this document is keyed on the host key ([D11](#63-the-remembered-host-key-row-37)). **That decision is vindicated rather than merely unaffected**: it was written against the container case alone and it holds against both. [Section 16](#16-unresolved) item 5 records the narrowing.

### 10.3 The not-Linux check (Row 35)

**Q11. It runs on the first connection to a server and before anything else acts on the machine** — ahead of the installation identity read, ahead of the hardware reading, ahead of any untracked-work read, and ahead of whatever a ticked setup option would do.

**Q12. How Smoozy tells: one reading over the command channel of the pre-package surface, asking the machine to name its own operating system, taken as a value.** The value is compared against the one value that means Linux; nothing is parsed for a cause, and `Server protocol and transfers` [1.3](Server%20protocol%20and%20transfers.md#13-what-the-surface-does-not-carry)'s rule that no tool's own output is mined for a cause is kept, because this is a value being read and not a failure being diagnosed.

**Q13. The check has three outcomes and they are not two.**

1. **The machine named the Linux value.** The sequence carries on.
2. **The machine named something else.** Smoozy says plainly that it is not a Linux machine and leaves the server **disconnected**. The sequence is abandoned at this step, so the connection the opening act was to make never becomes live and [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 5 ends the period the act began — the server reads **disconnected** and no repair runs under it ([N13](#33-the-three-places-repair-does-not-run-at-all)). The server stays in the list like any other, to be edited or removed. This is Row 35's promise.
3. **The machine named nothing Smoozy could read** — no answer, a refused command, an unreadable one. Smoozy says the first connection did not complete and what it knows, leaves the server disconnected, and **claims nothing about what the machine is**. That is the whole-app rule kept: Smoozy cannot tell three causes apart, so it never claims to know which it is. The sequence is abandoned here too, so [S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 5 ends the period and the server reads **disconnected**.

**Q14. The three outcomes are what make Row 35 keepable while Fact 59 is unanswered.** The promise is that Smoozy says so plainly and refuses once rather than letting every later action fail on its own, and outcome 2 keeps it wherever a machine answers at all. What Fact 59 would settle is **which machines land in outcome 2 rather than outcome 3**, and [Section 16](#16-unresolved) item 1 states what is and is not established.

**Q15. The SSH version banner is not used, and that is now an observation rather than a caution.** **Observed on the Creator's own Mac, macOS 26.5.2, 2026-08-19:** the banner is `SSH-2.0-OpenSSH_10.2`, carrying **no operating-system marker of any kind**, while a rented Ubuntu box announced `SSH-2.0-OpenSSH_8.9p1 Ubuntu-3ubuntu0.16` ([The host key](The%20host%20key%20—%20obtained%20without%20authenticating,%20and%20whose%20it%20turns%20out%20to%20be.md)). **So a bare banner is what a macOS machine gives and is also what a Linux build with no vendor suffix would give**, and the banner cannot separate **those two**. **That narrow claim is all this observation supports, and this clause said the banner was declined outright until 2026-08-21 — which is wrong for Windows.** Microsoft's own fork of OpenSSH — Microsoft's own overview page names `https://github.com/PowerShell/openssh-portable` as *"The Microsoft fork of this project"* — puts an operating-system marker in the version macro itself. Its `version.h`, read 2026-08-20 and re-read at `https://github.com/PowerShell/openssh-portable/blob/latestw_all/version.h` on 2026-08-23: `#define SSH_WINDOWS_VERSION "OpenSSH_for_Windows_10.0"`, with `SSH_VERSION` defined as that macro followed by `SSH_WINDOWS_BANNER`. Its `kex.c`, at `https://github.com/PowerShell/openssh-portable/blob/latestw_all/kex.c` in `kex_exchange_identification`, composes the identification string as `"SSH-%d.%d-%s%s%s\r\n"` with `SSH_VERSION` as its third argument, and RFC 4253 §4.2 puts that string on the wire *"When the connection has been established"*, before key exchange and so before any authentication. **The mechanism reproduces this project's own macOS reading as a cross-check**: the macro carries no `p1` suffix, and the Mac's banner said `10.2` where its binary says `10.2p1`. **So the banner does not separate macOS from Linux, and it does separate Windows from both.** Whether to use it for that is a design change and is `Servers`' — [Section 16](#16-unresolved) item 1 carries it and the one clause still unread. See `Preparation/Architecture/Sources/Servers.sources.md`.

## 11. The machine's work (Rows 42, 43, 40, 44 and 317)

**Constraint:** `Queue & History` [§17](Queue%20&%20History.md#17-what-this-document-supplies-and-to-which-document)'s handoff, taken whole — A1, A2, A5, C6, C7 and L13 to L17; `Rendering` [§8](Rendering.md#8-what-this-document-supplies-and-to-which-document)'s stop command and its deadline rule; Fact 60, closed against a real render; `Rented-server runtime` X6 and [The shape](The%20shape.md#each-rented-server) — **nothing is ever found by executable name, command-line pattern, or process search.**

### 11.1 The work is not remembered, and the period is what bounds it

**W1. The last-known queue reading is period-held and there is no durable cache of it anywhere.** `Queue & History` [C6](Queue%20&%20History.md#11-one-job-two-records-two-lifetimes) states it and names this document's period as the bound: process memory for the connected period, gone when the period ends. **This document's half is the period**, and [1.3](#13-what-the-period-holds-and-what-ends-with-it) is it.

**W2. So Row 28's *the work is not remembered* is that rule kept from this side.** Shown while connected; held as last-known for the rest of the run after a drop, because a drop does not end the period; absent on a fresh launch, because a launch has no period.

**W3. A last-known entry carries the moment it was taken and says it is not updating**, which is C7 and is Design's to word.

### 11.2 Work Smoozy is not tracking (Row 43)

**W4. The read is `Queue & History` [A1](Queue%20&%20History.md#13-reading-a-machine-and-adoption)'s queue reading and this document does not compose a second one.** One request, on demand, **after the installation identity confirms**, period-held, stamped with its moment and clock, returning the machine's whole working state. **It is never taken before the installation check confirms**, and on the absent or different branches nothing on the machine is read as Smoozy's at all. **The one request recurs within the connected stretch on `Desktop app and delivery` [3.3](Desktop%20app%20and%20delivery.md#33-ui-event-delivery) P10d's live-reading sequence — added 2026-08-22, scenario replays Pile 1 item R1** — still A1's reading, still no second one composed here; [Q18](#10-the-first-connection-in-order-rows-36-and-35) places it in the sequence of steps.

**W5. It runs on *any* connection, not only the first**, which is what the promise says, so it sits at step 7 of [Q1](#10-the-first-connection-in-order-rows-36-and-35)'s sequence on every connection that reaches it.

**W6. Tracked is told from untracked by the desktop's local record and never by anything on the machine.** `Queue & History` [A2](Queue%20&%20History.md#13-reading-a-machine-and-adoption): the reading reaches untracked and declined work because the store does not distinguish them, and *"identities it names are tracked; identities it does not are untracked."* **That is Row 43's *tell tracked from untracked* answered and cited.**

**W7. The offer is A5's and this document presents it.** One offer per machine, covering everything at once, composed from the reading, less any identity a history tombstone names. **Declining writes nothing durable, so the next connection that finds the work offers again** — which is the spec's *declining is not final*, delivered by the absence of a record rather than by a schedule.

**W8. It never resumes silently.** The offer is made and nothing enters the local record until the user accepts, which is A6's atomic write. **This is also the only route by which work abandoned by a *leave it be* removal ever comes back**, and it comes back only on a connection to a re-added server that succeeds.

### 11.3 An offer for work the current login cannot stop

**W9. The offer is not filtered by what the current login can do about the work, and no check of that kind is made in advance.** Two reasons, and the second is what settles it:

- **A5 composes one offer per machine covering everything at once.** Withholding part of it would leave the machine's state partly invisible, which is worse than an offer with a stated limit — the user would have work running on a machine they are paying for and no route by which Smoozy would ever mention it.
- **Smoozy cannot establish in advance that it could not stop a job.** Fact 60's refusal is discovered by trying, the existence probe by signal is refused too, and the shape forbids finding anything by process search. A pre-check would be a claim Smoozy has no evidence for.

**W10. What the offer does not promise is that an adopted job can be stopped.** Where an adopted job's stop is refused, that is the stop's own outcome and is reported as one, under `Rendering` [K10](Rendering.md#33-where-the-interrupt-does-not-take)'s bound — the stop was sent and the render had not ended when Smoozy stopped waiting, never *the render could not be stopped*. **Nothing anywhere promises otherwise, and nothing here adds a promise.**

**W11. `Queue & History` A5 as it stands admits this without moving**, and the question it does not answer is recorded as a seam at [Section 16](#16-unresolved) item 6 rather than answered in that document.

### 11.4 A username edit, and the work it leaves (Row 40)

**W12. Fact 60 is answered and closed against a real render: seen yes, stopped no.** From a second ordinary login **everything is visible** — both processes, owner, command line, thread count, start time — and **nothing can be stopped**: polite and forcible stops, a pattern kill of the render, and a pattern kill of every process of that login were all refused, and **all 44 threads survived**.

**W13. But Smoozy's own reach is narrower than *seen yes*, and this is the answer Row 40 actually gets.** Two things close it:

- **The supervisor's endpoint refuses any login but the one the installation was placed under.** `Security and licence` §8: *"The endpoint is reachable only by the login Smoozy holds; the supervisor rejects a request from any other local identity."* Fact 84 supplies the mechanism — peer credentials that *"cannot be lied to about who is calling"* — and Fact 60 supplies the observation: from the second login *"the endpoint's directory and the client binary were both `Permission denied`."*
- **The route Fact 60 saw the work by is forbidden here.** The shape and `Rented-server runtime` X6 are absolute: **nothing is ever found by executable name, command-line pattern, or process search.** A process listing is exactly that.

**W14. So after a username edit the work is neither seen nor stoppable through any route this architecture has.** The connection is made and authenticated; the installation identity may still be read from Smoozy's own state area over the pre-package surface, or may be refused by file permissions; **the supervisor does not answer**, so [§2.3](State,%20identity%20and%20recovery.md#23-the-machines-installation-identity)'s fourth branch is taken — *present, and the supervisor did not answer* — **nothing is discarded**, the supervisor-unavailable condition is raised against the server, and [§7](State,%20identity%20and%20recovery.md#7-reconciliation-on-the-desktop) stops at step 1. **[Q19](#10-the-first-connection-in-order-rows-36-and-35) re-takes the identity read while that branch stands, and here it never settles** — the login is the wrong one for as long as the edit stands — so the sequence runs and changes nothing, which is the correct outcome and not a route back.

**W15. Three consequences follow and each is stated rather than left to be met.**

1. **No queue reading is taken, so no adoption offer is composed.** Row 43 is **not** a route back to work abandoned by a username edit. The spec's own sentence — *"If a later connection finds that work again, it is picked up the same way as any untracked work"* — is conditional, and under the new login no later connection finds it.
2. **The route back is the username, and it is the user's.** Editing the username back to the one the installation was placed under restores every route at once, because nothing was destroyed: the work kept running, the queue and the journal are on the machine, and the next connection reads them.
3. **The jobs are abandoned in the fullest sense the spec allows.** They keep running there and Smoozy stops tracking them, which is what the spec says happens.

**W16. Smoozy is not quiet about it.** The supervisor-unavailable condition is raised and presented against the server by `Desktop app and delivery` [V1](Desktop%20app%20and%20delivery.md#12-the-automatic-supervisor-unavailable-repair-trigger), and the server connection is **not** marked down, which is that document's rule. So the user is told plainly that Smoozy could not read the machine, and nothing claims success over anything lost.

**W17. The spec now warns on a username edit on a server with live jobs, and this document's finding is why.** As written, the spec withheld that warning on the reason that a username change does not point the entry at another machine — true of the machine and not of the reach, which is what W13 to W15 establish. **The Creator ruled on 2026-08-19 that the warning is extended, and the spec says so**; `Audits/Specs/Servers/Decisions record.md` carries the Rule 7 line. **Nothing in W12 to W16 changes**: the mechanism is what it was, and what moved is what the user is told before it happens. [Section 17](#17-moments-that-reached-the-creator) records the escalation check that produced it.

### 11.5 Stop and clear, and what it says when it only partly worked (Row 42)

**W18. The mechanism is `Queue & History` [L13 to L17](Queue%20&%20History.md#4-acting-on-the-line)'s and this document neither chooses the order nor watches it.** Stop-and-clear is **one request, two ordered halves, applied on the machine**, the order held by the supervisor rather than watched by the desktop; both commands are recorded durably before anything acts, **so a connection dropping mid-way changes nothing**. The waiting jobs are cleared first and the running render is stopped second. **Where the clear's write is refused the stop is not attempted, and says so.** The stop command itself is `Rendering` [K5](Rendering.md#32-the-termination-contract)'s, exposed to this document.

**W19. The removal warning is composed from the period-held last-known record and from nothing else.** C7: *"`Servers`' removal warning reads this same period-held record; where Smoozy holds none, no warning appears."* So:

**The table is keyed on two facts and never on the two-value shorthand. Re-keyed 2026-08-22, scenario replays Pile 1 item R29** — as it stood the first column read *connected* and *disconnected*, and a period standing with a run of attempts in flight was in neither, while a period standing whose last-known reading holds **no** work had no row at all. The two facts are **whether a connected period stands**, which [K8a](#22-the-three-observed-values-and-what-servers-supplies) already publishes as one boolean, and **whether the primary connection is live**; [K6](#22-the-three-observed-values-and-what-servers-supplies)'s three observed values are compositions of those two and are not what a warning is cut on.

| A period stands | The primary connection is live | What the last-known record holds | The warning | What is offered |
|---|---|---|---|---|
| yes | yes | queued or running work | warns from the reading | both choices. **This warning cannot be switched off** |
| yes | yes | nothing queued and nothing running | none | a plain confirmation and nothing else — nothing to stop and nothing to clear |
| yes | **no** | work | warns from what Smoozy last knew, saying so | ***leave it be* only.** This warning **may** be switched off — one row in the one suppression table ([W20](#115-stop-and-clear-and-what-it-says-when-it-only-partly-worked-row-42)), so it silences this warning on every server at once, until warnings are restored in Settings |
| yes | **no** | nothing queued and nothing running | none | a plain confirmation. **Nothing is offered to stop or clear, and nothing is reached for to find out** |
| yes | either | **no record at all** | **none at all** | a plain confirmation. Smoozy does not reach out to find out |
| **no** | — | **no record at all**, by [S11](#13-what-the-period-holds-and-what-ends-with-it) | **none at all** | a plain confirmation. Smoozy does not reach out to find out |

**Row three covers the whole repair and not only part of it** — a run of attempts in flight and both of [3.1](#31-a-run-and-the-two-figures-in-it)'s and [3.2](#32-the-standing-repair-which-never-ends-while-the-app-is-open)'s pauses alike, which is every stretch in which a period stands over a connection that is not live. **So a *reconnecting* server whose last-known reading holds work is offered *leave it be* only**, and never *stop and clear*, which would have to reach a machine over a connection that is down.

**Row five is reachable while a period stands**: a connection that has not reached step 7 of [Q1](#10-the-first-connection-in-order-rows-36-and-35)'s sequence has taken no queue reading, which includes a connection sitting on [§2.3](State,%20identity%20and%20recovery.md#23-the-machines-installation-identity)'s fourth branch ([Q19](#10-the-first-connection-in-order-rows-36-and-35)) and a connection that dropped before step 7 ever ran.

**Row six is where a period-held record cannot outlive its period** ([S11](#13-what-the-period-holds-and-what-ends-with-it)): **a server the user disconnected by hand this run** — the disconnect ended the period and dropped the reading with it, which is [S11a](#13-what-the-period-holds-and-what-ends-with-it) — **alongside every case after the app was closed and reopened**. [Section 16](#16-unresolved) item 18 records the narrowing with the spec sentences it is read against.

**W19a. What the two ways out may be said to cost, before the user chooses. Added 2026-08-21, per Row 353.** [Design](../Design/Servers.md) offers them as statements rather than as buttons, so the screen states a consequence **before** the act, and the statement is only true if the machine behaves that way. **This document supplies what is true and does not word it.**

- ***Leave it running*** — the render carries on and Smoozy stops tracking it. That is [11.6](#116-disconnecting-does-not-stop-the-machines-work-row-44) and W22 together, and nothing about it is in doubt.
- ***Stop and clear first*, the order** — the waiting jobs are cleared first and the running render is stopped second (W18), one request in two ordered halves.
- ***Stop and clear first*, what the frames already written do** — they stay. `Rendering` [K7](Rendering.md#33-where-the-interrupt-does-not-take): *"what a stop leaves on disk is the frames, which are the user's."*
- ***Stop and clear first*, the frame being rendered, and this is the clause the evidence bounds.** The termination is `SIGINT` (`Rendering` K4), and it lands in one of two places. **Mid-render: that frame's file never appears and the frame does not arrive.** **During that frame's own write: the write finishes and the frame is whole** — K4 says so, and `Job files and outputs` C33 is the observation under it, *"An **interrupt** has never left a short image — not in one run, by anybody, in any version, on either machine, across hundreds of runs."*
- **So the outcome is one of exactly two and nobody can know which before the act.** **The statement this document can stand behind is that the frame being rendered *may not arrive*, and never that it *is lost*** — the flat form is false in the one case anybody has measured. **What the sentence is worded as is Design's**, and the drafted sentence said *is lost* when this was written, which is why it was recorded here rather than repaired in a document this stage does not own; [Design](../Design/Servers.md) changed it to *may not be saved* on 2026-08-25, per Row 353, which is the conditional form this clause asks for.
- **The half of the warning that is unconditional is the one worth keeping, and the evidence is stronger for it than for anything else here: nothing arrives damaged.** An interrupt has never left a short file at a frame's final name, and the frames already there are untouched. **A polite terminate and an outright kill each do leave a short file** (K4), which is exactly why the termination is an interrupt and not either of those.
- **And nobody is left guessing afterwards.** The completeness statement composed at the ending says which frames are there — Row 310's answer at `Rendering` 3.7 — so *may not arrive* is resolved into a fact the user reads, rather than into a doubt they carry.
- **This bounds what may be said *before* the act. W23 bounds what may be said *after* it**, and the two are separate: nothing may claim the render could not be stopped, because `Rendering` K10 and K11 make a failed stop and a slow one indistinguishable.

**W20. The switch-off is one row in the one suppression table** ([§10.3](State,%20identity%20and%20recovery.md#103-considered-and-not-filed)), carrying this document and this warning's identity, **which is declared here and is stable for the life of the application: `servers.disconnected-removal`** (`Desktop app and delivery` §15 G4–G5), and it is restored by the single whole-app control of Row 290. *(**Added 2026-09-12 by the build runner**, out of step 10a piece F. This clause said the row carries *this warning's identity* and **never said what the identity is**, here or anywhere — so under `Desktop app and delivery` §4 A7 and §15 G3 this module had not finished, and under G5 the spelling becomes permanent the day anybody first writes that row. Nothing writes one today, so nothing is lost by its having been missing. The prefix `servers.` is not decoration: piece F's ruling of the same day cut the table to one column on the reasoning that a module column would be the same fact in two places, so **the module lives in the identity string** and an identity without its module's prefix stops the row being *the module and the warning identity*.)* **The connected warning has no such row and no path can write one**, which is what makes *cannot be switched off* a structural fact rather than a rule to remember. The difference is the spec's own: the disconnected warning may be turned off because it can be wrong, and the connected one may not because it is not.

**W21. The three distinguishable results are L17's, verbatim, and this document presents them.**

| Result | What Smoozy says | What it asks |
|---|---|---|
| **could not begin at all** | that **nothing on the machine was changed** | whether to **try again** or to **remove the server and leave the work running** |
| **cleared and stopped** | what it did | nothing; the removal proceeds |
| **cleared and the stop failed or expired its waiter** | what worked and what did not — the waiting jobs went, and **the stop was sent and the render had not ended when Smoozy stopped waiting** | whether to **try the remainder again** or to **remove the server anyway and leave the rest alone** |

**A program that refuses the pair by name is *could not begin at all*. Added 2026-09-29.** Every release before the one whose program answers the clear refuses it, and nothing on the machine changed. What it may not be told as is a machine Smoozy could not reach, because Smoozy reached it. The same holds for `Desktop app and delivery` V15, whose update then goes on waiting (that document's V12).

**W22. Smoozy does not treat a machine it could not reach as a machine it cleared, and no path can produce that sentence.** The server row is removed only after the user has answered, and only where they answered *remove*. The enumeration of units and each unit's outcome are durable before the first unit is attempted ([§9.4](State,%20identity%20and%20recovery.md#94-the-outcome-record)), **so an interruption between doing the part and saying so loses the saying and never the fact** — the next presentation reads the record.

**W23. The middle result is the one the machine bills for, and the wording is bounded so it cannot lie.** `Rendering` [K10](Rendering.md#33-where-the-interrupt-does-not-take) is exact: Smoozy cannot tell a stop that failed from a render slow to honour it, so **nothing may claim the render could not be stopped**. What is kept is the spec's rule — Smoozy says rather than escalating quietly — and the words are Design's. **A render that honours the interrupt after the deadline records its own outcome**, and the expiry changed nothing.

**W24. Telegram's piece comes off on exactly one removal and this document decides which.** *Stop and clear first* is the one removal that reaches the machine, so on it — and on no other — the Telegram role's durable enabled-or-disabled desired state is set to **disabled** and the token file is taken off (`Security and licence` §10). **On *leave it be*, and on every removal of a disconnected server, nothing reaches the machine and the role stays exactly as it was.** What happens to the piece is `Telegram`'s; which removal reaches it is this document's and that is the whole of this document's part.

**W25. The machine-reaching removal's units, declared.** Three, in order: **the clear-and-stop ordered pair**, which `Queue & History` L16 already makes one unit; **Telegram's role off**, an independent unit reported like any other; and **the local forget**, which is atomic entire and runs last and only on the user's word. **The period ends with that third unit and not before** ([S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 6), because the first two reach the machine over the connection it holds.

### 11.6 Disconnecting does not stop the machine's work (Row 44)

**W26. A disconnect issues nothing to the machine.** It ends the period, drops what is period-held, and closes the connections under it. **No command is sent, no signal is sent, and nothing on the machine is told.**

**W27. The work survives because of how it was launched and not because of anything the connection does.** Observed — *"A render started detached survives the connection dropping"*, its parent the system itself, still writing frames after the connection was closed and a fresh one opened; *"A render **not** detached dies when the connection drops"*, ended at once with the frame in flight lost entirely ([The rented machine](The%20rented%20machine.md)). **The launch is `Rendering`'s and the machine-side arrangement is `Rented-server runtime`'s**, and this document neither chooses nor performs either.

**W28. *Resumes following* means re-attaching to something already running and never restarting it.** On the next connection, [§7](State,%20identity%20and%20recovery.md#7-reconciliation-on-the-desktop)'s steps read forward from the durable event cursor and take a fresh queue reading. **Nothing is re-submitted, nothing is re-launched, and nothing about the machine's line is written from the desktop.** The queue lives on the machine, which is `Queue & History`'s fact and the reason the promise holds at all.

**W29. The jobs waiting behind the render stay queued and run in their turn**, because the admission point that starts the next one is the supervisor's and needs no connection.

### 11.7 The edit warning, and where its knowledge comes from (Row 317)

**W30. The edit warning is not the removal warning and does not read the removal warning's source.** [W19](#115-stop-and-clear-and-what-it-says-when-it-only-partly-worked-row-42)'s table is composed from the period-held last-known queue reading and from nothing else, on `Queue & History` [C7](Queue%20&%20History.md#11-one-job-two-records-two-lifetimes)'s own naming of its one consumer — **and C7 names the removal warning, so this document extends it to nothing else.** The two warnings answer different questions. The removal warning states what is on the machine **now**, because *stop and clear first* acts on it. The edit warning states what the edit **puts out of Smoozy's reach**, which is a fact about Smoozy's own tracking rather than about the machine's line.

**W31. So the edit warning has two sources, taken in this order, and the second is durable.**

| The server, at the moment the edit is saved | Composed from | What the warning names |
|---|---|---|
| a period stands and a queue reading is held ([W4](#112-work-smoozy-is-not-tracking-row-43)), after [§7](State,%20identity%20and%20recovery.md#7-reconciliation-on-the-desktop)'s reconciliation has run | **the reading** | everything the reading shows on that machine, tracked and untracked alike ([W6](#112-work-smoozy-is-not-tracking-row-43) tells them apart) |
| no reading is held — a period ended by a disconnect, an application closed and reopened, or a launch that has not connected | **the durable local record alone** | the jobs this desktop tracks on that server for which it has learned **no ending** |

**W32. The durable set exists, and it is not a cache of the machine's state, which is the whole reason it may be read here.** `Queue & History` [C8](Queue%20&%20History.md#11-one-job-two-records-two-lifetimes) — the history record is *"Smoozy's own note, not a copy"* — and [C11](Queue%20&%20History.md#11-one-job-two-records-two-lifetimes): an entry whose machine never came back *"keeps the job with no ending Smoozy ever learned, shown as such, for good."* Job records are durable in the local record ([§1.1](State,%20identity%20and%20recovery.md#11-on-the-users-computer)) and each names the server it was submitted to. **D4 is untouched**: no queue reading becomes durable, no live figure is shown, and nothing is presented as current.

**W33. So W19's no-record rows do not reproduce here, and that is the whole of Row 317's answer.** The ordinary case the ruling of 2026-08-19 was made about — the user opens Smoozy, sees a disconnected server, and corrects a typo in the login name — has no period, no reading, and under the removal warning's rule no warning at all. It has a durable local record, because the jobs it is about are jobs this desktop submitted. **The warning appears.**

**W34. The warning built from the durable set says what it knows and never more.** It names **jobs Smoozy has not seen end**, never jobs queued or running: the durable record carries no line position, and a job with no learned ending may have ended hours ago (C11). **It is over-inclusive by construction and the wording must carry that.** The words are Design's; the bound on them is that nothing may state the work is still running. **W35. Where both sources are empty there is no warning, and that is a true statement rather than the removal warning's ignorance.** Smoozy tracks nothing on that server and learned an ending for everything it ever tracked there, so the edit abandons nothing of Smoozy's. **Untracked work is reached by the first source only**: where a reading is held it is named like anything else, and where none is held nothing can know of it without reaching out to the machine, which no edit ever does ([§1.2](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings)'s closed list).

**W36. **W37. **W38. ## 13. The connection identity (Row 24)

### 13.1 Four fields, and Fact 61 is closed

**C1. A connection identity is four fields: host, port, username, and a key reference.** Nothing is added for a gateway, and the row's shape is settled by the reading below rather than left open.

**C2. Fact 61 is answered by reading three providers' own documentation on 2026-08-19, and both halves come back the same way.** The exact words, the addresses and the dates read are in `Preparation/Architecture/Sources/Servers.sources.md`.

- **No provider read puts a server behind a gateway needing its own details.** All three document a single connection made with a host, a port, a username and a key. Where a provider offers a proxy route — two of the three do — **the proxy is an address and a port and not a second set of credentials**: the connection string is still one host, one port, one username, one key, and neither documentation names a jump host, a bastion or a second login step.
- **One rented machine handing out several containers, each on its own port, is documented rather than assumed.** One provider's own words: *"Each open internal port (such as 22 or 8080 etc) is mapped to a *random* external port on the machine's (usually shared) public IP address"*, and *"In essence each docker instance gets a fraction of a public IP address based on a subset of ports."* Another's: *"While SSH operates on port 22 within your Pod, Runpod assigns a different external port for access."*

**C3. So the spec's own duplicate check is resting on solid ground.** Host and port together name what Smoozy is reaching; the username and the key settle only who logs in once it is reached. **A different port means a different server**, and that is now a documented arrangement rather than a labelled assumption.

**C4. The port field starts at 22, the standard SSH port** — documented, `ssh_config(5)`: *"The default is 22."* A machine reached through a mapped port is reached at the mapped number, which the user reads off their provider's own interface and types in.

**C5. The four fields are held in the local record on the server row and nowhere else** ([6.1](#61-one-durable-store-and-one-row-per-server)), and all four must be filled in before the server can be saved, on an add and on an edit alike.

**C6. Nothing in this document is derived from a host, a port or a username.** [§2.1](State,%20identity%20and%20recovery.md#21-the-rules-that-bind-every-identity) rules 3 and 4 bind every identity, no path is synthesised from any of them, and the local server identifier is what everything is keyed on.

### 13.2 What the reading does not cover

**C7. Three providers on one date is what was read, and it is stated as that.** Provider pages change, which is why the date is recorded with each. A provider not read, or a machine at a corporate or academic host reached through a bastion, is outside it.

**C7a. One of the three pages was falsified in one respect by a rental of that same seller three days later, and this document records it rather than leaving it in the companion. ### 13.3 The pasted connection line

*Added 2026-10-04, on `Specs/Servers`' paragraph of that day (the Creator's want of 2026-09-21, asked for on 2026-10-04). No auditor has seen this subsection.*

**PL1. A pasted line is parsed as text and never run.** The parse is a pure function on the desktop, inside the Add dialog's handling: it opens no connection, starts no process, reads no file, and sends nothing anywhere. **A text pasted into the address field that begins with the word `ssh` and a space is handed to it**; anything else is an address, as before. Its result fills the host, port and username fields and replaces the pasted text with the host; the dialog's own checks — the four required fields (C5), the duplicate warning — then run exactly as on typed values, and nothing is written to the server row before *Add*.

**PL2. What the parse takes, and what it leaves.**

- **It takes the destination and the port, and nothing else.** The destination is `ssh(1)`'s own — the username before an `@`, the host after it — and the port is the value of its port option. **Which options take a value, so that a value is never mistaken for the destination, is `ssh(1)`'s own synopsis**, read from the manual and cited in `Preparation/Architecture/Sources/Servers.sources.md` by whoever builds it — never written from memory (Rule 2). **Read 2026-10-07 and cited at the companion's 10.9**: the value-taking options are `B b c D E e F I i J L l m O o P p R S W w`; the destination is `[user@]hostname` or `ssh://[user@]hostname[:port]`; and **the login option `-l` is a username too**, so a line giving one there is not a line with no username. Where the manual is silent, these are Smoozy's decisions, and the user sees every field before *Add*:
  - **an option is read wherever it stands**, before or after the destination, because Runpod's own documented line puts its port after it (the companion's 10.8). The first word that is not an option or an option's value is the destination, and every later word is dropped;
  - a value joined to its letter (`-p2222`) is that option's value;
  - where the destination names a username or a port and an option names another, the destination's own wins;
  - text in quotes is one word.
- **No port in the line is the port C4 already documents**, 22, because that is what the line means.
- **A line with no host or no username fills what it has and names what it lacks**, in one line under the field; nothing is guessed.
- **Everything else is dropped**: a key file, forwarded ports, any other option. The key is chosen in the dialog as always (`Keys`); a key file named in the line is a path on the user's computer that Smoozy has not been given, and no key is picked from it.

**PL3. A form that cannot carry files is judged only from a provider reading that has been filed.** The spec's rule: nothing is said about forms until one reading of the four providers' own connection pages is dated, quoted and filed in `Preparation/Architecture/Sources/Servers.sources.md` — the builder's first act. **Until then every form parses alike**. Where that reading finds a provider documenting a form that cannot carry files, how that form is told apart is written here from the provider's own words at that time, and a line of that form fills nothing and names the provider's direct form in one sentence. C7's limit carries over: what is read is those providers on that date.

**The reading was filed on 2026-10-07** (the companion's 10.8): Vast, Runpod, Hyperstack and Sesterce, each from its own documentation. **One form cannot carry files: Runpod's proxied line**, whose page says *"This method does not support commands like SCP (Secure Copy Protocol) or SFTP (SSH File Transfer Protocol)"*. **It is told apart by its host, `ssh.runpod.io`**, the only mark the provider's own words give, compared without regard to letter case. **Such a line fills no field**, and one line under the host field names Runpod's direct form, the one its console lists under *SSH over exposed TCP*. Vast's proxy form is documented as carrying data, so it parses like any other, as do Hyperstack's and Sesterce's single forms. *Added 2026-10-07 by the builder of step 10c's second notes, piece 15. No auditor has seen it.*

## 14. Declarations — atomic or partial

**Constraint:** [State, identity and recovery](State,%20identity%20and%20recovery.md#92-three-tests-applied-in-order-and-the-answer-is-declared-rather-than-inferred) §9.2 — *"Each feature document declares, per action, its partition unit and which of the three tests decided it."*

| Action | Partition unit | Test | Notes |
|---|---|---|---|
| **Connect** | the connection | 1 | The spec promises an outcome about connecting and about nothing smaller: the server is connected or it is not. The readings taken on the first-connection sequence are separate actions with their own outcomes; the two gates — host trust and the not-Linux check — are steps of this unit and their failure is its failure |
| **Disconnect** | the disconnect | 1 | Atomic entire. Nothing is sent to the machine, so nothing can half-happen |
| **Add** | the save; the connection where a setup option is ticked; the setup run | 3 | Independent units. **The server is always saved** whatever the other two do, which is the spec's own rule. The setup run is `Server Setup`'s |
| **Edit** | the save; the put-back | 3 | Ordered and independent. Where the save fails, the put-back is **not attempted**, naming the save. A put-back is merely useless without the save and not unsafe, so §9.3 does not apply |
| **Removal, not reaching the machine** | the removal | 1 | Atomic entire: one durable write removes the row and everything keyed to it, **and the period ends with it** ([S10](#12-the-closed-list-two-period-opening-acts-two-replacements-one-additional-connection-six-endings) item 6). An unconfirmed secret erase is a recorded debt and not a partial removal ([6.5](#65-what-a-removal-reaches-row-41)) |
| **Removal reaching the machine** | the clear-and-stop pair; Telegram's role off; the local forget | 1 and 3 | The pair is one unit by `Queue & History` L16 (§9.3, the second unsafe without the first). The other two are independent. The local forget is atomic entire and runs last and only on the user's word ([W25](#115-stop-and-clear-and-what-it-says-when-it-only-partly-worked-row-42)), **and the period ends with it** — the first two units reach the machine over the connection the period holds |
| **The hardware reading** | the reading | 1 | Atomic entire. A reading with a stated absence — no per-card memory, cards that could not be established — is a complete reading and not a partial one ([8.2](#82-what-the-reading-is-made-of-and-every-part-of-it-is-a-trap-closed)) |

**No unit here is retried inside its action** ([§9.5](State,%20identity%20and%20recovery.md#95-no-unit-is-retried-inside-its-action)). A repair run is not a retry of a connect: each attempt is its own action with its own identity, and the run is the period's repair rather than the connect's.

Added 2026-08-22, scenario replays Pile 1 item R30.** The single control on the row of a repairing server reads *disconnect*, and taking it drops the last-known queue reading and with it the removal warning's source, with nothing said before or after. **What was checked is whether this document should supply, beside [K8a](#22-the-three-observed-values-and-what-servers-supplies)'s boolean, a fact from which that could be said before the act. Declined.** The spec grants this disconnect as *"the ordinary disconnect"* with no separate action and no statement attached, so supplying the fact for one is putting something in front of the user that no spec says they get — [Method](Method.md)'s third moment, and the Creator's rather than this document's. **What is done instead is state the consequence where it is true** (S11a), which costs the user nothing new and is what [Rule 8](../Groundwork/Rules.md) requires of Smoozy about its own record. **The other half — whether the user should be told before disconnecting a repairing server — is a want and is raised rather than built.**

**Telling the user that a rented machine runs and bills until it is destroyed by hand ([11.8](#118-the-machine-runs-and-bills-until-it-is-destroyed-by-hand)). Added 2026-09-02.** A sentence is put in front of the user at every add, about a cost Smoozy does not control and offers no act against. **Declined, on three grounds.** It states a fact the spec itself already fixes — the machine is the user's, *"never rented, billed, powered on or off by Smoozy"* — so it introduces no cost and takes nothing away; it is no place to look, nothing to type and nothing that can be lost, being one sentence at an act the user is already taking; and it is not a warning, not a condition and not a gate, so it holds nothing up. **The opposite ruling would have been the escalation, and in two directions at once.** Saying nothing leaves a paid machine running with Smoozy silent about it, which [Rule 8](../Groundwork/Rules.md) makes a fault whatever the cause. And the only rescue anybody could build is an automatic destruction, which would destroy the work on the machine — the worse of the two failures, refused at [Rented-server runtime](Rented-server%20runtime.md#12-health-readings) V13 and not re-opened here.

**Where the remembered identity and the four secrets are held ([Section 6](#6-the-store-rows-25-28-37-38-and-41)).** **The escalation is spent:** the cost half of Fact 38 was ruled on 2026-08-16 and is now a promise in `Preparation/Specs/Whole app.md` — Mac remembers and accepts the system's own dialog after an update, Windows remembers silently, Linux remembers where the computer has somewhere to remember and otherwise asks each time and says so once. **This document was checked against that ruling and costs nothing beyond it:** the remembered identity is a field of the local record and not a store item, it is never shown and never asked about, and the one secret this document reaches — the machine password — is held under the store `Security and licence` §3 already chose. **No new place to look, nothing new to type, and nothing new that can be lost.** The escalation is not re-opened.
