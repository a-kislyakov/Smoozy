**F2. The worker writes no durable store itself.** Every durable fact it holds — its journal cursor, its Telegram update position, its 16-byte machine-routing key, its board and status-message identities, and the action-context records of [R1](#5-routing-naming-and-the-typed-requests) — lives in the Telegram worker's state store of [State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2 and is written by the supervisor on the worker's request through the ordinary command path, so S1's single-writer rule holds with no carve-out of this document's. **An accepted cross-machine instruction's authoritative durable home is the confirmed Telegram board entry of B8, outside every rental; no sender-local outstanding record is used to claim its survival.**

**F3. Both cursors advance after the work is done and never on receipt** (T2; §4 E3). For a Telegram update, *the work* is defined per kind below, and the kinds cover every update the listener can meet: for a routed action it is the full instruction, or a context-resolution instruction (R1, R1a), being present in a board edit the listener has read back exactly (B8); for an action on this machine's own job it is the command's submission to the supervisor being acknowledged; for an action refused because the bounded board cannot admit it, it is the truthful refusal being sent and the dismissal decision being durable; and **for an update this document ignores — one from another conversation, or one whose conversation cannot be established ([7](#7-the-conversation-proof-and-the-filter) P2, P3) — it is the recorded decision to dismiss it**, the decision alone and never the update's content. A worker that takes an update and dies before that point destroys nothing — the same updates came back *"identical, same ids"* when deliberately unconfirmed.

**F3a. A journal event whose send keeps coming back *not reached* does not hold every later event, and each such send is written in the worker's log. Added 2026-10-29, found by the Creator's two-server test (the twenty-first notes, note 8: the second server confirmed a job's start and then said nothing, though the job finished). Route (a) of `Audits/Build/Step 10c/The Creator's twenty-first notes — what each piece is, which files it owns, and in what order.md`. No auditor has seen it.** *Not reached* is a send that ended with no answer from Telegram: the line dropped, or the send was cut (C6a's note) — not a refusal, which C6a and the refused-and-not-sent rule already end.

- **Every *not reached* send is logged** in the worker's own lines with the event's journal position, the job identity where there is one, the message's kind and the try's count. Until this date such a send logged nothing, so a worker held at one event looked, from its records, like a worker with nothing to send.
- **A try counts against the event only when Telegram was reached by another send since the event's last try** — a heartbeat, a clock edit, an update read. While nothing reaches Telegram at all the line is down, nothing counts, and every event waits, late and not lost, as before.
- **After three counted tries the event is passed**: its message is not sent, the cursor moves past it (F3), and the worker sends one short user message in its place, under R7a's head: *A message about this job could not be sent.* That notice is tried by the same rule and, where it too is passed, is only logged, so no notice ever stands in for a notice.
- **An ending is passed like any other** under this rule: the user is told by the notice that something about the job did not arrive, and the desk's own entry still has the ending. C6a's *re-sent until it is accepted* stays the rule for a refusal, where Telegram answered.
- **Nothing else waits on it**: the status message, the heartbeat and other jobs' events go on as C6 orders them, so one server's stuck message never silences that server.

**Implementation seam, 2026-10-29, found by the Creator's two-server test.** The journal's sends run outside the listener's turn lock. Before a flood-wait retry whose full call timeout would meet the next renewal, the queue releases its serial slot and asks the listener to renew early through its ordinary board edit and exact read-back. Only after that confirmation does the retry get its full timeout. Like a file upload (C6b), that retry then occupies the upload lane, beside the serial lane, so a long retry cannot block the following heartbeat. If the listener is busy or the renewal cannot be confirmed, the retry is not started; its owner receives an unsent result and can try on a later turn. This also prevents a journal send from holding the lock the listener needs to renew. Each flood refusal and its wait are logged too, so an event that keeps honouring flood waits cannot look idle. F3a's try counts and notices are memory-only, like F3's per-event work; a restart starts the count again and can repeat a notice rather than silently pass a message. A pending notice is the last part of that event’s work for F3: the cursor passes only once the notice is sent, refused, or itself passed after three counted tries. Later events still run while it waits, so a crash before it is said replays the original event rather than losing its notice. No auditor has seen this paragraph.

**F4. The footing holds at the promise level.** A rented machine reached Telegram continuously for 24.022 hours — 578 calls, every one HTTP 200 with `ok: true`, no refusal, no gap over eight minutes (Fact 62, [Two more boxes](Two%20more%20boxes%20—%20the%20volume,%20the%20full%20disk,%20and%20a%20day%20left%20running.md)). ## 3. The slot, and the board

**Constraint:** Rows 257, 258 and 260 — one answer, per [Open Threads](../Groundwork/Open%20Threads.md)'s own statement that the listening question and the write protocol are one piece of machinery. T4 to T14 are taken as given ([Section 1](#1-the-t17-ruling)); what follows is the conversation's own conduct under T16. The observed ground: receiving is exclusive and the newest request always wins; reading the reported pin never disturbs the listener (168 reads, no refusals, a full 25-second poll undisturbed); any holder can edit any message the bot sent; a pin produces an update the listener hears; pinning is a stack, and the reported pin is the most recent pinned message **by sending date** (B13), so unpinning it reveals the next most recent by sending date, which is the one pinned before it only where messages were pinned in the order they were sent *(corrected 2026-09-14 from a code round — the bot and the chat, round 1, U2: this read "unpinning the newest reveals the older one underneath"; no auditor of this document has seen this correction)*; deleting a pinned message leaves the slot reading absent; a bot pins in a private chat with no administrator right.

### 3.1 The board

**B1. There is one shared pinned note and it is called the board: one message, created and pinned by the current slot holder, and the reported pin is the board in the steady state.** The board is the holder's own message, so T10 (a machine writes only into a message it created itself) and T11 (the note is written only by the slot holder) are both satisfied by construction, across every hand-over, because a hand-over creates a new board rather than inheriting one.

**B2. The board holds:** the holder's machine identity; the heartbeat — an opaque value the holder changes at every renewal, with the moment on the holder's own clock beside it; the **stated renewal interval** (T5's phrase), default 60 seconds; the **route mode** — asking, or registration-held ([4](#4-the-webhook-route-and-the-stale-registration) J2); the machine roster (B14); and the authoritative unacknowledged-instruction list (B8). It has one canonical, versioned serialization and every writer composes the complete candidate before editing. *(2026-08-29: the serialization opens with B23's plainly readable head — the head is what the conversation's service line quotes and what a phone's pinned banner shows; contents and bound unchanged.)* **The rendered message must be at most 4,096 characters after entity parsing, Telegram's published `sendMessage` and `editMessageText` bound; no writer sends an over-bound candidate.** An instruction or roster announcement that does not fit is not accepted, no existing entry is evicted, and the user is told which requested action or machine was not admitted and can try again after entries have left the list under B9's acknowledgement or B12's deadline rules. What the board's text looks like to a person is Design's, inside these contents and bound; the spec hands the conversation's arrangement and wording to Design, and `Preparation/Specs/Telegram.md` *Left for later* records it settled there on 2026-08-23, drawn in the mockup with no design document of its own. *(Until 2026-10-24 this said "the spec's own marker for the conversation's arrangement and wording covers it and is not cleared here", the marker written in its bracketed form. The spec no longer carries that marker.)* **What a board version costs a mixed fleet, stated:** machines are updated one at a time (L2), so two versions run at once; an older holder cannot read a newer machine's machinery message and unpins it without reading it (B11), so it may later say that machine *has not confirmed* work it did (B12). B3's stale-board rule is what keeps a newer board whose holder is gone from leaving older machines standing down. *(Added 2026-09-14 from a code round — the bot and the chat, round 1, U3. No auditor of this document has seen this text.)*

**B3. Taking the slot preserves accepted instructions before it moves the pin.** A machine whose ask is accepted (T4's rules decide when it may ask) first processes and unpins transient machinery messages until it can read the current board. It validates that board's serialization and copies its full unacknowledged-instruction list by identity. It then sends its own fresh board containing that list, pins it, and confirms the exact content by reading the reported pin back (T12). **Only after that confirmation does it unpin the previous board by that board's specific message identity**; an unpin without an identity is never used for this replacement. Thus a death before the new pin leaves the old board authoritative, and a death after it leaves the new board authoritative. Notifications are off in a private chat whatever the pin call passes (documented; [Sources](Sources/Telegram.sources.md)). *Observed otherwise, 2026-10-18, Creator-stated: a phone announced every pin made this way in a private chat; see B24. No auditor has seen it.* The janitor then removes any older board pins by their recorded identities until the new board is the one reported. A malformed or over-bound old board is not silently replaced: the claimant stands down and reports the board unreadable, because it cannot prove it preserved the accepted instructions. **Except where that board is stale.** A board the claimant cannot read **whose text has not changed across a full renewal interval**, on B5's own test — compared for equality only, between completed readings on the claimant's own clock, over the claimant's own stated interval since the unreadable board's cannot be read — is stale: the claimant starts its fresh board, unpins the unreadable one by its identity once the fresh board is confirmed, and tells the user plainly that instructions on the unreadable note could not be carried over. A live holder of any version changes its heartbeat, and so its board's text, at every renewal (B4), so it is never replaced by this rule; this keeps B5 and B7's promise that a holder which stops renewing is replaced within an interval and a read for the one case that broke it — a board from a later version whose holder is gone. *(Added 2026-09-14 from a code round — the bot and the chat, round 1, U3, the consolidator's call. No auditor of this document has seen this text.)* **The fresh board's roster is the copied roster with the claimant itself added, where B2's complete candidate fits** — under B14 this is how a machine alone on the bot gets onto its own roster, so its own jobs are in its gathers (R10, R13). **The reads by which a claimant waits out a report of nothing pinned after an unpin (§21 item 33) are spaced about half a second apart**, so one turn's reads cover the whole wait before nothing pinned is believed; B11's re-pin of an absent board waits the same way. *Added 2026-10-18, the Creator's fourteenth notes, note 2, with the two independent checks of that day folded in (`Audits/Build/Step 10c/The independent check of one pin per server — Claude Opus 5.5.md` and `… — GPT-6.1-Sol.md`). No auditor has seen it.*

**B4. The heartbeat is an edit of the board, confirmed by read-back (T12), on the renewal interval.** A holder whose read-back returns content that is not its own board has been displaced: it stands down (T4) and touches nothing.

**B5. Staleness is detected without subtracting across clocks.** A stood-down machine reads the reported pin on B13's cadence and asks again only when what it can read has shown **no change of the heartbeat value** — or no readable board at all — continuously for a full renewal interval **measured between its own reading moments, on its own clock**. The heartbeat value is compared for equality only and never subtracted from anything, which is [State, identity and recovery](State,%20identity%20and%20recovery.md#3-desired-state-and-observed-state) D5 kept exactly. A reported pin that is not a board (a machinery message in flight, B10) is *no readable board* for this rule and never a fresh heartbeat.

**A read that did not complete is not a reading of anything, and the interval accumulates only across readings that completed.** A refused, cut-off or unanswered read advances the interval by nothing and resets it by nothing; it is never counted as *no readable board*, because *no readable board* is something a completed read observed about the slot and not something the reader failed to reach. **And a machine that has not completed a read for a full renewal interval treats itself as out of contact and does not ask at all** until it has completed one. Without both halves the staleness test measures the reader's own reach rather than the holder's liveness, and T4 and T6's *newest asker wins* would hand the slot to the machine on the worst connection, again at every recovery.

**B6. Bootstrap.** A machine whose role worker starts reads before it asks: it asks only after B5's condition holds from its own first reading. Where several start together, the collisions resolve themselves — the newest asker wins, the refused stand down (T4, T6) — and cost nothing but seconds.

**B7. Which machine holds the slot is emergent and no machine is preferred.** A machine that dies releases the slot by not asking (T7); the recovery latency is bounded by the renewal interval plus a read, and nothing else arbitrates. Nothing in this arrangement requires a machine to reach another machine (T8).

### 3.2 The write protocol, and how an instruction crosses machines

**B8. An accepted instruction between machines is T13's request, and its authoritative durable home before acknowledgement is the board, outside every rental.** One list entry carries the protocol version, operation identity, addressee address, subject identities, action, complete payload, source update identity and acceptance moment. **The addressee address is the machine identity for a full action instruction; for a context-resolution instruction it is the one address the listener actually possesses — the token's 16-byte machine-routing key for a tap (R1), the source message identity for a reply (R1a). A role worker recognizes an entry as its own by equality against its own machine identity or its own machine-routing key — the machine identity in its role configuration ([20](#20-what-this-document-supplies-and-to-which-document)) and the routing key in the Telegram worker's state store ([State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2) — or by holding an action-context record bound to the entry's source message identity; no address is translated through the roster or any registry, and B13's read is what carries every entry to every enabled role worker.** For R1's indirection, the complete payload may instead be a **context-resolution instruction** carrying the opaque action token and callback evidence — or R1a's typed request and reply evidence — to the issuing machine; the resolved machine then replaces it by identity with the full action instruction before that action can be submitted. **B9. Delivery runs through the board.** The holder carries every unacknowledged instruction on the board's instruction list. - **An instruction entry whose protocol version the addressee does not speak** is never acted on, never partly acted on, and never guessed at. **The addressee records it as refused for that reason and acknowledges it** (B9), so the user is told in plain words, naming the server — that its Smoozy is an older version and could not do this — **and never that the machine *has not confirmed*** (B12), which would say the machine was silent when it answered.

**B11. **B12. An acknowledgement is observed or the user is told.** The holder keeps and re-presents an unacknowledged instruction until the acknowledgement is observed; an addressee that finds an instruction it has already acted on still on the board acknowledges again, harmlessly. The board entry carries its own reporting deadline, so whichever holder owns the board when that deadline passes says plainly that the machine has not confirmed; nothing is assumed delivered and nothing is converted into anything else. **This rule is for action instructions only. A state-request (R10) is completed by its reply and not by an acknowledgement**, under R12's own deadline, whose expiry is already answered by the gather's own *did not answer* line — and its entry leaves the board at that completion or deadline, removed by whichever machine then holds the board, which composes the gather's one message from the replies B11 fed it; the deadline is measured per holder exactly as R1's expiry is, so a gather that survives a hand-over costs latency, never silence. **A context-resolution entry (B8; R1, R1a) is not an action instruction either: it is a question addressed to one machine, and nothing has been acted on until it is replaced by the full instruction** — so it is completed by that replacement, and it expires under the deadline it carries, R1's for a tap and R1a's for a reply. **B13. Cadences, chosen and labelled.** **Every enabled role worker reads the reported pin every 2 seconds, whether or not it has anything live** — one cadence, and no second tier. **B14. ## 4. The webhook route, and the stale registration

**Constraint:** Row 257's webhook clause; Fact 63; [Security and licence](Security%20and%20licence.md#13-the-inbound-boundary-at-a-rented-server) §1.3, which no document may harden in either direction; and `Rented-server runtime` §10.2's hand-over — *the slot is held by the registration rather than by asking, and `Telegram` owns what removes a stale one.*

**J1. The webhook route is an optional path and nothing in this document needs it.** Fact 63's answer is provider-shaped: a webhook works where a provider permits one and needs nothing bought, and a URL naming a Vast container's own mapped port is refused, because the provider's port allocator assigns from its own range and Telegram accepts only 80, 88, 443 and 8443, refusing everything else in as many words. **Narrowed 2026-08-21: this said *cannot host one at any price*, and that generalises a fact about one address into a fact about a machine.** Telegram's own page constrains the **URL** — `setWebhook`'s `url` parameter, *"HTTPS URL to send updates to. Use an empty string to remove webhook integration."*, and the same method's Note 3, *"Ports currently supported for webhooks: 443, 80, 88, 8443."* (`https://core.telegram.org/bots/api`, read 2026-08-23) — and says nothing about the machine running the bot's code or what it is rented as, so a URL naming some other address on one of the four ports is excluded by nothing observed or documented. **Whether such an address can be put in front of a container is not settled and nothing here needs it.** The receiving call answers everything this module needs on any rental, and every rule in [Section 3](#3-the-slot-and-the-board) works on it alone.

**J2. Where the route is taken — a provider that permits it, and only ever the one machine holding the registration (§1.3) — the registration is the slot and everything else stands.** The registration holder keeps the board, the heartbeat, the janitor role and the instruction list exactly as an asking holder does; the board machinery is receiving-route-agnostic. Registering is written into the board so every machine can read that the slot is registration-held. Registration never passes `drop_pending_updates` — `setWebhook`'s own optional parameter, *"Pass True to drop all pending updates"* (`https://core.telegram.org/bots/api`, read 2026-08-23) — because queued updates are the user's messages, observed to survive sixty-seven minutes intact, and nothing here discards one.

**J3. The stale-registration removal, and it is this document's alone.** A registration proves nothing about reachability, and one `409 Conflict` covers both *a poll while a webhook is registered* — `Conflict: can't use getUpdates method while webhook is active; use deleteWebhook to delete the webhook first` — and *two pollers competing* — `Conflict: terminated by other getUpdates request; make sure that only one bot instance is running` — distinguishable only by the description text (observed; [Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), [One box](One%20box%20—%20the%20Telegram%20capture%20and%20the%20port%20that%20cannot%20be%20chosen.md)). So the heartbeat test alone cannot tell a dead registration from a live asker, and the rule joins the two signals: **a machine that meets B5's staleness condition and whose ask is then refused with the webhook-form description removes the registration with the documented removal call — *"Use this method to remove webhook integration if you decide to switch back to getUpdates"* ([Sources](Sources/Telegram.sources.md)) — never passing `drop_pending_updates`, and then asks under T4.** A live registration holder is protected by the same rule that protects a live asker: while it maintains the board's heartbeat, B5 never fires. A holder that cannot maintain the board is a holder that can tell nobody anything, and taking the slot from it is the arrangement working.

**What the removal's own answer is read from, and it is not the description text. Added 2026-09-02 at the stage-close gate repair, on Fact 103's builder rule.** The call was run on 2026-09-02 and **both its answers carry `ok` and `result` true** — *"Webhook was deleted"* against a standing registration and *"Webhook is already deleted"* against none — so **the description string is the only thing separating them and Telegram publishes neither.** A rule turning on it would be turning on an unpublished string. **So the pair of readings around the call is what decides**: `getWebhookInfo`'s `url` before it, and `getUpdates` succeeding rather than refusing after it — both published, both observed, and sufficient on their own. **The description may be recorded and may not be depended on.** **What this costs is nothing the rule needs:** the two readings are what recover the slot, and the description would only have let this document say *why*.

**J4. The route's remaining detail is unresolved and no promise rests on it. Narrowed 2026-09-02 by reading; what is still owed is one thing rather than four.** The POST wrapper, the `X-Telegram-Bot-Api-Secret-Token` header's use, the retry cadence against a failing endpoint, and the endpoint's authentication under §1.3's own requirements were all owed — `Security and licence` §14 item 12, inherited here as [Section 21](#21-unresolved) item 5. **Three of the four are now answered from Telegram's own pages, and the fourth on two of its three parts** ([Section 21](#21-unresolved) item 5; [Sources](Sources/Telegram.sources.md) entries 45c and 51a): the header is a value Smoozy chooses at registration and Telegram sends on every request, which is what §1.3's endpoint authentication was owed and which makes it one more secret of `Security and licence` §10's existing class rather than a new mechanism; the retry conduct is published as *repeat and give up after a reasonable amount of attempts*, with no number, alongside a 40-default bound on simultaneous connections; and the registration's own `allowed_updates` settles the filter question P6 handed here. **What is still owed is the wrapper's content type alone** — ~~the POST wrapper alone — the method, the content type and the body of the request Telegram makes to an endpoint~~ **narrowed again 2026-09-02, later the same day**: `setWebhook`'s own opening sentence publishes the method and the body, *"we will send an HTTPS POST request to the specified URL, containing a JSON-serialized Update"* ([Section 21](#21-unresolved) item 5(c); [Sources](Sources/Telegram.sources.md) entry 45d), and the earlier narrowing read the sentence after it and not that one. The content type of Telegram's request is named on neither first-party page and wants one registration against one reachable endpoint rather than a further reading. **Until it closes, no build takes this route; the asking route is complete without it**, and none of the three answers above changes a single clause of [Section 3](#3-the-slot-and-the-board), which never touches a registration.

## 5. Routing, naming, and the typed requests

**Constraint:** Rows 259, 261, 273 and 296. The observed ground: a tap arrives as a `callback_query` carrying the whole of the bot's original message and exactly the string the sender wrote on the button; a reply carries the id and text of the message replied to; both routes were run and correctly identified across machines; two presses of one button arrive as two updates.

**R1. A button carries one compact opaque action token and no full routing context.** Telegram publishes `callback_data` as **1–64 bytes**. Smoozy's token is the unpadded base64url encoding of exactly 33 bytes — one format byte, a 16-byte Telegram machine-routing key and a 16-byte action-context identity — so it is exactly **44 ASCII bytes** and has no user text, label, job identity, hold identity, action or payload inside it. The issuing machine first writes the action-context record durably through its supervisor. **The record binds the source message's identity, which exists only once the message is sent, so a message is sent without its buttons, its records are written against its identity, and only then are the buttons attached** — to a picture or a video by `editMessageReplyMarkup`, which Telegram's page describes as the method *"to edit only the reply markup of messages"* (documented; [Sources](Sources/Telegram.sources.md) entry 45e), and to a text message by that call or by an edit that keeps its text. **The page does not say which kinds of message that call accepts**, so that it is accepted on a photo and on a video is not established by reading and is for the live pass to see. Adding buttons to a text message by an edit that keeps its text is observed accepted (entry 84). *(Added 2026-09-14 from a code round — the bot and the chat, round 1, U4. No auditor of this document has seen this text.)* That authoritative record binds the token to the proved conversation identity, source message identity, owning machine identity, job and hold identities where present, action, complete payload, and the subject generation/state in which the action is valid. **Every button shows its label, because Telegram's contract has no other kind of button**: `InlineKeyboardButton`'s `text` field — *"Label text on the button"* — carries no *Optional.* mark on a page whose stated convention is *"Optional fields may be not returned when irrelevant."*, and the keyboard itself is *"an inline keyboard that appears right next to the message it belongs to"* (documented; [Sources](Sources/Telegram.sources.md)). So a message carries a keyboard only where it offers at least one visible tappable action, no keyboard is ever attached for resolution's sake, and a reply resolves by R1a's route, never from a keyboard.

**Resolution fails closed.** The listener uses only the routing key to address B8's context-resolution instruction to the issuing machine, which recognizes the key as its own from its state store; no roster or registry translates it (B8, B14). That machine compares the token, conversation, source message and live subject generation exactly and returns the stored context; a missing record, unknown format, expired subject, wrong conversation, wrong source message or mismatched generation is rejected and nothing is submitted. A successful resolution replaces the resolution entry on the board with the full instruction under the same operation identity. Action-context records are subject-held: they remain while that exact message and actionable job or hold state remain, and are removed when the message is superseded or the subject generation ends. Identities in the authoritative context remain opaque and load-bearing; labels never are ([State, identity and recovery](State,%20identity%20and%20recovery.md#21-the-rules-that-bind-every-identity) §2.1 rule 3).

**Expiry answers, never guesses.** The tap's context-resolution entry carries the listener's own deadline (R12's shape: a deadline belongs to the waiter), **default 10 seconds — the same default as R12 and R1a, not a third number, resting on the same order**: strictly greater than B13's 2-second read cadence, and wide enough for the whole board round trip this shape needs — the listener's board edit and its read-back, the addressee's next read, its replacement, and the holder's read-back, each of which waits on that cadence. **Corrected 2026-08-23: this said *roughly seven times the slowest observed resolution round trip (R5's 1.4 seconds)*, and no resolution round trip of this shape has ever been observed.** R5's 0.7 to 1.4 seconds were measured on a run that carried the routing context on the button itself; R1's context-resolution instruction crossing the board did not exist when they were taken, so they are not a measurement of what this deadline waits on. **The number is Smoozy's own choice, ordered against B13's cadence and against nothing observed** ([Section 21](#21-unresolved) item 22). An entry still unreplaced when it passes is removed from the board by whichever machine holds the board at that moment — the listener that boarded it may itself be gone — under the carve-out B12 states. The deadline is carried on the entry as an interval, and each holder measures it on its own clock from the moment the entry entered its board — acceptance (B8), or the hand-over copy (B3) — so nothing is subtracted across clocks (D5's discipline, B5's shape) and a hand-over restarts the measurement, costing latency and nothing else. The expiry changes nothing durable anywhere, exactly as R1a's: no action-context record is touched, nothing is submitted, and the removal is the whole of it — B15's late-replacement refusal is what holds *nothing is submitted* against a replacement still in flight when the entry was removed. **The user is answered rather than left silent**: the holder that removes the entry says plainly that the machine the action was addressed to has not responded and nothing was done — R3's rule; wording Design's. The message the button rides is another machine's and is never edited (T10), so a later press mints a fresh entry with a fresh deadline (R4), and a machine that is gone for good answers every press this same truthful way.

**R1a. A reply resolves by the replied-to message's identity, against the same authoritative action-context records.** A reply carries the id of the message replied to (the observed ground above) and no token, and its own text must be one of the two typed requests (R13, R15): *status* is R10's gather whatever it replies to, a reply whose text is neither request is R3's case, and ~~the resolution here serves the frame request alone~~ *the resolution here serves `frame`, `stop` and `reporting` (widened 2026-10-31, below; no auditor has seen it)*. The listener holds no map from a message to its issuing machine and builds none: it appends one context-resolution entry to the board (B8) whose addressee address is the **source message identity** — the one address the reply supplies — carrying the proved conversation identity and the typed frame request as payload. Only the machine whose action-context store holds a record bound to that exact source message identity and conversation *(or, from 2026-10-31, whose register holds a line for it: R1b)*, with a live subject generation, replaces the entry with the full instruction under the same operation identity — the action is the typed request over the record's subject and owning-machine identities, never the record's stored action, so no label and no message text routes anything (R7). Where the records bound to that message do not agree on one subject — R13's disambiguation message is such a message — no replacement is made. **Expiry falls back, never guesses** *(for `frame`; `stop` and `reporting` fail closed from 2026-10-31, below)*: the entry carries the listener's own deadline (R12's shape), measured and removed exactly as R1's expiry is — by whichever machine then holds the board, on its own clock — changing nothing durable, and that holder then handles the request exactly as if it had been typed without a reply — R13's disambiguation, from the typed request the entry's payload carries. So a reply to a message with no record costs one deadline and lands where the plain typed request lands, and a successful replacement is R14's routed frame request, unchanged from there on.

**R1a, widened: a reply makes `frame`, `stop` and `reporting` act on the replied-to message's job. Added 2026-10-31, a want entering at Specs (`Specs/Telegram.md`, *A command sent as a reply*), Creator-stated in the Telegram discussion of that day: *"Reply is for a job, no reply asks for what exactly, and reporting is for everything if it's not a reply."* No auditor has seen it.**

- **The entry.** Each of the three, sent as a reply, boards R1a's one context-resolution entry addressed to the source message identity, its payload naming the request (`frame` with its number or none, `stop`, `reporting` with its value or none). **Only a frame request with a number carries the `frame` field**, so a machine on an older release reads every other entry as one it cannot read, rejects it and replaces nothing; it never half-reads a stop or a reporting change as a frame. `status` stays R10's gather whatever it replies to.
- **Who claims it.** The machine whose register (R1b) holds a line for that message and conversation, or, for a message sent before the register, whose action-context records bound to it agree on one job (R1a above). **A status message's line names no job of its own: it is about the job that message shows now** (C1), and about no job when it shows none. A record whose Stop was taken off at the job's end (C1b) no longer speaks for the message.
- **What it becomes.** `frame` — R14's routed frame request for that job: the number typed, or, with none, the frame of the picture replied to where the line names one, or else the newest (R13a). `stop` — D0's confirmation for that job, opened exactly as a press of *Stop this job*; an ended job is answered *This job has already ended.* and nothing is stopped. `reporting` — V1c's change for that one job, a first-frame pair together, the job's own machine answering under R7a's head *Reporting set to “Alerts only” for this job.*; with no value the five buttons of V1d are offered for that job alone, and an ended job is answered *This job has already ended. Nothing was changed.* **The phone's choice and the app-wide default are untouched** (V1d is the request with no reply).
- **About no job, at once.** A reply to a message the listener knows is about no job — the board (B3), a message its own register marks as no job (its *Which job?*, its status reply, its refusals and asks), or, where the reply shows it, a message the user sent — is handled at once as if typed with no reply, and no entry is boarded.
- **Fails closed.** At the entry's deadline nobody has claimed it: `frame` falls back as R1a above. **`stop` and `reporting` are never widened** to *Which job?* or to every job: the holder that removes the entry answers *Could not tell which job that message is about. Nothing changed.*, and nothing is submitted (R3). The user aimed at one job, and offering others invites the wrong tap.

**R1b. Every message a machine sends to the conversation is registered with what it is about. Added 2026-10-31 with R1a's widening. No auditor has seen it.** Once Telegram accepts a send, the sending machine writes one line in its Telegram worker's state store (`State, identity and recovery` §1.2): the message identity, the conversation, and one of three — **a job and attempt**, with the frame and View Layer for a frame's picture; **this machine's status message**; or **no job**. A line is written after the send and never before, so a crash between the two loses one line, which costs that message's replies R1a's deadline and nothing else. **The register is bounded**: a job's lines go when the machine no longer holds that job's record folder (R13's candidate rule), and the store keeps at most 2,000 lines, the oldest leaving first. **The same rule ends a job's action-context records** (R1's *subject-held*): they stay while the folder does, so a late press on an ended job's button still answers *This job has already ended.* (C1b), and they leave with it. **A record issued for another machine's job, or for no job** — the listener's *Which job?* buttons and V1d's ask — **leaves with its message's line** (added the same day, by the builder: those have no folder on the issuing machine to follow). A machine that is gone, off or on an older release holds no line anyone can reach, and its messages' replies meet the deadline.

**R2. The listener routes and enforces nothing.** It uses R1's routing key, or R1a's source message identity, only to reach the issuing machine for resolution. An action whose resolved owning-machine identity is the listener's own is submitted to its own supervisor command path (U10). Any other is an instruction to that resolved owning machine (B8, B15), submitted to the **owning** machine's supervisor there — the machine that holds the job, which is U10's carriage sentence kept. *Holder* is this document's word for the machine holding the slot and is never used for the machine holding a job; the listener never assumes itself the owner.

**R3. An update the listener cannot resolve is answered, never guessed at.** A tap whose token or authoritative context fails R1, or a reply whose text is neither of the two typed requests, gets a plain answer saying it expired or no longer matches; a reply whose subject resolution fails falls back by R1a's own rule instead of being refused; nothing is submitted anywhere from a failed resolution. Wording is Design's.

**R4. Each action press is one instruction; a Stop press first opens D0’s confirmation and is not a stop instruction.** *Changed 2026-10-23 for sixteenth note 7; this heading formerly read “Each press is one instruction.”* A `callback_query`'s own id seeds the instruction's operation identity, so two presses are two instructions, and the second lands on the machine's own idempotency and arbitration: a second answer to a hold acts on nothing and the conversation reports which answer was applied and when (U13, U14; [Queue & History](Queue%20&%20History.md#3-held-jobs) H4 holds for a phone exactly as for the desk); a second stop finds the recorded outcome (`Server protocol and transfers` C4, C8).

**R5. Timing is stated, not promised, and it is timing of a different shape.** A tap reached the right one of two machines in 1.4 seconds and of three machines in 0.9 and 0.7 (observed); B13's cadences bound the ordinary case. **What those figures are not: a measurement of R1's resolution round trip.** The run that produced them passed the routing context on the button itself, and R1 routes through a board-carried context-resolution instruction that did not exist when they were taken, so nothing here reads them as this shape's number and **no deadline in this document is set as a multiple of them** (R1, R1a, R12; [Section 21](#21-unresolved) item 22). Anything slower is reported by B12's deadline machinery rather than retried into a second action — the reporting deadline for an unacknowledged action instruction, the resolution expiry for an unreplaced context-resolution entry.

**R6. The answer never goes to the machine that asked** — it goes to whichever is listening (observed, and it follows from receiving being exclusive) — and this document never writes a rule that assumes otherwise.

**R7. Every message names the machine and the job by their labels** — the server label `Servers` owns, the job label `Queue & History`'s note holds whole (N1) — with its routing held behind R1's token. Row 261's danger is defused by construction: **nothing is ever routed by a label**, so a stale label misleads a reader and can never land an action on the wrong job — the action a message's token resolves to is bound to the job identity that message was actually about.

**R7a. Every user message opens with one head, in one look, and the rest follows one rule. Added 2026-10-29, Creator-stated, the twenty-first notes, note 5 (`Specs/Telegram.md`, *Every message looks the same way*). Telegram has no Design document, so under Rule 10 this clause is the look. No auditor has seen it.**

- **Line one: the server's colour mark, a space, and the server label in bold.** The mark is one character chosen from the label's colour (L1): red 🟥, gold 🟧, green and jade 🟩, cyan and blue 🟦, violet and magenta 🟪. Two hues share each of the last three, and nothing routes on the mark (R7). A machine with no colour told yet sends the bold label alone.
- **Line two, for a message about a job: the job label in italic**, then, where the message is about one frame or a stretch, ` · Frame 147` or ` · frames 101–140` in plain text. A message about the machine alone — C1's status message, the idle message (V3), R10's reply per machine — has line one and then its own lines, a job named in them in italic.
- **Then the message's own words. Where it reports a state, the state word comes first**, capitalised and ending in a full stop: *Started.*, *Finished.*, *Failed.*, *Stopped.*, *Abandoned.*, *Needs your answer.*, *Waiting for driver update.* The rest is plain: numbers, sizes, durations and frame ranges in plain text, never bold and never in the fixed-width face. **So no message repeats the job label in its words**: *Kitchen — final finished.* reads *Finished.* under the job's line.
- **A picture's caption takes the same two-line head**, its second line continuing with the frame, the View Layer and *Not colour-accurate* as I2 has them; an album's pictures keep their own short captions under the album's head. An album's companion (C1b) and A3a's question take the head too.
- **A failure keeps the red dot every failure in Smoozy carries**, sent as the red circle character 🔴 before *Failed.* — a circle, because in Smoozy a circle is a state and a square is a server. No other message carries a mark of its own.
- **Button words stay plain**: a button's text takes no marked ranges (Sources entry 88). *Stop this job*, wherever it is offered, carries Telegram's `danger` style; every other button carries none. Nothing reads the style back, and an app that does not draw it loses nothing.
- **Sent as an entity list beside the text, in B25's manner, never as parse-mode markup**, so no label needs escaping whatever characters the user gave it. Offsets and lengths are counted in UTF-16 code units, as the page defines them (entry 88); the mark is counted with the text. On a machinery message B25's spoiler range is unchanged; R7a applies to user messages only, and no reader relies on any range.

Added 2026-08-25 per Row 470; the values are the drawing's (`Preparation/Design/Mockup/Smoozy.html`, the `#stgbot` dialog), which is this module's design of record.** The name is the literal string `Smoozy`, the same for every user's bot. The block is drawn at random from the twenty-six lowercase ASCII letters and the ten decimal digits — thirty-six characters, never an underscore. ## 7. The conversation proof, and the filter

**Constraint:** Row 262, its spec marker — `[PENDING: how Smoozy proves a conversation is the user's, and how the token is kept — Architecture]`, which this section and [Section 8](#8-the-token) settle and **whose clearing was the runner's and was done on 2026-08-23**; `Preparation/Specs/Telegram.md` now carries *Label: settled at Architecture (2026-08-23)* in its place. *(Corrected 2026-09-02: this read* whose clearing is the runner's*, present tense, ten days after the marker was cleared.)* And Fact 66.

**P1. The proof is possession at setup: the conversation the walkthrough's Start arrived from is the user's, because the user made the bot, holds its token, and pressed Start in it.** Its identity — the conversation identifier every update carries — is recorded in the local record against the bot, and delivered to every machine as part of the role material (Row 91), then kept current through the told-record.

**P2. Every machine answers the proved conversation and nothing else.** Every update carries the conversation it came from (observed on every update seen), so the filter is one comparison: an update from any other conversation is **ignored — never answered, never logged with its content, never routed.** Answering would tell a stranger the bot is alive; ignoring tells them nothing.

**P3. An update whose conversation cannot be established is ignored too.** The default is silence, so an update of a shape nobody has observed fails closed. **Only a person’s text request or button press is answered. Start (`/start`, also with a bot username or setup payload) belongs to pairing and gets no command reply; bot-authored messages and service messages get no command reply either. Pin service updates still reach the coordination reader.** *(Added 2026-10-28, found by the rented pass: Start was being answered as an unknown request. No auditor has seen this addition.)*

**P4. A replacement token for the same bot keeps the proof; a new bot needs a new proof.** The bot survives token replacement whole — same id, same username, and the confirmed update position holds (Fact 67) — so the proved conversation still belongs to the same bot and the walkthrough is not re-run. A different bot is a different conversation: the full proof runs again (S5).

**P5. The thing being filtered has never been produced, and that clause closes unresolved.** Whether a stranger can reach the bot at all, and what the bot sees when they do, is **answered on Telegram's own pages** — anyone may start a chat with a bot, and in a private chat the bot receives everything (item 2, corrected 2026-08-21; this used to say it needed a second Telegram account the Creator must supply, and it does not) — [Section 21](#21-unresolved) item 2. The filter above is complete on Smoozy's side without it, which is the whole of what the promise needs.

**P6. A second filter sits beneath the conversation one — it lives on the token, and every receiving call names what it wants. Added 2026-08-29 from Fact 102's record; it is not Row 506's promise and no spec sentence covers it.** Observed, 2026-08-29: the bot's token was carrying a leftover `allowed_updates` filter naming `my_chat_member` alone, and it silently dropped every ordinary message — `getUpdates` answered `{"ok":true,"result":[]}` while the user had genuinely written, nothing was queued or delayed, and a message dropped this way is gone. **The setting lives on the token every machine shares, so one caller setting it changes what every other machine can hear; it is invisible in an ordinary call's answer and is revealed only by `getWebhookInfo`.** Naming the wanted kinds on a `getUpdates` call reset it, and the dropped sender's next message arrived. **The rule:** every `getUpdates` call Smoozy makes — the listener's ask under T4, and the walkthrough's one desktop poll (S5) — **names the wanted update kinds explicitly, on every call, never relying on the token's standing filter**, so the fleet's hearing is re-asserted at every ask, every machine names the same kinds, and a leftover filter from any earlier holder of the token is displaced by the first ask. The kinds named are exactly those F3's work covers, and **their published identifiers are now in a record of this project's — [P6a](#7-the-conversation-proof-and-the-filter) names them, from the reference page read 2026-09-02** ([Section 21](#21-unresolved) item 29, closed; [Sources](Sources/Telegram.sources.md) entry 45b). *(This read* their published identifiers are in no record of this project's and are owed at item 29 *until 2026-09-02.)* **The webhook route's half is answered with it and no longer rides item 5**: `setWebhook` carries an `allowed_updates` parameter of its own, worded identically to `getUpdates`', *"If not specified, the previous setting will be used."* included — so a registration made without naming kinds carries the standing filter forward and one that names them replaces it, the same field and the same rule rather than a second mechanism, and P6's *on every call* covers a registration exactly as it covers an ask. *(This read* whether a registration carries or resets the filter is in no record either; it joins item 5's owed remainder *until 2026-09-02. **P6a. The kinds Smoozy names, and why it is two. **The heartbeat is a board edit and therefore a send, and it is never deferred past the renewal interval by any report send** — that is the rule its class carries. A heartbeat stuck behind a picture backlog until the interval passes lets every stood-down machine meet B5, ask, and take the slot from a live holder, which is the *newest asker wins* hazard this whole order exists to suppress.

**C6b. A file upload runs in its own lane beside the serial sends, and is never cut for the heartbeat. Added 2026-09-14 by the build runner, from a builder's finding; the reasoning is `Audits/Architecture/Telegram/Decisions record.md`. Labelled C6a when written, which the refused-send rule below already was; relabelled the same day, meaning unchanged.** Held to C6's one send in flight, an upload in progress when the renewal falls due had to be cut, so on the holding machine any file taking longer than about fifty seconds was cut at every renewal, and on a slow line a moving picture (M4) or a failure's words file (E3d) from that machine might never arrive — a promise quietly broken. **So a send that uploads a file — a moving picture, a words file, an album — goes in a lane of its own, one upload at a time, and runs to its end or to its own failure.** Every other send stays in C6's single serial lane in C6's order, and the heartbeat in that lane is never deferred, now because nothing in it waits on an upload. **What it does not change:** the per-chat pace of C3 is counted in messages, and an upload is one message however long it takes; frame pictures from the derivative set (I1–I3) are small and stay in the serial lane.

**And at most one clock edit is ever outstanding: a tick that falls due while one is in flight is dropped rather than queued.** The message shows the current state, so a superseded edit has no value, and at C2's cadence a queue of them would starve every class beneath it. That rule is what keeps pictures and media reachable at 0.2 edits per second, and it is also why a stretched clock costs currency rather than a backlog.

**C6a. A refused send is honoured and re-sent; it is never dropped and never treated as delivered.** Added 2026-08-21 — **the document had no rule for a refusal at all, because it believed the case did not arise.** A response with `ok` false and `error_code` 429 carries `parameters.retry_after`, an integer of seconds, documented under `ResponseParameters` on the reference page (read 2026-08-20). The worker waits that many seconds and re-sends the same message, and the wait blocks that machine's single in-flight slot rather than the class order — so the order in C6 above is unchanged and a refusal on one class does not reorder the rest. **Two things this fixes rather than styles.** A refused **ending, hold or drop** would otherwise have no defined outcome, and it is the class C6 puts above the clock precisely because it must not be lost; it is re-sent until it is accepted, and B12's at-least-once already covers a duplicate. A refused **clock edit** falls under the superseded-edit rule instead — the tick is dropped and the next one carries the current state, because a stale reading re-sent late is worth nothing. **Where `retry_after` is absent from a refusal**, the worker waits one second and re-sends, which is the only value this project has ever observed in that field. **What this does not do is pace the fleet**: nothing here stops three machines summing past the published per-chat rate, and item 4 carries that. *(**The re-send after a wait is never cut short for the heartbeat.** Where the heartbeat falls due within the re-send's own time, the heartbeat goes first, in C6's order, and the re-send then runs with its whole time. Until this date a re-send that met a due heartbeat was given two seconds and cut, which came back as not reached and, under F3, held every later event of that server. Two servers sharing one chat's limit make that wait common on the holder. Added 2026-10-29, found by the Creator's two-server test, the twenty-first notes, note 8; F3a bounds what is left. No auditor has seen it.)*

Bursts at the depths tried were absorbed by the service by delay (observed); refusals were observed on registration and carry a wait-this-long field (C6a); and **the published per-chat rate is one message per second, which this design is at 22% of at rest and over under load** — item 4's clause, with the arithmetic. **Corrected 2026-08-29: this said 62%, the flat interval's figure, which C2's fleet-wide rate of 2026-08-25 replaced.** Which pictures are sent at all is the job's own reporting settings (V1). *(And, under V1a's fourth member, how often: I2a. Added 2026-10-19. No auditor has seen it.)*

**C7. The status message's identity is durable, so no restart orphans one.** The board's identity is durable already (F2); the status message's is recorded in the same Telegram worker's state store, beside it, and **the recorded message is re-used across every restart**. Without that, every reboot, crash and restart would leave a frozen second message in the conversation under the same server label R7 names the live one by, and a user who scrolls to it reads more than twenty minutes of no update and concludes under C5 that the machine has stopped while it is rendering. At C2's cadence the live message moves 720 times an hour and the dead one never, so the two are further apart than any reader would expect and neither is marked. **A new status message is created only where the recorded one cannot be edited, and where a new one is created the old one is edited to say it is superseded.** The status-message identity is a named content of the Telegram worker's state store — [State, identity and recovery](State,%20identity%20and%20recovery.md#12-on-each-rented-server) §1.2 lists it beside the board identity, the two cursors, the machine-routing key and the action-context records, which is F2's list exactly — and the store-inventory seam this sentence once recorded is closed ([Section 21](#21-unresolved) item 14).
