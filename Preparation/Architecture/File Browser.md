## What binds this before anything is decided

**The transfer contract is `Server protocol and transfers`' §7 and it is taken entire.** Staging, integrity, resume, publication and cleanup, in both directions, for the whole of the machine's life: part-arrived bytes never sit at a final name (7.1 clause 1); the staging path is synthesised from the transfer identity and never from the file's name (S4); no tool ever chooses a staging name (S5); the progress record is durable on the desktop before the first byte (S7–S9); a resume verifies the staged prefix against Smoozy's own record (S12); the three endings do three different things with staged material (S26); a transfer is bound to its server and to nothing else (T3); admission is one point per server and one desktop-side point above it (T5); priority is a declared class and no class is starved (T8, T10). **No second transfer, staging or resume shape is invented here.** S13 assigns the unchanged-source answer for a file on the user's own computer to Row 201 by name, and [Section 9.3](#93-the-unchanged-file-row-201-and-fact-30) is that answer.

**`Servers` §15 hands four supplies whole**: a connection bound to a server and to its period; the two labels of its 12.2 that decide whether an upload resumes; the per-server session pool and the additional connection of its 1.4; and the free-space split — its figure is the server list's remembered one, this document's is the browsing one, both per-path under `Server protocol and transfers` F1. **A period ending drops every live reading, so a listing goes stale rather than empty** — [1.5](#15-the-listing-cache-and-the-stale-listing-row-198) is written against that sentence. Its 8.5-shaped constraint and `Server protocol and transfers` C18 bound everything here that could notice the line is down: no ping, no request made to find out, the connection condition read from `Servers` and never derived.

**`State, identity and recovery` §1.1: the local record is the only durable store on this side.** Four things this document keeps could tempt a second store, and each is placed against that sentence: the upload request's record and the source-path record are one §9.4 outcome record in the local record ([3.1](#31-the-request-and-its-record-row-190), [5.3](#53-the-source-path-record-row-187)); the partial's record is `Server protocol and transfers` S9's, already in the local record; the listing cache is process memory and durable nowhere, its lifetime stated per period ending at L16 rather than by a class name ([1.5](#15-the-listing-cache-and-the-stale-listing-row-198)). Its D4 and D5 bind every reading below — a reading carries its moment and its clock, readings on different clocks are never subtracted, and no durable copy is kept of an observed machine state the machine still holds. Its §9 partition discipline is applied per action in [Section 11](#11-declarations).

**The machine evidence is frozen snapshots and is read as such** — *this is what that box did on that day*, never *this is what a rented machine does*. The observations this document leans on hardest:

- **Nothing on the machine distinguishes a part-arrived file from a whole one** — identical mode, permissions, extended attributes, inode flags, allocation and file-type output — and an interrupted overwrite left a **40,000,000-byte hybrid**, *"Neither version, plausible size, no marker"* ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 18). Rows 191 and 197 rest on Smoozy's own record because of this.
- **Seventeen hostile names out, fourteen back, three destroyed on arrival with every fetch reporting success** — the loss at the Mac end, the rental keeping every variant distinct ([One box with Blender on it](One%20box%20with%20Blender%20on%20it%20—%20the%20reading,%20the%20listing,%20and%20the%20names%20that%20do%20not%20come%20back.md) §7). The up direction survived byte for byte, spaces, Cyrillic, Japanese, emoji, newline and tab included; **the down direction's loss is Row 303's and `Download`'s and is not read across to Row 186.** What it does establish for Row 192 is that the pair of filesystems disagree about names.
- **A name of 255 bytes is accepted and 256 is refused; a path of 4095 is accepted and 4096 is refused** — the refusal at open, before any byte is sent, reading `Bad message`, *"anything surfacing that string to a user reports the wrong problem entirely"* — and **the make-parents form returns success against an existing folder**, the silent collision path (same document, §7; Fact 29; corroborated *"255 accepted, 256 refused"* on three further machines across three sellers, with `statvfs@openssh.com` reporting `f_namemax` **255** on all three). **The unit is bytes, not characters.** **Corrected 2026-08-23: this said *refused at 255 bytes and a path at 4095*, stating each bound as the refused length rather than as the accepted one — a pre-flight built on that wording refuses a name the machine takes.**
- **A listing yields all four fields in one reading on both routes**: 5010 entries at 52 round trips on the file-transfer subsystem, the epoch form the unambiguous clock, and **partial output delivered before a connection dies — a truncated listing and a genuinely short one separable only by exit status** (same document, §5; Fact 7).
- **A full disk refuses identically everywhere at `No space left on device`, errno 28, and afterwards nothing at all can be written** ([Two more boxes](Two%20more%20boxes%20—%20the%20volume,%20the%20full%20disk,%20and%20a%20day%20left%20running.md), Fact 28) — so no record this document needs may be a marker written on the machine at the moment things go wrong. A part-written file a full disk cut off *"stays on disk under its final name"* at the size it reached ([The rented machine](The%20rented%20machine.md)).
- **Elevation differs by machine kind**: ordinarily present on a virtual-machine rental, often passwordless; **a container's non-root login has an elevation route that demands a password Smoozy does not hold** — `sudo -n` demands a password, `/root/onstart.sh` and `/etc/rc.local` are both `Permission denied`, and switching to root fails authentication — and root inside a container holds 13 of 41 capabilities (Fact 27, corrected 2026-08-22). **The outcome downstream is unchanged, on the register's own follow-on sentence** — *"a password Smoozy does not have is as good as no route"* — so [P5](#22-the-elevated-retry-row-180)'s *no offer* stands. ## 1. The listing

**Constraint:** Row 183 — *"For every file: its name, its size, when it was last changed, and its kind"* — with Rows 182, 184 and 198, quoted at their sections. How the list is laid out, sorted and shown is Design's; what each shown value is worth is settled here.

### 1.1 One reading, on the subsystem route (Rows 183 and 191)

**L1. A folder is listed by the file-transfer subsystem's directory reading on the connection's long-lived reading channel** (`Server protocol and transfers` 1.1 item 2), and the four fields — name, size, last-changed time, kind — come back in that one reading, batched. Observed: a 15-entry folder cost zero per-file stats, and 5010 entries cost **52 round trips rather than 5010**, 18.22 s on that route on that box (Fact 7). **No reading here ever issues a stat per entry**, and no ordinary listing is taken on the command channel — which program would answer it on an arbitrary rental, and whether its output survives Fact 37's caution, are unestablished ([Section 13](#13-unresolved) item 9). The one exception is the elevated retry of [2.2](#22-the-elevated-retry-row-180), which runs on the command channel because no *configured* subsystem carries elevation (P6) — **corrected 2026-08-22: this said the retry *has no subsystem route at all*, and P6 stopped saying that on 2026-08-21 because it is stronger than OpenSSH's own documentation supports.**

**L1a. A name that comes back from the machine is carried as bytes and decoded only for display, and a listing that decodes eagerly is forbidden. Added 2026-08-22, observed.** [The multi-provider batch](The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md): a directory listing that decoded entry names as UTF-8 **raised** on a non-UTF-8 name — `UnicodeDecodeError('utf-8', b'bad\xff\xfe.txt', 3, 4, 'invalid start byte')` — **while the write, the read-back over the subsystem and the machine's own `ls` all handled the same name.** **So the failure is the reader's, not the machine's, and it fails a name Smoozy is otherwise able to move.** The rule: the enumeration holds every name as the bytes the subsystem returned, every comparison and every path built from it uses those bytes, and a decode happens only at the point a name is shown — where an undecodable byte is replaced for display and never for identity. **This is X1's rule for the local side stated for the machine side**, where it was missing; `Server protocol and transfers` [Section 12](Server%20protocol%20and%20transfers.md#12-unresolved) item 12 records it as the second in-Smoozy instance of the same hazard.

**L1b. What those bytes become when they cross to the transfer surface is ruled once, and not here. Added 2026-09-06; no auditor of this document has seen it.** `Server protocol and transfers` [§2](Server%20protocol%20and%20transfers.md#2-request-framing-and-versioning) **P7** settles it for the whole seam — bytes on the machine side, the receiving system's own path unit on the desktop side, text only at the point a name is shown — and names `Desktop app and delivery` C3's name check as the single place one becomes the other. **This document restates none of it and holds no second version of it.** L1a above, N2 and X1 are that one rule seen from this module's own side and are unchanged by it.

**L2. No reading of a listing is line-oriented, and no rendered line is ever parsed.** A newline in a file name splits a listing across lines on both routes ([One box with Blender on it](One%20box%20with%20Blender%20on%20it%20—%20the%20reading,%20the%20listing,%20and%20the%20names%20that%20do%20not%20come%20back.md) §10), which is `Job files and outputs` N15's rule and it binds this document identically: every reading takes the protocol's own fields.

**L3. Output arrived is never read as listing complete.** A truncated listing and a genuinely short one were both four lines, separable only by the ending status (Fact 7). A listing is complete when the subsystem reports its end; a listing cut by the connection is no listing, and the cache of [1.5](#15-the-listing-cache-and-the-stale-listing-row-198) keeps the previous complete one rather than the fragment.

**L3a. A channel-lease change never turns a partly read directory into an accepted File Browser enumeration. Added 2026-09-01, closing the first audited seam with `Server protocol and transfers`.** That document's §1.1 item 2 names the transport fact: reopening loses the server's place, and retaining the entries already returned while discarding them from the second pass can still miss a name added or moved behind the new cursor. That continuation is sufficient for a best-effort walk and insufficient here — [X2](#41-the-walk-row-191) forbids a collision count wrong in the quiet direction. **For an interactive listing and for every directory of X1's already-exists walk alike, File Browser discards that directory's whole in-progress result after a lease change and reads the directory again from its beginning on the reopened channel. Only one open-to-end pass is accepted.** The last complete cache entry remains on screen until the replacement pass is accepted; the already-exists question starts no transfer until every required directory has an accepted pass. The cost of one lease change is therefore one current directory read again, and repeated lease changes repeat that cost while the reading continues to report underway. **This does not claim a snapshot:** after an accepted walk, X4's race with later machine changes still stands and publication remains the guard against a silent overwrite.

### 1.2 The clock and the size (Row 183)

**L4. The last-changed time is taken in the epoch form and carries its moment and its clock** (D5). The machine has no idea what time zone anyone using it is in, and no timezone was configured at all on the observed container — the `+0000` is a fallback, and **the epoch form is the unambiguous one** (Fact 7). The listing shows that instant rendered as a calendar time in the user's own zone, computed from the epoch value alone. **No age or elapsed-time presentation is ever derived from it against the desktop's clock** — that would subtract readings taken on two clocks, which D5 forbids.

**L5. The size shown is the apparent size, and it is declared as that wherever anything consumes it.** The subsystem route carries no allocated-block count, so the sparse file's lie — 500 GB reported on a 60 GB allocation, 0 blocks allocated — is not catchable on this route (Fact 7). What that costs: a sparse file shows its claimed size in the browser, which is true of its apparent size and says nothing about disk taken. **No will-it-fit decision is made from a listed size anywhere in this document**; the free-space reading of [1.4](#14-the-free-space-figure-row-184) is the only figure about room.

**L6. A zero-length file reads 0 on this route at no extra cost** (Fact 7), and nothing more is inferred from it: presence, name and size are never state (`State, identity and recovery` §1.3 rule 5).

### 1.3 The `.blend` version (Row 182)

**Constraint:** Row 182 — *"the Blender version it was saved with … Smoozy reads that version straight from the file, without running Blender on it or pre-loading its settings."*

**L7. The reading is a bounded prefix of the file's bytes, fetched by the desktop over the file-transfer subsystem's byte-offset reads on L1's one long-lived reading channel, and interpreted by Smoozy itself.** No Blender runs, nothing opens the file, and no machine-side program is asked — which programs an arbitrary rental carries is established nowhere, and the reading must work on the pre-package surface before anything is installed. **The channel is named because the alternative is expensive and silent**: a byte-offset read against an open handle is the operation a transfer is made of, so a reading that opened a channel of its own would offer sixty channel admissions for sixty `.blend` files in one folder, against a session cap a provider image may set to 1 (T2) and beside the four-slot pool of [6.1](#61-the-pool-row-188), carrying no priority class because [Section 11](#11-declarations) declares one and a prefix read is not a transfer. **The prefix reads ride the reading channel and are serialised behind the listing**, so reading traffic stays one session per connection whatever a folder holds — which is also what makes *the reading never blocks the listing* implementable without a second admission story: the four fields show first and the version tag fills in as each prefix arrives behind them. **`Server protocol and transfers` §1.1 item 2 names the byte-offset read against an open handle as a fourth operation on that channel and supplies the ordering — user-waited readings before unwaited ones, no reading starved, no walk rewound — so the serialisation above is that document's rule, taken and consumed here. Corrected 2026-08-29: this said that clause enumerates *"listings, attributes and free-space readings alike"* and *does not today name this operation on it*, and called it a seam for the runner rather than an edit made to that document, all of which stopped being true when [Section 13](#13-unresolved) item 12 closed on 2026-08-22.**

**L8. Two opening shapes are recognised, and both are observed rather than documented.** Blender 4.5 writes `BLENDER-v405REND`; 5.0, 5.1 and 5.2 write `BLENDER17-01v0500REND` with the version digits moving — label: **observed**, the same in all four versions on both machines (*Reading a file 1*; the spec's own sources carry it). From 5.0 an ordinary save is compressed with Zstandard, which every version's manual says outside tools can undo — label: **documented** (same question) — and a 4.5 save can be compressed too, while a 5.x save can be plain where the preference was changed. **So the reading is an attempt order, not a version model**: read the prefix; where it opens with a recognised Blender opening text, take the version from it; otherwise hand the prefix to Smoozy's own streaming Zstandard decode and read the opening text out of the first decompressed bytes; where neither yields a recognised shape, **the listing shows no version and never a guess**. An unrecognised shape covers a future Blender's header as much as a damaged file — 5.0's release notes say outright that parsers have to be updated when the header changes — and a blank tag is the honest answer for both.

**L9. The prefix is grown, never sized by a claim about the compression.** The first fetch is small; where the streaming decode wants more input before yielding the opening bytes, the next piece is fetched, up to a fixed cap, past which the tag is blank. Whether a given implementation yields initial bytes from a small prefix is a property of that implementation, not a fact anyone has established; the iteration makes the answer a cost rather than a correctness question ([Section 13](#13-unresolved) item 10). **The reading item 10 named was taken on 2026-09-04 and the item is closed; this clause is unchanged by it and is what stands.** The measurement is that the property is real and differs by implementation — the C library reaches the opening text from 16 to 43 bytes of prefix, a pure-Rust one can want the whole file, because it yields only what has left the frame's declared window and the window is the writer's choice — **so the clause's *property of that implementation* is now established rather than suspected**, and Build's choice of decoder is what decides the cost. On the one pinned the opening text arrives inside the first fetch, so the cap is not reached; **the cap is not moved and no promise rests on the figure either way** ([Sources](Sources/File%20Browser.sources.md) **J4**).

**L10. The reading is cached for the connected period, keyed by the path and the listing's own size-and-time values, and re-taken where those moved.** It is a live reading, so `Servers` §15's rule drops it wherever that rule drops one; the tag rides L14's entries and ends with them (L16). Nothing durable is written from it, and a fresh period reads afresh. **Limits carried with the answer**: no version's documentation describes the file's inside, so what the opening text holds rests on the tests; nothing outside Blender was ever pointed at a `.blend` in the research — this reading is exactly that, built on the observed opening text alone; and Windows was never tested, which does not reach this reading (it is byte arithmetic on the desktop) but is carried because the research names it ([Section 13](#13-unresolved) item 2).

### 1.4 The free-space figure (Row 184)

**L12. The split with `Servers` stands: that document's remembered figure serves the server list, this one serves the browser, and they cannot disagree in kind because both are F1's per-path reading.

### 1.5 The listing cache and the stale listing (Row 198)

**Constraint:** Row 198, quoted in full in the row file — the listing stays on screen, says plainly it is not live, everything needing the machine is unavailable rather than failing on a click, and the listing is read again when the connection comes back.

**L14. The cache is a stored tree, per server row, in process memory — and it is deliberately not durable.** Its lifetime is L16's per-ending list and the application run, and it is deliberately not given one of `State, identity and recovery` §11.1's five class names: the tree ends at four of `Servers` S10's six period endings — items 1, 2, 3 and 6 — stands at item 4, and never held a listing at item 5, which **period-held** — *the connected period ends, however it ends* — does not describe. That §11.1's complete list of local lifetimes has no class for it is still true — it closes at five and no sixth was made — but **§11.1 now names the listing tree among the objects outside the five, on the tombstone treatment it already establishes, with the lifetime kept at L16 where it lives. Corrected 2026-08-29: this called that a seam for the runner and not an edit made to that document, which stopped being true when [Section 13](#13-unresolved) item 14 closed on 2026-08-22.** One entry per folder Smoozy has listed in this connected period, holding that folder's last complete listing and the moment it was taken; the `.blend` version tags and the free-space figure ride the same entries. *Opening a folder Smoozy has not already seen* is unavailable while the line is down precisely because the ones it has seen are in this tree — a stored tree rather than a stored screen. **It does not survive Smoozy closing, and must not**: §1.1's one durable store holds no copy of an observed machine state the machine still holds (D4), and a durable listing would be a thing that can be lost and a thing that can be wrong for good. A fresh sitting reads afresh, which is the spec's own line that a connection the user opens in a fresh sitting is a fresh act. The check against the third escalation is recorded at [Section 14](#14-moments-that-reached-the-creator).

**L15. A drop does not empty it, because a drop does not end the period** (`Servers` S12). While the connection's observed value is *reconnecting* or *disconnected under a standing period*, the browser composes from the cache: the listing shown with its moment, stale said plainly, every machine-needing act unavailable rather than failing — opening an unseen folder, uploading, downloading, deleting, renaming, moving, copying, making a folder. Folders already in the tree stay openable from the tree. The connection's observed value comes from `Servers`' three values and is never derived here — no ping, no probe request (C18, K10 there).

**L16. A period ends at exactly six moments and `Servers` S10 closes that list, so what becomes of the tree is said per ending.** `Servers` §15's sentence is the rule underneath all six — *a period ending drops every live reading*, **so a listing goes stale rather than empty** — and the tree is what is left when the live reading is dropped, never a live reading itself.

- **The user disconnects** (S10 item 1), and **the application run ends** (item 2), and **the edit's save** on a server whose period stands (item 3): the tree goes. All three are the user's own act about that server — the run ending takes process memory with it in any case — and there the listing is thrown away by the user rather than taken from them. `Servers` S8 is why item 3 is named as the save: *"The edit put-back is not in any of the three lists"*, so it is period-opening and never a replacement, and L17's two labels never see it.
- **The server row is removed** (item 6, **added 2026-08-22, scenario replays Pile 1 item R21**): **the tree goes, and the fate is the bullet above's rather than a distinct one** — a removal is the user's own act about that server, so the listing is thrown away by the user rather than taken from them. What this ending adds is the **moment** and the **key**, and only those. The moment is `Servers` S10 item 6's: **the removal's local forget, not the request** — so on the removal that reaches the machine the tree stands through the two units that do (`Servers` W25's clear-and-stop ordered pair and Telegram's role off) and goes with the forget, and on the removal that reaches no machine the forget is the whole act and the tree goes with it. The key is L14's: the tree is per server row, the row it is keyed to is gone, and an entry left standing against a removed row would be a remembered observed machine state for a machine the user has just told Smoozy to forget — D4, and `Servers` D17's enumeration, which the removal walks entire. N8 states the same key rule for the upload-history lookup. **A removal that stops part-way and leaves the row standing** — `Servers` W21's *try again* and *try the remainder again* — **ends no period, so nothing here fires and the tree stands under L15 like any other standing period's.**
- **The opening act's connection never becomes live** (item 5): there is nothing to decide, because no period ever held a listing to show.
- **A break is declared while the server's key is not usable** (item 4, `Servers` P11): **the tree stands, with its moment, exactly as L15's does** — the listing shown, stale said plainly, every machine-needing act unavailable rather than failing on a click. This is the one ending that arrives underneath a user who is looking at a listing, and nothing about that listing's truth changed when the period ended; emptying it here would be the *"throwing away what the user was looking at"* Row 198 refuses. **There is no repair to wait for** — P11 forbids the attempt — so nothing is shown as pending and the route back is the user's own connect, which P11 grants the moment the key mark clears.

A server this run never held a period for shows no listing, because no entry was ever made.

**L17. When `Servers` hands over a repaired connection, the label decides.** A **replacement** re-reads the folder the browser is standing in — the spec's own instruction, *"the listing is read again and the controls return"* — and the cache's other entries stand until re-opened, each still carrying its own moment. A **period-opening** connection starts a fresh tree. Before anything is trusted, the installation-identity gate has run (`Server protocol and transfers` C14): on *present and different* or *absent*, the cached tree is disqualified with everything else machine-derived — it describes a machine that is gone — and the browser reads the fresh machine from nothing.

**L18. A destroyed machine and a restarted one look alike at first, and the browser does not decide which it is.** `Servers` owns the repair and the telling apart; what the browser does is the same in both cases and in the *not yet known* stretch: the stale listing stands with its moment, the controls stay unavailable, and they return only on a live connection. On a machine that never answers again the listing is stale for good and the controls never return, which is this promise as written.

### 1.7 A folder's size, counted on request (the Creator's twenty-third note 2)

**Added 2026-10-30, a want under Rule 7 entering at Specs and flowing down. No auditor of this document has seen this section, and no coverage row is filed for it.**

**Constraint:** Specs `File Browser`, *Browsing a server* — *"A folder's size is shown only when the user asks for it. Asked, Smoozy counts everything inside the folder — every file in every folder below it, to any depth — and shows the total until the folder is next listed."*

**L24. No listing gives a folder a size.** L1's reading returns a folder entry with no size of its contents, and nothing in this document walks a folder to make one. A folder row's size is absent until L25 runs for that folder.

**L25. The count is taken on the machine by one framed request, never by a walk over L1's reading channel.** A walk there costs at least one directory reading per folder, serialised behind the listing (`Server protocol and transfers` §1.1 item 2) — minutes on a deep project tree. So the desktop sends ***a folder's size is counted on the machine*** (`Server protocol and transfers` §1.1) carrying the folder's path as L1a's bytes, and the entry point walks it once and answers bytes, files, folders and one flag, *incomplete*. **One request per folder:** with several rows chosen, each chosen folder is sent on its own and its row fills in when its own answer lands; chosen files are not counted, since the list already shows their size.

**L26. The rules of the walk.** Every entry below the folder, at any depth. A regular file adds its apparent size — L5's value, the one the list shows — and counts one file; a name hard-linked twice counts twice, as two rows in the list would. A directory counts one folder and is descended. **A symbolic link is never followed and adds nothing**, so the walk cannot loop or count a tree twice through a link. Any other kind — device, socket, pipe — adds nothing. **A mount of the system's own in-memory pseudo filesystems** (process and kernel views such as `/proc` and `/sys`) is not descended, because their apparent sizes describe no disk — `/proc/kcore` alone reports more than any disk holds; every other mount below the folder is descended, since a rented machine's work disk is often one. **A directory the entry point cannot open or read is skipped and sets *incomplete***, and the answer is then a lower bound, shown as one. Nothing on the machine is written, so under `Server protocol and transfers` C6 the request is a pure reading.

**L27. The figure is run-held beside the listing and dropped on the next reading.** It rides the parent folder's L14 entry, keyed by the counted folder's path. When that folder's parent is read again — navigation back to it, L17's re-read, any act of this document's own landing in it — the figure goes and the row shows no size. Nothing durable is written. A count taken while a job writes into the folder is the size at the moment of the walk and is not refreshed. **While the listing is stale (L15) the count is a machine-needing act and unavailable**; a figure already shown stays with the stale listing and its moment. An answer that lands for a folder no longer in the composed list is dropped.

**L28. Where the machine cannot answer, the act is not offered.** Before hand-over there is no program, and a package whose release (`Server protocol and transfers` P3b, B8d) is below the one that first carries the request does not declare it; in both the act is unavailable with Design's one-line reason, gated as `Telegram` V1c's change is, and nothing is guessed from a refusal. The waiter's deadline is C16's (`Server protocol and transfers` §4.6), chosen knowing the walk reports nothing until it ends; a deadline passed, a dropped line or an error answer leaves the row uncounted and says so in Design's words. Nothing retries by itself.

### 1.8 A picture shown in Files (the Creator's seventeenth note 11)

## 2. Permission: the refusal told apart, and elevated access

**Constraint:** Row 181 — *"Where the login is not permitted to read something, Smoozy shows what it can and says plainly what it could not"* and *"Smoozy carries out the part it can and says plainly what it could not"* — and Row 180 — *"And where the machine allows it, Smoozy can offer to try again with **elevated access**, rather than only reporting the refusal."*

### 2.1 The limit, and the walk that recovers the separation (Row 181)

**P1. What is supplied is a separation, corrected 2026-08-20, and this section used to be written inside a limit that was never there.** `Server protocol and transfers` 1.3: at readdir **and at stat alike** the failures — *may not read it*, *gone*, *the machine did not answer* — are told apart on the subsystem route by distinct protocol statuses, in one request. The protocol's own codes are `SSH_FX_NO_SUCH_FILE` and `SSH_FX_PERMISSION_DENIED` (documented; the draft's own definitions are quoted at [Sources](Sources/File%20Browser.sources.md)). **What was byte-identical was the transfer client program's rendering**, which expands the path before it asks; that program is not on this route. **So Smoozy knows which of the two it met**, and no message anywhere may say otherwise.

**The two halves of that separation do not rest on the same weight of evidence, and the difference is stated rather than averaged — corrected 2026-08-23.** This clause said *a real subsystem was made to return each of them with a control on 2026-08-20* and left the reader to take one observation for both halves.

- **The readdir half is a rental's, with controls either side** — Fact 7 §5.5: `opendir` on an unreadable folder sent **Permission denied**, `lstat` on an absent path sent **No such file**, a successful reading either side of the pair. That is the half [P2](#21-the-limit-and-the-walk-that-recovers-the-separation-row-181) and [P3](#21-the-limit-and-the-walk-that-recovers-the-separation-row-181)'s component walk run on, and it is the half everything below actually needs.
- **The stat-refusal half — an attribute request on a file under an unreadable parent answering *refused* rather than *absent* — is observed on the caller's own end and not on a rental. Corrected 2026-09-01.** `Server protocol and transfers` 1.3 and its [Sources](Sources/Server%20protocol%20and%20transfers.sources.md) companion record the run re-performed on 2026-08-23: the Creator's Mac, macOS 26.6.2 build 25G83, `OpenSSH_10.3p1`, its own `/usr/libexec/sftp-server` driven over pipes, with a readable control beside status 3 for the unreadable-parent case and status 2 for the absent case. They also state the negative: the first two returning the same status, or either returning attributes. Label: **observed**, with the machine, software, controls and negative recorded. **The limit is the one that evidence actually has:** no rented machine's server has been posed at this stat case (`Server protocol and transfers` [§12](Server%20protocol%20and%20transfers.md#12-unresolved) item 24).
- **What holds outside that observed shape.** Where a rental's direct stat does not separate the two, [P3](#21-the-limit-and-the-walk-that-recovers-the-separation-row-181)'s walk still names the component from readdir statuses alone, on the rental-observed half, and [P4](#21-the-limit-and-the-walk-that-recovers-the-separation-row-181)'s residue message is written to be true either way. **No clause below is rebuilt and no offer moves** — what narrows is how early Smoozy knows which of the two it met on a path it was handed, not whether it ever knows.

**P2. Inside a listed folder the separation is whole and free.** Opening a child folder is a readdir on the subsystem: a permission refusal, an absence and a dead machine arrive as three distinct answers with controls either side (Fact 7 §5.5). The user is told which it was in as many words, and the elevation offer of [2.2](#22-the-elevated-retry-row-180) is attached to the refusal case alone. *The machine did not answer* is not a statement about the folder at all: it is the connection's case, `Servers`' condition covers it, and the listing goes stale under [1.5](#15-the-listing-cache-and-the-stale-listing-row-198) rather than the folder being reported broken.

**P2a. What can be told before a folder is opened, and it was less than the design drew. Added 2026-08-21, per Row 342.** [Design](../Design/File%20Browser.md) **as it then stood** had an unreadable folder *"greyed, saying why, with the offer to try again with admin access beside it"* — **in a listing the user has not clicked into.** **Corrected 2026-08-31: this stood in the present tense after the design took this clause's answer on 2026-08-24, so it described a sentence that is no longer there.**

- **The promise's own stated purpose is kept whole and for free.** *"It is not silently absent"* — **a folder is listed because its parent's reading names it, and being unable to read *into* a folder is a different permission from seeing its name in the parent.** So the folder always stays in the list, and the spec's *show what can be shown* is never at risk.
- **What cannot be done is the marking.** [L1](#11-one-reading-on-the-subsystem-route-rows-183-and-191) yields four fields in one batched reading and states *"**No reading here ever issues a stat per entry**"*; [X1](#41-the-walk-row-191) repeats the prohibition. **The per-entry probe that would answer this in advance is the one thing both forbid, for a measured reason** — 52 round trips against 5010.
- **And the probe would not answer it even if it were free.** The question is *can **this login** read into this folder*, which mode bits do not answer: supplementary groups, access-control lists and the login's own privilege all bear on it. **A mark composed from what the machine says about the entry would be a prediction, and a wrong prediction here stops a user opening a folder they could have opened.** P5 already takes the elevation readings *"at the refusal, beside each other, and never before one"*, for the same reason.
- **So the refusal is met on the click and told in as many words, which is [P2](#21-the-limit-and-the-walk-that-recovers-the-separation-row-181)**, and *before it is opened* is not kept. **The design sentence was a drafted one and was parked rather than repaired here; Design carried it on 2026-08-24 and no longer marks the folder in advance.**
- **The second clause is answered with a negative and it is [P5](#22-the-elevated-retry-row-180)'s.** *"with the offer to try again with admin access beside it"* was unconditional in the design and is conditional here: **on a container under a non-root login there is no offer at all**, and on a machine the kind table does not place, none either. **So a refusal shown with nothing beside it is a real state** — one the design had no drawing for until 2026-08-24, when it took the condition and gained the state.

**P3. The walk says *which component* is refused, and that is now its whole purpose — corrected 2026-08-20.** It used to be written as the only way to learn refusal from absence at all; [P1](#21-the-limit-and-the-walk-that-recovers-the-separation-row-181) settles that in one request. What one request does **not** give is which component of the path the refusal arises at, and *this login may not read `/jobs`* is a sentence Smoozy can only say by walking. So: where the browser lands on a path directly — *show outputs* opening at a job's folder, `Rendering`'s point-at-the-file entry, a path remembered from an earlier sitting — the stat answer names refusal or absence, and where it names refusal the browser opens each component in turn, from the deepest ancestor it can list, on the subsystem route. The component that answers *permission denied* is a refusal, named as the component it is — *this login may not read `/jobs`* is the accurate sentence even when the user asked about `/jobs/render-3/frame.exr` — and the elevation offer attaches there. A component absent from its parent's listing is *gone*, named at the component. The walk costs one directory reading per component and reports underway like any reading (G4).

**P4. Where the walk cannot name the component, the message says which of the two it met and stops there — corrected 2026-08-20.** A refusal met at the very top, or readings that disagree between two steps of one walk, end at *Permission denied.* (or *Not found.*), with the elevation offer where it is a refusal. *(Re-quoted 2026-10-28, step 13's final words sweep: the screen's words since 2026-10-27; it read* Smoozy could not read this — this login is not permitted *(or* — it is not there*).)* **The old wording said Smoozy could not tell missing from not permitted, and that was untrue**: the stat answer carries the distinct status whatever the walk does afterwards, so the residue is ignorance of *where*, never of *which*. It is written as ignorance of where. **On [P1](#21-the-limit-and-the-walk-that-recovers-the-separation-row-181)'s weights — corrected 2026-08-23 — *whatever the walk does afterwards* is the thin half's claim, and the walk itself carries the rest**: a refusal the walk reaches is named by a readdir status, which is the rental-observed half, so the residue message is correct on either weight and this clause never depends on the thinner one. **A message naming the wrong one of the two is worse than a message naming neither**, and *says plainly what it could not* is a promise about honesty, not about omniscience: Smoozy says plainly that it could not read the path, and where it knows why, it says why. Method's first stop was weighed here and declined — the promise survives whole in the listed case and the walked case, and narrowed only to honest ignorance in the residue; [Section 14](#14-moments-that-reached-the-creator) records the check. **The observed separations rest on one container with one unprivileged login shape** — no groups, access lists or read-only mounts — so permission shapes beyond the tested one may collapse the walk's readings, and the residue message is written to be correct there too ([Section 13](#13-unresolved) item 1).

### 2.2 The elevated retry (Row 180)

**P5. ## 3. The upload request

**Constraint:** Row 190 — *"The unit is the file, the request is still one thing"* — with the collision answer that *"still stand[s]"* across a drop and a resume, the waiting state, the per-file breakdown under a whole, and *"Closing Smoozy stops uploads and ends the request with them."*

### 3.1 The request and its record (Row 190)

**U1. An upload request is one multi-part action, and its durable half is one §9.4 outcome record in the local record.** Written when the user confirms the upload, before any transfer is arranged, it holds *(from 2026-10-04 there is no confirmation box — [Design — File Browser](../Design/File%20Browser.md), the Creator's note 2 on the test copy — so the pick in the system panel, or the drop, is the confirming act, and the record is written at it; nothing else in this clause moves)*:

- the server row and the installation identity the request was arranged under;
- the destination folder — where the user was browsing;
- **the enumeration**: one entry per file, complete before the already-exists question is asked and durable before the first byte moves (S8's ordering, §9.4's rule). Each entry carries the file's **source path on the user's own computer, as stored on disk**, its landing path on the machine, its size as enumerated, its disposition after the collision answer (to send; skip existing; renamed under Keep both), its transfer identity once a transfer is arranged, its unit outcome as it becomes true, and **the moment that outcome was written** — [U9a](#34-the-live-half-the-end-at-close-and-the-fresh-sitting-rows-190-and-197), **added 2026-08-25 for Row 486, and the only moment any upload record holds**;
- **the collision answer**, U4;
- **where the upload was pushed past the live-job warning, the affected jobs by identity and the act intended** — [8.4](#84-the-telling-row-196)'s telling, written before the act's first machine effect. They are fields of **this** record and never of a second one: §9.4 gives one outcome record per action, the disturbing upload is one action, and a second record beside this one would be two outcome records for one action, which that section forbids in its own words. A request that disturbed nothing carries neither field;
- the request's own ending — completed, stopped by the user, or ended by the run ending — derived from the unit outcomes and the run, never a second stored field.

The record is **user-held** (§11.1): it is the account of the upload and it goes when the user removes it, never by age. **It is also Row 187's record** — [5.3](#53-the-source-path-record-row-187) reads the same entries rather than keeping a second copy.

**U2. The partition unit is one file's transfer**: partial across files, atomic within one file (staging and a single publication — §9.2 tests 1 and 2; the spec promises per-file visibility and per-file survival outright). Three hundred textures are three hundred transfers, each with its own transfer identity, each admitted separately, each with its own S9 record; the request is the enumeration over them.

**U3. Every transfer the request arranges is `Server protocol and transfers` §7's, unmodified**: bound to the server row (T3), staged under S4's path, recorded under S9 before its first byte, ended under S26. This document adds the layer above — which transfers exist, in what order they are offered to admission ([Section 6](#6-the-pool-and-the-order)), and what the whole means.

### 3.2 The collision answer (Row 190's non-derivable piece)

**U4. The answer — Replace, Keep both, Skip existing, or Stop — is written durably into the request record at the moment the user gives it, before any transfer whose arrangement depends on it is arranged.** It is given once for the whole request and is never asked again for the life of the request: a drop, a repair an hour later, and every resume read the recorded answer. Every other field of the request can be rebuilt from the machine or the transfer records; **this one cannot**, and its durability is what makes *the answers the user already gave about collisions still stand* true by construction. The answer's effect is applied to the enumeration once — dispositions per file, Keep-both renames computed ([4.3](#43-keep-both-rows-192-and-186)) — so a resume re-derives nothing.

### 3.3 The third state (Rows 190 and 199)

**U5. *Waiting* is a composed presentation, not a fourth transfer ending.** A file reads as waiting for the connection where its transfer record says *interrupted* (S26), the request is still open, and the server's period still stands — which is exactly the stretch the spec means by *"waiting rather than finished or failed"*. **A record reading *stopped* never composes as waiting**, and that excludes by construction the two endings Smoozy writes itself: X7's create-intended refusal and K8's and K9's changed-source stop both record *stopped* ([4.2](#42-the-rule-collisions-are-judged-under-row-192), [9.3](#93-the-unchanged-file-row-201-and-fact-30)), so a file Smoozy stopped is shown stopped with its reason rather than amber as waiting for a line that is up. Files whose transfers were never arranged yet read as waiting their turn in the pool. Design's Transfers screen carries both readings and the amber presentation.

**U6. A waiting upload is stoppable exactly as a moving one.** The stop is S26's deliberate stop: the record is written *stopped* before anything else, the staged material's removal happens on the connection where one is up and is otherwise the owed cleanup of S27. Stopping the request stops the whole request — finished files stay, unarranged files are never arranged, the one in flight is stopped (the spec's own sentence; the stop control sits on the request, Design's ruling).

### 3.4 The live half, the end at close, and the fresh sitting (Rows 190 and 197)

**U7. The request's activity is run-held; its record is not.** Arrangement, admission, the byte loops and the waiting composition live in process memory and end with the application run. **Closing Smoozy ends the request**: channels die with the process, every in-flight transfer's record reads *interrupted* (S26's third ending — D6 makes a crash and a clean close leave the same records), and no activity survives to arrange anything.

**A period's end does to that server's requests what closing Smoozy does. Added 2026-09-28.** A request whose server's period ends (`Servers` S10), with a unit still owed, ends there. Nothing of it is arranged again, its *interrupted* records stay *interrupted*, and from then on it is what U8 describes: a leftover the user is told of and may remove, and staged material a fresh request may take up. That holds in this run exactly as in a fresh sitting. K3 is why: nothing resumes on a period-opening connection, so a request left open across a period's end could never move again and would read as under way for good.

**U8. What a fresh sitting finds is records whose request is no longer alive, and what it does with them is bounded on both sides.** On the next connection to that server — after the installation-identity gate — `Server protocol and transfers` C11 step 4 refuses to resume records written by an earlier run; that is taken, not softened. What this document adds:

- **The user is told the leftover is there and can remove it** — Row 197's third clause, granted by the spec for exactly this case. The telling is composed from the durable records: request records with unfinished units and transfer records reading *interrupted* under the current installation identity are presented in the transfer window as leftovers on that machine, with a remove act. Removing one first changes its transfer record durably to *stopped: staging removed by user*, then removes only the exact staging object whose synthesized name and stable file identity match that record (or records it as an owed cleanup, S27's shape). **Amended 2026-10-03, out of step 10c's map of the 38 promises (hole 12), ruled by the build runner; no auditor of this document has seen it: that identity match never holds** — the file service gives no stable file identity ([Section 13](#13-unresolved) item 9; `Server protocol and transfers` §12 item 15) — **so the transfer window's *Remove* takes X12's explicit removal of a named entry instead**: it writes *stopped: staging removed by user* to every record naming that staging path, then removes the named entry by path, **only where the path lies inside Smoozy's own staging directory on that machine**; a path outside it is refused and nothing is removed. The stable file identity stays the gate on automatic removal (X12, S28). A dependency send's leftover is the same (`Dependency Upload & Remap` A12). No new page exists for this: the transfer window is where transfers already live, and the reserved staging directory is visible in the browser under X12 *(while *Show hidden files* is on — L21, amended 2026-10-02; the telling here does not depend on it)*. **The offline leftover line carries no byte total.** `Server protocol and transfers` S9's expected total is the size of the finished files rather than what is staged, and its checkpointed high-water offset is an accounted boundary which S10a observes can sit either ahead of or behind the staged object's real size. The real size belongs to the machine's filesystem and cannot be read while that machine is disconnected; neither durable candidate is relabelled as disk use. The existence, server and remove act remain available from the records, and Design is handed back a line with no figure. A later carry-on starts from zero, which S12 step 1 makes safe, but **that is an outcome recorded before deletion rather than an inference made from a missing path**.
- **A fresh, user-started upload may take the staged material up, by continuing the interrupted transfer rather than arranging a second one.** Where a new request's enumeration matches an interrupted record's source path and landing path on that machine, that unit **takes up the interrupted transfer — its transfer identity, its record and its staging path** (the staging path is synthesised from the transfer identity, S4, so continuing the material means continuing the transfer) — and proceeds through S12 entire plus Row 201's unchanged-source gate ([9.3](#93-the-unchanged-file-row-201-and-fact-30)). Where either gate says no, the unit starts fresh under a new transfer identity and the old staging is abandoned to S28's sweep. C11 leaves exactly this to this document: the record carries which run wrote it, so the automatic case and the taken-up case are separable.
- **A taken-up unit is governed by the new request throughout, and the old request's collision answer never governs it.** A taken-up transfer is continued rather than arranged, so X7's *"Each transfer the request arranges"* would leave its publication ungoverned and a builder could reach for the only durable answer bound to that record — the old request's — and publish replace-intended over a file the user has just answered **Skip existing** for. So it is said outright: the unit's **disposition comes from the new request's enumeration** and its **publication intent from the new request's collision answer** (U4), applied to the enumeration once like every other unit's. What each disposition then does with the staged material: **skip existing** does not take it up at all — the unit is skipped and the staging is abandoned to S28's sweep; **replace** takes it up and publishes replace-intended; **to send** takes it up and publishes create-intended; and **Keep both** can never match in the first place, because the landing path it composes is a fresh name and the match is on source path *and* landing path.
- **Nothing starts itself.** *No upload starts itself again on a later connection* is kept by construction rather than by care: the only mechanism that resumes transfers unasked is C11 step 4, which excludes earlier-run records by the run marker S9 carries, and the only mechanism that arranges new transfers is a request the user opened in this run.

**U9. The already-exists check in that fresh sitting is what puts Skip existing forward.** The finished files sit at their final names and the walk of [4.1](#41-the-walk-row-191) counts them; the partial sits at a staging name and is never counted ([4.4](#44-the-partial-never-counted-row-197-and-row-191s-exclusion)). *Smoozy says what is already there and puts Skip existing forward* is therefore the ordinary collision question doing its ordinary work, with Design told which answer to lead with.

**U9a. Each enumeration entry carries the moment its unit outcome was written, and no other moment is recorded about an upload anywhere. Added 2026-08-25 for Row 486; the field is [U1](#31-the-request-and-its-record-row-190)'s.** It is taken from the desktop's clock at the durable write `State, identity and recovery` §9.4 item 2 already requires — an existing write at an existing moment, no second occasion and no sweep — and it is immutable with the outcome it sits beside (that document's §8.6). **No moment of the application run ending is recorded, and none can be:** D6 writes nothing on exit and [U7](#34-the-live-half-the-end-at-close-and-the-fresh-sitting-rows-190-and-197) ends the request with the process, so the *ended by the run ending* reading U1 derives has no write to hang a moment on. **This says nothing about another interruption.** `Server protocol and transfers` C23a requires a drop raised anywhere inside a transfer to write its record *interrupted* at that interruption; U9b composes only over a request whose ending derives from the **run ending**, where that write has no occasion. The field sits on this enumeration entry because it is the moment of the unit outcome U9b actually dates — the last file landed — and never a proxy for the interruption. **The field widens §9.4's outcome record for nobody**: it is this document's field on this document's enumeration entry. **It is a desktop-clock value used for presentation and for nothing a promise rests on** (D5), it is never subtracted from a machine reading, and a computer whose clock has moved can only mis-order two of the user's own earlier requests and misdate [U9b](#34-the-live-half-the-end-at-close-and-the-fresh-sitting-rows-190-and-197)'s line — the walk, the four answers and every disposition are untouched.

**U9b. The earlier request the reason line names, and the value that line dates, are composed at the new request's pre-flight and are one record and one value.** Design states why *Skip existing* is led with in a line inside the already-exists box, and the spec grants the saying: *"**Skip existing** put forward only where Smoozy holds the earlier request and can say why"* ([Specs/File Browser](../Specs/File%20Browser.md)). [U9](#34-the-live-half-the-end-at-close-and-the-fresh-sitting-rows-190-and-197) reaches the putting-forward and stops there; what is supplied for the line is this:

- **The candidate entries.** Among upload request records under this server row and this installation identity **whose ending derives as *ended by the run ending*** ([U1](#31-the-request-and-its-record-row-190)'s third ending, which by construction is a record no longer alive and so an earlier run's — a completed request and one the user stopped are both excluded, and the line is about neither), the candidates are the entries whose **landing path is one the walk of [4.1](#41-the-walk-row-191) found occupied for this request** and whose **unit outcome is *done***. Those are the entries whose files are the collisions being asked about.
- **The record named is the one holding the candidate entry with the most recent [U9a](#34-the-live-half-the-end-at-close-and-the-fresh-sitting-rows-190-and-197) moment, and the moment the line dates is that entry's moment.** That is one record and one value in every case where a candidate exists, which is what closes the two shapes U8's per-unit match leaves open: collisions drawn from **two** earlier unfinished requests name the later of them, and collisions **mixed** with files the user placed by hand are unaffected, because a landing path no candidate entry claims contributes no candidate and takes nothing from the ones that do. **What the value is, stated so nobody reads it as something else: the last file that upload landed at these paths** — the nearest recorded moment to the application run ending, the run ending itself having none (U9a).
- **Where no candidate entry exists, nothing is supplied.** The negative case in the box is Design's ruling and the spec has taken it; this clause only says what it is composed from and when there is nothing to compose.
- **The composition reads the local record and never the machine, and it reads no transfer record.** A leftover swept under `Server protocol and transfers` S28, or removed by the user under [U8](#34-the-live-half-the-end-at-close-and-the-fresh-sitting-rows-190-and-197)'s first bullet, moves neither the record named nor the value — the finished files the line is about are at their final names and their entries are immutable.

### 3.6 What the whole reports (Row 190, and `Server protocol and transfers` G6)

**U11. The whole is counted in files, and the bar is drawn in bytes; both totals exist before the first transfer starts.** G6 leaves to Row 190 what the whole is counted in and what it reads while a deep folder is still being listed. The count the user reads — *n of m files* — is unit outcomes over **the units whose disposition is to send**, and the bar is bytes staged against bytes expected over those same units, summed from the per-transfer counts of G4 against the enumerated sizes. **Skipped units are in neither total and are reported separately as what Skip existing did**, because the spec's own sentence for that answer is *"send up only the files that are not already there"* — counting them into *m* would draw a denominator holding bytes that will never cross, and counting them done before a byte moves would show progress for work nobody asked for. Neither is *"how far the upload as a whole has got"*. And because the enumeration is complete before the collision question and durable before the first byte (U1), **there is no state in which the whole is still being discovered while transfers run** — the walk happens first, and a request that has started moving knows its totals.

**A unit that starts over is stated, and the bar's fall is never the whole report. Added 2026-09-02, consuming `Server protocol and transfers` [G4a](Server%20protocol%20and%20transfers.md#102-what-each-kind-of-work-has-to-report-and-from-where) and closing that document's [Section 12](Server%20protocol%20and%20transfers.md#12-unresolved) item 25.** Every transfer this request arranges carries G4a's start-over mark beside its count, set at the fresh staging path and standing until that transfer ends. **While any unit's mark stands, the whole's report states that a file started over** — one statement over the request however many units carry the mark at once, standing for as long as any of them does. The record's absence is a legible state.** A path no published entry names — a file that reached the machine by the user's own tools, by another computer, by anything that is not this document's upload — answers **no record**, said as that, which is the spec's own negative case: *"A file that reached the machine some other way carries no such knowledge."* Nothing guesses.

**N7a. What *no record* does to the toolbar: nothing. Added 2026-08-21, per Row 343.** [Design](../Design/File%20Browser.md) puts **Render settings…** and **Check dependencies…** on the toolbar for a `.blend` and takes them away for anything else (**Creator-stated**, 2026-08-13), on the ground that *"a control that cannot apply to what is selected is not a control, it is a question"*.

- **The toolbar's rule is the file's kind and only its kind.** A `.blend` gets both controls whatever [N6](#53-the-source-path-record-row-187)'s lookup would answer for it. **No per-file record lookup is run to compose a toolbar.**
- **The third state lives where N7 already put it, which is in the answer rather than in the control — and the answer starts the check rather than refusing it. Entries retire when the user removes the request record they belong to (user-held, U1) and never by age; a removed server row takes the question with it, since the lookup is keyed by the row.

**So removing a request record removes the provenance of its files with it, and the removal act names that cost before it is taken.** Clearing finished transfers is the most ordinary tidying there is, and the record it clears is one Row 187 requires to *outlive the upload* and be read in a later sitting; after such a removal N6's lookup finds nothing and N7 answers *no record* for a file this document uploaded itself. **The lifetime is not moved to buy that back**: `State, identity and recovery` §9.4 declares the outcome record **user-held** in its own words and §11.1 places it in the class that ends when *"the user removes it, and never otherwise"*, so the class is a closed input's rather than this document's, and a second machine-keyed record holding the source path again would give one fact two homes. **The repair is the telling**, which is how this plan already answers its nearest question: the user is told what Smoozy could not do rather than protected from their own act. The requirement is carried to `Desktop app and delivery` at [Section 12](#12-what-this-document-supplies-and-to-which-document), beside the suppression row, because the presentation is that document's. N7 stays as written — *no record* is true after a removal, and there is nothing left to distinguish it with.

**N9. The keying was checked against `Dependency Upload & Remap` K3 and the two fit without either moving.** K3 keys located answers by the holding file and the reference's exact recorded bytes, with no machine anywhere in the key, so the answer travels; this record answers a question about one machine and is keyed under the server row and installation identity, which is K7's shape for machine-keyed records. ## 6. The pool and the order

**Constraint:** Row 188 — *"A set number of transfers run at once per server and the rest wait their turn, and the user does not set that number"* — and Row 189, whose `[PENDING]` marker the spec cleared on 2026-08-23 in favour of the settled order it now states: *"**The order is settled**, and it contains the pair the Download spec already fixed rather than re-deciding it: auto-download first, then manual download, then the uploads a submission is waiting on, then ordinary uploads."* — Label: **settled at Architecture** (2026-08-23), which is O4–O5 below. T5, T6 and T8–T10 supply the mechanism; the number, the order and the shares are declared here.

### 6.1 The pool (Row 188)

**O1. The per-server pool is four transfer channels.** The measured useful range is two to four and differs by direction — the knee is two streams down and about four up, and a number above the range buys setup-hiding rather than throughput (T6, Fact 25). One pool serves both directions (the spec's own sentence), so it is sized at the larger knee: a pool below four starves the upload direction — this document's direction, and the slow one at 1.2–1.3 MB/s against 12–15 down — for no gain anywhere, and a pool above four buys nothing Fact 25 measured. **The number is the pool's size, not a promise of sessions**: T2 makes the session cap the server's, a refused channel opens fewer, and at a cap of one `Server protocol and transfers` T5 alternates reading and command work on the primary connection while `Servers` 1.4's additional connection remains transfer-only.

**O2. Inside the pool, a per-direction ceiling keeps the wrong direction from spending slots it cannot use.** The upload direction's ceiling is the pool itself — four — declared here. **The download direction's ceiling is Row 206's to declare inside the same structure**, from the same T6 range; **`Download` Q1 declares it — two transfer channels — and its [§14](Download.md#14-what-this-document-supplies-and-to-which-document) supplies it here by name.** *(Corrected 2026-09-02: this read "until it is declared, downloads are bounded by the pool alone, and nothing here presumes their number", which stopped being true when Q1 landed; the ceiling was declared and `Rows/Download.md` Row 206 records that answer as landed. Nothing about the pool moves — the number is that document's and is consumed here, not re-decided.)* Two ceilings in one pool, not two pools: the count the machine sees is one count, admitted through the one per-server point (T5).

**O3. What actually governs a busy line is above the pool, and the pool does not pretend otherwise.** The desktop-side admission point knows every server at once, and the two shared rate budgets are `Desktop app and delivery`'s — a whole second machine bought about 20%, and uncoordinated upload fan-out was actively worse than one machine at a time (Fact 25). The pool exists so that one server's transfers queue fairly at that server and the command channel keeps its reserved session; throughput lives in the budgets.

### 6.2 The order and the shares (Row 189)

**O4. The declared classes, in one order — and the top pair is not this document's to order.** `Preparation/Specs/Download.md` settles it, Creator-stated (2026-07-22): *"Auto-download transfers take priority over manual download transfers in the server's transfer queue."* That sentence is Row 207's own promise and the settled half of this three-way order; this document declares the rest around it.

1. **auto-download** — first because the spec settles it above manual download, and the settled half sits at the top rather than mid-list so the declared order contains it legibly;
2. **manual download** — below auto-download by the Creator's sentence and above the upload classes by this document's own reasoning: the line is eleven-to-twelve times faster down than up (Fact 25), so a download slot moving the same bytes turns over that much sooner, and preferring the fast direction at a grant delays an upload by one short transfer while the reverse holds a short transfer behind a long one;
3. **dependency-upload** (`Dependency Upload & Remap` A9's class) — an interactive sitting whose rows gate a submission the user is trying to make;
4. **upload** (U10's class) — user-asked bulk, including the re-sent `.blend` a fresh request carries; below dependency-upload because the sitting's rows block a render and a bulk upload blocks nothing but itself;
5. **the preview fetch**, which `Queue & History` P6 already declared *"below every user-asked class and below auto-download, never starved"* — taken as declared, adding nothing.

The classes are declared by their arranging modules per T8; what this row fixes is the order among them, around the pair the spec fixed first. **`Download`'s Row 207 does not declare a rank into this list — it inherits an order that already contains the pair it settles**, confirms that half by citation, and what it declares of its own is its two classes' detail and Row 206's download-direction ceiling. No second structure exists for it to invent; a class a later document declares takes its rank by that document's declaration against this list.

**O5. The share, declared against T10's mechanism:** at each admission decision the highest-ranked class with work waiting is admitted — **except that a class which has had work waiting throughout the last N grants at that server without receiving one takes the next grant, where N is the count of declared classes.** **Where more than one class qualifies for that exception at the same decision, the highest-ranked of them takes the grant.** The tie is broken here because a rule that leaves it open can be carried out four ways — highest-ranked-among-qualifiers, longest-waiting-first, lowest-ranked-first, by arrival — each producing a different admission sequence, which is exactly the run-time class T8 forbids. Rank is the tie-breaker because it costs nothing and is how the plan answers *who goes first* everywhere else: T8 admits by class then by arrival, and O4 is a rank throughout. A second ordering that disagreed with the first would be the thing O6 says does not exist.

**What the rule delivers, stated as what it delivers.** A class holding work waiting continuously receives a grant within **at most 2N−1 grants at that server**: N grants before it qualifies, and at most the N−1 other classes that could qualify at the same decision taking theirs ahead of it by rank. With the five classes declared above that is nine — where all five hold work from the first grant, grants 1 to 5 go to auto-download, and grants 6, 7, 8 and 9 go to the four qualifiers in rank order, the preview fetch's first grant being the ninth. **Nine is the figure for the five classes listed above and is not a constant — added 2026-08-29, because the sentence below already said the guarantee scales and this one did not say it where the figure is read.** N is the count of declared classes wherever they are declared, so a class a later document declares against O4's list counts into N and widens the bound with it — `Rendering` §7's **submission class** is one, ranked below manual download and above dependency-upload, which makes six and eleven rather than five and nine. **A builder computes N from the declarations and never reads the worked figure as the bound.** **That is the number, and it is bounded rather than gated**, which is T10's requirement in its own words — *no class is starved* survives, and the guarantee scales by construction as documents declare classes in. The order is thereby a preference within each decision and never a gate. Admission happens when a slot frees; nothing preempts a running transfer, so a class's wait is the running transfers' completion plus that rotation.

**O6. Nothing about the order is decided at run time.** The classes, the order and the share rule above are the complete declaration; two callers cannot decide differently because there is nothing left for a caller to decide.

**O7. Within a class, admission is by arrival** (T8), and within a request, by the enumeration's order — which gives the user the plain reading that a folder uploads roughly front to back.

### 6.3 The repair moment (Row 189's bite)

**O8. The moment the order bites is one moment: a repaired connection resuming auto-downloads, manual downloads and uploads across several servers at once** (T9). Each server's pool admits by O4–O5; the desktop-side point above them holds the same declared order across servers, so the classes mean the same thing globally that they mean at one machine; **and it applies O5's share rule too, with grants counted at that point** — the order alone would let one server's auto-download arrangement, which keeps trying and never switches itself off (Row 219), outrank another server's only upload at every desktop-side decision for ever, which is T10's forbidden shape one layer above where T10 forbids it. O5 counts grants *at that server*; the desktop-side point counts its own, with the same N and the same rank tie-breaker. The share is declared here rather than routed because T10 assigns it to Rows 189 and 207 against this mechanism and Row 189 is this document's; `Desktop app and delivery` holds the rate budgets, not admission. And the budgets divide bandwidth beneath all of it (their non-zero floor per admitted channel is `Server protocol and transfers`' own requirement on the budget's holder). Nothing at the repair is decided that was not declared here.

## 7. Managing files

**Constraint:** the spec's *Managing files on the server* — delete, rename, move, copy or duplicate, make a new folder — with Row 194 and the Creator-stated collision rulings.

**Three things every act below shares. Added 2026-10-02, out of step 10c's map of Files' owed acts, ruled by the build runner; no auditor of this document has seen it.**

- **Each act takes a list of entries, and the screen hands it one.** Design draws one row chosen; choosing many is a screen nobody drew.
- **Which connection.** A new folder, a rename, a delete's removals and a move's renames go on the reading channel (`Server protocol and transfers` §1.1 item 2) as operations the user is waiting on. **A copy's bytes move on a subsystem channel of their own, opened as a transfer channel is**, so a long copy never holds the list. A delete whose removals hold the list for long moves them to such a channel too.
- **A symbolic link is acted on as itself and never followed.** A delete removes the link and never its target, and a folder's walk does not go through one; a move renames the link; a copy makes a new link to the same target.

### 7.1 Delete (Rows 194 and 181)

**M2. A delete is performed per entry over the subsystem — files removed, folders removed empty, bottom-up — and it is partial across entries** ([Section 11](#11-declarations)). **M3. ### 7.2 Rename (Row 192's third face)

**M4. A rename is the base rename, and the filesystem's own refusal is the judgement rather than the backstop.** *A rename that would collide is not allowed in the first place* — and the question is which reading answers *already taken*. **The listing's role is advisory**: L14 makes it a per-folder cache holding *"that folder's last complete listing and the moment it was taken"*, and only L12's free-space figure is re-taken on its own, so the listing behind a refusal may be minutes old on a live connection while the machine is the user's — a finished render, a second login or the user's own tool can have removed the name in between. A pre-check that refused from it would state that a name is taken when the machine holds nothing under it, which is the fault Row 192 names, arriving by staleness rather than by modelling. **So the browser may warn from the listing, the rename is attempted, and the base rename's own refusal (S16) is what reports *taken*** — the filesystem answers, nothing is modelled, nothing is ever replaced by a rename, and the name the machine really holds is the one that decides. The refused name is reported as taken and the user picks another. Atomic per item.

### 7.3 Move (Row 192, and the partial action)

**M5. A move within one filesystem is a rename per top-level item** — create-intended (base rename) where no collision was answered, replace-intended (the extension) where the user answered Replace on a colliding move. Atomic per item, partial across items.

**Two cases M5 left unsaid. **M6. ### 7.4 Copy (Rows 192 and 197's shape, machine-locally)

**M7. A machine-side copy never writes at a final name, for the same reason a transfer never does.** A copy killed part-way is Fact 18's partial arriving without a wire; so a copy is written to a staging path and published by one rename, create- or replace-intended per the answer, exactly the contract's shape. **The framed request, named. ### 7.7 The pasteboard (Row 340)

**M11. There is one pasteboard, it holds one thing, and it is period-held. Added 2026-08-21, per Row 340.** [Design](../Design/File%20Browser.md) makes cut, copy and paste the shape of a move and a copy (**Creator-stated**, 2026-08-10), and **a pasteboard is the only thing in this module that persists between acts.** Everything else names its victim and its destination in one moment.

**M12. What it holds:** the **server row** and the **installation identity** it was taken under; **which act it was** — cut or copy; and the **named entries**, as paths on that machine, exactly as the listing gave them. **Nothing else, and no reading of any of them.**

**M13. Its lifetime is the connected period's**, on `Servers` [S11](Servers.md#13-what-the-period-holds-and-what-ends-with-it)'s list beside the other machine-keyed readings — **not the application run's, and nothing durable is written from it** (D4, and `State, identity and recovery` §11.1's period-held class, this clause naming it a member). **A drop does not clear it**, because a drop does not end a period (S12), which is what lets a cut survive the connection being repaired under the user.

**M14. **M15. **M16. A machine that failed the identity gate takes the pasteboard with it.** The identity is on the pasteboard, so a recycled machine simply does not match and the paste is not offered; nothing is cleared by hand and no rule of its own is needed.

**M17. Nothing on the pasteboard is validated while it sits there.** The entries are **names**, not identities, and no reading is taken to keep them true — a source removed by the user's own second login is discovered by the machine's own refusal when the paste is taken, which is W2's ordering already (*"the readings run when the destination (or the victim) is named, before the warning box"*). **A pasteboard that quietly emptied itself would be worse**: the user would lose a cut for a reason nothing on the screen could show.

**M18. Which act it was is what [M8](#74-copy-rows-192-and-197s-shape-machine-locally) reads**, so *"Paste has to remember which it was"* is kept by M12's second field and needs nothing further: a colliding paste-after-copy offers Replace, Keep both or Cancel; a colliding paste-after-cut offers Replace or Cancel.

## 8. The three warnings, and the telling

### 8.1 The three warning readings (Row 193)

The delete warning and the plain-upload warning are answered from the local record at the moment a destination is named, before any write, with no read of the machine** — `Dependency Upload & Remap` V1–V3's readings, taken whole. The **delete warning** names anything the points-at reading shows depended on, whether or not a job is live — a shared asset another reference was pointed at, a fixed `.blend` that would be left pointing at nothing. **Where the victim is a folder, the reading is asked for the folder, and the warning names what the record shows underneath it. Added 2026-09-05, out of round 2 of the code audit.** `Dependency Upload & Remap` V2 answers for a named machine location, and the records name files rather than the folders holding them, so a folder asked about by its own path alone produced nothing at all — while the spec puts a folder among this warning's actions: the second warning *"fires on the same actions"*, and those actions are *"deleting, moving, renaming, or overwriting a file — **or a folder that holds one**"*. **The cost is said rather than hidden**: the reading is per location, so a folder victim walks the local record for the locations sitting under the folder, per component under [X5](#42-the-rule-collisions-are-judged-under-row-192)'s rule, instead of asking one question. **It touches no machine** — nothing is listed, nothing is connected to, and the folder's real contents are never read — which is the only limit this clause imposes. The **plain-upload warning** fires where an upload of this document's would land on a file that module placed or fixed, and offers to send it through that module instead. **The overwrite warning fires on no plain upload of this document's, and its trigger is not this document's — corrected 2026-08-22, scenario replays Pile 1 R28: this clause counted it among the record-answered warnings while that module's Q8 fires it from a contents test that reads the machine, and a builder could keep only one of those.** It is that module's Q8, replace-or-stop and nothing wider, **scoped to that module's own row sends**, fired from its Q5 establishment inside the send pre-flight — a reading the send decision takes anyway, never one added at warning time, and never one this document performs. A plain upload's own collision question stays X3's and U4's — Replace, Keep both, Skip existing, or Stop — with the plain-upload warning beside it where the record names the landing place; what that warning offers is the route through that module, and the send that then runs is a row send and meets Q8 there.

**W1a. Which of the colliding files were placed by the dependency check is a per-file class, read off two of that module's record kinds and off nothing this document keeps. Added 2026-08-23, per Row 428.** For each landing path the walk of [X1](#41-the-walk-row-191) found occupied, `Dependency Upload & Remap` V1's local-record reading returns one of three:

- **neither** — no such record names it. ***Neither* is not [N7](#53-the-source-path-record-row-187)'s *no record***: N6's lookup answers a different question about the same path — where the file came from on the user's own computer — and neither answer decides the other, which is N9's shape applied to a second pair of readings.

Both stay true where an earlier plain upload has already published over the location — which is the case the warning is needed in most, since what stands there is then already an unfixed file the render will read — so nothing here compares this document's enumeration entries against that module's records for recency, and **no write ordering across record kinds is established anywhere to compare them by.** N6's recency rule is within one kind of entry and is not read across.

**The third machine location a fixing record names is not in this class**: the machine copy the fixed copy was derived from (its K8, M14) is what the fixed copy was produced *from*, and the render reads the fixed copy, so publishing over it puts nothing pointing at the user's own computer in front of a render. What publishing over it does instead is routed rather than decided here ([Section 13](#13-unresolved) item 15).

**W1b. The line is composed over the intersection and never over the record alone.** The warning names the files that both **collide** — [X1](#41-the-walk-row-191)'s walk found the landing name occupied in the destination listing — and class *placed* or *fixed* under W1a. **A record naming a path is never evidence that a file is there** ([X13](#44-the-partial-never-counted-row-197-and-row-191s-exclusion)'s discipline, and that module's Q10's), and nothing removes an asset from a machine by itself (`Dependency Upload & Remap` U1), so a record outlives a file the user removed with their own tools; such a path produces no line, because there is nothing to replace and no collision to warn inside. The files the line names are counted in [X3](#41-the-walk-row-191)'s headline total and named separately — the spec's own arrangement, *"counted in this already-exists total, and that warning names them separately"* ([File Browser](../Specs/File%20Browser.md)) — and the reading is W2's pre-flight one from the local record, with no read of the machine. **Two limits ride with it and neither is repaired here**: an alias the record does not spell is not matched ([W4](#82-the-comparison-behind-the-warnings-rows-193-and-192), [Section 13](#13-unresolved) item 5), and every such record is disqualified under a superseded installation identity (its K7, K10), so the class is *neither* on a recycled machine and no line appears. What the offer beside the line then does to the request is [3.7](#37-the-hand-over-to-dependency-upload--remap-row-428)'s.

**W2. The moments are the acts' own gates.** For an upload, the readings run against the enumeration's landing paths during the pre-flight, and what they name is presented with the already-exists question — the warned files counted in the headline total and named separately, the spec's own arrangement, placement Design's. For a delete, a move, a rename or a paste, the readings run when the destination (or the victim) is named, before the warning box.

**W3. ### 8.2 The comparison behind the warnings (Rows 193 and 192)

**W4. ### 8.3 The live set, and the ownership rule (Row 195)

**W5. The live set and the per-job set are both supplied, and the composition is this document's.** A job is live from its record's publication until its recorded outcome is written, held jobs included — the records with state *waiting*, *held* or *rendering* per machine (`Queue & History` Q2). What a live job depends on is the manifest's `.blend` plus the per-job resolved set fixed at submission, the remap material named inside it (`Job files and outputs` R15, `Dependency Upload & Remap` V5/K9), **plus the job's own folder** — the spec covers *"the folder and files a running job is writing to"*, and the job folder's path is on the job's record under `Job files and outputs`' layout. The trigger is a containment test and it runs both ways: the warning fires where the destination, the victim, or any path inside a folder being disturbed **equals a member of any live job's set, contains a member, or sits inside a member**, compared per component under [X5](#42-the-rule-collisions-are-judged-under-row-192)'s rule, **every holding job named** (V6).

**The second direction was missing until 2026-09-05, and it is added out of round 2 of the code audit of this module.** The test used to ask one question only — does a job's file sit inside the thing being touched — and never the other one, does the thing being touched sit inside a folder the job owns. The spec asks both in one sentence pair: *"The trigger fires on touching a file the job depends on, or on any change inside a folder the job uses"*, and this warning *"covers a job's `.blend` and the assets it reads, as well as the folder and files a running job is writing to"*. **The job's own folder is a member for exactly that reason** — a running render's frames cannot be listed at submission, so the folder stands for them — and the one thing that member exists to cover was the one thing the old test could not reach: a user clearing space deletes a finished frame inside a live job's output folder, and no warning, no telling and no disturbance mark follows. **Nothing needs to say which members are folders**: a disturbed path sits inside a member only where that member is a folder, because nothing sits inside a file. **And the widening is in the comparison and nowhere else** — listing a folder's contents at warning time would be a read of the machine, which [W1](#81-the-three-warning-readings-row-193) forbids outright, and the comparison needs none.

**Where a live job's own manifest `.blend` has been disturbed by one of Smoozy's own recorded acts, that job's set falls back to W6's widest case for the rest of its life: the manifest `.blend` path plus the job folder, and no resolved set.** The act that reaches this is inside the warning the spec puts here — a Replace publishing over a `.blend` a live job is reading (X7, W3). W6 makes the resolved set a snapshot never re-derived, and after such a Replace the snapshot describes a file that is no longer at that path: it names files the job may no longer touch and misses the ones it now does, which is past the spec's *the set Smoozy has may be smaller* grant, because it is not smaller but wrong. So the set is not used for that job. **This is composition and nothing more** — the disturb records W8 writes are already durable and already local, so no reading of the machine is added, no re-derivation is attempted, and nothing is written into `Dependency Upload & Remap` K9's set, which that document holds *"immutable for the life of the job's record"*. What the user loses is the narrow warning; what they keep is the wide one, said rather than patched, exactly as W6 already says for a job whose file was never checked.

**R15's staleness rule is deliberately not consumed, and the omission is a decision.** W5 takes from `Job files and outputs` R15 the manifest `.blend`'s path alone, and not the four-value identity of R10 or the test of R13, because applying that test would mean reading the machine at the moment a destination is named — which is exactly what W1 forbids for the warnings it answers. Those warnings are answered from the local record or not at all, and a staleness test that needs the machine is not available to them.

**W5a. How wide the live-job warning's statement may be. Added 2026-08-21, per Row 344.** [Design](../Design/File%20Browser.md) has it *"telling the truth about each — a running render may finish with wrong frames."* *(Re-quoted 2026-10-28, step 13's final words sweep: still a uniform* may*.)* **Re-quoted 2026-08-31: this carried the wording Design held when the clause was written — *a render already going may finish anyway with the wrong picture in it* — which Design corrected under Rule 10 on 2026-08-23, citing this clause.**

- **Per job, the warning may differentiate**, and W5 supplies what on: the live set is the records with state *waiting*, *held* or *rendering*, so a job that is rendering and a job that is waiting are told apart.
- **Per file, it may not, and that is `Dependency Upload & Remap` [V8](Dependency%20Upload%20&%20Remap.md#72-the-live-job-dependency-set-and-the-one-staleness-rule--row-173)'s decision taken at length**: *"**What a touched file does to the running render is deliberately not modelled, and the warning is uniform because the behaviour is not**"*, closing *"the warning covers every touch the same way and **promises nothing about what the touch does**."*
- **So the design's clause survives as a uniform *may* and not otherwise.** *A render already going may finish anyway with something wrong in it* claims nothing about any file kind and is what V8's uniformity permits. **Naming the picture case as the consequence is a per-kind claim V8 forbids** — it is one of the several behaviours V8 lists, and the others are not it.
- **The two documents stated it at different widths and that was recorded rather than repaired here**, because the wording is Design's — and Design repaired it on 2026-08-23. **What this document supplies is the bound**: uniform across files, differentiated across jobs.

**W5b. The warning's truth is exactly the local record's truth, and on a full mount the record cannot learn that a job has ended. Added 2026-09-02, out of the disk-fill scenario replay's finding N-i.** W5 composes the live set from the records with state *waiting*, *held* or *rendering*, and a job is live *until its recorded outcome is written*. **On a mount that has filled, the recorded outcome is exactly the write that cannot land**: `Rented-server runtime` S14 holds it pending in the run's memory and re-attempts it at the next request the supervisor serves, so the ending exists and is readable nowhere until space returns — and the act that returns space is the user's own deleting, which is the act this warning fires on. **So in that window a job that has ended reads live, and the warning fires over it.**

- **The finding said the warning is *necessarily wrong* there, and that is one step too strong — the honest word is *unverifiable*.** A render on a full mount may still be running: Fact 1's disk-full form is every write refused loudly with every read still truthful, and S14 has the supervisor answering throughout. **The one record that would tell a running job from an ended one is the write that refuses**, so nothing anywhere holds the answer.
- **This is why no composition changes and why W1's rule is not the cause.** Reading the machine at warning time is forbidden by W1 and would not help: the machine's own queue record carries the same *rendering*, its ending being the pending write. **Suppressing the warning while the supervisor-unavailable condition stands is refused** — a genuinely rendering job would then have its files disturbed with no warning at all, which is the harm W5 exists against, and the warning is non-dismissible on the Creator's own ruling (W7).
- **What it costs, and the cost is real rather than nominal.** The user clearing space to repair the very fault meets a non-dismissible warning naming a job that may already be over, on W5a's uniform *may finish anyway with something wrong in it*. They push past it — W3, the warning blocks nothing — and W8's telling then writes a durable disturb mark against that job. **W9 does not catch it**: W9 composes from whether the *units* took effect, never from whether the job was live, so a mark whose words are true — the file was disturbed, and the job did depend on it — stands on the entry of a job whose failure the disturbance did not cause. W10 keeps it for the life of the record.
- **What holds.** The warning never fails in the dangerous direction: it over-warns and never under-warns, which is the direction W7's non-dismissibility was chosen for. The mark is a record of the user's own overruling and claims no cause (`Dependency Upload & Remap` V8: the warning *"promises nothing about what the touch does"*). And the entry the mark lands on carries the machine's own words and the completeness statement beside it (`Queue & History` E7, E9; `Job files and outputs` C27), so the mark is never the only account of what happened.
- **Whether the local record should carry a pending or unknown state instead is `Queue & History` §11's question and is deliberately not opened here.** It would not change what this warning does — a job whose ending is unverified must still be warned over, because it may be rendering — so opening it would move the mark's wording at best, and this document does not compose that wording. Routed to the runner with that reason. [Section 13](#13-unresolved) item 18 carries the cost.

**W6. The ownership rule the Open Threads item asked for, closed:** a live job's set is a **snapshot**, fixed at submission and never re-derived — the manifest and the remap material are immutable, so *what does this job depend on* has one durable answer for the job's life (V5). The record goes stale only by Smoozy's own recorded acts, never by watching the machine (V6); a fresh root check is required only where a file is submitted as a new root, which is that module's V9 and no invalidation at all. **A job whose file was never checked has no resolved set, and the warning covers what exists: its manifest's `.blend` and its job folder.** That is the spec's own smaller-set clause — *"the set Smoozy has may be smaller than the set the job really uses"* — arriving at its widest, and it is said rather than patched.

**W7. The warning stays wide, and this document does not re-take that decision.** Creator-stated, 2026-08-12: the evidence reaches a scene's material picture and a linked `.blend` and nothing else, so no narrowing to the rendering scene's files. The warning's non-dismissibility is Creator-stated too, and no suppression row exists for it (M3).

### 8.4 The telling (Row 196)

**W8. The telling precedes the act, and its record is the disturb action's own outcome record in the local record.** When the user pushes past the live-job warning, one durable write lands **before the disturbing act's first machine effect**: the disturb action's §9.4 record, enumerating the affected jobs (by job identity) and the act intended. **Both are fields of that same record and never of a second one beside it**, because §9.4 gives one outcome record per action and the disturbing act is one action; for an upload that record is U1's, whose field list names them. Where that write cannot be made, the act is **not attempted**, naming the telling — §9.3's ordered pair, declared in [Section 11](#11-declarations): the disturbance without its mark is exactly the unexplained-failure-hours-later harm the spec names, so the act is unsafe unless the telling stood first. **The same write lands each affected job's disturbed-file mark on that job's local record** (`Queue & History` N21), reading *may have been disturbed* until the act's outcome is learned; W9 then finishes it or removes it. *(Added 2026-10-02, out of step 10c's map of Files' owed acts, closing `Queue & History` §18 item 22; no auditor of this document has seen it.)*

**W9. The act's outcome completes the mark, per job and from that job's own units, and uncertainty reads as uncertainty.** An upload with Replace and a multi-file delete are both partial across their units ([Section 11](#11-declarations)), so the act's own outcome is §9.4's *"derived from the list of unit outcomes and never a separate durable field"* and there is no single outcome to write against anything. **So what is written against a job is composed from the outcomes of the units that touched that job's own members** — the file it depends on, not some other job's — and **a job none of whose members' units took effect carries no mark at all** (took effect meaning published, for an upload's Replace, and removed, for a delete). Without that, a request whose units disagreed would mark jobs whose files never moved, and the mark whose whole purpose is to explain a failure hours later would point the user at a file that was never touched. The field `Queue & History` carries onto the entry — the V6/V13-shaped disturbance mark, wording Design's — is composed from the pair: intent plus confirmed outcome reads as *a file this job depends on was disturbed*; intent whose act's outcome was never learned — the connection died around the delete — reads as *may have been disturbed*, which is the truth. **The failure of the telling after the disturbance cannot arise**, because the telling came first; the only residue is a mark for an act that then never ran, and the composed reading covers it without lying.

**W10. The mark's durability is the local record's, which is the gap it exists to span.** It survives Smoozy closing, the connection dropping and the machine being destroyed, and it is readable when the job fails hours later in a later sitting — the entry, and history after it, carry the fields unchanged (`Queue & History`'s supply). Nothing about the mark stops the user; the warning was theirs to overrule and the mark records that they did.

**W11. The check standing's *disturbed* mark is written by the act that disturbs, and this clause is the actor `Dependency Upload & Remap` V13a states and this document did not carry. - **Which acts of this document's owe it.** Every one that **publishes over** a machine location or **removes** one: an upload's publication ([X7](#42-the-rule-collisions-are-judged-under-row-192)), a copy's and a same-filesystem move's publication ([M5](#73-move-row-192-and-the-partial-action), [M7](#74-copy-rows-192-and-197s-shape-machine-locally)), a delete ([M2](#71-delete-rows-194-and-181)), and the source removal inside a cross-filesystem move's ordered pair ([M6](#73-move-row-192-and-the-partial-action)). - **When, and only for what took effect.** In the same act that records the unit's outcome, which is [X7a](#42-the-rule-collisions-are-judged-under-row-192)'s own moment, and **only for a unit that took effect** — published, for a publication; removed, for a removal; renamed, for a rename or a move away (added 2026-10-02). That is [W9](#84-the-telling-row-196)'s rule taken for the same reason: a request whose units disagreed would otherwise mark a standing over a file that never moved. - **Which standings, read off that module's own record and off nothing kept here.** For the machine location the unit published over, removed or moved away from, its [V2](Dependency%20Upload%20&%20Remap.md#71-what-smoozy-knows-about-a-machine-answerable-before-a-write--row-172) points-at reading answers which located answers resolve to it, and **every root whose tree those answers belong to has its standing marked**. - **The comparison, and the limit it carries.** [X5](#42-the-rule-collisions-are-judged-under-row-192)'s rule applied whole — byte-for-byte per path component against the location as that module's record holds it, no folding, no normalisation, no canonicalising, no resolution of any kind — exactly as X7a's two writes compare. **[W4](#82-the-comparison-behind-the-warnings-rows-193-and-192)'s alias limit rides on this write too and is not repaired here**: a location reached through an alias the record does not spell is not matched, no mark is written, and nothing at submission catches it. - **The two standing marks are independent and neither stands in for the other.** One machine location can be one standing's root file and another standing's resolved tree member at once — a linked `.blend` the user also checked as a root in its own right is exactly that — so X7a's replaced-since-check write and this one may both fall due at one publication, and both are made. **What this puts in front of the user is nothing, and that is the test it had to pass.** No warning is created and none is widened — V3's plain-upload warning, W1a's three classes and the two non-dismissible warnings are all untouched. ### 9.1 Carrying on across a repair (Row 199)

**K1. The two labels decide, and they are read rather than re-derived.** `Servers` 12.2: a **replacement** connection runs C11's four steps, whose step 4 re-establishes channels for every transfer whose record says *interrupted within the current application run* and resumes each under S12; a **period-opening** connection resumes nothing. **K3. The line not crossed:** nothing resumes on a period-opening connection, nothing resumes from an earlier run (C11 step 4), and no upload starts itself in a fresh sitting (U8) — C13's rule, the spec's own sentence, kept by construction.

### 9.2 Carrying on inside a single file (Row 200)

### 9.3 The unchanged file (Row 201, and Fact 30)

**Constraint:** Row 201's three clauses — a file changed mid-upload is stopped, not landed; a resume after a drop carries on only where the file has not changed; and an accepted offer waits until the file has been left alone for a moment. `Server protocol and transfers` S13 assigns the unchanged-source answer for a file on the user's own computer here by name; `Dependency Upload & Remap` A10 offers a contents test for this row to adopt or overrule.

**K6. Fact 30 was posed on the Creator's own Mac on 2026-08-20, with a real Blender save and a real Blender texture export, in a throwaway that touched nothing of the Creator's** — Blenders launched by the throwaway itself, all files inside a scratch directory, the open Blender instance untouched. Label: **observed** (macOS 26.5.2, APFS, Blender 4.5.12 and 5.0.1); the full evidence, the controls and what a negative would have looked like are in [Sources](Sources/File%20Browser.sources.md). The findings that decide this section:

- **A real `.blend` save is a swap-in.** Both versions wrote a temporary `name.blend@` beside the file and renamed it over the final name: the path's inode, size and modification time all changed in **one atomic transition**, caught by a path reading within 100 ms. **The handle held open across the save went on delivering the pre-save file, whole and coherent** — the swap-in case is real, and any arrangement that watches or trusts the open handle is defeated by it: the file the transfer holds open is no longer the file the name points at.
- **A real texture export writes in place.** The same application's image save truncated the existing PNG to zero and rewrote it under the **same inode**, and the rewritten file came out **byte-count-identical** to the old one — only the modification time moved. So the inode catches nothing there, the size catches nothing there, and a held handle delivers a mixture of old prefix and new tail — the torn read is real too.
- **A control run with no save produced zero identity changes and equal digests** — the watch can fail, so it is a test.

One application, two save shapes, each defeating the check the other suggests. What follows is built so that no clause rests on either shape.

**K7. The arrangement identity.** When a transfer is arranged — and again when a quiet period ends — the source's path identity is read and recorded: size, modification time at the finest the system reports, and the file identifier where the system has one. Read by path, never by handle. It is a reading and carries its moment (D5); comparisons of it are always desk-clock-to-desk-clock readings of one path, so no clocks are mixed.

**K8. The watch — the mid-upload clause's early half.** At each accounting interval of the byte loop — bounded in time by R6's fixed short period — the path identity is re-read and compared. **Any difference stops that transfer**: the record is written **stopped**, the staged material is never published (S24's shape) and is removed at once or owed as a cleanup under S27, and the user is told the file changed while it was being sent, with the offer to send the new version — the spec's flow, wording Design's. Both observed save shapes move the modification time, so both are caught within one interval on the observed system.

**The ending is named, because S26 closes the set at three and this document produces endings of its own.** *Published*, *Stopped, deliberately* and *Interrupted* are the whole list; *interrupted* is what U5 composes as *waiting* and what `Server protocol and transfers` C11 step 4 re-establishes and resumes. **A transfer Smoozy stopped must be neither of those**, or a failed file would show amber as waiting for the connection on a live and healthy line and would then be resumed at the next repair. **So the record says *stopped*** — here, at K9's refusal, and at X7's create-intended refusal — and S26's stopped row prescribes exactly the removal these three want, while excluding them from U5 and from C11 step 4 by construction rather than by an added exclusion. That S26 words the row *"Stopped, deliberately"* while this is Smoozy stopping rather than the user **is settled in that document: S26a says *deliberately* means *on a deliberate instruction* and need not be the user's, which is exactly these three endings. Corrected 2026-08-29: this called it a wording seam handed to the runner and not an edit made to that document, which stopped being true when [Section 13](#13-unresolved) item 12 closed on 2026-08-22.**

**K9. The publication gate — the clause the no-corruption promise rests on, and it rests on arithmetic.** Before any upload's publication, **the source is read through once more and digested, and publication happens only where that digest equals the transfer's own pass-through digest** — the digest of what was actually sent, computed as the bytes passed (S22). Where they differ, the transfer is stopped with the same changed-while-sending answer — the record written *stopped*, as at K8 — and nothing is published. **What the gate delivers, stated as what it delivers:** two full readings of one path being equal while their contents differ is impossible for a quiescent file and is *not* impossible for one being written concurrently, so no impossibility is claimed. What the gate does is reduce a miss to a coincidence — a concurrent writer leaving the second full reading with the same digest as the bytes that were actually sent — that is **astronomically unlikely rather than impossible**, and where the two agree, what was sent is one coherent version. **So a torn read, a swap the watch missed, a writer that restores modification times (Fact 72's observed shape), and any save on any operating system whose stat moves nothing are all caught at the last moment that matters, by contents alone.** The cost is one local read-through per file — about 1.3 to 2.2 seconds for a 670,000,000-byte file on the observed Mac (Fact 15), against an upload of the same file measured in minutes — and the check against the third escalation is recorded at [Section 14](#14-moments-that-reached-the-creator).

**K10. The resume rule — S13's answer, and A10 adopted.** A resume of an upload proceeds only where both hold:

1. **the path identity equals the arrangement identity** (K7). Where it differs, the upload does not resume: Smoozy says the file changed while it was being sent and offers to send the new version — the spec's own sentence for a save that landed while the line was down. Nothing is claimed beyond what the identity showed.
2. **the staged prefix verifies by contents against the source as it now is** — `Dependency Upload & Remap` A10's test, **adopted**: the source is read up to the highest checkpoint and digested, and the resume proceeds only where that digest equals the checkpoint's recorded running digest, so carrying on writes exactly the current source's bytes. Where the identity is unchanged and the prefix still does not verify, the transfer starts over from zero into a fresh staging path (S12 step 5) with no claim made about the user's file — staging damage and a stat-invisible change are indistinguishable there, and starting over is safe under both.

A resumed transfer's running digest continues from the checkpoint, so K9's gate still compares the whole file at publication.

**K11. The quiet period is two seconds, and it is a test on the path identity — so what it can see and what it cannot are both stated.** On accepting the offer — and before any send of a file that changed — K7's path identity is polled at the accounting period, and the send starts when it has held unchanged for **two seconds**.

**It detects an in-place writer.** Such a writer moves the path's own values while it works: the observed texture export truncated the file to zero and then rewrote it, and both moments were caught by 100 ms polling, so the quiet period sees the writing and waits it out.

**It cannot detect a swap-in writer still preparing its replacement.** That shape writes a temporary beside the file and moves nothing at the path until the final rename, and the observed `.blend` save is that shape — so through the whole time such a save spends writing, the target path's identity does not move, and **the two-second test passes immediately while the save is still running**. On the save shape Row 201's first clause is written about, the quiet period is vacuous.

**The number's justification is about the transition, not about the writing.** What the observation establishes is that each shape's identity *transition* completed inside one 100 ms poll — which is why two seconds is a comfortable margin for a change the poll can see, and why it says nothing about how long a save spends preparing one. Two seconds is imperceptible against a transfer measured in minutes. It is a declared constant, not a tuning left open. **No better test is invented here**: the temporary appearing beside the file is one Mac, one application and one naming convention, and Rule 2 forbids building on how any application usually saves. **What this sentence did not say, and now does — 2026-08-21 — is that a standard instrument for *has anything landed in this folder* exists and is documented on all three systems**, so the silence above should not be read as *nothing else exists*. Apple's File System Events — *"Get notifications when the contents of a directory hierarchy change."*; Linux's `inotify(7)` — *"When a directory is monitored, inotify will return events for the directory itself, and for files inside the directory."*, with events for a file created, a file renamed into the directory, and a file opened for writing being closed; and Microsoft's `ReadDirectoryChangesW`, whose name-change notification covers *"renaming, creating, or deleting a file"*. **None of them asks the caller for a filename or a naming convention**, so none of them is what Rule 2 forbids. **They are not adopted here and adopting one is not this document's to decide.** What they would improve is how early the watch fires; they do not touch what Rule 2 is actually about, which is whether a rename landing at the path is what a save looks like — that is Fact 30's and Blender's. **One caution travels with them if they are ever taken up**, from Microsoft's own page: on buffer overflow the entire contents of the buffer are discarded and the caller must then enumerate the directory itself, so a notification route needs the polling route underneath it rather than instead of it. What follows for the swap-in shape is the spec's own stop-and-offer loop — K8 catches the swap when it lands and K9 catches it at publication whatever the watch saw — and [Section 13](#13-unresolved) item 6 carries it.

**K12. This section is the one unchanged-source answer, for every upload of a local source.** `Server protocol and transfers` S13 reads it as: *a resume of an upload resumes only under K10, and otherwise starts over or enters the offer flow as K10 says*. `Dependency Upload & Remap` follows this row by its own words: its A10 stands as adopted inside K10, its uploads inherit the watch, the gate and the quiet period unchanged, and the torn-mid-read exposure its A10 deliberately left open is closed by K9 for its transfers exactly as for this document's.

**K13. What is answered where, and what breaks where it is not.** The mid-upload clause, the resume clause and the quiet period are **answered on macOS by observation**. On Windows and Linux the mechanism is identical and two things are unestablished: whether every real application save moves the path identity (K8's earliness) — and on Windows that is worse than untested, since Microsoft documents the modification time as not fully updated while a writing handle is open — and **which filesystem a given Linux machine actually carries**, Windows' granularity being documented and ext4's default now read at ext4's own documentation ([Section 13](#13-unresolved) item 6). **Corrected 2026-08-22: this put the granularity open on both systems, which item 6 stopped saying on 2026-08-20. Corrected again 2026-08-23: it then put Linux's granularity open, and the kernel's own ext4 documentation states the default inode size the widening turns on.** **What is at risk there is a promise, not a wording, and it is named as one.** Row 201's third clause reads *"the upload does not resume: **Smoozy says the file changed while it was being sent and offers to send the new version**"* — the saying and the offering are the promise. Where the path identity does not move, K10's two gates decide instead, and **both failure shapes are silent**:

- **a silent start-over** — clause 1 passes on an unmoved identity, clause 2 fails on contents, and S12 step 5 restarts the transfer from zero with nothing said and nothing offered;
- **a silent carry-on** — a writer that changed only the region beyond the highest checkpoint, in place, and restored the modification time: both clauses pass, and the resume carries on, again with nothing said and nothing offered.

**The no-corruption promise survives both**, because K9's gate is contents arithmetic at publication and lands nothing that changed — the transfer merely runs longer before stopping, or completes a file the gate has checked whole. **What each falls back to is honest and granted**: the start-over is the spec's own alternative in the same paragraph, *"sends that file again from the beginning where it cannot"* tell the file is unchanged; the carry-on completes the current source's bytes, which is what K10 clause 2 tested for. What neither delivers is Row 201's saying and offering, and calling that *wording* would invite a reader to treat it as cosmetic. **The Method's second stop was weighed and not reached**: the clause the spec's sources said the no-corruption promise rests entirely on is kept on every system by the gate, and the fact came back positive where it could be posed at all.
