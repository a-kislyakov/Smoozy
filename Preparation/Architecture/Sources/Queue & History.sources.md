### 1.5 The three supported systems' own cryptographic random sources (Y1)

**Added 2026-08-23.** Y1's *128 bits drawn from the operating system's cryptographic random source* stood **unlabelled in the body and with no citation anywhere in `Preparation/`**, recorded below in Section 4 as an assumption with no source found. It is now read off each system's own publication. Label: **documented**, all three read **2026-08-23**. The three supported systems are the shape document's: Mac, Windows and Linux.

- **Linux** — the Linux man-pages project, `getrandom(2)`, `https://man7.org/linux/man-pages/man2/getrandom.2.html`, page dated `Linux man-pages 6.18  2026-02-08`. *"The getrandom() system call fills the buffer pointed to by buf with up to size random bytes. These bytes can be used to seed user-space random number generators or for cryptographic purposes."*; *"By default, getrandom() draws entropy from the urandom source (i.e., the same source as the /dev/urandom device)."*; *"If the urandom source has been initialized, reads of up to 256 bytes will always return as many bytes as requested and will not be interrupted by signals."* The same publication and the same project already own `clock_gettime(2)` at [The computer itself](../The%20computer%20itself%20—%20its%20name,%20its%20identity,%20and%20its%20clock.md).
- **macOS** — Apple, *Security* framework, `SecRandomCopyBytes(_:_:_:)`, `https://developer.apple.com/documentation/security/secrandomcopybytes(_:_:_:)`. *"Generates an array of cryptographically secure random bytes."*; the `bytes` parameter is *"A pointer to an array that the function fills with cryptographically secure random bytes."*; `count` is *"The number of random bytes to return in the array pointed to by the bytes parameter."* Available on macOS from 10.7. **The page is drawn by script and its text was taken from Apple's own documentation feed for that address**, `https://developer.apple.com/tutorials/data/documentation/security/secrandomcopybytes(_:_:_:).json`, which is the same publication served as data.
- **Windows** — Microsoft, `BCryptGenRandom` (bcrypt.h), `https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgenrandom`. *"The BCryptGenRandom function generates a random number."*; the buffer is caller-sized — `cbBuffer` is *"The size, in bytes, of the pbBuffer buffer."*; and *"The default random number provider implements an algorithm for generating random numbers that complies with the NIST SP800-90 standard, specifically the CTR_DRBG portion of that standard."*

**What the three establish:** each supported system publishes a cryptographic random source, and each fills a buffer of the caller's own size from it. Sixteen bytes is inside every one of those — well inside `getrandom(2)`'s uninterrupted 256, and unconstrained on the other two.

**Not covered.** **No page states a collision bound**, and none is quoted as doing so: Y1's *uniqueness rests on the width of the draw alone* is the arithmetic of 128 bits and is Smoozy's own reasoning, not a documented claim. Nothing was read about what any of the three does before its source is seeded — `getrandom(2)`'s own wording is conditional on the urandom source *having been initialized* — which is a boot-time condition the desktop application does not run in. And the three pages are the systems' publications, not observations: nothing here was run.

**Routed, not edited.** The same claim stands unsourced at `Audits/Architecture/Access/Decisions record.md` D5 and at [Rendering](../Rendering.md) S3, which restates Y1. **Both are named for the runner and neither is touched here**; the addresses above are what they need.
