# Sources — Rented-server runtime (Architecture)

*Where every outside-world claim in [Preparation/Architecture/Rented-server runtime.md](../Rented-server%20runtime.md) came from. The document carries each claim's label in place; this file carries the citation, the exact words, the date read and what the source does **not** cover. **Decisions Smoozy made get no entry here** — [Conventions](../../Groundwork/Conventions.md) is explicit that copying a decision into a sources file gives it a second home that drifts.*

**Three shapes, and there is no fourth.**

1. **Owned by an input document of this stage** — one of the frozen observation documents in `Preparation/Architecture/`, or [Facts](../Facts.md) where it is the register entry that carries the answer. The entry names that document, quotes the fact in the words that document uses, and says what the observation does not cover. This is the commonest shape here and it is a pointer rather than a re-citation.
2. **A publication quoted directly** — a manual, a standard, a protocol draft, a vendor's own reference. The entry carries the exact words, the address and the date read, taken from the document or from elsewhere in `Preparation/` and from nowhere else.
3. **No source in this project** — recorded as an assumption, as unresolved, or as an address gap where the words and the date exist and the address does not. Nothing here is filled in from outside the project.

**Every entry of shape 1 inherits the input documents' own standing limit**, which the document restates at its head: *"Read it as *this is what that box did*, never as *this is what a rented machine does*."* It is not repeated per entry; where an entry's *not covered* names something narrower, that is in addition to it.

**Blender is never re-derived here.** Where the document leans on Blender, the entry names the joined answer and the comparison question the document itself already names, and nothing more. Those entries are gathered in section 3.

**What this carries:** three separate things. ## 2.5 POSIX `write()` and the signal definitions — keeping a child pipe drained (M5)

**Source 1:** The Open Group Base Specifications Issue 7, 2018 edition, `write()`, read **2026-08-21** at `https://pubs.opengroup.org/onlinepubs/9699919799/functions/write.html`. Label: **documented**, the standard's own text. Exact words:

> "A SIGPIPE signal shall be sent to the calling thread."

— where no process has the pipe open for reading, with the write returning `EPIPE`; and, of writes to a pipe or FIFO with `O_NONBLOCK` clear:

> "a write request may cause the thread to block"

**Source 2:** the same edition, signal definitions, read **2026-08-21** at `https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/signal.h.html`. Its signal table names `SIGPIPE` as *"Write on a pipe with no one to read it"* and gives the default action as termination.

## 2.17 `user@.service(5)` and the login manager's own source — what a lingering grant starts (K7's correction of 2026-09-21)

**Why the source and not only the page.** `loginctl(1)` says of the grant only *"If enabled for a specific user, a user manager is spawned for the user at boot and kept around after logouts"*, which does not say whether anything starts before the next boot. K7's correction rests on the grant starting the manager at once, so the login manager's own code is cited for that half. All read **2026-09-21** from the systemd project's own repository. Label: **documented**.

**Source A — `user@.service(5)`**, `https://raw.githubusercontent.com/systemd/systemd/v255/man/user@.service.xml`. Exact words:

> "user@UID.service is accompanied by the system unit user-runtime-dir@UID.service, which creates the user's runtime directory /run/user/UID, and then removes it when this unit is stopped."

**Source B — `method_set_user_linger`**, `https://raw.githubusercontent.com/systemd/systemd/v255/src/login/logind-dbus.c`, and the same function at `v249` (`https://raw.githubusercontent.com/systemd/systemd/v249/src/login/logind-dbus.c`). The enabling branch, identical at both tags:

> "r = touch(path); … if (manager_add_user_by_uid(m, uid, &u) >= 0) user_start(u);"

**Source C — `user_start`**, `https://raw.githubusercontent.com/systemd/systemd/v255/src/login/logind-user.c`, with its own comment *"Start user@UID.service"*, and `user_start_service`, whose comment reads *"Start the service containing the "systemd --user" instance (user@.service). Note that we don't explicitly start the per-user slice or the systemd-runtime-dir@.service instance, as those are pulled in both by user@.service and the session scopes as dependencies."* It queues the start (`manager_start_unit`) and does not wait for it.

**Which versions and why.** `v249` is the systemd Ubuntu 22.04 ships and `v255` the one Ubuntu 24.04 ships — the two images the second pass rented. **That pairing is itself not read from Ubuntu here**, and is an expectation.

**What this carries:** K7's correction — the grant creates the runtime directory by starting the user's service manager, with no session, and the start is queued rather than awaited, so the enable waits for the manager to answer. **Not covered:** any image whose polkit policy refuses the grant (K8, §16 item 2, and K5's read-back is what catches it); any systemd version but these two; and whether the image's own packaging changed this code. **Not observed**: no machine has run the corrected order.
