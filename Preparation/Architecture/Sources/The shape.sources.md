## The updater's replacement operation on the three systems (Fact 74; Row 280)

**Owned by:** [The user's own computer — where a download lands, what it will take, what it will show, and how the app replaces itself](../The%20user's%20own%20computer%20—%20where%20a%20download%20lands,%20what%20it%20will%20take,%20what%20it%20will%20show,%20and%20how%20the%20app%20replaces%20itself.md) §5, read against `Facts.md` Fact 74. Label: **documented**, with the macOS file-level half also **observed in a test**.

**What it answers.** *"The promise is reachable on all three systems, and not by one shared mechanism."* macOS: Apple's page names in-place modification as the wrong route — *"macOS caches information about the code's signature in the kernel"*, *"can cause a hard-to-reproduce code-signing crash"* — and write-to-temporary-then-rename as the right one, with a supported API carrying a named backup for rollback; *"No prompt, no elevation and no administrator appears anywhere on that page"*. Windows: an unpackaged per-user executable *"downloads the update to a hidden folder without any user interaction"*, *"verifies and installs it"*, stops and restarts, and users *"don't need administrative rights to install the update"*; every documented route puts the new build elsewhere — *"is reinstalled from a new side-by-side folder"* — so **the Windows answer is side-by-side, not in-place**. Linux: the rename call documents that an existing path *"will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing"*.

**Repaired in the body 2026-08-23.** The body's macOS and Linux clauses now read as `Desktop app and delivery` Z5, E4 and Z10 and the register's narrowing have them; the Windows clause was already right and did not move. The two rules the macOS clause rests on are quoted in that document rather than here — Apple, Technical Note TN2206, *macOS Code Signing In Depth*, `https://developer.apple.com/library/archive/technotes/tn2206/_index.html`, page updated 2016-09-13, read 2026-08-22: *"Code signatures made in Mavericks and later always seal all files in a bundle; there is no need to specify this explicitly any more"* and *"Bundles should be treated as read-only once they have been signed"*.

**Not covered, and what the two clauses were before they were repaired.** `Facts.md` Fact 74 records the narrowing of 2026-08-22: **on macOS the update no longer replaces the executable inside the bundle at all** — [Desktop app and delivery](../Desktop%20app%20and%20delivery.md) Z5 makes the replaceable unit the complete signed bundle at the installed path, on Apple's TN2206 sealing rule, and **the directory form of the named-backup replacement is unread** (that document's Section 22 item 43). **And the Linux half no longer describes the update route**: E4 and Z10 make the Linux artifact a signed, dependency-declaring package installed through the distribution's package mechanism, and Z10 states *"A raw executable copied over an old path is not a Linux release/update route"*; Fact 74's `rename(2)` reading underwrites ordinary data publication there and nothing about how a new version arrives. **That is what the body's macOS and Linux clauses said until 2026-08-23; the input document supported only its Windows clause.** Also not covered: whether a quarantined macOS app re-triggers first-open approval for the copy it writes for itself is documented on no first-party page read, and what clearing that dialog costs is unestablished; the Windows signing gate is an identity and cost gate, not a technical one, and Microsoft's own words are that a SmartScreen warning does not clear on its own at this scale.

## The machine-local endpoint's caller identity (Fact 84)

**Owned by:** [The host key — obtained without authenticating, and whose it turns out to be](../The%20host%20key%20—%20obtained%20without%20authenticating,%20and%20whose%20it%20turns%20out%20to%20be.md), through `Facts.md` Fact 84, on both machine kinds. **What it answers.** The mechanism is **peer credentials read from the kernel on the accepted connection** — `getsockopt(SOL_SOCKET, SO_PEERCRED)` on an `AF_UNIX` stream socket. On a container, a server at an endpoint deliberately left mode `0666` was told `pid=1628 uid=1000 gid=1000` for a caller running as the ordinary login, and the caller's own view agreed exactly; it survives the reduced capability set. **Not covered.** This is the boundary's **second** layer only. The first — the endpoint and its containing directory owned by the supervisor's login and permitting that login alone — was observed where Fact 1's narrow clause was posed and stands independently. Two rentals, one provider each.

## The package commit's and publication's interruption boundaries (Fact 78)

**Owned by:** [The last two boxes](../The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md) §8, with [Six machines](../Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md) for the ext4 rename reading. Label: **observed in a test**.

**What it answers.** The virtual machine posed **ext4** and **xfs**, the container posed **overlayfs**, and *"Every death was a real forcible kill without unwinding."* Across the four commit boundaries: **no part-arrived bytes at a final name, ever, on any of the three**; *"The pointer always named exactly one of the two versions — never neither"*; every retry under the same identity resolved correctly; and the container's checks returned empty mismatch, missing, unexpected-temporary and staging-leftover lists at every boundary. Publication into a final name by rename is atomic and swaps the whole file.

**Not covered.** **The rollback boundary could not be posed**, blocked twice over — a real rollback was observed and never interrupted mid-flight. The `pointer` and `pointer-done` boundaries leave the **same phase** and are told apart only by reading the pointer, so *the retry can tell from the phase record which branch it is on* is true only of the phase record **plus** the pointer. No single operation updates two independent files atomically: the matching pointer-and-registration pair is a design obligation built on single-rename atomicity plus ordering, not a filesystem primitive. The xfs pre-health retry rolled back where ext4 and overlayfs went to verified — one run each, attributed to the health-exchange deadline on a contended box, **not** to xfs. Litter nobody swept: the temporary file left by an interrupted hold publication survived hours, several supervisor restarts and full reconciliation on all three filesystems. Filesystems outside those three: nothing claimed either way.

## The genuine power cut — unresolved, no source in this project (Fact 44)

**Label: unresolved.** No input document answers it and none is expected to. `Facts.md` Fact 44 records it as **posable at all today: no** — *"No machine this project runs today can pose it"*. ## The desktop-side publication of a staged download — assumption (Fact 79; Rows 208, 209, 212, 281)

**Label: assumption, and the document says so in place.** *"the receiving filesystem on each of Mac, Windows and Linux can perform the desktop side's chosen final-name publication operation without exposing part-arrived download bytes, and can recover that operation without making an incomplete file look complete."* **The body stated that as open on all three systems without distinguishing the fact's two routes, until 2026-08-23; it now separates them, and the assumption's label rests on the untouched throwaway route rather than on the documentation route.**

**The Windows negative, read first-hand for this document. Label: documented.** No address for either Microsoft page existed anywhere in `Preparation/` — `Desktop app and delivery`'s own sources file records that gap as its item 5 — so both pages were read and the addresses recorded here.

- **`ReplaceFileW`**, Microsoft, *ReplaceFileW function (winbase.h)*, `https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew`, page dated 2018-12-05, read 2026-08-23. Among its named error codes, `ERROR_UNABLE_TO_MOVE_REPLACEMENT` 1176 (0x498): *"The replacement file could not be renamed. If lpBackupFileName was specified, the replaced and replacement files retain their original file names. Otherwise, the replaced file no longer exists and the replacement file exists under its original name."* The page's own opening line is *"Replaces one file with another file, with the option of creating a backup copy of the original file. The replacement file assumes the name of the replaced file and its identity."*, and `lpBackupFileName` is *"The name of the file that will serve as a backup copy of the lpReplacedFileName file. If this parameter is NULL, no backup file is created."* **This is the sentence the body now quotes.**
- **`MoveFileExW`**, Microsoft, *MoveFileExW function (winbase.h)*, `https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw`, page dated 2018-12-05, read 2026-08-23. `MOVEFILE_REPLACE_EXISTING`: *"If a file named lpNewFileName exists, the function replaces its contents with the contents of the lpExistingFileName file, provided that security requirements regarding access control lists (ACLs) are met."* `MOVEFILE_WRITE_THROUGH`: *"The function does not return until the file is actually moved on the disk. Setting this value guarantees that a move performed as a copy and delete operation is flushed to disk before the function returns. The flush occurs at the end of the copy operation."* **Read end to end for a crash guarantee: the page carries none** — the write-through flag is about flushing before the call returns, not about what survives a crash mid-operation.

**Both pages agree word for word with what `Facts.md` Fact 79 and `Desktop app and delivery` F16 and F20 already carried; nothing was corrected by the reading.** What the reading adds is the two addresses and a date, and the confirmation that the absence of a crash guarantee on `MoveFileExW` is an absence on the page rather than an unread page.

**What the project does hold, and it is more than the body claims.** `Facts.md` Fact 79 records the **documentation route answered for Mac** — Apple's `rename(2)` manual, macOS 26.5, page dated 2021-06-03, read 2026-08-17 while writing [Server protocol and transfers](../Server%20protocol%20and%20transfers.md): *"guarantees that an instance of new will always exist, even if the system should crash in the middle of the operation."* — and **for Linux through Fact 78**. ## The local computer identity (Fact 11)

**Owned by:** [The computer itself — its name, its identity, and its clock](../The%20computer%20itself%20—%20its%20name,%20its%20identity,%20and%20its%20clock.md), through `Facts.md` Fact 11. Label: **documented**, and the answer is **negative on all three systems**.

**What it answers.** Every identifier an ordinary downloaded application can read is a value the operating system hands over on request, and each vendor documents that it can be changed or spoofed — Apple: any I/O Registry property can *"be spoofed by knowledgeable persons"*; Microsoft: *"someone can easily spoof a software KSP as a TPM KSP with local administrator credentials"*; systemd: the kernel command-line override *"has higher priority and will be used instead of the ID stored in /etc/machine-id"*. Every route that resists forgery demands enrolment, an enterprise authority or out-of-band material a website-distributed binary does not have. Stability is documented only in patches.

**Not covered.** **Forgeability itself was never tested on any system** — all three are documented assertions rather than demonstrations. `Audits/Architecture/Access/Decisions record.md` §4 chooses the Windows identity on the strength of the only documented stability contract of the three, and **which `Source` an unpackaged, website-distributed binary receives is settled by no reading**: it wants running the call on a Windows computer, which this project has not got.
