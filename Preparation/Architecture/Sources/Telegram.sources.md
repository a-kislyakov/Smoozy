## 1. The 2026-08-12 behaviour run — one token, three rented Linux machines

Every entry in this section is a **pointer** to [`Preparation/Specs/Sources/Telegram.sources.md`](../../Specs/Sources/Telegram.sources.md), the spec's own companion, which is where that run's outcome is written down inside `Preparation/`. Label for the section: **observed in a test** (2026-08-12), except where an entry says otherwise. The run's own stated limits bind every entry and are not repeated one by one: **three machines and no more, no run longer than a minute, no webhook exercised at all, and one Telegram account.**

**1. Sending one token from several holders is not exclusive; receiving it is, and the refusal says so word for word.** Used at [Telegram](../Telegram.md) §3's observed-ground paragraph, B1, B7 and R6, and it is the ground the whole slot arrangement stands on. **Pointer:** *"two machines sent 120 messages into one conversation at the same time with no refusal, and every ordinary call behaved the same. Receiving is exclusive and says so plainly — `409 Conflict: terminated by other getUpdates request; make sure that only one bot instance is running`."* **Not covered:** more than three machines; any run longer than a minute; webhooks. **And documentation could not have answered it** — the same file records that Telegram's own pages, read that day, *"never addresses more than one program holding one token"*, the only stated exclusivity being between `getUpdates` and a webhook, with the nearest sentence a security warning: *"Everyone who has your token will have full control over your bot."* Nothing in [Telegram](../Telegram.md) rests on that warning; the token's own protection is `Security and licence` §10's.

**2. The newest request always wins, and two machines that both retry destroy each other.** Used at §1's one-line *why* for taking T4 to T14 as given, and at B5, B6 and B7, whose whole purpose is to stop the retry storm. **Pointer:** *"The newest request always wins, whichever machine it comes from, so a machine takes over listening simply by asking — which is a free hand-over and also a hazard"*, and *"three machines all polling for a minute produced 61 attempts, 60 conflicts and 1 success, with nobody listening for about 92% of the time."* **Not covered:** the same shape at more than three machines, and any arbitration attempted at the time — the run demonstrated the failure, not a remedy.

**3. Reading the reported pin does not disturb the machine that is receiving, and reading is cheap.** Used at §3's observed ground, B5, B13 and B15, and it is what makes a 2-second read cadence on every machine admissible. **Pointer:** *"one machine polled a full 25 seconds at 200 while another read the chat three times during it, and the listener was never thrown off"*, and *"three machines reading once a second for a minute gave 168 reads and no refusals."* **Not covered:** a day at that cadence; more than three readers; **which call the reads were made with is not named in that record** — see entry 37, which is where [Telegram](../Telegram.md) §21 item 4 calls them `getChat` calls.

**4. The pinned message reported for a chat is the most recent one by sending date.** Used at B1's *"the reported pin is the board in the steady state"*, B3, B4, B5 and B11. Label: **documented and observed in a test**. **Publication and pointer:** Telegram's Bot API documentation, `core.telegram.org/bots/api`, checked 2026-08-03 and again 2026-08-12, where `ChatFullInfo` describes `pinned_message` as *"The most recent pinned message (by sending date)"*; confirmed the same day, *"where one machine's pin displaced another's from the reading and both machines then read the newer one."* **Not covered:** group conversations, and what the reported pin says when the newest pinned message has been deleted rather than unpinned — that half is entry 5.

**5. Pinning is a stack rather than one slot, and deleting a pinned message is not the same as unpinning it.** Used at B3, B11, B17 and B18, and it is why the machinery unpins and never deletes. **Pointer:** *"Pinning is a **stack, not one slot**: unpinning the newest revealed the older one underneath, so an older pin is hidden rather than destroyed. Deleting a pinned message left the slot reading absent rather than falling back."* **Corrected 2026-09-14 from a code round (the bot and the chat, round 1, U2):** the reported pin is the most recent pinned message **by sending date** (entry 45a), so this run shows an older pin revealed only where the pins went in sending order; a machinery message older than the board is never revealed this way (`Telegram` B11, entry 83). **Not covered, in that file's own words:** *"group conversations, how deep the stack goes, and whether an older pin can be read without unpinning the newer one, which was not tried"* — the last two are Fact 64, entry 68. **Also observed and not relied on:** the bot's own messages can be taken back with `deleteMessage`, and *"An id that is not there answers `Bad Request: message to delete not found` — so *deleted* and *never existed* are not told apart"* ([One box](../One%20box%20—%20the%20Telegram%20capture%20and%20the%20port%20that%20cannot%20be%20chosen.md)); no rule in [Telegram](../Telegram.md) deletes anything.

**6. A bot can pin in a private chat with no administrator right, and a pin produces an update.** Used at B1, B3, B10 and B11 — the machinery channel is pins in the user's own conversation. Label: **documented and observed in a test**. **Publication and pointer:** Telegram's Bot API documentation *"states that in a private chat all non-service messages can be pinned, and that no administrator right is needed there"*, `core.telegram.org/bots/api`, checked 2026-08-03; pinned and unpinned repeatedly from three machines on 2026-08-12. **And the update:** *"One thing the test noticed and the documentation does not say: a pin produces an update"*. **Not covered:** pinning in a group conversation, and how many messages can be pinned at once. **That the observed update is the documented `pinned_message` service message** is entries 43 and 48, closed on Telegram's own sentence rather than on this run.

**7. Any holder of the token can edit any message the bot sent, including one another holder sent, and concurrent edits of one message do not conflict.** Used at B1's construction of T10 and T11, B4's heartbeat edit, B10's re-used machinery message and C1's status message. **Pointer:** *"any holder of the token can edit any message the bot sent, including one a different holder sent, and two machines editing the *same* message at the same time had fifteen edits each accepted with no conflict."* **Not covered, and it is the thing the write protocol exists for:** the same file's own next sentence — *"The one thing it does not make safe is two machines writing *different* instructions at once"* — entry 8.

**8. An instruction written on the pinned slot can be lost with nothing to show it existed.** Used at §1's second demonstrated failure, at B8 (the confirmed board entry as the authoritative durable home) and at B15. **Pointer:** *"two machines wrote ten milliseconds apart, Telegram told both they had succeeded, and a third machine reading every 1.5 seconds only ever saw the later one."* **Not covered:** the window's width, and whether a read-back immediately after the write would have caught it — B4's and B8's read-back discipline is Smoozy's answer to this, not something the run tested.

**9. A tap reaches the machine that owns the job, and how long it took.** Used at R5, and at B13's *"observed end-to-end routing at these shapes took 0.7 to 1.4 seconds"*. **Pointer:** with two machines, *"a tap reached the right machine and it acted **1.4 seconds** later"*; with three machines and two jobs, *"each of two taps reached the machine holding that job, in **0.9 and 0.7 seconds**."* **Not covered:** the shape [Telegram](../Telegram.md) actually builds — R1's context-resolution instruction crossing the board — was not what was timed; the run passed routing context on the button itself. **Corrected in the document 2026-08-23:** R1 used to state its 10-second default as *"roughly seven times the slowest observed resolution round trip (R5's 1.4 seconds)"*, which reads a measurement of the old shape as a measurement of the new one. R1 and R5 now say outright that these figures are not a resolution round trip of the built shape and that **no deadline in that document is set as a multiple of them**; the three 10-second defaults rest on the ordering against B13's 2-second cadence and on the board round trip's own steps, and are Smoozy's choice. [Telegram](../Telegram.md) §21 item 22 carries what breaks.

**10. The answer never goes to the machine that asked.** Used at R6, and it is why R2 never lets the listener assume itself the owner. **Pointer:** *"A tap or a reply goes to whichever machine is listening, never to the machine that sent the message — which follows from receiving being exclusive."* **Not covered:** nothing further is owed; it follows from entry 1.

**11. What a tap and a reply carry that is enough to route.** Used at R1a (a reply resolves by the replied-to message's identity) and at R1's statement that a button carries what the sending machine wrote into it. **Pointer:** *"the id and text of the message replied to, or whatever the sending machine wrote into its own button."* **Not covered:** a reply to a message no holder has a record for — that case is R1a's own expiry rule and rests on nothing observed. The byte-level shape of both is entry 21.

**12. The editing and sending pace at the depths tried, and the 2026-08-21 correction to what it means.** Used at §10's Constraint, C3 and §21 item 4. **Pointer:** *"Forty edits of one message in 9.3 seconds and thirty messages in 4.9 seconds both went through with **no refusals**; two machines sending sixty each into one conversation at the same time gave 120 messages and **no refusals**. The rate fell from about six a second to about three under two machines."* **The correction is in that file too, and it matters more than the figures:** *"this said Telegram pushed back by slowing down rather than by refusing, and that nothing in any run produced a `429` or a `retry_after`. Neither is true."* **What survives whole is the narrow form** — *"no *send* this project made was ever refused, at the depths tried."* **Not covered, in that file's own words:** *"any run longer than a minute; and whether an **edit** counts against a **message** rate is published nowhere"* — entry 76.

**13. A message holds ten pictures and no more.** Used at M2, which is what turns the contact sheet into a selection of at most ten rather than a composed image. **Pointer:** *"**Ten, and no more** — eleven was refused outright with `too many messages to send as an album`. Two albums of ten sent back to back read as **two blocks of ten rather than one of twenty**, confirmed by the Creator on the phone, so ten is the cap on what reads as one group and not merely on one call."* **Not covered:** what an album of ten costs in time or in the per-chat rate — §21 item 4 counts it as ten sends and says so.

**14. The two send caps, as observed before the published figures were read.** Used at I3, M8 and E3. Label: **observed in a test** (2026-08-12). **Pointer:** *"A photo is capped at **10,485,760 bytes exactly**, and the refusal says so in as many words. There is a **dimension limit besides the size limit** — 6000 by 6000 was refused as invalid dimensions at only 119 KB … An ordinary file caps somewhere between 45 and 55 MB, not narrowed further."* **What this observation could not explain, and entry 44 does:** the dimension refusal at 119 KB is `sendPhoto`'s published *width and height must not exceed 10000 in total*. **And the straddle is superseded rather than confirmed:** Telegram publishes 50 MB, and I3 and M8 were corrected to it on 2026-08-21 from the observed 45-to-55 floor. **Not covered:** what the ratio cap does — no send was ever made at a ratio Telegram would refuse.

**15. Every update carries the conversation it came from.** Used at P1 (*"the conversation identifier every update carries"*) and P2's one-comparison filter. Label: **partly observed in a test** (2026-08-12), and the label's second half is the point. **Pointer:** *"every update carries the conversation it came from, so a machine can tell one conversation from another and answer only the chosen one. That is the whole of what the promise needs on Smoozy's side."* **Not covered, and it is §21 item 2's remainder:** *"whether a stranger can reach the bot at all, and what the bot sees when they do — nobody else's Telegram account was available. So the filtering is known to be possible and the thing being filtered has never been produced."* The documented half of that is closed at entries 47 and 48; **the arrival itself is entry 80.**

**16. A moving picture must be an MP4 rather than a GIF for the conversation to play it.** Used at M3, and it is half of M3's *nothing is converted in between*. **Pointer:** *"A GIF sent as an animation was accepted but filed as a plain document; an MP4 sent the same way came back properly recognised, with duration, dimensions and a thumbnail, and the Creator confirmed on the phone that **it plays by itself without tapping**."* **Not covered:** every codec and container other than the one tried; how long the moving picture may be, which is entry 66's Blender half and is bounded here only by the file cap.

**17. The bot-making chat, and what setting a bot up actually meets.** Used at §6's settled ground, S1, S2 and S6. Label: **Creator-stated** (2026-08-12), from making one, with the link and the Start requirement **observed in a test** the same day. **Pointer:** *"It asks for exactly two names, as the spec assumed"*; *"the token arrived as its own field to copy rather than buried in a longer message, so the promise to take a whole pasted reply and find the token inside it is insurance rather than the ordinary case"*; *"A link of the form `t.me/<name>` opened a chat with the bot directly"*; and *"the user must press Start before the bot can be messaged at all … a requirement rather than a courtesy."* **Not covered, in that file's own words:** *"what the bot-making chat does when a unique name is already taken, which was not provoked"* — Fact 69, entry 73.

## 3. The webhook route, the ports, and the two forms of one conflict

**26. A Vast container's mapped port cannot be a webhook address, and the reason is the provider's allocator rather than the certificate.** Used at J1, and it is Fact 63's answer. Label: **observed**. **Pointer:** [One box](../One%20box%20—%20the%20Telegram%20capture%20and%20the%20port%20that%20cannot%20be%20chosen.md) — the rental was created asking `-p 443:443`, `-p 80:80`, `-p 88:88` and `-p 8443:8443`; *"**What came back was `45104`, `45181`, `45149` and `45191`**"*; the mapped port was genuinely open to the internet, answering a self-signed HTTPS request from the Creator's Mac at `HTTP 200`, connect `0.22 s`, TLS complete at `0.48 s`; and `setWebhook` refused it in as many words: `{"ok":false,"error_code":400,"description":"Bad Request: bad webhook: Webhook can be set up only on ports 80, 88, 443 or 8443"}`. **Not covered, and the input document carries the same narrowing J1 carries:** *"Narrowed 2026-08-21: this said *a Vast container rental cannot be a webhook host, whatever it is rented as, and no setup step changes it*. That reads a fact about one address as a fact about a machine."* A Vast **virtual machine** rental was not tried; whether a relay can be put in front of such a container *"is not settled"* — entry 79.

**26a. That Telegram's page constrains the URL rather than the machine — the address gap, filled 2026-08-23.** Used at J1's narrowing of 2026-08-21, which is the whole ground for *"Whether such an address can be put in front of a container is not settled"*. Label: **documented**. **Publication:** `https://core.telegram.org/bots/api`, **read 2026-08-23**, `setWebhook`. Its `url` parameter, type String, required: *"HTTPS URL to send updates to. Use an empty string to remove webhook integration."* Its Note 3: *"Ports currently supported for webhooks: 443, 80, 88, 8443."* **Both quotes are on the method itself and neither says anything about the machine the bot's code runs on or what it is rented as** — the method's other parameters name a certificate, a fixed IP address, a connection count, an update-type list, a pending-updates flag and a secret token, and no parameter or note is about the host. **What this fills:** the entry previously carried these words as [One box](../One%20box%20—%20the%20Telegram%20capture%20and%20the%20port%20that%20cannot%20be%20chosen.md) quoted them, *"with no address and no date anywhere in `Preparation/`"*, after searching that input document, [Telegram](../Telegram.md), [Facts](../Facts.md) (Fact 63 repeats the same sentence with the same attribution and no address), [Six machines](../Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), and this file's own `setWebhook` entry, which quoted the ports sentence (entry 31) but not the URL field. **What the reading changed:** the `url` quote is longer than the four words the project carried — the page adds *"Use an empty string to remove webhook integration."* — and the ports sentence is word for word what entry 31 already held.
