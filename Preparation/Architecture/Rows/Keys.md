Earns its row by test 1 — stated outright as Architecture's, with Rule 2 named in the same sentence. Answer: `Preparation/Architecture/Keys.md` **Section 3 (L1–L5)**, with the four resting promises named one by one at L4. **The usual key location is one directory per system by this document's decision** — `~/.ssh` on Mac and Linux, `%USERPROFILE%\.ssh` on Windows, that last documentation alone. **Those three strings name a directory and never resolve one (L1a):** the home part is answered by `Desktop app and delivery`'s platform adapter asked for a **user home directory** reading, never assembled from the login account name (I4) and never from an environment value — on macOS the tool's own offered default was observed **not** to come from `$HOME` — and that reading, owed by no document when this row was answered, is supplied since 2026-08-29 at `Desktop app and delivery` §5.1 **L3a**. **`C:\ProgramData\ssh` is ruled out and nothing in it is ever managed**, because Microsoft's own page names it for host keys and server configuration and its `HostKey` defaults name private key files — the machine's own host keys rather than the user's identities, in a machine-wide directory rather than the user's — so treating it as managed would put delete's destroying branch under private key files that are not the user's at all; a key there enters only by pointing, as a referenced key. **The one-place premise is confirmed false and the consequence is the rule inherited from `Security and licence` §6 P3, kept whole**: every entry records the path of the file that backs it, taken at the moment the key entered, and no path is ever synthesised from a name, a comment or an identity. **A key with no file never enters Keys at all** — agent-only and token-supplied keys have no private key file to point at — stated as a boundary rather than discovered at Build.

**Row 245 — what makes a key usable, and what in the key location is a key at all.** *Using a key that already exists.*
> "A key is **usable** when it is a supported type that Smoozy can read and verify. A key is **unusable** when its file is missing, unreadable, not a supported type, or no longer the same key Smoozy knew."

and
> "Pointing only adds a key Smoozy can use now, while the usual-location list shows everything found there, usable or not, so broken managed keys are visible rather than silently absent. If the user points at something that isn't a usable key, Smoozy says so plainly and does not add it."

So whatever verifying reads has to be readable without the passphrase, or the promise fails on every protected key the moment it is added. That is Fact 35.
- [Servers](../../Specs/Servers.md) puts a second demand on the same reading: "If the key file is missing, or the key needs a passphrase Smoozy is not holding, Smoozy does not make the attempt at all." So Smoozy must be able to tell **that a key is protected** without holding the passphrase, which is the same fact from the other side.
- The list shows **everything found there, usable or not**. The key location holds files that were never key pairs. Nothing says whether those are listed as unusable keys, which would show the user broken entries for files that are not keys, or filtered out, which needs a rule for telling a key file from anything else in that location. That is Fact 34, and the decision on top of it is this row's.

That half is Row 503's.

**Row 246 — the fingerprint, and where it is read from.** *Telling keys apart.*
> "Smoozy also shows each key's **fingerprint** — a short code effectively unique to every key — so keys that share a name can still be told apart, by both the user and Smoozy. *(documented — see [Sources](../../Specs/Sources/Keys.sources.md))*"

and
> "While Keys knows a key, it keeps that key's fingerprint and uses it to tell the key apart and detect a swapped file."

Waits on: Facts 35, 36 and **76**. Facts 35 and 36, both answered by reading OpenSSH's own manuals and neither wanting a machine. What the fingerprint **is** is settled and needs no research — [Keys.sources](../../Specs/Sources/Keys.sources.md) cites `ssh-keygen(1)` under the `-l` option, retrieved 2026-07-17, labelled **documented**. What is not settled is **where Smoozy reads it from in the two cases this document creates**:. **Fact 76 added by the runner on 2026-08-13**, on the both-ways check's ruling: the sources file settles only what a fingerprint *is*, and hedges even that as "effectively unique". Which form is taken, whether it is stable across operating systems and key types, and whether two keys can ever share one are not covered anywhere. That bites inside this module rather than only in the module map — a collision folds two keys into one entry under the second-reference refusal, and keeps a passphrase against a key it does not belong to. The fingerprint read from the private file alone and the one read with the public half present must also be the same value, or nothing matches.

- A key whose **public file is not present**. This document says copy stays unavailable then, because Smoozy "does not go looking for a public half that isn't there" — but the fingerprint is still required, since it is what tells the key apart and what a saved server matches against. So the fingerprint must be obtainable from the private file alone.
- A key **under a passphrase Smoozy is not holding**, for the reasons in Row 245.

**What rests on it, which is more than this module.** The fingerprint is the identity the whole app uses. [Servers](../../Specs/Servers.md) states that "Each saved server remembers the **fingerprint** of the key it uses, and matches against that", and [Whole app](../../Specs/Whole%20app.md) states that two keys Smoozy knows can never share one. Three separate behaviours in this document turn on reading it at the right moment: a second reference to a key already known is refused; a **new location** must match the fingerprint while a **replacement** must not; and a file swapped at a known place is caught by the fingerprint changing, which is what drops the remembered passphrase. Earns its row by test 3, a fact to get. Not the definition of a fingerprint, which is documented, but where it can be read from when half of a key pair is absent or locked. Answer: `Preparation/Architecture/Keys.md` **5.1 to 5.3 (F1–F6)**, with the residual carried at Section 13 item 1. **Both hard cases are answered by citation rather than by new work**: the private file alone yields the fingerprint with the `.pub` deleted and under a passphrase Smoozy is not holding (Fact 35 half A), and where the private read fails promptless with a `.pub` beside it the value is read from the public half, identical by Fact 76. It is read at entry and again at every check, and **the comparison is the swap detection** that fires the passphrase erasure — but only the comparison: U4's clause 4 is split, so a read that yields no fingerprint at all is *unreadable* by 4a and costs the passphrase nothing, and a value taken from the public-half fallback is never 4b's evidence (U7a), a `.pub` that changed beside a private half that did not being no swap of the key. **The second reference is refused on the fingerprint over every current row, one entry kept** — and where both wire-format blobs are readable the refusal compares the blobs beside the fingerprints, so **two different blobs under one fingerprint** are refused **as two keys Smoozy cannot tell apart** rather than folded into one entry. That is the only detection `Security and licence` §6 P10's handed consequence permits and the document says outright it is partial: where a blob cannot be read without a passphrase the comparison cannot run. **What was carried as not established turned out to be the wrong question, and the rule under it is now written (F8, 2026-08-21): the hash is pinned to SHA-256 explicitly wherever a fingerprint is taken or compared, and an MD5 fingerprint is never treated as an identity** — in MD5 two keys sharing one is a documented, cheap construction, in SHA-256 nobody has produced one, and what is genuinely left is a citation rather than a doubt, since no first-party sentence says a SHA-256 collision does not exist; whether Row 293's world-side clause may close on that basis is the Creator's; **stability across the three systems is answered** rather than observed on one machine, the figure being taken over bytes RFC 4253 §6.6 fixes for the protocol and reproduced by hand recomputation in both hash forms (Fact 76) — so this row is answered with a named unresolved residual rather than an assertion.

*Corrected 2026-10-16, owed piece 9 of Build step 10c, carrying the `Keys` code round 1's upstream item; the answer above is kept as it was written.* **Two of its sentences say more than the mechanisms deliver.** *The private file alone yields the fingerprint … under a passphrase Smoozy is not holding (Fact 35 half A)* is the inference `Keys` U7b struck: that observation was made with the `.pub` moved aside, the call used answers from the `.pub` whenever one is present, and the private half's own read (`-y -f`) refuses every protected key. **So a protected key's fingerprint comes from the `.pub` beside it, and a protected key with none has no fingerprint** (`Keys` §13 item 6). And **the swap detection that fires the passphrase erasure reaches no protected key** (`Keys` U7ab): a fallback value is never 4b's evidence, and only protected keys have a passphrase to erase — the next connect's failed load forgets it instead, and `Security and licence` §5.2 E6 now says so. **No mechanism and no status moves**: the row stays answered, with that cost stated in `Keys`.

**Row 247 — which files sit beside a private key, for copy and for delete.** *Using a key that already exists, and Deleting a key.*
> "For any key Smoozy knows — whether found in the usual place or pointed at — copying the public half stays available when the public half is present alongside the private one. When only the private file is present, Smoozy does not go looking for a public half that isn't there, and copy stays unavailable until a public file is present."

and
> "For a key sitting in the operating system's usual place (including any Smoozy generated there), deleting removes the actual key files — the private half, the public half, and a certificate file sitting beside it when one is present, whoever made the key (an extra file that a trusted authority signs to vouch for a key) *(documented — see [Sources](../../Specs/Sources/Keys.sources.md))* — after Smoozy asks the user to confirm."

Waits on: Fact 36 — answered by reading OpenSSH's own manuals, FILES and CERTIFICATES; no machine. **Partly answered already by the document's own sources file, and only partly.** [Keys.sources](../../Specs/Sources/Keys.sources.md) quotes `ssh-keygen(1)`'s FILES section on the `id_*.pub` file, retrieved 2026-07-20, and cites its CERTIFICATES section for what a certificate is, retrieved 2026-07-17. What neither entry carries is the thing this row needs: **the rule by which the public file and the certificate file are named relative to the private file**, which is what *sitting beside it* has to be turned into. The certificate half is the sharper of the two, because that entry establishes only what a certificate is, not how one is found. **Why the floor is cleared, and it is by the delete half rather than the copy half.** Delete removes real files from the user's own computer after one confirmation, and the confirmation names what will go. A naming rule that is too wide deletes a file that was not part of this key; one that is too narrow leaves a private half behind after the user was told the key was deleted, which is Smoozy saying something worked when it did not. The copy half fails softly by comparison: the control is simply unavailable. Earns its row by test 3, a fact to get, in front of the only irreversible act this module performs.
