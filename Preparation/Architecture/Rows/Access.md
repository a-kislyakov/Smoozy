**~~Row 223~~ — one trial per computer, and the bar an answer has to clear.** *The trial.*

**STRUCK 2026-10-04; marked 2026-10-26.** The Creator withdrew the paid layer. This promise is no longer owed; the former quotation, answer and limits below remain as the record. The number is permanent and is never reused.
> "**One trial per computer.** Smoozy has no notion of a person — there is no account, no registration and no email inside the app — so a computer is the only thing it can count. Each computer gets its own trial. Reinstalling Smoozy, or moving it, does not earn a fresh trial, and neither does putting the computer's clock back."

and
> "Nothing here promises it cannot be broken at all: somebody with full control of their own computer is past what any app can guarantee. That limit is not a reason to defend against the obvious and stop. **The bar is everything the architect can think of, not the two tricks this spec happened to name** — those are examples, and an answer that defeats only those has not met it. Whoever designs this is expected to spend real effort trying to break their own answer, and "nobody would go to that much trouble" is not an argument. How it is held is Architecture's. Label: **an assumption** *(see Sources)*."

Waits on: Fact 9 — what the licence service must be able to do — and Fact 11 — whether each supported operating system offers something that identifies a computer again from away, and how far it survives a person with full control of it. **The bar is part of the promise and is carried here in full.** A rewound clock and a reinstall are named as **examples**, and the spec states outright that an answer defeating only those two has not met the bar. So an answer to this row that lists the two tricks and stops does not close it. The same wording is in the sources file, which says a scheme that "stops those two and nothing else has not met it", and adds that the answer "meets the whole-app security concern" — the one question [Whole app](../../Specs/Whole%20app.md) settles as Architecture's over six things at once, of which the licence key is one. **The identity is Fact 11 and the name is Fact 12, and the answer here must never be inferred from Row 231's.** `Preparation/Architecture/Facts.md` keeps the two apart deliberately — Fact 11 is an identity a person must not be able to forge, Fact 12 is a name shown to a person — and attaches the warning that the Fact 11 answer must not be read off the Fact 12 one: a name that is unique and survives a reinstall is still not an identity, because Fact 11 also asks whether a person with full control can forge it and Fact 12 does not. **One thing the answer has to reconcile, named rather than ruled on.** [Whole app](../../Specs/Whole%20app.md) states that the record away from the user's computer holds each computer "by the name its own operating system gives it, which is what lets Smoozy name the two when a third is refused". That is the same name Row 231 says the user is shown, and it is a name a user can change. Whether the thing the trial is held by and the thing the user is shown are one thing or two is not settled anywhere, and this row and Row 231 cannot both be answered without settling it. **The *an assumption* label was checked on 2026-08-12 and stands.** The sources file carries it as raised while writing this spec on 2026-07-29, with no method chosen and nothing confirmed, and `Preparation/Groundwork/Open Threads.md` carries the same item, due at Architecture. Nothing anywhere has answered it. What breaks if it fails, from the sources file: "If a computer cannot be recognised again away from itself, the one-trial-per-computer promise must be rewritten rather than reworded." Answer: `Preparation/Architecture/Access.md`, Section 4 with Section 12. **The identifier is chosen per system** — macOS `IOPlatformUUID`, Windows `GetSystemIdForPublisher` with its `Source` recorded, Linux the machine ID through `sd_id128_get_machine_app_specific()` — each with a fallback chain and a last-resort generated identity that is held against nobody and exists so no computer meets a refusal no spec grants. **The raw identifier never leaves the computer on any of the three**: systemd's own derivation instruction is generalised to all three as Smoozy's own decision, so what crosses is a keyed one-way derivation. **The bar is answered by Section 12's fifteen-row table**, read together with `Security and licence` §12.4 L12 and `Licence service` §13, and it names the adversary behind nearly every *not held* rather than hiding it. §12.4's *second operating-system user* row becomes **held** under all three choices, as far as documentation reaches — observed nowhere. **Nothing here is inferred from Row 231's answer**: the identity and the shown name are two fields, which `Licence service` §4 I1 already settled.

**~~Row 227~~ — what a check can report, and what Smoozy does with each answer.** *The licence.*

**STRUCK 2026-10-04; marked 2026-10-26.** The Creator withdrew the paid layer. This promise is no longer owed; the former quotation, answer and limits below remain as the record. The number is permanent and is never reused.
> "A key reported invalid locks at once. A key refused because the licence is already on two computers gets the same naming-and-release offer as at entry, offered from the lock itself rather than leaving the user to guess they must paste the key again. Until a check happens Smoozy cannot tell a good key from a mistyped one, so the first check is the earliest a user learns their key was wrong. Smoozy does not guess at why, beyond saying what it was told."

Waits on: Fact 9. Constraints: three outcomes have to be told apart and two of them must never be confused — *this key is invalid* locks at once, *this licence is already on two computers* opens the release offer, and *the check could not be reached* does neither and starts the three-and-seven-day count instead. A service that answers a refusal without a reason collapses the first two into one, and a service whose unreachable case looks like a refusal locks a paying user immediately, which is the exact harm the count exists to prevent. The last clause binds the answer as much as the first: Smoozy says what it was told and adds nothing, so whatever the service returns is what reaches the user through [Whole app](../../Specs/Whole%20app.md)'s failure rules. A decision is owed on each of the three answers. Answer: `Preparation/Architecture/Licence service.md`. *A key reported invalid* — Section 5, with the four outcomes closed by construction rather than by a vendor's error strings. *The two-computer refusal with the release offer* — Section 5's third outcome, which carries a refusal reason and the slot list so the offer is made from the refusal itself, with Section 7's field-by-field slot rows behind it. *A check that could not happen* — Section 10. *Saying only what it was told* — Section 5, where the reason is a code and never prose and the service ships no sentence that reaches a screen, with Section 9's closed reason set and Section 10's one failure rule behind it.

Waits on: Fact 13. The reserve is what makes this row want the clock answer rather than only the service one. It is the one place in the document where two entitlements are held at once. Answer: `Preparation/Architecture/Access.md`, Section 5, R1 to R5. **The reserve is a stored duration rather than a deadline, so it stops consuming wall time** — and Row 222's exception is stated exactly rather than fudged: the seven days run while the trial is **running**, and a reserved trial is not running. It is written durably before the user is in, so it survives the app closing and reopening for days on a computer that never connected. At the refusal the branches are R2's — the trial resumed at *now\* + reserve* where days remain, and A4's *locked (reported not valid)* taken whole where none do — with R5 saying how a resumed trial's ending stands against the service's stored one. **R3 takes the same fallback on a second trigger the spec does not name**: the pending window reaching seven days with no check completed at all, where the reserve is discharged, the trial resumes at *now\* + reserve*, the reserve fields are cleared, the key stays pending on its cadence, and the first-entry moment does not move — so a later refusal meets R2's no-days-remaining branch and locks; **an *already on two computers* answer keeps the reserve held and the key pending**, which is what stops Row 232's promise being refused from this side. **It is bounded**: one pending window plus the genuine trial remainder, once, and not renewable.
