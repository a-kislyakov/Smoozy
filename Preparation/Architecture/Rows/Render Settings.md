**Row 140 — Pre-load Settings reads the file, on the machine, over the connection.** *Pre-load Settings*, and *Where Render Settings fits › Connections.*
> "**Pre-load Settings reads the `.blend` and fills the settings in with its real values.** It is a separate action the user takes, not something that happens on picking a file."

and
> "**One read covers the whole file.** A `.blend` holds every scene it has, so pre-loading once gives Smoozy all of them — their ranges, their view layers, their sample counts — not only the scene the user is currently looking at."

and
> "It needs a connected server from **Servers**, because both the file and the Blender that reads it are on the machine, and it depends on **Server Setup** having put a Blender there."

Waits on: Fact 5. This is the row the rest of the document stands on: nothing else on the page can show a file value until it is answered. What the one read has to bring back, gathered from the spec and settled in `Preparation/Blender Research/Across topics/What a file can be asked before it renders.md` — all of it reads out, and **none of it in one call**: every scene in the file, each with its frame range, its step, its view layers, its sample counts, its engine and its processor-or-cards choice (*Reading a file 3*, *Frames 8*, *Settings 4*, *Settings 9*, *Settings 12*); the scene's full size in pixels, which the percentage figure on the page is taken from; **every place the job will write, which is assembly work rather than a reading** — "The places read out one at a time — the scene's output path, a compositor output node's folder and its outputs' names, and the finished path a named frame would land at. What no version has is a complete list of the kinds of place a file can be set up to write to; three of the four say outright that no source publishes one" (*Reading a file 4*), and **no single means reaches them all in any version**, with the sweeps that walk a file's recorded locations reaching neither the render output path nor a compositor output node's folder (*Reading a file 5*, *Dependencies 17*); and **whether one scene pulls in another, by both routes** — the compositor and the video sequencer (*Settings 8*) — since the warning at *A scene that pulls in another scene* is drawn from it. What the output count is made of is [What a job writes](../../Specs/What%20a%20job%20writes.md)'s; that it comes out of this read is this row's. Constraints, all settled: **reading a `.blend` means opening it in Blender** — "no version's sources describe the file's layout, and every version's manual names one outside tool without saying a word about what it can read" — and peeking without opening hands back only local data, the version from 5.0 and the linked-file list from 5.2 (*Reading a file 1*). Nothing outside Blender was ever pointed at a `.blend` in any version, so that route is **untried rather than ruled out**. A read taken beside a render already running on the same machine **left both correct** — the read quit at 0 and the render finished at 0 with all 60 frames and no error or warning, in all four versions on two machines — though **neither run says anything about how long any of it took**, and whether a second or third Blender slows the render down neither machine can say; and how many Blenders one machine will carry at once is settled nowhere and no test can reach it (*Reading a file 2*). Answer: `Preparation/Architecture/Render Settings.md` **1.1 Q1–Q3**, **1.2 Q4–Q6** and **Q17**. The settings half rides `Job files and outputs` §4's one recorded reading rather than a second read — R1's own *all three payloads out of one read* is what houses it, observed 2026-08-17 in 4.5.9, 5.0.1 and 5.2.0. Q1–Q3 itemise what the page takes out of it, the per-frame view-layer set and the scene-pulls-in-scene reading included; Q4–Q6 settle what starts a read and where it runs.

**Row 141 — a read either succeeds whole or gives nothing.** *Pre-load Settings.*
> "**A read either succeeds whole or gives nothing.** The chosen Blender may fail to open the file — some files will not open in some versions (see [Which Blender](#which-blender)) — and then nothing about the file's insides is shown: no scenes, no view layer boxes, no sample count, no statement of what the file will write. Nothing is left half-filled."

Waits on: Fact 5. And a decision of its own that nothing in the document takes: what the read does when it comes back **partly** — the file opened and one of the several readings Row 140 lists failed, or the connection dropped halfway through it. The promise is that nothing is half-filled, and the read is by construction many readings rather than one, since no single means reaches every place a file writes. It also has to tell three endings apart and say which: the file could not be opened by this version, the machine could not be reached, and the read ran and something in it failed. The page says which version failed, so the first has to be distinguishable from the other two. Answer: `Preparation/Architecture/Render Settings.md` **1.3 Q7–Q10.** A reading is the complete sentinel-framed document with an empty error map, and anything else is no reading — nothing of it is stored or shown, so *nothing is left half-filled* is kept by construction. The three endings are told apart, and a fourth outcome is held out of them: the machine could not be reached, which is `Server protocol and transfers`' ending consumed rather than invented; the file could not be opened by this version, distinguished by the absence of the start sentinel **and by Smoozy not having ended the invocation itself**, with the version named from Smoozy's own record of the binary invoked and never mined from output; and the read ran and something in it failed. **A read Smoozy ended itself — a stop-and-clear, a supervisor shutdown, or the kind's own cancellation — carries every outward sign of the second ending and is diagnosed as none of the three: the page says the read was stopped, claims nothing about the file, and offers to run it again.** A partial read leaves nothing behind — the prior un-stale reading stands and the store is untouched.

Answer: `Preparation/Architecture/Render Settings.md` **1.4 Q11–Q12**, with the in-flight case at **1.2 Q17**. The reading and the chosen version travel together, per `Job files and outputs` R2 and R13; changing the version drops the file's half whole and keeps the user's; and a reading that lands after the version moved under it is discarded rather than stored.

**Row 144 — the user's answers survive, the file's do not.** *What the user typed is not lost while they look elsewhere.*
> "**What the connection does take is what was read from the file.** Those values were true of the file when it was last read, and Smoozy cannot vouch for them across a gap it was not watching — the file may have been replaced or changed in the meantime. So a reconnect keeps the user's own values and drops the file's, leaving the settings meaning exactly what they meant before anything was read: whatever the file says, plus whatever the user typed. Reading the file again fills the rest back in."

and
> "That split is the whole rule: **the user's answers survive, the file's do not.**"

Waits on: nothing to get, and a decision nobody has taken. Constraints, all stated in the same section and all load-bearing: what the user typed is held **per scene, per file and per server** at once — "**Switching files keeps them too**, and so does switching servers" — so the same file on two machines carries two sets; the split is exercised by three separate events, a dropped connection, the file changing on the machine, and the version changing, all doing the same thing; and "**Closing Smoozy takes everything.**", so none of it is kept on disk and the whole arrangement lives for one sitting only. The two halves have to be held apart at every setting, since a value the user has not touched and a value they typed that happens to equal the file's are the same number on screen and different answers to the render. Nothing in the document says how they are told apart, and getting it wrong sends the file's stale number as though the user had chosen it. Answer: `Preparation/Architecture/Render Settings.md` **2.1 J1–J6** and **2.3 J10**. Two objects that are never written from each other: an override store holding only the user's answers — keyed per server row, per file path and per scene name, living in `State, identity and recovery` §1.1's existing volatile class rather than in a second store — and the recorded reading holding only the file's values. **A setting the user never touched has no store entry**, so a stale file value is unrepresentable in the payload; that is D2's discipline applied to the page, and it is what keeps the two halves apart where they hold the same number.

Constraints: **the name is the only identity there is** — a scene and a view layer read out by name, and nothing in the document offers anything else to hold an answer against. The spec states outright that **nothing checks the name still exists**: "nothing here says whether the file on this machine still holds a scene of that name. Nothing checks that for the user." The cost of getting it wrong is settled and silent — a scene name no scene bears is named and then ignored and the run reports success, one of the six wrong names recorded in `Preparation/Blender Research/Across topics/What can be set from outside.md` that let a run finish at success (*Settings 12*). **And the spec's word is *job* where the mechanism's word is *attempt*, which is true here by two clauses in two other documents this row does not name.** Y14, J9, that document's Section 12 and Section 14 all read *fails the attempt*, and in this family the two are not the same thing — an attempt can end at *held for an answer* with the job untouched (`Rendering` P1 step 5, `Rented-server runtime` U6), and an interrupted attempt is re-run by the machine without the job failing (A2). **Row 146 — Smoozy tidies the frame list before the render is started.** *The frame range.*
