# Rows — Telegram

Rows **255 to 277**, **Row 296** filed later by the both-ways check, and **Row 506**, filed by the second stage-close re-sweep of 2026-08-29, from [Telegram](../../Specs/Telegram.md). Part of `Preparation/Architecture/Coverage.md`; how to read a row is there, and the facts they wait on are in `Preparation/Architecture/Facts.md`.

Every number here is permanent, never reused and never renumbered.

**Where this document's measurements come from.** Almost nothing here is a Blender fact. The figures in these rows — the polling conflicts, the ten-millisecond double write, the message size and dimension limits, the editing pace — were **observed** in a run against a real Telegram bot on 2026-08-12, on three rented Linux machines holding one token at once. Each is cited in [Telegram.sources](../../Specs/Sources/Telegram.sources.md), which says for every one what was seen and what it does not cover. Telegram's own documentation never addresses more than one program holding one token, for sending or for receiving, so nothing here could have been read rather than run.

**Row 255 — the bot runs on the machine and goes on reporting with Smoozy closed.** *Where Telegram fits*, and *What a machine tells the user.*
> "**The bot runs on the rented machine, not inside Smoozy.** That is the whole point of the module. A bot inside the desktop app could only send messages while the app was open, which is exactly when the user does not need it. Because it sits on the machine, the render still reports and still takes instructions with Smoozy closed and the user's computer switched off."

and
> "What it says is what a queue entry says, which **Queue & History** owns, together with the machine's own current readings of what it is using and how long it has been up; this module only carries it to a phone."

Waits on: Facts 1 and 62. This is the footing every other row in the document stands on, and it is the same fact Queue & History and Rendering already wait on: whatever Smoozy puts on a rented machine has to run with nobody connected and come back by itself after a reboot. The second quote adds a dependency of its own — everything the bot says is composed **on the machine** out of what another module owns, so nothing here can be answered before the shape settles what holds a queue entry there. The module's whole reason for existing is that it works when Smoozy does not, and nothing in this project has established that anything of Smoozy's can. **Answered** — [Telegram](../Telegram.md) §2 F1–F5, with the disk-full clause at §21 item 9. The role worker is `Rented-server runtime` §5.3's one role worker cited whole, and F2 is the load-bearing addition: it writes no durable store itself — cursor, update position, the 16-byte machine-routing key, the board and status-message identities, and R1's action-context records all live in the Telegram worker's state store and are written by the supervisor on request, so the single-writer rule holds with no carve-out. **An accepted cross-machine instruction is not among them**: its authoritative durable home before acknowledgement is the confirmed board entry of B8, outside every rental, and F2 states outright that no sender-local outstanding record is used to claim its survival. F3 defines *the work* per update kind, which is what makes the cursor discipline enforceable. F5 states Fact 1's negative cost exactly: on a full state mount the worker does not run either, so the messages stop and Row 265's readable silence is what the user gets.

**Row 256 — the setup walkthrough is the one moment Smoozy itself talks to Telegram.** *The bot.*
> "That is a minute of work and Smoozy takes every decision out of it: it offers both names ready to copy, gives another unique name on a tap if the first is taken, takes whatever the user pastes and finds the token inside it rather than making them pick it out, and checks the bot answers before moving on."

Waits on: Fact 69. Constraints already settled by the 2026-08-12 run and recorded in [Telegram.sources](../../Specs/Sources/Telegram.sources.md): the bot-making chat asks for exactly two names; **the token arrived as its own field to copy rather than buried in a longer message**, so finding it inside a pasted reply is insurance rather than the ordinary case; a link of the form `t.me/<name>` opens a chat with the bot directly; and **the user must press Start before the bot can be messaged at all**, which is a requirement rather than a courtesy. Not covered: what the bot-making chat does when a unique name is already taken, which was not provoked. The decision this row carries: every other exchange in this module runs between a machine and Telegram, while *checks the bot answers* runs between the **user's own computer** and Telegram, which is a second place that has to be able to reach it, and nothing says what the walkthrough does when it cannot. **Answered** — §6 S1–S6, with Fact 69's collision clause unresolved at §21 item 3. The decision the row asked for is S3: *checks the bot answers* is a `getMe` from the user's own computer, and its failure is **classified rather than guessed** — refused means the token was not accepted, unreachable is an ordinary failed action under the whole-app failure rules and is **never** read as a wrong token, answered proceeds. S4 orders it check, then proof, then store, then machines, and S5 confines desktop receiving to the walkthrough on a token no machine holds. **S1a to S1c, added 2026-08-25 for Row 470, are what *another unique name on a tap* costs and what it does not buy.** The tap re-draws a four-character block inside a fixed `smoozy_…_bot` shape and never repeats a block already offered, so every candidate satisfies Telegram's published username rule by construction — but **no availability is ever claimed or checked**, because nothing available to a bot answers whether a username may be used for a new bot, and occupancy is not availability. One refusal another candidate cannot cure is the per-account bot ceiling: *Another* cures nothing, Smoozy cannot see it, and the remedy is wholly Telegram's, in the chat the walkthrough already stands the user in. The one unpublished edge case every candidate carries — the underscore immediately before the suffix — is §21 item 25; if it goes the wrong way every offered candidate is refused identically and the user falls back to typing a name of their own, which no refusal ever prevents. **And S3's *disturbs no listener* was struck on 2026-08-23**: what was observed undisturbed was pinned-message reading, never the identity call. The walkthrough does not rest on it — no machine holds the token at a first setup and a replacement is checked before any machine is given it — and §21 item 24 carries what is not established.

**Row 257 — which single machine holds the listening slot.** *The bot.*
> "**The two facts this rests on were tested on three machines holding one token, and both hold**: every machine can send, only one can receive at a time, and a machine that is not receiving can still read a shared note without disturbing the one that is."

and
> "How several machines share one bot between them is still Architecture's, and it is genuinely awkward — the same tests showed that machines all listening at once knock each other off until almost nobody is listening, and that a shared note can lose an instruction."

Waits on: Fact 63, which is the only thing that could change the shape of the answer rather than its detail. **The register asks that Fact 63 be settled before the main rental batch is chosen rather than after**, because it wants a rental with a public address, an inbound port reachable from outside and whatever certificate Telegram requires — a different rental from the ordinary box every other fact here rides on. Nothing else to get: the behaviour is settled, and `Preparation/Groundwork/Open Threads.md` carries this as a **requirement** on Architecture rather than a refinement. Constraints the answer must honour, all from the spec's sources file and all load-bearing: receiving is exclusive and says so plainly — `409 Conflict: terminated by other getUpdates request; make sure that only one bot instance is running`; **the newest request always wins**, whichever machine it comes from, so a machine takes the listening slot simply by asking; because the newest wins, **a machine that retries beats one that asks once, so two machines that both retry destroy each other** — three machines all polling for a minute produced 61 attempts, 60 conflicts and 1 success, with nobody listening for about 92% of the time; the free half is that hand-over costs nothing, and a machine that has died releases the slot by simply not asking again; sending is not exclusive in any way, two machines having sent 120 messages into one conversation at once with no refusal; and nothing in Telegram arbitrates any of this. Not covered: more than three machines, any run longer than a minute, and webhooks, which were not exercised at all. **This is the constraint the three rows after it sit inside, so it is answered before them.** **Answered** — §3 B1–B7 for the asking route and §4 J1–J4 for the webhook one. T4 to T14 are **taken as given** (§1), so what this row adds is the conversation's own conduct: one pinned board created fresh at every hand-over behind an unpin-until-empty loop, a heartbeat edit confirmed by read-back, and staleness detected by comparing the heartbeat value for equality over a full renewal interval **measured on the reader's own clock**, which keeps D5 exactly — **with the second half that answers this row's own hazard: a read that did not complete is not a reading of anything, so it advances the interval by nothing and resets it by nothing and is never counted as *no readable board*, and a machine that has completed no read for a full renewal interval treats itself as out of contact and does not ask at all. Without both, *newest asker wins* hands the slot to the machine on the worst connection at every recovery.** J3 is the half nothing else could do: a stale registration is removed by joining B5's staleness test to the webhook-form `409` description text, since one conflict code covers two situations.

and
> "Both are recorded in [Sources](../../Specs/Sources/Telegram.sources.md) and parked in [Open Threads](../../Groundwork/Open%20Threads.md). What matters at this stage is unchanged: the user never meets any of it, and they make one bot that covers however many machines they run."

**The first quote is the same sentence Row 257 quotes, and it is repeated deliberately**: it is the one place the document hands both halves over, and a row that dropped it would be a row with no hand-off in it. Waits on: nothing to get. The failure is observed and exact: **two machines wrote different instructions to the same pinned message ten milliseconds apart; Telegram told both they had succeeded, and a third machine reading every 1.5 seconds only ever saw the later one.** The earlier instruction was gone with nothing anywhere to show it had existed. Constraints the answer must honour, all settled: any holder of the token can edit any message the bot sent, **including one a different holder sent**, and two machines editing the *same* message had fifteen edits each accepted with no conflict — that is what makes a shared noticeboard possible at all, and what it does not make safe is two machines writing *different* instructions at once; reading is cheap enough to lean on, three machines reading once a second for a minute giving 168 reads and no refusals, and a reader never threw the listener off during a full 25-second poll; a pin produces an update, so the listening machine hears about every pin the others make, and whether that is noise or a useful signal is this row's to decide; and the whole chain was run end to end and works — a tap reached the right machine 1.4 seconds later with two machines, and 0.9 and 0.7 seconds with three machines and two jobs, so what is missing is only the rule for writing when two want to write at once. Open Threads says outright that this and the listening question are the same piece of machinery and are answered together. **Answered** — §3 B1–B15, and B23 of §3.4 from 2026-08-29. *(Corrected 2026-08-29 at the re-gate. The range read B8–B15 and was wrong at both ends: this summary's own first claim — that T10 and T11 hold by construction — is **B1**, outside it; and §3 gained §3.4, B19 to B23, on 2026-08-29, of which **B23 is a write-protocol rule** binding B2, B10 and B15.)* The observed ten-millisecond loss is made harmless by construction rather than by a lock: the board is the holder's own message so T10 and T11 hold by construction; an accepted instruction's authoritative durable home **is** the board entry, appended by a complete bounded board edit and accepted only after exact read-back, with F3 refusing to confirm the causal update until then — so a sender destroyed after acceptance erases nothing, B3 carries the unacknowledged list into the successor board, and no sender-local copy is relied on for survival; each machine speaks to the holder through **one re-used machinery message of its own**, pinned with the notification suppressed, so an acknowledgement creates no new message of Smoozy's — what the pin does add is a service message in the user's own conversation, `Preparation/Architecture/Telegram.md` §21 item 17 — **and §3.4, written 2026-08-29 on Fact 102, says what that message turned out to be.** B21 has the line quote the pinned message's own text and follow its later edits, so the board's line rewrites itself at every heartbeat; a phone keeps a permanent banner showing one truncated line of whatever is pinned, which under B1 is the board. B19 has every line stand for the conversation's life, since an unpin takes none away. B20 prices it at one line per utterance with no ceiling on what one action can cost. **So this row's second quoted promise — that the user never meets any of it — is kept only as §21 item 28's ruling of 2026-08-29 narrowed it**: the acceptance stands, the spec's paragraph is corrected, and **B23 is the one rule the write protocol gained**, binding the board's serialization at B2 and every machinery message at B10 and B15 to open with a short, plainly readable head. *(This sentence stopped at "Telegram's own service line" until 2026-08-29, which is what §3.4 narrowed; corrected at the re-gate.)* *(This clause read "so acknowledgements leave no trail in the conversation" until 2026-08-29, and item 17's ruling of 2026-08-25 falsified it: a pin creates a real message in the conversation's history with its own identifier and moment, and silencing it silences only the notification. B10 is careful where this summary was not — it claims only that no new message is created, and says in the same clause that the pin puts a service message in the user's conversation. The answer does not move; the summary had collapsed a careful claim into a false one, and Row 506 is where the service line is now carried.)*; and the holder is the stack's janitor, popping to its own board by unpin-newest only, never reading beneath a top pin.

**Row 259 — an action taken on the phone reaches the machine that owns the job.** *What the user can do from the phone.*
> "Six things, and no more. Four of them are a tap on the message in front of the user, so nothing has to be typed and no machine has to be named."

*(**Re-quoted 2026-08-31, and the answer does not move.** The spec said *five* and *three* over a list of six, the sixth being the tap that asks the machine to send its own words, promised by the Creator's ruling of 2026-08-22 in *What a machine tells the user* and never counted. Waits on: nothing to get; it is the third part of the machinery in Rows 257 and 258 and is answered with them. Constraints already settled: **the answer never goes to the machine that asked** — it goes to whichever is listening, which follows from receiving being exclusive — and the listener can always tell who it was for, either from the id and text of the message replied to or from what the sending machine wrote into its own button. Both routes were run: a reply and a tap on one machine's message arrived at another and were correctly identified. Timings as in Row 258. The decision nobody has taken: *no machine has to be named* is a promise about the user, and it is kept by a routing rule nobody has written, since three of the five actions are a tap whose target is decided entirely by machinery the user never meets. One caution the spec plants elsewhere: *how buttons are offered* is settled during Design, and it is the same thing this row leans on, since a tap carries whatever the sending machine wrote into its own button. **Answered** — §5 R1–R6, and the carrier is the opposite of what this row assumed. **A button carries one 44-byte opaque token and no routing context at all** — a format byte, the issuing machine's routing key and an action-context identity — because Telegram publishes `callback_data` at 1–64 bytes. The identities this row is about live in the **issuing machine's authoritative action-context record**, bound to the proved conversation, the source message, the owning machine, the job and hold, the action, the payload and the subject generation the action is valid in; resolution fails closed on any mismatch and nothing is submitted. **The reply route is R1a's and not the button's**: Telegram's contract has no button without visible label text, so no keyboard is ever attached for resolution's sake and a reply resolves by the replied-to message's identity against those same records. R7's rule is what defuses the row's danger: **nothing is ever routed by a label**. R2 is the routing rule: the listener resolves first, submits to its own supervisor where the resolved owning machine is itself, boards an instruction to that machine otherwise, and never assumes itself the owner. R4 makes each press one instruction, seeded from the tap's own id, so a second press lands on the machine's existing idempotency.

B16 to B18 do not move, and §21 item 28 records the acceptance as ruled.

**Row 261 — every message names the machine and the job.** *The bot.*
> "**Every message says which machine and which job it is about.** With one machine that is a formality; with three it is what makes one conversation readable. A machine is named by the label the user gave its server, which **Servers** owns."

Waits on: nothing to get. A decision and a dependency: the label lives in Smoozy on the user's computer and can be changed there, while the machine writing the message holds only whatever it was last told — and by this document's own rule nothing reaches a machine except on the next connection, so a renamed server keeps naming itself the old way in the conversation until then. The job's identity has the same shape and is load-bearing twice over: it is what the message says, and it is what Row 259 matches a tap against. **This row sits at the floor**, and it is kept for the same reason Row 1's scene-name row is: what fails is silent, the user is reading a conversation about three machines billed by the hour, and an action routed by a stale identity is an action taken on the wrong job. **Answered** — §5 R7–R9. Naming is display and identity is routing: a message names the machine by the server label and the job by the note's label, while a button carries only R1's opaque token and the identities sit in the issuing machine's action-context record behind it, so a stale label misleads a reader and can never land an action on the wrong job. R8 states the staleness rather than hiding it — the machine holds the label it was last told, refreshed through the told-record on the next connection.

**Row 263 — how the token is kept.** *The bot.*
