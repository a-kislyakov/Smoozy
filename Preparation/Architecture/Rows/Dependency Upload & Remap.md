**Row 161 — what makes two references one row, and what keeps the check finite.** *Checking a file.*
> "**Two things follow for this module.** A remap that gives two ordinary library entries the same location merges them the next time the file is read, which is what Smoozy wants where two references really were one file and is a silent loss of one of them where they were not — so the check's one-row-per-thing rule has to be about the file the location reaches rather than about the text."

and
> "**The same thing reached twice is one row.**"

and
> "This is also what keeps the check finite: a file already reached is not walked again, so a chain that comes back round to something already read stops there rather than going round for ever."

Waits on: Facts 5 and 16. Constraints already settled and load-bearing, from the joined answer at `Preparation/Blender Research/Across topics/What has to travel with a file.md` and from *Dependencies 19*, which the document's sources file names: two recordings of the same file differing only in how the path is written are **one** library, because Blender tidies the writing before it decides; two recordings reaching the same file by two different names on disk — a shortcut of either kind, or the same folder mounted twice — are **a separate library each**, because the tidying stops at the text and never asks the disk what the file is; two different files sharing a file name are two libraries and the second gets a numbered ending; the decision is made when the file is read, so two entries forced to hold identical text stand until the file is saved and opened again; and from 5.0 packing linked data is the deliberate exception, leaving two entries with the very same recorded location that survive a save and a reopen. **Capitals decide it differently at the two ends and the two machines disagree** — on the rented Linux machine a wrongly capitalised library location is not a file and the link fails outright, on the Creator's Mac it succeeds quietly and leaves two libraries where one was meant — and the comparison says plainly that this settles those two machines and not the kind. Not covered, and named so the answer does not assume otherwise: what happens when a library is relocated onto a file another library already records, which is the one thing that round set out to settle and could not; and nothing at all with a window open, or on Windows. Answer: `Preparation/Architecture/Dependency Upload & Remap.md` 3.3, G10 to G13. **A row stands for the thing pointed at; the record beneath stays per reference** (1.2 K3), which is what keeps `METallic.png` and `metallic.png` two answers even where they turn out to be one file. G11 carries the load-bearing half: two references resolve to one row, and one remap target, **exactly where they resolved to the same file on the user's computer — the same stored whole location — and never on a name match alone**, because a remap giving two library entries one location merges them at the next read. G12 leans on neither end's folding: the mirror and the remap write exact stored bytes. G13 keeps the check finite with a visited set keyed by resolved location, no depth cap, and the uncovered relocation case leaned on nowhere.

**Row 162 — the check carries itself down the tree as files arrive, and a dropped connection leaves the sitting standing.** *Checking a file* and *Sending them up, and where they land.*
> "**Smoozy carries the check down itself as those files arrive:** when an upload puts a missing linked file on the machine, that file is read and whatever it points at appears alongside the rest."

and
> "So every location the check finds below the top file is read against the file that holds it."

and
> "**A connection lost during the *check* leaves the sitting standing.**"

Waits on: Fact 5. Constraints already settled, from the joined answer: "The readable chain stops at the first absent file: with a middle file gone, the file beyond it is named nowhere at all" (*Reading a file 8*), so "gathering is a loop rather than a pass"; a chain is recorded to at least nineteen libraries deep (*Dependencies 13*); a relative location inside a linked file "is measured from that file's own folder and never from the file that opened it", and "a tool that forgets to name it gathers the wrong location" (*Dependencies 13; Reading a file 9*); Blender 5.2 alone can be asked for one level of an unopened file's own links, "which shortens the loop by a step and does not remove it". Named limit: everything about the linked node-setup case rests on one library layout and one chain of three files. Separate from Row 161, which decides what counts as one thing; this decides how the walk is run and what survives it being cut — an unbounded number of read-upload-read passes driven over a connection that may drop between any two of them, with every user decision from the sitting kept and the partial result shown as partial. Answer: `Preparation/Architecture/Dependency Upload & Remap.md` 3.4, G14 to G18. The check is **a desktop-driven loop of single-file readings** rather than one long machine-side operation, so there is no unbounded machine-side loop to stop: G15 makes each reading its own operation with its own identity, and stopping is the desktop ceasing to issue them. G14 reads every location below the top file against the file that holds it, records that the readable chain stops at the first absent file, and treats 5.2's one-level shortcut as an optimisation nothing rests on. **G16 is what leaves the sitting standing**: every finding and every user decision is written to the record at the moment it lands, so a lost connection loses nothing already decided and nothing is re-decided on the next run. G17 refuses to carry on by itself.

**Row 165 — searching the user's own folders, deep, stoppable, and failing one at a time.** *Finding the files.*

> "**A search can be stopped, and a folder that cannot be read does not stop the rest.**"

and
> "The user sets the **order**, and the first folder holding a match wins — which is how a user says "my current work beats my archive" in a way they can predict. It settles which folder is taken from, never which file inside one."

Waits on: Fact 16 for how a match is made at all. Nothing else to get from outside; what is owed is a decision. The promise binds four things together that pull against each other: the search walks an arbitrarily deep tree on the user's own computer, it is stopped at any point and what it already turned up is kept, a folder that cannot be read is reported by name while the others carry on, and the **order** of the folders decides which folder a match is taken from — so the search cannot simply return the first thing it meets in whatever order the disk offers. Ordinary construction would be a walk; this is a walk that must be ordered, interruptible, partially failing, and honest about ambiguity. Answer: `Preparation/Architecture/Dependency Upload & Remap.md` 4.2, F3 to F8, with the folder list at 4.1. **F3 forces the full walk** — each subtree to completion, in the user's order — because neither *the first folder wins* nor *every place it matched* can be said without it. F6 keeps what a stopped search turned up and marks the search unfinished so a *not found* is not read as the disk's answer. **Row 166 — the search matches exactly, capitals included, on a disk that does not.** *Finding the files.*
> "Asked for `METallic.png` on a disk that does not mind capitals, the computer hands back `metallic.png` as a match, and there is nothing in the answer to say it is a different file — the disk itself calls the two names the same."

and
> "**But a name that matches except for capitals is still shown, as a proposal.**"

Waits on: Fact 16. **This is not a Blender question and does not go to research**: the research states outright that whether capitals matter "is decided by the disk, not by Blender" — that is *Dependencies 8*, which is where the document's own sources file carries it. (*Reading a file 10* is the neighbouring and different claim, that Blender's own **search** minds capitals; it reads that as Blender's own rule, records the same Mac behaving both ways, and chooses neither reading.) What is owed is a fact about the operating systems Smoozy runs on — how an exact-case answer is got out of a disk that reports a case-insensitive hit and says nothing about the difference — and Rule 2 forbids answering it from an agent's recollection of how a filesystem behaves. Constraints already settled, and every one of them argues the same way: a wrongly-cased reference loads on the Creator's Mac and fails on the rented Linux machine, in all four versions; Blender's own repair matches the name exactly, capitals included, on both machines, so nothing rescues the spelling; and the joined answer calls this "the one fault that is invisible on the machine the file was made on and certain on the machine the render runs on". Whether that strictness is Blender's rule or the disk's is labelled **unresolved** in the spec and in the sources file, checked and standing — and nothing here turns on it, which the spec says itself.

**What the answer must deliver, twice over.** The exact match decides what counts as *found*; the same search must also surface the case-only near-miss as a proposal, so one pass has to produce two different kinds of answer. **What breaks if it is got wrong**, in the spec's own words: "Smoozy would send the wrong file, point the reference at where that file landed, and the render would find it and use it. A wrong picture, at full price, with nothing missing and nothing to see." Answer: `Preparation/Architecture/Dependency Upload & Remap.md` 4.3, F9 to F15, **F14a included**. **F9 makes a match an equality of bytes against the enumerated stored name, capitals included, with no folding, normalising or canonicalising anywhere in the match path** — the trap the input document names is absent by construction. **F10 produces the near-miss by a separate comparison that never touches what counts as found**, folding by Unicode full folding because that is what the one measured disk does, so a deviant fold costs a proposal and never a wrong file. F12 records every resolution as the whole location as stored on disk, read from the system rather than rejoined from strings, which is also what the mirror carries. F13 asks the platform file adapter to own that reading rather than building a second route to the filesystem — a seam, recorded. **F14 closed the Windows half as unresolved with what breaks named, and F14a supersedes it in part (2026-08-21, per Row 406)**: Microsoft's own protocol specification documents `FileNormalizedNameInformation`, whose normalized name *"uses the exact letter casing stored on disk"* — the sentence F14 records as unwritten — **on NTFS and ReFS alone**, every other volume refusing the class loudly; and the Linux kernel's own documentation settles the folding-ext4 case in F8's favour. The arrangement takes exactness from the normalized name and never from what casing an enumeration returns, so F14's one missing word stops being load-bearing. **What stays unresolved is a Windows volume that is neither NTFS nor ReFS, NTFS's own folding rule, and every folding filesystem that is not ext4** (Section 12 items 3, 11 and 21) — and **neither citation has ever been run on a machine**, with no Windows computer and no Linux desktop scheduled. F15 leaves the Blender-or-disk question where the spec left it.

**Row 167 — the shift.** *Finding the files.*
