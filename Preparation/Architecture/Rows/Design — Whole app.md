**Row 318 — the file's value against the user's, everywhere the settings are worked in.** *The file's value against the user's.*
> "**Every setting read from a `.blend` is shown in italic grey. Every value the user typed is upright and bold, and carries a small cross that hands it back.** One glance says which settings the user has taken over and which the file still owns."

Kind of promise: **a drafted design sentence.**

Earns its row by the third test: the page cannot be drawn at all unless the two values are separately held. A setting the user never touched has to be distinguishable from one they typed to the same number, and the cross has to have something to hand the setting *back* to. That is an arrangement underneath the screen rather than a face chosen at Build.

The same paragraph's second clause is the same promise reaching a control that has no type to set — *"That convention has to reach places italic cannot. A checkbox has no type to set, so **a View Layer's label takes the weight instead** — upright and bold where the user pinned it, italic where it is only a reading of one frame."* It is answered by the same clause and is not filed separately.

Waits on: nothing to get.

**Answer: `Preparation/Architecture/Render Settings.md` Section 2, J1 and J4.** J1 is this promise in the words of the promise: *"There are exactly two objects and the display is composed from them; neither is ever written from the other. The **override store** holds the user's answers and only the user's answers. The **recorded reading** holds the file's values and only the file's values. For each setting the page shows the store's entry where one exists (the user's, upright), else the standing reading's value (the file's, italic), else the promise-form — whatever the file says, not yet shown. Which face each takes is Design's; that they are two objects is this clause."* The cross is the store entry's removal, and J4's rule that a file value never has a store entry is what makes the two unconfusable. The View Layer clause is answered by the same two objects together with **[4.2](../Render%20Settings.md#42-the-pin-and-the-mechanism-that-holds-it)**'s pin mechanism — the pin being a store entry (J3, per layer name with J7's provenance) and the italic reading being Q3's per-frame answer. **Which frame that reading is taken at was fixed later, at [V11 and V12](../Render%20Settings.md#41-what-one-read-answers-per-frame), added 2026-08-23 per Row 435**: the untouched box is the file's per-frame renderability evaluated at **the numerical minimum of the frame set the page has in hand** — never the first entry written and never the frame in view — and it moves with the range the user edits, composed on the desktop from the reading in force with no read of the machine.


**Row 319 — the file's own value named beside the user's on a job's entry.** *The file's value against the user's.*
> "On a job's entry, where the settings are settled and read at a glance rather than worked in, the same convention holds and the file's own value is named beside the user's."

Kind of promise: **a drafted design sentence.**

Earns its row by the third test in its sharpest form: **this is a screen showing a value nobody has arranged for it to have.** A job's entry is read from Smoozy's own record, on a computer that may not be connected, about a machine that may no longer exist — and the file's own values are not in that record.

Waits on: nothing to get. The obstacle is a decision already taken, not a missing fact.

**Not answered anywhere, and the architecture as written makes it unrepresentable rather than merely unbuilt.** `Preparation/Architecture/Render Settings.md` 9.1 Y1 composes the submission payload as *"a statement of overrides: one entry per setting the user answered, no entry at all for a setting they left alone"*, and names outright what it never carries: *"any file value re-sent as an override — J4 makes that unrepresentable, because a file value never has a store entry to be composed from."* Y2 puts that payload into the manifest unchanged, and `Preparation/Architecture/Queue & History.md` N10 and N11 make the entry's kept setup that payload. The file's values live in the **recorded reading**, which `Preparation/Architecture/Job files and outputs.md` 1.2 places in the job-record area **on the machine**; its Section 13 lists the fields of that reading a queue or history entry shows and they are all output readings — the folders, the count, the collision record, the duplicate-picture warning, the shared compositor, the video shape, and a destination not mappable. **No settings value is among them.** So on the entry there is nothing to name beside the user's value, and after the machine is destroyed there is nowhere the naming could be got from.

Where the sweep looked: `Render Settings` Sections 2 and 9, `Queue & History` Sections 6 and 11, `Job files and outputs` Sections 4 and 13, `Rendering` Section 8's payload contract, and `State, identity and recovery` §1.1's inventory of the local record.

**The architecture's own reason for excluding file values from the payload is a good one** — it is what keeps a stale reading from leaking into a render — **so the answer is not to relax it.** What was owed is a decision about where the entry's other half comes from.

**Answer, 2026-08-21: `Preparation/Architecture/Render Settings.md` [Y1a](../Render%20Settings.md#91-what-the-payload-is), held by `Preparation/Architecture/Queue & History.md` [N14](../Queue%20&%20History.md#10-the-note-the-figure-and-what-the-read-fills-in).** **The payload is not relaxed by one word** — the answer is a companion composed beside it and going somewhere else entirely.

- **What is composed:** for **each setting the payload carries an override for, and no others**, the file's value for that setting **as the reading in force at submission gave it**. One value per override, never the whole reading. **A setting the user left alone needs nothing**, because on those the entry shows the file's value as the only value there is.
- **Where it goes: the local job record on the desktop, and nowhere else.** Not the payload, not the manifest, never sent to a machine. **So Y1's prohibition stands exactly as written** — no file value is re-sent as an override, because this is not an override and reaches no render.
- **Why it is composed at submission and could not be got later**, which is the row's own finding acted on. `Render Settings` J1's two objects sit together only on that page, and both go: the store is volatile for the life of the run (J2) and the file's half is dropped by any of J10's three events. **After submission there is no route to the file's value for that job at all.** The row's *unrepresentable rather than merely unbuilt* was right, and composing at the one moment both halves exist is what makes it representable.
- **Where no reading stood, the entry says nothing.** No companion is composed and the file's side draws as **absent** — never as a value from a later read, because *what the file said when this job was submitted* and *what the file says now* are different facts.
- **It is display material and is refused as anything else** — no override composed from it, no validation against it, no comparison with a later reading, and it is not J7's provenance.

**Row 318's answer is untouched and this is its other half.** The two-object rule that makes the working page's italic and upright unconfusable is what supplies the entry's pair too; what was missing was only that nothing carried the file's side past the submission.

**Nothing reached the Creator**, and the answer was checked against the third escalation and declined: the user gets the entry Design already drew, with nothing new to type, to look for, or to lose.

**And an architecture document has already written a clause on top of it.** `Preparation/Architecture/Keys.md` F3 requires a key fingerprint's display line to be *"(in the fixed-width face, always — `Preparation/Design/Keys.md`)"*, citing the Design document for it. That was the clearest evidence the answer was owed: a closed architecture document leaning on the promise rather than answering it.

**Answer, 2026-08-21: `Preparation/Architecture/Desktop app and delivery.md` [2.7](../Desktop%20app%20and%20delivery.md#27-the-two-faces), H25 to H29.** **The row's own framing is what the answer corrects, and it is the useful part.** The question was put as *what does each platform name its faces, and does each engine resolve those names* — three platforms times two faces times three engines. **The mockup names no platform's face.** It names **generic families**, and the standard says what a generic family is and what each kind is guaranteed to do, so the whole grid collapses to one reading.

- ***The operating system's own interface font*** — **H25**. `system-ui` is *"the default user interface font … on the platform on which the UA is running"*, whose stated purpose is *"to allow web content to integrate with the look and feel of the native OS"*. **Nothing is shipped and no platform's face name is written down anywhere in this project.**
- ***The system's fixed-width face*** — **H25** again, `ui-monospace` being *"the monospaced variant of the system's user interface"* — **with the caveat the standard states itself**: *"ui-monospace is not expected to map to any font on platforms without an appropriate system font."*
- **H12, which the row expected to be the obstacle, does not bite** — **H26**. The standard divides generics into ones that *"will always match a locally installed font"* and ones that *"may not match … on some systems"*, and **each of the mockup's two stacks ends in one of the first kind** (`sans-serif`, `monospace`). So no interface behaviour rests on a capability that might be absent: **the worst case is a different face, never a failure.**
- **H27 states the thing a builder could break without noticing.** An engine that does not recognise `ui-monospace` as a generic reads it as a **family name** — one that matches nothing, so matching moves on — because `font-family`'s value is `[ <font-family-name> | <generic-font-family> ]#`. **The declaration is not thrown away.** And the standard notes generic keywords *cannot be quoted*, so a builder who quoted them would break exactly this.
- ***So they can be compared down a column*** — **H28**, and this is the clause the row called *a property of the face rather than of the layout*. It is, and the standard guarantees it: *"The sole criterion of a monospace font is that all glyphs have the same fixed width"*, and *"monospace must always map to at least one matched font face."* **So the column lines up on any conforming engine.** `font-variant-numeric: tabular-nums` is kept and is **not** what the promise stands on — it enables an OpenType feature a face may not carry, and a monospaced face lines figures up with or without it.

**Row 304's seam is not this seam, exactly as the row said.** X4's character substitutions survive three engines because they are in the string; **H26's stacks survive three engines because every engine implements CSS font matching and each stack ends in a guaranteed generic.** Two different arguments for two different problems, and Section 17 is untouched.
