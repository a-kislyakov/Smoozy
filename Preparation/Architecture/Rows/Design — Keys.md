**Row 418 — how a remembered passphrase is kept safely.** *A remembered passphrase.*
> "**It says the passphrase is held, never how.** How it is kept safely is Architecture's, and a screen that hinted at the answer would be making a promise this design cannot keep."

Kind of promise: **a drafted design sentence.**

**Earns its row by the first test.** The document says outright that this is Architecture's, in those words. **It is the only sentence in the document that does.**

Waits on: **Fact 38** — what each of Mac, Windows and Linux offers for holding a secret on the user's own computer, and what using it costs the user. Already numbered and answered; nothing new to get.

**Answered already.** `Preparation/Architecture/Keys.md` 8.1, which is a **clause-by-clause pointer table rather than a second arrangement**, and behind it `Preparation/Architecture/Security and licence.md` §3. The store per system: *"§3.1 (macOS file-based keychain via `SecItem`), §3.2 (Windows Credential Manager, `CRED_TYPE_GENERIC`, `CRED_PERSIST_LOCAL_MACHINE`), §3.3 (Linux Secret Service via libsecret, with the probe and the nowhere-to-remember promise)"*. The item's shape is the closed four-kind contract with an opaque subject *"carrying no host, path, comment or fingerprint"*, and 8.2 **S1** keys one store item per key against the local key identifier, **never against the path**.

**One clause of the answer runs the other way and is Design's to meet.** The design's *never how* holds for the screen's own words, **but the ruling of 2026-08-16 — recorded in `Preparation/Specs/Whole app.md`'s Security concern and cited at 8.1 as *what the user meets for that keeping* — is that the user does meet the store's cost, and it differs per system**: the Mac's own dialog after an update, Windows silently, Linux asking each time where the computer has nowhere to remember and saying so once. **That is a thing the user meets that this document does not draw.** It is not a gap in this row's answer; it is the answer arriving with a screen attached. **Both halves have since been answered and neither is owed: Row 316 at `Preparation/Architecture/Security and licence.md` §3.3 S32 and S34 — the durable *store's standing* value, its three readings and the one-sentence notice at its first transition — and Row 315 at `Preparation/Architecture/Keys.md` [8.4](../Keys.md#84-a-protected-key-on-a-computer-with-nowhere-to-remember-row-315), S8 to S13, where U9's answer is permanently *no* on such a computer, both connections Smoozy makes on its own are withheld for the life of the installation, and the mark says *cannot* rather than *not holding*, a permanent condition never worded as a passing one. What stays undrawn is Design's**: `Preparation/Design/Keys.md`'s *A remembered passphrase* still says nothing of the cost, and the words for the mark are S10's grant to Design.

Nothing in the spec arranges that. **Asking the place the passphrase actually lives is the obvious way to know, and it is the one way that cannot be used**: on at least one system a store read can raise the system's own unlock dialog, which would put a prompt on screen every time the keys list opens.

The answer is: the row's secret-store subject reference for the key-passphrase kind exists and is not marked as owing an erase. Reading the store itself could raise a system unlock prompt, which would break P1's *answerable without prompting*; the record read cannot."* 8.2 **S2** names that reference as the availability marker, and Section 10 **R1** puts it on the durable key row. **So the line is drawable from the record alone, at every draw, with no prompt and no store call. What makes that marker trustworthy was written later, and this line is what it protects: [U9a](../Keys.md#44-the-protection-reading-and-the-availability-answer-row-245), added 2026-08-25** — the marker is only as good as the mark going with the reference, so a sweep finishing an owed erase is finishing `Security and licence` §5.1 E4's **third** write and takes the row's reference with the mark, never the mark alone. **Without that reading U9 answers *yes* for an item that is gone and this row draws a *clear it* control for a passphrase that no longer exists**, which is *only where there is one* broken. [Section 13](../Keys.md#13-unresolved) item 21 is closed on §5.1 E4's confirming clause, and [R1](../Keys.md#10-what-keys-remembers-between-runs-and-what-it-genuinely-forgets-row-252) was corrected on 2026-08-29 to hold the reference **with its erase mark**, which is the field this line actually reads. **U9 still never reaches the store.**

**Row 420 — naming the servers that use a key, on every row of the list.** *A row.*
> "**Which servers use it is the fourth**, named rather than counted. *Used by RunPod 4090 and Vast 5060* is what makes taking a key away a decision; *2 servers* makes it a number."

Kind of promise: **a drafted design sentence.**

Earns its row by the third test: **every row of the keys list carries the labels of the saved servers that rely on that key, whenever the list is on screen.** That is a cross-module read — Keys reading Servers' saved rows — performed **at draw time for every key**, and nothing in either spec arranges it at that moment. The spec arranges it at one other moment only.

Waits on: nothing outside. It rests on the fingerprint being the match value, which is settled.

**Partly answered.** `Preparation/Architecture/Keys.md` 9.8, **W11 and W12**, which are Row 254's answer.

- **What is answered:** the mechanism and the wording source. **W11**: *"Before either act on a relied-on key, the server rows are read from the local record and matched on the fingerprint and nothing else… The warning names the matching servers by their labels"*. **Labels, not counts**, which is this promise's own point; a local-record read, so it costs no connection; and `Preparation/Architecture/Servers.md` **P16** holds the fingerprint on the server row for exactly this.
- **What is not: W11's moment is *before either act*, not *at every draw*.** Row 254's own words are *"naming the servers that rely on a key, **before the key is destroyed**"*, and both spec sentences it quotes are about the delete or remove warning. **This document's *Connections* paragraph reads the same way — it names the servers *"before one is taken away"* — but *A row* puts the same information on the standing list, in every row, all the time.** Nothing states that the standing display is the same read, taken at the same shape, at every draw of the keys list.
- **And the clause that makes the gap matter is W12's.** W12 rules that the warning must **distinguish a successful read returning no match from a read that failed**, because at the warning's moment a failure that reads as *no server relies on this key* stands in front of an unrecoverable act. **On the standing list the same read fails the same way and this document has drawn no third state for it**: the row would simply carry no *Used by* line, which reads as *no server uses this key*. **That is the same shape W12 closed, arriving one screen earlier.** The unanswered clause: **what the list row shows when the server rows cannot be read at the draw.** That is a decision, not a drawing choice — Design cannot invent a third state for a failure nobody has said can happen.

**Answer, 2026-08-21: the question does not arise on this screen, at `Preparation/Architecture/Keys.md` [W11a](../Keys.md#98-the-warning-that-names-the-servers-row-254) — because the read that would fail is the read the list itself is made of.**

- **The standing display is W11's read**, not a second one: the server rows read from the local record **once for the whole list rather than once per row**, matched on the fingerprint and nothing else, the matching servers named by their labels, taken off the drawing thread like every other record read (`Desktop app and delivery` P5).
- **The match value is the key row's recorded fingerprint** (Section 10 R1) and **never a fingerprint read from the file at the draw**, so **an unusable key names its servers exactly as a usable one does** — which is the case that matters, since a key whose file is gone is the one most likely to be taken away. U10's reading has no bearing on this line at all.
- **The third state the row asked for is removed rather than drawn.** U1 set 1 is *every key row in the local record*, so **a draw that has key rows to show has the server rows in the same hand**: either the read answered and every *Used by* line comes out of it, or it did not and there is no keys list at that draw. **So a row carrying no *Used by* line means what it appears to mean** — the read succeeded and no saved server holds this fingerprint.
- **That argument covers the rows that exist at the draw; the rows that arrive after it were closed later.** [U10a](../Keys.md#45-the-check-one-function-three-callers-row-253) gained a bullet on **2026-08-25**: [U1](../Keys.md#41-what-in-a-key-location-is-listed-as-a-key-row-245) set 2's *membership* is itself a reading, so a **discovered** row is absent from the draw entirely and arrives on P6's queue behind set 1's — and drawn with **no** *Used by* line it would say the thing W11a says that line means, **in front of a Delete control, for a key a saved server relies on**. **The rule: the server-row result is held for the life of that draw and the late row is matched against it.** No second read is taken, W11a's *one read per draw, one match for the whole list* is unchanged, and the promise *every row names its servers* reaches a discovered row too.
- **That is W12's distinction kept without a second reading of it being invented one screen earlier**, which is exactly what the row was right to be worried about. Where the read does not answer, **the failure is the local record's and the whole screen's rather than a row's**, reaching the user by `Whole app`'s *How a failure reaches the user*.
- **W12 is untouched.** The warning's read is still taken at the act's own moment, still fails there on its own, and every clause of it stands. **Nothing else composes the line** — no connection, no store call, nothing from a machine.
- **The limit that rode is closed.** [Section 13](../Keys.md#13-unresolved) item 15 — what the application does where the local record cannot be read at a draw — was **closed on 2026-08-22 at the Architecture seam close**: `Desktop app and delivery` **L8a** states the rule, that **a screen never draws a field from a read that did not answer and never draws an absence in its place**, so a failed read shows as a failure rather than as an emptied screen. **That is exactly the state this row was worried about, written down in the document that owns the store**, and W11a's *no third row state is written* now rests on a stated rule rather than on a seam.


**Row 421 — the fingerprint on screen for a key whose file is gone.** *An unusable key.*
> "**The fingerprint stays on screen while the key is unusable.** It is the only thing that can say whether the file the user is about to point at is the same key."

Kind of promise: **a drafted design sentence.**

**Earns its row by the third test in its sharpest form.** The fingerprint is read from the key's file. **This promise shows the fingerprint precisely when the file is missing, unreadable, or has been swapped for a different key** — so it can only be kept if Smoozy has been arranged to hold the value somewhere the file's absence does not reach, and to show *the value it remembers* rather than *the value it can read* in exactly this case.

Waits on: nothing outside.

**Answered already.** `Preparation/Architecture/Keys.md` Section 10 **R1** and 4.1 **U1**.

- **R1** puts the fingerprint on the durable key row in the local record, beside the recorded path and the name as last read, and drops it only at delete or remove (9.6, 9.7).
- **U1** set 1 makes the list *"Every key row in the local record whose recorded path lies in the usual key location or that was pointed at — shown whatever the current state of its file… a row whose file is missing, unreadable or swapped shows as unusable with the reason, **from the record, needing nothing from the file**."*
- 5.2 **F3** names the row's display line as one of the four places the value appears, and cites this Design document for the fixed-width face — **which is the clause Row 322 is owed for.**

**One thing the answer adds that the promise did not ask for, and it matters to the *new location* offer this sentence serves:** by 5.3 **F6**, a *new location* file whose fingerprint does not match is **refused by Smoozy**, not merely judged by the user's eye. **Row 422 — the unusable row saying what is wrong, at the moment the list is drawn.** *An unusable key.*
> "**It stays in the list, dimmed, and says what is wrong in the row.** The [spec](../../Specs/Keys.md) requires it to be shown rather than hidden — a key that vanished when its drive was unplugged would look like a key that was never there."

Kind of promise: **a drafted design sentence.**

Earns its row by the third test: two separate things have to hold — **the row must have a closed set of things it can say is wrong, and it must have the answer at the moment it is drawn.**

Waits on: nothing outside.

**Partly answered.** `Preparation/Architecture/Keys.md` 4.2 **U6** and 4.5 **U10**.

- **What is answered, completely: the vocabulary.** **U6** closes the set at five and each is the clause of *usable* that failed: *"*file missing* (clause 1), *unreadable* (clause 2, **clause 4a**, or a read the tool refuses), *not a supported type* (clause 3), *no longer the same key* (**clause 4b**), *file permissions too open* (clause 5)."* **U4's clause 4 has since been split in two** — *4a, the fingerprint reads*, whose failure is *unreadable* and costs the remembered passphrase nothing, and *4b, and it matches the row's*, which is the swap and the only one raising the erase — **so two of the five reasons name a half-clause, and the count of five is unchanged.** U6 also **forbids composing these out of any diagnostic string the tools emit**, so what the row says is Smoozy's own wording throughout — which is what makes it Design's to write at all. **U3** keeps the *shown rather than hidden* half honest from the other direction.
- **A state above the closed set arrived on 2026-08-25, and this row's promise is what it lands on.** [U6a](../Keys.md#42-usable-composed-row-245): where the tool a reading needs is absent — [G6](../Keys.md#63-the-generator-probed-never-assumed-row-248)'s probe answering that no `ssh-keygen` exists — the key is ***not checked***, which is **the absence of a verdict and not a sixth member of U6's set**. Nothing about the key failed, so no reason is composed for it, **nothing is handed to a caller in place of a verdict that was never read**, and no row is called unusable for the computer's missing tool. **The cause is the computer's rather than any key's, so it is said once above the list and never per row**, on the keys screen and on the server list, whose draw takes the same readings. **So *says what is wrong in the row* has one bounded case where the row says nothing and one line above the list says why** — U6's closed set untouched, the wording Design's, drawn at `Preparation/Design/Keys.md`'s *On a computer without the SSH tools* on 2026-08-29.
- **What is not answered anywhere: whether the verdict exists at the instant the list is drawn.** **U10** says the check is *"one function — U4's five clauses evaluated fresh against the row at the moment of the call — and the standalone keys view, the server list draw and the connection attempt all call that one function"*, run *"once per key per ask, over every key the caller asks about"*. **Every clause of it is a real reading**: U7 names an in-place header read of the private file, an `ssh-keygen -l -f` invocation **per key** — a separate process — and the filesystem's answers, and 4.3's fallback can add a second invocation against the public half. `Preparation/Specs/Keys.md` has the standalone view asking *"whenever it is on screen"*. **Nothing in `Preparation/Architecture/Keys.md`, `Servers` §9.3, or `Desktop app and delivery` says whether the list draws with the verdicts already in hand, or draws first and settles as each key answers.**

**This document already sensed the gap and parked it**, in a marker that names nobody: `[PENDING: what the row shows while Smoozy is checking a key, given the spec has it checked whenever this screen is on screen]`. **Design cannot clear that marker on its own, because whether there is a *while* at all is not Design's to decide.**

**The precedent that makes the silence a finding rather than an oversight.** Every document in `Preparation/Architecture/` was searched for a statement about a per-item reading holding up a list draw. **There is exactly one, and it is the same problem solved**: `Preparation/Architecture/File Browser.md` **L7** says of the per-file version reading that *"the four fields show first and the version tag fills in as each prefix arrives behind them"*, and names it as what makes *the reading never blocks the listing* implementable. **The keys list and the server list have the same shape and no equivalent sentence.** What breaks if it is left: on a keys list of three keys the answer almost certainly does not matter, and **on a server list drawn at every look it may** — but *may* is exactly what nobody has written down, and Design is being asked to draw a state that might not exist.

**Answer, 2026-08-21: the list draws first and each verdict fills in behind it, at `Preparation/Architecture/Keys.md` [U10a](../Keys.md#45-the-check-one-function-three-callers-row-253) — and the order is forced by a closed document rather than chosen here.**

- **Every clause of U4 is a filesystem call or a tool invocation** — U7's in-place header read, an `ssh-keygen -l -f` process per key, and 4.3's fallback can add a second — and `Desktop app and delivery` **P4 and P5** put every filesystem call and every such reading off the thread that draws: *"What runs on it is the drawing and nothing else."* **A list drawn with the verdicts already in hand is that thread waiting on them.**
- **So the shape is `File Browser` L7's**, cited as the precedent. **What a [U1](../Keys.md#41-what-in-a-key-location-is-listed-as-a-key-row-245) set 1 row carries before its verdict arrives is everything R1 holds** — name, fingerprint, recorded path, and W11a's *Used by* line — **and for a set 1 row what is absent is the usable-or-unusable verdict and U6's reason, and nothing else.** **For a set 2 row it is more than the verdict**: set 2's *membership* is itself a reading — a directory enumeration plus U2's in-place header read on every regular file — **so a discovered row is absent from the draw altogether**, arrives on P6's queue behind set 1's with its own verdict following it, and takes its *Used by* line from the server-row result that draw already holds. *(U10a, bullets added 2026-08-25.)*
- **How the row draws that absence is Design's, bounded by one rule**: **no verdict may be drawn that has not been read** — never usable and never unusable while it is still being asked.
- **One ask per appearance of the list, one reading per key**, each answer arriving as its own event on P6's one ordered queue, **so a slow key holds up no other row**. **A redraw caused by a verdict arriving is not a new ask**, or the list would ask for ever; an event whose row is gone is discarded (P8). **Nothing is cached and U10 is unchanged.**
- **The same shape reaches the other two callers, which is what one function means.** `Servers` P12's draw takes its mark this way and **P13 is untouched** — still a derivation computed at that draw and stored nowhere, arriving on the queue rather than ahead of the row. **The connection attempt is not a draw** and waits on its own call.
- **So Design's `[PENDING: what the row shows while Smoozy is checking a key…]` was answerable, and Design has since cleared it**: there is a *while*, it is bounded by one reading per key, and the record's own values stand in the row throughout it. **`Preparation/Design/Keys.md` drew it on 2026-08-23 as its own section, *While a key is being checked*** — the row draws first, the one place the verdict would go carries the underway mark, no verdict is drawn that has not been read, it is not a veil over the list, and it happens at every opening because nothing is cached. **The marker no longer exists in that document.**
- **One limit rides**, at §13 item 16: **how long a row stands without its verdict has never been measured** on any machine. **Nothing structural breaks** — the row carries R1's values throughout and never a verdict it has not read, so a slow reading costs a wait and never a wrong statement. It closes by timing the check against a real key at Build.
