**The promise is kept on all three systems and by three mechanisms rather than one, and on Linux it now costs the user one password. Corrected 2026-08-22:** macOS replaces the complete signed bundle at the installed path and **Linux hands a signed package to the distribution's own mechanism**, which is a privileged act (Fact 124) — so the user meets the system's own authentication once, which the Creator ruled on 2026-08-22 and which [Whole app](../../Specs/Whole%20app.md) now records. **The quoted promise still holds**: the user discovers nothing, fetches nothing and remembers nothing. This paragraph used to say macOS and Linux share the platform's own atomic rename over the old path; **Windows is side-by-side**, because Microsoft documents the unattended outcome and documents that replacing the running image at its own path fails. **The row's own worry — whichever system refuses a running application the right to replace its own files — is real and is Windows, and it costs a different shape rather than the promise.** **What triggers the check is named rather than left open, and the list is three**: application start, one repeating check while the application runs with the interval Build's to pick, and **one act of the user's, at the entry point Design draws** — the spec permitted the user to ask for a check on 2026-08-25 and Z26 carried it on 2026-08-29, per Row 508. A start-only check would leave a user who keeps Smoozy open across a long render on an old build until they restarted, which is the shape this row forbids. **The user's act neither widens nor narrows the promise**: it is the same act reached a second way, permitted rather than required, and Z1 stands word for word — the application checks, fetches, verifies and installs, whoever asked. Z27 coalesces a user's ask onto a check already in flight and starts none where an update is already past its check; Z28 has any completed check write the last-completed-check moment; Z29 keeps Z10b's Linux once-per-version suppression to the automatic route; and Z30 makes a check waiting on admission *underway* with no fifth reading drawn for it, the update fetch's admission class being declared at §11.3 R19. **The update fetch draws from the one download budget and is admitted at the desktop-side point like any other draw**, and the updater's writes go through the platform file adapter like every other write, the adapter carrying a publication variant with a named backup for it. **On macOS what is replaced is the replaceable unit rather than the executable alone**, because the document's own clauses already put a second file in the bundle.

**Two things ride with it and neither breaks the promise.** The shell chosen documents no self-update of its own, which costs work and not a promise: the replacement is the operating system's mechanism, below the framework, on every route. And **the Windows reputation warning is stated plainly rather than absorbed** — Section 19.2 — because no permitted answer removes it: signing does not, extended validation no longer bypasses it, and the store route is forbidden by the download promise. **And it is not always a warning.** E8a records that on Windows 11 Smart App Control may supersede reputation and **block** execution outright, which is an ending different in kind rather than a worse warning, and that its checks *"apply to all executable files, not just those downloaded from the Internet"* — so an update the application places for itself is inside the boundary as much as the first download is. **The Linux trust anchor is named, because Linux has no platform store to name one for it:** every build embeds an offline recovery public key and the current accepted online signing-key set (E19), and the **anchor** is never fetched and never read from the manifest, the hosting or anything served with them — *"The manifest never supplies an unanchored key"*, and a build that cannot form a chain from its embedded recovery public key does not verify and does not update. **The online set does rotate**, by key statements signed by the offline recovery key and retained on hosting indefinitely, the client refusing any statement below the highest trust-sequence it has accepted; that is a chain from the embedded anchor and never a key fetched into trust.

**Four things close unresolved and each names what breaks.** **Fact 97 on Windows** (Section 22 item 6), whether the reputation warning fires on a build the application launches itself, which no page joins — and E8a adds that on Windows 11 the ending may be a **block** rather than a warning, Smart App Control admitting an app only on recognition by Microsoft's services or a trusted certificate, with neither the share of machines enforcing it nor whether the certificate E7 prices is one it trusts established by any page read. **Fact 74's quarantine clause on macOS** (item 5), whether a quarantined app re-triggers first-open approval for the copy it writes for itself — narrowed by Z8 keeping the installation identity and the installed path, the complete signed bundle being replaced **at** that path and nothing written inside it (Z5) — and if it closes the other way it is a change to what the user gets and returns to Specs then. **On macOS and Linux, a new build that cannot start at all is rolled back by nothing** (item 46): Z21 names the performer on all three — Windows' relaunch helper, and on macOS and Linux the still-running old process, with Z21a's durable update-in-probe record surviving that process's death so a later launch finishes the rollback — but a build that never starts never reaches the record. **And on Linux, whether one authentication for the package transaction covers a rollback taken minutes later** (item 47); where it does not, Z21a's record survives and the next launch performs the rollback and asks then, which is a prompt the user is present for by definition. **What used to sit here and is now closed:** which mutable content a Wails bundle carries beyond the executable — Z25 fixes that every piece of bundle content moves as the one complete unit, the bundle immutable between signed releases and mutable user state outside it.

Waits on: Fact 72 — whether a transfer over the connection Smoozy holds already tells a whole arrival from a damaged one, or whether that has to be added. Evidence already in hand and not to be over-read, all from `Preparation/Architecture/The rented machine.md`, on one box on one day: **in both directions a killed copy leaves a piece of the file under the final name** — "No marker, no `.part`, no temporary name, nothing to say it is incomplete. Half a file looks exactly like a whole one — right name, right place, wrong size, and a fingerprint that does not match" — so the cut-off half of this promise is **not** kept by the transfer on its own, and the naming is the reason, since the piece already holds the name a finished file would carry; both **whole** transfers arrived intact, the fingerprint taken on the machine before sending matching afterwards in each direction over an ordinary home connection, which is two runs of one file and not a general statement about damage; **a broken copy can be picked up where it stopped**, with `rsync` rather than `scp` — a 20 MB file chopped to 5 MB was completed by sending only the missing 15.7 MB, "and the finished file's fingerprint was right"; **the user's own end may not have the tool**, since "The Mac's `rsync` is Apple's own, not the usual one, and it does not take the flags normally used for resuming" — `openrsync: protocol version 29`, which ignored `--append-verify` outright, against the rented machine's ordinary `rsync version 3.2.7`, so the two ends of one transfer do not offer the same abilities and the end that differs is the user's; and **a path with one space in it broke three tools three different ways** on that box, in opposite directions, which is a hazard for anything that composes a transfer command rather than a hazard to this promise itself. **Answer: ANSWERED 2026-08-31 at [`Server protocol and transfers`](../Server%20protocol%20and%20transfers.md#77-what-a-transfer-does-not-do-on-its-own-which-is-the-answer-to-the-second-clause) S31. - **The connection is left uncompressed**, which is the transport's own client default, on the transport's own advice: `ssh(1)`'s `-C` entry says compression *"is desirable on modem lines and other slow connections, but will only slow down things on fast networks"*. **No line this project uses has been measured and nothing here claims to know which it is** — the decision rests on the default and on the publication's own words. *(Corrected 2026-08-31: this read "and a rented machine is on one", which is an unsourced claim about the world.)* `ssh_config(5)` gives the client default as **no** and `sshd_config(5)` shows the far end permitting it after authentication, so the client is what decides. - **The file body is never compressed, and that half is a requirement rather than a preference — which is this row's own point, taken.** A checkpoint is a byte offset into the staged file and its digest covers that file's own bytes (S12 steps 1 to 3). A compressed body would make a resumed offset an offset into a compressed stream, so **a resumed offset would mean something different from a fresh one**, and S13's four-value unchanged-source reading would describe something other than what crosses. **So the staged bytes and the wire bytes are the same bytes.** Any later proposal to compress a body changes S31 and S12 together, never one of them.
