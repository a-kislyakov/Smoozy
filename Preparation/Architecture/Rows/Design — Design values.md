**Row 327 — whether the theme can be declared, and not only painted, in the window Smoozy is actually built in.** *Light and dark.*
> "**And the theme is declared, not only painted.** Scrollbars, form controls and focus rings are drawn by the operating system rather than by us, and they stay light — inside a dark app — unless the page says which theme it is in. So the light block declares *light dark*, which covers the system's own dark as well, and each of the two `:root[data-theme]` blocks declares the one it is. It is easy to miss, because everything Smoozy draws itself looks correct while the scrollbars give it away. Label: **observed** — see [Sources](../../Design/Sources/Design%20values.sources.md)."

Kind of promise: **a settled value** — it is a sentence in this document. The document's own label on it is **observed**, and **the observation is worth carrying intact: it was observed in the mockup, which is a page in a browser.**

**Earns its row by the first test**, though the sentence saying so is in the companion sources file the quote points at rather than in the body. `Preparation/Design/Sources/Design values.sources.md`, under *Native controls are painted by the browser, and stay light unless the page declares its theme*, says of the same claim: *"**What it does not cover.** Anything about the window Smoozy will actually be built in. The mockup is a page in a browser, and whether the same rule holds in whatever Architecture chooses is that stage's to find out. What is settled here is that the theme has to be declared and not only painted; how, on the real thing, is not."* That is this stage named, with the settled part and the unsettled part marked off from each other. **It also meets the third test in its sharpest form:** a scrollbar, a form control and a focus ring are drawn by the operating system and not by Smoozy, so no amount of drawing at Build reaches them. Keeping the promise requires the shell to carry a declaration **outward to surfaces Smoozy does not paint.**

Waited on: **an outside fact, not Blender's — what each of the three system web views does with a declared colour scheme, and whether the declaration reaches the operating-system-drawn controls inside it**, on macOS, Windows and Linux. **Nothing in `Preparation/Architecture/Facts.md` held it.** **It is now `Fact 118`, numbered and answered in part by the runner on 2026-08-21** — the standard and macOS documented, Windows and Linux owed, and the cost of the gap bounded.  The nearest numbered fact is **Fact 96**, the six-candidate shell comparison, which establishes the three-engine cost in the projects' own words and answers nothing about colour scheme. The fact wants each web-view project's own documentation and each operating system's own; **no rented machine bears on it**, and by `Preparation/Architecture/Desktop app and delivery.md` Y3 no Windows machine and no Linux desktop computer has run it, so two of the three would close as documentation alone.

**Was not answered anywhere, and the finding stands as the record of why the row exists.** `Preparation/Architecture/` in full, `Preparation/Specs/` in full and `Preparation/Groundwork/` were searched for *theme*, *dark*, *light and dark*, *colour scheme* and `color-scheme`, *scrollbar*, *focus ring*, *form control*, *native control* and *appearance*. **There is not one occurrence of the subject anywhere outside `Preparation/Design/`.** The three places it could have landed and did not:

- **`Preparation/Architecture/Desktop app and delivery.md` Section 2.2, H6** — the required properties of the shell, **seven when this row was filed and eight since 2026-08-21**. Native menu bar and native file picker are property 6; documented signing and notarization property 7. **The eighth was added with [2.6](../Desktop%20app%20and%20delivery.md#26-the-colour-scheme-read-and-declared) on the day this row was answered** — *"A window frame that follows the operating system's light-or-dark setting, or nothing set at all"*, which Wails holds on two of three and publishes nothing for the third (H23). **That is the window frame and not the page's declaration**, so the gap this row exists for was real when it was filed and the list still carries no property about a declaration reaching the controls the engine draws: a candidate that could not declare its theme would pass H6 even now.
- **The same document, Section 18** — **18.3** is the native menu bar (K9, K10) and **18.4** the system file picker (K11 to K13); the section has since gained **18.5**, the keyboard shortcuts beside the menu items, and **18.6**, the folder-reveal service (2026-08-25). **Not one clause of any of them mentions appearance, a colour scheme or a system-drawn control.**
- **The same document, Section 22 item 19** — the closest thing in the stage, and a recorded gap rather than an answer: *"**What each of the three system web views does with the two typography substitutions, and whether every design value the mockup carries renders on the frozen engine.**"* The colour-scheme declaration does sit in the mockup's token blocks, so item 19's second clause brushes this. But **item 19 asks whether a value renders, and this row asks whether a declaration reaches surfaces the engine does not draw at all** — the opposite direction, and the one X5 already names as the hard case for text: *"a great deal of what the user reads is drawn by no engine at all."* Item 19 names no scrollbar, form control or focus ring, and nothing else does either.

**One thing that makes the gap smaller than it looks.** H12 forbids building an interface behaviour on a capability not present on all three engines. It is a standing rule that would catch this at Build if anybody thought to check it against this promise. It names no capability and reads no documentation, so it is not an answer — but the promise is not unprotected.

**This row and Row 321 are one subject seen from two sides**: Row 321 is *do we ever learn which theme to declare*, this one is *does the declaration reach the controls we do not draw*. **Both were answered on 2026-08-21 in one act**, and together they had been the only place in the whole sweep-and-answer trail where a whole visible behaviour of the application had no mechanism behind it at all.

**Answer: `Preparation/Architecture/Desktop app and delivery.md` [2.6](../Desktop%20app%20and%20delivery.md#26-the-colour-scheme-read-and-declared), H19, H20 and H22.**

- ***The theme is declared, not only painted*** — **H19**. The instrument is the `color-scheme` property, and the standard requires of a conforming engine that the used colour scheme affect *"the default colors of scrollbars and other interaction UI"*, *"the default colors of form controls and other 'specially-rendered' elements"*, *"the default colors of other browser-provided UI, such as 'spellcheck' underlines"*, *"the value of system colors"* and *"the value of the light-dark() function"* — and on the root additionally *"the surface color of the canvas"* and *"the viewport's scrollbars"* (*CSS Color Adjustment Module Level 1*). **WebKit states the negative in the promise's own terms**: *"Without this declaration, it would not be safe for the engine to use dark form controls or a dark color scheme"*. So H19 says outright that the declaration is not decoration and its absence is the whole of this row.
- ***So each of those three blocks carries that declaration alongside its tokens*** — **H22**. The arrangement is Design's and H22 fixes what it rests on: three token blocks — the bare root, `@media (prefers-color-scheme: dark)`, and the explicit-declaration block — each carrying its own `color-scheme` declaration. **And it names something the sweep could not have known to ask**: the explicit-declaration block is the mockup's own affordance and **the shipped application never enters it**, because nothing in Smoozy sets that attribute and Smoozy has no switch. It is kept so the two files stay one file.
- **The third test the row raised — *no amount of drawing at Build reaches them*** — **H20**. That is right, and the resolution is that the declaration is not drawing: it is a stylesheet property, and it survives H11's three engines for the same reason X4's character substitution does. **What it does not survive is an engine that does not honour it, which is the limit below.**

**Answered for the standard and for macOS; carried with a limit for Windows and Linux, and the limit is written where a builder meets it.** `Desktop app and delivery` Section 22 item 35. **WebView2's own property page speaks only of *"WebView2 UI like dialogs, prompts, and menus"*** and says nothing about the page's `color-scheme` reaching a scrollbar; **WebKitGTK's own release announcement ties form-control rendering to the GTK theme rather than to the page's declaration** — *"Improve rendering of form controls when GTK theme is dark and enable prefers-color-scheme media query"*. **What the gap costs is a light scrollbar or a light dropdown inside a dark window** — exactly the giveaway this row's own Design sentence describes — **and never a wrong reading, a lost file or a silent success.** Two ten-minute readings on a Windows computer and a Linux desktop close it, and by Y3 this project has neither.

**And item 36 says the honest thing about all of it**: none of this is observed by anybody on this project, on any of the three systems. **The observation in `Preparation/Design/Sources/Design values.sources.md` is a page in a browser and that file already said it does not answer for the shipped window** — this row's answer is documentation, and the first build of the chosen shell at Build is what turns it into an observation. *(Corrected 2026-09-04 — this read *the first **Wails** build at Build*, a build that will never happen; the shell has been Tauri v2 since `Desktop app and delivery` H5b was filled on 2026-09-02. Only the shell's name moved; the row's answer and its standing are unchanged.)*

**Re-quoted 2026-08-25, after the Design close.** **The promise moved only in its arrangement clause.** One sentence changed — **So each of those three blocks carries that declaration alongside its tokens** became **So the light block declares *light dark*, which covers the system's own dark as well, and each of the two `:root[data-theme]` blocks declares the one it is** — and nothing else in the paragraph moved. **The claim the row exists for is word for word what it was** — that the theme has to be declared and not only painted, because scrollbars, form controls and focus rings are drawn by the operating system and not by Smoozy — and **the three-engine question the row waits on is untouched**. H22's own finding survives the change: there are now two explicit-declaration blocks rather than one, and the shipped application enters neither, because Smoozy sets no attribute and has no switch.

**One thing is not ruled here, and it is the runner's.** `Preparation/Architecture/Desktop app and delivery.md` **H22**'s descriptive text is stale: it describes three token blocks each carrying its own declaration, where the document now has **four blocks and three declarations** — the light root declaring `light dark`, the `prefers-color-scheme: dark` block carrying none, and one declaration under each of the two `:root[data-theme]` blocks. **Whether that matters turns on reading H22 as descriptive or as binding.** The re-sweep did not file it as a fault, on the ground that H22's own first sentence hands the arrangement to Design and that H19 and H20 are what the answer requires. Nothing further is decided on this row. *(2026-08-25.)*

**Row 483 — whether the interface face's *italic* is reachable and legible on the three engines, now that italic carries a meaning of its own app-wide.** *Colour, and what each one means.*
> "**A value Smoozy cannot confirm is shown by the italic face and the dash**, not by a colour of its own. Nothing is reserved for it."

Kind of promise: **a settled value** — it is a sentence in this document, new at the Design close.

**Filed 2026-08-25 by the Design close re-sweep of `Preparation/Design/Design values.md`.**

**Earns its row by the third test, on the outside-fact clause, and it is the same seam Row 322 sits on moved from a family to a style.** Before the close, *a value Smoozy cannot confirm* was a colour — `--ink3` — in the meaning table; the close took the colour away and put the weight on the face instead, and by the sentence's own words **nothing is reserved for it**, so the italic is the whole of the distinction. Neither face is shipped — `Preparation/Architecture/Desktop app and delivery.md` **H25** is explicit — *"Neither face is shipped and neither is named per platform"*, and *"No platform's face name has to be known by this project, and none is written down anywhere."* — so which italic the user sees is whatever each of the three engines resolves out of `system-ui`, and where the resolved face carries no italic of its own, whatever that engine does instead. **That is a fact to get, of exactly the kind Row 322's answer got by reading the standard, and nobody has been asked for it.**

**What makes it load-bearing rather than cosmetic.** Three other Design documents already rest on the italic being an unmistakable second state of the same face:

- `Preparation/Design/Servers.md` sends the app-wide question here by name — *"the mark [Design values](../../Design/Design%20values.md) gives app-wide for a value Smoozy cannot confirm"*.
- `Preparation/Design/Whole app.md`'s italic-and-bold convention — **Row 318** — is answered at `Preparation/Architecture/Render Settings.md` **Section 2, J1 and J4**, and J1 hands the face back to Design in as many words: *"Which face each takes is Design's; that they are two objects is this clause."* **So the two-object rule is answered and the face is not.**
- `Preparation/Design/Render Settings.md` puts a third state on every setting on the page as *"an em dash in the file's own italic face"*, and states the reason the italic must read: *"italic is already this page's word for* the file's*"*.

Waits on: **Fact 136** — whether `system-ui` and `ui-monospace` resolve a face with a true italic on each of the three system web views, and what each engine does where the resolved face has none — and whether that outcome is distinguishable from upright at this document's smallest type steps. **An outside fact, not Blender's.** Nothing in `Preparation/Architecture/Facts.md` held it; **Fact 119** is the nearest and is about which family resolves, not about style. **No rented machine bears on the standard's half**, and by `Preparation/Architecture/Desktop app and delivery.md` Y3 no Windows machine and no Linux desktop computer has run it, so the per-engine half would close as documentation alone, exactly as Rows 321, 322 and 327 did.

**Answered 2026-08-25 at the tenth sitting.** `Preparation/Architecture/Desktop app and delivery.md` §2.7 H29a.

Answered against **Fact 136**, and it is three different answers rather than one. **The Mac is settled and good** — both faces ship genuine designed italics, observed five ways in the system's own web view. **Linux has no answer to give by construction**, the face being whatever the desktop is configured to use. **Windows is open, and the check narrowed the question**: it is not a secret of the browser engine but *which face Windows reports as its menu font*, which is answerable without a Windows computer.
