**Row 1 — the scene name a job is pointed at.** *Submitting a job.*
> "So a mistaken name does not come back as a failed job. It comes back as a paid render of the wrong scene, and the promise that a job is exactly one named scene rests on Smoozy getting the name right rather than on being told when it is not."

Waits on: nothing to get. Constraints: the scene has an argument of its own in all four versions (*Settings 1*, *What a render demands 3*, joined at `Preparation/Blender Research/Across topics/What can be set from outside.md`); a scene name no scene bears is named and then ignored and the run reports success (*Settings 12*); an argument outside the after-the-file-before-the-render window is silently ignored. Named gap in the spec's own sources: every file tried was saved by a Blender with no window, so what a file saved from Blender's interface records as its showing scene is untested — and that is the fallback this promise fails into. **Answered** — [Rendering](../Rendering.md) 1.6 L15–L16 and 4.2 S6, with the untested interface-saved gap at §9 item 12. **The name is right by provenance rather than by checking**: the scene argument passes the manifest's name byte for byte, and the requirement this contract places on `Render Settings`' payload is that a scene name is only ever the exact bytes read from the file's own scene list by a reading of that file — never typed, never normalised, never carried across a file replacement. A job submitted without a read carries no scene name and names none at launch, which is the spec's own stated fallback; L16 records that what an interface-saved file's showing scene is has never been observed, and nothing is built on the untested half.

**Row 2 — a single job reaches the machine whole or does not exist.** *When only part of a submission arrives.*
> "**A single job is all or nothing.** It either reaches the machine and joins the line, or it does not exist at all. That is a promise this spec makes and Architecture has to deliver; a plan that cannot deliver it is a flawed plan rather than something to work around here."

Waits on: Fact 1. Depends on the shape document existing first — there is nothing to submit *to* until what runs on the rented server is settled. **Answered** — [Rendering](../Rendering.md) §4 S1–S8. **The partition unit is the scene-job**: the act is partial across scene-jobs and atomic within one, which is Row 292's mechanism holding this promise and `Queue & History`'s opposite one without either spec bending. One scene-job's submission is an ordered unit — remap material placed, the job's material published by a single rename, the job record written — and Q3's rule that a job is in the line exactly when its job record exists is what makes *all or nothing* checkable; published material with no job record is never a job, and its removal is S4b's recorded cleanup debt rather than `Job files and outputs` M7's sweep, which reaches only a submission that stopped before the material was published and never carried this case (corrected 2026-08-22). A refusal at any unit fails that scene-job whole and touches no other.

**Row 3 — reading the machine before naming which scenes went.** *When only part of a submission arrives.*
> "Where the connection comes back, Smoozy reads the machine before it names which scenes went, so what it says rests on what is actually there rather than on what it last heard. Where the connection does not come back, it names the scenes it could not account for as exactly that."

Waits on: Facts 1 and 8. Each job needs an identity Smoozy assigns before it sends and can match against the machine afterwards, or a job that arrived while its acknowledgement was lost is either counted twice or reported as not sent. Nothing in the spec says where that identity comes from. **Answered** — [Rendering](../Rendering.md) 4.3 S9–S12. On reconnection each provisional record is resolved by **asking the machine for that scene-job's submission command's own operation identity** — the job identity being what the answer resolves and never what is asked — under `Server protocol and transfers` C8's three closed answers: *a recorded outcome* → submitted or refused, per the outcome; *still in hand* → still provisional, asked again next connection, the machine having answered rather than been unable to; *no record of that identity* → removed, not submitted. Never by guessing and never by re-issuing under a fresh identity. The unaccounted are the records still provisional, named as exactly that. Fact 8 is what makes it answerable at all: the operation identity is chosen at the desk before the request is sent, the window is about three milliseconds wide, and *still in hand* was never once returned in the 230 usable trials of 312 run, the tester discarding the first 82 as cuts that landed before the request was sent — while cutting a connection does not guarantee the request never landed, which is why the ask is mandatory.
