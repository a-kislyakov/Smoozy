## 1. Trust boundaries

**Constraint:** Row 278 — *"Everything of the user’s stays with the user."* And [The shape](The%20shape.md#deployment-shape): two deployment trust domains — the user’s computer and each rented server.

### 1.1 What the sentence means, and what it does not

**B1.** A rented server is the user’s own machine: they rent it, hold its login and destroy it. Material placed there remains under the user’s control. Smoozy puts nothing of the user’s anywhere the user did not open and does not hold.

**B2.** That reading is load-bearing because one of the five held things — the Telegram bot's token — is deliberately placed on rented machines by [Telegram](../Specs/Telegram.md) and [Server Setup](../Specs/Server%20Setup.md). [Section 10](#10-what-smoozy-leaves-on-a-rented-machine) states what that costs and what it is protected against.

**B3. Telegram's service takes the same reading, applied a second time.** Material of the user's crosses it whenever the module is on, and [Section 1.2](#12-the-domains-and-the-complete-crossing-list) lists that crossing in both directions. The bot is made in the user's own Telegram account, the token is theirs, the account is theirs, and the module is off until the user turns it on — and [Telegram](../Specs/Telegram.md) states in its own words that *"Turning Telegram on is itself the asking."* So Telegram's service is a place the user opened, on the same argument this section has already made for a rented server. What crosses it is [Telegram](../Specs/Telegram.md)'s and is not restated here.

**B18. Desktop application → rented server.** The SSH connection is the authentication boundary for everything: the pre-package surface, the versioned command protocol, the bootstrap-and-repair request and the transfer channels all inherit it, and `Server protocol and transfers` owns their framing. The only secret that crosses and stays is the Telegram bot token. **One secret crosses without staying: the elevated-access password.** It crosses whenever a step needs it, under all three of [Whole app](../Specs/Whole%20app.md)'s arrangements, and it is never kept on the machine. How long the desktop application holds it is [Section 2](#2-the-five-held-things)'s and is not a property of this crossing. No SSH private key ever crosses, and no passphrase ever crosses, because neither is ever sent anywhere ([Section 6](#6-the-private-half-of-an-ssh-key)).

**B19. Rented server → desktop application.** Readings, events, captured streams, job state and transfer data are observations, never authority to alter desktop security.

**B20. Rented server → rented server.** Nothing. A rented server never holds another rented server's connection identity and never opens a connection to another rented server; the Telegram conversation is the only channel between machines. That is the shape's rule and this document does not widen it.

**B21. Smoozy → Telegram's service → the user's phone.** [The shape](The%20shape.md#deployment-shape)'s two domains are the places Smoozy's own code runs and holds state, and Telegram's service runs none of it. It is a further crossing destination here because material of the user's crosses it, and [Section 1.1](#11-what-the-sentence-means-and-what-it-does-not) states why that crossing is inside Row 278’s boundary. **Nothing crosses it but what [Telegram](../Specs/Telegram.md) sends**, which that document states in full and this one does not restate, together with the bot token the service authenticates every call with ([Section 10](#10-what-smoozy-leaves-on-a-rented-machine)).

**B22. The user's phone → Telegram's service → Smoozy.** The actions [Telegram](../Specs/Telegram.md) offers, on the one conversation it has proved is the user's, and nothing else.

**B23. The user's computer → the user's own mail → the Creator's mailbox. Added 2026-08-25, routed from [Reporting a problem](Reporting%20a%20problem.md) §10 B3 and §12 item 6; this list was stated as complete and was not, in the one direction a reader would least expect.** The two mailboxes are a **further crossing destination**, on the same ground as Telegram’s service — material of the user's crosses them — and they are the only entry on this list **Smoozy itself does not cross**. It composes a report file, writes it into a folder the user chose, and opens that folder; there its part ends. No mail handler is invoked, no share facility is reached for and no message is composed on the user's behalf, on any system (`Reporting a problem` V10), and Smoozy initiates no transmission of the diary, of a report, or of any value derived from either (B1). **The crossing is the user's own act of attaching the file and pressing send**, and it is entered on this list because what the list is checked against is what crosses, not who moved it.

- **Outbound: the contents of one report file, and nothing else ever leaves by this route.** Named as `Reporting a problem` holds them and not restated: the user's own sentence, verbatim; the diary slice, which holds **file paths, folder names, scene names, machine names and usernames** deliberately (N3) and never the contents of any file of the user's (N2); the report's completeness statements and its stated trim (S4, S5); and, where the report names a job whose server is reachable at the cut, that machine's journal tail and its note on that job (G1–G3). **The user's.**
- **Outbound: Smoozy's own version and which operating system it runs on** — `Desktop app and delivery` E11's two values, the same pair the update request already carries and no wider. **Smoozy's own.**
- **What is barred from the file is barred at the write and not at the cut** — no stored value or part of one, no host key or fingerprint, no machine environment ([Section 13](#13-logging-redaction); `Reporting a problem` N1, N2). The report cut performs no filtering of any kind, so a value that may not leave was never written down.
- **Nothing crosses back into Smoozy.** There is no reply path in the application, no ticket, no account, and nothing Smoozy reads from any mailbox. A written report file is the user's, exactly as a downloaded output is (`Reporting a problem` V9); the Creator answering is mail between two people and reaches no part of Smoozy.
- **The Row 278 ruling**, on [Section 1.1](#11-what-the-sentence-means-and-what-it-does-not)'s own test and no new one. The user opened and holds their own mail account, and Smoozy puts nothing anywhere. So the report's crossing is **inside Row 278's boundary rather than a second exception to it**, on the same argument [Section 1.1](#11-what-the-sentence-means-and-what-it-does-not) already makes for a rented server, for Telegram’s service. **Nothing about Smoozy sending anything is granted by this entry** — B1 and V10 are the floor and the ceiling, and nothing here softens either.
- **What the ruling does not soften, stated rather than glossed.** Once the user has sent it the file is out of their hands, and Smoozy can neither recall it nor know it was sent — it holds no list of reports made (`Reporting a problem` V9). The whole of the bound on this crossing is therefore **what may be in the file at all**, which is why that bound is enforced at the write.

### 1.3 The inbound boundary at a rented server

**B24. The ordinary case is that no rented server binds an inbound endpoint at all.** Fact 63's boundary half is answered and the answer is provider-shaped: a webhook works where a provider permits one, **a URL naming a Vast container's own mapped port is refused because the provider chooses the number, and a Vast virtual machine was not tried** (narrowed 2026-08-21 — this said *no Vast container rental can host one whatever it is rented as*, which reads a fact about one address as a fact about a machine; Telegram's page constrains the URL and says nothing about the machine), and it is therefore a **provider-dependent extra, not something Smoozy can rely on**. ~~The rest of the fact — the POST wrapper, the secret-token header and the retry cadence — is still owed~~ **The rest of the fact is one item rather than three — corrected 2026-09-02.** The POST wrapper and the `X-Telegram-Bot-Api-Secret-Token` header were **answered by reading** Telegram's own *Bot API* page that day, so **this boundary now carries a documented authentication and no longer waits on one**; the retry cadence alone stands open, no reading will ever close it, and it is not shut either ([Section 14](#14-unresolved), item 12). Observed — a Vast.ai container rental asked for all four ports Telegram accepts was given `45104`, `45181`, `45149` and `45191` instead; the mapped port was genuinely reachable from outside and answered a self-signed HTTPS request; and Telegram still refused it: `Bad Request: bad webhook: Webhook can be set up only on ports 80, 88, 443 or 8443` ([One box](One%20box%20—%20the%20Telegram%20capture%20and%20the%20port%20that%20cannot%20be%20chosen.md), Fact 63). Observed on a second provider — inbound was closed by default by an OpenStack security group the machine itself could not change, and a webhook then worked with no domain name, no certificate authority and nothing bought ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 63).

**B25.** So the boundary is written as follows, and **no document may harden it further in either direction**:

- **Default and ordinary case.** No Smoozy component on a rented server binds a listening socket reachable from outside the machine. The machine-local endpoint of [Section 8](#8-the-supervisors-machine-local-endpoint) is not such a socket.
- **The one exception, where a provider permits it.** Only the machine currently holding the registered Telegram webhook binds an internet-reachable endpoint. No other prepared server binds one. That endpoint belongs to the Telegram worker alone, authenticates every request, and reaches the supervisor only through the worker's existing command route — never directly. `Telegram` owns whether the route is taken at all; this document owns the boundary it is allowed to occupy.
- **No rental becomes ineligible for Smoozy or for Telegram because it cannot host one**, and no promise anywhere may be written so that it needs one.

**B26. Two observed properties of that exception, for whoever writes it.** Registering a webhook proves nothing about reachability — Telegram accepted a registration for a completely unreachable address, and the healthy and unreachable answers are byte-identical except for an error field that appeared within sixteen seconds. And a single `409 Conflict` covers both *a poll while a webhook is registered* and *two pollers competing*, distinguishable only by the description text ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 63; [One box](One%20box%20—%20the%20Telegram%20capture%20and%20the%20port%20that%20cannot%20be%20chosen.md), *Two holders do not race*).

### 1.4 Inside the desktop application

**B27.** There is one boundary inside the process and it is narrow. **A stored secret's plaintext exists at three hops and nowhere else**, and each hop holds it for one use only — *the word* stored *was added on 2026-08-25 with the origin clause below, because all three hops are a route out of the store and a value the user has just typed has never been in one, which made this sentence read as forbidding the field the user types into*:

1. **The platform secret-store adapter** named in [Section 3](#3-the-secret-store-on-each-system), for the length of the call that asked for it.
2. **The one-use broker that delivers the value to the endpoint** — the component that starts the askpass helper, that runs the elevating command, or, where the endpoint is inside this process, that hands the value to the transport's own key-loading step — for the length of that one delivery. **Widened 2026-09-02 with [§4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) R0 and hop 3's correction of the same day**, which were made together and left this hop reading *the one-use broker that opens the channel to the endpoint*, naming only the two brokers that cross a process boundary — so a connection's passphrase had a first hop, a third hop and nothing between them, while [B29](#14-inside-the-desktop-application) routes a typed value to *the one-use broker* on every route. **Where the delivery crosses no process boundary there is no channel to open and none is invented:** the broker is still one component, still holds the value for one delivery, and still holds it for nothing else. **The count of three is untouched and a fourth hop is still a fault.**
3. **The final endpoint that consumes it**: the askpass helper's own channel for a key passphrase, or the elevating command's standard input on the rented machine for a machine password ([Section 4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it)). **A key passphrase has two such endpoints and the list is closed at two — corrected 2026-09-02 with [§4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) R0.** The askpass helper's channel is the endpoint where the consumer is a **local tool read** — `Keys` G3's generation and S5's one `-y` load — and it is unchanged. Where the consumer is a **connection**, the endpoint is the transport's own key-loading step in Smoozy's process ([§4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) R2), which is a hop that opens no channel and starts no process. **The count of three is untouched and a fourth hop is still a fault**, so `Desktop app and delivery` S8 and its P3 closed list of two helpers both stand.

**B29. A secret the user is entering has an origin, and the origin is not a fourth hop. Added 2026-08-25, routed by the runner from [Keys](Keys.md#13-unresolved) §13 item 18.** The three hops above are the route a **stored** secret's plaintext takes **out of** the store, and a passphrase or machine password the user has just typed has never been in it — which [§3.0](#30-the-contract-every-system-implements) rule 6's third bullet acknowledges in as many words without saying where such a value lives. **The field the user enters it into is that value's origin**: it holds the plaintext for the length of the entry and until the act that raised the ask ends, and it is neither a hop nor an extension of the list. `Desktop app and delivery` S8's *a builder that needs a fourth has found a fault* is unchanged, and is about a fourth **hop**. **From the first destination onward the three hops govern in full**, whichever of the two the act reaches first: the one-use broker, for that attempt's one delivery, and the adapter's **put** where the value is to be remembered — and nowhere else (`Keys` S17). **Three rules bind the origin itself and not one of them is new.** It is never a process argument and never an environment value ([Section 13](#13-logging-redaction) rules 1 and 2). No feature module receives it as a value it may keep, nothing draws it, and nothing writes it into the local record. And it is discarded when the act ends however it ends, put or not put — [Section 2](#2-the-five-held-things) items 3b and 3c’s arrangement, keyed to the act. **What that costs nobody:** the value is one the user is holding already, so no store is reached, nothing is asked twice, and the box the design draws is buildable.

**B30. No feature module receives a stored secret as a value it may keep**; a module receives either a use of the secret carried out on its behalf, or a handle it can present again. Nothing outside those three hops and the origin above receives a plaintext at all, and none of the three retains one past the use it was opened for. *(The origin was added to this sentence on 2026-08-25 with the clause above, which is the whole of what it admits: a value the user has typed, before it has reached anything. The hop count is unchanged, and a fourth hop is still a fault.)* `Desktop app and delivery` owns the adapter, the helper and the module API boundaries; this document owns the rule and does not choose their implementation.

## 2. The five held things

**Constraint:** Row 278 — *"How each of those is kept safely is Architecture's, and it is one question rather than five."*

**H1.** One arrangement covers all five. The differences between them are which store, what the item is keyed by, what erases it, and — for some of them — whether they are stored at all.

| # | Thing | Where the value lives | Keyed by | Erased by |
|---|---|---|---|---|
| 1 | **SSH private key half** | Not Smoozy's to keep. The file stays where the operating system keeps keys or where the user pointed Smoozy at it. Smoozy holds a **path** and a **fingerprint**, never the contents. | the local key identifier | `Keys` deleting or removing the key (Rows 247, 251, 252) |
| 2 | **Key passphrase** | secret store, across restarts | the local key identifier | the key being deleted or removed; the user clearing it; the fingerprint at that path changing; the passphrase ceasing to work |
| 3 | **Machine password**, *remember it* | secret store, across restarts | the local server identifier | server edited and cleared; username changed; server removed; the password ceasing to work |
| 3b | **Machine password**, *while this connection lasts* | process memory only, never written to any store or file | **the connection**, not the connected period | that connection ending however it ends — the user disconnecting, the connection dropping, or the application closing. A connection Smoozy replaces underneath a standing connected period is a new connection and inherits nothing |
| 3c | **Machine password**, *do not remember it* | process memory only, for the one action | the action | the action ending, success or failure |
| 5 | **Telegram bot token** | secret store on the user's computer, **and a copy on every machine the Telegram role was placed on** | fixed, one item on the desktop; per machine on the server side | on the desktop, the token being replaced (E14; switching Telegram off erased it too until 2026-10-31); on a machine, [Section 10](#10-what-smoozy-leaves-on-a-rented-machine) |
| 6 | **Machine's remembered identity** | the local record, **not** the secret store — a host public key is not secret | the local server identifier | the server being removed; the host or port being edited; the user accepting a changed identity |

**H2. Item 6 is deliberately not in the secret store.** It is public material and it is comparatively large; the Windows store's documented per-credential ceiling is 2560 bytes (documented — `CREDENTIAL` structure, `CRED_MAX_CREDENTIAL_BLOB_SIZE` is `5*512`; Fact 38, [The manuals](The%20manuals%20—%20keys,%20secrets,%20and%20what%20cannot%20be%20told%20apart.md)), and spending that budget on non-secret material would be wrong even where it fits. It is protected by [Section 9](#9-the-local-record) instead, and it is never shown ([Section 5.4](#54-nothing-puts-a-fingerprint-or-a-host-key-on-a-screen)).

**H3. Items 3b and 3c are the things that are held and never stored.** [Whole app](../Specs/Whole%20app.md)'s Security concern says the middle choice dies with the sitting *"however it ends — the user disconnecting, the connection dropping, or the app closing"*, and neither Windows' `CRED_PERSIST_SESSION` nor Linux's session collection delivers that: both are documented against the **logon session** rather than the application, and Windows' is unresolved for whether it touches disk at all (Fact 38, [The manuals](The%20manuals%20—%20keys,%20secrets,%20and%20what%20cannot%20be%20told%20apart.md), *Windows — session-only*; *Linux — session-only*). macOS documents no such facility at all. So the one arrangement that exists on all three is process memory the application itself discards, and that is what is used. It also matches the spec exactly, which the session facilities do not.

## 3. The secret store on each system

**Constraint:** Fact 38, answered 2026-08-16 ([The manuals](The%20manuals%20—%20keys,%20secrets,%20and%20what%20cannot%20be%20told%20apart.md)); and the Creator's ruling of 2026-08-16 now written into [Whole app](../Specs/Whole%20app.md)'s Security concern, which settles what the user meets. Written three times per Row 282. The adapter itself is `Desktop app and delivery`'s to build.

### 3.0 The contract every system implements

**S1.** Five operations, and no others: **put**, **get**, **erase**, **probe**, and **enumerate the subjects this application has stored**. Every item is identified by a pair — a **kind** and a **subject**, which is an opaque identifier issued by the local record. **The three user-secret kinds form a closed set**: the key passphrase, the machine password and the bot token. A separate `StoreProbe` kind and reserved subject serve only S24’s throwaway probe. Those are the three rows of [Section 2](#2-the-five-held-things) whose value lives in the store; the copies of the token on rented machines are not items in this store, and no other row of that table is one.

**S2. Two of the five operations are not the same on all three systems, and neither is given a route here from anywhere but the documented ground the rest of [Section 3](#3-the-secret-store-on-each-system) rests on.**

- **Enumerate.** On Linux it is a search on this application's own attribute set, and the result is already split by the state each item is in — documented: *"The matched items will be returned in two sets. The `unlocked` return value will contain the object paths of all the items that are not locked. The `locked` return value will contain object paths of items that are locked, which can be unlocked if desired"* (Fact 38, [The manuals](The%20manuals%20—%20keys,%20secrets,%20and%20what%20cannot%20be%20told%20apart.md)). **On macOS it is `SecItemCopyMatching` with the match limit set to all, and on Windows it is `CredEnumerate` with a name-prefix filter** — both sourced, at [Section 3.1](#31-macos) and [Section 3.2](#32-windows), and [Section 14](#14-unresolved) item 13 is closed on them. **The narrowing must not be lost: each enumerates by a name filter, not by application**, which is what the prefix scheme gives and is not a per-application boundary. *(Corrected 2026-08-22, and the ruling is 2026-08-20's: this bullet said **on macOS and on Windows no page read names the call that returns what this application has stored** and pointed at item 13 as an open record, while §3.1, §3.2 and item 13 in this same document had already been corrected.)*
- **Probe.** It is a **Linux member of the contract**, which is what [Section 3.3](#33-linux) treats it as and the only system where it has a mechanism. It answers *is there somewhere to remember at all*, which is the question only Linux leaves open; nothing on macOS or Windows waits on it.

**S3.** Six rules bind the contract on all three systems:

1. **The subject is opaque and carries nothing about the user.** Never a host, a port, a username, a file path, a key comment or a fingerprint. The reason is documented and Linux-specific: the Secret Service specification states that *"The lookup attributes are not treated as secret material, and the service may choose not to encrypt attributes when storing them to disk"*, and libsecret's own page repeats that implementations *"will probably store attributes in an unencrypted manner"* (documented; Fact 38). An attribute set naming the user's servers and keys would be a plaintext inventory of them beside the encrypted secrets.
2. **No secret is ever passed as a process argument or placed in an environment value.** [Section 13](#13-logging-redaction) states why and what carries them instead.
3. **Every call is made off the thread that draws the interface.** Documented — `SecItemAdd`'s own page: *"`SecItemAdd` blocks the calling thread, so it can cause your app's UI to hang if called from the main thread"*, and the identical paragraph appears on `SecItemCopyMatching`, `SecItemUpdate` and `SecItemDelete`. Observed on the Creator's Mac: a `SecItemCopyMatching` with user interaction left allowed **did not return within 45 seconds and was killed**; whether it would ever have returned is not established (Fact 38). Linux says the same from the other side: *"A service may lock previously unlocked items for any reason at any time"* (documented).
4. **A get that fails is never treated as *the secret is wrong*.** It is classified into *not there*, *locked or refused*, or *store unavailable*, and only *not there* means the user is asked again as though nothing was remembered. The three are separable to different degrees per system, below. **The other two classes have one behaviour and it is stated here rather than left to the caller: they are ordinary failures, not secret failures.** Smoozy reports that it could not reach what it remembered, on the thing that failed, under [Whole app](../Specs/Whole%20app.md)'s *How a failure reaches the user*, and it offers the action again. **It does not ask the user for the secret, and it does not forget it.** Asking would be something to type at a moment no spec grants; forgetting would discard a secret that is present and readable at the next attempt.
5. **No store call is waited on without a deadline.** A call that does not return within it is classified as **store unavailable** — never as *not there*, which would ask the user for a secret the store may still hold. **What the user is told depends on the operation. Amended 2026-09-14 by the build runner, under the standing delegation; the reasoning is `Audits/Architecture/Security and licence/Decisions record.md`'s entry of that date.** A **get** that times out is an action that did not happen. A **put** or an **erase** that times out is reported as **not confirmed** and never as done, because a call past its deadline can still land and no deadline can take it back; **the next read decides what is held.** A put under a subject nothing yet records is undone if it lands late, since nothing points at it. **A put that replaces a value already held under the same subject is not undone if it lands late**: the old value is gone the moment it lands, so undoing it would leave neither, and the value that landed is the one the user just gave. This is a rule about how long Smoozy waits, not a claim about what any store does when it blocks; what the one observed blocked call was waiting on is [Section 14](#14-unresolved) item 14's and is unresolved, and **on Linux the deadline is not yet kept at all** — item 18.
6. **A value that came out of the store goes to the thing that consumes it and to nothing that draws. Added 2026-08-21, per Row 334.** No screen, notification, message, exported record or log carries a stored value or any part of one, and **no get is ever performed in order to compose something to show**. This is the shape [Section 5.4](#54-nothing-puts-a-fingerprint-or-a-host-key-on-a-screen) already has for a host key, written for the three stored user-secret kinds, which until now had no rule of it at any surface. Three consequences, each of them something a screen would otherwise do:
   - **That an item is remembered is answered from the local record's own subject, never by a get.** The (kind, subject) pair is the local record's and its presence is the whole of what a screen may say about a held secret. **§4's *read at the moment of use and not before* is what this keeps true** — a get made to draw is a use that nothing needed.
   - **A mask drawn to a fixed shape is a drawing of *remembered* and is permitted; a mask that preserves any part of the value, its length included, is the value.** **Nothing anywhere supplies a display fragment of a stored secret** — not the local record, not [§1.2](#12-the-domains-and-the-complete-crossing-list)'s check response, not the store — so a screen that wants one is asking for a record no document holds.
   - **A value the user is entering has not come out of the store and this rule does not reach it.** What such a field shows while it is being typed is Design's; from the put onward the value is the store's and the rule binds.

### 3.1 macOS

**S4. Store: the file-based keychain, reached through the `SecItem` API.** Documented — Apple's TN3137: *"macOS has two keychain implementations: File-based keychain [and] Data protection keychain"*, and *"The `SecItem` API can target either implementation. It defaults to targeting the file-based keychain."* Entry points `SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, `SecItemDelete`; observed on the Creator's Mac that the Security framework loaded and all four resolved with nothing installed (Fact 38).

**S5. The data protection keychain is not used.** Documented — TN3137: reaching it requires entitlements which *"must be authorized by a provisioning profile. Your program needs an app-like bundle structure in which to embed that profile"*, and it *"is only available in a user login context."* Whether a Developer ID application shipped without an embedded profile can reach it is **unresolved** (Fact 38, unresolved 3), and two runs on the same machine disagreed about whether a write from a process without the entitlement succeeds or returns `errSecMissingEntitlement` (Fact 38, unresolved 6). Nothing here rests on either. **That second one is permanently unresolved, ruled 2026-08-31: nothing recorded distinguishes the two runs, no side is picked, and it will not be re-run. Guard — the struck claim that every unentitled write is refused must never be quietly recovered here or anywhere downstream.** One write succeeded and had to be cleaned up, and that observation stands whatever caused the two runs to differ.

**S6. What the file-based keychain buys and what it costs.** Access is governed by per-item access lists. Documented — *"Otherwise, the system prompts the user for confirmation. The user may choose to Deny, Allow, or Always Allow the access."* Observed: the binary that created an item read it back silently with no dialog and no delay; a **different** binary reading the same item with user interaction disallowed was refused with `errSecAuthFailed` (Fact 38, *Observed — macOS only*; that this is ACL membership rather than some other cause is inferred, since the item's ACL was never read). **That is the per-application boundary macOS has and the other two systems do not.** Its cost is the dialog the ruling already accepts: documented — *"If an app is changed or infected by a virus after being granted access to your keychain, the app is no longer trusted, and you must grant access again. … This dialog appears if you recently updated your system software or the app, or if the app has been modified."* The same page also says *"You must sometimes reauthorize updated apps"* — **sometimes**, not on every update, and no source read says which updates trigger it. So `Desktop app and delivery` must treat the post-update dialog as an ordinary outcome of its own updater rather than as a failure path, without predicting when it appears.

**S7. Refused, missing, lost.** `errSecItemNotFound` is *not there*; `errSecUserCanceled` is the user refusing; `errSecInteractionRequired` is the keychain locked with interaction disallowed; `errSecNoSuchKeychain` and `errSecInvalidKeychain` are the store absent or unusable (documented, from Apple's one-line descriptions). **Unresolved:** that a **Deny** click returns `errSecUserCanceled` specifically is stated by no page read (Fact 38, unresolved 4). The numerals are documented — Apple's own shipped `SecBase.h`, read 2026-08-20 (Fact 38, unresolved 5, closed 2026-08-21), and all five of these symbols re-read there 2026-08-23 — and **the adapter maps by symbol and never by number regardless**, because a symbol is what the pages name. Any unmapped status is treated as *store unavailable* rather than as *not there*: an unknown status must never be read as permission to ask the user for the secret again.

**S8. Lost.** Documented — a login password **reset** destroys the keychain contents: *"If the login password was reset because the user forgot the old password, the keys, passwords, and other information in the keychain won't be accessible, and the user will need to create a new keychain."* That is the loss the ruling already accepts. Smoozy meets it as a store that returns *not there* for every item and asks for each as though new; nothing else is lost, because [Section 9](#9-the-local-record) keeps no secret in the local record and the local record survives.

**S9. Synchronisation is off.** Items are written without `kSecAttrSynchronizable`, so nothing goes to the user's other devices. Documented — *"Updating or deleting items using the `kSecAttrSynchronizable` key affects all copies of the item, not just the one on your local device."* Note also that `kSecAttrAccessible` is honoured on macOS only in the data protection world, so no accessibility class is relied on here.

**S10. Erasure is confirmable.** `SecItemDelete` returns a status and a subsequent query returns `errSecItemNotFound`; observed end to end on the Creator's Mac (Fact 38).

**S11. Enumerate is `SecItemCopyMatching` with the match limit set to all — sourced and observed on 2026-08-20, having been recorded as having no entry point at all until then.** Documented, from Apple's own `SecItem.h` shipped on this Mac at `/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk/…/Security.framework/Versions/A/Headers/SecItem.h`, dated 25 April 2026 on disk: *"By default, this function returns only the first match found. To obtain more than one matching item at a time, specify kSecMatchLimit with a value greater than 1. The result will be a CFArrayRef containing up to that number of matching items."*, and *"kSecMatchLimitAll Specifies that an unlimited number of results may be returned; used as a value for the kSecMatchLimit dictionary key."* **Observed** on a throwaway keychain file in a scratch area, never the Creator's login keychain: three items stored under one service name, the all-limit search returned **3** at status 0, the one-limit search returned a single dictionary, and a never-stored service returned `-25300` (`errSecItemNotFound`) as the control. **The narrowing matters and must not be lost: this enumerates by attribute, not by application.** The boundary is the service-name prefix Smoozy already adopts, which is a naming convention rather than an operating-system guarantee.

### 3.2 Windows

**S12. Store: Credential Manager, credential type `CRED_TYPE_GENERIC`, reached through `CredWriteW`, `CredReadW` and `CredDeleteW` in `Advapi32.dll`.** Documented, and **documentation alone — no Windows machine has run it, and none is rented today** (Fact 38; Row 282's Windows limit).

**S13. The whole documented guarantee is one sentence:** *"The credential will be stored securely but has no other significant characteristics."* What *stored securely* means comes from a different page: *"These credentials are stored on the hard disk drive and protected by using the Data Protection Application Programming Interface (DPAPI). Any program running as that user will be able to access credentials in this store."* That page is archived and dated 2016-08-31, and whether the sentence still holds for current Windows is **unresolved** (Fact 38, unresolved 11). It is nevertheless the sentence the Creator's ruling was made against, and the ruling accepts it.

**S14. There is no per-application boundary, so there is nothing to grant and no refusal state.** No page read documents any prompt on `CredWrite`, `CredRead` or `CredDelete` for the generic type. `ERROR_NOT_FOUND` is *not there*; `ERROR_NO_SUCH_LOGON_SESSION` is the only documented *store unavailable*; **no refusal state is documented at all**, which is consistent — nothing asks, so nothing can be declined.

**S15. DPAPI is not used as a second layer, and the reason is exact.** Documented — DPAPI *"merely applies cryptographic protection to the data. It does not store any of the protected data"*, and *"all applications running under the same user can access any protected data that they know about"* unless the application supplies secondary entropy, which is itself something the application must keep. An application-kept entropy value on the same disk, readable by the same user, moves the secret one step and protects it against nobody the ruling has not already accepted. **This is the same argument that decides [Section 9](#9-the-local-record).** A second reason not to lean on it: documented — *"the specific error code returned when tampering is detected may vary … Applications should not rely on a specific error code to detect data tampering"*, so a DPAPI blob that fails to decrypt cannot be classified from its error at all.

**S16. Persistence is `CRED_PERSIST_LOCAL_MACHINE` for every one of the three user-secret kinds, and the other two documented values are forbidden for them.** Documented — `CRED_PERSIST_LOCAL_MACHINE` is *"visible to other logon sessions of this same user on this same computer and **not visible to logon sessions for this user on other computers**"*; `CRED_PERSIST_ENTERPRISE` is visible *"to logon sessions for this user on other computers"*; `CRED_PERSIST_SESSION` *"will not exist after this user logs off and back on"* (Fact 38, [The manuals](The%20manuals%20—%20keys,%20secrets,%20and%20what%20cannot%20be%20told%20apart.md)). All three user-secret kinds are held across restarts, which rules the session value out. And the enterprise value would put a key passphrase, a machine password or the bot token on another computer, which is the boundary Row 278 draws and which [Section 3.1](#31-macos) refuses on macOS by leaving `kSecAttrSynchronizable` unset. **This is documentation and not observation**, and [Section 14](#14-unresolved) item 8's Windows label covers it as it covers every other claim in this section.

**S17. Naming and size.** Target names are prefixed as Microsoft asks — *"Microsoft suggests the name be prefixed by the name of the company implementing the service"* — and carry the kind and the opaque subject and nothing else. Each blob is at most 2560 bytes.

**S18. Erasure.** `CredDelete` returns TRUE or FALSE. That a following `CredRead` returns `ERROR_NOT_FOUND` is **inference, not citation** (Fact 38), so the adapter treats a TRUE return as the confirmation and does not require the read-back it requires on macOS.

**S19. Enumerate is `CredEnumerate` with a prefix filter, and it is documented — the candidate was struck in Fact 38 on the ground that no page had been read, and the page was read on 2026-08-20.** Microsoft's own reference at `https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credenumeratew`, page metadata `updated_at: 2024-11-20`: *"The **CredEnumerate** function enumerates the credentials from the user's credential set. The credential set used is the one associated with the logon session of the current token."* On the filter, which is the half the prefix scheme needs: *"Pointer to a **null**-terminated string that contains the filter for the returned credentials. Only credentials with a *TargetName* matching the filter will be returned. The filter specifies a name prefix followed by an asterisk. For instance, the filter \"FRED\\*\" will return all credentials with a *TargetName* beginning with the string \"FRED\"."* Its Requirements table gives **Library `Advapi32.lib`, DLL `Advapi32.dll`** — the same library already named for the other three calls. **Documentation alone, like everything else in this section**, and it carries the same narrowing as macOS: the filter is a name prefix and not a per-application boundary, which on Windows is doubly true, since the section above already records that there is no per-application boundary at all.

**S20. Lost.** Documented — DPAPI master keys are re-encrypted on a password **change**, and there are domain and Password Reset Disk recovery paths for a reset. What happens after an administrative reset on a standalone machine with no such disk, and the whole picture for Microsoft-account and Windows Hello logins, is **unresolved** (Fact 38, unresolved 10). Smoozy needs no answer: any outcome in which the items cannot be read presents as *not there* or *store unavailable*, both of which the contract already handles.

### 3.3 Linux

**S21. Store: the Secret Service, on the session D-Bus at `org.freedesktop.secrets`, through libsecret.** Documented, and **documentation alone — no Linux computer exists on this project** (Fact 38).

**S22. There is no single answer and the specification says so.** Documented — the Secret Service API is a **draft**, and it states outright: *"This specification does not mandate the use of master passwords to lock a collection of secrets"* and *"This specification does not mandate any form of access control."* Its "Notes for Service Implementors" chapter reads, in its entirety, *"[TODO: complete]"*. **So what a secret is protected against on Linux is whatever the installed implementation does, and Smoozy does not claim more.** GNOME's daemon *"is normally started automatically when a user logs into a desktop session"*; KDE's current split puts `ksecretd` behind the same interface; KeePassXC can replace both, exclusively, by the user's own choice.

**S23. The load-bearing case is a computer with nowhere to remember**, which is the case the Creator's ruling writes a promise about. **Unresolved, narrowed:** the specification's three errors and libsecret's nine-member enum name no *no-provider* error, and that stands — D-Bus's `ServiceUnknown` and GIO's `NameHasNoOwner` do, and **which of the two arrives, and what arrives with no session bus at all, is not established** (Fact 38, unresolved 13, narrowed 2026-08-21). *Whether any provider runs on a machine with no desktop session* is answered for the image this project rents — Ubuntu's own published server-image manifest carries no provider and not even the client library (Fact 38, unresolved 14, closed 2026-08-21) — and a machine somebody has added a provider to is a different question.

**S24. That unresolved fact is designed around rather than waited on, and the design does not claim to settle it.** *Is there somewhere to remember* is answered by a **probe**, not by an error code: the adapter writes a throwaway item under the `StoreProbe` kind and a reserved subject, reads it back, and erases it. **What a probe establishes is whether a round trip worked, and nothing beyond that.** Whether a failed round trip was no service reachable on the bus or a service reached that refused or locked is exactly what Fact 38's unresolved 13 leaves open, and this document does not claim the probe separates them; [Section 14](#14-unresolved) item 7 records what that costs.

**S25. So the reading taken is the one that does not lie about the store.** A probe that has **never succeeded in any run** is what drives the promise's one-sentence notice and makes Smoozy ask each time. A probe that succeeded once and later fails is a **failure and not a change of arrangement**, reported under rule 4 of [Section 3.0](#30-the-contract-every-system-implements) like any other *locked or refused* or *store unavailable*. The two mistaken readings are opposite lies to the user — a store that exists reported as nowhere, and nowhere reported as a passing failure so the notice never appears — and this rule is what keeps a single failed round trip from producing the first of them.

**S26. When the probe is taken, and what *first use* means.** It is taken at the first moment in a run when a secret is actually needed, and **not at application start**: reaching the store may prompt (*erasure* below), and at start nothing is being handed over. *First use* means first use **in this run** — the result is re-taken rather than cached across application runs, because a user can install a keyring between two sittings, and it is not re-taken again within one.

**S28. Locking is not assumed away.** Documented — *"A client application should always be ready to unlock the items for the secrets it needs … It must not assume that an item is already unlocked for whatever reason. A service may lock previously unlocked items for any reason at any time."* A locked item is `SECRET_ERROR_IS_LOCKED`, or arrives in the `locked` set of a search, and is therefore separable from absent. **A locked store is never reported to the user as an empty one.**

**S29. The user being asked for a password by their own keyring is that computer's arrangement and not Smoozy's**, exactly as the spec says. Where the implementation prompts, the application drives the `Prompt` object itself rather than leaving it to a helper — documented as the only way *"Either the user or the client application can dismiss a prompt"* is distinguishable at all, through the `Completed` signal's `dismissed` argument.

**S30. The session collection is not used.** Documented as memory-only by GNOME alone; **unresolved** for `ksecretd` and KeePassXC (Fact 38, unresolved 16). Items 3b and 3c stay in process memory as [Section 2](#2-the-five-held-things) states.

**S31. Erasure.** `secret_password_clear` reports whether anything was removed, but deletes **unlocked** items only. Erasure therefore unlocks first, which may prompt, and an erase that could not unlock is reported as an erase that did not happen rather than one that did.

**S32. The store's standing, and it is what makes *never succeeded in any run* executable at all. Added 2026-08-21, answering Row 316.** As written, this section's conservative rule read across runs while the probe result is **run-held** (§11.1) and `Desktop app and delivery` S5 re-takes it once per run and caches nothing — **so the two sentences could not both be carried out**, and the rule that stops a single failed round trip reporting a store as *nowhere* had nothing to stand on. **What stands under it now is one durable value in the local record, `the store's standing`, with three readings and one writer:**

| Reading | Written when | What it means |
|---|---|---|
| ***never probed*** | the value's absence at first launch | no probe has been taken on this installation |
| ***never answered*** | the first probe of this installation fails | a computer with nowhere to remember, until something proves otherwise |
| ***has answered*** | any probe succeeds, ever | the store exists here; every later failure is an ordinary failure under [3.0](#30-the-contract-every-system-implements) rule 4 and **never returns the standing to *never answered*** |

**S33. It is a note Smoozy wrote about its own history and not a cached store reading**, which is what keeps it inside `State, identity and recovery` §1.1's one store and away from D4: nothing reads it in place of taking the probe, and the probe is still taken at first use in every run exactly as above. Lifetime class **user-held** (§11.1), beside settings; **no control removes it**, and that is deliberate — clearing it would offer to tell the user again about a thing that has not changed.

**S34. And *it says so once* is that value's first transition and nothing else.** The one-sentence notice is shown at the moment the standing goes from *never probed* to *never answered*, once for the life of the installation. **Not once per run**, which is what the promise's own subordinate clause — *so the user knows it is not going to learn rather than thinking it keeps forgetting* — exists to prevent, and which is the only thing a run-held result could have delivered. It is Smoozy's own notice rather than a warning the user suppressed, so it takes no row in the suppression table (`State, identity and recovery` §10.3; that table is `Desktop app and delivery` §15.2 G4's module-and-warning identity and nothing else).

**S35. One named cost of rule 4 stated rather than left to be met.** A user who had a keyring and removes it leaves the standing at *has answered* for ever, so every later run reports an ordinary store failure and the once-only notice never appears for them. **That is rule 4 working as written** — a store that answered once is not re-classified as nowhere by any number of failures — and the alternative reopens the first of the two opposite lies this section exists to prevent. [Section 14](#14-unresolved) item 7 already carries what the probe cannot separate.

**S36. The third machine-password choice is not offered where the standing is *never answered*.** [Whole app](../Specs/Whole%20app.md) offers *Don't save*, *While connected* and *Save*, and the ruling of 2026-08-16 covers all five held things. On such a computer the third would behave exactly as the first, and **offering it is the pretence the promise forbids in as many words** — *does not pretend to remember*. So the offer is composed after the probe, from the standing: two choices where it reads *never answered*, three otherwise. The second choice is unaffected in every case, being process memory ([Section 2](#2-the-five-held-things) item 3b) and needing no store at all. **Nothing is silently substituted and no choice does something other than what it says.**

**S37. Transport.** Secrets cross the session bus. Documented — the specification's own warning that its transport encryption *"is not envisioned to withstand man in the middle attacks"*, and that *"The `plain` algorithm is almost always supported."* The negotiated encrypted algorithm is used where the service offers it and the plain one where it does not; neither is claimed to defend against a process that already has the user's session bus.

## 4. Reaching a secret, and giving it to the thing that needs it

**Constraint:** Row 244 (`Keys`, the passphrase), Row 37 (`Servers`, the remembered identity), Row 263 (`Telegram`, the token), and [Whole app](../Specs/Whole%20app.md)'s three machine-password choices. Facts 35 and 37 bound what can be done with an SSH key without its passphrase. **And [Servers](Servers.md#21-the-break-reporting-mechanism) K1, which this section was written against the opposite of until 2026-09-02:** *"The connection is held by the SSH transport Smoozy itself drives … the mechanism below is Smoozy's own and not a flag handed to a tool."*

**R0. Which of the two makes the connection was decided against this section and it is not reopened here. Corrected 2026-09-02, on the architecture runner's ruling of that date: `Servers` K1 stands and this section's prescription did not.** This section described the connection as an invocation of the standard SSH client configured by command-line options and environment values — the askpass route, `SSH_ASKPASS_REQUIRE`, `BatchMode=yes`. **Nothing else in the stage is built that way**: `Servers` 1.4's two connections at a low cap, `Server protocol and transfers` [R4](Server%20protocol%20and%20transfers.md#82-the-enforcement-point-is-smoozys-own-byte-loop-and-the-evidence-forced-it) and R5's byte loop driven directly against the server's own file-transfer subsystem, T5's per-connection session pool, K2's caller-side keepalive, and `File Browser` L3a's channel leases are each expressible only as a transport Smoozy holds, and R4 states outright that an external tool's flag *cannot* be the enforcement point. **So the connection is made by the SSH transport Smoozy drives, in Smoozy's own process, and no `ssh`, `sftp` or `scp` invocation makes one.** **Every requirement this section stated is kept and none is weakened** — each is restated below as a property of that transport, and in three places the transport makes the requirement structural where a flag only made it likely. **What the correction does not reach:** the **local** tool reads `Keys` makes on the user's own computer — a listing, a fingerprint, a container probe, a verification, a generation, and the one `-y` load of [R6](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) — which are invocations of `ssh-keygen` and stay exactly as written, askpass route included. **The line is *a connection* against *a local read*, and it is the line every clause below draws.**

**R1. A stored secret is read at the moment of use and not before.** Nothing pre-loads the store at start-up, and nothing keeps a plaintext in a module. A passphrase read to open a connection is discarded when that connection attempt ends, and read again for the next one; the *held across restarts* promise is a property of the store, not of the process.

**R2. A key passphrase goes to exactly one consumer per use, and which consumer it is depends on whether the use is a connection or a local read. Corrected 2026-09-02 under [R0](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it); this clause opened *"A key passphrase reaches the SSH client through the askpass route and never any other way"*, which was true of an external client and is not true of a connection.**

- **For a connection — the transport's own key-loading step, inside Smoozy's process, and no channel at all.** The transport `Servers` K1 names performs the public-key authentication itself, so it unlocks the key it was handed a path to and signs with it. The passphrase is passed to that step as a value in the process that already holds it; **it crosses no process boundary, so it is never an argument, never an environment value, never in a file, and there is no helper and no channel to compromise.** That is the same four prohibitions R2 already carried, made structural rather than configured: a value that never leaves the process cannot appear on any of the four surfaces. **It is discarded when the authentication exchange ends, and a replacement connection loads afresh** ([R1](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it)); nothing is carried across a reconnect.
- **For a local read — the askpass route, unchanged, and this is the half the correction does not touch.** `Keys` [G3](Keys.md#62-the-passphrase-route-row-248) at a generation and its S5 at the one `-y` load run `ssh-keygen` with no terminal, `SSH_ASKPASS` naming the one-use helper and `SSH_ASKPASS_REQUIRE=force`. Documented — `ssh(1)`, `SSH_ASKPASS_REQUIRE`: *"if the variable is set to “force”, then the askpass program will be used for all passphrase input regardless of whether DISPLAY is set"* (Fact 35, [The manuals](The%20manuals%20—%20keys,%20secrets,%20and%20what%20cannot%20be%20told%20apart.md)); observed for `ssh-keygen` on one build (Fact 115). **The helper receives the passphrase over a channel Smoozy opened for that one use — never as an argument, never in an environment value, never through a file**, which is [§1.4](#14-inside-the-desktop-application) hop 3 and is why `Desktop app and delivery` P3's closed list of two helpers is unchanged.

**R2a. What the transport does with the private key's bytes, stated because [§6](#6-the-private-half-of-an-ssh-key) P1 previously said the decryption happened outside Smoozy's process. Added 2026-09-02 with R0.** The transport reads the file at the path it was given, in place, and unlocks it **in memory, for one authentication exchange**. **The promise's three verbs are untouched and still true by construction — the file is never copied, never moved, never sent anywhere** — and four rules bound what replaces the old construction: the decrypted material is **never written to any file, any store, any record or any log**; it is **never a process argument and never an environment value** ([Section 13](#13-logging-redaction) rules 1 and 2); it is **never handed to another module**, which is [§1.4](#14-inside-the-desktop-application) B30 unchanged; and it is **discarded when that exchange ends**, so a second connection re-reads and re-unlocks rather than reusing anything. **What the change costs, said plainly:** the encrypted key material is now decrypted inside Smoozy's process, where before this section claimed it never was, so a fault in Smoozy that could read its own memory reaches a private key it previously could not. **What is bought for it** is the whole of `Servers` K1 and `Server protocol and transfers` R4 — a held connection, a caller-side keepalive, a shared rate budget and a resumable byte loop, none of which an invoked tool can deliver — and the passphrase's four prohibitions becoming structural rather than configured.

**R2b. `ssh-keygen`'s `-P` option, which does put a passphrase on a command line, is not used for anything but a local probe with an empty passphrase** ([Section 6](#6-the-private-half-of-an-ssh-key)). **Unchanged by R0**, and it is a local read. *(Kept as its own clause 2026-09-02 because `Keys` G3 cites it — "§4 closes `-P` to everything but the empty probe" — and it sat inside the sentence R2 replaced.)*

**R2c. The clause R2 replaced, kept whole so no citation of it dangles.** *"A key passphrase reaches the SSH client through the askpass route and never any other way."* Documented — `ssh(1)`: *"If ssh does not have a terminal associated with it but DISPLAY and SSH_ASKPASS are set, it will execute the program specified by SSH_ASKPASS"*, and `SSH_ASKPASS_REQUIRE`: *"if the variable is set to “force”, then the askpass program will be used for all passphrase input regardless of whether DISPLAY is set"* (Fact 35, [The manuals](The%20manuals%20—%20keys,%20secrets,%20and%20what%20cannot%20be%20told%20apart.md)). The helper receives the passphrase over a channel Smoozy opened for that one use — never as an argument, never in an environment value, never through a file. `ssh-keygen`'s `-P` option, which does put a passphrase on a command line, is **not** used for anything but a local probe with an empty passphrase ([Section 6](#6-the-private-half-of-an-ssh-key)). **Its second and third sentences are live and are R2's second bullet and R2b; its first is superseded for a connection only.**

**R3. A connection Smoozy makes on its own must not be able to ask for a passphrase**, which [Servers](../Specs/Servers.md) promises for reconnects and post-edit put-backs. **The construction is the transport itself, and the promise is structural rather than configured. Corrected 2026-09-02 under [R0](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it); this clause read *"The construction is: no controlling terminal, `SSH_ASKPASS_REQUIRE=never`, and `BatchMode=yes`"*, which are settings on a program Smoozy no longer runs to make a connection.** The transport `Servers` K1 names has **no interactive input route of any kind** — no terminal, no askpass program, no prompt — and takes a passphrase only as a value its caller hands it ([R2](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it)). A connection Smoozy makes on its own is handed none, because `Keys` U9's availability answer is what supplies one and `Servers` P3 refuses the attempt where it is *no*. **So there is nothing to prompt with and nothing to suppress**, which is a stronger statement of the same promise than three settings that had to be got right every time. **The three settings are not carried forward as a live construction**, and nothing in this stage now sets `BatchMode`. **This was observed rather than inferred, corrected 2026-08-20 — the *inferred, not documented* label came off with Fact 35 Half B's answer.** `BatchMode`'s own wording still names only *"password prompts and host key confirmation requests"*, so the manual is silent about a private-key passphrase; the behaviour was run instead, on 2026-08-20, against a real server with a terminal deliberately attached and a control either side — the prompt appears twice without batch mode and does not appear at all with it, the server having accepted the key. **What is still undocumented is what the client does when it needs a passphrase and every input route is closed**, and nothing here rests on that. The defence that does not depend on it is the one Servers already requires — Smoozy does not attempt a connection it can see cannot work, and *the key needs a passphrase Smoozy is not holding* is exactly such a case, established without connecting ([Section 6](#6-the-private-half-of-an-ssh-key)). **The prompt-suppressing construction is the second line, not the first.** **Under R0 the second line is gone and the first is unchanged, which is the whole of what the correction costs here.** The Fact 35 Half B run above is kept as a **record of what the standard client does**, because `Keys` §13 item 5 and [§14](#14-unresolved) item 3 both cite it; it is no longer a construction this architecture performs, and **nothing anywhere may be built on `BatchMode` again without a clause saying which tool is being run and why**.

**R4. A machine password reaches the elevating step on the rented machine over the command's own standard input, never as an argument.** **Unchanged by [R0](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it), and made more exact by it: that standard input is a channel Smoozy's own transport opens and writes to on the connection it holds, so no local program stands between the value and the far command.** Observed on a rental: from a second ordinary login, another login's process *"is visible with its owner and command line"* ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 60). A password in an argument on a rented machine is therefore readable by any other login on it. No comparable fact is established for the user's own computer, and none is needed: the rule is the same in both places, so nothing here waits on it.

**R5. Retry behaviour is bounded by Smoozy, not by the tool.** Observed — an `ssh-add` fed a wrong passphrase by an askpass helper made **59 askpass invocations in 12 seconds and was still running when killed**, with no diagnostic; `ssh-add(1)` documents no retry limit (Fact 37). `ssh` itself made three and then stopped, but *"the keyword was never varied, so the two threes are not established as connected"*. So whatever supplies a passphrase supplies it **once** per attempt and reports failure to Smoozy rather than being asked again by the tool. **Under [R0](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) this splits and both halves hold. For a connection it is structural:** the transport is handed one passphrase, makes one authentication attempt with it and returns the result, so there is no program with a retry policy of its own in the path and none of Fact 37's counts can arise. **For the local reads it is a rule and stays one**, because `ssh-keygen` and `ssh-add` are real programs with real behaviour — the 59-invocations-in-12-seconds observation is what it binds, and `Keys` S5's *once per attempt* and S6's *nothing retries* are the module-side statement of it.

**R6. A secret that stops working is forgotten rather than retried**, which is [Whole app](../Specs/Whole%20app.md)'s rule for a machine password and [Keys](../Specs/Keys.md)' for a passphrase. The detection is bounded by Fact 37 and the bound matters: **loading a key locally separates the causes and connecting does not.** Observed — locally, a wrong passphrase gives `incorrect passphrase supplied to decrypt private key` while malformed, truncated, empty and public-as-private all give `invalid format`; over a connection, at default log level, **wrong passphrase, empty passphrase, no passphrase available, key not authorised, and wrong account name all collapse into `Permission denied (publickey).` and exit 255** (Fact 37). **So *the passphrase stopped working* is established by a local load, never by a failed connection.** A failed connection is reported as a failed connection and forgets nothing. **[R0](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) hardens this rather than moving it, and the hardening is worth stating.** The connection half of the observation was a reading of one client's message text at one log level, which a version change could have altered; under a transport Smoozy drives, the connection carries **the protocol's own authentication failure and nothing else** — it names no cause at all, by the protocol's construction rather than by a client's choice of words. **So no future client, log level or release can make a failed connection separate the causes**, and the rule that a local load is the only establisher is now permanent instead of observed. Everything downstream is untouched: `Keys` S4, S5 and S7 read exactly as before.

**R7. And even the local signal is not proof.** Observed — the *correct* passphrase against a one-bit-corrupted key produced the identical `incorrect passphrase` message, and a flip at one interior offset produced exit 0 with correct-looking output (Fact 37). Forgetting a passphrase on that signal can therefore discard a good passphrase for a damaged key. That is accepted: the cost is one re-entry, and the alternative — keeping a passphrase that no longer opens anything — is the behaviour the spec rules out by name.

**R8. A machine password has no local load, so its trigger is stated as an invariant and not as a mechanism.** [Section 2](#2-the-five-held-things) erases the remembered password on *the password ceasing to work*, and the detection above establishes nothing for it: a wrong stored password, an elevation the login is refused, and an operation that failed after elevation succeeded are not separated by anything in Fact 37. So what is fixed here is the trigger. **The remembered password is erased only on an authentication result from the elevation step that is separable from the requested operation's own result.** Where the two cannot be separated, the password is **not** forgotten: the failed operation is reported as a failed operation and forgets nothing, exactly as a failed connection does above. Which elevation route is taken is `Server Setup`'s and `File Browser`'s through `Server protocol and transfers`, and it is not chosen here — the constraint each of them carries is that the route must yield that separable result. **The route is chosen and it does yield one — corrected 2026-08-23, this sentence having read *whether the route chosen does yield one is [Section 14] item 15's and is unresolved*.** `Server Setup` E4's validate-first order runs the elevating command's validate form, which runs no command, so its result is never an operation's result (Fact 108, documented 2026-08-19 and run on a rental 2026-08-22). **That result does separate a wrong password from a login not permitted to elevate, and the invariant's erase fires on it — corrected 2026-08-29.** This sentence read *"what that result does not separate is a wrong password from a login not permitted to elevate — the refusals differ only in text, which [Section 13] rule 5 forbids mining — so the invariant above withholds the erase in that case"*, and it was left standing when the Creator's ruling of **2026-08-25** put a named exception into [Section 13](#13-logging-redaction) rule 5 for this one tool; a builder reading here withheld the erase while a builder reading there performed it. **The ruling governs.** Rule 5's exception permits the elevation tool's own refusal strings to be matched as observed constants, so a failed validate carrying the wrong-password ending — `sudo: 1 incorrect password attempt`, observed at `sudo` 1.9.15p5 on 2026-08-22 (Fact 108) — **is an authentication result separable from the requested operation's own**, and [Section 2](#2-the-five-held-things)'s *the password ceasing to work* erasure fires on it. **What is still not concluded from, and the bar is rule 5's own:** the not-an-administrator message, which names the host and is therefore never matched as a constant. A failed validate that does not carry the wrong-password string is not established to be a wrong password, so the invariant withholds the erase there exactly as it does where nothing is separable — the safe direction, a good password never discarded. [Section 14](#14-unresolved) item 15 carries what is left.

**R9. Rate limiting corrupts the diagnosis and must not be provoked.** Observed — repeated attempts against a real server tripped the default source penalty, after which attempts *with the correct passphrase* failed as a closed connection, client-side indistinguishable from a broken server (Fact 37). Nothing in Smoozy retries an authentication in a tight loop; the retry policy that exists is `Servers`' reconnect policy and it is not a credential-guessing loop. **Under [R0](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) the transport makes exactly one authentication attempt per connection attempt and offers no second identity of its own**, so the only thing that can produce a run of attempts against a server is `Servers` §3's repair policy, which is bounded there and is read by nobody as a credential loop.

## 5. Erasure

**Constraint:** Row 41 (`Servers` — a removal forgets the details, the connection, the remembered identity, the remembered setup and any machine password), Row 252 (`Keys` — what has to be genuinely forgotten), [Whole app](../Specs/Whole%20app.md)'s three password choices, and [Telegram](../Specs/Telegram.md)'s replacement token.

### 5.1 The order, the recorded debt, and what a crash between the steps leaves

**E1.** Erasing one held thing is three writes, and the first is what makes the other two safe.

1. **The local record marks that subject as owing an erase.**
2. **The secret-store item is erased.**
3. **The local record's row is removed, and the mark with it.**

**E2.** A crash between 2 and 3 leaves a local reference to an item that is gone, which reads as *not there* and asks the user again — the safe direction. A crash between 1 and 2 leaves the mark, and the sweep below is what the mark is for. The reverse order — the record's row first and the store second — would leave a secret with nothing pointing at it and nothing that would ever notice.

**E3. A removal is never blocked by a store failure.** An erase that could not unlock is reported as an erase that did not happen ([Section 3.3](#33-linux)), and the caller does not stop on it: the local record's row is removed regardless, the subject stays marked as owing an erase, and the sweep retries it. The two readings this rules out are both worse — blocking the removal puts a refusal in front of the user that no spec writes, and removing the row without the mark leaves an orphaned secret that Row 41's *forget it* forbids.

**E3a. Where the mark lives, and it outlives the row. Added 2026-09-03 at Build, out of a fault demonstrated in code.** E3 asks for two things at once — *"the local record's row is removed regardless, the subject stays marked as owing an erase"* — and [Keys](Keys.md#44-the-protection-reading-and-the-availability-answer-row-245) U9a had put the mark and the reference in **two columns of one row**. **A column of a row cannot survive that row's removal**, so on the delete path the mark went with it, and on the store-failure path the reference was dropped and the mark was left with no subject under it. **Either way the sweep's input was empty and the store item was orphaned** — which is exactly the outcome [E2](#51-the-order-the-recorded-debt-and-what-a-crash-between-the-steps-leaves) says the reverse order would produce, arrived at by a different road. Demonstrated by two tests at `App/Desktop app and delivery/src/record/key_rows.rs`, both passing, each named for the direction it shows.

**So the mark is one durable register of its own in the local record, keyed by the stored kind and the subject, and it is not a field of anything it may outlive.** Write 1 puts an entry in it; write 3 removes that entry and the reference together. **A crash anywhere leaves the entry**, which is what the sweep is for, and **removing a row leaves it too**, which is what E3 asks for in as many words.

**U9a's rule is kept rather than overturned, and the two were never the same question.** That clause is about the **availability answer** — a reference standing with its mark cleared would make U9 answer *yes* for an item that is gone — and it is kept by U9 reading the reference **against this register**: a subject that appears here is owed an erase, so availability is no from the instant write 1 lands, exactly as before, and there is still **one** home for the fact rather than two that could drift. What moves is only where that one home is, and it moves so that it can outlive a row it must outlive.

**E4. The sweep acts on those marks and on nothing else.** It erases each marked subject and clears the mark when the store reports the item gone; **in doing so it completes the third write above, removing the local reference and the mark together, never the mark alone.** **It never treats the absence of a row as a reason to erase**: a local record that was replaced by an empty one, or by a migration or a repair, carries no marks, so it costs nothing rather than destroying every stored secret. **It does not run at all where the local record did not open.** And **it runs after the first successful store operation of a run rather than before one**, so it never reaches the store in a sitting where nothing was going to be handed over ([Section 15](#15-moments-that-reached-the-creator)). That is the only sweep, it is not a background watcher, and it is what makes Row 41's *forget it* true after an interrupted removal.

### 5.2 What each event erases

- **E5. A key deleted, or removed from Smoozy** — the passphrase item, the fingerprint, the path, and the local key row. Both removal paths drop everything Keys held, which is Row 252's promise; only the delete path touches files, which is `Keys`'.
- **E6. A key's file swapped at the same path**, detected by the fingerprint changing — the passphrase item. The passphrase belonged to the key that left.

  **What this trigger reaches, and why it stands. Added 2026-10-16, owed piece 9 of Build step 10c, carrying the `Keys` code round 1's upstream item.** The detection is `Keys` U4 clause 4b, and `Keys` U7ab settles which keys 4b reaches: **keys whose private half reads, which is keys with no passphrase, and no protected key at all**, because for a protected key every fingerprint is read from the public half and such a value is never 4b's evidence (`Keys` U7a, U7b). **A passphrase item exists only for a protected key, so as written E6 erases nothing.** It stands rather than being struck for two reasons. **It is still the rule**: a key's passphrase belongs to that key, and if a later reading lets 4b reach a protected key, this is what the event erases. **And the case it was written for is still closed another way**: at the next connect, `Keys` S5's supply runs the one local load, the load fails against the key that arrived, and [§4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) R6 forgets a passphrase that stops working — so the item goes and the user is asked fresh, at the cost of one failed connect (`Keys` U7ab, *What still holds*). **What is lost is only the row saying a swap happened**, which is `Keys`' to state and is stated there. *(The sentence above is kept as it was written; until this note it read as a trigger that fires for protected keys.)*
- **E7. The user clearing a remembered passphrase** — the passphrase item, and nothing else.
- **E8. A server edited: username changed** — the machine-password item, without asking. A password belongs to a login.
- **E9. A server edited: the user clearing the password** — the machine-password item.
- **E10. A server edited: host or port changed** — the remembered identity, which starts over. Not a secret-store operation.
- **E11. A server removed** — the machine-password item, the remembered identity, the remembered setup, and the server row. **Without reaching the machine**, which Row 41 requires: a disconnected server's removal starts no connection and asks for no passphrase.
- **E12. A connection ending** — every process-memory password held for that connection, however it ended: the user disconnecting, the connection dropping, or the application closing. A connection Smoozy replaces underneath a standing connected period carries none of them across, because the replacement is a new connection ([Section 2](#2-the-five-held-things), item 3b).
- **E14. The bot token replaced** — by a new token for the same bot, or by a different bot's — the desktop token item. What becomes of the copies on machines is [Section 10](#10-what-smoozy-leaves-on-a-rented-machine). *(Changed 2026-10-31: it named Telegram switched off as well. Switching off no longer erases (`Telegram` K1; the Creator's fifteenth notes, note 1, "Needs fixing."): the same token stays on every machine it was placed on, so the erase ended nobody's hold on the bot and cost the user a revoked token, a paste and every server reconnected. No auditor has seen it.)*

**Upgrade cleanup.** Record one erase debt for the former licence-key item using its unchanged old locator constant. Clear the debt only when the store confirms the item gone. Other secrets keep their existing prompts and sweep timing.

### 5.3 What erasure cannot reach, said plainly

**E15.** Two things, and both are already in the specs rather than being introduced here. A machine password or passphrase that has been used has been used, and erasure does not undo it. And a token already on a rented machine is not reachable by an erasure on the user's computer: [Telegram](../Specs/Telegram.md) states that where a removal does not reach the machine, *"the piece and the token stay on it, and that machine can go on sending messages until the user destroys it."*

### 5.4 Nothing puts a fingerprint or a host key on a screen

**E16.** [Whole app](../Specs/Whole%20app.md) and [Servers](../Specs/Servers.md) agree and Row 278 states it: a machine's remembered identity *"is trusted silently the first time and is never shown to the user."* This document extends that to everywhere a value can surface: **a host key or its fingerprint appears in no screen, no notification, no failure message, no exported record and no log** ([Section 13](#13-logging-redaction)). A key's own fingerprint is a different matter and `Keys` shows it deliberately; that is Row 246's and is not touched here.

## 6. The private half of an SSH key

**Constraint:** Row 278 — *"The **private half of an SSH key** — which Smoozy never copies, never moves, and never sends anywhere. It stays where the operating system keeps keys, or where the user pointed Smoozy at it."* Facts 33, 34, 35, 36 and 76.

**P1. Smoozy holds a path and a fingerprint.** It **never copies the file, never moves it, never sends it anywhere, never writes it to any store or to any other file, and never retains its bytes.** Every use of the key **starts from the path and never from the bytes**, so the key material is never a value Smoozy keeps. **Corrected 2026-09-02 under [§4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) R0.** This sentence read *"Every use of the key is carried out by handing the **path** to the tool that needs it — `IdentityFile` for a connection, `-f` for a local read — so the key material itself is never a value Smoozy keeps, and **the encrypted key material is never decrypted in Smoozy's process.** That is what makes the promise's three verbs true by construction rather than by discipline."* **The local-read half is unchanged: `-f` hands the path to `ssh-keygen` and nothing more.** **The connection half is not what this architecture does** — `Servers` K1's transport makes the connection and there is no `IdentityFile` and no tool, so **the transport reads the file at that path and unlocks it in memory for one authentication exchange** ([§4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) R2a, which states the four rules that bound it and what the change costs). **The promise's three verbs are still true by construction and by the same argument** — reading a file in place is not copying it, moving it or sending it anywhere, and nothing derived from it is written or kept — but the construction is now *never written, never kept, never handed on*, and no longer *never decrypted here*. `Keys` line 48 carries the old wording from this document's side and is routed rather than edited.

**P2. The one thing Smoozy does read is the container header, in place.** The route below reads the beginning of the file where it lies, transiently, to answer one yes-or-no, and discards those bytes when the question is answered. Nothing is written, nothing is kept, and the answer is the only thing that outlives the read.

**P3. The one-place premise the Keys spec asked to have checked is false, and the consequence is a rule.** Documented — OpenSSH's manuals call `~/.ssh` the **default** location and never the only one; `IdentityFile` and `-i` can name any path and may appear many times; a key can exist only inside `ssh-agent` with no file behind it; a PKCS#11 token supplies keys with no file at all; and Windows has a second Microsoft-named location, `C:\ProgramData\ssh`, which is where Microsoft says the **host keys** and server configuration live rather than the user's own identities, and that page's `HostKey` defaults name private key files — none of the four default paths carries `.pub` (Fact 33, [The manuals](The%20manuals%20—%20keys,%20secrets,%20and%20what%20cannot%20be%20told%20apart.md)). *(This quoted Fact 33's *"Whether the files there include private key files is not stated on that page"* until 2026-08-22; that unresolved closed on 2026-08-21 in the document quoted.)* **So Smoozy must track, per key, whether a file backs it at all**, and must never assume a listed key's file is `~/.ssh/<name>`. `Keys` owns what that means for delete against remove (Rows 247, 251); this document owns the rule that no code path may synthesise a private key path from a name.

**P4. The fingerprint's hash is pinned to SHA-256 explicitly, wherever one is taken or compared, and an MD5 fingerprint is never treated as an identity — added 2026-08-21.** The printed form is selectable: `FingerprintHash` takes *"md5 and sha256 (the default)"* on both the client's and the server's configuration pages. **Relying on the default is not enough**, because a default is a setting somebody can change, so the hash is named at every call. **The two forms are not equally safe and the identity question flips between them** — RFC 6151, read 2026-08-20: *"The attacks presented in [KLIM2006] can find MD5 collision in about one minute on a standard notebook PC (Intel Pentium, 1.6GHz)."* and *"MD5 is no longer acceptable where collision resistance is required such as digital signatures."* **So two distinct keys sharing one MD5 fingerprint is a documented, cheap construction**, and a fingerprint offered in that form tells this application nothing about which key it has. `Keys` F8 carries the same rule for the module that owns the list.

**P5. What is read from the file, and how, without the passphrase.** Documented and observed (Fact 35 Half A): type, bit size and fingerprint are readable from an encrypted private key file with no passphrase and stay readable with the `.pub` deleted; the **comment is not recoverable** without it.

**Corrected 2026-10-16, owed piece 9 of Build step 10c, carrying the `Keys` code round 1's upstream item. Fact 35 half A is not warrant for reading a fingerprint from the private file, and this clause used it as one.** That observation was made with `ssh-keygen -l -f` and **the `.pub` moved aside**; `Keys` U7b (2026-09-03) observed that the same call answers from the `.pub` whenever one is beside the key, so it is a public-half read in every ordinary case. **The private half's own read is `ssh-keygen -y -f`, which needs the key unlocked**: it answers for a key with no passphrase and is refused, without a prompt, for **every** protected key. So for a protected key the fingerprint comes from the public half beside it (`Keys` U7, bounded by U7a), and **a protected key with no `.pub` beside it has no readable fingerprint at all** (`Keys` §13 item 6). The comment half is unchanged. *(The sentence above is kept as it was written.)*

**P6. Detecting that a key is protected has two routes and only one of them is safe to read as a yes-or-no.** Observed — `ssh-keygen -y -P '' -f <path>` exits 0 on a key with no passphrase and 255 on a key with one. **Exit 255 does not by itself mean *this key has a passphrase*:** the same command exits 255 for a garbage file, a truncated key, a zero-length file, a public key passed as a private one, a missing file, and a key whose file permissions are too open — separated only by message text that **no OpenSSH manual documents** (Fact 37; Fact 35's own narrowing records that only two keys were tested). So the yes-or-no is taken from the container instead: strip the armour lines, base64-decode, and read the length-prefixed cipher and KDF names — `none`/`none` for an unprotected key. **That route carries three narrowings from its own source and none of them may be dropped.** It was observed on one build, OpenSSH 10.2p1, on four keys of which **only one was encrypted**, so the discriminating half rests on a single data point. The container layout is **documented on no OpenSSH manual page** — `openssh-key-v1` returns count zero on all six — and is an observation of the file bytes. And a key in the **legacy PEM format is not this container at all** — but that is a case the route does not *need* to cover, established 2026-08-20 after this sentence had recorded it as an uncovered gap. PEM states its own answer in plain text on the second line: `Proc-Type: 4,ENCRYPTED`, required by RFC 1421 for every encrypted message, with RFC 7468's `PRIVATE KEY` against `ENCRYPTED PRIVATE KEY` labels doing the same for PKCS8. Observed on the Creator's Mac across four keys with and without a passphrase. **So the in-place header read answers both container kinds and no inference is needed for either**; `Keys` U8 carries it. **The failure direction matters:** a key wrongly read as unprotected makes Smoozy attempt a connection it can see cannot work, which is the same first line of defence [Section 4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) leans on when it declines to depend on `BatchMode=yes`, so the two would fail together; a key wrongly read as protected asks for a passphrase that does not exist. The `-P ''` probe is used to confirm, not to decide.

**P7. The permission gate pre-empts everything else.** Observed — a private key file with mode 0644 is rejected with `bad permissions` before the passphrase question is reached at all (Fact 37). `Keys` owns what that means for *usable* under Row 245; the constraint supplied here is that a key Smoozy generates is written with the modes `ssh-keygen` itself sets, and that Smoozy never widens a key file's permissions.

**P8. Nothing that scans a key location may treat a successful fingerprint as proof of a key.** Observed — `ssh-keygen -l -f` correctly rejects `config`, plain text and empty files at exit 255, but **accepts `known_hosts` at exit 0 and fingerprints it** (Fact 34). Whether `authorized_keys` behaves the same way is **inferred from the shared line format and never run**. `Keys` owns the listing rule under Row 245; the security half owned here is narrower and absolute: **Smoozy's own host-key material is never written into any directory it also scans for keys**, which [Section 7](#7-host-trust) states outright for every file it writes, rather than leaving it to be a side effect of where the remembered identity is kept.

**P9. The fingerprint carries an identity claim and one clause under it is open.** Documented (Fact 76): SHA-256 is the default hash on the pages read, which are OpenBSD-current and say nothing about other platforms' builds. **Observed on one build, OpenSSH 10.2p1 on one Mac** (Fact 76): the printed form is `SHA256:` plus unpadded base64; the digest is taken over the decoded wire-format public key blob, which the source records as *"determined by **reconstruction, not from the manual**"*; so it is **independent of the comment and of file whitespace**, and identical whether taken from the private file or the public one, which is what Row 246 needs. **Unresolved — reframed 2026-08-22, and most of it closes.** **Cross-system stability is answered and needs no other machine** (Fact 76): the digest is taken over the bytes RFC 4253 §6.6 fixes for the protocol rather than for any system, and recomputing it by hand from a key's own bytes reproduced the tool's printed line in both hash forms. **The collision half was the wrong question** — it turns on which hash, and the hash is pinned in the paragraph above. What is left is a citation rather than a doubt: **no first-party sentence says a SHA-256 collision does not exist**, since an absence of published collisions is not citable, and whether Row 293's *two keys Smoozy knows can never share one* may close on that basis is the Creator's (`Preparation/Groundwork/Open Threads.md` item 8a). [Section 14](#14-unresolved) item 1 records what breaks. *(This said **stability across the three operating systems was observed on macOS alone and is stated by no source, and whether two distinct keys can ever share a fingerprint is stated by nothing cited**. The reframing is 2026-08-20's and it reached §14 item 1, `Keys` and `Servers` that day; this sentence, ten lines below the rule that settles it, was the fourth place and was passed over.)*

**P10. One consequence for this document rather than for `Keys`.** Because a passphrase is keyed by the local key identifier and the local record maps fingerprint to identifier, a fingerprint collision would attach one passphrase to two keys. The store contract cannot detect that and does not pretend to; the detection, if any, is Row 246's.

## 7. Host trust

**Constraint:** Row 36 (`Servers` — silent first trust, and the accept and decline paths on a change) and Row 37 (`Servers` — *"how the machine's remembered identity is stored"*, and that it is per server, started over by an address edit or an accept, and never shown).

**T1. The remembered identity lives in the local record against the saved server, and nowhere else.** Not in `~/.ssh/known_hosts`. That file is the user's own SSH configuration; writing to it would change how every other program on their computer connects to that address, and removing an entry from it on a server removal would take away something the user may have put there themselves. **Nothing Smoozy does modifies the user's own SSH configuration**, which is the same stance [Keys](../Specs/Keys.md) takes toward a referenced key file.

**T2. No throwaway known-hosts file is written for a connection, because there is no client to hand one to. Corrected 2026-09-02 under [§4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it) R0 and [Servers](Servers.md#21-the-break-reporting-mechanism) K1a; this clause read *"Each connection attempt is given a throwaway known-hosts file holding that server's remembered entry and nothing else, with the user's own configuration excluded, and the file is discarded when the attempt ends. That is what makes the identity per server, re-startable, and rewritable one entry at a time, which is exactly what Row 37 requires and what a single shared file does not give."*** A known-hosts file is an input to a command-line SSH client, and K1a runs no `ssh`, `sftp` or `scp` process for a connection at any moment. **What replaces it: the remembered entry is read from the local record at the attempt's own moment and compared in Smoozy's own process** ([T1](#7-host-trust), [T4](#7-host-trust)), and the approved host key is a value the transport `Servers` K1 names is handed on a call, exactly as the private key file's path is ([§6](#6-the-private-half-of-an-ssh-key) P1). **Every property this clause claimed is kept and all four become structural rather than configured** — *per server*, because what is compared is that server's row and no other server's entry exists anywhere to be consulted; *started over by an address edit or an accept*, because the row is re-read at every attempt and nothing caches; *rewritable one entry at a time*, because a row is the thing rewritten; and *the user's own configuration excluded*, because the transport reads no `~/.ssh/config` and no `~/.ssh/known_hosts` at all, so there is nothing to exclude. Row 37 is kept by the local record, which [T1](#7-host-trust) already made the identity's one home.

**T2a. The gap between the two reads of the host key is closed by the comparison, not by the file. Added 2026-09-02 with [T2](#7-host-trust), because the file was what closed it.** [T6](#7-host-trust) obtains the offered key before any connection and the decision is taken there. The transport then verifies the key it is offered inside key exchange — before authentication is asked for at all, which is [T6](#7-host-trust)'s quoted RFC 4253 §8 step 3 and §10 — against the same approved value, and stops the attempt where the two differ ([T5](#7-host-trust)'s third path). **So a connection either presents Smoozy's credential to the machine whose key the comparison approved or it does not connect**, which is exactly what the file was for, and it holds by a comparison this document owns rather than by a setting on a program it does not run. `Servers` [Q7](Servers.md#102-the-three-paths-and-the-two-reads-that-close-the-gap-between-them) states the superseded mechanism from that side — the file, and a client *"configured so that it can neither ask nor accept on its own"* — and is routed rather than edited here.

**T3. The throwaway known-hosts area, its placement rule and its start-up cleanup. Corrected 2026-09-02 with [T2](#7-host-trust): the mechanism the rule described is gone and the obligation is not.** The area is under the per-user application-data location [Section 9](#9-the-local-record) names, in a place kept for these files alone; `Desktop app and delivery` resolves it by name as one of the locations its platform file adapter may resolve. **The placement rule stands and is now satisfied by construction: no file of this kind is written into `~/.ssh`, into any directory Smoozy scans for keys, or into any directory the user's own SSH configuration reads — because none is written anywhere at all.** That is what makes [Section 6](#6-the-private-half-of-an-ssh-key)'s absolute rule a statement rather than a hope, and what keeps Fact 34's observed behaviour off Smoozy's own doorstep: `ssh-keygen -l -f` **accepts `known_hosts` at exit 0 and fingerprints it** ([Section 6](#6-the-private-half-of-an-ssh-key), Fact 34), so such a file in a scanned directory would be listed as a key that does not exist.

**The start-up cleanup rule is live and is unchanged in its obligation: any of these files found at application start is removed before any connection is attempted, and none is ever read back.** *(Kept because `Desktop app and delivery` reads it by name — its own sweep of Smoozy's temporary area is written to the shape this rule gives and for the reason it gives it.)* **What changed is why it fires, and it is stated so nobody reads the rule as evidence of a writer.** It was written to complete a *discarded when the attempt ends* rule that a process exiting first does not cover; nothing this architecture does writes such a file now, so anything found in the area was put there by something outside this architecture, and the rule's second half is the whole of its force — the material is removed, never read, and never a source of trust. The remembered identity lives in the local record and nowhere else ([T1](#7-host-trust)), so no file could be a source of trust even if one were found.

**Two rows elsewhere describe a per-attempt write that no longer happens, and neither is edited here:** `State, identity and recovery` [§1.1](State,%20identity%20and%20recovery.md#11-on-the-users-computer)'s durable table, whose entry for this area reads *"one file per connection attempt, swept at application start"*, and its §11 run-held table's *"the throwaway known-hosts files — deleted when the attempt ends"*. **The area, its placement and its sweep stay exactly as above; the per-attempt file is what went.**

**T4. The comparison is Smoozy's, not a reading of the client's words.** Fact 37 establishes that **no OpenSSH manual documents any of the diagnostic strings the tools emit**, and that a changed host key is observable at default log level only through a banner whose text is undocumented. So the decision is taken by comparing the host key value itself against the remembered one, and a diagnostic string is never what a changed identity is inferred from.

**T5. The three paths.**

- **First connection, nothing remembered.** The offered host key is accepted without asking and recorded against the server. That is Smoozy's own policy and not documented SSH behaviour, which [Servers](../Specs/Servers.md) states outright; `accept-new` is the documented setting nearest to it and it does not deliver the accept-a-change path below.
- **Later connection, key matches.** The connection proceeds. Nothing is said and nothing is shown.
- **Later connection, key differs.** The attempt stops before anything else happens, and the changed-identity warning `Servers` owns is raised. **Accepting** replaces the recorded key and repeats the first-connection path, which is why the record must be per server and rewritable. **Declining** keeps the old record, so the warning returns on the next attempt.

**T6. Which mechanism yields the offered key before authenticating is answered, and this section said it was open until 2026-08-21 — three days after the answer landed, and while `Servers` Q4, `Server protocol and transfers` A5 and `Coverage.md` were already writing from it.** Fact 82, **ANSWERED 2026-08-17**: `ssh-keyscan` obtains the offered key with no credential asked for and none supplied, its own manual saying so outright — *"For scanning, one does not need login access to the machines that are being scanned, nor does the scanning process involve any encryption."* (`ssh-keyscan(1)`, macOS 26.5, page dated October 4, 2025, re-read 2026-08-20). Observed against the German rental: all three key types at exit `0` with nothing on standard error, two independent scans **byte-identical**, and the comparison separating the real key from a generated impostor. **So the decision is made before any connection at all, and neither fallback below is forced.** **Two limits ride with the answer and both stay:** `ssh-keyscan(1)` has **no EXIT STATUS section**, so its `0` and its `1` are observed and documented nowhere; and where a connection *is* attempted against a wrong stored record, ssh exits **255**, its generic status, which separates a host-key mismatch from nothing. Both are Fact 37's shape. **The two fallbacks are recorded so nobody reaches for one:** parsing the undocumented banner, which a version change breaks silently; or accepting whatever key is offered, connecting anyway, and warning the user after the fact. **Corrected 2026-08-21: this route was described as *authenticating to an impostor* or *proving Smoozy's identity to an impostor*, and that cannot happen.** SSH checks the host key inside key exchange, before authentication is even asked for — RFC 4253 §8 step 3, read 2026-08-20: *"C verifies that K_S really is the host key for S (e.g., using certificates or a local database)."*, and §10 makes `ssh-userauth` a service requested *"After the key exchange"*; RFC 4252's abstract puts the authentication protocol *"on top of the SSH transport layer protocol"*. **Run with a control on the Creator's Mac, `OpenSSH_10.2p1`, 2026-08-20:** with a deliberately wrong stored key the client exited 255 at *"Host key verification failed."* and the whole trace contains no `userauth`, no `SERVICE_ACCEPT`, no key offered; with the true key in the same scratch file the trace reaches *"debug2: service_accept: ssh-userauth"*. **No credential can go first.** **What the bad route actually is** — accept whatever key is offered, connect anyway, and warn the user after the fact, which is a weaker and different harm. **Neither is adopted here**, and now neither has to be: the arrangement above stands on the answered mechanism rather than on a requirement waiting for one.

**T7. The second question under the same promise is answered, and this section carried it as open until 2026-08-23 — six days after the answer landed.** Fact 83, **ANSWERED IN FULL, 2026-08-17** ([The host key](The%20host%20key%20—%20obtained%20without%20authenticating,%20and%20whose%20it%20turns%20out%20to%20be.md); [Facts](Facts.md), Fact 83). **The proxy half is answered *no*:** the three keys offered through `ssh3.vast.ai:28452` are byte-for-byte the machine's own `/etc/ssh/ssh_host_rsa_key.pub`, `ssh_host_ecdsa_key.pub` and `ssh_host_ed25519_key.pub`, so the proxy forwards the connection rather than terminating it with an identity of its own. **One honest limit rides with it:** those files were read over an authenticated session through the same proxy, so a middle lying consistently on both the scan and the session would not show up; what is ruled out is the ordinary case the fact was filed against.

**T8. What the same answer does to the three paths above, and it narrows their reach rather than changing any of them.** Three readings, all of the answered fact:

- **A fresh container rental on the same physical machine presents byte-identical host keys** while being a demonstrably different container — different hostname, different start time, everything Smoozy installed destroyed — reached at a different proxy address and port ([The host key](The%20host%20key%20—%20obtained%20without%20authenticating,%20and%20whose%20it%20turns%20out%20to%20be.md), Fact 83).
- **A container's keys are the host's**, not the image's: the same offer re-rented gave three identical keys with the proxy port moved, and a different machine on the same image gave three different ones ([The multi-provider batch](The%20multi-provider%20batch%20—%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md), Test 19, 2026-08-22).
- **The virtual machine observed was shipped its keys in the image** — four keys, files dated 2025-11-06 20:55:50 to the nanosecond, every fingerprint, file size and timestamp identical after a recycle that destroyed everything else on the box ([The last two boxes](The%20last%20two%20boxes%20—%20the%20hook%20that%20cannot%20be%20read%20back,%20the%20full%20disk,%20and%20the%20unit%20that%20kills%20a%20render.md) §17).

**T9. So a host key names neither the rental nor the installation.** The register's own conclusion: the key *"is simply not a name for the thing Smoozy needs to recognise."* Two consequences bind every reader of the three paths.

- **The *key differs* path cannot fire on a machine replaced under one address**, which is the event Row 36's warning exists for — on either rented machine kind observed. And it **does** fire where a user re-rents on different hardware, which is a genuine change of machine rather than an impersonation.
- **An unchanged host key means nothing at all; a changed one still means something happened** and is not read as noise.

**T10. Nothing in the three paths changes, and nothing anywhere may be keyed on the remembered host key.** The paths perform Row 36's Creator-settled policy, which is not this document's to retake, and the value they compare is still per server, still started over by an address edit or an accept, and still never shown. What covers the case a host key cannot is `State, identity and recovery` §2.3's installation identity, which is why `Servers` D11 keys nothing on the host key. `Servers` Q10 and its Section 16 item 5 already carry this narrowing from the module side; it is stated here so no reader takes the three paths for a guarantee about the machine. **What stays open is smaller than the question was:** whether a machine's keys ever change without the hardware changing is not established, and the *on every host* half of the image reading is an inference from one machine watched across a recycle rather than from two rentals on two hosts. [Section 14](#14-unresolved)'s item 5 carries both.

**T11. And nothing here reaches the user's eyes.** No fingerprint at a first connection, none at a changed one, none in the warning, and none in any log ([Section 13](#13-logging-redaction)). Accepting a changed identity is a choice to trust the machine and not a check that has been passed, which [Servers](../Specs/Servers.md) says in its own words.

## 8. The supervisor's machine-local endpoint

**Constraint:** [The shape](The%20shape.md#each-rented-server) — *"The endpoint is reachable only by the login Smoozy holds; the supervisor rejects a request from any other local identity."* … *"`Security and licence` owns this local access boundary, and `Rented-server runtime` implements it as owner of the endpoint."* Facts 48, 1 and 63. *(Re-cut 2026-08-23: the shape now carries a Fact 84 sentence between those two, so the constraint is quoted as the two fragments it is.)*

**N1. The endpoint is a filesystem object in the machine's own namespace, not a network port.** It binds no address, so it is unreachable from off the machine whatever the provider's port mapping does, and it is outside the *no inbound listener* question entirely. `Rented-server runtime` owns its existence and lifecycle; what follows is the access boundary it must implement.

**N2. Three requirements, in order of strength.**

1. **The endpoint's containing directory and the endpoint itself are owned by the login the supervisor runs as, and permit that login only.** On both machines where Fact 1's narrow clause was posed — two of the six — the supervisor runs as an ordinary login rather than as root: `uid=1000 user=smoozy` on the container and uid 1001 on the virtual machine ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 1's narrow clause). On the container that is reached only because root installs the provider hook and the hook drops privilege — *"a non-root login has, on its own, no boot-registration route at all on a container"* — so the ordinary login is where the supervisor ends up rather than where it starts. Either way the owning identity is a real boundary against other ordinary logins on the same machine.
2. **The supervisor establishes the caller's local identity from the connection itself and rejects any caller that is not the login it runs as.** It never takes the caller's word for who it is: no field in a request may name the caller's identity, and any such field is ignored rather than checked. The directory permission is the outer gate; this is the check that survives a mode being widened by a setup step, a provider image, or a careless repair.
3. **Every request is still framed, versioned and correlated as `Server protocol and transfers` defines.** The endpoint is not a trusted channel that skips validation; it is a channel whose peer is known.

**N3. Requirement 2's mechanism is answered, so the boundary has two layers rather than one.** Fact 84, answered 2026-08-17 on **both machine kinds and both halves** ([The host key](The%20host%20key%20—%20obtained%20without%20authenticating,%20and%20whose%20it%20turns%20out%20to%20be.md); [Facts](Facts.md), Fact 84). The mechanism is **peer credentials read from the kernel on the accepted connection** — `getsockopt(SOL_SOCKET, SO_PEERCRED)` on an `AF_UNIX` stream socket. Observed: a server told `pid=1628 uid=1000 gid=1000` for a caller running as an ordinary login, `uid 1000` resolving to that login, and the caller's own independent view of itself agreeing exactly — on a container rental whose capability set `00000000a80405fb` does not include `CAP_SYS_ADMIN`, so **it survives a container's reduced capabilities**, and identically on a genuine virtual machine with the full set. The endpoint in the test was deliberately left mode `0666`, so what was observed is credentials rather than file permissions — which is exactly the case requirement 2 exists for. **And the endpoint cannot be lied to:** an unprivileged caller attaching a `uid 0` claim to the connection was refused outright by the kernel with `errno 1 Operation not permitted`, and attaching nothing yielded the same truth. `Rented-server runtime` implements it, and `Server protocol and transfers` states the same requirement from the request side.

**N4. What the answer does not reach is the machine's own root**, and neither layer ever did: the paragraph below states that limit and no mechanism available on a rented machine changes it.

**N5. What this boundary does not claim, and the evidence is exact.** On a Vast.ai virtual machine the login handed over **was real root**, holding every capability including `cap_sys_module`, `cap_sys_admin` and `cap_sys_boot`, and *"Root ignores file permissions"* ([The rented machine](The%20rented%20machine.md), *The edges of the rental*). On a container root inside held 13 of 41 capabilities and was not in a user namespace, and even there it could not be excluded from the container's own filesystem ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 48). **So the endpoint boundary separates one login from another on a machine. It does not separate Smoozy from the machine's owner, and no arrangement on a rented machine could.** That is the same limit `Audits/Specs/Access/Decisions record.md` states for the user's own computer, and it is stated here so no document downstream writes a promise on top of it.

**N6. Nothing about the endpoint is a secret.** Its path is not a credential and is not treated as one, because a path is not protection.

## 9. The local record

**Constraint:** [The shape](The%20shape.md#the-users-computer) — the durable local record holds saved servers, history, settings, suppressed warnings, transfer arrangements and remembered server state; `Desktop app and delivery` owns the database and its migrations. Rows 41 and 252 require enumerable, genuinely-erasable per-server and per-key state.

**D1. The local record holds no secret value.** For each of the three stored user-secret kinds — the key passphrase, the machine password and the desktop copy of the bot token — it holds a subject identifier and nothing else; the value is in the operating system's store. That is what makes [Section 3.1](#31-macos)'s login-password-reset case cost the user only re-entry, and it is what makes `Desktop app and delivery`'s migrations safe to write, copy and back up.

**D2. It does hold two things that are sensitive without being secret**: each machine's remembered identity, and each key's fingerprint and path. Neither belongs in the secret store ([Section 2](#2-the-five-held-things)); both must survive, be per-server or per-key, and be individually erasable ([Section 5](#5-erasure)).

**D3. The record is not encrypted, and that is a decision rather than an omission.** Encrypting it needs a key, and the key would have to live in the same store the secrets already live in. On Windows that buys nothing at all: documented — *"Any program running as that user will be able to access credentials in this store"*, so a same-user reader who can reach the key can reach the secrets directly (Fact 38). On Linux the key would sit behind a store whose specification *"does not mandate any form of access control"* and which may not exist on the machine at all — and where it does not exist, an encrypted record would mean asking the user for something to type, **which is a cost no spec grants and would be [Method](Method.md)'s third escalation**. On macOS it would add the one real per-application boundary of the three, but only against a reader who is already running as the user, which is the case `Audits/Specs/Access/Decisions record.md` says outright is past what any app can guarantee. **So the record is written in the per-user application-data location the platform adapter names, created for the owning user only, and protected by the operating system's own file permissions and nothing further.**

**D4. Two rules bind every writer of it.** No secret value is written to it, including into a log table, a migration backup or a crash record. And no field of it is ever placed in a filename, because a filename is not covered by the contents rule.

## 10. What Smoozy leaves on a rented machine

**Constraint:** Row 263 — *"Whoever holds the token can act as the bot, so the token is a secret Smoozy keeps in the same spirit as an SSH key passphrase."* [Telegram's sources companion](../Specs/Sources/Telegram.sources.md)'s quotation of Telegram's documentation, read 2026-08-12: *"Everyone who has your token will have full control over your bot."* Facts 48 and 67.

**M1. One secret is placed on a rented machine: the Telegram bot token.** Nothing else. No SSH private key, no SSH passphrase, no other machine's password, no host key of another machine, and no record from which any of those could be derived.

**M2. How it is placed and held.** It travels inside the authenticated SSH connection as part of Server Setup's material placement under Row 91 — never as a command argument, for the reason in [Section 4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it). On the machine it is a file owned by the login the supervisor runs as, permitting that login only, inside the server package's own state area — **outside every job folder**, so nothing the user browses, uploads, downloads or renders can reach it, and no job cleanup can remove it by accident. It is read by the Telegram worker at start and is never passed to a child process as an argument or in an environment value.

**M3. What that protects against, and what it does not.**

- **It protects against the user's own browsing and against every other Smoozy operation on that machine**, because those all run under paths `Job files and outputs` owns.
- **It does not protect against root on that machine, and on some rentals the login Smoozy holds is root** (observed; [The rented machine](The%20rented%20machine.md)). Nor against the provider, which demonstrably holds power of life and death over the box — a reboot and a destruction were both carried out from the provider's own console (observed; [The rented machine](The%20rented%20machine.md)).
- **It does not protect against a later tenant of the same disk.** Observed on one box: *"The record of a boot from November 2025 was still on the disk in August 2026"*, and, on the container batch, `/var/tmp` *"is the only temporary area that both survives a reboot and sits on disk, which also makes it an easy place to leave one rental's data for the next tenant"* ([The rented machine](The%20rented%20machine.md); [Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 6). **So nothing may be placed under a shared temporary area**, and the package state area is the only permitted home.

**M4. The token's blast radius is bounded and the bound is what makes this acceptable.** Observed (Fact 67, [One box](One%20box%20—%20the%20Telegram%20capture%20and%20the%20port%20that%20cannot%20be%20chosen.md)): revoking a token cuts the old holder off immediately — an in-flight poll returned and every call after it was refused with `{"ok":false,"error_code":401,"description":"Unauthorized"}`, 58 bytes — *"So revoking replaces who may act as the bot and nothing else."* A leaked token costs the bot and no more: no server, no key, no file is reachable through it, because none of those crosses this boundary.

**M5. A machine cannot tell it has been retired, and Smoozy must.** Observed — *"A token that never existed answers byte for byte the same. So a machine still holding a replaced token knows only that it is out — it cannot tell replaced from mistyped from bot deleted … Whatever tells a machine it has been retired has to come from Smoozy, not from Telegram."* That is the mechanism Rows 264 and 277 already need, and it is named here so the token's replacement path does not invent a second one.

**M6. Erasure on the machine.** The one machine-reaching removal takes the Telegram role off and erases the token file with it; every other removal leaves the machine alone and the token stays, which [Telegram](../Specs/Telegram.md) states and this document does not soften. **A container recycle destroys it along with everything else Smoozy installed** — observed, *"Everything Smoozy installed was destroyed, down to the `cron` package"* — but that is the provider's act and not an erasure Smoozy can ask for, and **nothing in the connection distinguishes a recycled machine from a rebooted one**, so no erasure may ever be inferred from a machine being reachable again.

**M7. How long the exposure on such a machine lasts, stated plainly.** [Telegram](../Specs/Telegram.md) says a machine a removal did not reach *"can go on sending messages until the user destroys it"*, and destroying the rental is the ordinary end of the journey. **Destroying it is not an erasure.** A boot record from November 2025 was still on a disk in August 2026 (observed, above), and a recycle is the provider's act rather than something Smoozy can ask for — which this section already says of a recycle and which holds equally of a destruction. So a token on a machine whose Telegram role was never removed is exposed **for the life of that disk**, and not until the rental ends: Smoozy cannot reach the machine, and nothing the provider does with the disk afterwards is an erasure Smoozy can request or observe. **The package state area is not a defence against that**, and is not offered as one — what it protects against is the user's own browsing and Smoozy's other operations on that machine, which is what the bullets above claim and the whole of what they claim.

**M8. The remedy is downstream and is named here rather than decided here.** [Telegram](../Specs/Telegram.md)'s replacement-token path is the only thing that ends the exposure, because revoking cuts the old holder off immediately (observed, above), and the record of machines Smoozy has not reached — which Row 264 requires — is what such a decision would be taken against. Whether the user meets anything about it is `Telegram`'s and Design's.

**M9. One further observed hazard, recorded because it fixes the altitude.** A Vast.ai per-instance key found on the container *"listed every instance on the account with models, prices and images, and could restart them"* ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md)). Smoozy does not put it there and cannot remove it, and it is named only to make the point that a rented machine already carries the provider's own secrets in the clear.

## 13. Logging redaction

**Constraint:** [Whole app](../Specs/Whole%20app.md)'s Security concern and Row 286 — the machine's own words are kept and shown to the user, so anything that reaches those words reaches a screen.

**G1. Redaction here is *never emitted*, not *filtered before display*.** A filter has to recognise what it is hiding, and the three stored user-secret kinds have no recognisable shape.

**G2.** Five rules, retaining their original numbers (1–3, 5 and 6), each with the thing it prevents.

1. **No secret is ever a process argument.** Observed on a rental: from a second ordinary login, another login's process is visible *with its owner and command line* ([Six machines](Six%20machines%20—%20the%20container,%20the%20webhook%20and%20the%20ready%20action.md), Fact 60). An argument is also the one place a value survives into whatever the machine or a tool prints.
2. **No secret is ever placed in an environment value**, and **the machine's environment is never captured into any record Smoozy keeps or shows.** Observed on a rental: the provider's own settings *"hold secrets in plain text — an access key for the provider's own service, and a password for a web page it runs"*, with the finding's own conclusion that *"Anything that reads the machine's settings and writes them into a log would be writing those out too"* ([The rented machine](The%20rented%20machine.md), *What identifies the rental*). Smoozy would be publishing a third party's secrets into a panel the user can open.
3. **No host key, and no host key fingerprint, appears in any log, message or exported record** — the same rule as [Section 5.4](#54-nothing-puts-a-fingerprint-or-a-host-key-on-a-screen), extended past the screen.

5. **A tool's own output is captured whole or not at all, and is never mined for a cause — with one named exception, and it is named on a string observed in fixed wording rather than on a documented one. Corrected 2026-09-02, where the headline read *and it is named because its strings are documented*.** **The rule's own body already relabelled it four sentences on** — *"no publication anywhere in `Preparation/` supports either half of that"*, the exception standing on what is *"observed in fixed wording on the release the rented image ships"* — and [§14](#14-unresolved) item 17 says the strings are documented nowhere this stage reads, so the headline was the last place in the stage still calling them documented. **The half every other document quotes is unchanged word for word** — *"A tool's own output is captured whole or not at all, and is never mined for a cause"* — and so is the exception itself, its reach and its bound; only the ground named in the headline moves. `Server Setup` E4 and `Rented-server runtime` M24 quote that half and are unaffected. Fact 37 establishes that **no OpenSSH manual documents any of the diagnostic strings the tools emit**, and that at default log level five materially different causes collapse into `Permission denied (publickey).` Raising the log level to reach `-vv`, where they do separate, is not done on any ordinary path: those levels print key paths and identity material, and the separation itself is observed on one build rather than documented. **This supports [Whole app](../Specs/Whole%20app.md)'s rule that Smoozy says what happened and does not guess at a cause it cannot establish.**

   **The exception: the elevation tool, and it reaches that tool alone.** Creator-stated, 2026-08-25. **The ruling stands and is not reopened; its stated ground is relabelled and its reach narrowed to what that ground carries — corrected 2026-08-29.** This read *"the elevation tool's refusal messages **are documented, in fixed wording, on both versions Ubuntu ships**"*, and **no publication anywhere in `Preparation/` supports either half of that**: no manual page read names one of these strings, and no source read covers a second Ubuntu release. What stands under the exception is **observed**, on one rental — `sudo` **1.9.15p5** under Ubuntu 24.04's stock sudoers, 2026-08-22, three refusals all at exit 1 and differing word for word (Fact 108; `Sources/Security and licence.sources.md`). **So the exception as it now reads:** the elevation tool's refusal strings are **observed in fixed wording on the release the rented image ships**, so telling a wrong password apart from a failed elevation is **matching an observed constant** rather than guessing at a cause — which is the same distinction `Servers` Q12 already draws for the operating-system name it reads over the command channel, that one from documentation. **Why it earned an exception, unchanged:** without it a password that has genuinely stopped working is kept and re-offered, and the user meets the same failure again on every attempt until they clear it themselves. Smoozy can now drop a password it knows was refused, which is what `Keys` already does for a passphrase that stops working. **The bound, and it is the whole of the exception:** it applies to the elevation tool's own refusal strings **as observed**, matched as exact constants and to nothing else. **Exactly one of the three is such a constant** — the wrong-password ending `sudo: 1 incorrect password attempt`. The **not-an-administrator** message **names the host**, so it is never matched as a constant and nothing is concluded from it ([Section 4](#4-reaching-a-secret-and-giving-it-to-the-thing-that-needs-it), [Section 14](#14-unresolved) item 15). **An unrecognised string, a release whose strings were never observed, or any other tool falls back to the rule above** and Smoozy claims nothing about the cause. The blanket rule is otherwise untouched, and **the failure direction of the narrowing is the safe one**: an unmatched refusal forgets nothing.
6. **A failure message names the thing that failed, never the credential it failed with.** *The passphrase for this key did not work* is a statement about a key; it carries no passphrase, no fingerprint and no path beyond what the user already sees.

**G3. The three stored user-secret kinds are covered at the screen as well, and that rule is [§3.0](#30-the-contract-every-system-implements) rule 6. Added 2026-08-21, per Row 334.** A value that came out of the store reaches no screen, notification, message, exported record or log, and no get is made in order to compose something to show — the same pairing rule 3 has with [Section 5.4](#54-nothing-puts-a-fingerprint-or-a-host-key-on-a-screen), in the other direction.

**G4. One boundary this does not cross.** Row 286's raw record is the machine's own output for a job, held by `Rented-server runtime`. Nothing in these rules edits it — Smoozy does not alter what the machine said. The rules are about what Smoozy puts *into* the machine's reach in the first place, which is rules 1 and 2.
