## 1. What binds this before anything is decided

**The private half is `Security and licence` §6's and nothing here retakes it.** Smoozy holds a **path and a fingerprint and never the contents**: it never copies the file, never moves it, never sends it anywhere, never writes it to any store or to any other file, and never retains its bytes. **Corrected 2026-09-02, this sentence having restated `Security and licence` §6 P1 in the wording that document replaced the same day under its §4 R0 and `Servers` [K1a](Servers.md#21-the-break-reporting-mechanism).** It read *"every use hands the path to the tool that needs it — `IdentityFile` for a connection, `-f` for a local read — and the encrypted key material is never decrypted in Smoozy's process"*, and its connection half describes a program this architecture does not run. **The local-read half is unchanged and it is the whole of what this document performs:** `-f` hands the path to `ssh-keygen` and nothing more, at every listing, fingerprint, probe, verification and the one `-y` load. **A connection is not this document's act**, and there `Servers` K1's transport reads the file at that path and unlocks it **in memory for one authentication exchange**, bounded by `Security and licence` §4 R2a's four rules: the decrypted material is never written to any file, store, record or log; is never a process argument and never an environment value; is never handed to another module; and is discarded when the exchange ends, so a second connection re-reads and re-unlocks. **What that costs, carried here rather than dropped: the encrypted key material is now decrypted inside Smoozy's process, where §6 previously claimed it never was, so a fault in Smoozy that could read its own memory reaches a private key it previously could not.** The one thing Smoozy reads itself is the container header, in place, transiently, to answer one yes-or-no. The one-place premise is ruled false there and the consequence is inherited whole: **Smoozy tracks, per key, the file that backs it, and no code path synthesises a private key path from a name.** The permission gate pre-empts the passphrase question; a key Smoozy generates is written with the modes `ssh-keygen` itself sets and Smoozy never widens a key file's permissions. A successful fingerprint is not proof of a key. What is readable without the passphrase is type, bit size and fingerprint; the comment is not.

**The store, the route and the erasure are `Security and licence` §3, §4 and §5's.** Five operations, three user-secret kinds closed — the key passphrase is one of the three; StoreProbe is reserved for the adapter’s probe. The subject is opaque and carries nothing about the user. No secret is ever a process argument or an environment value (§13 rules 1 and 2). A key passphrase's route is split at §4 R2 and the split is this document's line too — **for a connection, the transport's own key-loading step inside Smoozy's process**, which crosses no process boundary, so the value is never an argument, never an environment value, never in a file and reaches no helper; **for a local read, the askpass route and never any other way**, which is the only one this document performs ([G3](#62-the-passphrase-route-row-248), [S5](#83-a-passphrase-that-stops-working-row-250)). *(Corrected 2026-09-02 with the paragraph above; this read *"A key passphrase reaches the SSH client through the askpass route and never any other way"*, which is the sentence §4 R2c keeps as superseded for a connection.)* `ssh-keygen`'s `-P` is used for nothing but a local probe with an empty passphrase (§4 R2b). A stored secret is read at the moment of use and discarded when the attempt ends. Erasing one held thing is §5.1's three writes in order, a removal is never blocked by a store failure, and the sweep acts on marks and nothing else. *The passphrase stopped working* is established by a local load and never by a failed connection (§4), and whatever supplies a passphrase supplies it once per attempt.

**The adapters are `Desktop app and delivery`'s.** The secret adapter and its S6 boundary: no module receives a plaintext — Keys holds a handle naming a kind and a subject, or is handed the outcome of a use carried out on its behalf. The application-identity adapter (§10) is the only reader of the computer name and the login account name, one named source per system; the login account name is never used to build a location (I4) and a computer name is never a key (I5). The platform file adapter (§6): every local write in the application goes through it, no return value is an outcome, the destination is re-checked by path after closing (F1), and no path is synthesised from an identity by anything but the one document that owns that path (F11, `State, identity and recovery` §2.1 rule 7). The system file picker is reached through the adapter alone, and whatever a picker returns is a path from the user, judged like any other name (K11, K13).

**The record, the identifiers and the lifetimes are `State, identity and recovery`'s.** The local record is the only durable store on this side that holds state, and *key rows* are in its §1.1 inventory. The **local key identifier** is issued by the local record when a key is added; the **secret-store subject** is its own identity, issued at first store of a kind against a subject (§2.2), and both obey §2.1's seven rules. Key rows are **user-held** (§11.1): they end when the user removes them and never otherwise. Every multi-part action below declares its partition unit under §9.2's three ordered tests, and Section [11](#11-declarations--partition-units) holds the declarations.

**`Servers` §9 (P1–P17) and §15 *To `Keys`* are a closed document's citation of this one, and everything below is written to make that citation true.** Its P1 asks two questions before every attempt — *is this key usable*, and *if it needs a passphrase, is one available for this attempt without asking* — taken at the moment, never cached (P2), at every list draw over every server (P12), as a derivation and not a stored state (P13), as a local read that never reaches a machine (P14). Both questions are answered below without prompting, without a network call and without the passphrase. The row holds the fingerprint and hands it over to be matched; **the recognition is this document's** (P16).

**Decisions already ruled, performed here rather than retaken:** the user meets the store's cost as the Creator ruled it on 2026-08-16 (`Preparation/Specs/Whole app.md`, Security concern). There is deliberately no *don't remember this* option when a passphrase is entered. A remembered passphrase belongs to the key, not to where its file sits. Keys never adds, changes or removes the passphrase on an existing key, never renames a key, never moves or copies a referenced file, never produces certificates, never gives the public key to a provider, never connects to a server. The name is the comment and never an identity. Smoozy never silently replaces an existing local file — collisions prompt or append non-colliding names, the only two outcomes. Nothing modifies the user's own SSH configuration (`Security and licence` §7's stance, kept true of everything below). The delete warning covers only Smoozy's own saved servers — a stated limit under Rule 8, not widened here.

**Every local read this document makes is constructed to fail rather than prompt.** Each tool invocation for a listing, a fingerprint, a probe or a verification runs with no terminal input available and the askpass route disabled (`SSH_ASKPASS_REQUIRE=never`, standard input closed), so a read that would have asked a question becomes a failed read with an exit status. **The disabling half of that construction was inherited as *inferred, not documented*; the run that raised it left no record anywhere in `Preparation/`, so it was performed again on 2026-08-23 and the label stands: *observed on this build, documented nowhere for this tool*.** The documentation gap is real and was re-confirmed: `SSH_ASKPASS_REQUIRE=never` is documented for `ssh(1)` and nowhere for `ssh-keygen`, whose whole ENVIRONMENT section names only `SSH_SK_PROVIDER` (see [Sources](Sources/Keys.sources.md)). What is no longer true is the clause saying only the `force` direction was ever observed on this binary. **Run on the Creator's Mac, macOS 26.6.2 (build 25G83), `OpenSSH_10.3p1` — a later build than the `OpenSSH_10.2p1` every other observation in this document was taken on — from a process with no controlling terminal at all (its own session, standard input on `/dev/null`, `/dev/tty` unopenable) and a helper that logs whenever it is called**, `ssh-keygen -y` against an encrypted key obeyed every clause of `ssh(1)`'s documented rule: helper called at exit 0 with the requirement unset, **not called at exit 255 with it set to `never`**, called at exit 0 with `prefer`, called at exit 0 with `force` and no display set, and not called at exit 255 with the display unset and the requirement unset. **The first two lines differ in one variable and each is the other's control** — if `never` did nothing here the second would have looked like the first. And in every refusing case the tool **failed with an exit status rather than hanging**, which is exactly what this construction claims and previously could not show. **One clause of the refusal is sharper than this document had it, and is written down rather than smoothed:** `never` closes the helper and not the terminal route. The tool still writes `Enter passphrase for "<path>": ` to its **standard error** and then reads standard input; because that input is closed it takes the empty read as an empty passphrase and ends at `Load key "<path>": incorrect passphrase supplied to decrypt private key`, exit 255. **That string is a byte on a captured stream and not a question put to anybody** — the invocation is a subprocess of this application, no diagnostic of the tool's is ever parsed ([U6](#42-usable-composed-row-245)), and what the construction needs is what it got: no helper, no wait, an exit status. **What is still not established:** Windows and Linux, which are unobserved, and this is one build on one system. **What is observed:** standard input closed turns a would-be question into a failed read rather than a hang on this binary — the overwrite question printed and exited 1 with nothing changed ([6.4](#64-the-filename-scheme-and-the-collision-row-243)) — and every probe the writing throwaway ran with standard input closed answered or failed without a prompt appearing. **What breaks if the inference is wrong:** a local read asks instead of failing, which is exactly what `Servers` P1 forbids. **What holds without it:** an attempt that is never made cannot prompt, and a read constructed to fail is judged by its exit status either way. [Section 13](#13-unresolved) item 3 carries it. The only invocations that carry an askpass helper are the two deliberate ones: applying a passphrase at generation ([6.2](#62-the-passphrase-route-row-248)) and the local load that supplies one ([8.3](#83-a-passphrase-that-stops-working-row-250)). This is what makes every answer `Servers` P1 and P12 read promptless by construction — a construction carried with its label. **Narrowed 2026-09-18, from a code round (step 10b, Round 1 — holding a connection, the runner's R2), written up by that step's loose ends; no auditor of this document has seen it.** Every run above was taken from a process with **no controlling terminal**, and that is the half the construction had not said it rested on. **Observed on this Mac, `OpenSSH_10.3p1`, 2026-09-18:** `ssh-keygen -y -f` on a passphrase-protected key, run from a pseudo-terminal with standard input closed and `SSH_ASKPASS_REQUIRE=never`, **wrote its passphrase prompt to the terminal and was still waiting six seconds later**; the same run with `-P ""` ended at exit 255 at once, and `-P ""` on a key with no passphrase changed nothing. So a Smoozy started from a terminal — a builder's, or a test run from one — had a local read that waited for a person, which is what `Servers` P1 forbids. **The read of the private half therefore carries `-P ""` as well**, the empty-passphrase probe §4 leaves open and not a secret, and with it the construction holds whether or not a terminal is there: closed input, the helper refused, and an empty passphrase given, so a protected key is refused with an exit status at once.

## 2. The supported types, the offered set and the default (Row 241)

**T1. The supported set is fixed at three: `ed25519`, `ecdsa`, `rsa`.** These are three of the four plain file-backed key types `ssh-keygen(1)` documents — the type list is the documented part (see [Sources](Sources/Keys.sources.md)); the fourth, `mldsa44-ed25519`, is left out because **no binary this project has read offers it** — the page serves OpenBSD-current, and the observed 10.2p1's own installed manual renders the `-t` list without it (Fact 32, observed) — so admitting it would put a type in the accepted set on the manual's authority alone, which is exactly what [T2](#2-the-supported-types-the-offered-set-and-the-default-row-241)'s runtime reading exists to refuse. *(This said the type was excluded by [T3](#2-the-supported-types-the-offered-set-and-the-default-row-241)'s decision until 2026-08-23; T3's stated grounds are the authenticator-hosted types' hardware and their fileless shape, and they reach `mldsa44-ed25519` not at all.)* The same set serves both halves of the module: **generation** offers a subset of it ([T2](#2-the-supported-types-the-offered-set-and-the-default-row-241)), and **acceptance** — Row 245's *supported type* clause — admits a key of any of the three, however it was made.

**T2. The offered set for generation is a runtime reading of the installed binary, never the manual's list.** Fact 32's constraint: the manual serves OpenBSD-current and documents a type the observed binary does not offer (`mldsa44-ed25519` on the page read, absent from the observed 10.2p1 — the page's list is quoted in [Sources](Sources/Keys.sources.md); the absence is Fact 32's observation, not the writing throwaway's, which never attempted that type). The reading: for each of the three supported types, attempt a generation with `-N ""` and a throwaway comment into Smoozy's own temporary area, verify a key pair resulted, and delete it at once. A type whose attempt fails is not offered. Observed on the Creator's Mac, OpenSSH 10.2p1: all three succeed; `dsa` fails at `unknown key type dsa`, exit 255, leaving no files (observed — see [Sources](Sources/Keys.sources.md)). The probe is taken once per application run, at the first moment the make-key dialog needs the list, never at application start, and its failure doubles as the no-generator detection of [6.3](#63-the-generator-probed-never-assumed-row-248).

**Smoozy's own temporary area has no stated owner, and it is routed rather than invented here.** `Desktop app and delivery` L2's durable non-record areas are four, five with L2a, and **none of them is it** — so the place this probe writes three real key pairs into is named by no document. It is routed at [Section 13](#13-unresolved) item 20, with the home-directory reading of [L1](#3-the-key-locations-and-the-one-place-premise-row-242). What this document needs from it, and states rather than decides, is `Security and licence` §7's stance kept: **the area is never a directory Smoozy also scans**, so it is never [L1](#3-the-key-locations-and-the-one-place-premise-row-242)'s usual key location and nothing the probe writes can be discovered as a key by [U1](#41-what-in-a-key-location-is-listed-as-a-key-row-245) set 2.

**T2a. The probe is a reading like any other, so the dialog draws first and the type control fills in behind it — the same shape [U10a](#45-the-check-one-function-three-callers-row-253) takes for the list.** Three generations, each its own process, are exactly what `Desktop app and delivery` P5 keeps off the drawing thread, so on the first opening in an application run neither the offered set nor the no-generator answer is in hand at the moment the dialog is asked for, and on every later opening both are.

- **The dialog draws without waiting**, and **the type control carries no entry that has not been read** — no type is offered on the manual's authority while the probe is still running, which is the same refusal [T2](#2-the-supported-types-the-offered-set-and-the-default-row-241) makes at every other moment. [T4](#2-the-supported-types-the-offered-set-and-the-default-row-241)'s default is taken from the offered set once that set exists and never ahead of it.
- **Where the probe answers *no generator*, the dialog is replaced by [6.3](#63-the-generator-probed-never-assumed-row-248)'s statement rather than opened beside it** — a dialog whose one control can offer nothing is not a screen the user asked for.
- **What the control looks like while it fills is Design's**, exactly as U10a left the row's own transient.

**T2b. The probe stays as it is — a throwaway key of each supported type, made and deleted — and the documented instant alternative is declined. Ruled 2026-09-02 by the architecture runner; recorded so nobody re-opens it, since nothing about it breaks either way.** **The cost was measured, and the figures carry their provenance rather than standing bare.** Three runs of each supported type on the Creator's own Mac — **macOS 26.6.2, build 25G83, arm64**, `/usr/bin/ssh-keygen` reporting `OpenSSH_10.3p1, LibreSSL 3.3.6` — on **2026-09-02**, each run `ssh-keygen -q -t <type> -N "" -C smoozy-probe -f <path>` into a throwaway directory: **`ed25519` 0.031 to 0.034 s, `ecdsa` 0.031 to 0.032 s, `rsa` 0.173 to 0.278 s** at the build's own 3072-bit default. Label: **observed on this build**; the machine record, the command and the runs are in [Sources](Sources/Keys.sources.md). **The rsa figure is the one that varies** — a prime search is not constant work — so the spread is stated and no single number is offered; what the clause rests on is that the whole probe is a fraction of a second, once per application run ([T2](#2-the-supported-types-the-offered-set-and-the-default-row-241)), three private key files written and deleted in Smoozy's own temporary area — not the key location ([Section 13](#13-unresolved) item 20) — and nothing the user sees ([T2a](#2-the-supported-types-the-offered-set-and-the-default-row-241) draws the dialog first). *(Corrected 2026-09-02 at the stage-close gate repair. This read* the cost was measured rather than argued: 0.03 s, 0.03 s and 0.51 s*, with **no date, no machine, no build, no command, no label and no entry in the companion**, whose only timing line said no key check had been timed anywhere on this project — and the sitting that wrote it recorded that nothing was run. That is Rule 2 breached in a clause written the same day, and this document's own precedent is to re-perform a run that left no record rather than defend it (Section 1, [Section 13](#13-unresolved) item 3). The two small figures reproduce; **the 0.51 s does not**, and is replaced by the observed spread.)* **Three grounds decline the alternative, and each is established rather than supposed.** `ssh -Q key-plain` **answers a narrower question**: `ssh(1)`'s own description of `-Q` is *"Queries for the algorithms supported by one of the following features"*, with `key-plain` given as *"non-certificate key types"* — and run on this build it prints seven names, **not one of which is a value `-t` accepts**: `ssh-ed25519`, `sk-ssh-ed25519@openssh.com`, `ecdsa-sha2-nistp256`, `ecdsa-sha2-nistp384`, `ecdsa-sha2-nistp521`, `sk-ecdsa-sha2-nistp256@openssh.com`, `ssh-rsa`. It splits one accepted type into three curves, so Smoozy would need a mapping rule between the two lists and this project has no source for one — composing it would be assembling a fact, which [Method](Method.md) bars. It **includes the two authenticator-hosted types [T3](#2-the-supported-types-the-offered-set-and-the-default-row-241) excludes by decision** — the second and sixth names in that output, both `sk-` — so its list is not the offered set even where the names line up. And **it asks the wrong program**: `-Q` is the client's own flag on the client's own manual page, so a run of it cannot detect a missing **generator** — which is [G6](#63-the-generator-probed-never-assumed-row-248)'s second job for this same probe and the live risk on exactly one system, a customised Windows image where client and generator are separate components. *(The three grounds carried the phrase* each is established rather than supposed *over three uncited outside claims until 2026-09-02; the manual sentence and the run behind them are now in [Sources](Sources/Keys.sources.md), labelled **documented** and **observed on this build**.)* **One further route was checked and rejected on the project's own rule**: reading the generator's usage text is parsing an undocumented diagnostic string, which `Security and licence` §13 rule 5 forbids and which [U6](#42-usable-composed-row-245) already refuses everywhere else in this document. **What it costs, stated:** about six-tenths of a second once per run, and three key pairs written to disk and removed. **What it buys:** an offered set read off the binary in front of the user rather than off a manual page (Fact 32's own constraint), and the no-generator answer, from one reading.

**T3. Excluded by decision, not by probe: the authenticator-hosted types (`ed25519-sk`, `ecdsa-sk`) and everything else the manual lists.** A `-sk` key's private half is completed by hardware Smoozy has no route to drive, its generation requires an enrollment interaction (observed: `Key enrollment failed: invalid format`, exit 255, with no token present), and `Security and licence` §6 already establishes that token-supplied keys can exist with no file at all — the shape this module's file-backed record does not hold. A key of an unsupported type in a key location is listed and shown as **not a supported type** ([4.4](#44-the-protection-reading-and-the-availability-answer-row-245) U6), which is the truth the spec's *unusable* vocabulary already carries. This is a stated limit of the supported set, not a fault; the spec promises a sensible default plus an advanced choice, not every type.

**T4. The default is `ed25519`, and it is a judgement, labelled as one.** The grounds: the manual's own no-argument behaviour — *"If invoked without any arguments, ssh-keygen will generate an Ed25519 key"* (documented — see [Sources](Sources/Keys.sources.md)) — and the same page labelling SHA1 `ssh-rsa` signatures not recommended, which is Fact 32's reading of that page rather than the sources file's. Where the probe finds `ed25519` absent, the default falls to `ecdsa`, then `rsa`, in that order — the same judgement applied down the list. The advanced control offers the other members of the offered set and nothing else.

**T5. A type never leaves the supported set at runtime.** The offered set may narrow with the binary; the accepted set is T1's three, fixed in this document, so no reading of any binary turns a working key of a supported type into an unusable one on the user's own computer. A key whose type the installed binary itself cannot read fails the fingerprint reading and is unusable as **unreadable**, with that said rather than a type verdict invented ([4.4](#44-the-protection-reading-and-the-availability-answer-row-245) U6).

## 3. The key locations, and the one-place premise (Row 242)

**L1. The usual key location, per system, is the per-user default directory OpenSSH's own manuals document, and it is one directory per system by this document's decision:**

- **macOS:** `~/.ssh` (documented; Fact 33).
- **Linux:** `~/.ssh` (documented; Fact 33).
- **Windows:** `%USERPROFILE%\.ssh` (documented, and documentation alone — Fact 33's Windows half; no Windows machine has run it).

**L1a. The location's path is a reading of the system and never a path this document composes.** The three strings above name a directory; **what resolves the home part of any of them is `Desktop app and delivery`'s platform adapter**, asked for a **user home directory** reading and answering with whatever that system's own call answers, exactly as `Desktop app and delivery` L3 already answers for the per-user application-data location. **Two ways of arriving at the path are closed by name.** It is never assembled from the login account name — I4, already stated, and `Desktop app and delivery` L3's own reason for closing it. And **it is never assembled from an environment value either**: on macOS the tool's own offered default was observed **not** to come from `$HOME` — run with `$HOME` set elsewhere, the offered default was the real account home (Fact 33, observed; see [Sources](Sources/Keys.sources.md)) — so reading `$HOME` is not established to reproduce what `ssh` and `ssh-keygen` do, and on Windows which of `$HOME` and `%USERPROFILE%` wins where they disagree is settled by nothing read. **The reading itself is owed by `Desktop app and delivery` and is not written here**: [Section 13](#13-unresolved) item 20 routes it, with the four promises of [L4](#3-the-key-locations-and-the-one-place-premise-row-242) as what breaks. [G9](#65-the-parent-directory-and-the-modes-row-248) supplies the path to the tool and takes it from this reading and from nowhere else.

**L2. `C:\ProgramData\ssh` is not a usual key location and nothing in it is ever managed.** Microsoft's own page names it for **host keys and server configuration**, and its `HostKey` defaults name private key files — none of the four default paths carries `.pub` (Fact 33). *(This quoted Fact 33's *"whether private key files live there is not stated on that page"* until 2026-08-22; that unresolved closed on 2026-08-21 and the answer is a stronger reason for the same rule, not a weaker one.)* It is machine-wide rather than the user's, and what it holds is the machine's own host keys — treating it as managed would put delete's destroying branch under private key files that are not the user's identities at all. A key file there enters Smoozy only by pointing, as a referenced key, exactly like any other path outside L1.

**L3. The one-place premise is false and the inherited rule is kept whole.** `~/.ssh` is the default and never the only place; `IdentityFile` and `-i` may name any path; a key can exist only inside `ssh-agent`; a PKCS#11 token supplies keys with no file (`Security and licence` §6). So: **every Keys entry records the path of the file that backs it, recorded at the moment the key entered — generated, discovered, or pointed at — and no path is ever synthesised from a name, a comment or an identity.** The scheme of [6.4](#64-the-filename-scheme-and-the-collision-row-243) composes a *new* name before a generation; it never reconstructs an existing key's path.

**What the row records is the canonical path of the file that actually backs the key, resolved at the moment the key entered.** A symbolic link — handed over by the picker, or found in the usual key location by discovery — is resolved to its target through the platform file adapter's canonical resolution ([W1](#91-ownership-is-a-derivation-from-the-canonical-path-row-251)'s, the same one), and **the target's path is what the row holds**; the link's own path is recorded nowhere. `Security and licence` §6's handed rule is what this is: Smoozy *"must never assume a listed key's file is `~/.ssh/<name>`"*, and a symbolic link is not that file. **This is not a synthesis and Row 242's inherited rule is untouched**: the path is still read from the world at the moment of entry and never composed from a name, a comment or an identity. **And it stores no kind** — the resolution answers *which file*, not *managed or borrowed*, which stays [W2](#91-ownership-is-a-derivation-from-the-canonical-path-row-251)'s derivation computed at the draw and at the act.

**What the row holds is therefore the one path every later clause composes from**: the companion names ([W5](#94-the-file-set-and-the-confirmation-that-names-it-row-247)), delete's file set and its confirmation ([W6](#94-the-file-set-and-the-confirmation-that-names-it-row-247)), the copy read ([W7](#95-the-copy-half-row-247)) and the unlinks and the re-check by path ([W8](#96-delete-rows-247-251-and-252)). **A link left behind is not one of the three names and nothing here removes it** — it was never the file that backed the key, so it is outside delete's set exactly as any other neighbour is, and the confirmation never names it.

**L4. What each of the four resting promises means with L1 singular.** The standalone list scans exactly the one L1 directory ([4.1](#41-what-in-a-key-location-is-listed-as-a-key-row-245)); a generated key is stored in it ([6](#6-making-a-key-rows-248-243-and-249)); ownership compares a key's canonical path against it ([9.1](#91-ownership-is-a-derivation-from-the-canonical-path-row-251)); and the public half and certificate are looked for **beside the private file wherever that file sits**, by [9.4](#94-the-file-set-and-the-confirmation-that-names-it-row-247)'s naming rule — the companion rule follows the private file, not the location.

**L5. A key with no file never enters Keys.** Agent-only keys and token-supplied keys have no private key file to point at, and pointing is done by selecting a private key file (`Preparation/Specs/Keys.md`, *Using a key that already exists*). They are not listed, not addable, and no promise in this document reaches them. Stated as a boundary rather than discovered at Build.

## 4. What in a key location is a key, what *usable* is, and how a list gets its answers (Rows 245, 253 and 423)

**Constraint:** Rows 245 and 253; Facts 32–35 as carried in `Preparation/Architecture/Rows/Keys.md`; `Servers` P1, P2, P12–P14; and `Security and licence` §6's traps — `ssh-keygen -l -f` accepts `known_hosts` at exit 0 and fingerprints it, so a successful fingerprint is not proof of a key.

### 4.1 What in a key location is listed as a key (Row 245)

**U1. The list is the union of two sets and nothing else.**

1. **Every key row in the local record whose recorded path lies in the usual key location or that was pointed at** — shown whatever the current state of its file, which is what keeps *broken managed keys are visible rather than silently absent* true: a row whose file is missing, unreadable or swapped shows as unusable with the reason, from the record, needing nothing from the file.
2. **Every regular file in the usual key location that passes the private-key container test and has no row** — a discovered key, given a row (local key identifier, path, fingerprint where readable, name where readable) at first sight.

**U1a. Discovery refuses a second row for a fingerprint a current row already holds.** [F4](#53-the-second-reference-new-location-against-replacement-row-246) and [F5](#53-the-second-reference-new-location-against-replacement-row-246) both live inside the **pointing** refusal, and discovery does not run them — so without this clause a private key copied to a second filename in the usual key location, or hard-linked there, gives two files that both pass the container test, both lack a row, and both take one, each with its own local key identifier and the same fingerprint. **The rule: a discovered file whose fingerprint reads and equals a current row's is refused a row, the existing row surviving and keeping its recorded path.** The existing row survives because a row holds one path ([R1](#10-what-keys-remembers-between-runs-and-what-it-genuinely-forgets-row-252)) and saved servers may already hold its identifier; moving a live row onto a file that appeared beside it would carry those servers onto a path their rows never named.

**What the rule cannot reach, said plainly rather than covered over: where the discovered file's fingerprint cannot be read, the comparison cannot run and the case is not caught.** That is [Section 13](#13-unresolved) item 6's class, which since U7b is **any protected key with no readable `.pub` beside it** and not the legacy-PEM rarity this sentence named until 2026-09-03; there the second file takes its own row. [F7](#54-the-identity-claim-row-293) is narrowed to what the mechanisms actually deliver rather than claiming construction. **[U2](#41-what-in-a-key-location-is-listed-as-a-key-row-245) is untouched:** the fingerprint read is still not the discriminator for *what is a key*, and this is a second use of a value the discovery pass has already read.

**U2. The container test is the discriminator, and it is a filename-free rule because no closed filename list is possible** (Fact 34 — a key location holds `config`, `known_hosts`, `authorized_keys`, `environment`, `rc`, `-cert.pub` certificates, `Include` fragments and an `agent/` directory of sockets). A file is a private key when its content opens with a private-key armour line — the `openssh-key-v1` container's `-----BEGIN OPENSSH PRIVATE KEY-----`, or a legacy PEM private-key armour — read in place, transiently, by the same header read `Security and licence` §6 owns. Everything else in the location fails the test and is not listed: `known_hosts`, `authorized_keys`, `.pub` and `-cert.pub` files, configuration, sockets, directories. **The fingerprint read is never the discriminator**: observed on the writing throwaway, 2026-08-20, `ssh-keygen -l -f` fingerprints an `authorized_keys` file at exit 0 — including a line carrying an options prefix — exactly as it fingerprints `known_hosts` (observed, one build — see [Sources](Sources/Keys.sources.md)); Fact 34's inference about `authorized_keys` is now an observation on that build.

**U3. A file that was never known and does not pass the container test is not shown.** The spec's *everything found there, usable or not* is a promise about keys — broken **managed keys** stay visible — not an obligation to render `known_hosts` as a broken key. A once-known key that decays past recognition stays visible from its row (U1 set 1), so nothing a user was ever shown goes silently absent.

### 4.2 *Usable*, composed (Row 245)

**U4. A key is usable when all of the following hold, and every clause is a local read, promptless, passphrase-free and network-free:**

1. **A regular file is present and readable at the recorded path.**
2. **Its content passes the container test** (U2).
3. **Its type is in the supported set** — read from the container/fingerprint reading, and the set is [T1](#2-the-supported-types-the-offered-set-and-the-default-row-241)'s three.
4. **Split into two clauses, because one verdict was carrying two different failures and only one of them is a swap.**
   - **4a. The fingerprint reads.** A failure here is *unreadable* and nothing more.
   - **4b. And it matches the fingerprint the row holds.** A mismatch is *no longer the same key Smoozy knew* — the swap case.

   **Only 4b raises `Security and licence` §5.2's swap event and with it [8.2](#82-keys-own-half-the-subject-the-marker-and-the-triggers-row-244)'s erasure. 4a failing raises none**, and the remembered passphrase is untouched — a file that cannot be read at this moment is the direction the spec has already chosen for a file that goes away, *"A key's file going missing does not cost the passphrase"*. §5.2's event is *the fingerprint changing*, and a read that produced no fingerprint is not this key's fingerprint changing.

   **A row that has never held a fingerprint is judged on 4a alone.** At first entry, and at every later check on such a row — a **protected** key discovered with no readable `.pub` is the standing case ([Section 13](#13-unresolved) item 6, whose class U7b widened from the legacy-PEM rarity this sentence named until 2026-09-03) — **4b is not evaluated, 4a is, and the reason shown is 4a's**, which is what [Section 13](#13-unresolved) item 6 already says such a key shows.

   **And a value taken from [U7](#43-the-readings-behind-the-clauses)'s public-half fallback is never 4b's evidence.** Where the row's fingerprint has only ever come from a `.pub` beside the file, a disagreement at a later check is not established to be a swap of the key — it is equally a `.pub` that changed beside a private half that did not — so **4b is not evaluated on it, the row reads *unreadable* by 4a, and no erase is raised.** U7 states the recording half of the same rule, and **[U7ab](#43-the-readings-behind-the-clauses) states which keys 4b therefore reaches at all — keys with no passphrase, and no protected key — with the cost of that written out.**
5. **The permission gate passes, on macOS and Linux:** the private file grants no access to group or other. Observed: a private key at mode 0644 is refused by the tool with `bad permissions` before the passphrase question is reached (`Security and licence` §6, Fact 37). Smoozy never widens permissions to mend this; the key shows unusable with the reason, and mending is the user's, outside Smoozy. **Labelled, because the rule is wider than the observation behind it: the gate is `ssh(1)`'s documented recommendation applied as a rule — *"ssh will simply ignore a private key file if it is accessible by others"* — and only mode 0644 has been observed to trip the client. Which modes short of 0644 do is established by nothing read**, so a key at, say, 0640 is refused by Smoozy on the strength of the recommendation and not of a reading — with what that costs riding at [Section 13](#13-unresolved) item 8. **On Windows the clause is not applied**: the gate's Windows form is an ACL judgement, not mode bits, and while the **requirement** is stated — the Windows port's own project wiki says private keys *"need to be owned by the user and no other user should have access to user's key files"* — that the client **refuses** a key whose access control is loose is established by nothing read, and inventing a verdict would manufacture unusable ones. *(This said the Windows form **is established by nothing read**, flat, until 2026-08-22; it was narrowed on 2026-08-20 at [Section 13](#13-unresolved) item 8 and not here.)* What that costs is carried in [Section 13](#13-unresolved) item 8 — a key the Windows client would refuse is caught at connect and reported as a failed connection, which forgets nothing and lies about nothing.

**U5. The passphrase is no part of *usable*.** A protected key whose passphrase Smoozy is not holding is usable; *is a passphrase available for this attempt without asking* is `Servers` P1's second question and is answered separately ([4.4](#44-the-protection-reading-and-the-availability-answer-row-245)). This is what keeps *"Existing keys protected with a passphrase are supported the same as ones Smoozy made itself"* true without holding anything.

**U6. The unusable reasons are a closed set and each is the clause that failed:** *file missing* (clause 1), *unreadable* (clause 2, **clause 4a**, or a read the tool refuses), *not a supported type* (clause 3), *no longer the same key* (**clause 4b**), *file permissions too open* (clause 5). Pointing at something that fails U4 is refused with the failed clause said plainly, and nothing is added (Row 245's second quote). No diagnostic string of the tool's is ever parsed to compose these — the clause that failed is Smoozy's own reading, which is `Security and licence` §13 rule 5 kept.

**U6a. Where the tool a reading needs is absent, the key is *not checked*, and that is a state above U6's set rather than a sixth member of it.** [G6](#63-the-generator-probed-never-assumed-row-248)'s probe can answer that no `ssh-keygen` exists on this computer, and every reading in [4.3](#43-the-readings-behind-the-clauses) that produces a type or a fingerprint is an invocation of it. **A key whose clauses could not be evaluated is not an unusable key** — nothing about it failed, and *unreadable* would be a statement about the key that is false; the keys are fine and the tool is absent.

- **No verdict is drawn that has not been read**, which is [U10a](#45-the-check-one-function-three-callers-row-253)'s own bound reaching its widest case: the row is shown as neither usable nor unusable, no member of U6's set is composed for it, and **nothing is handed to a caller in place of a verdict that was never read**.
- ***Not checked* is not an unusable reason**, so U6's closed set is unchanged. It is the absence of a verdict, and the reason for the absence is a property of the computer rather than of any key — which is why it is said once above the list and never per row (`Preparation/Specs/Whole app.md`'s *said once, not once per file*).
- **The cause is said where the readings are needed and not only behind the make-key dialog**: on the keys screen, and on the server list, whose own draw takes the same readings (`Servers` P12). [6.3](#63-the-generator-probed-never-assumed-row-248) carries the same statement into the make-key dialog, and it is one statement said in each place a reading was needed rather than three different ones.
- **The wording is Design's under Rule 10. That a false per-key verdict may not be shown is this document's**, and it is `Preparation/Specs/Whole app.md`'s third promise applied rather than a new grant.

### 4.3 The readings behind the clauses

**U7. Three readings serve every clause, all from `Security and licence` §6's established ground:** the in-place container header read (armour, cipher and KDF names — clauses 2 and the protection answer below); **the fingerprint read, which is two different invocations and not one**; and the filesystem's own answers for presence, readability and mode. **Where the private half's own read fails without prompting and a `.pub` sits beside it by [9.4](#94-the-file-set-and-the-confirmation-that-names-it-row-247)'s naming rule, the fingerprint is read from the public half instead** — the two halves of one pair are identical (Fact 76) — **which is the ordinary reading for every key that carries a passphrase, and a rare exception for nothing**; the residual where neither reads is [Section 13](#13-unresolved) item 6.

**Which keys each of the two invocations answers for, stated once here because four clauses were left describing the fallback as an edge case. Corrected 2026-09-03 at this module's code round 1.** [U7b](#43-the-readings-behind-the-clauses)'s `-y -f` derives the public half **from the private key itself**, so it needs the key unlocked: it answers for a key with **no passphrase** and is refused, promptlessly, for **every protected key** — including every key Smoozy itself makes with one. So the fallback is not the legacy-PEM rescue this clause first called it. It is what reads the fingerprint of every protected key, and the class it cannot reach is a protected key with no `.pub` beside it ([Section 13](#13-unresolved) item 6). *(This clause read* which is what keeps an encrypted legacy-PEM key readable at all *until the correction; [W7a](#95-the-copy-half-row-247), [Section 13](#13-unresolved) item 6's* Holds *and* Breaks *lines, and U7b's own closing bullet carried the same mistake and are corrected with it. **No mechanism moves**: U4's five clauses, U7a's two rules and W7a's comparison all stand exactly as written, and the code keeps every one of them.)*

**U7b. Which invocation reads which half, corrected 2026-09-03 at Build, and this clause named the wrong one for the private half from the day it was written.** It said the read was `ssh-keygen -l -f <path>` and that it *"works from the private file alone, with the `.pub` deleted"* — which is exactly what Fact 35 half A observed, **with the `.pub` deleted**, and which this clause then generalised into a claim about the ordinary case, where a `.pub` is sitting right there.

- **`ssh-keygen -l -f <private path>` answers from the `.pub` beside it whenever one exists.** Observed on the Creator's Mac, OpenSSH_10.3p1, 2026-09-03: two keys were made, `b`'s public half was copied over `a.pub`, and `-l -E sha256 -f a` then printed **`b`'s fingerprint and `b`'s comment**. With `a.pub` removed, the same call printed `a`'s own. So the invocation is a **public-half read** in every ordinary case and a private-half read only in the case the research happened to construct.
- **`ssh-keygen -y -f <private path>` derives the public half from the private key itself and is uninfluenced by the `.pub` beside it.** Same run, same machine: with `b.pub` still standing in for `a.pub`, `-y -f a` printed `a`'s own public line, whose fingerprint is `a`'s. **This is the private half's own read**, and it is the invocation this document should have named. It is promptless under §1's construction — `SSH_ASKPASS_REQUIRE=never` and standard input closed — and for an encrypted key with no passphrase available it ends at **exit 255** with the tool's own refusal, which is precisely the failure U7's fallback is written for.
- **No mechanism in this document changes, and that is the point of correcting it here rather than reopening anything — but four sentences describing what those mechanisms *reach* did change, and this bullet said they did not.** *(Corrected 2026-09-03 at this module's code round 1. It read* Nothing else in this document changes*, flat. The correction reached [U4](#42-usable-composed-row-245), [U7a](#43-the-readings-behind-the-clauses), [U7](#43-the-readings-behind-the-clauses) and [W7a](#95-the-copy-half-row-247) as mechanisms and left behind four sentences that still called the public-half fallback a rare exception: U7's own* keeps an encrypted legacy-PEM key readable at all*, W7a's* every `openssh-key-v1` key*, and [Section 13](#13-unresolved) item 6's* Holds *and* Breaks *lines. All four are corrected in place. **The mechanisms are untouched**, which is why this is a repair of the account and not a reopening.)* [U4](#42-usable-composed-row-245) clause 4a, clause 4b's swap, [U7a](#43-the-readings-behind-the-clauses)'s bound on a fallback value, and [W7a](#95-the-copy-half-row-247)'s comparison are all written as though the two halves' readings were distinguishable. **They were not distinguishable in the invocation this clause named**, which is what made all four of them silently inoperative: a row's fingerprint labelled *read from the private file* was, for any key with a `.pub` beside it, the `.pub`'s value; W7a compared the `.pub` against itself and could never refuse; and 4b's swap event fired on a `.pub` changing beside an unchanged private key, and stayed silent on a private key swapped under an unchanged `.pub`.
- **How it was found:** by a test written against W7a's own words — a key's `.pub` replaced with a different key's — which passed the comparison it was written to fail. The plan was the bug and it is repaired here rather than papered over in the code (`Preparation/Groundwork/Auditing.md`; the Build [Method](../Build/Method.md)'s *plan is the bug* case).

**U7a. The fallback value is bounded, because Fact 76 does not say what the fallback needs it to say.** Fact 76 establishes that the two halves of **one pair** print the same fingerprint. It does not establish that the file at `<path>.pub` is **this** key's public half, and in the only case where the fallback fires nothing can establish it, since that case is defined by the private file's own fingerprint being unreadable. The file beside a private key is the user's own file state — a dotfile sync, a backup restore, their own hand can put a stranger's public half there — and [W5](#94-the-file-set-and-the-confirmation-that-names-it-row-247)'s naming rule says where Smoozy looks, never whose key it finds.

- **A fingerprint read from the public half is recorded and used only where the private file's own read has never succeeded for this row.** Once a private-file read has answered, that value is the row's and the fallback is not consulted again for it — so a `.pub` appearing or changing beside a key whose private half reads is not a source of identity at all.
- **A disagreement whose only source is the fallback value raises no erase** ([U4](#42-usable-composed-row-245) clause 4's last paragraph): the row reads *unreadable* by clause 4a and the remembered passphrase is untouched. **The two rules are one rule reached from two directions** — what may be recorded, and what a later disagreement in it may cost — and neither may be read without the other.

**U7ab. What the swap check therefore reaches, with the cost written out rather than discovered. Added 2026-09-03 at this module's code round 1; nothing here is a new rule and no mechanism moves.** The two rules above, taken with [U7b](#43-the-readings-behind-the-clauses), settle a reach neither of them states: for a **protected** key every reading is a fallback reading — at entry and at every later check — so no value on such a row is ever clause 4b's evidence, **and clause 4b is the only thing that raises `Security and licence` §5.2's swap event**. So the swap check reaches **keys whose private half reads, which is keys with no passphrase**, and reaches **no protected key at all**. **A remembered passphrase only ever exists for a protected key**, so the erase-on-swap rule of [S3](#82-keys-own-half-the-subject-the-marker-and-the-triggers-row-244) item 3 can never fire in the one situation it was written for.

- **What that costs, stated:** for a key with a passphrase, a file swapped underneath it is not caught at a check. The row never reads *no longer the same key*, and the passphrase for the departed key stays held until the next connect.
- **What still holds:** the next connect's [S5](#83-a-passphrase-that-stops-working-row-250) supply runs the check, then the one local load, and the load fails against the key that arrived — which is a passphrase that stopped working, so §5.1's erasure runs, the item goes and the user is asked fresh. **It self-heals at the cost of one failed connect.** What is permanently lost is the row telling the user a swap happened.
- **Why the bound is stated rather than mended.** Giving clause 4b a second kind of evidence for protected keys — the public half's blob against the blob the row last saw — would put a second identity mechanism beside the fingerprint, which [F3](#52-what-the-value-is-used-for-and-where-it-appears) makes *the key's identity everywhere in the application* and which [F5](#54-the-identity-claim-row-293) already treats as a guard on the *form* of an identity rather than as an identity itself. [Section 13](#13-unresolved) item 6 met the same shape of question — a reading that cannot answer for a class of key — by naming the class and saying what breaks, and this follows it. Ruled by the code round's consolidator on 2026-09-03, the question having been put to the Creator and handed back.

### 4.4 The protection reading and the availability answer (Row 245)

**U8. *Is this key protected* is decided from the container, and the `-P ''` probe confirms, never decides** — `Security and licence` §6's rule, carried with its three narrowings intact (one build; four keys, one encrypted; the container layout documented on no manual page). For the `openssh-key-v1` container: cipher and KDF names `none`/`none` is unprotected, anything else is protected. **For the two legacy armours the answer is in plain text on the file's own first two lines, and it is two different reads under one rule rather than one — corrected 2026-08-23**, this clause having folded both into a single sentence about the second line, which is true of PEM alone. The armour and header lines are standardised and say it outright, and this clause said the rule had no ground until 2026-08-21.

1. **A legacy PEM key is decided on line 2.** RFC 1421 §4.6.1.1 and §4.6.1.3, read 2026-08-20 at `https://www.rfc-editor.org/rfc/rfc1421.txt`: *"The \"Proc-Type:\" encapsulated header field, required for all PEM messages, identifies the type of processing performed on the transmitted message."* and *"the field is required for all messages specified as \"ENCRYPTED\" in the \"Proc-Type:\" field."* **Line 1 decides nothing here** — both PEM keys carry the identical `-----BEGIN RSA PRIVATE KEY-----`.
2. **A PKCS8 key is decided on the armour label on line 1**, which is what RFC 7468 §10 and §11 fix, read the same day: unencrypted key structures *"are encoded using the \"PRIVATE KEY\" label"* and encrypted ones *"are encoded using the \"ENCRYPTED PRIVATE KEY\" label"*. **Line 2 decides nothing here** — it is base64 body.

**Observed on this Mac, 2026-08-23**, four keys made with `-m PEM` and `-m PKCS8` with and without a passphrase: the encrypted PEM key carries `Proc-Type: 4,ENCRYPTED` and `DEK-Info: AES-128-CBC,…` on lines 2 and 3 under a first line identical to the plain PEM key's, which carries neither; the two PKCS8 keys differ on line 1 alone, `-----BEGIN PRIVATE KEY-----` against `-----BEGIN ENCRYPTED PRIVATE KEY-----`. **The read is therefore ordered: the armour label on line 1 first, and where that label is a PEM armour, line 2 as well.** **So the same in-place header read this document already performs decides it**, on the same bytes, with no inference. **The `-P ''` probe stays as confirmation and it was not broken** — run against all four keys on 2026-08-23, with the `.pub` moved aside, it gave the right answer every time and promptlessly: exit 0 for both plain keys, exit 255 with *incorrect passphrase supplied to decrypt private key* for both encrypted ones. It was redundant, not wrong. The failure directions still hold where the probe is what answers: wrongly-unprotected costs an attempt Smoozy could see cannot work; wrongly-protected asks for a passphrase that does not exist and any entry fails the local load, said as a failed load. **[Section 13](#13-unresolved) item 6's inference half closes with this.**

**U9. *Is a passphrase available for this attempt without asking* is answered from the local record and never by reaching the store.** The answer is: the row's secret-store subject reference for the key-passphrase kind exists and is not marked as owing an erase. Reading the store itself could raise a system unlock prompt, which would break P1's *answerable without prompting*; the record read cannot. The store is reached only at the moment of use, inside the attempt ([8.3](#83-a-passphrase-that-stops-working-row-250)); a marker that turns out to be ahead of the store — a get returning *not there* — surfaces there, erases the reference under §5.1's order, and the availability answer is no from then on.

**U9a. The marker is only as good as the mark going with the reference, and this is the reading of `Security and licence` §5.1 that U9 depends on: an erase owed against a key-passphrase subject takes the row's reference with the mark whenever it completes, including where the sweep is what completes it.** §5.1's three writes are mark the subject, erase the item, and remove the row's reference and the mark together. **A crash between the first and the second leaves both the mark and the reference standing**, which is the state the sweep exists for; and a sweep that erased the item and cleared only the mark would leave a reference with no mark behind it — **U9 would then answer *yes* for an item that is gone**, `Servers` P1's second answer would be yes, and an automatic attempt would be made where P3 withholds one. **The reading that closes it is that the mark and the reference are cleared together, and the sweep finishing an owed erase is finishing §5.1's third write and not its second alone.**

**Where the mark is kept, corrected 2026-09-03 at Build.** This clause said the mark and the reference are *"two columns of one row"* and *"never two tables"*, and that made the mark die with the row — on delete, where the row is removed, and on a refused erase, where the reference is dropped and the mark is left naming nothing. **`Security and licence` [E3a](Security%20and%20licence.md#51-the-order-the-recorded-debt-and-what-a-crash-between-the-steps-leaves) now holds the mark in one durable register of its own**, keyed by kind and subject, which outlives any row. **Everything this clause argues is unchanged and is kept for the first time**: there is still one home for *is an erase owed*, U9 still answers from the local record and never reaches the store, and availability is still no from the instant write 1 lands — U9's read is the row's reference taken against that register. [Section 13](#13-unresolved) item 21 routes the confirming clause to `Security and licence` §5.1; **nothing here is a second rule about the sweep, and U9 still never reaches the store** — the whole point of the record-read marker is that it cannot raise a system unlock prompt, and reading the store to check the marker would break `Servers` P1's *answerable without prompting*.

### 4.5 The check: one function, three callers (Row 253)

**U10. The check is one function — U4's five clauses evaluated fresh against the row at the moment of the call — and the standalone keys view, the server list draw, a server dialog's key list and the connection attempt all call that one function.** *(A server dialog's key list added to the callers 2026-10-12, Creator-stated, the Creator's eighth notes (2026-10-11), note 3: the Add and Edit dialogs' key field is a dropdown of the usable keys, drawn first and filled in per U10a. **U10a. A list draws first and each key's verdict fills in behind it; no draw waits on a reading. An event whose key row is gone is discarded (P8).
- **Nothing is cached and U10 is unchanged.** Leaving the screen and coming back is a new ask. The verdict is never durable — R1's *derived, never stored* — so carrying it on P6's queue is not state under P7, which governs durable state.

## 5. The fingerprint (Rows 246, 293 and 429)

**Constraint:** Rows 246 and 293; Fact 76 as `Security and licence` §6 carries it — SHA-256 over the decoded wire-format public key blob, printed as `SHA256:` plus unpadded base64, independent of the comment and of file whitespace, identical from the private file or the public one; and §6's handed consequence — a fingerprint collision would attach one passphrase to two keys, the store contract cannot detect it, and the detection, if any, is Row 246's.

### 5.1 Where the fingerprint is read from (Row 246)

**F1. From the private key file, by path, with the tool's `-y -f` reading. Corrected 2026-09-03 at Build; this clause named `-l -f`, which [U7b](#43-the-readings-behind-the-clauses) establishes is a *public*-half read wherever a `.pub` exists.** The correction reached U7, U7a, U4 and W7a on the day it was made and did not reach this clause, which is the one headed *where the fingerprint is read from*; found by the counted gate before this module's first code audit.

- **It reads with no public file present**, and it is uninfluenced by a `.pub` that is present — which is the whole reason it is the private half's read (U7b's second observation).
- **It does not read under a passphrase Smoozy is not holding, and this clause claimed it did.** The claim rested on Fact 35 half A, which observed `-l -f` — the invocation that was answering from the `.pub`. Under `-y -f` an encrypted key with no passphrase available ends promptless at exit 255 with the tool's own refusal.
- **That refusal is not a hole**, because it is the exact failure U7's fallback is written for: the public half is read instead, identical by Fact 76, bounded by [U7a](#43-the-readings-behind-the-clauses), and the residual where neither half reads is [Section 13](#13-unresolved) item 6. What changes is which clause carries the encrypted-key case — the fallback, not this one.

**F2. When it is read: at entry, and at every check.** At entry — generation's verification, discovery, or pointing — the reading becomes the row's fingerprint. At every U10 check it is read again ([U4](#42-usable-composed-row-245) clause 4a) and compared (clause **4b**), and **the comparison is the swap detection**: a file swapped at the same path is caught by the fingerprint changing, and that firing is one of `Security and licence` §5.2's four events — the passphrase item is erased, because it belonged to the key that left. **Only 4b fires it.** A read that produced no fingerprint at all is clause 4a failing and is *unreadable*, which costs the passphrase nothing; and a value from [U7a](#43-the-readings-behind-the-clauses)'s public-half fallback is never 4b's evidence.

### 5.2 What the value is used for, and where it appears

**F3. The fingerprint is the key's identity everywhere in the application** — the row's display line (in the fixed-width face, always — `Preparation/Design/Keys.md`), the saved server's match value (`Servers` P16), the delete warning's join ([9.8](#98-the-warning-that-names-the-servers-row-254)), the second-reference refusal below, and the passphrase box's naming of a key whose row has no name ([S15](#85-who-raises-the-ask-and-what-the-box-is-handed-row-501)). A key's own fingerprint is shown deliberately; a **host** key's never is (`Security and licence` §5.4 — a different thing, not touched here).

### 5.3 The second reference, new location against replacement (Row 246)

**F4. Pointing at a key whose fingerprint equals a listed row's is refused, with a plain message naming the existing entry, and one entry kept.** The comparison is the fingerprint, over every current row, at the moment of the point.

**F5. Where both wire-format public key blobs are readable — both public halves present, or either key unprotected — the refusal compares the blobs beside the fingerprints.** Two different blobs under one fingerprint is refused **as two different keys that Smoozy cannot tell apart**, said in those words, rather than folded into one entry. **What the comparison guards is the identity arriving in the wrong form** — an MD5 fingerprint, whose collisions are documented as cheap ([F8](#54-the-identity-claim-row-293)) — rather than a SHA-256 collision, which nobody has produced. *(This called two blobs under one fingerprint **a genuine collision** until 2026-08-22; the reframing is 2026-08-20's and it reached [Section 13](#13-unresolved) item 1 that day, not this clause. The mechanism is unchanged.)* It is the only detection Row 246's handed consequence permits, and it is partial: where a blob is unreadable without a passphrase the comparison cannot run, and the refusal stands on the fingerprint alone. [Section 13](#13-unresolved) item 1 carries the residual.

**F6. Mending an unusable key has two offers and the fingerprint decides which happened.** **New location:** the pointed-at file's fingerprint must equal the row's — then the row's path is updated and nothing else moves; a non-matching file is refused as not this key. **Replacement:** a different fingerprint, taken deliberately through the replacement offer — the row takes the new path and fingerprint, **the remembered passphrase is erased** (it belonged to the key that left — §5.2), and servers still holding the old fingerprint show as needing a new key, which is `Servers`' side and already written.

### 5.4 The identity claim (Row 293)

**F7. Within Keys, two entries never share a fingerprint wherever the fingerprints can be read, and the rule is stated as what the mechanisms deliver rather than as construction.** Three refusals stand on three routes in: **F4** refuses a pointed-at key whose fingerprint equals a listed row's, **F5** refuses the detectable collision, and **[U1a](#41-what-in-a-key-location-is-listed-as-a-key-row-245)** refuses a discovered file whose fingerprint equals a current row's — *this clause read* by construction *and named F4 and F5 alone until it was narrowed, and discovery ran neither of them, so a private key copied or hard-linked to a second name in the usual key location took a second row.*

**What the three cannot reach is stated in the same honest shape [F5](#53-the-second-reference-new-location-against-replacement-row-246)'s own partiality already takes: where a fingerprint cannot be read, no comparison can run.** That is [Section 13](#13-unresolved) item 6's class at discovery — since U7b **any protected key with no readable `.pub` beside it**, and not the legacy-PEM rarity this sentence named until 2026-09-03 — and a file of that class beside a row of that class takes its own row with no comparison having been possible. **So the guarantee is bounded by readability and not by construction**, and that is the half of Row 293's promise this document keeps by mechanism.

**F8. The hash is pinned to SHA-256 explicitly, wherever a fingerprint is taken or compared, and an MD5 fingerprint is never treated as an identity.** **This rule was written nowhere until 2026-08-21, and it is the answer to a question this clause had been asking in the wrong form.** The printed form is selectable — `FingerprintHash` takes *"md5 and sha256 (the default)"* — and the two forms are not equally safe, so *can two distinct keys share a fingerprint* has no single answer. **In MD5 they demonstrably can**: RFC 6151, read 2026-08-20, *"The attacks presented in [KLIM2006] can find MD5 collision in about one minute on a standard notebook PC (Intel Pentium, 1.6GHz)."* and *"MD5 is no longer acceptable where collision resistance is required such as digital signatures."* **In SHA-256 nobody has produced one.** Relying on the default is not enough, because the default is a setting somebody can change; the hash is named at every call.

**What survived as unresolved was a citation and not a doubt, and it is now closed.** No first-party sentence says a SHA-256 collision does not exist, because an absence of published collisions is not a citable statement, and this document does not assert it. ~~**Whether Row 293's world-side clause may close on that basis is the Creator's**, filed as such — this project carries no equivalent worry about someone guessing a private key.~~ **CLOSED 2026-09-02 by the architecture runner's ruling: it closes on the footing this project already accepts elsewhere** — this project carries no equivalent worry about someone guessing a private key, which rests on exactly the same kind of reasoning, so demanding a citation here and not there was a standard held in one place only. **The rule this clause states is unchanged and is the part that mattered**: the hash is pinned to SHA-256 explicitly at every call, and an MD5 fingerprint is never treated as an identity. **Nothing is asserted about the world that no source says** — the clause claims the pin, not the absence of a collision — and no mechanism moves, every one below working identically under either answer. [Section 13](#13-unresolved) item 1 carries the closure; `Servers` [§16](Servers.md#16-unresolved) item 4 carries it from that side. What breaks if it somehow fails: F4 folds two keys into one entry and the store holds one passphrase against a key it does not belong to, except where F5's partial detection reaches. What holds: every mechanism above, which functions identically whatever the answer, and F5 — **which stays, and stops being described as detecting a genuine collision.** Under a pinned SHA-256 what F5 actually guards is that the identity has not been taken in the wrong form, which is cheap and worth keeping. **Cross-system stability is answered rather than observed on one machine — corrected 2026-08-21:** the figure is taken over bytes RFC 4253 §6.6 fixes for the protocol rather than for any operating system, and recomputing it by hand from the key's own bytes reproduced the tool's printed line exactly in both forms, so nothing is left for a system to vary. ### 5.5 The replacement act, and the cost said before it is pressed (Row 429)

**F9. The two offers of [F6](#53-the-second-reference-new-location-against-replacement-row-246) are two acts with different writes, and only the replacement writes anything the row has to state ahead of it. Added 2026-08-23, per Row 429.** F6 settles which offer a pointed-at file may take and what each does to the row; nothing stated that the replacement carries an erasure of its own, what it does to the server rows, or what composes the sentence the row shows before the control is pressed.

- **The picked file is judged before either act runs**: [U4](#42-usable-composed-row-245)'s five clauses, a failure refused with the failed clause said ([U6](#42-usable-composed-row-245)); then [F4](#53-the-second-reference-new-location-against-replacement-row-246) over every other current row. **A file whose fingerprint equals this row's own is the new location and never a replacement**; a file whose fingerprint equals a different row's is F4's refusal, which is what keeps [F7](#54-the-identity-claim-row-293) true across a replacement exactly as across a first point.
- **The new location's act is one write — the row's recorded path.** The fingerprint does not change, so [S1](#82-keys-own-half-the-subject-the-marker-and-the-triggers-row-244)'s keying, the server rows' match value (`Servers` P16) and the *Used by* line ([W11a](#98-the-warning-that-names-the-servers-row-254)) are untouched. **It costs nothing, and the row states nothing ahead of it.**
- **The replacement's act is two writes taken as one ordered unit** — `Security and licence` §5.1's erasure, then the row taking the new path and the new fingerprint — declared at [Section 11](#11-declarations--partition-units).

**F10. The erase fires because the act raises it, not because the keying went stale — the keying survives a replacement intact.** [S1](#82-keys-own-half-the-subject-the-marker-and-the-triggers-row-244) keys the store item against the **local key identifier and never against the path**, and a replacement keeps the row and therefore keeps that identifier: without the act raising it, the item stays reachable under the same subject while belonging to a key that is gone, and no reading anywhere would notice.

- **The trigger is [S3](#82-keys-own-half-the-subject-the-marker-and-the-triggers-row-244) item 3's second half, raised deliberately rather than detected** — the replacement offer's re-point raises `Security and licence` §5.2's swap event, and the erasure is §5.1's three writes in their order.
- **The erasure runs first, and §5.1's own first write is what closes the window**: marking the subject as owing an erase turns [U9](#44-the-protection-reading-and-the-availability-answer-row-245)'s availability answer to **no** at that instant, so no attempt taken between the two writes is told a passphrase is available.
- **A passphrase later entered for the replaced key is a first store and takes a new secret-store subject** (`State, identity and recovery` §2.2), because §5.1 removed the reference — and it removes it whether or not the store's own erase succeeded (§5.1: a removal is never blocked by a store failure; the mark stays and the sweep retries). **So the departed key's item is never reachable by the key that took its place**, including in the window where that item still exists.
- **Nothing else on the row is erased.** §5.2's swap event names the passphrase item alone; the **local key identifier** is untouched, which is what keeps the row and its servers' reference to it ([R1](#10-what-keys-remembers-between-runs-and-what-it-genuinely-forgets-row-252)).
- **What the act writes is four fields, not two, and the two added ones are the replacement's own — *this clause named the path and the fingerprint alone and left the other two untouched until it was repaired.*** A replacement is a **different key** with its own comment, so leaving R1's *name as last read* and *was-default-at-entry* bit standing would have the row permanently displaying the departed key's name — permanently where the replacement has no `.pub`, since R1 refreshes the name only from one — and would run [N1](#7-the-later-reading-of-is-this-name-the-default-one-row-249)'s duplicate-name reading against a name and a bit belonging to a key that is gone. **So the act writes the recorded path, the fingerprint, the new key's name as last read, and the was-default-at-entry bit recomputed against [G11](#66-the-default-name-pre-fill-row-249)'s default string at that moment** — exactly as [N1](#7-the-later-reading-of-is-this-name-the-default-one-row-249) computes it at any other entry, because a replacement **is** an entry of a key into this row. The partition unit is unchanged ([Section 11](#11-declarations--partition-units)); what the unit writes grows by two fields.

**F11. The replacement leaves the server rows unmatched, and this document re-points none of them.** A server row holds a pair — a local key identifier and the fingerprint beside it (`Servers` D3) — and the recognition `Servers` P16 hands to this document is taken **over both**: the key a server row names is the key row its identifier names **and** whose current fingerprint equals the fingerprint that server row holds. - **This document writes nothing into a server row, ever.** A server's fingerprint changes only by that server's own edit (`Servers` D15), and the mark clears at the next list draw however the key was mended (`Servers` P15). The route back is per server and is `Servers`'.
- **After the act the row's *Used by* line is empty and means exactly what [W11a](#98-the-warning-that-names-the-servers-row-254) says it means** — the read answered and no saved server holds **this row's current** fingerprint. **The servers the act stranded are the ones the statement named before it was pressed**, and each says so on its own list (`Servers` P12, P13). No line is kept on the key row for them, and no second value is recorded anywhere to hold them.

**F12. What composes the statement, and both halves are values the row already carries.**

## 6. Making a key (Rows 248, 243 and 249)

**Constraint:** Row 248 — four things applied in one act on three systems; Fact 39 as the row carries it — probe, never assume, never silently run Windows' elevated install command, and macOS does not create a missing parent directory; `Security and licence` §3.0 rule 2, §4 and §13 — no secret as a process argument or environment value, `-P` for nothing but the empty-passphrase probe; and the whole-app rule that local files are never silently overwritten.

### 6.1 The one act, and the tool (Row 248)

**G1. Generation is one act carrying four things: a type from the advanced control (default [T4](#2-the-supported-types-the-offered-set-and-the-default-row-241)), the comment the user typed, an optional passphrase, and a filename composed by [6.4](#64-the-filename-scheme-and-the-collision-row-243).** The tool is `ssh-keygen`, invoked as a process with an argument array and never through a shell: `-t <type>`, `-C <comment>`, `-f <path>` — the comment is arbitrary text passed as one argument, and a comment with spaces, apostrophes and non-Latin characters was observed accepted and carried into the `.pub` and the fingerprint line verbatim (observed — see [Sources](Sources/Keys.sources.md)). A comment is not a secret, so an argument is a permitted place for it.

**G2. With no passphrase, the invocation carries `-N ""`** — an empty passphrase is not a secret, and this is Fact 39's established route.

### 6.2 The passphrase route (Row 248)

**G3. A real passphrase reaches the generator through the askpass route and never any other way.** `-N` would put the user's passphrase on a command line another login can read (Fact 60; `Security and licence` §13 rule 1) and §4 closes `-P` to everything but the empty probe — so the one documented flag is closed, and the route is: the invocation runs with no terminal, `SSH_ASKPASS` naming the one-use helper and `SSH_ASKPASS_REQUIRE=force`, the helper being `Desktop app and delivery` S7's askpass helper, fed over the channel the broker opened for that one delivery. **The route is established by observation, not documentation — it is Fact 115, and the writing throwaway answered its Mac half.** Observed on the Creator's Mac, OpenSSH 10.2p1, 2026-08-20: `ssh-keygen -t ed25519 -C … -f …` with those two variables and standard input closed invoked the askpass program exactly twice — *"Enter passphrase for …"* and *"Enter same passphrase again:"* — exited 0, and wrote the pair; the key verifiably carries the passphrase: the `-P ''` probe fails at exit 255 with `incorrect passphrase supplied to decrypt private key`, and a load supplied the passphrase through askpass exits 0 and prints the public half byte-identical to the `.pub` (observed — see [Sources](Sources/Keys.sources.md)). **`ssh-keygen(1)` documents no askpass behaviour at all** — its ENVIRONMENT section holds only `SSH_SK_PROVIDER` (documented — see [Sources](Sources/Keys.sources.md)) — so the route is one build's observed behaviour, macOS only; Windows and Linux are unobserved and [Section 13](#13-unresolved) item 3 carries what breaks.

**G3a. What the route is per system, and on one of the three it is not there at all. Added 2026-09-03 at this module's code round 1, because G3 named the route and said nothing per system, and a reader took that for a route that exists everywhere.**

- **macOS: built and observed.** The channel is a Unix socket in Smoozy's own temporary area, the helper is Smoozy's own binary re-entered, and G3's own run is the observation. **A socket's path has a length limit far shorter than a file's, and the area's own path carries the account name** (added 2026-09-18 at step 10b's audit round's loose ends; no auditor of this document has seen it). *Observed on this Mac, 2026-09-18:* a channel whose path came to 116 bytes could not be opened, so no passphrase reached the tool and every connect with one failed; the same copy under a short folder connected. The limit is read from the system's own socket address rather than written down as a number. **So the channel's own name is as short as it can honestly be — a letter and a number unique in the run, with a name already present never removed but passed over — and where even that makes a path the system refuses, the act fails saying so**: no key with a passphrase can be made or used on that computer, which is the same size of consequence as Windows' below and is said the same way — a statement about the user's computer, in Design's words. **The area does not move**: L3a of `Desktop app and delivery` places it and nothing here reopens that.
- **Linux: built and unobserved.** It is the same channel and the same helper, on the same construction; no Linux computer has ever run it ([Section 13](#13-unresolved) items 2 and 3).
- **Windows: not built.** A Unix socket is not the shape there, what shape the route would take is a claim about Windows that nothing this project has read establishes, and **inventing one would be Rule 2 broken in the one place a wrong guess costs the user their key.** So **no channel is arranged on Windows and none is attempted**: a delivery that has never been arranged on any Windows computer is refused rather than guessed at.

**The consequence, written out because it is larger than G3's own act and this document stated only the smaller half.** The askpass route carries **both** deliberate passphrase deliveries — G3's generation, and [S5](#83-a-passphrase-that-stops-working-row-250)'s **one local load, which stands in front of every connection made with a held passphrase**. So on Windows **no key can be made with a passphrase, and no key that has one can be used at all**, including a key the user already owns and has been connecting with for years. What still works there is everything that opens no channel: every promptless read, every listing, every fingerprint, and a generation with `-N ""`.

**What the user meets is a statement about their key and their computer and never about a part of Smoozy** — the act is reported failed, plainly, the same ending G4's verification gives for a system that ignores the route. The wording is Design's under Rule 10 and is ruled: *Keys with a passphrase are not supported on Windows.* — `Preparation/Design/Keys.md` *Where the passphrase cannot be handed to the SSH tools*. *(Until 2026-10-24 this ended in an open marker, "Design — what a Windows user is told about a key with a passphrase". The words were ruled on 2026-09-13 at Build step 10a piece 4, under the Creator's standing delegation, and stood only in the code until this date.)*

**The named condition that would change this, stated so the limit is not read as permanent and not read as a promise either.** In order: one reading of the Windows OpenSSH port's own publication on whether its `ssh-keygen` honours the askpass route at all, under Rule 2 and from that project's own pages. **If it does, the channel is built and proved on the Windows machine this project builds and tests on, the same way the Mac's half was proved. If it does not, the limit above is the permanent answer** and `Preparation/Specs/Keys.md` keeps its Windows qualifier. **Nothing here schedules that reading and nothing waits on it**, and until it is taken the limit stands as written rather than as work that is coming.

**G4. The act verifies what it made, and the verification is what makes G3's gap fail loudly everywhere.** After the tool exits, and before any row is written: the private file at the composed path is re-checked by path (`Desktop app and delivery` F1's discipline), the container test runs, the fingerprint is read, **and the protection reading of [U8](#44-the-protection-reading-and-the-availability-answer-row-245) must agree with what was asked** — a passphrase was given and the container says protected, or none was and it says unprotected. Any disagreement, any missing file, any failed reading: the act is reported failed, the files the act itself just wrote are removed, and no row is created. **So on a system where the askpass route turns out not to be honoured, the outcome is a failed generation said plainly — never a key quietly weaker than the user asked for.** A passphrase mismatch (mistyped confirmation) surfaces the same way: the tool refuses, the act reports, nothing half-made survives.

**G5. A passphrase entered at creation is remembered, the same as one entered at a connect.** `Preparation/Specs/Whole app.md`'s Security concern: Smoozy remembers a key's passphrase *"as soon as it is entered"*. So the act's last unit puts it to the store — kind *key passphrase*, subject issued by the local record at first store (§2.2) — through the secret adapter, off the act's critical path: a put that fails is an ordinary store failure, said once under §3.0 rule 4's classification, and costs the key nothing; the passphrase is simply not held and the first connect asks, which is the spec's own fallback.

### 6.3 The generator, probed, never assumed (Row 248)

**G6. Whether a generator exists is probed at runtime — T2's generation probe is the reading — and never assumed from any documentation.** On macOS the binary was observed at `/usr/bin/ssh-keygen`, present with nothing installed (observed — see [Sources](Sources/Keys.sources.md)). rarity is a statement about frequency and not about behaviour, and the behaviour is the same on however few machines it happens.)* The machine is still a rare, customised one rather than every fresh Windows PC.

### 6.4 The filename scheme, and the collision (Row 243)

**G7. The scheme: the name the user typed, made safe as a file name, in the usual key location.** The typed name, which is also the comment, is the filename: *hyperstack* gives `hyperstack` and `hyperstack.pub` (the spec, Creator-stated 2026-10-08). Any character a file name cannot hold on a supported system (`/ \ : * ? " < > |` and the control characters) becomes `_`, and spaces and dots are trimmed from both ends. An empty result, or a name Windows reserves for a device (`CON`, `NUL`, `COM1` and the like), falls back to `smoozy_<type>` — `smoozy_ed25519`, `smoozy_ecdsa`, `smoozy_rsa`. The counter of G8 stays positional, not an identifier (§2.1 rule 7). Keys already made keep their files; none is renamed. *(Until 2026-10-08 the name was always `smoozy_<type>`, from the type and a counter and from nothing the user typed.)*

**G8. A collision is the ordinary case and the outcome taken is the whole-app rule's second: append a non-colliding name.** A second key with the same name is `<name>_2`, then `_3`, the first integer whose **three** names — `<name>`, `<name>.pub`, `<name>-cert.pub` — are all free in the location, checked immediately before the invocation. Appending rather than prompting puts nothing new in front of the user: no dialog the spec does not describe, and the filename surfaces only where Design already draws it — the row's path line, and the end of the made-key dialog that names the file it wrote. **The window between the check and the tool's write is not defended by the check, and the backstop is the tool's own refusal**: observed, `ssh-keygen` handed a `-f` naming an existing file with no terminal input available answers *"already exists. Overwrite (y/n)?"*, exits 1, and **changes nothing** — the file was byte-identical after, and the askpass helper was never consulted for it (observed, one build — see [Sources](Sources/Keys.sources.md)). A generation failing that way re-runs the composition once with the next free name; G4's verification judges the result as always. So *never silently overwrite* holds twice over — by the check, and by the tool's observed refusal — and the residual (the refusal is one build's observation) is [Section 13](#13-unresolved) item 4.

### 6.5 The parent directory, and the modes (Row 248)

**G9. Where the usual key location does not exist, the act creates it, mode 0700, before the invocation — because macOS's `ssh-keygen` does not create a missing parent (Fact 39, observed) and the spec's promise is a key *stored where the operating system keeps SSH keys*.** The directory is what that promise needs, so creating it is inside the promise rather than beside it; the escalation check and its declination are recorded in [Section 14](#14-moments-that-reached-the-creator). **G10. The key files carry the modes the tool itself sets — observed 0600 private, 0644 public — and Smoozy never changes them, in either direction** (`Security and licence` §6's constraint, kept).

### 6.6 The default name pre-fill (Row 249)

## 7. The later reading of *is this name the default one* (Row 249)

**N1. The reading taken is recorded-at-entry, not computed-at-question.** When a key enters Smoozy — generated, discovered, or pointed at — Keys computes the default string of [G11](#66-the-default-name-pre-fill-row-249) **at that moment** and records one bit on the row: *this key's name equalled the default when it entered*. The later question — a new or newly referenced key sharing a name with a listed key under a different fingerprint, where the spec warns unless *the shared name is the default one* — reads that bit on both rows: the warning is suppressed when **both** carry it, and fires otherwise.

**N1a. Two rows carrying no name do not share a name, so the warning does not fire between them.** [R1](#10-what-keys-remembers-between-runs-and-what-it-genuinely-forgets-row-252) records an unrecoverable or empty comment as **absent** rather than as a value, and absence is not a value two rows can hold in common: the spec's warning is about *two different keys under one name*, and two keys with no name are not that. Without this, two encrypted legacy-PEM keys with no `.pub` — neither of which can yield a comment, and neither of which carries the was-default bit — would fire N1's *fires otherwise* branch at each other and Smoozy would warn about a shared name that neither key has. **The rule reaches only the pairing**: a row with no name is still listed, still shown, and still tells one key from another by the fingerprint, which is what [F3](#52-what-the-value-is-used-for-and-where-it-appears) already says the fingerprint is for.

**N2. Why this reading and not the other.** The spec's quiet case is *two ordinary keys made on one machine*. The recorded bit is precisely *this name was this machine's default when the key appeared here*, and it survives the computer being renamed: two keys made before a rename still read as ordinary, which is the spec's ruling kept. **Computed-at-question inverts that ruling on every renamed computer**: the moment the computer's name changes, every older default-named pair reads as a clash and Smoozy warns about two ordinary keys — the exact warning the spec says to withhold — and it never recovers, because the old default never becomes current again. The recorded reading's own cost, stated: a key that enters *after* a rename carrying the old default name reads as non-default and can draw a warning beside an old key — a warning about what genuinely can no longer be shown to be two ordinary keys, which is the safe direction of the two the row names. The bit also makes Fact 12's steadiness gap non-load-bearing: nothing here re-derives yesterday's default, so whether the names survive a reinstall or a rename is a question this answer never asks. Both names' multiplicity is the adapter's solved problem (G11).

**N3. For a key that entered before this rule existed there is no such bit, and none is invented.** The register of what a row holds is [Section 10](#10-what-keys-remembers-between-runs-and-what-it-genuinely-forgets-row-252)'s from the first build; the case of a legacy row arises in no planned state.

### 8.2 Keys' own half: the subject, the marker, and the triggers (Row 244)

**S1. The keying: one store item per key — kind *key passphrase*, subject the secret-store subject issued by the local record against the local key identifier** (§2.2). The passphrase therefore belongs to the key and not to where its file sits, by construction: the path appears nowhere in the keying, so a file going missing costs nothing and a file coming back somewhere else finds the passphrase still held.

**S2. The availability marker is the row's subject reference** ([U9](#44-the-protection-reading-and-the-availability-answer-row-245)), which is what `Servers` P1's second question reads.

**S3. The four erase triggers, as this module raises them, and they are `Security and licence` §5.2's and §2 item 2's exactly, with nothing added:**

1. **The key deleted** ([9.6](#96-delete-rows-247-251-and-252)) — the passphrase item, the fingerprint, the path and the local key row.
2. **The key removed from Smoozy** ([9.7](#97-remove-from-smoozy-rows-251-and-252)) — the same, files untouched.
3. **The file swapped at the same path, detected by the fingerprint changing** (F2/U4 clause **4b**, and never by 4a failing) — the passphrase item; and the replacement offer's deliberate re-point (F6) raises the same trigger for the same reason.
4. **The user clearing the remembered passphrase** — that item and nothing else; the control is the row's, per `Preparation/Design/Keys.md`.

### 8.3 A passphrase that stops working (Row 250)

**S4. The detection is `Security and licence` §4's and is cited, not re-decided: *the passphrase stopped working* is established by a local load, never by a failed connection** — over a connection five causes collapse into one message at exit 255, and a failed connection is reported as a failed connection and forgets nothing.

**S5. Where the trigger fires, as Keys raises it.** When a held passphrase is supplied for an attempt, the supply is ordered: the U10 check first (fresh, at the attempt's moment — file present, container good, fingerprint matches, permissions pass), then **one local load** — the tool's `-y` read of the key, fed the held passphrase through the askpass route, once — then the connection. Observed on the writing throwaway: the load with a correct passphrase invoked askpass once and exited 0; with a wrong one, **once** and exit 255 — the tool does not loop the way `ssh-add`'s 59 invocations did (observed, one build — see [Sources](Sources/Keys.sources.md)). A load that fails after a passing check is attributable to the passphrase without parsing any diagnostic string, because every other 255 cause the tool separates only by undocumented text — missing file, bad permissions, malformed container — was just ruled out by the check in the same moment. On that signal the item is erased (§5.1) and the user is asked fresh on their next user-started connect; an automatic attempt finds the marker gone and makes no attempt (`Servers` P3). **Even the local signal is not proof** — §4 records the correct passphrase against a one-bit-corrupted key giving the identical message — and the cost is the one accepted there: one re-entry, against the spec's rule that a passphrase that opens nothing is never kept.

**S6. Nothing retries.** The load runs once per attempt, the passphrase is supplied once per attempt, no tight loop exists anywhere in this module, and the store is reached once per use — Fact 37's source-penalty finding is honoured by construction.

**S7. This and `Whole app`'s machine-password rule are one answer, not two.** The shared invariant, from §4: **a secret is forgotten only on a signal that separates the secret's own failure from the operation's failure** — the local load here, the separable elevation result for a machine password there — and every unseparated failure is reported as a failed operation and forgets nothing. A store get failing as *locked or refused* or *store unavailable* is an ordinary failure under §3.0 rule 4: reported on the thing that failed, the action offered again, the user not asked for the secret and the secret not forgotten.

### 8.4 A protected key on a computer with nowhere to remember (Row 315)

**S8. The mechanism is right and stays exactly as it is; what was missing is that its answer here is permanent.** [U9](#44-the-protection-reading-and-the-availability-answer-row-245) answers `Servers` P1's second question from the row's secret-store subject reference. Where `Security and licence` §3.3's **store standing** reads *never answered*, no reference is ever written for a key passphrase, so **the answer is *no* for every attempt for the life of that installation** — not for this attempt, and not until something is retried. `Servers` P3 then applies and no automatic attempt is made, which is the promise being kept rather than broken: *an automatic attempt never puts a passphrase prompt on screen*.

**S9. So the consequence, stated because neither spec states it: a protected key on such a computer never reconnects by itself and never survives an edit.** Both connections Smoozy makes on its own — the repair of a dropped connection, and the edit put-back — are withheld for ever, together with the additional connection of `Servers` 1.4. **A connect the user starts works normally**, asking for the passphrase each time (`Servers` P4), and that is the whole of the route the user keeps.

**S10. What the server is marked with says *cannot* rather than *not holding*, and that is this row's one behavioural change.** `Servers` P3 leaves the server marked with what is wrong. **Where the standing reads *never answered* and the key is protected, the mark states that the passphrase cannot be held on this computer**; where the standing reads anything else, it states the ordinary *a passphrase Smoozy is not holding*. The two read identically to a builder and differently to a user: the first is a property of their computer that will not change by waiting, the second is a miss that their next connect fixes. **The words are Design's; the bound is that a permanent condition may not be worded as a passing one.**

**S11. The repair does not spin against it.** `Servers` [3.2](Servers.md#32-the-standing-repair-which-never-ends-while-the-app-is-open)'s standing repair never ends while the app is open, and each of its attempts would take U9's check and be refused. **Where the refusal is the permanent one of S10, the repair for that server stops rather than retrying for ever**, and the server is left disconnected and marked. It is not a fourth entry in `Servers` 3.3's list — the period is not ended and the key is usable — it is the standing repair recognising an answer that cannot change while the standing does not.

**S12. Nothing here is a second notice.** `Security and licence` §3.3 says the one sentence once per installation, at the standing's first transition, and this module adds none of its own: [6.2](#62-the-passphrase-route-row-248) G5's failed put is still an ordinary store failure said once under §3.0 rule 4, and [8.2](#82-keys-own-half-the-subject-the-marker-and-the-triggers-row-244) S3's erase triggers are unchanged. **The mark of S10 is a server's condition and not a notice**, which is why it may stand permanently without repeating anything.

**S13. Checked against [Method](Method.md)'s three escalations and declined.** No new place to look — the mark sits where `Servers` P3 already puts one. Nothing to type beyond the passphrase the user is already asked for. Nothing that can be lost: the work is reachable by a connect the user starts, and the route out is the user's own — install a keyring, or take the passphrase off the key. **The one thing that would have escalated is the opposite answer** — making the automatic attempt anyway, which puts a passphrase prompt on screen for a connection the user did not start, against `Servers` Row 33's promise.

### 8.5 Who raises the ask, and what the box is handed (Row 501)

**S14. `Keys` raises the ask, and it is an ordinary window of the application rather than a tool's. Added 2026-08-25, per Row 501.** `Servers` [P4](Servers.md#91-before-a-connection-row-33) hands the question away in as many words — *"Who holds and supplies a passphrase is the module map's and `Keys`', and this document neither holds one nor asks for one itself"* — and [8.3](#83-a-passphrase-that-stops-working-row-250)'s S5 covered only the case where a passphrase **is already held**, so who puts the question on screen when none is held was written nowhere. **It is the module map's answer, taken rather than decided**: `Preparation/Specs/Whole app.md` — *"Keys holds and supplies the passphrase while Servers makes the connection"* — and `Preparation/Specs/Keys.md` — *"the user is asked and Keys keeps what they enter"*.

- **Three already-standing readings raise it and no other combination does**: the key is **usable** ([U4](#42-usable-composed-row-245)'s five clauses at [U10](#45-the-check-one-function-three-callers-row-253)'s check, taken at the attempt's own moment), it is **protected** ([U8](#44-the-protection-reading-and-the-availability-answer-row-245)'s container read), and [U9](#44-the-protection-reading-and-the-availability-answer-row-245)'s availability answer is **no**. Where the first is no, `Servers` P3 applies and no attempt is made, so **the box never appears for an unusable key**; where the second is no, there is nothing to ask for.
- **Only on a connect the user started, and by construction rather than by suppression.** For every connection Smoozy makes on its own P3 forbids the attempt, so no route to the ask exists from one. On a computer with nowhere to remember, [8.4](#84-a-protected-key-on-a-computer-with-nowhere-to-remember-row-315) is unchanged and reads through this clause: U9's answer is permanently no, so the ask is raised at **every** user-started connect, which is [S9](#84-a-protected-key-on-a-computer-with-nowhere-to-remember-row-315)'s *"asking for the passphrase each time"* seen from this side.

**S15. What the box is handed, and every value is a display-only field of a row that is already held.**

This is [U11](#46-the-pick-from-a-server-dialog-row-423)'s hand-over in the other direction and the same three fields; **this document supplies what exists and composes no name from anything else**, exactly as U11 does, and which of the three the box shows is Design's on the rule its own server list already carries (`Preparation/Design/Servers.md`: *"The name, or `username@host` where the server has none"*). **`Keys` does not read a server row for this**: [W11a](#98-the-warning-that-names-the-servers-row-254)'s read matches on the fingerprint, and one fingerprint can name several servers, so it cannot say which one is being connected to.
- **The key**: [R1](#10-what-keys-remembers-between-runs-and-what-it-genuinely-forgets-row-252)'s **name as last read** where the row has one, and **the row's own fingerprint where it has none** — never a path. *(This clause banned the fingerprint outright and gave no reason, which left a nameless key's box naming nothing at all: R1 records an unrecoverable or empty comment as absent, and an encrypted legacy-PEM key with no `.pub` is exactly that.)* **A key's own fingerprint is granted here rather than invented**: `Security and licence` §5.4 says so in as many words — *"A key's own fingerprint is a different matter and `Keys` shows it deliberately"* — and `Preparation/Design/Keys.md` already puts it under the name on every row of the list because it is *"what actually tells one key from another"*. **The rule is [U11](#46-the-pick-from-a-server-dialog-row-423)'s own shape: what exists, and nothing where there is none.** Which of the two the box shows, and how, is Design's under Rule 10; this document supplies the two values and composes no third.
- **Nothing else, and in particular nothing about the keeping.** No line here is composed from a stored value and no get is made to draw one — `Security and licence` §3.0 rule 6, which already makes the design's *says nothing about how it will be kept* true without this document adding a rule of its own. **The box carries no statement that a passphrase was ever held**; the one case where it carries anything more is [8.6](#86-the-ask-that-follows-an-erase-and-what-carries-the-message-to-it-row-502)'s.

**S16. The ask comes before the broker, and the askpass helper is never the asking surface — forced by what already stands, and written here because it stands nowhere.** `Desktop app and delivery` [S7](Desktop%20app%20and%20delivery.md#9-the-secret-adapter-and-its-helper) — *"The askpass helper is started by the one-use broker and lives for one delivery"* — and `Security and licence` §4 — *"The helper receives the passphrase over a channel Smoozy opened for that one use"* — describe a helper that **carries a plaintext Smoozy already holds**, so it cannot be where one is collected. It could not carry S15's values either: no secret and no context is ever a process argument or an environment value (`Security and licence` §13 rules 1 and 2), so a helper window could name neither the server nor the key. **The order at a user-started connect is therefore: S14's three readings, then the box, then [S5](#83-a-passphrase-that-stops-working-row-250)'s supply in its own order — the check, the one local load over the askpass route, the connection** — and the broker and the helper come into existence only at that last step, with a value already in hand. **A builder reaching for the helper's own window has this clause to stop them.**

**S17. What the box takes, and it goes to two places and no third.** The two outcomes are a value or nothing, in [U11](#46-the-pick-from-a-server-dialog-row-423)'s shape: **nothing** ends the act — no attempt is made, nothing is put to the store, and the connect is reported as one that did not happen, the same ending P3's no-attempt case has; a **value** opens the attempt.

- **The value has not come out of the store, and the rule that reaches it says so.** `Security and licence` §3.0 rule 6's third bullet: *"A value the user is entering has not come out of the store and this rule does not reach it… from the put onward the value is the store's and the rule binds."* Its two destinations are the ones §1.4 already names — **the one-use broker, for this attempt's one delivery**, and **the secret adapter's put** — and no module holds it, nothing draws it, and nothing writes it into the local record ([R2](#10-what-keys-remembers-between-runs-and-what-it-genuinely-forgets-row-252)).
- **The put is [G5](#62-the-passphrase-route-row-248)'s shape and takes the load's own signal as its moment.** `Preparation/Specs/Whole app.md`'s Security concern remembers a passphrase *"as soon as it is entered"* and offers no choice at the moment of entering; what fixes the instant is [S5](#83-a-passphrase-that-stops-working-row-250)'s local load, the same act's next step and the only thing that separates a passphrase which opens the key from one which does not. **The load succeeding is what puts it** — kind *key passphrase*, subject issued by the local record at first store (§2.2) — as an independent unit whose failure is an ordinary store failure said once under §3.0 rule 4 and costs the attempt nothing, exactly as at generation. **The load failing puts nothing**, which is `Preparation/Specs/Keys.md`'s rule that a passphrase opening nothing is never kept, and it keeps [U9](#44-the-protection-reading-and-the-availability-answer-row-245)'s marker from ever standing for a value that was never any good. **Nothing retries and no second box is raised inside one attempt** ([S6](#83-a-passphrase-that-stops-working-row-250)).
- **Where that value's own plaintext lives between the box and those two destinations is stated by no document, and this document does not decide it.** `Security and licence` §1.4 fixes three hops for a **stored** secret's plaintext and §2 items 3b, 3c and 4b are the standing arrangements for a value that is never in the store; neither reaches the field a user is typing into, which §3.0 rule 6's third bullet acknowledges exists without saying where it lives. [Section 13](#13-unresolved) item 18 carries it, routed.

### 8.6 The ask that follows an erase, and what carries the message to it (Row 502)

[Section 13](#13-unresolved) item 19.

Recorded 2026-08-25, per Row 502.** S5 was written for the trigger and the detection, and what it settled about the ask is where the ask is **not**: never on an automatic attempt, which finds the marker gone and makes none (`Servers` P3). **That half is untouched and this clause does not withdraw it.** What it did not settle is that the connect the user is standing in front of is itself a user-started connect. **Two things force the reading.** `Preparation/Specs/Keys.md` puts the ask in the place of the failure — *"Smoozy drops it and asks for it fresh rather than failing again with the same stale one"* — and deferring it to a later connect would cost the user a second press for a connect they already asked for and got nothing from, which no spec grants ([Section 14](#14-moments-that-reached-the-creator)).

## 9. Ownership, delete, remove, and the warning (Rows 251, 247, 254 and 252)

**Constraint:** Row 251 — the two branches are *delete the user's files* and *do not*, the wrong branch is unrecoverable, and it was confirmed by a user who was told something else; Row 247 — too wide deletes a stranger's file, too narrow leaves a private half behind after the user was told the key was gone; Fact 36; `Security and licence` §5.1 and §5.2; Rule 8's stated limit on the warning.

### 9.1 Ownership is a derivation from the canonical path (Row 251)

**W1. A key is managed when the canonical form of its recorded path has the canonical form of the usual key location as its immediate parent directory; otherwise it is borrowed.** Canonical means the platform's own full resolution — symbolic links followed, `.` and `..` collapsed, the same resolution applied to both sides — through the platform file adapter. *Immediate parent*: a file in a subdirectory of the location is not *sitting in* it.

**W1a. What the comparison does about a case-only difference is asked of the filesystem and never modelled here.** W1's enumeration reaches links, `.` and `..` and stops, and on macOS and Windows **a case-only difference is the commonest way of writing one path two ways** — which is [W3](#92-the-pointed-at-file-that-lies-in-the-location-row-251)'s own phrase. Both readings a builder could take on their own are wrong in one direction: a byte-for-byte comparison makes a key genuinely sitting in the location read **borrowed**, against the spec's *regardless of who created them*; a case-folding comparison makes a borrowed key on a case-sensitive volume read **managed**, and delete destroys a file Smoozy promised only to borrow — Row 251's unrecoverable branch.

- **So neither is chosen. Both sides are read back as the receiving filesystem stores them**, through the reading `Desktop app and delivery` F10a's third bullet already owns — *"Reading a name back as the filesystem stores it is the adapter's"* — and the comparison is made over those two readings. **It is a property asked of the volume rather than a rule about a platform**, which is the same move `Desktop app and delivery` §7 C10 makes for *is this name taken*: the question goes to the filesystem and the filesystem answers, because the answer differs between two volumes on one machine.
- **Labelled, because the ground is missing rather than thin: whether any of the three platforms' canonical resolution answers a case-only difference at all is established by nothing this project has read**, and nothing here guesses in either direction. The [companion](Sources/Keys.sources.md) carries it as a stated question, with both failure directions above as what breaks.

**W2. The derivation is computed when the controls are drawn and when the act runs, never stored** — the same shape as `Servers` P13's mark, so there is nothing to go stale and no recorded kind to disagree with the world. The Delete-against-Remove control the row shows (`Preparation/Design/Keys.md` — the control says the kind) is this derivation's output at that draw, and the act re-derives at its own moment.

### 9.2 The pointed-at file that lies in the location (Row 251)

**W3. Location decides, not the route in.** A file the user pointed at that canonically lies in the usual key location is **managed** — the spec's rule is *whatever sits in the operating system's usual key location*, *regardless of who created them*, and the fingerprint refusal (F4) has already closed the only aliasing case inside Smoozy, a second row for the same key. The same location written two ways, a path with `..` in it, and a symbolic-link route into the location all canonicalise to the same answer — and *the same location written two ways* includes a case-only difference, which [W1a](#91-ownership-is-a-derivation-from-the-canonical-path-row-251) is what covers.

### 9.3 The indirect routes (Row 251)

**W4. A symbolic link inside the location pointing out of it is borrowed** — canonical resolution lands the file outside, so delete never follows a link in the managed place out to a file that only looks managed. The wrong branch this closes is the unrecoverable one: destroying a file Smoozy promised only to borrow. **A hard link is invisible to path resolution** — a managed file deleted here may survive under another name elsewhere, which deletes the entry and this key's files and leaves the other name standing; that is the filesystem's own semantics, outside what Smoozy can see, and the confirmation names paths rather than promising the bytes are unrecoverable. Named, not defended.

### 9.4 The file set, and the confirmation that names it (Row 247)

**W5. The companion rule is Fact 36's, exactly: the public half is the private key path plus `.pub`; the certificate is the private key path plus `-cert.pub` — the `.pub` dropped rather than doubled.** The rule follows the private file wherever it sits (L4). **The path it is composed from is the row's recorded path, which [L3](#3-the-key-locations-and-the-one-place-premise-row-242) fixes as the canonical path of the file that actually backs the key** — so the companions are looked for beside the real private half and never beside a symbolic link that pointed at it, whose neighbours are not this key's files at all.

**W6. Delete's file set is exactly the members of `{path, path.pub, path-cert.pub}` that exist at the moment of the act, and the confirmation names exactly those, by full path.** Nothing wider — no backups, no similarly-named neighbours, no directory sweep — so *too wide* cannot happen by construction; and nothing narrower — the private half is in the set always — so *too narrow* is only reachable by a unit failing, which is then said, not silent ([9.6](#96-delete-rows-247-251-and-252)). A `.pub` or certificate stored under any other name is outside the documented naming rule and outside the promise; the warning's stated limit covers it.

**`path` here is the row's recorded path and therefore the real file ([L3](#3-the-key-locations-and-the-one-place-premise-row-242)), which is what keeps *too narrow* out of the one route that could still reach it.** Where a symbolic link outside the location points into it, [W1](#91-ownership-is-a-derivation-from-the-canonical-path-row-251) and [W3](#92-the-pointed-at-file-that-lies-in-the-location-row-251) rule the key **managed** — so a set composed over the link's own path would unlink the link, leave the private half standing at its real path in the usual key location, and [W9](#96-delete-rows-247-251-and-252)'s re-check by that same path would report *gone*. The row would be removed, and the next draw would discover the surviving private half as [U1](#41-what-in-a-key-location-is-listed-as-a-key-row-245) set 2 and list it as a new key: **the user was told the key was deleted and it comes back**, which is Row 247's stated floor and is Smoozy saying something worked when it did not. Recording the canonical path at entry closes it once rather than at each of four uses. **The link itself is not one of the three names, is not in the set, is not named by the confirmation, and nothing here removes it.**

### 9.5 The copy half (Row 247)

**W7. Copy reads `path.pub` and only that.** Present: its contents go to the clipboard. Absent: the control is unavailable — Smoozy does not go looking for a public half that isn't there, and does not reconstruct one from the private file (a `-y` reconstruction would need the passphrase for a protected key, which the control has no route to and no grant to ask for; **the control failing soft is the spec's own shape, and that is the whole of the reason**). *(This clause read* would ask *until 2026-08-29, and [Section 1](#1-what-binds-this-before-anything-is-decided)'s own 2026-08-23 matrix falsified it on this binary: under the construction every local read runs with, `ssh-keygen -y` against an encrypted key fails with an exit status rather than asking. The rule is unchanged — it never stood on the prompt — and only its stated reason moves.)* **The `path` it composes from is the row's recorded path and therefore the real private half ([L3](#3-the-key-locations-and-the-one-place-premise-row-242))**, so a key whose row was entered through a symbolic link still finds the public half sitting beside its target rather than looking for one beside the link.

**W7a. Where the private file's own fingerprint is readable, the `.pub` beside it is fingerprinted and the two are compared before the contents reach the clipboard.** A stale `.pub` left beside a key the user re-made is the user's own file state and Rule 8 owes them no rescue for it. **What is not past that line is Smoozy showing one fingerprint on the row and copying a different key's public half without noticing** — the app being wrong on screen about its own state, which `Preparation/Specs/Whole app.md`'s third promise never excuses, and which costs the user a rented machine they can never connect to, on a failure Fact 37 establishes collapses five causes into one message. **Nothing new is read for it**: for any key whose private half yields a fingerprint — **which under [U7b](#43-the-readings-behind-the-clauses) is every key with no passphrase, and no protected key at all** — [U4](#42-usable-composed-row-245) clause 4a reads exactly that value at the same moment, and the public half's own fingerprint is [U7](#43-the-readings-behind-the-clauses)'s existing reading. *(Corrected 2026-09-03 at this module's code round 1. This read* every `openssh-key-v1` key, so everything Smoozy generates and nearly everything a user has*, which was true while the private half's read was `-l -f` and is false for every protected key under `-y -f`. **The comparison is unchanged**; what moves is the statement of which keys it runs for — and it runs for fewer than this clause claimed, which is a cost stated in the bullet below rather than a mechanism repaired.)*

- **A disagreement makes the control unavailable with the reason said**, in the same shape as an absent `.pub`. Nothing is deleted, nothing is rewritten, and no `.pub` is reconstructed — the file is the user's and stays exactly as it is.
- **Where the private read is refused, the comparison cannot run and the limit is stated rather than a verdict invented.** **That is every protected key** — whose row takes its fingerprint from the `.pub` in the first place ([U7a](#43-the-readings-behind-the-clauses)), and where comparing the file against itself would answer nothing. **Copy stays available there and says what it could not check** — the same honest ending [Section 13](#13-unresolved) item 6 already takes. *(This read* the legacy-PEM class of item 6 *until 2026-09-03; the class is wider and is stated rather than narrowed, so the guard is off for exactly the keys a user is most likely to have, and copy has to say so.)*

### 9.6 Delete (Rows 247, 251 and 252)

**W8. The order:** confirmation ([W6](#94-the-file-set-and-the-confirmation-that-names-it-row-247), with [W11](#98-the-warning-that-names-the-servers-row-254)'s warning where servers rely on the key) → **the file units, private half first**, each an unlink through the platform file adapter with the outcome established by re-check-by-path after (`Desktop app and delivery` F1's discipline — gone is the outcome), **every one of those paths composed from the row's recorded path and therefore naming the real file** ([L3](#3-the-key-locations-and-the-one-place-premise-row-242), [W6](#94-the-file-set-and-the-confirmation-that-names-it-row-247)) → **the erasure unit**: §5.1's three writes — mark the subject owing an erase, erase the passphrase item, remove the local key row, the subject reference and the mark. The partition declaration is [Section 11](#11-declarations--partition-units)'s.

**W9. ### 9.7 Remove from Smoozy (Rows 251 and 252)

### 9.8 The warning that names the servers (Row 254)

**W11a. The match value and the wording are [W11](#98-the-warning-that-names-the-servers-row-254)'s unchanged: the fingerprint and nothing else, the matching servers named by their labels, never counted.

**W12. Where the server rows cannot be read at that moment, the warning says so and never reads as good news.** The two states are distinct and never conflated: *no saved server uses this key* is said only on a **successful** read returning no match; a failed read produces *Could not check which servers use this key*, named as what could not be done, with the user still free to proceed — the spec lets them go ahead in every case, and `Whole app` forbids the one thing this rule closes: a failure presenting as *nothing relies on this key* in front of an unrecoverable act.
