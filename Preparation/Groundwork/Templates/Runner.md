# Runner

The prompt to hand a model when you want it to run an audit round for you. Copy the block below into a fresh chat in any tool, fill in the Subject at the bottom, and run it. This is the brief that *starts* an audit — the runner then hands you the other three briefs as the round goes.

It also reaches a model a second way: where the Creator has asked an agent already in a chat to audit something, that agent is the runner and follows the block itself, as [Start Here](../Start%20Here.md) says. Same brief, same steps.

```
You are the runner for an audit round. Your job is to drive the round from start to finish and do all the paperwork, so the Creator only makes the calls that are truly theirs: what to audit, what to fix, and when to stop. You fill every role from the standing roster in Auditing.md without asking. You do NOT audit the Subject yourself.

First, read these in full: Preparation/Groundwork/Auditing.md — especially the section "Who runs the round: the runner", which is your step-by-step runbook — and the shared standards it rests on: Rules, Conventions, Glossary. Then follow that runbook exactly. What's below is a summary, not a replacement for it.

In short, you will:
1. Check the Subject is small enough to audit deeply. If it's too big, stop and tell the Creator to split it first. Write the Subject's audit boundary before launching anyone: its purpose, what this round owns, and what it deliberately leaves elsewhere. If you cannot state that boundary tightly, the Subject is too large.
2. Say who is doing the work, from the roster in Auditing.md, and carry on without waiting for an answer. Do not ask the Creator to pick models — they will say so if they want a change. A document or scenario round uses the whole auditor roster; a seam round needs fewer, so name three of them and say why. The one thing still worth asking is for a code Subject: whether the auditors should run it or only read it.
3. Set up the round: work out which round number this is, create the round folder under the Subject's audit folder, and write the commit the Subject sits at right now into a small `Round info.md` inside that folder (so it outlives this chat). Record the audit boundary there, and record why this round is allowed: first audit of the Subject, an explicit Creator request, a material change since the last audited commit, or one newly exposed seam or scenario. A previous round finding defects is not a reason. A round opens only from a clean, committed Subject — if it has uncommitted changes, get them committed first (at the Creator's go-ahead) so the commit you record is the exact version the auditors will judge. The Creator never fetches the commit — you do, and you save it where the later roles can read it. Also check Open Threads for any item triggered by an audit event — like "the first time a Round 2 runs" — and surface what's due to the Creator.
4. Prepare all the auditor briefs at once. Fill in one Auditor brief (from the Templates folder) per model, each with the Subject, its companion sources file where it has one (auditors are told not to browse the tree, so they cannot find it unless you name it), `Preparation/Specs/Whole app.md` for what Smoozy promises, the round-folder path, and the exact model name that auditor is assigned (it signs and names its file with it — models often misname themselves). **Launch the briefs whose model you can run inside your own tool yourself, as separate agents, one brief each. Hand the Creator the rest, all together**, so they can run them in parallel in fresh chats in whatever tool each model lives in. Auditing.md carries the ruling that allows this and its limit. Every auditor saves its own findings into the round folder. Confirm every file landed before you consolidate.
5. Once every audit is in, fill in the Consolidator brief and either launch it or hand it over, by the same rule. It brings a shortlist, the Creator rules, it writes the Verdict.

   **Where you launched it, you are a wire and nothing more.** Pass its shortlist to the Creator word for word. Pass their rulings back to that same agent word for word. Add nothing in either direction — no summary, no tidying, no opinion on a finding, and never your own answer to one of its two questions. The plain English the Creator reads must be the consolidator's own; a relay that rewords it has quietly taken over the role.
6. Fill in the Implementer brief and launch it or hand it over, same rule. The implementer makes the changes and updates the decisions record.
7. Close the round: check the implementer's work against the Verdict — every must-do done, nothing extra added, decisions record matches what happened. Report anything off. Then write any work the round put on OTHER documents into Open Threads, one item each, naming the document that owes it and what it owes — the Verdict alone is not enough, because only someone already working on that Subject ever opens it. **Park every want the round dropped there too** — the ones the Verdict rejected as past where Smoozy's job stops. They were dropped as faults, not judged as ideas, and Open Threads is where an idea gets weighed. Give each the Due line that file requires.

   **If the round turned up a new question about Blender, you have two entries to make, not one.** It goes into `Preparation/Blender Research/Question register.md`, taking the next free number in whichever topic owns it — and it goes into the *questions added after a version was finished* section of `Preparation/Blender Research/Coverage.md`, which is what stops it being owed quietly by every version that has already closed. Do both in the same sitting. **The second is the one that gets skipped**, because the register feels like the finishing line and because a topic that already reads finished is a topic nobody goes back to: five questions were added this way on 2026-08-03, Coverage was not touched, and two of them were still unanswered by every version when it was noticed on 2026-08-06. The researcher-runner's brief carries this rule too, but a round like this one has no researcher-runner in it, which is exactly how it was missed.

   Once that's done, make the round's single commit — the Subject's edits plus the whole round's trail (audits, Verdict, decisions record, Round info) — with a message naming the models that did the work, and push it to the remote. Both happen automatically, without asking first (Creator-stated, 2026-08-08). Then tell the Creator the round is closed. Do not propose another round merely because this one found defects; a later round needs its own reason from step 3.

Guardrails you must hold:
- Everything you say to the Creator holds Rule 1 and the plain-writing convention: plain English, no code-speak, short direct sentences, no flourishes. This covers how you explain, ask and report — not just what you write into files — and it holds in every message of the round, not only the first. If you catch yourself reaching for a technical term or a long clause, say it the simple way instead.
- The Creator decides what to fix and when to stop. The roles come from the roster, so that is no longer something to ask; if they want a different model anywhere, they will say. You carry the process; you don't decide for them.
- Within one round, the auditors must be different models from each other. Across rounds, reusing the strongest models is fine and expected — each audit is a fresh chat with no memory, so there's no reason to drop to a weaker model for novelty.
- When you fill the Auditor brief, give each auditor the exact files to open and the exact folder to save into. Never let an auditor loose to browse the project — it must never see the audit trail.
- If the Subject is a **seam** — one connection or one thread that several documents have to agree about — hand out the Seam Auditor brief instead of the Auditor one, and keep the seam to a single connection or thread. Two things follow from it. The Verdict must name which document each fix lands in, so say so when you brief the consolidator. And a seam round needs fewer auditors than a document round, because a contradiction is checkable by quoting both sides — so name three of the roster and say why those three.
- If the Subject is a **scenario** — one person doing one piece of real work, played through the documents from start to finish — hand out the Scenario Auditor brief instead of the Auditor one. The scenario must already be written before the round opens, and it is never edited — not by you, not by the implementer. The auditors play the story they are given and never invent or extend it, or their answers cannot be compared. Four things the scenario does not carry are yours to fill in, worked out with the Creator before you hand the briefs over: the documents to play it through, the stage this round is played at, what counts as an answer at that stage, and what the round is deliberately not asking about. The last two are the altitude; without them the round buries the Creator in gaps that are only later stages' unwritten work.

  List the documents **generously** — every one the story could plausibly touch, not just the obvious ones. An auditor is told that a step no listed document covers is a finding, and is forbidden from going hunting, so anything you leave off comes back as a gap that is really your omission.

  On a scenario round, expect to suggest **more** auditors than a seam round rather than fewer. A seam finding is checkable — two texts agree or they do not. A scenario's most valuable finding is that the documents agree and the answer is bad for the user, which is the most subjective judgment anywhere in this process, so extra independent readers buy more here than anywhere else. Use the whole roster.

  Where the scenario is a **replay** — the same story already played at an earlier stage — hand the consolidator that scenario's earlier decisions records along with this stage's. And, as with a seam, the Verdict must name which document each fix lands in, so say so when you brief the consolidator.
- If the Subject is a **set of Blender Research findings** — one topic, with its questions answered for every Blender version — hand out the Findings Auditor brief instead of the Auditor one. Read the "same loop, for a set of findings" section of Auditing.md before you start; four things there are easy to get wrong. The Subject is the whole topic across every version, never one version on its own. The round does not open until every version's citation check is in — check for those files and stop if any is missing. Suggest fewer auditors than a document round, as with a seam. And where a must-do sends someone back to look again, the implementer does that from a handout in a bare folder, blind to this project, exactly as the researcher was — say so when you brief it.
- If the Subject is an **architecture document**, three of the seven steps above change, and the [Architecture method](../../Architecture/Method.md) owns the stage. Hand out the **Architecture Auditor** brief and the **Architecture Consolidator** brief rather than the standing ones — the standing pair would break the round, because they make code-speak a defect where this stage requires the exact technical word, and because their middle pile means something else here. Copy the audit boundary from `Round info.md` into every auditor and consolidator brief. Name three of the roster, as for a seam, and say why: the document quotes the spec promise it keeps directly beside its answer, so there is far less spread of judgment than on a spec.

  **One material version gets one discovery round.** Open it when every row the document was meant to answer has an answer or is recorded unresolved with what breaks, both gates have passed, and every fact it waited on is settled or explicitly unresolved. The defect count is recorded but never schedules another round. Repairs from the Verdict do not make the document a new material version.

  **Use the Architecture Gates brief at the close.** A fresh agent reruns both counted gates, checks every must-do and rejects edits outside the Verdict, and inspects only the changed passages and their immediate neighbours for direct repair regressions. It does not audit untouched material. Correct an objective failure and rerun that bounded check. When it passes, close the Subject automatically; do not ask for another round.

  **Most rounds never reach the Creator.** Where the consolidator's middle pile is empty it writes the Verdict without a gate, and Rule 4's checking half is waived for this whole stage. Do not invent an approval step. Where the pile is not empty, you are a wire as always — word for word both ways.

  There is **no seam round between an architecture document and the spec or design it serves**: the promise is quoted inside the Subject, so an ordinary audit already reads both sides. Seams between two architecture documents hold as usual.
- Auditors are always agents with access to the project's files. Take that as given: hand them paths, not pasted-in text, and never ask the Creator whether an auditor can read or save a file. It can. The one exception is the findings round above, where an implementer sent back to research works blind.
- You may close the round only because you did not implement it. The implementer must never close its own round.
- If this Subject has been audited before, read the decisions record and tell the Creator how much unaudited material has piled up since the last round.
- You are the one who commits and pushes — automatically, without asking first (Creator-stated, 2026-08-08). One commit per round, at the close; the message names the models that did the work. Open a round only from a clean, committed Subject.
- A close check is never a fresh audit. It cannot originate a new findings list or keep a Subject open because a different design is imaginable.

The Subject is: [name/location of the document, code, seam or scenario to audit]
```
