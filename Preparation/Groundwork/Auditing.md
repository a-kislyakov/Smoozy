# Auditing

How a document, a piece of code, the fit between documents, or what the documents give a user doing real work gets checked once, repaired, and closed with bounded verification.

The clearest way to understand auditing is to watch one happen. So let's follow a single document — say, the File Browser module's Specs document — all the way through.

## The Creator picks something to audit

Not everything gets audited; the Creator decides what's worth it. Here, the Creator decides the File Browser Specs document matters enough to harden. The thing being audited — a document, a chunk of code, a **seam** between documents, or a **scenario** played through them — is called the **Subject**. The walkthrough follows a document; the other three are the same loop with a different Subject, and each gets its own section at the end.

**A Subject must be small enough to be audited deeply.** Hand a model a sprawling document and it spreads its attention thinly across the whole thing, returning findings that are broad and shallow. Hand it one tight document about the file browser and it goes deep. So when a Subject is too big for an auditor to be thorough about, the answer is to **split it before auditing it** — not to audit it harder, and not to run more rounds. More rounds on something too large only produce more of the same shallow findings.

**An audit is a bounded attempt to disprove the Subject, not a search for enough faults to justify having run one.** No findings is a valid and useful result. The Subject's opening purpose is a hard ceiling: an auditor may find that the Subject fails its purpose, but may not enlarge the purpose and call the missing material a defect. A finding must point to a permitted situation and a concrete promise, instruction, or invariant that fails in that situation. “This could say more,” “another design is possible,” and “Build will still have to choose something” are not defects.

## Several auditors read it, blind

The Creator hands the same document to several strong models at once — each a **different** model, since running the same one twice gives you one opinion twice, not two. Each is an *auditor*, and each gets the same package — its *brief*:

- the document itself, together with its companion sources file where it has one — that file is part of the Subject, not audit trail, and its citations are as open to challenge as anything in the body,
- and its instructions: judge it against its own stated purpose (its opening line), be exhaustive, work alone, and sign the audit with the exact model name it was assigned from the roster — models often misname themselves, so the assigned name is the authoritative one.

This brief isn't retyped for every audit — it's a reusable template (kept in `Groundwork/Templates/`), filled with the Subject each time.

**Auditors are always agents, with access to the project's files.** This is settled and is not a per-round choice: the Creator does not use plain chat windows for auditing. So a brief hands an auditor file paths rather than pasted-in text, and the auditor saves its own audit into the round folder itself. Nobody needs to ask whether an auditor can read a file or write one — it can, always. *(Creator-stated)*

The crucial part: no auditor sees any other auditor's work — they are blind to *each other*. That's deliberate: you want several genuinely independent judgments, not the same opinion repeated. But blindness is only about others' *judgments*. An auditor may freely read the project's shared standards — Start Here, the Rules, the Conventions, the Glossary — and anything the Subject links to. That's just context, and it makes for a sharper audit. What it must never see is the **audit trail**: other audits, past verdicts, or the decisions record — and that ban wins even when something it *is* allowed to read links to one.

An auditor also brings something this project has no other way of getting. Nearly everything Smoozy does leans on the world outside it — Blender, the rented machine, the system it runs, the services it talks to — and Rule 2 says no agent's memory of any of that counts as a fact. But that rule governs *stating* things, not *doubting* them. So an auditor is asked to use everything it knows to spot a promise resting on something nobody has checked, and is forbidden to use the same knowledge to answer it. The finding is a question, and its fix is only ever to label the claim, record what breaks if it turns out wrong, and park the question for research. Without this said out loud, an auditor reads Rule 2 and censors itself, and the audit shrinks to checking whether the document agrees with itself.

Two things stop that flooding the round. It counts as a finding only where **the plan breaks if the answer comes back the other way** — Rule 2's own test — so a promise that merely gets weaker is not one. And the auditor's reasoning, which it has to give or the doubt can't be weighed, is marked as a guess and never handed to whoever goes and researches the question: a researcher told what to expect stops looking.

**A finding has to be a promise Smoozy breaks.** Rule 8 sets the line, and *Where Smoozy's job stops* in the [Whole app spec](../Specs/Whole%20app.md) is where it is written; every auditor is handed that document and reads it before it judges anything. A user who supplies a folder of assets with pieces missing, sets a file up to write nothing worth having, or shuts a laptop with transfers running has done that to themselves, and the plan owes them no rescue. Two things are still always fair: Smoozy going quiet or claiming something worked when it did not, because telling the truth is on Smoozy's side of the line whoever caused the trouble; and a mistake Smoozy itself makes.

Where an auditor sees something helpful past the line, it says so plainly and calls it a **want**. The consolidator drops it with that reason, and the runner parks it in [Open Threads](Open%20Threads.md) at the close, where it is decided on its own merits. Without this, every round returns safety nets nobody asked for and they have to be turned down one at a time.

Each auditor hands back an *audit*: a list of *findings*. Every finding says:

- **where** — the part of the document it's about, quoting the exact words that show the problem,
- **what** — the problem,
- **why** it matters,
- **which kind** — a **defect** (something wrong, unclear, missing, or self-contradictory), a **preference** (a judgment call where reasonable people could differ), an **unchecked fact** (the document is sound as written but rests on something outside it that nobody has confirmed), or a **want** (something helpful that sits past where Smoozy's job stops),
- **how serious** — High, Medium, or Low. On an unchecked fact that means how much breaks if the answer comes back wrong, never how sure the auditor is: a shaky doubt about something a whole module rests on outranks a confident one about a detail,
- and a **suggested fix** — always, even if tentative.

There's also a small free space at the end for general thoughts that don't fit a single finding, and a **Leave alone** list: what the auditor judges right as it stands, especially where another reader might be tempted to change it. This is evidence, not praise. It gives an auditor somewhere honest to put the judgment that a passage needs no intervention, and gives the consolidator a way to tell a discriminating audit from a fault list written for the sake of contributing. The first Architecture round tried the device before it became standing practice; all three lists were substantial, and the consolidator used their agreement to reject a proposed change and to weigh the findings around it. Label: **Creator-stated** (2026-08-13).

An audit carries **no quota of findings**. An auditor files everything that meets the finding bar, worst first, including none. That is not licence to pad: a thin finding filed to lengthen the list wastes the consolidator's attention and buries the ones that count, and severity has to mean something.

## The consolidator turns many audits into one verdict

Now one model — the *consolidator*, named in the roster below — reads every audit and boils them down. It is normally a model that also audited this round, and that is settled: a fresh chat holds no memory of its own audit, and one model family is not one opinion. Label: **Creator-stated** (2026-08-07).

First it groups the findings that are really the same point wearing different words. Then it sorts them by **who decides**, and that sort is the heart of the role. Most findings hold no choice at all — a document contradicting itself, a pointer aiming at nothing, a sentence that has to be read twice. Putting those in front of the Creator one at a time buries the few that are genuinely theirs under the many that are not. So every finding lands in one of three piles:

- **Fix it** — a fact about the Subject, where the fix has one sensible form. It goes ahead unless the Creator pulls it, and they see it as a single line rather than an argument.
- **The Creator's** — carrying it out would change what the user gets, or there are two honest answers and choosing between them is a product decision. Only these get the full treatment: what it is, a worked example of somebody running into it, and the fix.
- **Dropped** — with its reason. This is where a **want** lands: something helpful that sits past where Smoozy's job stops, dropped by that name so the runner parks it at the close.

The consolidator also reads the auditors' **Leave alone** lists as evidence. Agreement there can show that a proposed change is not a repair, or that the surrounding answer is sound even where one detail is not. An empty or perfunctory list beside a long fault list is a reason to examine that audit more carefully. The list never becomes findings of its own.

One question settles the sort: if the consolidator did this without asking, could the Creator fairly say it had decided something that was theirs?

**The Creator's pile holds at most two findings, and that is a hard cap.** Label: **Creator-stated** (2026-08-07). A round can turn up a dozen honest product choices, and ruling on a dozen of them, round after round, is more than the Creator will keep doing — so the plan gets worse, not better. The two are the ones that genuinely shape the app: what the user gets, or a choice the whole product leans on. Where a round has more, the consolidator **takes the two biggest and decides the rest itself**, and each one it decided shows in the *fix it* list as a single line saying plainly that it was the consolidator's call and which way it went. Nothing is hidden and nothing is skipped; the Creator can pull any line. A round with no genuinely app-shaping choice brings **none** — the cap is a ceiling, not a quota, and inventing a decision to fill it is worse than bringing nothing.

**Trivia is grouped.** With no cap on findings, one round can produce fifty small ones, and fifty lines is as unreadable as a wall of argument. So near-identical small fixes go into the list as one line — *eleven small wording fixes* — and every one of them is written out in full in the Verdict. Grouping is for things that are alike and small. Two unrelated fixes are two lines however minor they are.

Headcount used to make this call and no longer does. It stays visible, because knowing that three auditors landed on the same thing is worth knowing — but two agreeing was never proof they were right, and one auditor alone is often right about the most important thing in the round. On an **unchecked fact** it counts for nothing whatever: several models doubting the same thing about Blender is one training set speaking three times, not three independent readers. **Severity** still orders what the Creator sees inside each pile.

It also does one thing no auditor can do. An auditor sees a single document, so it can be right about a problem and still suggest a fix that breaks a project-wide standard — most often by writing a second copy of something, which *Every fact has one home* forbids. So the consolidator reads the Rules and the Conventions and weighs each **suggested fix** against them. Where a fix would breach a standard, it keeps the finding, says which standard the fix breaks, and puts the choice to the Creator rather than carrying it forward as written. This is not the consolidator auditing the Subject — the finding is still the auditor's — and unlike the decisions-record check it is never skipped, including on round 1.

Then it brings the Creator the three piles, and the two live ones work differently. A **fix it** finding goes through *unless* the Creator pulls it. One on the Creator's own pile goes through *only if* they accept it. Either way, nothing reaches the implementer that the Creator hasn't seen, and only what survives this gate becomes a **must-do**. What comes out the far side is the **Verdict**: the final must-do list, everything that was rejected and *why*, and the commit the Subject sat at when the round began.

**It comes in one message, and the Creator answers once.** The whole shortlist — the fix-it list, the two decisions, the dropped pile — arrives together, so the round costs one reading and one reply rather than a conversation. The consolidator answers a follow-up question, of course; what it does not do is meter the round out in instalments.

**And it says all of it in dead plain English.** This is the role that talks to the Creator, so the whole plain-writing rule lands here hardest: short sentences, no code-speak, nothing ornamental, and no assumed technical knowledge. Each of the two decisions carries a **concrete example of the user being let down by the plan as it stands** — a real moment, not a description of the problem — and then one line on how the fix stops it happening. A finding the Creator cannot feel is a finding they cannot rule on.

This hands the consolidator real weight — it decides what the Creator only ever meets as one line, and with the cap of two it decides most of the product choices as well. Three things hold it. The *fix it* pile is shown in full, so anything wrong in it can be pulled. Every call it made instead of asking is labelled as its own, so the Creator can see where the weight fell. And the round is not closed until the runner has checked the implementer's changes against the Verdict. Choose the consolidator's model knowing all of that.

## The implementer applies the verdict

A fresh chat — the *implementer* — takes the document and the Verdict and makes the changes. Its model comes from the roster below. It has seen none of the auditing; its model may be one that audited or consolidated, because a fresh chat remembers nothing of that.

Its discipline is narrow on purpose: **free in how it writes each fix, but it touches nothing beyond the must-do list.** No freelance improvements, no polishing of untouched paragraphs. If it spots something new and genuinely good, that waits for a future round — slipping it in now would put unaudited words into the document. And if a fix can't be made cleanly — it clashes with something else, breaks the flow, or writing it would break one of the Rules or Conventions — the implementer stops and asks the Creator rather than force a bad edit. A must-do is not permission to breach a project standard: the consolidator is meant to have caught that, and the implementer is the last chance to.

When it's done, it saves the new version and writes one entry into the **decisions record**: what changed this round, and what was rejected, with the reasons.

## Closing the round

A round isn't finished until someone checks the implementer's work **against the Verdict**: was every must-do actually carried out? Was anything changed that the Verdict never asked for? Does the decisions record match what really happened?

Git makes this a single glance at the diff. The runner does it — it never did the implementing, so it isn't checking its own work. (The Creator can also do it directly.) What must never happen is the implementer closing its own round — nobody should check their own work.

## Round two — and why the memory sits where it does

A hardened document can go around again only for the independent reason set out below: an explicit Creator request, a material change, or one newly exposed seam or scenario. Same loop: a fresh set of audits, blind to each other — and the models can be the same strong ones as last time, since each audit is a new chat that remembers nothing of the round before.

But this time they're blind to something else too — **the history**. They never see what earlier rounds decided. They read the current document with completely fresh eyes and say whatever they think, even if it repeats a past round.

The **decisions record** — the running memory of everything that has happened to this Subject — goes only to the *consolidator*, never to the auditors. That is the important bit. When a fresh auditor re-raises something the Creator already settled, the consolidator checks it against the record and sets it aside, recording it in the Verdict's rejected list as already decided — *unless* the auditor brings new evidence or a concrete failure path the earlier decision did not consider. Several models repeating the same concern is not new evidence and never reopens a settled point by itself.

The record holds one more thing, and it matters here. A settled document doesn't stay frozen: a new feature can land in it between rounds (Rule 7), and every such addition leaves its own line in the record. So the consolidator alone knows which parts of the Subject no auditor has yet seen — usually the newest, least-examined text — and can weight the round accordingly. The auditors read the whole document without knowing which parts are old and which are new. That's deliberate: the newest text is what most needs a close, independent read, and it only gets one if the auditors aren't told which parts they can safely skim.

Keeping the memory at the consolidator instead of the auditors is what lets us have it both ways: the auditors stay honest and unbiased, and settled points still don't waste the Creator's time.

It is also why the Subject itself carries **no marks** saying which of its parts have been audited. A stamp reading "settled, three rounds" is a piece of the audit trail, and putting it inside the one document every auditor is guaranteed to read would bias exactly the auditors this whole process works to keep independent. Git already answers the question far more exactly anyway: every Verdict records the commit its round began from, so whatever has changed in the document since then is precisely what no auditor has seen.

## A round ends; another does not start by default

One material version of a Subject gets one discovery round. The implementer repairs that Verdict, and the runner checks those repairs against it. That closes the round. The repair check is not another audit: it checks that every must-do landed, nothing outside the Verdict changed, and the repairs did not directly contradict each other or the surrounding text. It does not hunt through untouched material for new findings.

A later round needs a reason independent of the previous round's finding count: the Creator explicitly asks for another; a material change has landed since the audited version; or a new neighbour exposes one named seam or scenario worth checking. **Material** means a new or changed promise, product decision, ownership boundary, or constraint that changes what another document or Build must do. Verdict repairs, wording, links, signatures, source labels, and coverage administration do not qualify merely because they changed lines. Where a material change is local, the new Subject is that changed decision and its immediate seam, not the whole settled document.

This gives up the fiction that repeated model reads prove perfection. They do not. The process instead buys one independent attempt to break a stable Subject, applies what survived consolidation, verifies the repair, and moves on. A real defect found later still goes back under Rule 7; it is fixed because there is evidence for it, not because another open-ended round was due.

When the Creator says *"I want to audit X,"* any agent in the project should know this is what they mean, and step into the runner's shoes:

1. **Check the size.** Is the Subject small enough to audit deeply? If it's too big, say so and stop — it needs splitting first (see the top of this document). For a seam, too big means more than one connection or one thread. For a scenario, it means more than one person, one sitting, or one sequence of steps — and, where it belongs to a family, differing from its siblings in more than one thing.
2. **Say who is doing the work, from the roster above** — the auditors for this kind of Subject, the consolidator, the implementer — and carry on without waiting for an answer. Do not ask the Creator to pick models; they will say so if they want a change. The one thing still worth asking is for a **code** Subject: whether the auditors should run it or only read it. The auditors in one round must differ from each other; two chats of the same model give you one opinion twice, not two. Across rounds, reusing the same strong models is expected — each audit is a fresh chat with no memory of the last.
3. **Set up the round.** Work out which round number this is, create the round folder under the Subject's audit folder, and write the commit the Subject sits at right now into a small `Round info.md` inside that folder — so the version being judged has a home that outlives any chat. Write the audit boundary there too: the Subject's purpose, what this round owns, and what it deliberately leaves elsewhere. Record the independent reason this round is allowed — first audit, explicit Creator request, material change, or one newly exposed seam or scenario. The previous round's finding count is not a reason. A round opens only from a **clean, committed Subject**: if it has uncommitted changes, get them committed first (at the Creator's go-ahead) so the commit you record is exactly the version the auditors will judge — otherwise the starting commit points at a version nobody read. The Creator never has to fetch this, and later roles read it from there rather than trying to work it out again. While setting up, also check Open Threads for any item whose trigger is an audit event — like "the first time a Round 2 runs" — and surface whatever is now due to the Creator.
4. **Prepare all the auditor briefs at once.** First pick the brief that matches the Subject: **Auditor** for a document, **Seam Auditor** for a seam, **Scenario Auditor** for a scenario. (A set of Blender Research findings is not audited this way at all — see below.) Then fill in one per model, each carrying the exact model name that auditor is assigned — the auditor signs and names its file with it, because models often misname themselves. Every brief also names `Preparation/Specs/Whole app.md`, because an auditor cannot apply Rule 8's line without reading where Smoozy's job stops, and it is told not to browse for it. A scenario brief needs two more things the scenario itself does not carry: the documents to play it through, listed generously, and the round's **altitude** — the stage being played, what counts as an answer at it, and what the round is not asking about. Launch the briefs whose model you can run inside your own tool yourself, as separate agents, one brief each. Hand the Creator the rest, all together, so they can run them in parallel in fresh chats, each blind to the others. (See the ruling below.) Each auditor saves its own findings into the round folder. Confirm every file actually landed before consolidating.
5. **Consolidate.** Once every audit is in, fill in the Consolidator brief and either hand it over or launch it, by the same rule as step 4. Where the Subject is a scenario being replayed at a later stage, hand over its earlier stages' decisions records too, since it is the same story and the same judgment calls come round again. The consolidator reads the audits, brings its shortlist, and the Creator rules. The consolidator writes the Verdict.

   **Where you launched it, you are a wire and nothing more.** Pass its shortlist to the Creator **word for word**, pass their rulings back to that same agent word for word, and add nothing of your own in either direction — no summary, no tidying, no opinion on a finding, and never your own answer to one of the two decisions. The plain English the Creator reads is the consolidator's, and a relay that rewords it has quietly taken over the role.
6. **Implement.** Fill in the Implementer brief and hand it over or launch it, the same way. The implementer makes the changes and updates the decisions record.
7. **Close the round.** Check the implementer's work against the Verdict (the three questions above). Report anything off. This is bounded repair verification, not another audit; do not hunt untouched material for new findings. Then look at whether the round decided anything that falls on **other** documents — a fact that belongs elsewhere, a marker another document owes, a dependency no map records. The Verdict records those, but a Verdict is only ever opened by someone already working on that Subject, so work decided in one round waits to be found by luck. Write each one into [Open Threads](Open%20Threads.md) instead, naming the document that owes it and what it owes, with the **Due** line that file requires, and delete the item once it is carried out. **Park the round's dropped wants there too** — the findings turned down as past where Smoozy's job stops. They were dropped as faults, never weighed as ideas, and this is where an idea gets weighed. While you are in there, check every other item's Due line against what this round has just changed: anything whose trigger has now fired moves into that file's **Due now** section and is offered to the Creator as work. A parked item is only ever found by somebody going to look, and a close is when something has just landed that might have fired one. Once all that is done, make the round's **single commit** — the implementer's edits to the Subject together with the whole round's trail (the audits, the Verdict, the decisions record, and `Round info.md`) — with a message naming the models that did the work, then push it to the remote. Both happen automatically, without waiting on the Creator first. Label: **Creator-stated** (2026-08-08). **One commit per round is about the round's trail arriving whole, not a ban on committing while the round runs** — Creator-stated, 2026-08-20: *when* to commit and push is the agent's judgment and never the Creator's, so a long round that commits at its milestones and pushes each time is doing this right. What the rule forbids is a round whose trail reaches the remote in pieces that do not stand on their own, or not at all. Do not open the next one merely because this one found defects. Then tell the Creator the round is closed.

The Creator's part is ruling on the findings (step 5) — one reading, one reply. The runner carries the rest, including everything that used to be asked: it fills the roles from the roster, it records the starting commit, it makes the round's single closing commit and pushes it, it closes the round, and because it reads the decisions record anyway, it can tell the Creator how much unaudited material a document has built up since its last round.

**The runner launches every role whose model it can run inside its own tool, and the Creator runs the rest by hand.** So a runner working in Claude Code launches the Claude roles as separate agents — with the roster above, that is Opus 5 auditing, consolidating and implementing — while **DeepSeek V4 Pro is the Creator's to run in Zed** and **Gemini 3.7 Flash High is the runner's to run through the `agy` CLI**. Label: **Creator-stated** (2026-08-19). The runner still composes every brief in full and saves each as its own file in the round folder, so the Creator's part is opening a chat and pasting; and it still checks every quotation in what comes back before the audit is used.

Blindness holds either way; it comes from what each role can see, not from whose hand is on the keyboard. What used to stop this was money: the Creator spreads the roles across tools and models, some far cheaper than others, and a runner launching everything would put an expensive model on work that does not need one. Launching a role the roster already assigns to the runner's own tool does not do that — the same model does the same work either way, so nothing costs more and the Creator opens fewer chats. Label: **Creator-stated** (2026-08-07), replacing the ruling of 2026-07-30 that the Creator ran every role. Do not widen it into launching models the round would otherwise have run somewhere cheaper.

One caution the runner must respect. The **auditors write into the audit folder but must never read it.** An auditor is told to open only the files it's given and never to browse the project or open `Audits/`. This keeps them blind to each other's judgments. It's an instruction, not a wall — so if it ever proves leaky, a stronger fix waits in Open Threads.

## Where everything lives

Everything for one Subject sits together in its **audit folder**, under the top-level `Audits/` folder — one audit folder per Subject, named after it, with one folder per round inside. It holds the individual audits, each round's verdict, and the running decisions record. The Subject itself stays where it normally lives, easy to find. (The exact file and folder names are set out in the Conventions.)

Versions are never archived by hand. Git already keeps the full history of every document and every line of code, so each round's verdict simply notes the commit the Subject sat at when the round began — and you can always see exactly what a round changed, or roll it back.

## The same loop, for a seam

A document can be sound on its own and still disagree with its neighbour. The Keys spec describes the hand-off to Servers; the Servers spec describes the same hand-off from its side; the module map describes it a third time. Nothing in the walkthrough above checks that all three say the same thing. An auditor is told to read the Subject and what it points to, and not to go hunting through the rest of the project — which is what keeps a single audit deep, and is worth keeping. So the gap closes by widening what counts as a Subject, not by loosening the auditor's brief.

A **seam** is one connection between documents, and it is audited exactly like a document: same rounds, same four roles, same Creator gates, its own audit folder, its own decisions record. It takes two shapes:

- A **pair seam** — two modules that connect, read against each other and against what the [module map](../Specs/Whole%20app.md) says about the pair. The list of pair seams is already written: every *Connects to* line in the map is one.
- A **thread seam** — one behaviour running through many documents. What a disconnect does, what stopping and clearing means, how a warning is worded. This is where contradictions hide, because no single document owns the thread.

The size rule binds here hardest. A seam is *one* connection or *one* thread — never "the specs, read against each other." Hand an auditor five documents and the word "consistency" and you get the same thin, broad findings that too-large Subjects always produce.

**What a seam auditor looks for.** Not whether each document is good — that is the ordinary audit's job, and a seam round does not repeat it. A seam finding is that two texts do not fit: they state the same fact differently, one promises what the other never delivers, one hands work to a document that does not accept it, or a marker in one points at a home in the other that is empty. So a seam finding rests on **two quotes, one from each side**, and is worth nothing without them.

**The usual fix is ownership, not matching.** Most disagreements are the "every fact has one home" convention already broken: two documents both state a thing, and one has drifted. Editing both until they agree leaves two copies to drift again. The fix is to decide which document owns the fact and make the other point at it. Only a fact with genuinely one home is fixed for good.

**A seam round needs fewer auditors than a document round.** A contradiction is checkable — either the two texts disagree or they do not, and the finding quotes both sides. There is far less spread of judgment than in an ordinary audit, so extra independent readers buy less. So a seam round takes three of the roster rather than all of them, and the runner says which three and why. **Since 2026-08-19 the roster is three, so this no longer cuts anything** — a seam round takes all three, and there is nothing left for the runner to choose.

**The Verdict must name where each fix lands.** A seam must-do is a change to a particular document, so the Verdict says which one. That means two kinds of record get written, and both are needed. The seam's own decisions record gets the round's entry, like any Subject. On top of that, every document the round edited gets a line in *its* own record — because that edit happened outside that document's rounds, and its next auditors have not seen it. That is Rule 7's requirement for any change to an already-audited document, and it is what stops a seam fix from slipping into a spec unrecorded.

Blindness is unchanged. A seam auditor reads several documents because that is its Subject; the ban is on the audit trail, and it holds as firmly as ever.

Seams also run **between stages** — a Design that quietly contradicts the Spec it was built from, an Architecture that serves a Design it has drifted away from. Those are audited the same way, with one difference: the fix goes to the higher document, or down from it, never sideways. It is the same rule as *when the plan is the bug*, below.

**When a seam gets audited.** Two moments. The first is at a **stage close** — a stage's seams are checked before the stage is called complete, because a contradiction carried into the next stage is copied into everything built on it. The second is when a settled document changes in a way another one leans on; the runner already writes that kind of work into [Open Threads](Open%20Threads.md) at a round's close, and a seam it names is a candidate for its own round. Which seams are worth a round, and when, stays the Creator's call like every other Subject.

A seam round uses its own auditor brief — the Seam Auditor template in `Templates/`. The ordinary Auditor template judges one document against its own stated purpose, which is not what a seam round asks for. The Runner, Consolidator and Implementer templates serve every kind of round.

### One seam has a drawing on one side, and it runs without stopping

**The Design stage's mockup seams are the exception to the Creator's gate, and only they are.** Each Design document is read against the part of `Preparation/Design/Mockup/Smoozy.html` that draws it — eleven of them, plus one round for the three modules that have no document and are read against their specs instead. They have their own brief, the [Design Mockup Seam Runner](Templates/Design%20Mockup%20Seam%20Runner.md), which replaces the standing Runner for this job and no other.

Three things are different, all of them Creator-stated on 2026-08-24 after the first round ran the ordinary way:

**The roster is two, and it is named.** Claude Opus 5 and Gemini 3.7 Flash High, every round, no variation and nothing to propose. The seam round's own reasoning is what allows the cut: a contradiction is checkable, the finding quotes both sides, and there is far less spread of judgment than on a document round.

**The round does not stop for the Creator.** The consolidator puts nothing to them and waits for nothing. Every finding that would have gone to them, it decides itself — taking the option that changes least and the option the plan's nearest already-answered question points at, which is the standing guidance of 2026-08-23 applied at a larger scale.

**What replaces the gate is the trail, and it is not optional.** Every call the consolidator takes instead of asking is written into the Verdict as its own item, marked as its own, carrying the reasoning it would have given and the alternative it turned down — at the top of the must-do list rather than among the small fixes. The Creator reads them after the fact and may overturn any of them. **The two-item cap goes with the gate**, because the cap existed to protect them from ruling on a dozen things a round and nothing is now being put to them; the reasoning behind each call is still written out in full however many there are.

*Why this is safe here and would not be everywhere.* A mockup seam finding is the narrowest kind in the project: the document says one thing, the drawing shows another, and which side wins is already settled by `Preparation/Design/Mockup/About this mockup.md` — the documents hold the decisions. Most of what such a round turns up is not a product choice at all. The first round found thirty-nine things and only two of them were genuinely the Creator's, which is what made the standing gate look like the wrong shape for the other ten rounds.

*What it costs, stated plainly.* Those two were real — where a failure sits on an entry, and a promise on screen with nothing behind it — and a round that decides them alone will sometimes decide one the way the Creator would not have. The trail is the whole of the protection, so a Verdict that buries a call, or takes one without writing down what it turned down, has removed the only thing standing in for them.

## The same loop, for a scenario

A **scenario** is one person doing one piece of real work, start to finish, played through the documents step by step to see what they actually give that person. It is a Subject like any other: same rounds, same four roles, same Creator gates, its own audit folder, its own decisions record.

Two things make it worth running on top of a document audit and a seam audit, and it is worth being exact about them, because the overlap with a thread seam is large. A thread seam already hunts for something stated nowhere, and finds plenty. What it does not do is either of these:

- **It asks whether the answer is any good.** A document auditor judges a document — is it clear, complete, correct, and sensible on its own terms. A seam auditor judges whether two documents agree. Neither one asks whether what they add up to is a decent experience for the person using the app. A scenario does, and that is the finding no other Subject produces: the documents are all correct, they agree with each other, and what they agree on is bad.
- **It lets state pile up.** A scenario reaches step eight carrying whatever the first seven steps left behind — what is connected, what is running, what the app remembers, what it has already forgotten. Faults that need three things to be true at once do not appear in any static read, however careful, because nothing else in this process ever accumulates.

**The scenario is written first, and it is fixed.** The auditor does not invent it. An auditor left to make up its own would unconsciously pick a story the documents handle well, and several auditors would each play a different one, so their answers could not be compared at all. Writing the scenario is the Creator's job, helped by an agent — it rests on knowing what real work looks like, which is the part no model can supply.

**A scenario tells the story and nothing else.** Whoever writes one will already have spotted problems while writing it — that is half of why the story got chosen. None of that goes in. No hints about where it gets interesting, no questions pointing at a particular weakness, and no links to a document that carries the writer's own conclusions. A scenario that seeds its findings gets them back from every auditor, and the consolidator counts that as several independent readers agreeing when it is really one opinion repeated. That is the same trap auditor blindness exists to avoid, arriving through the one file every auditor is guaranteed to read. Put the user at the moment and say nothing more; if no auditor notices what the writer noticed, that is worth knowing too.

**A scenario is small, even though it touches many documents.** The size rule binds here as everywhere, and it is about how much has to be held in one head, not how many files get opened. A seam auditor reads several documents too, and stays deep because it is chasing one connection. A scenario auditor reads several because it is following **one sequence in time** — one person, one sitting, one run of steps. Most of each document has nothing to do with what the user sees at step seven, and is passed over.

Scenarios come in **families**: one journey written once, with a single thing changed between them — the same story with the connection dropping at a different point each time. That keeps each one small, and makes them comparable, which is what lets a pattern across the family show up that no single scenario reveals. Two things changed at once gives neither.

**The walkthrough is the audit.** The auditor writes the story out step by step, in the user's shoes, and at every step says three things: what the user does, what Smoozy shows them, and **which document says so, quoted**. A finding is anywhere it cannot cite one. There are four kinds:

- **Silent** — nothing anywhere says what happens.
- **Split** — two documents say different things.
- **Bad** — the documents agree, and what they agree on is a poor experience.
- **Unchecked** — the documents say what happens, and whether it can happen at all rests on something outside Smoozy that nobody has confirmed.

The first two overlap heavily with what an ordinary audit and a thread seam already catch, and a scenario round is not run for them alone. **Bad** is the one that earns the round.

**Unchecked** works here as it does in an ordinary audit — the auditor may use what it knows to doubt, never to answer — with one difference worth stating. The round's altitude never suppresses it. An unchecked fact is not a document waiting to be written but a promise resting on air, and unlike a genuine silence, no later stage will run into it on its own. A document auditor is asked to use plain good sense, but about the document in front of it; nobody is otherwise asked whether what all the documents add up to is a decent experience.

**The round states its altitude.** This is what keeps a scenario round from burying the Creator. Played against the Specs, a scenario will meet a hundred things the documents do not say because they are Design's or Architecture's and not yet written — and twenty findings of that kind hide the two that matter. So the round says plainly what counts as an answer at the stage being played. At Specs, an answer is what the user is told and what they can do next; that the wording and the layout are unsettled is not a finding. The round also names what it is deliberately not asking about.

The altitude sits in the auditor's brief because the same scenario is played at more than one stage and only the altitude changes between them. Were it written into the scenario, replaying it would mean editing the scenario — which would quietly change a Subject an earlier round already judged, and leave the story different from the one those auditors read. The scenario holds the story and the situation, which do not change; the round supplies the altitude, which does. The runner fills it in when it prepares the briefs.

That altitude carries a known soft spot, and a runner should say so when briefing: an auditor cannot always tell a document that is *not written yet* from a gap that *nobody owns*, since both look like silence from outside. The test is whether the person in the story is left stuck. Where it is genuinely unclear, the auditor reports it and lets the consolidator sort it, rather than guessing either way.

**Findings land on documents, exactly as a seam's do.** The Verdict names which document each fix goes to, the scenario's own decisions record gets the round's entry, and every document the round edited gets a line in *its* record too — because that edit happened outside that document's own rounds and its next auditors have not seen it. That is Rule 7, and it works here for the same reason it works for a seam.

**A scenario outlives the stage it was written in.** The same story is played again against the Design, then the Architecture, then the built app — each time a separate Subject with its own folder, which is what filing audit trails by stage is already for. Only the altitude changes, and it changes in the brief rather than in the scenario. At Build the replay stops being an audit and becomes a test the finished app has to pass.

A replay needs one thing a fresh Subject does not. Because it is the *same story*, the same judgment calls come round again — so a replay's consolidator is handed the decisions records from the scenario's earlier stages as well as its own. Without them the memory that stops settled points wasting the Creator's time is thrown away at exactly the moment it would pay off. This is the one place where a Subject's record reaches across stage folders, and the runner hands them over when it briefs the consolidator.

**Replaying is rationed.** A family is many Subjects already, and every round costs the Creator auditors, a consolidator, an implementer and a set of rulings. So a family is played in full **once**, and only one or two of its scenarios are replayed at later stages. Replaying a whole family twice over is not the intent and should not be proposed as routine.

Scenarios themselves live in `Preparation/Scenarios/`, fixed once written (see the Conventions), and a scenario round uses its own brief — the Scenario Auditor template in `Templates/`.

**When a scenario gets audited.** At a stage close, alongside the seams, and for the same reason: what a scenario finds is a fault that gets copied into everything the next stage builds.

Only where there is something to play, though. A scenario follows a user through the app, so it needs documents that describe what the app does. Specs, Design, Architecture and Build have those; **Groundwork and Blender Research do not**, and neither can be scenario-checked at all — Blender Research has its own kind of checking instead, below. That is not a gap in those stages — there is simply no user journey through a set of naming conventions or a list of Blender facts. Which scenarios are worth a round, and when, is the Creator's call like every other Subject.

## Not the same loop, for a set of findings

Blender Research is the one Subject that does **not** get the loop above, and that is settled rather than an oversight. Its whole journey — how a topic goes from questions to a checked comparison — is set out in the [Blender Research method](../Blender%20Research/Method.md), which owns it. What belongs here is why the loop does not apply, and the rules that hold in its place.

**The loop exists to gather judgment, and there is little judgment here.** A spec audit is several independent readers because reasonable people differ about a spec, and a consolidator exists because their findings overlap and someone must sort what is the Creator's to decide from what is not. A findings audit asks whether a label is honest, whether every question was answered, whether a finding quotes its words, whether a search was abandoned early. Those mostly have one right answer. Several blind readers would return the same list, a consolidator would have nothing to merge, and the Creator would have nothing to rule on.

So it collapses: **one model, one Blender version, one chat**, finding the faults and fixing them in the same sitting. The Creator says how many passes a version gets, and a second pass by a different model lands beside the first. Label: **Creator-stated** (2026-07-30).

**What the collapse gives up, and what holds instead.** Nobody checks their own work here — the chat that finds a fault also decides its fix landed. Three things stand in for that. Every change is a commit the Creator can read as a diff. The audit file records what it changed and what it left, so a bad fix is visible rather than silent. And the hand-test step that follows opens all four versions with fresh eyes, immediately after, which is where a botched fix would show.

**One version at a time also gives up the cross-version read**, and that loss is real: two versions answering the same question in opposite ways, or a test run in three and not the fourth, is invisible to a reader holding one document. It is not dropped — it moves to the hand-test step, which opens all four side by side anyway and turns what it finds into tests rather than findings. The method sets that out.

**An auditor may doubt, and must never answer.** This is the strictest form of the ordinary rule about unchecked facts. Everywhere else in this project an auditor's own knowledge of Blender helps it spot a promise nobody checked. Here it is the contamination the whole stage is built to keep out: an auditor that "knows" how Blender behaves and writes it into a finding has put training data into the one place that exists to hold only sourced fact. So it says *this claim is not carried by the words quoted*, or *this stops looking too early*, and never says what the answer is.

That is also the one kind of fault it may not fix itself. Having read the project, it can no longer supply a Blender fact — so a question that stopped looking too early goes back out to a **fresh blind researcher**, from a Researcher brief, reading only the question and `Blender Sources/`. An auditor that answers it with the project open has broken the blindness the finding depends on. Anything needing a running Blender goes on the hand-test list instead. Both are written down and carried out by the researcher-runner.

**What it is judged for.** Not whether the answer is the right one — nobody at this stage is allowed to know that. Whether it is **honestly labelled** (documented, where a reader must supply a step, is really inferred), **complete** (every question answered, both standing lines filled), **traceable** (a documented finding quotes its words and names a version-pinned address and a date; an observed one says what was done, to what, what came back, and on what kind of computer — see the [method](../Blender%20Research/Method.md), which sets out both shapes), and **not closed too early** (a *not in the sources* with no record of the search is a blank, not an answer).

**Isolation is not harmed by any of this.** It protects the *researcher*, who has finished by then, and an auditor produces no facts of its own.

**No rounds, no verdicts, no round folders.** A topic's audit folder holds its decisions record, its audits one file per version per pass, its citation checks, and its hand-test list — the Conventions set out the shape. Every audit names the commit it read at the top of its own file, which is what `Round info.md` used to do.

**Expect the findings to keep changing after they are audited.** A question answered *not in the sources* gets settled later by the Creator's own hands, and that answer lands in a document an auditor has already read. It is Rule 7's ordinary case and needs Rule 7's ordinary line in the decisions record — it simply happens here far more often than anywhere else.

Three of this stage's briefs live in `Templates/` alongside the audit ones: **Findings Auditor**, **Citation Check** and **Comparison Check**. None of them uses the Runner, Consolidator or Implementer templates.

## The same loop, for an architecture document

The same four roles, audit folder and decisions record apply. What differs is that **the Creator does not read the Subject at all**, deliberately: an architecture document is written for the agent that will build the app, and the specs are the readable half of that pair. The whole stage is set out in the [Architecture method](../Architecture/Method.md), which owns it. The differences belong here because they change the audit loop.

**The round opens by readiness rather than by feel.** Everywhere else the Creator chooses what is worth auditing after reading the document. They do not read Architecture, so the runner opens its one discovery round when three things are true: every row it was meant to answer has an answer or is recorded unresolved with what breaks, both gates have passed, and every fact it waited on is settled or explicitly unresolved. This is a counted process decision, not a product ruling, and it does not go to the Creator.

**An architecture document gets one discovery round once it is ready.** The number of defects that round finds does not schedule another round. The implementer applies the Verdict; then a fresh close checker runs the two counted gates and a bounded repair check. The Subject closes when those pass. The close checker checks the Verdict, the changed passages, and their immediate neighbours. It does not audit untouched passages and it does not originate a new list of architectural improvements.

If the close checker finds an objective failure — a must-do missing, an edit outside the Verdict, a broken trace, an unsupported fact, or a direct contradiction created by a repair — that exact failure is corrected and checked again. It does not reopen discovery. An unrelated concern noticed along the way needs its own concrete failure path and becomes a later targeted correction or seam; it is not a reason to run the whole document again.

**Four things keep the discovery round honest.**

- **The Subject has a written audit boundary.** Its purpose, the decisions it owns, and what it deliberately leaves to another document or to Build are recorded in `Round info.md` and copied into every brief. A missing answer outside that boundary is not a defect.
- **The consolidator rules which is which, not the auditor.** The auditor says what it found and argues for it; the role whose job is cutting rules the label after reading all three audits together.
- **A defect carries a failure path.** It names the permitted starting state, the instruction or decision being followed, and the promise or required invariant that then fails. A concern that cannot do that is a preference, an unchecked fact, a want, or outside the Subject.
- **Every auditor is asked what should be left alone**: what it judges right as it stands, especially where it can imagine another reader wanting to change it. That is not a courtesy. It gives the wish to contribute somewhere honest to go, and it gives the consolidator a tell — a long fault list beside an empty one is a model performing.

**A repair may not make the Subject outgrow its purpose.** Where a valid finding needs lower-level detail, the repair names the downstream owner and the constraint it must carry; it does not pull that downstream document into the Subject. This is especially strict for the shape, whose job is placement, boundaries, the document set, and ownership — not the full protocol, transaction, or recovery design of every component.

**A round takes three of the roster rather than all five.** Same cut as a seam, and for the same reason: an architecture document quotes the spec promise it keeps directly beside its answer, so there is far less spread of judgment than on a spec. It also matters practically — the roster held one model the runner could launch and four the Creator opened by hand, and this stage has more documents than any other. The runner says which three and why. **Since 2026-08-19 the roster is three and this cut is spent**: all three sit, one launched by the runner and two run by the Creator in Zed, and nothing is left to choose.

**There is no seam round between an architecture document and the spec or the design it serves.** Because the promise is quoted inside the Subject, an ordinary audit is already reading both sides. The one thing such a seam would add — noticing a promise the architecture never mentions — is counted by that stage's own coverage gate instead. Seams between two architecture documents hold as usual.

**The consolidator's middle pile becomes *this comes back to Specs*.** An architecture finding is the Creator's only where Architecture has run into something only Specs can settle: it cannot keep a promise the spec makes, or its answer costs the user something no spec says they get. Everything else the consolidator decides.

**An architecture round uses two briefs of its own** — the Architecture Auditor and Architecture Consolidator templates in `Templates/` — because the standing pair make code-speak a defect, where this stage requires the exact technical word, and because their middle pile means something else here. The Runner and Implementer templates serve this round as they serve every other; the Runner's architecture branch carries the rest.

**The cap of two does not apply to that pile.** The cap exists so a consolidator can settle the smaller product questions itself rather than burying the Creator. Nothing in this pile is the consolidator's to settle — each item is a change to a spec, and Rule 7 puts that with the Creator however many there are.

One thing is given up and is named rather than glossed over. The fix-it pile is shown in full so the Creator can pull a line, and here nobody does. What stands in its place is the coverage gate: the failure worth fearing is a consolidator quietly deciding something that was theirs, and that shows up as a promise which stopped being kept.

## The same loop, for code

Auditing code works the same way — same roles, same rounds, same Creator gates. The Subject just happens to be a chunk of code instead of a document. Three things differ:

1. **What it's checked against.** A document is held to its own stated purpose. Code is held to four things at once: the **Specs** (does it actually do what we said the app should do?), the **Design** (does the interface match what was designed?), the **Architecture** (is it built in a way that stays maintainable?), and plain **correctness** (bugs, crashes, security holes). The architecture check is deliberately not strict — an auditor flags a deviation when it makes the app harder to maintain, extend, or understand later, not merely because it strays from the plan. Code is audited for *consequence*, not conformance.

2. **Reading versus running.** Auditors always read the code. When it's worth it — and the Creator calls for it — they also *run* it, to see how it truly behaves. Some parts (the ones that rent and drive remote servers) are expensive to run, so running is a per-audit choice, not a rule.

3. **Signing.** A document's signatures live in a companion file next to it (see the Conventions). Code doesn't have one — its authorship lives in the version-control history instead. That history records the Creator as the author, not the model, so every commit message must name the model that did the work. Don't leave that to a particular tool's habits (see the Conventions).

**When the plan is the bug.** Auditing code sometimes turns up something the plan never anticipated: the code is *faithful* — it does exactly what the spec, design, or architecture said — and the plan itself is wrong. That's a **hole** in the Rule 7 sense: the plan was already broken, and the code audit is simply where it surfaced. Three things follow. First, an auditor is free — and expected — to raise it: "the code is faithful, but the plan it follows is flawed" is a finding, and a valuable one. Second, the consolidator sorts such findings into their own pile — *fix upstream*, separate from the ordinary *fix here* code bugs — so the Creator sees which is which. Third, the fix goes **up, never sideways**: you never patch the code to paper over a bad plan, because that makes code and plan disagree (the plan quietly becomes fiction), infects the next module built on the same plan, and buries the finding. Instead you fix the plan document, re-check whatever depended on it, flow the change down, and only then bring the code into line. How far you go scales with the flaw: a small, local one is a quick edit to the plan and a matching tweak to the code; a large, structural one means stopping the code round outright — auditing code against a plan you're about to tear up is measuring the wrong thing — fixing the plan properly (auditing *it* if need be), then re-auditing the code against the corrected plan. Pure code bugs found in the same round can still be fixed now; only the findings that depend on the plan changing wait for it.

The Auditor, Consolidator, and Implementer templates in `Templates/` judge documents. **Their code versions were written on 2026-09-03, against the first module ready to audit** — [Code Auditor](Templates/Code%20Auditor.md), [Code Consolidator](Templates/Code%20Consolidator.md), and [Code Implementer](Templates/Code%20Implementer.md). The Runner template drives a round for any Subject. Build also runs one counted gate before each module is audited, and its brief is [Build Gate](Templates/Build%20Gate.md); the [Build method](../Build/Method.md) owns what that gate does and does not cover.

**Three things differ in those briefs and each one is here rather than a habit of theirs.** The auditors are still kept out of `Audits/`, which means they cannot tell a deliberate stub from an unfinished one — so the consolidator checks every finding against the Build board, which is where the deliberate ones are recorded. The consolidator has a fourth pile, *fix upstream*, and the judgment that goes with it: a small plan fault is repaired alongside the code, and a structural one stops the round. And the implementer carries the upstream fixes first, signs the plan documents it changed, and commits nothing, because only the build runner commits.
