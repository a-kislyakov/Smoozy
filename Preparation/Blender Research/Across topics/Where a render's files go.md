# Where a render's files go

Where a render's files land, what they are called, how many there are, and which one of them is the finished picture.

> **This joins answers that live in several topics.** Every claim below names the comparison
> questions it rests on; open those for the exact words, the exact messages, and what each
> version does. Where this document and a comparison disagree, the comparison is right.

*All four versions* and *every version* below mean Blender 4.5 to 5.2, and *the newer three* mean 5.0 to 5.2, as they do in the comparisons; 5.3 is named wherever it is meant. Every 5.3 result is the 5.3.0 Beta on the Creator's Mac and nothing else — no Linux machine, no NVIDIA card and no machine without a screen ran it.

## The short answer

A render writes from two places at once — the scene's own output path, and any File Output node in the compositor — and they are recorded differently, named differently, counted differently and fail differently. **There is a third route and it is easy to miss**: a scene brought into another through the video sequencer writes its own node's files while the containing scene renders, governed by the brought-in scene and not by the one being rendered. All of them make folders that are not there, silently, in every version and in 5.3. The number of files is never simply the frame count: views, small copies, each node's connected inputs, the one-file-per-run shape of a video, and a strip's own length all change it, and several view layers do not. It can also be nothing at all, with the run still ending at success. Which file is the finished picture is one question and what actually landed in it is another — compositing, the view layer chosen, and the sequencer each change the second without changing the first. Nearly every rule below holds in all four versions and again in 5.3 on the Mac; the File Output node is where they part, and it parts in several places at once, the sequencer route most of all, and some extra 5.3 cases leave the earlier versions unsettled (*Writing 2, 4, 8; File output nodes 6, 13, 15, 16, 17; Images 1, 5, 8; Frames 9, 12; Reports 12; The compositor 1, 7*).

## Where the write lands, and the folders

**Both writers make the folders they need.** A missing folder, or a whole chain of them, is made silently, with no window, in all four versions and in 5.3, for the scene's own output path and for a node's folder alike — and no version's own documents say a render does this for either of those two places. The one corner 5.1, 5.2 and 5.3 do document is the sub-folder a separator inside an output's name asks for (*Writing 4, Dependencies 17, File output nodes 5*).

**The one place folder-making parts by version** is a folder asked for by a separator inside an output's name: 4.5, 5.1, 5.2 and 5.3 make it and 5.0 flattens the name instead, and where it is made the folder is not called the same thing in 4.5 as in 5.1 to 5.3. In 4.5 such a name can also climb out of the node's folder and land the file outside it, where 5.1 to 5.3 hold that folder as a floor it cannot climb past. In 5.3, with the node's own file name left as it ships, the open file's name is joined to the front of the sub-folder — or a fixed placeholder, in a file never saved. The boundary and the names are in *Writing 3, Writing 12, File output nodes 4*.

**Whose folder it is decides what else lands.** When the scene's own folder cannot be made, the render stops at the first frame and nothing lands anywhere. When a node's folder cannot be made, that node's folder stays empty and every other file for the frame is still written, the scene's own among them — and nothing in the status the render ends with tells that case apart from a clean run. 5.3 does the same on the Mac, though every folder it could not make sat on a read-only volume or behind a file standing in its place, and a folder refused by its own permissions was not tried there (*Writing 12, File output nodes 15*).

**Where a path is measured from, and three cases that are not one case.** With the file loaded and saved, the shorthand for the file's own folder means that folder, and a render aimed at it writes there and ends at success, 5.3 included (*Reports 12*). In a file that has never been saved the shorthand resolves to nothing and the frames land in the folder the command was started from; a fresh Blender starts pointed at a temporary folder; 5.3 does the same (*Dependencies 10*). But a 5.3 session never saved, aimed at the shorthand with a name straight after it and no folder between, refused to save and wrote nothing, with a window and without; no earlier version was asked that (*Writing 3, Writing 12*). With **no file loaded at all** the versions part: 4.5 writes into the current folder, and 5.0, 5.1 and 5.2 stop with a render error and write nothing — on the Creator's Mac, which is the only machine that ran it — and 5.3 was not tried (*Settings 17*). An emptied output path splits the same way — 4.5 writes into the working folder and 5.0 to 5.3 fail and stop after the first frame (*The compositor 2*). A path longer than the enforced limit is cut as it is typed, with nothing said, so a long path can land somewhere other than where it was written (*Writing 2*).

**What joins those four, stated as narrowly as the runs allow, because Smoozy hands Blender an output path.** They are not four unrelated results and they are not one rule either. **Wherever a file is loaded and the path itself carries a name, all four versions do the same thing** — the shorthand meaning that file's own folder where the file has been saved, and resolving away to leave an ordinary relative path where it has not, the frames then landing in the folder the command was started from. Both of those were run on two machines in all four versions, and 5.3 did both on the Mac (*Reports 12, Dependencies 10*). **The versions part in exactly the two cases where one of those two conditions is missing**: with no file loaded at all, and with the path emptied. In both, 4.5 falls back to the folder the command was started from and the newer three refuse — a render error and nothing written, and with the emptied path the run stops after the first frame. 5.3 refuses the emptied path as they do, and was not tried with no file loaded (*Settings 17, The compositor 2*). **So for 4.5 to 5.2 the thing to check before handing a path in is not the path's shape but whether there is a loaded file and a name for it to resolve against. In 5.3 that does not stand as a rule:** in a session never saved, a name with a folder after the shorthand landed in the folder the command was started from, and a name with nothing between was refused (*Dependencies 10; Writing 3, Writing 12*).

**What separates the agreeing cases from the parting ones was never varied on purpose by anybody**, so the line above is a description of results and not an established boundary: nothing says whether it is the loaded file, the name in the path, or the two together that decides it. The two 5.3 runs in a session never saved differ visibly in one thing, a folder between the shorthand and the name, and the no-file-loaded runs of 5.0 to 5.2 that refused had none either; nobody varied that on purpose, and the runs came from different topics' set-ups, so it is a pattern and not a rule (*Dependencies 10; Settings 17; Writing 3, Writing 12*). Two bounds travel with it. The no-file-loaded half is **the Creator's Mac alone**, two runs per version, met beside another question rather than asked as part of one, with nothing rented for it and nothing run in 5.3 (*Settings 17*). The emptied-path half is two machines in all four versions and the Mac in 5.3 (*The compositor 2*). **Neither has been tried on Windows** (*Settings 17; The compositor 2*).

## How a name is built, and what can be known in advance

**The scene's own output is identical in all four, and in 5.3 on the Mac.** Templates first, then the folder shorthand, then the frame number where the hash marks are — or added on the end when there are none — then the ending, decided by an extension switch and the chosen format. The padding is a floor and not a ceiling. **All of that was measured on three routes only** — a single frame asked for from the command line, an animation asked for from the command line, and an animation asked for from a script — and there is a fourth route where the frame-number half of it does not hold at all, below (*Writing 8*).

**A node's name is assembled from more pieces, and the pieces changed at 5.0** (*Writing 8, Reading a file 4*). Whether an input's own name reaches the file is decided by the node's mode rather than by the version (*File output nodes 6, Images 8*).

**In image mode, "the node's format" is two formats, not one.** The node carries a fallback format and each output can carry a format of its own; a switch on the output decides which of the two writes that file, and **both the switch's name and its sense changed at 5.0** — it reads one way in 4.5 and the opposite way from 5.0, 5.3 included. So anything working out an ending, or setting one from outside, has to read that switch before it reads either format, and must not take the node's own as the answer. The same switch decides which of the two levels' display-transform settings reaches the file, and that precedence rule is the same in every version, 5.3 included (*File output nodes 2*). **In multi-layer mode the node's mode wins:** in 5.3 an output set to its own image format still went into the gathered file, with no image of its own (*File output nodes 6*).

**The trap that four topics each record separately.** A freshly added node starts on a different mode in 4.5 than from 5.0, 5.3 included, so a file nobody touched writes differently named files in a different format from one version to the next. That starting value, and not the node behaving differently, is the version change — so an untouched node's format must be checked before its name is predicted (*File output nodes 1, File output nodes 6, Images 8, Reading a file 4, Dependencies 10*).

**A fifth record of the same trap, and this one is a name on disk.** A File Output node left entirely alone writes a file named after a fixed word in 4.5, after a different fixed word in 5.0 and 5.1, and after **the open file's own name** in 5.2 and 5.3 — because their node ships with its file name set to a template standing for that name, where the earlier three ship a plain word. On both of that test's machines in all four versions, and on the Mac in 5.3, and the reason is settled rather than open (*Writing 14, Dependencies 10*). **That last one is a name that tells jobs apart**: an untouched node in two different files writes two different names in 5.2 and 5.3 and one and the same name in 4.5 to 5.1. It tells **saved** files apart — a file that has never been saved has no name to stand for, and the template resolves to one fixed placeholder for all of them. Nobody ran the collision itself; this is what the names say.

**Where the frame number ends up depends on how the render was started, and the two writers do not agree.** For the scene's own output, a still is not written by itself: the window's own still entry writes nothing at all, and the render call writes only when it is told to (*Writing 6, The compositor 2*). Told to, it writes with no number in the name at all, and that same call leaves typed padding marks standing in the name instead of filling them — **so that route is the one place the frame-number rule above does not hold**, and nothing in such a name tells one frame from another. Only one still was ever rendered that way, so no run has put two of them in one folder (*Writing 6, Dependencies 17, Writing 8*). For a node, 4.5 always adds the number and 5.0 to 5.3 add it only on an animation render — and a render started from the command line is always an animation (*File output nodes 13*).

**What the file says in advance is reliable about names and not about sizes.** Asked where a frame will land, the file's answer matches disk for a frame render and for an animation, templates and padding and all — the still route above is the one exception (*Dependencies 17, Reading a file 4*). Asked for a negative frame, the name-building call and the render disagree (*Writing 8*). The template that reports the picture's size reports the scene's own numbers rather than what was written (*The compositor 6*). **And a name on disk is no evidence of a size either**: a node's file can be named for one size and hold a second, decided by a scaling step earlier in the tree, and come out a couple of pixels wider than even that (*The compositor 6, File output nodes 17*). From 5.0, 5.3 included, a node displays its finished names before anything renders, and 4.5 displays nothing of the sort. **The panel holds one row per output** — the one photograph of it showing a single row was of a node gathering its outputs into one file, which is one file for the whole node. No way was found in any version for a script to read those names (*Writing 8, Reading a file 4, File output nodes 10, File output nodes 17*). Read for the sequencer route — on a rented Linux machine in 5.0 to 5.2 and on the Mac in 5.3 — the rows hold the name without a frame number, which is the name that route actually writes (*File output nodes 17*).

**The path lists and relative sweep miss these places, and saving elsewhere leaves the tested write places alone.** The whole-file path lists and the relative-path command miss the render output path and a node's folder, in every tested version, 5.3 included. The absolute-path command was tried only with those places already in full form, so its reach there is not settled (*Reading a file 4, 9; Dependencies 17*). There is no command-line argument for a node's place either; the argument that exists moves the scene's own path and leaves every node exactly where it was (*Writing 9*). And saving the file into a **different folder** rewrites the tested relative places it reads from while leaving the tested places it writes to exactly as they were — which after the move means a different place on disk, in all four versions and in 5.3. The 5.3 geometry-nodes folder was on a bare modifier; an actual bake was not tried (*Dependencies 20*).

**Where an output path handed in at launch sits on the line decides whether it survives at all.** Given before the file is named it is wiped when the file loads; given after, it takes. Either way it reaches the **active scene alone**, and a second scene in the file keeps its own stored path. **In 5.3 that is the scene active at the moment the argument is read**, so a scene chosen on the same line has to come before the output path to receive it; no earlier version was asked (*Writing 13*). A script handed in at the same launch sees whichever of the two was written before it, and the last of them on the line is the one the render uses (*Writing 13, Dependencies 20*).

## How many files a run leaves

The frame count is the starting point and rarely the answer.

- **One file per frame from the scene's own output**, however many view layers are enabled — never one per layer, and no layer name enters the name (*Frames 9, Images 1*).
- **Written as a multi-layer file, all the view layers sit inside that one file** (*Frames 9, Images 5*).
- **With several views**, the settings left as they come give two files per frame, one per view — the left one written and then the right — and told to put both views in one file, every version writes one. The count rests on one rented Linux machine in 4.5 to 5.2 and on the Mac in 5.3; the order of the two was watched on both machines and again in 5.3 (*Images 5, Writing 14*).
- **The small-copy setting adds a second, plainly viewable file beside every frame** in the two output formats that offer it — the multi-layer format and its plain form — and in no other. In the others the setting reads back as on and nothing is written (*Images 8*).
- **Each File Output node adds one file per connected input in one mode and one gathered file in the other** (*File output nodes 6*). An input with nothing joined to it writes nothing at all, a muted node writes nothing — and in the one version where anybody looked it did not even make its folders — and a node inside a group writes from every depth it was tried at (*File output nodes 8, File output nodes 7*). A group used twice leaves one file; 5.3's own printed lines show it written once for each use (*File output nodes 7*).
- **In 5.3 the compositor is a stack of effects**, and a node writes only while the effect holding it is switched on for render — any such effect, whether or not it is the one marked active (*File output nodes 13*).
- **A scene reached through the video sequencer adds its own node's files on top of all of this**, counted by the strip rather than by the scene — the section below (*File output nodes 16*).
- **At least two thousand outputs can sit on one node**, with nothing above that established (*File output nodes 1*).
- **A render's own output holds one format at a time and no version's node can write video**, so a run leaving a video and separate stills together is the scene writing the video and the nodes writing the stills (*Frames 12, File output nodes 11*).
- **A video is one file whose name carries the whole frame range**, fixed before Blender knows the render will finish; with the splitting switch on, past a size boundary Blender closes it and opens a second file under a differently shaped name (*Writing 8, Frames 5*).
- **The formats are not one list.** What a render can be written as and what a node offers are different lists, and both changed across the four versions; 5.3 offers 5.2's (*Images 3, File output nodes 9*).
- **Switching the scene's own output off does not stop a node.** 5.2 and 5.3 have that switch and the earlier three do not. With it off, a two-frame animation wrote nothing at all from the scene's own path — neither to the path stored in the file nor to one handed in on the command line — while a File Output node in the same tree wrote both frames, on both machines in 5.2 and on the Mac in 5.3; and the run ended at success with an empty output folder. In 5.3, with the switch off and no File Output node, nothing is rendered at all, still or animation, and the run still ends at success (*The compositor 2, Reports 12*).
- **A run can end at success having written nothing at all.** Three ways do it in every version, 5.3 included: a frame number that is not a number, the output option given with nothing after it, and an animation whose start frame is past its end frame. The scene's output switched off does it in 5.2 and 5.3. And in 5.3 a command-line render of the tested Cycles scene on the processor, with its Camera object deleted, does it, where 4.5 to 5.2 and the 5.2.2 run end at a failure status. That does not settle other engines or ways of leaving a scene without a camera; a render called from a script still fails in 5.3. A frame argument left empty does the same in 5.3, with no earlier counterpart tested. Blender says something for the first two and says it on the error stream, while the status stays at success (*Reports 12*).

## A scene reached through the video sequencer

**A scene brought into another through the video sequencer writes its own File Output node's files, and the containing scene's own compositing switch does not stop it.** Rendering the containing scene writes that node's file once for every frame of the strip that is rendered, beside the containing scene's own render. It is the **brought-in** scene's own compositing switch that governs; the containing scene's has no effect either way. The containing scene's own File Output node writes nothing at all. What does stop it: the containing scene's sequencer switch off, the strip muted, the strip taking the sequencer rather than the camera, and a scene sitting two levels down behind a middle scene — that last is never reached at all, because a scene reached through a strip is rendered through its camera and its own sequencer is not used (*File output nodes 16*).

**The count follows the strip, not the scene.** A strip stretched over more frames than the scene has writes once per strip frame over the scene's own names; a trimmed strip writes fewer; a frame step writes at the brought-in scene's own stepped frames. **Two strips of one scene, overlapping or apart, write twice for every frame over the same names**, so the second strip's files land on top of the first's (*File output nodes 16, File output nodes 17*).

**Every part of the name that could come from either scene comes from the brought-in one** — the frame number, and every naming variable that was tried. The file's own name and the folder shorthand name the open file and not a library the scene was linked from. The node's own format decides the ending, whatever either scene's output format is — which of its two formats that is being the switch above (*File output nodes 2*). The strip's camera override does not reach the name, and the command line's output override does not reach the node here either (*File output nodes 17*).

**The frame number splits by version, and that split costs files.** In 4.5 it is always put in, so a five-frame strip leaves five separately numbered files. From 5.0, 5.3 included, it is not put in on this route, so the same five frames leave **one** file written over five times. Writing the padding marks into the name by hand puts the number back in every version. Set that beside the ordinary rule: through a strip, an animation render of the containing scene does not count as an animation render for the brought-in scene's node from 5.0 on (*File output nodes 17, File output nodes 13*).

**Two smaller things about this route.** Blender 4.5 takes four of the naming variables and refuses three, writing nothing at all for a name that asks for one of those three while the containing scene's own render carries on; 5.0 to 5.3 take all seven that were tried (*File output nodes 17*). And in 4.5 the node writes while somebody merely plays the sequencer preview at rendered shading, with no render started at all — settled on one rented Linux machine. 5.3 on the Mac wrote nothing that way, and whether 5.0 to 5.2 do is not settled, because their runs never set which scene the sequencer shows (*File output nodes 16*).

## When two writes want one name

Two outputs on one node cannot carry the same name: the second is renamed and both files are written — though in 5.3 two outputs whose names ask for one sub-folder, one with each kind of separator, went to one path, and one file was left with nothing said (*File output nodes 4*). In image mode, two separate nodes aimed at one name give one file, holding the picture of the node that was made first; in 5.3 two nodes writing multi-layer files to one name were merged instead, both nodes' layers in one file (*File output nodes 6*). Two strips of one scene write over each other, as above. A file already on disk is replaced without a word. The scene's own skipping arrangement — a frame whose name is already on disk is passed over, an empty file counting as done — does not reach a node, and neither does the scene's placeholder switch; with that arrangement on in 5.3, the scene's own frames alone decide which frames are rendered, and a node then writes over its own files for them (*File output nodes 10, File output nodes 16, Dependencies 17*).

**Timing, and it is the strongest positive result this document has.** Every write belonging to one frame — the node's file, the scene's own, a preview picture, a second view — is finished before the next frame's first file appears, in all four versions on the Creator's Mac and on one rented Linux machine, and in 5.3 on the Mac, with the node's file first and the scene's own second. The instrument was fine enough to have shown an overlap: the write was made slow on purpose and the output folder read every two milliseconds, with dozens of readings falling inside a single write, and no frame ever came out of order (*Writing 14*, and the same ordering found separately in *File output nodes 13* and *Writing 11*). **The folder watchers saw only final names; on Linux the file-call trace also showed no rename**, so a name in the output folder is always a final name — which is why the name alone can never say whether the file under it is finished (*Writing 14*). Cycles' tile cache is one file per frame rather than one for the job, written in Blender's own temporary folder and gone by the time that frame's output file appears; the strict ordering of those two is a Linux result in 4.5 to 5.2, and in 5.3 a finer instrument showed it on the Mac (*Writing 14*). **A video is the exception to all of it**: there is one file, which grew through the longer runs and sat nearly empty through short ones until the render closed it — where the line falls has never been measured — and nothing announces a frame inside it as safe to take (*Writing 14, Writing 15, Writing 16*).

**A frame's write event is not one event per file.** In 5.3's tested animations it fires once per written frame even with several files, but never for a single still written only by a File Output node. For video it says nothing about what reached disk. Whether it fires after a failed write is not settled (*Writing 16*).

**Frames arrive in the order they were asked for, and for a list that is the order of the list rather than numeric order** (*Writing 14, Frames 10*).

## Which file is the picture

**One named pass is the finished picture** (*Images 1*).

**What actually landed in the scene's own file is a separate question**, and three things change the answer without changing the first: with compositing on it is the compositor's result — measured on a tiny picture with the compositing work done on the processor, and at nine thousand pixels wide with that work on the graphics card 5.1 wrote a black frame instead, neither the compositor's picture nor the render's, on two machines and two makes of card (*Images 1, The compositor 1*); with several view layers and an ordinary image format it is the first layer's pixels alone, unless the node that reads the render is pointed at another layer; and with the sequencer producing the output it is the strip's picture, the scene's own compositor result never reaching the file (*Images 1, Frames 9, The compositor 7*). Which layer that reading node is pointed at can be read out of the file, as the real name, in every version (*The compositor 5*). **Three 5.3 results qualify that.** Its compositor is a stack of effects, and one switched off for render leaves the raw render in the file. Its starting compositor has no node that reads the render, and puts the first layer's picture in the file. And read across the whole frame, with the compositor set to graphics on the Mac, only 8,192 pixels along the longer side held the compositor's result and the rest the raw render — as the 5.2.2 run did; the earlier versions were read at the first pixel only, so that is not a difference between versions. Whether that 5.3 run actually used the card was not verified (*The compositor 1, Frames 9*).

**Inside a multi-layer file** the finished picture is found by view layer and pass name, and the shape of that naming changed at 5.0. A layer a node wrote carries the socket's name and no view-layer part in front of it (*Images 5*). In 5.3, with a compositor in use, the compositor's result is a part of its own, placed first, while each view layer's own finished pass still holds the picture from before the compositor; no earlier version was looked at for this (*Images 5*). **Find a pass by its name and never by its position**: with the denoising feature passes stored, how many of them there are and what order they sit in both change between the versions (*Settings 19*).

**Showing it.** The small-copy setting writes a viewable file with the same number of pixels, not fewer. A genuinely smaller file can be made during the render by scaling before a node, and that works with no window. Two of the picture-editor commands refuse without a window, and the plain call that stands in for one of them writes in the scene's format whatever the path's ending says (*Images 8*).

**The size written is not always the scene's.** A node writes at the size of the picture fed to it, and a cropped render region or a stereo layout changes the written size too. On the one size measured through a node, 5.1, 5.2 and 5.3 wrote two pixels wider than 4.5 and 5.0 (*The compositor 6*).

## What this does not cover

- What is left at any of these paths when a render fails or is stopped part-way.
- What can be handed to a render at the moment it starts, and what it sets aside.
- What can be read out of a `.blend` before a render, and how many files that comes to.
- A folder reached over a network from a second computer. A rented container can mount a share — one mounted a folder over the network from itself — so what is missing is a second computer sharing a file system with the first (*File output nodes 5, Writing 14*).
- Two renders sharing one folder, and whether a placeholder holds a frame against another render (*Dependencies 17*).
- A node and the scene's own output aimed at the same name. The collisions tested are two outputs on one node, two nodes, and two strips of one scene; a node against the scene's own output is still untested (*File output nodes 10, File output nodes 16*).
- What a node does in 5.2 when an output's name asks for a sub-folder and the node's own file name has been left exactly as it ships. Every 4.5 to 5.2 run behind the folder rule above set that name to a plain word by hand, and 5.2 ships a template there; 5.3, which ships the same template, joins the open file's name to the front of the sub-folder, as above, and 5.2 is untried (*File output nodes 4, File output nodes 6*).
- What a File Output node writes on the sequencer route when the scene's own output is switched off. No test there switched it off, in any version, 5.3 included — the ordinary case is answered above (*File output nodes 16*).
- A multi-layer file written through a strip in Blender 4.5. The test used a mode switch that 4.5 does not have and left its node writing ordinary pictures. What its multi-layer route writes through a strip is not settled (*File output nodes 17*).
- Windows, under every question cited here but one. No Windows machine ran any of the rest, in any version, 5.3 included. **This is untried rather than out of reach** — this project has a route to a Windows computer, described in the equipment section of `Preparation/Blender Research/Method.md`. The exception is *Dependencies 20*, whose account of what a save does to a recorded place was taken on a machine reporting itself Windows Server 2025 Standard as well as on the other two, in 4.5 to 5.2; **a desktop edition of Windows has never been reached**, and a Windows answer that does not name its edition is not yet an answer.
- Blender 5.3 anywhere but the Creator's Mac, and its finished release. Every 5.3 sentence here is a macOS result in a beta build; where 5.3 is said to agree with a 4.5 to 5.2 result that only a Linux machine gave, the two stand on different machines.

## What the evidence could not have shown

- Every run behind the failed-write answers put the scene's own output on a disk with room to spare on purpose, so a node's write and the scene's write have never failed together, in any version, 5.3 included (*File output nodes 15*).
- In 4.5 to 5.2 the group used twice carried the same folder and the same output name, so one file written once and one written twice over itself look identical; only 5.3's printed lines tell them apart (*File output nodes 7*).
- Two thousand outputs were added and nothing refused, so no higher ceiling could have appeared (*File output nodes 1*).
- On the Linux machine the account driving Blender could walk through file permissions, so the unwritable-folder answer rests on the single run with that power dropped (*File output nodes 5*). In 5.3 a folder that refused writing was always a read-only volume, so what a folder's own permissions do there could not have shown (*Writing 12, File output nodes 15*).
- Every render into a path shaped for the other machine ran as a user who owns the root of that disk, so a render user who cannot write there was never tested (*Dependencies 10*).
- Neither machine refuses anything in a name but length, so no run could show what a render does where the computer rejects an ordinary character (*Writing 10*).
- Every view-layer test on every machine drove Blender from outside its window, 5.3's included, so what a render started at a window writes with several view layers could not have appeared (*Frames 9*).
- The compositor half of that answer — which layer's pixels land when compositing is on — was run on the Linux machine alone in 4.5 to 5.2 and on the Mac alone in 5.3 (*Frames 9*).
- The whole several-views half was run on the Linux machine alone in 4.5 to 5.2 and on the Mac alone in 5.3 (*Images 5*).
- The one measurement where the written size parts by version rests on a single scaled size, so what the two extra pixels follow is unknown (*The compositor 6*).
- The switch that stops the scene's output being written was exercised in 5.2 on a two-frame animation from a terminal, and in 5.3 on a single frame as well; no other way of starting a render is recorded against it (*The compositor 2*).
- The files each socket kind wrote were listed and sized and never read back in 4.5 to 5.2, so wrong contents inside them would not have shown; 5.3 read back the three it wrote (*File output nodes 12*).
- Two builds of each of 4.5 to 5.2 were tried, both from Blender's own download server, and one build of 5.3, so a differently built format list could not have appeared (*File output nodes 9*).
- The commands that rewrite a file's paths were tried against six recorded locations, so a write place outside those six could not have shown up as reached or missed (*Dependencies 17*).
- The call that walks a file's paths was run with no options at all, and 5.2's own options for it were never passed, nor checked for in 5.3, so nothing they might reach could have shown (*Writing 9*).
