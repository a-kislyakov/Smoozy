# Running Blender with nobody there

What changes when Blender runs on a machine with no screen, no display server, and nobody sitting at it.

> **This joins answers that live in several topics.** Every claim below names the comparison
> questions it rests on; open those for the exact words, the exact messages, and what each
> version does. Where this document and a comparison disagree, the comparison is right.

*All four versions*, *every version* and *any version* mean Blender 4.5 to 5.2 here, and *the newer three* means 5.0 to 5.2. Blender 5.3 is named wherever it is meant, and every 5.3 result is the 5.3.0 Beta built 2026-10-16 on the Creator's Mac alone — so no Linux machine, no NVIDIA card and no machine without a screen ever ran 5.3. *Settings 6, The machine 1*

## The short answer

- Rendering loses nothing, as far as each version was run. Every engine every version has rendered on a Linux machine with no display server. Cycles was confirmed on the cards and on the processor; the other engines named no device. 5.3 was never run on such a machine; on the Mac with no window, all three of its engines rendered. The tested pictures matched with a window and without one, in all five on the Mac. *Settings 6, The machine 1, What a render demands 4, The compositor 8*
- A bare machine is not a ready machine, and none of what it lacks is about a screen. One package has to be added before Blender's own archive will open at all, and nine libraries before what comes out will start. Unpacking 5.3 was never tried. *Builds 10*
- Nothing on the ordinary render path tried waited for a person, in any version, 5.3 included on the Mac, with a window or without one. *The machine 7*
- Two things wait for ever anyway: a script that reads from the input stream with something holding the other end open, and Blender 4.5 asked for a window where there is no display. 5.3 was never asked for a window with no display. *The machine 7, Settings 13*
- **Every version can fail to end, 5.3 included, not only 4.5.** Anything running Blender unattended needs a time limit and something outside ready to kill it, whichever version it is running. *Settings 13, Reports 12*
- A render outlives the shell that started it, in every version tried. Whether a hang-up signal sent to its process group ends it is not settled. *The machine 7, Reports 12*
- A run that is given a window does not end when its render does. Asking for a frame without the no-window mode is not a way to render on a machine with nobody at it. *The machine 7, The compositor 8, Reports 9*
- Some commands need an editor; others need a window. The picture-editor ones have plain calls that do the same work. In 5.3 and in 5.2.2 on the Mac, the image, strip and shader-script commands run once handed the right editor and what it must show. Undo, the viewport render route and the sequencer's own render command did their job no way that was tried with no window. *Images 8, Writing 6, Reading a file 9, Reading a file 10, Reading a file 11, File output nodes 16*
- A machine can be asked with no window what add-ons it holds and which graphics cards Blender can see. Neither answer settles everything a launcher needs, and one route to the cards exists only from 5.2. **A machine asked which cards it has before anything else answers none** — the list is empty until something fills it, and in 5.3 on the Mac a card render from settings nobody had saved went to the processor in silence for that reason. *Add-ons 10, The machine 4, The machine 5, The machine 6*
- What is lost is what a person would have seen. A windowless run is told less about its own failures — in 4.5 to 5.2 in different words from the window's — and one whole class of signals has no printed form at all. *Reports 2, The machine 4, File output nodes 15*
- An empty error stream is not a property of having no window. What the machine's display is doing decides it, and so does which graphics library Blender is given — and some of Blender's own messages go there anyway. *Reports 2, The machine 7, What actually ran 5, Reports 13, Reports 14*
- Blender does say whether it has a window. One launch flag reports it, reads true in every windowless run, and refuses to be written to. Counting the screen's areas says nothing. *Writing 13, The compositor 8*

## Rendering, and the work around it, needs no screen

On a Linux machine with no display server — none installed, none started, the graphics cards sitting there driving nothing — every render engine each version has rendered and ended by itself: Cycles on the cards and on the processor, and the other two engines beside it. *Settings 6, The machine 1, What a render demands 4* **5.3 was never run on such a machine.** On the Mac with no window its three engines rendered and ended by themselves, which says nothing about a machine with no display server. And 5.3's release notes move the default drawing system on Linux and Windows, apart from Windows on ARM, from OpenGL to Vulkan; what 5.3 starts on there, and what it does where Vulkan is missing, has never been tried. *Settings 6, The machine 1*

The tested pictures rendered with a window matched those rendered without one, in all five versions on the Mac. *The compositor 8*

The work tried around the render also works with no window. Reporting which of a file's references are missing, searching a folder for them and rewriting the recorded locations all work with no window, in all four versions on both machines and in 5.3 on the Mac (*Reading a file 6*). A whole compositor graph reads back out of a saved file with no window at all (*The compositor 8*). Finished frames are built into a moving picture with no window (*Images 7*). An add-on can be found, fetched, installed, switched on and set up on a machine with no display server, in 4.5 to 5.2; 5.3 installed and set up an add-on from a folder with no window on the Mac; no successful internet fetch was tried, and it never ran without a display server. The command line that does it forces the no-window mode in all five. In 5.3, the only version asked, a switch-on made by a script is kept only if that script saves the preferences, where the install command's own switch-on saves itself (*Add-ons 3, Add-ons 5*).

**And what the machine already holds can be asked with no window, though a complete add-on inventory is not settled.** Which add-ons a computer has comes back by three routes, all working with no window and all behaving identically in every version on two machines and in 5.3 on the Mac: what the repositories hold, which shows an installed package whether or not it is switched on and never shows one that ships with Blender; what is switched on, which drops an add-on the moment it is switched off and so is not an inventory; and what is on the machine at all, which is the closest thing to one found in any version. **Whether any route gives a complete inventory of everything installed is not settled**, and whether one Blender can be asked about another Blender's add-ons is not settled, in any of the five. In 4.5 to 5.2, which Blender an answer belongs to is a matter of the folder alone, exactly as for where an add-on was installed; 5.3 was not asked about another version's folder (*Add-ons 10, Add-ons 6*).

Blender's own system-information report is written with no window and with no prompt of any kind, in all five versions, and it names each switched-on add-on with its version and its place on disk. Asked for from a script it worked with no window in all five, and in 4.5 to 5.2 on a machine with no display server at all (*Add-ons 10, The machine 6*). **What it will not carry with no window is the graphics half**: all five versions replace the whole graphics section with a single line saying there is none in this mode, and drop the drawing-limit sections with it; in 5.3, starting the graphics module first does not fill it in (*The machine 6*).

Cycles' own list of cards does answer with no window, in all five versions, and it named every card on machines with one, two and four of them, two of which had no display server at all; 5.3 was asked only with the Mac's one device (*The machine 6*). **But it answers with nothing until something fills it.** On a factory-fresh Blender that list is empty, in all four versions and in 5.3 on the Mac, with an untouched settings folder and again when Blender is started at factory settings; it fills only once a refresh has been asked for, the preferences panel has been drawn, or a preferences file saved earlier is read. **A rented machine asked what cards it has, before anything else, says none** — and that is not the machine having none (*The machine 5*). The route that refuses instead is below.

## What a bare machine is missing, and none of it is a screen

The gap between opening Blender's package and running what comes out is real and wide, and it is the same in all four versions. Nothing of it was tried for 5.3, whose documents name the same requirements. *Builds 10*

A rented Linux machine holding a plain archive tool and nothing else opens none of the four archives and leaves nothing on disk; one further package makes it open all four. With the archives open and nothing else added, none of the four will start: the machine cannot satisfy nine libraries, and asking for those nine pulls in forty-two packages. **Nothing about the unpacking needs any of those libraries, and the program needs all of them.** And the one alternative unpacking tool every version's manual names as unsupported, 7-zip, reports success and breaks what it produces, in every version, with no warning of any kind. *Builds 10*

None of that is about a display. It is what stands between a freshly rented machine and a Blender that will render on it at all, and a plan that assumes a rented machine is ready will fail before any of this document's other answers apply. *Builds 10*

**And what a machine needs depends on how the Blender got onto it — in the same list of ways in all five versions.** One of those ways decides whether a rented machine can render on its cards at all: **a copy built by a Linux distribution may not contain Cycles graphics-card rendering.** That is what every version's own documents say, and **no test ever reached such a copy**; the one route that was tested is the one this project uses, and the official Linux build taken from Blender's own download server reports itself carrying CUDA, OptiX, HIP and oneAPI, in all four versions. No Linux build of 5.3 was read. So the sharp case is not what the official download gives, and nothing anywhere says which distributions' copies fall into it. The other ways it depends on the route are quieter: what raised privileges an install wants, what package system or store client has to be there first, and where Blender's own files end up. *The machine 3*

## Nothing on the render path waits for a person

Every case tried ended by itself and gave the prompt back, in all four versions on two machines and in 5.3 on the Mac, with the Creator logged in: a refused script inside the file, unsaved changes at exit, an output file already on disk, a texture the file needs and cannot find, an output folder that cannot be written to, and a render whose shell went away while it ran. Two of those have to be read exactly. **Whether the unsaved-changes runs ever reached a state that could prompt is not settled**: in 5.3 Blender did not count the change as unsaved at all, and no earlier run read that. And the missing texture is settled on the Linux machine in 4.5 to 5.2 and on the Mac in 5.3 and 5.2.2; the Mac's earlier runs used a texture the picture did not show, so what 4.5 to 5.1 do there is not on record. *The machine 7*

**A render outlives the shell it was started from**, in every version tried: on Linux the connection was cut and the render kept going, in 4.5 to 5.2, and in 5.3 on the Mac a killed shell left it running. **Whether a hang-up signal sent to the render's process group ends it is not settled.** On one day it did not, in 4.5 to 5.2 on the Mac. On a later day, sent to a process group Blender led, it ended 5.3 within seconds and 5.2.2 the same way, and 5.3 does not catch that signal. A cut connection on a rented machine was never tried in 5.3. *The machine 7, Reports 12*

Three things underneath that are worth knowing. Automatic running of a file's stored scripts starts switched off in all five versions, and when Blender declines it prints a line and carries on rather than asking — **and a run can find that out for itself without reading the terminal**, in all four versions on both machines and in 5.3 on the Mac. Commands driven from a script take the route that does not put a question to anybody, in 4.5 to 5.2; that is not recorded for 5.3. And a still render writes nothing unless something asks for the write — which is a setting, not a person. *The machine 7*

Two things do hold a run. A script hooked into a render holds the render for as long as it runs. A script that reads from the input stream waits for ever, if something is holding the other end open — the only thing found anywhere in that question that waits indefinitely on an unattended machine. *The machine 7*

And one command changes shape with what it is handed rather than with what the machine has. Asked to write the sound with **no path named** — which is what picking it from a menu does — it opens a file chooser as a window of its own, hands back that it is still running, and leaves any existing file alone. Given a path it writes straight over that file without asking, with a window or without one, on both machines. **What decides is whether the path was named** — established for the path-named half on both machines, with a window and without. **The no-path half has only ever been run with a window open, on the Mac**, so what it does on a machine with no display — refuse, write nothing, or sit there waiting — is untried, and a file chooser is a window. *The machine 7*

The other dialogs named are outside the ordinary render path tried here. **What becomes of them when there is no window to draw them in is not settled**, in any of the five versions. *The machine 7*

## What refuses, and what has to be killed

Ask for a window where there is no display and Blender refuses in every version. That is where they part: Blender 4.5 never ends and has to be killed, while 5.0, 5.1 and 5.2 stop by themselves. 5.3 was never asked. *Settings 6, Add-ons 3, The machine 1*

**That is one case in a pattern, and the pattern is not one version's.** Blender 4.5 fails to end properly in a family of cases, seen on four machines, and the symptom differs from machine to machine rather than being one predictable ending (*Settings 13*). The later versions have a family of their own: an unknown argument written before the file — the shape the manual itself gives as an example — ends 4.5 and leaves 5.0, 5.1 and 5.2 running with no end in sight, on two machines, on repeated runs, and 5.3 the same on the Mac. **That is an argument in Blender's own part of the launch line.** Past the bare double dash the line stops being Blender's, and an argument nothing there knows is ignored in silence and the run ends normally — so the same mistake hangs a machine on one side of that mark and vanishes without trace on the other (*Reports 12*). Two more endings from that question are outside any number a caller can use: in 4.5 an engine name no engine bears ends on the Mac at a status that means an abort, and **on every rented Linux machine that has been asked it does not end at all** — sometimes after printing its refusal, sometimes after printing nothing — while 5.0 to 5.3 refuse it and stop. **Which way 4.5 fails is the operating system, not the machine**, and no Linux run of 4.5 anywhere in this research has been recorded ending by itself after a refusal (*Reports 12, Settings 13, Add-ons 3*).

**So anything running Blender unattended needs a time limit and something outside ready to kill it, whichever version it is running.** There is no version here that can be trusted to end by itself in every case. *Settings 13, Reports 12*

A third thing needs something outside to stop it, and it is not a refusal. A Blender given a window does not end when its render is done: on a machine with a screen it was still sitting there in all five versions when a two-minute limit ran out. Asked by a script to quit, it went — within a few seconds or some tens of seconds on the Mac, 5.3 included — while on a rented Linux machine with a display the same request had not closed it four minutes later. **That split is the operating system and not the version.** The same request made by a timer a few seconds after the render closed it every time, on both machines, in all four versions. **Asking for a frame without the no-window mode is not a way to render on a machine with nobody at it.** *The machine 7, The compositor 8, Reports 9*

Routes tried with no window, in all four versions unless the entry says otherwise:

- The viewport render route, in all three of its shapes, and it writes nothing — in 5.3 on the Mac too. Given a real window all three run: on a rented Linux machine in every version, and on the Mac in 5.3. So the refusal is about having no window rather than about the route. *Writing 6*
- Two picture-editor commands, in all five. In 4.5 to 5.2 one of them refuses even with a window until that editor has been drawn once; whether 5.3 needs that was not tried. Plain calls do the same two jobs instead — with one catch, the same in all five: the plain save writes in the **scene's** own format whatever the name it is given ends in. *Images 8*
- The command that replaces the file a picture is loaded from, when nothing is handed to it. Handed an Image editor showing the picture, it runs with no window in 5.3 and in 5.2.2 on the Mac; whether 4.5 to 5.2.0 run it then is not settled. The neighbouring command that repoints a sequencer strip does **not** need a window, given what it asks for. *Reading a file 9*
- Undo, in every arrangement tried, 5.3 included. The tested undo calls cannot take back a path repair with no window. *Reading a file 10*
- From 5.0 onward, the two commands that make a replaced strip file reach the next render, when nothing is handed to them. In 4.5 the replaced file reaches the render by itself. Handed a Sequencer editor and the sequencer's own scene, both run with no window and the next render shows the new file, in 5.3 and in 5.2.2 on the Mac; in 5.0 to 5.2.0 they refused in every arrangement tried, and whether that route works there is not settled. *Reading a file 11*
- The command that updates a shader script refused in every arrangement tried in 4.5 to 5.2.0. In 5.3 and in 5.2.2 on the Mac it runs with no window once handed a Shader editor showing the material's tree and script node. Whether that call works in the earlier builds is not settled. *Reading a file 11*
- The video sequencer's own render command, which writes nothing with no window in all five and refuses differently: 4.5 with an error, 5.0 to 5.3 by cancelling. With a window, whether it runs is not shown to turn on the version: on a rented Linux machine 4.5 ran it and 5.0 to 5.2 cancelled, in runs that never set which scene the sequencer shows; on the Mac, 5.3 and 5.2.2 ran it once that scene was set. *File output nodes 16*
- Blender's general graphics module, in 4.5, 5.0 and 5.1 — with no window it refuses every question put to it, and it holds no way of asking for a list of devices at all. **5.2 and 5.3 can be told to start it**, after which it answers with no window and can be asked for that list. And from 5.2 a request made on the command line prints a numbered list of the cards Blender can **draw** with and exits; 5.2 did so on a machine with no display server of any kind, and 5.3 on the Mac named no card, its copy carrying no Vulkan drawing. That is a second list and not another way of reading Cycles' own — it names the card Blender draws with, not the card Cycles renders on. *The machine 6*

One route that looks like a way out is not one: the compositor's own preview picture fills only when there is a window in 4.5 to 5.2, does not fill even then in 5.3, and in 5.0 does not exist at all without one. *The compositor 8*

**And a window put on a rented machine in software is not a workstation's screen.** Where a display server was installed on a rented machine for a single test, it draws in software. That test settles **what its software display drew**. It does not establish how another display would draw the control. In 5.3 the Mac's own screen showed the same dimmed, still-ticked checkbox. Neither machine ran the other's versions, and no drawing speed was measured. *Settings 19*

**A caution that belongs beside it and is not this document's to settle.** Several of this project's machines with a display had that display drawn in software, and the engine that renders only on a graphics card has been timed on one of them. **Nothing anywhere establishes which device that render used** — neither on that machine nor on any other — so no reading of it may be carried into what an unattended machine's cards are doing. Which device that engine renders on when the screen is drawn by the processor or in software, and whether it renders at all on a software drawing device, is not settled in any of the five; that a Cycles render set to the card uses the card whatever draws the screen is inferred for 5.3 and was never tested. *Settings 6, The machine 2, The machine 8*

## What an unattended run is never told

A failure with a window open is announced in three places at once. In 4.5 to 5.2 the printed words differ from the window's — same machine, same file, same day. In 5.3 a windowless render from the command line prints the window's words and a render called from a script with no window prints the other ones, so there the words follow how the render was started. **Printed output must not be expected to carry the window's wording.** *Reports 2*

**The route can change what a failure hands back too.** In 5.3 on the Mac, a command-line render of the tested Cycles scene, on the processor with its Camera object deleted, wrote nothing, fired no render handler and ended at success. A render of that file called from a script still ended at failure. The 5.2.2 command-line control failed. This does not settle Workbench with its camera unassigned: that is a different setup, with the Camera object still present. *Reports 2, Reports 12, Settings 6*

Blender's own list of reports exists in 5.2 and 5.3 alone. It was empty every time a failing run with no window read it — after a missing-files report, after a blocked write, and beside a control that certainly failed and left it empty too — and empty after a failure a script started. **It is not always empty, though**: opening a file whose linked library is missing fills it with the messages that raises, and in 5.3 a failure started by a key fills it with that failure's message. **Both were read with a real window open, and whether a windowless Blender fills the list at all is not settled** — which is the case that matters, because a rented machine never has a window. *Reading a file 6, Reports 2, Reports 13, File output nodes 15*

**One thing a windowless run started from a script is told, and it is not printed.** A render asked for by a script rather than from the command line does not report a failure — it raises it back into the script, carrying the message, so a farm that starts its renders that way can catch what went wrong in the script itself. What such a route puts on the streams is a separate matter and mostly uncaptured: **what becomes of a tagged error line under it was never watched**, because every run behind that question wrote its picture and so had no error to show. *Reports 2, Reports 9, Reports 13, The machine 4*

The line Cycles carries about finding no compatible graphics card is drawn in the preferences panel and nowhere else. A windowless render never prints it; it falls back to the processor and says nothing. For 5.3, which never met that case, the line belonging to the panel alone is inferred. **That silence belongs to the file's and the machine's own settings and not to every route**: a technology named on the command line with no hardware behind it ends the run at a failure status and writes no file, in every version on two machines and in 5.3 on the Mac, and nothing falls back to anything. *The machine 4, What a render demands 7*

**The sharpest case of that silence is the one a freshly rented machine is already in.** At factory settings every card is ticked and no technology is chosen, so a scene asking for the graphics card renders on the processor and Blender says nothing at all — both streams were searched for the words that would say it and nothing matched. Anybody who rents a machine for its cards and never chooses a technology pays for the cards and gets the processor. **Two things about that sentence have to be read exactly.** The ticks were read **after the card list had been refreshed**; before anything fills it the list is empty and the machine answers that it can see no cards at all. And **what the technology starts at is a fact about the machine, not about Blender** — it reads as nothing on a rented Linux machine and as the Mac's own graphics name on the Creator's Mac, in all five versions from a fresh settings folder — so it has to be read on the machine in hand and never assumed. **In 5.3 on the Mac a chosen technology was not enough either**: with Metal already chosen and a settings folder nothing had ever been saved into, a card scene rendered on the processor and said nothing, because the card list had not been filled; once one run had refreshed it and saved the preferences, the same render went to the card. Whether the earlier Mac builds do the same in this never-used-folder setup is not settled. *The machine 4, The machine 5, Add-ons 3*

When one of several files for a frame cannot be written, the node's own property list holds nothing carrying warning text, in all five versions, so none of it can be read without a window — and in 5.3 on the Mac, with the window open, nothing on screen named the lost file either. Nor is there a hook to catch it: Blender's list holds a failure hook for loading a file and one for saving a file, and **none for writing a render frame**, in all five. The printed line is all there is. *File output nodes 15*

The one thing that runs the other way: **with a window open, no way of starting a render prints any progress at all, in any version, 5.3 included.** With no window, a render started from the command line prints its full progress. The unattended arrangement is the one where progress can be read. *Reports 9*

## No screen and no display server are not the same thing

For the refused window they cannot be told apart: a machine merely pointed away from its display and a machine with none gave the same message and the same endings, word for word, in every version. *Settings 6, The machine 1, Add-ons 3*

Everywhere else the machine's display state leaks in. On a Linux machine that has a screen running, a windowless render in one version, 5.2, wrote display-library complaints to the error stream on a completely successful run, and turning the display off silenced them. 5.3 was never run on such a machine. *Reports 2*

Nor are those complaints the mark of a machine without a display server. On a machine that has none they stayed away when Blender was given the card's own graphics library and came word for word when it had only a software one, so what decides is which library Blender gets. Two runs there disagree, and the disagreement stands unresolved. *The machine 7*

Which stream a message lands on is not fixed either. The refusal to open a window goes to the error stream in 4.5 and to the ordinary output in the other three; and some of Blender's own words reach the error stream in every version anyway, 5.3 included on the Mac — one kind of render complaint, and the tested complaints Blender makes about the command line itself, with more of them in 4.5 than in the later versions. **Both streams have to be watched.** *Settings 6, Add-ons 3, Reports 2, What actually ran 5*

Beside that, three topics state the rule with no such condition: with no window and no display attached, everything goes to the ordinary output and the error stream stays empty, bar named exceptions — in 5.3 on the Mac as well. Two of them looked for that silence deliberately rather than meeting it — one ran the empty stream as a control before every silence it reports, the other fed a whole run's error stream to a reader and got nothing at all — so the rule rests on more than chance. *What actually ran 5, Reports 13, Reports 14*. **Neither having no window nor having no display attached guarantees an empty error stream.** The controls settle those runs; the failed runs and the graphics-library tests still require both streams to be watched. *Reports 2, The machine 7*

And what Blender can be asked about its own state is one thing and not another. Counting the screen's areas tells you nothing: on macOS a windowless run reports the same screen with the same areas as a windowed one (*The compositor 8*). **One launch flag does report it**, reads true in every run started with no window, in all four versions on two machines and in 5.3 on the Mac, and refuses to be written to, so nothing inside the run can forge it (*Writing 13*).

## What this does not cover

- What a render prints line by line, and what an exit status is worth. Only the screen's part in both is here.
- What a stopped or crashed render leaves on disk.
- Two Blenders sharing one output folder, which is its own subject.
- Blender 5.3 on any machine but the Creator's Mac. No Linux machine, no NVIDIA card and no machine without a screen ran it, so every Linux, card and no-display-server answer here is an answer for 4.5 to 5.2 unless 5.3 is named. *Settings 6, The machine 1*
- Windows, apart from one test. One question behind this document reached a Windows machine: a stop delivered to Blender 4.5 on a machine reporting itself as **Windows Server 2025 Standard**, with no graphics card at all, which ended the run at the same number macOS and Linux give for a stop of that kind. Everything else about screens, windows and unattended running there is untried rather than out of reach — a Windows machine can be rented, and the unpacking half is written out and waiting on one. *Frames 15, Builds 10, The machine 7*
- A Linux machine with no graphics hardware at all, and a machine whose screen is physically unplugged. The one machine here with no graphics card of any kind was a Windows one, and only that single stop test ran on it. *Add-ons 3, Settings 6, Frames 15*
- A Mac with no display server. The screenless answer is a Linux answer. *Settings 6*
- What a display going to sleep, or a screen lock, does to a running render. *The machine 7*

## What the evidence could not have shown

- The screenless engine answer rests on 64 by 64 pictures on Linux machines with no display server; a Mac with none, a machine with no graphics hardware, and 5.3 on any such machine were never run. *Settings 6*
- "An add-on can be set up with no screen" was got on a machine that still has two graphics cards; no screen was ever unplugged anywhere. *Add-ons 3*
- The refused engine-list call ran on a machine that **has** a display server and was merely pointed away from it. A list was printed on a machine with none; the setups must be kept apart. *Add-ons 2, Settings 13, The machine 1*
- The window-against-no-window picture comparison was run on the Creator's Mac, in all five versions, the only machine that topic had with a screen. No rented machine with a display server has been asked it. *The compositor 8*
- "Nothing waits for a person" rests on two machines in 4.5 to 5.2, and in 5.3 on the Mac with its screen on and the Creator logged in, which is never a machine with nobody at it. Every dialog on record is one that could be reached only where a window exists; the sources say nothing about any of them without one. *The machine 7*
- The sleep-and-screen-lock test was written out in full and deliberately not attempted: it needs a machine with a screen of its own put to sleep and left alone, and the only such machine that topic had is the Creator's. *The machine 7*
- A bare command-line render ignores the workspace's sequencer scene and renders the active scene, in 5.0 to 5.2 on both tested machines and in 5.3 on the Mac. Naming the scene selects it; in 5.3 the script command's sequencer-scene choice also reaches it. *The compositor 7, Settings 12*
- Thirteen of seventeen windowless compositor tests were run on Linux alone in 4.5 to 5.2, and 5.3's on the Mac alone; nothing blocked the other half, it simply was not run, so those thirteen settle Linux for the earlier four. *The compositor 8*
- Whether the sequencer's repointing command runs with no window on Linux was never asked; the run there supplied neither of the two things the command wants. *Reading a file 9*
- The report list's being empty proves nothing on its own, in 5.2 or 5.3: a control that certainly failed left it empty too. *File output nodes 15*
- In 4.5 to 5.2 everything a screen would show on a failed write was untested on **both** machines, so a screen-only signal could not have appeared; 5.3's window was looked at on the Mac alone. *File output nodes 15*
- "With a window, nothing prints progress" rests on windowed runs all begun by one operator call, never by a key press. *Reports 9*

## Keep the engine-list setups apart

An engine list was printed on a machine with no display server in 4.5 to 5.2, though 4.5 then hung. On a machine merely pointed away from its display, the call in *Add-ons 2* printed a display failure instead. These are different setups; the refusal does not erase the successful listing, and neither promises every launch will work. 5.3 was never asked on a machine without a display. *Add-ons 2, Settings 13, The machine 1*
