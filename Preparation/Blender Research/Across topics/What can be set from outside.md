# What can be set from outside

What a render can be handed at the moment it starts, without changing the artist's file — and what it will not take.

> **This joins answers that live in several topics.** Every claim below names the comparison
> questions it rests on; open those for the exact words, the exact messages, and what each
> version does. Where this document and a comparison disagree, the comparison is right.

*All four versions*, *every version* and *any version* mean Blender 4.5 to 5.2 here, and *the newer three* means 5.0 to 5.2. Blender 5.3 is named wherever it is meant, and every 5.3 result is the 5.3.0 Beta built 2026-10-16 on the Creator's Mac alone — so no Linux machine and no NVIDIA card ever ran 5.3. *Settings 1, The machine 5*

## The short answer

- The scene values tried have to be set in one window: **after the file, and before the render instruction**. Outside that window it is silently ignored — no message, no failure, the render goes ahead on the file's own value. One argument is not bound by it: a non-zero thread count is taken whichever side of the file it sits on (*Writing 1*, *What a render demands 3*, *Dependencies 17*, *Settings 16*, *Writing 13*).
- Only a short list of settings has an argument. Everything else is reachable by a small script or expression handed in at launch, inside the same window (*Settings 1*, *What a render demands 3*, *Settings 17*, *Settings 19*).
- **What is handed in at launch may or may not be checked. Four kinds of thing end the run at a failure status; ten let it finish and report success; one more is refused loudly and leaves the run going** (*Reports 12*, *Settings 9, 12, 13, 15, 17, 18*, *Dependencies 17*, *What actually ran 4*, *Images 3*, *Frames 7*, *Add-ons 3*, *What a render demands 7*). One of the four is a failure only where it sits — in one place it does not end at all, and in another it is swallowed in silence and the run reports success; see *One window on the command line*, below.
- Nothing imposed at launch is written into the file unless something saves it in that run. The output-path and engine arguments each affect one scene; in 5.3 the output path reaches the scene active when the argument is read, so a scene named on the line has to come before it (*Settings 1*, *Writing 1*, *Writing 13*, *The compositor 9*, *Reading a file 9*, *What a render demands 3*).
- An imposed value is not the last word. The file, the machine's saved preferences and the engine can all displace it, and mostly say nothing when they do (*Settings 16*, *Settings 13*, *The compositor 2*).

## One window on the command line

Two comparisons carry the two edges of that window and neither carries both.

- **The left edge.** Loading the file overwrites whatever was set before it, so a value placed ahead of the file is lost (*What a render demands 3*, *Writing 1*). The same rule read from the other side: the path stored in the file beats one given before it and loses to one given after it (*Dependencies 17*). One argument escapes it: a non-zero thread count is written into the scene whichever side of the file it sits on; zero leaves the stored value alone (*What a render demands 3*, *Writing 13*).
- **The right edge.** A value placed after the render instruction arrives too late; the render has already happened on the file's own number (*Settings 16*).

Both edges are silent. Nothing is refused and nothing is reported — the run simply produces the file's own result. *Writing 1, What a render demands 3, Settings 16*

**The left edge is a test result and not only a reading of the manual, and it has a way round it.** Five arrangements of the file, the setting and the script were run in all four versions on two machines and in 5.3 on the Mac, and they came out exactly as the ordering rule says. A script placed before the file runs in a Blender that has none of the file's scenes yet — but a handler it registers there, marked to survive a file load, does fire after the load and then sees the file's own scenes. **So a script that ran too early has a second chance, and it works.** *Writing 13*

**Part of that window belongs to somebody else.** After a bare double dash the line is Cycles', and every Cycles argument — the render device among them — is read only there and nowhere else (*Settings 9*, *The machine 5*, *What a render demands 7*, *Settings 17*, *Reports 12*). The engine argument is Blender's own and is held to the left edge like the rest (*What a render demands 3*).

**An argument name the running version does not carry is taken for a file to open, and where that leaves the run depends on where it sat.** Written after a valid argument and before the double dash it ends the run at a failure status, sometimes with nothing written and sometimes with a frame already on disk (*Settings 9*, *Settings 1*, *Settings 17*, *Reports 12*). **Written before the file it is worse.** That is the shape the manual itself gives as an example, and it ends 4.5 at a failure status while 5.0, 5.1 and 5.2 open the file that followed and **never end at all** — still running at ninety seconds, on two machines, on repeated runs — and 5.3 the same on the Mac (*Reports 12*). **Written after the double dash it is not a failure at all**: the line there is Cycles', an argument Cycles does not know is swallowed without a word, and the render goes ahead and ends at success — with a control proving arguments in that position genuinely are read, in all five (*Settings 17*, *Reports 12*). So an argument a version does not know is not reliably a failure a caller can wait for, and in one of the three places it is not a failure at all.

## What has an argument, and what needs a script

An argument of its own, in all five versions: the frame range and the interval to skip by, a list of separate frames, the engine, the scene, the output path, the image format, whether the ending is added, the thread count, and the render device and statistics switch (*Settings 1*, *What a render demands 3*). Frame lists are taken in the order written, may mix single frames and stretches, and repeat a frame if it is named twice (*Frames 7*).

No argument in any of the five: the sample count, the resolution percentage, whether a view layer renders, tile size, persistent data, render region, simplify, the time limit, denoising, bounces, every denoising setting a scene or a view layer carries, the three hardware ray-tracing switches, and every setting belonging to the other two engines (*Settings 1*, *What a render demands 3*, *Settings 17*, *Settings 19*, *What a render demands 7*). All of them can be set by a script or expression handed in at launch. An instruction that names no scene sets **the active scene** (*Settings 1*, *What a render demands 3*, *Settings 17*, *What a render demands 7*). Where the picture comes from a second scene pulled in through the compositor, that scene's own values are what render and the compositing scene's do not leak into it; a launch script that names the pulled-in scene and sets its count before rendering does reach that render (*The compositor 9*). A compositor output node's own place is in that group too — no version has an argument for it, and the two values a script has to set are not the same in 4.5 as from 5.0; and in 4.5, where the node gathers its outputs into one multi-layer file, the first of those two is the start of the file name and not only a folder, so a script writing a folder there has to end it with a separator (*Writing 9*, *Reading a file 9*). **No argument anywhere sets a sample count**, by each version's own account of itself; offered one, Blender neither takes it nor refuses it (*The compositor 9*).

**One argument name is a trap of its own.** From 5.2 there is an argument that names the card Blender **draws** with; it is not the one that names the card Cycles renders on, it applies to one graphics interface only and is otherwise ignored with a warning, and in 4.5, 5.0 and 5.1 it does not exist — so a launcher that passes it to those three has handed them a file name (*Settings 1*, *The machine 5*).

That the three most-wanted of these have no argument was re-established from the built program rather than from the manual: each version's whole help listing was captured and searched, with a control proving that an argument in that position really is read (*Settings 17*).

**Setting a value from a script is not the same as starting the render from one.** From 5.0, 5.3 included, a render started by calling Blender's own render command from a script prints nothing at all while it works, where the command-line route prints its full progress (*Reports 9*). A builder who reaches for a script to set a sample count should still start the render the ordinary way. All five ways of handing a script in at one launch — a file, an expression on the line, a text block inside the blend-file, a registered command, and text piped in — see exactly the same thing (*Writing 13*).

Two more things can be imposed at launch. An add-on can be switched on for that one run, leaving the machine's saved preferences untouched and gone by the next run (*Add-ons 3*, *Add-ons 5*). And whether the file's own stored scripts are allowed to run is decided by a preference on the machine, which two launch arguments override in either direction (*Settings 11*) — those two arguments do not reach the script handed in at launch, which runs either way (*Writing 13*). **Nor do they reach everything stored in the file**: in 5.3, the only version asked, a text block named on the launch line and a shading-language script stored in the file both ran whatever those arguments said (*Settings 11*). **A run can find out for itself that a stored script was blocked**, without anything having to read the terminal: two values inside Blender report it and carry the reason, in all four versions on two machines and in 5.3 on the Mac (*Settings 11*, *The machine 7*).

## What is checked, and what is taken on trust

**Four kinds of thing end the run at a failure status.** Three of them write no frame at all: an engine name no engine bears — from 5.0, 5.3 included; in 4.5 the run ends at nothing a caller can use, and which way it fails is the operating system: an abort on the Mac, and on every rented Linux machine that has been asked, in this topic and in three others, no ending at all (*Settings 13*, *Reports 12*, *The compositor 9*, *Add-ons 7*); a device or a technology the machine cannot serve, named at launch, where nothing falls back to anything (*Settings 9*, *What a render demands 3*, *What a render demands 7*, *What actually ran 4*); and a broken template in the output path — tested on the path stored in the file, for a single frame as well as an animation (*Dependencies 17*). The fourth is an argument name the version does not have, which is taken for a file to open: there the frame can already be on disk when the run fails, **and it is a failure only where it sits** — before the file 5.0 to 5.3 do not fail but never end, and after the double dash it is swallowed in silence and the run ends at success (*Settings 9*, *Settings 1*, *Settings 17*, *Reports 12*).

**Ten let the run finish and report success**, and three of the ten render nothing at all:

- A scene name no scene bears is named and then ignored (*Settings 12*).
- An image-format name Blender does not know draws a complaint and then the frame is written in the file's own format (*What actually ran 4*).
- A format name a version has not got yet is refused the same way (*Images 3*).
- A malformed frame list renders nothing at all (*Frames 7*).
- An add-on name that does not exist is reported and the run carries on (*Add-ons 3*).
- A number above a setting's own ceiling but still inside a whole number is corrected without a word and the render goes ahead at the corrected value (*Settings 15*, *Settings 18*).
- **A misspelled property name inside a launch instruction, with the ordinary script-error handling.** In every settings group, in every version and in 5.3, Blender names it on the terminal — bar Cycles' own settings in 4.5, where nothing is said at all and the value is gone the instant it is read back. Either way the render goes ahead, the picture is saved and the run ends at success — **neither the ending status nor a read-back separates a working instruction from a broken one** (*Settings 17*).
- A frame value that is not a number: the complaint lands on the error stream, the run ends at success, and the output folder is empty (*Reports 12*).
- An option whose value is missing, which behaves the same way — error stream, success, empty folder (*Reports 12*).
- A graphics-interface name the operating system does not accept is named in an error and then ignored; the render still finishes and saves the frame (*What a render demands 7*).

**And one kind is refused loudly and leaves the run going.** A sample count past what a whole number can hold, or given as a decimal, a word, or nothing at all, is refused with an error naming the setting, and the setting keeps the value it had; the value true was accepted and stored 1. False was not tested. **What such a run hands back at the end is not settled** (*Settings 18*).

All fifteen came out the same way in 5.3 on the Mac, where 5.3 was tried. A launch option can turn an uncaught script error into a failure ending and stop the render; it must come before the script. That also applies to a refused assignment inside the script (*Reports 12*).

Three cautions sit under all of that.

**A number inside the range is not safe either.** One that works out to a picture too small to make stops the render with a complaint, writes no file, and still ends at success (*Settings 15*, *Reports 12*).

**A saved scene's failure can also turn on the route used to render it.** In 5.3 on the Mac, the tested Cycles scene on the processor with its Camera object deleted ended at success from the command line, with no picture and no render handler. Called from a script, the same file still ended at failure. The 5.2.2 command-line control failed. That is this scene's result, not a rule for every engine or every way a camera can be absent (*Reports 12*).

**The refusal is not printed the same way everywhere.** It gives the whole-number limits in ordinary figures on one operating system and in a shorter notation on the other, so anything reading Blender's output to catch it has to match both shapes — and a third shape on Windows is possible and untried (*Settings 18*).

Two names need care beyond that.

- **The engine name changed at 5.0, and which name a version takes depends on the route.** The version's own name works by every route. In 5.0 to 5.2 the command line also takes 4.5's name, while a script takes only the version's own; whether 5.3's command line takes 4.5's name was never tried (*Settings 13*, *Images 9*, *What a render demands 3*, *The compositor 9*).
- **After 4.5, which route asks for multi-layer output decides whether it is granted, and the two routes do not behave alike.** A script that assigns the format name has it refused from 5.0 until a media type is set to multi-layer first, and setting the format alone writes an ordinary picture at a success status — in 5.3, and in 5.2.2, with a refusal printed on the error stream; whether 5.0 and 5.1 print one is not settled. 4.5 has no media type and takes the name straight. **The launch argument is the other route and does not behave this way** — handed the same name on the line, all four versions write a real multi-layer file, on two machines; Settings 17 also records that argument writing a real multi-layer file in 5.3 on the Mac. So a builder taking the script route sets the media type as well and checks what came out, and one taking the argument does not have to (*Reports 11*, *Images 3*, *What a render demands 3*, *Settings 17*, *Settings 1*).

## What an imposed value does not set aside

- **A sample count handed in is a ceiling, not a quantity.** Five things in Cycles stand between it and the samples a pixel gets, and a view layer's own number can stand in place of it entirely; in the other real-time engine two features push the number up instead, and in 5.3 that engine has a time limit of its own that can stop it short (*Settings 16*, *Settings 17*). Nothing announces any of this while it happens (*Reports 11*, *Settings 16*).
- **A count too large is not one number's problem.** Each count is corrected against its own limits, so the same number handed to two engines is cut down by one and taken whole by the other, and neither says a word. **There is no single ceiling for "the sample count".** Two places carry the corrected figure and neither announces it — the setting read straight back, and the progress line Blender prints while it renders — and the second is not to be relied on: a sample subset or a view layer's own count makes that line count against something else instead, and on a render started from a script rather than from the command line it is not printed at all from 5.0, which leaves the read-back as the only reading (*Settings 18*, *Settings 16*, *Reports 9*).
- **An engine does not survive its add-on being switched off, and what that costs depends on where the engine was named.** Left to the file's own saved engine, the render goes ahead on the real-time engine at that engine's own sample count rather than failing, a picture is written and the run ends at success — the same whether the missing engine is Blender's own or one that was never installed. **Named at launch instead, the same missing engine is refused outright and nothing is written**, which is the loud failure above and not this quiet substitution (*Settings 13*, *Add-ons 7*).
- **And an engine is not a setting that leaves the picture alone.** A scene set up for one engine does not come out the same in another, in all five versions: some features work in only one of them, one approximates where the other computes, and the third engine does not use shader nodes at all. The earlier four versions' manuals also say it is not meant to make finished pictures. **That rests on the manuals and on nothing else** — it is the one question behind this document that no test touched, in any version, on any machine — and it is the bound to put on every engine argument here. Handing an engine in, or letting one fall back because its add-on was off, changes what is rendered and not only how long it takes (*Settings 7, Settings 13*).
- **An imposed output path does not reach a compositor output node** (*Writing 9*), including where that node belongs to a scene pulled in through the sequencer, where the containing scene's own render moves and the node's path does not (*File output nodes 17*). And from 5.2 a switch inside the file stops the scene's own frames being written even when a path is handed in on the command line, while a compositor output node in the same tree keeps writing; with that switch off and no such node, 5.3 writes nothing at all and still ends at success (*The compositor 2*).
- **An imposed output path does not decide that anything is written there.** Whether a render skips frames already on disk is a switch in the file with no argument of its own, and where it is set to skip, a frame is skipped on the bare presence of a name — a folder of empty files means nothing is rendered at all and the run still reports success. Every skip test used one view; what the check tests with several views is not settled (*Dependencies 17*, *Frames 4*).
- **An engine handed in at launch does not reach a scene pulled in through the compositor.** That scene is rendered with its own engine and its own count, always; the argument writes onto the active scene and onto that scene alone (*The compositor 9*).
- **The switch that would render one view layer only never reaches a render started from outside**, so a second view layer renders, at whatever sample count it carries (*Settings 1*, *What a render demands 3*, *Settings 16*). **But a view layer can be switched off from outside all the same** — by a different setting on the view layer itself, whose name looks nothing like the near-miss one, and setting it removes that layer's channels from the file Blender writes, in all five versions. That was got on the Creator's Mac and on no other machine (*Settings 17*). Switch every layer off, and 5.3 renders nothing and still ends at success; that was never tried in an earlier version (*Settings 1*). Whether a view layer renders can also change from frame to frame inside one run (*Settings 1*).
- **A non-zero thread count given as an argument caps what a later script may assign**, whichever order the two sit in (*What a render demands 3*, *Writing 13*).

## Denoising, which has no argument at all

Not one denoising setting has a launch argument in any of the five versions, and every one of them is reachable by a script handed in at launch (*Settings 19*, *Settings 1*).

- **Cycles denoises only when both switches are on** — the scene's and the view layer's. Either alone denoises nothing at all, which is worth knowing before a script is written to turn denoising off by moving one of them (*Settings 19*).
- **Two of the settings do nothing under another denoiser.** The prefilter and the quality change nothing whatever unless one particular denoiser is chosen; the documentation says only that they are not drawn, never that they are ignored. That was got on the rented Linux machine alone, because it needs two denoisers on one machine, and it is untested in 5.3 (*Settings 19*).
- **A denoiser named in a file that the machine has not got is quietly replaced.** The render goes ahead, the picture is still denoised, and the setting reads back as empty text rather than as the name that was stored. A warning is printed only when a script reads the setting, so a run that never asks says nothing about it (*Settings 19*).
- **One card-and-driver failure is on record and must not be widened.** On one rented machine, with one card on one driver, asking Cycles to trace on the card under one of the two NVIDIA methods failed outright in 5.2.1 and worked in the other three versions. That is a result about that card on that driver and not a statement about Blender 5.2 anywhere, and 5.3 had no such card to try — and it is kept because anyone choosing a driver for a render farm would want to know it can happen (*Settings 19*).

## What the machine still decides, and what is never written back

- **Which card renders is settled by three things that must line up**, and only one of them is in the file. The launch option forces a technology and can never name one card; where there is a choice it takes every card of that kind, whatever the machine's saved preferences said, and it writes nothing back — in 4.5 to 5.2; 5.3 was never run with more than one card (*The machine 5*, *Settings 9*).
- **The launch option beats the stored preference and the file, in both directions.** A machine whose preferences name no technology and a scene set to the processor still rendered on the card when the argument named one, and a machine set up for the card was still pulled onto the processor when the argument said so (*What a render demands 7*).
- **With no argument, a card render needs both halves of the preference.** The technology chosen, a card ticked under it, and the scene set to the card. The technology chosen with nothing ticked renders on the processor instead, with the scene still asking for the card (*What a render demands 7*).
- **The scene's processor-or-card choice travels in the file; the technology does not** — that reads back as whatever the machine's own configuration holds (*What a render demands 7*, *Settings 9*).
- **The list of technologies a machine offers is not built from the cards in it.** One rented machine with a single NVIDIA card offered four technologies and None; what was empty there was the list of cards under two of them, not the choice itself. **A technology appearing on the list is no evidence the machine can use it**, and reading Cycles' own files suggests the opposite (*What a render demands 7*).
- **Where a device request comes from decides whether it fails loudly or quietly.** Named at launch with no hardware behind it, the run stops with a failure status and no frame (*What a render demands 3*, *What a render demands 7*, *What actually ran 4*). Left to the file or to the machine's preferences, the same impossibility renders on the processor, writes the picture and reports success (*Settings 9*). A builder who wants to know that a render used a card must name the technology at launch; success alone proves nothing.
- **Blender can be asked which cards it sees, and the obvious check answers wrongly.** Every route named every card on machines with one, two and four of them, in all four versions, and a plain count of cards came back right on each. **But the question whose name reads as *has this Blender more than one device* answered false with two cards ticked and false again with four** — in all four versions on both machines — so it must never be used to confirm that a job took every card. And what Blender was **built** with is a separate question from what it can **find** in that run; Blender answers the two apart, and hiding a card left the built-with answer untouched while both card lists came back holding the processor alone (*The machine 6*). **But the list is not there until something fills it.** On a factory-fresh Blender, asked before a refresh has been called for, before the preferences panel has been drawn and before any preferences file has been saved, the card list comes back empty in all four versions and in 5.3 on the Mac — so a launcher that asks once and asks first is told the machine has none (*The machine 5*). And in 5.3 on the Mac a card render from a settings folder nothing had been saved into went to the processor in silence for that reason, with the technology already chosen (*The machine 4*).
- **The machine's saved preferences are a third home for settings**, read by a plain run and discarded by a factory-startup one (*What a render demands 3*, *The machine 5*).
- **Naming a scene picks that scene, and its own settings and its own compositor are what run** — though from 5.0 two scenes can be pointed at one compositor, and a shared one follows the scene named inside it rather than the one being rendered (*Settings 12*, *The compositor 3*).
- **Nothing set at launch touches the file**, unless something in the same run saves it, which writes the imposed value in. Otherwise the file's size, modification time and stored values are unchanged afterwards (*Settings 1*, *Writing 1*, *Reading a file 9*, *What a render demands 3*, *Dependencies 20*).
- **The output-path and engine arguments each reach one scene.** A search of the file's data, the preferences and plain launch values found an imposed output path among Blender's own settings in one place only: the active scene's own output path. A second scene in the same file kept its own. The engine argument behaves the same way — it writes onto the active scene alone, and reopening the file afterwards shows both scenes unchanged (*Writing 13*, *The compositor 9*). **In 5.3 which scene that is turns on order**: a scene named on the line before the output path takes the path and renders into it, and one named after it renders to its own stored path while the path lands on the scene that was active before (*Writing 13*).
- **A launch-time script can check what it was given and refuse.** A script that reads the setting back, compares it against what the caller intended and stops when they differ ended the launch at a failure status with nothing rendered and nothing written, and let the run through when they matched. **The value it reads back is the raw text handed in**, template marks and all, so the comparison is against that text and not against a finished file name (*Writing 13*).
- **A value read out of an older file is not always the value that was saved.** In 5.0 to 5.2 one Cycles tiling pair is rewritten as a 4.5 file loads, so what is read back is not what was stored; 5.3 was not given such a file (*What a render demands 5*).

## What this does not cover

- Preparing the machine — installing Blenders and add-ons, and what the machine's saved preferences hold. Only the one-run add-on switch is here (*Add-ons 3*, *Add-ons 5*).
- What a render prints while it runs, what its ending is worth, and where its files land.
- What a file can be asked before a render starts.
- **Whether an add-on switched on at launch arrives early enough for the engine argument to see it.** No third-party engine was ever installed on a machine that could have posed it, and installing one was not allowed there, so it is untried in every version, 5.3 included (*Settings 13*, *The compositor 9*). What a file naming a **missing** third-party engine does is settled: one was built for the purpose and run in all four versions on two machines and in 5.3 on the Mac, and it behaves exactly as a missing built-in engine does, which is above (*Add-ons 7*).
- A render a person starts inside Blender's own window by pressing a key. **Having a window is not the same exclusion**: a script running inside a Blender with a window produced the same picture to the last bit as one started from a terminal, and a launch-time script read the same setting with a window open as without, on two machines in all four versions and in 5.3 on the Mac (*The compositor 9*, *Writing 13*).
- Blender 5.3 on anything but the Creator's Mac. No Linux machine and no NVIDIA card ran it, so every Linux, device and card answer here is an answer for 4.5 to 5.2 unless 5.3 is named (*Settings 1*, *What a render demands 7*).
- Windows. **Not one of the questions cited here was run on a Windows machine, in any version, 5.3 included.** For most of it that is untried rather than out of reach: a Windows machine can be rented, and every one this project has read reported itself a **Server** edition, so any answer taken there has to name its edition. **The card half is untried too, and not out of reach.** The one Windows machine this project has ever read for hardware had no graphics card of any kind and was ordered without one; of the others, one was abandoned unread and the rest carry no graphics reading at all. Nothing establishes that the route cannot supply a Windows machine with a card, so **a device, a technology and a rendering method wait on a machine asked for with one**, rather than being unaskable there (*What a render demands 7*).

## What the evidence could not have shown

- *Settings 1* — that the sample count, the resolution percentage and the view-layer switch have no argument comes from searching each version's help text for four word fragments. An argument worded otherwise would have been missed. *Settings 17* re-established the same absence from the built program with a control, which is stronger evidence for the same answer.
- *What a render demands 3* — "nothing else has an argument of its own" is a read of the whole arguments page against a named list of settings. A setting nobody listed could not have shown up as missing.
- *Settings 17* — **every run in that question was on the Creator's Mac.** For 4.5 to 5.2, other questions exercised the resolution percentage, Cycles' count, the layer switch and its count on Linux. EEVEE's and Workbench's count names were not exercised there. The silent misspelling, labels and other Mac-only results keep that bound; no setting name was exercised on Linux in 5.3 (*Settings 1*, *Settings 16*, *What a render demands 3*).
- *Settings 18* — the ranges and the refusals rest on two machines, and the corrected-value trap is the same on both. What it cannot show is one ceiling for anything: each count has its own, so no figure from it may be read as *the* limit. The very large corrected-count renders were stopped before finishing. The low-end control did finish and write its picture, but no corrected-count picture's own stored count was read.
- *Settings 19* — the prefilter-and-quality result needed two denoisers on one machine, so it ran on the rented Linux machine alone; the Mac offers one denoiser and could not have posed it, in any version. The channel counts in the compositor-denoise result are not reproducible in 4.5, 5.0 or 5.1, so the last digit of any of them is not a number to build on, though the verdict beneath it is not in doubt.
- *The compositor 9* — its own runs were on the Creator's Mac. The EEVEE layer-override difference also has Linux tests in 4.5 to 5.2 under *Settings 16*. The other results keep the Mac bound.
- *What a render demands 7* — the Mac answers Apple's method and nothing else and the rented Austrian machine answers NVIDIA's two and nothing else, so **a card result from one is never a card result from the other**. The long measurement of how far two runs of the same method come apart is macOS and Apple's own graphics only; the NVIDIA rows rest on a floor measured once.
- *Writing 13* — in 4.5 to 5.2, that an imposed output path reaches the active scene alone rests on one file holding two scenes, so whether it turns on which scene is active could not have shown. In 5.3 it does turn on it, on the Mac.
- *Writing 13* — the search for the output path followed links to a depth of five in 5.3. Its one match is what that search found, not proof about every possible place.
- *Settings 16* — the rule that a count must come before the render instruction rests on one file, and every Cycles render behind that question was on the processor, 5.3's included, so a different rule on a graphics card could not have appeared. Every time-limit run used one view layer; a limit per layer is not settled.
- *Settings 13*, *Images 9* — that 5.0 to 5.2 accept 4.5's engine name at the command line rests on one run, on one machine, on a 64 by 64 scene, and whether that run really used that engine was never captured.
- *What a render demands 3* — that a script at launch reaches the render was shown at a sample count of seven and at a 160 by 120 picture; nothing at a size a real job reaches was tried.
- *The compositor 2* — that 5.2's switch writes nothing rests on one two-frame animation from a terminal, with no other way of starting a render tried while it was off; 5.3 was tried with a single frame as well, on the Mac.
