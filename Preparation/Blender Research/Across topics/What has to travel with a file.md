# What has to travel with a file

What a `.blend` needs beside it on a machine that has never seen it, what can be found before it is sent, and what has to be repointed once it arrives.

> **This joins answers that live in several topics.** Every claim below names the comparison
> questions it rests on; open those for the exact words, the exact messages, and what each
> version does. Where this document and a comparison disagree, the comparison is right.

*All four versions* and *every version* below mean Blender 4.5 to 5.2, and *the newer three* mean 5.0 to 5.2, as they do in the comparisons; 5.3 is named wherever it is meant. Every 5.3 result is the 5.3.0 Beta on the Creator's Mac and nothing else — no Linux machine, no Windows machine and no NVIDIA card ran it, and no 5.3 file was carried to another computer.

## The short answer

- Following the file's own outward pointers gathers most of what has to travel, not all of it: no established list inside the file tells which add-ons a render needs (*Add-ons 1*), the receiving machine has to match the file's colour names and denoiser choice (*Dependencies 15; Settings 19*), and which of a card's rendering methods does the work is not in the file at all (*What a render demands 7*).
- No single tested way of listing or rewriting reaches all of a file's recorded locations, in any version, 5.3 included, and most of what the plain ways miss is the places the file writes to (*Reading a file 5, 9; Dependencies 17*). Nor do two of those ways reach the same set: in the Windows test the plain list missed a linked library's own image while the map found it. That is not a rule that the plain list never reaches into libraries: it listed a linked node setup's image and, from 5.0 through 5.3, its import file (*Dependencies 20; Node setups 2*). In 5.3 a path typed on a geometry-node modifier is missed by both lists and both rewrites (*Node setups 1*).
- One recorded location can stand for many files on disk, and the plain ways of listing hand back the written text rather than the files. Only 5.2 and 5.3 can be asked to expand it (*Dependencies 4*).
- A relative location is measured from the file that holds it, so each linked file's paths belong to that file, and the chain can only be read as far as the files already in hand (*Dependencies 13; Node setups 2; Reading a file 8*).
- A relative location survives the move to another kind of computer and a full one does not — in 4.5 to 5.2, for no 5.3 file was carried — and home shorthand or an environment variable was not expanded in the tested paths (*Dependencies 5, 6*).
- **Opening a file re-spells its separators to the computer's own, and a plain save then writes that in.** Carried between a Windows machine and a Mac or a Linux machine, a file's whole recorded text is rewritten, both ways, by a save that touched nothing — in 4.5 to 5.2, the only versions taken to Windows (*Dependencies 20*).
- **Saving into a different folder rewrites the tested relative places the file reads from and leaves the tested places it writes to exactly as they were** — which after the move means a different place on disk (*Dependencies 20*).
- When a file is loaded, capitals follow the disk: the Creator's Mac has the forgiving disk and **the machine a render runs on has the strict one**, so a path that loads for the artist can fail on the render machine — in 4.5 to 5.2, for 5.3 was not run on Linux. The repair does not close it, because the repair follows Blender's own exact rule instead and refuses a differently-spelled name on either machine (*Dependencies 8; Node setups 1; Reading a file 9, 10*).
- Packing takes some kinds and leaves others, in all four versions and in 5.3, and says nothing about the gap (*Dependencies 3; Node setups 1, 2*).
- When something the file points at did not arrive the render usually finishes and reports success (*Dependencies 12; Images 9; Add-ons 7*). The one exception is the engine named at launch: with its add-on absent, no image is written, and 4.5 aborts on the Mac or hangs on Linux (*Add-ons 7; Settings 13*). Asking before the render is the only check, and it has holes.

## What the file names, and what it does not

The tested kinds of outside reference agree in all four versions and in 5.3; a complete, identical set is not established. What exists inside Blender to find and name them is not, and that boundary falls at 5.0 with one further addition at 5.2, which 5.3 has too (*Dependencies 1*). No version's own sources claim the list of kinds is complete, and every version says so (*Dependencies 1*).

Four needs cannot be gathered from the file's paths alone.

**Add-ons.** No version's sources describe a record inside a file of the add-ons it needs, and none describes a way to read one out (*Add-ons 1*). One partial trace closes at 5.0: a Blender that does not have the add-on which planted a scene's settings can still list that add-on's block as a bare key on the scene in 4.5, and lists nothing at all from 5.0 onward, 5.3 included (*Add-ons 1*). An add-on does not travel with the file, and it does not simply travel on its own either: carried between two kinds of computer, in 4.5 to 5.2, the install and the plain part arrive and the compiled part does not, with nothing said until something uses it; 5.3 was not carried (*Add-ons 4*). An installed add-on is kept apart from another Blender's only by the folder it sits in — in 4.5 to 5.2, for no 5.3 add-on was set beside another version's (*Add-ons 6, Add-ons 14*) — and an extension is expected to bring what it needs rather than find it already there (*Add-ons 11*).

**Four tested things affect whether an add-on set up for one Blender works in another**: which folders that Blender reads; the Blender range the add-on itself declares; the Python that Blender carries, for anything compiled; and the kind of computer the add-on was built for. All four were tested in 4.5 to 5.2. In 5.3 the last three were tested from one Blender alone, using hand-made packages with no compiled code. Changes to Blender's own Python interface or features can also break an add-on; those were not tested. The first is the loose one — five ways of handing one folder to several Blenders all work, and an installed folder copied by hand from one version's place into another's works in both directions, so **nothing in Blender 4.5 to 5.2 refuses an add-on because another version installed it** — though all five of those sharing tests used an add-on that is plain Python and nothing else. A compiled part is unpacked into a folder named for the running Blender's own Python, inside the very settings folder being shared, and nothing goes back to unpack another version's copy; so whether a shared folder serves an add-on with a compiled part across the boundary where that Python changes is untried in every version, and the check that would catch it cannot fire, because the second version installs nothing. The declared range is the strict one, and it is enforced for an extension and ignored outright for an older-style add-on, whose declaration is read back intact and switched on by a script with no message at all; in 5.3 the preferences command switches it on too, with a warning as it does. **A refused install still ends at success**, 5.3 included, so anything reading the ending status to learn whether an install worked is told nothing; a part built for the wrong Python is refused at install too, and that one does end at a failure — though in 5.3, and in the 5.2.2 run, the refused package is then left on disk and listed as installed, neither switched on nor usable. Which Python Blender carries changed at 5.1, and 5.3 carries 5.2's, so one compiled part does not serve all of them (*Add-ons 14*).

**The settings folder must exist too.** In one 5.3 Mac run, a folder named for user settings did not exist and Blender wrote the switch-on preference into its ordinary user folder instead. A later run pointed at another missing folder inherited that switch-on. This was not repeated or tried in earlier versions (*Add-ons 6*).

**A compiled half that does not travel is not only an add-on's problem.** Blender itself, unpacked onto a bare machine, will not start until nine libraries are on it — the same nine in 4.5 to 5.2, and none of them needed to unpack it. That is settled on a rented Linux machine that was deliberately bare, and a repeat on a machine that already had those tools would prove nothing; unpacking 5.3 was not tested at all (*Builds 10*).

**The colour treatment.** The file keeps colour names; the receiving machine supplies the configuration that gives them meaning. In 5.3 an image also carries a colour-space identity, and a project can choose a configuration, by the release notes. Where that choice stands against the machine's two configuration variables is not settled. In 5.3 a script can ask, with the file open, whether its colour names were missing from the machine's configuration; in 5.0 to 5.2 that was asked only with no file open, and 4.5 has no way to ask (*Dependencies 15*).

**The denoiser, which is the same shape and quieter.** A file records the name of a denoiser. On a machine that has not got it the render goes ahead, the picture is still denoised by whatever the machine has, **the setting reads back as empty text rather than the stored name**, and nothing about the substitution appears in the render's own output — a warning is printed only when a script reads the setting. Which denoisers a machine offers follows the card, as far as two machines can show (*Settings 19*).

**What renders the picture is not in the file at all.** A file records whether it renders on the computer's graphics cards or on its processor, and never which of a card's rendering methods does the work; that lives in the machine's own preferences, and a choice given on the command line beats both the preferences and the file. Asked for a method outright, it does not fail quietly: named on the command line, a method the machine has no hardware for ends the run at a failure status with no file written, in all four versions and in 5.3. **Left to the preferences it has a quiet half.** A card render then needs both halves of the receiving machine's preferences — the technology chosen **and** the card ticked under it. With the technology chosen and no card ticked, the work went to the processor while the file was still asking for the card, and nothing said so (*What a render demands 7*).

So following the file's pointers alone cannot establish that a job will render the same way (*Add-ons 1, 14; Dependencies 15; Settings 19; What a render demands 7*).

## No one list reaches everything, and what is missed is where the file writes

One file was built holding twenty-one kinds of recorded location and every way of listing and rewriting was pointed at it. The plain list, the map and the relative rewrite reach the same sixteen readings and miss the same seven; walking Blender's own marks on its settings finds nineteen and misses two — one that every other way misses too, and one that the others do reach. No single tested means reaches everything, in any version, 5.3 included (*Reading a file 5, 9*). **The absolute rewrite's reach over those seven is untried:** they already held full paths when it ran (*Reading a file 9*). **The two lists need not return the same set either.** On Windows the map found a linked library's image that the plain list missed (*Dependencies 20*). But the plain list did name the image in a linked node setup, and its import file from 5.0 through 5.3 (*Node setups 2*). Which outside files a listing reaches therefore needs checking in the setup in hand.

**Gathering an input can also bring a write beside it.** A connected external shader script writes its compiled copy beside the source during rendering in 4.5 to 5.2, and in 5.3 and the 5.2.2 run on the Mac. Runs that found no copy do not establish a version difference: their script node was not recorded as connected. What prevented those runs from writing is not settled (*Dependencies 10; Reading a file 11*).

**And in 5.3 there is a path none of them sees.** A geometry-node setup can read a file through a path typed on its modifier rather than in its node, and both listings, both rewrites and the missing-file check pass that path by; no earlier version was asked (*Node setups 1*).

Six of the seven that are missed are places the file writes to, and that matters more than it looks. A write location that was not repointed does not fail. A whole foreign folder tree is built at the root of the receiving machine's disk, the frames go into it, and the run reports success — in 4.5 to 5.2, for no 5.3 file was carried to another machine (*Dependencies 10*).

A second topic came at it from the other end, with six recorded locations of its own, and the rule it settles is narrow rather than flat: **among the five write places in that test, the wholesale rewrites and the missing-file check reach the ocean modifier's cache path alone** — not the render output path, not a compositor output node's folder, not a point cache, not a geometry-nodes bake folder — in every version, 5.3 included. What separates the ocean cache from the other four is not established. In 5.3 the geometry-nodes folder was entered on a bare modifier, with no group, bake or Disk target. A modifier set to Disk with a bake setup is reached by both rewrites, both lists and the check in 5.3. The rule separating these setups is not settled (*Dependencies 17; Node setups 1; Reading a file 9*).

One version boundary changes what is found rather than how. A geometry-node import path sits outside all of that housekeeping in 4.5 and inside it from 5.0, 5.3 included, so in 4.5 the check that reports missing files answered that a file with a missing one had none (*Node setups 1, 2*). Anything treating that check as an all-clear is reading a version-dependent answer.

One recorded location can also stand for many files on disk — a numbered sequence, a set of tiles, one volume file per frame, a cache archive cut into pieces, a strip's folder, a point cache, the render output — and the plain ways of listing hand back the written text rather than the files it stands for (*Dependencies 4*). So a gathering built on those lists collects one name where a render wants many. Blender 4.5 cannot be asked to do better; 5.0 and 5.1 can walk a file's locations without expanding any of them; 5.2 and 5.3 can be asked to expand a sequence and a set of tiles into the real files (*Dependencies 4; Reading a file 5, 9*). What an under-gathered set costs is measured elsewhere: one tile left behind, or one frame, goes to the substitute colour on its own while the rest of the picture is unharmed (*Images 9*).

Gathering can be narrowed to one scene, up to a point. Rendering one scene of a file opens that scene's own picture and never the other scene's, while a linked file is opened whichever scene is rendered (*Dependencies 14*). The tested images can be traced forward to their scene by walking the record of what uses what. The direct image, the one reached through a node group, the driver's target and the one held by a custom property all appeared; asking for scene users directly came back empty. That does not establish every kind of reference or that every walk ends. In 5.3 a driver's target without a fake user disappeared on saving, so a visible reference does not itself keep that image in the file (*Reading a file 7*).

Repointing itself works. A recorded location can be read, written back, and the write sticks, all of it with no window (*Reading a file 5*). Three limits travel with that. A wholesale rewrite shows in the running Blender and never reaches the file on disk unless it is saved (*Reading a file 9*); what is handed to a render at the moment it starts leaves the artist's file untouched (*Settings 1; Writing 1*) — but only until something saves, since an output path handed in after the file is named sticks, and a following plain save writes it in, so a driven run can move a recorded place with nobody editing anything (*Dependencies 20*); and **on Windows the command that makes paths relative can leave a place behind and still report itself finished.** Saving a file onto a second drive turns every relative place into a full path naming the old drive and says nothing about it, because Windows cannot form a relative path across drives; the command then names the place it could not do, counts the failure, and reports success anyway — so a caller reading only the answer will not know. All four versions, on a machine reporting itself Windows Server 2025 Standard (*Dependencies 20*).

**Repointing a path and refreshing its data are separate checks.** In 5.3, assigning an image's ordinary path brought in its new picture, while assigning the raw path or using the one-pass rewrite with its default options kept the old one. The rewrite's reload option brought in the new picture (*Reading a file 5*). After a search repaired a missing linked file's path in 5.3, the library and collection still read as missing until the file was saved and reopened. Those cases were not tried in the earlier versions (*Reading a file 6*).

**A repair's path form has to be read back.** In 4.5 to 5.2 each run got back the form it was handed: five locations written out in full from the disk root came back written out in full, and locations written in the file's own relative shorthand came back in that shorthand, and neither run repaired the other kind, so that the repair keeps the form it found is the pattern every run fits and nothing one run showed (*Dependencies 8, 12; Reading a file 6, 10*). In 5.3 on the Mac both kinds were repaired, and each came back in the form it was recorded in (*Reading a file 10*), which also fits the relative-only repairs under *Dependencies 8*. In 5.3 the repair kept the form it found; for 4.5 to 5.2 that remains an inference from separate runs. All five manuals say the repair writes full paths (*Dependencies 8; Reading a file 10*). Read the recorded location back after a repair rather than assume its form.

## How deep it goes, and where each location is measured from

A file that links another brings that file's own references with it, recorded to at least nineteen libraries deep (*Dependencies 13*). A relative location inside a linked file is measured from that file's own folder and never from the file that opened it — established for library paths at eight levels and at twenty (*Dependencies 13*), and again through a chain of three files for a geometry-node import path, where a decoy of the same name beside the top file changed nothing (*Node setups 2*). Whether a file path supplied on a local modifier using a linked group is measured from that local file or from the library is not settled by a test; the 5.3 reading is inferred (*Node setups 2*). Turning a stored location into a real one gives a different answer depending on whether the library it came from is named in the question, and a tool that forgets to name it gathers the wrong location (*Dependencies 13; Reading a file 9*).

**A chain being recorded does not mean its object reaches the picture.** In the tested collection-instance chain the object arrived through eight files and vanished at nine, while the library records still resolved. A chain built with child collections instead still rendered at twenty files — on Linux in 4.5 to 5.2 and on the Mac in 5.3. That separates instance nesting from the linked-file chain; it establishes no general maximum (*Dependencies 13*).

That is why gathering is a loop rather than a pass. The readable chain stops at the first absent file: with a middle file gone, the file beyond it is named nowhere at all (*Reading a file 8*). A list of what to send is therefore only as complete as the files already in hand. Blender 5.2 and 5.3 alone can be asked for one level of an unopened file's own links without opening it, which shortens the loop by a step and does not remove it (*Reading a file 8; Dependencies 13*).

Arriving is not the same as being found. A reference into another file names the thing it wants, and the name is the whole identity: rename that thing inside the library and the reference breaks exactly as it does when the thing is deleted, reported in the same words, with only a count of missing libraries telling a lost file from a lost item inside a file that loaded (*Dependencies 11*). What is left behind keeps the name and the library and holds nothing, and the render still writes a frame. Names inside a file are told apart exactly, on both machines and in every version — and one of the two ways of asking another file for a name it does not hold reports that it finished, prints nothing, and links nothing (*Dependencies 8*).

One thing about when files are read once they have arrived. A fresh Blender read the changed files in the tested cases, with two exceptions: an Alembic import with no cache reader, and a prepared texture copy made in the same whole second as the image changed. In 5.3 and the 5.2.2 run on the Mac that copy kept the old picture even in a fresh Blender (*Reading a file 11*). Inside a Blender already running the answer depends on the kind of file: a changed picture reaches the very next render with nothing done at all — **except where Persistent Data is switched on, which is the one setting that turns that rule into its opposite**, in all five tested versions on the processor, so that the second render shows the old picture and goes on showing it even after the image is told to reload — and a replaced linked file does not until it is told to reload (*Reading a file 11*), while a file a geometry-node setup imports is read again only once something marks the setup for a fresh run, and then only if its recorded time has moved by a whole second — a file overwritten inside the same second is handed back as it was, with nothing said (*Node setups 1*).

## How a location is written, and what survives the move

A location can be written as a full path from the disk root, or relative to the file that holds it, and both were carried from the Creator's Mac to a rented Linux machine and opened there, in all four versions; 5.3 was never carried to another computer. The relative one resolves against the file's new folder and loads, climbing above that folder included. The full one is kept exactly as written, resolved exactly as written, found nowhere — and nothing is said about it until something asks (*Dependencies 6*).

Three forms look as though they would help and do not. A home-directory shorthand and an environment variable written into a path are stored exactly as typed and not expanded in the tested image paths, on both machines in 4.5 to 5.2 and on the Mac in 5.3, and a path naming a disk by letter is treated as an ordinary full path that finds nothing (*Dependencies 5*). A geometry-node import path behaves the same way: the relative mark is honoured and a single dot standing for the current folder finds nothing (*Node setups 1*). In 5.3, on the Mac, a location written with two leading slashes and a server's name is read as a folder beside the blend-file, one written with two leading backslashes keeps them and has its other backslashes turned, and a network or web address is kept as typed; none finds anything, and no earlier version was asked (*Dependencies 5, 7*).

Two forms stand for something rather than for themselves, and they are the ones a gathering has to leave alone. Characters standing for the frame number, and tokens standing for tiles, sit inside the location itself; curly-brace expressions are worked out at the moment the location is used, so the braces stay in the stored text — which is why every way of listing and rewriting passes such a location by (*Dependencies 5; Reading a file 9*). In 4.5 to 5.2 those expressions are taken in the render output place and in the compositor's output node and nowhere else, and the vocabulary inside them grows at 5.0. **5.3 also takes one in a geometry-nodes bake folder**, so the folder such a file records may not be the folder its bake uses — and a bake folder holding two variables sent the bake into the file instead, with one line said and the bake command still reporting success, for a reason not established. 5.3's release notes add a project's own variables too, untried inside a project (*Dependencies 5; Node setups 1*).

A name written outside the Latin alphabet survives the move. Carried whole from the Mac to the rented Linux machine, such a path was found in all four versions with nothing printed on either machine; 5.3 was not carried. Two things sit beside it. How long a data-block's name may be changes at 5.0, and 5.3 keeps 5.0's limit. That bites hardest on those characters because each of them takes more than one byte; the limits on a path's own length are the same in every version (*Dependencies 9*). And reading a location out can fail where reading anything else out would not, because a location is exempt from the rule that a file's text is all written one way — real disks hold names that are not (*Dependencies 9*).

**What a file records about itself does survive the crossing.** A scene's own recorded limits on subdivision, child particles and texture size came back unchanged in both directions between the Mac and a rented Linux machine, in all four versions, and again on a second rented Linux machine in one direction — so that direction was got twice, on two different machines; 5.3 was not carried (*What a render demands 6*).

## What opening and saving do to the places a file records

**Two things can change at a plain save without a path being edited, in all five versions** (*Dependencies 20*).

**The separator is re-spelled to the computer's own, and it happens when the file is *opened*.** The plain save then writes it in. On a Mac and on a Linux machine a backslash comes back as a forward slash. **On Windows it runs the other way and it is much larger: every forward slash in a recorded place becomes a backslash.** Seven recorded places keep their forward slashes on Windows and five of them are real ones — the other two hold no separator to change — and **the render output path is not among them**, so the rule is not that places written to are left alone. Nothing else about the text moves in either direction: the leading shorthand stays, a doubled separator stays doubled, a step upward stays, letter case stays, a trailing space stays, characters outside the Latin alphabet come through unharmed, and a place pointing at nothing is re-spelled just the same. **So a file carried between the two kinds of computer has its whole recorded text rewritten, both ways, by a save that touched nothing** — and the five places that keep their forward slashes are the only text that survives a round trip unchanged. 5.3 re-spelled the Mac's way on the Mac, and no 5.3 file was taken to Windows (*Dependencies 20*).

**A data-block nobody is using is dropped at the save, taking its recorded place with it.** An unused image disappears, and so does the weak reference beside it recording the library it was appended from; an unused image shielded with a fake user survives. The consequence is a builder's. No plain save in that question produced the same file twice, in any version on any machine — **though that is not established as a rule about plain saves**, because the file under test carried an unused data-block and so was certain to shrink once; in 5.3, with that data-block already gone, the size came back the same and the bytes still differed. The advice stands whichever way it falls: the re-spelled separator and the dropped data-block both move the bytes, so a check comparing whole files or their checksums says nothing about whether a recorded place moved. Only the path text can be compared. 5.3's release notes record initial support for keeping a file the same when it is opened and saved, without saying what it covers, and nothing in the 5.3 runs showed it (*Dependencies 20*).

**Saving somewhere else is a different answer, and it is the case a render farm meets.** Saving into a **different folder** rewrites the tested relative places the file *reads* from — collapsing a step upward and a doubled separator, keeping letter case and a trailing space, rewriting a place pointing at nothing just the same, and leaving a full path untouched. **The tested places the file *writes* to are not touched**, which after the move means a different place on disk. Saving into the same folder under a new name changes nothing, and neither does a plain save with the repointing switched deliberately on, so a different folder is the real boundary; switching the repointing off leaves the text alone and the pictures then stop loading. All of it the same in 5.3, whose geometry-nodes folder sat on a bare modifier rather than an actual bake. What a save does to an actual bake's paths is not settled by this test (*Dependencies 20*). Set that against this document's own finding that a write location which was not repointed builds a foreign folder tree and reports success (*Dependencies 10*).

**Two things a save does not do, and one it may or may not.** Opening a file made by another version and saving it rewrites no recorded place, in either direction — an older file saved by each of the newer three, and a 5.2 file opened and saved in 4.5, both on the Creator's Mac alone; 5.3 was not given another version's file. And switching on automatic packing and saving leaves every recorded place with exactly the text it had. **What that save does on a file holding a place that points at nothing is not settled**: in 4.5 to 5.2's runs the packing refused outright, named the one it could not find, and the save never happened; in 5.3, and in the 5.2.2 run, the same error was raised and the file was written anyway, partly packed. So that error does not mean nothing was saved (*Dependencies 20*).

## Capitals

Two topics found the same thing on their own machines, in all four versions. A recorded location whose capitals do not match the name on disk loads on the Creator's Mac and does not on a rented Linux machine (*Dependencies 8; Node setups 1*). 5.3 was not run on Linux; on a Mac disk image that minds capitals it failed to load, as Linux did (*Dependencies 8*). For a library the two outcomes are worse than a plain failure: on the Linux machine the link fails outright, and on the Mac it quietly succeeds and leaves the file holding two libraries where one was meant, 5.3 included (*Dependencies 19*). A later question met it again while carrying a file between machines, and puts it plainly: the recorded text is identical on the two and the file system's answer is not (*Dependencies 20*).

The repair does not close it. The search that repairs missing references matches the file name exactly, capitals included, on both machines and in 5.3 (*Reading a file 10*), and handed a search folder it does not match a name whose capitals differ (*Dependencies 8*).

So the same spelling can load on the tested Mac's forgiving disk and fail on the tested Linux disk. **Whose rule it is has two answers, and both are settled.** When a file is loaded, the disk decides: Blender makes no attempt of its own to match a name whose capitals differ, and the Creator's Mac has the forgiving disk while the render machine has the strict one (*Dependencies 8; Reading a file 9*). When the repair searches, the rule is Blender's own and not the disk's: that same Mac, asked directly for a name written in capitals, finds the file, and the repair on that same Mac still refused it (*Reading a file 10*). Windows is untried for both.

## What packing takes with it

Packing is per item rather than all or nothing, and some kinds can never be held inside a file at all (*Dependencies 3*). Two more kinds fall outside it that a reader would not guess: a geometry-node import file is not packed in any version (*Node setups 1*), and packing a linked library carries the setup inside it and not that setup's own outside files (*Node setups 2*). That packing holds at all is shown by the control case — a packed picture is genuinely unaffected by its file on disk being deleted (*Images 9*) — though in 5.3 a volume that packs, and keeps its packed mark, is not used once its file is gone, and the render comes out as if the volume were not there; no earlier version was asked (*Dependencies 1*).

One version boundary sits at 5.0, and how wide it is is not agreed — see below. What is not in doubt: from 5.0 onward, 5.3 included, packing linked data leaves the file holding two library entries with the same recorded location (*Dependencies 19*). In 5.3 such a packed linked object was still there, and not marked missing, with its library moved away (*Dependencies 19*); and 5.3's release notes narrow which packed linked items a save writes to the directly linked ones, which no test exercised (*Dependencies 13; Reading a file 8*).

A fully packed file is therefore not a general answer, and nothing announces the gap: a partly held file whose remaining files are gone says nothing at all when it is opened (*Dependencies 3*).

## What a render does when something did not arrive

It finishes and reports success. That was found separately for a missing picture, a missing font, an absent cache, a missing library, a missing geometry-node import file, a missing render engine add-on and a denoiser the machine has not got, in every version — and in 5.3, on the Mac, for a missing Alembic file, a missing object inside one, a missing light-profile file, a missing shader script and a missing sound as well (*Dependencies 12, 16, 18; Images 9; Node setups 1, 2; Add-ons 7; Settings 19*).

**That is true of things the file points at. It is not true of the engine itself when the name is handed in at launch.** With the engine named on the command line and its add-on absent, every version says the engine was not found and writes no image; 5.0 to 5.3 end at a failure status, and **4.5 aborts on the Mac and hangs on Linux** until it is killed. That is a refusal of the run, rather than a finished render with a changed picture (*Add-ons 7; Settings 13*).

What the finished picture shows depends on what the missing thing was feeding, and there is no one sign to look for. A colour texture leaves a flat substitute colour carrying no identity in it, and the same substitute appears whether the file is gone, unreadable or empty (*Images 2, 9*). The same missing picture leaves no mark at all where it was feeding surface detail, shrinks the object where it was feeding displacement, and gives a different substitute again inside the compositor and inside a geometry-node setup (*Images 9*). A missing font leaves one empty shape per character (*Dependencies 16*). A physics simulation without a bake is worked out again, but not from the beginning when a frame is jumped to. Removing a recorded disk cache changed the picture in silence without establishing what replaced it; in 5.3 an ocean whose baked files are gone renders as an even grey sea with no waves, and a missing Alembic file leaves the object's own mesh drawn in place of the cached one (*Dependencies 18, 12*). A colour name the machine cannot match is replaced without the render stopping, with lines printed for it and, in 4.5 alone, nothing at all on screen (*Dependencies 15*), and the fourteen render fields do not name the view transform. A 5.3 JPEG does carry an sRGB profile, so that narrower absence must not be read as no colour information anywhere in the file (*Images 10*). A denoiser the machine has not got leaves a picture that is still denoised, by a substitute (*Settings 19*).

**Where the complaint lands, for anything reading Blender's output.** Nearly all of it is on the ordinary output stream and not the error stream — a missing library, a missing font and, from 5.0, a missing image texture; the texture exception is 4.5's line about a missing texture under EEVEE, which lands on the error stream, and 5.3's line under EEVEE is the first of any version to name the file. Missing footage in the sequencer says nothing on either stream in any version, and 4.5's Cycles says nothing whatever about a missing image texture. **A missing Alembic file is another exception in 5.3:** Blender's warnings reached ordinary output, while the Alembic library's own errors reached the error stream. A missing volume file said nothing on either stream. That an empty error stream means anything at all rests on a control run first, in the same shape, on both of that question's machines. **And from 5.0, 5.3 included, the log-file switch takes the whole reason off the streams and into the file, so a program watching the ordinary output sees none of it** (*Reports 13*). That is the question behind this document's own rule that any check built on Blender's words has to be written per version.

So neither the status a run ends with nor the look of the frame is a check. Asking before the render is, and it has holes: the check works with no window and names what is missing (*Dependencies 12; Images 9; Reading a file 6*), but in the five-write-place test it reached only the ocean cache path. In 5.3 it also reached a geometry-nodes bake setup set to Disk, while a folder on a bare modifier was missed; the boundary is not settled (*Dependencies 17; Node setups 1*), in 4.5 it does not reach a geometry-node import path (*Node setups 2*), and in 5.3 it said nothing of a missing item inside a library that loads (*Dependencies 11*), nor of a path typed on a geometry-node modifier, which no earlier version was asked (*Node setups 1*). It can also name as missing what is not: in 5.3 a file using one of Blender's own bundled node groups holds it packed under a library path into the application folder of the Blender that saved it, and carried where that path leads nowhere the group is whole while the check names the path as missing (*Node setups 1*). And its answer comes only as a message — four topics looked for a way to read it as data and none found one, the fourth finding that a missing image texture leaves the reports list, Info editor and report box empty with a window open in 5.2 and 5.3. A script-called missing-file check is also absent from the reports list; in 5.3 choosing that check from the File menu does show its warning in the status bar (*Dependencies 3, 12; Reading a file 6; Reports 13*). That list is not always empty in 5.2 and 5.3: with a window open it holds the five messages a missing linked library raises when the file is read. Whether a windowless Blender fills it is untested, and a render farm is always windowless (*Reports 13*).

## What this does not cover

- **Windows, except for one question.** *Dependencies 20*'s account of what opening and saving do to a recorded place rests on six tests taken on a rented machine reporting itself **Windows Server 2025 Standard**, five of them in all four versions and the crossing in 4.5 and 5.2. **A desktop edition of Windows has never been reached**, and a Windows answer that does not name its edition is not yet an answer. Every other question behind this document is untried there, and 5.3 is untried there for all of them — untried rather than out of reach, since this project has a route to a Windows computer, described in the equipment section of `Preparation/Blender Research/Method.md`.
- **Blender 5.3 anywhere but the Creator's Mac, and any crossing in 5.3.** No 5.3 file was carried to another computer, no 5.3 Blender ran on Linux, and no 5.3 add-on was set beside another version's, so every crossing, every Linux disk and every add-on shared between versions here is 4.5 to 5.2's; every 5.3 sentence is a macOS result in a beta build.
- A location naming another computer, and a folder on network storage two machines can reach at the same moment. No version's sources describe one and no test could make one (*Dependencies 2, 7*); in 5.3 a web address given as a library or a picture, and three server spellings, were tried on the Mac and reached nothing (*Dependencies 2, 5*). The second drive in the Windows tests is a drive letter mapped onto a folder, which answers the two-drives question and not the share one, and there is no folder on network storage two of this project's machines can reach at once (*Dependencies 20*).
- Whether the list of kinds a file can point at is the whole list (*Dependencies 1*).
- What a save records for a cache file, a movie clip or a movie strip, in 4.5 to 5.2. Each needs a real file of its kind, and none was in the file every one of those tests started from. 5.3 was given all three, and a plain save kept each one's text (*Dependencies 20*).
- Kinds of missing file nobody put through the stream-splitting test, in any version: a sound, a point cache, a USD cache, an external OSL script, an image the compositor points at, and an environment texture in the world; a volume file and an Alembic cache were put through in 5.3 alone (*Reports 13*). What the render shows is answered elsewhere for a volume file and a compositor image under *Images 9*, and for a point cache at length under *Dependencies 18*, including the one absent-cache case Blender does announce: a disk cache written by 4.5 is refused by 5.0, 5.1 and 5.2, with a warning naming the object printed when the file is opened and again during the render; 5.3 was not given one. So this is a gap in one question's stream test and not a gap in the research.
- What a scene reached from the rendered one drags in. Rendering one scene reads only that scene's own picture, and the case where the rendered scene reaches another was touched by no test (*Dependencies 14*) — while a second scene reached through a video-sequencer strip does run its own compositor (*The compositor 4*), and 5.3's release notes add one more road, a scene referenced inside a compositor node group, which no test touched (*Dependencies 14*). Which files that second scene needs is open.
- What a tool that is not Blender can list or rewrite inside a file (*Reading a file 9*).
- Whether an add-on obtained from Blender's own platform may be copied between your own machines (*Add-ons 8*).

## Where two topics do not agree

**Whether repointing a library at a file no library records moves it is not settled, and the readings disagree.** *Reading a file 9* made that call on a file linking one library and the library moved. *Dependencies 19* made the same call on a file linking two and nothing moved at all. Both windowless, both in all four versions, both on two machines, and both again in 5.3 on the Mac, and the call reported success either way. What separates them is not established — the number of libraries is only one of the things the two set-ups differ in — so read neither as a general rule, and check what a repointing did rather than trust the answer it hands back.

**Whether a 4.5 file can hold packed linked data at all is not settled, and the readings disagree.** *Dependencies 19* records that 4.5 refuses the packing option on the Python call that loads a library, and reads that as 4.5 having none of the machinery for it. *Node setups 2* ran Blender's own command for packing linked libraries in all four versions and records 4.5's library holding a packed copy afterwards, with the setup still arriving when the library file was moved away; *Reading a file 8* says that command is present in all four and that what is new at 5.0 is the archive arrangement rather than the packing. The two topics took different routes and neither has been chosen here. **Nothing in *Dependencies 20* settles it either** — that switching on automatic packing and saving leaves every recorded place with the text it had is about paths and not about whether 4.5 can pack. Until it is settled, do not assume a 4.5 file cannot hold packed linked data.

**Whether the two ways of asking a file for its recorded places ever spell one of them differently is not settled, and the readings disagree.** Three runs on the Creator's Mac in 4.5 to 5.2: two find the two ways agreeing in the process that has just built the file, one finds them disagreeing there; 5.3's one run on the Mac agrees with the two. On a Windows machine the two agree with each other, in the building process and after a reload alike — and both then disagree with any file written anywhere else, which moves the danger rather than removing it. What is settled is that a reload re-spells the text; whether the way of asking does as well is not (*Dependencies 20*).

**Which geometry-nodes bake setups the path tools reach is not settled.** In 5.3 on the Mac, a modifier set to Disk with a bake setup has its folder rewritten, listed and checked, before and after baking. A bare modifier with only a folder entered is missed. The wider path test also missed its geometry-nodes folder, without establishing the condition separating the setups. So Blender does reach a bake folder, but a tool must check which folder it changed rather than assume one rule for all of them (*Node setups 1; Dependencies 17; Reading a file 9*).
