## 1. What in a scene can make its look on one frame depend on the frames worked out before it? Name every kind your sources describe.

**Label:** documented for Cloth, Dynamic Paint (Vertex and Displace), Geometry Nodes simulation zones, the iTaSC solver in Simulation mode, and Ocean baked foam; documented that Particles, Soft body, Hair dynamics, Rigid body, Dynamic Paint (Image Sequence), and Fluid have caches or simulation ranges, and inferred that their look on one frame depends on earlier frames.

The sources describe these kinds:

**A. Physics that use the shared "point cache" — rigid body, cloth, soft body, particle systems (including hair dynamics), and Dynamic Paint.**
- **Label:** documented for Cloth and for Dynamic Paint (Vertex and Displace); documented that the others use the point cache or a simulation frame range, and inferred that their look on one frame depends on frames worked out before it (step: they share the caching system described as caching results as the animation is played, and for particles the cache page in Question 4 states that playback must start on or before the simulation start frame for the cache to fill).
- Manual, Baking Physics Simulations: "The result of a simulation is automatically cached to memory when the animation is played, so that the next time it runs, it can be replayed more quickly by reading the results from the memory." — https://docs.blender.org/manual/en/5.3/physics/baking.html (read 2026-11-08).
- Python API, PointCache, section "References": "ClothModifier.point_cache", "DynamicPaintSurface.point_cache", "ParticleSystem.point_cache", "RigidBodyWorld.point_cache", "SoftBodyModifier.point_cache" — https://docs.blender.org/api/5.3/bpy.types.PointCache.html (read 2026-11-08).
- Cloth (documented) — Manual: "Do Not Jump Ahead … the cloth simulator may not be able to compute or show you an accurate mesh shape for that frame, if it has not previously computed the shape for the previous frame(s)." — https://docs.blender.org/manual/en/5.3/physics/cloth/introduction.html (read 2026-11-08).
- Particles (documented that it uses the unified cache and requires playback from the start to fill the cache; inferred that a frame's look depends on earlier frames) — Manual: "The Emitter particle system uses a unified system for caching and baking (together with Soft Body and Cloth)." and "When an animation is played, each physics system writes each frame to the cache. Note that for the cache to fill up, one has to start the playback before or on the frame that the simulation starts." — https://docs.blender.org/manual/en/5.3/physics/particles/emitter/cache.html (read 2026-11-08).
- Soft body (documented that it uses the unified cache; inferred that a frame's look depends on earlier frames) — Manual: "Soft Body physics simulations use a unified system for caching and baking." — https://docs.blender.org/manual/en/5.3/physics/soft_body/settings/cache.html (read 2026-11-08).
- Hair dynamics (documented that it uses cloth simulation for hair; inferred from the cloth quote above that a frame's look depends on earlier frames) — Manual: "Hair particles can have dynamic properties using physics." — https://docs.blender.org/manual/en/5.3/physics/particles/hair/dynamics.html (read 2026-11-08). Python API: ParticleSystem.cloth "Cloth dynamics for hair"; use_hair_dynamics "Enable hair dynamics using cloth simulation" — https://docs.blender.org/api/5.3/bpy.types.ParticleSystem.html (read 2026-11-08).
- Rigid body (documented that it uses a point cache and has an active frame range; inferred that a frame's look depends on earlier frames) — Manual: "The Cache subpanel specifies the frame range in which the simulation is active." — https://docs.blender.org/manual/en/5.3/physics/rigid_body/world.html (read 2026-11-08).
- Dynamic Paint (documented for Vertex and Displace; inferred for Image Sequence from sharing Dynamic Paint surface processing) — Manual: "Results are stored by point cache" (Vertex format), and effects such as "Paint slowly spreads to surrounding points eventually filling all connected areas." and, for Displace surfaces, "Incremental: A new displace is added cumulatively on top of an existing displace." — https://docs.blender.org/manual/en/5.3/physics/dynamic_paint/canvas.html (read 2026-11-08). The Image Sequence format of Dynamic Paint — Manual: "generates UV wrapped image files of defined resolution as output" — https://docs.blender.org/manual/en/5.3/physics/dynamic_paint/canvas.html (read 2026-11-08), and is baked with its own operator — Python API: "Bake dynamic paint image sequence surface" — https://docs.blender.org/api/5.3/bpy.ops.dpaint.html (read 2026-11-08).

**B. Fluid (liquid and gas/smoke) domains, with their own cache.**
- **Label:** documented that fluid simulations have their own cache that bakes during playback when every frame is played; inferred that one frame's look depends on the frames worked out before it.
- Manual: "Fluid simulations use their own cache. All other physics simulations make use of the General Baking operators." and "Replay: The cache will be baked as the simulation is being played in the viewport." and "'Replay' only works when the Playback Sync mode is set to 'Play Every Frame'." — https://docs.blender.org/manual/en/5.3/physics/fluid/type/domain/cache.html (read 2026-11-08).

**C. Geometry Nodes simulation zones.**
- **Label:** documented for simulation zones and the XPBD Solver / Hair Dynamics node descriptions; inferred for how the node assets carry state.
- Manual: "Simulation zones allow the result of one frame to influence the next one." and "The simulation is tied to the animation system. It will only be evaluated while the animation frame changes, and is cached like the existing physics simulations in Blender." — https://docs.blender.org/manual/en/5.3/modeling/geometry_nodes/simulation/simulation_zone.html (read 2026-11-08).
- Related nodes in 5.3 — Manual: the XPBD Solver node "provides a physics simulation system for hair, cloth, and particles" and "is used in the Hair Dynamics and Cloth Dynamics experimental node assets." Its output is "Modified simulation data after a single time step has been applied." — https://docs.blender.org/manual/en/5.3/modeling/geometry_nodes/simulation/xpbd_solver.html (read 2026-11-08). Hair Dynamics node — Manual: "The motion of the hair curves simulated over time using the XPBD Solver node." — https://docs.blender.org/manual/en/5.3/modeling/geometry_nodes/simulation/hair_dynamics.html (read 2026-11-08). **Inferred:** these node assets carry history only through a simulation zone around them; the sources do not say what is inside the assets, so whether they bring their own simulation zone is not stated.

**D. The iTaSC inverse-kinematics solver in its Simulation mode.**
- **Label:** documented.
- Manual: "The Simulation mode is the stateful mode of the solver: it estimates the target's velocity, operates in a 'true time' context, ignores rotation from keyframes (except via a joint rotation constraint) and builds up a state cache automatically." and "only on the first frame (i.e. a frame which doesn't have any previous frame in the cache)." — https://docs.blender.org/manual/en/5.3/animation/armatures/posing/bone_constraints/inverse_kinematics/introduction.html (read 2026-11-08).
- Python API, Itasc.mode: "Simulation – State-full solver running in real-time context and ignoring actions and non-IK constraints." — https://docs.blender.org/api/5.3/bpy.types.Itasc.html (read 2026-11-08).

**E. The Ocean modifier, but only its baked foam.**
- **Label:** documented.
- Manual: "When simulating live, the ocean simulator retrieves data for that current frame only. … With baking, it is possible to approximate that behavior, by accumulating foam from previous frames, leaving it remaining on the surface." — https://docs.blender.org/manual/en/5.3/modeling/modifiers/physics/ocean.html (read 2026-11-08).
- Python API, OceanModifier.bake_foam_fade: "How much foam accumulates over time (baked ocean only)" — https://docs.blender.org/api/5.3/bpy.types.OceanModifier.html (read 2026-11-08).

A cross-check list the Python API itself gives (documented): the timeline's cache display has one switch per cache kind — "cache_cloth", "cache_dynamicpaint", "cache_particles", "cache_rigidbody", "cache_simulation_nodes", "cache_smoke", "cache_softbody" (plus "cache_compositor", described as "Show the interactive compositor playback cache") — https://docs.blender.org/api/5.3/bpy.types.SpaceDopeSheetEditor.html (read 2026-11-08). This matches kinds A–C; it does not include D or E. Whether "cache_compositor" makes a rendered frame depend on earlier frames is not in that entry.

Manual: "Only available for viewport denoising" — https://docs.blender.org/manual/en/5.3/render/cycles/render_settings/sampling.html (read 2026-11-08). **Inferred:** because it is only available for viewport denoising, it does not apply to a render of chosen frames.
- Cycles' "Denoise Animation" operator and denoising motion passes (**observed** for what is in Cycles' files; **inferred** for what they do beyond those words). Cycles file `operators.py`, class `CYCLES_OT_denoise_animation`, around lines 30–110 (copy taken 2026-10-16) requires "animation must be complete", and the file does not say it uses neighbouring frames (**observed**); **inferred:** it works on already-rendered files as a step after rendering, not something in the scene. Cycles file `properties.py`, around line 1637 (copy taken 2026-10-16) has "Store the denoising motion passes, for temporal denoisers" (**observed**); **inferred:** this only stores passes for a denoiser rather than making one scene frame depend on earlier frames during rendering.
- Path guiding (documented; inferred that it is within one render): Manual: "Important light directions are learned over time, improving as more samples are taken." — https://docs.blender.org/manual/en/5.3/render/cycles/render_settings/sampling.html (read 2026-11-08). **Inferred:** this is over samples within a render, not across animation frames.
- The Bake node in Geometry Nodes (**not in the sources** that it carries one frame into the next): checked on https://docs.blender.org/manual/en/5.3/modeling/geometry_nodes/geometry/operations/bake.html (read 2026-11-08), which describes storing baked geometry but does not describe one frame influencing the next.
- Python frame-change handlers (documented that they run on frame change; **not in the sources** that they carry state across frames): Python API describes them as "Called when a frame change is triggered for playback and rendering" — https://docs.blender.org/api/5.3/bpy.app.handlers.html (read 2026-11-08) — and nothing on that page describes them carrying state from one frame to the next.

## 2. For each kind, from which frame does it begin, where is that set, and what is it when nobody has set it?

A caution that applies to several Python API figures below. The Python API prints a "default" for every setting, and what it prints is **documented**; however, for some settings on the same pages the printed default lies outside the setting's own allowed range. Examples — Python API: PointCache.frame_end "(in [1, 1048574], default 0)" and frame_step "(in [1, 20], default 0)" — https://docs.blender.org/api/5.3/bpy.types.PointCache.html (read 2026-11-08); Itasc.step_count "(in [1, 50], default 0)" — https://docs.blender.org/api/5.3/bpy.types.Itasc.html (read 2026-11-08); DynamicPaintSurface.frame_start "Simulation start frame (in [1, 1048574], default 0)" — https://docs.blender.org/api/5.3/bpy.types.DynamicPaintSurface.html (read 2026-11-08). **Inferred:** where these pages print "default 0" (including on PointCache.frame_start and NodesModifierBake.frame_start, where 0 sits inside the allowed range), that printed figure may be a placeholder rather than the value a newly created cache starts with in a running Blender; what a newly created cache holds when untouched is **not in the sources** beyond the API's printed default.

## 4. For each kind, what does a render of one frame show when no frame before it was worked out in that session, and when only the frames from the kind's own first frame onward were?

**General statements that apply to the cached kinds (documented):**
- Manual: "The result of a simulation is automatically cached to memory when the animation is played" and "It is generally recommended to bake your physics simulations before rendering. Aside from no longer needing to go through the time-consuming process of simulating again, baking can help prevent potential glitches and ensure that the outcome of the simulation remains exactly the same every time." — https://docs.blender.org/manual/en/5.3/physics/baking.html (read 2026-11-08).

**A. Point-cache physics.**
- **No earlier frame worked out — Label:** documented for cloth in the viewport and for how the particle cache fills; inferred for what a render does; not in the sources for what the picture actually shows across all point-cache kinds.
  - Cloth — Manual: "if you jump ahead a lot of frames forward in your animation, the cloth simulator may not be able to compute or show you an accurate mesh shape for that frame, if it has not previously computed the shape for the previous frame(s)." — https://docs.blender.org/manual/en/5.3/physics/cloth/introduction.html (read 2026-11-08). **Inferred:** a render of one cloth frame with nothing before it worked out may not show the right shape; the step is that the passage describes working in the viewport and the sources give no separate rule for a render. What shape it shows instead is **not in the sources** (checked on that page and https://docs.blender.org/manual/en/5.3/physics/cloth/settings/cache.html, read 2026-11-08).
  - Particles — Manual: "When an animation is played, each physics system writes each frame to the cache. Note that for the cache to fill up, one has to start the playback before or on the frame that the simulation starts." — https://docs.blender.org/manual/en/5.3/physics/particles/emitter/cache.html (read 2026-11-08). **Inferred:** without the frames from the start, the cache holds nothing for the frame being rendered; what a render of that frame shows is **not in the sources** (checked on that page and https://docs.blender.org/manual/en/5.3/physics/particles/emitter/render.html, read 2026-11-08).
  - Rigid body, soft body, hair dynamics, Dynamic Paint: what a lone frame shows is **not in the sources** (checked on https://docs.blender.org/manual/en/5.3/physics/baking.html, https://docs.blender.org/manual/en/5.3/physics/rigid_body/world.html, https://docs.blender.org/manual/en/5.3/physics/soft_body/settings/cache.html, https://docs.blender.org/manual/en/5.3/physics/particles/hair/dynamics.html, and https://docs.blender.org/manual/en/5.3/physics/dynamic_paint/canvas.html, all read 2026-11-08).
- **Frames from the first frame onward worked out — Label:** documented for the operators and playback rule; inferred for what the render shows.
  - Manual: the operators "Calculate to Frame: Bake only up to the current frame. Limited by End frame set in the cache settings." and "Update All to Frame: Bake all physics systems in the scene to the current frame." — https://docs.blender.org/manual/en/5.3/physics/baking.html (read 2026-11-08); and for particles, "for the cache to fill up, one has to start the playback before or on the frame that the simulation starts." — https://docs.blender.org/manual/en/5.3/physics/particles/emitter/cache.html (read 2026-11-08). **Inferred:** after the frames from the kind's own start frame up to the wanted frame have been worked out in that session, the cache holds the wanted frame and the render uses it. Whether that picture matches a full bake is **not in the sources**.
  - Rigid body, a further point (documented) — Manual: "If you have not saved the blend-file, the cache is created in memory, so save your file first or the cache may be lost." — https://docs.blender.org/manual/en/5.3/physics/rigid_body/world.html (read 2026-11-08).

**B. Fluid.**
- **No earlier frame worked out — Label:** documented for how the cache fills; not in the sources for what a render of an unbaked lone frame shows.
  - Manual: "Replay: The cache will be baked as the simulation is being played in the viewport." and "'Replay' only works when the Playback Sync mode is set to 'Play Every Frame'." Modular and All are baked with bake operators — https://docs.blender.org/manual/en/5.3/physics/fluid/type/domain/cache.html (read 2026-11-08). The fluid introduction lists "Save the blend-file." then "Bake the Cache for the simulation." as steps — https://docs.blender.org/manual/en/5.3/physics/fluid/introduction.html (read 2026-11-08). - **Frames from the first frame onward worked out — Label:** inferred.
  - Manual: "Frame Start: The simulation starts on this frame, and this is the first one that is baked." and "Replay: The cache will be baked as the simulation is being played in the viewport." — https://docs.blender.org/manual/en/5.3/physics/fluid/type/domain/cache.html (read 2026-11-08). **Inferred:** when the frames from `cache_frame_start` up to the wanted frame have been worked out into the cache in that session, the cache holds that frame and the render shows that cached fluid state; how or whether a session without viewport playback works out those frames without baking is **not in the sources** (checked on those two pages).

**C. Simulation zones.**
- **No earlier frame worked out — Label:** documented that baking allows out-of-order rendering and that evaluation happens as the frame changes; inferred that an unbaked lone frame is not the simulated result; not in the sources what it shows instead.
  - Manual: "When the result is ready to be sent to a render-farm, it can be baked to disk. This allows for the simulation to be rendered in a non-sequential order." — https://docs.blender.org/manual/en/5.3/modeling/geometry_nodes/simulation/simulation_zone.html and https://docs.blender.org/manual/en/5.3/physics/simulation_nodes.html (both read 2026-11-08). Manual: "It will only be evaluated while the animation frame changes" — https://docs.blender.org/manual/en/5.3/modeling/geometry_nodes/simulation/simulation_zone.html (read 2026-11-08). **Inferred:** unbaked, a frame rendered without the earlier frames is not the simulated result; what it shows instead is **not in the sources** (checked on those two pages and https://docs.blender.org/manual/en/5.3/modeling/geometry_nodes/baking.html, read 2026-11-08).
- **Frames from the first frame onward worked out — Label:** documented for the operator and cache toggle; inferred for what the render shows.
  - Manual: "Calculate to Frame: Calculate simulations in geometry nodes modifiers from the start to current frame." — https://docs.blender.org/manual/en/5.3/physics/simulation_nodes.html (read 2026-11-08). **Inferred:** working out the frames from the simulation's start to the current frame leaves the wanted frame in the cache for rendering, provided caching is on. A per-object switch can turn the cache off — Python API: Object.use_simulation_cache "Cache frames during simulation nodes playback (default True)" — https://docs.blender.org/api/5.3/bpy.types.Object.html (read 2026-11-08); Manual: "For the cases where the current frame is the only one relevant, users can opt-out of 'Cache' to save memory." (read 2026-11-08; exact manual page URL not recorded in this pass).

**D. iTaSC Simulation mode.**
- **No earlier frame worked out — Label:** documented for the cache and reiteration rules; inferred for what a lone render shows.
  - Manual: the solver treats "a frame which doesn't have any previous frame in the cache" as the first frame. With Reiteration "Never": "The solver starts from the rest pose and does not reiterate (converges) even for the first frame. This means that it will take a few frames to get to the target at the start of the animation." With "Initial": "The solver starts from the rest pose and re-iterates until the given precision is achieved, but only on the first frame". With "Always": "The solver re-iterates on each frame until the given precision is achieved." — https://docs.blender.org/manual/en/5.3/animation/armatures/posing/bone_constraints/inverse_kinematics/introduction.html (read 2026-11-08). **Inferred:** a lone frame with nothing before it in the cache is handled as a first frame — under Never, the pose starts from rest and has not yet reached the target; under Initial or Always, the pose converges on the target on that frame. The step is assuming that a lone render starts with an empty iTaSC cache; when that cache is emptied is **not in the sources** (checked on that page and https://docs.blender.org/api/5.3/bpy.types.Itasc.html, read 2026-11-08).
- **Frames from the first frame onward worked out — Label:** inferred.
  - **Inferred** from the same passage on https://docs.blender.org/manual/en/5.3/animation/armatures/posing/bone_constraints/inverse_kinematics/introduction.html (read 2026-11-08): when the frames from the first frame onward have been worked out in that session, the cache holds the previous frame at each step ("builds up a state cache automatically"), so the rendered frame is solved from the cached previous frame's state rather than starting from the rest pose.

**E. Ocean baked foam.**
- **Label:** documented for live vs baked evaluation; inferred for what a render shows in the two cases of Question 4.
- Manual: unbaked, the ocean "retrieves data for that current frame only"; baked, "the simulator engine is completely bypassed, and all information for the modifier or texture is retrieved from the baked files." — https://docs.blender.org/manual/en/5.3/modeling/modifiers/physics/ocean.html (read 2026-11-08). **Inferred:** whether no earlier frame was worked out in that session or the frames from `frame_start` onward were worked out in that session, an unbaked ocean computes only the current frame (without accumulated foam from earlier frames), and a baked ocean reads that frame's baked file from disk without needing earlier frames worked out in the session.

## 6. Can such a kind sit anywhere other than directly in the scene being rendered and still change what that scene shows? Name each such place, and say whether a script can find the kind and its first frame there.

**Label:** documented that each place below exists and can hold simulations or be rendered; inferred that this changes the rendered picture and that a script finds them; not in the sources for whether simulations on instanced collections, particle-instanced objects, or objects read through Geometry Nodes or cross-object modifiers/constraints affect the render.

2. **Scene strips in the Video Sequencer.**
   - Manual: "Pipeline – Sequencer: Renders the output of the Video Sequence editor … If the sequence contains Scene strips, these will also be rendered as part of the pipeline." — https://docs.blender.org/manual/en/5.3/render/output/properties/post_processing.html (read 2026-11-08). ## 7. Is there anything that makes one frame depend on earlier ones that a script cannot find, or whose first frame it cannot read? Name each.

**Label:** documented for each quoted API/manual fact; inferred for what a script can or cannot determine from them; not in the sources where marked.

1. **iTaSC in Simulation mode — has no start-frame setting to read.** **Documented:** it can be found via Pose.ik_solver and Pose.ik_param — https://docs.blender.org/api/5.3/bpy.types.Pose.html (read 2026-11-08) — and Itasc.mode — https://docs.blender.org/api/5.3/bpy.types.Itasc.html (read 2026-11-08), while its first frame is described as "a frame which doesn't have any previous frame in the cache" — https://docs.blender.org/manual/en/5.3/animation/armatures/posing/bone_constraints/inverse_kinematics/introduction.html (read 2026-11-08) — and `bpy.types.Itasc` lists no start-frame property (**not in the sources**). **Inferred:** a script can find that iTaSC Simulation mode is on, but there is no start-frame property for it to read. ## 9. When such a kind has been baked, what does a render use, and can a script tell whether every frame the render needs is in the bake?

**A. Point-cache physics.**
- **What a render uses — Label:** documented (that baking protects the cache from recalculation and stores it in the file or on disk); inferred (that a render reads the baked cache).
  - Manual: "It is generally recommended to bake your physics simulations before rendering. Aside from no longer needing to go through the time-consuming process of simulating again, baking can help prevent potential glitches and ensure that the outcome of the simulation remains exactly the same every time." and "If you bake the simulation the cache is protected, and you will be unable to change the simulation settings until you clear the baked frames by clicking Delete Bake." — https://docs.blender.org/manual/en/5.3/physics/baking.html (read 2026-11-08). Manual: "The system is protected against changes after baking. If for example the mesh changes the simulation is not calculated anew." — https://docs.blender.org/manual/en/5.3/physics/particles/emitter/cache.html (read 2026-11-08).
  - Where the bake lives — Manual: "The cache of a baked simulation will be stored inside the blend-file when you save it. When Disk Cache is checked, Blender will save the cache separately to the drive in a folder named blendcache_[filename] alongside the blend-file. (The blend-file must be saved first.)" Also External: "Allows you to read the cache from a drive using a user-specified file path." — https://docs.blender.org/manual/en/5.3/physics/baking.html (read 2026-11-08).
  - Cache Step — Manual: "Some physics systems (such as particles) allow for positions to be stored only on every nth frame, letting the positions for in-between frames be interpolated." — https://docs.blender.org/manual/en/5.3/physics/baking.html (read 2026-11-08).
  - Motion blur, hair — Manual: "If you use motion blur in your animation, you will need to bake one extra frame past the last frame which you will be rendering." — https://docs.blender.org/manual/en/5.3/physics/particles/hair/dynamics.html (read 2026-11-08).
  - Rigid body can also be turned into ordinary keyframes — Manual: "Rigid body dynamics can be baked to normal keyframes with Bake To Keyframes in the Object ‣ Rigid Body menu." — https://docs.blender.org/manual/en/5.3/physics/rigid_body/tips.html (read 2026-11-08).
- **Can a script tell every needed frame is there — Label:** documented for the `PointCache` properties, the manual pictures of `info`, and the disk file-naming pattern; inferred for how a script combines them to check coverage of a named disk cache or range; not in the sources for an API list of baked frames or for the unnamed disk-cache prefix rule.
  - Python API, PointCache: is_baked "The cache is baked"; is_frame_skip "Some frames were skipped while baking/saving that cache"; is_outdated (no description); frame_start, frame_end, frame_step; info "Info on current cache status"; use_disk_cache, use_external, filepath, name, index — https://docs.blender.org/api/5.3/bpy.types.PointCache.html (read 2026-11-08). Manual pictures show examples of `info` (**documented**): "0 frames in memory (0 B)." in `_images/physics_particles_emitter_cache_settings.png` on https://docs.blender.org/manual/en/5.3/physics/particles/emitter/cache.html (read 2026-11-08) and "0 frames on disk, cache is outdated!" in `_images/physics_dynamic-paint_canvas_cache-panel.png` on https://docs.blender.org/manual/en/5.3/physics/dynamic_paint/canvas.html (read 2026-11-08). **Inferred:** a script can check `is_baked`, `is_frame_skip`, and `is_outdated` and compare `frame_start`/`frame_end` with the frames to render (plus one frame past the end for motion blur on hair). A property listing which individual frames are present is **not in the sources** (checked on https://docs.blender.org/api/5.3/bpy.types.PointCache.html, read 2026-11-08).
  - On disk — Manual: "a cache named MyCache will be stored in MyCache_xxxxxx_yy.bphys" and "The cache files name format is name_frame_index.bphys." — https://docs.blender.org/manual/en/5.3/physics/baking.html (read 2026-11-08). **Inferred:** for a named disk cache, a script can check for the `.bphys` files on disk across the needed frames (taking `frame_step` into account). For an unnamed cache — Manual: "the filename of the cache will depend on the object it is attached to, although this is not immediately obvious. For example, a cache on an object Cube will be stored in 43756265_xxxxxx_yy.bphys" — https://docs.blender.org/manual/en/5.3/physics/baking.html (read 2026-11-08). Because the rule for turning the object name into that prefix is **not in the sources** beyond that one example, a script cannot work out an unnamed cache's file names from the sources alone. For a cache stored inside the blend-file, a per-frame check is **not in the sources**.

**B. Fluid.**
- **What a render uses — Label:** documented that the cache stores the simulation outcome so it is not recalculated and uses `Offset` when loading; inferred that a render loads the baked simulation from the cache directory.
  - Manual: "The Cache panel is used to Bake the fluid simulation and stores the outcome of a simulation so it does not need to be recalculated." "Cache Directory: Directory to store baked simulation files in." "Offset: Frame offset that is used when loading the simulation from the cache." — https://docs.blender.org/manual/en/5.3/physics/fluid/type/domain/cache.html (read 2026-11-08).
- **Script check — Label:** documented for the `FluidDomainSettings` properties; inferred that a script can read whether a part is marked baked and its configured frame range; not in the sources for checking whether every frame inside that range is present.
  - Python API, FluidDomainSettings: has_cache_baked_any, has_cache_baked_data, has_cache_baked_guide, has_cache_baked_mesh, has_cache_baked_noise, has_cache_baked_particles (each only "(default False)", no description); cache_frame_start, cache_frame_end, cache_frame_offset, cache_directory, cache_type, cache_resumable; cache_frame_pause_data/guide/mesh/noise/particles (no description) — https://docs.blender.org/api/5.3/bpy.types.FluidDomainSettings.html (read 2026-11-08). **Inferred:** a script can tell that a part is marked baked and read the set range (`cache_frame_start` to `cache_frame_end`, shifted by `cache_frame_offset`), but no documented property on `FluidDomainSettings` states that every frame in that range is present, and what the `cache_frame_pause_*` values or disk files hold is **not in the sources** (checked on those two pages).

  - Manual: the timeline shows "Baked simulations will be shown as fully opaque, cached simulations will be slightly transparent, and invalid caches will be slightly transparent with dark diagonal stripes." — https://docs.blender.org/manual/en/5.3/editors/dope_sheet/navigating.html (read 2026-11-08).   - Release notes for 5.3 (documented): "**Bake**: Path template support. (blender/blender!164240)" — https://developer.blender.org/docs/release_notes/5.3/geometry_nodes/ (read 2026-11-08).
