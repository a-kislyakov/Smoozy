# Question register

Every Blender question this project owes, with its permanent number, where it came from, and what breaks if the answer comes back wrong — together with the questions deliberately not asked, and why.

## This is not what a researcher sees

Each entry below carries its origin and its stakes, which is exactly what blind framing exists to withhold. A researcher gets a **question sheet**: the numbered questions for one topic, worded blind, and nothing else. Whoever prepares a sheet reads this file and then does no research themselves. How and why is set out in the [Method](Method.md).

Some entries say a question was **raised by an agent from its own knowledge**. Those carry a hazard the others do not: the question already contains a guess at its own answer, so the wording needs more care than the rest.

The labels and dates below record **who raised a question and when** — they are not claims to be relied on, and the register states no outside fact of its own. Where a fact is actually leaned on, its label lives in the document that leans on it, as Rule 2 requires.

## Questions deliberately not asked

Eight facts the Creator has settled and asked not be reopened. A researcher is never handed them, and a later agent should leave them alone rather than treating the silence as an oversight.

The five Blender concepts in the [Glossary](../Groundwork/Glossary.md) — scene, frame, view layer, the render atom, and output — together with a frame's outputs landing only once every view layer active on it has finished, and a frame with no active view layer writing nothing. That a frame range can begin at any number, including zero and below. That a view layer can carry its own sample count. That reading a `.blend` for its settings needs a Blender on the machine. That Cycles and EEVEE are Blender's own engines, and that a resolution percentage is a percentage of the output size the file names in pixels. All Creator-stated.

**One of those was narrowed on 2026-08-01.** That Cycles and EEVEE are Blender's own is still settled and still not asked. What is no longer taken as settled is that they are the only engines a file can name, since something installed on a machine may add to the list — so **Settings 13** asks what decides that list. The Render Settings spec offers a choice of two and describes the samples box in terms of both, so this is a hole in that spec rather than a detail, and it is the first entry here to be reopened.

**A second was narrowed on 2026-08-08.** The Creator's ruling of 2026-07-30 about the resolution percentage is narrowed rather than reversed. What it settled, and what stays settled and unasked, is **what the percentage means**: the file carries a percentage of the scene's full size, and a typed number is of that same full size. What it never covered is **the range of values the setting will take**, and what a render does with one outside it — so **Settings 14 and 15** ask those, and the ruling above must not be read as a blanket ban that sends the next researcher-runner past them.

Two more are not asked for a different reason: that file output nodes are ordinary work rather than a power user's trick, and that other render farms want a file packed before it is sent. Both are facts about how people work rather than about Blender, and both rest on the Creator's own professional experience.

## Questions that are not Blender's

Several things parked across this project as research questions will never be answered by Blender's documentation, and are not asked here. All are sent to **Architecture** in [Open Threads](../Groundwork/Open%20Threads.md) instead.

Restarting a rented machine and what a restart stops. Whether a machine can be a locked container with its drivers fixed. Whether one machine hands out several containers. Elevated access and how it is obtained. Reading a machine's hardware, its live graphics-card memory, and its free disk space. Whether a file deleted on a machine is recoverable. Whether an interrupted upload can be carried on. Whether a file changing mid-upload can be noticed. Whether a machine can be read for the work left sitting on it. Whether changing a server's username still reaches work already running. Every fact about Telegram. Whether two files on one computer can share a full location. Jump hosts. Transfer priority. Whether anything is squeezed on the way.

One sits on the line and is kept here: **what a machine must have on it before Blender will render**. Blender publishes what it requires, so that half is genuinely Blender's; what a particular rented machine provides is Architecture's.

## A question that cannot be answered in isolation

**Settings 10** asks what a version states about opening a file saved by a different version. That half a lone researcher can answer. The other half — what a given mismatch actually *costs*, which files will not open, which render differently, which are harmless — is a fact about two versions meeting, so no isolated pass can reach it. It waits for the comparison, or for its own small research job with its own rules.

It is the first question of that kind. There may be more, and they should be marked here as they turn up.

## The machine

*What a machine must have before Blender will run and render on it.*

The Creator has marked this topic as heavier than its size suggests: there may be system dependencies nobody has thought of, and it is not a footnote. Creator-stated (2026-07-30).

1. **What a machine must have on it before Blender will run at all.** *(Server Setup, unresolved. The heaviest question here: until it lands, Server Setup cannot write the fuller choice it is meant to offer over how a machine is prepared, and the spec says so.)*
2. **What a machine must have on it before Blender will render on its graphics cards.** *(As above. The Creator's ruling of 2026-07-27 is that this must not be framed as the graphics card alone, since nobody yet knows what a bare machine needs; drivers are the obvious part and there may be more. Whatever comes back is not the whole of what a machine needs: an add-on can carry a requirement of its own on top of Blender's, which is **Add-ons 11**. Noted 2026-08-01.)*
3. **Whether what a machine needs differs by how Blender was obtained and put there.**
4. **Whether Blender says anything about what it is missing when it will not start, or will not render.**
5. **How Blender decides which of a machine's graphics cards a render uses, whether all of them can be used at once, and how that is settled from outside its interface.** *(Rendering, unresolved, agent-raised. A machine rented for its cards rendering on its processor instead is the whole point of the product failing quietly and expensively. The Creator states that a render must always use every card the machine has — Creator-stated, 2026-07-30 — so an answer that reaches only some of them is a hole.)*
6. **Whether Blender can be asked which graphics cards it can see and use.**
7. **Whether anything a render does can wait for a person, and what happens on a computer with nobody at it.** *(Added 2026-08-06. On a machine with nobody at it, a render that is waiting looks exactly like a render that is working — same clock, same bill, no output, and nothing to tell the two apart. This topic already owns running with no screen and running with no display server, and failing loudly; simply sitting there is the next question in that line and nothing anywhere had asked it. Reaches Rendering and Queue & History, both of which read a job that produces nothing for hours as a job that is working.)*

8. **On a computer that has a graphics card but whose screen is drawn by the processor rather than by that card, what a render does under each render engine.** *(Added 2026-08-30 from the cross-sweep of that date, `Audits/Blender Research/Cross-sweep/2026-08-30 — What survived — Claude Opus 5.md`, which lists it among the things the comparisons cannot settle and calls it a question nobody has asked rather than a contradiction anybody can rule on. **Question 2** of this topic records all four manuals saying EEVEE only ever renders on the graphics card and cannot fall back to the processor, and `Settings 6` leans on that; `Frames 15` records EEVEE running on a rented machine with its viewport drawn by the processor, where a frame took about ninety seconds. **Six of this project's machines with a display had that display drawn in software**, and nothing anywhere says whether such a machine counts as having a card for an engine that needs one. What breaks if it comes back wrong: Smoozy renders on rented Linux, where a display server — if the machine has one at all — may well be software-drawn, so a wrong answer means either an engine offered on machines that cannot run it, or an engine withheld from machines that can, and either is found only after the machine has been paid for. It also decides how much of four topics' window-drawn evidence stands. **Questions 1 and 2** ask what a computer must have before Blender will run at all and before it will render using its cards; neither asks about a computer that has a card and draws its screen with something else, and **Settings 6** asks about a machine with no screen attached, which is not this.)* **Permanently unanswered: the 2026-08-31 ruling. Nothing above is work that is coming.**

9. **On a computer where Blender has just been put on and nothing in it has been changed, what a render asked for the graphics card actually uses.** *(Added 2026-08-30 from the mechanism sweep of that date, `Audits/Blender Research/Cross-sweep/Mechanism sweep/Repairs — the list.md`, which lists it among the things no rewriting can settle. **Question 5** asks how Blender decides which of a machine's cards a render uses and how that is settled from outside its interface; it was answered from runs on machines whose preferences had already been saved at least once, and this project's own hand tests say in their own words that the two runs behind that answer do not separate what made the difference. **Every machine Smoozy renders on is the untested one**: a rented computer with a Blender put on it minutes earlier and nothing ever opened in it. What breaks if it comes back wrong is the failure this project has already paid for three times over — a scene set for the card rendering on the processor, silently, at full price, reporting success. `What actually ran 1` asks what can be learned **afterwards** about which parts of the computer were used; this asks what a fresh machine actually does.)* **Permanently unanswered: the 2026-08-31 ruling. Nothing above is work that is coming.**

## Add-ons

*Questions 1 to 7 were raised by an agent from its own knowledge, at the Creator's request, with labelling deliberately set aside for that conversation (2026-07-29). Each needs rewording with more care than the rest.*

*Three of them were re-aimed on 2026-08-01, after a look at the add-ons arriving in Blender from other software — a cloth solver and a particle system were the two in hand. Neither product is named in any question and neither should be: Blender's documentation will never mention them, one such product had already been discontinued by the time it was looked at, and the class moves faster than this project will. What they showed is that questions 3, 4 and 5 were aimed at a vaguer thing than the one that exists, and would have come back thin. They are worded here as questions about the mechanism, so one answer covers the products that do not exist yet.*

1. **Whether a `.blend` can be read for the add-ons it needs.** *(Everything else in this topic is downstream of it. If a file records nothing, Smoozy's guess is worth much less and Server Setup's whole add-on section needs rethinking rather than rewording.)*
2. **What makes a `.blend` need an add-on at the moment it renders, and whether an add-on that takes part in producing the render can be told apart from one that only rearranges Blender's existing tools while the artist works.** *(The distinction the section rests on. The Creator confirmed this reading on 2026-07-30 — and that the earlier wording was unclear enough that they had to ask. The first half arrived here on 2026-07-30 from question 9, which was retired.)*
3. **Whether an add-on can be installed, switched on, and given whatever it needs before it will work, on a machine with no screen attached.** *(Every rented machine is of that kind. The promise that installing means switched on rests on it entirely, and a negative answer is a hole in Server Setup rather than a weakening. The Creator notes this is a genuinely open question, unlike whether Blender itself runs without a screen. Widened on 2026-08-01 from switching on to being made ready to work at all: an add-on that installs and switches on and still sits there wanting something typed into it is not set up, and Server Setup's promise fails just as squarely. The wording stays open about what that something might be, since naming it would hand over the answer.)*
4. **What an add-on records about the kinds of computer it is meant for, what happens on one it does not name, and whether an add-on set up on one computer still works when copied to a different kind.** *(The path that reaches a paid add-on rests on this entirely: the copy goes up already set up, so that Smoozy never handles a licence. Two ways it might fail were raised with it — an add-on carrying parts built for the artist's kind of computer, and one tied to the particular machine it was set up on. Opened out on 2026-08-01: the original asked only whether a copy works, which invites a yes or no. What Smoozy actually needs is what can be known **before** the copy is sent, since an artist on one kind of computer sending to a rented machine of another is the ordinary case rather than the edge of it.)*
5. **How an add-on can be found, fetched and installed without a person at a screen, and what decides the places it can be fetched from.** *(Decides whether the free case is as easy as installing Blender or has no path at all. Reworded on 2026-08-01: it used to ask only about the add-ons Blender itself publishes, which is narrower than what Smoozy has to work with. Where an add-on may be fetched from reaches question 8 as well, and may turn out to be one mechanism rather than two — in which case Smoozy's free path and its paid path are the same path with different permission on it.)*
6. **Whether an add-on belongs to one Blender on a machine or to the machine itself.** *(Decides three separate things in Server Setup: whether a machine holding two Blenders needs an add-on once or twice, whether installing one can disturb a running render, and whether changing the Blender version after a pre-load silently undoes the add-ons just installed.)*
7. **What a render does when an add-on it needs is not there** — whether it stops, or carries on and produces something quietly wrong. *(The user is left to decide whether to submit anyway, and cannot weigh it without this. Likely the same shape as Dependencies 12, and may share its answer.)*
8. **Where add-ons come from besides Blender's own, how they are sold, and what that means for taking a copy of one from one computer to another.** *(Raised in the Server Setup round 1 audit, 2026-07-29, and widened at the Creator's request on 2026-07-30: paid add-ons are sold through many separate places, each with its own arrangement, and the Creator has asked that this not be answered thinly. What rests on it is what Server Setup says about licences — it no longer promises that Smoozy never sees a licence key, only that it does not ask for, read, or check one, and that wording changes again if a copied add-on carries licence material to a rented machine. Two notes from 2026-08-01. Part of this is now asked better by question 5, which covers where an add-on may be fetched from — so what is left here is how add-ons are **sold**, and that half should be expected to come back *not in the sources* from every version, since it is a fact about other people's businesses rather than about Blender. Treat that as the answer rather than as a thin one, and let Architecture carry the selling half with the other fast-changing outside facts. The Creator's instruction that it not be answered thinly stands, and question 5 is where it is now met.)*
9. **Retired 2026-07-30, and the number is not reused.** It asked whether a file needing an add-on to render is the exception rather than the rule. Two faults: it stated its own expected answer, and no Blender documentation can answer how common something is. How common it is stays **Creator-stated** (2026-07-29) on their professional experience, and is why add-ons get no read of their own. The researchable half — what makes a file need one at all — moved into question 2.
10. **Whether a machine can be asked which add-ons it holds, and for which Blender.** *(Added 2026-08-01. Server Setup compares what a job's guess asks for against what the machine already holds, so that nothing is installed twice, and says out loud that whether a machine can be read this way is unresolved. **Builds 7** asks the same of Blenders and covers only those, so the add-on half had no question. 11. **Whether an add-on can depend on something else being on the machine, or on a machine elsewhere, before it will work, and whether what it needs can be read anywhere.** *(Added 2026-08-01. Server Setup draws a clean line — a separate program with its own installer is not an add-on and Smoozy does not handle one — and that line does not cut where things actually divide. 12. **Whether installing an add-on disturbs a render already running on the same machine.** *(Added 2026-08-06. **Builds 6** asks exactly this of installing a Blender and covers only that, so the add-on half had no question — and Server Setup installs add-ons on machines that may be busy. **Question 6** is its neighbour: if an add-on belongs to one Blender rather than to the machine, the answer may turn on which Blender is rendering.)*
13. **Whether anything more can be learned about an add-on working, once it is installed and switched on.** *(Added 2026-08-06. 14. **Whether an add-on set up for one Blender works in another on the same machine, and what decides that.** *(Added 2026-08-06. 15. **Where on a machine an add-on can be installed to, and whether installing one in each of those places disturbs a render already running.** *(Added 2026-08-30 from the mechanism sweep of that date. **Question 12** asks whether installing an add-on disturbs a running render and was answered **no** — but every install behind that answer landed in a place of its own, well away from anything the running Blender reads, and the sweep found that the ordinary route lands somewhere else entirely. ## Reading a file

1. **What a `.blend` gives up without a Blender to open it, and what needs one.** *(That the version it was saved with is readable without opening it is Creator-stated 2026-07-23 and held as needing no confirming; the general rule is open, and Render Settings' default version choice leans on the first half.)*
2. **How many Blenders can be at work on one machine at the same time, and whether one reading a file while another renders causes trouble.** *(Creator-raised, 2026-07-30. Pre-loading the settings of one job while another renders is an ordinary thing for a user to do, and nothing establishes it is possible.)*
3. **Whether one read of a file answers, for every view layer, whether that layer renders at any frame later asked about.** *(Creator-stated 2026-07-29, held at about 95% rather than certain. Render Settings' view layer section rests on it entirely — the boxes redraw for any frame the user types without a second read — so a negative answer means that section is rewritten rather than trimmed.)*
4. **Whether the places a file is set up to write to can be read out of it.** *(Creator-stated 2026-07-28, to confirm. Pre-load Settings is what supplies the read.)*
5. **Whether the locations a file records for the things it points at can be read out and written back, and by what.** *(Half of Dependency Upload & Remap has to be built another way if not — the in-place fixing of every linked file rests on it, and so does the check itself.)*
6. **Whether anything can be asked to report which of a file's references are missing, to search for them, and to rewrite the recorded locations.** *(Close to the question above and worth keeping apart from it: that one asks whether the locations can be read and written at all, this one whether the finding and fixing can be handed over rather than worked out. The wording was made blind on 2026-07-30 — it had named where to look.)*
7. **Whether what a file points at can be traced to the scene that uses it.** *(Dependency Upload & Remap's whole-file check is defended by the user setting irrelevant rows aside, which they can only do by eye if a row can name its scene.)*
8. **Whether a file's full chain of references can be read while some of the referenced files are absent.** *(The spec states that reaching the deeper levels may take more than one pass, because a missing linked file is not there to be read. A different answer removes that.)*
9. **What separate means exist for listing and rewriting the locations recorded in a `.blend`, and which kinds of recorded location each of those means reaches.** *(Added 2026-08-06. **Question 5** is the neighbour and asks whether it can be done at all and by what; this asks something question 5 does not — how much each way of doing it actually covers. That gap is where the geometry-node hole came from: a means that reaches most locations and silently misses a class of them looks exactly like a means that reaches all of them, and Dependency Upload & Remap rewrites every location it can find and calls the file ready. Word it so it does not simply repeat question 5.)*
10. **When a search for a missing reference finds more than one possible file, what makes a file a possible match, which one is chosen, and what location is written back.** *(Added 2026-08-07 from stress-test questions 1, 3 and 6, and kept because the Creator ruled duplicate dependency matching to be Smoozy's responsibility. **Question 6** establishes that Blender can search and rewrite, but does not say how it chooses among duplicate names, different contents, different sizes or different library roots. A wrong answer silently binds the project to the wrong asset, so Smoozy cannot hand repair to Blender or copy its choice until this is known.)*
11. **What happens when a file Blender has already read is changed or replaced on disk, and what has to happen before a later render uses the changed file.** *(Added 2026-08-07 from stress-test questions 4, 8 and 10. File Browser lets a user replace a checked main file or a nested library, while Dependency Upload & Remap keeps a record of what the old file pointed at. **Questions 5 and 8** say what can be read and how deep, but nothing says whether a Blender kept open notices replacement or keeps using what it loaded. The Blender answer supplies the reload boundary; Architecture still owns how Smoozy notices that its checked record is stale.)*

12. **When a reference that was missing is found again and its recorded location rewritten, what form the new location is written in.** *(Added 2026-08-30 from the mechanism sweep of that date, which found three separate documents saying in their own words that this has never been asked — this topic's questions 9 and 10, `Dependencies`' own account of the same command, and the joined answer *What has to travel with a file*. **Question 6** asks whether the finding and fixing can be handed over at all, and **question 5** whether recorded locations can be read and written back; neither asks what the writing-back produces. Two runs of the same command exist and neither ever met the other's case, so the rule everybody reads off them is drawn from two halves that never overlapped. 13. **What a render puts on each of its output streams when a file the scene points at is not there.** *(Added 2026-08-18 from Batch E of the Architecture stage, agent-raised from a machine observation. **Question 4** establishes what the streams are and what they contain, and **Images 2 and 9** ask what a **picture** shows when an image is missing — none asks which stream, if either, carries the complaint. **What one box did on one day:** a scene whose texture pointed at a file that does not exist rendered a hundred frames and put **nothing at all** on the second stream, in two different versions, while the first stream carried its ordinary output — so whatever was said about the absent file went to the first stream or was not said. Two things rest on it. Smoozy keeps the two streams apart and reports *the render printed nothing* as a recorded fact per stream, and a second stream that is empty even when something is genuinely wrong makes that report true and useless at the same time. And the volume a render prints on each stream was measured on that box **at zero** for the second one, which is a measured zero rather than a demonstrated capacity, so nothing may size that stream from it.)*
14. **When a render's printed output is sent somewhere other than a terminal, what decides when each line of it becomes available to whatever is reading.** *(Added 2026-08-29 from `Preparation/Groundwork/Open Threads.md`, carried there on 2026-08-21 by the Architecture stage's verification round, and due when this stage was next opened. **Posed as something to watch rather than something to read**, with arrival times recorded. **Why it is asked:** a render whose printed lines sat unsent until it ended would look exactly like a render that prints nothing at all, and this project has already watched a stream behave that way on the Creator's own Mac — one box, one day. **Questions 3, 4 and 8** ask what a render prints and over what span; **question 9** asks what each way of starting one reports. None asks when a printed line arrives at a reader that is not a terminal. **Blocks nothing:** `Queue & History` R4 names the case and no clause infers an ending from silence, so what is at risk is whether a display is live rather than any recorded state. Wants no rental — one machine with a card is enough.)*

15. **When a render works a frame in more than one piece, what the numbers in each line it prints about its progress count.** *(Added 2026-08-30 from the mechanism sweep of that date. **Question 7** established that a large enough frame is worked and reported piece by piece, and settled that the sample number cannot be a count across the whole frame; **it did not settle what it is a count of**, because the one capture that shows it is squeezed into five thousandths of a second and no line in it can be tied to a piece. **Question 3** asks what a render reports about how far it has got and never asks what the numbers in that report are measured against. What breaks if it comes back wrong: Rendering reads a job's progress out of what the render prints and shows the user how far through a frame it is, and a number that restarts several times inside one frame read as a count across the frame gives a progress display that goes backwards, or one that reports a frame nearly done several times over. It wants a capture taken slowly enough to be read, which is the whole of the difficulty.)* **Permanently unanswered: the 2026-08-31 ruling. Nothing above is work that is coming.**

16. **What a render does when a graphics card's memory runs out while it is sampling, and what it reports about the memory it is using from the first line of such a run to the last.** *(Added 2026-08-30 from the mechanism sweep of that date, which merged two of its own proposed runs into one because one run answers both. **Question 10** asks what a render does when the **machine's** own memory runs out while sampling, and its loud answer was measured on a processor render; the one card render this project holds that ran a machine out was silent in all four versions, so what makes the difference — the card or the moment — is not separated by anything on record. **Question 6** asks what Blender reports about the memory it is using on a card, and **question 8** what a render prints from first line to last; neither has ever been answered from a run that actually overfilled a card, because on the one run that did, only the last two lines were kept. What breaks if it comes back wrong: the Creator holds that running out of graphics-card memory is the cause of nearly every failed render they have had, so this is the failure Smoozy will meet most — and Queue & History reads a job that dies without a message as a job that is working. Whether the reports arrive early enough to be a warning rather than an obituary is the second half and is why the whole run is wanted.)* **Permanently unanswered: the 2026-08-31 ruling. Nothing above is work that is coming.**

## What actually ran

*Added 2026-08-06, and the first of the three new topics to be done. It cuts across **The machine**, **Settings** and **Add-ons** rather than sitting inside any of them, because what it asks is not what Blender does but what it can be made to say about what it did.*

*Three broken promises share a single root, and all three are recorded in the specs as broken. A graphics driver that is gone, a render engine that is missing, and an add-on built for the wrong machine each produce a clean render of the wrong thing and report success. If any of it is knowable, Server Setup, Render Settings and Rendering get their promises back together. If none of it is, those three have to say plainly that Smoozy cannot tell.*

*The Creator has settled one thing in advance, and it matters: **nothing** is a real possible answer to every question here. What the specs say in that case is a product decision, and it is cheaper to settle it before this runs than to discover it and reopen three documents.*

1. **What can be learned, once a render has finished, about which parts of the computer it used.** *(Rendering, Server Setup. The promise that died: that the first job run on a machine would show whether it renders on the cards. It does not — a broken driver produces a successful processor render in every version, silently.)*
2. **What can be learned, once a render has finished, about which render engine produced it.** *(Render Settings. A missing engine falls back to EEVEE and renders at EEVEE's sample count, reporting success, so a file's engine name does not reliably reach the render.)*
3. **What can be learned, once a render has finished, about which add-ons were in use while it ran.** *(Server Setup. Meets **Add-ons 13**, which asks the same thing from the other end — what can be read of an add-on before anything uses it.)*
4. **What a render does when it is asked for something the computer or the installed Blender cannot provide, and what it reports.** *(The general case behind the first three. Reports 1 and 2 ask what a failure looks like; this asks what a *quiet substitution* looks like, which is the case that has cost this project every one of the three promises.)*
5. **Where each of those things can be learned from** — what a render prints as it works, what it leaves on disk, or what can be asked afterwards. *(Decides whether Smoozy can read any of it over a connection at all, which is what turns an answer into a feature.)*
6. **At what point each of those things can be learned** — before a render starts, while it runs, or only once it has finished. *(Added last and the one that matters most in practice. The first five all ask about a finished render, and by then the machine has been paid for: a six-hour render on the processor costs the same whether the mistake is found afterwards or never.)*

## What a render demands

*Added 2026-08-06, Creator-raised. They named a group of settings that caps texture resolution and does other work on a scene to make a render cheaper. **The feature is deliberately not named in any question.** Smoozy will outlive the versions we can see, and a question naming a feature dies the day that feature is renamed. The Creator's own words about it are in [Open Threads](../Groundwork/Open%20Threads.md) and must not reach a researcher.*

*Why it is a topic of its own. Every other lever the specs have for making a job cheaper changes what the user gets — fewer samples, a smaller picture. If a render's demands can be cut by capping what a scene loads rather than by shrinking what it produces, that is a different kind of lever from anything Render Settings offers, and it bears on two open threads at once: what is worth changing after a failure, and what to do about a job that quietly cost ten times what it should have.*

***It overlaps Settings, and the sheet carries the boundary.*** *Settings has already answered which of a render's settings can be imposed at the start of a render. This topic asks only about settings that change what a render **costs the computer**, and the sheet's opening line says so. Expect samples and picture size to come back among the answers; trimming the question to exclude them would leak what is being fished for, and the noise is cheaper than the leak. The same trap was avoided once already, by keeping add-ons out of the dependency questions.*

1. **What settings, if any, change how much a render demands of the computer it runs on.**
2. **For each of them, what it changes about what the render produces.** *(The cost side. A lever nobody can price is a lever Smoozy cannot offer.)*
3. **Which of them can be settled at the moment a render is started from outside Blender, and which only by changing the file.** *(Decides whether Smoozy can offer any of it without touching the artist's file.)*
4. **Whether any of them belong to a particular render engine rather than to every engine.**
5. **Whether their values can be read out of a file.** *(Pre-load Settings is what would supply the read.)*
6. **What a saved scene records about limits on subdivision, child particles and texture size, including any switch governing those limits, and what can be read back when the file is opened from outside Blender's interface.** *(Added 2026-08-28 from Architecture Fact 134 and Row 472. Question 5 established the general reading route and directly tested the switch and maximum subdivision, but its round-trip list did not name Child Particles or Simplify's Texture Limit; the texture limit it did name was the separate Cycles control. The missing two values decide whether the render-settings drawing is showing values read from the file or defaults invented by Smoozy. This question is written to cover the whole group so the direct result cannot mix controls from different owners.)*

7. **What a graphics card's rendering methods are, what choosing one rather than another changes about a render, and whether that changes with the size of the scene.** *(Added 2026-08-29 from `Preparation/Groundwork/Open Threads.md`, carried there on 2026-08-21 by the Architecture stage's verification round, and due when this stage was next opened. **Fact 107 re-posed on the narrower gap.** This project holds one pair of readings already — one small scene on a machine shared with another test while both ran, where the mode usually assumed slower came back faster — and that is one box on one day rather than a claim about Blender. What is wanted is a scene big enough that the time spent preparing the card is not a large share of the whole, on a machine nothing else is using. **Blocks nothing:** `Rendering` L23's chosen value is untouched either way. ~~The measurement wants a rental with a card and rides free on any batch that has one.~~ **Struck 2026-09-02: the question is answered and no measurement is wanted.** All four versions answered it, its hand tests were run on 2026-08-30 on two machines, and the checked comparison is written. **The sentence was true when this entry was written on 2026-08-29 and stopped being true the next day.** Question 1 asks what a render demands of the computer and never asks what the choice between methods costs.)*

8. **What decides whether a render works a frame whole or in several pieces, and what a file made by a different Blender carries about that.** *(Added 2026-08-30 from the mechanism sweep of that date, which merged two of its own proposed runs here because they are one question asked from two ends. **The rule this project has been using is arithmetic and not a measurement.** Every size ever tried crossed two possible boundaries at once, so which of them decides has never been separated, and the rule everybody quotes was read out of a piece of Cycles' own interface code whose only effect is to draw an advisory label — this project's own findings say so and refuse to interpret it, and one comparison then called the inference "exactly right". What breaks if it comes back wrong: `Reports 7`'s progress reading, `Frames 19`'s stop deadline and `Frames 20`'s two-renders limit are all stated against this boundary, so three separate answers move with it — and a user's own file carried onto a rented machine is exactly the second half's case.)* **Permanently unanswered: the 2026-08-31 ruling.
