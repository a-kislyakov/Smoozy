# The machine — Blender 4.5, 5.0, 5.1, 5.2 and 5.3 side by side

What a computer must have on it before Blender will run and before it will render on its graphics cards, how Blender chooses and reports those cards, what a render does on a computer with nobody at it, and what it does when the screen is drawn by something other than the card.

## The machines behind the tests

Five machines. **1. The Creator's Mac** — a MacBook Pro with an Apple M1 Pro chip, Apple's own 14-core graphics (Metal) and no other card, 16 GB of memory, and a screen; **the only machine Blender 5.3 was run on**. **It is not one fixed machine across this topic.** 4.5 to 5.2 were run on it on 2026-08-01 and 2026-08-07 under macOS 26.5.2 — the question-7 runs record their builds as 4.5.12, 5.0.1, 5.1.2 and 5.2.0 — and 5.3 on 2026-10-17 under macOS 26.6.2, as **5.3.0 Beta**, built 2026-10-16, hash `5d8151335b6b`, with **5.2.2** beside it for same-day controls and the Creator's session logged in throughout. No time or memory figure here is used as a Mac performance measurement; where a 5.3 answer gives seconds, they are what Blender or the shell printed, used only to judge whether a run lasted. **2. A rented Linux machine with one NVIDIA GeForce RTX 4090**, and a real display server, so Blender's window could be opened and photographed on it; it shared somebody else's hardware with up to four topics at once, so nothing from it says how long anything took or how much memory was free. **3. A rented Linux machine with two NVIDIA GeForce RTX 4090s and no display server at all** — not a run cut off from a display, but a machine with none; the two cards are not joined by NVLink; nothing else was running on it, so its timings are honest, and its graphics driver was then broken on purpose. **4. A rented Linux machine with four NVIDIA GeForce RTX 4060 Ti of 16 GB each, 197 GB of memory and no display server**; these four are not NVLink-joined either, and nothing else was running on it. **5. A rented Linux machine with one NVIDIA GeForce RTX 4080 SUPER and no display server of any kind**, which with the Mac ran everything under question 7 for 4.5 to 5.2; its first sitting was shared with other topics' work, so no timing from it is a measurement either. Machines 2, 3, 4 and 5 have all been destroyed. Machines 2, 3 and 4 all carried the same four official Linux x64 builds of Blender, taken from Blender's own download server. The equipment section of `Preparation/Blender Research/Method.md` holds every machine in full and is not repeated here; **the numbering above is this document's own count**, and machines 2 to 5 are the **first**, **second**, **third** and **fourth** rented Linux machines in that section.

**One naming rule, so nobody has to guess.** Where an answer below says "the Linux machine" or "the rented Linux machine" with nothing else, it means **machine 2, the one-card machine** — everything in this topic other than the several-card, no-screen and broken-driver work and question 7 was run there. Results from machines 3, 4 and 5 always say which they are.

**Scope of the version names.** Below, *all four* means 4.5–5.2; *the newer three* means 5.0–5.2. 5.3 is named where included. All 5.3 observations are from the Mac. The same-day 5.2.2 controls separate four observed version differences from results shared by 5.2.2 and 5.3; the question entries identify each. A disagreement with the older Mac run remains open when both newer runs agree, because the point release, macOS version and test conditions also changed. No Linux-only result establishes a 5.3 result.

**A difference between the machines is not a difference between Blender.** They differ from each other in the number of cards, the model of card, the number of cores, the amount of memory and whether they have a screen at all, and nothing in the first list below rests on comparing one machine with another. **Machine 4 differs from machine 3 in three ways that can each explain a result on their own** — four cards rather than two, a smaller and slower card, and twice the system memory. So **no timing from one is ever set beside a timing from the other**, and none is below.

**A result settles only the machines it ran on.** Of the five, only the Mac can still be reached; the four Linux machines are gone, so every Linux result below stands as a record and none of it can be repeated or extended on the machine that produced it. **Nothing in 5.3 was run on Linux**, so every Linux answer below is an answer for 4.5 to 5.2 only.

**Windows was never tried** in this topic, in any version, on any question. No observed result here settles Windows, including its desktop and Server editions.

## 1. What must a computer have on it before Blender will run at all?

**The same in all five:** the manual states that minimum requirements exist and sends the reader to a download page it does not reproduce, so those manuals do not give a complete numeric machine specification. The graphics troubleshooting pages of all five give one number — a card and driver reaching OpenGL 3.3 — and in 5.3 that paragraph still names no 5.x version. All five name X11 and Wayland as supported Linux window systems; 4.5 to 5.2 add that under Gnome-Shell the libdecor library is needed or Blender falls back to X11, not established for 5.3. All five state that Blender carries its own Python and needs no internet connection. All five give the same two non-hardware conditions: no antivirus software blocking Blender, and the right user permissions. All five say Windows comes in x64 and arm64 builds and the download must match the processor.

**Where they part company — the Mac.**

- **4.5** — supports both Intel and Apple Silicon Macs. Its release notes say plainly that this is the last release with an official Intel macOS build.
- **5.0** — its release notes say support for Intel Macs has been removed. Its own installing page still says both Intel and Apple Silicon, which contradicts the release note inside the same version's documentation.
- **5.1** — its installing page also still says both. The requirements page, in the one line that names versions, says Blender 5.0 and later need Apple Silicon on macOS 13 or later.
- **5.2** — its installing page says outright that Blender 5.0 and later only support Macs with Apple silicon.
- **5.3** — its installing page says the same as 5.2's.

**Where they part company — what a graphics card must be.** 5.0's release notes carry the line "Increase Minimum GPU requirements for Blender". The new figures are not established by the version-named sources. The requirements page's one 4.5-named line says 4.5 supports NVIDIA GeForce 400 and newer, AMD GCN 1st generation and newer, and Intel Broadwell and newer; the page's current table, which names no version, says GeForce 900, GCN 4th generation and Kaby Lake. Those "supports" lines do not say whether they are about running Blender or about rendering on the card. **5.3's release notes add one more figure**: "Vulkan minimum requirements has been lowered to Vulkan 1.1 and some GPU/driver features have been made optional to support more devices." What Vulkan needed before is not in any version's version-named sources; the requirements page, which names no version, says Vulkan 1.3. 5.3's manual also says that on Linux with NVIDIA, drivers before 550 do not support Vulkan — a line no earlier version's findings record, which is a silence and not a change.

**Where they part company — which drawing system Blender starts on.** In 4.5, 5.0, 5.1 and 5.2 the drawing-system setting read OpenGL with no window on the Linux machines, and the System page there showed `Backend: OpenGL`. **5.3's release notes say "Vulkan backend is now default on Windows (not ARM) and Linux"**, and its API page gives Vulkan as that setting's default without saying whether it differs by operating system. No 5.3 Linux or Windows machine was run, so what 5.3 actually starts on there, and what it does when Vulkan is missing, is untried. **On the Mac nothing differs.** Every version draws with Metal there. A fresh 5.3 opened with its window drew with Metal and its drawing-system setting read `METAL`, while offering three choices; its own `--help` offers `metal` alone for `--gpu-backend`, as 5.2.2's does on the same Mac, though the manual lists vulkan, metal and opengl. Asked for `--gpu-backend vulkan` or `opengl`, 5.3 printed `Error: Unrecognized GPU backend for '--gpu-backend', expected one of [metal].` and carried on with Metal, exit status 0, with a window and without one. Observed on the Mac only, in 5.3 only.

**Where they part company — Linux windows.** `--no-window-frame` is absent in 4.5 and present in 5.0, 5.1 and 5.2, worded identically in all three. That was read out of each program's own help text on the one-card Linux machine, in all four versions. 5.1's release notes are what introduce it in writing, and they say that on Wayland it removes the dependence on libdecor — so the writing arrived a version after the argument did. What it changes on Wayland is untested: the only Linux machine with a display server ran Xorg. Whether 5.3 has it is not recorded; it is a Linux argument and 5.3 was read on the Mac.

**Where they part company — two more launch arguments.** `--gpu-vsync` is in 5.0, 5.1 and 5.2 and not in 4.5; whether 5.3 has it is not recorded. `--gpu-device` and `--gpu-device-no-fallback` are in 5.2 and not in 4.5, 5.0 or 5.1; in 4.5 the name is not recognised and Blender tries to open it as a file. Read and exercised in all four versions on the one-card Linux machine. **5.3 has both**: its `--help` on the Mac lists them, under the same `GPU Options:` block 5.2.2 prints word for word on the same Mac. `--gpu-device` names the card Blender *draws* with, not the card Cycles renders on, and applies only to the Vulkan backend — on the Mac, 5.3's `--gpu-device help` printed `(Vulkan backend not built)` and exited 0.

**Verdict: it differs.**

- 4.5 runs on Intel Macs; 5.0, 5.1, 5.2 and 5.3 need Apple Silicon. Established by release notes in 4.5 and 5.0 and stated outright in 5.2's and 5.3's manuals — not by one version's silence.
- What a graphics card must be to run Blender changed at 5.0. Established by 5.0's release note. What it changed to is not established for any version.
- A way to open a window without decorations on Linux exists in 5.0, 5.1 and 5.2 and not in 4.5; 5.3 is not recorded.
- Two further launch arguments arrived after 4.5, one at 5.0 and one at 5.2; 5.3 has the second, and the first is not recorded for it.
- Asked for a window with no display server to open it on, 4.5 refuses and then hangs where 5.0, 5.1 and 5.2 refuse and exit 1. Observed on two Linux machines, one whose display was taken away and one that never had one. Not tried in 5.3.
- The drawing system Blender starts on in Windows (not ARM) and Linux moves from OpenGL to Vulkan at 5.3. Established by 5.3's release note, against OpenGL read on Linux in 4.5 to 5.2; untried in 5.3.
- Vulkan's own minimum was lowered to 1.1 at 5.3. Established by 5.3's release note; the figure before is not established.

**Not established:** the complete numeric minimums for memory, disk, processor and operating-system version. There is one version-named macOS statement: Blender 5.0 and later require Apple Silicon running macOS 13 or later. It comes from the separate requirements-page copy, outside the four named 5.3 sources; 5.3's findings flag that limit. No test here reaches that floor. Whether the floor is the manual's OpenGL 3.3 or the requirements page's OpenGL 4.3; all five report both and none reconciles them, and the one-card Linux machine reported OpenGL 4.6, above both, so it tested no floor either. Whether that floor applies at all when Blender is started with no window. What Blender prints when it refuses to start for want of graphics.

**Settled by hand, on every machine and identically in all four versions:** Blender started, ran and rendered with no window open. On the Mac that was macOS 26.5.2 on an Apple M1 Pro. On the one-card Linux machine the display could be taken away, and with no display **reachable**, all four versions started and rendered, with Cycles on the graphics card and with EEVEE. Every machine is far above whatever floor applies, so none tests a floor. **5.3 did the same on the Mac**, under macOS 26.6.2: with no window all three engines rendered and ended by themselves. Cycles' device report confirmed both a card-only and a processor-only run. EEVEE and Workbench named no device; giving them Cycles' CPU option does not establish processor rendering.

**On a machine with no display server at all.** The one-card machine had a real display and its runs were merely cut off from it. The two-card machine had none — no X socket, no Wayland, session type `tty`, nothing installed to change it. There, **in all four versions, every render engine each version has completed: Cycles on the cards and on the processor, EEVEE, and Workbench**, each writing its picture and exiting 0. The four-card machine also had no display server, and everything run on it ran the same way. On those Linux machines, 4.5–5.2 rendered on the graphics cards without a display server. Only one engine name failed, and that is the naming difference already listed: 4.5 has no `BLENDER_EEVEE`, and asked for it, it printed its error and then hung. **5.3 was never run on a machine with no display server.**

**Asked for a *window* with no display server**, Blender in every version refused and named both windowing systems it had tried. Then 5.0, 5.1 and 5.2 exited with status 1, and 4.5 printed the same and never returned, having to be killed. Run on the one-card machine with its display taken away, and again on the two-card machine which had none — **word for word the same message and the same exit statuses both times**. Those two tested Linux conditions gave the same message and exit behaviour. This case could not arise on the Mac, which has a display, and so was not tried in 5.3.

**A disagreement between the machines, recorded and not resolved.** In 4.5, `-b -E help` printed its engine listing and stopped on the Mac; on the one-card Linux machine it printed nothing at all and hung until it was killed, tried three ways and hanging every time; on the two-card machine it printed its listing and then hung. Three machines, three results, and nothing chooses between them. The other three versions printed their listing and exited 0 everywhere, and 5.3 did the same on the Mac, listing `BLENDER_EEVEE`, `BLENDER_WORKBENCH` and `CYCLES`. The engine name was got another way on Linux and came back the same as the Mac's.

## 2. What must a computer have on it before Blender will render using its graphics cards?

**The same in all five:** the five technologies are CUDA, OptiX, HIP, oneAPI and Metal. CUDA, OptiX, HIP and oneAPI are stated as Windows and Linux only; Metal as macOS and Apple Silicon only. OptiX needs compute capability 5.0 in every version, and a driver figure that is the same in 4.5 to 5.2 and higher in 5.3 (the table below). HIP needs an AMD card of the RDNA1 architecture or newer in every version. oneAPI needs an Intel Arc card with the Xe HPG architecture in every version's manual. Metal is stated the same way in all five manuals, "macOS 13.0 or newer is required to support all features"; in 4.5 to 5.2 Cycles' own shipped file says macOS 12.2 instead — the same unreconciled disagreement, in the same place, in each of those four — and in 5.3 Cycles' file says 13.0 too. All five say the CUDA toolkit is normally not needed. All five say a copy of Blender built by a Linux distribution may leave Cycles graphics-card rendering out. All five manuals say EEVEE only renders on the graphics card and has no processor mode, and all five say headless rendering is not supported on headless Windows systems. 5.3's sources say nothing about what Workbench needs.

**One contradiction sits on that EEVEE sentence and nothing in this stage reconciles it.** **Frames 15** records the longest stop-waits it measured anywhere as coming from a rented Linux machine "with EEVEE drawn by its processor", where a frame took about ninety seconds. **Six of this project's machines that had a display had that display drawn in software rather than by a card**, which the equipment section of `Preparation/Blender Research/Method.md` says of each of them. **Nothing anywhere in this stage says whether such a machine counts as having a graphics card for EEVEE's purposes**, or what the manual's sentence means about one. It is written down here because Smoozy renders on rented Linux, where a display server — if there is one — may well be software-drawn, and because **Settings 6** leans on the same manual sentence. 5.3's manual carries the same sentence, and question 8, which asks about this case directly, was put to 5.3 alone; its answer is below. **This is not settled either way**; neither the manuals nor any run in this project is chosen over the other.

**Which technologies a machine offers is a fact about the computer, not about the version.** On the Mac, the technology row offered exactly two choices, None and Metal, in all four versions and in 5.3, and in 5.3 the setting refused any other value — `ONEAPI` was rejected as not among `('NONE', 'METAL')`. On the one-card Linux machine it offered five — None, CUDA, OptiX, HIP and oneAPI — and no Metal, in all four versions. Asked directly what it was built with, each Linux build reported CUDA, OptiX, HIP and oneAPI present and Metal absent, on every Linux machine, and each Mac build, 5.3's included, reported the opposite. None of that is a difference between versions and it must not be read as one.

The one-card Linux machine has an NVIDIA card and no AMD or Intel one, so choosing HIP or oneAPI there draws the text. **It is the only machine in this topic this could be seen on** — the only Linux machine here that both lacked an AMD card and had a screen. So what a running Blender puts on screen is known for two of the three makes in 4.5 to 5.2. The Intel figure it draws matches Cycles' own file in 4.5 and 5.2 — where those two sources give different numbers, so that disagreement is settled for what is displayed — and matches the manual in 5.0 and 5.1, where both sources give the same number anyway. The AMD figures are drawn as both sources give them, so nothing was in dispute there, and the 5.1-to-5.2 change is shown. **For NVIDIA nothing is settled, and cannot be on this machine**, because the compute-capability line is only drawn when no compatible card is found and this card is compatible.

**One more difference, in what Blender will say.** The Intel requirement line inside Cycles' own file reads "Requires Intel GPU with Xe-HPG architecture" in 4.5, 5.0 and 5.1, and "Requires Intel(R) Arc(TM) GPUs or newer Intel(R) Graphics" in 5.2 and 5.3. Observed in the supplied files for all five and on screen for 4.5–5.2.

**And one difference in the tick box beside it.** Under the requirement text sits a greyed HIP RT box, unticked in 4.5 and 5.0 and ticked in 5.1 and 5.2. Photographed in all four versions on the one-card Linux machine, the only machine in this topic whose window could be photographed with that text on it. **In 5.3 it was not seen**: the box has only ever been seen under the AMD and Intel requirement text, which the Mac never draws. A script on the Mac read 5.3's `use_hiprt` setting as on, which is a reading of the setting on another machine and not of the box.

**And one difference the hand tests settled.** EEVEE's engine name, as Blender itself gives it, is `BLENDER_EEVEE_NEXT` in 4.5 and `BLENDER_EEVEE` in 5.0, 5.1, 5.2 and 5.3. Run in all four earlier versions on the Mac and on the one-card Linux machine, with the same answer, and seen again on the two-card machine, where asking 4.5 for `BLENDER_EEVEE` produced `Error: engine not found` while the other three accepted it. 5.3's own engine listing on the Mac names `BLENDER_EEVEE`.

**And one 5.3 addition, by release note.** "Support for NVIDIA RTX Spark devices running Windows 11, including unified memory optimizations." Not tested here.

**What Blender does when the graphics driver itself is broken.** Every other answer here is about a technology having no card behind it. This is the other case — the cards are physically present and the **driver** is gone or wrong. It was run in all four versions on the two-card machine, whose driver was purged on purpose and then reinstalled without a restart so that the running kernel module and the new library disagreed. The machine was destroyed afterwards; repeating this needs another machine. It was never tried in 5.3.

- **With the driver removed**, every version was asked to render on the card through OptiX. Every version listed the processor as the only device it could see, rendered on it, wrote its picture and **exited 0**. 4.5 said nothing at all about it; 5.0, 5.1 and 5.2 each printed one line, `WARNING CUEW initialization failed: Error opening the library`.
- **With the driver mismatched**, the machine itself reported `Failed to initialize NVML: Driver/library version mismatch`. Every version printed `CUDA cuInit: Unknown CUDA error value`, listed only the processor, rendered on it, wrote its picture and **exited 0** — the same in all four but for the line shape. A restart is what mends this state; reinstalling does not.

**So in both broken states a render asked for on the card silently happened on the processor and the program reported success.** Nothing in the exit status separates a job that used the card from one that did not. Anything that needs to know has to read the run's own words, or ask Blender which devices it can see before starting.

**What the broken driver did not settle.** In both states Blender found no graphics device at all, which is the condition the "no compatible card" text is drawn under — but that machine had no display server, so no panel could be drawn on it and nothing was seen. The compute-capability disagreement therefore stands exactly where it did.

**5.3's Cycles file also covers a card whose driver is too old; whether this is new is not established.** Where a technology has cards but one card's driver is below the figure, 5.3's panel code marks that card's name " (Disabled)" and adds a line saying what it needs — "Requires NVIDIA driver version %s or newer", and likewise for AMD and Intel, or "Driver upgrade required" — and such a card is left out of the cards counted for use. That is Cycles' own 5.3 file, observed in the supplied file; no machine with such a card was available, so none of it was drawn or tested. Whether the earlier versions carry it is under question 6.

**Verdict: it differs.** The list of technologies and the shape of the requirement are identical everywhere. The numbers moved: what a NVIDIA card must be rose at 5.0, what an AMD driver must be rose at 5.0 on Windows and at 5.2 on Linux, what an Intel driver must be moved at nearly every version, the NVIDIA driver figure rose in 5.3 — to 575 in its manual and 580 in its Cycles file, for CUDA as well as OptiX — and the macOS figure in Cycles' Metal line moved to 13.0 in 5.3, all of that in the documents. 5.3 also adds RTX Spark support on Windows 11, by its release note. **What Blender draws on screen confirms the Intel figures and only the Linux half of the AMD ones, for 4.5 to 5.2**: the panel's text branches on the operating system, so the one machine here that could draw it drew the Linux lines and never the Windows ones, and nothing drew 5.3's. Anything that checks a machine against these figures has to check against the right version's figures.

**Not established for any version:** whether any of these figures is enforced against a real AMD or Intel card; how much graphics memory is needed; whether a card below the stated floor is hidden, greyed out, or offered and then fails — 5.3's preferences code marks it "(Disabled)" and leaves it out of the active count; what a render does with it is untested; anything at all about EEVEE's own card requirements, or Workbench's; and the CUDA compute-capability figures, for the reason above — settling those still needs a card whose compute capability falls between the two, or a machine with both a broken driver and a screen. Which of 5.3's two OptiX figures, 575 or 580, 5.3 enforces. Whether the Metal requirement Blender enforces is macOS 13.0 or macOS 12.2 is not established for 4.5 to 5.2: those four carry both figures, in the same two places, and it needs a Mac running macOS 12.x; in 5.3 both sources say 13.0, and that is untested too. **Whether the broken-driver results can be checked** is not established: they were run once, on a machine destroyed straight afterwards, and the result has no independent repeat on another machine. Which AMD cards can denoise on the card is not set out version by version here: the manual gives separate conditions for denoising on the card, and the findings that carry them word the AMD line differently — in 5.3, Radeon RX 6000 and newer on Linux and RX 7000 and newer on Windows — while 5.2's carry none.

**Settled by hand on every machine, and identically in all four versions:** a Cycles render on the graphics card, and an EEVEE render, both completed with no window open — on the Mac under Metal, and on the one-card Linux machine under both CUDA and OptiX, there with no display reachable. **On the two-card and four-card machines, with no display server, every available engine completed. The processor and card selections were established for Cycles.** The result was the same in all four versions. **5.3 did the same on the Mac under Metal**: Cycles on the card, named by its `Path tracing on:` report, EEVEE and Workbench, all with no window. Whether EEVEE really cannot render headless on Windows is untested everywhere, and none of the Linux results says anything about it.

**One thing worth knowing about how the work is split.** On the one-card Linux machine, in every graphics-card render in every version, denoising ran on the processor while path tracing ran on the card. 5.3 did the same on the Mac: path tracing on the Metal card, `Denoising on: Apple M1 Pro (CPU)`.

## 3. Does what a computer must have on it depend on how Blender was obtained and put there?

A copy built by a Linux distribution may not contain Cycles graphics-card rendering at all, for licensing or other reasons — the sharpest case, and stated in all five. The Windows installer needs administrator rights and the zip does not, in all five. Snap needs snap already installed in 4.5 to 5.2, and 5.3 gives Snap's install command; Steam needs the Steam client, in all five, and 5.3 also states that a Steam account is needed. macOS asks the person's approval the first time Blender is opened, in all five. Blender's archive cannot be unpacked with 7-zip and must be unpacked with TAR, in all five. The Microsoft Store copy is sandboxed and Blender knows it, through a read-only flag Blender carries, in all five. Where Blender's own files end up differs by route in all five. Advice to install a newer CUDA developer toolkit is given only to people who built Blender themselves, in all five. And in all five the Windows download must match the processor, x64 or arm64.

**Verdict: the same for the routes covered in all five.** The shared installation routes have the same documented conditions. The Python-module route is not established for every version.

**Not established for every version: Blender as a Python module.** 5.3's findings describe one more route, the `bpy` module from PIP, which is not on Blender's own download page. It works with one matching Python version and ignores the user's startup file and preferences, as if `--factory-startup` were given. **Inferred in 5.3's findings:** that matching Python must be installed, and saved card choices are not applied unless preferences are loaded on purpose. **Documented:** Blender's command-line arguments, `--cycles-device` among them, do not reach it; it writes no crash log and has no Control-C handling; and other Python modules may use the graphics card in a way that keeps Blender from it. No earlier version's findings record this route at all. That is a silence, not a difference, and whether any of it holds for 4.5 to 5.2 is not established.

**The official Linux download, observed in 4.5–5.2.** The official Linux x64 build taken from Blender's own download server reports itself as carrying CUDA, OptiX, HIP and oneAPI, and not Metal. So the sharpest case in the answer above — a copy that leaves Cycles graphics-card rendering out — is not what the official download gives. That is the only route any machine could test: the Mac has only the disk image, and no other copy of Blender was ever put on a rented machine. The one thing that *was* installed and removed on a rented machine was its graphics driver, on purpose, and that is question 2's answer rather than this one's. **5.3 was read on the Mac alone**, from one copy whose route the findings do not record: it carries Metal and no other card technology, with Cycles and OSL built in.

**A note, not a difference.** Each version's manual spells out slightly different incidental details — 5.2, for instance, separately mentions that registering Blender for all users needs raised privileges. Nothing any version says contradicts anything another says. A detail one manual mentions and another does not is a difference in the writing, not in Blender.

**A second note, marked as a difference and small.** What each Linux build reports it was built with is not the same tuple in all four versions. Asked directly, 4.5 and 5.2 answer `(True, True, True, False, True, True)` and 5.0 and 5.1 answer `(True, True, True, False, True, False)`. The first five values are CUDA, OptiX, HIP, Metal and oneAPI, and they are identical everywhere — the official Linux build carries the four its operating system supports and no Metal. Cycles' own file names the sixth value as HIP ray tracing, and it reads true in 4.5 and 5.2 and false in 5.0 and 5.1. The same split came back on all three Linux machines. What the sixth means for a render is not established, and there was never an AMD card to find out with. **No 5.3 Linux build was read.** 5.3's Mac build answers `(False, False, False, True, False, False)`, which is a reading on the other operating system and stands beside nothing above.

**Not established for any version:** whether the hardware requirements themselves change with the route (no version says they do, and none says they do not); which distributions leave Cycles graphics-card rendering out; whether the Snap, Steam or Microsoft Store copies can render on graphics cards; what the Microsoft Store sandbox actually restricts; what building Blender from source needs; and whether the Python module from PIP can render on graphics cards at all, or with which technologies.

## 4. Does Blender say anything about what is missing when it will not start, or when it will not render?

**The same in all five.** The manual names one startup error and gives its meaning — "Unsupported Graphics Driver Error", meaning the card and driver do not reach OpenGL 3.3 — but never prints its literal text. The manual warns that messages go to a console you may not see, and tells you to start Blender from a command line so you can. In 4.5 to 5.2 exactly two startup messages are quoted by name, `found bundled python: {DIR}` and `Read prefs: {DIR}/userpref.blend`, and the Python one is described as diagnostic by its absence; For 5.3 the first is documented with the same description and the second was observed in its output. Blender writes a crash file, named and placed differently on each of the three operating systems, in all five. The manual names the same four render-time errors in all five: out of memory, the NVIDIA display-driver timeout, the unsupported GNU version, and the CUDA kernel-compilation failure. Cycles' own shipped file carries the same "No compatible GPUs found for Cycles" line, followed by a per-technology "Requires…" line, in all five.

**The same in all four, and settled by hand on the Mac and on Linux — and in 5.3 on the Mac.** Asked for a technology the machine does not have, all four exited 1, wrote no image, and printed a message naming the fault — "Found no Cycles device of the specified type". On the one-card Linux machine that covered `METAL` (not built in there), `HIP` and `ONEAPI` (built in, but no card), and the message was the same for all three: **a technology built in but with no card says exactly what a technology not built in at all says.** Given a value that is not a device name, all four exited 1, wrote no image, and printed "NOTADEVICE is not a valid Cycles device." And the quiet cases are quiet in all four, on every machine: asked to render on graphics cards with every card switched off, with the technology set to None, and — on Linux — with the technology set to one the machine has no card for, all four exited 0, wrote the image, rendered on the processor, and printed nothing at all naming a missing or unusable device. **5.3 did all of that on the Mac**: `OPTIX`, `CUDA`, `HIP` and `ONEAPI`, none of them built into the Mac's copy, each exited 1 with `ERROR Found no Cycles device of the specified type` and no picture; `NOTADEVICE` exited 1 with `ERROR NOTADEVICE is not a valid Cycles device.`; and every card saved off, the technology saved as None, the never-used settings folder and `--factory-startup` each rendered on the processor at exit 0 and said nothing about it — the None run's whole informational log, searched, held no line saying so. The built-in-but-no-card case cannot arise on the Mac and was not tried in 5.3.

**The no-compatible-card message, observed in 4.5 to 5.2.** The "No compatible GPUs found for Cycles" text was never reached on the Mac, in any version, 5.3 included. On the one-card Linux machine it was reached both ways, in all four versions. **In the preferences panel it is drawn**, with its "Requires…" lines under it, photographed in all four. **In a windowless render it never appears at all**: with the technology saved as one this machine has no card for, the phrase was searched for in the whole output of every run in every version and found nought times, and no "Requires…" line appeared either. The render simply fell back to the processor and said nothing. So that text lives in the panel and nowhere else — which means a program watching Blender's output cannot learn from it that no compatible card was found. **Inferred for 5.3:** the message belongs only to the panel, because its drawing code is its only caller in the supplied files. No 5.3 run could reach the no-card case.

**Four more silences, and they are the practical heart of this answer.** Each was found on a Linux machine, and each says below which versions it was run in. A fifth was found in 5.3 on the Mac.

1. **At factory settings, with no technology yet chosen, a scene asking for the graphics card renders on the processor and Blender says nothing.** Every card is ticked at factory settings, but a technology is a separate choice, and **what it starts at is a fact about the machine rather than about Blender** — it read None on the four-card Linux machine, and **Add-ons 3** reads `METAL` on the Creator's Mac in all four versions from a fresh settings folder, as 5.3 did. So it has to be read on the machine in hand and never assumed. Run in all four versions on the four-card machine, with a search of both output streams for "no compatible", "no device" and "falling back" matching nothing. In those factory-settings Linux runs, leaving the technology unchosen gave the processor without a warning.
2. **With the graphics driver removed or mismatched**, the render happens on the processor and the program exits 0 — in every version tried. 4.5 says nothing at all; 5.0, 5.1 and 5.2 print one line. Run in all four on the two-card machine; not in 5.3. Question 2 has the whole of it.
3. **With the cards hidden from Blender** but the preferences still naming them, the render falls to the processor with no error and exits 0. Asked for the cards outright in the same state, it exits 1 and says so. **Run in 4.5 only**, on the two-card machine, so the other four versions are untested for this one.
4. **When the card's memory is filled by the render's own scene**, Blender says nothing, exits 0, writes the picture, and takes about ten times longer for twice the data. Run in all four versions on the four-card machine, whose 16 GB cards and 197 GB of system memory made it possible for the first time; not in 5.3. That run belongs to the topic *Reports* rather than this one, and it is named here because it is the fourth silence and a reader of this document would otherwise never meet it.
5. **In 5.3 on the Mac, with the technology already at Metal and a settings folder nothing had ever been saved into, a scene asking for the card rendered on the processor and said nothing.** The card list was empty because nothing had yet filled it (question 5); once one run had refreshed it and saved the preferences, the same render went to the card. Whether 4.5 to 5.2 do the same on the Mac from a never-used settings folder is not recorded.

**What all of them have in common is that the exit status is 0 and the picture is written.** Nothing Blender returns separates a render that used the graphics card from one that quietly did not. In 5.3 on the Mac the only line that named where a render ran was the `Path tracing on:` report Cycles prints with `--debug-cycles`; the `Added device` line appeared whether the card was then used or not.

**Where they part company — the shape of the lines Blender prints.** In 4.5, Blender's output lines are plain: `Error: Found no Cycles device of the specified type`, and progress lines of the form `Fra:1 Mem:74.69M (Peak 169.62M) | Time:00:39.15 | … | Sample 16/16`. In 5.0, 5.1 and 5.2 the same information arrives stamped with an elapsed time and a category: `00:01.263  reports          | ERROR Found no Cycles device of the specified type`. This was seen in every test that produced output, in all four versions, on the Mac and on all three Linux machines; 5.0's release notes separately describe a rebuilt logging system. **5.3 prints the newer shape**, on the Mac: `00:00.346  reports          | ERROR Found no Cycles device of the specified type`. **Every run behind that started the render from the command line, and the route matters:** started the other way, by calling the render operator from inside a script, 5.0, 5.1 and 5.2 print no progress line at all, while 4.5 prints its plain lines under both routes — settled under **Reports 9**; the one script-started 5.3 render on the Mac quoted in full printed no progress line either, only its `Saved:` line. **What becomes of the categorised `ERROR` line under that route was never captured**: every run behind **Reports 9** wrote its picture, so none of them could have shown an error line at all. What **is** settled about a failure on that route is that it is raised back into the script itself, carrying the message — **Reports 2**. So anything reading a background render's output has to know both which version it is reading and how the render was started.

**The marker for a graphics-card render, on macOS.** 4.5, 5.0 and 5.1 finish with `(Using optimized kernels)`; 5.2 finishes with `(1 kernels to optimize)`, and its own record shows `(Using optimized kernels)` at sample 0 of the same run. Settled by tests run in all four on the Mac. **Those are Metal's markers**: on the Linux machines they did not appear at all, in any version, and the line that names the device there is a different one. So this is a real version difference in what a Metal render prints, and not a difference to expect anywhere else. **5.3 prints the `kernels to optimize` wording** — `(7 kernels to optimize)` on its first sample line — and what its last line carries is not recorded. And in 5.3 the memory figure on that line is not a card marker either: a render the `Path tracing on:` report names as running on the card and the processor together ended on `Mem: 18M`, the figure the processor-only renders printed, not the `1410M` of the card-only ones.

**A line about AMD's missing library.** On the one-card Linux machine, 5.0, 5.1 and 5.2 each print `WARNING HIPEW initialization failed: Error opening HIP dynamic library`, and 4.5 prints nothing of the kind in its ordinary output. The same split was seen again on the two-card machine and on the four-card machine, which have no AMD card either. **The line appears whenever something makes Cycles look at its device list** — asking for HIP by the saved preference or the launch argument is one way, and writing the system-information file, a script that sets the device, and a plain refresh of the device list are others. It does **not** appear in an ordinary render at factory settings, in any version. And 4.5 prints the same message at debug level rather than as a warning, so what differs between the versions is **how loudly it is said, not whether**. It is a Linux line, and 5.3 was not tried there.

**An extra line after a bad device name, and it is not a version marker.** Given a value that is not a device name at all, every version refuses and exits 1. In that test, on the one-card Linux machine, 5.0, 5.1 and 5.2 then print `Error: Not freed memory blocks: 1, total unfreed memory 0.000004 MB` and 4.5 prints nothing further; the refused window on the same machine splits the same way. 5.3 printed the same line after `NOTADEVICE` on the Mac. Outside that test the line comes and goes in every version: 4.5 prints it elsewhere, and the newer three sometimes do not. **Nothing reading Blender's output may treat the line's presence or absence as telling it which version is running**, and it is in no list of differences between versions.

**Verdict: it differs.** What Blender says is the same everywhere it was tried. How it says it is not: 4.5 prints plain lines, and 5.0, 5.1, 5.2 and 5.3 print timestamped, categorised ones, with three smaller printed differences beside that — the Metal marker, the HIP line's loudness, and the driver-removed warning — and in the last of those, 4.5's difference is that it says nothing where the others say something. 5.3 says what 5.0 to 5.2 say, in their shape, as far as the Mac reaches.

**Observed crash-file names and locations on Linux and macOS.** On the one-card Linux machine, forcing a crash gave exit status 139 and one printed line in all four versions: the file went into `/tmp`, named after the loaded blend-file when there was one and `blender.crash.txt` when there was not. It did not sit beside the blend-file. **On the Mac this rule was observed in 5.3, with a loaded-file control in 5.2.2.** In 5.3, a crash forced with no window exited 139 and printed `Writing:` with the file's place: Blender's temporary folder, the file named after the loaded blend-file — `crashme.crash.txt` — and `blender.crash.txt` with no file loaded. 5.2.2, run the same way on the same Mac the same day, also named it after the loaded file. The original 4.5–5.2 Mac runs record `blender.crash.txt` during add-on crashes; whether a blend-file was loaded for each sighting is not established. Those runs do not settle their loaded-file naming rule. With `--disable-crash-handler`, 5.3 printed no `Writing:` line and wrote no crash file. **macOS's own crash reporter also recorded every 5.3 crash**, the one with the handler switched off included, writing a `Blender-…ips` file into `~/Library/Logs/DiagnosticReports`, and its Problem Reporter started in the same second (question 7). Windows is untested. No version difference is established here; the older Mac naming rule remains open.

**And one 5.3 observation about scripts.** On the Mac, a script given with `--python-expr` that raised a Python error left 5.3 exiting with status 0. `--python-exit-code`, which sets the exit status for an error in a script run from the command line, is documented in 5.1's, 5.2's and 5.3's findings. What the earlier versions' exit status was after a script's error is not set out here.

**A note, marked as not established.** 5.0's findings quote the manual saying that with CUDA, OptiX, HIP and Metal, a full graphics card will make Blender fall back to system memory automatically. No other version's findings record that sentence. That is a silence in four sets of findings, not evidence that four versions behave differently, and it is not in either difference list. A release note of 4.5's likewise says Blender on Windows now shows a crash popup with recovery options; the others are silent on it, and none of it could be tested.

**Not established for any version:** the literal words Blender prints when it will not start; whether any of these messages carries a code a program could match on; the "Error: Out of memory" message, which was never reached even with a card filled, because that machine had 197 GB of system memory to spill into, so what Blender prints when there is nowhere left to spill to is still unknown. **One of these is now partly answered:** what Blender says when the driver is broken is known for 4.5 to 5.2 — nothing in 4.5, one line in the other three — but what it says when a card is present and supported and only its *driver version* is too old is still unknown, no card below any stated driver floor having been available; 5.3's file says on paper what its panel would draw (question 2). The exit statuses are known only for the cases tested above. And everything Windows-side is untested: whether the console is hidden until it is switched on, what the helper scripts produce, where a crash file lands, and the display-driver timeout error.

**One thing to keep out of the record as a difference.** Several runs on the Mac ended in a crash, in more than one version. The crash files named a background thread in a third-party add-on installed on that Mac, not anything to do with graphics devices, and re-running the same command completed normally each time. That is a property of one person's installation. The 5.3 runs each used a settings folder of their own and met no such crash.

## 5. How is it decided which of a computer's graphics cards a render uses, can more than one card be used for the same render, and how is that decided from outside Blender's own interface?

**How it is decided — the same in all five.** Three settings, and all three must line up. One technology is chosen for the whole of Blender in the preferences, and it is a single choice, not a set. Each card Blender has found carries its own on-or-off switch, saved in the preferences; a graphics card starts switched on and the processor starts switched off. And each scene separately asks for the processor or for graphics cards, with the processor as the starting value. In all five, only cards matching the chosen technology are offered, plus the processor. In all five, the list of cards is deliberately not rebuilt when Blender starts, because some drivers can crash when asked.

**Three differences in the manuals, without a matching behaviour difference.** 4.5's GPU-rendering instructions say to pick a technology and set each scene, omitting the individual-card enabling step that 5.0–5.3 include. The switches themselves were read, written and honoured in 4.5–5.2 on the Mac and Linux machines, and in 5.3 on the Mac. The scene's device choice has no full render-settings entry in 4.5's manual and has one in 5.0–5.3; the setting exists in all five and starts at CPU. Finally, 4.5's System-page picture has the Cycles panel collapsed, while 5.0–5.3 show None, CUDA and HIP on the pictured machine. The tested Mac instead offers None and Metal in all five; the Linux machine offers None, CUDA, OptiX, HIP and oneAPI in 4.5–5.2. The different screenshots do not establish a version change in available technologies.

**Which technology it starts at is a fact about the computer.** In all four versions it starts as Metal on the Mac and as None on every Linux machine. 5.3's Cycles file says the same — Metal on an Apple-silicon Mac and None everywhere else — and 5.3 started at Metal on the Mac; no 5.3 Linux machine was read.

**And one thing about the Creator's own installation, which must not be read as a difference.** In 5.0, the saved preferences on the Mac had the graphics card switched off, where 4.5, 5.1 and 5.2 had it on. That is the state of one person's settings file. It says nothing about how the four versions behave.

**And that starting value is the most expensive silence in this topic.** At factory settings on a Linux machine, **every graphics card is already ticked** — read after a refresh, the list being empty before one, as the entry below on the empty list sets out — and the technology is **not chosen**. A scene whose own setting asks for graphics cards then renders on the processor, and Blender says nothing whatever about it. Run in all four versions on the four-card machine, with a search of both output streams turning up no warning, no fallback notice, nothing. So "the cards are all switched on at factory settings" is true of the ticks and false of the render. Anything that rents a machine for its cards has to choose a technology itself and check what the render actually used. **On the Mac, 5.3 also fell back silently**: with the technology already at Metal, a never-used settings folder rendered a graphics-card scene on the processor, silently, because the card list was still empty (question 4).

**More than one card — the same in all five as documented, and tested twice in 4.5 to 5.2.** Yes for Cycles, stated outright in every version's manual. Memory is not pooled, except on NVIDIA cards joined by NVLink, where "Distribute Memory Across Devices" can be switched on; that setting starts off in all five. The processor can join the cards. No for EEVEE, in all five: EEVEE cannot use more than one card. It renders perfectly well on a machine that has several — it did so on the two-card and four-card machines in all four versions — but only one of them is used, and no route was found to ask it which. **5.3 was never run with more than one graphics device**, so none of what follows is tested for it. **What the tests showed, on the two-card machine and again on the four-card machine.** Each entry says which versions it was run in, because two of them were watched card by card in one version only:

- **Every card is ticked at factory settings, and each card is listed once per technology.** Two cards gave five entries — each card under CUDA and under OptiX, plus the processor. Four cards gave nine entries the same way. The processor starts unticked. Run in all four versions on both machines, and the two machines agree. **Every one of those readings was taken after `refresh_devices()` was called.** On a factory-fresh Blender the card list is empty until something fills it — a refresh asked for, the preferences panel drawn, or a preferences file saved earlier — so a machine asked which cards Blender can see, before anything else, answers none. See the note below on the empty list.
- **A render uses every ticked card at once, without being asked.** With a technology chosen and the ticks left exactly as they came, both cards, and then all four, were named by Blender one to a line — **in all four versions on both machines**. Watching each card separately doing the work was **run in 4.5 only**, on each machine: around 98 % use on every card for the whole render, each holding its own copy of the scene. The two machines agree.
- **More cards make it faster, but not proportionally.** On the four-card machine, with nothing else running, forty-eight timed renders of one scene gave about **1.9 times** faster per doubling of the cards on the render itself, and about **1.7 times** on the whole run, where loading the file and building the scene do not shrink at all. One card to four was about 3.6 on the render and about 2.9 on the whole run — **on a scene that fits on one card. It does not hold for one that does not.** *Reports 6*'s 128-picture scene, on this same machine in Blender 4.5, took 03:28.53 on one card and 13:11.85 on four — about 3.8 times **slower** — with every one of the four cards filled to the same 15.6 GB a single card reached. One run each way, in 4.5 alone. Nothing in either run says which case a scene is in; the render succeeds, writes its picture and exits 0 either way. Every one of the four-card figures was reproduced independently on the same machine to within a fraction of a per cent, in all four versions. **The four cards are as fast as each other, within about 2 %.** *(No figure here is set beside anything from the two-card machine: that machine had different, faster cards and a different scene, and both machines are gone.)*
- **Distribute Memory Across Devices is offered on cards that are not joined by NVLink, and does nothing there.** The setting exists in all four versions, is a yes-or-no setting, starts off, and can be turned on, saved and read back with two unlinked cards and with four — all of that in all four versions on both machines. **The measurement of what it changes was run in 4.5 only**, on each machine, **and on scenes that used about a seventh of a card** — 1,710 to 2,190 MiB of 16 GB on the four-card machine, 3,557 MiB of 24 GB on the two-card one. The setting's own description says it is for making room for large scenes to fit. The one scene in this research that did fill a card, under *Reports 6*, was never run with it on, so nothing here says what it does under the condition it names. With it on, each card still held as much as it held with the setting off and as much as a card working alone held, Blender's own memory figure was identical to the hundredth of a megabyte, and **Blender said nothing about the setting at all**. The two machines agree, and no other version was measured. What it does when cards really are linked is still unknown; no machine ever had an NVLink pair. In 5.3 on the Mac, with its one device, the setting exists, starts off and describes itself as making room for large scenes by spreading memory across linked cards, and its box was not drawn in the panel at all.

The processor can join the cards, and on the one-card Linux machine the report named both, giving the processor eleven threads alongside the card where it had twelve alone. **5.3 did the same on the Mac**: with `-- --cycles-device METAL+CPU` the report named the Metal card and the processor, the processor with seven threads where it had eight alone.

**And one line in that report differs between the versions.** From 5.1, the report that names the devices puts a `Hardware Ray-Tracing: Off` line under each one; 4.5 and 5.0 do not. Seen in all four versions on the one-card Linux machine, and again in all four on the two-card and four-card machines, where it appears under every card named. All the cards were NVIDIA. **5.3 prints it too, on the Mac**, under the Metal card and under the processor. That is a 5.3 reading on another machine from the rest, and it agrees with *from 5.1* without settling 5.3 on Linux.

**From outside — the same in all five.** One command-line option, `--cycles-device`, taking exactly the same six values in every version — CPU, CUDA, OPTIX, HIP, ONEAPI, METAL — with `+CPU` available to add the processor, and only read when a bare `--` comes first. Its help text is worded identically in 4.5 to 5.2, and 5.3's manual and Cycles' own file give the same six values and the same `+CPU`. In all five, that option names a technology and has no way of naming one card out of several. In all five, individual cards are reachable only through the saved preferences file or through Python.

**And what the option does when there is a choice of cards is now settled, on two machines, for 4.5 to 5.2.** It does not merely re-enable the one card the preferences had switched off — **it takes every card of that technology, whatever the preferences said**. With one card of four ticked and the option given, all four were named and all four were watched doing the work, and the run took a four-card time instead of a one-card one. With every card unticked and the option given, all four were taken again. The option writes nothing back: the saved preferences were unchanged afterwards. Run in all four versions on the two-card machine and again on the four-card machine, and the two agree. **5.3 was tried in the one-card form only**: on the Mac, with every device saved off, `-- --cycles-device METAL` rendered on the card, and the saved preferences read back unchanged afterwards. Which of several cards 5.3's option takes is untried.

**Settled by hand on the Mac and on Linux, and identically in all four versions — and in 5.3 on the Mac.** The add-on key needed to reach Cycles' preferences from a script — which no version's documentation gives — came back as the literal string `cycles` on both, and in 5.3. The per-card switches were read, written and saved with no window open. A saved preferences file was honoured by a windowless render: switching every card off changed what the render did. The launch option displaced both the saved switches and a scene saved with its own setting on the processor. `--factory-startup` discarded the saved per-card switches — in 5.3, with the card saved ticked, the same render went to the processor with it and to the card without it. The stored identifier held steady across every run of the day on every machine: `METAL_Apple M1 Pro (GPU - 14 cores)` and `CPU` on the Mac, in 5.3 as well, and on Linux the technology, the card's name and its place on the bus, so that two cards and four cards each carry their own distinct identifier.

**Verdict: the same everywhere.** Three settings decide it, more than one card is allowed for Cycles and not for EEVEE, and from outside the technology can be forced but individual cards cannot — in all five versions as documented; as tested, in 4.5 to 5.2 on the Mac and on three different Linux machines with one, two and four cards, and in 5.3 on the Mac with one.

**A change made by a script inside the render's own run — observed in 5.3 and 5.2.2 on the Mac.** On the one-card Linux machine it took effect in all four earlier versions: the report named exactly the devices the script had asked for, whether switched on, switched off or set to None. On the Mac under macOS 26.6.2, both 5.3 and 5.2.2 also took all three changes, without changing the saved preferences. With every device switched on the report named the card and processor together.

**The original Mac results remain unresolved for 4.5, 5.0, 5.1 and 5.2 under macOS 26.5.2.** They showed no graphics-card marker, using kernel text and memory rather than the device report. In the 5.3 combined card-and-processor run, that memory figure was the processor's figure, so it cannot by itself exclude card use. This makes a missed card possible; it does not establish what happened in those original runs. The later 5.2.2 result does not settle a run under an earlier point release and operating system. No version difference follows.

**One thing about several cards that is recorded and read into nothing.** With four cards, Blender moved work between them repeatedly during a single render; with two, it did not move it at all. The count of moves changes from one run to the next on the same machine in the same version, so **it is not any version's figure and it is not a version difference**. It is written down here only so nobody meets it cold and reads it as one.

**And how far a card can be taken out of use, tried in 4.5 only, on the two-card machine.** A card cannot be unplugged from a machine reached over a network, so what was tried is what the machine's own tools offer. Hiding a card before a render works: the render names one card and takes a one-card time. Hiding every card sends the render to the processor at exit 0 with no error, unless the cards are asked for outright, which exits 1. Putting a card out of service before a render works and the render uses the rest. **During a running render nothing safe took a card away**: a reset was refused outright while the card was in use, and the one command that was accepted removed the card from the system's own listing while the render carried on to its usual two-card time and wrote its image. Only 4.5 was tried, so the other four versions are untested for this.

**The empty list, and it is settled on Linux — and in 5.3 on the Mac.** On the one-card Linux machine the windowless runs came back **empty in all four versions** with an untouched settings folder, and empty again in all four when started with `--factory-startup`, filling only once a refresh had been asked for or preferences had been saved. So the card list is not there until something fills it, and a machine asked which cards Blender can see before anything else answers none. **5.3 on the Mac, from never-used settings folders, did the same**: empty with no window and empty with a window until a refresh, already filled at start once a refresh had been saved, and empty again under `--factory-startup` whatever was saved. A refresh listed the card ticked and the processor unticked.

**A note beside it, marked as not established.** Inside Blender's own window on the Mac, the stored list came back empty before a refresh was asked for in 4.5, 5.0 and 5.1, and already filled in in 5.2. With no window open, all four came back already filled in, and all four came back empty under `--factory-startup`. Drawing the preferences panel can fill the list, as can saving it. That leaves the different starting states unexplained; they do not establish a version difference. 5.3, run from never-used settings folders, came back empty both ways, which fits that reading; it does not re-run the earlier versions. It is recorded here and appears in neither difference list.

**A second note, also not a difference between these versions.** 4.5's release notes warn that a machine with more than one **Intel** graphics card may crash when rendering, and say a fix was already in 5.0 and planned for 4.5.1. The 4.5 tested here was 4.5.12, well past that. Nothing in the findings establishes that any version still carries the fault, and no Intel card of any kind was ever available. Machines with two and four **NVIDIA** cards were tested and nothing of the sort happened, but that is a different make and says nothing about this warning.

**Not established for any version:** whether cards of two different makes can ever be used together; whether a slow card holds a fast one back — every several-card machine had cards of one model, within about 2 % of each other; what Distribute Memory Across Devices does when the cards **are** joined by NVLink, and whether its box is drawn or greyed on a machine with several cards — that one needs eyes on a window, and no several-card machine had a screen; whether a card's stored identifier survives a driver update or being moved — the two-card machine's driver was purged and put back, but no one recorded whether the identifiers survived it; how EEVEE picks its one card on a machine with several — EEVEE rendered on both several-card machines, but no route was found to ask it which card it used. **And every several-card result above, for 5.3.**

**And one thing that is a fact about the computer rather than about Blender.** Control over which card draws Blender's own interface does not exist on the Mac at all: the System preferences page there carries no Display Graphics section and no backend or device control, in all four versions and in 5.3, and the tested 5.3 Mac build reports that Vulkan is not built in. In 5.3 the setting behind it read `METAL` with a window, while listing only `AUTO` among its choices; 5.3's manual documents the control as "Device Vulkan", for "display drawing operations" on systems with several cards. On the one-card Linux machine that section is there in all four versions, offering a Backend control; with the backend saved as Vulkan and Blender restarted, a Device control appears beside it. On that one-card machine the Device control offered only `Auto`, and the setting behind it held only that one value. **What it offers with more than one card has never been seen**: it needs a window, and both of this topic's several-card machines had no display server. It remains untried on a machine with several cards and a display server. The Linux page also carries an Operating System Settings section, with buttons to register and unregister Blender for blend-files, which the Mac's page has not. **And one version difference sits inside it**: with the Vulkan backend saved, 4.5 and 5.0 draw a "Current Vulkan backend limitations" note and 5.1 and 5.2 do not, photographed in all four versions on the one-card Linux machine, the only machine in this topic that had those controls **and** a screen to draw them on. 5.3 was not seen there.

**The Mac's own Cycles panel, in 5.2 and 5.3.** The same in both: two buttons, None and Metal, with Metal selected; the card ticked and the processor unticked; Kernel Optimization at Full and MetalRT at Auto, which Linux's panel has not; unticking the card greys MetalRT; choosing None leaves the row alone. 5.3's panel was photographed by Blender's own screenshot command on the Mac, and nothing in it carried " (Disabled)" or " (Unoptimized Performance)". **One reading is not matched**: in 5.3's picture, unticking the card also greyed the processor's line, where the 5.2 record, taken by eye, says nothing else changed. That is two different ways of looking on two different days and is not established as a difference.

## 6. Can Blender be asked which graphics cards it can see and can use?

**The same in all five.** Blender writes a system-information file on request, from the Help menu or from a script, and the manual of every version says it has a GPU section and a Cycles section; 5.3's graphics troubleshooting pages still call the graphics part "the OpenGL section". Cycles' own shipped files carry the same set of questions in all five — refresh the list, read the list, count the graphics cards in use, ask whether any is active, ask whether more than one is. In all five, the older way of asking has been hollowed out and now returns nothing. In all five, asking Cycles' compiled part directly for a list carries a warning in Cycles' own comments that it can crash Blender on some drivers. And in all five, none of this appears in Blender's published Python documentation as a page of its own — it exists only inside the add-on's own files; 5.3's API change log names one new member, `has_dlss_gpu_devices`, and nothing more.

**Settled by hand on the Mac and on Linux, and identically in all four versions.** The system-information file had the same headings in the same order in all four on each machine, and on no machine was one of them `OpenGL` — so no version's own report names an OpenGL version at all. Written with no window, all four replaced the whole GPU section with the single line `GPU: missing, background mode`, and dropped the drawing-limit sections. Writing it from a script worked with no window in all four, **and worked on a machine with no display server at all**, returning `{'FINISHED'}` and writing its file in every version. Cycles' own list answered with no window in all four, each entry an eight-field record, with the no-argument form of the direct call refused in all four in the same words. The direct call did not crash Blender on any machine, in any version, despite the warning in Cycles' own comments.

**5.3, on the Mac, did the same in every part but one.** Its system-information file carried the same main headings, in the same order, as 5.2's on the Mac with no `OpenGL` heading. Written by a script with no window it returned `{'FINISHED'}`, its graphics part was the one line `GPU: missing, background mode`, and the drawing-limit sections were gone; **calling `gpu.init()` first did not fill that section in** — the two files differed only in the temporary folder's name. Written with the window open, it carried the `GPU` section and the drawing limits. Cycles' own list answered with no window, the no-argument form refused in the same words, `TypeError: function takes exactly 1 argument (0 given)`, and the direct call did not crash. **The one part that differs: each entry is a ten-value record in 5.3.** 5.2.2 on the same Mac, asked by the same script the same day, gave eight. Cycles' own 5.3 file reads the ninth value as whether the card meets its driver requirement and names the tenth among its denoiser and DLSS flags; 5.2's findings name all eight of 5.2's values and neither is among them.

**What the report says depends on the machine, not on the version.** On the Mac the Cycles section is short — in 5.3, `CPU device capabilities:`, then `Metal device capabilities:`, `Number of devices: 1` and the card's name. On the one-card Linux machine it runs to about ninety lines of the NVIDIA card's own capabilities, and it names the card's compute capability outright — which is what the card has, not what Blender demands. On every machine the section covers only the technology whose cards were found: with OptiX saved, the heading was still `CUDA device capabilities`. With two cards, the file listed the card twice under that one heading. Identical in all four versions on each machine.

**And how the asking routes behave with several cards, on two machines that agreed.** Every route named every card — the Cycles lists, the count, and the system-information file. **The count of graphics cards returned 2 on the two-card machine and 4 on the four-card machine**, in all four versions. And one thing worth knowing because its name misleads: the question that asks whether Blender has "multiple devices" **came back false with two cards ticked and false again with four**, in all four versions on both machines. Whatever that name means, it is not the number of cards. 5.3 was asked only with its one card, which counted 1 and answered false.

**And one thing settled on the one-card Linux machine, in all four versions.** *What Blender was built with* and *what it can find right now* are two different questions, and Blender answers them separately. Hiding the card for one command left the built-with answer unchanged while both card lists came back holding the processor alone, and a render then asked for that technology exited 1 with the ordinary "found no device" message. In 5.3 on the Mac, asking for a technology the copy does not carry returned the processor alone and no error, as in the earlier versions.

**Where they part company — asking the graphics module.**

- **4.5, 5.0 and 5.1** — `gpu.platform.devices_get()` does not exist. Asking for it raises an error saying the module has no such thing. `gpu.init()` does not exist either. With no window open, the whole graphics module refuses to answer: "GPU functions for drawing are not available in background mode."
- **5.2 and 5.3** — `gpu.init()` exists and succeeds with no window open, and after it the whole graphics module answers, including `gpu.platform.devices_get()`, which returned one entry on each machine. Without calling it first, 5.2 and 5.3 give a different refusal from the other three: it names `gpu.init` and tells you to use it. In 5.3 on the Mac, `gpu.init()` returned `None`, and after it the module answered `METAL APPLE Apple M1 Pro Metal API 1.2` and one device, `(0, 'Metal API', 'METAL')`; with a window open it answered the same without being asked to start.

That is a test run in all four earlier versions on the Mac and on the one-card Linux machine, coming back the same way on each, and in 5.3 on the Mac; 5.2's release notes separately record `gpu.init()` as added.

**Where they part company — asking from the command line, new in 5.2.** `--gpu-device help` printed a numbered list of the cards Blender can draw with — index, device identifier and name — and exited. It exists in 5.2 and 5.3; in 4.5 the argument is not recognised. Run in all four versions on the one-card Linux machine, and again on the **two-card machine, which has no display server of any kind**, where 5.2 listed both cards with an index apiece. It names the card Blender *draws* with rather than the card Cycles renders on, so it is a second, separate list and not another way of reading the first — and it is the only route that ever gave each card a plain number. It was not run on the four-card machine. **In 5.3 on the Mac it names no card**: it printed its heading and `(Vulkan backend not built)`, and exited 0.

**One smaller difference, read out of Cycles' own files in all five.** The field on each card's stored record that says whether its kernels are optimised is called `optimized` in 4.5 and `is_optimized` in 5.0, 5.1, 5.2 and 5.3. Anything reading it by name has to know which version it is talking to.

**And one difference in what the report says, from the Mac's tests.** The graphics drawing limits in the system-information file read 128 image units in 4.5, 5.0 and 5.1, and 64 in 5.2 and 5.3, on the same machine. This is a reported drawing limit on this Mac; it does not identify cards usable by Cycles. It could not be repeated on any Linux machine, whose windowless files drop those sections.

**Verdict: it differs.** Every version can be asked. Cycles' listing and counts answered in 4.5–5.2 with one, two and four cards, and in 5.3 with the Mac's one device. The longer 5.3 record is a real difference on that Mac. What has changed is the graphics-module route and the command line — 5.2 and 5.3 can be asked with no window open and can be asked for a list of devices at all, and 5.2 answered from a terminal on a machine with no display server, where 4.5, 5.0 and 5.1 can do none of those; 5.3 was never tried on such a machine — and, in 5.3, the record Cycles keeps for each card, which grew from eight values to ten.

**Not established for any version:** whether the graphics module's device list names cards Cycles could render on or only cards the drawing side knows about — the two routes gave different names for the same hardware, and the machine that could be asked both ways had one card, as 5.3's Mac did; whether the stored identifier is stable across driver updates or a card being moved; whether the crash warning in Cycles' own comments is still live on some other driver; what any of this returns with cards of two different makes, or with no compatible card at all; and, for 5.3, everything with more than one card. **And whether 5.3's per-card driver check is new in 5.3**: its file marks a card whose driver is too old " (Disabled)", with a line saying what it needs, and the ninth value is where it reads that from; the earlier records show nothing like it and the earlier record has no place for it, but no earlier version was asked the same question, so whether it is new remains not established.

## 7. Can anything a render does wait for a person, and what happens on a computer with nobody at it?

This covers the whole run that ends with rendered files on disk. "Nobody at it" may mean an unattended logged-in computer or one with no display or session. No supplied finding documents sampling, denoising, compositing or image writing stopping for a person. The tests below cover particular runs, not every possible render.

For 4.5 to 5.2 the tests come from two machines and no others — the Creator's Mac and the fifth rented Linux machine, both named at the head of this document — and every answer below says which of the two it came from. **5.3's come from the Mac alone**, on the later day, with its screen on and the Creator's session logged in throughout — so it was never a computer with nobody at it. **No figure below is a time or a memory measurement**: none was taken on the Mac, and the Linux machine's first sitting was shared with other topics' work, so every result is judged on whether a command ended by itself and on what it wrote.

### The same in every version that records it, as the documents give it

The shared documented answers follow. Where 5.3 has no answer, that limit is stated.

- **One thing on the render path is documented as putting a question to a person: the automatic-execution warning.** Blender does not run a blend-file's stored Python unless told to, and when it declines, "a dialog will appear" offering Allow Execution or Ignore. All five carry the same picture of it, showing the same warning text, the same tick-box "Permanently allow execution of scripts", and the same two buttons — and in 5.3 that picture no longer matches 5.3's own dialog (*What differs* below). Automatic execution starts switched off in all five — checked in all four earlier versions on both machines, and in 5.3 on the Mac, rather than assumed, which matters because most of this question turns on that starting value.
- **What that catches**, in all five: registered text data-blocks, and driver expressions written as Python.
- **The way to settle it in advance**, in all five: `-y` / `--enable-autoexec` and `-Y` / `--disable-autoexec`, with the same worked example in every version — a background animation render.
- **Freestyle is excused from it**, in all five: its line-style scripts are described as running even when automatic execution is off.
- **A still render is not written unless something asks**, in all five; `write_still` and `-f` are the two things that ask instead of a person. 5.2's and 5.3's manuals state it more plainly than the other three do; the behaviour is identical.
- **Other things wait for a person, and none is documented as sitting on a render's path**, in all four earlier versions: the file browser ("wait for you to select a file"), the unsaved-changes pop-up on exit or on loading another file, and the first-run set-up on the splash screen. For 5.3, the first-run setup and interface save prompts are documented; the file-browser wording is not established.
- **Writing over existing frames is a setting, not a question**, in all four earlier versions: Overwrite and Placeholders, with the warn-before-overwriting option belonging to the saving commands and not to any render command. For 5.3 this is observed on the Mac, without a matching documented answer here.
- **Driven from Python, commands take the path that does not ask**, in all four earlier versions: `EXEC_DEFAULT` is the default and does not call the interactive half. Not recorded for 5.3.
- **There is a mode with no interface at all and it is meant for this**, in all five: `-b` / `--background`, "often used for UI-less rendering", needing no graphical display and workable over a remote shell. 5.3's help line adds that the audio device is off in that mode by default.
- **The manual's own picture of unattended machines**, in all four earlier versions: the Primitive Render Farm, and the advice to render to single frames so a run can be picked up where it stopped. Not recorded for 5.3.
- **One documented limit, and it is about Windows**, in all five: "Headless rendering is not supported on headless Windows systems", said of EEVEE, with no version defining what a headless Windows system is or what happens when you try.
- **Cycles' own Python files contain nothing that waits for a person**, observed in the supplied Python files for 4.5–5.2. The compiled rendering code was not supplied, so this does not establish that Cycles never waits. The corresponding answer for 5.3 is not established.
- **And the one thing that matters most is missing from all five.** No version's sources say what becomes of any of those dialogs when there is no window to draw them in. **A silence shared by all five is not a difference between them.**

**Other documented 5.3 conditions.** macOS's Crash Reporter may show a backtrace window after a crash. `--disable-crash-handler` and `--disable-abort-handler` exist. The Python-module route has no special Control-C render cancellation. These are not established as new in 5.3. The release-note changes to the Dock icon and viewport renders are under *What differs* below.

### The same in all four, settled by hand on both machines — and in 5.3 on the Mac

The shared observed results below cover 4.5–5.2 on the Mac and the fifth Linux machine, and 5.3 on the Mac except for two Blenders sharing a folder. They do not settle Windows, or Linux in 5.3. The hang-up results disagree under the different Mac test conditions, as stated below.

**Nothing on the ordinary render path stopped and waited for a person, in any version, on either machine.** Every one of these ended by itself and gave the prompt back:

- **A refused scripted-expression driver.** The warning the manual describes becomes text on the terminal naming the refused driver; the render carries on and writes its frame. The picture is the picture of a scene whose driver did not run — the refused and allowed runs differ by `max_channel_difference=0.517647`, the same figure in all four versions on both machines and in 5.3 on the Mac. A run can find out for itself that it happened, by reading `bpy.app.autoexec_fail` and `bpy.app.autoexec_fail_message` — in 5.3, `True` and `"Driver '__import__('math').floor(4.5)'"`, with the driven value left at 0.0 where `-y` gave 4.0.
- **A refused registered text data-block.** One printed line, `scripts disabled for "<the file>", skipping 'Text.py'`, and the render carries straight on. The same line in 5.3.
- **Unsaved changes at Blender's own exit.** Nothing asked, and the file on disk left untouched — in 5.3 too, by checksum. **But in 5.3 Blender did not count the change as unsaved at all**: with no window, its own changed-file flag read false after a script moved the cube, and false again after an operator added one. So in 5.3 this test never reached a state the unsaved-changes prompt is for. The earlier runs did not read that flag, so whether they reached it is not recorded.
- **A second file loaded over unsaved changes.** Nothing asked — in 5.3 too, with the same flag reading false. The picture went to the second file's own output path, not to one given with `-o` before the script, as the earlier versions' Mac runs also found.
- **A save with a render result in memory.** Nothing asked, in all four versions — including 5.2, where the preference that would ask is present and starts at Ask Every Time — and in 5.3, where it read `ASK` and the file was saved, with a `.blend1` copy of the old one beside it. What that preference is, and the dialog it governs, is under *What differs between the versions* below.
- **An output file already on disk.** Written over silently. With Overwrite switched off the run skips it and says so — in 5.3, `Skipping existing frame` and `No frames rendered, skipped to not overwrite` — which is the control that shows the switch was being read.
- **Two Blenders sharing one output folder.** They divided forty frames between them without being told to, both ended by themselves, and nothing was asked — but the frames are divided by each Blender checking as it reaches a frame, not by a lock, and **the check and the claim are two steps**. This run kept only the last fifteen lines of each copy's log, so it could not have shown a collision either way. What it did show is the opposite failure: on the Linux run of 4.5 one of the forty files came back empty, and both copies printed a line saying they were skipping that frame because a placeholder was already there. **The frame was claimed, never rendered, left empty — and the job still ended with the full count of forty files and exit status 0, a silently lost picture reported as a complete job.** On that machine 5.0, 5.1 and 5.2 left no empty file, and on the Mac 4.5 left none either — one run each, on two machines. The mirror failure, two copies both getting past the check and rendering the same frame, was caught on the Creator's Mac in 4.5, 5.0 and 5.1 — settled under **Frames 4**. Neither is a difference between versions. All of it is two Blenders on one machine sharing one ordinary local folder — not the manual's several machines sharing a network folder, which could not be built here and which nobody has tried in any version. **The folder itself matters, though, and one machine is enough to show it: Frames 14** ran thirty repeats of the same sharing over a network folder and got four to six collisions in thirty in all four versions, against none on the same machine's own disk. **Not tried in 5.3**, whose sitting ran one Blender at a time.
- **A texture the file needs and cannot find.** The texture was assigned to the faces used in the picture, and changing or deleting it changed the picture. With it missing, 4.5–5.2 on Linux and 5.3 on the Mac ended by themselves at exit 0 and wrote a frame. The original 4.5–5.2 Mac runs used an unassigned texture and do not settle the missing-texture case. 5.2.2 has a later Mac control. The messages are under *What differs* below.
- **An output folder that cannot be written to.** An error, no file, and **exit status 1** — the only place in this whole question where an unattended run's *exit status* told the outside world that something had gone wrong. The folder was made unwritable two ways and both ways gave the same words, in eight runs: an error, nothing written, nobody waited for, exit status 1. 5.3 did the same on the Mac, aimed at `/usr`, a folder owned by the system that the test had not made. What each version *said* is under *What differs between the versions* below.
- **Render Audio aimed at a file already there.** Written straight over, with no window and nothing asked — in 5.3 too.
- **Freestyle with automatic execution switched off.** It reaches the picture: the two pictures differ by `max_channel_difference=0.658824`, the same figure in all four versions on both machines and in 5.3 on the Mac, and nothing was printed about scripts being refused. So the manual's sentence about Freestyle's scripts running anyway is borne out on a run nobody started by hand.
- **Blender asked to do no render at all** ended by itself with exit status 0, in 5.3 too.
- **A render outlived the shell it was started from.** On Linux the SSH connection was cut; on the Mac the shell was killed. In all four versions the render was still going and frames kept appearing — and in 5.3, killed the same way on the Mac, Blender carried on under process 1 and its frame count rose from 16 to 28.
- **A hang-up signal to the render's process group — and here the Mac's two days disagree.** On the earlier day, a hang-up signal was sent to the whole process group, which is what closing a terminal window really sends, and in all four versions the render was still going and frames kept appearing; the records do not set out how the group was formed. **On the later day, with Blender started as the leader of a process group of its own and a hang-up sent to that group, 5.3 was gone within three seconds**, its output stopping part-way through a frame with no line about the signal — **and 5.2.2, sent it the same way on the same Mac, ended the same way.** So this is not a difference between 5.2 and 5.3, and **whether a hang-up ends a background render is not settled**: the two readings disagree, and the cause is not established. The Linux machine's cut SSH connection, which is the case a rented machine meets, was never tried in 5.3.

**Two things do hold such a run, and they are worth as much as everything above.**

- **A script hooked into a render holds the render for as long as it runs.** A hook that sits still for forty-five seconds added forty-five seconds inside the render, in all four versions on both machines — on the Mac, Blender's own clock puts the save at `00:45.895` for a scene that renders in about a second — and in 5.3 on the Mac, where the frame was saved at `00:46.022`, only after the hook had finished.
- **A script inside Blender that reads from standard input waits for ever**, if something is holding the other end of standard input open. In all four versions on both machines, and in 5.3 on the Mac, it was still sitting there after sixty seconds and only a time limit stopped it. With nothing on the other end, the same script fails at once with an end-of-file error instead. **This is the only thing found anywhere in this question that waits indefinitely on a machine with nobody at it.**

**And Python's standard input in a background Blender is not `None`.** Asked directly, all four versions on both machines, and 5.3 on the Mac, printed the same thing with and without `--debug`, and it was not nothing: `STDIN IS <_io.TextIOWrapper name='<stdin>' mode='r' encoding='utf-8'>`. That stream permits the waiting script above. The manuals' `--debug` description says it keeps standard input instead of setting it to None. That suggests, by inference, no input wait without `--debug`, but the observed streams and waits contradict it. The documented description and observed behaviour disagree; neither establishes a version difference.

### The same in all four, settled on the Linux machine alone

**Cycles rendered on the graphics card on a computer with no display server at all** — through OptiX and through CUDA, in all four versions, every run ending by itself with exit status 0 in two to five seconds and writing its picture. Nothing waited and nothing was asked. No run named the card outright, but a run that finished at all is a run that got what it asked for, because Blender says `Found no Cycles device of the specified type` and stops with exit status 1 rather than quietly using the processor. **The Mac cannot speak to this** — it has no NVIDIA card and no second card of any kind — so this is settled for one machine and one operating system, and **not for 5.3**, which was never run there.

Two smaller things came with it, both the same in all four versions. The whole record of the Cycles runs was searched for the words error, warning and failed, and nothing matched. And loading the render kernels for the first time in a fresh settings folder took about a second and a half, where Blender's own message warns it "may take a few minutes the first time".

**And the `libEGL` lines are not the mark of a machine without a display server.** On that machine, with the card's own graphics library, EEVEE renders with no display server at all and prints none of them, in all four versions; with that library hidden and only a software one left, all four print them word for word. So what decides is which graphics library Blender gets. **Here two runs on the same machine disagree** — the lines appeared on one and not on the other — both were reproduced on demand, the machine's driver was mismatched for the first of them and cannot be put back, and **the disagreement stands recorded and not resolved.** Nothing in it separates one version from another. 5.3's Mac logs held no line containing `EGL` under any engine, which is a Mac reading and stands beside none of this.

### Settled on the Mac alone — the window

The window results below are observations on the Mac alone. They do not establish the same behaviour on Linux or Windows. Window-server registration differs between the older 4.5 run and the later 5.2.2/5.3 runs; the registration result for the original 5.2 run is not independently established.

- **The automatic-execution warning is a dialog in the middle of the main window, not a warning in a header** — which settles a contradiction inside the manual itself, where one page calls it a dialog and a caption on another calls it "An Auto-run warning in the Info editor's header". The screenshots settle it for all five versions. Its words and buttons changed in 5.3 (*What differs* below).
- **And it reports rather than blocks.** The render started, finished and wrote its frame with the dialog sitting there unanswered — and with the first-run Quick Set Up unanswered underneath it. In all five versions; in 5.3 the frame was written within two seconds.
- **A file chooser opened on top of a running animation render stopped nothing.** The frame count roughly trebled while it sat there unanswered: 12 to 34 to 107 in 4.5, 13 to 35 to 109 in 5.0, 12 to 33 to 105 in 5.1 and in 5.2. A window waiting for a person and a render going on live side by side. In 5.3, on a heavier scene of about four seconds a frame, the count went from 2 to 3 to 10 with the chooser standing in a window of its own; that scene's figures are not set beside the others.
- **A still render nobody asks to be saved still writes nothing, while an image-editor window opens.** In every version, 5.3 included, with and without the switch, a second window appeared holding an image editor, and it was still open when the render had finished. **In 5.3 the window's photograph was grey, so it does not establish that the rendered picture was visible.**
- **The splash screen and the first-run set-up do not hold up a render asked for on the command line** — the frame was written within about a second of the file being read, with nobody dismissing anything, and in 5.3 within about two seconds of starting from a never-used settings folder. **But a Blender started with a window does not quit when that render is done.** In all five versions it was still sitting there when a two-minute limit ran out and had to be stopped. So asking for a frame without `--background` is not a way to render on a machine with nobody at it.
- **Whether a `--background` render registers with the Mac's window server — unresolved across conditions.** On macOS 26.5.2, 4.5 was registered throughout, marked foreground and not hidden, but never came to the front or drew a window. The original 5.2 registration is not independently established. On macOS 26.6.2, both 5.3 and 5.2.2 were absent in eight checks by process number during an eight-frame render. The older check selected Blender by name. The operating system and query changed, so these observations establish no 5.2.2-to-5.3 difference and no general registration rule. The documented Dock-icon change is below.
- **And one thing behaves differently when a menu asks for it than when a script does.** Render Audio with **no path named** — which is what choosing it from a menu does — opens a file chooser as a window of its own, returns `{'RUNNING_MODAL'}`, and leaves an existing file exactly as it was. With a **path named** it writes straight over that file without asking, window or no window, on both machines. 5.3 did both on the Mac. **What decides is whether the path was named** — established for the path-named half on both machines, with a window and without. **The no-path half has only ever been run with a window open, on the Mac.** What it does on a machine with no display — refuse, write nothing, or sit there waiting — is untried, and a file chooser is a window. This is the only place in the whole question where the two routes part company.

**And one more thing a crash on the Mac leaves behind.** After 5.3's forced crashes (question 4), macOS's Problem Reporter started in the same second and was still the front program about fifteen minutes later. Its window was not looked at, so what it shows, and whether it waits for an answer, is not recorded.

### What differs between the versions

Nine things. None of them changes whether a render on the unattended path finishes: eight are things Blender says, shows or offers, and the ninth, by 5.3's release note, is about the interface's own viewport render.

- **Which frame an animation render says it is on.** In 4.5 the frame being worked on appears only inside a progress line, as `Fra:2`. In 5.0, 5.1, 5.2 and 5.3 it is named outright on a line of its own, `Rendering frame 2`. Run in all four earlier versions on both machines and in 5.3 on the Mac, and matched by a release-note entry of 5.0's, "Show currently rendered frame in background mode". Anything watching a background render's output to see how far it has got has to read a different thing in 4.5.
- **What Blender says when it cannot write its output.** All five fail in the same way — nothing written, nothing asked, exit status 1 — but they do not say the same thing. 4.5 prints one line with a word in brackets — `Error: Render error (Read-only file system) cannot save: '…'` on Linux and `(Permission denied)` on the Mac — and on the Linux machine it also prints the real reason on a plain line above it. 5.0, 5.1 and 5.2 put a word in those brackets that has nothing to do with the failure — `Success` on Linux, `Undefined error: 0` on the Mac — and carry the real reason on a separate line of their own, `ERROR OpenImageIO write failed: Could not open file "…"`. Run in all four versions on both machines. **5.3 says it as 5.0 to 5.2 do on the Mac**: `ERROR OpenImageIO write failed: Could not open file "…"`, then `ERROR Render error (Undefined error: 0) cannot save: '…'`. **The bracketed word cannot be trusted to say what went wrong in any version, 4.5 included.** In 4.5 it moves with which graphics library Blender is given — `(Invalid argument)` with the card's own, `(Read-only file system)` with a software one — while 5.0, 5.1 and 5.2 said `Success` throughout. **What moves 4.5's bracketed word on that machine is settled: it is which graphics library Blender is given.** The folder was made unwritable two different ways and gave the same word both times; hiding the card's library gave the other word back. What stays open is which state that machine was in on the earlier day, which cannot be recreated — and why a graphics library should reach the word in those brackets at all, which is not established.
- **A step line naming Freestyle.** With Freestyle switched on, 5.0, 5.1, 5.2 and 5.3 print `Rendering freestyle` as a step of their own; 4.5 prints no such line. Seen in all four earlier versions on both machines and in 5.3 on the Mac.
- **A dialog new in 5.2, for saving a file that holds modified images.** 5.2's release notes state that a new dialog now asks whether modified images should be saved with the file, and that a new preference governs it; its own manual gives that preference's starting value as Ask Every Time and names Render Results among what it covers. 4.5, 5.0 and 5.1 do not have it; 5.3 does, its preference reading `ASK`. Established by the release note, not by any silence. **On the unattended path it never fired**: a save with a render result in memory asked nothing, in all four earlier versions on both machines, 5.2 included, and in 5.3 on the Mac.
- **The sound file Render Audio writes.** For the same silent scene it is 8316 bytes in 4.5, 5.0 and 5.1 and 8302 bytes in 5.2, with the same checksums on both machines — which is what shows the difference is in Blender rather than in either machine. Run in all four versions on both machines. **5.3 wrote 9816 bytes** on the Mac, with and without a window, and 5.2.2 on the same Mac the same day wrote 8302, as 5.2 had. Small, and named only so nobody meets it cold.
- **What Blender says about a texture it cannot find, under EEVEE.** With the missing image actually in the picture, **4.5 prints `GPUTexture: Blender Texture Not Loaded!`** before anything else it prints, with no marking of any kind, and without naming the file — so it says a texture is missing and never which one. **5.0, 5.1 and 5.2 print `ERROR Failed to create GPU texture from Blender image`** in a column of their own named `gpu.texture`. Different words, not merely a different line shape. **5.3 prints different words again, and names the file**: `image.gpu | ERROR Image file "…/tex.png" does not exist`. The message is tied to the file being missing rather than to the file being open: the runs with an image present were searched for the words texture, not loaded and failed and returned nothing, and only the run with the image deleted printed anything — in 5.3 as well. In every version the run still ended by itself with exit status 0 and wrote its frame. 4.5 to 5.2 were run in one sitting, **on the rented Linux machine alone**; 5.3 on the Mac, where 5.2.2 the same day printed 5.2's `gpu.texture` line, so the 5.3 change rests on the same machine. 4.5, 5.0 and 5.1 have no Mac reading. What a **Cycles** render prints for the same missing file is not the same and is settled elsewhere — in all four earlier versions on both machines, under **Images 9**; 5.3 printed `WARNING Image file … does not exist.` and `ERROR Failed to load 1 image files` on the Mac, as 5.2.2 did beside it.
- **The automatic-execution dialog, with a window.** In 4.5 to 5.2 it reads "For security reasons, automatic execution of Python scripts in this file was disabled:", names the refused item, says "This may lead to unexpected behavior", and offers a "Permanently allow execution of scripts" tick box with the buttons **Allow Execution** and **Ignore**. **In 5.3 it carries a red cross, adds "Allow at your own risk.", has no tick box, and offers Allow Execution and Continue Safely**, the second highlighted. 5.2.2, opened the same way on the same Mac the same day, showed the tick box and Ignore. 5.3's manual still shows the earlier dialog. What the dialog does is unchanged: in every version a render ran and wrote its frame with it unanswered.
- **The Dock icon for a background render on macOS.** 5.3's release notes say: "The Blender application icon no longer shows up in the Dock when running in background mode via the command line." Established by that note. **No test shows the change**: the Dock itself was never looked at, and on the window server the same day 5.2.2 and 5.3 were both absent (above), so whether 5.2 as it stands still shows the icon is not settled.
- **Viewport renders are paused during a final render** from 5.3, by its release note: "Viewport renders are automatically paused during final renders." Never tried, and nothing on the unattended path turns on it.

### Verdict: it differs

Blender does the same thing in all five versions on everything this question is really about, as far as each was tried. Nothing on the ordinary render path tried here waited for a person. The observations cover 4.5–5.2 on the named Mac and Linux machines, and 5.3 on the Mac alone. The one thing that waits for ever waits in all five. The one thing that holds a render up holds it in all five.

**What differs is what Blender says, shows or offers while it does it, and one dialog that exists only from 5.2.** Four of the differences are printed output run in all four earlier versions on both machines, coming back split the same way both times — which frame an animation render names, what a failed write says the reason was, whether a Freestyle step gets a line of its own, and how many bytes Render Audio writes — and 5.3 sides with 5.0 to 5.2 on the first three and writes a different number of bytes again. **A fifth is printed output too, from one machine for 4.5 to 5.2**: what Blender says about a texture it cannot find under EEVEE, run in all four on the Linux machine alone, with 5.3 naming the file on the Mac where 5.2.2 did not. The sixth is 5.2's new dialog for saving a file that holds modified images, established by 5.2's own release note and still in 5.3, and it never fired on the unattended path in any version. **5.3 adds three**: its automatic-execution dialog's controls, settled on the Mac against 5.2.2; the Dock icon, by its release note alone; and the pause of viewport renders, by its release note alone.

**The practical shape of it: anything reading a background render's output has to know which version it is reading, and how the render was started.** 4.5 prints plain lines and the other four print lines stamped with an elapsed time and a category — that is the line-shape difference under question 4, and everything above is consistent with it. The printed differences above are of the same family — and the missing-texture one goes further, because 4.5's words there are not merely unstamped but different words, and 5.3's are different again. The failed-write wording is the one that could mislead a person rather than merely a program, and it misleads in every version.

### Not established for any version

- **Everything about Windows.** Whether EEVEE really cannot render on a Windows machine with no screen — the sentence is in all five manuals and none of them defines it or says what happens when you try. Whether the Windows crash pop-up appears when there is no window: 5.0's release notes record that a "Windows graphical crash report appears in background mode" was a fault that was fixed, and a release note of 4.5's says Windows "now shows a crash popup with recovery options". Neither was tried — no Windows machine ran this topic, though one can be rented — and **neither is treated as a difference between versions**: the first was backported into 4.5.1, and the 4.5 tested here is 4.5.12.
- **Everything 5.3 does on Linux**, the cut SSH connection and Cycles on a card with no display server among it.
- **Whether a hang-up signal ends a background render.** The earlier day's runs say it did not, in 4.5 to 5.2; the later day's say it did, in 5.3 and in 5.2.2, sent to a process group Blender led. The records do not say how the earlier group was formed, and nothing chooses.
- **Whether a background render registers with the Mac's window server**, and whether 5.2 as it stands still shows the Dock icon 5.3's release note says is gone. 4.5 was registered on the earlier day; 5.2.2 and 5.3 were not on the later one, asked a different way under a later macOS.
- **Whether macOS's Problem Reporter**, left in front after a crash on the Mac, waits for an answer.
- **Whether the unsaved-changes tests reached the unsaved-changes prompt.** In 5.3, with no window, Blender did not count the changes as unsaved; the earlier runs did not read that.
- **What screen locking or display sleep does to a render.** Neither was tested. Surviving a killed shell is a different event and does not settle either.
- **A whole machine going to sleep under a render, or the user logging out.** Neither was tested.
- **The manual's own Primitive Render Farm.** It needs several machines sharing a directory over a network file system, and there is no such folder between the Mac and a rented machine. What was run is the nearest thing that could be built and is written up as that and nothing more.
- **Two Blenders sharing one folder, in 5.3**, which was never run with more than one Blender at a time.
- **The approval macOS asks for the first time Blender is opened.** Every Blender on the Mac has already been opened, so that moment has passed and cannot be made to happen again without moving or reinstalling them.
- **What Blender does with a dialog when there is no window, as the sources give it.** The window observations do not fill this documentation gap. That is the same silence in all five and it stays open as a documentation gap.
- **The Mac's half of the missing texture for 4.5, 5.0 and 5.1.** 5.2 has one, from the 5.2.2 control, and 5.3 has one; nothing says what a Mac prints about a missing texture that really is in the picture in the three earlier versions. The tests varying the graphics library for unwritable-output errors cover Linux alone.
- **Documentation of the automatic-execution status values.** In 4.5, `bpy.app.autoexec_fail`, `autoexec_fail_message` and `autoexec_fail_quiet` say "Undocumented, consider contributing". In 5.1 and 5.2 they have descriptions. This is an established documentation difference between those versions. Their documentation in 5.0 and 5.3 is not recorded. The values behaved alike in the tested cases: 4.5–5.2 on the Mac and Linux, and 5.3 on the Mac.
- **Whether a system permission dialog on macOS can ever stand in a render's way.** 5.1's release notes say that on macOS scripts and extensions can now reach the device camera, microphone and system audio, and that "A system permission dialog will be prompted to the user" — a new thing at 5.1 that can wait for a person on one operating system. That it could stand in a render's way is an inference the 5.1 finding itself calls weak, and nothing was tested. It remains an untested possibility, listed above as not established.

### Things that came back looking like differences and are not

- **Freestyle progress lines.** The Linux record shows 4.5 printing no Freestyle line of its own; on the Mac, 4.5 printed a whole run of `Freestyle:` progress lines, and 5.0, 5.1 and 5.2 printed those *and* the `Rendering freestyle` step line, as 5.3 did. The step line splits the versions the same way on both machines and is a real difference. **The progress lines are a difference between the two records of what was printed, not between versions.**
- **The `libEGL` and `EGL Error` lines**, and the per-sample progress lines in the Mac's 5.0, 5.1 and 5.2 that the Linux record does not show — 5.3 printed them on the Mac too. Neither touches any answer, and neither separates one version from another. The per-sample lines are a difference between the two records. What the `libEGL` lines really depend on, and the disagreement left open about them, is set out under *settled on the Linux machine alone* above.
- **The hang-up signal and the window server.** 5.3 came back otherwise than the Mac's earlier record on both, and 5.2.2, run the same way on the same Mac the same day, came back as 5.3 did. Each is a disagreement between two days on one machine, set out in its own entry above, and neither is a difference between 5.2 and 5.3.

## 8. On a computer that has a graphics card but whose screen is drawn by the processor rather than by that card, what does a render do under each render engine?

**Asked of 5.3 alone.** This question was put to 5.3 and to no earlier version, so 4.5, 5.0, 5.1 and 5.2 have no answer to it. Nothing below is a difference between versions.

**5.3 reads the question two ways and answers both.** **(a)** Graphics built into the processor chip — the manual's "onboard GPU integrated into the main CPU" — draw the screen, while a separate card sits unused for display. **(b)** No graphics hardware draws the screen at all, and a software stand-in running on the processor does it.

- **Cycles — inferred, not stated.** The manual treats the card that renders and the card that draws as separate things — "the only complete solution for this is to use a dedicated GPU for rendering, and another for display" — and Cycles picks its cards through its own technologies (question 5). Cycles' own 5.3 file shows its render engine does not ask Blender for a drawing context: it does not set the switch the API describes as giving a render engine one. From those three, 5.3's finding infers that under both readings a Cycles render set to the graphics card uses the card, whatever draws the screen, provided the card meets question 2 and its driver is installed. **No source states the case outright, and the label is inferred.**
- **EEVEE — not in the sources.** The manual says EEVEE renders only on a graphics device and has no processor mode, has no support for several cards, and cannot render on headless Windows systems. It offers one setting that picks a device — "Device", for Vulkan only — and describes it as choosing the card for "display drawing operations" and "UI rendering", never for a final EEVEE render; it does not say what its Auto value picks here. Blender's drawing layer can report its device type as `SOFTWARE`, and nothing says whether EEVEE runs at all on such a device. For reading (a), which device EEVEE renders on is not in the sources; for reading (b), whether it renders at all is not either. Nothing in 5.3's sources speaks of headless EEVEE on Linux or macOS.
- **Workbench — not in the sources.** The manual describes it as made for the 3D Viewport and says nothing about which device a Workbench render uses.

**Settled by hand: nothing.** The only 5.3 machine, the Creator's Mac, has one graphics device that both draws its screen and renders, so neither reading could be reached. Two things seen there bear on the question's terms without answering it. A windowless Cycles render on that card named it `(display)` in its `Path tracing on:` line; what sets that mark, and whether a card that draws no screen loses it, could not be seen with one device. And EEVEE and Workbench rendered with no window and printed nothing naming a device, while the drawing module, after `gpu.init()`, named one device, `Metal API`.

**Nearby records for 4.5 to 5.2, which are not answers to this question.** Two results already in this comparison come close to reading (b) and are pointed at so nobody meets them cold. Under question 7, on the fifth rented Linux machine, with its card present but the card's own graphics library hidden so that only a software one was left, EEVEE drew in software and rendered its frame at exit status 0, in all four versions; that machine had no screen at all. And under question 2, **Frames 15** records EEVEE drawn by a rented Linux machine's processor at about ninety seconds a frame, and six of this project's machines with a display had that display drawn in software. Neither was put this question, and neither was run in 5.3.

**Verdict: not established for every version.** 4.5 to 5.2 were never asked. In 5.3, Cycles rests on an inference, EEVEE and Workbench are not in the sources, and no machine that could settle either reading was available.

**Not established for any version:** what Cycles, EEVEE and Workbench each do under either reading, on any operating system; whether EEVEE renders on the processor's built-in graphics or on the separate card, and whether the Vulkan Device setting or its Auto value decides that; whether EEVEE renders at all when Blender's drawing layer is software; and what Cycles' `(display)` mark means. Settling any of it needs a machine with a separate card whose screen is drawn by the processor's own graphics or by software, which this project has rented before and did not have for 5.3.
