Where the files a render produces end up, how the places a render writes to are recorded and set at the moment a render is started, in what order a render's frames reach the disk, and what happens when a write fails.

## 1. Can where a render writes be settled at the moment the render is started, without changing the file?

**4.5.** Yes. The command line takes an output-path argument that sets the place for that run, and the order of the arguments decides whether it takes effect — loading the blend-file overwrites a value set before it. The mechanism is documented. The half of the answer that says the file on disk is not changed is **inferred**; the sources never say it.

**5.0.** The same, with the same split: documented for the argument and the ordering rule, **inferred** for the file being left alone. A second route is a script handed to Blender at launch, and that route is **inferred** too.

**5.1.** The same again, with the same two inferred parts.

**5.2.** The same.

**5.3.** The same, with the same split: documented for the argument, the ordering rule and path templates being worked out only when the path is used; **inferred** for the file being left alone and for the Python route.

**Verdict: the same everywhere.** Where a render writes can be set at the moment the render is started, from the command line, and the blend-file on disk is not changed by it. A hand test settled the second half in all four earlier versions **on both machines**, and in 5.3 on the Mac: the file was byte-for-byte identical before and after, its size and modified time unchanged, the stored path still there when the file was reopened, and the image landed where the argument said. Linux is untried in 5.3 and Windows in every version.

**The second route — a script handed in at the same launch — is settled by test rather than inferred.** In all four earlier versions, on the Creator's Mac and on a rented Linux machine, and in 5.3 on the Mac, a script handed in with the file wrote a new output path and the render then wrote its frame there. Which of the two wins when both the argument and the script are given, and what the argument reaches, are under question 13.

## 2. How is a place to write recorded in a file — what parts does the recorded thing have?

**The scene's own output** is recorded the same way in all five: **one single piece of text** holding the folder and the front of the name together. The rest of the name is recorded separately — a File Extensions switch and the chosen file format. All five document this, and all five quote the same published length limits: 767 for a directory, 255 for a file name, 1023 for a whole path. Hand tests showed 1023 is the one actually enforced, in all four earlier versions **on both machines** and in 5.3 on the Mac: text longer than that is silently cut as it is entered, and the 1023 characters kept are exactly the first 1023. On the Mac 1400 characters pasted at the window came back as 1023 — in 5.3 both pasted over the field and pasted into the field opened for editing, with no message shown either way; from a script, 5.3 kept 1023 of 1268 characters asked for; on Linux, from a terminal, 1239 characters asked for came back as 1023, with nothing said about the cut.

**The File Output node is recorded differently, and this is where the versions part.**

- **4.5.** One folder string on the node, and one piece of path per slot. A new node arrives with one input already called `Image`, and that input's own path piece reads `Image`.
- **5.0, 5.1, 5.2 and 5.3.** Two strings on the node — a folder and a file name — plus a name for each input item. The old folder string, the slots and the layer slots are all gone. A new node arrives with no items at all and one unnamed input. In 5.3 a node made fresh by a script starts with its folder at `/tmp/` and its file name at `{blend_name}`, though the two settings' own built-in defaults read empty. In 5.3's window the node's face shows the folder and the file name as two text fields, each with a folder button, and each input by its own name.

**Verdict: it differs.**

**What differs, version by version.**

1. **The node's shape**, as above. 5.0's release notes say so outright: the node was redesigned, the base path was split into a Directory and a File Name, and the API notes list the old three names as removed and the new three as added. 5.3 has the 5.0 shape.
2. **How the compositor is reached.** In 4.5 the scene carries a node tree of its own, switched on with a `use_nodes` flag. In 5.0, 5.1, 5.2 and 5.3 the scene carries a compositing node group instead and has no node tree. In 5.3 every script use of the scene's `compositing_node_group` printed a warning that it is expected to be removed in Blender 6.0; whether the earlier versions print it is not established.
3. **A switch for turning automatic saving off.** 5.2 and 5.3 have one, called `save_output`, on by default, with a checkbox in the Output panel's header. 5.2's tooltip reads "Save Output / Write frames to disk for animation renders"; 5.3 gives the setting the same name and description, read from Blender's own description of it because no tooltip could be photographed in 5.3. 4.5, 5.0 and 5.1 have no such property and no such checkbox. Seen from a terminal in all five versions, at the Mac's window by the Creator in 5.2, and at the Mac's window in 5.3. 5.2's release notes record it as added: "Saving render output can now be disabled."
4. **The built-in default behind the output path.** Empty text in 4.5, 5.0 and 5.1; `//` in 5.2 and 5.3. This is the property's own default, not what you see on screen — a fresh Blender starts at `/tmp/` in all five, because the startup file puts it there. The preference that seeds a new scene reads `//` in all five.
5. **A Media Type setting.** Absent in 4.5; present and reading `IMAGE` in 5.0, 5.1, 5.2 and 5.3. It has a practical edge: from 5.0 a File Output node's file format cannot be set from a script until the media type is set first, because the node starts out as a multi-layer OpenEXR; 4.5 has no such setting and the format can be set on its own. What that starting format does to the file a node writes is under question 8.
6. **Two extra node settings in 5.2 and 5.3.** Their File Output node carries its own File Extensions switch and one more setting recorded only as a name, `panel_states`. Neither is on the node in 4.5, 5.0 or 5.1. The File Extensions switch was seen by the Creator too, in the node's Output Paths panel in 5.2 and not in the other three; in 5.3 it was seen from a terminal only. What `panel_states` holds is nowhere in any version's findings, so nothing is claimed about it here beyond its being present in 5.2 and 5.3.
7. **The built-in defaults of two node settings, on the Creator's Mac.** The node's `save_as_render` setting reads off as its own default in 4.5, 5.0, 5.1 and 5.2, and its File Extensions switch reads off in 5.2; **in 5.3 both read on.** The 5.2.2 run, with the same script on the same Mac the same day, printed off for both, as 5.2's record does, so the change is 5.3's. A node made fresh in 5.3 starts with both on. What a fresh node starts with in 4.5 to 5.2 was never printed, so whether a newly added node behaves differently there is not established.

**Items 1 to 6 were seen on both machines**, in all four earlier versions, item for item: 4.5's node listing its folder, its slots and its layer slots where the later three list a directory, a file name and a list of items; 5.2 alone of the four adding its own File Extensions switch and `panel_states`; `save_output` present in 5.2 alone of the four; the built-in default reading `//` in 5.2 and empty text in the other three, with a fresh Blender starting at `/tmp/` in all four on both machines; and the Media Type setting absent in 4.5 and reading `IMAGE` in the later three. How the compositor is reached was not put as a test of its own on Linux, but every Linux run there had to reach the tree by its own version's name, and each did. The only part resting on the Mac alone is what the Creator saw in the node's own panel, and the Linux run reached the same setting from a terminal. **In 5.3, on the Mac, items 1 to 6 came out as in 5.2. Item 7 rests on the Mac alone.**

**What is the same.** The single-string shape of the scene's own output. The switches beside it for extension, overwrite, placeholders and render cache, and their defaults. The published length limits and the 1023 that is really enforced. All four earlier versions label this answer **documented**; so does 5.3, except that it marks **inferred** the step joining the 1023 limit to the output path, because its limits page does not name that field. The test settles it either way.

**One thing about the machine rather than the version, and Smoozy needs it.** A separator test was run on Linux only, in all four earlier versions, and all four did the same thing. A path typed with backslashes is **stored exactly as it was typed** — Blender does not tidy it when it goes in — and is turned into forward slashes when the path is used. A doubled forward slash in the middle of a path is collapsed to one. Blender's own helper for this turned `a\b\c.png` into `a/b/c.png`. That is what a system whose separator is a forward slash does. **Using the path is not the only moment it is re-spelled:** the same re-spelling happens when the file is next opened, and a plain save then writes it into the file — settled under **Dependencies 20**, which also holds the Windows half, where the re-spelling runs the other way. Nothing in this topic was ever run on Windows. This is an operating-system fact, not a version one: the four versions did not differ. **5.3 ran the same test on the Mac and came out the same shape** — stored as typed, written with forward slashes into a real folder, a doubled slash collapsed, the helper giving `a/b/c.png`. Because the machines differ, that says nothing about macOS in the earlier four or Linux in 5.3.

**What the Output panel itself looks like, seen at a real window in all four earlier versions on both machines, and in 5.3 on the Mac.** Its rows run File Path, then Saving — holding two checkboxes, **File Extensions** and **Cache Result** — then File Format, Color, Color Depth, Compression, and Image Sequence. In 5.0, 5.1, 5.2 and 5.3 a **Media Type** row reading `Image` sits between Saving and File Format, and 4.5 has no such row, which is the difference already stated above seen from the panel's side. In 5.3 the **Image Sequence** section holds two checkboxes, **Overwrite** ticked and **Placeholders** unticked, and two closed sub-panels, Color Management and Pixel Density, follow it; whether the earlier panels carry those two sub-panels is not recorded. The path field at the top of the panel holds exactly what a script reads back as the scene's output path — see question 13.

**Not established, in 4.5 to 5.2:** what the panel's Image Sequence section holds, and whether Blender says anything when over-long text is entered in the File Path field. Both need eyes on Blender's window, and no window test in those versions looked at either. Both were seen in 5.3, as above.

## 3. What characters or marks can a recorded place to write carry that stand for something else rather than for themselves, and what does each of them do?

**The common path marks agree on the machines tested.** The earlier four ran on the Mac and Linux, and 5.3 on the Mac. The order test in 4.5 has a narrower machine limit, and the additional 5.3 tests have no earlier counterpart, as stated below:

- **`//` at the front** means the folder of the saved blend-file. In a session that has never been saved it means nothing: in 5.3 `//` came back as empty text, the name was left bare — `//frame_####` became `frame_0001.png`, with no folder in front — and a render then refused to save it, with Blender's window and without. No earlier version was asked; see question 12 for what the refusal says.
- **`#`** means the frame number, and how many of them there are sets how many digits it is padded to. It is honoured in the name only. A run of hashes sitting in the folder part is left alone: a folder literally called `seq_##` was made in all five. **In 5.3, with two separate runs of hashes in the name, only the last became the frame number** — `a_##_b_###_` gave `a_##_b_007_.png` for frame 7. No earlier version was asked.
- **`{something}`** is a template expression, replaced by a value at the moment the path is used.
- **A colon inside a template expression** introduces a number format, and inside that format a `#` counts digits rather than standing for the frame number. In 5.3 `{fps:###}` gave `024` and `{fps:#.##}` gave `24.00`.
- **`{{` and `}}`** each stand for one literal brace.
- **`%`** is named in one place only, as the mark that a path-building call replaces with a view's name. In all five versions a real render **never replaced it**: it stayed in the file name as a plain character, and the view's own ending was added after the frame number instead. No version treats `%` as plainly documented, but they do not all say so the same way: 4.5 and 5.1 label it **inferred**; 5.0 calls it "documented, but thinly"; 5.2 calls it documented and says in the same breath that the sources never state a render supplies the view name by itself; 5.3 calls it documented in one API description only, with what it produces not shown.
- **A backslash** stands for a folder separator. Setting a path ending `back\slash_` made a folder called `back` in all five — in the earlier four on both machines, in 5.3 on the Mac. On Linux this was pinned down further: the machine itself takes a backslash in an ordinary file name without complaint, so turning it into a separator is **Blender's own doing and not the computer's**. In 4.5 to 5.2 that was never established on the Mac. In 5.3 it was: the Mac itself took `back\slash` as an ordinary file name, and Blender still made the folder.
- **Order.** The template is put in first, and any hashes it brings are then read as a place for the frame number. Observed in 4.5 on the Mac, in 5.0–5.2 on both machines, and in 5.3 on the Mac. The 4.5 Linux run refused the unknown `{scene_name}` variable; it did not establish this order. The sources leave the order unstated in every version.

**Marks that do not exist, tried in 5.3 alone.** A home-folder mark `~/`, `$HOME/` and `%HOME%/` were all left exactly as written in the name. `${HOME}/` was refused as a template naming an unknown variable, `{HOME}`, because the braces are a template's. No earlier version was asked, so none of this is a difference between versions.

5.3 labels the marks **documented**, and marks **inferred** that marks in a stored path apply however the render is started; its tests settle that on the Mac, from the command line and from Python alike.

**Verdict: it differs**, on two points.

**First — the list of template variables grew at 5.0, and 5.3's release notes add to it.**

- **4.5** knows four: the blend-file's name, the frames per second, and the two resolutions.
- **5.0, 5.1, 5.2 and 5.3** know those four and six more: the scene's name, the camera's name, the node's own name, the blend-file's folder, and the library blend-file's name and folder.
- **5.3** adds, by its release notes, `{project_root}` and variables a project defines; its API says a project variable's name may not start with a digit and may hold only letters, digits and underscores, and its manual's templates page does not yet list them. In a file that belongs to no project, `{project_root}` was refused on the Mac as "Unknown variable referenced in template expression '{project_root}'", which is what any unknown name gets. What it gives inside a project was never tried.

5.0's release notes record the first addition in so many words, under the heading "More Path Template Variables". The hand tests confirmed it in all four earlier versions on both machines: in 4.5 a path holding `{scene_name}` is refused outright with "Unknown variable referenced in template expression", while in the other three it resolves to the scene's name. In 5.3 on the Mac `{scene_name}`, `{camera_name}` and the resolutions all resolved.

**Second — a slash inside a File Output node's input name.**

- **4.5** keeps the slash and makes the folders it implies. Inputs named `passes/diffuse` and `masks/object_01` produced folders called `passes` and `masks`.
- **5.0** replaces the slash with an underscore the moment the name is set. The names came back as `passes_diffuse` and `masks_object_01`, and **no folder was made**.
- **5.1, 5.2 and 5.3** keep the slash and make the folders, as 4.5 does. In 5.3 an input named `passes/diffuse` on a node writing PNG produced a folder called `passes`, and the slash stays on the node's face in the window. With the node left on the multi-layer OpenEXR it starts on, the same input made no folder and the node wrote one file — the manuals tie the folders to the Image media type.

Run in all four earlier versions on both machines, and it came back the same way on each — 5.0 alone replacing the slash and making no folder — so the difference holds on macOS and on Linux both; 5.3 was run on the Mac. 5.1's release notes say the same thing in their own words: the node "now allows specifying directories in item names. This was possible in older versions of Blender and the functionality is now restored." 4.5's and 5.0's manuals say nothing about slashes in a name; 5.1's, 5.2's and 5.3's document the rule.

**Documented and observed disagree in all four earlier versions, identically.** Every one of those manuals shows a picture of the tooltip for a broken template expression, headed "Syntax error(s):". In every one the Creator saw the live tooltip headed "Path template error(s):" instead. That is the manual being out of date in all four, not a difference between versions. **In 5.3 it is not established:** its manual's picture is recorded as a tooltip reading "Invalid or incomplete template expression '{blend_name.png'.", with no heading noted, and no tooltip could be photographed at 5.3's window. What 5.3's window did show is under question 5.

## 4. Does Blender make folders that are not already there when it writes?

**Yes, in all five, and it makes a whole chain of them rather than only the last one.** A hand test rendered into one missing folder and then into two nested missing folders, and both were made and both frames written, in all four earlier versions. Another did the same for a File Output node's own folder, two levels deep, and it too was made in all four. Both were run from a terminal with no window open, so folder-making is not something the interface does on Blender's behalf. **Both were run on the rented Linux machine as well, in all four versions, and agreed with the Mac exactly** — one missing folder made, a chain of two made, and the node's own two-level folder made, windowless there too. **5.3 did the same on the Mac**: with no window, the scene's own output folder one, two and three levels deep, from Python and from the command line, the node's own two-level folder, the folder a slash in a node input's name asks for, and the render cache folder were all made; and Ctrl-F12 at 5.3's window made a missing chain of two and wrote all three frames, with nothing in the Info list.

**Verdict: the same everywhere** — settled on macOS and Linux in 4.5 to 5.2, which agreed, and on macOS in 5.3.

**What the documents say, which is not the same.**

- **4.5 and 5.0** — not in the sources. Not one of the four manuals mentions folder-making at all.
- **5.1, 5.2 and 5.3** — one narrow case is documented: folders implied by a slash in a File Output node's input name are made. The scene's own output path is not in the sources. In 5.1 and 5.2 the documented sentence does not reach the node's own folder field either; 5.3 reads the same sentence — "Any missing directories are created automatically during output" — as possibly broader, but sitting under the paragraph about input names, so whether it covers the node's own folder is left open there.

**This is the documentation differing, not Blender.** The documented corner in 5.1, 5.2 and 5.3 is exactly the case that question 3 shows works in 4.5, 5.1, 5.2 and 5.3 and does not work in 5.0. The general folder-making — the scene's output path, and the node's own folder — is undocumented in all five and behaves identically in all five, the earlier four on both machines and 5.3 on the Mac.

**Not established, and worth saying plainly:** whether any of this holds on Windows is untried in every version, and on Linux it is untried in 5.3.

## 5. What does a write do when its folder is not there, when there is no room left, or when it cannot be written to?

**All three cases below are the scene's own output path.** Every test behind this answer set that path and nothing else — there was no File Output node in any of them. A node's own write fails differently, and question 12 holds that case: the render carries on and the exit code stays 0.

**All five versions answered "not in the sources" for all three cases.** All five also record the one failure their manuals *do* describe, which is a different failure: a broken template expression in the path, which makes an animation render fail with a message naming the fault. 5.3 adds two more documented failures that are different again: an error when render output is switched off and no File Output node exists, and a video that "might become unplayable" if a problem occurs while rendering.

**A folder that is not there** — no failure at all. It is made and the frame is written. All four earlier versions, on both machines, and 5.3 on the Mac, from Python and from the command line alone.

**A folder that cannot be written to** — all four versions, on both machines. **What the render does is identical everywhere**: it stops at the very first frame, frames two and three are never attempted, the folder is left completely empty with not even a part-written file in it, and a Blender started with no window ends with an exit code of 1. The same happens whether the render is started from Python or straight from the command line.

**In 5.3 a folder refused by its own permissions was not run**: a folder on a disk image mounted read-only was tested instead. It behaved the same way — stopped at the first frame, the folder left empty, exit code 1, from Python and from the command line alone — and printed the same two lines 5.0, 5.1 and 5.2 print on the Mac for a folder refused by its permissions, `ERROR OpenImageIO write failed: Could not open file "…"` and `Error: Render error (Undefined error: 0) cannot save: '…'`. The refusal comes from the volume and not from the folder's permissions, so it is not the same test, and what 5.3 does in the earlier versions' case is not established.

**No room left on the volume** — settled on macOS and on Linux in all four earlier versions, and on macOS in 5.3. It was run four times over, once on the Mac and three times on Linux, and **the exit code is not the same in all four runs**.

- **A three-frame animation onto a two-megabyte volume, on the Creator's Mac**, at 2000 by 2000 in uncompressed 32-bit OpenEXR. The first frame is written as far as it will go, leaving a part-written file of 1,908,736 bytes that Blender reports as `Saved` on the same line as the failure; the render then stops at the second frame, the third is never attempted, and the process ends with an exit code of **1**. All four earlier versions, and 5.3 the same to the byte.
- **The same test on a rented Linux machine**, with a control run into a folder with room to spare that wrote all three frames and ended at 0. The same shape as the Mac, in all four versions: a part-written first frame of 1,945,600 bytes announced as `Saved`, the render stopping at frame 2, frame 3 never attempted, exit code **1**. Linux added two things. It left an **empty second file** of no bytes where the Mac's volume held only the first. And the part-written frame is **not a picture in any version** — handed back to Blender's own image reader it was refused as an unknown kind of file, reported as 0 by 0 with no channels, and gave back no colour, where the control's whole first frame opened as a 2000 by 2000 picture with four channels. The byte counts differ between the two machines because the two volumes had different amounts of room; that is the disk and not Blender.
- **One still onto a disk already full, on a rented Linux machine**, at 1920 by 1080 in PNG, rendered on the graphics card, the machine's real disk filled with ballast until two megabytes were left. Blender printed its ordinary `Saved:` line and ended with an exit code of **0**, in all four versions, over a PNG that is not whole. That much was checked twice, the second time with a corrected check. What Blender printed in those runs was not kept, so nothing here says whether it said anything about the disk.
- **A 400-frame animation that filled the disk part way, on a rented Linux machine with four cards**, at 4000 by 4000 in PNG with compression off, about 1.5 gigabytes left at the start. Blender ended with an exit code of **1**, announced twenty-five frames as saved, and the twenty-fifth is half a picture — 33,988,608 bytes where a whole one is 64,105,848. **Blender 5.2 alone**; the other four were never run for this. As above, what it printed was not kept.

**And the rule that reconciles the four.** The part-written frame never sets the exit status. What sets it is the next write, the one that cannot even be opened. Where there was no next frame — the single still — Blender ended at 0.

**Verdict: it differs** — not in what a render does, but in what it says while doing it.

**What differs, version by version.** The wording changed at 5.0. For a folder that cannot be written to the split falls in the same place on both machines: **4.5 gives the operating system's own reason for the failure, and 5.0, 5.1 and 5.2 give an image-library line that does not say why.**

- **Unwritable folder, on the Mac.** 4.5 prints a line naming the file and `Permission denied`, then `Error: Render error (Permission denied) cannot save: '…'`. 5.0, 5.1 and 5.2 print `ERROR OpenImageIO write failed: Could not open file "…"` instead, followed by `Error: Render error (Undefined error: 0) cannot save: '…'`. 5.3 was not run with this case; its read-only stand-in is above.
- **No room left, on the Mac.** All four end with `Error: Error writing render result, No space left on device (see console)`, but the lines before it differ: 4.5 says `OpenEXR-writePixels: ERROR: Failed to write pixel data to image file "…". No space left on device.`; 5.0 says `IMB_exr_write_channels: Failed to write pixel data … No space left on device.`; 5.1 and 5.2 say only `Unknown error in IMB_exr_write_channels`. **5.3 names the cause**: `imb_exr_write_channels: Failed to write pixel data to image file "…". No space left on device.`, then `IMB_exr_write_end: No space left on device.`, then the same closing line and `Error: Render error (No space left on device) cannot save: '…/img_0002.exr'`. **The 5.2.2 run — the same test on the same Mac the same day — named the cause too**, as `IMB_exr_write_channels: Failed to write pixel data …` and then `IMB_exr_begin_write: No space left on device.`, where 5.2's record, taken on an earlier 5.2 build under an earlier macOS, says `Unknown error`. So the lost reason belongs to 5.1 and that 5.2 build as they ran on their day; whether the build or that day's macOS decided it is not settled, and it is not a 5.3 change. What does differ between 5.2.2 and 5.3 on the same day is the names of Blender's own writing steps in those two lines — `IMB_exr_write_channels` against `imb_exr_write_channels`, and `IMB_exr_begin_write` against `IMB_exr_write_end` — which is on the list at the top.
- **No room left, on Linux**, in the three-frame run — the only one of the three Linux runs whose output was kept. Every version names the cause and the file: 4.5 says `OpenEXR-writePixels: ERROR: Failed to write pixel data to image file "…". No space left on device.`, and 5.0, 5.1 and 5.2 say `IMB_exr_write_channels: Failed to write pixel data to image file "…". No space left on device.` **So the reason 5.1 and 5.2 lose on the Mac they keep on Linux** — a change between versions that shows on one machine and not on the other, which is how it is written on the list at the top. 5.3 was not run on Linux.
- **The layout changed too.** From 5.0 each line carries a timestamp and a channel name — `00:00.533  image.write      | ERROR …` — where 4.5's lines are plain. That held on both machines, and 5.3 prints the same layout on the Mac. 5.0's own release notes corroborate it: "The format of logging output has changed, including background render progress. Add-ons or render farms parsing this output may need to be updated."

The unwritable-folder test was run in all four earlier versions on each machine and came back differently between the versions on each, which is what settles this as a real difference in Blender rather than a gap in anybody's manual. 5.3 was not run with it.

**The exact words differ between the two machines as well, and that is the operating system rather than the version.** For an unwritable folder:

- **4.5.** The Mac put the real reason in the brackets — `Error: Render error (Permission denied) cannot save: '…'`. Linux put `Error: Render error (Invalid argument)` in the brackets instead, and printed the system's own `Permission denied` on the line above. **Both machines print that `Permission denied` line**; what changes is what the brackets carry.
- **5.0, 5.1 and 5.2.** Both machines print the image-library line and then an empty reason in the brackets, but they word the emptiness differently: the Mac says `(Undefined error: 0)` and Linux says `(Success)`. Neither says why the write failed.

**What Smoozy should take from that.** A program watching for particular words in a failure will see different words on the artist's Mac and on the machine the render actually runs on, in the same Blender. And the exit code carries less than it looks:

> Exit 1 is trustworthy where Blender means it: a missing blend-file, no camera, a device it will not take, a broken path template, a folder it cannot write into, a name too long, an interrupt — every one ends at 1 with nothing written, in all four versions on both machines. **Exit 0 is what cannot be trusted.** Where a write starts and then runs out of room, Blender leaves a part file, prints an ordinary `Saved:` line for it, and does not treat that as a failure. The render ends at 1 only when a **later** write fails outright, which needs there to be a later frame — a single still on a full disk ended at 0 in all four versions, a three-frame animation on a full volume ended at 1 in all four, and a 400-frame animation that filled the disk part way ended at 1 in the one version it was run in. A File Output node's failure never ends the render and never moves the status. **So the rule is narrow: exit 1 means something went wrong; exit 0 does not mean every file is whole.**

**5.3 breaks one item on that list.** A scene with no camera, rendered from the command line, ends at **0** in 5.3 with nothing written — settled under **Reports 1, 2 and 12**, and met in this topic when `-S` switched a 5.3 render to a scene with no camera (question 13). The rest held in 5.3 wherever it was run, which is the Mac: a broken template, a read-only folder and a name too long each ended at 1 with nothing written, and a three-frame animation onto a full volume ended at 1 over a part-written first frame announced as `Saved`.

**One thing that is easy to read the wrong way.** Catching a render failure inside a Python script does not change the number the run ends with. In 5.2, with saving switched off, a caught refusal ends at 0 — and **Reports 12** records the same refusal ending at 0 from the plain command line, with no script anywhere. A scene with no camera ends at 1 whether the script catches it or not — **Reports 2** — and in 5.3 a script's own render call still does, though the command line ends at 0. The number is whatever that particular failure gives; the catching does not move it. What settled the 0 was one test, on macOS, and in 4.5, 5.0 and 5.1 that test raised no render failure at all, because the switch it turns off does not exist there. **5.3 does what 5.2 does**, on the Mac: with saving switched off, a caught refusal from Python ends at 0, and a single frame and an animation started from the command line on a file saved that way each print `ERROR Render output disabled in Output properties and no active compositing File Output nodes`, write nothing and end at 0. A broken template caught inside a 5.3 script still ends at 1.

**The broken-template failure is the same in all five**, word for word — the earlier four on both machines, 5.3 on the Mac: the same message from the path-building call and from the render, nothing written, exit code 1 with no window. At the window — the Mac only — 4.5 to 5.2 showed a File Path field drawn filled dark red with white text, the same tooltip, a render window holding no image, and the same message in the status bar and in the Info list. At 5.3's window the field was drawn in red, nothing was written, and the status bar showed, beside a red error mark, `Parse errors in path '//out_{blend_name.png':- Invalid or incomplete template expression '{blend_name.png'.`; the tooltip and the Info list were not seen.

**Not established.** What any of the three cases does on Windows, in any version, and on Linux in 5.3. What 5.3 does with a folder refused by its own permissions. What a disk filling part way through a long animation does in 4.5, 5.0, 5.1 and 5.3 — that run was made in 5.2 alone. What Blender printed about the disk in the two Linux runs whose output was not kept. And which of the differences between those two Linux set-ups — the file format, the number of frames, or whether the disk was already full before Blender started — accounts for their different exit codes.

## 6. What are the ways a render can be started, and what does each of them write?

**The routes that are the same in all five.** 5.3 labels them **documented**, apart from the two Sequencer entries below.

- **The Render menu** holds the same six entries in all five, in the same order: Render Image on F12, Render Animation on Ctrl-F12, Render Audio, View Render, View Animation, and Lock Interface. Neither of the two render entries passes a "write image" argument at all. In 4.5 to 5.2 it was seen at the Mac's window, by the Creator, with the same tooltips in all four. One limit on that claim of sameness: the tooltips were read for all six in 4.5, for four of the six in 5.0 and for two of the six in each of 5.1 and 5.2, all matching, and the rest were never read. In 5.3 the menu was opened at the Mac's window and photographed, and its own drawing code read: the same six, with the Mac showing Render Animation on ⌘ F12, View Render on F11 and View Animation on ⌘ F11; Render Image starts the render with only "use the 3D Viewport" set and Render Animation adds the animation switch. No tooltip appeared under 5.3's simulated pointer, so 5.3's tooltips were not read.
- **What F12 and Ctrl-F12 write** is the same in all five: F12 writes nothing, Ctrl-F12 writes the frames. At the Mac's window, by the Creator in 4.5 to 5.2, where Ctrl-F12 wrote one file, `img_0001.png`; in 5.3 by a script starting the render exactly as the menu does, which wrote `img_0001.png` to `img_0003.png` for a three-frame range. A key pressed by a person was never tried in 5.3.
- **The command line.** A single frame is written; an animation is written. Same in all five — the earlier four **on both machines**, 5.3 on the Mac.
- **From Python.** A still asked to save writes one file with **no frame number** in its name; an animation writes with the frame number. Same in all five — the earlier four **on both machines**, 5.3 on the Mac.
- **The viewport route refuses to run with no window**, in all five, with the same message: "Cannot use OpenGL render in background mode (no opengl context)". Nothing is written on any of its three shapes. Same in all four earlier versions **on both machines**, and in 5.3 on the Mac — and on Linux the machine had a working screen of its own with the display deliberately hidden from Blender, so the refusal really is about having no window and not about the computer lacking a screen.
- **A video.** One file holding the whole frame range in its name. Same in all five — the earlier four **on both machines**, 5.3 on the Mac. In 5.3 a script cannot choose the video format while the media type is still Image — the format is not among those offered and the attempt is refused — and the 5.2.2 run refused it the same way on the same Mac the same day; with the media type set to Video first, it is taken. Two runs of the earlier versions disagree with each other about which of them take the format directly, and nothing here settles that.

**And the Linux machine answered the half the Mac never could, in 4.5 to 5.2.** The Mac's terminal tests could only show the viewport route being refused, and the Creator's window tests used the menu rather than the call. The rented machine has a screen of its own, so Blender was started **with a window** there and asked for the same three calls. All three succeeded, in all four versions, and what they write is: told to save a still, one file with **no frame number**; an animation, one file **with** the frame number; told not to save, nothing at all. So the refusal recorded above is about having no window, not about the route itself. Run on Linux only in those versions. **5.3 was asked on the Mac, with its window open**, and came out the same shape: the still entry, started as a click starts it, wrote nothing; the animation entry wrote numbered frames; called directly and told to save a still, it wrote one file with no frame number and printed `OpenGL Render written to '…'`; told to render an animation, numbered frames. Because the machines differ, that says nothing about macOS in the earlier four or Linux in 5.3.

**Verdict: it differs**, on four points.

**First — the 3D Viewport's render entries are named differently.** In 4.5 they read `Viewport Render Image`, `Viewport Render Animation`, `Viewport Render Keyframes`. In 5.0, 5.1, 5.2 and 5.3 they read `Render Viewport Preview`, `Render Playblast`, `Render Playblast on Keyframes`. The calls behind them are identical in all five, and neither of the first two passes a "write image" argument. Seen at the Mac's window, in all four earlier versions, **on the Mac only** — nobody has opened those menus on the Linux machine. In 5.3 the names and calls were read from the menu's own drawing code on the Mac; the menu was not photographed open. What they write is the same everywhere it was tried: the still one writes nothing, the animation one writes the frames.

**Second — two Sequencer render entries exist from 5.0 and not in 4.5.** 5.0, 5.1, 5.2 and 5.3 all document `Render Sequencer Image` on Alt-F12 and `Render Sequencer Animation` on Ctrl-Alt-F12, appearing when a sequencer scene differs from the active one. 4.5's documents find nothing of the kind anywhere in its manual. 5.0's release notes record them as new: "If the sequencer scene differs from the active scene, the Render menu will show new options for 'Render Sequencer Image' / 'Render Sequencer Animation' on top of the normal scene render operators." What they write is not stated in 4.5 to 5.2; 5.3 marks **inferred** that they write as the two ordinary entries do, from its manual saying a sequencer scene's render and output settings are the same as any scene's. The Creator's look at the Render menu saw no Sequencer entries in any of the four earlier versions, and 5.3's menu in its factory start-up file drew none either, but no sequencer scene was ever set up, so that says nothing either way. This difference rests on the manuals and the release notes, which say nothing about any particular computer.

**Third — the File Output node stopped naming single renders with a frame number.** In 4.5 the node writes on all three shapes of the Python render call, and its file carries the frame number every time. In 5.0, 5.1, 5.2 and 5.3 the node still writes on all three, but the frame number appears only on the animation call: a single render writes `nd_Image.png`, an animation writes `nd_Image0001.png`, and `-f` and `-a` from the command line both write `nd_Image0001.png`. All four earlier versions **on both machines**, and 5.3 on the Mac. 5.0's release notes state the change: "The File Output node now only appends the frame number to the image name when doing an animation render. Rendering through the command line always does an animation render, so no change of behavior is expected."

**Fourth — 5.2 and 5.3 can be told not to write at all**, and 4.5, 5.0 and 5.1 cannot. See question 7. In 5.3 a single frame from the command line is refused that way as well as an animation (question 5).

**A documentation difference sitting inside this question, which is not a behaviour difference.** 5.1's, 5.2's and 5.3's manuals state plainly that a still render is not saved automatically. 4.5's and 5.0's leave a reader to work it out from a contrast between a still held in a buffer and an animation saved to a drive. Blender does the same thing in all five — the Creator's hand test at the Mac's window proved it in 4.5 to 5.2, and the window test proved it in 5.3 — and only the manuals differ.

## 7. If a render can be set up so that it writes no files, what does it leave behind?

**In all five versions**, a still render that is not told to save writes nothing, and what it leaves behind is an image held inside Blender called the Render Result. A hand test showed the same thing in all five, from a terminal with no window at all: the Render Result data-block is present before the render as well as after, it reports a size of zero, nothing is written to the output folder, and Blender's temporary folder is empty both before and after. **The same test in all four earlier versions on the rented Linux machine agreed exactly**, so this rests on two operating systems for those four, and on macOS for 5.3. What becomes of the Render Result once the process ends was not tested and cannot be — the process is gone. 5.3 labels the parts it documents — a still not saved, the Render Result being temporary, the error when an animation has nowhere to write — **documented**, and whether any of the leftovers it lists is actually present after such a render **inferred** or not stated.

**A related worry is settled the same way in all five**: a large Cycles render, with the tile size forced small, left **nothing** in Blender's temporary folder — before, during or after. This matters because two readings of the sources lead the other way: the manual says the temporary folder holds render layers at run time, and Cycles' own words say tiles are cached to disk while rendering. The test settled it: nothing was in the temporary folder before, during or after, in every version. **What "during" means here:** the listing was taken at the moment the frame was announced written, and a listing at three moments cannot see a file made and removed between them. Question 11, item 8, watched continuously and found Cycles' tile file in the temporary folder while a large frame renders, gone before Blender exits, in all five versions. Nothing of it is left behind.

**And it was run twice over on the second machine, once on the processor and once on the graphics card.** On Linux the same large render on the processor left the temporary folder empty before, during and after, in all four versions. Then Cycles was pointed at the NVIDIA card with the processor switched off — something only that machine can do — and the temporary folder was empty before and after there too, in all four versions. The earlier runs cover the tested Mac and Linux machines, with the NVIDIA graphics run on Linux. They do not establish the earlier versions on the Mac's graphics. In 5.3 the large render was also run on the Mac's own graphics: the tile file came and went inside the render, and the temporary folder was empty afterwards.

**One thing a Cycles render on the graphics card does leave behind, seen in 5.3 alone.** On the Mac's own graphics, 5.3's Cycles read its compiled kernels from a folder in the user's home folder, `~/.cache/cycles/kernels/Apple_M1_Pro/`, created four new files there and changed the modified time of 83 others, and those stayed afterwards. That folder is outside both Blender's temporary folder and the run's own settings folder, so neither kept it out. macOS's own graphics-library cache was written to as well, and EEVEE and Workbench held that cache open too. No earlier version was looked at this way, so this is not a difference between versions.

**One thing a windowed Blender does leave behind.** When a Blender started with a window was told to quit, it printed `Saved session recovery to "…/quit.blend"` — a recovery copy of the open file, written into Blender's temporary folder on the way out. No windowless run on any machine printed anything of the kind. In 4.5 to 5.2 it was seen on the Linux machine — `/tmp/quit.blend` — and not established at the Mac's window, where a windowed Blender was opened and quit without anything being recorded either way. In 5.3 every windowed run on the Mac printed it, into that run's own temporary folder. Because the machines differ, that says nothing about the Mac in the earlier four or Linux in 5.3.

**Verdict: it differs**, on two points.

**First — 5.2 and 5.3 can be told to stop writing altogether, and 4.5, 5.0 and 5.1 cannot.** 5.2 and 5.3 have a `save_output` switch, on by default, with a checkbox in the Output panel's header. In 4.5, 5.0 and 5.1 there is no such property at all and the attempt to set it fails outright; in 5.2 and 5.3 it is there and can be set. Run in all four earlier versions **on both machines**, and in 5.3 on the Mac. 5.2's release notes record it as added: "Saving render output can now be disabled."

**And turning it off is not a silent render.** With the switch off and no File Output node present, an animation render is **refused**, with the message `Error: Render output disabled in Output properties and no active compositing File Output nodes`. In 5.2 that refusal was seen on both machines, word for word, and on Linux the output folder was not even created; in 5.3 it was seen word for word on the Mac, from Python and from the command line, and the output folder was not created there either. 5.2's and 5.3's manuals document the rule: with the switch off Blender relies on other systems, and if no File Output node exists an error is reported. 5.3's manual adds that the two playblast entries raise an error when render output is switched off.

**Second, and much smaller — what else is left in memory.** The listing of image data-blocks came back with two entries in 4.5, 5.1, 5.2 and 5.3 — the Render Result and a second one called Viewer Node — and with the Render Result alone in 5.0. **The Linux machine gave exactly the same split** in the earlier four, so this is not a quirk of one computer; 5.3 was run on the Mac. Nothing in any version's findings explains why. It is recorded here because the same test came back differently between versions on both machines, and left alone because nothing more is known about it.

**What is the same.** The Render Result exists in a windowless Blender and can be reached from a script, in all five. The small no-save tests left the output and temporary folders empty: the earlier four on both machines, and 5.3 on the Mac. This does not establish that every render told not to save leaves the whole disk untouched; the 5.3 graphics run wrote the kernel files described above. The render cache is off by default in all five, and switching it on writes a cache file.

## 8. How does the place a file records for writing become the name of a file on disk? Say where a frame's number appears in it, and what decides the end of the name.

**For the scene's own output path, the answer is identical in all five versions.** The hand tests behind it were run in all four earlier versions on the Mac and again in all four on the rented Linux machine, coming back the same name for name, so for those four what follows rests on two operating systems rather than one; 5.3 ran the same tests on the Mac and every name matched. **The rules below were taken from a command-line frame render, a command-line animation render and a Python animation render.** The Python still call is the exception, and it has a bullet of its own at the end. 5.3 labels the padding, the four added digits and the extension **documented**, and marks **inferred** that the path-building method gives exactly the name a render writes, that File Extensions off leaves no extension, and that a File Output node's single render carries no frame number without hash marks; its tests settle all three on the Mac.

- Template expressions are replaced when the path is used, and a leading `//` becomes the blend-file's folder. Their order relative to each other is not established.
- **The frame number goes wherever the hash marks are**, padded to as many digits as there are marks. If there are no hash marks it is added on the end, four digits wide. A run of hashes in a **folder** name is left alone. With two separate runs of hashes in the name, 5.3 turned only the last into the frame number and left the first as written; no earlier version was asked.
- **The padding is a minimum, not a maximum.** Frame 99999 with no marks writes `img_99999.png`; frame 12345 against two marks writes `img_12345.png`.
- **What decides the end of the name** is the File Extensions switch plus the chosen format. With it off, nothing at all is added. With it on, the extension for the chosen format is added — except that a matching extension already typed at the very end of the name is not doubled. One typed in the middle of a stem **is** doubled: `out_.png` becomes `out_.png0007.png`. In 5.3 the same held for a single frame from the command line given `-o …/typed.png` with no hash marks: the frame number went after the typed extension and the file was `typed.png0001.png`.
- A path ending in a separator gives a file whose whole name is the frame number. **An empty path was only ever put to the path-building call, which builds a name and writes nothing**: asked for frame 7 it gave back `0007.png`, in all five versions. Nothing here says what a render does with an empty output path — a real render with one fails from 5.0 on, settled under **The compositor 2**.
- A view's own ending lands **after** the frame number and **before** the extension, whether a `%` is in the name or not.
- A video gets one file with the whole frame range in its name — `mov_0001-0005.mkv` — unless hash marks are typed in, in which case the marks are left in the name untouched.
- All five record the same observed finding from Cycles' own files: Cycles builds the names it looks for by calling Blender's own path-building method, under a comment saying it is matching Blender's render output file naming. All five label that **observed**. They then part company over the step beyond it. 4.5, 5.0 and 5.3 take that step — the method therefore gives the name a render writes — and mark it **inferred**. 5.1 and 5.2 refuse to take it at all. The caution is earned, and a hand test shows it the same way in all five: asked for frame minus two, the method gave `img_-0002.png` and the render wrote `img_0000.png`.
- **Through the Python still call — `render(animation=False, write_still=True)` — the frame-number rule does not hold.** Hash marks are left in the name as literal characters, settled under **Dependencies 17**; and with no hash marks no frame number is added at all, so an output path ending `s_` gave `s_.png` where the same file's animation render gave `s_0001.png` — all five versions, and the same `Saved:` line either way (**question 6**, from the same run). Only one still was rendered that way, so nothing on record shows two frames colliding on the one name; but nothing in the name would tell them apart.

**Verdict: it differs** — for the File Output node, and only for it.

**What differs, version by version.**

- **The format a fresh node starts on.** With the node's own format left exactly as the version gives it, 4.5 wrote `nd_0001.png` and 5.0, 5.1, 5.2 and 5.3 wrote `nd_0001.exr` — because a freshly added node starts on PNG in 4.5 and on Multi-Layer OpenEXR from 5.0 on, and **that starting value is itself the version change**. The general rule for what each mode names its file is settled under **File output nodes 1** and **6**.
- **The name, with a still-image format set on the node.** In **4.5** it is the node's folder, then the slot's own piece of path, then the frame number, then the extension; the input socket's name does not appear separately, and the file came out `nd_0001.png`, on both machines. In **5.0, 5.1, 5.2 and 5.3** it is the node's folder, then the node's file name, then the input's name, then the frame number, then the extension, and the file came out `nd_Image0001.png` in all four — 5.0 to 5.2 on both machines, 5.3 on the Mac. 5.0's and 5.3's manuals state the shape outright.
- **And from 5.0 the frame number appears only on an animation render** — see question 6.
- **From 5.0 the node shows the finished names before anything is rendered.** The Creator found a panel headed **Output Paths** in the node's sidebar in 5.0, 5.1 and 5.2, holding the full finished file name. 4.5's sidebar has no such panel; it shows a File Subpath and a Use Node Format switch for each input instead. Seen at the Mac's window only; nobody has opened that sidebar on the Linux machine. 5.0's release notes record it: "The final paths of the images are displayed in the UI to remove guess work." **In 5.3 this topic did not see the node's own sidebar panels**; **Reading a file 4** and **File output nodes 2** record its Output Paths panel in 5.3, on the Mac.

**One caution about the sidebar look.** The file the Creator opened carries three inputs in 4.5 and two in the other three. What the screenshots show is still what each version's node looks like; **the input count is an accident of the file, not a version difference**.

**On the order of the steps:** the sources do not state one. Template-before-frame-number was observed in all five on the Mac and in 5.0–5.2 on Linux; the 4.5 Linux run did not establish it. No fuller sequence is established.

## 9. Can the place a file output node writes to be settled for a render — at the moment the render is started, and by writing it into the file from outside Blender?

**Yes on both halves, in all five versions**, and by the same route.

- **There is no command-line argument for it in any version.** The argument lists document only the option for the scene's own output path. A hand test confirmed in all five: pointing that argument at a third folder moved the scene's own output and **left the node exactly where it was**, with its stored value unchanged afterwards. The same on the Linux machine, in all four earlier versions; 5.3 on the Mac.
- **A script handed to Blender at launch reaches the node's values, and the render that follows uses them.** All five versions — the earlier four on both machines, 5.3 on the Mac. Every version labels the reasoning **inferred** and every version's test confirms it.
- **A windowless Blender can write the new place into the file and save it.** All five versions — the earlier four on both machines, 5.3 on the Mac: the values were still there when the file was reopened.
- **Path templates are the one documented way** to make a node's place come out differently per render without anything being edited, in all five.
- **Editing a blend-file with a tool that is not Blender** is not in the sources in any version, and was never tested. 5.3's manual says only that a compressed blend-file uses a compression other tools can undo, and nothing about editing what is inside.

**Verdict: it differs** — not on whether it can be done, but on what you have to write and what else is available.

**What differs, version by version.**

1. **The two values you set have different names.** In 4.5 they are the node's base path and the slot's path piece. In 5.0, 5.1, 5.2 and 5.3 they are the node's directory and file name. This is question 2's difference showing through, and anything driving Blender from outside must get it right per version. **And in 4.5, when the node is gathering its outputs into one multi-layer file, that base path is used as the start of the file name and not only as a folder** — without a trailing separator the file lands *beside* the folder rather than in it (**File output nodes 6**). Anything writing a folder into that property in 4.5 should end it with a separator.
2. **The call that walks every file path a blend-file holds does not exist in 4.5.** Run in all five: in 4.5 there is no such call at all and the attempt fails outright; in 5.0, 5.1, 5.2 and 5.3 it exists and works. In 5.0, 5.1 and 5.2 it visited only an ordinary loaded image and did **not** visit the File Output node's folder, nor the scene's own render output path; in 5.3, on a file with no image loaded, it visited nothing at all, which is what the earlier three gave on the same kind of file — **but the call was made with no options at all**, and 5.2's three options were never passed. The same in all four earlier versions on both machines, and in 5.3 on the Mac. 5.2's release notes add those three options and aim them at exactly this kind of work: "Three new options for `bpy.data.file_path_foreach` so render farms and other scripts can find all relevant image files for rendering, including the new Cycles texture cache." What they do was never tried, and whether 5.3 carries them was not checked.
3. **A node's place can be made to depend on the node's own name from 5.0**, through a template variable that 4.5 does not have, and in 5.3 on project variables as well, by its release notes. See question 3.

**The node's shipped file name.** 5.3's release notes say a new File Output node's file name is *now* `{blend_name}`, so rendered images are named after the blend-file; a node made fresh by a script in 5.3 does start with it. 5.2 already behaves that way in the same test — question 14 — so the note marks no change between 5.2 and 5.3; it is on the documentation list at the top.

## 10. Can the place a render records for writing carry characters that the computer it lands on will not accept, and what does a render do when it does?

**All five versions answered "not in the sources"** for what a render does. All five record the same near-miss and refuse to carry it across: Blender ships a helper that replaces awkward characters in a name, but nothing says a render path is ever passed through it. All five note that the only place any Blender manual writes down a forbidden character set is about asset catalogs, not file paths. 5.3 marks **inferred** that a path can carry such characters at all, from its manual saying names may hold any text but the null character and that templates put names into the path.

**What the hand tests showed, identically in all five versions** — the earlier four on both machines, 5.3 on the Mac. As in question 5, every one of them is the scene's own output path.

- **Neither computer refuses anything but length.** On the Mac, ordinary empty files were made with a colon, an asterisk, a question mark, a pipe, a backslash, Cyrillic letters, an emoji and a trailing space in their names, and macOS refused none of them. On the Linux machine the same list was tried, plus a semicolon, a dollar sign and a name holding a line break, and every one succeeded. Length is the one thing Linux refuses: a name of 255 characters was made and one of 256 was not, and a whole path built past the system's own maximum failed as well. In 5.3's sitting the Mac again refused none of its eight names.
- **Blender stores and writes them as asked**, in all five — the earlier four on both machines, 5.3 on the Mac, where `dot._` also came out as asked, `dot._0001.png`. Nothing was cleaned up, nothing was refused, and the name on disk is the name that was asked for. The one exception is the backslash, which Blender itself turns into a folder separator — so a folder appeared rather than a file with a backslash in its name. On Linux this was pinned down: the machine itself takes a backslash in a name quite happily, so the folder is Blender's doing.
- **The field silently cuts a path at 1023 characters**, in all five — from a script on either machine and when text is pasted in at the Mac's window, and in 5.3 both ways on the Mac.
- **A name longer than the computer will take is refused at the moment of writing**, in all five — the earlier four on both machines, 5.3 on the Mac: the render stops, nothing lands on disk, and a windowless Blender ends with an exit code of 1.

**Characters that arrive through a template, tried in 5.3 alone.** With the scene renamed `a:b*c?` and the path holding `{scene_name}`, 5.3 wrote `a_b_c__0001.png`: the colon, the asterisk and the question mark that came in through the template were each replaced with an underscore, while the same characters typed into the path itself reached the file name unchanged. Hash marks that come in through a template are not replaced — they become the frame number, as question 3 records. No earlier version was asked, so whether they clean template values too is not established, and this is not a difference between versions.

**Verdict: it differs** — on one point only, and it is the same point as question 5.

**What the refusal says differs between versions.** **4.5 gives the real reason and the later four do not** — 5.0, 5.1 and 5.2 on both machines, 5.3 on the Mac.

- **On the Mac.** 4.5 says `Error: Render error (File name too long) cannot save: '…'`. 5.0, 5.1, 5.2 and 5.3 print an image-library line — `ERROR OpenImageIO write failed: Could not open file "…"` — followed by `Error: Render error (Undefined error: 0) cannot save: '…'`, which does not say why. With a path already cut at 1023 characters, 5.3's image-library line carried a zero byte where its closing quote would be, and its `Render error` line ended in `... truncated` with no line break before the next line; no earlier record says what those lines looked like.
- **On Linux.** 4.5 prints the system's own `File name too long` on its own line, with `Error: Render error (Invalid argument) cannot save: '…'` after it. The later three print the same image-library line as on the Mac, followed by `Error: Render error (Success) cannot save: '…'`, which again does not say why.

The test was run in all four earlier versions on each machine and came back differently between the versions on each; 5.3 was run on the Mac. **The change of words between the two machines is the operating system, not the version**, and it is set out here rather than on the list of differences between versions.

**And in 4.5 on Linux, one and the same over-long name came back with two different wordings on different runs** — `(Invalid argument)` and `(File name too long)`. Both are real and neither was chosen. The explanation offered afterwards — that it turns on whether the folder in front is long enough for the whole path to meet Blender's own 1023-character cut — does not fit the runs that were recorded: the shorter 300-character name, which no cut touches, also came back `(Invalid argument)` on Linux. **What decides which of the two appears is not established.** **What Smoozy should take from that is that a program watching for one of those wordings would miss the other** — and there are four such wordings across two machines for what is one and the same failure.

**Everything else about this question is the same in all five**, on the machines each was run on.

**Not established, and this is the question where it hurts most.** Which characters an output path may hold on **Windows**, and what a render does when it meets one it may not, was never tried in any version, 5.3 included. That matters more than it sounds, because the two machines this project does have both refuse almost nothing: neither macOS nor Linux can show what a render does when the computer rejects an ordinary character, and Windows is the system that rejects them. The only refusal either machine produced was an over-long name — and even there, Windows has a shorter whole-path limit and is untried. That is a silence in every version equally, and it is **not** a difference between versions.

## 11. While a render is still working, what is present in the places it writes to, and how does that change with the size of the picture?

**All four earlier versions read the question the same way, and all four said so.** Every one of those documents flags the same ambiguity — "the size of the picture" could mean the number of pixels or the number of bytes — answers the pixel reading first, and then covers the byte reading separately. So the readings themselves do not differ. All four also note that a render writes to more places than the folder it was pointed at, and handle the wider circle separately. 5.3 takes the pixel reading without flagging the other, and handles the wider circle under question 7; its tests cover both readings.

**What the documents alone gave, and how it is labelled.** Finished frames already sitting in the output folder during an animation render — **documented** in all four. That the Placeholders setting exists, that the file it makes is empty and that it is off out of the box — **documented** in all four; that the empty file is put down *before* its frame is worked on is **inferred**, from the manual's render-farm recipe. A still render writing nothing at the output path unless it is asked to — **inferred**, from the manual's contrast between a still held in a buffer and an animation saved to a drive. The growing, not-yet-playable video file — **inferred**, from the manual's warning that an interrupted render can leave the file unplayable. Cycles' tile settings, the name, the default of 2048 and the range of 8 to 8192 — **observed** in all four, read straight out of Cycles' own files. The arithmetic comparing the picture's area against one tile's is **observed in 5.0, 5.1 and 5.2 only**, quoted out of Cycles' own interface file with the care that those lines exist to decide whether to show a warning rather than to decide how a picture is cut up; **4.5's sources state no such rule**, and 4.5 reaches the same threshold by inference from the manual's wording instead — **that is one version's search coming up empty, not an established difference in what Cycles' files hold**, and it is on none of the three lists. Where the cached tiles land — **not in the sources** in all four. Whether a frame's own file is ever visible on disk part-written — **not in the sources** in all four. At what moment within a frame a File Output node writes — **not in the sources** in all four either. The two-gigabyte video split — **documented** in all four, and all four carry the same words for Placeholders, for Overwrite and for Cache Result. **5.3 labels the same way, with two differences of reading.** It calls a still render writing nothing **documented**, from the manual sentence 5.1 and 5.2 also carry; and it does not take the step that the empty file comes before its frame, leaving that open. It quotes the area comparison out of Cycles' interface file as 5.0 to 5.2 do, **observed**, and adds from the same lines that the tile size Cycles uses is the setting rounded up to a multiple of 128 and no larger than 8192, once the setting is 128 or more. It too has nothing on where the tiles land, on a frame's file being visible part-written, or on when a File Output node writes, and it documents the two-gigabyte split in the same words.

**The rest was settled by hand**, in all five versions — the earlier four on the machines each item names, 5.3 on the Mac. Every test below was run with no window at all unless it says otherwise, each run pointed at a settings folder of its own.

**Verdict: it differs** in the two writing features below. The engine name and the tested OpenEXR size also differ, as noted under items 11 and 13 and question 14.

**What differs, version by version.**

**First — Cycles' Use Tiling switch still works in 4.5 and does nothing in 5.0, 5.1, 5.2 and 5.3.**

At 8000 × 8000 with the tile size left at its default, turning `use_auto_tile` off gave:

- **4.5** — **no tile file at all**, and no tiling line on the console. The switch works.
- **5.0, 5.1, 5.2 and 5.3** — the tile file appears anyway. Turning the switch off changes nothing that reaches the disk. In 5.3 the switch read back off and the tile file still reached 89,572,097 bytes, as with it on.

Run in all four earlier versions **on both machines**, and both machines gave the same split; 5.3 on the Mac. The documents agree with the test from their own side: 4.5's Cycles files carry Use Tiling as a live switch that is on by default, and 5.0's, 5.1's, 5.2's and 5.3's carry it as deprecated with the description "tiling is always enabled". 5.0's release notes record the removal outright. So this is a real difference in Blender, not a gap in anybody's manual, and it is on the behaviour list at the top.

**Second — 5.2 and 5.3 alone can write a texture cache beside the pictures a render reads.**

A picture written by Blender itself was used as an image texture and rendered with Cycles at 4096 × 4096.

- **4.5, 5.0 and 5.1** — nothing new appeared beside the picture, before or after. Asked what settings they even have for this, all three answered `no such setting: use_texture_cache` and `no such setting: use_auto_generate_texture_cache`. The switches do not exist.
- **5.2** — the switches exist. `use_texture_cache` reads **true** out of the box and `use_auto_generate_texture_cache` reads **false**, and there is a `texture_cache_directory` preference which starts empty. **At factory settings nothing appears beside the picture**, because one of the two switches is already on and it is the second that changes what lands on disk. With **both** turned on, a `blender_tx/` folder appears next to the image file, holding one file whose name is the image's own name followed by a long code and `.tx`, at 57,115 bytes for that picture.
- **5.3** — the same: the same two switches with the same values out of the box, the same empty preference, nothing beside the picture at factory settings, and with both on a `blender_tx/` folder holding `smoozytex.png.0-926BDA8569F1F2504902F06ABA51E46D.tx`, 535,017 bytes for its 1024 × 1024 picture. 5.3's manual says the files go in `blender_tx/` beside the image by default and its API says an empty preference means the image's own folder; the run went the manual's way.

Run in all four earlier versions **on both machines**, and both machines agreed; 5.3 on the Mac. 5.2's release notes describe the folder in the same terms. A real difference in Blender, and on the behaviour list.

**What is the same everywhere.** Every result below came back the same in every version it was run in — items 1 to 14 in all five, the earlier four on the machines each names and 5.3 on the Mac; items 15 and 16 in the earlier four alone.

1. **A still render writes nothing at the output path unless it is asked to** — with a window on screen and without. The folder was empty before the render, empty after a render with no save switch, and held one file after a render with the switch. The same test from the command line wrote one file. **Both machines**, all four earlier versions, and 5.3 on the Mac with its window and without. This agrees with what question 6 above already records.

2. **While a frame is being rendered, nothing at all stands for it in the output folder.** For the ten seconds or so a frame took, the folder held only the frames already finished. **Both machines**, all four earlier versions; 5.3 on the Mac, where a frame took about fifteen.

3. **While a frame is being *saved*, its file is on disk part-written.** It appears at or near zero bytes and climbs to its full size in about a fifth of a second at 1920 × 1080. **The file is built up in place** — no file under another name appears first, and nothing is renamed. **Both machines**, all four earlier versions; in 5.3 on the Mac each frame's file appeared at zero bytes and grew through 36 or 37 readings over about a tenth of a second, under its final name. This is the part every version's documents call *not in the sources*, and it is settled both ways: nothing while the frame renders, a growing file while it saves. The exact first size the watcher caught varies between runs, because it is a property of how often the folder was looked at rather than of Blender. **Question 14 settles the same point with a second instrument** — every file call Blender made, on Linux — and adds when that part-written window closes against the next frame.

4. **The bigger the picture, the longer that part-written file is visible, and nothing else changes.** At 10000 × 10000 a PNG climbed through some seventy recorded sizes over about three and a half seconds; the same animation at 8192 × 4608 took about two seconds where 1920 × 1080 took a fifth of one. OpenEXR and multi-layer OpenEXR behaved the same way over a shorter stretch. **Nothing appeared in the output folder at the large size that was not there at the small one.** **Both machines**, all four earlier versions. 5.3 on the Mac came out the same shape — a 10000 × 10000 PNG visible part-written for about four seconds, the two OpenEXR forms for about half a second, 8192 × 4608 for two to seven seconds, and nothing else in the folder — read by a watcher that looked every two milliseconds rather than every fifty, so its counts of sizes are not to be set beside the earlier four's.

5. **With Placeholders on, the empty file for a frame is put down before that frame is rendered, and is then filled in place.** It appears within about half a second of the render starting, ten seconds before the frame finishes, at **zero bytes**; the empty file for the next frame appears at the moment the previous frame's picture is complete. **They are made one at a time, for the frame in hand, never all at once.** **Both machines**, all four earlier versions, and 5.3 on the Mac. This settles the step the earlier documents mark inferred and 5.3 leaves open, and settles it the earlier documents' way.

6. **Whether a render stopped part way leaves the empty file for the frame in hand behind is not settled in 4.5 to 5.2.** These runs left it behind, at zero bytes, alongside the whole frames already done, with Blender ending at 143 — **both machines**, all four earlier versions, stopped by a terminate signal once frame 3's empty file had appeared, and 5.3 on the Mac, stopped by a terminate signal at a fixed thirty seconds, inside the third frame's render. **Frames** records the opposite from the same kind of stop, in its questions 3, 6, 10 and 15: nothing at all for the frame in flight, a placeholder included, in every version. The Creator's Mac is common to both topics and both claim all four versions, and neither reading can be read into the other. **Both records do say what Overwrite was set to, and both say off.** This topic's stop test runs on the set-up of the placeholder test above it, Placeholders on and Overwrite off, and the **Frames** side is recorded with the same two settings. So Overwrite is not what separates them, and neither is the signal — the Frames side covers an interrupt, a terminate and a kill alike, and this topic's used a terminate. **What does differ:** this topic's earlier-version stops were fired the moment frame 3's empty file appeared, and Frames' was sent fifteen seconds into a five-frame render at no particular moment; and only one of the four version records on the Frames side names the setting at all, the other three pointing back at a stop test whose set-up does not mention it. **Frames 16** holds the whole of the disagreement and what it costs; the short of it is that a leftover one blocks its frame for good, so anything restarting a stopped job must not trust the file count until this is settled by a run. **In 5.3 it is settled on the Mac, and the signal decides it**: there a terminate and a kill leave the empty file and an interrupt takes it away, which is Frames 16's 5.3 result and agrees with this topic's 5.3 terminate. That settles 5.3 and not the earlier four. **The stop was not aimed at the moment a frame is written**, so this does not settle what a stop landing *during* a save leaves behind either — and item 3 above shows that moment is a real window, about a fifth of a second wide at 1920 × 1080.

7. **Blender holds the file open with a write handle while it writes it.** Renaming the file at that moment was allowed, and the render still finished. **Both machines**, all four earlier versions, and 5.3 on the Mac.

8. **Where the cached tiles go: Blender's own temporary folder.** One file, an OpenEXR, named `cycles-tile-buffer-<process number>-<number>-0-0.exr`, reaching about 89 megabytes for one 8000 × 8000 frame, and **gone before Blender exits**. The same render at 1000 × 1000 opened no such file at all. **Both machines**, all four earlier versions, and 5.3 on the Mac — 89,572,097 bytes on the processor and 93,076,491 on the Mac's own graphics, which no earlier version was run on. This is the gap every version's documents name as the important one. Where within a run each tile file is made and removed — one per frame, not one for the job — is under question 14.

9. **The boundary is one tile's worth of pixels.** At 2048 × 2048 with the tile size at 2048, nothing appeared. At 2048 × 2049 the tile file appeared and grew. One row of pixels more than a single tile is enough. **Both machines**, all four earlier versions, and 5.3 on the Mac, where the file reached 6,169,360 bytes. Blender's own `Rendered 1/2 Tiles` line beside it is recorded in 4.5's documents only; the other four record the file appearing and say nothing about a console line. The area comparison 5.0, 5.1, 5.2 and 5.3 quote out of Cycles' interface code — the picture's area against one tile's area — gives the right answer at this boundary, and so does the same threshold 4.5 reached from the manual's wording instead. **It is not the arithmetic a picture is cut up with.** Every tile count on record is the number of whole tiles across times the number down, each side rounded up on its own: 2 at 2048 × 2049 above, 1024 at 8000 × 8000 with a tile of 256 in item 10 below, 4 at 2049 × 2049 under **Reports 7**, and 53,284 under **Settings 15**, for a render asked for at 32,767 per cent of 1920 × 1080 with the tile size never touched, which works out at 629,126 × 353,883. The area rule gives 977 and 53,081 for the two largest of those. The two rules agree at every threshold anybody has actually reached, so what crosses the threshold is still untested. And the quoted lines exist to decide whether to show a warning rather than to decide how a picture is cut up, which is the caution the *how it is known* paragraph above already carries.

   **A warning about how this test must not be read.** It was run two ways. The first instrument asked which files the Blender process had open, twice a second; a render at 2048 × 2049 is over in seconds, so a file opened and closed quickly can fall between two samples — and on the Creator's Mac it did, in three versions out of four, while the same run's own console line said tiling had happened. A second test watched Blender's temporary folder by name every twenty milliseconds instead, and found the file in **all four versions on both machines**. In 5.3 both instruments ran together on the Mac: the half-second one missed the file, and the one watching the folder every two milliseconds found it. **The miss is a fault in an instrument, not a difference between versions**, and nothing about it should be read as one.

10. **The tile size decides whether the tile file happens at all.** At 8000 × 8000 — 64 million pixels — a tile size of 8192 produced no tile file and no tiling line, because one tile is then larger in area than the whole picture. A tile size of 256 produced the file and had it written to far more often. **Both machines**, all four earlier versions, and 5.3 on the Mac. The `Rendered 1023/1024 Tiles` line is again recorded in 4.5's documents only. The counts of how often the file was seen open are properties of the sampling, not figures Blender produces: **do not compare those counts between versions.**

11. **EEVEE and Workbench write no tile file and put nothing in the temporary folder.** The same 8000 × 8000 frame under each of them opened nothing. **The tile cache is Cycles' alone.** **Both machines**, all four earlier versions, and 5.3 on the Mac, where both held only macOS's own graphics-library cache open besides their picture and log.

    The engine is reached by `BLENDER_EEVEE_NEXT` in 4.5 and by `BLENDER_EEVEE` in 5.0–5.3, the only EEVEE name 5.3 offers. This changes the name a script must use, though these runs show no change in the files written. It is on the behaviour list.

12. **A File Output node's folder is made by the render and fills as the render goes.** The folder did not exist before the render; the node's file for a frame lands **just before** the scene's own file for the same frame, frame by frame. **Both machines**, all four earlier versions, and 5.3 on the Mac. The names the node writes differ between versions — 4.5 wrote `n_0001.png` where the later four wrote `n_Image0001.png` — and that is the difference already on the behaviour list under *2 and 8*, not a new one.

13. **With Cache Result on, one cache file is written for every frame, before that frame's picture.** It is called `cached_RR_UNSAVED_Scene_00000000000000000000000000000000.exr` in all five versions. There is **one file, not one per frame**: it drops back to zero and grows again for each frame, and it is still there when the render ends. **Both machines**, all four earlier versions, and 5.3 on the Mac, where Blender also printed `Caching exr file, 1920x1080, …` once per frame. This settles the step the earlier documents mark inferred. Its recorded size for a 1920 × 1080 frame with two view layers was 132,729,040 bytes in 4.5, 132,799,542 bytes in 5.0 and 5.2 and 132,799,543 in 5.3, with 5.1's document recording only "about 133 MB". No version's findings treat that gap of seventy kilobytes as a difference, and it is **not established** as one; the one byte between 5.2 and 5.3 belongs with the one-byte gap on the behaviour list.

14. **A video render puts one file in the folder from the very start, and over this run it grew.** The name carries the whole frame range from the first moment — `movie_0001-4000.mkv` — and the file appears at zero bytes within about a second and grows in steps of 262,144 bytes. **Whether it grows at every size is not settled, and two topics disagree**: **Frames 5** and **Frames 12** watched twenty-frame video renders throughout, on both their machines in all four versions, and the file sat at 48 bytes until the end — question 12 across ten different containers, one of them a run that finished. This run was 4,000 frames into Matroska. **Where the line between the two falls has never been measured by anybody**, and no explanation offered for it has been established. `Frames 5` holds the whole of the disagreement. Stopping the render leaves a file **Blender's own reader will not open as a movie**: handed back to Blender it reported zero frames at 256 × 256. Blender ends with exit code 143. **Both machines**, all four earlier versions, and 5.3 on the Mac, where the file also grew in steps of 262,144 bytes and Blender's reader again found zero frames at 256 × 256. The same test run short enough to finish produced a file that opened properly at its full frame count, which is how it is known the failure is the stop and not the format. **A reader that is not Blender gets more out of it than that** — see question 14, where the same kind of part-finished file was read by an ordinary media tool and gave up the frames written so far, and question 15, where in 5.3 a media tool read this very file. Which reader is asked decides what the file appears to hold.

15. **Past about 1.87 gigabytes with Autosplit on, a second file appears**, and the names gain an extra block of digits — `long__0000001-1400.avi` and `long__0010001-1400.avi` where Autosplit off gives one `long_0001-1400.avi`. **The rented Linux machine only**, in all four versions; it writes several gigabytes four times over and the Creator's Mac is their working machine, so **this settles Linux and leaves macOS open**. The recorded sizes were 2,003,416,672 and 1,022,242,144 bytes in 4.5 and 2,003,090,368 and 1,022,075,648 in 5.0, 5.1 and 5.2, with the single unsplit file at 3,025,649,192 bytes in 4.5 and 3,025,156,392 in the other three. The split falls in the same place in all four; no version's findings treat the small difference in encoded size as a version difference, and it is **not established** as one. A run of 900 frames reached 1,945,065,136 bytes in one file and never split, which is where the figure for the threshold comes from — and it is a figure of that rented machine, not of the machines behind questions 1 to 10. **This topic did not run 5.3 with this**; **Frames 5** holds a 5.3 run of the split, on the Mac. Its manual documents the split at two gigabytes in the same words.

16. **Two Blenders rendering into one folder with Placeholders on and Overwrite off divided the work between them.** One took the odd frames and the other the even ones, each printing `skipping existing frame "<path>"` for the frames the other had claimed, and in this run no frame was rendered twice. **The rented Linux machine only**, in all four versions, because that is the one test whose whole subject is two Blenders at once. The folder was on that machine's own disk. **Do not read the clean division as a property of the arrangement.** A placeholder is a claim and not a lock: the check and the claim are two steps, and the project has caught both failures elsewhere — two copies rendering the same frame, and a frame claimed by one copy, skipped by both and never rendered, with the job still ending at the full file count and exit code 0. Settled under **Frames 14** and **The machine 7**. **A folder shared over a network between two machines — which is what the manual's render-farm recipe is actually about — was not tried in any version.** 5.3 ran one Blender at a time and was not run with this at all.

**What is the machine rather than the version.** The very same `cycles-tile-buffer-…-0-0.exr` file sat under `/var/folders/…/T/blender_XXXXXX/` on macOS and under `/tmp/blender_XXXXXX/` on Linux, in all four earlier versions; in 5.3 on the Mac it sat in a `blender_XXXXXX` folder under whatever folder the run's own `TMPDIR` named. That is each system keeping its temporary files where it keeps them. It is an operating-system fact and it is deliberately not on the list of differences between versions.

**What is still open.** Windows, on every one of the sixteen results above, and Linux for all of them in 5.3. A folder shared over a network. Whether the two-gigabyte video split behaves the same on macOS in 4.5 to 5.2, and anything about it in 5.3 from this topic's runs; Frames 5 holds a 5.3 run on the Mac. Two Blenders in one folder, in 5.3. What a stop landing during a frame's own save leaves behind. What a multi-view render puts in the folder while a frame is still being worked on — the order its two views are written in is settled under question 14, and this is not. And whether any of this turns on the make of graphics card, which nothing tested; 5.3 ran on Apple's own graphics and processor only. **Every one of those is untried somewhere, and untried is not a difference between versions.**

## 12. What does a render do when it must make a folder and cannot?

**All five versions answered "not in the sources" for the failure.** None says what a render does when a folder it needs cannot be made. Creation of the scene's own missing output folder is also undocumented in all five. The documented node-input case is narrower, as below.

**All four earlier versions also record the same near misses, and all four refuse to carry any of them across.** The Ocean modifier's cache folder, which the manual does say is created if missing. The temporary-files preference, where a missing folder is ignored and a fallback used rather than created. The File Browser, where a person typing a path that does not exist is offered the chance to make it. And the one documented way a bad output path stops a render — a broken template expression, which is a different fault. None of these is about a render making a folder. 5.3 records the Ocean modifier's cache folder and the temporary-files preference among its near misses and rules them out the same way.

The one thing 5.1's, 5.2's and 5.3's manuals do carry, and 4.5's and 5.0's do not, is the sentence that the folders implied by a slash in a File Output node's input name are made automatically during output. That sentence covers the sub-folders an input's name asks for. Whether it also covers the node's own base folder is left open in 5.3; the earlier answers read it narrowly. Question 4 holds that distinction.

**The hand tests then settled the whole of it**, in all four earlier versions, on both machines. Every run below was made with no window unless it says otherwise, and on the Linux machine by an ordinary account rather than root, for the reason given near the top of this document. **5.3 was run on the Mac, with one gap.** Every 5.3 folder that could not be made sat inside a disk image mounted read-only, or behind an ordinary file standing in its place; refusal through folder permissions was not tested. A read-only volume refuses for a different reason from a folder's permissions, so those 5.3 results are given as what they are, and what 5.3 does in the earlier versions' own case is not established.

**Verdict: it differs** — almost all of it in what Blender says rather than in what it does, with **one exception**. The folder that a slash in a File Output node's input name asks for is made in 4.5, 5.1, 5.2 and 5.3 and not made at all in 5.0, and where it is made it carries a different name in 4.5 than in 5.1, 5.2 and 5.3. That is a difference in what lands on disk, not in wording, and it is the fourth item below.

**What is the same everywhere.** Every one of these came back the same in all four earlier versions, **on both machines**, and in 5.3 on the Mac — like for like where 5.3 ran the same set-up, and the same shape where a read-only volume stood in, as each item says.

1. **A missing output folder is made** — one level, or a whole chain of three at once. The render printed `Saved:` three times, the operator returned `{'FINISHED'}`, the folder existed afterwards holding all three frames, and the exit code was 0. So the step no version's sources describe does happen, in all five.

2. **When the scene's own output folder cannot be made, the render stops at the very first frame.** Frames two and three are never attempted. Nothing at all is left behind — the locked folder is still empty afterwards. The failure is raised to Python as a `RuntimeError`, and **a windowless Blender ends with exit code 1**. Three missing levels behave exactly as one does. In 5.3 the same, inside a read-only volume.

3. **A file standing where the folder must go behaves the same way** — stopped at the first frame, nothing written, exit code 1 — and gives a *different* reason in words. That matters to anything watching Blender's output: the two causes are told apart by the wording and by nothing else. 5.3 ran this one exactly as the earlier four did.

4. **A File Output node that cannot make its folder does not stop the render, and the exit code stays 0.** The failure is printed once per frame, the render carries on, all three of the scene's own frames are written, the node's folder is left empty, and the operator returns `{'FINISHED'}`. **So the same failure stops the render when it is the scene's own path and does not when it is a node's — and in the second case nothing outside Blender can tell from the exit code that anything went wrong.** That is true in all four earlier versions on both machines, and in 5.3 on the Mac with the node's folder inside a read-only volume, and it is the single most useful thing on this page for anything driving Blender.

5. **The render cache folder is made when it is missing under a writable parent.** When it cannot be made, the render **writes all three of its frames anyway**, prints its failure once per frame, returns `{'FINISHED'}` and ends with exit code 0, and the cache folder is never made. In 5.3 the same, under a read-only volume, with Cycles and with Workbench.

6. **With a window open on screen the terminal says exactly the same thing** — the same lines, the same error raised to Python. All four earlier versions, both machines. In 5.3 the windowed render was started the way the menu starts it rather than from a script, and the terminal printed the same `Couldn't create directory` line and the same `Render error` words, the second carrying the channel name `operator` where a windowless command-line render shows `reports`.

7. **What a person at the screen would see was not settled in 4.5 to 5.2.** Blender took a picture of its own window in all four versions on both machines, and every picture shows the first-run Quick Setup panel sitting over the middle of the layout with an empty Info list behind it. **That is a silence, equal in all four versions, and it is not a difference of any kind.** **In 5.3 it was seen, on the Mac**, with Ctrl-F12 started as the menu starts it. Aimed inside a read-only volume, the status bar and the Info list both showed, beside a red error mark, `Render error (Read-only file system) cannot save: '…/locked/newfolder/f_0001.png'`. Aimed at `//frame_####` in a file never saved, both showed `Render error (No such file or directory) cannot save: 'frame_0001.png'`. Aimed at a missing folder that could be made, the folders were made, the frames written, and the Info list stayed empty.

**What differs, version by version.** Everything below is about the words printed, with one exception — the fourth, which is about a folder that is made or not made and what it is called on disk.

**First — the scene's own output folder cannot be made.**

- **4.5.** Two lines, neither of which mentions a folder or a permission. On the Mac: the bare `<path>: No such file or directory`, then `Error: Render error (No such file or directory) cannot save: '<path>'`. On the rented Linux machine the same shape, with `(Invalid argument)` in the brackets instead.
- **5.0, 5.1 and 5.2.** `ERROR Couldn't create directory for file <path>: Permission denied`, then `Error: Render error (Permission denied) cannot save: '<path>'`. **The two machines printed those words identically**, in all three versions.
- **5.3**, inside a read-only volume on the Mac: `ERROR Couldn't create directory for file <path>: Read-only file system`, then `Error: Render error (Read-only file system) cannot save: '<path>'` — the 5.0 shape, with the volume's own reason. A folder refused by its permissions was not run.

So **from 5.0 the message names the folder and gives the real reason, and 4.5 does neither**. The test was run in all four earlier versions on each machine and came back differently between the versions on each, which is what settles it as a real difference in Blender rather than a gap in anybody's manual. The change of layout that came with 5.0 — a timestamp and a channel name in front of each line, where 4.5's lines are plain — holds here too, on both machines.

**Read this beside questions 5 and 10, and read it carefully.** The wording changed at 5.0 in all three places, and it did not change the same way: for a failed write and an over-long name it is 4.5 that gives the reason and the later three that lose it, and here it is 4.5 that gives no reason and the later three that do. A program built on "4.5 tells you more" will be wrong on this one. 5.3 follows 5.0 to 5.2 in all three places, wherever it was run.

**Second — a file standing where the folder must go.**

- **4.5.** `Error: Render error (Not a directory) cannot save: …` on the Mac; `Error: Render error (Invalid argument) cannot save: …` on Linux.
- **5.0, 5.1, 5.2 and 5.3.** `ERROR Couldn't create directory for file …: File exists`, then `Error: Render error (File exists) cannot save: …`, identical on both machines in the earlier three and the same in 5.3 on the Mac.

Worth noticing, because a program watching for words will trip on it: **on the rented Linux machine 4.5 gives the same `(Invalid argument)` for both causes**, so in that one version on that one system the two reasons cannot be told apart at all. On the Mac 4.5 does tell them apart. That last part is the operating system, not the version.

**Third — a File Output node whose folder cannot be made.**

- **4.5.** `Error: Render error (No such file or directory) cannot save: …` on all three frames on the Mac. On Linux, `(Invalid argument)` on the first frame and `(No such file or directory)` on the second and third.
- **5.0, 5.1 and 5.2.** `ERROR Couldn't create directory for file …: Permission denied`, once per frame, identical on both machines.
- **5.3**, inside a read-only volume on the Mac: `ERROR Couldn't create directory for file …: Read-only file system` and `ERROR Render error (Read-only file system) cannot save: …`, once per frame.

**Fourth — the folder a slash in a node's input name asks for, and what it is called on disk.** Run in every version with a writable folder, as the control:

- **4.5** made a real folder called `passes`, and wrote `passes/diffuse0001.png` inside it.
- **5.0** made **no folder at all**: the slash became an underscore the moment the name was set, and the files landed flat as `n_passes_diffuse0001.png`.
- **5.1, 5.2 and 5.3** made a real folder called `n_passes` — the node's own file name carried onto the front of it — and wrote `n_passes/diffuse0001.png` inside.

Both machines agreed in every earlier version; 5.3 was run on the Mac. This is the difference already on the behaviour list under *3 and 4*, and the node's changed shape already listed under *2 and 8*, showing up together in one test; the folder's *name* is the part these runs add.

**Fifth — the node's own base folder exists and cannot be written to.** This is a different set-up from the one above and it produces different words, because the failure happens at a different moment.

- **4.5.** The bare `<path>: No such file or directory`, then `Render error (No such file or directory)` — on the Mac, on all three frames. On Linux, `(Invalid argument)` on the first frame and `(No such file or directory)` on the second and third.
- **5.0.** `ERROR OpenImageIO write failed: Could not open file "…"`, then a reason that is empty: the Mac said `(Undefined error: 0)` and the rented Linux machine said `(Success)`. **Neither says why.** The reason 5.0's message is about opening a file rather than making a folder is that 5.0 turned the slash into an underscore, so there was never a folder to make.
- **5.1 and 5.2.** `ERROR Couldn't create directory for file …: Permission denied`, then `ERROR Render error (Permission denied) cannot save: '…'`, **identical on both machines**.
- **5.3**, with the node's base folder a read-only volume on the Mac: `ERROR Couldn't create directory for file …/n_passes/diffuse0001.png: Read-only file system`, then `ERROR Render error (Read-only file system) cannot save: '…'` — the 5.1 and 5.2 shape, with the volume's own reason.

In every version and on every machine it ran on the render carried on to all three frames, the scene's own frames were written, the node's folder was left empty, and the exit code was 0.

**Sixth — the render cache folder cannot be made, and this is where the two machines part company.** The first of the two lines printed, laid out in full:

| Version | The Creator's Mac | The rented Linux machine |
|---|---|---|
| 4.5 | `IMB_exr_begin_write: ERROR: No such file or directory.` | `IMB_exr_begin_write: ERROR: No such file or directory.` |
| 5.0 | `ERROR IMB_exr_begin_write: No such file or directory.` | `ERROR IMB_exr_begin_write: No such file or directory.` |
| 5.1 | `ERROR Unknown error in IMB_exr_begin_write` | `ERROR IMB_exr_begin_write: No such file or directory.` |
| 5.2 | `ERROR Unknown error in IMB_exr_begin_write` | `ERROR IMB_exr_begin_write: No such file or directory.` |
| 5.3 | `ERROR IMB_exr_write_end: No such file or directory.` — a read-only volume, not a folder's permissions | not run |

The second line was `Error writing render result, No such file or directory (see console)` in every version on both machines, and in 5.3 on the Mac.

Read that table one column at a time, because reading it across mixes two things.

- **Down the Mac's column**, the words change twice: 4.5 puts `ERROR:` inside the line and 5.0 puts `ERROR` in front of it — which is the logging-format change 5.0's release notes describe — and then **from 5.1 the reason is lost altogether**, replaced by "Unknown error". That is a difference between versions, established on the Creator's Mac, in all four versions.
- **Down the Linux column**, only the layout changes at 5.0. **No version loses the reason on that machine.**

So the loss of the reason is a change between versions that appears on one machine and not on the other, and it is written that way on the behaviour list at the top rather than as a plain version difference or a plain machine difference.

**The 5.3 row is not the same test, and the 5.2.2 run shows why that matters.** 5.3 names the reason, but against a read-only volume. The 5.2.2 run, with that same read-only set-up on the same Mac the same day, named the reason too — `ERROR IMB_exr_begin_write: No such file or directory.` — where 5.2's row above says `Unknown error`. So whether the lost reason in 5.1 and 5.2 came from those builds, from the macOS of their day, or from a folder's permissions is not settled, and 5.3 naming the reason is not a 5.3 change. What does differ between 5.2.2 and 5.3 on the same day and the same set-up is the step the line names — `IMB_exr_begin_write` against `IMB_exr_write_end` — which is on the behaviour list at the top.

**One and the same failure has produced more than one wording on the same machine on different days.** In three places a version's own runs of the same test, made on different days, printed different words, and no run was chosen over another: 4.5's node-folder failure, 5.0's node-folder failure, and 5.1's render cache failure. Question 5 holds a near relative: on the Mac the full-disk failure lost its reason in 5.2's record and kept it in the 5.2.2 run, a later build under a later macOS. What a reader should take from them is not which run was right but that **any program watching Blender's output for particular words is on ground that has already shifted underneath it once**. Which of those runs is right is **not established**.

**What is the machine rather than the version.** **What the render does is the same on macOS and on Linux in every earlier version**, and 5.3 does the same on the Mac: the folder is made when it can be, the render stops at the first frame and ends with 1 when the scene's own folder cannot be made, and it carries on and ends with 0 when only a node's or the render cache's cannot. **What changes between the two systems is the reason printed in the brackets**, and it changes in three places: 4.5's wording for both folder failures, 5.0's wording for the node's own folder, and 5.1's and 5.2's wording for the render cache. Those are operating-system facts and they sit inside the answers above, not on the list of differences between versions.

**What Smoozy should take from that.** Across four versions and two machines, one and the same failure has produced at least seven different wordings, and 5.3 adds more. What is reliable everywhere is what the render *does* and the exit code it ends with: **1 when the scene's own output folder cannot be made, and 0 when only a File Output node's or the render cache's cannot.** Watch the exit code and the file that should have appeared, not the words — and see question 5 for the one place an exit code of 0 still hides a broken file.

**What is still open.** Windows, on all of it, in every version, and Linux in 5.3 — nothing here was tried there and none of that silence is a difference between versions. What 5.3 does when a folder's own permissions refuse it. What Blender's own window shows — the status bar and the Info list, word for word — in 4.5 to 5.2: nobody put a failing render in front of an open window in those versions, though question 13's runs show such a window can be opened and photographed on either machine; 5.3's is above. And which of two runs is right in the places where the same test printed different words on different days.

## 13. When Blender is started with a setting given on the command line and with a script to run at the same launch, what does that script see of that setting?

**All four versions read the question the same way, and all four say so.** Each flags the same ambiguity — "a setting" can mean one of Blender's own start-up arguments, or a value of the caller's own handed in for the script to pick up — and each answers both readings rather than choosing. So the readings themselves do not differ. 5.3 answers both readings too, without flagging the choice.

**What the documents alone gave, and how it is labelled. This part is identical in all four earlier versions but the last line; where 5.3 reads it differently, the line says so.**

- That the command line is a list of steps carried out one after another, left to right — **documented** in all four, quoted from two separate pages of each version's manual.
- That loading the blend-file is itself one of those steps, and wipes an output path set before it — **documented** in all four.
- That the script argument is a step like any other, so where the script sits on the line decides what it sees — **inferred** in all four. Every version states plainly that no page in its sources shows a script argument and a setting argument in one example.
- **Which Python value the output-path argument writes into — not in the sources, in all four.** Every version searched for a sentence joining the two and none found one. 5.3 takes the step — the argument sets the scene's own output path — and marks it **inferred**.
- That anything written after a bare `--` reaches the script unchanged, as text, and that `--` ends Blender's own reading of the line — **documented** in all four.
- That a small set of facts about the launch can be read off `bpy.app` — **documented** in all four. Of those entries, only the one about the internet-access override says in so many words that it cannot be written to — in 5.3 the entry for the auto-run override says so too; that the others cannot is in no version's sources, and the tests below show it is not true either.
- That a script can register a command of its own and be handed the rest of the line — **documented** in all four; 5.3's answer does not take it up.
- That Cycles reads its own command-line settings out of the raw argument list and hands them to a call rather than writing them into any property — **observed** from Cycles' own files in all five, with the consequence for a reading script marked **inferred** in all four earlier versions and left open in 5.3.
- That a path carrying template marks or hash marks is stored as typed and worked out later — **documented** in 4.5, 5.1 and 5.2, which all quote the same manual sentence for it. **5.0's documents do not carry it**, and 5.0 says plainly that whether a script reads such a path as typed or already worked out is not stated in its sources. That is one version's search coming up empty rather than a difference: result 8 below settles the behaviour by test, and it is the same in all five. 5.3 quotes the same manual sentence, and marks **inferred** that it holds for a path given on the command line.

**Everything below was settled by hand**, in all four earlier versions, on the Creator's Mac and on the rented Linux machine with the RTX 3060 — sixteen tests, every one run on both machines in every version. The two machines agreed line for line everywhere except two lines the machine itself supplies, which are set out at the end. **5.3 ran the same sixteen, with the same scripts, on the Mac**, and one more of its own — `-S` with `-o`, under item 2.

**Verdict: it differs** in the readable launch facts. The meaning of the earlier handler counts is unresolved. What a script sees of a command-line setting otherwise agrees on the machines tested.

**What differs, version by version.**

**First — the list of launch facts a script can read off `bpy.app` is not the same list.** A search that read every name on it found seventy in 4.5 and 5.0, seventy-one in 5.1 and 5.2, and seventy-three in 5.3. 4.5 carries `debug_ffmpeg` and lacks `cachedir` and `memory_usage_undo`. 5.0 has lost `debug_ffmpeg` and gained `memory_usage_undo`. 5.1 and 5.2 carry `cachedir` too. 5.3 carries everything 5.1 and 5.2 carry plus `autoexec` and `autoexec_override`, the second of which 5.3's own documentation describes as the auto-run setting given on the command line. The lists were identical on both machines in the earlier four; 5.3's was read on the Mac and set against 5.2's record there, and no 5.2.2 run read it. 5.0's release notes record the change behind the first of those: the command-line switch for video logging was replaced by a general logging one. **No name on any of the five lists holds a render output path**, and the search found nothing there in any version.

**The after-load handler count is unresolved in 4.5–5.2.** The totals are two for 4.5 and three for 5.0–5.2 on both machines, but they are attributed both to the list before registration and to the list including the script's own handler. The printed lines label them after registration. The totals cannot be used as an established count at either moment without resolving that conflict. In 5.3 on the Mac, the printed total after registration is three.

**What is the same everywhere.** Every result below came back the same in all four earlier versions, on both machines, and in 5.3 on the Mac, line for line where a line can be compared.

1. **Where the value lands, found by searching rather than by guessing a name.** A search walked the file's data, the preferences and plain values on `bpy.app`, looking for the exact text handed in. In 5.3 it followed links to a depth of five. Among Blender's own settings it found that text in **exactly one place: the active scene's own render output path**. Nowhere else, and nothing at all under `bpy.app`. It also found the same text in the raw command line, which is item 7 below and a different thing.

2. **The argument reaches the active scene only.** The test file held two scenes, each with its own stored output path. The second scene kept its own in every version on every machine. An output path given on the command line is not applied to every scene in a file. **5.3 also ran it with `-S`**, on a file of its own with two scenes: with `-S Second` written before the output-path argument, the value landed on `Second` and `Second` rendered into the folder given; with `-S Second` written after it, the value landed on the first scene and `Second` rendered to its own stored path. So in 5.3 the argument reaches **the scene that is active at the moment it is read**. No earlier version was asked. When `Second` had no camera, both launches that rendered it printed `ERROR No camera found in scene "Second"`, wrote nothing and ended with exit code 0 — the 5.3 change under question 5.

3. **Order decides what the script sees, exactly as the ordering rule says.** Five arrangements of the file, the setting and the script were run. With the file first, then the setting, then the script, the script reads the value handed in. With the script written before the setting, it reads the file's own path. With the setting written before the file, the file load wipes it and the script again reads the file's own path. The long form of the argument behaves identically to the short one. So the inference every version drew from the manual is right, and it is a test result rather than an inference.

4. **A script placed before the file runs in a Blender that has no scene from that file yet** — one scene, holding the factory startup file's own `/tmp/`, and the file's scenes not there at all. A handler registered at that moment and marked to survive a file load **does** fire after the load, and then sees both of the file's scenes with their own stored paths. So a script that ran too early has a documented second chance, and it works.

5. **The last thing written on the line wins.** With the script before the setting, the render wrote to the path the setting gave; with the setting before the script, the render wrote to the path the script set. A script's own write is not privileged, and neither is the argument.

6. **A read-back check works end to end, and stops the launch when it fails.** A script that reads the output path back, compares it against what the caller intended and stops when they differ: in the right arrangement it matched, the render ran and one frame was written, and the launch ended with exit code 0; in the wrong arrangement it did not match, **nothing was rendered and nothing was written, and the launch ended with exit code 1**.

7. **The whole command line is visible to the script as plain text.** Blender's own program path is the first item, its own arguments follow, and `--` appears as an item of its own when it is typed, with everything after it unchanged. `bpy.app.python_args` is not the command line — it holds only `('-I',)` in every version on both machines.

8. **A path handed in with template marks or hash marks reads back exactly as typed.** The braces and the hashes are still there. Blender's own path-building call resolves them on request — a template gave the blend-file's name, four hashes gave a four-digit frame number — and the call that makes a path absolute expands a leading `//` to the blend-file's folder while leaving the hashes alone. So a read-back check compares the text that was handed in, not a finished file name.

9. **The other settings on the line follow the same order rule** — the engine, the frame range and step, the file format and the extension switch all take effect when written before the script and are not yet in force when written after it. **One does not: the thread count.** Asking for three threads gave three, and a fixed rather than automatic thread mode, whether it was written before the script or after it, against a control run that gave the automatic mode and the machine's own core count. That is the one setting in this question that does not obey the order it was written in.

10. **All five ways of handing a script in at one launch see the same thing** — a script file, an expression typed on the line, a text block stored inside the blend-file, a registered command, and text piped into the interactive console. Every one printed the same path, in every version on both machines, and none of them failed.

11. **Two scripts with the setting written between them see different things** — the first the file's own path, the second the path handed in. So a launch can mix scripts and settings in a chosen order and each script sees the state as it stood at its own place.

12. **The switches that turn automatic script running on and off do not touch a script handed in at launch.** With the switch on, with it off, and with neither given, the script ran, and the preference a script reads came back the same under all three. So that preference cannot be used to find out which was given.

13. **The graphics device named for Cycles on the command line lands nowhere a script can read.** The scene's own Cycles device stayed on the processor under every argument, and a blind search for the device's name found exactly the same places with the argument and without it — that is, the machine's own hardware, present in the control run. This confirms what all four versions inferred from Cycles' own files.

14. **Add-ons are already registered when a launch-time script runs**, even when the script is written before the blend-file — the same eight add-ons enabled, Cycles' modules already loaded, the scene already carrying its Cycles settings, and Cycles already registered as a render engine.

15. **The launch flags on `bpy.app` are not all of one kind: some can be written and some cannot.** `bpy.app.debug` accepted a write and read back changed; `bpy.app.background` refused one outright, reporting a read-only attribute. Of the launch flags, only the internet-access override is described as read-only in any earlier version's own documentation — 5.3's describes the auto-run override that way too — and this is what the flags actually do.

16. **Those flags do report what the launch was given.** Three of them moved with the switches that set them — factory startup, Python debugging, and the internet-access override — and the background flag read true in every run started without a window.

17. **A launch with a real window open sees the same thing as one without.** The script read the same path, one window was open, and the path field at the top of Blender's Output panel showed that same path — in all four earlier versions on both machines, and in 5.3 on the Mac. On the rented Linux machine the windowed Blender also printed the session-recovery line already recorded under question 7, and printed it without the timestamp and channel name in 4.5; 5.3 printed it on the Mac, with them.

**One thing seen in 5.3 alone, and not established as new.** During the search in item 1, 5.3 printed twenty `bpy.rna` warning lines saying a stored value matches none of a setting's choices. Whether earlier versions print them is not established.

**Two things carried through from elsewhere, showing up again in these runs.** The saving line Blender prints is bare in 4.5 and carries a timestamp and a channel name in 5.0, 5.1, 5.2 and 5.3 — the logging change already on the list at the top under questions 5 and 10, seen here on both machines and in 5.3 on the Mac. And the engine name the test file's own scene holds reads `BLENDER_EEVEE_NEXT` in 4.5 and `BLENDER_EEVEE` in the other four, which is the naming difference under question 11 and on the behaviour list; it does not change what these runs write.

**What is the machine rather than the version.** Two lines, and both come from the machine rather than from Blender or from the command line. The control run's core count read 8 on the Creator's Mac, in 5.3 as before, and 32 on the rented Linux machine, which is that machine misreporting its share of a bigger chip — the real quota there is about fifteen. And the graphics device the preferences hold read `METAL` on the Mac, in 5.3 as before, and `NONE`, with a device of type `OPTIX` listed beside it, on the Linux machine. Both were there in a control run before any argument was given. Neither is on the list of differences between versions.

**What Smoozy should take from this.** The arrangement that works is the file first, then the setting, then the script — and a script in that position can read the scene's own output path back and refuse to render when it is not what was asked for, ending the launch at exit code 1 with nothing written. The value it reads back is the raw text handed in, so the comparison is against the text and not against a finished file name. Three things do not fit that pattern and each has to be handled on its own: the thread count ignores where it was written, the Cycles graphics device cannot be read back at all, and an output path given on the command line reaches only the active scene — in 5.3, the scene active at the moment the argument is read, so a `-S` meant to choose the scene must come before it.

**Not established.** Everything on **Windows**, in every version, and on **Linux** in 5.3 — nothing here was tried there, and that silence is not a difference between versions. **What the Cycles graphics device given on the command line does to a render** — the runs show only that it leaves nothing readable behind; in 5.3 a render given the Mac's graphics this way opened Cycles' compiled kernels for those graphics (question 11), and what the renderer used was never read back. And, in 4.5 to 5.2, **whether the output-path argument reaching the active scene alone turns on which scene is active**, or on how a file names its scenes: one file, holding two scenes, was used. 5.3 answers it as above.

## 14. When a render works through a range of frames, how do the writes belonging to one frame stand in time against the writes belonging to the frame after it?

*This is not question 11 asked again. That one asks what is present where a render writes while it is still working; this one asks about the order in time of one frame's writes against the next frame's.*

**What the documents alone gave, and how it is labelled. It is the same in all five versions.** That a render of a range takes the frames from start to end and steps forward after each rendered frame — **documented** in all four. That each frame is saved after that frame is rendered, during the run rather than at the end — **documented** in all four. That there is a per-frame moment Blender itself calls "directly after the frame is written", which a script can be notified of — **documented** in all four. That a stopped run leaves the frames already rendered in the output folder and can be picked up from there — **documented** in all four. That a video output is one file holding every frame, split at two gigabytes and left unplayable if the run goes wrong — **documented** in all four. That the Placeholders setting exists, makes an empty file while frames are being rendered, and is off out of the box — **documented** in all four. That a frame can carry writes beyond its own picture — a placeholder, a preview, a File Output node's file, Cycles' tile cache — **documented** in all four that they exist. 5.3 documents the same things, with 5.2's wording for when frames are saved, and adds that the render statistics carry a saving time for each frame.

**The ordering itself is *not in the sources* in all five**, and every earlier version says so in the same words: no page anywhere states that frame N's file is finished before frame N+1 begins, and no page states that the two may overlap. All four earlier versions offer the joining-up as an **inference** — frames go in order, each is saved after its own render, so the saves fall in that order — and every one of them stops short of the strong claim the question asks about. 5.3 marks the timing *not in the sources* too, and does not offer the joining-up at all. **No version's manual is thinner than another's here.** This is a silence shared by all five, not a difference between them.

**Verdict: the same everywhere.** **Every write belonging to one frame is finished before any write belonging to the next frame begins.** Settled by test in all four earlier versions, on the Creator's Mac and on a rented Linux machine whose four Blenders matched the Mac's to the exact build hash, and in 5.3 on the Mac — with no window, and again with Blender's own window open and the render started the way the Render Animation menu item starts it.

**How well established this is, because it is a negative.** A negative is only as good as the instrument that looked for the thing, and this instrument was fine enough to have shown an overlap. The write was made slow on purpose — a 3000 by 3000 uncompressed OpenEXR, 144 megabytes a frame, taking about 190 milliseconds on the Mac and about 60 on Linux — and the folder was read every two milliseconds while it happened. **Sixty-three separate readings fell inside one write on the Mac and thirty-one on Linux**; a repeat of the same measurement on the Mac got seventy-five and seventy-six. Two frames' writes running at the same time by even a few milliseconds could not have been missed at that rate. Those counts and durations are one run's figures on machines that were not quiet — the rented machine's processor is shared, and the Mac was running another Blender that day — and they are not constants. In 5.3, on the Mac, the same frame took between about a quarter and six tenths of a second to write, and 88 to 177 readings fell inside each write.

**Two instruments were used and they are two separate claims. Do not let one carry the other.**

- **Blender was asked, and the disk was watched** — on both machines, in all four earlier versions, and in 5.3 on the Mac. That is what settles macOS.
- **Every file call Blender made was traced, thread by thread** — **on the rented Linux machine only**, in 4.5 to 5.2. `strace` has no equivalent on the Creator's Mac that does not need a system setting changed, and no system setting on that machine was touched. **That trace settles Linux and says nothing whatever about macOS**, and 5.3 was never traced.
- **In 5.3 alone, a third instrument** — a loop with no pause, about 19,000 passes a second, that looks at the output folder first and Blender's temporary folder second in every pass — settles one ordering on the Mac that the watcher could not: item 6.

**What the runs show, in all five versions** — the earlier four on the machines each item names, 5.3 on the Mac.

1. **Blender's own account.** For every frame in the range, the write announcement for frame N is printed before the render announcement for frame N+1. The gaps are positive every time — 21 to 37 millionths of a second with no window, 27 to 272 with a window — and **no frame came out of order in any of the sixteen runs**. Both machines. In 5.3 the gaps were 29 to 34 millionths of a second with no window and 29 to 98 with one, and no frame came out of order.

2. **The disk agrees.** No file's size ever changed after a later file had appeared, on either machine, in any version, 5.3 included.

3. **Nothing is written under a temporary name.** No name ever appeared in an output folder that was not a final frame name, on either machine, in any version. The Linux trace shows more than a watcher could: **there is no rename call anywhere in it**, and every file is written under its final name from the first byte.

4. **Where the write succeeds, the file is complete at the moment Blender says it is written.** A handler that read the whole file at that moment got exactly the number of bytes the finished file holds. Both machines, all four earlier versions, and 5.3 on the Mac — 144,048,850 bytes for each of five frames. **That is as far as these runs reach, and the limit matters.** Every one of them was a 3000 by 3000 uncompressed OpenEXR into a folder with room for it, so **no write in this question ever failed** and none of them could have shown what an announcement over a short file looks like. **It does not follow that the announcement proves a whole file exists** — **File output nodes 15** records a `Saved:` line printed over a part-written file left by a full disk, exactly as for one written in full, in every version on both machines, and this document's own question 5 records the same from the other side.

5. **The other files a frame writes all fall inside that frame's own turn.** A File Output node's file is written first and the scene's own output second. A preview picture saved beside a frame comes after the frame's own file. With two views written as separate files, the left view is written and then the right. In every one of those cases a frame's pair of files is finished before the next frame's first file appears, with seconds between them. Both machines, all four earlier versions. Where two of those events fell in the same two-millisecond reading, nothing is claimed about which came first. 5.3 on the Mac: the same three orders.

6. **Cycles' tile cache is one file per frame, not one for the job.** It is written in Blender's temporary folder during that frame's render, and it is finished and **removed no later than the reading in which that frame's own output file first appears**. Both machines, all four earlier versions, and 5.3 on the Mac. **On Linux the trace shows it strictly** — a different thread writes each frame's tile file and closes it before the frame's own file is opened, and the process's first thread removes it about two milliseconds before that, three removals in the whole trace, one per frame. **On the Mac the watcher cannot separate the two events**: it stamps everything it finds in one sweep with a single time, and in two of three frames the removal and the next file's first appearance share a stamp. So in 4.5 to 5.2 the strict "before" is a Linux result, and the Mac's answer is the narrower one written above. **In 5.3 the strict "before" is shown on the Mac**, by the third instrument: in every frame at least one pass saw neither the tile file nor the frame's file, the frame's file appeared 0.4 to 5.1 milliseconds after the tile file was last seen, no pass in over two million saw a new frame file with a tile file still there, and no two frames' tile files were ever present at once. The ordinary watcher alone again stamped one removal and the next appearance with the same time.

7. **Placeholders are made one at a time, for the frame in hand.** The empty file for a frame appears within a few milliseconds of that frame's render beginning, sits at zero bytes for the whole of that render, and then grows to full size; the next frame's empty file appears within one reading of that. **Only one empty file is ever waiting**, and the write announcement fires once per frame, not twice. Both machines, all four earlier versions, and 5.3 on the Mac.

8. **A video container grew through this run.** About half its bytes are on disk by the half-way frame and about nine tenths by the time the last frame is written, with two to five further changes of size after that. Both machines, all four earlier versions. 5.3 on the Mac came out the same shape: 67,108,864 of its final 153,188,689 bytes at the twentieth of forty frames, 145,489,920 at the fortieth, and five more changes within 41 milliseconds after. **Whether that holds at every size is not settled**: **Frames 5** and **Frames 12** watched twenty-frame video renders throughout and found the file sitting at 48 bytes until the end, in all four versions on both their machines and across ten containers. **Where the line falls has never been measured**, and question 11's item 14 holds the pointer to the whole of it.

9. **A video render stopped part way leaves a file that reads.** Interrupted six seconds in, the part-finished container was accepted by an ordinary media tool, which reported its format and duration, and a decoder walked it and got out the frames written so far. **The rented Linux machine only**, in all four versions, because a media reader had to be installed and nothing was installed on the Creator's Mac. The frame counts differ between the versions — 23, 23, 18 and 17 announced — because a fixed six-second interrupt lands at different places in renders of different speeds, and that is not a difference in Blender. **In 5.2 the decoder read one frame more than Blender had announced written**, and nothing in the findings explains it. **5.3 ran the same test on the Mac**, with a media reader that was already installed there: interrupted six seconds in, Blender printed its break line and ended at exit code 1, and the file read with a duration of 1.25 seconds and gave up 30 frames, the same number Blender had announced written. Because the machines differ, that says nothing about Linux in 5.3 or the Mac in the earlier four, and nothing about 5.2's extra frame.

10. **Frames given as a list are written in the order given.** Asked for 5, 1, 3, Blender wrote 5, then 1, then 3 — not in numeric order. Both machines, all four earlier versions, and 5.3 on the Mac. This is the one thing on the question sheet that no version's sources touched at all.

11. **The ordering is not the render engine's.** The same runs under EEVEE gave the same answer as under Cycles, with no overlap, on both machines in all four earlier versions, and in 5.3 on the Mac.

12. **One thread does the frame's own writing.** On Linux, the frame's file is opened, written with about three thousand calls and closed by the process's first thread, with the close following the last write within a tenth of a millisecond, and no write to one frame's file happened after the next frame's file was opened. **Linux only, in 4.5 to 5.2.**

**Four version differences turned up in these runs, and not one of them is about timing.** The timing answer is identical in all five versions. Two of the four are about how a setting is reached; the third is about the words Blender prints; the fourth is about a file's size. Each is already stated elsewhere in this document, and where it belongs on a list it is already on one.

- **The compositor and the File Output node are reached differently.** In 4.5 the scene carries a node tree and the node carries a base path; in 5.0, 5.1, 5.2 and 5.3 there is no scene node tree at all, the route is a compositing node group, the node carries a directory and a file name, and an item has to be added to it before a link writes any file. Already on the behaviour list under *2 and 9*.
- **EEVEE answers to a different name.** 4.5 offers only `BLENDER_EEVEE_NEXT` and the later four only `BLENDER_EEVEE`. See question 11 and the behaviour list.
- **The line Blender prints when it saves a frame.** Plain in 4.5, carrying a time and a channel name from 5.0, 5.3 included. Already on the behaviour list under *5, 10, 13 and 14*, and recorded in full under question 5.
- **The size of a 3000 by 3000 uncompressed OpenEXR frame.** 144,048,849 bytes in 5.2's record and in the 5.2.2 run on the same Mac the same day; 144,048,850 in 5.3. On the behaviour list under *11 and 14*. Nothing in the timing turns on it.

**And one thing seen here that is a difference in what a file is called rather than in when anything is written.** With its file name left at its shipped value, a File Output node's file came out named `Image` in 4.5, `file_name` in 5.0 and 5.1 and `Unsaved` in 5.2 and 5.3 — the same test, in all four earlier versions on both machines and in 5.3 on the Mac, and seen twice over in three of the four earlier ones. **What 5.2 and 5.3 do there is the blend file's own name**: their node ships with the file name set to a template meaning exactly that, and the file in this test had never been saved, so it resolved to `Unsaved`. **Dependencies 10** settles it, having run the same test on a blend file called `file output` and got `file output0001.exr`. So what parts 5.2 and 5.3 from 5.0 and 5.1 is a shipped value rather than the node's changed shape that question 8 owns, and it is a name that lands on disk, so it is on the behaviour list at the top. 5.3's release notes describe that shipped name as new in 5.3; this test shows it in 5.2 already, which is why the note sits on the documentation list.

**One place where only the manuals differ.** 4.5's, 5.0's and 5.1's say an animation's frames are "automatically saved directly out to a drive after being rendered"; 5.2's and 5.3's say they are "typically saved directly to disk as they are rendered". The word *typically* leaves room for a reader to wonder whether 5.2 or 5.3 might hold writes back. **Neither does** — the tests above came back identical in all five. The manuals differ and Blender does not.

**What Smoozy should take from this.** Where the write succeeds, a frame's file is whole the moment Blender announces it written, and nothing later touches it: a program watching the output folder can pick up frame N as soon as it is announced, and does not have to wait for frame N+1 to appear before trusting it. Nothing is ever written under a temporary name, so a file appearing in the folder is the real one and a part-written file cannot be told from a finished one by its name. **The announcement is not the proof, though, and nothing here shows that it is**: every run behind this question had room on disk, so none of them could have printed a `Saved:` line over a short file. **A write that fails prints the same line** — **File output nodes 15** and this document's own question 5 both record it, in every earlier version on both machines and, under question 5, in 5.3 on the Mac, one of them ending at exit status 0 over a PNG that is not whole. Question 11 holds how wide the part-written window is. Frames arrive in the order they were asked for, which for a list is the order of the list and not numeric order. And a video render is the exception to all of it: there is one file, it was being added to throughout these runs — though whether it grows at every size is not settled, and item 8 says why — and nothing announces a frame in it as safe to take. The interrupted lossless files gave a media tool frames; Blender's own reader found no frames in the terminated H.264 files. Those are different tests, not two readers checked against the same lossless file. Question 15 gives the 5.3 readings of the same H.264 file by both readers.

**Not established.** **Windows**, on every result above, in all five versions, and **Linux** in 5.3. **Whether the strict ordering of Cycles' tile file against the frame's own file holds on macOS in 4.5 to 5.2** — the instrument that shows it there is a Linux one; 5.3 shows it on the Mac. **Several machines writing into one shared folder**, which is what the manual's render-farm hint is about, and **an output folder on a network share** — both need a second computer of the same kind and a file system shared between them. A rented Linux machine **can** mount a network share — one mounted a folder over the network from itself, and `Frames 14` measured two renders colliding in it four to six times in thirty against none on that machine's own disk, in all four versions — so what is missing is the second computer and not the share. **What a script is handed when Blender prints its render statistics** — the API description changed at 5.2; for 5.3 the quoted description is "the render progress as a string containing current frame, current sample, render time and saving time"; nothing in this topic tested what a script receives, in any version, and **Frames 15** holds what it is handed. And **why 5.2's stopped video held one frame more than Blender announced**.

## 15. While a render is writing an animation as a single video file, what is in that file at each point of the run, and what decides that?

*This is not question 11 asked again. That one asks what is present in the places a render writes to while it is still working, and how that changes with the size of the picture. This one asks about one video file across a whole run.*

**The full question is answered for 5.3 only.** The earlier four carry partial answers from tests under questions 11 and 14 that watched a single video file through a run; those are set beside 5.3's below, and only where the same test ran on the same kind of machine.

**How it is known, in 5.3.** *Not in the sources* for what the file holds at each point of the run, and for what decides it. **Documented**: video output encodes every frame into one container holding all of them; a problem while rendering can leave the file unplayable and needing a render from the start; Autosplit splits the output once the first file reaches two gigabytes; the keyframe interval and the B-frame settings bear on file size and seeking. **Inferred**, from the unplayable warning: the file exists and is unfinished while the render runs. Nothing in 5.3's sources says how a video file is named; its tests do, under question 8.

**What 5.3 showed, on the Mac.**

- **One file, under its final name, from the first frame.** It is named for the whole frame range — `frame_0001-0040.mkv`, `movie_0001-4000.mkv` — the same name the path-building call gives for frame 1, and it appeared at 0 bytes about 1.2 seconds into the render.
- **In the two longer runs it grew as frames were added.** Forty lossless frames at 1920 by 1920 held 67,108,864 bytes at the twentieth frame's announcement and 145,489,920 at the fortieth, then changed five more times within 41 milliseconds to reach their final 153,188,689 bytes. A 4,000-frame H.264 render into Matroska at 1280 by 720 grew in steps of 262,144 bytes.
- **The smallest run did not grow during the render.** Three frames at 64 by 64 into Matroska stood at 0 bytes at every frame's announcement and reached 1,455 bytes only when the render completed.
- **The two stopped runs left different files, and the readers gave different answers about the same file.** The 4,000-frame H.264 render, sent a terminate signal 25 seconds in, ended at exit code 143 and left 1,310,720 bytes. A media tool read it as Matroska with H.264 but no duration and reported that the file ended prematurely, and its decoder took 1,153 frames out of it, against the 1,257 Blender had announced appending; a copy taken twelve seconds in gave the decoder 468. Blender's own movie reader found 0 frames, at 256 by 256, in both. The forty-frame lossless render, interrupted 6 seconds in, printed Blender's break line and ended at exit code 1; its file read with a duration of 1.25 seconds and gave up 30 frames, exactly the 30 Blender had announced written.
- **Blender prints no `Saved:` line for a video.** It prints `Video append frame N` once per frame instead — question 16.
- **The two-gigabyte split was not run in this topic's 5.3 runs**; **Frames 5** holds a 5.3 run of it, on the Mac.

**What decides it is not established, in any version.** The smallest tested video held no bytes at the frame announcements, while the larger ones grew. Picture size and codec were not varied separately, so these runs do not establish which decides the growth. The stopped runs also used different codecs and different signals, so they do not establish what the signal alone changes. **Where the line falls has never been measured.** **Frames 5** holds the whole of that disagreement, and question 11, item 14, the pointer to it.

**Set beside 4.5 to 5.2.**

- **The same test on the Mac, the same answer in all five.** The 4,000-frame H.264 render into Matroska stopped by a terminate signal (question 11, item 14): one file named for the whole range from the start, at zero bytes, growing in steps of 262,144 bytes; exit code 143; and a file in which Blender's own reader finds no frames. The forty-frame lossless render (question 14, item 8): about half its bytes on disk by the half-way frame, most of the rest by the last frame's announcement, and a few changes after. The earlier four on the Mac and on Linux; 5.3 on the Mac.
- **Different machines, never compared.** The interrupted lossless file read by a media tool: Linux in 4.5 to 5.2 (question 14, item 9), the Mac in 5.3. The same shape came back — a file that reads and gives up the frames written so far — and because the machines differ that says nothing either way.
- **5.3 alone.** A media tool's reading of the stopped H.264 file, and of a copy taken while the render was still running.
- **4.5 to 5.2 alone.** The two-gigabyte split, on Linux (question 11, item 15).

**Verdict: not established for every version.** The earlier versions establish the parts tested under questions 11 and 14, but not the full answer. Where the same test ran on the Mac in all five, it came back the same, and nothing here shows a difference between versions. Whether a video file grows during the run at every size is settled in no version.

**Also in 5.3, on the Mac:** a script cannot choose the video format until the media type is set to Video — question 6.

**Not established.** Linux in 5.3, and Windows in every version. The two-gigabyte split on macOS in 4.5 to 5.2, and in 5.3 in this topic's runs; Frames 5 holds a 5.3 run on the Mac. What any player but Blender's own reader and the one media tool makes of a stopped file. What decides whether a file grows during the run. Whether a video carries the scene's sound — never run in any version.

## 16. Under what conditions does a render report that a file has been written, and what is on disk at the moment it reports it?

*This is not questions 5 or 14 asked again. Those ask what a write does when it cannot finish, and how one frame's writes stand in time against the next frame's. This one asks what the report itself corresponds to on disk.*

**The full question is answered for 5.3 only.** Parts of it were tested in the earlier versions under questions 5 and 14; those are set beside 5.3's below, and only where the same test ran on the same kind of machine.

**How it is known, in 5.3.** **Documented**: the one documented report is the script event Blender fires "on writing a render frame", "directly after the frame is written". *Not in the sources*: whether it fires for a still saved with the save switch, for a File Output node's files, for each frame of a video, or for placeholders; whether "written" means the data has reached the disk rather than been handed to the system; and any printed message — no line in the terminal or the Info list about a saved file is documented. **Inferred**: that the event fires for renders with no window.

**What 5.3 showed, on the Mac**, with a reporter on Blender's render events listing every file and its size at each event.

- **When the announcement fires.** Once per frame for an animation, from Python and from `-a`; with a File Output node writing beside the main output; with the node writing alone and saving switched off; for each frame of a video; and with Placeholders on. Once for a still saved with the save switch, and once for `-f 1`. **Never for a still not asked to save, and never for a still written only by a File Output node** — that node's file was written, and no announcement came.
- **What is on disk when it fires.** Every picture file belonging to that frame, the node's file included, at its final size. A 3000 by 3000 uncompressed OpenEXR read back inside the announcement gave every one of its 144,048,850 bytes, for all five frames. With Placeholders on, the next frame's empty file was not yet there at this frame's announcement; it was there, at 0 bytes, when the next frame began. **For a video the announcement says nothing about the file**: the small Matroska run stood at 0 bytes at every frame's announcement and reached 1,455 bytes only when the render completed.
- **Blender's own printed line.** Every picture file gets a `Saved: '<path>'` line, printed before that frame's announcement — a File Output node's file and a preview picture each their own. A video gets `Video append frame N` for each frame and no `Saved:` line at all. With Blender's window open, the announcement still came before the next frame began.
- **A write that fails.** On a full volume 5.3 printed `Saved:` over a part-written first frame (question 5). Nobody watched the announcement in that run.

**Set beside 4.5 to 5.2.**

- **The same test on the Mac, the same answer in all five.** Where the write succeeds, the frame's file is complete at the moment of the announcement (question 14, item 4). And on a full volume Blender prints `Saved:` over a part-written file (question 5), as **File output nodes 15** also records. The earlier four on the Mac and on Linux; 5.3 on the Mac.
- **5.3 alone.** Which renders fire the announcement and which do not, and what stands on disk for a video at each one.
- **The printed line** is plain `Saved:` in 4.5 and carries a time and a channel name from 5.0, 5.3 included — question 5. What each version prints for a video frame is **Frames 5**'s and **Frames 14**'s.

**Verdict: not established for every version.** The earlier versions establish the parts tested under questions 5 and 14, but not all the conditions that trigger an announcement. Where the same test ran on the Mac in all five, it came back the same: a successful frame is whole on disk when it is announced, and a `Saved:` line is no proof that a file is whole.

**What Smoozy should take from this.** In 5.3 the announcement is one per frame, not one per file; it never comes for a single still that only a File Output node writes; for a video it says nothing about what is on disk; and in every version a `Saved:` line can stand over a short file. Check the file itself.

**Not established.** Everything about the conditions in 4.5 to 5.2. Linux in 5.3, and Windows in every version. Whether the announcement fires at all when a write fails. Whether "written" means the data has reached the disk itself — nothing here could tell.
