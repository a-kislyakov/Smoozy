## 1. What can cause a render to fail, and what does Blender do in each case?

**How it is known.** All four versions answer the general question **not in the sources** — no version's manual gathers render failures into a list. All four then quote the same scattered set of specific ones, nearly all about the graphics card, all **documented**. One item is additionally marked **observed** from Cycles' own file, with the step to what Blender does marked **inferred**. Nine failure situations were then run from a terminal in all four versions on the Creator's Mac, and two were repeated by the Creator with the window open in all four. **All nine were then run again in all four versions on the Linux machine**, along with six more the Mac could not reach. **Blender 5.3's** documents answer the same way and quote the same scattered set, all **documented**, with the same line from Cycles' own file **observed**; they add the manual's own sentences that with saving switched off "the render will fail unless an alternative output method is provided" and that "rendering operations will report errors". **5.3's failures were run on the Creator's Mac alone**, with no window and with one; what only a Linux machine or a graphics card could reach was not run.

**Verdict: it differs.**

**What “no camera” means in this answer.** The tested file is `nocamera.blend`: the factory scene `Scene`, with its cube and light left in place and its Camera object deleted. It uses **Cycles on the CPU**, 16 samples, 160 by 120 pixels at 100 per cent, PNG, and frames 1 to 3; the command asks for **frame 1 with `-f 1`**. Adaptive sampling and denoising were left at their factory values, and the script did not change the time limit. The handler, log-file and Python-call tests use this same scene. The 5.2.2 control built its own copy with the same script. These results do not establish what Workbench does with its camera set to none, or what other engines or scene settings do.

**What is the same in every version.** Each of these held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise.

- **What the exit status is worth.** Exit 1 is trustworthy where Blender means it: a missing blend-file, no camera, a device it will not take, a broken path template, a folder it cannot write into, a name too long, an interrupt — every one ends at 1 with nothing written, in all four versions on both machines. **In 5.3 a scene with no camera breaks this and ends at 0** (below); a missing blend-file, a refused device, a broken template and an interrupt end at 1 as before, and an unwritable folder, a name too long and a full disk were not run. **Exit 0 is what cannot be trusted.** Where a write starts and then runs out of room, Blender leaves a part file, prints an ordinary `Saved:` line for it, and does not treat that as a failure. The render ends at 1 only when a **later** write fails outright, which needs there to be a later frame — a single still on a full disk ended at 0 in all four versions, a three-frame animation on a full volume ended at 1 in all four, and a 400-frame animation that filled the disk part way ended at 1 in the one version it was run in. A File Output node's failure never ends the render and never moves the status. **So the rule is narrow: exit 1 means something went wrong; exit 0 does not mean every file is whole.** The full-disk runs were settled under **Writing 5**. What Blender printed about the disk was not kept, so nothing here says whether it said anything about it. That the status carries the outcome at all is the fact none of the five documentation sets gives.
  **Question 12 widens both halves of that rule, and it is worth reading beside this one.** Four more endings give 0 having rendered nothing at all — a frame argument that is not a number, an option whose value is missing, an animation whose start frame is after its end frame, and, in 5.2 and 5.3, saving switched off — and 5.3 adds a scene with no camera. And exit 1 is not what every refusal gives: `blender -ba <file>` does not end at all from 5.0 to 5.3, and Blender 4.5 handed an engine name that does not exist aborts at 134 on the Mac and never ends on the Norway machine. A Python script that fails leaves the run at 0 and lets the render happen anyway.
- **A missing output folder is not a failure.** Blender makes the folder — both levels of it — writes the frame into it, and ends at 0. No message of any kind, in any version.
- **A failed frame stops an animation.** With the output folder pulled out from under a six-frame render after frame 1, every version printed its error for frame 2 and stopped. Frames 3 to 6 were never attempted, exactly one file survived, and no part-written file was left. Status 1.
- **A broken template in the scene's own output path fails before frame 1** in every version, with the same wording — `Parse errors in path '…':` and, on a second line, `- Invalid or incomplete template expression '{blend_name.png'.` Nothing is written and the status is 1. **The same fault in a File Output node's name behaves the opposite way**: the affected outputs are skipped, everything else writes, the render finishes and exits 0 — settled under **File output nodes 15**.
- **A blend-file that is not there** ends at status 1 in every version, with the same wording: `Cannot read file "…": No such file or directory`.
- **A scene with no camera** ends at status 1 in 4.5 to 5.2 with nothing written, and the message reads `Cannot render, no camera`. **Not in 5.3** — see below.
- **A Cycles device Blender will not take** ends the whole process before any render happens, status 1, no output, in every version. The message reads `NONSENSE is not a valid Cycles device.` **A device name that is on Cycles' own list but has no hardware behind it gives the same 1 and different words** — `Error: Found no Cycles device of the specified type`, on standard output in every version, and in 5.3, as in 5.0 to 5.2, a `reports | ERROR` log line printed once the render has begun — so the two kinds of refusal cannot be told apart by the number. See question 12. In this test, and only in this test, Blender 5.0, 5.1 and 5.2 added a line afterwards about unfreed memory blocks and 4.5 did not; 5.3 added it too. Outside it the line comes and goes in every version: 4.5 prints it elsewhere — opening a file saved by 5.2 and rendering it ended with `Error: Not freed memory blocks: 4, total unfreed memory 0.000427 MB` on both machines — and the newer three sometimes do not. **Nothing reading Blender's output may treat the line's presence or absence as telling it which version is running.**

**All seven of those came back the same on the Linux machine, in all four versions.** So for 4.5 to 5.2 they rest on two operating systems rather than one; for 5.3, on the Mac alone.

**And six more were settled on the Linux machine, in all four versions, that the Mac could not reach.** Every one came back the same in all four:

- **An output folder that is genuinely read-only.** Nothing is written and the process ends at 1. What is said follows the same split as every other saving failure: 4.5 gives the system's own `Permission denied` on standard error with `Error: Render error (Invalid argument) cannot save: '…'` on standard output; 5.0, 5.1 and 5.2 give two log lines on standard output with `Render error (Success)` — an empty reason that says nothing. One thing about that machine belongs with the result: it is reached as the root user, and root walks straight through a read-only folder, so the plain run wrote the file and ended at 0. Only the runs with root's override dropped for the single command are what this answer rests on. **The same folder was made read-only on the Creator's Mac as well, and gives 1 with nothing written there too — but the reason in the brackets differs again**: 4.5 says `(Permission denied)` where that Linux machine said `(Invalid argument)`, and the newer three say `(Undefined error: 0)` where it said `(Success)`, their first line reading `image.write | ERROR OpenImageIO write failed: Could not open file "…"`. The version split falls in the same place on both. The Norway machine could not answer this at all, being used as root throughout.
- **A truncated blend-file.** Status 1 in every version, `Failed to read blend file '…': Missing DNA block`.
- **A file that is not a blend-file at all.** Status 1 in every version, `File format is not supported in file "…"`.
- **A file saved by a newer Blender is a warning, not a failure.** Handed a file written by 5.2, Blender 4.5, 5.0 and 5.1 each opened it, rendered it and ended at **0**, printing `File written by newer Blender binary (502.44), expect loss of data!` Blender 4.5 also printed a run of warnings about missing interface regions. *(How many of those region warnings there are is the one thing here nobody has pinned down: one run counted sixteen and another counted fifteen, and neither was written over the other. The count is not what the answer turns on.)*
- **A crash writes a file, and on Linux it is named after the blend-file.** Blender was made to crash on purpose. With a file loaded it printed `Writing: /tmp/simple.crash.txt` and wrote that file — named after the blend-file, not `blender.crash.txt`, which is the only name the manual gives for Linux (it gives the blend-file's name for Windows). With no file loaded it printed `Writing: /tmp/blender.crash.txt`. The process ended with status **139**, and the file held a version line, a backtrace section and a Python backtrace section. Anything printed immediately before the crash never reached standard output. The same in all four versions. On Windows this is untried.
- **Which handlers fire on four more kinds of failure.** A blocked save fires init, pre and cancel. A broken path template fires init and cancel only — `render_pre` never fires at all. A missing texture, which succeeds, fires the whole good-render set. And in 5.2 with output saving switched off and nothing else arranged, **not one handler fires**, not even the first; whether they fire when a File Output node is in the tree is unasked by anyone. The same in all four versions where the case exists.

**In 5.3, four of those six were tried, on the Mac, and none on Linux.** A file that is not a blend-file and a blend-file cut short end at 1 with the same words. The handlers fire as above on a blocked save, a broken template, a missing texture and saving switched off. **A crash** ends at status **139** and prints `Writing:` with the crash file's path, which is Blender's own temporary folder: named after the blend-file when one is loaded (`simple.crash.txt`) and `blender.crash.txt` when none is, holding a version line, a backtrace section and a Python backtrace section; the line printed just before the crash is lost; and macOS adds a Blender report of its own to the system's reports folder. That is the same shape the earlier versions gave on Linux, on another machine, so whether the versions agree on one machine is not established. Every version's manual says that on macOS the system's Crash Reporter shows a window and that `.crash` files may appear in `~/Library/Logs/DiagnosticReports/`; none mentions the `.crash.txt` file in Blender's temporary folder on macOS. **A read-only folder was not run** — the tests could not make one — and a file from a newer Blender cannot be made for the newest version there is.

**Where it differs, version by version.**

**A scene with no camera, in 5.3.** 4.5 to 5.2 refuse it at status 1 with `Cannot render, no camera` — 5.0 to 5.2 after announcing the frame — and fire `render_init`, `render_pre` and `render_cancel`. **5.3 ends at status 0**, writes nothing, prints `No camera found in scene "Scene"` on standard output under `reports` — the words Blender's window uses for the same failure — prints no `Rendering single frame` or `Rendering frame 1` line, and **fires no render handler at all**, not even `render_init`. With the log-file switch the message goes into the file and the run still ends at 0, so nothing on standard output and nothing in the status says the frame was never made. A render called from a script with no window is unchanged: it raises `Cannot render, no camera` and the run ends at 1, even when the script catches it. On the Creator's Mac; the same file built the same way and run on the same Mac the same day in the 5.2.2 run ended at 1, with 5.2's words and 5.2's three handlers, so the change is 5.3's own. On Linux it is untried.

**Switching off the automatic saving of render output.** The switch that stops a render's output being saved exists in **5.2 and 5.3**, and in no earlier version. Asked for by name in 4.5, 5.0 and 5.1 it is simply absent — the probe gets `AttributeError: 'RenderSettings' object has no attribute 'save_output'` on standard error — and the render goes ahead and writes as usual: all three frames rendered, all three saved, status 0. In **5.2**, turning it off stops the scene's own frames being written even when a place is named on the command line, reports `Render output disabled in Output properties and no active compositing File Output nodes`, and ends at **status 0** — while a **File Output node in the same tree keeps writing**. So "no file is written" holds for the Output panel's own file and not for the run as a whole. Run in all four versions on both machines. Blender 5.2's release notes state the change — "Saving render output can now be disabled." — and the Creator confirmed by eye that the Output panel's header carries a checkbox in 5.2 and in none of the other three, with the tooltip `Save Output` / `Write frames to disk for animation renders.`

**In 5.3**, on the Mac, the setting is present and on, and the Output panel's header carries the same ticked checkbox with the same tooltip. Turned off with nothing else arranged, **the run renders nothing at all**: it prints `Read blend:`, then `reports | ERROR Render output disabled in Output properties and no active compositing File Output nodes`, and quits — no `Rendering` line, no progress, no `Time:` line, no handler — at **status 0**, with no output folder made, for a still and an animation alike. With the window open and Ctrl-F12 pressed, the same words appear in the Status Bar, a floating report box and the Info editor. Called from a script with `--python-exit-code 7`, the refusal is raised into the script and the run ends at 7. This topic did not try a File Output node with saving off in 5.3. **The compositor 2** records it writing both frames on the Mac, while the scene's own output wrote nothing.

That is one of the endings that leave the process looking successful with nothing whole to show for it — see what the exit status is worth, above. **Whether the frame is rendered before the run ends is not settled in 5.2**: two runs of the same test agree that the status is 0 and the output folder empty, and disagree over whether the ordinary progress and the `Time:` line are printed first. See question 12. 5.3's refusal outright is its own answer and does not settle 5.2's.

**A saving failure's message.** In **4.5** it reads `Error: Render error (Not a directory) cannot save: '…'` on standard output, with one bare line on standard error naming the path and `Not a directory`. In **5.0, 5.1, 5.2 and 5.3** it is two log lines on standard output and nothing on standard error: `image | ERROR Couldn't create directory for file …: File exists` followed by `reports | ERROR Render error (File exists) cannot save: '…'`. The render itself finishes in every version; it is the saving that fails. 5.3 on the Mac.

**And this is the one message the two machines word differently.** On Linux, Blender 4.5 says `Error: Render error (Invalid argument) cannot save: '…'` where the Mac said `(Not a directory)`. The bare line on standard error reads `…: Not a directory` on both. The newer three say `(File exists)` on both machines. That is the operating system, not the version, and the version split — 4.5 giving one line with a real reason, the newer three giving two log lines — falls in the same place on both. **What Smoozy should take from it is that the reason in the brackets is not something to match on:** it changes with the computer.

**An image texture that has gone missing.** Every version rendered the frame and ended at 0. What is said about it differs at every step.

On Blender 4.5, a **Cycles** render whose image texture is missing prints nothing that separates it from the same render with the file in place: the frame is written, the run ends at 0, and standard error is empty. The whole of both streams was searched for "error", "warn", "cannot", "unable", "missing" and "not found" and no line about the texture matched. The picture's file name does appear, in the ordinary progress line `Updating Images | Loading <name>`, but that line is printed whether the file is there or not, in every version, so it identifies nothing. On an **EEVEE** render, 4.5 does print one line — `GPUTexture: Blender Texture Not Loaded!` — and prints it only when the texture is missing; it carries no error marking and does not name the file, so it says a texture is missing and never which one. **Run in all four versions on the Creator's Mac and on the Norway machine, 4.5's line lands on standard error**, while 5.0, 5.1 and 5.2 print `gpu.texture | ERROR Failed to create GPU texture from Blender image` on standard output instead, and 5.3 prints a different line again, `image.gpu | ERROR Image file "…" does not exist`, naming the file — question 13 has it. The Cycles half of 4.5 was captured against a control in the same runs and prints nothing. See question 13. A file that is present but **corrupt** is named in 4.5, by `IMB_load_image_from_memory: unknown file-format (<path>)`, where a missing one is not. From 5.0 the missing file is named outright:

- **5.0**: one line, `cycles | ERROR Image file '…/gone.png' does not exist.` — with the path in quotation marks.
- **5.1**: the same line without the quotation marks.
- **5.2**: two lines, `cycles | WARNING Image file … does not exist.` and then `cycles | ERROR Failed to load 1 image files`.
- **5.3**: the same two lines as 5.2, on the Mac, with the frame written and the cube painted magenta.

The same test in all four versions on the Linux machine gave the same four answers, so for 4.5 to 5.2 this difference rests on two operating systems. The Cycles half is settled again, from six kinds of absence, under **Images 9**.

**What each version's sources happen to name, and what that is worth.** The named failures are not the same set from version to version:

- All five document the graphics-card memory fallback for CUDA, OptiX, HIP and Metal, with oneAPI missing from the list in every version; the `Error: Out of memory` message; the Windows NVIDIA display-driver timeout; the Linux "Unsupported GNU version"; "CUDA Error: Kernel compilation failed"; EEVEE's warning that too much graphics memory can crash, freeze or kill the application; crashes and the crash file; and OSL compilation errors going to the system console.
- **EEVEE's "Shadow buffer full" is quoted by 5.0, 5.1, 5.2 and 5.3 and not by 4.5.** Do not read that as a change. The setting behind the message, the shadow pool size, was read in all four and reads the same in every one, including 4.5. Whether the message itself exists in 4.5 could not be reached — producing it needs a card whose memory can be exhausted on its own. **Not established.**
- **An incompatible video container and codec is quoted by 5.0, 5.2 and 5.3 and not by 4.5 or 5.1.** That is documentation alone. The refusal itself was run in all four versions on both machines, and not in 5.3, and reads `Error: Could not initialize streams, probably unsupported codec combination`, and it ends at **exit status 0** — another thing that fails without moving the status. Which pairings are refused is settled under **Images 4**.
- **A Cycles repeat-zone node whose iteration count is not constant is quoted by 5.0 alone.** Never tested. **Not established.**
- **Blender 4.5's release notes name graphics-card stability problems particular to that release** — AMD RDNA2 artifacts in volumes on Windows, HIP RT crashes, and crashes with more than one Intel card, the last with a note that a solution was already in 5.0. The first two describe 4.5 without a version comparison. The Intel note is a **documented change**, specifically a solution in 5.0 alpha and a planned 4.5.1 fix; it does not establish a difference between every 4.5 and every 5.0 build. None was tested here.
- **Blender 5.1's and 5.2's release notes name render failures that were fixed** — a cancelled command-line render's memory warnings, a CUDA illegal-address error, and an out-of-memory error on a file that rendered in 5.0.1. These are titles of fixed bugs. None was tested in any version.

**What the one-card machine could and could not reach among those.** It has a real NVIDIA card, and both `CUDA` and `OPTIX` were accepted as a Cycles device and both rendered, in all four versions — the NVIDIA half of a question the Mac could only answer for Apple's own graphics. But the memory fallback was not seen there: it needs the card filled while the machine's own memory is not, and that machine was shared with other jobs. The Linux compiler failure could not be reached even on Linux, for a reason worth keeping: it comes from a graphics kernel being built while Blender runs, and every Blender there ships one already built for that card, so no build is ever attempted.

**And on the four-card machine the memory fallback was finally seen — and it is silent.** A scene was grown until it needed about 33 GB on a card that holds 16. **The render did not fail.** The card filled to its own size and stopped, the rest was taken from the machine's own memory, the picture was written, the process exited **0**, and searching both output streams for `out of memory`, `failed to allocate`, `cannot allocate` and `insufficient` matched **nothing**. The only sign was the cost. The same in 4.5, 5.0, 5.1 and 5.2. The figures are under question 6.

**So a documented failure turns out not to be a failure.** Every version's manual says a full graphics card makes Blender fall back to system memory. The tested fallback happens, it says nothing, and it costs an enormous amount of time. For anything renting a machine by the hour that is the expensive case: the job succeeds and the bill is ten times what it should be. **What was *not* reached is `Error: Out of memory`** — that machine had 197 GB to spill into, and running that out as well was not attempted.

**And the one scene that ever filled a card was made of 128 pictures of 8192 by 8192 pixels.** The heaviest scene this research ever built out of geometry never filled a card at all — under **What a render demands 7** OptiX peaked at 8,353 MiB of a card's 10,240 and finished, and CUDA never passed 1,775 MiB. So whether the card fills first or the machine does may be the kind of scene or may be the ratio between the two, and nothing on record separates them.

**EEVEE's "Shadow buffer full" still hangs unanswered**, in every version, 5.3 included: the scenes that filled a card were Cycles scenes and nobody attempted the EEVEE case. **None of the graphics-card failures was reached in 5.3**, which never ran on a machine with a card of its own; on the Mac a card cannot run out while the machine's memory holds, the two sharing one pool.

**Running the machine's own memory out during a render is under question 10.** It was reached, in all four versions, and the two endings it produces are the sharpest version difference in this topic. It was not tried in 5.3.

**One place a live tooltip and the manual's picture disagree, in 5.2.** The manual's picture of the bad-path tooltip is headed `Syntax error(s):`; the build on the Creator's machine reads `Path template error(s):`. The error line under it is word for word the same. 5.3's tooltip reads the same `Path template error(s):` heading and line, in red, with the path field itself drawn red — on the Mac.

## 2. Where does Blender say that a render failed, and what does it say there?

**How it is known.** All four versions **document** the same set of general reporting places — the Status Bar's report message, the Info editor, the console or terminal, and the render engine's own `report` and `error_set` calls — and all four say plainly that no version's sources state where a failed render in particular reports itself, or what it says. Blender 4.5, 5.1 and 5.2 mark as **inferred** the step from "this place carries errors" to "a render failure appears here". Blender 5.0 adds a release note saying operator reports now travel through the logging system, and 5.2 adds the reports list. The rest was settled by tests in all four versions on the Creator's Mac, by the Creator at the window in all four, and then by tests in all four versions on the Linux machine, with a window and without. **Blender 5.3's** documents **document** the same reporting places, a script's exception and the crash file, and mark the same step **inferred**. 5.3 was tested on the Creator's Mac alone, with no window and with one, its keys and pointer sent through Blender's own event system rather than by a person.

**Verdict: it differs.**

**What is the same in every version.** Each held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise.

- **With no window, the message is printed and the process status carries the outcome.** Status 1 on failure, 0 on success — with the limits on what a status is worth set out under question 1. **In 5.3 a scene with no camera breaks this**, ending at 0.
- **All seven render handlers exist in every version** — init, pre, post, write, complete, cancel and stats. On a render that succeeded, the order was init, pre, a long run of stats, then post, write, complete. On the tested no-camera failure, the whole of what fired in 4.5 to 5.2 was init, pre and **cancel** — no complete, no post, no write; **in 5.3 nothing fired at all** (question 1). Other failures were also tested: a blocked save fires init, pre and cancel; a broken template fires init and cancel; a missing texture fires the good-render set; saving switched off with nothing else arranged fires none. Question 1 gives the machines and limits for those results.
- **With the window open, a failure is announced in three places at once**, each carrying a round white-on-red cross: along the bottom of the window on a red field, in a floating box headed `Report: Error`, and as an entry in the Info editor. All three read the same words. Same in all four versions, seen on the Creator's Mac, and in 5.3 after a simulated F12 on the no-camera file and a simulated Ctrl-F12 with saving switched off. On a broken path template 5.3's picture caught the Status Bar and the Info editor and no floating box.
- **The same failure is worded differently depending on whether Blender has its window open — in 4.5 to 5.2.** A scene with no camera, rendered with F12 at the window, is announced as `No camera found in scene "Scene"`. The same prepared file rendered with no window prints `Cannot render, no camera`. Same machine, same day, same file, in each of those four. Anything reading their printed output must not expect the window's words. **This is not a macOS oddity**: the same file was rendered with a window open on the Linux machine, in 4.5 and 5.2, and the window's wording came back the same there. **5.3 is the exception**: its windowless command-line render prints the window's words, `No camera found in scene "Scene"`, and only a render called from a script with no window still says `Cannot render, no camera`. So in 5.3 the words follow how the render was started rather than whether there is a window.
- **What the render operator hands a script**, in every version, with a window and without. Success gives back `{'FINISHED'}`. Failure **raises** — `RuntimeError Error: Cannot render, no camera` with no window, `RuntimeError Error: No camera found in scene "Scene"` with one. That was run in all four versions on the Linux machine and settles a step every version's document had only been able to mark **inferred**, because the documentation describes operators in general and never names rendering. One thing worth knowing beside it: a windowless run whose script *caught* the exception still ended at status 1.
- **The broken template in the scene's own output path is the counter-example, and it is also the same in all five.** There the window and the terminal agree word for word, in 5.3 as before: `Parse errors in path '…':` and `- Invalid or incomplete template expression '…'.` The path quoted differs only because the Creator's own file used a different one.
- **No Blender Render window opens for the no-camera failure**, in any version. One does open for the broken-path failure, showing an empty checkerboard, in all four versions; 5.3's small window was photographed as plain grey, in pictures known to lag the window.
- **How the render was started decides whether the window is told at all.** Pressing F12 gives the three places above. A render invoked from a script instead **raises** the failure back into that script and puts nothing in the Info editor, no report box on the bottom of the window, and — in 5.2 and 5.3, where the list exists — nothing in the reports list. The same in all four versions on the Creator's Mac and on the Norway machine, and in 5.3 on the Mac. See question 13.

**Where it differs, version by version.**

**Whether Blender's reports can be read from Python.** In **4.5, 5.0 and 5.1** the window manager has no reports attribute at all — the probe printed `REPORTS: attribute not present in this version` in each, on both machines. In **5.2 and 5.3** it exists, and in 5.2 so does the report object behind it, carrying a message, a severity and a session-wide identifier. Blender 5.2's release notes state the addition. **In 5.2 the list is empty after every render failure anybody tried** — after a failed background render, after a no-camera failure with the window open that a script started, and after a render whose image texture was missing, across three machines. **In 5.3 it is empty after a failure with no window and after a failure a script started, and it holds one entry after a failure started by a key** — the failure's own message, typed `ERROR`, after F12 on the no-camera file and after Ctrl-F12 on a broken template or with saving switched off. No 5.2 list was read after a key-started failure, so whether that is new in 5.3 is not established. **In both it is not always empty.** Opening a file whose linked library is missing fills it with all five of the messages that raises, two marked `WARNING` and three `INFO` — see question 13. And in 5.3 a render engine's own `report` call lands in it with the window open (below).

**The shape a failure message takes when printed.** In **4.5** every failure message begins with the word `Error:` and a space, and nothing else — `Error: Cannot render, no camera`, `Error: Cannot read file "…": No such file or directory`. From **5.0 to 5.3** each is a log line: an elapsed time, a category, a vertical bar, a level word and the message — `00:00.268  reports          | ERROR Cannot render, no camera` in 5.0 to 5.2, and in 5.3, whose words for that failure differ, `00:00.331  reports          | ERROR No camera found in scene "Scene"`. Three categories carried failure messages in the newer three: `reports` for what an operator reported, `image` for the file-writing complaint, and `cycles` for the render engine's own. 5.3 used those three and, on the Mac, three more: `image.gpu` for EEVEE's missing texture, `object.modifier` for a missing cache, and `operator` for a broken template with the window open. A message that runs to more than one line keeps the vertical bar and leaves the timestamp and category blank.

**But not every message is a log line in the newer three.** What Blender prints while it is still reading the command line, and what a sub-command prints, stays a plain `Error:` line in every version — `unknown argument, loading as file: …`, `Error: not a number '-f / --render-frame abc'.`, `Error: engine not found '…'`, `Unrecognized command: "maketx"`, and the unfreed-memory line. The log shape covers what travels through the logging system and nothing else. See questions 12 and 13. 5.3 keeps the same plain lines, and adds one: a render called from a script with saving switched off prints a plain `Error: Render output disabled in Output properties and no active compositing File Output nodes`.

**Which stream carries it.** Almost everything is on standard output in every version, and **every version puts some of Blender's own words on standard error**. Six are shared by all five, on every machine that ran them — 5.3 on the Mac: `unknown argument, loading as file: …`; the three complaints about a frame value that is not a number, a stray comma and a missing `-o` value; `Error: engine not found '…'`; and a failing Python script's traceback, joined by `Error: script failed, file: '…', exiting.` when `--python-exit-code` is set. **Four more go there in 4.5 and nowhere else**: the line that ends the `-ba` run, the refusal of a Cycles device name that is not on Cycles' list, the EEVEE complaint about a missing image texture, and the bare one-line complaint when saving fails. **One more in 4.5, 5.0 and 5.1**: `Unrecognized command: "maketx"`, that command existing in 5.2 and 5.3 alone. **And one in 5.2 and 5.3 that no earlier version has**: `maketx`'s own `Error: Source image not found`, which is the only failure in this topic announced on both streams at once. Two further ways standard error fills sit elsewhere — a windowless 5.2 on a Linux machine with a display running, just below, and a refused memory allocation in 5.1 and 5.2, under question 10 — and in 5.3 a missing Alembic cache brings four lines from the Alembic library itself, which are that library's words and not Blender's (question 13). **What is settled and easy to misread the other way: on an ordinary render with nothing wrong, standard error is empty in every version**, 5.3 included on the Mac, and that was measured against a control run rather than assumed.

**One warning about "standard error stays empty", and it is the kind of thing a render farm trips on.** On a Linux machine that has a screen running, a windowless Blender **5.2** wrote four display-library complaints to standard error on a **completely successful** render; 4.5, 5.0 and 5.1 wrote nothing. Turning the display off silenced them, and every other Linux run recorded had the display off first. The words are the display libraries' and not Blender's, so they must never be quoted as Blender's — but the practical point stands: on that kind of machine, in that version, standard error is not reliably empty even when nothing has gone wrong. Run in all four versions. **Why only 5.2 does it is not established** — no version's findings say what makes that build reach for the display where the other three do not. What is established is that it does. 5.3 never ran on such a machine, so whether it does the same is untried. Standard error is not reliably empty in any version, for other reasons as well: see questions 7, 10, 12 and 13.

**Where else a failure message can end up, and this one is a trap.** From **5.0 to 5.3** the log-file switch moves the whole log into the file, and **the failure message goes with it**. Standard output drops to three lines — the version banner, a blank line, `Blender quit` — and a program watching standard output for a reason sees none, while the exit status still says 1. **In 5.3 a scene with no camera closes even that**: the message goes into the file and the status is 0, so nothing outside the file says anything went wrong. In **4.5** the switch makes the file, leaves it empty, and everything still goes to standard output as usual. 4.5 to 5.2 were run on the Linux machine; 5.3 on the Mac.

**A render engine's own reporting calls, tried in 5.3 alone, on the Mac.** A tiny engine registered from a script called `report` with a warning and, last, `error_set`. Every call returned, with no window and with one. With no window, `report` printed a `reports | WARNING` line on standard output. With the window open it reached the Status Bar, the Info editor and the reports list; that run's terminal capture contains no line from either `report` or `update_stats`. **The `error_set` text appeared nowhere looked at** — not on the terminal, not in the reports list, the Status Bar or the Info editor — and the run still ended at 0; the render window's own status line ran past the window's edge, so whether it was drawn there is not established. No earlier version tried either call.

**The sharpest thing this topic learned, and it is about who filled the card rather than how full it is.** On the four-card machine, a separate small program was made to take and hold almost all of one card's memory — 15,616 MiB of 16,380 — and Blender was then asked to render on that card alone. **Blender failed, loudly, and exited 1.** In 4.5 the message is `Out of memory in CUDA queue enqueue (integrator_shade_surface)`, and a script running the render had the error raised at it as well. In 5.2 the same message arrives as log lines, with two more beneath it — one pointing at the Cycles graphics-card documentation and one reading `System is out of GPU memory`.

**Set that beside question 1's answer, because the two are opposite and the condition is the same.** When **this render's own scene** is too big for the card, Blender says nothing, exits 0, writes the picture, and takes about ten times longer. When **another program** has taken the card's memory, Blender stops and says so plainly, exits 1, and writes nothing. The card is equally full in both cases. Which of the two happens depends on **who consumed the memory**, not on how much is left. For anything renting a machine by the hour: a neighbour is loud, a heavy scene is silent, and the silent one is the one that costs money.

**This is not established for every version.** It was run in **4.5 and 5.2 only**, on that one machine, and 5.0, 5.1 and 5.3 were never asked. So the *difference in wording* between 4.5 and 5.2 above is the same difference the whole of this comparison already records — plain lines against log lines — and nothing here says any version behaves differently. That the failure is loud at exit 1 is settled for 4.5 and 5.2 on Linux with an NVIDIA card, and for nothing else. The machine is gone, so the missing versions cannot be filled in on it.

## 3. What does Blender report about how far through a piece of work it has got?

**How it is known.** All four versions **document** the same three things from their sources: a Status Bar item for the running task, showing a task name, a filled bar, a whole-number percentage and a cancel button; a render engine's own progress call, taking one fraction between nought and one with no unit attached to it; and the general job-progress calls a script can use. Blender 4.5's and 5.1's documents add the fluid-bake and point-cache readouts. Blender 4.5 and 5.2 document a call that tells a script only whether a job is running, never how far — it returns true or false, so it cannot carry a position; 5.0's and 5.1's documents do not mention it, and nothing suggests that is a change. Blender 4.5, 5.1 and 5.2 all record that their sources say nothing about progress being printed; only 5.0's release notes give a worked example. The rest was settled by tests in all four versions on the Creator's Mac, by the Creator at the window in all four, and then by the same tests in all four versions on the Linux machine, **which agreed with the Mac on the line shape, the fields, the frame announcements and the line counts**. **Blender 5.3's** documents **document** the same Status Bar item, engine progress call and script progress calls, and a render-statistics sentence worded as 5.2's; they say nothing about progress being printed. 5.3 was tested on the Creator's Mac alone.

**Verdict: it differs.**

**What is the same in every version.** Each held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise.

- **Progress is reported when there is no window**, in every version, which is the thing four of the five documentation sets do not mention at all — but only when the render is started with `-f` or `-a`. Started by calling the render operator from a script, progress is printed in 4.5 alone. See question 9.
- **No running figure spans a whole animation**, in any version. There is no animation-wide sample count, no animation-wide percentage and no animation-wide time estimate. The frame range itself *is* announced from 5.0 to 5.3, once, before any frame starts — see below.
- **A frame that runs to its full count prints its own sequence**, from `Sample 0/16` to `Sample 16/16`, then `Finished`, then `Saved:`, then `Time:`, and starts over. That is the shape of one frame small enough not to be split into tiles. A frame big enough to tile carries a `Rendered <n>/<total> Tiles` field inside the same line, before the sample count — see question 7. In 4.5 to 5.2 a frame that stops short ends on `Sample 0/<maximum>` instead; **5.3 prints no such line** — see question 11.
- **The Status Bar's percentage is a whole number, tracks the samples within the current frame, and restarts at each frame**, in all four versions on both machines — see question 7. **In 5.3** it is a whole number, and a render engine's own `update_progress(0.5)` drove it to exactly 50%; what it tracks across a Cycles frame, and whether it restarts at the next, is not established, because 5.3's pictures lag the window by several seconds — they read 0, 92, 78 and 92 per cent across a two-frame render, and cannot be tied to frames.
- **No percentage tracks the samples in the printed output**, in any version — that percentage belongs to the window. Percentages do appear in the printed output, inside stage lines rather than on sample lines: `Updating Scene BVH | Building BVH 0%` is on record in 4.5, 5.2 and 5.3, and 4.5 with Freestyle switched on prints `Freestyle: Visibility computations 0%`. Every percentage anywhere on record reads `0%` and nothing shows one moving; whether they ever climb is unresolved. No percentage is on record for 5.0 or 5.1, which is a silence in the record and not a finding about those versions.
- **The Blender Render window carries its own one-line status** in every version, with the frame number, the previous frame's time as `Last:`, an elapsed `Time:`, often a `Remaining:`, memory, and then a sample count or a stage. A bracketed note follows the sample count and moves through the loading and optimising of render kernels — recorded as it appeared, with nothing read into it, in all four versions. 5.3's line carried the same fields — `Frame:2 | Last:00:13.19 Time:00:00.01 | Remaining: 00:11.98 | Mem: 5M` — but its narrow window cut the line off before any note.
- **A different engine reports differently, and does so in every version.** EEVEE printed roughly a dozen lines against Cycles' fifty-odd, with a sample count of the form `Rendering 25 / 64 samples`, no remaining time and no per-stage lines. What an EEVEE line carries besides that sample count is **not** the same in every version — see below.
- **Preparation stages are named before sampling begins** in every version — building the scene's acceleration structure, synchronising objects, loading denoising kernels, and so on, one line each.

**Where it differs, version by version.**

**The shape of the printed line.** In **4.5**: `Fra:1 Mem:9.77M (Peak 9.77M) | Time:00:00.02 | Remaining:00:00.05 | Mem:1.48M, Peak:1.48M | Scene, ViewLayer | Sample 1/16` — a frame number, two memory pairs, an elapsed time, sometimes a remaining time, the scene and view layer, and the stage or sample count. From **5.0 to 5.3**: `00:00.430  render           | Fra: 1 | Remaining: 00:00.05 | Mem: 2M | Sample 1/16` — an elapsed timestamp, the category `render`, a vertical bar, then a frame number, sometimes a remaining time, one memory figure and the stage or sample count. The scene and view layer and the second memory pair are gone from 5.0 on; the timestamp and category are new from 5.0. Blender 5.0's release notes say the logging system was unified and the output format changed, and warn that render farms parsing this output may need updating. Every line of either shape quoted here came from a picture small enough not to be split into tiles. **A tiled line has been kept**: question 7 holds the thirteen lines a tiled frame prints in 4.5 to 5.2 and the twelve 5.3 prints, with their tile and sample numbers in order, and they are these same two shapes with a tile count added inside the line, before the sample count.

**Whether frames are announced.** From **5.0 to 5.3** a single-frame run opens with `Rendering single frame`, `Rendering frame 1`, `Start rendering: Scene, ViewLayer` and `Engine: Cycles`, and an animation opens with `Rendering animation (frames 1..3)` and then names each frame as it begins. That frame range is the one figure covering the animation that any version gives, and it is stated once, at the start. In **4.5** none of those lines exists. Nothing announces the start of a frame, and no line anywhere names the frame range — the frame number inside the running progress line is the only marker there is.

**What the render-statistics handler receives.** In **4.5** the handler is handed the whole printed line, so `Fra:2 Mem:9.77M (Peak 10.95M) | Time:00:00.00 | Remaining:00:00.01 | Mem:1.48M, Peak:1.48M | Scene, ViewLayer | Sample 1/16` arrives complete, frame number included. From **5.0 to 5.3** it is handed only the message part — no timestamp, no category and **no frame number** — so `Remaining: 00:00.01 | Mem: 2M | Sample 1/16` arrived word for word identically at frames 1, 2 and 3, and which frame each belonged to rests on the order they printed in. In every version the handler receives one string plus a second value that printed as nothing (`None`, in 5.3), and it fires once per stage rather than once per render, with no window open: over three frames that is 127 times in 4.5, 130 in 5.0 and 5.1, 133 in 5.2 and 5.3. The per-frame counts are under question 8.

**What an EEVEE progress line carries.** In **4.5** it carries a memory pair and an elapsed time: `Fra:1 Mem:40.65M (Peak 40.65M) | Time:00:00.28 | Rendering 1 / 64 samples`. From **5.0 to 5.3** it carries neither: `Fra: 1 | Rendering 1 / 64 samples`. Same test in all four, on both machines, and in 5.3 on the Mac, so this is a real difference, at the same boundary as everything else here.

**The name the Status Bar gives the task.** `Render...` in **4.5**; `Rendering...` from **5.0 to 5.3**. Seen by eye on the Creator's Mac in all four and photographed on the Linux machine in all four, so for 4.5 to 5.2 it rests on two operating systems; 5.3 was photographed on the Mac. A sequencer render is labelled `Rendering sequence...` in all five, 4.5 to 5.2 on both machines and 5.3 on the Mac.

**The Blender Render window's status line.** In **4.5** it carries the scene and view layer and two memory figures — `Mem:1457.36M, Peak:1457.36M`. From **5.0 to 5.3**, while a frame renders, it carries one — `Mem: 1482M` — and no scene or view layer. Seen at the Creator's window, on the Mac only. Once 5.3's render had finished the line read `Frame:2 | Time:00:13.21 | Mem:5M, Peak: 5M`, two figures again; no earlier record shows the line after a render, so nothing is compared on it.

**The name of the EEVEE engine, and the route that decides which name works.** Which name a version accepts depends on **how** it is set:

| | `-E` on the command line | `scene.render.engine` set from a script |
|---|---|---|
| 4.5 | `BLENDER_EEVEE_NEXT` only. `BLENDER_EEVEE` errors, writes nothing, then hangs | `BLENDER_EEVEE_NEXT` only. `BLENDER_EEVEE` is refused |
| 5.0, 5.1, 5.2 | **Both** names accepted, exit 0, same file size | `BLENDER_EEVEE` only. `BLENDER_EEVEE_NEXT` is refused |
| 5.3 (the Mac) | `BLENDER_EEVEE` accepted, exit 0; the old name not tried | `BLENDER_EEVEE` only. `BLENDER_EEVEE_NEXT` is refused |

**The name that works everywhere, by every route, is the version's own** — `BLENDER_EEVEE_NEXT` in 4.5, `BLENDER_EEVEE` from 5.0 to 5.3. The script route was run here in all four versions on the Linux machine, and again from the running program in all four versions on both machines and in 5.3 on the Mac. Two things about the command-line route are still open: whether a 5.x run under the old name really renders in EEVEE, and whether it warns. Neither was captured, and the acceptance rests on one run on one machine on a 64 by 64 scene.

**One more thing about reading progress rather than about any machine.** Blender's printed output **can be read as it arrives** — piped into a reader, the lines came out spread across the run rather than in one lump at the end, with each line reaching the reader within a fraction of a second of the elapsed time Blender itself stamped on it. The same in all five versions, 5.3 on the Mac. **Question 14 holds the whole of that**, including what a script's own printing does instead, which is the opposite. Worth knowing beside it: in a background render Cycles prints only three sample lines per frame, so there is little to read between them.

## 4. What does Blender write out as it works, what is that stream called, and what does it contain?

**How it is known.** All four versions **document** the same name for the destination — the Console Window, also called a Terminal — and all four record that their sources never use the words "standard output" or "standard error" for Blender's own writing. All four **observe** the one place a stream is named: the help text of Cycles' own statistics switch, which reads "Print rendering statistics to stderr" in every version's file, and all four are careful that this is the help text, not the behaviour, marking the step to the behaviour **inferred**. The rest was settled by tests in all four versions on the Creator's Mac and on the Linux machine. **Blender 5.3's** documents do the same — the same name, the same silence about the two streams, the same help text **observed** in Cycles' file and set apart from the behaviour — and 5.3 was tested on the Creator's Mac alone.

**Verdict: it differs.**

**What is the same in every version.** Each held in 5.3 on the Creator's Mac as well.

- **Almost everything Blender writes goes to standard output**, in every version. On an ordinary render with nothing wrong, standard error is empty in every version on every machine, and that was measured against a control rather than assumed. **It is not empty in general**, and every version puts some of Blender's own words there. Question 2 holds the split by version; the individual cases are under questions 2, 7, 10, 12 and 13.
- **The Cycles statistics go to standard output too**, in every version and on both machines — despite the help text in Cycles' own file naming standard error in every version. Every version's document notes the mismatch. This is one of the few places all five documentation sets agree with each other and all five are wrong about the machine.
- **The statistics are printed plainly, not as log lines** — no timestamp, no category, no vertical bar — in every version.
- **The statistics are labelled by what the memory holds** — geometry, textures or images, per object, per shader — in every version. See question 6.
- **The statistics come in two blocks**, `Update statistics:` during the preparation stages and `Render statistics:` later, in every version on both machines. **No sample count appears anywhere in either block, in any version.**
- **The quiet switch's own help text is word for word the same in all five**, and the same on both machines: "Suppress status printing (warnings & errors are still printed)." What it actually does is not.

**Where it differs, version by version.**

**What quiet mode removes.** In **4.5**, `-q` leaves the whole of standard output at one line — the version banner. The file-read line, every progress line, the `Saved:` line and the `Time:` line all go. From **5.0 to 5.3** the render log survives in full, from `Rendering single frame` through every sample line to the closing time, and exactly three lines go: the line naming the file that was read, a blank line, and `Blender quit`. The picture is still written and the run still exits 0 in all five. Same in all four versions on both machines, and in 5.3 on the Mac. How long the run is either way is under question 8.

**All of that is a run that finished. A run that is stopped adds one more line under `-q` in all four versions** — the break sentence answering the stop, `Sent an internal break event. Press ^C again to kill Blender`, recorded under **Frames 15** on both machines, and there in 5.3 on the Mac too; this topic did not try it in 5.3. Which stream it lands on is written down nowhere, so whether it reaches standard output is not settled.

**What the log-file switch does.** In **4.5** the file is made and stays **empty**, and all the usual output still goes to standard output. From **5.0 to 5.3** the whole log is **moved** into the file, standard output drops to three lines, and a failure message goes into the file rather than to the terminal. Run in all four versions on the one-card Linux machine, and again on the Creator's Mac and the Norway machine, where a missing-file complaint went into the file the same way; 5.3 on the Mac, with an ordinary render, a missing texture and a scene with no camera.

**Where the Cycles statistics block sits, and what shape it is.** In **4.5** the block sits after the last sample line and before `Saved:`. From **5.0 to 5.3** it sits last of all, after `Saved:` and after `Time:`. Blender **4.5, 5.0 and 5.1** write the image section as three lines under a `Textures:` heading; **5.2 and 5.3** write it as two, `Image statistics:` then `Total image memory: 0B (0)`, and write small byte counts with a `B` where the other three write them plain. Run in all four versions on both machines, which agreed on the order in every version and on the byte counts; 5.3 on the Mac.

The block's own figures are the scene's, not the version's fixed output, and two different runs are on record with no way to tell from the numbers which scene each came from. One gives `Total memory: 575 (575)` in 4.5, `579 (579)` in 5.0 and 5.1 and `386B (386)` in 5.2. The other gives `24.03K (24,607)` in 4.5, `24.04K (24,615)` in 5.0 and 5.1 and `16.36K (16,750)` in 5.2, broken down as `Sphere 23.55K (24,113)` and `Cube 413 (413)` in 4.5, `Sphere 23.55K (24,117)` and `Cube 417 (417)` in 5.0 and 5.1, and `Sphere 16.02K (16,405)` and `Cube 289B (289)` in 5.2. **Neither set is a correction of the other** — they are two runs on two scenes. 5.3's run gives `16.41K (16,800)`, with a `backgroundlight` line no earlier figure carries; the 5.2.2 run of the same scene on the same Mac printed exactly the same block, so the extra line and the extra bytes are that scene's world light and not 5.3. What is a version difference is the shape and the place, not the figures. Everything below the kernel heading is times and percentages that changed from one run to the next on the same machine, so none of that is any version's fixed output either.

**Which stream the Cycles debug switch uses.** `--debug-cycles` writes to standard error in **4.5** and to standard output, as `cycles` log lines, in **5.0, 5.1 and 5.2**. Run in all four versions on the Linux machine. That is the same boundary as everything else here, and it matters because that switch carries figures nothing else does — see question 6. **5.3** writes it to standard output as `cycles` log lines, on the Creator's Mac, where no earlier version was run with this switch; so 5.3's place beside the others rests on a different machine and is not established.

**Listing the logging categories.** **4.5** has no such switch. Handed `--log-list-categories`, it takes it for a file name, prints `Cannot read file "…/--log-list-categories": No such file or directory`, and ends at status 1. 5.0 to 5.3 accept it and end at 0. **The count grows with the version on both machines, and the whole list is longer on Linux**: **135** categories in 5.0, **139** in 5.1 and **149** in 5.2 on the Mac, against **169**, **173** and **182** on Linux, where a run of window-system names appears that a Mac would have no use for. The same three Linux figures came back on the Ada machine, which is worth having, since the two machines were not the same one. Two things about the counting: a list read straight off the terminal gives one more in each — 170, 174 and 183 — because the list is printed with the version banner at the top, so the larger figures count lines and the smaller count categories; and **5.2's own two readings of Linux disagree, 182 against 183, with neither chosen**. Which exact names differ cannot be worked out, because the Mac's list was kept only as a count. The list is the same whether Blender is started with a window or without. Blender 5.2's Mac list holds sixteen names 5.0's does not, about asset libraries, graphics, hydra and a handful of others. **5.3 lists 153 on the Mac.** Set against the 5.2.2 run on the same Mac the same day, which listed 149, 5.3 adds six names — `geom.annotations`, `gpu.metal`, `io.otio`, `io.spz`, `project` and `seq.edit` — and lacks two, `geom.gpencil` and `gpu.debug.metal`. `render`, `cycles`, `image` and `reports` are in both. 5.3's Linux list is untried.

**Setting the logging level.** **4.5** wants a number — the manual's own form is a level of 1 by default and -1 for everything — and refuses the word `info` with `Error: not a number '--log-level info'.`, after which the render goes ahead anyway and ends at 0. From **5.0 to 5.3** they take named levels: fatal, error, warning, info, debug, trace. What each setting adds to a run's length is under question 8. **At information level 5.3 logs one line the 5.2.2 run on the same Mac does not**, first of all: `color_management | Using Blender config: "…/config.ocio"`.

**Whether the render is in the log at all.** In **4.5**, logging everything at the deepest level produced 431 lines and not one of them carried a `render` or a `cycles` category — the categories that appeared were about application folders, collections, library overrides, sound, file reading, the Python interface and translations. The render progress lines were printed alongside the log without being part of it. From **5.0 to 5.3**, `render` is one of the categories and the progress lines are log lines.

**The shape of a log line.** In **4.5**: a level, a category in brackets, the source file and line, the function name, then the message — `INFO (bke.appdir): source/blender/blenkernel/intern/appdir.cc:329 test_env_path: env … found: …`. From **5.0 to 5.3**: an elapsed timestamp, the category, a vertical bar, then the message. Blender 4.5 has a separate switch to add a timestamp; the later versions carry one on every line without asking.

**Which switches the built-in help lists.** Blender **4.5** lists `--log`, `--log-level`, `--log-show-basename`, `--log-show-backtrace`, `--log-show-timestamp` and `--log-file`. Blender **5.0 to 5.3** list `--log`, `--log-level`, `--log-show-memory`, `--log-show-source`, `--log-show-backtrace`, `--log-file` and `--log-list-categories`, with worked examples of the matching patterns. The same switch sets came back on both machines. The whole help text grows with the version on both, and is a little longer on Linux: 434, 466, 498 and 518 lines on the Mac, against 447, 479, 505 and 525 on Linux. That last difference is the machine, not the version. 5.3's help is 521 lines on the Mac, against 518 from the 5.2.2 run on the same Mac, its logging section word for word the same.

**Whether `--verbose` still works in 5.0 is not settled.** Blender 5.0's release notes say `--debug-cycles` and `--verbose` were replaced by the new logging switches, while its manual's arguments page still lists both. Nothing chooses between them and no test settled it: `--debug-cycles` was run and works in all four versions, and `--verbose` was never given to a running Blender in any version. The other versions' documents, 5.3's included, do not raise it, and 5.3's built-in help does not list it among its logging switches.

## 5. Does Blender estimate the time left, for what unit of work, and how does it describe that estimate?

**How it is known.** All four versions **document** exactly one sentence from their sources — that resting the mouse pointer on the progress bar shows a time estimate — and all four say the wording, the units and the unit of work are not given anywhere. Blender 5.1 marks as **inferred** the step that the estimate belongs to the currently running task, from the neighbouring sentence. The rest was settled by tests in all four versions on the Creator's Mac, by the Creator at the window in all four, and then by the same tests in all four versions on the Linux machine. **The two machines agreed on everything about the printed field** — its spelling, its units, where it appears and what it covers — so all of the printed half below rests on two operating systems. The tooltip was seen at the Creator's window, on the Mac only. **Blender 5.3's** documents **document** the same one sentence and give nothing more. 5.3 was tested on the Creator's Mac alone, the tooltip reached with Blender's own simulated pointer.

**Verdict: it differs — but only in how the printed field is spelled**, between 4.5 and the four after it.

**What is the same in every version.** Everything the question asks. Each held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise:

- **Blender does estimate the time left when there is no window**, in every version, which no version's sources say. The estimate is a `Remaining:` field on Cycles' progress lines, sitting between the elapsed time and the memory figure.
- **It covers the current frame and nothing more**, in every version. In a three-frame animation it appeared once inside each frame in turn and started over each time. No line in any version gave a remaining figure for the animation as a whole.
- **It does not appear on every line**, in every version — it was absent from the first sample line, the final sample line and the `Finished` line. That is a frame that ran its full count. **Under adaptive sampling in 5.3** it appeared on every sample line and on `Finished` too, rising and falling, and read 22 seconds on a frame that had finished in about one; the 5.2.2 run on the same Mac printed a figure just as far out on its closing `Sample 0/4096` line. So the figure is no forecast when a frame stops early, in either.
- **EEVEE prints no estimate at all**, in every version.
- **The figure is in minutes, seconds and hundredths**, in every version.
- **The tooltip at the window is two lines and is worded identically in all five**: `Time Remaining: 00:33.73` and `Time Elapsed: 00:13.01.` — a forecast, a companion figure for time already spent, and a full stop closing the second line. So it counts down rather than towards a finishing clock time. 5.3's read `Time Remaining: 00:13.50` and `Time Elapsed: 00:07.48.`
- **The tooltip and the render window's own `Remaining:` disagree during an animation**, in every version where both were caught at once: the tooltip reads the larger of the two figures. How much larger varies — about seven times in 4.5, about twice in 5.0 and 5.1, about a third more in 5.2. The figures are recorded in each version's finding and nothing is read into them there. **5.3's two were not caught at once**, so this is not established for 5.3.

**Where it differs.** One character. Blender **4.5** writes `Remaining:00:00.05`, with no space after the colon, in the printed progress line and in the Blender Render window's status line alike. Blender **5.0, 5.1, 5.2 and 5.3** write `Remaining: 00:00.05`, with one. That is part of the wider change in line shape described under question 4, and it is the whole of the difference here.

## 6. What does Blender report about the memory it is using on a graphics card?

**How it is known.** All four versions **document** one setting and one only — a preference to show graphics-card memory in the Status Bar, off by default — and all four record that it appears in the Python documentation and not in the manual, whose list of Status Bar items names five things and not this one. Blender 4.5 marks as **inferred** the step that the setting is a Status Bar item at all, from its name and its company. All four say plainly that no other memory figure Blender reports is stated to be the card's. The rest was settled by tests in all four versions on the Creator's Mac, by the Creator at the window in all four, then on the one-card Linux machine — which is where the readout was finally seen — and then on the two-card and four-card machines, which is where the several-card question and the filled-card question were finally answered. **Blender 5.3's** documents **document** the same one preference and say the same about every other figure. 5.3 was tested on the Creator's Mac alone, on the processor and on the Mac's own graphics, and never on a machine with a card of its own.

**Verdict: not established for every version.** Among 4.5 to 5.2 nothing any of the machines found differs between the versions, and everything 5.3 reached agrees with them. But the one readout that shows a card's memory was never seen in 5.3, so the whole answer is not established for it.

**The answer, once.** Blender reports nothing in its printed output that is marked as graphics-card memory, in any of the four versions, on any machine, whether there is one card or four — and in 5.3 on the Mac, on the processor and on Metal. It has one readout that does show the card's memory, and it lives in the Status Bar and is off until somebody turns it on — the same in all four versions; in 5.3 the preference is there and off, and the readout itself was never seen.

- **The preference exists and is off in all five.** Reading it back gave the same answer in every version, on every machine.
- **On the Creator's Mac it cannot be switched on at all, in 5.3 and in the 5.2.2 run alike**: setting it from a script raises an error saying the attribute is read-only. On the one-card Linux machine a script switched it on in all four versions. The builds differ as well as the machines, so which of the two decides it is not established; it is not a difference between versions.
- **The Status Bar offers no way to switch it on that anybody has found, in any of the five.** Right-clicking the bar on the Mac opens a menu of exactly five items in every version, 5.3 included — Scene Statistics, Scene Duration, System Memory, Extensions Updates, Blender Version — and none of them mentions video or graphics memory. Nothing was cut off in any of the four screenshots. On the one-card Linux machine the menu could not be opened at all: there was no menu that could be called by name and no way to send a right-click into the window. So it was switched on from a script instead.
- **The Status Bar's own memory figure is main memory, by the manual's own words**, in every version. It is labelled `Memory:` and given in mebibytes to one decimal place. The manual's picture in every version is an old screenshot showing the label as `Mem:`; what all four of these builds draw is `Memory:`. 5.3's manual describes the item the same way, as an estimate of Blender's own memory use; the item was left off in 5.3's runs and not drawn.
- **A render actually running on the graphics card prints nothing about the card's memory**, in any version, on any machine, 5.3 included. On the Mac a script turned the Metal device on; on Linux a script turned the NVIDIA cards on and confirmed the render used them. Every time the progress lines came out the same shape as a processor render, with the same memory field or fields and no extra one. Every version's whole output was searched for "VRAM", "video memory", "GPU memory" and "device memory" and matched nothing.
- **The Cycles statistics name what the memory holds, never which device it is on**, in every version — geometry, textures or images, per object and per shader. Nothing in the block names a card, and that stayed true with two cards: the block has the same shape it has with one and names no device. On a render using the card, it loses its kernel, shader and object sections and prints one line instead: `Profiling information not available (only works with CPU rendering)`. Seen on Linux, in all four versions, and on the Mac's own graphics in 5.3 and in the 5.2.2 run alike.
- **The other memory figures Blender offers are not said to be the card's either**, in every version: the current-and-peak pair a render engine hands back, the memory stamped into a rendered image, and the memory inside the render-statistics string. No version's sources say which memory any of them counts.

**What the readout shows.** The one-card Linux machine switched the preference on from a script, opened Blender's window and photographed the Status Bar, in all four versions. Four things came back the same every time, in every version:

- **The item is labelled `VRAM:`.**
- **It is a used-of-total figure**, two numbers with a slash between them, each to one decimal place.
- **The units are GiB.**
- **The right-hand figure is the card's whole memory** — `24.0`, against the 24564 MiB the card itself reports.

It sits between the system-memory item and the version. That much is settled for all four versions, on that one card, on Linux. **None of it was seen in 5.3**: on the Mac the preference is read-only, and 5.3 never ran on a machine with a card.

**What the left-hand figure counts is still open.** It moves: during a heavy render on the card it read `4.0` and then `3.8` while the card's own tool reported 3673 and 3459 megabytes, so it follows the card's overall use without being equal to it. At rest one agent read `1.0` at a moment when the card's own tool said 568 megabytes, and a second agent, following the same procedure minutes later on a quiet card, read `1.2`, `1.1`, `1.1` and `1.2` in the four versions. **Both readings stand and neither was written over the other.** So the exact number must not be quoted as a fixed string, and nothing establishes whether the figure is Blender's own use, the card's, or something else again. Two things are worth saying beside that: the machine was shared, so other work may have held part of the card at any of those moments, and the moving test was run in 5.2 rather than in all four. **The differences between those readings are between two runs on one machine, not between versions. The shape of the readout is settled; the number on the left is not.**

**And the readout with more than one card has never been seen, and cannot now be.** It needs Blender's window. It was read on the one-card Linux machine and nowhere else: the two-card and four-card machines had no display server of any kind, and the Ada machine, which had two cards and a screen at once, was never asked for it. All of them are destroyed. So whether the readout names a device, adds the cards together, or shows only one is completely unknown, in every version. That is the sharpest thing this topic still owes.

**With more than one card, what Blender prints on the one line that was kept is settled, in all four versions.**

- **One figure, never several, and no card named beside a memory number — on the `Finished` line.** That was the only line kept from the several-card runs. It came back the same with two cards on the two-card machine and again with four cards on the four-card machine, in all four versions, on two different scenes. **What the rest of those runs printed is not known**: it was discarded before anybody read it.
- **The figure is far smaller with more than one card than with one — and it does not go on shrinking.** On the four-card machine, **two of its cards and all four of its cards printed exactly the same figure**, to the hundredth of a megabyte, in every version and on both scenes: about `7M` against about `384M` with a single card on one scene, and `Mem:480.88M, Peak:494.94M` at both two cards and four against `Mem:1224.33M, Peak:1694.79M` at one on the other. **Both halves of that comparison are the four-card machine's own** — two of its cards against four of its cards, on the same machine on the same day. **It says nothing about the two-card machine and no figure from that machine is used here.** So whatever the figure counts, it is not the memory divided by the number of cards. **What it does count is not settled and nothing is read into it.**
- **The heavier scene's half of that comparison was measured in Blender 4.5.** It is not a version difference and is not written as one.
- **The Cycles debug output gives one memory block with several cards, and says outright that it is system memory.** Two of its lines are printed once per card, and neither of them says how much of a card's memory is in use.

**And a card was finally filled, which is what this question has been about from the start.** On the four-card machine — 16 GB cards against 197 GB of system memory, the only combination the project ever had that could produce this — a scene was grown until Blender's own figure asked for about 33 GB on a card that holds 16.38. **The card filled to its own size and stopped there. The render carried on out of the machine's own memory, wrote its picture and exited 0. Nothing whatever was printed about it.** The same in all four versions, one card each. The only sign was the cost: about ten times longer for twice the data, at the same size and the same sample count. With all four cards ticked, every one of them filled to the same amount and the run took about four times longer still — four 16 GB cards gave a 32 GB scene no more room. **That four-card form was run in 4.5 only**, and the other three versions were never tried that way, as question 1 also says.

**Set that beside The machine 5, because the one-to-four ratio runs both ways.** That question timed one card against four on a different scene and found four cards about 3.6 times *faster* on the render. This 128-picture scene goes the other way on the same machine in 4.5 — 03:28.53 on one card against 13:11.85 on four, about 3.8 times slower — with all four cards filled to the same amount a single card reached. **One run each way, and the other scene's card memory was never measured**, so nothing on record says which way a given scene will go before it is run.

**So the documented fallback to system memory is real, and it is silent.** Every version's sources carry the sentence; the tested fallback happens, says nothing, and is very expensive. **What was not reached is the `Error: Out of memory` message the manual names** — that machine had 197 GB to spill into. It **was** reached in the neighbouring case, where another program held the card's memory, and there Blender failed loudly at exit 1; that case is under question 2, and was run in 4.5 and 5.2 only.

**What still could not be tried at all.** The readout with several cards, above. An NVLink bridge — no pair the project ever had was joined by one, and both several-card machines' cards talked through the host bridge. Any card that is neither Apple's nor NVIDIA's, so HIP's documented fallback stays untried, while oneAPI's fallback is not established by any version's sources. And on the Mac the filled-card case cannot be set up even in principle: the Apple M1 Pro shares one pool between processor and graphics, so a scene big enough to fill the graphics memory fills the machine's memory as well. All of that is untried in every version, and in 5.3 so is everything about several cards and a filled card.

**The closest Blender comes to reporting the card's memory in its printed output, and it is not close.** The Cycles debug switch names the devices outright — which one is path tracing and which is denoising — and gives figures nothing else gives, including a limit naming how much of the machine's own memory a card may reach into, and a block of system-memory statistics. **That limit tracked each machine's own memory wherever it was read** — `193.93G` on a machine of 197 GB, `94.92G` on one of 98, `75.11G` on one of 79 — and it appears only with the debug switch. On the one run that overfilled a card, Cycles' own end-of-run block put the peak system memory at 28.50 GB, which is most of an ordinary rented machine's memory and not all of it; no run has ever tested the fallback behind less memory than 197 GB. **The one figure plainly labelled is system memory. No line anywhere states how much of any card's memory is in use.** Run in all four versions on every Linux machine. Which stream that switch writes to differs by version, and is under question 4. One figure inside it is worth a caution: the line naming a small reserved amount of local memory **differs by version and possibly by run**. **In 5.3, on the Mac's own graphics**, the debug switch names the Metal device it rendered on and one block of system memory, and prints neither the limit line nor the reserved-memory line; on a machine whose graphics share the processor's memory that says nothing about Linux, and nothing is compared on it.

**One difference in memory reporting that is not about the card.** The number of memory figures on a printed progress line, and the units and labels in the Cycles statistics block, do differ between 4.5 and the newer three and again at 5.2, and 5.3 follows 5.2. Those are described under questions 3 and 4. None of them is a graphics-card figure in any version, so none of them bears on this answer.

**One thing only 5.2 and 5.3 recorded, both on the Mac, kept here because it is easy to misread.** In 5.2 a render whose device was chosen through the Cycles command-line switch printed `Mem: 1458M` where the same file with the device enabled through the preferences printed `Mem: 2M`. 5.3 did the same: `Mem: 1394M` against `Mem: 1M` and `2M`. Both carry the same label and the same unit, and nothing says what either counts. The other three versions did not run that comparison, so it is **not** a difference between versions.

## 7. What does a render report about its own progress, across the whole range of picture sizes a render will accept?

**How it is known.** All four versions **document** the same three settings and the same ranges — the two size settings hold a whole number from 4 to 65536, and the percentage scale holds a whole number from 1 to 32767. All four then answer **not in the sources** for the question actually asked: no version's manual, API documentation, release notes or Cycles files says that what a render reports about its progress differs at one picture size from another. Blender 5.1's and 5.2's documents go one step further than 4.5's and 5.0's and quote a block of Cycles' own interface code that works out, from the picture size, whether a render will be split into more than one tile; both mark the step from that code to a render's behaviour as **inferred**. All four then observe the tile settings from Cycles' own files. The rest was settled by tests run in all four versions on both machines. **Blender 5.3's** documents **document** the same settings and ranges, answer **not in the sources** for the question asked, **observe** the tile settings in Cycles' own file, and mark as **inferred** that a picture larger than one tile is split. 5.3 was tested on the Creator's Mac alone.

**Verdict: it differs** — the progress report itself is the same in 4.5 to 5.2, and what differs there sits beside it; 5.3 changes how a tiled frame's lines end.

**What is the same in every version.** 4.5 to 5.2 on both machines; each held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise.

- **The report does change with picture size, and it changes at exactly one place.** The same frame was rendered at 4 by 4, 160 by 120, 1920 by 1080, 2048 by 2048, 2049 by 2049 and 4096 by 4096. At the first four sizes the run prints **three** lines carrying a sample count and mentions no tile. At the last two it prints **thirteen** in 4.5 to 5.2 and **twelve** in 5.3, and every one of them names a tile: the end of the line becomes `Rendered <n>/<total> Tiles, Sample <s>/<max>`. All forty-eight runs exited 0 and wrote a picture of the size asked for, and so did 5.3's, at those sizes and at 64 by 64 and 10000 by 10000.
- **The tested boundary is between 2048 by 2048 and 2049 by 2049.** The default tile is 2048, so the first is exactly one tile's area and prints no tile; the second is one pixel more on each side and prints four. The same boundary held in 4.5 to 5.2 on both machines and in 5.3 on the Mac. **What crosses the threshold is not settled**: every size tried crossed one tile's area as well as one tile's side — **Writing 11** grew one side only, from 2048 by 2048 to 2048 by 2049, and one extra row crosses the area too — so whether it is the picture's area or a side that decides is untested. No Cycles picture wider than one tile but smaller in area was tried: **The compositor 6** rendered 9000 by 400 in all four versions on both machines, but under Workbench, which writes no tile file and prints no tile line.
- **The tile count is not the area rule's arithmetic.** Every tile count on record is the number of whole tiles across times the number down, each side rounded up on its own — 2 at 2048 by 2049, 4 at 2049 by 2049, 25 at 10000 by 10000 in 5.3, 1024 at 8000 by 8000 with a tile of 256, 225 at 30000 by 30000, and 53,284 at 629,126 by 353,883 — where the area rule gives 977, 215 and 53,081 for three of those. The two rules agree at every threshold anybody has reached, which is why what crosses it is still untested.
- **Once a picture is tiled the sample number restarts inside each tile.** At 2049 by 2049 the thirteen tile lines carry sample numbers 0, 1, 16, 16, 1, 16, 16, 1, 16, 16, 1, 16, 0 against a maximum that stays at 16, so the number falls back three times and cannot be a count across the whole frame; the maximum is the scene's own count and is not divided among the tiles. 5.3's twelve carry the same numbers without the closing 0. **The tile number counts tiles finished, starts at 0 and never reaches its total** — the last line of that finished run reads `Rendered 3/4 Tiles` in all five, 10000 by 10000 in 5.3 stopped at `24/25`, and the 65536-square run reached `1023/1024` and no further. That whole stream is compressed into five thousandths of a second, so which tile any one line belongs to is not readable from it.
- **The three size settings clamp silently and never refuse.** Set from a script and read straight back: 0, 3 and 4 all become 4; 65536, 65537 and 70000 all become 65536; the percentage turns 0 into 1 and 32768 and 70000 into 32767. Nothing was raised and nothing was printed, in any version on either machine.
- **The percentage cuts down rather than rounds.** At 1920 by 1080 the written picture is 1920 by 1080 at 100 per cent, 960 by 540 at 50 per cent and **633 by 356** at 33 per cent. Rounding would have given 634. The written files were measured without Blender.
- **A picture of no pixels is refused, and the run still ends at 0.** At 4 by 4 with the percentage at 1, nothing is written and the message is `Image too small`. Every one of the eight runs exited 0 despite writing nothing — another of the endings that leave the status at 0, as under question 1. The wording of the message follows the same split as every other message in this topic — plain in 4.5, a log line from 5.0 to 5.3.
- **A size the settings accept is not necessarily a size a render can finish.** At 65536 by 65536 with one sample per pixel, every version divided the picture into **1024 tiles**, printed a line for each — 1026 tile lines in all — reached `Rendered 1023/1024 Tiles, Sample 0/1`, and then failed at the point of putting the tiles together. Each printed `Error reading tiles from file`, each put a message from the image library on standard error saying the uncompressed image exceeds a size limit, each **exited 1 and wrote nothing**. Blender's own memory figure stayed low throughout — about 241 MB in 5.2 and about 249 MB in 4.5, the two versions whose figures were written down — and the machine's at about 3.5 GB of 49. **Run on the Ada machine only** — a picture that size is not something to attempt on the Creator's 16 GB Mac on purpose. **Not run in 5.3.**
- **Picture size makes no difference at all to what is shown on screen.** With a window open there is exactly one progress bar, never two, carrying a whole-number percentage with no decimal point anywhere, at 4 by 4 and at 4096 by 4096 alike. Nothing about tiles is named or counted on screen even at the sizes where the printed stream counts them. **5.3's window was photographed at 720 by 405 alone**, with one bar and a whole-number percentage, so across sizes this is not established for 5.3.
- **A render engine's own progress calls are not window-bound.** `update_progress`, `update_stats` and `update_memory_stats`, called from a tiny engine registered from a script, all returned without complaint with a window and without, and in 4.5 to 5.2 none of them produced any output of its own. **With no window in 5.3 `update_stats` did print**: handed two texts, it put the second on a `render` line — `Fra: 1 | PROBE INFO TEXT` — and the first nowhere; the other two printed nothing, and `update_progress(0.5)` drove the window's bar to exactly 50%. What texts the 4.5 to 5.2 runs handed the call is not on record, and no 5.2.2 run was made beside it, so **whether the printing is new in 5.3 is not established**.

**Where it differs, version by version.**

**The tiling switch's name and description, read from the running program.** In **4.5** the switch `use_auto_tile` is named **Use Tiling** and described "Render high resolution images in tiles to reduce memory usage, using the specified tile size. Tiles are cached to disk while rendering to save memory", and the tile-size setting beside it has **no description at all**. From **5.0 to 5.3** the same switch is named **Auto Tile** and described **"Deprecated, tiling is always enabled"**, and that description has moved onto the tile size. The default is True and the tile size 2048 with a range of 8 to 8192 in all five — 5.3 read from the running program on the Mac. Blender 5.0's release notes state the change in so many words: "Remove Use Tiling option, it is now always assumed to be on." **What the switch is called changed, and on a fresh scene at the default tile size the threshold is in the same place in every version.** It is not necessarily the same place for a file carried across: **What a render demands 5** records a 4.5 file saved with tiling off and a tile of 256 reading back in 5.0, 5.1 and 5.2 as tiling **on** with a tile of **8192**, and **Writing 11** records both that the tile size decides whether a picture is split at all and that 4.5's switch still works where the newer three's does not. No converted file has ever been rendered, so what each version does with one is arithmetic and not a measurement.

**How a tiled frame's sample lines end, at 5.3.** In 4.5 to 5.2 the thirteenth and last sample line at 2049 by 2049 reads `Rendered 3/4 Tiles, Sample 0/16`, on a frame that finished. **5.3 prints twelve and stops on the last tile's full count**, `Rendered 3/4 Tiles, Sample 16/16`. On the Creator's Mac; the 5.2.2 run of the same scene on the same Mac the same day printed the same twelve and then `Rendered 3/4 Tiles, Sample 0/16` as a thirteenth, so the change is 5.3's own. It is the same change question 11 records for a frame that stops short. On Linux it is untried.

**One run turned that switch off, and the tile count still appeared — in 5.2, and again in 5.3.** At 30000 by 30000 with `use_auto_tile` set to `False`, Blender 5.2 printed `Fra: 1 | Mem: 805M | Rendered 0/225 Tiles, Sample 1/1`. **So the tile count in the printed line does not depend on the switch being left on, in that version.** **One run, on one machine, on one day** — the RTX 4080 SUPER machine, now destroyed — from a run that did not finish: the machine's own memory gave out and killed it, so nothing about a whole tiled stream at that size follows from it, and the tile size was never read back, so nothing here says what produced the figure 225. **5.3 did the same on the Creator's Mac**: at 4096 by 4096 with the switch off it printed the same twelve lines and the same four tiles as with it on. Two versions, two machines, two sizes. **4.5, 5.0 and 5.1 were never run with the switch off for what they print, so this is not a difference between versions.** `Writing 11` turned the same switch off in all four versions and watched the disk rather than the stream, and found 4.5 alone stops making the tile file — see [that comparison](Writing.md).

**The tiling warning inside Cycles' own installed add-on, observed in the installed files.** The exact words "May work poorly with render tiling", and the comment naming the tile-size calculation, are **absent in 4.5** and **present in 5.0, 5.1 and 5.2**, on both machines, and present in 5.3 on the Mac.

**The name the Status Bar gives the running task.** `Render...` in **4.5**, `Rendering...` from **5.0 to 5.3**, photographed in all four versions on both machines and in 5.3 on the Mac. A sequencer render drives the same bar in all five versions and is labelled `Rendering sequence...` — not `Sequence Render`, which is the label in the one picture every version's manual carries of that bar, 5.3's included.

**One thing worth knowing beside the verdict.** The progress bar never names a frame, for a still or for an animation, in any version, 5.3 included. During a three-frame animation the percentage **restarts at each frame** rather than climbing across the range: fourteen photographs of one such animation, in order, read 16, 16, 16, 16, 16, 0, 16, 0, 48, 80, 0, 80, 0 per cent. **All four versions record the restart, on both machines**; that run of readings is Blender 5.1's, and the other three state the restart without giving figures. **Whether 5.3's restarts is not established**: its pictures lag the window by several seconds, so the readings cannot be tied to frames.

## 8. What does a render print over the whole of a run, from its first line to its last?

**How it is known.** Blender **5.0's** sources answer **documented**, for the one worked example of a render's printed output its release notes publish — the only such example in any version's sources — but a complete first-to-last sequence is **not established by that example**: the published block is labelled an example, carries an elision in the middle, and has a clock that runs backwards across that elision. Blender **4.5's, 5.1's, 5.2's and 5.3's** answer **not in the sources**: no page and no file in their sources gives the lines a render prints, in order, from the first to the last. Every version also documents the same surrounding machinery — the console the output goes to, the quiet switch, the logging switches, and Cycles' own statistics switch. The rest was settled by capturing whole runs in all four versions on both machines, and in 5.3 on the Creator's Mac alone.

**Verdict: it differs.**

**What is the same in every version.** 4.5 to 5.2 on both machines; each held in 5.3 on the Creator's Mac as well.

- **Exactly three lines carry a sample count for a sixteen-sample frame** — `Sample 0/16`, `Sample 1/16`, `Sample 16/16` — never one line per sample. The elision in 5.0's published example hides nothing but stage lines. That is the shape of a frame small enough not to be split into tiles; a tiled frame prints more, and question 7 has the counts.
- **Every render line carries a memory figure**, and exactly one line carries a time estimate, called `Remaining`, on the `Sample 1/16` line.
- **A successful run ends `Saved:`, then `Time:`, then `Blender quit`, and exits 0.**
- **Standard error stays empty** on an ordinary run in every version on the Mac, and in 4.5, 5.0 and 5.1 on Linux. The exception on an ordinary run is 5.2 on a Linux machine with a display server running, which is on the behaviour list at the top. It is not empty on every kind of run: see questions 4, 7, 10, 12 and 13.
- **Cycles' own statistics arrive on standard output, not standard error**, in every version on both machines — despite the help text in every version's own Cycles file naming standard error. What the block holds and where it sits is under question 4. Without a bare `--` before it, the switch is taken for a file name and the run exits 1, in all five — 5.3 having rendered and saved the frame first.
- **Workbench prints no progress line at all**, in any version, on either machine: the run goes from the announcements straight to `Saved:`.
- **EEVEE ignores the scene's Cycles sample count and uses its own**, which is 64 out of the box and which every run behind this answer left alone: it printed four progress lines of the shape `Rendering <n> / 64 samples` at 1, 25, 50 and 64, and nothing about the mismatch. That is the same in all four. What moves the number after the slash is under question 11; what else an EEVEE line carries is under question 3.
- **The render-statistics handler fires once per stage with no window, not once per render**, in every version, and is handed two things: a string and nothing. Over one frame the counts are 43 in 4.5, 45 in 5.0, 44 in 5.1, 45 in 5.2 and 45 in 5.3, which follow each version's own count of stage lines rather than marking anything about the handler. The last string is always the closing `Time: … (Saving: …)` line. What the string holds is under question 3.

**Where it differs, version by version.**

**The two ends of a run.** In **4.5** the first line is the version banner and the last is `Blender quit` with **two** blank lines before it. From **5.0 to 5.3** the first line is `blend | Read blend:`, the version banner arrives seven lines in — in the middle of the run, and it is the one line with no timestamp and no category — and the last line is `Blender quit` with **one** blank line before it.

**How long a plain single-frame run is, is not settled.** Two captures disagree by exactly one line in 4.5 to 5.2: one gives 53 lines in 5.0 and 5.1 and 54 in 5.2, the other gives 54, 54 and 55, and 4.5's own count is recorded at fifty. Neither was chosen. The capture that gives 53 and 54 gives the same runs under quiet mode at 50 in 5.0 and 5.1 and 51 in 5.2 — three lines fewer either way, which is what question 4 describes. **5.3 printed 54 on its own scene, and 51 under quiet mode** — and the 5.2.2 run of that same scene on the same Mac printed the same 54, differing only in the banner and the saved file's name. So the count follows the scene, which points at the scene as the cause of the earlier gap; the earlier counts themselves stay unsettled.

**What is announced before the sampling starts.** **4.5** announces nothing at all and prints no line beginning `Rendering` anywhere; 5.0 to 5.3 announce the frame and the range, and question 3 has the wording. Nothing follows the last frame's `Time:` line in any version but the blank line and `Blender quit`.

**The published example is not the measured 5.0.1 output.** Its sample line reads `Mem: 2983M | Sample 1/16`, where the tested build prints `Fra: 1 | Remaining: 00:00.05 | Mem: 3M | Sample 1/16`. Its `Rendering single frame (frame 1)` arrives as two lines in the tested build. These are differences between an example and a running build of the same version, not between versions.

**The stage names.** **5.0 and 5.1** print a stage `Updating Volume` that **4.5** does not. **5.2** prints a stage `Updating Scene Attribute` that none of the three before it does, and **5.3** prints it too. Everything else in the stage block is the same set of names, and on one scene 5.3's stage lines matched the 5.2.2 run's line for line.

**What quiet mode removes** is under question 4, and was captured again here in all four versions on both machines with the same result: the whole render silenced in 4.5, three lines gone in the newer three, the picture still written and the run still at 0 in all four. 5.3 gave the newer three's result.

**The logging switches.** **4.5** accepts numeric logging levels and has no category-list switch. `--log-level info` is refused with `not a number`, after which the render proceeds normally and exits 0; `--log-list-categories` is taken for a file name and the run ends at 1. Its own `--log "*"` adds four lines about the file being read and nothing else. **5.0 to 5.3** have both, and both add a great deal: against fifty-odd lines, `--log-level info` gives 138, 139 and 140 on the Mac in the newer three and `--log "*"` gives 138, 140 and 141. 5.3, with both switches given together on its own scene, printed 146 lines, against 142 from the 5.2.2 run of the same scene; the difference includes the `color_management` line question 4 records. The category list exists from 5.0 to 5.3 and holds both `render` and `cycles`; its counts are under question 4.

## 9. What does a render report about its progress under each of the ways a render can be started?

**How it is known.** All four versions answer **not in the sources** for the question as asked: no version's sources set out, way by way, what is reported. All four **document** the ways separately, page by page, and all four are careful that no source enumerates them — Blender 4.5's document marks its set of six as **inferred** for that reason. **Three of the four** — 4.5, 5.0 and 5.1 — quote the one sentence that ties reported content to a way of starting, the render-statistics handler's "in background mode" clause, and 4.5's and 5.1's documents mark the reverse reading of it — that a windowed render therefore carries less — as **inferred**. **Blender 5.2's page carries a different sentence altogether**, naming a current frame, a current sample, a render time and a saving time, and tying none of them to a way of starting; 5.2's document says in so many words that the sentence is attached to a handler rather than to any way of starting, and that the page never says under which ways the printing happens. So there is no such clause in 5.2 to read either way. That is the documentation difference the third list records, and it is not a change in Blender. Blender 5.2's document alone quotes a fixed-bug title asking whether Cycles sample progress is reachable from Python without `-f`, and reports it as a title and nothing more. The rest was settled by starting the same frame five ways in all four versions on both machines. **Blender 5.3's** documents answer the same way, **document** the ways separately — the Render menu with its four keyed commands, the viewport renders, the command line, the operator, Blender as a Python module — and carry 5.2's sentence about the render-statistics string; one release note says viewport renders pause during a final render, which is not about progress. 5.3 was tested on the Creator's Mac alone, with no window and with one.

**Verdict: it differs.**

**What is the same in every version.** 4.5 to 5.2 on both machines; each held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise.

- **The split that matters most is between having a window and not.** With a window open, **no way of starting prints any progress at all** in any version. All that reaches the terminal is `Saved:`, and in 4.5 the `Time:` line as well.
- **What the operator hands back.** Called plainly it blocks until the render is finished and returns `{'FINISHED'}`. Started the way the F12 key starts it, it returns `{'RUNNING_MODAL'}` at once and the render goes on afterwards. A picture was written in every case, in every version.
- **A render started with `-f` or `-a` and no window prints its full progress**, in every version — three sample lines per frame, the stage block, a memory figure and a `Remaining:` estimate.
- **A sequencer render drives the same status bar as an ordinary one**, in every version, labelled `Rendering sequence...`. With no window it prints `Rendering frame 1` and then the ordinary three sample lines — not tried in 5.3, whose sequencer render was run with the window open and put only its ten `Saved:` lines on the terminal.
- **A render engine's own progress calls work whether there is a window or not**, in every version, on both machines, and in 4.5 to 5.2 produce no output of their own. With no window in 5.3 `update_stats` printed one of its texts; whether that is new is not established — see question 7.

**Which key starts which render command** could not be read in 4.5 to 5.2 with no window, where Blender's key configuration holds no items, and every windowed run of those four was started by the operator call the F12 key is bound to, not by a key. **With the window open it was read in 5.3, and in the 5.2.2 run on the same Mac, and the two are identical**: F12 renders a still, Ctrl-F12 or Cmd-F12 the animation, and Alt with either renders the sequencer scene instead; F11 shows the render view and Esc is bound to closing it. 4.5, 5.0 and 5.1 were never read that way.

**Where it differs, version by version.**

**A render started from Python with no window.** In **4.5** it prints its full progress — three sample lines and the whole stage block, exactly as `-f 1` does. From **5.0 to 5.3** it prints nothing but the file it saved. The whole of a 5.0 capture is four lines of Blender's own. Run twice in each version on each machine, once with the call in an expression and once in a script file, with the same result every time; 5.3 the same, on the Mac. **This is the sharpest thing this question found**, and it means a render farm that starts renders from a script sees a full progress stream in 4.5 and silence in every later version.

**What the render-statistics handler receives when a window is open.** In **4.5, 5.0 and 5.1** it fires **once**, and is handed only the closing `Time: … (Saving: …)` line. In **5.2 and 5.3** it fires once per stage — forty-four to forty-six times — with the same strings a windowless run produces, sample counts and all; a two-frame 5.3 render started the way F12 starts it fed it 102 strings. So a script can follow a render's samples with the window up in 5.2 and 5.3 and in no earlier version.

**What ways of starting there actually are.** The Python render operator takes **five** arguments in **4.5** — `animation`, `write_still`, `use_viewport`, `layer`, `scene` — and **eight** from **5.0 to 5.3**, the three added ones being `use_sequencer_scene`, `frame_start` and `frame_end` — a switch about the sequencer's scene and a start and end frame. Every argument carries a description in all five versions, contrary to the API page's "Undocumented, consider contributing" for the operator itself from 5.0 on; the operator describes itself as `Render active scene` in 4.5 and as undocumented from 5.0 to 5.3. The Render menu draws **two** render commands in **4.5** — `Render Image` and `Render Animation` — and **four** in 5.0, 5.1 and 5.2, adding `Render Sequencer Image` and `Render Sequencer Animation`. **What 5.3's Render menu holds is not established**: in the one file it was photographed in, it drew `Render Image`, `Render Animation`, `Render Audio...`, `View Render`, `View Animation` and `Lock Interface`, and no sequencer entries — while 5.3's own manual lists both sequencer entries in that menu and the running 5.3 binds keys to both. The 5.2.2 run on the same Mac could not photograph its menu at all, so nothing says whether 5.2 would have drawn them in that file. The 3D viewport's render commands were renamed after 4.5: `Viewport Render Image`, `Viewport Render Animation` and `Viewport Render Keyframes` in **4.5**, against `Render Viewport Preview`, `Render Playblast` and `Render Playblast on Keyframes` from **5.0 to 5.3**, all three calling the same operator. There is no further rename at 5.2.

**The setting that switches off saving.** `save_output` is present on the render settings in **5.2 and 5.3** and in none of the three before, with the value True. Read from the running program in all four versions on both machines and in 5.3 on the Mac. What it does when switched off is under question 1.

**Whether a windowed 5.2 render with a render-statistics handler attached ends cleanly or in a segmentation fault is not settled.** On the one-card Linux machine it ended in a **segmentation fault, exit 139**, three times out of three, with a crash file written and forty-four strings handed to the handler. On the Ada machine it ended, three times out of three, with **exit 0, no crash file of any name, nothing about a segmentation fault, and forty-five strings**; on the Creator's Mac the same, with the handler firing forty-six times once and forty-five twice. Both runs stand and neither was chosen. Blender 4.5, 5.0 and 5.1 were run the same way on the same day and each exited 0 on both machines with the handler firing once. 5.3 was run the same way on the Mac five times, closed two ways, and every run ended at 0 with no crash file and the handler firing forty-five or forty-six times. **Nothing in this is a difference between versions**, and it must not be read as one.

**Two differences between the machines, the same in all four versions.** `bpy.ops.wm.quit_blender()` called straight from a start-up script **closes a windowed Blender on the Creator's Mac** — after 6.3 seconds in one run and 24.7 in another — and **did not close it on the Ada machine within four minutes**. A timer calling the same thing three seconds after the render closed it on both machines every time, in all four versions. In 5.3 on the Mac the straight call closed it within a second and a half, twice, and the 5.2.2 run on the same Mac the same day closed as fast; so the Mac's times are not fixed figures for any version. And at quit time the Mac saves a session recovery file — 5.3's too, into Blender's own temporary folder — where the Linux machine reports that it cannot open `/tmp/quit.blend@` for writing. **These are the operating system, not the version**, and how a windowed run is ended matters because the exit status of such a run belongs to whoever ended it.

## 10. What does a render do when the machine's own memory runs out while it is sampling?

**How it is known.** All four versions answer **not in the sources**, in the same words and for the same reason: nothing in any version's manual, API documentation, release notes or Cycles files describes what a render does when the machine's own memory is exhausted during sampling. All four quote the same nearby things and all four say plainly that none of them answers the question — running out of memory named as a common cause of crashes in general, a report category called Out of Memory that nothing says a render ever raises, and the graphics-card fallback, which runs the other way round by moving work **onto** the machine's own memory. The rest was settled by one hand test, run in all four versions. **Blender 5.3's** documents answer **not in the sources** for the same reason and quote the same nearby things, adding a warning from another page of the manual that too little memory can make Blender hang as well as crash; from those general statements 5.3's document **infers** a crash or a hang and nothing more. **Nothing was run in 5.3**: the Creator's Mac is not to have its memory filled on purpose, and the 5.3 tests had no other machine.

**Verdict: not established for every version.** Among 4.5 to 5.2 it differs, settled by a test run in each of those four and by nothing else. 5.3 is answered by nothing, so everything below is 4.5 to 5.2's, and what 5.3 does is open on every machine.

**Which machine settled it, and what that limits.** The test was run on **the Ada machine only** — 49 GB of memory. It was not run on the Creator's Mac, whose memory must not be filled on purpose, and it was not run on Windows, where it is untried rather than untestable. **So this answer covers Linux and leaves macOS and Windows open, in every version.** It was run twice through, the second time with the four versions taken in the opposite order, and every version behaved the same way both times. **It was also a processor render** — Cycles on the processor, 2000 samples, 8192 by 8192, forty light groups. No render on a graphics card has ever run a machine out of memory while sampling, so the split below is a processor result as well as a sampling one, and the two conditions have never been separated.

**What is the same in all four.**

- **Getting the memory to run out while sampling is harder than it sounds, and the first two attempts are results of their own.** More pixels do not do it: at 12288 by 12288 the run reached the top of the machine's memory and **kept sampling**, and at 16384 by 16384 Blender's own figure was the same again. Tiling caps what is held — the tile size cannot exceed 8192 — so the buffers stop growing with the picture. What did it was **more passes**, not more pixels: forty light groups added to an 8192 by 8192 scene with every pass switched on. *(The readings taken differ a little between the versions — 48.8, 48.9, 48.9 and 49.8 GB. Those are one run against another, not a difference between versions, and they are ordinary readings on a rented container rather than figures for the machine itself — see the caution below.)*
- **The last line on standard output is a sampling line**, in every version. That is what says the memory ran out while sampling rather than while the scene was being loaded.
- **No picture is written, not even part of one, and no crash file appears anywhere**, in any version. The crash file the manual describes did not appear for this kind of ending.

**Where it differs, version by version.**

**Blender 4.5 and 5.0 fill the machine and are killed by the operating system.** Standard error is **empty**. Nothing whatever is printed about memory. The process ends with status **137**, and the kernel's own log holds the record of the kill. The machine's memory use climbed until the kill.

**Blender 5.1 and 5.2 refuse the allocation, say so, and abort.** Standard **error** carries Blender's own words — a line naming the size of the request in bytes, in Cycles' own aligned allocation, followed by two lines about a failed allocation being thrown and not caught. The process ends with status **134**. **The machine's memory use stayed at about 2.9 GB throughout** — the request was refused whole rather than filled piece by piece. The size asked for was **about 80 GB in 5.1 and about 81 GB in 5.2**, which are Blender's own figures and are far above anything that machine had.

**A caution about the memory readings above, and it is the equipment section's standing rule.** Every figure in this answer that describes the *machine's* use — the 2.9 GB, and the readings in the note about getting the memory to run out — is an ordinary reading taken on a rented container, and the equipment section's rule is that such a reading is not that machine's own figure unless the entry says the two were compared. That entry does not say so, and one of the readings is larger than the size the machine is described as having. **So none of them may be quoted as a fact about how much memory that machine had**, and no ratio should be built out of them. `Writing 13` met the same trap on a core count and named it. **The version split is untouched by this**: both endings were seen on that one machine in one sitting, twice through, so what separates 4.5 and 5.0 from 5.1 and 5.2 stands whatever the real ceiling was. Blender's own 80 and 81 GB figures are unaffected too.

**An animation does not go on to the next frame.** A three-frame run printed one `Rendering frame` line, aborted on frame one, wrote nothing, and ended at 134. Tested in 5.1 and 5.2, which are the two versions that abort this way.

**What this means for anything watching a render.** **For a shortage that arrives while the render is sampling** — which is the whole of what this question asked, and the whole of what its runs did — the two endings look different from outside in every way that matters. One is silent, leaves nothing on either stream, and reports 137. The other puts three lines on standard error and reports 134. A program that watches only standard output learns nothing in either case: in both, the last thing it ever sees is an ordinary sampling line.

**A shortage that arrives at another moment is a different ending, and this question does not cover it.** **What a render demands 7** reached the same kind of ceiling while the acceleration structure was being built, and there **all four versions were killed by the system with nothing said** — 5.1 and 5.2 included, the two that abort loudly here. So the version split above belongs to the sampling case and must not be carried across: **anything watching standard error for the newer two will see nothing at all if the shortage arrives while the scene is being built.** Nothing in this stage holds the two statements joined; each topic holds its own half.

## 11. What, if anything, does a render print that shows whether a frame took the number of samples it was asked for?

**How it is known.** Blender **4.5's** and **5.1's** documents answer **not in the sources** for anything printed. Blender **5.0's** answers **documented** for the `Sample n/m` lines in its release notes' example, and marks as **inferred** the step from those lines to an answer, since nothing says the second number is the count asked for or that the line is printed when sampling stops early. Blender **5.2's** answers **documented** for one printed item that carries a sample number, its API page being the only source in any version that says the printed statistics carry a current sample. All four **document** the Sample Count render pass, which holds exactly the ratio the question is about but is picture data rather than printed text, and all four document the same three reasons a frame can stop short — adaptive sampling, the time limit and the sample subset — with no announcement documented for any of them. All four record that the manual's Metadata panel lists no sample field. The rest was settled by tests in all four versions on both machines. **Blender 5.3's** documents answer as 5.2's do — **documented** for the API sentence that the printed statistics carry a current sample, **documented** for the Sample Count pass and for the time limit and adaptive sampling, with adaptive sampling **observed** on by default in Cycles' own file — and say nothing printed marks a frame that stopped short. 5.3 was tested on the Creator's Mac alone.

**Verdict: it differs** — in the files written under this question's setup, between 4.5 and the rest, and, at 5.3, in the printed ending under a time limit and adaptive sampling. Images 10's setup writes the Sample Count pass in all five; the condition deciding whether it is written remains unresolved.

**What is the same in every version.** 4.5 to 5.2 on both machines; each held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise.

- **In 4.5 to 5.2 a printed line does show it, and the mark is not the one anybody would expect. 5.3 marks it differently** — see below. A frame that finished ends on its full count, `Sample <maximum>/<maximum>`, in all five. In 4.5 to 5.2 a frame cut short shows the count it reached and then **resets to zero**, so its **last** sample line reads `Sample 0/<maximum>` and the count actually reached sits on the line before it. That happens whatever stopped the frame, not only adaptive sampling: it is on record for a frame converged with adaptive sampling on, for a frame cut short by the time limit with adaptive sampling explicitly off, and for a frame **cancelled by an interrupt** — `Sample 1025/4096`, the break message, `Sample 0/4096`, then `Cancelled`, in all four versions on both machines. **Reading the largest count seen, not the latest, is the safe rule for telling whether a frame reached its count — and it is not a rule about whether the frame reached disk.** **Frames 15** records the other ending: on the Creator's Mac, in all four versions, a Control-C typed eight seconds into a frame gave `Sample 600/600`, then `Finished`, then `Cancelled`, exit status 1, and **no file for that frame**. The same machine gives either ending. So neither a full count nor `Finished` means a picture was written. **And every run behind this mark was a picture small enough not to be split into tiles** — the condition is set out at the end of this answer.
- **Nothing else is printed.** No notice, no warning, nothing naming the time limit or the noise threshold, in any version on either machine. Every one of the twenty-four runs exited 0 and wrote its picture, whether the frame finished or not, and so did 5.3's three.
- **The counts reached differ with the machine and the run, and never with the version.** On the Mac the time-limited run reached 549 of 4096 in 4.5, 513 in 5.2 and 545 in 5.3 — and 545 in the 5.2.2 run beside it; on the Ada machine it reached 809, 771, 798 and 769. Those are two different processors doing five seconds of work, and nothing more.
- **A saved image carries a sample figure that the manual's Metadata panel does not list.** A PNG carries eleven fields, identical in all four versions on both machines, among them `cycles.ViewLayer.samples`; 5.3's PNG carries eleven as well, that one among them. The fields were read without Blender.
- **That figure is the maximum asked for, not the number reached.** A run whose sample lines showed 160 of 512 reached carried 512; in 5.3 one that reached 96 of 512 carried 512. So the one sample figure that survives into a file is the one that cannot answer the question.
- **Cycles' own statistics carry no sample count**, in any version, in either of the two blocks they print.
- **The render-statistics handler carries a sample count only while a sampling stage is running**, in every version, and the maximum appears beside the count. With a window open, 4.5, 5.0 and 5.1 receive one string carrying no sample count at all; 5.2 and 5.3 receive them all, which is under question 9.
- **The settings behind all this are the same in all four**, read from the running program on both machines: samples default 4096, adaptive sampling **on** by default, its threshold 0.01, the time limit 0, the sample subset off with a length of 2048, and the debug Sample Count pass named Debug Sample Count, off by default, with the same description in every version. 5.3's Cycles file gives the same samples default, adaptive sampling on, the time limit 0 and the pass off by default; its threshold and sample subset were not read.
- **EEVEE counts differently and says nothing about it**, in every version: `Rendering <n> / 64 samples` against its own sample setting rather than Cycles'. The scene in that run had set a **Cycles** sample count, which EEVEE does not read, and EEVEE's own count was left at its factory 64 — as it was in every run behind this answer. **Settings 17** sets EEVEE's own count (`taa_render_samples`) from the launch line and the printed line follows it, `Rendering 3 / 3 samples`, in all four versions. **The number after the slash moves**: `Settings` records 3, 8, 16, 256 and 99,999,999 on the same line, and records motion blur and camera jitter pushing it *above* the number asked for — 65 at a setting of 64, 19 at a setting of 16. So nothing should compute a percentage from a denominator of 64, and nothing should read the second number as the count that was asked for. **Workbench prints no sample line at all.**

**Where it differs, version by version.**

**Whether the Sample Count pass reaches a saved file.** With the pass switched on, adaptive sampling on at a threshold of 0.1, a maximum of 512 samples and the output a multi-layer OpenEXR, **Blender 4.5 writes the pass** — its channel list carries `ViewLayer.Debug Sample Count.X` alongside four Noisy Image channels — and **Blender 5.0 to 5.3 write only the four Combined channels**. The switch was confirmed set to True in all five before every render, no version printed anything about it, and every run exited 0. The channel lists were read without Blender. Both machines gave this for 4.5 to 5.2, and the Mac for 5.3. In 5.3 the scene was a saved file, the pass and the format were set by an expression handed in at launch, and the frame was rendered with `-f 1` from the command line. **Images 10** records the pass written in all five versions from another setup — in 5.3 a factory scene at 64 by 64 and one sample, the pass and the multi-layer media type set from a script, and the render started by that script. Which difference between the two setups decides whether the pass is written is not established. **In 4.5 the pass is one channel and its values do fall below one**: a run saved without compression read a minimum of 0.3, a maximum of 1.0, and 172,791 of its 172,800 pixels below 1 — that run's own sample lines having ended `Sample 160/512` and then `Sample 0/512`.

**What it takes to ask for multi-layer output at all, which is a trap rather than a feature.** Blender **4.5** has no `media_type` setting; setting the file format is enough. From **5.0 to 5.3** the media type must be set to multi-layer **as well**, and setting only the file format writes a **PNG**, at exit status 0. **In 5.3, and in the 5.2.2 run on the same Mac, it is not silent**: Python refuses the setting with a `TypeError` on standard error, saying the multi-layer format is not among the formats it accepts, and the render goes on as a PNG. The runs that found the trap in 5.0 to 5.2 noted no error, and the 5.2.2 run contradicts that for 5.2, so whether 5.0 and 5.1 print the refusal is not established. Anything that asks for multi-layer output **from a script** by file format alone will get something else in every version after 4.5, with nothing but a line on standard error to say so where it says anything at all. **The `-F` launch argument is a different route and does not behave this way**: handed `-F OPEN_EXR_MULTILAYER` on the launch line, all four versions wrote a real multi-layer file, its header carrying both view layers' channels — **Settings 17**.

**Four metadata fields in an OpenEXR.** `Software`, `colorInteropID`, `name` and `type` are present from **5.0 to 5.3** and absent from **4.5**. Read without Blender, on both machines, in all four versions, and in 5.3 on the Mac. None of them is about samples.

**How a frame that stopped short is marked, at 5.3.** In 4.5 to 5.2 the last sample line of such a frame reads `Sample 0/<maximum>`, with the count reached on the line before. **5.3 prints no such closing line.** Under a five-second time limit its last sample line read `Sample 545/4096` and the next line `Finished`; under adaptive sampling, `Sample 160/4096` and then `Finished`; a frame that ran its full count ends `Sample 4096/4096`, then `Finished`, as before. On the Creator's Mac; the 5.2.2 run of the same scene on the same Mac the same day reached the same 545 and 160 and still printed the closing `Sample 0/4096` under both, so the change is 5.3's own. A frame cancelled by Ctrl-C in 5.3 went the same way — `Sample 1025/1000000`, then straight to `Cancelled` — with no 5.2.2 run beside it. On Linux all of it is untried.

**What a reader should take from this.** In 4.5 to 5.2 the only reliable printed sign that a frame stopped short is a line reading `Sample 0/<maximum>` at the end of that frame's sampling. **In 5.3 that line does not exist, and the sign is the last sample line's own count falling short of its maximum.** Neither is a message or an error, and neither is distinguishable from a normal line by anything but its position and its numbers. **One rule reads both**: the largest count seen in the frame, set against its maximum — which in 5.3 is also the latest. **That holds for a picture small enough not to be split into tiles, which is what every run behind it was — 480 by 360 here and 320 by 240 under Settings 16.** On a tiled frame neither mark works. In 4.5 to 5.2 the closing `Sample 0` fires on frames that finished: at 2049 by 2049 the last line of a run that exited 0 and wrote its picture reads `Rendered 3/4 Tiles, Sample 0/16` (question 7). In 5.3 the same frame ends on the last tile's `Sample 16/16`, and the count restarts in every tile, so the largest count seen is one tile's. No tiled frame that really stopped short has ever been captured in any version, so on a tiled picture nothing printed separates the two. The one place the truth is recorded per pixel is the Sample Count pass. Under this question's setup it reached a saved file in **4.5 alone**; under **Images 10**'s setup it reached one in all five, as set out above.

## 12. What ending status does a run of Blender give back to whatever started it, for each of the ways a run can end — finishing normally, being interrupted, and being refused because something it was handed cannot be used?

**How it is known.** All four versions answer **not in the sources**. No version's manual, API documentation, release notes or Cycles files states the number a run hands back for a normal finish, for an interruption, or for a refusal. All four then quote the same narrow set of things that touch it and answer none of it, all **documented**: the `--python-exit-code` option, which sets a status the caller chooses and only for a Python exception raised by a script given on the command line; the advice that a command registered for `-c` / `--command` should return 0 for success and 1 for failure, which no page says becomes the run's own status; the manual's own example `blender -ba test.blend`, which says the run "will exit" and not with what; and `--debug-exit-on-error`, `-h`, `-v` and their neighbours, each described as exiting with no status named. All four **observe** the four lines of Cycles' own `engine.py` that ask for the process to end with 1 when a render device cannot be set, and all four mark as **inferred** the step from that call to what the caller receives. Blender 5.2's documents observe two more of their own — `maketx.py`, which gives back 1 after catching an error and 0 otherwise, and the release note naming that command — and 5.1's and 5.2's quote the documented statement that Blender loaded as a Python module has no special handling for an interrupt. The whole of the answer below was then settled by tests run in all four versions on the Creator's Mac and on the Norway machine. **Blender 5.3's** documents answer **not in the sources** in the same way and quote the same narrow set, all **documented**, with Cycles' device line and `maketx.py` **observed** in its files, the statement about Blender as a Python module quoted, and the step from a command's return value to the run's own status marked **inferred**. 5.3's numbers were all got by tests on the Creator's Mac alone.

**Verdict: it differs** — settled by tests run in every version, 4.5 to 5.2 on both machines and 5.3 on the Mac, and by nothing else.

**What is the same in every version.** 4.5 to 5.2 on both machines; each held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise.

- **A run that finishes normally gives 0.** A single frame, a three-frame animation, and a run with no render argument at all: 0 every time. The first wrote its picture, the second wrote three, and the third rendered nothing and still gave 0.
- **One interrupt gives 1.** Whether the interrupt character is typed into a real terminal or `SIGINT` is sent from another program, and whether the run is a single frame or an animation, the status is **1**. **These runs left no picture file of any kind** — and that half is about when the interrupt landed, not about what an interrupt does. **The 4.5 to 5.2 record does not say when its interrupt was sent. In 5.3 it was sent twelve seconds into a million-sample frame, before that frame finished.** A run stopped before its first frame finished has nothing on disk to find whatever Blender does. **Frames** records the other case in three places, in every version on both its machines: an animation interrupted at frame 3 keeps frames 1 and 2 at full size (`Frames 10`), an interrupt, a terminate and a kill each leave the finished frames whole (`Frames 3`), and an interrupt aimed at a frame's own write does not cut it at all — the frame is finished and opens (`Frames 13`). **So an interrupted animation keeps the frames it had finished**, and nothing here says otherwise. The terminal shows `^C`, then `Sent an internal break event. Press ^C again to kill Blender`, then a stage line ending `| Cancelled`, then `Blender quit`. So Blender catches that signal and turns it into the same orderly ending a person gets by hand, and a program can stop a render exactly the way a person can.
- **Two other signals are not caught.** `SIGTERM` kills the process and a shell reports **143**; `SIGKILL` kills it and a shell reports **137**. **Nothing was written in either of these runs, and that carries the same limit as the bullet above**: `Frames 3` and `Frames 10` record a terminate and a kill leaving the finished frames at full size, in every version on both machines, and `Frames 13` records each of them leaving a short file at the frame's own path when the stop is aimed at the write. **Whether an empty reserving file is also left in 4.5 to 5.2 is not settled** — `Frames 16` holds that disagreement and the separate 5.3 answer. **5.3 adds a third, `SIGHUP`** — what a program receives when the terminal it was started from is closed — and does not catch that either: the process is killed and a shell would report **129**. No earlier version was sent it.

  **One number, two readers, and this is where the two topics look as though they disagree and do not.** `Frames` reports the same three endings as **1**, **−15** and **−9** for the same three signals, in the same versions on the same machines, where this question reports 1, 143 and 137. Neither topic ever ran the other's reader, so there was nothing for either to disagree with: **the number belongs to whatever reads the ended process, not to Blender**, and no comparison in this stage records which reader took its figure. **Anything reading a Blender's ending must know which of the two it is reading**, and must not take 143 against −15, or 137 against −9, for a difference between versions or machines. No test settles this; naming the reader does.
- **A blend-file that cannot be used gives 1.** One that is not there, and one that exists but is not a blend-file, both end at 1 with nothing written.
- **An argument Blender has never heard of, given after a valid one and before any bare double dash, gives 1** and writes nothing: Blender says `unknown argument, loading as file: --no-such-flag` on standard error, then fails to read a file of that name and stops. **After a bare double dash the line belongs to Cycles**, and an argument Cycles does not know is ignored in silence — the render goes ahead and Blender neither complains about it nor acts on it, against a control showing that arguments in that position genuinely are read. See **Settings 17**. That second half was not tried in 5.3.
- **A Cycles render device gives 1 whether the name is nonsense or merely absent.** A name that is not on Cycles' list gives 1; so does a name on the list with no hardware behind it — `OPTIX`, `CUDA` and `HIP` on the Mac, `METAL` and `HIP` on the Norway machine, and `CUDA`, `OPTIX`, `HIP` and `ONEAPI` in 5.3 on the Mac, where `METAL` gave 0. A name the machine does have gives 0 and renders. So **the two kinds of refusal give the same number and different words**, and in 4.5 the two words arrive on different streams — see question 2. Cycles' own file asks for the process to end with 1 when a device cannot be set, and the runs bear that out.
- **A scene with no camera gives 1** and writes nothing, in 4.5 to 5.2. **5.3 gives 0** — below.
- **A Python script that fails leaves the run at 0**, and with `--python` **the render goes ahead and the picture is written** although the script failed; the traceback lands on standard error. With `--python-exit-code 42` **placed before the script argument** the run gives **42**, the render does not happen, and `Error: script failed, file: '…', exiting.` joins the traceback on standard error. **Placed after the script argument the option does nothing** — the script has already run and failed by the time it is read — and the run gives 0 and writes its picture. `--python-expr` behaves the same way. So the option does what the manual describes, and the position in the command decides whether it does it at all.
- **The number a registered command returns does become the run's ending status, and it is not limited to 0 and 1.** A command registered through `bpy.utils.register_cli_command` whose callback returns 7 gives **7**; one that returns 0 gives 0.
- **An output path of `//` is not a refusal.** Status 0, and the picture is written into the folder the blend-file sits in, as `0001.png`.
- **A folder that cannot be written to gives 1 on the Mac**, with nothing written. **On the Norway machine the same run gives 0 and writes the picture**, because that machine is used as the root user and root walks through the folder's permissions. **That is the machine and the account, not the version**, and it is not one of the zero-endings below. Question 1 holds the same test on a Linux machine where root's override was dropped for the single command, and there it gives 1 with nothing written, as on the Mac. **Not run in 5.3**: the tests could not make the folder read-only.

**Five ways a run ends at 0 having rendered nothing at all.** This is the sharpest thing this question found, and it is why a status of 0 must never be read as "the frames are there".

- **A frame argument that is not a number** — `-f abc`. Status 0, output folder empty.
- **An option whose value is missing** — `-o` with nothing after it. Status 0, output folder empty.
- **An animation whose start frame is after its end frame** — `-s 10 -e 5 -a`. Status 0, output folder empty.
- **Saving the render output switched off**, in **5.2 and 5.3**. Status 0, output folder empty. In 4.5, 5.0 and 5.1 the setting does not exist, the probe comes back `AttributeError: 'RenderSettings' object has no attribute 'save_output'` on standard error, and the same command renders and writes its picture at 0.
- **A scene with no camera, in 5.3 alone.** Status 0, nothing written, no render handler fired. 4.5 to 5.2 give 1. Question 1 has the whole of it.

The first three are the same in all five versions, 4.5 to 5.2 on both machines and 5.3 on the Mac; the fourth is 5.2's and 5.3's and the fifth 5.3's alone, and both are on the behaviour list. 5.3 adds one more of the same shape whose status no earlier version has on record: an empty frame argument, `-f ""`, complained about on standard error as incorrect comma use, ends at 0 having rendered nothing. In the first two Blender does say something — `Error: not a number '-f / --render-frame abc'.` and `Error: you must specify a path after '-o  / --render-output'.` — and it says it on **standard error** while the status stays 0. Each run was made into a folder emptied immediately beforehand, so "nothing was written" is a fact about that folder rather than about a stale file. Two more endings of the same shape sit under other questions: a picture of no pixels, refused with `Image too small` at status 0 in all four versions and in 5.3 (question 7), and an incompatible video container and codec, refused at status 0 in all four versions (question 1). And a plain `blender -b <file>` with no render argument gives 0 having rendered nothing, which is what it is for.

**Where it differs, version by version.**

**The tested Cycles scene with its Camera object deleted.** 4.5 to 5.2 give **1**. **5.3 gives 0**, with nothing written, on the Creator's Mac, where the 5.2.2 run built the same way the same day gave 1. Question 1 holds the scene, settings and full answer; this does not establish the result for Workbench with its camera set to none. A render of the same file called from a script with no window still ends at 1 in 5.3.

**The manual's own unknown-argument example.** Every version's manual carries `blender -ba test.blend` and says it "will exit since -ba is an unknown argument". In **4.5** it does: status **1** on both machines. From **5.0 to 5.3** the run **does not end at all**. It prints `unknown argument, loading as file: -ba` on standard error, fails to read a file of that name, opens the blend-file that followed and stays running until something kills it — still going at ninety seconds on both machines, in every one of those versions, on repeated runs, and in 5.3 on the Mac. The line 4.5 prints that ends the run, `Error: argument has no '.blend' file extension, not using as new file, exiting!`, is gone from the later versions. **So all five manuals describe the same behaviour and only 4.5 has it.**

**An engine name that does not exist.** From **5.0 to 5.3** it gives **1** at once — 4.5 to 5.2 on both machines, 5.3 on the Mac — with `Error: engine not found 'NOSUCHENGINE'` on standard error. In **4.5** it does not give 1, and **the two machines part company**: on the Creator's Mac the run ends on an abort, which a shell reports as **134**, printing the C++ runtime's own `libc++abi: terminating` after Blender's error — three runs out of three, and a fourth with five minutes allowed; on the Norway machine it **never ends**, still running at ninety seconds three times over and at five minutes on a fourth. Both are recorded and neither is explained. **The version difference is that 4.5 aborts at 134 on the Mac or stays running on the Norway machine, where 5.0 to 5.3 hand back 1 on the machines tested.** Which way 4.5 fails is the operating system: on the Mac it aborts, and on every rented Linux machine that has been asked, in this topic and in three others, it does not end at all — sometimes after printing its refusal, once after printing the engine list, once after printing nothing. See **Add-ons 7**, **Add-ons 3**, **Settings 6** and **What actually ran 2**. No Linux run of 4.5 has been recorded ending by itself after a refusal. Why is not known.

**A second interrupt, typed three seconds after the first.** **Blender 4.5** ends on an abort, reported as **134**, on both machines. **Blender 5.1 and 5.2** end with exit code **2**, on both machines, and **5.3** with **2** on the Mac, printing an unfreed-memory line after `Blender killed`. **Blender 5.0's two machines disagree** — the Mac ends on a crash, reported as **139**, and names a crash file under the system's temporary folder, while the Norway machine gives exit code **2**. Four runs each way, and nothing chooses between them, so **no version claim rests on 5.0's answer here**. **That is not the same as unpredictable.** Each machine's answer is steady: **Frames 15** ran the same test on the same two machines and got the same split. What is undecided is only whether the crash is macOS or that particular Mac. In every version the terminal shows `Blender killed` after the second press.

**Cycles' own `maketx` command.** It exists in **5.2 and 5.3** and in no earlier version. In **4.5, 5.0 and 5.1** both runs give **1**, with `Unrecognized command: "maketx"` on standard error and nothing on standard output. In **5.2 and 5.3** a picture that is there gives **0** and prints the path of the file it wrote; a picture that is not there gives **1**. So a sub-command's own return value reaches the calling program, which is the same thing the registered-command test shows from the other side. 5.3 on the Mac.

**What `blender --command help` lists.** One command, `extension`, in **4.5, 5.0 and 5.1**. Three — `asset_listing`, `extension` and `maketx` — in **5.2 and 5.3**.

**A Python handler that runs just before Blender exits.** `exit_pre` is in the handler list from **5.1** and absent from **4.5 and 5.0**, read from the running program in all four versions on two machines, and Blender 5.1's release notes state the addition. **It carries no ending status**: the one argument it is documented with says only whether Blender is running with no window or is exiting because of arguments it could not use. 5.3's documentation describes it in the same words; it was not read from a running 5.3.

**One disagreement, and it is about what 5.2 prints rather than about what it hands back.** With saving switched off in 5.2, two runs of the same test disagree. One says the run went on to render, printed its ordinary progress and its `Time:` line, and then ended. The other says it printed no progress and no `Time:` line at all — only `reports | ERROR Render output disabled in Output properties and no active compositing File Output nodes` — and quit, which reads as refusing the render outright. **Both agree on what the trap turns on: status 0 and an empty output folder.** Whether the frame is rendered before the run ends is not settled, and the two readings disagree. **5.3 has no such disagreement**: with nothing else arranged it refuses outright, still and animation alike, printing only that same `reports | ERROR` line — no progress, no `Time:` line, no handler — at status 0. That is 5.3's own answer and settles nothing about 5.2.

**Two conditions could each account for it, and nothing in this stage chooses between them.** The first is **whether a File Output node was in the tree**: with none present, **Writing 7** records the refusal word for word on both its machines, the message itself names the absence of a node as the reason, and this question's own handler test records that with saving off and nothing else arranged not one handler fires — while **The compositor 2** has both frames on disk from a node with the switch off. The second is **whether the run was a still or an animation**: the switch's own tooltip, quoted under question 1, reads `Write frames to disk for animation renders`, and every run on the refusing side that names its shape is an animation. **This question's own record does not say which of the two its disagreeing runs differed in** — which is a gap in a record rather than a thing about Blender, and it is settled by reading what those two runs were rather than by renting anything.

**What is not settled here.** Anything on Microsoft Windows except one number: **Frames 15** records a stop delivered as a console control event to Blender 4.5.12 on Windows Server 2025 Standard ending at **1**, the same as macOS and Linux give for an interrupt. One version, one edition, one machine, one way of stopping. Every other number a Windows shell would report is still owed, and so is whether Ctrl-Break behaves as Ctrl-C does. What a *working* HIP or oneAPI device gives back, both having been refused for want of an AMD or an Intel card. What Blender loaded as a Python module hands back. Whether an unwritable output folder gives 1 on a Linux machine reached by an account that is not root — question 1 settles it with root's override dropped for the one command, and no plain account was ever available. And what a run stopped by pressing Esc inside the window hands back. **Pressing Esc into Blender's window is not impossible** — **Frames 13** and **Frames 15** both drove it, on three rented Linux machines, and it stops the render in every version; neither recorded the ending status. On the Creator's Mac it is refused for a system security setting nobody here may change. **In 5.3 an Esc sent through Blender's own event system did not stop the render at all** — no cancel handler fired and sampling went on — and the running 5.3 binds Esc to closing the render view; whether a person's own Esc stops it is not settled. And in 5.3, also not settled: an unwritable output folder, which was not run, and everything on Linux and Windows.

## 13. When a file the scene points at is not there, what does a render put on each of its output streams?

**How it is known.** All four versions answer **not in the sources**, twice over. No version's manual, API documentation or release notes separates standard output from standard error anywhere — the one hit for those words in any of them is a compositor socket called "Standard output image" — and none of them says what a render prints when a file the scene points at is missing. All four **observe** the single line in Cycles' own `engine.py` whose help text names a stream, "Print rendering statistics to stderr", and all four mark as **inferred** the step from that help text to what a running render does with it. Blender 5.2's documents observe one more, in `maketx.py`, where a failure is written to the error stream by name while the ordinary result goes through `print` — a sub-command rather than a render, and 5.2's own document declines to carry it across. All four then quote the same things the sources do say about a missing file, none of it about streams: placeholder data for a missing library, the Report Missing Files menu item putting a warning in the Info editor's header, and the sequencer's Show Missing Media setting, which is about pixels. Blender 5.1's and 5.2's documents additionally observe the colour Cycles' own files name for a texture that is not found, and mark as inferred that those four numbers read as magenta; Blender 4.5's records the same four numbers and draws nothing from them. Everything below was settled by tests in all four versions on the Creator's Mac and on the Norway machine, with a control run first. **Blender 5.3's** documents answer **not in the sources** twice over in the same way, quote the same things about a missing library, the Report Missing Files item and `show_missing_media`, and **observe** `maketx`'s split between the two streams, carrying nothing across to a render. 5.3 was tested on the Creator's Mac alone, with a control run first, and with two kinds of missing file no earlier version tried.

**Verdict: it differs.**

**What is the same in every version.** 4.5 to 5.2 on both machines; each held in 5.3 on the Creator's Mac as well, except where a bullet says otherwise.

- **The control makes an empty error stream mean something.** On an ordinary render with nothing missing, the whole run lands on standard output and **standard error is empty**, in every version. That was run first, in the same shape, on the same machines, so every silence below is a silence that was looked for. *(No run in this question had a display attached. On a Linux machine with a display running, a windowless 5.2 does put display-library lines on standard error — question 2.)*
- **A missing linked library is loud, and all of it is on standard output.** Five messages, standard error empty, and the render finishes and writes its picture at status 0. In plain terms: the library was read, it could not be opened, it cannot be found, the collection is missing from it, and one library and one linked data-block are missing and the Info and Outliner editors should be checked. In 5.3 all five carry the category `reports` with no window; with the window open three of them carried `blend.readfile` instead, the words unchanged.
- **A missing font is louder still, and again all on standard output.** Twelve lines — the same three, four times over: twice `Unable to pack file, source path '…' not found`, then one saying the font file does not exist. Standard error empty, status 0, picture written.
- **Missing sequencer footage says nothing whatever, on either stream**, in any version, with the setting on or off. Status 0, and the frame is written. What changes is the picture and not the output: magenta across the whole frame with the setting on, fully transparent with it off.
- **A missing blend-file handed on the command line is complained about on standard output**, standard error empty, status 1, no picture. **That is worth setting beside the argument complaints, which go the other way** — a frame value that is not a number, a stray comma and a missing `-o` value each land on standard error. So Blender uses both streams in every version, and which one it uses does not follow from how serious the trouble is.
- **Cycles' statistics land on standard output and standard error stayed empty in these runs**, in every version, although Cycles' own help text for the switch says they go to standard error. **Standard error is not reliably empty in any version** — question 2 holds the warning and the condition. That is question 4's finding, captured again here on two more machines.
- **A missing image texture is painted magenta**, in Cycles and in EEVEE alike, in every version — 4.5 included, whose Cycles render prints nothing about it at all. On the 4.5 to 5.2 scenes a missing linked library and a missing font leave black. In 5.3 the library run shows the grey background, and the font run still shows the cube, with the text absent. The 5.2.2 control of those same scenes gives the same result. The colours belong to the scenes, not to a version change. *(The exact colour figures are one scene's and not a fixed output of any version: they turn on where the camera and the light sit and how bright the light is, which the record does not fix. The two machines agreed with each other to four decimal places in every row.)*
- **A missing image texture is invisible to Blender's own channels with a window open**, in every version: the Info editor is empty, no report box appears along the bottom, and in 5.2 and 5.3 the reports list holds nothing — while the Blender Render window in 4.5 to 5.2 shows a magenta cube. In 5.3 the saved picture is magenta, but the small render window was photographed as plain grey in pictures known to lag. 5.3's terminal still received Cycles' two lines.
- **A render invoked from a script raises instead of reporting.** For a scene with no camera the operator raised `RuntimeError('Error: No camera found in scene "Scene"\n')` back into the start-up script, no Blender Render window opened, and the Info editor stayed empty. That is the route and not the machine: the same failure started by pressing F12 is announced in three places at once, in all four versions — question 2.
- **One setting reads back against its own documentation.** Every version's API documentation gives the sequencer's `show_missing_media` a default of `False`; in the file these runs used it read back **`True`**, in all four versions on both machines. What was read is recorded and nothing is concluded from it.

**Where it differs, version by version.**

**A missing image texture in Cycles.** **4.5 says nothing whatever, on either stream** — its output is the control's with one ordinary stage line added, `Updating Images | Loading missing_tex.png`, which is printed whether the file is there or not. **5.0** puts `cycles | ERROR Image file '…' does not exist.` on standard output, with the path in single quotation marks. **5.1** prints the same sentence **without** the quotation marks. **5.2** downgrades it to a `WARNING` and adds a second line, `cycles | ERROR Failed to load 1 image files`, which no earlier version prints. **5.3** prints 5.2's two lines. Standard error is empty in all five. This is the difference question 1 already records, measured again on a second pair of machines; 5.3 on the Mac.

**A missing image texture in EEVEE, and here the stream itself changes.** **4.5 puts `GPUTexture: Blender Texture Not Loaded!` on standard error.** **5.0, 5.1 and 5.2** put `gpu.texture | ERROR Failed to create GPU texture from Blender image` on **standard output** and leave standard error empty. Neither line names the file. So the message changed stream and wording together, at 5.0. **5.3 changes the wording again**: `image.gpu | ERROR Image file "…" does not exist`, on standard output, under a category of its own, and the first of the three to name the file. On the Creator's Mac; the 5.2.2 run of the same file on the same Mac the same day printed 5.2's `gpu.texture` line, so the change is 5.3's own. On Linux it is untried.

**What quiet mode does to the complaint.** In **4.5** quiet mode silences the whole run — one line, the version banner, nothing else — though the picture is still written. From **5.0 to 5.3** the missing-file complaint survives quiet mode on standard output. **In 5.3 the render progress survives too**: the missing-texture run has 57 lines without `-q` and 54 with it. The 5.0 to 5.2 missing-texture results say the ordinary progress lines were removed, while their ordinary-render results under question 4 retain them. No full quiet missing-texture capture resolves that difference in the earlier answers, and no 5.2.2 control of this case was run beside 5.3. Whether this is a version change is **not established**.

**What the log-file switch does to the complaint.** In **4.5** the file is made and stays **empty**, and the two streams are exactly as they were without it. From **5.0 to 5.3** the whole log goes into the file, the missing-file line with it, and the streams are left with the version banner and `Blender quit`. **So in the later versions a program watching standard output for a reason sees none.** That is the behaviour question 4 records, and for 4.5 to 5.2 it rests on three machines rather than on one; 5.3 on the Mac.

**How a missing font's warning is written.** All twelve lines are on standard output in every version. In **4.5** the warning carries the source file and line number inside Blender — `WARN (bke.vfont): source/blender/blenkernel/intern/vfont.cc:225 BKE_vfont_data_ensure: Font file doesn't exist: //missing_font.ttf`. From **5.0 to 5.3** it reads `geom.vfont | WARNING Font file doesn't exist: //missing_font.ttf` and the file and line are gone. The two error lines above it follow the same split as the rest of this topic — a plain `Error:` in 4.5, a `reports` log line in the later versions — and so do the five library lines.

**Whether Blender's own window says anything about a missing linked library, and it starts speaking at 5.0.** In **4.5** the Info editor is empty on both machines although the terminal carries all five messages — the terminal is told and the window is not. From **5.0 to 5.3** the Info editor lists the five with a warning triangle, and in **5.2 and 5.3** the window manager's reports list holds all five with their types, two `WARNING` and three `INFO` — read with a real window open. **Whether a windowless Blender fills that list is not established, and a render farm is always windowless.** In **5.0** a report box was also caught along the bottom of the window, shortening the last message with an ellipsis of its own, and in **5.3** the Status Bar carried that last message the same way; whether one appears in 4.5, 5.1 or 5.2 is unread, because those messages are raised when the file is read and the box has gone before a render finishes.

**Cycles' `maketx` command is the one place a failure is announced on both streams at once**, and it exists in **5.2 and 5.3** alone. Handed a picture that is not there, each prints `cycles | ERROR Source image not found: <path>` on standard output **and** `Error: Source image not found` on standard error, and ends at 1. In **4.5, 5.0 and 5.1** there is no such command, and the refusal — `Unrecognized command: "maketx"` — is on standard error alone. **This is 5.2's and 5.3's own exception and not a general rule about either**: everything else they say about a missing file in Blender's own words is on standard output with standard error empty.

**Two more kinds, tried in 5.3 alone, on the Mac.** **A missing Alembic cache**, read through a Mesh Sequence Cache modifier: the render goes on, ends at 0 and still draws the object as it was; standard output carries two `object.modifier | WARNING Object: "Cube", Modifier: "MeshSequenceCache", Could not create cache reader for file //cube.abc` lines, and **standard error carries four lines from the Alembic library itself** — `Could not open as Ogawa file from provided streams.` and `Unable to open …`, twice — which are that library's words, not Blender's. **A missing volume file says nothing at all**, on either stream; the only trace is three stage lines about loading and building the volume that no longer appear, and the render ends at 0. No earlier version was put through either, so neither is compared.

**Missing sequencer footage with the window open, in 5.3 alone**: nothing reached the terminal, the reports list held nothing, and the Info editor and the Status Bar were empty.

**What is not settled here.** Anything on Microsoft Windows, including whether its hidden console changes what a starting program can capture. Kinds of missing file nobody put through this question's stream-splitting test, in any version: a sound, a point cache, a USD cache, an external OSL script, an image the compositor points at, and an environment texture in the world; a volume file and an Alembic cache were put through in 5.3 alone. **Three of the kinds are answered elsewhere for what the render shows and whether it says anything.** A missing volume file draws nothing at all and says nothing, and a missing compositor image gives black rather than magenta — **Images 9**. A point cache is answered at length under **Dependencies 18**, including the one absent-cache case Blender announces: a disk cache written by 4.5 is refused by 5.0, 5.1 and 5.2 with a warning naming the object, printed when the file is opened and again during the render. Missing sequencer footage was never opened with a window in 4.5 to 5.2. The exact wording of the Report Missing Files menu item's warning, which is the one destination the documentation names and needs a menu picked with a pointer. And why `show_missing_media` reads back against its own documented default, 5.3's included.

## 14. When a render's printed output is sent somewhere other than a terminal, what decides when each line of it becomes available to whatever is reading?

**How it is known.** All four versions answer **not in the sources**, and this one is a complete silence rather than a thin one. No version's manual, API documentation or release notes contains the word for either output stream at all, nor anything about output being held back, released, or behaving differently when the destination is a file or another program. Every version's manual describes Blender's printed output only as something that appears in a terminal window a person started it from. The Cycles files supplied to this research hold **no session, progress or logging code of any kind** — every version's documents establish that separately, by listing what is in the folder rather than by assuming it — so the place this answer would live is in no file anybody was given. All four versions do **observe** the same one line in Cycles' own file, the help text of the statistics switch naming the error stream, and all four say plainly that it names a stream and settles nothing about timing. **The whole of the answer below was settled by tests**, run in all four versions on the Creator's Mac and on the UK machine. **Blender 5.3's** documents are silent in the same complete way; the one console setting they name keeps a number of lines for display and says nothing about when a line reaches a reader. 5.3 was tested on the Creator's Mac alone.

**Verdict: the same everywhere** — settled by tests run in every version, and by nothing else. The versions were silent equally, so the silence is not a difference between them either. **The two machines agreed on every result that was run on both**, so nothing here divides macOS from Linux any more than it divides the versions. **Every result below held in 5.3 too, on the Creator's Mac**, run the same way with the reader proved first; 5.3 on Linux is untried, so the 5.3 half of this verdict covers the Mac alone.

**A render's own printed lines reach a pipe exactly as they are produced.** Over a three-frame run they arrived in dozens of separate arrivals spread across the whole run, in bursts at each frame boundary, in all four versions on both machines. Put behind a real terminal instead of a pipe, the same run gives the same pattern and the only difference in what arrives is the line endings, which are the terminal's doing. **So a pipe is no different from a terminal for these lines.**

**The same is true of a plain file.** Watched from a second program while the render was still going, the file grew in steps, and **the steps are the frames** — it grows at the moment each frame finishes, not at the end of the run. All four versions, both machines.

**A Python script's own printed lines do not reach a pipe or a file at all until the run ends, and this is the one place the answer splits.** A script printing one line a second for fifteen seconds delivered nothing until the run finished, whereupon all fifteen lines arrived in a single arrival; sent to a file, the file stayed at nought bytes and reached its full size in one step at the end. All four versions, both machines. **The two behaviours were then shown inside one run**, so that nothing could be blamed on two runs differing: a script line printed within the first second reached the reader only after both frames were finished, while the render's own lines arrived throughout. That run was made in all five versions, on both machines in 4.5 and 5.2 and on the Creator's Mac alone in 5.0, 5.1 and 5.3. **Behind a real terminal the same script ticks once a second.** So what decides the timing is **which part of Blender did the printing**, not whether a person is watching.

**What changes a script's lines, and what does not.** A script that asks, on each line, for that line to be sent at once — `print(…, flush=True)` — gets its wish: the lines arrive one a second through the same pipe, in all four versions on both machines. Three other things were tried on a script that asks for nothing. **Two switches change nothing on their own** — `--python-use-system-env`, which lets Python read the system's own settings, and `PYTHONUNBUFFERED=1`, one of those settings, which asks Python not to hold its printing back — **and the two together make the lines arrive one a second.** The third, `stdbuf`, a system tool put in front of the whole command, **changes nothing for a script's lines in any version**, though it does move the version banner from last to first. The wrapper was tried in all five versions; the two switches, alone and together, in 4.5, 5.2 and 5.3 only. All of this is the Creator's Mac alone.

**Progress arrives as whole separate lines, and nothing is ever rewritten in place.** A whole run captured to a file holds well over a hundred line endings and **no carriage returns at all**, in every version on both machines. So anything reading Blender's output can split it on line endings and will never meet a line that is later overwritten.

**The error stream carried nothing whatever on these two machines.** Fed alone to the reader, a whole run gave nought arrivals and nought bytes; kept apart in files, the ordinary stream held thousands of bytes and the error stream **nought**. In every version, on both machines, and with the Cycles statistics switch turned on — **the statistics were in the ordinary output**, under their own headings. **Cycles' own help text, in every version's file, says those statistics go to the error stream.** One of those is what the file says and the other is what the machine did, and **both stand**: the documented line is quoted correctly and the observed result is measured correctly. This is question 4's finding measured again on a third pair of machines; what these runs add is that the error stream held nothing at all across a whole run rather than merely not holding the statistics.

**That must not be read as a general rule, and question 2 already says why.** The one case this project has found of a successful render putting lines on standard error needs a Linux machine with a display server running, in 5.2 — and **neither of this question's machines could have produced it**: one is the Creator's Mac, and the other is a rented Linux machine with no display server at all. So these runs could not have come out the other way. **Standard error is not reliably empty in any version** — question 2 states it in those words and names the condition, and questions 7, 10, 12 and 13 add further reasons. Smoozy renders on rented Linux and does not control whether such a machine has a display server running, so nothing may be built on the belief that the error stream stays empty.

**The file written by the log-file switch fills in as the run goes**, in every version on both machines. **What goes into it differs, and that difference is question 4's rather than this question's**: in **4.5** almost all of it is written at startup and the whole of a two-frame render adds about a hundred bytes, because that version's log has no category for the render; from **5.0 to 5.3** the file grows in steps through the run as the frames finish.

**Nothing already printed is lost, even when the run is killed outright.** A render sent to a file and then stopped part-way kept everything it had printed — after an interrupt the file gained the cancellation lines, and after an outright kill, which cannot flush anything a program is still holding, the file held **exactly the bytes it held before**, ending on the most recent line the run had printed. All five versions, on both machines in 4.5 and 5.2 and on the Creator's Mac alone in 5.0, 5.1 and 5.3.

**Blender's own help list names no switch for any of this.** Each build's list was searched for every word that would name one and holds a single unrelated hit, the animation player's option about reading picture files. The same in all five versions, so the installed builds offer nothing the manuals leave out. Read on the Creator's Mac.

**One caution about every timing above.** Other agents were running Blender on the Creator's Mac throughout the day the 4.5 to 5.2 runs were made, so **its seconds run long and none of them is a quiet machine's timing.** They are given because the shape of an arrival pattern needs them, not as a measure of how fast anything is. What the answer turns on — whether lines arrive during a run or all at its end — a busy machine shows as plainly as an idle one.

**What is not settled here.** Anything on Microsoft Windows: **whether a printed line reaches a reader there as it does here is untried**, and whatever comes back will have to name the machine's Windows edition. Whether the two switches together make a script's lines prompt in **5.0 and 5.1**, neither of which was tried, and whether any of the switch tests behaves differently away from the Creator's Mac. Anything in 5.3 on Linux. And what any of this does when Blender has its own window open: every run here was Blender started with no window, its output read by another program.
