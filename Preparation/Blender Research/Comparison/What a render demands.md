# What a render demands — Blender 4.5, 5.0, 5.1, 5.2 and 5.3 side by side

What a render asks of the computer it runs on, what can be settled about that from outside the file, and what any of it changes about the picture.

## The machines behind the tests

Five machines supplied the observed results below.

- **The Creator's Mac** — a MacBook Pro with an Apple M1 Pro chip, Apple's own 14-core graphics reached through Metal and no second card, 16 GB of memory, with a screen. Every version was tested on it, and **it is the only machine Blender 5.3 ran on** — 5.3.0 Beta, built 2026-10-16, under macOS 26.6.2.
- **A rented Linux machine for questions 1 to 5** — one NVIDIA GeForce RTX 4080 SUPER and an AMD EPYC 7B12, with no display server at all. 4.5 to 5.2.
- **The first rented Linux machine of question 6** — one NVIDIA GeForce RTX 3060, no display server. 4.5 to 5.2.
- **The second rented Linux machine of question 6** — one NVIDIA GeForce GTX 1660, no display server. 4.5 to 5.2.
- **A rented Linux machine in Austria for question 7** — one NVIDIA GeForce RTX 3080 and an AMD EPYC processor, no display server as rented, one added in software for a single test. 4.5 to 5.2.

**Questions 1 to 5, for 4.5 to 5.2, were tested on the Mac and the first of those Linux machines, and nothing in them was run anywhere else.** The Linux machine is the kind of computer a Smoozy render actually happens on, and it carries every timing and every memory figure for 4.5 to 5.2 under those questions; it was shared with other work, so its figures are a busy machine's figures. The Mac was shared with other topics' work too, so **for 4.5 to 5.2 no time and no memory figure was taken on it under questions 1 to 5**. It is the only machine where anything about a window could be looked at.

**Question 6, for 4.5 to 5.2, was tested on the Mac and the two question-6 Linux machines**. Neither is the machine of questions 1 to 5, and **they are not each other either**: different processors, different cards, different countries. A result from one is not a result from the other, and where a test ran on only one of them, question 6 says which. Question 6 needed no display server.

**Question 7, for 4.5 to 5.2, was tested on the Mac and the Austrian machine** — the whole card and the whole processor were confirmed free before those tests ran, so its times are reported as clean and are given as three repeats. The Mac was the opposite case that day — another agent was running Blender on it throughout, so **no Mac time under question 7 for 4.5 to 5.2 is a clean one**; its times are three repeats and nothing rests on a single one, and what the contention does not touch is what the machine printed, the memory Cycles itself reported, and whether two pictures match.

**Blender 5.3 was tested on the Mac alone, under every question.** No Linux machine, no Windows machine, and no NVIDIA, AMD or Intel graphics ran anything for 5.3. Unlike the earlier versions' Mac runs under questions 1 to 5, 5.3's did take times and memory figures there, on a Mac that was also running other work, so they are a busy machine's figures, given as they came. Where 5.3 came out differently from what 5.2 had recorded on the Mac, Blender 5.2.2 supplied same-day controls on the same Mac for the property count and Kernel Optimization. The smaller processor-against-Metal and MetalRT picture gaps had no such control.

**One thing about the Creator's Mac bears on every question here.** It is the only machine in this document that is not one fixed thing: its operating system and its unversioned Blender have both changed while this stage ran, and the 5.2 runs made beside 5.3 used 5.2.2 where the earlier 5.2 runs used 5.2.1 or older. So a figure from an older test is a reading taken on that day, not a mistake to be corrected against a later reading of the machine — and a difference between an older Mac reading and a 5.3 Mac reading can belong to the build, the operating system or the day as easily as to the version.

**The machines cannot settle each other on the graphics device.** The Mac offers Metal and has no CUDA and no OptiX; the Linux machines offer CUDA and OptiX and have no Metal. Where a device result is given below, it says which machine and which backend it came from. **A result from one machine is never set against a result from another and called a difference between Blender versions**: every version difference below rests either on the same test run on the same machine in every version it names, or on a release note that states the change, and no number from one machine was ever subtracted from a number on another. **Every 5.3 result is a Mac result**, so a 5.3 answer set beside a 4.5–5.2 answer that only a Linux machine gave is not established, and is never a difference.

A result settles only the machines it ran on. **Windows was not tested in any version.** Its card rendering is untried, not established as impossible; results on other systems do not settle either Windows edition. No AMD or Intel graphics, no machine with more than one graphics card, and no Blender packaged by a Linux distribution were tested. **For 5.3 nothing at all was run on Linux**, so every Linux result below is for 4.5 to 5.2 only. These are gaps in testing, not differences between versions.

## The answer in short

### Where Blender itself differs between versions

These are short entries. The numbered questions give the evidence and its limits.

- **1 — Settings appear and disappear**, including four names added in 5.3 on the Mac.
- **1 — The compositor device starts at graphics in 5.2 and 5.3**, rather than processor in 4.5–5.1 on the machines tried.
- **1 — Use Tiling was removed as an option in 5.0**, though its stored property remains.
- **1 and 3 — The engine-list command fails in 4.5**, and works in 5.0–5.3 on the machines tried.
- **3 — EEVEE's engine name changed in 5.0.** Acceptance of the other name depends on the route; 5.3 was not offered it.
- **3 — The multi-layer output format is set differently by script from 5.0 on**, as reported under that question; this topic did not test 5.3, and Reports 11 records 5.3 refusing the name from a script.
- **2 — The Texture Cache changes the tested picture in 5.2 and 5.3.** The earlier three versions lack it.
- **4 — The Performance panels gain Texture Cache and Anisotropic Filtering in 5.2**, retained in 5.3 on the Mac.
- **4 — Only 4.5 draws Feature Set**, on the Mac.
- **4 — Only 4.5 prints an extra unavailable-Cycles message with the add-on off**, on the Mac; the Linux record does not show it.
- **5 — Loading a 4.5 file changes its saved tiling values in 5.0–5.2**; 5.3 untested.
- **5 — The blend-file layout changed in 5.0**, by release note, untested here.
- **6 — Saved Simplify limits gain two texture-resolution values in 5.2**, retained in 5.3.
- **7 — AMD hardware ray tracing starts on from 5.1**, rather than off.
- **7 — CUDA's minimum NVIDIA card was raised in 5.0**, by release note, untested near that minimum.
- **7 — Refused-device messages change after 4.5.** The Linux HIP-library warning also differs in 4.5–5.2; 5.3 on Linux untested.
- **7 — Vulkan becomes the default on Windows except ARM, and Linux, in 5.3**, by release note, untested here.
- **7 — RTX Spark support on Windows 11 is added in 5.3**, by release note, untested here.

### What is not established

No question is wholly unanswered. The numbered questions give these limits in full.

- **1–7 — Every Linux result in 5.3, and every Windows result in all five.** The Mac alone ran 5.3.
- **1 and 3 — What `--qos` does on Windows, and whether 4.5 offers it.**
- **1 and 3 — Availability of the single-thread dependency-graph argument in every version**, and its effect.
- **1 and 4 — What thread count and Persistent Data change in every engine, version for version.** The earlier time measurements are Linux-only; 5.3's are Mac-only.
- **2 — Reproducibility beyond the tested scenes and machines**, including 5.3's varying processor pictures with texture-cache files in use.
- **1 and 2 — The Texture Cache when textures press on memory**, and the effects of the four names added in 5.3.
- **4 and 7 — What is inside the Acceleration Structure panel under OptiX.** Its visibility was tested in 4.5–5.2 only.
- **1 — Whether a saved Metal preference costs graphics memory during a processor render.**
- **1, 2 and 7 — Render effects of HIP RT, Embree on GPU, NVLink memory sharing and shader-compilation settings** on the hardware they need.
- **1 — What the difference between eight and seven recorded preset values changes.**
- **1 — Whether four further starting values differ between versions**: the sampling pattern and three EEVEE volume or fast-GI values.
- **3 — The three-against-five count of offered Linux backends in 4.5–5.2.** Five preference values are accepted in the fresh-process tests; what the older count includes remains unresolved.
- **3 — What a 5.x command-line render given 4.5's engine name actually uses and warns about**; 5.3 was not offered it.
- **3 — Whether Cycles' own log names the device in 4.5–5.2.** It did in 5.3 on the Mac.
- **1–7 — Whether results tested only in 5.3 on the Mac hold in earlier versions.** Each question names those cases.
- **2 — Whether graphics denoising changes the picture.** Every 5.3 final-render test reported processor denoising.
- **2 — Whether the path-guiding tiling warning and tile-size rounding describe identical behaviour in every version.** The picture tests did not test those conditions.
- **5 and 6 — Reading saved settings without Blender**, and the physical storage of untouched defaults.
- **6 — Untouched Simplify defaults in 4.5, 5.0 and 5.1.** Only 5.2 and 5.3 were tested.
- **7 — What happens when a card's own memory fills.** The large Linux case reached host memory instead.
- **7 — MetalRT Auto against Off in pixels**, and what Auto weighs on other Apple hardware or scenes.
- **7 — Kernel Optimization's effect on the picture and the order of its times.** The Mac readings disagree within versions.
- **7 — Whether the smaller method-to-method picture gaps in 5.3 belong to the version.**
- **7 — Why same-method graphics renders sometimes come much farther apart.**
- **7 — How 4.5–5.2 draw the Mac's MetalRT and Kernel Optimization controls.** Only 5.3 was photographed there.
- **7 — The NVIDIA driver minimum in 5.3.** Its manual and Cycles file give different figures.
- **7 — What the device label “(Unoptimized Performance)” means for a render.**
- **7 — A hardware ray-tracing control on a machine mixing cards with and without it.**
- **7 — Whether the drawing backend changes a final render, and whether that depends on scene size.**
- **7 — Whether the small MetalRT memory effect has a scene-size threshold.** Three scenes do not establish one.
- **7 — The untested AMD and Apple feature-support wording differences.** They establish neither a version change nor identical behaviour.

### Where only the documentation differs

- **2 — A curve-shape warning about different devices' pictures** is recorded in 5.0–5.2; the tested device comparisons differ in all five on the machines tried.
- **4 — Acceleration Structure drawing rules are recorded from Cycles' files in 5.1**, over the same tested controls on the Mac in all five.
- **5 — The sources label the route to another file's settings with different confidence**, over matching tests on the machines tried.
- **7 — The manual sentence about the Acceleration Structure panel under OptiX** is recorded in 5.2 and 5.3; matching behaviour was tested in 4.5–5.2 only. 5.3's condition was read from its Cycles file and not run under OptiX.

## 1. What settings, if any, change how much a render demands of the computer it runs on?

**Verdict: it differs** — narrowly, in which settings exist, and in one command that fails in 4.5. The shape of the answer, and almost every setting in it, is the same in all five versions.

**What every version says, and agrees on.** Every version answers this, labelled **documented** for the settings themselves, with parts marked **observed** where the claim comes from Cycles' own files rather than from a manual page, and a few marked **inferred** where something is grouped that the sources do not group. The four earlier versions say Blender gathers most of these into a panel called Performance, one per engine, whose stated purpose is properties that affect render speed or memory; 5.3's findings cite the same Performance pages. The four earlier versions name the same families:

- **Blender's own render settings, shared by every engine**: Threads Mode and Threads, Persistent Data, Resolution and its percentage, Render Region and Crop, Simplify with its Max Subdivision, Child Particles, Texture Limit and culling, High Quality Normals, Lock Interface, the compositor's device, precision and denoise-node quality, and the per-view-layer sample override.
- **Cycles' own settings**: Device (processor or graphics), Tile Size, the four acceleration-structure options, Samples, Time Limit, adaptive sampling, Sample Subset, denoising and where it runs, the bounce ceilings, Light Tree and Light Threshold, Scrambling Distance, the volume step settings, Fast GI, the render texture limit, and the adaptive-subdivision dicing settings.
- **EEVEE's own settings**: Render Samples, the Shadow Pool and Light Probes Volume Pool, shadow rays, steps and resolution, ray-tracing resolution and precision, volume resolution and steps, Overscan and its own Light Threshold.
- **Workbench**: the anti-aliasing method for final rendering, and nothing else beyond what it shares with EEVEE.
- **Settings that are not in the file at all**, held in the preferences: which compute backend Cycles uses and which devices are ticked, Distribute Memory Across Devices, MetalRT, HIP RT, Embree on GPU, Kernel Optimization and the shader-compilation method and count.
- **Settings that exist only as a command-line argument**: the thread count, the engine, the Cycles device, the graphics backend and the shader-compilation subprocess count.

**5.3's findings use the same groups and a narrower list inside them.** Among the settings above they do not name resolution or render region, the bounce ceilings, Light Threshold, the volume step settings, Fast GI, EEVEE's samples and its shadow and ray-tracing settings, Workbench's anti-aliasing, or the shader-compilation settings. They name the Texture Cache and Anisotropic Filtering, which only 5.2 and 5.3 have; they list `--qos` among the settings rather than as an exception; and they add a handful of others whose descriptions name a cost — Freestyle, output colour depth, the displacement method, motion-blur steps, the world's map resolution. 5.3's findings say their list is what their searches found, not a complete one. **That is how far the 5.3 reading went, not a change in Blender**: the property sweep found every name 5.2 has on the render, Cycles, EEVEE and display settings and the Cycles preferences still present in 5.3.

The four earlier versions also say the same thing about what is **not** there: no setting caps how much memory a render may use, and none sets the process's priority or which cores it is pinned to. Every one of them searched for it and found nothing; 5.3's findings do not take the point up. **One qualification belongs on the second half of that**: `--qos` on the command line is documented from 5.0 on, 5.3 included, as putting Blender's threads on a machine's efficiency cores or its performance cores, which is core pinning of a kind. It is documented as Windows only and no Windows machine ran it; 4.5's findings record no page entry for it. That is a difference between the documents. Whether the 4.5 build lacks the argument or merely lacks the page entry cannot be told from here, because the argument is Windows-only and no Windows machine has run it. It is untried rather than unreachable. Neither a Blender change nor identical behaviour with different documentation is established; the question stays under What is not established.

**Where they differ, and it is settled by a test rather than by a document.** A sweep of every property on the render settings, on Cycles, on EEVEE, on the display settings and on the Cycles preferences was run in 4.5 to 5.2, three times, on both machines. **All three runs produced exactly the same list of names that are not in all four of those versions**, which is what says these are Blender's differences and not the operating system's. The same sweep was run in 5.3 on the Mac, and once more in 5.2 on the same Mac the same day, where 5.2 came back with its recorded figures exactly.

- **In 5.2 and 5.3 and in none of the others**: the Texture Cache and its Auto Generate companion, two texture-resolution settings, two texture-cache debug settings, Anisotropic Filtering, a save-output setting, and a pixel-jitter setting.
- **In 5.3 alone**: `scene.cycles.name`, `scene.cycles.preview_denoising_upscale_quality`, `scene.eevee.time_limit` and `scene.render.use_compositor_frames_cache`. Nothing in 5.2 is missing from 5.3. Counted by the same rule, 5.3 has four names more than 5.2 and that is the whole of the gap. What the four do is not in the findings; the names are the evidence and nothing more.
- **In 4.5 and in none of the others**: Cycles' Feature Set, three EEVEE ambient-occlusion settings, and eleven bake settings on the render settings.
- **In 5.0 to 5.3 and not in 4.5**: Cycles' Biased volume option. 5.0's release notes state the change — a new volume algorithm became the default, and the previous one, with its step size and max steps, is what the Biased option restores.
- **In 5.1, 5.2 and 5.3 only**: two EEVEE light-intensity settings. **Absent from 5.2 and 5.3 only**: one EEVEE fast-GI thickness setting.

Two default values differ: the compositor's device reads processor in 4.5, 5.0 and 5.1 and graphics in 5.2 and 5.3, and the HIP RT preference reads off in 4.5 and 5.0 and on in 5.1, 5.2 and 5.3 — which matches 5.1's release notes saying hardware ray tracing is now on by default for AMD cards. 4.5 to 5.2 were read on both machines, 5.3 on the Mac. Whether four further starting values differ between versions — the sampling pattern, one EEVEE volume clamp, one EEVEE fast-GI thickness and one EEVEE volume range switch — is **not established by the supplied findings**: they give no complete per-version readings for those four. Their 5.3 values were not read.

**Use Tiling is the one setting that changed status rather than merely appearing or disappearing.** In 4.5 it is a working switch, documented in the manual and written by the Performance presets, which carry eight values. In 5.0 and 5.1 Cycles' own file calls it deprecated and says tiling is always enabled, the presets carry seven from 5.0 on, and 5.0's release notes say the option was removed and the tile size can be raised instead. 5.2's and 5.3's findings do not name it at all. The property is still present and still stores what it is given in every version — 4.5 to 5.2 on both machines, 5.3 on the Mac — and switching it off left the picture untouched in all five (question 2).

**And one command fails in 4.5.** `blender -b -E help` printed a list of three engines and exited cleanly in 5.0, 5.1 and 5.2, on both machines, and in 5.3 on the Mac. In 4.5 it failed on both machines, but differently: on Linux it printed nothing at all and never returned, and had to be killed; on the Mac it printed the whole list and then stopped with an abort and a failure code. So a caller that reads the list gets it on the Mac and never gets it on Linux, and a caller that checks the exit code is told the command failed on both. **That the command misbehaves in 4.5 and not in the newer four is the version difference; that it misbehaves differently on the two operating systems is a fact about the operating systems.**

**What the tests found to be the same in every version.** Applying the three Cycles Performance presets in sequence moved five distinct properties in total and nothing outside the Performance settings — the same five, in every version, 4.5 to 5.2 on both machines and 5.3 on the Mac. What the seven-against-eight difference in the preset files themselves changes is not settled. A preset can also write a value the scene already holds; that produces no change in this test. `--cycles-print-stats` printed statistics and **no line in any version named the device that rendered**, 4.5 to 5.2 on both machines and 5.3 on the Mac; on the Mac a render that ran entirely on Apple's graphics said no word about Metal anywhere. Two lines come close and do not cross it. In every version, with that switch on, a render on a graphics device prints a line saying profiling information is available only for processor rendering — which tells a card render from a processor render without naming the card. And on the Linux machine under OptiX, `Building OptiX acceleration structure` appears in the ordinary progress lines, which says which backend built an acceleration structure and not which device rendered; CUDA prints nothing equivalent. **In 5.3 one route does name the device**: Cycles' own log, switched on at launch — question 3. It was never switched on in an earlier version.

On the Linux machine with the card working, in 4.5 to 5.2, choosing the card rather than the processor cut the render time several times over, dropped the processor demand from about fifteen hundred per cent of one core to about one hundred, and **raised** ordinary memory rather than lowering it — the same shape in all four. (How many times over is not worth a number here: the machine was busy throughout, every run was a single run, and the findings' own tables give ratios from about two to about ten depending on which pair is read. **Question 7 carries times taken three at a time on a machine checked to be quiet**, and those are the figures to use.) On that machine a backend preference of CUDA cost about 248 MB of card memory through a render that ran entirely on the processor, where a preference of None cost none; that was measured in 4.5 to 5.2 and never on the Mac, so whether a saved Metal preference costs the same is not known.

**What 5.3 measured on the Mac, where no earlier version was measured.** All of it is **observed**, on a busy Mac, and none of it is set against the Linux figures above.

- **The thread count reaches the renderer.** On a 320 by 240 Cycles scene on the processor, `-t 1` held the render to about one processor and made it about five and a half times as long; `-t 2` held it to about two and took about half as long as that; `-t 0` matched the run with no argument. A file saved with Threads Fixed at 1 did the same as `-t 1`, and `-t 8` on that file undid it. Peak memory did not move with the thread count.
- **On Apple's graphics the thread count changed nothing measurable.** Eleven of twelve renders, with `-t 1` or without, took between 1.52 and 1.72 seconds by Cycles' own count at about half of one processor. The twelfth, a `-t 1` run made while other work was running, took about seven times longer and is unexplained.
- **The same file on Apple's graphics** took less than half the processor's time, kept about a twelfth as much of the processor busy, and had more than twice the peak memory — about 590 MB against about 263 MB.
- **Tile size and the acceleration-structure options** moved nothing beyond the spread between repeats, except Tile Size 64, which raised peak memory by about 7 MB in all three repeats.
- **Persistent Data** moved neither EEVEE's nor Cycles' wall time or peak memory by more than about one per cent across a ten-frame animation of an unchanging scene. One run of each on a busy machine cannot separate a small effect from noise.
- **The Texture Cache's cost** is under question 2.

**Where the answers are labelled.** Every version's list of settings is documented from the manual and the API pages, with the Cycles ones observed from Cycles' own files, because Cycles is an add-on and its settings have no page in Blender's API documentation in any of the five versions. In the four earlier versions a smaller set is marked **inferred** — resolution, render region, two Simplify settings, two EEVEE ones and Sample Subset — because their quotes state no cost in time or memory at all; in 5.3 the inferred items are that choosing the engine chooses the hardware, and the grouping itself. In every version the claim that the narrow list is complete is marked inferred, and no version claims its list is closed.

## 2. For each of them, what does it change about what the render produces?

**Verdict: it differs** — on one point only, and that point is a setting only 5.2 and 5.3 have. For every setting all five versions share, the answer is the same everywhere it was tested.

**What every version says.** The settings split three ways, and the split is the same in all five:

- **Settings the sources describe as a pure cost, saying nothing about the picture**: Threads Mode and Threads, Persistent Data, Use Tiling and Tile Size, and the four acceleration-structure options. 5.3's findings put Lock Interface, Distribute Memory, denoising on the graphics and the compositor's device in this group too. Every version quotes descriptions phrased entirely in time and memory. **Every version refuses to conclude that the picture is therefore unchanged**, and says so in almost the same words: the sources are silent, and silence is not a statement. The label for this group is **not in the sources**, in all five versions.
- **Settings the sources say change the picture, and how**: samples, the time limit, the noise threshold, resolution and percentage, render region and crop, the Simplify ceilings and culling, denoising and its quality and passes, the bounce ceilings, Light Tree, Light Threshold, Scrambling Distance, clamping and filter glossy, the volume step settings, Fast GI, EEVEE's samples, shadow rays and steps, ray-tracing resolution, volume resolution and steps, Overscan, and Workbench's anti-aliasing. Labelled **documented** where the sources directly describe the picture. Some steps remain **inferred**: in 5.3, that Simplify's reduced geometry, hair and textures show in the picture, and that an undersized EEVEE pool leaves shadows or probe data short; in the earlier findings, some links from sample count to picture quality are inferred too.
- **The device, which every version treats as its own case.** All five say the same two feature limits: path guiding is unavailable on any graphics device, and Open Shading Language is only supported on OptiX. 5.3's findings add a third, a render-time pass offered only on the processor. All five decline to say that a scene using none of these features comes out identical.

**The one place the versions' documents part company, and it is not a difference in Blender.** 5.0's, 5.1's and 5.2's manuals carry a sentence about one curve-shape option saying results will not look exactly the same on different processor and graphics devices, and naming render farms with mixed hardware. 4.5's manual does not carry it — the sentence was searched for there and is not in it, and 4.5's own answer says instead that a general statement the two match is not in the sources. 5.3's findings do not record it, and say that whether the two give the same pixels is not in the sources. **The hand test settles the behaviour and it is the same in all five**, so this is a difference in what the documents say and not in what Blender does.

**What the tests settled, identically in every version — 4.5 to 5.2 on both machines, 5.3 on the Mac.**

- **Eleven settings left the picture untouched, pixel for pixel.** Thread count at one and at eight, tile size at 64 and at 8192, tiling off, spatial splits on, compact BVH on, curves BVH off, four BVH time steps, Persistent Data on, and High Quality Normals on — each compared against an unchanged render of the same scene. In 5.3, Tile Size 256, Threads Fixed at 1 saved in the file, and Lock Interface on were compared the same way and left it untouched too. Two control renders in each version, changing the seed and dropping one sample, both came back different, which is what says the comparison could see a change at all.
  **Here is exactly how far that reaches.** All of them were compared on **one small scene per version** — Cycles, 640 by 480, 64 samples, a fixed seed, denoising and adaptive sampling off — and **every one of those renders ran on the processor**, not on a graphics device. So what is settled is: those settings, on that scene, on the processor, on two makes of processor and two operating systems for 4.5 to 5.2 and on the Mac's processor for 5.3. Nothing was compared on a graphics device, on a heavier scene, or at other values than the ones named. And the controls show that the comparison could see *a* change; they do not show that each setting had something in that scene to bite on.
- **The settings labelled Viewport reach none of a render started from outside.** Six of them pushed to extremes changed nothing, in 4.5 to 5.2 on both machines; in 5.3 on the Mac, seven, with the viewport texture resolution added. One of the six had nothing to bite on in the original scene, and on the Mac a run was made on a scene where it did, with the render-side setting held still: still no change, against a control on that same file that does change the picture. 5.3 added the same check for the two viewport texture settings on a textured scene, against a render-side texture limit that changed the picture by up to about 2.1: with the Texture Cache off, the viewport settings left every value unchanged, and with the cache's files in use they moved it by less than two unchanged runs differ.
- **A Cycles time limit writes a complete file of the usual size holding a different picture** — not a blank one and not a missing one. Every version.
- **The device changes the picture.** On the Linux machine with the card repaired, the same file rendered on the processor and on the card differed in more than half of its channel values, in 4.5 to 5.2, under CUDA and under OptiX, and the two backends disagreed with each other as well. On the Mac the same held for Apple's own graphics, in all five versions; in 5.3 the largest difference was about 0.028 on a nought-to-one scale, in more than half of the channel values. The control is what makes it mean anything: the processor repeats its own render exactly, and here each graphics device repeated its own to within about a millionth, which is tens of thousands of times smaller than the gap between devices. **Read that last figure as the usual case and not as a bound** — question 7 measures how far apart two runs of one method come, at length, and finds it is not one number on a card. **Two makes of graphics processor, three backends, two operating systems, five versions — all give a picture that differs from the processor's.**
  **How far the difference will show is a separate matter, and it is small.** For 4.5 to 5.2 the comparison was made on a full-float OpenEXR file. Its average difference was about 0.00015 on a nought-to-one scale, about a twenty-fifth of one step of an eight-bit picture, so on that measure alone most of it could not appear in an eight-bit file at all; its largest single difference, about 0.04, would. In 5.3, on the Mac's own scene, the average was about four millionths and the largest about 0.028. Another topic that compared a processor render against a card render on a tiny factory scene written to PNG found the two identical — recorded under **Frames**. Nobody has run both comparisons on one scene.

**What 5.3 tested on the Mac and no earlier version tried.** All **observed**, all on Apple's graphics or the Mac's processor, and none of it says anything about the earlier versions.

- **"+CPU"** — the processor and Apple's graphics rendering one frame together — gave a third picture, matching neither the processor's nor the graphics' own, by more than the graphics' own repeat in each case.
- **The compositor's device changes the picture, a little or a lot depending on the node.** A Blur node run on the processor and on Apple's graphics differed by at most about two millionths, across most of the picture; a Denoise node differed by up to about 0.018. Each device repeated its own result exactly. The compositor's precision, Auto against Full, gave the same picture in a final render — which is what 5.3's sources, read closely, imply, labelled **inferred** there.
- **Whether denoising on the graphics changes the picture was not settled.** Every final render reported denoising on the processor, whether the setting was on or off and whether the render ran on the processor or on Apple's graphics, so there was no graphics-denoised picture to compare. Switching the setting on changed nothing beyond what two identical runs differ by.

**And the one difference.** In 5.2 and 5.3, with the Texture Cache and its Auto Generate switch both on, Blender wrote a `blender_tx` folder beside the images and the picture changed — 5.2 on both machines by a wide margin, 5.3 on the Mac by up to about 0.12. Peak memory rose rather than fell, on Linux in 5.2 and on the Mac in 5.3, on scenes whose textures fit easily in memory; only that small-scene case was run in either version, so what the cache does when a scene's textures do not fit is unanswered. 5.3 adds what its factory state does: the cache on and Auto Generate off, with no cache files beside the images, wrote nothing and gave exactly the picture of the cache off. Once the cache files existed, the same file loaded them and gave a picture close to, but not identical with, the Auto Generate run — and two such renders did not repeat each other exactly, by up to about 0.0004, where every other processor render in 5.3 did. In 4.5, 5.0 and 5.1 the setting does not exist, so there is nothing to switch and nothing to compare. That is the same difference already reported under question 1, seen from the output side.

**What neither the tests nor the sources reach.** Whether the picture is bit-for-bit reproducible across machines or across thread counts is not stated in any version's sources; the tests show only that a change of thread count leaves the picture untouched on the machines tried. What MetalRT, HIP RT, Embree on GPU, Distribute Memory Across Devices, Kernel Optimization and the shader-compilation settings change about the picture is answered by no version's sources; MetalRT and Kernel Optimization are taken as far as the tests go under question 7, and the rest no test reached. And 5.1's and 5.3's findings record, from Cycles' own files, a warning that tiling "may work poorly" with path guiding and a tile-size rounding calculation; nobody looked for the same lines in the other three versions' files, The tested tile sizes left the picture untouched on the small processor scene with path guiding off. That does not test the warning or establish that the rounding calculation is the same in every version.

## 3. Which of them can be settled at the moment a render is started from outside Blender, and which only by changing the file?

**Verdict: it differs** — on two narrow points about the engine argument, and on one output format name. Everything else is the same in every version tried.

**What every version says.** Every version gives the same shape of answer, labelled **documented** for the arguments that exist and **inferred** for the general lever:

- **A short list of arguments settles things directly.** The four earlier versions name the engine, the thread count, the Cycles device, the graphics backend, the shader-compilation subprocess count, and Cycles' statistics switch, and three of the four also name the argument that picks the active scene. 5.3's findings name the engine, the thread count, the Cycles device and `--qos` under this question, and the graphics backend and the statistics switch under question 7. The Cycles ones must come after a double dash, which every version quotes.
- **Nothing else has an argument of its own.** Every version read the whole command-line page and found no argument for samples, tile size, tiling, persistent data, resolution, render region, simplify, the acceleration-structure options, the time limit, denoising, bounces, or any EEVEE or Workbench setting.
- **The general lever is Python at start-up**, and every version labels this **inferred** and writes out the step: the command line runs a script or an expression, arguments run in order, and these settings are writable properties, so a script placed after the file and before the render can set any of them without touching the file on disk. No version found a page that says this in one sentence.
- **Loading the file overwrites what was set before it.** Quoted in every version from the same manual passage.
- **The preferences are a third home**, in a file of their own, and a blend-file does not carry them. The Cycles device argument is the one documented override.
- **Every version records the same unanswered thing about the thread argument**: the API documentation says it has no Python equivalent, even though the scene property exists, and no version's sources say which wins when the file and the argument disagree. The tests answer it, below.
- From 5.0 on, 5.3 included, the list also carries `--qos`, documented as Windows only. 4.5's findings record no page entry for it, and no Windows test ran it.
- The argument that switches the dependency graph to a single thread is in the same position as `--qos`, more weakly: 5.1's and 5.2's findings name it and 4.5's, 5.0's and 5.3's do not, nobody ran it anywhere, and nobody recorded looking for it in the other pages. Its availability in every version, and its effect, remain under What is not established.

**What the tests settled, identically in every version tried — 4.5 to 5.2 on both machines, 5.3 on the Mac.**

- **The thread argument writes the scene's own Threads value**, whichever side of the file name it sits on. Giving it zero leaves the stored value alone. Under Auto-Detect the property reports the machine's own logical processor count — eight on the Mac, twenty-four on Linux, which is the point of that reading rather than a disagreement.
- **The thread argument also caps a later script.** A start-up script that assigned five threads and then printed what it had just assigned got three back when the argument said three, and five when no argument was given. Order on the command line made no difference, and the processor share followed the printed number.
- **The engine argument works only when it comes after the file name**, refuses an unknown name by name, and never changes the file on disk — though a session that saves afterwards writes the overridden engine into the new file. Line for line in every version. In 5.3 the refusal also ended the run with a failure status before any later script on the line ran; the earlier versions' records do not say what status they returned.
- **The Cycles device argument beats both the file and the saved preferences, in both directions, and writes nothing down.** A file saying processor, with no backend named in the preferences, renders on the graphics device the moment the argument names one; a file saying graphics, with a backend saved, is pulled back onto the processor by the argument. Neither the file nor the preference can stop it. The stored device reads back unchanged either way, before a render and after one. On Linux this was shown by timings and by watching what the process held on the card; on the Mac it was shown by which of two reference pictures came out, and in 5.3 also by Cycles' own log line naming the device. Every route gave the same answers in every version.
- **What the file and the preference do decide is what happens when no argument is given.** The file's Device says whether the graphics device is used at all; the preference says which backend; and a file asking for graphics with no backend named renders on the processor and never touches the card. Shown on Linux with the card working, as a picture comparison — the run came out identical to the processor's own render, down to the last number, and missed the card's render by the whole gap between the two devices, and it held no card memory at any point — and again on the Mac whose graphics work perfectly, so it is a fact about the preference and not about a broken driver. Every version — 4.5 to 5.2 on both machines, 5.3 on the Mac.
- **Naming a backend the build accepts but has no hardware for does not quietly fall back to the processor.** On the Linux machine, given each of the six backend names in turn, the argument produced the processor's picture for the processor, the card's picture for CUDA, a third picture for OptiX, and for the three with no hardware behind them it **stopped the render, wrote no image and returned a failure code**, saying it found no Cycles device of the type asked for — 4.5 to 5.2, word for word. The no-hardware half was also run on the Mac, in all five versions, with the same ending — question 7. This matters to anything driving Blender from outside, because the failure code is visible to it where the device that rendered is not.
- **Which backend names a build will even accept is a fact about the operating system, not about the version.** The Linux machine took five of the six names and refused one by name in 4.5 to 5.2; the Mac took two and refused four in all five versions. So a value that can be written on one machine cannot be written on the other, and this is nowhere counted as a difference between versions. The fresh-process listings accepted None, CUDA, OptiX, HIP and oneAPI, with graphics devices behind CUDA and OptiX only. A count of three offered backends also stands in the findings, without making clear whether it counts accepted names or available methods. The three-against-five reading remains unresolved; neither is chosen as the complete answer.
- **A driver that does not match its own library leaves Cycles with an empty device list.** While the Linux machine's loaded driver and its driver library did not match, nothing on it could start work on the card and Cycles listed no devices at all, in 4.5 to 5.2 alike.
- **A plain background run reads the saved preferences, and factory startup does not.** The same rule on both machines, and in 5.3 on the Mac; neither kind of run wrote a preferences file into an empty settings folder. What differs between the machines is the factory value itself — Metal on the Mac, in 5.3 too, and None on Linux — and that is not a difference in Blender.
- **The resolution percentage reaches a render started from outside** — a 160 by 120 file at 37 per cent wrote a 59 by 44 image in every version. **Render Single Layer does not**: both view layers were rendered in every run, ticked or not, exactly as every version's manual says.
- **A start-up script can set a setting that has no argument of its own**, and it reaches the render: samples set to seven printed seven and produced a picture that is not the 64-sample picture, in every version. In 5.3 the time limit was set the same way and reached the render too.

**In 5.3, Cycles' own log names the device that rendered.** Started with `--log "cycles" --log-level info`, every render printed a line naming where the path tracing ran — the Mac's processor, or Apple's graphics under Metal — and, on Apple's graphics, whether hardware ray tracing was on; denoising runs printed where the denoising ran. Across all eight crossings of file, preference and argument, the device the log named was the device the picture says rendered, including the two where the file asks for graphics and the work went to the processor. **Observed**, on the Mac. That log was never switched on in an earlier version, so whether 4.5 to 5.2 print the same is not established.

**The differences.** First, the name to give the engine argument is not the same in every version — `BLENDER_EEVEE_NEXT` in 4.5 and `BLENDER_EEVEE` in 5.0 to 5.3. 5.0's release notes state the change, and each version here accepted and stored its own name — 4.5 to 5.2 on both machines, 5.3 on the Mac, where its engine list offers `BLENDER_EEVEE` and a file saved with EEVEE reads back under that name. One version here was offered a name that was not its own, and refused it: 4.5, given the newer name from a script on the Mac, stopped on that line and printed the three engines it does take — EEVEE under its own older name, Workbench and Cycles.  Which name a version will accept turns out to depend on the route. On the command line, 4.5 takes its own name alone and 5.0, 5.1 and 5.2 take either; set from a script, every one of those four takes its own name alone and refuses the other. **So the name that works everywhere, by every route, is the version's own.** That was run under **Settings** on the command line and under **Reports** and **Images** from a script; the command-line acceptance rests on one run on one machine on a 64 by 64 scene, and whether a 5.x command-line run under the old name really renders in EEVEE, and whether it warns, was never captured. This topic did not offer 5.3 the old name by either route; **Images 9** records 5.3 refusing it from a script.

Second, `blender -b -E help`, the documented way to ask which engines a build offers, works in 5.0 to 5.3 and fails in 4.5, as set out under question 1. Anything that asks 4.5 for its engine list must handle a failed command: on the tested Mac the list was printed before the failure; on Linux it was not.

**And one output format name is not set the same way in every version.** `OPEN_EXR_MULTILAYER` is refused in 5.0, 5.1 and 5.2 when a script assigns it as the file format, until the media type is set to multi-layer first; 4.5 has no media type and takes the name straight. On the launch line, `-F OPEN_EXR_MULTILAYER` is accepted in all four on both machines and writes a real multi-layer file — settled under **Settings 17** and under **Settings 1**. The refusal was met here in passing while testing something else, on both machines, and it is the script route alone that it belongs to. This topic did not try 5.3 by either route; **Reports 11** records 5.3 refusing the name from a script until the media type is set, and **Settings 17** records the launch-line name writing a multi-layer file in 5.3.

## 4. Do any of them belong to a particular render engine rather than to every engine?

**Verdict: it differs** — the split itself is identical in all five versions, but what each engine's Performance panel holds is not.

**What every version says, and they agree.** Every version answers yes, and describes the same split, labelled **documented** for where each setting is kept, with the placement facts **observed** from Cycles' own files:

- **Cycles' own**, kept on a settings block the add-on attaches to the scene: Device, Tile Size, the four acceleration-structure options, samples, time limit, adaptive sampling, sample subset, denoising, the bounce and clamping settings, Light Tree and Light Threshold, Scrambling Distance, path guiding, the volume settings, Fast GI, the render texture limit and the dicing settings. Every version quotes the same gate in Cycles' interface file that stops its panels being drawn under another engine.
- **EEVEE's own**, kept on its own block: the two pools, render samples, the shadow settings, the ray-tracing settings, the volume settings and Overscan.
- **Workbench's own**: the final-render anti-aliasing method, kept on the display settings.
- **Blender's own, belonging to no engine but shown inside Cycles' panel**: Threads Mode, Threads and Persistent Data — and, in the four earlier versions' findings, High Quality Normals; 5.3's findings place High Quality Normals with EEVEE and Workbench instead, which is where the window test found it drawn in every version (below). Every version makes the same point — Cycles' interface reads these off Blender's render settings, not off its own — and every version says the same thing about the limit of that observation: it shows where a setting is drawn, not which engines act on it.
- **In 5.2 and 5.3, which have them**: the Texture Cache, a general render setting that 5.3 labels Cycles-only by **inference** from its documentation; and Anisotropic Filtering, which 5.3 documents for EEVEE and Workbench. The compositor's settings belong to no engine.
- **Every version records the same gap**: whether EEVEE and Workbench honour the thread count and Persistent Data is not stated anywhere in the sources.

**What the tests settled, identically in every version tried — 4.5 to 5.2 on both machines, 5.3 on the Mac.**

- **Cycles' settings cannot be read at all with the Cycles add-on switched off**, and the wording of the failure is identical in every version. With the add-on off, a file whose engine is Cycles even reads back as the EEVEE name. Cycles' values **are** readable while EEVEE is the engine. Both machines agree — with one small exception: on the Mac, 4.5 printed one extra line saying the Cycles engine was not available for the scene, which the newer versions did not print, and which the Linux record does not show for 4.5 either.
- **Cycles' own values survive the engine being switched to EEVEE and back**, unchanged. Every version.
- **Simplify's Render column reaches all three engines** — Cycles, EEVEE and Workbench each rendered a different picture with the Max Subdivision limit on. Every version. So it is not Cycles-only in effect. 5.3 also tried the child-particle limit under all three engines, and it changed each engine's picture too.
- **EEVEE and Workbench both render on a machine with no display server**, in 4.5 to 5.2, and both wrote their image. That is a Linux-only result, never run in 5.3; the Mac cannot be put in that state, because its window server cannot be taken away. What the Mac did show is that both engines render in a background run there too, in every version.
- **The thread count moved nothing measurable under either EEVEE or Workbench** on the Linux machine, in 4.5 to 5.2, where under Cycles the same argument changed the time by a factor of fifteen. That is recorded as no effect seen, not as the engines ignoring it. On the Mac only 5.3 was run: on renders under a second long, EEVEE with eight threads came out about 0.05 seconds shorter and about 28 MB higher than with one, Workbench did not move, and every process used under one processor's worth either way. A ten-frame EEVEE animation with Persistent Data on and off moved by about one per cent, one run each. None of these can be set against the Linux figures.

**Where it differs, and it was run on the Mac only because it needs a window.** In all five versions the three engines show different Performance panels: Threads, Acceleration Structure and Final Render appear under Cycles and under neither of the others; Memory and Viewport appear under Cycles and EEVEE but not Workbench; Compositor appears under all three; and High Quality Normals is drawn straight into EEVEE's and Workbench's panel and is not in Cycles' Performance panel at all. **Two things differ between versions:**

- **5.2 and 5.3 alone** show a Texture Cache panel under Cycles — in 5.3 with its own tick, Auto Generate, and buttons to generate and clear — and an Anisotropic Filtering control alongside High Quality Normals under EEVEE and Workbench.
- **4.5 alone** draws a Feature Set row above Device, which is the Feature Set property that only 4.5 has. That row is on the Render tab rather than inside the Performance panel, and it is named here because it was seen in the same run.

Both were run in all five versions on the Mac. Their results settle the versions **for macOS and for the interface**, and say nothing about how the panels look on Linux or Windows.

**The Acceleration Structure controls change with the device, the same way in all five versions**, also on the Mac only. With the device set to the processor the panel shows Use Spatial Splits and Use Compact BVH; with the device set to graphics **and** a backend named it shows Use Spatial Splits, BVH Time Steps and Use Curves BVH. It takes both halves: a file set to graphics with no backend named keeps the processor's controls and greys out the Device field, which is the interface saying in its own way what the picture comparisons found — such a run goes to the processor. In 5.3, with graphics and Metal, the Open Shading Language tick under Device is not drawn either. The panel is drawn in all four combinations tried there; what changes is what is inside it. **Whether it is drawn at all under OptiX is settled separately, under question 7**, by asking the panel itself rather than by looking: on the Linux machine it goes away only when OptiX is chosen, the scene is set to the card, and the processor is not ticked beside it — the same in 4.5 to 5.2. The Mac offers no OptiX, so it cannot be asked there at all; under the two technologies it does offer, the panel is always present in all five versions. What is inside it under OptiX has still never been looked at, because nobody has photographed that panel on a machine with an NVIDIA card and a screen. 5.1's findings alone record the rules in Cycles' own files that decide which of these controls are drawn for which device, and nobody looked for the same lines in the other versions' files.

**The panel's own visibility test is not the whole story.** Asked on its own whether it should be shown, the Acceleration Structure panel answers yes under all three engines, because its own test looks at the device and not at the engine. It is not drawn under EEVEE or Workbench all the same, because its parent panel is not drawn. Every version.

**What Simplify panel EEVEE and Workbench show was photographed in 5.3 alone.** Under both, a Simplify panel holds the same switch, Max Subdivision for viewport and render, and the child-particle limit under the label "Max Child Particles", with no texture limits and no culling — those appear under Cycles only, whose own Simplify panel also holds the texture resolution, the texture size limit and both culling settings. **Observed**, on the Mac; no earlier version was photographed.

## 5. Can their values be read out of a file?

**Verdict: it differs** — on what a newer version reads out of a file an older one saved, and on the file's own layout. How you read the values is the same in every version.

**What every version says.** Every version gives the same three-part answer:

- **Yes, for everything stored in the file**, by opening it in Blender and reading the property in Python, which can be done with no window at all. Every version labels the general claim **inferred** and writes out the step: each piece is documented separately — the settings are properties of the scene, scenes live in the file, a background run can execute a script — and no page joins them. For one single property the API documentation shows it being read and the value coming back, and the earlier findings label that one **documented**.
- **Without Blender: not established.** Every version searched for a description of the blend-file's layout or a tool for reading one, and every version came back **not in the sources**. 5.3's findings add the one related fact they found: a compressed blend-file uses a common compression that other tools can undo — which says nothing about reading a setting out of it.
- **No, for anything held in the preferences** — which backend Cycles will use, which devices are ticked, MetalRT, HIP RT, Embree on GPU, Kernel Optimization, the shader-compilation settings. They are in a different file, so a scene file cannot tell you which device a render will actually use. Every version says this, and every version adds that anything set by an argument at launch is in no file by definition — labelled **not in the sources** in 5.3, which found no statement either way.
- **Another file's settings can be reached only by linking its scene in**, not by peering into the file. Every version quotes the same facility and the same limit — what it hands back before you link is a list of names. That claim is labelled **documented with a caveat** in 5.1 and **inferred** in 4.5, 5.0 and 5.2; 5.3 quotes the limit and leaves the route itself to the test.
- Every version also records the same caution: a value read out of a file is not necessarily the value the render will use, because arguments and preferences can override it.

**What the tests settled, identically in every version — 4.5 to 5.2 on both machines, 5.3 on the Mac.**

- **Nineteen settings all came back exactly as they were written**, after being saved into a file and read out of it again — thread mode and count, Persistent Data, resolution percentage, Simplify and its render subdivision, High Quality Normals, Render Single Layer, tile size, tiling, samples, max bounces, the render texture limit, the three acceleration-structure switches, BVH time steps, the time limit, and EEVEE's render samples. Including tiling, which 5.0 and 5.1 describe as deprecated and every version stores anyway.
- **Another file's render settings can be read after its scene is linked in, and not before.** Inside the loading block what comes back is a name and nothing else; after it, the other file's scene is present and every setting reads back at the value saved into it, arriving as a second scene beside the current one. The same result in every version.
- **Cycles' values cannot be read with the add-on off**, in any version, with identical wording — the same result reported under question 4. In 5.3, asking the scene for its stored Cycles block directly returned nothing, with the add-on off and with it on, and the scene listed no stored entries at all — so neither of those two reads exposed the Cycles values in the tested 5.3 file. Other ways of reading stored values were not tested. Not tried in an earlier version.
- **A value read back in the same run as a launch option can be the option's rather than the file's.** The thread argument changes the scene's own Threads value, so reading it back gives the argument's number; the Cycles device argument changes neither the scene's Device nor the saved preference, so reading those back gives what the file and the preferences say, not what rendered. Every version tried, from question 3.

**Where it differs.** A file saved by Blender 4.5 with Use Tiling off and Tile Size 256 reads back **as saved** in 4.5, and as Use Tiling **on** with Tile Size **8192** in 5.0, 5.1 and 5.2. Samples was untouched in all four. The two machines agree line for line, so this is Blender and not one machine or one file. 5.0's own findings show the mechanism, observed in Cycles' versioning code: on loading a file written before a certain 5.0 build, it switches tiling on and sets the tile size to 8192. **So a tile size read out of an older file through a newer Blender is not necessarily the tile size that was saved.** 5.3 was not tried; whether it does the same is not established.

**And one difference nobody could test.** 5.0's release notes say the blend-file format changed — the file header and the header of every block — and that any code parsing blend-files has to be updated. No version documents a way to read a file without Blender, so nothing in this project reads one that way, and the release note is the whole of the evidence; 5.3 comes after the change. 5.2's release notes separately record three new options for finding all the image files a render needs, including its texture cache files; that is 5.2's note, and it reads file paths rather than settings values.

## 6. What, if anything, does a saved scene record about limits on subdivision, child particles, and texture size, including any switch governing those limits, and what can be read back when the file is opened from outside Blender's interface?

**Verdict: it differs** — in how many values a scene records. 4.5, 5.0 and 5.1 record seven; 5.2 and 5.3 record nine. Everything else about this question is the same in every version tried: what is stored, where it is stored, that it survives saving, and that all of it can be read back with no window open.

**What a saved scene records, in every version.** One switch, and then a pair of values for each limit — one used for the viewport and one used for the final render:

- **The switch**, `scene.render.use_simplify`. Off unless somebody turns it on.
- **Maximum subdivision**, `scene.render.simplify_subdivision` for the viewport and `simplify_subdivision_render` for the render. A whole number from 0 to 32767; the documented defaults are 6 and 0.
- **Child particles**, `scene.render.simplify_child_particles` and `simplify_child_particles_render`. A fraction from 0 to 1; the documented defaults are 1.0 and 0.0.
- **Texture size limit**, `scene.cycles.texture_limit` and `scene.cycles.texture_limit_render`. Either off, or a ceiling of 128, 256, 512, 1024, 2048, 4096 or 8192 pixels. Both start off.

The switch, the subdivision values and the child-particle values are Blender's own render settings. The two texture values belong to Cycles and sit on the scene's Cycles block, which is why they are reached by a different path. **The labels are the same in all five versions**: the names, meanings, ranges and defaults are **documented** from the manual and the API pages, except the Cycles values, which are **observed** from Cycles' own files because Cycles has no API page in any of these versions.

**The difference. 5.2 and 5.3 record two values the other three do not have**: a texture resolution scale, `scene.cycles.texture_resolution` for the viewport and `texture_resolution_render` for the final render, which shrinks image textures by a fraction rather than capping them at a size. It runs from a hundred-thousandth to one and starts at one. **5.2's release notes state it as a new setting in the Simplify panel, alongside the texture limit that was already there** — so this is not a gap in anybody's documentation. It was also asked of the software itself: a test that ran in 4.5, 5.0 and 5.1 asked each running Blender whether the final-render resolution property existed, and each answered that it did not, while the same property was set, saved and read back in 5.2 and in 5.3. **All five versions were asked on the Creator's Mac, so the difference rests on one machine across the five, and no result from one machine was set against a result from another.** The three older versions were asked again on the second question-6 Linux machine, and 5.2 was set and read again on the first, and both agreed with the Mac.

**Everything written into these values survives saving and comes back unchanged.** A file was saved with every value set away from its default, then reopened by a fresh background process with no window, and every value came back as it was written — in 4.5 to 5.2 on the Mac and on the first question-6 Linux machine, and in 5.3 on the Mac. Two scenes in one file each kept their own values, so this is recorded per scene and not once per file. **Turning the switch off changes nothing about the other values**: a file saved with Simplify off came back with the switch off and every subordinate value still exactly as written, in every version tried. Those results are **observed**. Before them, no version's sources showed the round trip at all: every version's answer to whether these values survive saving was **inferred** from the general rule that values assigned to Blender's data are saved, and every version said in as many words that its sources do not report the trip itself.

**Reading them back from outside Blender's interface works, and it is the documented route that does it.** Blender is started with the file, told to run without a window, and handed a short script that reads each scene's properties by the paths above. That route is documented in every version — running in the background, running a script, and reaching the scenes through Blender's own data module — though every version marks the joining of those pieces into this exact task as **inferred**. The hand tests then ran it, in every version, and it returned every value. **Reading these values without Blender at all — by looking into the file directly — is not established in any version**, for the same reason given under question 5: no version's sources describe the file's layout.

**A file written on one operating system reads back unchanged on the other.** Files were carried between the Mac and the first question-6 Linux machine in both directions, in 4.5 to 5.2, and every value and every property path survived the crossing. The Mac-to-Linux direction was then run again, in those four versions, on the second question-6 Linux machine, in processes with no add-ons loaded at all. So that one direction was got twice, on two different Linux machines, and those are two results and not one. 5.3 was not tried across systems.

**What the switch does has two answers, and they must not be confused with each other.**

- **What the documentation carries is narrow.** In every version the quoted lines from Cycles' own interface file show the switch drawn in the Simplify panel's header and both groups of controls made active from it. That is all they show. **No version's sources say the switch changes what a render produces** — 5.3's findings mark the claim that it governs the texture limits **inferred, and possibly wrong**.
- **A hand test settles that separately, and it came out the same in every version.** Controlled cases were built at 128 by 128 pixels: a cube subdivided four times against a render subdivision limit of zero; thirty hairs carrying interpolated children against a render child-particle percentage of zero; and a flat plane carrying a 512-pixel checker against a texture limit of 128 pixels. Each was rendered twice with the switch off, as a control on whether the renderer repeats itself, and once with it on. **In every version, switching it on changed the picture materially** — thousands of the picture's 65,536 colour values in the first two cases, and in the texture case three quarters of them in 4.5 to 5.2 and about three fifths in 5.3; at the largest by more than half the full range of a value in 4.5 to 5.2, and by up to nearly half in 5.3 — while the repeats came back either identical or apart in 15 of those values by a hair, at most a step or two of an eight-bit picture. **So the switch reaches a render started from outside Blender, in all five versions.** In 5.2 this was run on the Mac and the first question-6 Linux machine; in 4.5, 5.0 and 5.1 on the Mac and the second; in 5.3 on the Mac alone. The two machines agreed exactly in 5.0, 5.1 and 5.2. In 4.5 they agreed on every count and every largest difference and parted only in the last few digits of two averages, which is a fact about two different processors and not about Blender. One thing was necessarily not identical across the versions: 5.2's texture case also set the resolution scale it has, the three older versions set the size limit alone, and 5.3 ran the size limit and the resolution scale as two cases, one at a time — each changed the picture only with the switch on, as the subdivision and child-particle limits did.

**What the subdivision limit reaches, in 5.3.** With the switch on, a render Max Subdivision of zero changed the picture of a cube carrying a Multiresolution modifier, and left the picture of a cube using adaptive subdivision unchanged to every value — controls showed that cube really was rendered with adaptive subdivision. **Observed**, on the Mac; not tried in an earlier version.

**The saved values are still there when Cycles is not the engine doing the work.** A file saved with EEVEE as the active engine reopened with the Cycles block present and its texture values unchanged, tested here in 5.0 and 5.2 on the Mac and the first question-6 Linux machine, and in 5.3 on the Mac. Question 4's own test showed the same thing in every version.

**One thing a reader should not assume: an untouched scene does not read back at the documented defaults.** In 5.2, on the Mac and on the first question-6 Linux machine alike, and in 5.3 on the Mac, a scene nobody had touched reopened with a render subdivision of 6 and render child particles of 1.0 — not the 0 and 0.0 the documentation gives for those two properties — while a scene where every field had been set by hand to those documented defaults reopened with 0 and 0.0. So the value a fresh scene carries and the value the documentation calls the default are not the same thing on the render side, and a reader deciding whether a file has been edited cannot tell from the value alone. In both versions, Blender's own listing of what the untouched scene's Cycles block holds named none of the texture values, and in 5.3 asking for the stored texture limit directly returned nothing while reading the setting by name gave "off" — so through Blender, an untouched texture value looks unrecorded and reads back as the default of the Blender doing the reading. **This was tried in 5.2 and 5.3 only**, so nothing here says whether the older three behave the same way. It also says nothing about what is physically written into the file: the tests read values through Blender, not bytes.

**What none of this reaches.** Whether these values are written into the file or rebuilt from their defaults when it opens is answered by no version and by no test. Windows was not tried, on either kind of processor, Linux was not tried for 5.3, and neither was a Blender packaged by a Linux distribution rather than published by Blender itself. Those are silences in what could be tried, and they are not differences between versions.

## 7. Where a render can be told which of a graphics card's rendering methods to use, what methods are there, what does choosing one rather than another change about the render, and does anything establish whether that changes with the size of the scene?

**Verdict: it differs** — on three narrow points between the earlier versions, and on two more that 5.3's release notes state. Where the choice lives, what the methods are, that the choice changes the picture, and that what it changes turns on the size of the scene, are the same in every version tried.

**What the sources establish.** No version's sources answer this whole question or explain what MetalRT's Auto weighs. Source claims below keep their labels. The render results are **observed** on the Creator's Mac with Apple's graphics and, for 4.5 to 5.2, on the Austrian Linux machine with one NVIDIA RTX 3080. The Mac answers Metal; the Linux machine answers CUDA and OptiX. **5.3 has the Mac's answer alone.**

### Where the choice is made

**Three places, and they are not equal. The same in every version.**

- **The preferences hold the technology**, and which of the machine's devices are ticked under it. Their separate configuration file is documented. In 5.3, the conclusion that these values are outside the scene file is **inferred** from that file and their status as add-on preferences; the Mac tests below also **observed** the separation.
- **The scene holds only whether a card is used at all** — processor or graphics — and never which technology. **Documented** in every version, and **observed** in Cycles' own files.
- **The command line holds an override**, `--cycles-device`, which every version's manual documents — the four earlier versions' with a background example — and which must come after a bare double dash. Every version reads Cycles' own help text saying it beats the preference and the scene, and every version marks the claim that it really does so as **inferred**.

**What the tests settled, identically in every version tried — 4.5 to 5.2 on both machines, 5.3 on the Mac.**

- **The command-line choice beats both the stored preference and the scene's own setting, in both directions.** A configuration naming no technology and a scene set to the processor still rendered on the card when the argument named one; a configuration naming the card's technology and a scene set to the card was still pulled onto the processor when the argument said so. On the Mac with Apple's method, on the Linux machine with NVIDIA's. Which method actually ran was read from lines only that method prints, or from which reference picture came out, not assumed.
- **The scene's own device setting travels in the file; the technology does not.** A file saved asking for the card read back asking for the card whichever configuration opened it, and the technology read back as whatever that configuration held.
- **Both halves of the preference are needed for a card render with no argument.** The technology chosen **and** the card ticked under it **and** the scene set to the card put the work on the card. The technology chosen with no device ticked rendered on the processor instead, with the scene still asking for the card.
- **No version offers a command-line option for the three hardware ray-tracing switches**, and every version's Cycles defines exactly two options of its own. But **all six of the settings can be assigned from a script in a run with no window, and read back at the assigned value** — the technology, MetalRT, HIP RT, Embree on GPU, Kernel Optimization and Distribute Memory Across Devices — and MetalRT and Kernel Optimization were then shown to change what the render did, so the assignment is not merely accepted and ignored.

**What that preferences page looks like on screen.** On the Linux machine, with a display server added for the test, it was photographed twice — once in 5.2 with OptiX chosen and once in 4.5 with None chosen. It shows a row of the technologies and, under it, a tick-box for each device the chosen one offers; with None chosen the tick-box list is gone entirely. **None of the five extra settings is drawn on that page**: no MetalRT, no HIP RT, no Embree on GPU, no Kernel Optimization and no Distribute Memory Across Devices. **On the Mac it was photographed in 5.3 alone.** With Metal chosen: a row of two buttons, None and Metal; a tick-box for Apple's graphics, ticked, and one for the processor, not ticked; then **Kernel Optimization: Full** and **MetalRT: Auto**, drawn like the rows around them and not dimmed. With None chosen: the two buttons and nothing else — no tick-boxes, no Kernel Optimization, no MetalRT. No device carried an "(Unoptimized Performance)" label. How the earlier versions draw the two Apple-only controls was never photographed.

### What the methods are

**Five technologies and None, named in every version's manual**: CUDA and OptiX for NVIDIA cards, HIP for AMD, oneAPI for Intel, Metal for Apple. **Documented** in all five. Inside them sit three hardware ray-tracing switches, one per maker — MetalRT, which is off, on or automatic; HIP RT; and Embree on GPU — all three **documented** on every version's preferences page. Two more settings sit beside them: Kernel Optimization, which is in every version's Cycles files and in none of the four earlier versions' manuals, and Distribute Memory Across Devices, which every version's manual ties to cards joined by NVLink. 5.3's own Cycles file adds three things nobody tried: MetalRT and Kernel Optimization are shown only on Apple silicon; any hardware ray-tracing switch is dimmed when a chosen card lacks hardware ray tracing; and a device that is not optimised carries the label "(Unoptimized Performance)", with nothing saying what that means for a render.

**The list a machine offers is not built from the cards in it.** Asked directly, in 4.5 to 5.2, the Linux machine — one NVIDIA card, no AMD card, no Intel graphics — offered None, CUDA, OptiX, HIP and oneAPI, and started at None; the Mac offered None and Metal, and started at Metal, in all five versions, refusing the other four by name. What was empty on the Linux machine was the list of devices under HIP and under oneAPI, not the choice itself. **So a technology appearing on the list is no evidence the machine can use it.** Reading Cycles' own files suggests the opposite, and it is wrong.

### What choosing one rather than another changes

**What every version's documents say, and they agree.** Which cards and which operating systems each technology works on. Which features are available: path guiding on no graphics device at all, Open Shading Language only on OptiX, custom cameras only on OptiX or the processor. Which denoising can be accelerated, and that one denoiser is NVIDIA's own. That speed differs — with the manual declining outright to say by how much, and in the four earlier versions pointing at an outside resource. And that when a card's memory fills, four of the five technologies fall back to system memory, with Intel's simply not named in that sentence; every version records the omission and no version calls it a denial. **On whether two methods generally give the same pixels, every version is "not in the sources".** The curve-shape warning under question 2 is narrower than that general claim.

**The choice of method changes the picture, and how firmly that is established depends on the scene.** In every version, the same file rendered by two different methods came out different — the processor against CUDA, the processor against OptiX, CUDA against OptiX, all on the Linux machine in 4.5 to 5.2, and the processor against Apple's method and MetalRT off against on, on the Mac in all five. It is not a handful of stray pixels: in 4.5 to 5.2, on the mesh scenes between 224,257 and 230,015 of the picture's 230,400 pixels differ, and on the curve scene about 149,000 to 162,500.

What that is worth depends on how far apart two runs of the *same* method come, and that was measured at length on the Mac — a hundred and twenty pairs across 4.5 to 5.2, three scenes, five repeats each, and thirty more in 5.3.

- **On the processor these measured pairs have no difference at all.** Every one of the sixty pairs in 4.5 to 5.2 and the fifteen in 5.3 came back identical to the pixel. That establishes repeatability for those processor renders on this Mac.
- **On a card the floor is not one number.** In 4.5 to 5.2, fifty-eight of the sixty pairs sat between about three and six ten-millionths of a channel value; the other two — about one card pair in thirty, one in each of two versions — came back at 5.3 × 10⁻⁵ and 0.0182, the second of those some forty thousand times the rest. In 5.3, fourteen of fifteen sat between about one and two ten-millionths and one — the first pair on the curve scene — came back at 0.0098.
- **On the small scene and the mesh-heavy scene the Mac's own rows are safe.** In 4.5 to 5.2 they run from 0.0103 to 0.0205 — hundreds to tens of thousands of times the worst same-method figure those scenes ever produced. In 5.3 they run from 0.0039 to 0.0088, still a thousand to tens of thousands of times every same-method pair on those scenes.
- **On the curve-heavy scene the Mac's rows are not as safe.** In 4.5 to 5.2 they run from 0.1134 to 0.1425 against a worst same-method figure of 0.0182 on that same scene — a factor of six to eight, not orders of magnitude. In 5.3 the processor against Metal came out at 0.0205 and MetalRT off against on at 0.0148, against that version's own excursion of 0.0098 on the same scene — about twice it and one and a half times it. These measured curve-scene differences are the weakest of these claims; a reader leaning on it should lean less hard, in 5.3 most of all.

**Nothing explains the high same-method pairs.** **And this long measurement is macOS and Apple's own graphics only** — the Linux machine's own same-method control was one pair per row rather than a spread, and that one pair came back between 4.17 × 10⁻⁷ and 9.54 × 10⁻⁷ on every row it was taken for. That machine no longer exists, so the NVIDIA rows above rest on a floor measured once rather than measured at length.

**The 5.3 gaps are smaller than 5.2's recorded ones, and that is not established as 5.3's.** On the same Mac, the processor against Metal came out at 0.0039, 0.0063 and 0.0205 on the small, mesh and curve scenes in 5.3, against 0.0103, 0.0185 and 0.1199 in 5.2's record; MetalRT off against on at 0.0047, 0.0088 and 0.0148, against 0.0103, 0.0205 and 0.1425. No 5.2 run was made beside these, and under Kernel Optimization below a same-day 5.2 run is seen to part from 5.2's record, so the smaller gaps may belong to the build, the operating system or the day as easily as to 5.3. **That the methods differ is the same in all five; by how much is not a version fact here.**

**What a method the machine cannot do does, and it is the same in every version tried.** Asked on the command line for a real technology the machine has no hardware for, or for a name that is not a technology at all, Blender **ends the run with a failure status and writes no file** — 4.5 to 5.2 on both machines, 5.3 on the Mac. Nothing falls back to the processor, and nothing falls back to the card that is actually there. The message says either that no device of that type was found or that the name is not a valid one. This matters to anything driving Blender from outside, because the failure status is visible to it where the device that rendered is not.

**Memory on the card moves with the method too.** On the small scene the two NVIDIA methods took much the same, with OptiX slightly the greater; on the mesh-heavy and curve-heavy scenes OptiX took less, and on the curve scene least of all. Same in 4.5 to 5.2.

**On the Mac, in 5.3, Apple's graphics against the processor in time.** Apple's graphics took about half the processor's time on the small and the curve scenes and about two-thirds of it on the heavy mesh, so the gap did not simply grow or shrink with the number of triangles. A busy Mac's times, five repeats; the earlier versions were not timed this way on the Mac.

### Whether it changes with the size of the scene — yes, sharply, and it changes direction

**The documents establish only that it varies with the scene, never how.** Every version says the ranking between technologies depends on the scene tested, that MetalRT's saving is tied to scenes using curves heavily, that cards are limited on complex scenes by their memory, and that pooling memory across NVLink-joined cards exists to make room for larger scenes. 5.3's files also carry an "extended limits" variant of the Metal kernel, with nothing saying what selects it. **No version gives a threshold, a count or a figure of any kind.** For the question in its numeric form, every version answers **not in the sources**.

**The tests answer it, on the Linux machine, in 4.5 to 5.2, three repeats of every measurement on a machine checked to be quiet.** 5.3 had no NVIDIA card and none of this was run in it.

- **At 322 triangles the two NVIDIA methods are within a tenth of a second of each other**, with CUDA marginally ahead — both under three quarters of a second against about six seconds on the processor.
- **At 10,485,762 triangles OptiX is about four times faster than CUDA** — around one and a half to two seconds against six to eight and a half. On the curve-heavy scene the gap is three to five times, the same way round.
- **At 125,829,122 triangles the choice decides whether there is a render at all.** Every OptiX run finished and wrote its frame, in all four versions. **Every CUDA run was killed by the system**, in all four versions, part-way through building the structure, with no frame written.
- **A negative result was available and did not happen.** Had the ratio between the two methods held steady across the sizes, within the spread of the repeats, the answer would have been that the effect does not depend on the size of the scene.

**The same shape shows in the ray-tracing switch, on the Mac, in all five versions.** At 322 triangles turning MetalRT on left the reported memory unchanged in 4.5 to 5.2 and raised it by 2 MB in 5.3. On the mesh-heavy scene it costs about 455 MB more, about 458 MB in 5.3. On the curve-heavy scene it saves about 34 MB, about 48 MB in 5.3 — the direction its own description promises, and the opposite of what it does on a mesh scene of comparable weight. The three scenes show that the memory effect varies with the scene; they establish no size threshold, and the 5.3 small scene already shows a 2 MB change. In 5.3 the first measured render with MetalRT on spent almost four minutes loading render kernels before its first sample, and no later one did; whether the earlier versions do the same on a first run was not recorded.

**What the huge-scene result does not say, and it is the important limit.** The condition reached was the **host machine's** memory ceiling, not the **card's**. OptiX never used more than about eight of the card's ten gigabytes and CUDA died long before it got near, so **nothing here touches what happens when a card's own memory fills**, and the fall-back to system memory every version's manual describes was never exercised.

### The differences between the versions

- **AMD hardware ray tracing starts off in 4.5 and 5.0 and on in 5.1, 5.2 and 5.3.** Read at factory settings in 4.5 to 5.2 on both machines and in 5.3 on the Mac, and 5.1's release notes state the change in so many words. The other five settings start the same in every version.
- **The oldest NVIDIA card CUDA will take was raised in 5.0.** 4.5's manual gives compute capability 3.0 and higher; 5.0's and 5.2's give 5.0 and higher, and 5.0's release notes say the minimum is now `sm_50`, about a GeForce 900 card. What 5.1's and 5.3's manuals give was never recorded, and that silence is read neither as agreement nor as a further change: the release note fixes the change at 5.0, and both come after it. **The release note is what makes this a change in Blender rather than two manuals disagreeing** — and **nobody had a card near that floor to try it on**, so what a 5.x Blender actually does with one is untested.
- **How a refused device name is printed.** 4.5 prints an `Error:` line; 5.0 to 5.3 print an `ERROR` line through their own message system. The words after that are identical, and every version ends the run the same way with no file. On the Linux machine, asking for AMD's method with no AMD card also draws a warning about the AMD library in 5.0, 5.1 and 5.2 and not in 4.5.
- **The default drawing backend on Windows and Linux** — see the other reading, below.
- **5.3 adds support for NVIDIA RTX Spark devices running Windows 11, "including unified memory optimizations"**, by its release notes, which also record unspecified "various GPU render optimizations". Nobody tried either.

**Not established: the NVIDIA driver a render needs.** The manuals of 4.5, 5.0 and 5.2 say OptiX needs a driver of at least 535; 5.3's manual says 575, and 5.3's own Cycles file sets 580 for OptiX and for CUDA; 5.1's findings do not record the line. A real rise in 5.3 is likely, but no release note in the findings records one and no NVIDIA card ran 5.3, so whether the floor moved, when, and to which of 5.3's two figures is not settled — and the two 5.3 sources disagree with each other.

**MetalRT Auto against Off is not settled in pixels.** On the Mac, Auto built the same structure as Off in every tested version; 5.3 also logged hardware ray tracing off and the same memory for both. Pixel comparisons disagree within the earlier versions. Differences above the measured same-method spread appeared in 4.5, 5.0 and 5.2 in one set of measurements, and in 5.1 alone in another, at about 0.0125 and 0.0188. A set of three hundred comparisons across 4.5–5.2 found no difference above that spread. In 5.3, seventy-five comparisons stayed within the measured Off-against-Off range. **No version-specific difference is established by these inconsistent results.**

**Kernel Optimization's effect on the picture is also not settled.** On the Mac, Full against Off gave about 0.0125 in two sets of measurements in 4.5, 5.0 and 5.2, against a same-setting spread of a few ten-millionths. In 5.1 two sets gave only that spread and one gave 0.0125. In 5.3 all thirty-six pairs of nine renders stayed at the same-setting spread; only Full logged optimised kernels, so the setting took. **5.2.2 on the same Mac, the same day, with a heavy-mesh scene built the same way, also kept every pair at that spread.** The changed reading therefore does not establish a difference between 5.2 and 5.3. The scene, build or day may account for it; which one is not established. Equivalent controls were not run in 4.5 or 5.0. Both outcomes remain part of the answer.

**The time order of Kernel Optimization's values is not established.** The earlier Mac measurements put Off slowest in 4.5–5.2. The 5.3 measurements put Full slowest and Off among the fastest. The same-day 5.2.2 times did not reproduce a clear matching order. These are busy-Mac times, and none establishes a general ranking.

### The other reading, and what the documents say about it

"A graphics card's rendering methods" can also mean the graphics interface Blender draws through — OpenGL, Vulkan or Metal — which every version documents in the same preferences section and offers as `--gpu-backend` on the command line. It governs drawing; whether it changes a finished picture is not established in any version. Tested in 4.5 to 5.2 on both machines, and in 5.3 on the Mac: **a value the operating system does not accept is named in an error and then ignored** — the render still finishes and still saves the frame, with a success status. The Linux machine takes two of the three names in 4.5 to 5.2 and the Mac takes only its own in all five; that is a fact about the operating systems and is nowhere a difference between versions. In 5.3 the Mac build's own help lists `metal` alone for that argument, where the manual lists all three.

**What does differ is the default, and only the release notes and API pages say so.** 4.5's release notes say OpenGL is still the default in 4.5, and 5.0's and 5.1's API pages give OpenGL as the default; 5.2's findings do not record it. 5.3's release notes say "Vulkan backend is now default on Windows (not ARM) and Linux", and 5.3's API page gives Vulkan. **So the default drawing backend on Windows and Linux changed in 5.3.** Nobody tried it: the Mac takes only Metal and nothing in 5.3 ran on Linux or Windows. 5.3's release notes also give a table of frame rates under OpenGL and Vulkan for seven scenes, with gaps that vary scene by scene, and say nothing about final renders or scene size.

### Wording differences, and what is established about their behaviour

**5.2's and 5.3's manuals say the Acceleration Structure panel is absent under OptiX; no earlier version's findings record that sentence.** The panel was asked directly, in 4.5 to 5.2 on both machines. On the Linux machine it goes away under exactly one crossing — OptiX chosen, the scene set to the card, and the processor not ticked beside it — and is present under every other. **The Mac cannot be asked this**: it offers only None and Metal, and under both the panel is always present, in all five versions. So that is a line two manuals carry and the others do not, over behaviour that is the same in 4.5 to 5.2 on the one machine that can show it. 5.3's own Cycles file has the panel go away under OptiX unless the processor is used as well — the same condition, read from the file — and no 5.3 run could ask it.

Four smaller wording differences sit in the same place, and nothing here can test any of them — this project has never had an AMD card, and nothing on the Mac separated ray tracing from denoising — so none is claimed as a difference in Blender. 4.5's and 5.0's manuals say denoising is accelerated on Apple silicon where 5.1's and 5.2's say ray tracing and denoising; 5.3's findings do not record the line. The AMD cards named as able to denoise on the card are the same in 4.5 and 5.0, wider in 5.1, and split by operating system in 5.2 and 5.3. 5.0's, 5.1's and 5.2's manuals carry a sentence saying AMD hardware ray tracing is available with recent drivers on Radeon RX 6000 and newer, which neither 4.5's nor 5.3's findings record. On shadow caustics, 4.5's manual says they are unsupported with HIP; 5.2's carries a narrower line about one AMD card family on Windows; 5.3's carries that same line and says shadow caustics are unsupported on HIP without hardware ray tracing. **5.2's release notes record no change at all to how a method is chosen, to which methods are offered, or to the ray-tracing switches, and 5.3's record none to how a method is chosen or to the switches.**
