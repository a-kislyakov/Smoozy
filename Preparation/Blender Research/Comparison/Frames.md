# Frames — Blender 4.5, 5.0, 5.1, 5.2 and 5.3 side by side

What a render does with the frames it is given, what it does when it is asked to stop, and what is left on disk when it does not run to the end.

## The machines behind the tests

Nine computers ran this topic's tests. A result settles only the machines and builds it names. **Every 5.3 test ran on the Creator's Mac alone.**

- **The Creator's Mac** — a MacBook Pro with an Apple M1 Pro, its own graphics and no second card, 16 GB of memory and a screen. The 4.5–5.2 tests used 4.5.12, 5.0.1, 5.1.2 and several 5.2 builds; its operating system and 5.2 build changed between tests, so timings from different sittings are not directly comparable. The 5.3 tests used **5.3.0 Beta, hash `5d8151335b6b`, built 2026-10-16, on macOS 26.6.2**, with 14-core Apple graphics through Metal. Selected controls used **5.2.2 LTS, hash `d13f752e3b9c`**, on the same Mac with the same scripts; each is named beside its result.
- **The one-card rented Linux machine** — one NVIDIA GeForce RTX 4090 and a display server. Its four versions were **4.5.12, 5.0.1, 5.1.2 and 5.2.0**. Questions 1–11.
- **The two-card rented Linux machine** — two NVIDIA GeForce RTX 4090s and no display server. Three tests under question 10.
- **The four-card rented Linux machine** — four NVIDIA GeForce RTX 4060 Ti, more memory than the two-card machine, and no display server. Two tests under question 10. **Both multi-card machines used 4.5.12 `84afd5f785f7`, 5.0.1 `a3db93c5b259`, 5.1.2 `ec6e62d40fa9` and 5.2.0 `fbe6228777e7`.** The tests changed which cards were selected; the two-card runs did not verify that both selected cards were used.
- **The RTX 5060 rented Linux machine** — one NVIDIA GeForce RTX 5060 and no display server. Question 12.
- **The Ada rented Linux machine** — two NVIDIA RTX 4000 Ada Generation cards and a display server. Questions 13 and 14.
- **The RTX 3060 rented Linux machine** — one NVIDIA GeForce RTX 3060, a display server drawn by the processor, and a processor shared with another tenant. Question 15's sixteen tests.
- **The GTX 1080 rented Linux machine** — one NVIDIA GeForce GTX 1080 and a display server drawn by the processor. Three of question 15's tests.
- **The rented Windows machine** — Windows Server 2025 Standard, four shared cores, 8 GB of memory and no graphics card. The first of question 15's sixteen tests, in **4.5.12 alone**. This is a Windows Server result, not a Windows 11 result.

## 1. Can a render that was interrupted by the computer going down be picked up from where it stopped?

**How it is known.** All five versions answer **documented** from the same manual passage, which addresses a computer turning off mid-render by name. Blender 5.0 additionally labels the second half — what happens inside the frame that was under way — **not in the sources**; 4.5, 5.1 and 5.2 record the same gap in their "not covered" notes rather than as a label, and 5.3 marks **inferred** that recovery goes only to whole frames and **not in the sources** whether a video render can be picked up at all. The hand tests were run from a terminal in 4.5 to 5.2 on both machines and in 5.3 on the Creator's Mac.

**Verdict: the same everywhere.**

Yes, if the animation was being written as separate image files. The recovery is not a resume inside a frame: it is a fresh render with Overwrite switched off, which skips the frames already on disk. All five manuals give the same instruction, and all five say nothing at all about resuming part-way through a single frame — no partial samples, no partial tiles, no checkpoint of any kind.

The nearest thing to a power cut that could be reproduced is a Blender killed outright, with no chance to tidy up. Sent at no particular moment during the rendering, with Placeholders off as Blender ships, in 4.5 to 5.2 on both machines and in 5.3 on the Mac, the kill left the finished frames whole and nothing whatsoever for the frame in flight. On the Mac the process ended at once — 0.2 seconds after the kill in the earlier four, 0.01 in 5.3 — with exit status `-9` in 5.3; on Linux the exit code was `-9` and the folder afterwards held only whole frames. **With Placeholders on, what a kill leaves for that frame is question 16's**: in 5.3 it left the frame's empty file at zero bytes, and in 4.5 to 5.2 it is not settled. **A kill aimed instead at the moment the frame's own file is being written leaves a short file at its own path. That is question 13's ground.** With the output set to a single video file instead, the same kill left a 48-byte file holding no frames, in 4.5 to 5.2 on both machines and in 5.3 on the Mac — recorded under question 5.

**What is still open, in every version and on every machine equally.** The half of this question where the operating system had not yet written a file out to the disk when the power went. That test was declined on the Mac, and the rented machines are reached over the network, so cutting the power would leave nothing to read the result from. **A reset at the kernel is as close as a machine reached over a network can come, and it was run in 4.5 to 5.2** — see question 13, where no frame's contents survived at all, including a frame that had been reported saved seconds earlier. In 5.3 only the program was ever stopped. A real power cut is out of reach on every machine this topic had. This is a silence in every version at once and is not a difference between them.

## 2. Can a render that was stopped on purpose be picked up later?

**How it is known.** All five versions answer **documented**, from the same manual sentence about a render job being cancelled and resumed at the last rendered frame by changing the frame range. 4.5 to 5.2 call the Overwrite route documented as well; 5.3 marks it **inferred**, joining the manual's "resume rendering where you left off" to the Overwrite hint, and marks **not in the sources** whether a stopped video render can be continued. The hand tests were run from a terminal in 4.5 to 5.2 on both machines, and in 5.3 on the Creator's Mac, from a terminal and inside Blender's window with Blender's own simulated events.

**Verdict: the same everywhere.**

Yes, for an animation written to image file formats, and by either of two routes: move the frame range so it starts at the last rendered frame, or leave the range alone and switch Overwrite off. Both are scene settings, so both survive into a render driven from outside the window. In 5.3 a render started again with Overwrite off, set from Blender's own Python, skipped the finished frames and carried on to the end.

All five manuals stop at "the last rendered frame" and none of them says whether the frame that was in progress when the stop arrived counts as rendered. **The tests answer it the same way in every version: it does not.** An interrupt, a polite terminate signal and an uncatchable kill, each sent at no particular moment during the rendering, with Placeholders off as Blender ships, left exactly the finished frames and nothing for the one in flight — in 4.5 to 5.2 on the Mac and again on the one-card Linux machine, and in 5.3 on the Mac. The three stops gave exit codes `1`, `-15` and `-9`, the same three in every version on Linux and in 5.3 on the Mac, and an interrupt printed `Sent an internal break event. Press ^C again to kill Blender` and then `Blender quit`. **With Placeholders on, what is left at that frame's path depends in 5.3 on the signal and is not settled in 4.5 to 5.2 — question 16.** In 5.3 a kill with Placeholders on left the frame's empty file, and a render started again with Overwrite off skipped that frame and left it empty.

**Inside Blender's window in 5.3**, a click on the status bar's cross, sent as Blender's own simulated event, ended the render and left the finished frames whole, and Blender's own simulated Escape did not stop the render at all — nor in 5.2.2 on the same Mac (question 15). Whether a person's Escape stops a 5.3 render is not established.

**A stop aimed instead at the moment the frame's own file is being written does leave something at that frame's path** — a short file, for a polite terminate and for an uncatchable kill, though not for an interrupt. That is question 13. It matters here, because a frame is skipped on the bare existence of a file at its path (question 4), and question 14 records a later render meeting exactly such a leftover, skipping the frame and leaving the file as it found it.

**How long the render takes to actually stop after being asked is not here.** It is not a difference between versions: question 11 holds the figures, and question 15 what settles them.

## 3. Do frames already written survive a render ending part-way, whether it was stopped on purpose or not?

**How it is known.** Blender 4.5 and 5.1 answer **documented** for both the accidental and the deliberate case. Blender 5.0 and 5.2 answer **documented** for the accidental case and mark the deliberate case **inferred**, because the manual says a job can be "resumed at the last rendered frame" without separately saying the earlier frames are still on disk. All four quote the same manual sentences. Blender 5.3 answers as 5.0 and 5.2 do — **documented** for the accidental case, **inferred** for the deliberate one — and quotes the same sentences, with the manual's wording about frames reaching the disk as 5.2's (see the documentation list at the top). The hand tests were run from a terminal in 4.5 to 5.2 on both machines, and one was run by the Creator at Blender's own window in all four of those versions on the Mac; in 5.3 they were run on the Creator's Mac, from a terminal and inside Blender's window with Blender's own simulated events.

**Verdict: it differs — but only in what Blender prints while it runs. Whether frames already written survive is the same in all five, on every machine each ran on.**

The finished frames survived every tested way of stopping the program, in every version. This does not settle a whole-machine failure; questions 1 and 13 retain that limit. An interrupt, a polite terminate and an uncatchable kill, each sent at no particular moment during the rendering, all left the finished frames at their full size and nothing at all for the frame in flight — on the Mac and again on Linux in 4.5 to 5.2, and on the Mac in 5.3, where every frame left opened as a whole picture in Blender's own loader. The Creator's own run inside Blender's window on the Mac gave the same result, in 4.5 to 5.2: two whole files after pressing Esc during frame 3, and nothing else in the folder. So the deliberate stop behaves exactly like the accidental one, which is the step 5.0, 5.2 and 5.3 had marked inferred. **In 5.3 no person pressed a key.** A click on the status bar's cross, sent as Blender's own simulated event during frame 3, left the two finished frames whole; Blender's own simulated Escape did not stop the render (question 15).

**One half of that is not settled: whether an empty reserving file is left for the frame in flight.** In 4.5 to 5.2 these runs found nothing at all for it, and **Writing 11** item 6 records the empty file left behind at zero bytes after the same kind of stop, on the same Mac, in all four versions. In 5.3 it depended on the signal. The whole of it, and what it costs, is under question 16. **What is not in doubt here is the question asked: the frames already finished survive, in every version, both ways.**

**A stop aimed at the moment a frame's own file is being written is a different case**, and what it leaves at that frame's path is question 13's answer: a short file for a terminate and for a kill, nothing short for an interrupt.

**On the one-card Linux machine a render was also started the way Blender's own Render Animation menu item starts it**, by calling the operator that item calls, in all four versions. It returned that it was running, a separate render window opened, and when the render was ended part-way the folder held only whole frames and nothing for the frame in flight. **What that does not show is an Esc cancel:** the machine's display is shared with other work and no key press could be demonstrated to land in the intended window, so this is a render that was ended rather than one that was cancelled from the keyboard. The Esc half rests on the Creator's Mac alone, for 4.5 to 5.2, and is not established for 5.3.

**What differs, and this is where the logging change is set out in full.** What the terminal shows during that run. Blender 4.5 prints only a `Saved:` line and a `Time:` line per frame, with no timestamps and no announcement of a frame before it is rendered. Blender 5.0, 5.1, 5.2 and 5.3 print `Rendering animation (frames 1..5)` first, then `Rendering frame N` before each frame, all of it timestamped and tagged `render`. Blender 5.0's release notes say the logging system was unified, that the output format changed, and that render farms parsing it may need updating; Blender 5.1's bug-fix list separately records "Show currently rendered frame in background mode", backported to 5.0.1. This is a real difference in Blender, found in the same shape on both machines in 5.0 to 5.2 and on the Mac in 5.3. Those four also print `Start rendering: Scene, ViewLayer` and a line naming the engine before each frame — that is quoted from the Mac's own runs, and the Linux runs are recorded as printing the same shape of output as the Mac. **The two machines agree here; there is no machine difference in what is printed during a plain run.** The same split turns up under questions 4, 5, 7, 8, 10, 13, 14 and 15, on other lines, and those questions name the lines they saw.

**One condition on every printed-output result in this document: the render was started from the command line**, with `-f` or `-a`. That matters, because the route decides what is printed. A render started instead by calling Blender's render operator from inside a script prints no progress line at all in 5.0, 5.1 and 5.2, while still printing its `Saved:` line, where Blender 4.5 prints its full progress by either route — settled under **Reports 9**. Whether the two lines this topic's own claim turns on, `Rendering animation (frames 1..N)` and `Rendering frame N`, survive the operator route was never asked, so nothing here says that they do or that they do not. In 5.3 a render started by the operator inside Blender's window printed its `Saved:` lines, and with Overwrite off no skipping line (question 4).

**One thing noticed in passing, which nobody asked about.** The same scene rendered by the four versions produces files of slightly different size — 94,352 bytes in 4.5, 92,406 in 5.0, 92,486 in 5.1 and 92,440 in 5.2 for the same Cycles frame on the Mac. The two machines differ too: the same fast Workbench frame came to 3,658 bytes on the Mac and 3,583 bytes on Linux in Blender 4.5. Nothing on this sheet asks about pixels and no version's findings explain the sizes. **Part of the explanation is under question 10:** an image Blender writes carries pieces of text as well as a picture, several of them times and file paths, and those differ from run to run and from machine to machine whatever the picture does. So a size difference of a few dozen bytes says nothing about the render. Nobody should read anything into these numbers beyond this: **do not compare two of Blender's images as files. Compare the picture inside them**, which is what question 10 sets out.

**Documentation only.** The 4.5, 5.0 and 5.1 manuals say animation frames “are automatically saved directly out to a drive after being rendered”; 5.2 and 5.3 say they “are typically saved directly to disk as they are rendered”. The observed result is one file saved after each finished frame in all five versions, on the machines named above.

## 4. Can Blender be asked to render only the frames that are not already on disk, and if so, how does it decide what counts as already there?

**How it is known.** All five versions answer **documented** that the Overwrite switch exists and is used for exactly this, and all five mark the decision rule itself **inferred** — the manuals say only "existing files" and never spell out the test. Blender 5.0, 5.1 and 5.2 additionally record as **observed** that Cycles' own denoise operator uses a plain file-exists check against the path a frame would be written to, and all three say plainly that this is the denoiser deciding what is on disk and not the renderer deciding what to skip. Blender 5.3 marks **not in the sources** whether anything beyond a file being there is checked, when the check is made, and whether Overwrite touches a video. The hand tests were run from a terminal in 4.5 to 5.2 on both machines, and in 5.3 on the Creator's Mac, one of them inside Blender's window.

**Verdict: it differs — but only in what Blender prints while it skips. The rule itself is the same in all five, on every machine each ran on.**

Yes: switch Overwrite off, and a frame is skipped when a file already exists at the path that frame would be written to. Everything about that rule came back identical in all five versions:

- **The test is bare existence.** A file emptied to zero bytes and left in place was skipped, and stayed at zero bytes, in every version — 4.5 to 5.2 on both machines, 5.3 on the Mac. Nothing looks at size, content or age. In 5.3 a zero-byte file, twenty bytes of text, a whole picture of the wrong size and a folder, each at a frame's name, were all skipped and left exactly as they were, down to their last-changed times; question 14 records the same five-way test for 4.5 to 5.2.
- **The path is the one the frame would be written to**, formed exactly as the manual describes. Asked what path frame 7 would take, all four versions on the Mac answered identically for every output path tried: `f_` gives `f_0007.png`, `f_##_x` gives `f_07_x.png`, `plain` gives `plain0007.png`, `six_######` gives `six_000007.png`. With File Extensions switched off the answer loses the `.png` in all four. A frame number wider than the padding is not truncated in any of them. The rented machine gave the same six answers in all four versions. 5.3 gave the same six answers on the Mac, and the files it skipped and wrote were at exactly those names.
- **The check happens once per frame, as the render reaches it** — not once at the start. Two copies of the same version, started at the same instant into one shared folder, each skipped frames that did not exist when either of them started. That held on both machines, in all four versions. **5.3 settled the same thing with one Blender instead of two**, on the Mac: a frame's file put in place while the render ran was skipped when the render reached it, and a frame's file deleted while it ran was rendered. A skipped frame took no time Blender's clock could show, where a rendered one took about 6.7 seconds.
- **Overwrite has no effect on a video output.** Rendering the same short video twice, the second time with Overwrite off, printed no skipping line, took the full rendering time and moved the file's modification time — in all four versions on both machines. 5.3 did the same on the Mac, with a two-frame MPEG-4: no skipping line, both frames rendered again, the file's last-changed time moved.

**Two things recorded for 5.3 alone, on the Mac.** `-f 1..7` honoured Overwrite off exactly as `-a` did, skipping the same frames with the same words, each item announced as a single frame. And in a render started inside Blender's window the way Render Animation starts it, with Overwrite off, the frames already there were left untouched, down to their last-changed times, and the missing ones were written — but no skipping line was printed at all. With every frame already there, 5.3's last line was `No frames rendered, skipped to not overwrite`, the report question 14 records for 4.5 to 5.2.

**Every one of those answers, and every Overwrite test on this sheet, was taken on a scene with one view.** With two views switched on, no file with that name is written at all — the files are `img_0001_L.png` and `img_0001_R.png` (*Writing 8*, *Images 5*). What the skip check tests on such a scene has never been asked, in any version.

**About two Blenders sharing a folder — and here the two machines disagree.** With Overwrite off and Placeholders on, the question is whether a placeholder reliably reserves a frame.

- **On the Creator's Mac, it did not.** The test was run twice in each version. In Blender 4.5, 5.0 and 5.1 at least one of the two runs had both copies render the same frame — frames 1 and 2 in some runs, frame 1 alone in others. In Blender 5.2 neither run's printed log shows a frame rendered twice. **Whether both copies rendered frame 1 in the first 5.1 and 5.2 Mac runs is not settled:** the reported collision conflicts with a saved line from one copy and a skipping line from the other. Neither outcome is assumed here. Either way it is a race and not a difference between versions.
- **On the one-card Linux machine it never happened at all.** Two copies were run three times in each of the four versions, twelve runs, and every one of them shared the six frames out with no frame rendered twice. Both copies exited cleanly every time.

**Both records stand and neither is chosen.** This is a race between two programs and which way it falls is not fixed. One collision is enough to show that a placeholder is a claim and not a lock, so what the Mac saw is not undone by twelve Linux runs that happened not to collide — and nothing here says a shared folder is safe on Linux. It is also **not a difference between versions**, and nothing should be built as though it were. **Question 14 ran the same arrangement far harder and found collisions on Linux as well, and in the one version this test did not collide in**, which is what a race predicts and is the reason the per-version tally above should be read as two draws rather than as a pattern. What both machines agree on is the other half: every skipped frame was one the other copy had written during the run, so the check is made per frame as the render reaches it.

Neither of this question's two machines wrote to a shared network folder — both wrote locally. **A network file system was tested too, with both renders on one machine, and it changed the answer; that is under question 14.** Two separate computers sharing one folder, which is the render-farm case the manual hints at, is untested everywhere. **5.3 ran no two Blenders at once**, so the placeholder race is untested in 5.3.

**What differs between versions.** The printed output again. Blender 4.5 writes `skipping existing frame "…"` with a small s and says nothing before the frames it skips. Blender 5.0, 5.1, 5.2 and 5.3 announce `Rendering frame N` and then write `Skipping existing frame "…"` with a capital S, timestamped. Same on both machines in 5.0 to 5.2, and on the Mac in 5.3. The frames skipped and written are the same. This is the logging change set out under question 3.

**One measurement, offered as background rather than as an answer.** In the two-Blender test on the Mac, one frame of the same 800-sample Cycles scene took 6.31 seconds in 4.5, 4.84 in 5.0, 4.79 in 5.1 and 6.01 in 5.2 with one Blender rendering alone. Nothing on this sheet asks about speed, this is one scene on one machine, and the one-card Linux machine cannot measure time at all.

## 5. What does an animation written as a single video file leave behind when the render stops part-way?

**How it is known.** All five versions answer **documented** for the warning — the manual says the file might become unplayable and that all frames would have to be rendered again from the beginning. Blender 4.5, 5.1, 5.2 and 5.3 additionally label the actual state of the file **not in the sources**; Blender 5.0 labels its answer documented and records the same gap in its "not covered" notes instead. 5.3 marks **inferred** that a stop after an Autosplit leaves more than one file. The hand tests were run from a terminal in 4.5 to 5.2 on both machines, and one was run by the Creator opening the leftover files in QuickTime Player on the Mac; in 5.3 they were run from a terminal on the Creator's Mac and every file was read back with Blender's own movie reader alone.

**Verdict: it differs — but only in what Blender prints while it encodes. What the file holds is the same in all five.**

The answer turns entirely on how the render was stopped, and it turns the same way in every version and on every machine each ran on:

- **The file exists from almost the moment the render starts**, at 48 bytes, and it did not grow while these renders ran. Its name has the whole frame range baked into it — `movie_0001-0020.mp4` — chosen before Blender knew the render would not finish. Identical in 4.5 to 5.2 on both machines, and in 5.3 on the Mac, where the file was there at 48 bytes within a second of the start and stayed at 48 bytes while three frames were appended. **Whether a video file grows through a run is not settled, and two topics disagree** — see the paragraph after this list.
- **Stopped politely, it holds the frames finished before the stop** and opens. Blender itself opened every one of them and reported a real frame count, on both machines, and QuickTime Player played each of the Mac's for about half a second. In 5.3, on the Mac, an interrupt during frame 4 of 20 left 2,427 bytes in which Blender's reader found 3 frames, the file growing once, as the process ended. QuickTime Player was not used in 5.3. So "might become unplayable" does not happen for this way of stopping, in any version, as far as Blender's own reader can tell — and in 4.5 to 5.2, as far as QuickTime on the Mac can tell. **"Politely" here does not stretch to a polite terminate, and the word is the trap.** Question 12 separated the three ways of stopping on the same kind of file and found that only an **interrupt** leaves a file with frames in it; **a polite terminate and an uncatchable kill each left 48 bytes with no frames**, in 4.5 to 5.2 on both machines and in 5.3 on the Mac, and **Writing 11** item 14 agrees on the one thing it can: its stopped video ends at 143, a terminate, and Blender's own reader will not open it as a movie. **It does not agree on the 48 bytes** — that file had grown to 1,310,720 bytes and holds 1,499 frames' worth of appends. No reader but Blender's has been put on it. This question's record does not say which signal it sent. **Read question 12 before acting on this bullet**: a terminate sent on the strength of the word *politely* leaves nothing.
- **Killed outright, everything is lost.** All five left the file at 48 bytes with no frames in it — 4.5 to 5.2 on both machines, 5.3 on the Mac — and QuickTime Player refused all four of the earlier versions' Mac files with the same message, the file name being the only thing that changed. Question 12 puts a polite terminate on this side rather than the one above.
- **With Autosplit Output switched on**, and the same interrupt below the 2 GiB boundary, every version left one file under a different name — an extra underscore and seven-digit frame numbers, `movie__0000001-0020.mp4` — that opened just as the Autosplit-off file did. Same in 4.5 to 5.2 on both machines, and in 5.3 on the Mac, where it held 2,288 bytes and 2 frames.

**Whether a video file grows while the render runs is not settled, and two topics disagree.** **Writing 11** item 14 and **Writing 14** item 8 record a video file appearing at zero bytes and growing through the run — about half its bytes on disk by the half-way frame and about nine tenths by the last one — on both their machines in all four versions. This question's twenty-frame run and question 12's, watched throughout, sat at 48 bytes until the end, and question 12 stopped a completed twenty-frame run in each of ten containers and found no file at all for one of them, 0 bytes for six, and tens or hundreds of bytes for the rest. **Both readings are of runs that were really watched, and neither can be read into the other at the sizes each used.** What no run anywhere has measured is where the line between the two falls — nothing in this project says at what frame count, frame size or container a file starts moving, and no explanation offered for it has been established. That growth happens somewhere is not in doubt, and this question's own 2 GiB test below shows it: a first file closed at more than two thousand million bytes part-way through a 170-frame run, with the render still going. Question 12's Autosplit run shows the same. **5.3 shows both kinds on one machine**: on the Mac its twenty-frame MPEG-4 sat at 48 bytes until the end, while its 3840 by 2160 lossless Matroska run below grew frame by frame, the second file at 16 and then 32 million bytes one and two frames after it appeared. **So: long runs grow, these short ones did not, and nobody has found the line.**

The number of frames each leftover file held varies a little between versions — two in 4.5 and 5.2, three in 5.0 and 5.1 on the Mac, three in 5.3 on its own scene. That is only how many frames each version happened to finish in the same twenty seconds; the versions render this scene at slightly different speeds. **It is not a difference in what an interrupted video render leaves behind.**

### The 2 GiB boundary — Linux for 4.5 to 5.2, the Mac for 5.3

**In 4.5 to 5.2 the Creator's Mac never reached this boundary**, and nothing below is established for macOS in those four. Two attempts were made there and produced 3.8 MB from a hundred frames and 4.8 MB from fifty, because Blender's own startup scene compresses to almost nothing; reaching 2 GiB that way would need tens of thousands of frames. **In 5.3 the Mac reached it**, with the same two changes as below, and nothing about 5.3 is established for Linux.

On the one-card Linux machine it was reached, in all four versions, by changing two things and nothing else: the picture was made out of high-frequency noise so the encoder has nothing to compress away, and the output was a lossless intra-frame codec — MKV with FFV1, Lossless Output on — at 3840 by 2160 pixels with one Cycles sample. That is about 16 MB a frame, which puts the boundary a hundred and twenty-odd frames away rather than tens of thousands. 5.3 used the same picture, codec, size and sample count on the Mac, over 300 frames.

**What happens, and it is the same in all five versions** — 4.5 to 5.2 on the one-card Linux machine, 5.3 on the Mac:

- **Blender closes the first file just under two thousand million bytes and opens a second.** The size at which the first file was closed: 2,032,129,255 bytes in 4.5, 2,028,653,135 in 5.0, 2,028,638,404 in 5.1, and 2,024,660,891 in 5.2. In 5.3, on the Mac, the first file stopped growing at 2,024,699,916 bytes, when frame 125 was written. All five sit **below 2 GiB** (2,147,483,648 bytes) and above two thousand million. The small spread between versions is encoded video, not a difference in where the boundary is. Nothing was printed about the split in 5.3.
- **The second file's name carries a counter in its leading digits, not the frame it starts at.** `big__0000001-0170.mkv` is followed by `big__0010001-0170.mkv`, and in 5.3 `big__0000001-0300.mkv` by `big__0010001-0300.mkv`.
- **Run to the end, nothing is lost at the join.** In 4.5 to 5.2 the render carried on into the second file and finished normally, exit code 0, leaving two files. **How the 170 frames fell between the two files was counted once only** — in Blender 4.5, where 125 frames came out of the first file and 45 out of the second, 170 between them, the whole range. The other three versions' findings do not give frame counts for the finished run, and 5.3 was not run to the end.
- **Interrupted soon after the split, the first file is whole and readable.** In 4.5 to 5.2, interrupted eight seconds after the split, it was left at exactly the size it had been closed at and opened with 125 frames. In 5.3, interrupted three frames after the second file appeared, it was left at exactly 2,024,699,916 bytes and opened with 125 frames, and the second file held 48,672,835 bytes and 3 frames. Only the file being written when the stop arrived was short.

**That last point is the one that matters to Smoozy: a long video render interrupted late has not lost everything.** Everything already closed off into a completed file survives the stop intact. The whole boundary test was repeated three times over, in Blender 4.5 and 5.2, and every figure above came back the same to the byte. **5.3's result is from the Mac and the earlier four's from Linux**: they came out the same shape, down to 125 frames in the first file, which says the boundary behaves this way on macOS in 5.3 and on Linux in 4.5 to 5.2, and nothing about macOS in the earlier four or Linux in 5.3.

**One figure did not repeat, and both runs stand.** How big the *second*, short file was after the interrupt, and how many frames it held: one run records 16,263,351 bytes with 1 frame in 4.5, and a repeat of the same procedure gave 32,520,429 bytes with 2 frames. The likely reading is that this figure depends on how much encoding fitted into the eight seconds before the stop, on a machine shared with other work — 5.0, 5.1 and 5.2 recorded around 32.4 to 32.5 MB with 2 frames, and 5.2's figures repeated exactly. No run on an otherwise idle machine settled that count. 5.3's interrupt landed three frames after the split rather than eight seconds after it, so its second file is not set beside these. **Nothing else in the entry is in doubt, and none of the points above depends on it.**

**What differs between versions: what Blender prints while it encodes.** Blender 4.5 prints `Append frame 1` and `Append frame 2`. Blender 5.3 prints `Video append frame 1`, `Video append frame 2` and so on, on the Mac, from a terminal and inside the window. What Blender 5.0, 5.1 and 5.2 print in its place is **not settled**: one run on the Creator's Mac records no such line printed at all, while a later run on the same Mac and a run on the one-card Linux machine each record `Video append frame 1`, `Video append frame 2` and so on. All those records stand and none is chosen; it may simply be that the first Mac run searched for 4.5's wording. Either way 4.5 differs from the other four, which is part of the same logging change set out under question 3. **What lands on disk is the same.**

**What is still open.** What any media player other than QuickTime on macOS makes of either file — the one-card Linux machine has no media player installed at all and installing one was not permitted, so only Blender's own reader has opened those files there. In 5.3 nothing but Blender's own reader was used, not even QuickTime, so whether 5.3's leftover files play anywhere is not established. And what Blender's own Video Sequencer makes of them, on any machine, in any version.

## 6. Is a file existing proof that the frame finished writing?

**How it is known.** Blender 4.5 and 5.2 label the answer **inferred** and the Placeholders setting **documented**. Blender 5.0 and 5.1 split it three ways: **documented** that empty placeholder files are created while frames are rendering, **inferred** that their existence is therefore not proof, and **not in the sources** for whether an ordinary frame file can be caught half-written. All four quote the same two source sentences. Blender 5.3 marks **inferred** that a file is not proof with Placeholders on and for a video, **not in the sources** whether a part-written image can sit at the final name, and **documented** the Placeholders setting and the handler that runs "directly after the frame is written". The hand tests were run from a terminal in 4.5 to 5.2 on both machines and in 5.3 on the Creator's Mac.

**Verdict: the same everywhere.**

No, and for two separate reasons, both of which came back identically in all five versions, on every machine each ran on.

**With Placeholders on**, a zero-byte file sits at exactly the path the finished frame will occupy. It is created immediately before that frame's own work begins — not all of them at the start — and the finished frame replaces it in place at the same path. Every version on every machine it ran on showed the same sequence: nothing in the folder, then `f_0001.png` at 0 bytes as frame 1 begins, then the same name at full size when frame 1 finishes, then `f_0002.png` at 0 bytes as frame 2 begins. In 5.3 the folder was listed at each of Blender's own render events, and the empty file was there at the event that starts each frame and not before.

**With Placeholders off**, no file exists for the frame in progress at the moment it starts — but a file can still be caught part-written, so a non-zero size proves nothing either. Watching a folder twenty times a second during a slow OpenEXR render, the Mac caught Blender 5.0 with the file at 5,448 bytes and then, sixty milliseconds later, at its finished 477,472 bytes. The one-card Linux machine caught **5.0 and 5.2** with the file at 0 bytes before it reached its finished size, and did not catch 4.5 or 5.1. So a frame file can be seen at a size that is not its finished size on both machines, and **which version a watcher happens to catch is a matter of luck rather than a difference between versions** — the two machines caught different sets. Every version's findings say plainly that not catching it is no evidence the file appears whole: the write is fast, not atomic, and Blender does not write to a temporary name and rename. **Question 13 watched that happening**, through more than a hundred distinct sizes at the frame's own final name and no other name at all, in all five versions.

Two more things. A render stopped at no particular moment during the rendering, with Placeholders off, leaves no file at all for the frame in flight, in every version on every machine it ran on; **with Placeholders on that is not settled in 4.5 to 5.2, and in 5.3 a terminate and a kill left the empty file while an interrupt took it away — question 16 holds the whole of it.** And a frame is skipped purely because a file exists at its path, even an empty one, in every version. **A stop aimed at the moment a frame's file is being written is the other case, and it does leave something**: a short file at the frame's own path for a polite terminate and for an uncatchable kill (question 13), and a placeholder left at 0 bytes by a killed render, which no later render fills (question 14). Both make the answer to this question sharper rather than softer.

**How reliably a placeholder reserves a frame is a separate matter, and the two machines disagree about it.** That is set out in full under question 4, and taken further under question 14. It does not change the answer here: what it settles is whether a placeholder holds a frame against another Blender, not whether a file's existence proves a frame finished.

## 7. Can Blender be given a set of frames that is not one plain run — single frames, or two separate stretches?

**How it is known.** This question carries the widest spread of labels on the sheet, all drawn from the same manual text.

- **Blender 4.5** — **documented** for a list of single frames and for a two-dot range; **inferred** for two separate stretches, the step being that the two forms can be combined.
- **Blender 5.0** — **documented** for the command-line forms and for the Frame Range panel; **not in the sources** for whether the two forms may be mixed in one argument, and for whether any other interface control offers a list.
- **Blender 5.1** — **documented** for the list and the range separately, **not in the sources** for the mixed form, and **inferred** for getting two stretches out of two render instructions in one command.
- **Blender 5.2** — the mixed form carries conflicting **documented** and **inferred** labels. The quoted help is the same; this is uncertainty about what that wording establishes in 5.2, not a difference between versions.
- **Blender 5.3** — **documented** for a list of single frames and one two-dot range, and for the Frame Range panel and the render operator offering only a start, an end and a step; **inferred** for several ranges, or ranges and single frames, in one list; **not in the sources** for any list inside the interface.

The manual sentences quoted are word for word the same in 4.5 to 5.2, and 5.3 quotes the same help for `-f`. **The spread of labels is a spread of readings, not a change in Blender's documentation and certainly not a change in Blender.** The hand tests were run from a terminal in 4.5 to 5.2 on both machines, and one was run by the Creator at Blender's window in those four versions on the Mac; in 5.3 they were run on the Creator's Mac, from a terminal and with Blender's window open.

**Verdict: it differs — in the Python render operator's arguments, in the names of the viewport-render menu items, and in what Blender prints. What you can hand a render is the same in all five.**

Yes, from the command line, identically in every version — 4.5 to 5.2 **on both machines**, 5.3 on the Mac:

- **A comma-separated list of single frames works**, and is rendered in the order written rather than sorted. `-f 5,1,9` gave 5, then 1, then 9, in all five. In 5.3 `-f 5,1,3..4,2` gave 5, 1, 3, 4, 2.
- **A two-dot range works**, and both ends are rendered.
- **The two forms can be mixed in one argument.** `-f 1..3,10..12` was accepted with no error and wrote all six files in all four versions on both machines. It did the same in 5.3 on the Mac. This settles the label that 4.5 and 5.3 called inferred, that 5.0 and 5.1 called not in the sources, and that 5.2's own documents could not agree on.
- **A repeated frame is rendered twice**, over the same file, in all five. Duplicates are neither rejected nor collapsed.
- **A malformed list is refused, nothing is rendered, and Blender still exits with the code 0** — in all five versions, with the same three messages, word for word: `Error: incorrect comma use`, `Warning: negative range ignored`, `Error: not a number`. In 5.3 a list ending in a comma was refused the same way, with nothing rendered and the code 0.
- **Each item of a list is its own single-frame render** in Blender 5.0, 5.1, 5.2 and 5.3, which announce `Rendering single frame` before each one. Blender 4.5 prints no such announcement. **The frames written are the same in all five**, which is what the question asks. Whether the Step setting has anything to act on in a list is tested, and is among the results below that no version has on both machines.
- **The same list behaves identically with Blender's window open**, in 4.5 to 5.2 on both machines and in 5.3 on the Mac, where `-f 1..3,10..12` without `-b` printed the same lines and wrote the same six files.
- **Two separate stretches also come out of two render instructions in one command.** `-s 1 -e 2 -a -s 20 -e 21 -a` wrote four files in every version, 4.5 to 5.2 on both machines and 5.3 on the Mac.
- **The tested engines gave the same order.** The same list gave the same order under Workbench and under Cycles. The Mac tried this in 5.1, 5.2 and 5.3 — in 5.3 under Cycles and EEVEE as well; the one-card Linux machine ran it in 4.5 to 5.2. The tested graphics card gave the same order as the processor on each machine: the same list on the one-card Linux machine's NVIDIA card, through OPTIX with the processor switched off, gave the same order in 4.5 to 5.2, and on the Mac's own graphics, through Metal, gave the same order in 5.3. Two machines and two makes, so this says nothing about Apple's graphics in the earlier four or NVIDIA's in 5.3.
- **A list of five thousand frames is accepted** and renders in all five — 5,000 files in 28 seconds in 5.3 on the Mac. A list of two hundred thousand never reaches Blender at all — the shell refuses it first. **The limit is the operating system's, not Blender's**, which the two machines demonstrate between them: macOS said `argument list too long` and returned 127, and Linux said `Argument list too long` and returned 126. Same in every version on each machine it ran on, 5.3 on the Mac giving 127.
- **The keyframes-only playblast cannot be reached without a window.** 4.5 to 5.2 refused it with the same message, on both machines, and 5.3 refused it on the Mac with `Error: Cannot use OpenGL render in background mode (no opengl context)`.
- **Inside Blender's window there is no route to a list.** The Frame Range panel holds Frame Start, End, Step and a Time Stretching section, and nothing else — the same in all five. The Creator confirmed this on the Mac and it was photographed on the one-card Linux machine in 4.5 to 5.2, and photographed on the Mac in 5.3.

**The keyframes-only playblast with a window, and one comparison that should not be relied on.** In all five versions — 4.5 to 5.2 on both machines, 5.3 on the Mac — a six-frame range with keys on only two frames produced **six files**. So it picks a scattered set of frames to *render* and still writes a full set of *files*, everywhere. In 4.5 to 5.2 the six were all the same size as one another. The Creator, looking at them on the Mac, reported the six files identical. On the one-card Linux machine the six were compared as *files*, and no two of the fifteen pairs matched, while every file was the same size and they looked like the same picture.

**That second comparison should not be relied on.** Question 10 establishes that Blender writes times into every image it saves which change from run to run whatever the picture does, so two files differing tells you almost nothing. In 4.5, 5.0 and 5.1 the six files were never compared picture against picture, so **nothing here says their pictures differ** and nothing says the Creator was wrong.

**In 5.3 they were compared picture against picture, and so were 5.2.2's**, on the Mac, with one script that keyed the cube's height at frame 3 and at frame 5 to two different values, the cube selected. In 5.3 the six files held **two pictures**: frames 1 to 4 one, frames 5 and 6 the other, differing in 111,164 values by up to 0.596; no two of the six files were the same byte for byte, and they came in two sizes. Blender 5.2.2 gave the same two pictures, frames 1 to 4 and 5 and 6. The `Saved:` lines came out of order in both — 1, 3, 2, 6, 4, 5 in 5.3 and 2, 6, 5, 1, 4, 3 in 5.2.2, one run each. Whether the earlier scenes keyed two different positions is not recorded, so this does not say the earlier six were not one picture; it says that on this script each skipped frame carries a keyed frame's picture, in 5.2.2 and 5.3 on the Mac.

**Five things run for 4.5 to 5.2 on the one-card Linux machine only, and for 5.3 on the Creator's Mac only.** All five came back the same in every version, so none of them is a version difference either; but no version has both machines, so none is established for macOS in 4.5 to 5.2 or for Linux in 5.3:

- **`-f` may be given twice in one command**, and both stretches are rendered — `-f 1..3 -f 10..12` wrote six files.
- **`-f` and `-a` may be mixed in one command.** `-s 1 -e 2 -a -f 20` carried out both, writing frames 1, 2 and 20.
- **Step has no effect on a frame list.** With the scene's step set to 3, `-f 1,2,3,4,5` wrote all five files. This is the thing three versions had reasoned their way to from the `Rendering single frame` announcement; it is tested in all five, 4.5 included, which had neither the announcement nor the reasoning. In 5.3 `-j 4 -f 1..10` wrote all ten as well.
- **Whitespace inside a list is accepted.** `-f "1, 2, 3"` rendered frames 1, 2 and 3, even though the manual says "no spaces". That says what these machines took, not that the manual is wrong about what is supported.
- **The alternative playback range does not change what a real render writes** — recorded under question 8, since that is where the range belongs.

**A gap in the record rather than in Blender.** Blender 5.0's, 5.1's and 5.2's findings quote a manual passage describing the keyframes-only playblast and stating that the skipped frames are still written as repeats of the last one rendered. Blender 4.5's and 5.3's findings do not quote any such passage, and do not say whether their manuals carry it. Whether those manuals lack the passage is not established, so it belongs in neither list at the top. **The behaviour is the same in all five** — six files every time, in every version, on every machine each ran on.

**What differs between versions.** Three things, none of them changing what can be rendered:

1. **The Python render operator's arguments.** In Blender 4.5 the operator takes no frame range: `bpy.ops.render.render(*, animation=False, write_still=False, use_viewport=False, layer='', scene='')`. From 5.0 on it takes `frame_start` and `frame_end`, and Blender 5.0's release notes say so in as many words; 5.3's own Python reference lists the same two. Blender 5.0's corrective-release notes then record a fix in 5.0.1 for that operator using the wrong frame range. So a script wanting two stretches must set the scene's range between calls in 4.5, and may pass them straight to the operator from 5.0 on.
2. **The names of the viewport-render menu items.** Blender 4.5's 3D Viewport View menu reads *Viewport Render Image*, *Viewport Render Animation*, *Viewport Render Keyframes*. Blender 5.0, 5.1, 5.2 and 5.3 read *Render Viewport Preview*, *Render Playblast*, *Render Playblast on Keyframes* — 5.3's read off a photograph of the menu on the Mac. The tooltip and the operator behind them are the same in 4.5 to 5.2, and so is what they do; in 5.3 no tooltip showed for Blender's simulated pointer, so its words were not read. Only the names differ.
3. **What Blender prints**, set out under question 3.

**What is still open on every machine.** Which frames the keyframes-only playblast picks when nothing at all is selected. It was run with the cube selected everywhere, in every version.

## 8. What does a frame range consist of?

**How it is known.** All five versions answer **documented**: three numbers, Frame Start, End and Step, with both ends of the range included. Blender 5.0 marks one narrow step **inferred** — that the scene's range is always end-inclusive, since the "(inclusive)" wording comes from the command-line argument's description rather than from the panel. Blender 5.3 marks **inferred** which frames a step above 1 picks, and **not in the sources** whether the end frame is rendered when the steps miss it and what a step of 0 does. The hand tests were run from a terminal in 4.5 to 5.2 on both machines, and one was run by the Creator at Blender's window on the Mac; in 5.3 they were run on the Creator's Mac, from a terminal and in Blender's window with Blender's own simulated events.

**Verdict: it differs — in what Blender prints for a step of 0 and for a stepped run, in how the manual describes Step, and in Blender 5.2 crashing when the Frame Range panel is opened by name, where 4.5, 5.0 and 5.1 on Linux and 5.3 on the Mac do not. What a frame range is, and what a stepped run renders, are the same in all five.**

A frame range is three numbers: a first frame, a last frame, and how far the render moves on after each frame it renders. All three are scene settings, and all three have command-line equivalents. The panel that holds them also holds Time Stretching, which every version's manual is explicit does not change the start or end frames — so it is not part of the range.

Everything tested came back identical in all five versions — 4.5 to 5.2 on both machines, 5.3 on the Mac:

- **A step that lands on the end frame renders it.** Start 1, end 10, step 3 gave frames 1, 4, 7 and 10.
- **A step that overshoots does not reach back for the end frame.** Start 3, end 12, step 4 gave 3, 7 and 11. Frame 12 was not rendered. So a stepped run walks forward from the start frame and stops at the last frame at or below the end.
- **A step of 0 is accepted, reads back as 0, and writes the first frame once.** No version hung, and all five ended on their own, leaving one file. The exit code 0 is recorded for 5.0, 5.1, 5.2 and 5.3; 4.5's Mac findings record that it stopped by itself but do not record the code.
- **The panel accepts a step of 0 too**, and shows it, with no error or warning. The Creator typed it into 4.5 to 5.2 on the Mac and reported no visible difference between them; on the one-card Linux machine the panel was photographed in those four versions with the step set to 0 from Python, and the field reads `0` — it does not snap back to 1. In 5.3 on the Mac the field showed `0` both when the step was set from Python and when a 0 was typed into it with Blender's own simulated keys, and the scene's step read back 0.
- **The panel holds nothing else.** Photographed in 4.5 to 5.2 on the one-card Linux machine and in 5.3 on the Mac: Frame Start, End, Step and a Time Stretching section, and nothing more — on Linux the section was opened and holds Old and New. That agrees with what the Creator reported on the Mac.
- **An end below the start renders nothing at all** and exits with the code 0, in all five.

**Two things run for 4.5 to 5.2 on the one-card Linux machine only, and for 5.3 on the Creator's Mac only.** Both came back the same in every version; no version has both machines:

- **Step has no effect on a frame list.** With the scene's step set to 3, a `-f 1,2,3,4,5` list wrote all five files.
- **The alternative playback range does not change what a real render writes.** With the scene range 1 to 8 and an alternative playback range of 4 to 5 switched on, a plain animation render wrote all eight frames, and 5.0, 5.1, 5.2 and 5.3 announced `Rendering animation (frames 1..8)`. This was documented in every version as being for playback and view renders; it is tested against a final render on one machine per version.

**What differs between versions.** Three things, none of them changing what is rendered:

1. **What Blender prints for a step of 0, and for a stepped run.** Blender 5.0, 5.1, 5.2 and 5.3 announce `Rendering frame 1` four more times after writing it, once for each frame of the one-to-five range, without rendering or writing anything further. Two more details are the same version split: those four announce each frame of a stepped run once per step (`Rendering frame 4` three times over for a step of 3), and an overshooting run ends with a bare `Rendering frame 15` past the end frame, for which nothing is rendered or written. For 5.0 to 5.2 those two were recorded on the one-card Linux machine and not by the Mac run; for 5.3 they were recorded on the Mac. Blender 4.5 announces nothing at all, because it announces no frames at any time. One file is left in every version. This is the logging change set out under question 3 and no more.
2. **How the manual describes Step.** Blender 4.5 says “Controls the number of frames to advance by for each frame in the timeline.” Blender 5.0, 5.1 and 5.2 say “Controls the number of frames to advance for each frame rendered, a value above 1 skips frames. This is also used when viewing rendered animations.” Blender 5.3 carries the same first sentence. The tested frames are the same; the difference is in the wording alone.
3. **Blender 5.2 crashes when the Frame Range panel is opened by name, where 4.5, 5.0 and 5.1 on Linux and 5.3 on the Mac do not.** On the one-card Linux machine, `bpy.ops.wm.call_panel(name="RENDER_PT_frame_range")` brought Blender 5.2.0 down twice out of two attempts, printing only that it was writing a crash file and that the command had dumped core. Blender 4.5.12, 5.0.1 and 5.1.2 opened the same panel with no trouble in the same sitting on the same machine, and 5.2.0 opened the neighbouring Time Stretching panel with no trouble — so the crash is 5.2's, not the machine's or the script's. What 5.2's panel holds is therefore taken from a picture of the Properties editor rather than from a popup, and it holds the same things as the other three. **On the Creator's Mac the same call, made by one script, brought Blender 5.2.2 down, writing a crash file, while Blender 5.3 opened the panel as a popup — Frame Start 1, End 250, Step 0 and Time Stretching — carried on, and later quit normally.** So the crash is 5.2's on both operating systems, in two of its builds, while 4.5, 5.0 and 5.1 do not have it on Linux and 5.3 does not have it on the Mac; 4.5, 5.0 and 5.1 were never asked on the Mac, and 5.3 never on Linux. Nothing on this sheet depends on the crash, and nothing Smoozy does opens a panel by name; it is here because a crash is a version difference and somebody should know.

**Typing a 0 into the Step field, and what the panel header's right-click menu offers — by hand on the Mac in 4.5 to 5.2, by Blender's own simulated events on the Mac in 5.3, and not at all on Linux.** Both need a pointer put on a control, and on the one-card Linux machine's shared display no click could be shown to land in the intended window — so nothing there was allowed to rest on one, and the step was set from Python instead. On the Mac the Creator, with their own hand, reported that right-clicking the header did nothing, in 4.5 to 5.2. In 5.3 a simulated right click on the header opened a menu headed `Context Menu` holding one item, `Area`, whose submenu begins `Horizontal Split`, `Vertical Split`, `Maximize Area`; **Blender 5.2.2, given the same simulated click on the same Mac, opened the same menu.** So 5.2.2 and 5.3 agree, and what differs from the earlier report is the hand: a simulated click against a person's. Whether a person's right click on the header in 5.3 opens the menu is not established.

## 9. What does a frame write when several view layers are active on it?

**How it is known.** This is the question the sources answer worst, and they fail in different ways in different versions — which is exactly the trap this stage exists to avoid.

- **Blender 4.5** — **documented** for the surrounding pieces; **not in the sources** for what an ordinary image file actually contains when several view layers are on.
- **Blender 5.0** — **inferred** for the whole answer, joining three separate sentences to reach it.
- **Blender 5.1** — **not in the sources** for what a frame's file contains; **documented** for each surrounding quote; **inferred** for the command-line result.
- **Blender 5.2** — **documented** for the surrounding pieces; **not in the sources** for what a single-image file writes when several view layers are enabled.
- **Blender 5.3** — **mixed**: **documented** for the surrounding pieces, and that with the compositor in use the file holds the Group Output node's first image; **inferred** that each active view layer is a layer in a multi-layer file and that the Image type writes one file per frame; **not in the sources** for which view layer a single-image file holds with the compositor off, and which one the compositor's default Group Input carries.

**One version reaching an answer where three said their sources were silent is not evidence that Blender changed.** It is a difference in how much is inferred from the same surrounding facts. The hand tests were run from a terminal in 4.5 to 5.2 on both machines and in 5.3 on the Creator's Mac, and they settled it the same way everywhere.

**Verdict: it differs — in how the multi-layer route is reached and which formats are offered, in where the compositor lives and which node decides its final image, and in the default compositor tree Blender 5.3 builds. What a frame writes with an ordinary image format is the same in all five.**

With two view layers enabled that plainly show different things, and an ordinary image format, all five versions did exactly the same thing — 4.5 to 5.2 on both machines, 5.3 on the Mac:

- **One image file is written for the frame** — never one per layer.
- **No view-layer name enters the file name.** With one view the file is named from the output path and the frame number alone; where a scene has two views, a view's own ending goes in as well, after the frame number and before the extension (*Writing 8*).
- **The pixels are the first view layer's alone** — identical to the same frame rendered with only that layer enabled, and different from the same frame rendered with only the second layer enabled. In 5.3 the second comparison could not be made, because a render with only the second layer enabled crashed (below).
- **Render Single Layer changes nothing** when the render is driven from outside the window. The file written with it on is pixel-for-pixel the file written with it off, in every version on every machine it ran on. That is what every version's documented "ignored when rendering from the command line" note amounts to in practice — and it means the inference several versions recorded, that ignoring the switch yields *all* enabled view layers in the written file, does not hold for the file. Whatever is rendered, one layer's image is what lands on disk.

**The multi-layer OpenEXR route keeps both view layers in one file, in all five versions.** The written file held both layers, named, inside it — in 5.3 as two parts, `ViewLayer.Combined` and `Second.Combined`.

**With the compositor switched on — run for 4.5 to 5.2 on the one-card Linux machine only, and for 5.3 on the Creator's Mac only.** The same two view layers, rendered five ways in 4.5 to 5.2, and in 5.3 with the compositor off and on three ways, and compared pixel by pixel, gave the same answer in every version:

- **Still one image file for the frame.** Switching the compositor on does not make a second file, and no view-layer name enters the name.
- **What lands in that file is whatever the compositor's Render Layers node is set to read.** With that node on the first view layer the file is pixel-for-pixel the compositor-off file. With it moved to the second view layer the file is pixel-for-pixel the *second* layer's own image, and different from the first's — even though both view layers are enabled and the first is the active one. In 5.3 the file with the node on the second layer differed from the first layer's, and could not be checked against the second layer alone, for the crash below.
- **The tree 5.3 makes by default** — a Group Input joined to a Group Output, no Render Layers node, which is what 5.3's release notes say the default now is — put the first view layer's picture in the frame's file, value for value. That test was run in 5.3 alone, on the Mac; the earlier four were not given that tree. Whether a File Output node fed from a compositor group's own input writes a file was tested across 5.0 to 5.3 and is set out in full under question 13.

**Stopped between the two view layers — 5.3 alone, on the Mac.** With both layers on and the frame's single file written only after both had rendered, a stop while the second layer was rendering left nothing at all for the frame — PNG or multi-layer OpenEXR, interrupt or kill.

**Not settled: a render with only the second view layer enabled crashed in 5.3.** Three times, it wrote nothing and ended with exit status -11, writing a crash report. Blender 5.2.2, given the same scene by the same script on the same Mac, crashed the same way, and with both layers on wrote the same two-part multi-layer file as 5.3. 4.5 to 5.2's own runs, on scenes their own script built, rendered that layer alone and wrote its file on both machines. So the crash is not a difference between 5.2 and 5.3 on this Mac, and whether it is the scene or something else is not settled.

**What differs between versions.** Three things.

First, **how the multi-layer route is reached and what else is on offer.** Blender 4.5 has no media-type setting; the multi-layer format is simply one entry in its single file-format list. Blender 5.0, 5.1, 5.2 and 5.3 have a media-type setting, and choosing the multi-layer value narrows the file-format list to that one format. Blender 5.1 and 5.2 additionally offer AVIF as an image format, which 4.5 and 5.0 do not; **whether 5.3 offers it was not recorded in this topic's runs** — **Images 3** records AVIF in 5.3's list. **The file-format lists and the media-type setting were read off the Creator's Mac, in 4.5 to 5.2**, and the AVIF split was seen again on a rented Linux machine under question 12, so it is not a Mac-only reading. In 5.3 the media-type setting was read off the Mac, with the same three values; its file-format list was not recorded here. The one-card Linux machine reached the multi-layer route too and kept both view layers in one file there, but its runs do not list the formats on offer. **What lands on disk for an ordinary image format is the same in all five, on every machine each ran on.**

Second, **where the compositor lives.** Blender 4.5 keeps it on the scene, as a node tree holding a **Composite** node. Blender 5.0, 5.1 and 5.2 have no such scene node tree at all — asking for it raises an error — and the compositor is a node group hung on the scene's own compositing node group, which starts out empty and needs a **Group Output** node built into it. Blender 5.0's release notes record the Composite node removed and replaced by a Group Output node whose first input is used and whose other inputs are ignored, and the Linux run found exactly that arrangement in 5.0, 5.1 and 5.2 and the old one in 4.5, in one sitting. It is **observed on the one-card Linux machine only**, in all four versions, and the release note carries the 5.0 change on its own. 5.3 keeps it the same way as 5.0 to 5.2, observed on the Mac: every 5.3 test built its compositor as a node group put on the scene's compositing node group, and the operator that makes a new one in 5.3 made a Group Input joined to a Group Output. This does not change what a frame writes, which is the same in all five with the compositor off and with a Render Layers node in the compositor. Noticed on the way and belonging to the compositor's own topic rather than this one: touching the scene's old "use nodes" switch prints a warning in 5.0, 5.1 and 5.2 that it is expected to be removed in Blender 6.0, and in 5.3 setting the scene's compositing node group itself printed a warning that it is expected to be removed in Blender 6.0. No earlier version's record mentions that second warning; that is a silence, not a difference.

Third, **the default compositor tree Blender 5.3 builds** — 5.3's release notes record that the default node tree is now a Group Input connected to a Group Output with no Render Layers node, and in 5.3 on the Mac that tree writes the first view layer's picture to the frame's file; what a File Output node fed from a group input does across 5.0 to 5.3 is set out under question 13.

**What is still open, in every version and on every machine equally.** What a render started from inside Blender's own window writes when several view layers are active. Every view-layer test on every machine drove Blender from outside its window.

## 10. In what order does a render work through the frames it was given — a plain run, a run that skips frames at a fixed interval, and a list of separate frames — and what does an interruption leave behind in each case?

**How it is known.** All five versions land in the same place by slightly different routes. Blender 4.5, 5.0 and 5.1 mark the plain run's *ascending order* **inferred** rather than documented — "render frames from start to end (inclusive)" names which frames are rendered and the direction the range is described in, not the sequence they are worked through. **Blender 5.2 and 5.3 call the plain run documented**, putting their inferred step on the stepped run instead. Those are different labels for the same sentence, not evidence that the manuals or Blender changed. All five mark the stepped run's forward direction **documented** and the exact set it produces **inferred**. All five mark the order of a list of separate frames **not in the sources** — no version's documentation says anything about it at all. 5.3 also marks **inferred** what an interruption leaves in a plain run on a deliberate stop and in a stepped run, and **not in the sources** what it leaves with a list. Blender 5.1 adds an **observed** reading of Cycles' own files: Cycles holds a per-frame render call and a per-frame finish call and no loop that walks the frames, from which it infers that the choice of frames is made outside the engine. The hand tests were run from a terminal in 4.5 to 5.2 on both machines, except the one that varied the render engine, which the Mac ran in 5.1 and 5.2 only; in 5.3 they were run on the Creator's Mac, on its processor and on its own graphics, from a terminal and in Blender's window. **This is also the only question the two multi-card machines were rented for.** The two-card machine ran three tests here in all four versions, and the four-card machine ran two, one of which went further than the question asks and settled how any two of Blender's images may be compared at all. Repeated results from the four-card machine are given separately below where they disagree.

**Verdict: it differs — in printing and the engine's script name. The observed order is the same on the tested machines — with one or several cards selected in 4.5 to 5.2, and on Apple's own graphics in 5.3. What an interruption leaves is the same in all five — 4.5 to 5.2 on the Mac and on the one-card Linux machine, 5.3 on the Mac; neither multi-card machine was ever interrupted.**

- **A plain run works forward, ascending, one frame at a time.** Frames 1 to 5 came out in the order 1, 2, 3, 4, 5 in every version, on every machine it ran on, each file saved straight after its own frame.
- **A stepped run starts at the start frame and moves forward by the step**, and stops at the last frame at or below the end without reaching back for the end frame. Identical in all five, and identical whether the step was given on the command line or as the scene's own setting.
- **A list of separate frames is rendered in the order written**, not sorted, and a repeat is rendered twice. Identical in all five. This is the part every version's sources were silent on, and the same test answered it the same way everywhere.
- **The tested engines gave the same order in every version.** The Mac tried it in 5.1, 5.2 and 5.3 — in 5.3 under Cycles and EEVEE; the one-card Linux machine ran it in 4.5 to 5.2, and the same list gave the same order under Workbench and under Cycles every time.
- **The tested graphics card and processor gave the same order — NVIDIA's in 4.5 to 5.2 on Linux, Apple's in 5.3 on the Mac.** With Cycles pointed at the one-card Linux machine's NVIDIA GeForce RTX 4090 through OPTIX and the processor switched off, the same list gave the same order in 4.5 to 5.2, and an interruption left nothing for the frame in flight and printed the same break line. In 5.3, with Cycles pointed at the Mac's own graphics through Metal, `-f 5,1,9` gave 5, 1, 9; the first frame there took 184 seconds before it was saved and the next two under a second each, with nothing printed about the wait. These runs cover those devices and version/machine pairings only. They do not establish that the order is independent of card make.
- **A render started the way Blender's own Render Animation menu item starts it also works forward, ascending, one at a time — 4.5 to 5.2 on the one-card Linux machine, 5.3 on the Mac.** Six files were written in ascending order, one at a time, the same as a render driven from a terminal, in every version. This tests an inference every version's findings had recorded, that the window and the command line follow the same order. **Nothing here was driven by a click**: the operator that menu item calls was called directly, in every version — on Linux because on that machine's shared display no click could be shown to land.
- **An interruption sent at no particular moment during the rendering leaves whole frames only, in every version, on every machine it ran on.** A plain run interrupted at frame 3 left frames 1 and 2 at full size and nothing at all for frame 3; a polite terminate and an uncatchable kill left the same. That is with Placeholders off; with Placeholders on, see question 16. **A stop aimed instead at the moment a frame's own file is being written comes out differently, and both halves of that are elsewhere on this sheet**: question 13 for the short file a terminate and a kill each leave at the frame's own path, and question 14 for the 0-byte placeholder a killed render leaves behind and no later render fills. Switching Overwrite off and skipping frames does not change the order: the run still walks the range forward, passing over each frame it skips. For a video output the answer is different and is under question 5. **Every one of these runs was on a scene with one view.** `Writing 14` item 5 records that with two views the left is written and then the right, so on such a scene the frame in flight is two files, and what a stop landing between them leaves has never been tried.
- **Interrupting a list and a stepped run — 5.3 alone, on the Mac.** `-f 5,1,3..4,2` interrupted two seconds into frame 3 left frames 5 and 1 whole and nothing for 3, 4 or 2; after the interrupt Blender announced the two remaining items, `Rendering single frame`, `Rendering frame 4` and then frame 2, each reaching `Initializing` and no further, and quit. A stepped run of 1 to 10 by 3, interrupted two seconds into frame 7, left frames 1 and 4. A kill left the same files in both. No earlier version was interrupted this way.
- **Selecting more cards did not change the order in these 4.5–5.2 runs.** 5.3 never ran on more than one card. On the two-card machine a four-frame animation was rendered with both cards ticked and then with one, in all four versions: ascending, one frame at a time, both ways. **Those runs record the saved card selection, not a device list or card load proving both cards were used.** On the four-card machine the same animation was rendered four times over in each version — four cards, one card, four again, one again — and came out ascending, one frame at a time, every time. **Neither of those machines has a display server**, so both results are renders driven from outside Blender's window and neither says anything about the inside case.

**Whether a stopped render leaves the frame's empty reserving file behind is question 16's**, and the whole of it is there: not settled in 4.5 to 5.2, and in 5.3 decided by the signal.

**Whether more cards change the picture: no change was shown, and no change was ruled out.** Because two of Blender's images cannot usefully be compared as files — see below — the pictures themselves were compared, value by value, always against a control of two runs made with the same cards.

- On the **two-card** machine, of 921,600 values in one frame, between two cards and one: 57 differing in 4.5, 11 in 5.0, 17 in 5.1, 11 in 5.2. The controls ran from 8 to 14.
- On the **four-card** machine, between four cards and one: 38 in 4.5, 8 in 5.0, 17 in 5.1, 9 in 5.2, against controls of 4 to 9. The second run on the same machine gave 36, 16, 17 and 10, against controls of 13, 11, 7 and 10.
- **The largest difference in every one of those comparisons, on both machines, was one step in 255** — the smallest a picture can hold.
- **The ratio between a comparison and its control did not survive being run twice**, so nothing should be read out of one figure being larger than another. What every run agrees on is the conclusion: **nothing here shows the number of cards changing the picture, and nothing here rules it out either.** It is the same conclusion in all four versions, so it is not a difference between them.

### What Blender writes into an image, and how two renders may be compared

Observed on the four-card machine in 4.5 to 5.2. Repeated runs agree on what decides whether files match, but not on how often they do.

- **A scene at factory settings carries sixteen stamp settings, seven of them switched on. Identical in all four versions.**
- **A PNG written at those settings carries eleven pieces of text beside the picture.** Seven of them answer to the seven settings that are on — the file's name, the date, the time, the frame, the camera, the scene and how long the render took. **The other four are Cycles' own**, and **no setting on the scene removes them**. Identical in all four versions.
- **Switch all sixteen settings off and the seven go. The four stay.** Three of those four are times: how long the whole thing took, how long the rendering took, and how long the preparation took.
- **So two files of the same frame match exactly when every time written into them happens to land on the same reading, and nothing else decides it** — not the version, not the stamp settings, not the number of cards. Cycles' times are written to the hundredth of a second and the date to the second, so two quick renders one after another often land alike and two slower ones often do not. That is the statement that survived every run, in every version.
- **In every one of those pairs the picture itself was identical** — the small scene rendered fast and rendered slowly, at factory settings and with stamping off, on the processor and on the cards, in all four versions. Whenever two of those files differed, the difference was inside the text and nowhere else. **That was measured on a 64 by 64 factory cube at four samples written to PNG, and it holds for that scene and that format rather than as a general rule about the device**: on a heavier scene written as full-float OpenEXR the device does change the picture, which is settled under **What a render demands 2**. (The card comparison further up used a heavier scene and did find the picture differing by one step in 255, which is exactly why that comparison needed a control.)

**5.3, on the Creator's Mac, came out the same shape.** At factory settings two renders of one frame — Cycles, 64 by 64, 4 samples — each carried eleven pieces of text: `File`, `Date`, `Time`, `Frame`, `Camera`, `Scene`, `RenderTime` and four of Cycles' own. The two differed only in the date, a second apart, and their pictures were identical. With all sixteen stamp settings off, only the four Cycles pieces were left, and the two fast renders were the same file byte for byte; two slower ones, 256 by 256 at 400 samples, differed only in Cycles' own times, the picture again identical. One pair at each setting, so it says nothing about how often a pair matches. It is the four-card machine's mechanism on another machine and another version, and it is not set beside those figures.

**How often a pair happens to match is not settled.** Repeated runs on the same four-card machine gave different counts in every version. Neither a guaranteed match with stamping off nor a guaranteed mismatch at factory settings follows from those runs.

**The rule this produced, and it reaches past this topic: compare the picture, never the file** — and compare it only within one build. Any test anywhere that tells two renders apart by comparing files is as likely to be reading a clock as a render. Every comparison behind this rule was made inside one version. The one place a picture was compared across versions found it moving: pixel values differing in the fourth decimal place between 4.5 and the newer three (*Images 1*). No run anywhere has compared a picture between two builds and found it identical, and two point releases have never been compared at all, though this document's own machines section records one machine on 5.2.0 against another on 5.2.1.

**What differs.** What the terminal shows while all of that happens. See question 3.

**Two things noticed in passing.** First, the render engine's own name. Setting it from a script takes each version's own name and no other — `BLENDER_EEVEE_NEXT` in 4.5, `BLENDER_EEVEE` in 5.0, 5.1 and 5.2, the other name refused outright — while `-E` on the command line is accepted under both names by 5.0, 5.1 and 5.2. 5.3 lists its engines as `BLENDER_EEVEE`, `BLENDER_WORKBENCH` and `CYCLES`, and its scripts set `BLENDER_EEVEE`. **The name that works everywhere, by every route, is the version's own**, and it is settled under **Settings 13**. Second, on the one-card Linux machine, Blender 5.0, 5.1 and 5.2 print a warning that they could not open AMD's graphics library. That is Cycles looking for hardware this machine does not have, and it appears whenever something makes Cycles look at its device list — here, a script that set the device before anything rendered — rather than at every start; it does not appear in an ordinary render at factory settings in any version. Blender 4.5 prints the same message at debug level rather than as a warning, so what differs between the versions is how loudly it is said and not whether. Seen on the one-card Linux machine in 4.5 to 5.2; untested in 5.3. Nothing about frames turns on it.

## 11. Can a render be told to stop once the frame it is working on is finished, rather than the moment it is asked?

**How it is known.** All five versions answer **not in the sources**, after searching the manual, the Python API documentation, the release notes and Cycles' own files. All five record the same short list of what the sources *do* say about stopping: a cancel button on the status bar, the Esc key, a call a render engine makes on itself to test whether it should stop "regularly for responsiveness", and a handler that fires when a render job is cancelled. None of those is a deferred stop, and several versions point out that the "regularly for responsiveness" wording points the other way. 5.3 also rules out Cycles' own time limit, which limits each frame's render time and is not a request to stop the job. The hand tests were run from a terminal in 4.5 to 5.2 on both machines, and one was run by the Creator at Blender's window in those four versions on the Mac; in 5.3 they were run on the Creator's Mac, from a terminal and in Blender's window with Blender's own simulated events.

**Verdict: it differs — in the word the status bar shows while a render runs. No deferred-stop control was found in any version. In the empty-folder, Placeholders-off runs, a stop during rendering saved nothing for the frame in flight, in all five versions on their tested machines. How long a stop takes to take effect is not a difference between versions; that is set out below and settled under question 15.**

**No deferred-stop control was found** in the checked menus, command-line help or sources, in any version. Lowering the end frame from a handler was tried and did not stop the run; that does not rule out every possible script.

- **The checked window controls offer nothing of the kind.** In all five versions, the topbar's Render menu holds six items — Render Image, Render Animation, Render Audio, View Render, View Animation and a Lock Interface checkbox — and no stop, pause or finish-this-frame item at all. The Creator read that off the Mac in 4.5 to 5.2; it was photographed during a running render in those four versions on the one-card Linux machine, using Blender's own commands and no pointer; and in 5.3 it was photographed on the Mac, opened by a simulated click, with no render running. In 5.3 a simulated right click on the status bar's progress bar during a render opened a menu headed `0%` holding only `Header`, which offers to show or move the header and nothing else. The only stop there is is the status bar's cross. Its tooltip reads "Stop this job." — hovered and read in 4.5, 5.0 and 5.2 on the Mac, and photographed under the pointer on the GTX 1080 rented Linux machine in 4.5, 5.0 and 5.1 while question 15's cancel-button runs were made. So the tooltip rests on two machines across those versions; no Linux run photographed it in 5.2, where the button lit under the pointer with no tooltip showing at that instant. In 5.3 Blender's simulated pointer rested on the cross for three seconds and no tooltip showed, so 5.3's tooltip was not read.
- **The tested script route did not work in 4.5–5.2 on both machines or in 5.3 on the Mac.** Lowering the end frame the moment a frame is written — attaching a handler to Blender's own "frame written" event and setting the end frame to the frame just written — did not stop anything: all eight frames were rendered anyway in all five versions. The animation loop does not re-read the end frame as it goes. In 5.3 the command-line help, read whole, offers no such option either.
- **No frame file was written when the stop landed during rendering in these empty-folder, Placeholders-off runs**, in every version on its tested machines, by all three signals. Placeholders on or an older file already there require question 16's separate answer. With a list of frames in 5.3, the items after it were announced and not rendered (question 10). **A stop aimed instead at the moment the frame's own file is being written leaves a short file at that frame's path for a polite terminate and for an uncatchable kill, though not for an interrupt — question 13.**
- **The three ways of stopping a render with no window gave matching results across versions in these empty-folder, Placeholders-off runs.** An interrupt, a polite terminate and an uncatchable kill each stopped it and left only the finished frames, in all five versions, with the same exit codes on each machine.
- **No freeze was seen on Linux.** Blender 5.0's release notes carry a fixed bug, "Linux Freeze when force cancelling a CLI render". Twelve interrupts across the four versions on the one-card Linux machine, plus a polite terminate and a kill in each, all ended the render without hanging. **That is a record of what did not happen in those runs, not a claim that the bug is gone**, and it says nothing about a machine that is not this one.

**How long the stop took in these runs — measured on the Creator's Mac, and not a difference between versions.** The same interrupt, sent fifteen seconds into the same render, three times in each version, steady each time:

- **Blender 4.5** — 5.8, 5.6 and 5.6 seconds after the interrupt.
- **Blender 5.0** — 0.8, 0.8 and 0.8 seconds.
- **Blender 5.1** — 1.0, 1.0 and 1.0 seconds.
- **Blender 5.2** — 5.0, 5.0 and 5.0 seconds.

Those figures stand as measurements, and **they are not four versions stopping at four different speeds.** What settles the gap is where in the frame the stop lands — question 15 establishes that in all four versions on two machines, by moving the stop around inside the frame and by raising the sample count. The four versions render this scene at slightly different speeds (question 4 records one frame at 6.31 seconds in 4.5, 4.84 in 5.0, 4.79 in 5.1 and 6.01 in 5.2), so a stop sent at the same clock time lands at a different point in each version's frame, and the gap that follows is different for that reason alone. **In a run where the stop landed at the same point in the frame in every version, the four gaps came out the same** — 12.0 to 12.9 seconds on the same Mac, with a frame of about twenty-one seconds; that is question 15's first test. In 5.3 an interrupt two seconds into a frame of about 6.5 seconds ended the run 3.7 to 4.0 seconds later, three runs; that is a different scene on a Mac that ran it faster, and it is not set beside these figures.

**When the interrupt lands during the rendering, no file is written for the interrupted frame in any of the five**, so the wait costs you time, not output. An interrupt that arrives once the frame's file has begun to be written is the other case: Blender finishes the write and the frame is whole — question 13.

**On Linux the same shape holds and the figures are their own.** Three interrupts were sent in each version on the one-card Linux machine and the numbers came back scattered, because the machine was shared with other work throughout; those numbers are kept in the findings as raw output and are not offered as a measurement. Question 15 measured the gap again on the RTX 3060 rented Linux machine, in all four versions, and found no version pattern there either. **No timing on an otherwise idle Linux machine was established.**

The Creator, stopping a render inside the window in each version on the Mac, reported it the same way for all four: "Stopping isn't instant, there's a slight lag. All versions." They did not time it, and Esc pressed in a window is not the same thing as an interrupt sent to a Blender with no window, so the timings above stand on the terminal runs alone. In 5.3 no person stopped a render; a click on the status bar's cross, sent as Blender's own simulated event, had the render job stop reporting itself running 0.344 seconds later (question 15).

**What else differs: the word the status bar shows while a render runs.** Blender 4.5 shows **Render…**; Blender 5.0, 5.1, 5.2 and 5.3 show **Rendering…**. Then a progress bar with a percentage and a small cross, the same in all five. This was photographed on the one-card Linux machine in all four versions in one sitting, and photographed again during question 15's window runs on the RTX 3060 rented Linux machine, in all four versions, with the same split. The Creator's Mac reports also record `Rendering...` in 5.0, 5.1 and 5.2; for 4.5 they describe the bar and the cross without naming a word. **So the 4.5 half rests on two rented Linux machines, 5.0 to 5.2 rest on those two and on the Mac, and 5.3 rests on the Mac**, photographed during a render. In 5.3 a photograph taken just after a click on the cross showed the status bar reading `Canceling...` with the bar and the cross greyed; the earlier versions' photographs, on Linux, show the status bar emptying and record no such word, which is two machines and different moments, so it is not a difference. Nothing turns on it.

**What could not be shown on the one-card Linux machine.** Whether the Esc key reaches Blender at all. Esc was sent to that Blender's own windows and in 5.1 a further frame was written afterwards, which says the render was still going — so what the folder showed there is what a render ended by other means leaves, not a demonstrated Esc cancel. **Under question 15**, the same kind of key press stopped a render in all four versions on the RTX 3060 rented Linux machine and again in 5.1 on the GTX 1080 one, with the status bar emptying and no further frame saved, and a click on the status bar's cross stopped it in all four versions as well. The Esc half of this question therefore rests on the Creator's Mac for macOS and on those two rented machines for Linux, in 4.5 to 5.2. **In 5.3 it is not established**: Blender's own simulated Escape did not stop a render — nor in 5.2.2 on the same Mac — and no person pressed the key.

## 12. When one render writes one video and separate image files over the same frame range, what does an interruption leave if all the images have been written but the video has not finished closing?

**How it is known.** No version's documentation answers this question. Seven of the eight documents for 4.5 to 5.2 label their answer *not in the sources* outright, the eighth labels itself *mixed* and then says the same thing about the part the question actually asks, and 5.3's labels its answer *not in the sources*. All of them looked hard: none found any description of a video file being closed off at the end of a render, and none found any description of what a stopped render leaves on disk for a video. The one sentence every version's manual does carry is a warning — that rendering straight to a video is not recommended, that the file "might become unplayable" if a problem occurs while rendering, and that the remedy is to render every frame again from the beginning. That is a warning about a possible outcome, not an observed result.

What each version labelled around that gap:

- **Blender 4.5** — **not in the sources** for the answer itself. Documented beside it: that a File Output node saves an image writing to the current frame, and a whole sequence when an animation is rendered; the unplayable warning; and that Blender fires one notification for a cancelled render job and a different one for a completed one. Two steps are **inferred** — that the node's images reach the disk as the render goes rather than all at the end, and that two checkboxes drawn greyed in a screenshot are two settings that cannot be used. The premise the whole reading rests on, that the render output holds one file format at a time, is **observed**.
- **Blender 5.0** — **not in the sources** for what the interruption leaves, both for the video and for the images; **inferred** that one render can write a video and separate image files at once; **inferred** that the video is written as the render goes rather than all at the end; **documented** that the Python interface lists a separate notification for a cancelled render and for a completed one, which settles nothing about files.
- **Blender 5.1** — **not in the sources**, and **inferred** that a File Output node's images survive an interruption, since the manual makes that promise only about a render whose own output is an image sequence. Also **inferred**: the narrowing that a render's own output is one kind of media at a time. On one point the gap is put two ways within the version: the manual lists two media types for the File Output node while the underlying setting allows three, and whether the node can write a video is called **not settled** by the sources. That is one version describing how open a point is in two ways, not two versions disagreeing.
- **Blender 5.2** — **not in the sources** for the question itself; **documented** that the node writes its images to disk during the render, **inferred** that an interruption leaves them alone, **inferred** that a video file is left on disk at all (the words "might become unplayable" say what may happen to a file, not that one is there to find), and **inferred** that Autosplit would leave more than one video file.
- **Blender 5.3** — **not in the sources** for the video's state and for whether there is a distinct step of closing it; **inferred** that the node's images are on disk; **documented** that the node writes during rendering, that the render's output can be a video, and the unplayable warning.

**A version labelling a step more generously than another is not evidence that Blender changed.** What settled this question was twelve hand tests, run in 4.5 to 5.2. Four of them were run on **both machines** — the Creator's Mac and the RTX 5060 rented Linux machine — as two separate results; the other eight were run on the rented Linux machine alone. **In 5.3 the same tests, but question 12's own Autosplit run, were run on the Creator's Mac alone**, with one more of its own: a stop while the last frame's separate image was still being written.

**One thing about the reader, because every answer below depends on it.** Neither machine had a media player or any video tool on it, and 5.3's runs used none, so every video file was read back by loading it into Blender itself as a movie clip. That reader says a file loaded fine even when the file holds nothing — a 48-byte file comes back as loaded, with no frames in it and a made-up size. So every result records three separate things: whether the file exists, how many bytes it holds, and how many frames the reader found. **Nothing below says "playable"**, and nothing below says what another player would make of any of these files.

**Verdict: it differs — but only in how a video output is reached and how a File Output node is set up. What an interruption leaves is the same in all five versions, on every machine each ran on.**

### What happens, and it is the same in all five versions

Every bullet below holds in 5.3 on the Creator's Mac as well as in 4.5 to 5.2 on the machines it names, unless it says otherwise. Where 4.5 to 5.2 ran a test on the RTX 5060 machine alone and 5.3 on the Mac alone, the two came out the same shape and are two machines, not one result.

- **There is a closing step, and it is the whole of the video in these runs.** The video file is created as soon as the render starts, at **48 bytes** — within the first second on the Linux machine in three of the four versions and just over a second in the fourth — held 48 bytes for the entire render while every frame was worked through, and only then reached its full size. On the Linux machine, watched ten times a second, it reached its full size in the very same tenth of a second in which the process let go of it, in all four versions. On the Mac, watched four times a second, it was still at 48 bytes at the last look before the process ended and at its full size afterwards, in all four versions. In 5.3 the folder was listed at every one of Blender's own "frame written" events: the video stood at 48 bytes at all eight, and at its full 2,861 bytes when the render-completed notification fired. Meanwhile the File Output node's images arrive on disk one per frame as the render goes, on both machines. So the state the question describes is real: for a run this size there is a finishing step at the end, and the whole video is in it. **Whether that holds for a longer or heavier run is not settled**: **Writing 11** item 14 and **Writing 14** item 8 record a video file growing throughout, on both their machines in all four versions, and the Autosplit run below shows a file well past two thousand million bytes while this topic's own render was still going. **Where the line falls has never been measured by anybody**, and question 5 holds the whole of that disagreement.
- **The exact case the question asks about leaves a full set of images beside an empty video.** Stopping the process at the instant the last frame was written — done from inside the render itself so the moment was hit exactly, and done twice, once politely and once with an uncatchable kill — left every image on disk and a video file of 48 bytes holding no frames. **The same in 4.5 to 5.2 on both machines, and in 5.3 on the Mac for a kill and for a terminate.**
- **The last image in that case was whole.** The last image of the stopped run and the last image of a complete run were compared picture against picture, not file against file: not one colour value differed anywhere, in any version, on any machine. The two files were not the same size — nine bytes apart on Linux, eight on the Mac — which is the same lesson question 10 draws. **Compare the picture, never the file.**
- **How the render is stopped changes what is left of the video, and this is the most useful thing on this question.** Interrupted part-way, with ten of twenty images on disk: an **interrupt** — what Ctrl-C in a terminal sends — left a video file of a few thousand bytes that the reader found frames in, in 4.5 to 5.2 on both machines and in 5.3 on the Mac (3,164 bytes, 10 frames). A **polite terminate** and an **uncatchable kill** each left 48 bytes with no frames in them, in all five. Same three exit codes everywhere, on each machine. **This is the bullet that separates the three, and question 5 does not**: that question describes one of them as *stopped politely* without naming the signal, and a reader who takes the word to cover a polite terminate gets a file with nothing in it. **Writing 11** item 14 lands on this side too, its stopped video ending at 143.
- **How many frames the reader finds in an interrupted file is not a fixed number.** It was not always the same as the number of images on disk, it came back as nine on Linux and ten on the Mac for Blender 4.5, and it moved between two runs of the same signal on the same machine in the same version. **What did not move is the whole-number contrast above**, and that is what should be relied on rather than the count.
- **An interrupt arrives as a cancel; a terminate does not.** With handlers watching, an interrupt fired Blender's own render-cancelled notification in all four versions, and by the moment it fired the video file was already at its full size — a copy taken then was the same file, byte for byte, as the one left behind afterwards. So nothing reaches the video after the cancel. A polite terminate fired nothing at all and left 48 bytes. The render-completed notification never fired in any of the eight runs. **RTX 5060 rented Linux machine only, in 4.5 to 5.2**; in 5.3 on the Mac the cancelled notification fired on an interrupt with the video already at its full size, a copy taken then was the same file byte for byte, and the completed one fired in no stopped run.
- **A second run replaces the leftovers rather than adding to them.** Starting from what a kill left — a 48-byte video and ten images, the last of them cut short in Blender 4.5 and 5.0 and whole in 5.1 and 5.2 — and rendering the same range again to the end: the video was replaced, and every image was written again, including the ones the first run had already finished. **RTX 5060 rented Linux machine only, in 4.5 to 5.2**; the same in 5.3 on the Mac, every image given a new last-changed time.
- **The container changes how many bytes are left, not how many frames.** Stopped at the last frame, each of the ten containers every version offers left a different amount: no file at all for DV, 0 bytes for six of them, 36 bytes for QuickTime, 48 for MPEG-4, and about 262 for WebM. **The reader found no frames in any of them, in any version.** Two of the ten never reached the interruption at all and said why — WebM refused the codec combination and DV refused the frame width — so eight of the ten carry information and two do not; a control run to the end, in the same containers, is what shows the difference. **RTX 5060 rented Linux machine only, in 4.5 to 5.2.** 5.3 on the Mac gave the same pattern: no file for DV, 0 bytes for six, 36 for QuickTime, 48 for MPEG-4 and 264 for WebM, no frames in any, and the same two refusals — `ERROR Could not initialize streams, probably unsupported codec combination` and `ERROR Render width has to be 720 pixels for DV!`, each ending with exit status 0.
- **One render's own output cannot be a video and separate image files at once.** The file-format setting holds one value at a time and not a set of values, in all four versions, and in the three that have a media setting at all that setting holds one value too. (Blender 4.5 has no media setting — that is the version difference below.) That was the unsourced premise two versions' readings rested on, and it holds. **RTX 5060 rented Linux machine only, in 4.5 to 5.2**, and the same in 5.3 on the Mac.
- **A File Output node cannot be set to write a video, in any of the five versions.** So the other way of reading the question cannot be built at all. **RTX 5060 rented Linux machine only, in 4.5 to 5.2**, and the same in 5.3 on the Mac. This closes the point Blender 5.1's documents called "not settled".
- **Overwrite and Placeholders can both be changed with a video output in force**, in all five versions, printing the same six lines each. **RTX 5060 rented Linux machine only, in 4.5 to 5.2**, and the same in 5.3 on the Mac. This says nothing about how those two boxes are *drawn* in a panel, which needs a window and was not looked at.
- **With Autosplit on, a video file that has already been split away survives an interruption in full.** Killed the moment a second file appeared, all four versions left exactly two files: the first holding every frame that had gone into it — over two thousand of them, and over two thousand million bytes — and the second, the one being written, at 36 bytes with nothing in it. **RTX 5060 rented Linux machine only, in 4.5 to 5.2; the Creator's Mac was never asked in those four, because each run writes over two gigabytes and took between thirty and sixty-seven minutes.** The small spread between versions in how many frames fitted into the first file, 2,179 in 4.5 against 2,197 in the other three, is encoded video and not a difference in where the split falls. 5.3 reached the boundary on the Mac with a different scene and codec, under question 5, and the closed first file survived there too.
- **A stop while the last frame's separate image is still being written — 5.3 alone, on the Mac.** The File Output node's image is written before the frame goes into the video. An interrupt landing in the middle of the node's second and last image let that image finish, whole, and the process then quit without appending the frame: the video held 994,360 bytes and one frame where both images were whole. A terminate and a kill left the second image part-written and unopenable and the video at 48 bytes with no frames. Three runs of each, alike.

### The one thing three sets of runs could not agree on

**Whether the last image file on disk is whole when a render is stopped part-way is not settled, and none of the three answers is chosen between.** All three stand on the record and none has been struck.

- **The original hand tests**, one run per signal per version, **on the RTX 5060 rented Linux machine alone** — the Mac's interrupted images were not measured for size in those runs, so they do not settle this point. Blender 4.5: the kill left a 0-byte last image, the terminate and the interrupt left all ten whole. Blender 5.0: the kill and the terminate each left the last image at 155,648 bytes against a whole one of 254,253, and the interrupt left all ten whole. Blender 5.1 and 5.2: all ten whole after all three signals.
- **A repeat**, also one run per signal. On the rented Linux machine, all ten whole after every signal in every version. On the Creator's Mac, in Blender 4.5 alone, a 0-byte last image after the **terminate** — and whole images after the interrupt and after the kill.
- **A second batch**, ten runs for each signal in each version on each machine, 248 runs in all, with the signal sent within about a thousandth of a second of the image file appearing and a frame taking four to six seconds. The interrupt left the last image whole in all eighty of its runs. The terminate left it short in all eighty. The kill left it short in all eighty. On the rented Linux machine every one of the short files was exactly 0 bytes; on the Creator's Mac most were 0 bytes and the rest held a whole number of 4,096-byte blocks — 4,096, 16,384, 24,576, 40,960 or 73,728 — every one far short of a complete image. **No count of how many of the Mac's eighty were empty and how many were block-sized is given here**: the reported total conflicts with the individual run counts, so that count remains unsettled. Nothing else in this entry depends on it.

**5.3 was not run in any of these three forms**, so this disagreement is about 4.5 to 5.2 alone. What 5.3 did run sits beside it without settling it: a stop at the "frame written" moment left the last image whole after all three signals, and a stop in the middle of the image's write left it short for a terminate and a kill and whole for an interrupt.

**What all three agree on:** an interrupt has never left a short image, in any run by anybody, in any version, on any machine. **What is not fixed** is whether a terminate or a kill leaves one, and how often. **The disagreement is between the runs, not between the versions** — in the largest of the three all four versions behaved identically, and none of the three sets shows a version doing something the others do not do somewhere else. So this is not a difference between versions, and nothing version-specific should be built on it.

**Two of the results above are not in conflict, and it is easy to think they are.** The whole last image in the exact case the question asks about came from a stop made from inside the render, after that image's write had returned. The short last images here came from a signal sent from outside, within a thousandth of a second of the file first appearing. They are two different moments.

**What can be relied on either way: an image file being on disk is not proof the frame finished.** That is question 6's answer and this question agrees with it.

### What differs between versions

Two things, and neither changes what an interruption leaves.

1. **Whether there is a Media Type setting, and how a video output is reached.** Blender 4.5 has none, on the render output or on the File Output node. In 4.5 the render output's file format is set straight to FFmpeg, and a video format and a still format are each accepted one after the other. In Blender 5.0, 5.1, 5.2 and 5.3 there is a Media Type with three values — Image, Multi-Layer EXR and Video — and with it set to Video the only file format the render output will take is FFmpeg; asking for PNG comes back refused. The File Output node splits the same way: 4.5's node has no Media Type and FFmpeg is not among its file formats at all, while 5.0 to 5.3 have the setting, list Video among its three values, and refuse Video when it is set. **The same script was run unchanged in 4.5 to 5.2 on the RTX 5060 rented Linux machine**, and 5.3's own script gave the same refusals on the Mac. The outcome is identical in all five — one render's own output cannot be a video and separate image files at once, and no version's File Output node will write a video. Only the route differs. (Question 9 records the same setting from the other side, for the multi-layer route; this is the File Output node's half of it, and the refusal.)
2. **How a File Output node is set up before it will write anything.** In Blender 4.5 the node has a single folder setting and connecting an input to it was enough to make it write. In Blender 5.0, 5.1, 5.2 and 5.3 it has a directory and a file name, and it writes nothing at all until an item is added to it, its format's media type starting at Multi-Layer EXR. **Observed in 4.5 to 5.2 on the RTX 5060 rented Linux machine**, while this question's test file was being built, and in 5.3 on the Mac. What the node writes once it is set up is the same in all five. Anyone building a File Output node from a script has to do it two different ways — and from 5.3 the node may also be fed from the compositor group's own input, which 5.0 to 5.2 would not write from; that is set out under question 13. This question also met the compositor in two places — a node tree on the scene in 4.5, a compositing node group in 5.0 to 5.3 — which is question 9's ground and came out the same way here.

**Two smaller observations.** The format list printed under the Media Type in 5.1 and 5.2 carries AVIF where 4.5's and 5.0's do not, which is what question 9 already says and is seen here on the rented Linux machine as well as on the Mac; 5.3's list was not recorded in this topic's runs, and Images 3 records AVIF in it. And the leftover WebM file was 262 bytes in three versions and 264 in Blender 5.2 on Linux, and 264 in 5.3 on the Mac — one run each, in a container that never worked in this set-up whether the render was interrupted or not, and the reader found no frames in it in any version. Nothing turns on either.

**One thing noticed and not established.** In Blender 5.2 the interrupted run also printed a line saying the render was cancelled, which no other earlier version's record shows; 5.3's interrupted video runs printed one too (`Fra: 4 | Mem: 3M | Cancelled`, question 5). Nobody says whether 4.5, 5.0 and 5.1 printed it and it went unrecorded, or whether they printed nothing. It is one run, it is about words on a terminal rather than files on disk, and it is in neither list at the top.

**One thing inside Blender 4.5 that looks like a version difference and is not one.** Blender 4.5's release notes announce that a Media Type able to be Video was added to the format settings of the Render Output, the File Output node and image saving — and 4.5's own reference lists no such setting. The test then found no such setting in 4.5 at all, and found it in 5.0 to 5.3. **That is a release note disagreeing with the version it belongs to, inside one version. It is not a difference between versions, and the difference between versions is the one already stated above.**

### What is still open

- **Everything inside Blender's own window, for this question's case.** What pressing Esc or clicking the status bar's cancel button leaves when one render writes a video and images; how the Overwrite and Placeholders boxes are drawn with a video output; what the File Output node's own panel offers for Media Type. The RTX 5060 machine has no display server and the Creator ran nothing for this question, so every stop above came from outside — which is how Smoozy would ever stop a render, and the results say so rather than standing in for the in-window case. What a stop inside the window leaves of a plain video, in 5.3, is question 17's.
- **Autosplit on macOS in 4.5 to 5.2, and on Linux in 5.3**, for the reason given above.
- **Whether an audio track mixed into the video changes any of it.** No scene here had audio.
- **Anything on Windows.** The one Windows machine this topic ever had ran a test under question 15 and nothing under this question.
- **Anything on Linux in 5.3.**
- **Everything above rests on one scene and one frame rate, and — apart from the container test and the Autosplit test — on one container and one codec.** The Autosplit test stands apart in more ways than that: it used a different container and codec, a much larger picture, and the Workbench render engine rather than Cycles, because nothing else would reach two gigabytes in the time available. It is the only result here whose set-up differs from all the rest.

## 13. When a render is stopped at the exact moment it is writing a frame's own image file, what is left where it writes?

**How it is known.** All five versions answer **not in the sources**: no version's manual, Python reference or release notes describes a part-written image file, a truncated one, an empty one, or a file written under a temporary name and moved into place at the end. What sits near the gap is the same in all five — that a frame is saved after it is rendered; that saving is timed separately from rendering; that there is a moment defined as "directly after the frame is written" and a separate one for a cancelled render; and that an optional setting creates empty placeholder files while frames are rendered. One step beside that is marked **inferred**: that the placeholder sits at the frame's own path, and that it appears before the frame is rendered rather than after. That step was then watched happening, in every version. What settled the question was hand tests, most of them run in 4.5 to 5.2 on both of this question's machines and in 5.3 on the Creator's Mac, and each result below says which. **5.3's stop was placed differently.** In 4.5 to 5.2 it landed the instant the frame's file first appeared; in 5.3 it landed in the middle of a write made long on purpose — an 8,192 by 8,192 picture of fine noise that took between half a second (JPEG) and 52 seconds (16-bit PNG) to write — so 5.3's byte counts are not set beside the earlier ones.

**Verdict: it differs — but only in the machinery around the write: a setting that 5.2 has and 4.5 to 5.1 do not, the route to a multi-layer OpenEXR, how the compositor's File Output node is built and what may feed it, and what Blender prints. What is left where it writes is the same in all five versions, on every machine each ran on.**

### What is left, and it is the same in all five versions

- **Blender writes the frame straight to its final name and the file grows in place.** A three-frame render at 4096 by 4096, uncompressed OpenEXR, with the whole output folder listed every two milliseconds: the file appears at a small size and climbs through more than a hundred distinct sizes to its finished figure of about 268 million bytes. **The only names that ever appeared were the three final frame names** — no hidden name, nothing ending `.tmp` or `.part`, nothing that appeared and vanished. Same in 4.5 to 5.2 on both machines, and in 5.3 on the Mac, where the first frame climbed through 127 sizes in about 0.3 seconds. So there is no safe-write dance to rely on: the file you can see part-written is the file.
- **How the stop is delivered decides what is left, and the three ways differ from each other in the same way everywhere.** Each run was stopped at the instant the second frame's file first appeared. An **interrupt** — what Ctrl-C sends — did not cut the write at all: Blender finished the frame, printed its saved line, said `Sent an internal break event. Press ^C again to kill Blender` and quit with the code 1, and the frame was whole and opened. A **polite terminate** left a short file at the frame's own path, exit code -15, with no saved line. An **uncatchable kill** left a short file too, exit code -9. Neither of those opened. **Same in 4.5 to 5.2 on both machines, with the same three exit codes.** **And the same in 5.3 on the Mac, with the stop in the middle of a 16-bit PNG's write**: the interrupt left 170 million bytes on disk at the moment it arrived, and Blender went on writing and printed its saved line thirty seconds later, the file whole at 414,531,599 bytes and opening, exit code 1; a terminate left 172 million bytes, exit code -15, and a kill 174 million, exit code -9, no saved line and neither opening.

  **This is the case questions 1, 2, 3, 6, 10, 11 and 16 do not cover**: those stops were sent at no particular moment during the rendering, where nothing is left for the frame in flight, and this one is aimed at the write.

  **About those numbers, because another topic gives different ones for the same three signals.** **Reports 12** records the same endings as **1**, **143** and **137**, in the same versions on the same kinds of machine. **That is one event read by two instruments and not two behaviours**: the number belongs to whatever reads the ended process rather than to Blender, and no comparison in this stage records which reader took its figure. So −15 must not be set against 143, or −9 against 137, as a difference between versions, machines or operating systems. Anything reading a Blender's ending has to know which of the two readers it is.
- **The exact number of bytes a stop leaves is a race, and it is not a fact about a version or a machine.** The single figures first recorded ran from 0 bytes to some tens of thousands with no pattern by version. Ten repeats per format per version per machine, 160 runs, showed that and **fifteen of the sixteen cells came back a spread of sizes and a mixture of files that opened and files that did not**. The sixteenth is Blender 5.1's JPEG on the Creator's Mac, which came out at 0 bytes ten times out of ten, and none of the ten opened. It is the only cell that did not vary, and a cell of ten zeroes is not a version difference either — the same version's JPEG on the other machine gave 4,096 bytes three times out of ten. Two things did hold across all 160: a file of 0 bytes never opened, and a file of exactly 1,306 bytes usually opened but not always. In 5.3 the size left is simply how far into a long write the kill landed — 16.8 to 56.9 million bytes of a 59.6-million-byte JPEG, for example. **So no byte count anywhere in this answer should be read as a difference between versions.**
- **A part-written file cannot always be told from a finished one by asking whether it opens.** In 4.5 to 5.2 a stopped TIFF, and sometimes a stopped JPEG, loaded in Blender and reported the full picture size with real data. What still tells them apart is size: a whole TIFF of that scene is about 5.4 million bytes against a leftover of about 1,300. Same in all four versions on both machines. In 5.3 every one of five JPEGs cut short in the middle of the write opened as a full-size picture, with up to half its values wrong; no part-written PNG or OpenEXR opened, and a part-written multi-layer OpenEXR did not either, which says nothing for the reason given under item 2 below. **The rule to build on, in every version: never treat "it opens" as proof a frame finished.**

  **Whether a TIFF cut short in the middle of its write opens is not settled.** None of five did in 5.3, each refused with a read error. Blender 5.2.2, killed the same way on the same Mac once, left a TIFF that opened as a full picture. One run against five cannot say whether that is the version or where the kill landed, and 4.5 to 5.2's TIFFs were cut at a different moment.
- **Nothing was still being held back by the operating system.** After a kill the folder was listed at once and again sixty seconds later, and the two listings were identical, byte for byte and time for time. All four earlier versions, both machines, and 5.3 on the Mac with a cut-short OpenEXR. What is on disk at the moment of the stop is what is on disk a minute later.
- **With Placeholders on, an empty file is put at the frame's own path before that frame is rendered, one frame at a time.** The frame's file appeared at 0 bytes roughly a second before any pixels reached it, and the next frame's file did not appear until the one before it was finished. **No file ever appeared for a frame the render had not reached.** All five versions — 4.5 to 5.2 on both machines, 5.3 on the Mac. That is the step the documents marked inferred, now watched. In 5.3 a kill in the middle of the write, with Placeholders on, left the frame's file part-written, not empty.
- **The optional JPEG preview copy exists and is written after the frame it belongs to.** With that setting on and OpenEXR output, a small JPEG sat beside every EXR, and the run printed the EXR's save immediately followed by the JPEG's. All four versions, both machines. **Not established for 5.3.**
- **A Compositor File Output node writes before the render's own frame file, and a stop between the two leaves the node's file short and no frame file at all.** In a complete run the node's save is printed first, every frame, in all four versions. Stopped the instant the node's own second file appeared, the folder held that file short and unopenable and **nothing whatever at the Output panel's own path for that frame**. So the two writers do not behave alike at a stop. **Run on both machines for Blender 4.5, and on the Creator's Mac alone for 5.0, 5.1, 5.2 and 5.3**, where it came back the same shape in all four. In 5.3 the node's save was printed about twelve and a half seconds before the Output panel's, and a kill in the middle of the node's second file left it at about half its size, unopenable, and no Output-panel file for that frame.
- **Over an older finished frame, with Overwrite on, a stop in the middle of the write loses the older frame — 5.3 alone, on the Mac.** The finished file went to 0 bytes as the new write began and grew from there, and a kill left it cut short and unopenable; the older picture was gone. During the rendering, before the write begins, an older file is left alone (question 16).
- **A machine going down loses even a frame it had already reported saving.** The Ada rented Linux machine was reset at the kernel with nothing written out, the instant the second frame's file appeared. Afterwards **no frame's contents survived, in any version** — including the first frame, which had been reported saved seconds earlier. This is the one case that comes out worse than every kill above, and it is the same in all four versions. **Ada rented Linux machine only, in 4.5 to 5.2; macOS is untested, because the Creator's machine is not reset for a test, and 5.3 is untested everywhere.** This is also as close as anything got to question 1's power cut.

### An Escape sent to the window, and what a kernel reset leaves

- **An Escape key sent to Blender's own window by a tool does stop a running render, in all four versions, on Linux.** On the Ada rented Linux machine the test was run three times: the first run said the render carried on, and two later runs — the second with a control, an identical sitting in which no key was ever sent — said it stopped, Blender 4.5 holding at 30 files, 5.0 at 35, 5.1 at 38 and 5.2 at 33 while every control ran on to all forty frames. **Question 15 then ran the same act on two further Linux machines**: on the RTX 3060 machine in all four versions and again on the GTX 1080 machine in 5.1, and every one of those runs stopped the render — nothing more printed, the status bar emptied, and no `Saved:` line ever came for the frame in hand. **So it stops, and the one run that said otherwise is the odd one out.** What it leaves at the frame's own path is a separate matter and is still open, because no run of this shape was ever aimed at the instant of a frame's write. Nothing in this section was run in 5.3.
- **What a kernel reset leaves in the output folder is not settled, and both runs stand.** The first run left the folder empty in 4.5 and 5.1, left no folder at all in 5.0, and left the first frame's file present at 0 bytes in 5.2 — which reads exactly like a version difference and is not one. The second run left the folder **present and empty in all four versions**. The reading is that which directory entries survive is whatever the file system happened to have written down. **Ada rented Linux machine only.** What came out the same way both times, in every version: no frame's contents survived at all.

**Documentation only: the Output-page headings.** Blender 4.5 labels the descriptions “Overwrite” and “Placeholders” separately. In 5.0 to 5.3, “Image Sequence – Overwrite Image Multi-Layer EXR” appears above both “Overwrite existing files when rendering.” and “Create empty placeholder frames while rendering.” The API and panel distinguish the two settings. In the tested versions they remain true-or-false settings, Overwrite defaulting to true and Placeholders to false. This wording difference does not establish a change in either setting's behaviour.

### What differs between versions

Four things in the surrounding settings, setup and printing. The observed stop results above retain their stated limits.

1. **A setting that switches saving off, present in 5.2 and absent in 4.5, 5.0 and 5.1.** `RenderSettings.save_output` is absent in 4.5, 5.0 and 5.1 and present in 5.2 as a true-or-false setting starting at true, described as writing frames to disk for animation renders. Asked of Blender itself in all four versions on both machines, and announced in Blender 5.2's own release notes — "Saving render output can now be disabled." It is the only property anywhere in the render settings, in any of the four versions, whose name or description speaks of saving render output. So a script can switch a render's own saving off in 5.2, and cannot in the other three. **Whether 5.3 has it was not recorded in this topic's runs**; **Reports 1** and **The compositor 2** record it present in 5.3 and test it there. **Nothing else about what a stop leaves depends on it**, and every result under this question was measured with saving on.
2. **The route to a multi-layer OpenEXR.** In Blender 4.5 the format is chosen straight from the one file-format list. In 5.0, 5.1 and 5.2 that choice is refused — the format is not in the list at all — until the media setting is changed to the multi-layer one first. 5.3 has the same media setting and its tests set it first; this topic did not record the refusal without it. **Reports 11** records that refusal from a script in 5.3 on the Mac, and acceptance after the media type is set. Once set, all four earlier versions write one file per frame holding both view layers, at about 537 million bytes, and 5.3 wrote its multi-layer frames the same way. This is question 9's ground and it came out the same way here. **One limit of the test, in all four versions: Blender's own image loader reports no data for a *complete* multi-layer file as well as a part-written one, so for that one format the reader used here cannot tell whole from part.** That is a limit of the reader, not a finding about the file.
3. **How the compositor's File Output node is built, and what may feed it.** In Blender 4.5 it hangs on the scene's own node tree, takes a single folder setting, and names its files `Image0002.exr`. In 5.0, 5.1, 5.2 and 5.3 it hangs on the scene's compositing node group, takes a directory and a file name, has no real input until an item is added to it, and names its files `nodeImage0002.exr`. This is question 12's ground and it came out the same way here. What the node writes, and what a stop leaves of it, is the same in all five.

   **What may feed it changes in 5.3.** On the Creator's Mac the set-up was built seven times, each time with one piece left out, in 5.0, 5.1, 5.2 and 5.3. 5.0, 5.1 and 5.2 gave the same seven answers: the node needs the item, the link into it, `use_compositing` on and the group put on the scene, it does not need a Group Output — and **fed from the group's own input instead of from a Render Layers node, the File Output node wrote nothing** (while the Output panel still wrote its own frame file, whose pixels were not checked). 5.3 gave the same answers but that one: **fed from the group's input, the File Output node wrote its file.** Blender 5.2.2, given 5.3's own script on the same Mac, wrote no File Output file that way and wrote both files with the Render Layers node in place. 5.3's release notes also record the compositor's default tree as now a Group Input joined to a Group Output with no Render Layers node, and question 9 shows that tree putting the first view layer's picture in the frame's file in 5.3; what pixels the File Output node's file held in 5.3 when fed from a hand-added group input, and what a Group Input joined to a Group Output puts in the Output-panel file in 5.0 to 5.2, were not tested. Mac only, in every version; 4.5 has no node group. In 5.3 setting the scene's compositing node group also printed a warning that it is expected to be removed in Blender 6.0 (question 9).
4. **What Blender prints while it saves and while it skips.** Blender 4.5 prints `Saved: '…'` and `Time: 00:01.20 (Saving: 00:00.34)` bare, with no elapsed time and no tag; Blender 5.0, 5.1, 5.2 and 5.3 print the same two lines behind an elapsed time and the word `render`. This is the logging change set out under question 3, met on two more lines. **What lands on disk is identical.**

### What is still open

- **What a stop given inside the window leaves at the moment of the write** — whether an Escape or a click on the status bar's cross can cut a frame's own write. Both controls are known to stop a render on Linux in 4.5 to 5.2 (question 15), and the cross stopped one on the Mac in 5.3, but no run of either was ever aimed at a frame's write, so what they leave at that path is untested. **What a hand-pressed Escape leaves when it lands during the rendering is settled**, on the Creator's Mac in 4.5 to 5.2 — whole frames only, and nothing for the frame in flight; that is under question 3.
- **Anything on Windows.** One test in one version has been run on Windows and it is under question 15; nothing under this question has.
- **A real power cut, as against a reset at the kernel.** Out of reach on every machine, and the reason is under question 1.
- **Sending Escape to a window, and resetting the machine, on macOS.** Both were run on Linux alone, in 4.5 to 5.2. On macOS a tool's key press is not merely untried but refused: it needs a system security setting changed, and the refusal was checked twice.
- **Anything on Linux in 5.3**, the kernel reset included.

## 14. When two renders write into one folder and are started at the same instant, what does each of them produce, and what does the folder hold at the end?

**How it is known.** No version's documentation answers this either. All five versions' manuals carry the same short hint — that an easy way to get several machines to share the work is to set up a shared directory over a network file system, switch Overwrite off, switch Placeholders on, and start as many machines as you wish rendering to that directory — and **not one of them says what each render produces, how the work divides, what happens if two reach the same frame together, or what the folder holds at the end**. Inferences about what follows from the hint differ, which is not a change in Blender; 5.3 marks **inferred** how the recipe divides the work and **not in the sources** the same-instant case and the case on Blender's own defaults. What settled it was hand tests, run in 4.5 to 5.2 on both of this question's machines, except the network file system, which was run on the Ada rented Linux machine alone. **In 5.3 two renders were never run at once** — one Blender at a time was run on the Creator's Mac — so the question as asked has no answer in 5.3; the parts one Blender can reach were run there.

**Verdict: not established for every version.** Two renders started at once were never run in 5.3. In 4.5 to 5.2 everything below is the same in all four, on both machines, except how many path-template variables the output path substitutes and what Blender prints. The one-Blender parts were run in 5.3 as well and came out the same.

### What happens in 4.5 to 5.2, and it is the same in all four

- **On the shipped defaults, two renders started together both render every frame.** Two renders of frames 1 to 8, Overwrite on and Placeholders off, both started by one command: each printed a saved line for all eight, and the folder ended with eight files, every one of them a readable image. **No work was divided and nothing was co-ordinated.** Same in all four versions on both machines. That is the case a person hits if they simply start two renders, and no version's documentation describes it.
- **On the manual's recipe, two renders started together divide the frames between them.** With Overwrite off and Placeholders on, one run reported saving a set of frames and skipping the rest, and the other reported the exact complement. Eight files, each written once, all readable. Same in all four versions on both machines **but one**: in Blender 5.0 on the Ada rented Linux machine both runs saved frame 1, so the two lists were not exact complements and that one frame was written twice. Eight files were still there at the end and all of them opened. **That is the race counted three bullets below, and it is not a version difference** — the same collision showed in a different version, Blender 5.2, on the Creator's Mac. Which run takes which frames varies from run to run and means nothing.
- **Overwrite off skips a frame *before* rendering it, not after.** With a complete file placed by hand at one frame's name beforehand, that frame cost a thousandth of a second where its neighbours cost three to five seconds each, and the file placed by hand kept its own size and its own last-changed time. Same in all four versions on both machines. **That is the step the whole arrangement rests on, and it holds.**
- **"Already there" means a name exists, and nothing more.** Five things were put at five frames' names before a six-frame render with Overwrite off: a complete image, a file of zero bytes, nineteen bytes of text that is not an image at all, a complete image of the wrong size, and **a folder**. All five were skipped, none was touched, and only the sixth frame was rendered. Same in all four versions on both machines. **Nothing looks inside the file, and a placeholder cannot be told from a finished frame by the thing doing the skipping.** That is question 4's rule, met again from the other side.
- **The placeholder is a claim, not a lock.** The recipe was run over a single frame with both Blenders started by one command into a fresh empty folder, **thirty times per version per machine**. On a local disk both runs claimed the frame twice out of thirty in one version on the Creator's Mac and never anywhere else — **and that is a race, not a version difference**: the same collision showed in a different version in the eight-frame run on the Ada rented Linux machine. In all 240 local runs the resulting file was present and larger than zero bytes. **Question 4 records the same arrangement colliding on the Mac in three other versions and not on its own Linux machine at all**, which is the same race falling different ways and not a pattern by version or by operating system.
- **A network file system raises the collision rate sharply, in every version.** The same thirty repeats over a folder mounted over the network from the rented machine itself gave four, five or six collisions in thirty **in all four versions** — against none in thirty on the same machine's own disk. That is the arrangement the manual's own hint recommends. **Ada rented Linux machine only, and both renders were on one machine writing to a network file system, so it settles the file system and leaves two separate computers open.**
- **Two renders over overlapping but different ranges behave as the settings say they should.** One run over frames 1 to 10 and one over 6 to 15, started together. On the defaults each wrote the whole of its own range, so the overlapping five were written twice; on the recipe one saved 1 to 5 and skipped 6 to 10 while the other saved 6 to 15. Fifteen files either way, each written once on the recipe. Same in all four versions on both machines.
- **A placeholder left behind by a killed render blocks its frame for good.** A render on the recipe was killed the instant the second frame's file appeared, leaving that file at 0 bytes. Started again and run to the end, the render skipped that frame and left it at 0 bytes, unopenable. With two renders and one killed part-way, the survivor finished the rest and left the killed one's claimed frame empty in exactly the same way. Same in all four versions on both machines. **A render that dies leaves a hole no later render fills**, and that is the sharpest thing on this question. **And a render does not have to die to leave one. The machine 7** records the same hole from two copies that both finished by themselves at exit status 0, on one Linux machine in 4.5, with all forty files present and one of them empty. That test kept only the last fifteen lines of each log, and its arrangement differed from this question's in several ways at once, so nothing here says which of them matters.
- **With a video output the two settings do nothing.** Both renders wrote to one file whose name Blender built from the whole range, both appended all eight frames, and the folder ended with a single file that Blender's own movie reader read back as eight frames — the same on the defaults and on the recipe. Same in all four versions on both machines. **The reader used was Blender itself and nothing else**, neither machine having a media player, so nothing here says what another player would make of the file.
- **The two settings take when they are set from outside Blender's window.** A file saved with the shipped defaults was rendered twice, once as saved and once with the two settings changed through Blender's Python beforehand. Run again over their own folders, the first wrote over every frame while the second skipped every one and reported that no frames were rendered so as not to overwrite. Same in all four versions on both machines. **So the whole of this answer holds outside the window, which is where every result in it was measured.**

### What one Blender showed in 5.3

On the Creator's Mac, with one Blender at a time, the steps the arrangement rests on came out as they did in 4.5 to 5.2. Each is written out under question 4.

- **Overwrite off skips a frame before rendering it.** A skipped frame took no time Blender's clock could show, against about 6.7 seconds for a rendered one, and the file in place kept its size and its last-changed time.
- **"Already there" means a name exists.** A complete picture, an empty file, twenty bytes of text, a picture of the wrong size and a folder were all skipped and left untouched; only the missing frame was rendered.
- **The check is made per frame, as the render reaches it** — a frame put in place during the run was skipped, a frame removed during the run was rendered.
- **A placeholder left by a killed render blocks its frame.** Killed two seconds into frame 2 with the recipe set, the render left that frame's empty file; started again and run to the end, it skipped that frame and left it empty and unopenable.
- **The two settings take when set through Blender's Python from outside the window**, and with every frame already there the run ended `No frames rendered, skipped to not overwrite`.

What none of that says is what two renders do together. That was never run in 5.3.

### What differs between versions

Two things, and neither changes what the folder holds.

1. **How many path-template variables the output path substitutes.** Twenty-one names were put into the output path in turn and Blender was asked what path frame 1 would take, in all four versions on both machines. Blender 4.5 substituted **four** — the blend-file's name, the frames per second, and the two resolution figures — and refused the rest with `Error: Parse errors in path`. Blender 5.0, 5.1, 5.2 and 5.3 substituted **nine**, adding the blend-file's folder, two library equivalents, the scene's name and the camera's name — 5.3 asked on the Mac, refusing the other twelve, among them `pid`, `hostname`, `machine`, `user`, `run`, `uuid`, `random`, `time` and `date`, with `Unknown variable referenced in template expression`. The manuals match: 4.5's lists four and says the set will expand over time, while 5.1's lists ten. What matters for this question is what the versions have in common: **not one variable in any version identifies the machine, the process or the run**, and two runs of the same file returned identical paths for every name, in 5.3 as well. So no version offers a built-in way of keeping two renders' file names apart, and Overwrite and Placeholders are all that stand between them.
2. **What Blender prints while it skips a frame and while it appends to a video** — a small s against a capital S, and `Append frame` against `Video append frame`. That is the logging change set out under question 3, and the video line's exact shape in 5.0, 5.1 and 5.2 is the one part of it that is not settled — see question 5; 5.3 prints the capital S and `Video append frame`. **The frames written and the files left are identical in all four earlier versions**, on both machines.

### What is still open

- **Two renders at once in 5.3**, into any folder, local or shared, on the defaults or on the recipe.
- **Two separate computers writing into one shared folder**, in every version. This is the arrangement the manual's hint is actually written for, and it is the one thing about this question neither machine could answer. The two machines have no file system shared between them, and sharing one would have meant installing software on the Creator's working machine. The network file system was tested with both renders on one machine, and it changed the answer, **so the two-computer case is worth taking up the moment a shared folder exists.**
- **Any network file system but the one tested**, and any media player other than Blender itself for the video case.
- **Anything on Windows.** The one Windows machine this topic ever had ran a test under question 15 and nothing under this question.
- **Anything on Linux in 5.3.**

## 15. When a render working through a range of frames is interrupted, what does it do between the moment it is asked to stop and the moment it ends — how long does that take, what settles that, and what does it print in the meantime?

**How it is known.** All five versions answer **not in the sources** for the question as asked. No version's manual, Python reference, release notes or Cycles files puts any length on the stretch between a stop being asked for and a render ending, says what settles that length, or gives one line of what is printed during it. What sits near the gap is the same in all five: a call a render engine makes on itself to test whether it should stop, described as fast and advised to be used "regularly for responsiveness"; a handler fired on cancelling a render job, listed separately from the one for a completed render; a per-frame finishing step; a way for an engine to hand results back marked cancelled; Esc and the status bar's cancel button; and switches that suppress or add printing. Every version marks **inferred** the step from that "responsiveness" wording to what settles the delay, and every version marks **inferred** the reading that the ordinary `blender` program handles Control-C — which each of them reaches by inverting a page about Blender used as a Python module, where it says there is no such handling. 5.3 marks the same two steps **inferred**, and records as **observed** that Cycles' own Python files hand the rendering to its compiled part and hold no code for cancelling a final render. **The tests measure the delay; they do not show where the engine checks for cancellation.** What settled the question was sixteen hand tests, run in 4.5 to 5.2 on the Creator's Mac and on the RTX 3060 rented Linux machine — except the two that need Blender's own window, which ran on the Linux machine alone. Three of the sixteen were run again on the GTX 1080 rented Linux machine, two of those three in one version only, and one was run on the rented Windows machine in Blender 4.5 alone. **In 5.3 tests of those cases, and additional cases, ran on the Creator's Mac alone** — with a real terminal and the Control-C typed into it, with no terminal and a signal from outside, and with the stop sent by Blender's own process — and the window half was run there with Blender's own simulated events. 5.3's scene was built to the same description — 320 by 180, 600 samples — and rendered a frame in about 15.7 seconds on the Mac, against about 21 in the earlier four.

**Verdict: it differs — in what Blender prints as it winds down, in which handlers exist, and in how a second stop request ends it. The measured delays follow the same pattern on the tested machines; the tests do not establish the internal mechanism or a general upper bound.**

### What happens, and it is the same in all five versions

- **Blender answers the stop in words and then goes quiet.** A Control-C typed into the terminal prints `^C` and `Sent an internal break event. Press ^C again to kill Blender` within a thousandth of a second, in 4.5 to 5.2 on both machines and in 5.3 on the Mac. **Nothing whatever is printed for the whole of the stretch that follows.** The Windows machine printed the same sentence word for word in 4.5; when each line appeared there is not established, for the reason under Windows below.
- **At the end of the stretch a short burst arrives and the process goes.** Three lines for the frame in hand — a sample count, then either a `Finished` line or a second sample count, then a `Cancelled` line — then `Blender quit`, then the process is gone in the same instant, with exit status 1. Same in 4.5 to 5.2 on both machines, and in 5.3 on the Mac whenever the frame's samples ran out first. On Windows in 4.5 the burst was one `Cancelled` line, then `Blender quit`, and the same exit status. **Where the frame was cut short in 5.3** — at 2,400 samples on the processor and at 20,000 on the card — the burst was one sample line and then `Cancelled`, with no `Finished` line and no second sample line. On Linux in 4.5 to 5.2 a frame cut short printed a second sample count (`Sample 0/600`) in that place. That is two machines, so it is not a difference between versions.
- **Nothing reaches a watching program until the end either.** With every render handler the version has attached, the whole set was recorded arriving within a thousandth of a second at the very end of the stretch and not before it: in the ordinary 600-sample Cycles run, the statistics handler three times, then the cancel handler. The handlers for a frame rendered, a frame written and a render completed **never fire for the frame in hand**, in any version, on any machine. In 5.1, 5.2 and 5.3 the exit handler fires last, after the cancel handler. So a program watching Blender learns nothing at all during the wait.

  **One line of doubt, on one half of that.** This question does not record what instrument noted when each handler fired. **Reports 14** establishes that a script's own printed lines do not reach a pipe or a file at all until the run ends, though behind a real terminal the same script ticks once a second — so if these handlers recorded themselves by printing into a pipe or a file, they would appear at the end whatever time they really fired. Some of these runs used a typed Control-C at a real terminal, where the artefact does not bite. **What the doubt reaches is only the claim that the handlers fire at the end rather than throughout.** It does not touch the claim that three of them never fire at all, which is about whether and not when; and it does not touch what a watching program learns, because that program sits on the far end of the pipe either way. **Settling it costs one run in which each handler writes a clock reading instead of a printed line** — `Writing 14` shows that instrument exists. **In 5.3 that doubt is settled for the Mac**: each handler wrote the clock reading at which it fired into its own line, behind a real terminal, and every one read the end of the stretch, within a thousandth of a second of the others. It stays open for 4.5 to 5.2.
- **The frame in hand is thrown away.** No file is written for it, whole or partial, in any version — which is questions 3, 10 and 11's ground and comes out the same way here. A stop aimed instead at the moment the frame's own file is being written is question 13's case. **What these runs do not settle is the empty reserving file**, which none of them says was switched on; question 16 holds the whole of it.
- **The length of the frame range makes no difference.** Rendering frames 1 to 5 and frames 1 to 100, stopped at the same point of the same frame, gave gaps within a few tenths of a second of each other in every version on every machine — 7.19 and 7.33 seconds in 5.3 — and **no line printed after the stop ever named a frame later than the one in hand.** Nothing is being wound down for the frames not yet reached.

### What settles how long it takes

**Observed: the delay varies with the work in progress, the sample count and the device.** The reading that it is waiting for work already under way is **inferred from these tests**, not a general timing guarantee. The main Cycles timing tests used a 320 by 180 scene, without tiles; other-engine tests used a different scene, in 5.3 at 1920 by 1080. **Reports 7** establishes that past one tile's worth of area a frame is worked and printed tile by tile, and that the sample number restarts inside each tile rather than counting across the whole frame. What the wait is made of once a frame is tiled — whether “the work in hand” is then the frame or the tile — has never been tested here. The following observations are from 4.5 to 5.2 on both machines and 5.3 on the Mac:

- **Where in the frame the stop lands.** On the Creator's Mac, with a frame of about twenty-one seconds: stopped during the set-up before any sample, about twenty seconds; two seconds into the frame, about eighteen or nineteen; half way through, about seven to ten. The four versions sit within two and a half seconds of one another at every one of those moments. In 5.3, with a frame of about fifteen and a half seconds on the same Mac: during the set-up, 15.5 seconds — the whole of frame 1; two seconds into the frame, 13.7; about half way, 8.5; eight seconds in, 7.6.
- **The sample count.** Four times the samples, with the stop at the same moment, took about thirty-one to thirty-seven seconds instead of about eighteen, and in 5.3 24.5 seconds instead of 13.7. The frame was not run to its end: the last sample line before `Cancelled` read `Sample 1025/2400`, the same figure in all five versions on the Mac.
- **The render device.** With Cycles pointed at the graphics card instead of the processor, the same stop at the same 600 samples ended in a fraction of a second on the Mac — 0.2 to 1.3 seconds depending on the version — because the frame was nearly done. Raised to 20,000 samples on the card, the wait came back to twenty-six to thirty-nine seconds. On the RTX 3060 machine the card finished all five frames at 600 samples before the stop could be asked for at all, in every version. **In 5.3 the Mac's card did the same** — all five frames, about three and a half seconds each, done before the stop was due — and so did Blender 5.2.2 given the same run on the same Mac. So 5.3 against the earlier four's Mac card figures is not a difference between versions: those were taken on an older macOS and an earlier 5.2 build, with the stop timed from slower processor frames. At 20,000 samples on the card 5.3 waited 23.3 seconds, the frame cut short at sample 8,527 with no `Finished` line and nothing on disk.
- **The render engine.** EEVEE and Workbench, which render this scene in a fraction of a second, ended almost at once — 0.04 to 2.4 seconds on the Mac across the four versions, and 0.55 for EEVEE and 0.05 for Workbench in 5.3.
- **A stop landing between frames ends the run almost at once** — under a tenth of a second in every version on every machine, 0.035 seconds in 5.3, with one `Initializing` line for the frame that had just begun.
- **A stop landing during compositing — 5.3 alone, on the Mac.** With a compositor made slow on purpose, an interrupt 3.6 seconds into seven seconds of compositing ended the run 0.83 seconds later, with no `Cancelled` line, no `Saved:` line and nothing on disk for the frame.

**What does not change it:** the length of the frame range; asking for memory debugging; and switching off the abort handler. All of those matched their ordinary runs in 4.5 to 5.2 on both machines. In 5.3 the range and the abort handler matched; with memory debugging the frames ran slower, so a stop at the same clock time landed earlier in the frame and took 10.9 seconds against 7.6 — what the stop's place in the frame predicts. 5.3 also printed `Switching to fully guarded memory allocator.` as it started; Blender 5.2.2 printed the same on the same Mac, so that is not a difference between versions.

**Writing one video file instead of separate images is not settled.** It was tried once, on a five-frame render, and seven of its eight cells sat within a second and a half of their plain-image control while the eighth — 5.0 on the RTX 3060 machine — took 22.0 seconds against a control of 8.8. That machine's processor was shared, so nothing is concluded from it either way. Nothing was printed about the video or its closing in any of those runs. In 5.3 on the Mac the video run took 7.54 seconds against its plain-image control's 7.57, printed nothing about the video, and left a file of 4,954 bytes holding 2 frames. **Question 12** establishes that for a run this size the whole video is written out in a closing step, and that on an interrupt that closing happens before the process ends — so the closing is inside the wait. What it adds for a video of two or three thousand million bytes has never been measured at any size.

**What these timings say about a deadline.** They establish no constant stop time or general upper bound. In these untiled Cycles runs the wait depended on the work and the point at which the interrupt arrived. Larger tiled frames, longer video closing and untested machines need their own evidence. The longest waits seen anywhere in these runs were the EEVEE runs on the RTX 3060 machine, a machine whose display is drawn by its processor, where a frame took about ninety seconds and the stop took **sixty-five to seventy-three seconds** in the four versions. **That machine's display is drawn in software, and nothing in this stage reconciles that with the manuals' sentence that EEVEE only ever renders on the graphics card and cannot fall back to the processor** — the contradiction is written down under **The machine 2** and is not settled either way, so nothing should be read out of these figures about what EEVEE does on a card. On the same machine's ordinary Cycles frame of about thirty-seven seconds the wait was six to nine seconds, and on the Mac's twenty-one-second frame it was twelve to thirteen; in 5.3, on the Mac's fifteen-and-a-half-second frame, a stop eight seconds in took 7.6.

### The other ways of stopping, and they differ from each other rather than by version

- **A polite termination request and an uncatchable kill both end it in about two to four hundredths of a second**, with **nothing whatever added to what the render had printed.** An interrupt sent as a signal takes the full wait, exactly as a typed Control-C does. Same in 4.5 to 5.2 on both machines and in 5.3 on the Mac (0.01 seconds for a terminate and a kill, 7.7 for an interrupt), and the same for a render started detached with no terminal at all — so nothing here depends on there being a terminal to type into.
- **A second Control-C ends the process, in every version** — the first one's own line says it will. How quickly is recorded once for the earlier four: 3.1 seconds, in 4.5 on the Linux machine. In 5.3 on the Mac the process went at once on the second Control-C, typed five seconds or three tenths of a second after the first. What it prints and how the process dies is where the versions part, and that is below.

### Inside Blender's own window — Linux, in 4.5 to 5.2

- **Escape stops the render, in all four versions.** Nothing at all is printed — a render started inside the window prints only a `Saved:` line per frame, and in 4.5 a `Time:` line as well — which is what **Reports 9** records independently, and what this question's own captures show — with no per-sample lines, and after the key press no line of any kind comes and no `Saved:` line for the frame in hand ever arrives. On screen the status bar's task, wording, progress bar and cross all vanish together, the render window's header loses its `Remaining:` figure, and the timeline's current frame goes back to the start of the range. **The screen settles within about two seconds** in every version; which side of one second it falls on moved between runs of the same version and is not a difference between versions.
- **The status bar's cancel button stops the render too, in all four versions**, and the third frame was never written in any of the four runs that used it. **Six earlier attempts to click it failed**, and the reason is Blender's own Quick Setup panel, which factory startup opens and which no window list shows because it is drawn inside the main window rather than as a window of its own: it takes the first click made anywhere. **That was read off Blender 5.1's photographs**, where the picture taken immediately before the click shows the panel and the one a second later shows it gone with the cross's tooltip under the pointer. For 4.5, 5.0 and 5.2 the narrower statement is what stands on their own photographs: the first click did not arrive, and a second at the same place a moment later did. With one click spent first, the cross lit under the pointer in all four versions.
- **The render job stops reporting itself as running within a beat of the key press**, in all four versions, and asking it does not crash Blender. How long that beat is is not settled — two sets of measurements are about seven tenths of a second apart, and in the earlier set Blender 5.0's job had already stopped reporting itself running at the instant of the press — but it is inside a second or two of the key press either way.

### Inside Blender's own window — the Mac, in 5.3, by Blender's own simulated events

Every key and click here was sent from inside Blender as its own simulated event, not by a person and not through macOS. The render was started the way Render Animation starts it, by calling that item's operator, after a simulated Escape had closed the Quick Setup panel.

- **The status bar's cross stops the render.** Clicked two seconds into frame 3, the render job stopped reporting itself running 0.344 seconds later on an image render and 1.739 seconds later on a video render; nothing more was saved or added to the video. A photograph just after the click showed the status bar reading `Canceling...`, the bar and the cross greyed. No tooltip showed with the pointer resting on the cross for three seconds beforehand.
- **Blender's own simulated Escape does not stop the render.** Sent into both windows two seconds into frame 3, four times, with the pointer at Blender's default position and at each window's middle, it changed nothing: the render ran on, frame after frame, and with nothing else to stop it wrote all six frames. **Blender 5.2.2, given the same simulated Escape by the same script on the same Mac, did not stop either.** So this says that Blender's own simulated Escape does not stand in for a key press, in either version — not that Escape fails to stop a render in 5.3. Whether a person's Escape stops a 5.3 render is not established.
- **Blender's own quit, called while a render runs**, ended it, saved a recovery file, and left the frames finished so far; for a video, the frames appended so far (question 17).

### Windows — one test, one version, and it is a Windows Server result

**Blender 4.5.12 on Windows Server 2025 Standard, on a machine with four cores and no graphics card, where one frame took about thirty seconds.** A stop delivered as a console control event — which is what a key press produces, though it is not the act of typing one — was answered with the same sentence the Mac and Linux print, word for word. The wait was **21.3 seconds**, with the frame reporting about five seconds of work left when it was cancelled. Then one cancelled line, then `Blender quit`, and **exit code 1** — the same code the other two operating systems leave. No memory or leak lines appeared, but memory debugging was not switched on.

**Nothing else on Windows is answered.** Blender 5.0, 5.1, 5.2 and 5.3 were not reached, and the other fifteen tests were never begun, so nothing may be read across to them. **Never set these figures beside the Mac's or the Linux machine's**: it is a different operating system, a different edition from the desktop one this project wanted, and a machine whose frame takes half as long again as the Mac's.

### What differs between versions

Six things. Five of them are printing; the sixth adds one step at the very end of the stretch. **None of them changes how long the wait is, or what is left on disk.**

1. **What is printed while it winds down.** Blender 4.5 prints its lines bare and untimed; 5.0, 5.1, 5.2 and 5.3 put an elapsed time and the word `render` before their lines. The number of lines depends on where the stop lands, as described above. This is the logging change set out under question 3, met at the moment of a stop.
2. **What `-q` leaves of that.** In Blender 4.5, nothing at all is printed after the break sentence and before the process goes. In the ordinary 600-sample Cycles runs in 5.0, 5.1, 5.2 and 5.3, the three render lines still come and only `Blender quit` is dropped. **The break sentence is printed under `-q` in every version on every machine.**
3. **A handler that runs as Blender exits, and it exists in 5.1, 5.2 and 5.3 alone.** `exit_pre` is absent in 4.5 and 5.0, present in 5.1, 5.2 and 5.3, and it fires during this stretch, after the cancel handler. So what runs between a stop and an end is not the same set of steps in every version. Same on both machines in 5.1 and 5.2, and on the Mac in 5.3.
4. **What a second stop request prints, and how the process dies.** Blender 4.5 prints `Blender killed` and, on the Mac, `libc++abi: terminating`, and is killed by signal 6 on both machines. Blender 5.0, 5.1, 5.2 and 5.3 print `Blender killed` and a line naming unfreed memory blocks — in 5.3 `Error: Not freed memory blocks: 30675, total unfreed memory 8.477425 MB`; 5.1 and 5.2 then exit with code 2 on both machines, and 5.3 with code 2 on the Mac, while 5.0 exits with code 2 on Linux and is killed by signal 11 on the Mac, writing a crash file as it goes. **One thing was seen once and only once**: in 5.0 on the RTX 3060 machine, and in none of the other seven runs of this test, Blender also printed a sentence about freeing memory after the leak detector has run, sixteen times over. Blender 5.1's own bug-fix list records exactly that warning as an issue that existed in 5.0 or older, so the release note and the run agree. Blender 4.5 never printed it on either machine, which the release note does not rule out but no run has shown.
5. **What the render statistics handler is handed.** In Blender 4.5 it is the whole progress line, memory figures and all. In 5.0, 5.1, 5.2 and 5.3 it is a much shorter line — the memory figure, a remaining time where there is one, and the state; in 5.3, `Mem: 2M | Sample 600/600`. Same on both machines in 5.0 to 5.2, and on the Mac in 5.3. **The documentation changes at a different version.** The 4.5, 5.0 and 5.1 API describes “the render stats (render/saving time plus in background mode frame/used [peak] memory)”. In 5.2 and 5.3 it describes “the render progress as a string containing current frame, current sample, render time and saving time.” Both descriptions name an argument. The observed shortening starts at 5.0, so the 5.2 wording change is not a behaviour change at 5.2.
6. **What the logging switches take and add.** Blender 4.5 refuses `--log-level debug` with `Error: not a number '--log-level debug'.` — its own help says the level is a number — and **then carries on and renders normally** on the GTX 1080 Linux machine. Whether it does so on the other two machines is disputed: the same error was recorded both with and without the animation continuing. Its fullest logging adds three lines of its own after the cancelled line. Blender 5.0, 5.1, 5.2 and 5.3 take the word, and their fullest logging adds a block of the engine's own lines at the stop: 5.0 and 5.1 print a full path-tracing report there, while **5.2 and 5.3 print a line saying the rendering was cancelled and no report block at all** — 5.3's block, line for line, the same as 5.2's. That last split was seen on the Creator's Mac, in all five versions, and is not offered for Linux.

### What is still open

- **The window half on macOS, by a tool, in 4.5 to 5.2** — Escape and the status bar's cancel button inside Blender's own window on the Creator's Mac. **This is a refusal, not an untried test**: driving a key press into another program's window there needs a system security setting changed, which is nobody's here to change, and the refusal was checked twice rather than assumed. It will stay open while the setting stays as it is. 5.3 reached the window by Blender's own simulated events instead, which is a different road again.
- **Windows beyond the one test in Blender 4.5** described above, and any Windows that is not Server 2025 on this build. **Linux, Windows and any card but the Mac's own in 5.3.**
- **A clean timing on a machine to itself.** The RTX 3060 machine's processor was shared with another tenant, and its display was drawn by the processor rather than by its card, so its figures are its own and its EEVEE figures are not a comparison with anything.
- **Whether a person's own hand gives the same result as a tool's key press or click.** Every in-window run here was driven, and none of them can show that the key or the click arrived by the same road a hand would use. In 5.3 the two roads plainly part for Escape: a key sent by a tool stopped renders on Linux in 4.5 to 5.2, and Blender's own simulated Escape stopped nothing on the Mac in 5.2.2 or 5.3.
- **A second machine of the same kind, and any graphics card that is neither Apple's nor NVIDIA's.**

## 16. When a render working through an animation is stopped at no particular moment, what is in the place it writes to for the frame it had not finished?

**How it is known.** Blender 5.3 answers **not in the sources**, and marks **inferred** that with Placeholders on an empty file was put at the frame's name when the frame began; nothing in its sources says whether Blender takes it away on a stop. For 4.5, 5.0, 5.1 and 5.2 the answer is the stops recorded under questions 3, 10 and 15 — **observed**, from a terminal, on the Creator's Mac and on rented Linux machines — set against **Writing 11** item 6, observed too. In 5.3 hand tests on the Creator's Mac settled it: each stop landed about two seconds into a frame of about six and a half to ten seconds, while the frame was still being sampled, and the folder was listed just before the stop and after it.

**Verdict: not established for every version.** With Placeholders off and no older file at that name, the tested runs all leave nothing. With Placeholders on it is not settled in 4.5 to 5.2, and in 5.3 it depends on how the render was stopped.

- **Placeholders off, with no older file there: nothing.** No part-written file and no empty one is at the frame's name afterwards — after an interrupt, a terminate and a kill, in all five versions; 4.5 to 5.2 on the Mac and on Linux, 5.3 on the Mac. A person's Escape inside the window in 4.5 to 5.2 on the Mac left nothing either (question 3).
- **Placeholders on, in 5.3: the signal decides it.** With Overwrite off, as in both earlier records below, an empty file sits at the frame's name from the moment the frame begins (question 6). **An interrupt took it away**: just before the stop the folder held `f_0003.png` at 0 bytes, and afterwards nothing was at that name. **A terminate and a kill left it**, at 0 bytes, and Blender's own loader opens nothing from it. A render started again with Overwrite off then skips that frame and leaves it empty — question 4 shows that happening after a kill. Inside Blender's window, a click on the status bar's cross, sent as Blender's own simulated event, left nothing at the frame's name.
- **Placeholders on, in 4.5 to 5.2: not settled.** Set out in full below.
- **Over an older finished frame, with Overwrite on — 5.3 alone, on the Mac.** An interrupt or a kill during the rendering left the older file exactly as it was — the same size, the same last-changed time and, compared value by value, the same picture — with Placeholders off and with Placeholders on. So during the rendering nothing touches the frame's file. Once the frame's own write has begun it is different: the older file is emptied and written again, and a stop then leaves the new write cut short and the older picture gone (question 13).

**Placeholders on, in 4.5 to 5.2: not settled, and this is where that is written down for the whole sheet.** Question 10's runs, and questions 3, 6 and 15's, found nothing at all for the frame in flight, a placeholder included. **Writing 11** item 6 records the opposite from the same kind of run: the empty file for the frame in hand left behind at zero bytes, alongside the whole frames already done, on both its machines in all four versions, with the stop fired the moment frame 3's empty file appeared. The Creator's Mac is common to both, both claim all four versions, and neither reading can be read into the other — on `Writing`'s own account an empty file stands at very nearly every moment of an animation render, and on question 10's it was never there to find. **Writing's runs and the explicitly specified 5.1 Frames run had Placeholders on and Overwrite off.** In that 5.1 case neither Overwrite nor the signal explains the disagreement: Frames records an interrupt, a terminate and a kill leaving nothing, and Writing records a terminate leaving the empty file. The Placeholders setting is not established for the 4.5, 5.0 and 5.2 Frames stop runs. **What does differ:** the moment each stop was aimed at — Writing's at frame 3's empty file appearing, and Frames' sent fifteen seconds into a five-frame render at no particular moment — and that in the Frames runs only Blender 5.1's run had Placeholders explicitly recorded as on in its set-up, the 4.5, 5.0 and 5.2 runs sharing a stop test whose set-up did not state the setting. This is recorded as a thing about Blender that is not settled; neither side is chosen, and the reading that a placeholder is what an interruption leaves for the frame in progress is not restored by it either.

**What 5.3 suggests, marked as not established for the earlier four.** In 5.3 the signal decides it, and Writing's stop was a terminate — so with 5.3's behaviour both earlier records could have come out as they did, had the Frames runs all been interrupts. But the Frames record for 5.1, the one version that names the setting, has a terminate and a kill leaving nothing as well, which 5.3 does not do. So 5.3 does not settle 4.5 to 5.2, and nothing about the earlier four should be built on it.

**Why it is worth settling.** It decides whether restarting a stopped job silently loses a frame. Question 14 settles what a leftover one does — the frame is skipped for good and left at 0 bytes, unopenable — and **The machine 7** records the same ending reached by a different route, a frame claimed, never rendered and left empty with the job still ending at exit status 0 and the full file count. So the cost is established twice over while the question of whether a stop produces one is not established at all. **Until it is, nothing that restarts a stopped render may trust the file count.** In 5.3 it is settled on the Mac, and the answer is the costly one for two of the three ways of stopping: a terminate or a kill with Placeholders on leaves an empty file that a restart with Overwrite off skips and never fills.

**What is still open.** Placeholders on in 4.5 to 5.2, above. A person's own key in Blender's window, in 5.3. Linux and Windows, in 5.3. And a scene with two views, where the frame in hand is two files (question 10), in any version.

## 17. When a render writing an animation as a single video file is stopped before the end, what does each of the ways a render can be stopped leave of that file?

**How it is known.** Blender 5.3 answers **not in the sources** one way of stopping at a time. Its sources name the ways — Esc and the status bar's cancel button, **documented**; Control-C at a command line, **inferred** from a page about Blender used as a Python module; and the computer turning off, **documented** as a case to guard against — and say only, for all of them together, that the file "might become unplayable". For 4.5, 5.0, 5.1 and 5.2 the answer is the stops recorded under questions 5 and 12 — **observed**, from a terminal, on the Creator's Mac and on rented Linux machines; no stop inside Blender's window was ever made on a video in those four. In 5.3 hand tests on the Creator's Mac settled it, from a terminal and inside the window by Blender's own simulated events, and every file was read back with Blender's own movie reader and nothing else.

**Verdict: not established for every version.** The three stops from outside the window leave the same in all five. The stops inside the window were tried on a video in 5.3 alone. A person's own Escape, Force Quit and a power cut were tried on a video in no version.

What each way leaves of the MPEG-4 video these runs used, which stood at 48 bytes through a short render until it was closed (question 5):

- **An interrupt** — what Control-C sends — **leaves the frames appended before the stop**, and the file grows to hold them as the process ends. All five versions; 4.5 to 5.2 on the Mac and on Linux, 5.3 on the Mac — 2,427 bytes and 3 frames when stopped during frame 4 of 20, 3,164 bytes and 10 frames at frame 10, all 8 frames when stopped the moment the last was written. One moment is different, in 5.3 alone: an interrupt landing while a File Output node was still writing the last frame's separate image let the image finish and left that frame out of the video (question 12).
- **A terminate and a kill leave 48 bytes and no frames.** All five versions, on every machine each ran on. Other containers, killed at the last frame, leave anything from no file to a few hundred bytes and never a frame — question 12, on Linux in 4.5 to 5.2 and on the Mac in 5.3.
- **With Autosplit on, files already closed survive whole**, and the one being written holds what the stop let it — question 5, on Linux in 4.5 to 5.2 and on the Mac in 5.3.
- **Inside Blender's window — 5.3 alone, on the Mac, by Blender's own simulated events.** A click on the status bar's cross two seconds into frame 3 of 20 left 2,288 bytes holding 2 frames, and the render job stopped reporting itself running 1.7 seconds after the click. Blender's own quit, called while the render ran, left 2,583 bytes holding the 6 frames done. A kill sent from the terminal to the windowed Blender, standing in for Force Quit, left 48 bytes and no frames. Blender's simulated Escape did not stop the render (question 15).
- **Never tried on a video, in any version:** a person's Escape; Force Quit from the Apple menu, and End Task on Windows; and the computer going down.

**Two limits on every result here.** In 4.5 to 5.2 the Mac's leftovers were also opened in QuickTime Player (question 5); in 5.3 only Blender's own reader was used, and it reports a file as loaded even with nothing in it, so the bytes and the frame count are what count, and whether 5.3's leftovers play anywhere is not established. And these were short renders: what a terminate or a kill leaves of a long video that has grown through its run is the disagreement under question 5.
