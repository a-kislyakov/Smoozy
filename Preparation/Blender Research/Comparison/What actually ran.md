# What actually ran — Blender 4.5, 5.0, 5.1, 5.2 and 5.3 side by side

What a finished render can be made to say about the parts of the computer that did the work, the engine that produced it and the add-ons that were loaded — where each of those can be read, and when.

## The machines behind the tests

Two machines, and the difference between them matters as much as the difference between versions; each answer below names its own. **The Creator's Mac** — a MacBook Pro with an Apple M1 Pro chip, its own 14-core graphics reached through Metal and no other card, 16 GB of memory, and a screen, so the only machine here where a window question could be reached; **the only machine Blender 5.3 was run on**. **It is not one fixed machine across this topic.** 4.5 to 5.2 were run on it on 2026-08-07 under macOS 26.5.2, as 4.5.12, 5.0.1, 5.1.2 and 5.2.0; 5.3 was run on it on 2026-10-17 under macOS 26.6.2, as **5.3.0 Beta**, built 2026-10-16, hash `5d8151335b6b`, with **5.2.2** beside it for same-day controls. Other work was using the Mac both times, so it offers no timings and no memory measurements. **A rented Linux machine with one NVIDIA GeForce RTX 4080 SUPER** — the **fourth** rented Linux machine in the equipment section — no display server at all; its graphics card was unreachable on the first day of testing and repaired for the second, so some of its answers come from a machine that had a card and could not use it, and some from the same machine with the card working. Both states are recorded, and **a result got with no usable card and a result got with one are not two versions disagreeing** — they are the same machine on two days. It ran 4.5 to 5.2 only, and has since been destroyed. The equipment section of `Preparation/Blender Research/Method.md` holds both machines in full.

**Which Blender each machine carried.** The Linux machine carried the four Linux x64 builds at the versions the Mac ran on 2026-08-07, and each of those Mac builds reported the same build hash as its Linux counterpart, built at a different hour. The OpenEXR files written in this topic name their maker as `Blender 5.0.1`, `Blender 5.1.2` and **`Blender 5.2.0 LTS`** on both machines, and `Blender 5.3.0 Beta` on the Mac, so the 5.2 behind every 4.5–5.2 answer here is **5.2.0**. **The 5.2.2 runs are controls and nothing more.** Where a 5.3 result on the Mac differs from the earlier Mac record, the same test was run in 5.2.2 on the same Mac the same day. A control that goes with 5.2 makes the difference a 5.3 one. A control that goes with 5.3 puts the gap between the two days — a point release, a macOS update and a test scene rebuilt by a newer Blender — and not between the versions.

**How the version names are used below.** *All four* means 4.5 to 5.2, and *the newer three* means 5.0 to 5.2. 5.3 is named wherever it is included, and every 5.3 result is from the Mac.

**A result that came back the same in every version still settles only the machines it was run on**, and a difference found on one machine is a difference established on that machine. **Nothing in 5.3 was run on Linux**, so every Linux answer below is an answer for 4.5 to 5.2 alone, and no 5.3 result is ever set against a Linux one as a version difference. **Windows was not tested anywhere** in this topic. Neither was any graphics card of another make tried, nor any machine with more than one card, in any version. Those are gaps in what could be tried, not differences between versions.

## The answer in short

### Where Blender itself differs between versions

Each line points to the full answer below. Test results cover only the machines named there. Every 5.3 test was on the Mac; a change at 5.3 has a release note or a same-day 5.2.2 control.

- **Question 1** — reaching the device line, its stream, and the closing report's heading and prefix: 4.5 against 5.0 to 5.3.
- **Question 1** — the `Hardware Ray-Tracing:` line: Linux 4.5–5.0 against 5.1–5.2; Mac 4.5 against 5.0–5.3.
- **Question 1** — the indent of that line changes between 5.2.2 and 5.3 on the Mac.
- **Question 1** — the Render Time pass starts at 5.0.
- **Question 1** — `gpu.init()` starts at 5.2; 5.3 has it too.
- **Question 2** — the printed engine name starts at 5.0.
- **Question 2** — the OpenEXR `Software` and `colorInteropID` attributes start at 5.0.
- **Question 2** — EEVEE's identifier changes at 5.0; 5.3 keeps it.
- **Question 2** — `-E help` works from 5.0; 4.5 fails on both machines.
- **Question 2** — refusing an unknown engine ends differently in 4.5 and the newer versions.
- **Question 4** — refused devices and unwritable output have different messages in 4.5 and the newer versions; 5.3 matches the newer Mac results.
- **Question 4** — a GPU Compute scene without a usable card finishes in all five; the ordinary log can name the processor from 5.0.
- **Question 4** — the HIP-library message changes level and stream after 4.5. Linux only; 5.3 untried.
- **Question 4** — switching off saved render output starts at 5.2; this topic did not try 5.3, and The compositor 2 and Reports 1 did.
- **Question 4** — 5.3's Mac build reports two more build options than 5.2.2's.
- **Question 5** — `--log-level` changes from a number to a name at 5.0.
- **Question 5** — `--log-list-categories` starts at 5.0.
- **Question 5** — category lists change between versions on each machine, including 5.2.2 against 5.3 on the Mac.
- **Question 5** — statistics strings lose the frame and peak-memory fields at 5.0, while keeping current memory.
- **Question 5** — with a window, the statistics handler receives the full stream from 5.2. Mac only; 5.3 matches.
- **Question 5** — 5.3 ships an OpenEXR Python module that reads saved headers; 5.2.2 on the Mac lacks it.
- **Question 6** — a separate frame-announcement line starts by the tested 5.0.1 builds.
- **Question 6** — the closing report after the tested Control-C differs between 4.5, 5.0–5.1 and 5.2. Mac only; this topic did not try 5.3, and Frames 15 records 5.3 printing 5.2's lines.

- **Questions 1–6** — 5.3 on Linux, Windows, other makes of graphics card, or several cards; its untried memory, driver, crash and unprepared-Metal-program cases.
- **Questions 1–6** — the extra tests shared by 5.3 and 5.2.2, but not run in 4.5–5.2.0: combined devices, per-frame statistics blocks, a one-value statistics handler, Workbench fields, multi-layer channel names, engine argument order, a missing engine, other engines' information-level output, guiding and OSL on Metal, extra add-on checks, and the render window.

## 1. When a render has finished, what can be learned about which parts of the computer it used?

**Nothing in Blender's own documentation records which processor or which graphics card did the work.** All five versions say that, in different words. What the documented metadata can carry about the machine is the host name, the peak memory and the render time, and only when switched on before the render and only into a format that can hold it. Documented in all five. The step from "no device entry on the list" to "nothing about the device is written at all" is inferred rather than read. `system-info.txt` and the `gpu.platform` calls are documented too, with an explicit warning that treating those calls as naming the card that rendered a Cycles image would be an unsupported step. 5.3's sources say that EEVEE renders only on the graphics — which graphics being inferred — and do not establish whether Workbench uses the graphics. One version-specific note is documented and untested: in 5.0.0 the peak-memory field printed `ddM`, and 5.0's corrective notes record it as fixed in 5.0.1.

**A background render with no switches at all names no device, in any version.** Exit 0, a frame written, the error stream empty. Run in all four versions on both machines, and in 5.3 on the Mac. Nothing printed names a processor, a card, or a technology — not on Linux with a broken card, not on Linux with a working one, not on the Mac. Lines such as `Copying Mesh to device` carry the word without naming one. **The same everywhere.**

**But every version can be made to name it, and this is where they part.** The line reads `Path tracing on:` and carries the model, and for a processor the thread count, and for a card the route taken to it and its place on the bus; on the Mac it reads `Apple M1 Pro (GPU - 14 cores) (Metal) (display)` for the graphics. Every version prints it. What differs is how you reach it:

- **4.5** — no log switch reaches the line at all. `--debug-cycles` is the only route, and it lands on the **error** stream. Run with every log switch this version has, 4.5 printed hundreds of lines and not one named a device.
- **5.0, 5.1, 5.2 and 5.3** — `--log-level info` on its own is enough, and it lands on **standard output**.

Run in all four versions on both machines, and on Linux both with the card broken and with it working; 5.3 on the Mac, eight ways, every one with the line on standard output and nothing on the error stream. **It differs.** In 4.5 this line is Cycles' own printing rather than Blender's log, which is why no log switch narrows to it.

**One line near it must not be read as saying what ran.** `Added device "Apple M1 Pro (GPU - 14 cores)" …` is printed in runs whose `Path tracing on:` line names the processor. It names what Cycles found, not what did the work — in 5.0 to 5.3 on the Mac at `--log-level info`, and in 4.5 there under `--debug-cycles`.

**Asked for both at once, the line names both.** In 5.3 on the Mac, `-- --cycles-device METAL+CPU` rendered with exit 0, and the report listed the Metal graphics and, beneath it, the processor at seven threads, after `CPU render threads reduced from 8 to 7, to dedicate to GPU.` printed three times before the render began. Nothing printed says how the work was shared. 5.2.2 on the same Mac did the same. The earlier versions' sources describe appending `+CPU` to a graphics device. Its absence from 5.3's quoted list does not establish removal: the 5.3 test accepts it. Not run in 4.5 to 5.2.0. **Not established for every version.**

**The block that line sits in is not the same block in every version.** It is headed `Full path tracing report`, and it was transcribed word for word in all four versions on the Linux machine, five processor runs and three card runs each, on the same day, and in 5.3 on the Mac:

- **4.5** — the heading has **no colon**, and the block carries no `cycles           |` prefix, because here it is Cycles printing for itself. There is no `Hardware Ray-Tracing:` line in any of the eight Linux runs, on either stream, on the processor or on the card, nor in 4.5's block on the Mac.
- **5.0** — heading with a colon and prefixed, like 5.1 and 5.2, and **no `Hardware Ray-Tracing:` line** on the Linux machine. Eleven runs on that machine with this build, ten of them without the line; the one run that recorded it came from the day the machine's card driver was broken and is not evidence that the version prints it. The comparison also records the line absent in 5.0 on two further Linux machines, under **The machine** and **Settings**. On the Mac, 5.0's observed block carries `Hardware Ray-Tracing: Off`; the Mac and Linux results differ without establishing another version change.
- **5.1 and 5.2** — the heading has a colon, the block is prefixed and comes through Blender's log, and a `Hardware Ray-Tracing: Off` line sits under the device line in every one of their eight Linux runs each. It reads `Off` on the processor and `Off` with an NVIDIA card doing the work. The Mac blocks in 5.0, 5.1 and 5.2 carry it too, marked observed.
- **5.3** — on the Mac, the heading with a colon, the block prefixed, and `Hardware Ray-Tracing: Off` under every device line: on the processor, on Metal, and under each of the two devices when both worked at once. It is indented two spaces less than in 5.2.2 on the same Mac the same day — twenty spaces after the bar against twenty-two. Nothing else in the block differs.

**So on the Linux machine the line arrives at 5.1: absent in 4.5 and 5.0, present in 5.1 and 5.2.** **On the Mac the observed blocks carry the line in 5.0, 5.1, 5.2 and 5.3, and not in 4.5.** This Mac result does not overturn the Linux result. The indent is the one change at 5.3, and it is established on the Mac alone. What the line is actually reporting, and what would make it say anything but `Off`, is settled by no run anywhere and is not claimed.

**Two things hint at a card without naming one.** OptiX puts its own name into the ordinary progress lines — `Building OptiX acceleration structure` — where CUDA puts nothing, so the default output can say OptiX was used and cannot say CUDA was. And the memory figure jumps from about one megabyte to six or seven hundred for a scene of one cube. Both hold in all four versions on the Linux card; the memory jump was seen on the Mac's graphics too, and in 5.3 there it went from `2M` to about `1370M`. **The same in all four**; 5.3 was tried on the Mac alone, where the memory jump held. (The number of times the OptiX line appears is not stable between repeats and no count should be relied on.) On the Mac a render on Metal can also say in its progress lines that Metal programs are still being prepared — `(8 kernels to optimize)`, `(4 kernels to optimize)`, `(Using optimized kernels)` — while it goes ahead and writes its frame. Seen in 5.3 and 5.2.2.

**No field written inside a finished image names a device, a card or a technology, in any version.** True of PNG and OpenEXR, true whether the processor or the graphics did the work, true on both machines for all four, and in 5.3 on the Mac. What moves is the Memory field, which reads the card's figure instead of the processor's. **The same everywhere.**

**The settings read back after a run do not say what ran, in any version, and can be shown to say the wrong thing outright.** With the preference set to OptiX, the scene set to GPU Compute and the command line sending the work to the processor, both settings still name the card's route. On the Mac the same run misleads in the other direction: in 5.3 there, a scene set to GPU Compute and overridden to the processor read back `METAL` and `GPU` while its device line named the processor. All four versions on both machines, and 5.3 on the Mac. **The same everywhere.** One difference between the two operating systems sits beside this and is not a version change: the Cycles preference reads Metal at factory startup on the Mac, 5.3 included, where it reads None on Linux.

**The Render Time pass exists from 5.0 and not in 4.5.** The property is absent in 4.5 and present in 5.0, 5.1 and 5.2 on both machines, and in 5.3 on the Mac. 5.0's release notes say in so many words that the pass was added. Where it exists, it follows the **scene's setting** and pays no attention whatever to what did the work — written when the scene said CPU and the card ran the frame, withheld when the scene said GPU and the processor ran it. Shown in both directions on the Linux machine with its card working, and confirmed on the Mac; in 5.3 all six pairings of the scene's setting with the command line were run on the Mac, Metal standing in for the card, with the same result. **It differs**, and the difference is 4.5's. A file carrying this layer tells you what the scene asked for and nothing about what happened. Inferring a processor render from this pass does not follow; only the scene's setting is established. In a multi-layer OpenEXR, 5.3 and 5.2.2 on the Mac write the file in two parts when the pass is on, the pass in the second; anything that reads only the first part sees no pass.

**`bpy.ops.wm.sysinfo` works with no window in all five versions**, returning a finished result and writing its file. Its Cycles section names the machine's processor and, once the card works, describes the card in full; on the Mac it names the Metal device. Its **GPU** section reads `GPU: missing, background mode` in every version, with the card working and with it broken — that sentence is about the missing window, not the missing card. With a window open on the Mac, the GPU section fills in with the renderer, vendor, version, device type and backend, and nothing else in the file changes. All four versions on both machines, and 5.3 on the Mac, where the file was 96 lines without a window and 120 with one, as in 5.2. **The same everywhere.**

**The `gpu` module refuses to answer with no window — except from 5.2.** In 4.5, 5.0 and 5.1 the calls fail in the same words on both machines, with the card working and with it broken. **5.2 has `gpu.init()`, and so has 5.3**: it succeeds with no window and no display server at all, after which the module names the machine's graphics. 5.2's own release notes say the call was added for background mode. 5.3 on the Mac answered word for word as 5.2 did there: `Metal API`, `APPLE`, `METAL`, `Apple M1 Pro`. Established in all four versions on both machines and in 5.3 on the Mac. **It differs.** Two limits on it: it names the machine's card, not what a render used, and it reports the drawing backend rather than the one Cycles would path-trace on.

**The sixteen metadata switches have identical factory values in all five versions** — on both machines for all four, on the Mac for 5.3 — with the master switch off, Memory off and Hostname off. The panel itself, photographed in all five versions on the Mac, shows the same thirteen boxes with the same ones ticked. **The same everywhere.** The API pages for 5.0, 5.1, 5.2 and 5.3 state that the Memory switch defaults to on, and a running Blender and its panel both show it off in all five; what 4.5's own API page says on this point was never read, so that disagreement is established for four versions and untested for the fifth.

**The thread count reads the machine's own core count in all five versions** — twenty-four on Linux, eight on the Mac — not the documented default of one. **The same everywhere.**

**`--cycles-print-stats` names no device in any version** — no statistic in the block names one — and when the graphics did the work the block replaces its profiling sections with one sentence refusing to answer, `Profiling information not available (only works with CPU rendering)`, word for word the same in all four versions on both machines and in 5.3 on the Mac. **The same everywhere.**

**Nothing printed by an EEVEE or a Workbench render names the graphics chip that drew it.** In 5.3 on the Mac, with the fullest information-level logging, neither printed a line naming the chip, a vendor, a renderer or a drawing route, while a Cycles run beside it printed its device line; 5.2.2 on the same Mac gave the same at that level. At the most detailed level, 5.3 names the drawing route — `gpu.metal` lines about stored shader variants, twelve for EEVEE and five for Workbench — and still not the chip; The 5.2.2 EEVEE control at that level printed no `gpu.metal` line; Workbench was not run at debug level in that control. The unresolved category question is under question 5. Not run in 4.5 to 5.2.0. **Not established for every version.**

**A finished render shown in Blender's own window names no device.** In 5.3 on the Mac, a render on Metal started the way the interface starts one showed above the picture only `Frame:1 | Time:00:00.81 | Mem:1419M, Peak: 1419M`. 5.2.2 on the same Mac showed a frame, time, memory and sample line and no device, though its window showed the render as it stood at the first sample — what the line says depends on when the window last redrew. Not run in 4.5 to 5.2.0. **Not established for every version.**

**A timing worth having, from the Linux machine only.** The same frame finishes between six and fifteen times sooner on the card than on the processor, in every one of the four versions. One machine, one scene, one day, with nothing else running. The Mac was deliberately not timed, in any version, because other work was using it.

## 2. When a render has finished, what can be learned about which render engine produced it?

**The documented metadata list has no engine field.** An engine may add fields of its own, and the API provides the call; whether shipped engines use it is not established by those descriptions. Reading the file's engine setting establishes what it asks for, rather than what rendered it. 5.0's release notes document a printed `Engine: Cycles` line through a worked example. Silence about that line in the other versions' sources is not a behaviour difference; the tests below establish the actual split.

**The tested finished images carry a trace of the engine — observed.** Cycles writes four fields of its own into every image it renders — `cycles.ViewLayer.samples`, `cycles.ViewLayer.total_time`, `cycles.ViewLayer.render_time` and `cycles.ViewLayer.synchronization_time` — and an EEVEE render of the same frame carries none of them. The names are identical in all four versions on both machines and in 5.3 on the Mac, whether the processor or the graphics did the work. **The same everywhere.** A Workbench render carries none of them either, in 5.3 and in 5.2.2 on the Mac, so a file without them could be EEVEE or Workbench and its fields do not say which. Workbench was not tried in 4.5 to 5.2.0.

**An OpenEXR carries a `Software` attribute naming Blender and its version from 5.0 on, and not in 4.5.** Absent in 4.5; present in 5.0 as `Blender 5.0.1`, in 5.1 as `Blender 5.1.2`, in 5.2 as `Blender 5.2.0 LTS` and in 5.3 as `Blender 5.3.0 Beta`. A `colorInteropID` attribute follows the same split. Neither reaches a PNG in any version. Read on both machines for all four, from processor runs and from graphics runs, and on the Mac for 5.3. **It differs.** In 5.3 an OpenEXR also carries `name` and `type` attributes; 5.2.2 on the same Mac carries the same names, so they are not a 5.3 change.

**A render names its engine in what it prints from 5.0 on, and never in 4.5.** A background render started from the command line with no switches at all prints `render | Engine: Cycles` in 5.0, 5.1, 5.2 and 5.3, before any work begins. 4.5 has no such line anywhere, at any log level, on either machine. **It differs.**

**EEVEE's identifier changed at 5.0.** A running Blender reports `BLENDER_EEVEE_NEXT` in 4.5 and `BLENDER_EEVEE` in 5.0, 5.1 and 5.2, on both machines, and in 5.3 on the Mac. 5.0's release notes state the change outright. **It differs.** Which name Blender will take, though, depends on **how** it is set: **the name that works everywhere, by every route, is the version's own** — `BLENDER_EEVEE_NEXT` in 4.5, `BLENDER_EEVEE` from 5.0. The split between the two routes is settled under **Settings 13**. Whether 5.0, 5.1 or 5.2 really renders in EEVEE when given the old name on the command line, and whether it warns, is not established here: acceptance alone was recorded on one machine with a 64 by 64 scene. The refusal of a name no version has is below.

**The engine list a running Blender reports holds exactly one entry, in every version.** So the single-entry list on the API pages is not an artefact of how the documentation was generated, and it is not an operating-system matter either — the same one-entry list came back on both machines, and in 5.3 on the Mac. `has_multiple_engines` exists in all five versions and reads True in all five. Its API description is available for 5.1, 5.2 and 5.3; that description is not established here for 4.5 or 5.0. Meanwhile `-E help` lists three engines in the same Blender. **The same everywhere.**

**`-E help` works from 5.0 on and is unusable in 4.5, but it fails differently on each machine.** In 5.0, 5.1 and 5.2 it exits cleanly and prints three engine names, on both machines, and so does 5.3 on the Mac. In 4.5 on Linux it printed nothing at all and never returned, and had to be killed after twenty-five seconds, three times out of three. In 4.5 on the Mac it printed the full listing — the three names, with `BLENDER_EEVEE_NEXT` in place of `BLENDER_EEVEE` — and then aborted, three times out of three. **It differs between the versions.** How 4.5 fails is an operating-system fact and belongs inside the answer, not in any version comparison.

**An engine name Blender does not know is refused in every version**, with the same message, no frame written, on the error stream. What happens after the message differs. On the Mac, 5.0, 5.1, 5.2 and 5.3 exit 1 and 4.5 aborts. On Linux, 5.0, 5.1 and 5.2 exit 1 straight away, and 4.5 printed the message and then never returned — it sat for nine minutes with the message already written and had to be killed, so no exit status can be recorded for that case. **It differs.** The refusal is the same everywhere; only 4.5's ending is not.

**An engine named before the file on the command line does not count.** In 5.3 on the Mac, `-E BLENDER_EEVEE` written before the file name rendered with the file's own engine, `Engine: Cycles`; written after it, the render used EEVEE. That is the rule the manual states for the output path, which it does not state for the engine. 5.2.2 on the same Mac did the same. Not run in 4.5 to 5.2.0. **Not established for every version.**

**A file whose engine is not installed renders with EEVEE, and once loaded no longer says which engine it asked for** — in 5.3 and in 5.2.2 on the Mac. A script reading the engine afterwards sees EEVEE; the only record is one printed `ERROR` line and the `Engine: EEVEE` line. The full answer is under question 4.

**Channel names in a multi-layer file do not tell Cycles from EEVEE**, for a scene with only the Combined pass switched on: both wrote `ViewLayer.Combined.R`, `.G`, `.B` and `.A`, in 5.3 and in 5.2.2 on the Mac. A pass only one engine offers was not tried. Not run in 4.5 to 5.2.0. **Not established for every version.**

**Which part of the computer did the work changes nothing about the engine**, in any version. The field set a card's render writes is identical to the processor's, and nothing new names the engine. Both machines for all four; 5.3 on the Mac, on Metal.

## 3. When a render has finished, what can be learned about which add-ons were in use while it ran?

**No add-on field appears on the documented metadata list.** That a render records no add-ons elsewhere is inferred from that absence; the image-field tests below provide a narrower observation. What exists instead is a report Blender writes when asked, listing the add-ons currently enabled with their versions and paths; a plain list in the preferences that a script can read; and a command-line switch for turning add-ons on for one run. Those routes are documented in every version; reading the preferences list as a full account of enabled add-ons is inferred. "In use while it ran" is a stronger question than "enabled", and the sources reach only the weaker one.

**Nothing about add-ons reaches a rendered image, in any version.** Every field written into a PNG and an OpenEXR with every switch on was read back, on both machines for all four, from processor runs and from graphics runs, and in 5.3 on the Mac from Cycles on the processor and on Metal, from EEVEE and from Workbench. None names an add-on. **The same everywhere.**

**The report can be written with no window in all five versions**, and its add-on section is filled in with the same eight modules, their versions and their paths. On the Mac the paths are macOS ones and everything else is identical. Repairing the graphics card changed nothing in this section — the file grew by ninety lines and every one of them was in the Cycles section. With a window open on the Mac the add-on section is the same, in 5.3 as before. **The same everywhere.**

**The list that report holds is current, not stale.** In one session, without restarting, the file was written, an add-on switched off, and the file written again: the add-on is in the first file and gone from the second. Identical in all four versions on both machines and in 5.3 on the Mac. **The same everywhere.**

**`--addons node_wrangler` produces no message and no failure, and leaves the list a script reads unchanged.** Observed in all four versions on both machines and in 5.3 on the Mac. **The same everywhere.** That common result alone does not establish whether an absent add-on was requested in the earlier builds: `node_wrangler` sits in the add-on folder of 5.3 and of 5.2.2 on the Mac, among thirteen add-ons shipped with eight switched on. What 4.5 to 5.2.0 shipped in their folders was not looked at. Their response to a genuinely absent add-on is therefore not established here.

**What 5.3 and 5.2.2 do with `--addons`, on the Mac.** An add-on that is not there is named in a message — `Add-on not loaded: "space_view3d_math_vis", cause: No module named 'space_view3d_math_vis'` — and the run carries on with the list unchanged. A shipped add-on that is off has its code loaded for that run — Python's own list of loaded code holds it — while the add-on list read in the same run leaves it out, wherever `--addons` sits on the line. The next run without the flag does not have it, and nothing is saved into the settings folder. `--factory-startup` leaves the list as it is. Not run in 4.5 to 5.2.0. **Not established for every version.** So in 5.3 and 5.2.2 a record of add-ons in use, read from that list during or after a render started with `--addons`, misses what `--addons` brought in.

**The same in the tested images.** None of the inspected PNG text fields or OpenEXR header fields names an add-on. No supplied finding establishes an automatic record of which add-ons contributed to a render. **The only route is to ask the running Blender, which answers for the moment you ask and not for any render that has been** — and in 5.3 and 5.2.2 on the Mac, its answer leaves out what `--addons` loaded.

## 4. What does a render do when it is asked for something the computer or the installed Blender cannot provide, and what does it report?

4.5 to 5.2 say there is no general rule in the sources — only a handful of named cases, described unevenly — and 5.3's sources likewise describe only named cases. The named cases are largely the same in every version: a card short of memory borrows system memory; an outright shortage gives a named error; a preference set to None means the processor is used; a device named on the command line that cannot be set ends the run; a build without Open Shading Language reports so; crash files land in different places on each system. 5.3's sources also state that path guiding works only on the processor and Open Shading Language on graphics only through OptiX, which the tests below take up. 4.5 to 5.2 each say plainly that **no exit status for a failed render is documented anywhere**; 5.3's findings likewise give no general documented exit status. Cycles' own files contain `sys.exit(1)` for a failed device override — observed in those files — and the manual says an unknown argument makes Blender exit, which the test below does not bear out. One documented note sits in 5.0's sources alone and was never tested: a release note saying most of Blender now uses one logging system, including operator reports and background render progress, and warning render farms that parse the output.

**A device demanded on the command line that Cycles will not give: exit 1 and no frame, in all five versions**, on both machines for all four and on the Mac for 5.3. Which names are refused is a fact about the machine, not the version, and the two machines are mirror images of each other. On Linux only `CPU` succeeded while the card was broken, and `OPTIX` and `CUDA` joined it once the card worked; `HIP`, `ONEAPI` and `METAL` were refused. On the Mac only `CPU` and `METAL` succeeded, and `OPTIX`, `CUDA`, `HIP` and `ONEAPI` were all refused, as was any name Cycles does not know. The tables are identical in all four versions on each machine, and 5.3's on the Mac is the Mac's table exactly. **The same everywhere** for the outcome. The wording and the stream are not:

- **4.5** puts an unknown device name on the **error** stream. A real backend with no hardware behind it puts one line on standard output and, on Linux, a second on the error stream.
- **5.0, 5.1, 5.2 and 5.3** put both refusals on **standard output**, through the log, each with its category in front of it. 5.3's words match 5.2's on the Mac. In 5.3 the unknown-name runs also print an unfreed-memory line; the absent-backend runs do not.

Run in all four versions on both machines, and in 5.3 on the Mac. **It differs.** Two cautions travel with it. The unfreed-memory line is not a fact about the version: in the unknown-name runs 4.5 added no such line and the newer ones did, but outside it the line comes and goes in every version — 4.5 prints it elsewhere, and the newer ones sometimes do not — so **nothing reading Blender's output may treat the line's presence or absence as telling it which version is running.** And the CUDA line that accompanies an absent backend on Linux has no counterpart on macOS, which is an operating-system difference and not a version one.

**With the card working, the refusal can be shown to mean what it says.** `OPTIX` and `CUDA` give exit 0, a frame and complete silence; `HIP` and `ONEAPI` give exit 1 and `Found no Cycles device of the specified type`. Identical exit statuses and frames in all four versions. Linux machine with its card working; 5.3 was not run there. One thing is not identical: 5.0, 5.1 and 5.2 print a warning about the HIP library ahead of the refusal, and 4.5 prints the same message at debug level rather than as a warning — in 4.5 it comes out only under `--debug-cycles`, on the error stream — so **what differs between the versions is how loudly it is said, not whether**. The line is not tied to asking for HIP either. It appears whenever something makes Cycles look at its device list — writing the system-information file, a script that sets the device, a plain refresh — and it does not appear in an ordinary render at factory settings in any of the four versions.

**A scene set to GPU Compute where no graphics card can be used renders anyway.** Exit 0, a frame written, in all five versions, with the error stream empty. Established twice over: on Linux with a card physically present and unusable, and on the Mac with the graphics working and every Cycles device switched off — in 5.3 too, with the preference set to None. What differs is whether anything says so:

- **5.0, 5.1, 5.2 and 5.3** print the `Path tracing on:` line naming the processor, word for word the same as an ordinary processor run beside it. Nothing warns, and the line needs a log switch.
- **4.5** is silent. Nothing printed names a device at any log level, and `--debug-cycles` on the error stream is the only way to bring the line out at all.

**It differs.** For 4.5 the honest record is *finished, frame written, nothing reported* — which is not the same as a fallback and must never be written up as one. One machine fact belongs beside this, found on the Mac and owed on Linux, and it is not a version difference: a scene set to GPU Compute reached the graphics only when the settings folder had had preferences saved into it, and path-traced on the processor otherwise — in the same run in which Cycles printed that it had found the graphics. It behaved the same way in all five versions on the Mac. In 5.2 and 5.3 the preferences were saved after a refresh of the device list, and no run separates the saved file from the refresh. **The machine 5** holds a neighbouring Linux run that goes the other way — a preference change made inside the render's own run, never saved, took effect there in all four versions and produced no graphics-card marker on the Mac. That is a different test (it calls a refresh; this one does not), so it does not settle this one, and the Mac result here must not be carried to Linux.

**A render that cannot write its output: exit 1 in all five versions**, with the failure named, on both machines for all four and on the Mac for 5.3. The shape differs: 4.5 prints one line, and 5.0, 5.1, 5.2 and 5.3 print two, from two different log categories — in 5.3 word for word as in 5.2 on the Mac. **It differs.** The words inside the brackets are an operating-system fact, not a version one — 4.5 passed through a different one on each machine, while 5.0, 5.1 and 5.2 gave the same words on both.

**An invalid output-format name: it complains, then renders anyway.** Exit 0, a frame written in the scene's own format, and the complaint on the **error** stream — identical in all four versions on both machines, 4.5 included, and in 5.3 on the Mac. **The same everywhere.** The message covers a bad name and a missing build feature in one sentence, so the two cannot be told apart from it; and since every conditional format is compiled into every build on both machines, 5.3's included, the second case could not be provoked anywhere.

**A format that cannot hold metadata says nothing at all.** The file is written, the run exits 0, and neither stream carries a word about warnings, metadata or preservation. Identical in all four versions on both machines and in 5.3 on the Mac, for two such formats. **The same everywhere.** The metadata is simply gone, quietly. The 5.1, 5.2 and 5.3 manuals state that a format which cannot hold metadata loses it. The supplied descriptions for 4.5 and 5.0 establish only the format table; they do not establish whether that sentence is absent from those manuals. All five behave identically.

**A file whose engine is not installed renders with EEVEE, reports one error, and exits 0.** In 5.3 on the Mac a file saved with an engine this Blender does not have printed `ERROR Engine 'SMOOZY_TEST_ENGINE' not available for scene 'Scene' (an add-on may need to be installed or enabled)` on standard output, rendered with `Engine: EEVEE`, wrote a frame and exited 0, the error stream empty; once loaded, the scene's engine read `BLENDER_EEVEE`. So the exit status says the run succeeded on an engine the file did not ask for. 5.2.2 on the same Mac did the same. Not run in 4.5 to 5.2.0. **Not established for every version.** An engine named on the command line that does not exist is refused instead — question 2.

**An argument Blender does not know is read as a file name.** In 4.5, on both machines, `--log-list-categories` — a switch that version lacks — printed `unknown argument, loading as file:` on the error stream, then failed to read a file by that name, and exited 1. In 5.3 and 5.2.2 on the Mac the same happened: `--not-a-real-option` placed among ordinary render arguments printed that line on the error stream and `Cannot read file` on standard output, rendered nothing, and exited 1; the arguments after it were never acted on. `blender -ba scene.blend`, the manual's own example, printed the same line, read the scene, and was still running eight seconds later — not the immediate exit 5.3's manual describes. Not run in 5.0, 5.1 or 5.2.0. **Not established for every version**; where tried, the same.

**Path guiding or Open Shading Language asked of the graphics: the render finishes on the graphics and says nothing.** In 5.3 on the Mac, with either switched on and Metal doing the work, the render exited 0, wrote its frame, named Metal in its device line, and printed output identical — times and figures aside — to the same run with the switch off. On the processor each one takes effect: path guiding reports its samples in steps of four, and Open Shading Language prints `Using shader search path: …`; neither prints a line naming itself. 5.2.2 on the same Mac did the same. Open Shading Language through OptiX was not tried. Not run in 4.5 to 5.2.0. **Not established for every version.**

**What the build carries, as it reports itself.** 5.3's build on the Mac reports Open Shading Language present, every image format the manual calls optional compiled in, and no entry naming Embree, as every earlier build did. It reports forty-six build options where 5.2.2's on the same Mac reports forty-four: `io_spz` and `opentimelineio` are added and no option changes value. **It differs**, at 5.3, on the Mac.

**A single-frame render stopped part-way by a terminate leaves nothing at the output path, and a shell reports the ending as 143.** Identical in all four versions and in 5.3. Run on the Mac only, and the last thing printed before it stopped was an ordinary progress line — nothing announced the stop. **The same everywhere, on the Mac.** That holds for the stop that was made — a signal sent six seconds in, at no particular moment, against the scene's own PNG output — and must not be read as "a stop never leaves a part file". Nobody has yet aimed a stop at the moment the scene's own image is being written, and that window is known to be real. **This was one frame, so there was nothing earlier on disk to survive**, and it says nothing about an animation: **Reports 12**, **Frames 3** and **Frames 15** all record that an animation's finished frames survive an interrupt, a terminate and a kill alike. The other two ways of stopping give different numbers — 1 for an interrupt, 137 for a kill.

The Linux run of this test did not interrupt anything: with adaptive sampling left on, the render converged and finished by itself before the stop signal arrived, so the complete file and the exit 0 it recorded describe a render that ended normally. What that run does still establish, and it holds: **a finished image records the sample count that was asked for, not the one that was reached.** 5.3 on the Mac shows the same: its run with adaptive sampling on finished by itself at 960 samples, and its image says 100000.

**Saving render output can be switched off from 5.2.** Asked for by name in 4.5, 5.0 and 5.1 the switch is simply absent, and the render goes ahead and writes as usual. In 5.2, turning it off stops the scene's own frames being written even when a place is named on the command line — while a **File Output node in the same tree keeps writing**. Run in all four versions on both machines. **It differs.** The test is recorded under **The compositor**, **Reports**, **Writing** and **What a render demands**. 5.2's release notes state the addition, and 5.2's manual describes errors being raised when no output method is left; that second half is documented and untested. This topic did not try the switch in 5.3; **The compositor 2** and **Reports 1** record 5.3 tests of it.

**Three failures could not be produced on either machine, in any version.** A graphics card running out of memory, attempted three ways on the mended card and defeated by the machine's own memory giving out first. The words "No compatible GPUs found for Cycles", which need a backend that finds nothing on a machine with a screen: on the Mac the preferences offer only None and Metal, and set to None the panel shows the two buttons and nothing else, in 5.3 as before. And the build-dependent OSL and Embree messages. Every tested build has OSL, and none reports an Embree option. The lines `Cycles built without Embree support` and `CPU raytracing performance will be poor` were observed in 4.5's own Cycles files; whether it reaches a user is inferred and untested. Its absence from the other supplied source descriptions does not establish that Blender removed it. These are silences in what could be tried. **They are not differences between versions and nothing above or below treats them as any.** What a render does when a project file it needs is missing is also not established by these findings.

## 5. Where can each of the things above be learned from — what a render prints while it works, what it leaves on disk, or what can be asked afterwards?

The three places are printed output, files on disk, and answers from a running Blender: what is printed is the only place that names the part of the computer that did the work; what is left on disk names the engine only through Cycles' own four fields and, from 5.0, an OpenEXR attribute; what can be asked afterwards answers about the moment you ask and never about a render that has been. 5.3 adds a shipped OpenEXR module that can read saved headers from Blender's own Python.

**Everything below about what a render prints comes from a render started from the command line.** A render started instead by calling the render operator from inside a script prints no progress line at all in 5.0, 5.1 and 5.2 — no samples, no tiles, no stages — while still printing `Saved:` at the end, and 4.5 prints its full progress whichever way the render is started. Settled under **Reports 9**, which records 5.3 printing no progress on that route either; this topic did not ask it of 5.3. What becomes of the lines that name the engine and the device under that route was never captured.

**With no window, everything a render prints goes to standard output and the error stream stays empty** — in all four versions on both machines, and in 5.3 on the Mac. The exceptions are the same on both machines: the invalid-format complaint and the unknown-engine refusal in every version, and in **4.5 only**, the device line and the `--cycles-device` messages. An unknown argument's line goes to the error stream too, in 4.5, 5.2.2 and 5.3. **It differs**, and the difference is 4.5's.

**`--cycles-print-stats` goes to standard output in every version**, with the error stream at zero bytes — the opposite of what Cycles' own help text for the switch says, in every version, and the manual says only "log". Both machines for all four, processor runs and graphics runs, and 5.3 on the Mac, processor and Metal. **The same everywhere.**

**`--log-level` takes a number in 4.5 and a name in 5.0, 5.1, 5.2 and 5.3.** 4.5's manual describes it as taking a number and the other three describe it as taking a name from a list of six, and the test agrees with all four, in all four versions on both machines; 5.3's manual names its `info` level, and 5.3 took `info` on the Mac. Given a name, 4.5 says it is not a number, puts that on the error stream, and then **renders anyway and exits 0** — the refused switch does not stop the run. **It differs.**

**`--log-list-categories` does not exist in 4.5 and does exist in 5.0, 5.1, 5.2 and 5.3.** The manual carries it for 5.0, 5.1 and 5.2 and 4.5 never mentions it, and the test agrees, in all four versions on both machines. 5.3 has it on the Mac too. In 4.5 it is treated as a file name and the run fails. In the others it exits cleanly and lists the categories, and the list grows with the version. **It differs.**

**The list is a fact about the operating system and about the version, and both halves have been measured.** macOS returns fewer categories than Linux for the same version, and carries Metal-flavoured graphics categories where Linux carries OpenGL and Vulkan ones: 5.0 gave 135 entries on the Mac against 169 on Linux, 5.1 gave 139 against 173, and 5.2 gave 149 against 182. **5.3 gave 153 on the Mac**, three runs identical; 5.2.2 on the same Mac the same day gave 149, as 5.2.0 had. Against 5.2.2, 5.3 adds `geom.annotations`, `gpu.metal`, `io.otio`, `io.spz`, `project` and `seq.edit`, and drops `geom.gpencil` and `gpu.debug.metal`. **It differs**, at 5.3, on the Mac. So the list grows with the version on both machines, and shrinks on the Mac at every version compared. One entry is not settled: 5.2.0's Mac reading lists `gpu.metal` beside `gpu.debug.metal`, and 5.2.2 carries only the second, so whether `gpu.metal` arrives at 5.3 or was already in 5.2.0 is open.

**One named entry can be dated to a version on Linux.** Each version's Linux list was searched for `gpu.opengl`, three runs per version, identical to the byte each time: **absent in 5.0, present in 5.1, present in 5.2**, with no such switch at all in 4.5. 5.0 was run as the control on the same machine on the same day, and it is what the search came back empty on — so the search works, and the entry arrives at 5.1. **It differs.** This is one machine's answer. On the Mac the entry is absent in 5.3 and in 5.2.2; the Mac's earlier versions were not searched for it, and 5.3 has no Linux list.

The three categories that matter here — the one for add-ons, the one for Cycles and the one for rendering — are on both machines in every version that has the switch, and on the Mac in 5.3. **A plan that hard-codes any other category name, taken from one machine or from one version, may not find it on the other.**

**`--log-show-memory` is described in the supplied manual extracts for 5.0 to 5.3; no test was run on it in any version.** Whether 4.5 has it is not established by that silence.

**The render handlers behave identically in all five versions.** All six exist; they fire in the order init, pre, post, write, complete; the frame is already on disk when the write handler fires; the cancel handler does not fire on a finished render; and every handler written to accept any number of values is handed two rather than the one the documentation describes. Both machines for all four; 5.3 on the Mac. **The same everywhere.** A statistics handler written to take one value works too, and is handed the progress string alone — in 5.3 and in 5.2.2 on the Mac; not tried earlier.

**What the statistics handler is handed differs between 4.5 and the rest.** 4.5, 5.0 and 5.1's documentation describes the `render_stats` handler as carrying render and saving time plus, in background mode, the frame and used and peak memory; 5.2's and 5.3's describe something different — the render progress as a string holding the current frame, the current sample, the render time and the saving time. What the test found: 4.5's string carries the frame number, the current memory and the peak. The 5.0, 5.1, 5.2 and 5.3 strings keep current memory — for example, `Mem: 0M | Synchronizing object | Cube` — and carry neither the frame number nor peak memory. The frame number sits in the printed line's `Fra:` prefix, which the handler never sees. The strings are identical in shape across 5.0 to 5.3. The last string is the closing time line in every version. **The first and last statistics strings do not carry a sample count.** The intermediate strings under **Reports 3** and **Reports 11** do: the handler carries a sample count, with the maximum beside it, whenever a sampling stage is running, in every version they ran. 5.3's strings carry it the same way. Both machines for all four; 5.3 on the Mac. **It differs** — and 5.2's reworded documentation describes something that was already true in 5.0 and 5.1, so that rewording on its own is a documentation change and nothing more.

**With a window open, 5.2 and 5.3 hand over the whole stream and the others hand over one string.** Counted with the render driven the same way in both halves: with no window, 4.5 gave 42 calls, 5.0 and 5.1 gave 43 each, and 5.2 and 5.3 gave 44. With a window open, 4.5, 5.0 and 5.1 gave **one** call each, and 5.2 and 5.3 gave **44** — in 5.3 the same strings in the same order as with no window, one `Remaining:` figure aside. The control that makes this a window result rather than a way-of-rendering result is that the same script run with no window gave the same counts as the plain command-line render. Run on the Creator's Mac, the only machine with a screen. **It differs** — established on one machine, and on that machine only. Whether it holds on Linux is untested everywhere, which is not a difference either.

**The tested loaded-image attributes expose no metadata; 5.3 ships another route for OpenEXR — observed.** In every version the image loads and reports its size, and none of its inspected attributes holds the fields — identical in all four versions on both machines and in 5.3 on the Mac. But 5.3 ships an `OpenEXR` module, which its release notes name: inside 5.3 with no window, asked to read a written OpenEXR's header, it returned every field — the stamp fields, Cycles' four fields, `Software` — matching what the file's bytes hold. Its own description covers OpenEXR files only, and nothing here reads a PNG's fields that way. 5.2.2 on the same Mac has no such module. **It differs**, at 5.3, on the Mac.

**And the panel the manuals name does not exist.** Every version's manual describes a Metadata panel in the Image editor that lists an image's fields. Asked what sidebar panels the Image editor defines, a running Blender lists five tabs and no metadata panel among them, in all five versions; asked the same of the whole program, the only two panels anywhere whose label mentions metadata belong to the Asset Browser and to Output Properties. Run on the Mac, and photographed there in 5.3. **The same everywhere** — a route every version's manual names could not be found in any running Blender.

## 6. At what point can each of the things above be learned — before a render starts, while it runs, or only once it has finished?

All five document the render handlers. Placing settings and printed lines in time also includes inferred steps; the observations below settle only the runs and machines named. Settings and descriptions of the machine can be read at any time; progress and statistics arrive while the render runs. The final render time and final peak memory are only complete at the end. No supplied documented description establishes the complete handler order; 5.3's sources do not say when `--cycles-print-stats` prints. Two version-specific notes exist, both in 5.0's sources, both about 5.0.0 rather than the 5.0.1 that is installed, and both untested: a fix titled "show currently rendered frame in background mode", and a fix for a crash when a background run asked whether a job was running.

**Which parts of the computer are available can be learned before a render starts, in all five versions**, from outside the window. The card can be listed by the Cycles preferences before anything is rendered, and it comes back identically in all four versions; in 5.3 on the Mac the preference already reads Metal at factory startup, but the device list is empty until something asks for it, and lists the processor and the Metal graphics once asked. The report describing the machine can be written at any moment. **The same everywhere.**

**Which part actually did the work can only be learned once the render has finished, in all five versions.** The line that names it is a closing report, printed after the last sample and before the frame is written. Established on the Linux machine with its card working, and in 5.3 on the Mac, on the processor and on Metal. **The same everywhere.** **A completed frame's closing report does not establish what a frame genuinely cut short prints.** Under **Frames 15**, with the fullest logging on, a Control-C on the Creator's Mac gives 5.0 and 5.1 the whole `Full path tracing report:` block, device line included, after the stop and before the process goes — but in those runs the frame's own sampling completed inside the wait, so the report was reached. 5.2 and 5.3 print `Rendering was canceled.` there and no block — 5.3 line for line as 5.2 — and 4.5 prints no report at any level. What a frame **genuinely cut short** prints at that logging level is recorded nowhere, 5.3 included; Frames 15 records its ordinary lines. And 5.2's own bug-fix list calls that block on exit fake with wrong numbers — the 5.0 run bears that out, its block reporting 600 samples for a frame the line above it calls 599 — so nothing establishes that the device name inside it is right.

**A refused `--cycles-device` stops the run at one of two points.** In 5.3 on the Mac, a name Cycles does not know is refused as the first line printed, before the file is read; a real backend with no hardware behind it is refused only once the file is read and the render has begun, before the first sample. Both end with exit 1 and no frame. The earlier versions' records carry the same words without placing them in the run. **Not established for every version.**

**The frame in hand is knowable while a background animation runs, in every version — but not by the same means.** 5.0, 5.1, 5.2 and 5.3 print a line of its own announcing each frame before rendering it. 4.5 has no such line; the frame number sits in the prefix of every progress line instead. Both machines for all four; 5.3 on the Mac. **It differs.** 5.0's own corrective notes describe this as a fault mended in 5.0.1, which is the build tested, so nothing here speaks for 5.0.0.

**`--cycles-print-stats` prints once per frame, not once per run.** In 5.3 on the Mac, three frames gave three `Render statistics:` blocks, each at the end of its frame and before the next frame is announced, and three `Update statistics:` blocks, one early in each frame. 5.2.2 on the same Mac gave the same, line number for line number. The statistics lines carry no time of their own, so where exactly a block falls against the `Saved:` line beside it is not established. Not run in 4.5 to 5.2.0. **Not established for every version.**

**The handler order is identical in all five versions**, with the frame already on disk when the write handler fires, and the same order holds with a window open on the Mac — where the post and write handlers arrive after the last statistics call and the completion handler after them, in 5.3 as before. Both machines for all four; 5.3 on the Mac. **The same everywhere.**

**Asking whether a job is running works with no window in all five versions**, returning a value and not crashing. Both machines for all four; 5.3 on the Mac. **The same everywhere** — and since both installed 5.0 builds are 5.0.1, this says nothing at all about 5.0.0, which is what the corrective note was about.

**The add-on report describes the moment it is written**, not the start of the session — established in all four versions on both machines and in 5.3 on the Mac.

**The peak memory and the render time reach disk when the frame is written**, in all five versions; the write handler finds the file already there. Both machines for all four; 5.3 on the Mac. **The same everywhere.** In 5.3, once an OpenEXR is written its fields can also be read back from Blender's own Python — question 5.

**One line arrives before the render begins on the Linux card, in all four versions**, announcing how much of the machine's memory Blender is willing to lend the card. It needs `--debug-cycles` in 4.5 and `--log-level info` in the newer three, and a run with no switches never prints it. The figure reproduced exactly in all four. 5.3 was not run on that machine. Whether anything is said when that memory is actually used is not settled and could not be on either machine.
