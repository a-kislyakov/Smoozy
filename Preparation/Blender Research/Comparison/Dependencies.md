# Dependencies — Blender 4.5, 5.0, 5.1, 5.2 and 5.3 side by side

What a `.blend` file points at outside itself, how those locations are written down and found again, and where the five versions part company.

## The machines behind the tests

**The Creator's Mac** is a MacBook Pro with an Apple M1 Pro chip, Apple's own graphics and no second card. Earlier runs used 4.5.12, 5.0.1, 5.1.2 and several 5.2 builds; the operating system also changed between sittings. An earlier result is bounded to the build and system used for that run.

**Blender 5.3 ran on this Mac alone:** 5.3.0 Beta, hash `5d8151335b6b`, built 2026-10-16, under macOS 26.6.2, with 14-core Apple graphics (Metal) and 16 GB of memory. Its window was driven by scripts and simulated pointer and key events. No later 5.3 build was tried. **The 5.2.2 run** means a control using the same test on this same Mac, in Blender 5.2.2 LTS, hash `d13f752e3b9c`. It answers only for that build on that Mac.

**The rented Linux machines are separate machines:**

- **First:** one NVIDIA GeForce RTX 4090 and a display. Questions 1 to 16, except question 8's names inside a file and question 14's file trace and memory readings. Exact build numbers and hashes are not recorded for this machine.
- **Second:** one RTX 4080 SUPER, no display server. Questions 17 and 18, question 8's names inside a file, and question 14's file trace and memory readings. Recorded as carrying the Mac's four versions, without hashes or a firm pairing of the moving 5.2 build.
- **Third:** one RTX 5060, no display server. Question 19. Recorded as carrying the Mac's four versions, without hashes or a firm pairing of the moving 5.2 build.
- **Fourth:** one RTX 3060 in Poland, with a display server for the window tests. Question 20. Builds matched the Mac: 4.5.12 `84afd5f785f7`, 5.0.1 `a3db93c5b259`, 5.1.2 `ec6e62d40fa9` and 5.2.1 `9e2066aef7ef`.

**The rented Windows machine** ran question 20 alone, in those same four versions with matching hashes. It reported **Windows Server 2025 Standard**, build 26100.32995, 24H2, 64-bit. It had two Intel Xeon sockets and no graphics card; nothing was rendered there. Its results establish nothing about a desktop edition of Windows.

**All four**, **every version**, **the four**, and **both machines**, unless 5.3 is named, mean 4.5 to 5.2; **the newer three** means 5.0, 5.1 and 5.2. **All five** includes 5.3. Both machines means the Mac and the Linux machine named for that question. Every Linux and Windows result is for 4.5 to 5.2 alone. A result settles only the tested machines, builds and setups, including their graphics hardware. Untested machines and systems are not version differences.

Most renders in questions 17 and 18 used Cycles on the processor. The light-probe test used EEVEE and therefore the machine's graphics. The Mac has no trace or memory measurement for these questions. No result from one rented machine should be treated as a result from another.

## The answer in short

### Where Blender itself differs between versions

*Tests involving 5.3 establish that beta build on the Creator's Mac alone. Changes stated in release notes are labelled separately under their questions.*

- **Path tools and property names:** the 4.5, 5.0–5.1 and 5.2–5.3 groups differ — question 1.
- **Archive libraries from 5.0; online asset libraries from 5.2; project, extension and authenticated asset libraries in 5.3** — question 2. The asset-library changes do not add a remote file pointer.
- **Path expansion in 5.2 and 5.3** — question 4.
- **Template variables from 5.0, and project variables and bake-folder templates added in 5.3's release notes** — question 5.
- **Longer data-block names from 5.0** — question 9.
- **File Output defaults and names, and the texture cache added in 5.2** — question 10.
- **Missing-input messages, the reports collection and EEVEE's engine name; 5.3's missing-strip icon is a release-note change** — question 12.
- **Library-list access from 5.2, and packed linked data's directness and saving rule changed in 5.3's release notes** — question 13.
- **Scenes referenced inside compositor node groups rendered from 5.3, by its release notes** — question 14.
- **Colour variables, spaces, flags and warnings; 5.3 adds properties and a colour space in the Mac tests, and project configuration, interoperability and sRGB ICC changes in its release notes** — question 15.
- **Point-cache compression differs among 4.5–5.2; 5.3 was not asked. Texture-cache tools exist from 5.2** — question 17.
- **The older point-cache compression and the availability of a texture cache** — question 18. Reading a 4.5 cache in 5.3 is untried.
- **Linked-data packing from 5.0** — question 19.
- **Save Modified Images from 5.2, the compression preference from 5.0, and initial support for unchanged files on opening and saving in 5.3's release notes** — question 20. The last change's reach is unknown.

### What is not established

- **Other machines, systems, graphics hardware and later builds:** especially 5.3 outside the Mac beta, and Windows outside question 20's Server-edition runs — all questions.
- **A complete inventory of outside references, and kinds named in only some versions** — question 1.
- **A real remote library, network share or online asset library** — questions 2 and 7.
- **Partial packing within one dependency, or comparison with a changed original** — question 3.
- **Sequence membership and expansion of absent files** — question 4.
- **Windows paths, separator storage, combined forms, tooltips and project variables; the two-variable bake fallback** — question 5.

- **Compiled OSL files in 5.0–5.1 under the connected setup, and untested unwritable destinations** — question 10.
- **Relocate on an indirect item, the Outliner menu label, and saved placeholders** — questions 11 and 13.
- **Untested missing-input kinds, exit-status exceptions and report presentation in 5.3** — question 12.
- **Depth beyond the tested chains, earlier Mac silence, and untested indirect-library cases** — question 13.
- **Other dependency kinds, cross-scene references, and Mac memory use** — question 14.
- **Colour-configuration storage and precedence, flag timing and untested warning tooltips** — question 15.

- **The path-walking function missing from 5.1's documentation is present in its running Blender** — question 20. Its absence in Blender 4.5 is a behaviour difference under question 1.

## 1. What kinds of thing can a `.blend` file point at outside itself? Give the full list.

**How it is known.** The named reference kinds are documented where quoted; the list being complete is unestablished or inferred. The seven-path file and the tool names were observed in 4.5 to 5.2 on the Mac and Linux, and in 5.3 on the Mac. The extra 5.3 dependencies below retain their own labels.

**Common documented kinds.** The inventories overlap but do not establish a complete, identical set. The earlier versions name another `.blend` file (a library, and a weak reference to one); image and movie files; sound files; font files; volume files; cache archives and their extra layers; text files; OSL shader scripts; IES light profiles; external displacements for the Multires and Mesh Cache modifiers; physics point caches; fluid cache folders; geometry-node bake folders; ocean bake folders; dynamic-paint output folders; sequencer image-strip folders and movie-strip files; proxy folders for strips and for movie clips; render output; bake output; the compositor's File Output node; collection exporters; a brush icon; a node socket whose value is a file path; and the record kept with a packed file. Blender 5.3's list names the same kinds apart from the brush icon, and adds some of its own, each a silence in the other records rather than a difference: collection importers beside the exporters; the Cycles texture cache's `.tx` files, which its API marks as a separate kind of path; the OSL shader for a custom camera; and four dependencies described without a file path — the colour configuration (question 15), the active project, the file that defines an asset's catalog, and an OSL shader given by module name alone. The asset's dependence on its catalog definition is **inferred**; the other named mechanisms are documented where stated.

The test agreed in all four, and again on the Linux machine. A file built with an image, a sound, a font, an OpenVDB volume path, an OSL script path, an IES light-profile path and a text file returned exactly the same seven paths in every version on both machines, and `file_path_map()` returned the same seven non-empty rows. The render output path `//renders/frame_` appeared in neither list, in any version on either machine. Asking for library paths as well changed nothing, anywhere.

**5.3 on the Mac gave the same seven** in both listings, the render output path in neither, and the same rows with library paths asked for. `blend_paths` alone listed an eighth: a weak reference into the Blender application itself, `//../../../../../../Applications/Blender 5.3b.app/Contents/Resources/5.3/datafiles/assets/brushes/essentials_brushes-gp_draw.blend`, recorded relative to the blend-file by climbing six folders and carried by the starting scene's own material, which the build left in place. The 5.2.2 run of the same build on the same Mac listed the same eighth path in the same way, so it belongs to the build and not to 5.3; it is the same file the crossing below found.

**Two API and setup limits.** `bpy.utils.blend_paths` accepts no `include_libraries` keyword in any of the four versions on either machine — that keyword belongs to `file_path_map`, where it was used. And the light's IES profile could not be set on the Linux machine the way the Mac's file set it, because that setting does not exist in these builds, so an IES Texture node was used instead; the path appears in both lists either way.

**One thing only the crossing could show.** A blend-file saved on the Mac and opened on Linux listed, among its own paths, a path into the Mac's own Blender application — `/Applications/Blender 4.5.12.app/…/essentials_brushes-gp_draw.blend`, a folder that exists on no Linux machine. It comes out of the file rather than out of the running Blender, and Report Missing Files does not name it.

Two smaller things came back the same everywhere. `Text.filepath` is the one path property no version's documentation marks as taking the `//` prefix, yet the test stored the text file's path as `//assets/notes.txt` in all five — so it takes the form anyway. And the manual's data-block table marks Cache File and Volume with a dash in the Pack column in every version while the API gives both a path, which every version's findings report as a tension in their own sources rather than resolving. **The dash does not mean the type has no file**: the column's own legend says packing is "not applicable for **most** data-blocks which have no file reference" — most, not all.

**5.3 was asked whether a volume packs, and the answer is only half yes.** On the Mac, Pack All packed a real OpenVDB file into a Volume data-block (`Info: Packed 1 file(s)`), and the packed mark survived a save and an opening, with the packed listing naming the volume's path. But with the file on disk gone the volume loaded no grids (`'smoke.vdb not found'`), and a Cycles render with no window came out pixel for pixel as if the volume were not in the scene, saying nothing. With the file put back it rendered. Whether the saved blend-file holds the volume's bytes at all was not read. No earlier version was asked.

**Where it differs, version by version.** In the machinery, settled by tests run in all four.

**Blender 4.5.** No `bpy.data.file_path_foreach` — asking for it raises an error. No `Library.is_archive`, no `Library.archive_libraries`, no `bpy.data.colorspace`, no `WindowManager.reports`. The compositor's File Output node carries `base_path`, `active_input_index`, `format`, `save_as_render`, `file_slots` and `layer_slots`.

**Blender 5.0 and 5.1.** `bpy.data.file_path_foreach` is present — 5.0's release notes record it as added — along with `Library.is_archive`, `Library.archive_libraries` and `bpy.data.colorspace`. `WindowManager.reports` is still absent. The File Output node carries `file_output_items`, `active_item_index`, `directory`, `file_name`, `format` and `save_as_render`; asking it for `base_path` fails outright, and `Scene.node_tree` no longer exists either — the compositor tree is reached through `Scene.compositing_node_group`.

**Blender 5.2.** Everything 5.0 and 5.1 have, plus `WindowManager.reports`, and the File Output node also carries `use_file_extension`.

**Blender 5.3.** Everything 5.2 has, each asked for by name on the Mac, `Library.archive_parent_library` among them, and the File Output node carries the same seven properties as 5.2's. `Scene.node_tree` is still gone. Setting or reading `Scene.compositing_node_group` printed `DeprecationWarning: 'Scene.compositing_node_group' is expected to be removed in Blender 6.0`; whether 5.2 prints it was not asked, so that is not a difference between versions.

Present in all five, checked by name — in 5.3 the last three by being used rather than asked for: `bpy.data.file_path_map`, `bpy.utils.blend_paths`, `bpy.ops.file.pack_libraries`, `bpy.ops.file.pack_all`, `bpy.ops.file.report_missing_files`, `bpy.ops.file.find_missing_files`, `bpy.ops.outliner.id_linked_relocate`, `Library.parent`, `ID.is_missing`, `ID.library_weak_reference`, `bpy.path.resolve_ncase`, `SequenceEditor.show_missing_media`, `Volume.filepath` and `VolumeGrids.error_message`.

**Verdict: it differs.** The tool names and the compositor's folder property differ. The seven kinds in the test file matched; a complete inventory of what every version can point at is not established. Anything driving Blender from outside meets this immediately. 4.5 stands alone, 5.0 and 5.1 together, 5.2 and 5.3 together. **Settled by the same test run in all four versions on the Creator's Mac and again in all four on the rented Linux machine, with no row differing between the two machines** — though the Linux file's light was built differently, as above — **and in 5.3 on the Mac.** Windows is untested, and so is 5.3 on Linux.

**Not established.**

- **Whether any version's list is the whole list.** Every version says so in its own words, and no test can close it: the test file was built to hold seven kinds, so a kind nobody thought to include would not have appeared.
- **Geometry-node import nodes as a kind a file points at.** Documented for 5.0, 5.1, 5.2 and 5.3; absent from 4.5's findings. No release note says they were added and no test touched them. **A silence, not a difference.**
- **`Camera.custom_filepath`.** Documented for 5.0, 5.1 and 5.3; absent from 4.5's and 5.2's findings. Same reading.
- **A brush icon.** Documented for 4.5, 5.0 and 5.1; absent from 5.2's and 5.3's findings. Same reading again — nobody looked and found it gone.
- **The active project, the asset catalog's definition file, and collection importers.** Named by 5.3's findings alone. 5.3's release notes record several project features as new — project asset libraries, project path variables, a project's own colour configuration — but none says projects themselves are new, so whether a file in 4.5 to 5.2 can rely on a project is unanswered rather than answered no.
- **Whether a packed volume is used once its file is gone, in 4.5 to 5.2.** Only 5.3 was asked.

## 2. What kinds of library can a file point at, including one that does not sit on the same computer?

**How it is known.** Library forms are documented; the archive and asset-library additions are stated in release notes. Archive properties and packing were observed on the tested machines. A file holding an online asset rather than a remote pointer is inferred from the append-and-pack descriptions. Real network-library behaviour is unestablished.

**The same in all five.** A `.blend` file points at exactly one kind of library: another `.blend` file. Every version describes it in the same words — an external `.blend` from which data is linked, with a path to that file. Every version also carries a second, weaker pointer at a `.blend`: the weak reference kept after appending, so already-appended data can be reused instead of appended again. Every version says an asset library is a directory registered in the Preferences, which is a setting of the machine and not something a file points at. And no version's sources give any network-address form for a library path — no share syntax, no host name, no address of any kind.

**Where it differs, version by version.**

**Blender 4.5.** One kind only. `Library.is_archive` and `Library.archive_libraries` do not exist in this build; the test raised nothing for them because they are simply absent.

**Blender 5.0, 5.1, 5.2 and 5.3.** A second kind of `Library` data-block exists — the archive library, which holds linked data-blocks that have been packed into the current file, is owned and managed by the real library it came from, and exists so that packed data does not collide by name. Blender 5.0's release notes record this as new in 5.0. The test confirms both names are present in 5.0, 5.1 and 5.2 and absent in 4.5; in 5.3 all three archive names — `is_archive`, `archive_libraries` and `archive_parent_library` — answered present on the Mac, and question 19 shows what packing makes there.

**Blender 5.2 and 5.3, additionally.** Asset libraries may be online, identified by a URL rather than a directory, and downloaded on demand. Blender 5.2's release notes record this as new. But 5.2's own manual says twice that linking is not supported for an online asset library — assets must be appended or packed, and each remote `.blend` must be self-contained with its textures packed inside it. 5.3's manual says the same: linking is not supported for an online asset library. **So an online asset library is still not a library a file points at.**

**Blender 5.3, additionally.** Its release notes add asset libraries defined by a project, asset libraries delivered as extensions, and asset-library servers that can require a login. All three are asset libraries — a setting of the machine — so none is a new kind of library a file points at. 5.3's records also describe a library whose data stays editable though linked, used for brush assets; no earlier record mentions it, which is a silence and not a difference.

**Verdict: it differs.** Blender 4.5 has one kind of library data-block; 5.0 to 5.3 have two, the second being the archive library. A release note carries it, and the same test settles it in all four versions **on both machines** — the two archive-library names came back on the rented Linux machine exactly as on the Mac — and in 5.3 on the Mac.

**Not established.** The whole of the second half of the question — what a library that does not sit on the same computer means. No version's documentation covers it, and it could not be tested in any version: there is no folder on network storage that two of this project's machines can reach at the same moment. The one adjacent thing that is settled is what each version does with a path naming a volume that is not mounted, which is under question 7.

One more adjacent thing was asked of 5.3 alone, on the Mac. A web address given as a library — `https://example.invalid/lib.blend` — was refused with `OSError: load: https:/example.invalid/lib.blend failed to open blend file`, the address printed with one slash after the colon, and no library was recorded. The same address given as an image's location was kept as typed through a save and an opening, loaded nothing, and Report Missing Files printed it with one slash. The address was one that cannot exist, so whether Blender would try to reach a real one is not shown, and no earlier version was asked.

## 3. Can a file hold the things it depends on inside itself partly rather than wholly, and what does a partly-held file report when it is read?

**How it is known.** Per-item packing is documented. Silence on opening, image loading, path listings and missing-file reports are observed results: Mac and Linux in 4.5 to 5.2, Mac alone in 5.3. No source establishes a single report saying a file is partly packed.

**The same in all four.** Yes — packing is per item, not all or nothing. Every version's manual describes packing a single file with the gift-box icon beside its path field, and unpacking one the same way. Every version carries the sweeping operations alongside it, and every version says the packing does not happen when you ask for it but on the next save. Every version states the same limit: some files, such as videos in the sequencer and movie clips, cannot be packed at all, so a fully packed file is not always achievable. Every version records that linked libraries are packed by a separate command from ordinary resources. 5.3's records say the same, name text files among the kinds that cannot be packed, and add that a geometry-nodes bake is packed or kept on disk bake by bake.

The behaviour, tested in all four with no window, was identical:

- Nothing at all was printed when a partly-packed file whose files are gone was opened.
- The packed image survived its original being gone — a packed file present, a size of 32 by 32, its data loaded. The unpacked one reported no packed file, a size of zero, and no data.
- Report Missing Files worked with no window, returned success, and printed one line naming the missing path and the local data-block it came from, in the same words in every version.
- Listing the file's paths without packed data returned the unpacked one alone; listing them with packed data returned both.
- A Cycles render of the same file finished with exit status 0 in every version.

**5.3 on the Mac gave the same at every point.** Opening the file printed nothing about it — the only line was Blender's own naming the file it read; the packed image loaded at 32 by 32 from its packed copy and kept its recorded path `//assets/packed.png`; Report Missing Files named only the unpacked image, in the same words; the two listings matched; and the Cycles render ended with exit status 0, printing the missing-image lines given under question 12.

With the window open, the same in all four and on both machines: the packed image carried a small preview of itself in the browse list and the unpacked one carried none; the plane using the packed image rendered in its own colour and the plane using the unpacked one rendered bright magenta; the unpacked image showed an empty checkerboard in the Image editor; and Report Missing Files put on screen word for word the same warning the terminal shows.

**Beside a packed image's file-path field on Linux**, the row was photographed both ways round. With the packed image selected it reads: the image icon, the name field, a shield, a two-sheets copy button, **a stack of boxes**, and an X. With the unpacked image selected the row is identical except that where the stack of boxes was there is **a plain folder** — the ordinary open-a-file button. So the packed one carries a parcel and the unpacked one carries a folder, and that is the whole visible difference beside the name. The window was photographed in all four versions, but the row itself was enlarged only from the 4.5 and 5.2 pictures; what is said for 5.0 and 5.1 is read across from those two.

**Through 5.3's window on the Mac**, with the viewport in Material Preview: the packed plane in its own blue and the unpacked one bright magenta, an empty checkerboard in the Image editor for the unpacked image, and the same row beside each name — **a stack of boxes** for the packed image and **a plain folder** for the unpacked one, each photographed twice in a run of its own. Report Missing Files, called from a script inside that window, printed its warning to the terminal and put nothing in the status bar in the picture taken a second later. The earlier window runs had a person use the menu, and there the warning came up on screen; the two routes are not the same, so how the report reaches the screen in 5.3 is not established.

One difference of machinery does not change the answer. `WindowManager.reports` does not exist in 4.5, 5.0 or 5.1. It exists in 5.2 and 5.3, and after Report Missing Files ran its length was zero in both — the warning went to the terminal, not into that collection. So **no version puts the report there**, and the answer to the question is the same in all five. The existence of the collection is recorded under question 12, where it belongs.

Two further partly-held cases were met in 5.3 and belong to other questions: a packed volume, which keeps its packed mark and is not used once its file is gone (question 1), and a file left partly packed by Automatically Pack Resources (question 20).

**Verdict: the same everywhere.** A file can hold its dependencies partly, item by item, with some kinds that can never be held inside. A partly-held file reports nothing of its own accord when it is read — you have to ask, and when you ask, every version names the missing unpacked file and the data-block that wants it, in the same words with a window and without one. **It rests on both machines for 4.5 to 5.2** — the same tests run in all four versions on each, agreeing throughout — **and on the Mac for 5.3**. Windows is untested, and so is 5.3 on Linux.

**Not established.**

- **Whether a packed copy and a still-present original that differs are compared on load.** Every version's documentation mentions a differs-or-identical status only in the context of unpacking. Untested on every machine.
- **Whether a single dependency can be held inside only in part.** Blender 5.0's findings looked for this specifically and found nothing; 5.3's say an image can hold one packed part per UDIM tile and per view, and mark it inferred that this is partial packing within one image; the others do not address it. Untested on every machine.
- **How Report Missing Files reaches the screen in 5.3.** Called from a script inside the window, it showed nothing there; nobody used the menu.

## 4. Can one thing a file points at mean several files on disk?

**How it is known.** One path standing for several files is documented. The available tools, flags and sequence and tile expansion were observed on the Mac and Linux in 4.5 to 5.2, and on the Mac in 5.3. The expansion flags are also a stated 5.2 release-note addition.

**The same in all five.** Yes, in several ways, and every version names the same ones: an image data-block whose source is a sequence, standing for many numbered files; an image whose source is UDIM tiles, where one written path carries a `<UDIM>` or `<UVTILE>` token standing for many tiles; a volume sequence, one file per frame; a cache archive that is separated into a series of files, and one that carries several layers each with its own archive; a sequencer image strip, which records a folder and a list of names; a physics point cache, which records a folder and a naming pattern; one render output path, which becomes one file per frame and, with multiple views, one per view. 5.3's record names the same and adds a movie clip pointing at an image sequence, the fluid cache folder and geometry-node bake folders, which the others leave out without saying otherwise.

The storing came back identical in all four, and **in 5.3 on the Mac word for word the same**:

```
   image=shot_0001.png  source=SEQUENCE  stored='//seq/shot_0001.png' tiles=[1001]
   image=tile.1001.png  source=TILED     stored='//tiles/tile.<UDIM>.png' tiles=[1001, 1002]
```

Blender rewrote the tiled image's path into the token form on its own in every version, and in every version both `blend_paths()` and `file_path_map()` returned the un-expanded text — so neither of those two ways of listing a file's paths tells you the real files.

A volume whose file is not there answered identically in all five: not loaded before, `load()` returned false, still not loaded after, the error message read `'smoke.vdb not found'`, and the frame's own file path came back empty.

**Where it differs, version by version.** In whether Blender will expand one recorded path into the files it stands for.

**Blender 4.5.** It cannot be asked. `bpy.data.file_path_foreach` does not exist; the call raises an error.

**Blender 5.0 and 5.1.** The path walk exists and visited the three un-expanded paths. There is no expand option: probing the accepted flags returned exactly `SKIP_LINKED`, `SKIP_PACKED`, `RESOLVE_TOKEN`, `SKIP_WEAK_REFERENCES`, `SKIP_MULTIFILE`, `RELOAD_EDITED`. The information handed to the callback carries no mark saying whether a path was expanded or is a cache.

**Blender 5.2.** The same probe returned three more flags — `EXPAND_TOKENS`, `EXPAND_SEQUENCES`, `EXPAND_CACHES` — and with them the walk visited the three actual sequence files and the two actual tiles as absolute paths, each marked as expanded. Blender 5.2's release notes name the three as added, and say plainly what they are for: so render farms and other scripts can find all the image files a render needs.

**Blender 5.3.** The same as 5.2, on the Mac: the probe returned the same nine flags, and with the three expand flags the walk visited the three sequence files and the two tiles as full paths, each marked `is_expanded=True`. The function's own description in this build gives its default as skipping packed data and weak references.

**Verdict: it differs.** The answer to the question itself — yes, one recorded thing can mean several files — is the same in all five, and so is how the path is stored. What differs is whether Blender will tell you which files: 4.5 cannot be asked, 5.0 and 5.1 answer with the un-expanded text only, and 5.2 and 5.3 expand. **Settled by the same test run in all four versions on both machines** — the flag probe returned the same list on each, and 5.2's expansion visited the same three sequence files and two tiles — **and in 5.3 on the Mac**, and corroborated by 5.2's release notes.

**Not established.**

- **How Blender decides which files on disk belong to a sequence** — the numbering rule in the general case, and what happens when only some members exist. Every version leaves this open, and no test on either machine touched it.
- **Whether the expansion in 5.2 and 5.3 visits files that do not exist.** Only present files were on disk during either test.

## 5. In what ways can a recorded location be written?

**How it is known.** The named path forms and template additions are documented, including the OSL module-name form in 5.3. OSL lookup was also observed in Cycles' own files in earlier versions. Expansion, stored spellings, renders and window results below are observed, with their machine limits. The manual and API disagree on which places accept templates in 5.3.

**The shared forms behave the same in the tests below.** Extra forms asked only of 5.3 establish no comparison with earlier versions.

Documented in every version: a full path from the system's root; a path relative to the blend-file, written with a leading double slash, which cannot be used in a file that has never been saved; `#` characters standing for the frame number, with the count of them setting the padding; `<UDIM>` and `<UVTILE>` tokens in angle brackets standing for tiles; and template expressions in curly braces, substituted at the moment the path is used so that the braces stay in the field, with a format specifier allowed after a colon and a literal brace written doubled. Two more forms are named by four versions each and unmentioned by the fifth, which settles nothing about that version: `%` standing for a view name (named by 4.5, 5.1, 5.2 and 5.3), and, for OSL scripts only, a bare module name with no folder at all, looked up on a search path (named by 4.5, 5.0, 5.1 and 5.3). Every version's manual records the same restriction on templates: they work only in the render output path and the compositor File Output node's output paths — though 5.3's own API and release notes add a third place, under *Where it differs*. Every version records that relative resolution inside a linked library is measured from the library, not from the file you opened.

The behaviour, tested identically in all four and identical whether the file was saved with path remapping on or off:

```
NAME=absolute       STORED='<BASE>/proj/assets/tex.png'   ABSPATH='<BASE>/proj/assets/tex.png' SIZE=(8, 8)
NAME=relative       STORED='//assets/tex.png'             ABSPATH='<BASE>/proj/assets/tex.png' SIZE=(8, 8)
NAME=relative-up    STORED='//../outer/tex.png'           ABSPATH='<BASE>/proj/../outer/tex.png' SIZE=(8, 8)
NAME=backslash-rel  STORED='//assets/tex.png'             ABSPATH='<BASE>/proj/assets/tex.png' SIZE=(8, 8)
NAME=tilde          STORED='~/smoozy-path-test/tex.png'   ABSPATH='~/smoozy-path-test/tex.png' SIZE=(0, 0)
NAME=dollar-var     STORED='$SMOOZY_DEP_TEST/tex.png'     ABSPATH='$SMOOZY_DEP_TEST/tex.png' SIZE=(0, 0)
NAME=dollar-brace   STORED='${SMOOZY_DEP_TEST}/tex.png'   ABSPATH='${SMOOZY_DEP_TEST}/tex.png' SIZE=(0, 0)
NAME=drive-letter   STORED='C:/textures/tex.png'          ABSPATH='C:/textures/tex.png' SIZE=(0, 0)
NAME=no-such-mount  STORED='/Volumes/NoSuchShare/tex.png' ABSPATH='/Volumes/NoSuchShare/tex.png' SIZE=(0, 0)
```

A size of 8 by 8 means the file was found; 0 by 0 means it was not. So, the same in all four: every form is stored exactly as typed at the moment it is assigned; a relative path may climb above the blend-file's own folder with `//../`; a home-directory shorthand is stored as typed and never expanded; an environment variable in either form is stored as typed and never expanded; and backslashes come back as forward slashes.

**When the re-spelling happens is not settled here, and this table cannot say.** Its readings were taken after a save *and* a reload, so they cannot tell one from the other. **Question 20** varied that condition on purpose, separating the process that built the file from a fresh one that opened it, and reading the path text out of the file's bytes as well as through Blender; it puts the change at the **reload**. That reading is itself a macOS result taken three times with one of the three disagreeing, so it is not firm either. **What is not in doubt is the outcome: after a save and a reload the backslashes read as forward slashes, in all four versions on both machines.**

**The Linux machine gave the same nine rows in all four versions, for both ways of saving.** Backslashes read as forward slashes there too; a home-directory shorthand and an environment variable in either form are stored as typed and never expanded; a drive letter is treated as an ordinary absolute path that finds nothing. **So every form of writing a location is stored and resolved the same way on macOS and on Linux.**

**5.3 on the Mac gave the same nine rows, for both ways of saving**, each spelling stored exactly as typed at the moment it was set. It was given four more, none of which any earlier version was asked about (the text as stored, not as Python prints it):

```
NAME=two-slash-server STORED='//server/share/tex.png'          ABSPATH='<BASE>/proj/server/share/tex.png' SIZE=(0, 0)
NAME=backslash-unc    STORED='\\server/share/tex.png'          ABSPATH='\\server/share/tex.png'          SIZE=(0, 0)
NAME=smb-url          STORED='smb://server/share/tex.png'      ABSPATH='smb://server/share/tex.png'      SIZE=(0, 0)
NAME=web-url          STORED='https://example.invalid/tex.png' ABSPATH='https://example.invalid/tex.png' SIZE=(0, 0)
```

So in 5.3 on the Mac a location typed `//server/share/…` is taken as relative to the blend-file; one typed `\\server\share\…` keeps its two leading backslashes and has its other backslashes turned to forward slashes; and an `smb://` or `https://` address is kept as typed and finds nothing. 5.3's own run puts the backslash re-spelling at the opening of the file rather than at the save (question 20).

**One thing about the drive-lettered form that neither machine had noticed before, and it happens on both.** Report Missing Files prints that path as `/c/textures/tex.png` while the stored text and the resolved path both still read `C:/textures/tex.png`. The warning and the stored value disagree. That is an operating-system-independent oddity, not a version difference — it came back the same in all four versions on both machines, and in 5.3 on the Mac. 5.3 does the same kind of thing to the two addresses: it prints `smb://` and `https://` with one slash after the colon, while the stored text keeps two.

Templates behaved identically in all four, on both machines. `//templated/{blend_name}_frame_` produced the real file name and made the folder. The same braces in an image texture path were left alone, stored and resolved with the braces still in them. A broken template in the scene's own output path, `//broken/{blend_name_frame_`, stopped both the path calculation and the render with the same message in all four, printed to the terminal on its own, and made no folder. **That is the scene's own write**; a broken template in a File Output node's name is a different case, and this topic never ran one. With the window open on the Mac the same thing appeared in all four: the field filled red, a tooltip carrying the same error text in red, an empty checkerboard where the render should be, and the same line in the Info log and in the status bar. With the window open on the Linux machine the field is filled solid red in 5.0, 5.1 and 5.2, with the same error on the terminal; in 4.5 the panel sat below the visible part of the editor there, so the 4.5 picture is the Mac's alone, and the tooltip needs a pointer resting on the field and could not be photographed on Linux at all.

**5.3 on the Mac, the same.** The template produced the real file name and made the folder; braces in an image path were left alone; the broken template stopped the path calculation and the render with the same message, printed on its own, and made no folder. Through 5.3's window: the broken field drawn red — measured, red about three and a half times the green and blue, against an even grey for a sound template — with its text in white; the tooltip was not reached, a pointer moved by Blender's own simulated events bringing none up; and a render started the way the menu starts it made no folder, put the error in the status bar after a red mark, in the Info log, and in the reports collection a script can read. Its render window held a plain grey picture where the earlier Mac pictures showed an empty checkerboard; the 5.3 window was 160 by 128, and whether size or version makes that difference is not established.

**Where it differs, version by version.** In which template variables exist, and where a template is taken.

**Blender 4.5.** Four: `blend_name`, `fps`, `resolution_x` and `resolution_y`. Its release notes record path templates as introduced in 4.5, enabled only on the scene's render output path and the compositor File Output node's output paths.

**Blender 5.0, 5.1, 5.2 and 5.3.** Ten. The four above plus `blend_dir`, `blend_name_lib`, `blend_dir_lib`, `scene_name`, `camera_name` and `node_name`. Blender 5.0's release notes name those six as newly introduced. The last three are restricted — `scene_name` and `camera_name` to render output paths, `node_name` to a path property on a node — and the two ending `_lib` exist for the library case, giving the name and folder of the library a linked data-block came from rather than of the open file.

**The variables were also asked for one at a time on the Linux machine, which turns a release note into a test.** Each name was put into a render output path in turn. Blender 4.5 accepted four and refused six, each refusal reading `Unknown variable referenced in template expression`. Blender 5.0, 5.1 and 5.2 accepted nine of the ten and refused only `node_name` — which is the one the documentation restricts to a path property on a node rather than a render output path. So the four-against-ten difference is carried by a test run in all four versions as well as by the release note. 5.3's manual lists the same ten, and 5.3 asked the same way on the Mac accepted nine and refused `node_name` — the same shape on a different machine. `blend_dir` gave the blend-file's whole folder as a full path, so placed after a relative prefix it repeated the folder inside itself.

**Blender 5.3, additionally — carried by its release notes.** They add `{project_root}` and variables a project defines. With no project active, `{project_root}` in the render output path was refused on the Mac as an unknown variable; whether it is taken with a project active was not tried. They also add template support for bake paths, and 5.3's API marks the geometry-nodes bake folder as taking templates, though its manual still names only the two places. On the Mac a bake folder `//gnbake/{blend_name}/` wrote the bake into a folder named after the blend-file. `//gnbake/{blend_name}_{scene_name}/` printed `Info: Cannot determine bake location on disk. Falling back to packed bake.`, wrote no folder, and the bake command still answered `{'FINISHED'}` — so a bake asked for on disk can end up packed in the file with nothing but that line to say so. No earlier version was asked about a template in a bake folder.

**Verdict: it differs.** The shared forms tested behave identically in all five, **on both machines for 4.5 to 5.2 and on the Mac for 5.3**. What differs is the vocabulary available inside a curly-brace template and where one is taken: four variables in 4.5, ten from 5.0, 5.3 included; and 5.3 alone adds project variables and a template in a geometry-nodes bake folder. Release notes carry all of it; the four-against-ten split is also a test run in all four versions on the Linux machine, and the bake folder a test in 5.3 on the Mac.

**Not established.**

- **What a Windows Blender writes into a path, and what a drive-lettered path made on Windows means elsewhere.** Not run on Windows for this question. What both machines here do with such a string is known and is the same, and what a Windows Blender writes into a recorded place at a save is under question 20.
- **Which separator character is actually stored in the file.** Not in the sources in any version. What is settled is only that a backslash typed in reads back as a forward slash after a save and a reload, on macOS and on Linux alike; **at which of the two steps it changes is question 20's, and is not firm there either**.
- **Whether several of these forms may be combined in one path.** No version's documentation discusses combinations, and no test tried one.
- **The number of forms.** Each version's records count them differently — four, five, six, seven or eleven, depending on whether packing, wholesale re-writing on save, and relative-to-a-library are counted as ways of their own. That is a difference in counting inside each version, not between versions.
- **What the tooltip on a broken output-path field says beyond the error text.** It needs a pointer resting on the field, which could not be done on the Linux machine at all, and a simulated pointer did not bring it up in 5.3.
- **Whether `{project_root}` is taken in 5.3 when a project is active.** Not tried.
- **Why a geometry-nodes bake folder holding two variables falls back to packing in 5.3** while one variable is taken. The fact is recorded; the cause is not.

## 6. What does a location recorded on one kind of computer mean on another, including a kind that names its disks?

**How it is known.** Relative and absolute forms are documented. Their portability across operating systems is inferred from nearby descriptions, not stated outright. The Mac-to-Linux crossing is observed in 4.5 to 5.2. In 5.3 only strings typed on the Mac were tested; no crossing was run.

**The same in all four.** Two documented facts, in the same words in every version: a relative path is measured from the folder of the referencing blend-file, which is what lets a blend-file and its subfolder of images travel together; and an absolute path is a full path from the system's root. Every version also finds the same near-miss and rules it out the same way — the OBJ and FBX exporters say absolute paths may only be correct on your own system, and that their relative mode works except when the target is on a different drive on Windows, but that is documentation of an exporter writing into a foreign format, not of what a `.blend` records or resolves. Every version finds the same two Python helpers, one that replaces the separator with the system's own and one that skips the `//` prefix for Windows compatibility, and every version notes that these are tools offered to a script writer rather than statements about what Blender itself does.

Both machines answer the drive-letter string the same way, identically in all four versions: a location typed as `C:\textures\tex.png` is stored as `C:/textures/tex.png`, resolved as `C:/textures/tex.png`, treated as an absolute path, and the file is not found. Nothing is printed about it until Report Missing Files is asked — and then it is printed differently again, which is under question 5. Same on macOS, same on Linux. 5.3 on the Mac did exactly the same with that string, and with a path naming a Mac volume that is not mounted. 5.3's documentation carries the two exporter lines and the two helpers as the others do.

**And the crossing itself was run, which is what the question asks.** A blend-file was built on the Creator's Mac in each version, saved so that every path stayed exactly as typed, carried whole to the rented Linux machine, and opened there. **The result was the same in all four versions**, and the three differences between the two machines are the whole answer:

- **A relative path survives.** `//assets/tex.png` and `//../outer/tex.png` both resolved against the file's new Linux folder and both loaded. Climbing above the file's own folder works the same on both.
- **An absolute Mac path does not survive.** It is kept exactly as written, resolved exactly as written, and not found. Blender does not rewrite it, does not translate it, and does not fail on it — it resolves to a place that is not there, and says nothing until asked.
- **A path written with capitals against a file named in small letters is found on the Mac and not on Linux.** That is question 8's answer and it belongs there, but it is also the sharpest thing the crossing showed.

A path naming a Mac volume behaves the same on both — kept, resolved unchanged, not found. A non-Latin path survives the crossing and is found on both (question 9). And a render given a Mac output path does not refuse on Linux: it builds the whole Mac-shaped folder tree at the root of the disk and writes into it (question 10).

**Verdict: not established for every version.** For 4.5 to 5.2 it is the same everywhere, for the crossing that could be tried: no version's documentation answers the question, but the same test was run in all four versions across two machines and came back identical in all four. How a recorded location is stored, and what it means when the file is opened on the other machine, is one behaviour in 4.5, 5.0, 5.1 and 5.2 alike, and what differs is the operating system, as set out above. **Blender 5.3 was never carried to another computer**, so what its locations mean there is untried; everything 5.3 did with the same strings on the Mac matches the earlier versions' Mac results. **Nothing here is a difference between versions.**

**Not established.** What a location written by 5.3 means on any other computer — the crossing above was not run in 5.3. Everything about Windows: what a Windows Blender writes into a path, whether a drive letter is kept verbatim on a system that has none, whether the separator is translated on load, and what a Mac-written or Linux-written path means when opened there. No Windows machine ran this question, in any version — the one Windows machine this topic reached ran question 20 alone. The reverse crossing — a file written on Linux and opened on the Mac — was tried only for the missing-font case (question 16) and not for the nine forms of path. And what form Find Missing Files writes a repair in, which 5.3's manual says is always a full path, is under question 8.

## 7. What does a location pointing somewhere other than the computer the file sits on mean, at either end?

**How it is known.** Actual network-reference behaviour is not in the sources and was not tested. The nearby browsing and output features are documented. The unmounted-volume result is observed on Mac and Linux in 4.5 to 5.2, and on the Mac in 5.3; it does not answer the network question.

**The same in all five.** Every version finds the same three adjacent facts and rules each one out the same way. The render-output page's render-farm hint says to set up a shared directory over a network file system and to disable overwriting and enable placeholders — that is about several machines *writing* to one place, not about what a recorded path means. The File Browser's bookmark list has a Volumes category covering drives and network mounts — a browsing convenience, not path resolution. And the extensions documentation gives a `file://` form for network shares on Windows — that is an extension repository index, not anything a `.blend` points at.

Two versions add one fact each that the others do not, and neither changes the answer: Blender 5.0's findings record a 5.0 bug-fix note saying that reading memory-mapped images from network drives could crash Blender when the file is not valid, which at least establishes that Blender does read images from network drives; and Blender 5.2's and 5.3's findings record their online asset libraries, which are reached by URL but explicitly cannot be linked to, so they are not a location a file points at. 5.3's record adds that its sources never say how a location that itself begins with two slashes is told apart from a relative one.

The test settled one narrow thing, identically in all four **and on both machines**, and in 5.3 on the Mac: a path naming a volume that is not mounted is kept exactly as written, resolved exactly as written, and the file is simply not found, with nothing printed about it until Report Missing Files is asked. 5.3 was also given three spellings that name a server, all on the Mac and none tried in an earlier version: `//server/share/tex.png` is taken as a path beside the blend-file and resolves into a folder `server/share` there; `\\server\share\tex.png` keeps its two leading backslashes and has the rest turned to forward slashes; and `smb://server/share/tex.png` is kept as typed. None was found, and each was named only when Report Missing Files was asked — the full rows are under question 5.

**Verdict: not established for every version.** Every version, 5.3 included, answers "not in the sources" for the question as asked, and it could not be tested anywhere. The reason is narrow: there is more than one machine, but no folder on network storage that two of them can reach at the same moment, so a location that really does point at the other machine could not be written or read. **The uniform test result about an unmounted volume is not an answer to this question** and must not be read as one.

**Not established.** Everything the question asks: whether Blender treats a path on a mounted network volume any differently from a local one; what the machine at the far end sees or must provide; permissions, locking, latency and partial reads; and whether a reference over a share is retried or given up on. And what a location starting with two slashes or two backslashes means on Linux or Windows, where 5.3 was not run.

## 8. Does the difference between capital and small letters in a name matter, and does it matter the same on every kind of computer?

**How it is known.** The case-repair helper is documented. A general case-sensitivity rule is inferred or unestablished in the sourced findings. The disk, repair and internal-name results below are observed on the named machines; 5.3 used two disks on the Mac and no other system.

**The same in all five.** The test used two places on one Mac: its ordinary disk, which does not mind capitals, and a case-sensitive disk image made for the purpose. On each, a file referencing `assets/Texture.PNG` was saved and then the file on disk was renamed to `texture.png`. The results were identical in all four versions, and in 5.3, where `diskutil` named the two disks `APFS` and `Case-sensitive APFS`.

On the ordinary Mac disk the stored path resolved, the image came back at 32 by 32 with its data loaded, the resolved path existed, `resolve_ncase` returned the path unchanged, and Report Missing Files said nothing.

On the case-sensitive disk the stored path resolved to the same text, the image came back at 0 by 0 with no data, the resolved path did not exist, `resolve_ncase` returned the real lower-case path, and Report Missing Files printed a warning naming the missing path and the data-block.

**And the same thing happens on the real crossing, in all four versions.** A file built on the Mac referencing `//assets/Texture.PNG`, with the file on disk named `texture.png`, was carried to the rented Linux machine and opened there. **On the Mac it loads. On Linux it does not** — the path does not exist, the image comes back at 0 by 0, and Report Missing Files names it. `resolve_ncase` returns the real small-letter file the moment it is asked, on Linux as on the Mac's case-sensitive disk image. So Blender knows how and does not do it on load. **This is a way a file that works on an artist's Mac stops working on a rented Linux machine, and it is not a version difference in any reading** — all four versions behave the same on each machine. 5.3 was not carried to Linux; on the Mac's case-sensitive disk image it behaved as the earlier versions did there.

**Find Missing Files minded capitals in the tested case-sensitive setups.** With a search folder holding a file named `texture.png` and the reference written `Texture.PNG`, it found nothing and changed nothing, in all four versions. With a search folder holding the right name, the same call repaired every other missing path — and **rewrote each repaired path as a full absolute path into the search folder**, leaving alone the paths that already resolved. It works with no window. This set-up cannot be posed on the Mac's ordinary disk, because there the capitals reference is not missing in the first place. **Reading a file 10** reaches the same question through a set-up the Mac can pose — the file put in a separate search folder, so that the reference is missing on either machine — and got the same answer there, in all four versions, with a control that recovered. **5.3 posed it on the Mac's case-sensitive disk image** and got the same answer: with a search folder holding only `texture.png` it printed `Could not find 'Texture.PNG'` and `Could not find 'other.png'`, answered `{'FINISHED'}`, and changed nothing; with the right names in a second search folder it repaired both, printing nothing.

**Find Missing Files repaired only relative paths in this topic's 5.3 runs.** The five paths repaired on Linux in 4.5 to 5.2 were all written in an absolute form rather than the blend-file's own `//` shorthand, and all five came back as full paths; in 5.3 on the Mac the two paths repaired had been recorded as `//assets/Texture.PNG` and `//gone/other.png` and came back as `//search2/Texture.PNG` and `//search2/other.png`, relative to the blend-file. The 5.2.2 run of the same steps on the same disk image did exactly the same. These Dependencies runs fit the repair keeping the form it found. None repaired both forms in one file, so that rule is not established by this topic. **5.3's own manual says the opposite of its own Mac result**: "Those recoveries will be done as absolute paths."

**Names inside a `.blend` file are told apart exactly, and that is the same on both machines and in all four versions.** A file was built holding three objects named `Cube`, `cube` and `CUBE`, three images named `Texture`, `texture` and `TEXTURE`, and three materials named `Mat`, `mat` and `MAT`. All nine survived being saved and opened again, as nine separate things. Asked for by the right spelling each was found; asked for by a spelling with the capitals moved about, `CuBe` or `TeXtUrE`, nothing was found. 5.3 on the Mac gave the same, and two objects made one after another as `Test` and `test` kept both names, neither renamed.

Asking another file for one of its objects by name behaves the same way, and **one of the two ways of asking says it went well when it did nothing**. Through `bpy.data.libraries.load` the right spelling gives the object and a wrong one gives nothing back, with a warning naming the file and the name it does not hold. Through `bpy.ops.wm.link` the right spelling links the object; a wrong one **answers `{'FINISHED'}`, prints nothing at all, and links nothing**. Same in all four versions, same on both machines, and the same in 5.3 on the Mac. Anything driving Blender from outside and trusting that answer will believe it linked something it did not.

**And the Mac's own disk was asked plainly what it does with capitals in a file name, with a control that could fail.** One image file named `tex.png` and one library file named `lib.blend` were each asked for by three spellings. Every spelling found the file — `tex.png`, `TEX.PNG` and `Tex.Png` all loaded the image at 32 by 32, and all three spellings of the library offered and linked its object — while a name that genuinely was not there failed and said so. The recorded spelling is kept exactly as written either way. Same in all four versions, and in 5.3.

**Verdict: the same everywhere, and the two halves pull in opposite directions.** Capitals matter or not according to the file system, not according to Blender. Blender does not attempt case-insensitive resolution itself when it loads a dependency — even though the helper finds the file the moment it is asked directly — and Find Missing Files does not do it either. A name **on disk** follows the disk: the Creator's Mac finds it whatever the capitals, and the rented Linux machine does not. A name **inside** the file is exact everywhere. So a file that records `Texture.PNG` for a file named `texture.png` works perfectly on the Creator's Mac and fails on the machine a render actually runs on — while nothing inside the file behaves that way at all. **None of this is a difference between Blender versions.** 5.3 matched at every point it was run — both of the Mac's disks, Find Missing Files on the case-sensitive one, and names inside a file — and it was not run on Linux, so that it fails there rests on 4.5 to 5.2 alone. Windows is untested here: the one Windows machine this topic reached ran question 20 alone.

**Not established.**

- **Whether 5.3 behaves on a Linux disk as 4.5 to 5.2 did.** Untried; the Mac's case-sensitive disk image is the nearest it came.
- **What form Find Missing Files writes a repair in.** Set out above: every run fits it keeping the form it found, and none tested that.
- **Which operating systems are which.** No version's sources name macOS, Windows or Linux in this connection; they say only "a case sensitive system". What the two machines do is known by test rather than from the sources.
- **Whether Windows behaves like either machine.** No Windows machine ran this question.

## 9. Do names written in characters outside the Latin alphabet survive being read out of a file, moved to another computer, and found again by a render?

**How it is known.** Storage rules and name limits are documented where stated; a cross-computer round trip is not. The longer name limit is a stated 5.0 release-note change. The round trip is observed from Mac to Linux in 4.5 to 5.2; 5.3 was read, rendered and moved only on the Mac.

**The same in all five.** How Blender stores such text. Every version that reaches the point states the same rule and the same deliberate exception: all strings in a blend-file must be UTF-8, but **paths are exempt**, because non-UTF-8 paths exist on real file systems and cannot be ignored — so reading a path out through Python can raise an encoding error, and the advice is to encode and decode paths with the file-system helpers and to print them through `repr` first.

The test agreed in all four, before and after moving the blend-file and its folder together to another place on the same Mac:

```
  repr(filepath)      = '//Тестовая папка/текстура_日本語.png'
  size                = (32, 32)
```

The bytes were plain UTF-8 in every version, the image was found in every version, and the rendered centre pixel was the texture's own red in every version, both before and after the move. Nothing was printed about the path in any version. **5.3 on the Mac gave the same**, with the same bytes before and after the move and the texture's red in both frames.

**5.3 was also given one name spelled two ways, on the Mac alone.** A file `café.png` was written with the é as one character, and the Mac's disk kept it that way; a location `//café.png` typed with a plain `e` and a separate accent mark was stored byte for byte as typed, and on the Mac's disk it found the file whose name is held the other way. No earlier version was asked, and no other kind of disk was tried.

**And the name survived the real move too.** A file built on the Mac referencing `//Тестовая папка/текстура_日本語.png` was carried whole to the rented Linux machine and opened there. The image was found, at 32 by 32, in all four versions, with nothing printed about the path on either machine. **One limit, stated plainly:** the two names were checked on the Mac's own disk before the copy and are the same bytes under either way of writing Unicode, because neither uses a combining accent. So this does not settle what happens to a name the two systems would store differently, which is the case that would actually break. 5.3 was not moved to another computer at all.

**Where it differs, version by version.** In how long a data-block name may be, which is the part of this question that bites hardest on non-Latin text, because those characters use more than one byte each.

**Blender 4.5.** Data-block names have a fixed length of 63 bytes — that is 63 plain ASCII characters, or fewer with diacritics or non-Latin glyphs.

**Blender 5.0, 5.1 and 5.2.** The same limit is 255 bytes. Blender 5.0's release notes record the change outright, saying names can now be up to 255 bytes, increased from the previous limit of 63, and adding a caution of their own: Windows file names stop at 255 characters, so a long data-block name used to build a file name can now more easily run into it.

**Blender 5.3.** 255 bytes, and here it was measured. 5.3's own manual gives two figures — its data-blocks page says 255 bytes, and its limits page lists `identifier: 63` among fixed strings used for data-block names. On the Mac a name of 300 Latin letters was cut to 255 bytes when it was made, and names of 100 Latin and 100 Cyrillic letters — 100 and 200 bytes — were kept whole through a save and an opening.

The limits on a *path* are stated the same in all five: a folder 767, a file name 255, a whole path 1023, with the same note that multi-byte characters use more than one.

**Verdict: it differs.** The round trip the question describes — stored, read out, moved, found again by a render — came back identical in all four, **and the move to another computer has been made, from macOS to Linux, in all four versions**; in 5.3 the same round trip came back the same on the Mac, with no move to another computer. The difference is the byte budget for a data-block name: 63 in 4.5, 255 from 5.0, 5.3 included, carried by 5.0's own release note and by the quoted limit in each version's manual, and measured in 5.3 on the Mac.

**Not established.**

- **The move to another computer, in 5.3.** Not run.
- **The move to Windows.** No Windows machine ran this question, in any version. Question 20 built such a name on Windows, where a save kept it whole in all four versions and it survived the crossing to the Mac and back in two of them, and rendered nothing.
- **What a path containing non-UTF-8 bytes becomes when opened on a system with a different file-system encoding**, and whether Blender normalises Unicode. Not in the sources in any version, and the names used in the crossing could not raise it, because they are the same bytes under either way of writing Unicode. 5.3's two-spellings test shows only that Blender kept the spelling it was given and the Mac's disk matched the other; whether any other disk would match is untried.

## 10. Are some of the things a file points at places it writes to rather than reads from, and where does such a write land?

**How it is known.** The write destinations are documented. OSL compilation was also observed in Cycles' own files, with an inferred step from code to a render writing there; connected-node runs directly observed the write in 5.3 and the 5.2.2 Mac control. Output and directory-creation results below are observed. The texture cache is a stated 5.2 release-note addition.

**The same in all five.** The list of write destinations, and every version names the same ones: the render output path; the compositor's File Output node; bake output; physics caches, which land by default in a folder named `blendcache_` plus the file's name, beside the blend-file, with a documented naming pattern inside it; geometry-node bakes, which may be packed into the file or written to a folder on disk; the ocean modifier's bake folder, which every version says is created if it does not exist; the fluid cache folder; dynamic paint's output folder; proxy folders for strips and for movie clips; collection exporters; and unpacking, which is a write back out to disk with a documented choice of destinations. Every version records the same rule for where such a write lands: a leading `//` means the folder of the file that holds the setting, and for a setting on library-linked data it means the library's folder. 5.3's record names the same and adds a Multires displacement saved externally, a texture bake saved to an external file, the texture cache, the compiled OSL file, and a save that may also write out changed pictures; it adds that a strip's proxies land by default beside the *source footage*, not beside the blend-file.

Two results came back identical in all four, and in 5.3 on the Mac:

```
A. file never saved. bpy.data.filepath = ''
   factory default render.filepath = '/tmp/'
   set render.filepath = '//never_saved_out/frame_'
   bpy.path.abspath now  = 'never_saved_out/frame_'
   frame_path(frame=1)   = 'never_saved_out/frame_0001.png'
   contents of the current working directory that look like output: ['never_saved_out']
```

So in an unsaved file the `//` prefix resolves to nothing at all, leaving a plain relative path, and the frames land in the folder the terminal was started from. And with the file saved and the output path naming a folder that does not exist, all four created the folder and wrote both frames into it. **The Linux machine gave the same answer in all four versions, including the same factory default of `/tmp/`.** 5.3 gave the same factory default and the same landing place, and from the command line it also made two missing folders deep in one go, saying nothing about either.

One more thing was the same in all five, on both machines for 4.5 to 5.2: the operator that updates an external shader script cannot be called with no window, and says so — it refuses because the context is wrong, in every version and both folders.

**And here is where a render lands when the path was written on the other machine.** A file whose render output path is a full Mac path, opened and rendered on the Linux machine, **does not refuse**. It builds the whole Mac-shaped folder tree at the root of the Linux disk, writes the frames into it, prints an ordinary `Saved:` line naming the Mac path, and finishes with success. Nothing said anything was unusual. The same in all four versions. **That is an operating-system fact and belongs in no version list.** One limit, stated plainly: every such run was made as a user who owns the root of that disk, so this test never asked what happens to a render user who cannot write there, and dropping file permissions does not test it because ownership is what allows the write. Where the folder already exists and refuses the write, the answer is known and is not this topic's: the render stops at the very first frame, the folder is left completely empty, and a windowless Blender ends with exit code 1, in all four versions on both machines — settled under **Writing**. The case this topic's own test raises, a folder Blender must **create** and cannot, is settled under **Writing 12**. 5.3 was not carried to Linux, and its run into a folder that cannot be written was not made: the tool the tests ran through refused the command that makes a folder read-only.

**Where it differs, version by version.** In two places, each settled by a test run in all four, and in 5.3 on the Mac.

**What the compositor's File Output node is called and what it writes.** The folder setting is `base_path` in 4.5 and `directory`, with a separate `file_name`, in 5.0 to 5.3; 5.2 and 5.3 also carry `use_file_extension`. Set up through the window the same way in each version, connected to the Render Layers node's image output, with its folder set to a folder that did not exist, it created that folder and wrote two frames in all four — but wrote different files:

```
4.5   Image0001.png       Image0002.png
5.0   file_name0001.exr   file_name0002.exr
5.1   file_name0001.exr   file_name0002.exr
5.2   file output0001.exr file output0002.exr
5.3   fo_window0001.exr   fo_window0002.exr
```

PNG in 4.5, OpenEXR in the 5.x versions, with nothing about the format changed by hand. In 5.2 and 5.3 the name is the blend-file's own — 5.3's file was `fo_window.blend` — and in 5.0 and 5.1 it is the literal `file_name`. 5.3's node was added through its window's node editor by a command from a script, and the rest set by script; it arrived with no output items, its folder filled in from the scene's render output path and its file name the template `{blend_name}`, and the animation was rendered inside the window.

**The format is the node's own starting value, and that starting value is itself the version change.** A freshly added File Output node starts on PNG in 4.5 and on Multi-Layer OpenEXR in 5.0, 5.1 and 5.2 — settled under **File output nodes 1** — and 5.3's started on multi-layer OpenEXR too. In multi-layer mode no socket name reaches the file and the single file takes the node's own base file name, which is exactly the pattern above.

**The Linux machine produced exactly the same four results with no window at all, which closes a question the Mac left open.** A File Output node was built by script, its folder set, connected, **saved**, and then rendered in a separate run with no window. It created the folder that was not there and wrote the files — `Image0001.png` and `Image0002.png` in 4.5, `file_name0001.exr` and `file_name0002.exr` in 5.0 and 5.1, `file output0001.exr` and `file output0002.exr` in 5.2. **So a File Output node does write with no window, in all four versions.** Two things fall out of it. The earlier script-built node that wrote nothing in the 5.x versions failed for a plain reason: in those versions the node arrives with no output items and so no usable input socket, and the link from the Render Layers node went nowhere; adding one output item first and linking to that makes it write. And 5.2's file carries the blend-file's own name because its `file_name` holds a template meaning exactly that — which the Mac run could see the effect of but not the cause. **5.3 on the Mac did the same with no window**: a node built by script, given one output item and saved, made its missing folder when rendered from the command line and wrote `fo_script0001.exr` and `fo_script0002.exr`, named after `fo_script.blend`.

**In 5.3's window the old command for making a compositor node group did nothing.** It answered `{'FINISHED'}` and made no group — its own description in that build says it is deprecated and will be removed in 6.0 — while the editor's **New** button made one. No earlier version's window run used that command, so this is a 5.3 result and not a difference.

**A new kind of write in 5.2 and 5.3.** Blender 5.2 documents a Cycles texture cache: `.tx` files stored by default in a `blender_tx/` folder next to the image file, generated and updated automatically when rendering if that is switched on — and the setting that switches it on, `use_auto_generate_texture_cache`, is documented as off by default. The folder is changeable by a preference and there is a command-line route of its own. Blender 5.2's release notes record it as new, and 5.2's path-walking flags gained an option specifically so that scripts can find these cache files. Nothing of the kind appears in 4.5's, 5.0's or 5.1's findings. 5.3 documents the same, and on the Mac it wrote the cache file beside the image — under question 18.

**The compiled OSL file, which is not a version difference.** In Blender 4.5, after a render, a writable folder holding `simple_col.osl` also held `simple_col.oso` — the compiled file landed beside its source. With that folder set read-only, no `.oso` appeared and the terminal carried `ERROR: error: Could not open "<path>/readonly/simple_col.oso"` and `Cycles shader graph: failed to read file <path>/readonly/simple_col.oso`; the render still finished and wrote a frame. In Blender 5.0, 5.1 and 5.2 no `.oso` appeared in either folder and nothing at all was printed about the script; the render finished and wrote a frame in every case. **The Linux machine gave word for word the same result in all four versions**, with one trap worth knowing: it is driven as a user who ignores file permissions, so the read-only half had to be run a second time with those permissions given up before the folder really refused the write. The first run wrote down the opposite of the truth.

**That is not enough to say the newer three write no compiled file.** Another topic watched the compiled file through seven stages, in all four versions on both machines, and found one in every version, rebuilt during the render — settled under **Reading a file**. The two set-ups are not the same: that one connected the Script node's output through a shader, so the script is really in the material, and this topic's record never says its node was connected to anything. So the version difference is **not established**.

**5.3 wrote the compiled file, with the node connected.** On the Mac, with the Script node's output linked through an Emission shader into the material, setting the node's path with no window compiled the script at once, gave the node its output and wrote `simple_col.oso` beside the `.osl`. With that `.oso` deleted, a render from the command line wrote it again, printed nothing about the script, and rendered the shader's own colour. **The 5.2.2 run of the same build on the same Mac did exactly the same.** So with the node connected 5.2 and 5.3 both write the compiled file beside its source, as the other topic found. The one difference on record between those set-ups and this topic's earlier 5.x runs is the connection; whether that is what kept the earlier runs from writing one is not recorded. The read-only half was not run in 5.3.

**Verdict: it differs.** Where an ordinary render lands, and what happens when its folder is missing, is the same in all five. One write is not: the compositor's File Output node writes a differently named file in a different format in each of the three groups — 4.5; 5.0 and 5.1; 5.2 and 5.3 — and the format it starts on is itself what changed at 5.0. **That was settled by the same test run in all four versions on the Creator's Mac and again in all four on the rented Linux machine, with the same result on both, and in 5.3 on the Mac.** Blender 5.2 and 5.3 additionally have a kind of write the others do not — the Cycles texture cache — recorded as new in 5.2's release notes and switched off by default; 5.3 wrote one on the Mac when it was switched on.

**Not established.**

- **Whether Blender 5.0 and 5.1 write a compiled `.oso` beside an external `.osl` at all.** This topic's test found none and printed nothing in 5.0, 5.1 or 5.2, on both machines, but its Script node is not recorded as connected to anything; a test that connected one found a compiled file in every version, and so did 5.3 and the 5.2.2 run here. Open in 5.0 and 5.1 within this topic.
- **What happens when any other write destination is not writable**, except for the OSL case in 4.5 and the documented note that a physics cache silently does not happen if the folder cannot be written to. 5.3's read-only runs were not made.

## 11. Can a reference point at a named thing inside another file, and what happens when that thing is renamed or is gone?

**How it is known.** Named links, missing-library placeholders and repair operations are documented. A rename breaking a link is documented or inferred in the sourced answers and directly observed in every version tested. The placeholder, render and menu results below are observed, with their stated machine limits.

**The same in all five.** Yes, references are by name, and the name is the whole identity. Every version records that a data-block's name is unique within its type and its file, that a weak reference stores the full name including the two type letters together with the library's path, and that the Python route for linking names the data-blocks it wants as strings. 5.3's record adds that an Alembic or USD cache points at a named object path inside its archive, and that most library-override data survives a lost reference, posed armatures being the noted exception.

The test agreed completely, in all four versions. With the whole library file renamed out of the way:

```
Unable to open '<path>/lib.blend': No such file or directory
Cannot find lib '<path>/lib.blend'
LIB: Collection: 'PropCol' missing from '<path>/lib.blend', parent '<direct>'
1 libraries and 1 linked data-blocks are missing (including 0 ObjectData), please check the Info and Outliner editors for details
```

With the library present and the named collection inside it renamed — and, separately, with it removed — the output was **exactly the same in both cases and in all four versions**:

```
LIB: Collection: 'PropCol' missing from '<path>/lib.blend', parent '<direct>'
0 libraries and 1 linked data-blocks are missing (including 0 ObjectData), please check the Info and Outliner editors for details
```

So a rename does break the reference, it is reported, and **nothing in what is reported tells a rename from a deletion**. The only number that separates the cases is the count of missing libraries: one when the whole file is gone, none when the file is there and the item is not.

In all three cases and all four versions what is left is a placeholder that keeps the name and the library and holds nothing:

```
   name='PropCol'  library='//lib.blend' is_missing=True is_library_indirect=False objects=[]
```

The count of evaluated instances dropped from four to three in every version, and a Cycles render still finished and wrote a frame in every version.

**5.3 on the Mac gave the same in all three cases**, line for line, in the newer message shape: `reports          | WARNING Unable to open '<path>/lib.blend': No such file or directory`, `reports          | Cannot find lib …`, the `LIB:` line, and `reports          | WARNING 1 libraries and 1 linked data-blocks are missing …` with the whole file gone, or the `LIB:` line and `… WARNING 0 libraries …` with the item renamed or removed. The same placeholder, instances from four to three, and exit status 0. Report Missing Files, asked as well, named the library as a data-block of the file (`LIlib.blend`) when the whole file was gone, and said `Info: No missing files` when only the item was — so it does not notice a missing item inside a library that is there.

With the window open the same in all four: the Outliner lists both libraries, and the ID Data submenu offers `Unlink`, `Make Local`, `Delete`, `Remap Users`, `Copy`, `Paste`, `Add Fake User`, `Clear Fake User`, `Rename`, `Select Linked`, `Relocate` — for the indirectly linked collection exactly as for the directly linked one, with Relocate not greyed out in either case, while three entries in the parent menu are visibly greyed. **5.3's window on the Mac showed the same eleven entries in the same order** for both collections, Relocate at full brightness for both, and three entries greyed in the parent menu — *Mark as Asset*, *Clear Asset* and *Clear Asset (Set Fake User)*. Two things about how it was reached: a simulated right click opened no menu in three tries, so the menus were opened by name from a script; and the entry leading to them is labelled **Data-block** where the earlier records name **ID Data**. Whether that is a renaming is under *Not established*.

**Verdict: the same everywhere.** A reference points at a named thing inside another file; a rename breaks it exactly as a deletion does and is reported in identical words; what remains is an empty placeholder marked as missing that keeps the name and the library; and the render still produces a frame. **It rests on both machines for 4.5 to 5.2**, the same test in all four versions on each, **and on the Mac for 5.3**. Windows is untested.

One difference in how it is said, not in what happens: in 4.5 those lines carry an `Info:` or `Warning:` prefix, and in 5.0 to 5.3 a `reports          |` prefix. That is the general change of message format recorded in full under question 12, not a separate finding here.

A named object path inside an Alembic file that is not there was tried in 5.3 alone, and is under question 12.

**Not established.**

- **Whether the Relocate entry does anything when used on an indirectly linked item.** The menu was photographed in all four on the Mac and the entry was never used; on Linux the operator's own test said it may run, but calling it changed nothing and an Outliner selection cannot be set from a script, so no result can be pinned to the item that was meant. In 5.3 the operator's own test answered that it may run with each collection chosen and with nothing chosen at all, so it tells the items apart no better, and the entry was not used. Open in every version.
- **Whether the menu entry 5.3 calls *Data-block* is the one 4.5 to 5.2's records call *ID Data*.** It leads to the same eleven entries. A renaming is likely and not established: 5.3's menu was opened by name from a script, the earlier ones by a person's right click, and no 5.2.2 run was made.
- **Whether the placeholder survives a save and reload**, and what it looks like inside the file. Silent in every version, untested on every machine.

## 12. What does a render do when something the file points at is not there, and does it say so anywhere?

**How it is known.** Specific missing-library, sequencer, volume-error and malformed-template cases are documented. Cycles' missing-image constant was observed in its own files; that alone does not establish a rendered image's colour. The render outcomes and messages below are observed. 5.3's EEVEE message differs from the 5.2.2 control on the same Mac; the strip icon is a release-note change and untested.

**The same in all five.** What the render *does*.

In the tested missing-image cases, the render did not stop. In all four versions and both engines it finished, wrote a frame and exited 0 on both machines. The plane whose texture was missing came out magenta, with the same centre pixel in every version — on the Mac, Cycles `(1.0, 0.1373, 1.0, 1.0)` and EEVEE `(1.0, 0.1294, 1.0, 1.0)`, against `(0.1373, 1.0, 0.1373, 1.0)` and `(0.1294, 1.0, 0.1294, 1.0)` with the texture present. **The Linux numbers are different because that scene was rebuilt by a script of its own with a different plane size and light distance, so the two sets of numbers must not be set against each other**; what matches is the shape — red and blue equal and green far lower with the texture gone, green high with it present, in all four versions. **5.3 on the Mac rendered the missing texture magenta in both engines too**, exit status 0: Cycles `(1.0, 0.7412, 1.0, 1.0)` and EEVEE `(1.0, 0.7333, 1.0, 1.0)` against `(0.7412, 1.0, 0.7412, 1.0)` and `(0.7333, 1.0, 0.7333, 1.0)` with it present. Those numbers come from a scene of its own and are not to be set against the earlier Mac numbers; the 5.2.2 run of the same scene gave 5.3's numbers exactly. The shape is the same.

The rest, also identical in all four, and in 5.3 on the Mac wherever it was asked: a missing font still renders, exit status 0, with the letterforms lost rather than falling back to the built-in font; a missing linked library still renders a frame, with placeholder data-blocks in place of what is gone; a missing volume answers `grids.load() = False` and `grids.error_message = 'smoke.vdb not found'`; a partly-packed file whose files are gone prints nothing at all when opened; Report Missing Files works with no window and prints the same warning naming the path and the data-block, in the same words with a window and without one; and a broken template **in the scene's own output path** stops the render with the same message in all four, printed to the terminal and, with a window, shown in the tooltip, the Info log and the status bar. (In 5.3 the tooltip was not reached; the rest is under question 5.)

**In 5.3 every render with something missing ended with exit status 0 and wrote its frame**, across more kinds than any earlier version was asked about: an image in both engines, a font, a linked library, an item inside a library, a library that arrived indirectly, an Alembic file, a named object inside an Alembic file, an IES file, an OSL file and a sound. The kinds no earlier version was asked about, and what each said, all on the Mac:

- **An Alembic file gone**: `Could not open as Ogawa file from provided streams.`, `Unable to open <path>/assets/cube.abc` and `object.modifier  | WARNING Object: "AbcCube", Modifier: "MeshSequenceCache", Could not create cache reader for file //assets/cube.abc`, each twice; the object drew its own mesh instead of the cached one.
- **A named object inside an Alembic file gone**, the file there: `Alembic: unknown how to handle objects of schema '', skipping object ''` and the same reader warning, each twice — the path not named — and the same picture as with the whole file gone.
- **An IES file gone**: `cycles           | ERROR Could not read IES file from <path>/assets/light.ies`; the picture changed slightly.
- **An OSL file gone with its compiled `.oso` left beside where it was**: nothing printed and the same picture as with both there. **Both gone**: `ERROR: error: Input file "<path>/assets/shader.osl" not found` and `cycles           | ERROR Shader graph: failed to read file <path>/assets/shader.oso`; the picture changed.
- **A sound gone**: nothing printed. The render writes no sound, so the picture could not have shown it.
- **A library that arrived indirectly gone**: the load named it and counted it, the render still finished — under question 13.

One more thing came back the same in all four, on both machines, and in 5.3 on the Mac, and is worth having on its own: on a sequence editor made from a script, the missing-media switch reads **on**, although the property's declared default is **off**. So the "default False" every version's documentation quotes is not what a newly made sequence editor actually carries.

**Find Missing Files, with no window.** Find Missing Files works with no window, returns success, and in 4.5 to 5.2 rewrote every repaired path — each of them recorded as a full path to begin with — as a full path into the search folder, leaving alone the paths that already resolve. It does not match a name case-insensitively (question 8). Same in all four versions. In 5.3 on the Mac, and in the 5.2.2 run there, paths recorded relative came back relative; what form a repair takes is set out under question 8.

**Where it differs, version by version.** In what is said, and in where it can be read.

**Blender 4.5.** Cycles says **nothing at all** about a missing image. The whole run contains no mention of the file; the only line naming it is the ordinary progress line `Updating Images | Loading green.png`. EEVEE prints one line, `GPUTexture: Blender Texture Not Loaded!`. Messages generally carry the older shape — `Info:` and `Warning:` prefixes for reports, and `WARN (module): source/path/file.cc:line function:` for warnings from inside Blender. `WindowManager.reports` does not exist; reading it raises an error.

**Blender 5.0.** Cycles prints `cycles           | ERROR Image file '<path>/assets/green.png' does not exist.` — with the path in quotation marks. EEVEE prints `gpu.texture      | ERROR Failed to create GPU texture from Blender image`. Messages carry the newer shape, a module name and a level separated by a bar. `WindowManager.reports` does not exist.

**Blender 5.1.** The same as 5.0, except that Cycles prints the path **without** quotation marks. `WindowManager.reports` does not exist.

**Blender 5.2.** Cycles prints two lines instead of one: `cycles           | WARNING Image file <path>/assets/green.png does not exist.` followed by `cycles           | ERROR Failed to load 1 image files` — so 5.2 downgrades the individual file to a warning and raises a separate error that counts the failures. EEVEE prints the same line as 5.0 and 5.1. `WindowManager.reports` **exists**, and 5.2's release notes record it as new — but after Report Missing Files ran, its length was zero, so that warning still goes to the terminal and not into the collection.

**Blender 5.3.** Cycles prints the same two lines as 5.2. **EEVEE prints `image.gpu        | ERROR Image file "<path>/assets/green.png" does not exist`** — a different module, and the file named, in quotation marks — where **the 5.2.2 run of the same scene on the same Mac printed 5.2's `gpu.texture      | ERROR Failed to create GPU texture from Blender image`**. With a window, opening a file whose image is missing printed the same new EEVEE line once the viewport drew in Material Preview. `WindowManager.reports` exists and stayed empty after Report Missing Files, with no window and when called from a script inside a window; after a render inside the window was refused for a broken output template it held that error (question 5). **5.3's release notes add one thing on screen**: a sequencer strip whose media is missing or broken now shows the strip's type icon where its thumbnail would be. Nothing tested that.

**Verdict: it differs.** What a render does is the same in all five; what it says is not. Between 4.5 and 5.0 the whole message format changes, and 4.5 alone is silent about a missing image texture in Cycles. Between 5.1 and 5.2 the severity of that message changes and a counting line is added. **At 5.3 EEVEE's line changes and names the missing file.** Only 5.2 and 5.3 have a place a script can read Blender's reports from, and even there the missing-files warning does not land in it — which was checked on Linux with a window open as well as without one, and in 5.3 on the Mac. **Settled by the same test run in all four versions on the Creator's Mac and again in all four on the rented Linux machine, where every message came back the same; and in 5.3 on the Mac, where EEVEE's line differed from the 5.2.2 run of the same test there.** The strip icon rests on 5.3's release notes alone. Windows is untested, and so is 5.3 on Linux.

**One more version difference, recorded here because it turned up in this test and anything driving a render from outside meets it.** **The engine name used successfully on the command line in these tests is** — `BLENDER_EEVEE_NEXT` in 4.5, `BLENDER_EEVEE` in 5.0, 5.1, 5.2 and 5.3. What this topic ran was the command line, in all four versions on both machines and in 5.3 on the Mac, where `BLENDER_EEVEE` is the only EEVEE name offered. Which of the two names a version will *also* accept depends on how the engine is set, and that is not this topic's result.

**Not established.**

- **Whether a missing dependency ever changes the exit status.** Every version returned 0 in every case tested, on both machines, and 5.3 on the Mac across the most kinds; no case was found where it did not. That is true of missing inputs and of nothing wider.
- **What a missing Alembic file, Alembic object path, IES file, OSL file or sound does in 4.5 to 5.2.** Only 5.3 was asked.
- **What a placeholder linked data-block renders as.** Not in the sources in any version; the test shows only that the render still produces a frame.
- **Where a report goes with no window in 4.5, 5.0 and 5.1.** The collection that would hold it does not exist there; the messages reach the terminal, but nothing establishes that as the general rule.
- **How Report Missing Files reaches the screen in 5.3.** Called from a script inside its window, it printed to the terminal and showed nothing in the status bar; nobody used the menu, which is how 4.5 to 5.2's window runs put it on screen (question 3).
- **Whether the floating error panel over the render window is a version difference.** The Creator's screenshots show a floating `Report: Error` panel in the 5.1 and 5.2 shots and not in the 4.5 or 5.0 ones. The findings say plainly that whether this is a difference or a matter of when the picture was taken is not reported. **Do not read it as a difference.**

## 13. Does a file pointing at another `.blend` file bring that file's own references with it, how deep does that go, and can they be reached the same way?

**How it is known.** Library-relative paths and indirect links are documented or inferred in the sourced answers; no source gives a depth limit. The chain, render and menu results below are observed. The library-list addition in 5.2 and packed-data change in 5.3 are stated in release notes; no 5.3 test checked either.

**The shared chain tests agree in all five.** The untested cases remain open below.

A chain of eight files, seven libraries deep, resolved completely in every version. The load printed one line per level naming each library and its parent, and the recorded parent chain was complete from the deepest file to the top. At twenty files, nineteen libraries were recorded with a complete parent chain in every version. Every object below the top was marked as indirectly linked, in every version. **5.3 on the Mac gave the same** for a chain built with collection instances, at eight files and at twenty.

Where a path inside a library is measured from came back identically in all five, 5.3 on the Mac, and it is the most consequential result in this question:

```
   name='img.png'  stored='//tex/img.png'      library='//../L1/L1.blend'
      abspath WITHOUT library arg: '<path>/L8/tex/img.png'
      abspath WITH    library arg: '<path>/L8/../L1/tex/img.png'
      size=(32, 32)
```

Only the second names a real file. A tool that forgets to say which library a path came from gathers the wrong path, in every version, and this held at twenty levels as well as at eight.

The render is where the depth shows, and it showed the same in all four:

```
files=7  LIBS 6  centre_rgba=(1.0, 0.6275, 0.1373, 1.0)
files=8  LIBS 7  centre_rgba=(1.0, 0.6275, 0.1373, 1.0)
files=9  LIBS 8  centre_rgba=(0.0, 0.0, 0.0, 1.0)
```

The first colour is the texture's own; the last is an empty frame. At nine files the object stops arriving in the render in every version, while the library records and the paths still resolve. At twenty files the frame was empty too. **The Linux machine gave the same boundary in all four versions**, with the same complete parent chain at eight files and at twenty, and the same wrong-path trap above. **5.3 on the Mac gave the same boundary**: the texture's colour at seven and eight files, an empty frame at nine and at twenty, exit status 0 every time, and ten evaluated instances in every chain from eight files up.

**What is printed when the object stops arriving.** The Mac's runs of 4.5 to 5.2 recorded that nothing was printed. On the Linux machine the load prints `Warning: Maximum instance recursion level reached` in the object's name, from eight files upward, in all four versions. **5.3 on the Mac printed it too** — twice on reading from eight files up, naming `"Prop"` at eight, `"I2"` at nine and `"I13"` at twenty, and once more while rendering at nine — and **the 5.2.2 run of the same chains on the same Mac printed the same**. So the warning appears on both kinds of machine, and the earlier Mac record of silence is the one that does not fit; what made it silent is not recorded. None of this is a difference between versions.

**And this is what causes the boundary.** The same chain was built a second time with **no collection instancing at all** — each level links the level below and puts it in as a child collection rather than as an instance, so the number of linked files grows and the nesting of instances does not. Nineteen libraries deep the object still arrives, the texture still renders, and nothing is printed, in all four versions. **So the boundary is set by the nesting of collection instances, not by the chain of linked files.** That is a test rather than a reading of the message. **One limit:** in 4.5 to 5.2 that second shape of the chain was built and run on the rented Linux machine only. **5.3 ran it on the Mac** and got the same: the object arrived at eight, nine and twenty files, with no warning. So the cause is settled on Linux for 4.5 to 5.2 and on macOS for 5.3.

**Built that way, the chain records no parents.** In 5.3, with child collections rather than instances, every load line named its library's parent as `'<direct>'` and every library read `parent=None`, at eight files and at twenty. A chain of three files built the same way gave the same once the top file was reopened, though in the run that built it the deepest library's parent read as the middle file. No earlier version's record says what a chain without instancing records as parents.

**A missing library that arrived indirectly**, asked in 5.3 alone, on the Mac. With the deepest file of a three-file chain moved away, the load named it and counted it — `WARNING Unable to open '<path>/base.blend': No such file or directory`, `Cannot find lib …`, `LIB: Collection: 'BaseCol' missing from …` and `WARNING 1 libraries and 1 linked data-blocks are missing …` — and left a placeholder for its collection, marked missing and indirectly linked, holding nothing. Report Missing Files named it as a data-block of the top file, `LIbase.blend`, and a render finished with exit status 0.

With the window open the same in all four: Relocate is offered, and not greyed out, for the indirectly linked collection exactly as for the directly linked one — which is a plainer offer than every version's documentation makes, since all four quote the same note saying the operation is only available on data-blocks that are directly linked and are not a dependency of any other linked data. **5.3's window on the Mac showed the same**, its menu reached under an entry labelled *Data-block* (question 11), and 5.3's documentation carries the same note. 5.3's Outliner, in its Blender File view, listed both libraries under *Current File*, and with only collections shown it drew the indirectly linked collection inside the directly linked one, under the middle library's entry.

**Where it differs, version by version.** In one added capability, and in one change 5.3's release notes make.

**Blender 4.5, 5.0 and 5.1.** To see the libraries a file uses, you open the file.

**Blender 5.2 and 5.3.** `bpy.data.libraries.load()` hands back, on the way in, the list of other libraries the loaded file itself uses — each as a path and a mark saying whether it is an archive library. Blender 5.2's release notes record this as newly exposed, and give a worked example in which the paths come back relative. The same page records that packed linked data-blocks are not linkable and do not appear in that list. 5.3's API describes it in the same words; no 5.3 test read it.

**Blender 5.3, additionally — carried by its release notes and untested.** A linked item that has been packed into the file now counts as directly linked if a local item uses it, or if another packed item that is itself directly linked uses it; and writing linked data now writes only directly linked packed items. So which packed linked data a saved file keeps follows a rule 5.3 changed.

**Verdict: it differs.** Everything the question asks about how deep the chain goes, what comes along, and how paths inside a library are resolved came back identical in all five, **on the Creator's Mac and again on the rented Linux machine for 4.5 to 5.2, and on the Mac for 5.3**. The difference is that 5.2 and 5.3 let a script read a file's own library list without opening the file, which 5.2's release notes record as added — for anything that gathers a job's files before sending it anywhere, a real difference in what can be done — and that 5.3, by its release notes, changes which packed linked items count as direct and are written.

**Not established.**

- **Any maximum depth.** Not in the sources in any version. The tests show recording works to at least nineteen libraries and that the render stops bringing the object at nine nested collection instances, in all four versions on both machines and in 5.3 on the Mac.
- **Whether the cause of that boundary holds on macOS in 4.5 to 5.2.** The chain built without collection instancing was run in those four on the Linux machine only. 5.3 ran it on the Mac.
- **Why the Mac's runs of 4.5 to 5.2 printed nothing when the object stopped arriving**, when the Linux runs, 5.3 and the 5.2.2 run on the Mac all print a warning.
- **Whether 4.5 to 5.2 leave a placeholder for a missing library that arrived indirectly, and what parents they record for a chain built without instancing.** Only 5.3 was asked.
- **Whether Relocate does anything when used on an indirectly linked item.** Photographed in all four on the Mac and never clicked; on Linux the operator's own test said it may run, but calling it changed nothing and an Outliner selection cannot be set from a script, so no result can be pinned to the item that was meant. In 5.3 it was not used.
- **What the ID Data menu holds beyond what was photographed.** It needs a pointer resting on a control, which could not be done on the Linux machine; in 5.3 it was opened by name.

## 14. Does rendering one scene of a file pull only that scene's references?

**How it is known.** The general question is not answered by the sources. Cross-scene features are documented; their needing the other scene's files is inferred. The tested image and library results are observed by the separate machine readings below. Rendering scenes referenced inside compositor node groups is a stated 5.3 release-note change, untested here.

**The same in all five.** Rendering one scene of a two-scene file said nothing about the other scene's missing image, in every version, on both machines, and in 5.3 on the Mac.

**Where that test stops, and why it is not a difference.** In 5.0, 5.1 and 5.2 the control run — rendering the *other* scene, where the missing file certainly is reached — did name the file, on both machines, so the silence in the first run means something there. **In 4.5 the control said nothing either, on either machine**, because 4.5's Cycles never names a missing image at all (question 12). So 4.5's silence carries no information, and that test does not settle this question for 4.5. **That is the shape of a trap, and it must not be written down as 4.5 behaving differently.** A test that cannot come out the other way settles nothing.

Even where the control worked, the evidence was one-sided in every version: it shows that a render of one scene does not complain about the other scene's missing file. It does not show the file was never opened. An image's loaded-state and size readings after the render do not settle this: the loaded-state reading was false for both, and asking for size loaded both images.

**Two readings that could each come out either way answer it, and neither of them asks Blender anything.** They watch the computer instead, so 4.5's silence stops mattering. The file was the same shape in both: one `.blend` with two scenes. SceneA has a plane whose material uses one image; SceneB has a plane using a second image, and also an object linked from a third file, a `.blend` library. Both scenes render with Cycles on the processor, one sample, 64 by 64.

**On the second rented Linux machine every render was run under a trace that records every file the program opens.** In all four versions, rendering SceneA opened SceneA's image and never opened SceneB's; rendering SceneB opened SceneB's image and never opened SceneA's. The linked library was opened both times. The same run was also measured a second way: the image only SceneB uses was swapped for one of 6000 by 6000, and the peak memory of the SceneA renders did not move, while the SceneB control jumped by between about 145 and 225 MB depending on the version. Both readings agree, and both controls worked.

**On the Creator's Mac neither of those readings could be taken** — a file-activity trace there needs an administrator password, and the Mac was shared with other work all through the sitting, so a memory figure would have measured the machine rather than the render. **A third reading was used instead: the time the disk records for when each file was last read.** The three files were set to one old moment, one scene was rendered, and the times read back. In all four versions, rendering SceneA moved the time on SceneA's image and on the library and left SceneB's image untouched; rendering SceneB did the mirror image of that. Both controls worked, and that the disk records access times at all was checked first on an ordinary text file.

**5.3 on the Mac gave the same by both of the Mac's readings.** With SceneB's image moved away, rendering SceneA chosen by `--scene` said nothing about it, while the control, rendering SceneB, printed 5.3's two missing-image lines for it — so in 5.3 the silence does carry information. And by the disk's access times, rendering SceneA moved the time on SceneA's image and on the library and left SceneB's image untouched, and rendering SceneB did the mirror image, with the access-time check run first on a text file. No trace and no memory reading were taken in 5.3.

**So: rendering one scene does not open the other scene's image at all.** A `.blend` linked as a library is opened whichever scene is rendered, because it is read when the file is loaded rather than when a scene is drawn. **The same in all four versions, on both machines, by two different readings, and in 5.3 on the Mac** — and the readings are kept as separate results rather than folded into one, since each answers only for its own machine.

**Where it differs — carried by a release note and untested.** Blender 5.3's release notes record that the compositor now renders scenes referenced inside node groups. That is one more way a render of one scene can reach another scene, and so need its files, which 4.5 to 5.2 did not have by that note's own wording.

**Verdict: it differs, in that one way; the part these tests reach is the same everywhere.** Blender 4.5 to 5.3 all read only the rendered scene's own image, and all read a linked library either way. The one small thing that is not identical is a count and not a behaviour: 5.2's trace shows it opening its own scene's image six times where the other three open it four times; 5.3 was not traced. What differs is that 5.3, by its release notes, renders scenes referenced inside compositor node groups. Windows is untested, in every version, and 5.3 on Linux is untried.

**Not established, and the verdict above does not reach it.** The tests cover an image used by a scene's material and a `.blend` linked as a library, and nothing else a file can point at. They say nothing about a scene reached *from* the rendered one — as a background scene, through a compositor Render Layers node, through a sequencer scene strip, or in 5.3 through a compositor node group — which is the case 4.5's, 5.2's and 5.3's findings describe from the documentation and which no test on any machine has touched. Nor do they say whether choosing the scene on the command line changes any of it, or whether such a scene's files are gathered before the render begins or as each is reached. **How much memory a render of one scene needs on macOS** is also unmeasured, and was deliberately not measured rather than measured and hedged.

## 15. Can a file rely on a colour management profile that lives on the computer rather than inside the file, and how does Blender find it?

**How it is known.** External configurations and the order of the two environment variables are documented where stated. A file depending on names from that configuration is inferred in the earlier sourced answers. Configuration selection, substitutions, counts, properties and warnings below are observed. The 5.3 count and new properties differ from the 5.2.2 control on the same Mac; its project, interoperability and ICC changes are stated in release notes.

**The same in all five.** Yes, a file relies on a configuration held on the computer. Blender ships one inside its own folders; a different one held on the computer replaces it; and what the file stores is a colour-space name, not the profile. Every version says the list of colour spaces available depends on the active configuration.

Two test results came back identically in all four. Pointing at a configuration that does not exist: all four fell back to the bundled configuration, offered the full list again, and printed an error naming the file. **5.3 on the Mac did the same**, printing two lines: `color_management | ERROR OpenColorIO Error: Error could not read '<path>/no_such.ocio' OCIO profile.` and `color_management | ERROR Failed to load config from BLENDER_OCIO: <path>/no_such.ocio`. And opening a file whose image colour space is `ACEScg` and whose view transform is `Filmic` under a small configuration that has neither name gave, in all four:

```
  image colorspace name now = ''
  scene view transform now  = 'TinyView'
```

with the same three lines printed in every version: the scene view not found and a default set, the image colour space not found and a default to be used instead, and a warning that the current value matches no entry in the list. So in every version **the file's own colour-space name is silently thrown away and comes back as an empty string, the view transform is silently replaced, and the render is not stopped.** With a window, in every version, the two fields read `TinyLinear` and `TinyView` — the configuration's own substitutes — so what a script reads and what the field displays are not the same thing, in all four. **Both machines gave both of those results, and disagree with themselves in the same way on each.**

**5.3 on the Mac, from a file a little different.** Its file's view transform was `AgX` rather than `Filmic`, because `Filmic` was not on offer to the script that built it. Opened under the small configuration, the image's colour-space name came back `''` and its interoperability id `'NONE'`, the view transform became `TinyView` with no line printed about it, the render was not stopped, and the file was marked as made with a configuration that is missing (`is_missing_opencolorio_config = True`). It printed `color_management | WARNING sequencer colorspace "sRGB" not found, will use default instead.`, `color_management | WARNING image colorspace "ACEScg" not found, will use default instead.` and `bpy.rna          | WARNING current value '-1' matches no enum in 'ColorManagedInputColorspaceSettings', '(null)', 'name'`. Because the file differed, those lines are not set against the earlier three. With a window, the image's Color Space field read `TinyLinear` and the scene's panel read Display `TinyDisplay` and View `TinyView` — the same split between script and screen.

**What was found in the tested 5.3 file.** Its uncompressed text held `ACEScg` and `lin_ap1_scene`. No configuration path or name was found by the search for `ocio`, `config` and `colormanagement`; the `config` matches were Blender field names. That limited search does not establish that no 5.3 file can record its configuration. It cannot see three-letter strings such as `AgX`.

**One reading of a name differs between the two records and settles nothing.** With the small configuration active in 5.0, 5.1 and 5.2 the list drops to two entries; the Mac's record has the second as `scene_linear` and the Linux record has it as `Working Space`. Both are written down, which reading each run took is not established, and it is uniform across the three versions on each machine — so it is not a version difference. 5.3 on the Mac reads `scene_linear`.

**Where it differs, version by version.**

**Blender 4.5.** Only `OCIO` works. `BLENDER_OCIO` was ignored entirely: with it set, the bundled 21 colour spaces were still offered and the view transform was still `AgX`. Blender does not put `OCIO` into its own environment at start-up. The bundled configuration offers **21** colour spaces; with the small configuration active the list drops to `['TinyLinear']`. `bpy.data.colorspace` does not exist at all, so there is no flag to read saying a configuration is missing. The unreadable-configuration error reads `ERROR (imbuf.color_management): source/blender/imbuf/opencolorio/intern/libocio/error_handling.cc:19 report_exception: OpenColorIO Error: Error could not read '<path>' OCIO profile.` And with the window open, **nothing on screen says anything happened** — the two fields show the substitutes and there is no warning anywhere.

**Blender 5.0.** Both variables work; 5.0's release notes record `BLENDER_OCIO` as new, to change the configuration for Blender only. Setting `BLENDER_OCIO` also set `OCIO` in the process environment. Blender does not put `OCIO` into its own environment at start-up. The bundled configuration offers **25** colour spaces; with the small one active the list is `['TinyLinear', 'scene_linear']`. `bpy.data.colorspace.is_missing_opencolorio_config` exists and returned `False` in every case tried, including the unreadable one. The unreadable-configuration error reads `color_management | ERROR OpenColorIO Error: Error could not read '<path>' OCIO profile.` **Two further warnings appear that 5.1 and 5.2 do not print**: a display used by the scene output not found and set to the configuration's own, and a scene output view not found and set to the configuration's own. With the window open, a yellow warning reading `Color Management` sits in the corner and cannot be clicked, its tooltip saying that displays, views or colour spaces in this file were missing and have been changed; and closing Blender brings a second warning saying the same and adding that saving the file with this configuration may cause loss of data.

**Blender 5.1.** Both variables work, and **at start-up Blender sets `OCIO` in its own environment** to the bundled configuration inside the application. The bundled configuration offers **25** colour spaces; the small one gives `['TinyLinear', 'scene_linear']`. The missing-configuration flag exists and returned `False`. The error message carries the same newer shape as 5.0's. The two extra warnings 5.0 prints do not appear. On screen, the same standing warning and the same close-dialog warning as 5.0.

**Blender 5.2.** As 5.1 for the variables and the start-up environment. The bundled configuration offers **63** colour spaces — more than twice as many as 5.0 and 5.1, and three times 4.5 — and 5.2's release notes record new input colour spaces for several camera makers, new spaces for Adobe RGB and common gamma values, and the list being organised into menus. The small configuration gives `['TinyLinear', 'scene_linear']`. The missing-configuration flag exists and returned `False`. On screen, the same standing warning and close-dialog warning as 5.0 and 5.1.

**Blender 5.3.** As 5.1 and 5.2 for the variables and the start-up environment: both honoured, `BLENDER_OCIO` setting `OCIO` as well, and `OCIO` set at start-up to the bundled configuration inside the application. The bundled configuration offers **64** colour spaces, where **the 5.2.2 run on the same Mac offered 63**. The small configuration gives `['TinyLinear', 'scene_linear']`. The two warnings only 5.0 prints did not appear, from the slightly different file above. And four things exist that **the 5.2.2 run did not have**: `bpy.data.colorspace` carries `is_failed_opencolorio_config`, `ocio_config_path` and `ocio_config_source` beside the missing flag, and an image carries an `interop_id` beside its colour-space name. With nothing set they read `False`, the bundled file's path, `'BLENDER'`, and for a new image `'srgb_rec709_display'`; with `OCIO` or `BLENDER_OCIO` pointing at the small file the source read `'OCIO'` or `'BLENDER_OCIO'`; and with `BLENDER_OCIO` pointing at a file that does not exist the source read `'BLENDER'` and both flags read `False`. On screen: the same yellow `Color Management` panel at the right-hand end of the status bar, in every picture, and the same close-dialog words — *Displays, views or color spaces in this file were missing and have been changed. Saving it with this OpenColorIO configuration may cause loss of data.* — under *Save changes before closing?*, with *Don't Save*, *Cancel* and *Save As...*. The tooltip was not reached.

**5.3's release notes add three more things, none tested**: better interoperability between files and assets made with different configurations, which is what the interoperability id is for; a project choosing its own configuration — Blender's own, ACES 1.3, ACES 2.0 or a custom one — which is the `Project` value among the sources, with nothing saying where it stands against the two variables; and saved sRGB image files carrying an ICC profile.

**Verdict: it differs**, in six separate ways among 4.5 to 5.2: which environment variable is honoured, what Blender puts in its own environment at start-up, how many colour spaces the bundled configuration offers, whether a flag exists to ask about a missing configuration, which warnings are printed on the terminal, and whether anything on screen says a substitution happened. **All six were settled by tests run in all four versions on the Creator's Mac and again in all four on the rented Linux machine, with the same answer on both** — including the on-screen half, which was photographed again there: no warning of any kind in 4.5, and a yellow `Color Management` panel in the corner in 5.0, 5.1 and 5.2. Corroborated by 5.0's and 5.2's release notes. **5.3 sits with 5.1 and 5.2 on the variables, the start-up environment and the screen, and differs from 5.2 in more:** one more bundled colour space, and four new properties, both against the 5.2.2 run on the same Mac; and, by its release notes, a project able to choose the configuration. 5.3 rests on the Mac alone.

**Not established.**

- **The tooltip on that yellow warning, and the warning shown when Blender is closed.** Both were seen on the Mac only; each needs a pointer resting on a control, and that could not be done on the Linux machine. What they say is recorded from the Mac and is the same in 5.0, 5.1 and 5.2. In 5.3 the close dialog carried the same words and the tooltip was not reached.
- **Which name the small configuration's second colour space carries.** The Mac's record has `scene_linear` and the Linux record has `Working Space`, uniform across 5.0, 5.1 and 5.2 on each machine; neither reading was chosen. 5.3 on the Mac reads `scene_linear`.
- **What the missing-configuration flag says, and when.** In 5.0, 5.1 and 5.2 `is_missing_opencolorio_config` was read at each start-up, with nothing open, and came back false every time on either machine, including with the configuration unreadable; it was not read with a file whose names had been substituted. 5.3 reads the same at start-up, and reads **true** once such a file is open — which fits the flag's own description of names not found in a file. Whether 5.0 to 5.2 read true in that case is untested. 5.3's second flag, for a configuration that failed to load, read false when the configuration named by `BLENDER_OCIO` did not exist and the bundled one was used instead; why is not stated. 4.5 has no such flag.
- **Whether the configuration's path is ever recorded in the file.** Every version says nothing suggests it is. 5.3's file, searched, held no configuration path or name; 4.5 to 5.2's were not searched.
- **Where a project's configuration stands against the two variables, in 5.3.** Not stated, not tried.
- **Whether the variables are read once at start-up or again when a file loads.** Not in the sources in any version.

## 16. How is a font installed on one kind of computer recorded in the file, and what does Blender do when a font it points at is not on the computer?

**How it is known.** A font recorded as a file path is documented. The claim that Blender never looks up a font by family name is inferred from silence, not established. Missing-font behaviour is observed: Mac and Linux in 4.5 to 5.2, and the Mac alone in 5.3. The Font panel was seen on the Mac alone.

**The same in all five.** How it is recorded. A font is an ordinary external file path on a data-block, with the same relative option as any other resource, and it can be packed into the file. No source here describes a separate family name or lookup into the operating system's font list. That Blender never uses one is **inferred from silence**, not established. A font taken from the Mac's own font folder and copied beside the blend-file was recorded as `//assets/testfont.ttf`, exactly like any other file, in all five versions. And the built-in font is recorded, in all five, as the literal string `<builtin>`:

```
FONT name='Arial Regular' filepath='//assets/testfont.ttf' packed_file=None
FONT name='Bfont Regular' filepath='<builtin>' packed_file=None
```

What happens when the font is gone was also identical in all four, on both machines. The stored path is unchanged. The render finishes with exit status 0 and the frame differs from the good one. The text object does **not** fall back to the built-in font: its evaluated mesh fell from 332 vertices and 334 polygons to 16 and 16 for the two letters `AB` — one empty rectangle per character, and that fall was measured again on Linux. Report Missing Files names the font in every version, as a warning naming the path and the data-block. With the window open, the same in all four on both machines: the text is a row of hollow rectangles, one per character. On the Mac the Creator also read the Font panel: it says `Regular  Arial Regular` in ordinary white text with **no mark of any kind**, and the three other style slots read `Bfont Regular` greyed. In the Creator's own words, covering all four: nothing is marked as missing. That panel could not be photographed on the Linux machine — it starts closed and there is no way to open it from a script — so it is the Mac's alone.

**5.3 on the Mac gave the same at every point.** The path was kept, the render finished with exit status 0 and a different picture, the mesh for `AB` fell from 332 vertices to 16, and Report Missing Files named the font as `VFArial Regular`. Through 5.3's window the text was a row of hollow rectangles, one per letter, in the viewport and in a render made inside the window; and the Font panel, opened by a simulated click on its header, read `Regular` `Arial R…` — the name cut by the panel's width — in ordinary white with no mark of any kind, the other three slots `Bf…`, greyed.

The words Blender uses differ between 4.5 and the 5.x versions — `WARN (bke.vfont): …: Font file doesn't exist:` against `geom.vfont | WARNING Font file doesn't exist:`, each preceded by two `Unable to pack file` lines in the matching shape — but that is the general change of message format recorded in full under question 12, not a finding of its own here. It came back the same on both machines. 5.3 prints the 5.x shape — `reports          | ERROR Unable to pack file, source path '<path>/assets/testfont.ttf' not found` twice and `geom.vfont       | WARNING Font file doesn't exist: //assets/testfont.ttf` once, the group of three printed twice — and, with a window, the group again each time the text is drawn.

**When the two `Unable to pack file` lines appear is not established.** The Mac's first run found them appearing when the file is merely opened in 4.5, and only on a render in 5.0, 5.1 and 5.2. **Three later runs contradict it.** The Linux-built files opened on Linux with nothing asked of them, those same files carried back to the Mac and opened the same way, and the Creator's own prepared files — the ones the first result came from — opened on both machines: in every one of those runs, **all four versions printed the lines at load**, on the Mac as well as on Linux. The findings record both results, choose between neither, and say plainly that what makes the lines appear at load in one run and not another is not established. So this is not a difference between versions. **5.3 printed them when the file was merely opened**, and again once a render had started; **the 5.2.2 run of the same build on the same Mac printed them on opening too**. So the first run's reading is now alone against five.

**Verdict: the same everywhere.** The tested font is recorded as an ordinary external file path, and the built-in one as a literal marker. That Blender never looks up a font by family name remains **inferred from silence**. When the font is gone the path is kept, the render still finishes, the letterforms are lost with no fallback, nothing on screen marks the font as missing, and Report Missing Files names it. All of that is the same in 4.5, 5.0, 5.1, 5.2 and 5.3, **resting on both machines for 4.5 to 5.2 and on the Mac for 5.3**. Windows is untested.

**Not established.**

- **When the two `Unable to pack file` lines appear.** One run says 4.5 only; three later runs on both machines say all four versions; 5.3 and the 5.2.2 run on the Mac print them on opening. Nobody has settled what made the first run differ.
- **Where Windows keeps its fonts, and what a font path written there means elsewhere.** Only the Unix note exists, in every version, and it is hedged. No Windows machine ran this question. A font path relative to the blend-file was shown to survive the crossing from macOS to Linux.
- **Whether Blender ever resolves a font by family name rather than by path.** Nothing in any version suggests it does, and nothing rules it out.
- **Whether the four style slots behave differently when one of them is missing.** Only the Regular slot was tested, in all five.
- **What the Font panel says beside a missing font on any machine but the Mac.** It could not be photographed on the Linux machine at all, and 5.3 was not run there.

## 17. What use does a `.blend` file make of the places it records for writing, besides writing to them?

**How it is known.** The named uses are documented where stated. The existence check behind Overwrite is inferred from the settings' wording; the tests below directly observe skipping and writing. Cycles' denoiser reading the output place was observed in its own files and by running it. Other results below are observed with the machine and setup limits beside them.

Ten of the results below were run from a terminal in all four versions on the Creator's Mac **and** in all four on the second rented Linux machine; four need a screen and are the Mac's alone; and one — two Blenders rendering into one folder — was run on the Linux machine alone. **In 5.3 the ten and the four were run on the Mac**, the window ones through a window driven from a script; the two Blenders were not run.

**The same in all five, and the same on both machines for 4.5 to 5.2.** Every paragraph below held in 5.3 on the Mac unless it says otherwise.

**A render creates an output folder that is not there**, one level deep and two levels deep, puts the frames in it, finishes with success, and says nothing about having done it. **No version's documentation says this happens.** Three versions quote a sentence saying the compositor's File Output node creates missing directories; no version says it of the render output path, and two of them say outright that they looked and found nothing. It happens in all five.

**Overwrite off makes a render skip frames that are already there, and Blender names each one it skipped.** Of five frames with two deleted, only the two deleted ones were written again; the other three kept their original modification times.

**A zero-length file already at the output place counts as a frame already done.** With Overwrite off and Placeholders on, five empty files meant nothing was rendered at all, all five were still zero length afterwards, the run finished with success, and Blender said "No frames rendered, skipped to not overwrite". So the shared-folder arrangement rests on the mere presence of a name, not on the file holding a picture.

**With Overwrite off, the regular output alone decides whether a frame is rendered — and a File Output node then writes over its own files.** Asked in 5.3 alone, on the Mac. A file with a File Output node, rendered once, was rendered again with Overwrite off: with the regular frames there nothing was rendered and nothing written, the node's files untouched; with the regular frames moved away and the node's files left, both frames were rendered and the node rewrote its two files, saying nothing about them. No earlier version was asked.

**Two Blenders rendering into one folder divide the frames between them — in a run where one was five seconds ahead of the other.** Four seconds into the first render the folder held one empty file, for the frame being rendered; the second Blender was started a second after that, so by the time it looked at the first frame that frame had already been claimed. The two runs then took alternate frames with none claimed twice, and no frame was left empty. **That is not evidence that a placeholder holds**, because no two renders in it ever reached the same frame at once. This one was run on the Linux machine only; the Mac never ran it, and that is a gap in this topic rather than anything about macOS — two Blenders do run at once on the Creator's Mac, and two started together were caught claiming and rendering the same frame there, settled under **Frames 14**. 5.3 was not run this way.

**A bad path template in the scene's own output path stops a render started from outside, for a single frame as well as for an animation.** Exit status 1, and a message naming the path and the incomplete expression. A sound template as a control rendered normally, so the failure is the template's and not the set-up's. Asking the file where the frame would land raises the same error before anything runs. **That is the scene's own write, which is the only one this topic tested.**

**The output path recorded in the file beats one given on the command line before it, and loses to one given after it.** In 5.3 the one given after it was also written into the file by a plain save from a script (question 20).

**The file agrees with itself about where a frame will land — with one exception worth knowing.** For a frame render and for an animation, the name the file predicts and the name that appears on disk are the same, templates and frame-number padding and all. For a still render through `bpy.ops.render.render(write_still=True)` they are not: the template is substituted but the `##` padding is left exactly as it stands, so the file is written with the hash characters in its name. Same on both machines.

**In the six-place test, the path commands reach the image and ocean cache path.** Of six recorded locations — an ordinary image loaded from disk, the render output path, a File Output node's directory, an external point cache, a geometry-nodes bake directory and an ocean modifier's cache path — Make Paths Relative, Make Paths Absolute and Report Missing Files reach **the image and the ocean cache path and nothing else**. `bpy.utils.blend_paths` lists the same two. In this setup, making paths relative leaves the render output path alone, and Report Missing Files does not name the entered geometry-nodes folder. Blender's own walk over a file's paths visits the same two and none of the other four, with the cache-expanding flag as well as without it. **What separates the ocean cache from the other four write places is not established.** **In 5.3 this was a folder on a bare Geometry Nodes modifier:** it had no node group, simulation zone, bake entry or baked files, and no Disk bake target was selected. The 5.2.2 Mac control used that same setup. This does not establish whether the tools reach an actual geometry-nodes bake. The simulations baked under questions 5 and 18 were different files, never given these path-tool checks. Question 20's save test also used a bare modifier with a folder, not an actual bake.

**Cycles' animation denoiser reads the recorded output place, and stops on a frame that is not there**, naming it: `Frame '…' not found, animation must be complete`. In all five versions, writing nothing. Only one of the first four versions' findings had this at all, read out of Cycles' own files, as 5.3's has; running it everywhere is what shows the others are silent rather than different.

**With a window open — the Creator's Mac alone, since the second rented Linux machine has no display server.** The render output path field really is drawn red for a bad template and ordinary grey for a good one, in all five versions; measured, the red is about twice the green and the blue in every bad one of the first four and about three and a half times in 5.3's, and all three are equal in every control. Overwrite-off skips frames inside Blender's own window as well as outside it. The Animation Player is a second Blender started with `-a`, told the frame rate and the frame range, and handed **the first frame at the file's own recorded output place**, in all five versions — and with nothing at that place it says so by name, which is what shows it reads the recorded place rather than doing something generic. **That last part, the empty-folder control, was run in Blender 4.5 only**, so what a reader can lean on for the others is the frame name the player was handed, not the complaint. And the viewport render writes into that same recorded place, in all five; in 5.3 its five `Saved` lines came out of frame order.

**Where it differs, version by version.**

**Machinery observed in 4.5 to 5.2 on both machines, and the names queried in 5.3 on the Mac.** The compression setting was not queried in 5.3.

**Blender 4.5.** `PointCache.compression` exists, reading `'NO'`, with the choices NO, LIGHT and HEAVY. `bpy.data.file_path_foreach` does not exist. There is no texture-cache setting of any kind, no `texture_cache_directory` preference, and no `generate_texture_cache` operator.

**Blender 5.0 and 5.1.** `PointCache.compression` is gone. `bpy.data.file_path_foreach` exists and takes six flags. Still no texture cache of any kind.

**Blender 5.2.** `PointCache.compression` is gone. `bpy.data.file_path_foreach` exists and takes nine flags, three of them for expansion. And 5.2 alone of these four carries `RenderSettings.use_texture_cache` (which reads true), `use_auto_generate_texture_cache` (which reads false), a `texture_cache_directory` preference and `bpy.ops.render.generate_texture_cache`.

**Blender 5.3.** As 5.2: the nine-flag walk, `use_texture_cache` reading true, `use_auto_generate_texture_cache` false, the `texture_cache_directory` preference and the `generate_texture_cache` command. Whether 5.3 has `PointCache.compression` was not asked.

Present and reading the same in all five: `use_render_cache` (false in 5.3), `use_overwrite` (true), `use_placeholder` (false), and Cycles' `denoise_animation` and `merge_images`.

**Verdict: it differs.** The shared uses tested agree in all four versions on the named machines, and in 5.3 on the Mac: reading back, checking before writing, playback, validation and refusal. In the six-place test, the path tools reached the image and ocean cache path; 5.3's geometry-nodes entry was only a folder on a bare modifier. Tools reaching an actual bake remain unestablished. What differs is what exists to work with: 4.5 has a point-cache compression setting that 5.0 to 5.2 lack, while its presence in 5.3 is untested; 5.2 and 5.3 alone have a texture cache and its operator and preference, and 4.5 alone cannot be asked to walk a file's paths. **Settled by the same tests run in all four versions on both machines, and in 5.3 on the Mac.** What Blender *says* while it skips frames is a separate matter and is not settled — see below. Windows is untested, in every version.

**Only the documentation differs — four things inside this question.** In each, the behaviour was tested in all five versions — 5.3 on the Mac — and came back the same; only some versions' documents mention it. **None of these is a difference in Blender.**

- **The compositor's File Output node creating missing directories.** Quoted from the manual for 5.1, 5.2 and 5.3; 4.5's and 5.0's records say they looked and found nothing equivalent. It was tested: the node creates the folder that is not there and writes, in all five versions, with no window.
- **The viewport render borrowing the recorded output path.** Documented for 5.0 alone; the others are silent. Tested at the window on the Mac in all five, and it does.
- **Cycles' animation denoiser reading the recorded output path.** Found in 5.1's and 5.3's readings of Cycles' own files and in no other version's. Tested in all five, and it behaves the same in each.
- **Cache files being counted among a file's own paths.** Blender 5.1's record quotes two of its own corrective-release fixes saying so by name, and 5.2's and 5.3's record the flag that expands them; 4.5's and 5.0's say nothing. The test above shows what is actually reached, identically in all five.

**Not established.**

- **Whether the path tools reach an actual geometry-nodes bake in 5.3.** The modifier in the six-place test had only a folder entered, as set out above.
- **Whether `PointCache.compression` exists in 5.3.** Not asked.
- **Whether what Blender says while it is skipping frames really differs between the versions.** With a window open on the Creator's Mac, Blender 4.5 named each skipped frame on the console exactly as it does with no window, while 5.0, 5.1 and 5.2 named none, though the frames were plainly skipped and the modification times prove it; with no window all four name them. It cannot be asked on the second rented Linux machine, which has no display server. **That is not enough to call it a window difference.** The same grouping — 4.5 speaking where the newer three are silent — is also produced by *how* a render is started rather than by whether there is a window: a render started by handing Blender an instruction to render, rather than by naming the frame on the command line, prints nothing of that kind in 5.0, 5.1 and 5.2 where 4.5 prints in full, which is settled under **Reports 9**. Nothing in this topic's record says how the 4.5 to 5.2 window run was started, so which of the two is at work is open. 5.3's window run was started by a render command from a script — both conditions at once — and named no skipped frame either, while its runs with no window named each one; that fits either reading.
- **What the tooltip on a red path field lists.** The field can be photographed; the tooltip cannot. Reading it means hovering, and in 4.5 to 5.2 a Blender window started from a terminal on the Creator's Mac never ran its event loop — a registered timer never fired, the redraw command never returned, and the quit command never quit. The second rented Linux machine has no display server at all. In 5.3 the window ran its timers, but a pointer moved by Blender's own simulated events brought no tooltip up. Open in every version.
- **What a File Output node does with Overwrite off, in 4.5 to 5.2.** Only 5.3 was asked.
- **Whether frames are claimed the same way over a network, and what two renders reaching the same frame at the same instant do.** The one test here ran two Blenders on one Linux machine into one ordinary folder with the second started five seconds late, so no race could occur in it. There is no folder on network storage that two of this project's machines can reach at the same moment.
- **Why a still render leaves the frame-number padding unsubstituted.** The fact is recorded in all four on both machines and in 5.3 on the Mac; nothing establishes the cause.
- **What Blender's own marks say about the six recorded locations above.** Blender publishes three marks on each of its own settings — whether the setting is an output path, whether it takes the blend-file-relative shorthand, and whether it takes templates — and in this project they have been read for four properties only, under **Reading a file 4**. They have never been read for the six locations in this question, nor for the five places that keep their forward slashes on Windows under question 20. Nothing here says what they would report, and the four that were read do not settle it: the render output path reads true for the output-path mark and is **not** reached by the file-wide commands, while an image's path reads false and **is** reached.
- **Whether any of this behaves the same on Windows.** No Windows machine ran this question.

## 18. What does a render do when a cache or a bake that a file records is absent?

**How it is known.** Missing-cache behaviour is mostly not in the sources. Physics recalculation and out-of-order geometry-nodes behaviour are partly inferred from documented descriptions. The world-light fallback for a light probe is inferred, not measured. The render, flag and picture results below are observed; the old compression change and the texture-cache addition are stated in release notes.

Ten of the results below were run in all four versions on the Creator's Mac **and** in all four on the second rented Linux machine; two need a screen and are the Mac's alone. The light-probe test was rendered with EEVEE, which uses the graphics stack, and on the Linux machine it printed graphics warnings before working; every other render here used Cycles on the processor. **In 5.3 all twelve were run on the Mac**, the two screen ones through a window driven from a script, with the light probe in EEVEE and everything else in Cycles on the processor; and two more were run there that no earlier version completed — the ocean modifier's bake, and an Alembic cache.

**The same in all five, and the same on both machines for 4.5 to 5.2.** Every paragraph below held in 5.3 on the Mac unless it says otherwise.

**With a physics simulation and no bake, the render works the simulation out rather than skipping it — but not from the beginning.** A falling cloth reaches one state when every frame from 1 to 60 is stepped through and a different state when frame 60 is jumped to directly, in all five versions. The evaluated geometry differs and so do the pictures. Nothing is said about a cache in either run. In 5.3, jumping left the cache reading `'2 frames in memory (12 KiB), not exact since frame 1'`.

**With a physics disk cache the file records deleted, the render is silent and the picture changes.** Exit status 0, nothing printed, and `is_baked` still reading true with the folder gone. That change alone does not establish what replaced the missing cache. **One part of that rests on the Mac alone**: only the Mac run compared the cache-present frame against the frame the same file gives when every frame is stepped through, and found them the same pixel for pixel, which is what shows the cache was being read at all. The Linux run did not take that comparison in any version; 5.3 took it on the Mac and got the same.

**With an external point cache pointing at an empty folder, there is a report and it can be read with no window.** `PointCache.info` reads `'No valid data to read!'` and `is_baked` reads false, before and after going to the frame. Nothing on the console, exit status 0, and in 5.3 the render gives exactly the unbaked jumped picture, compared pixel for pixel. That equality is not established for 4.5 to 5.2, as the limit below explains. A program outside Blender can read the External cache's failure string; the Mac disk-cache result also exposes a count of zero.

**With a geometry-nodes simulation zone and no bake, the result is nothing like the cloth.** Stepping through every frame moved the cube about 9.1 units; jumping straight to the last frame moved it 0.015. The zone barely advances at all when a frame is taken out of order. Same numbers on both machines, and in 5.3.

**With a geometry-nodes disk bake deleted, the render is silent and the picture changes** — and with the bake present a single frame taken out of order matches the stepped-through result exactly, which is what shows the bake was being read in the first place. In 5.3 the bake-gone picture fell back near the unbaked jumped one without matching it.

**With a fluid cache folder taken away, the file does not notice.** All five `has_cache_baked_*` flags still read true with the folder gone, in the same session and after the file is closed and opened again: they are held in the file, not worked out from the disk. Same in 5.3. **Whether opening the file puts a folder back is not settled.** In 4.5 to 5.2, on both machines, opening the saved file **made the cache folder again and wrote a frame into it**. In 5.3 on the Mac it did not — not on opening, nor after the scene was evaluated and stepped to frame 3 — and **the 5.2.2 run of the same steps on the same Mac did not either**. Those two bakes wrote six sub-folders where the earlier one wrote two; what separates the runs is not recorded. So it is not a difference between versions.

**An EEVEE light probe volume with no bake renders a different picture from a baked one, and the loss is silent.** The bake changes the render, and freeing it puts the render back where it was — the Mac took that third comparison and got the same picture pixel for pixel, which is what shows the freeing undid the bake rather than doing something else. Nothing was printed about the missing bake in any run, in any version. In 5.3 on the Mac EEVEE printed no warning of any kind before rendering. **What the test does not show is what stands in for the bake.** That the world's diffuse lighting is used is every version's reading of one manual sentence, marked **inferred** because the sentence names an "Irradiance Volume" and the page is headed "Light Probe Volume"; no test looked at what the light actually was. The engine's own name differs between the versions, which is recorded under question 12.

**With a window open — the Creator's Mac alone.** The Timeline does show a lost cache, and it shows it by drawing nothing. With the cache present a solid blue bar runs under the frame numbers for the whole baked range. With the folder deleted **no bar is drawn at all** — not faint, not striped, absent. Same in all five versions.

**What a render does when an ocean modifier's baked files are gone — answered in 5.3 on the Mac.** With no window the bake command answered `{'FINISHED'}` and wrote nothing, as on the Linux machine in 4.5 to 5.2. Called from a script inside a window the way the interface calls it, it wrote five files, one per frame, and the modifier read `is_cached` true — straight after the bake and after the file was saved and opened again. A render reads those files: given another seed's bake files in its folder, it drew that seed's sea exactly. With the bake folder gone the modifier still read `is_cached` true, the render ended with exit status 0 and said nothing, and the picture was an even grey with no waves at all — unlike both the baked sea and the same file never baked. **The 5.2.2 run of the same steps on the same Mac did the same at every point.** 4.5 to 5.2's own Mac runs never saw `is_cached` turn true, and that remains open below.

**An Alembic cache file gone**, asked in 5.3 alone: the render named it, finished with exit status 0, and drew the object's own mesh in place of the cached one (question 12).

**Two readings differ between the tested machines. Neither establishes a version difference or a general operating-system rule.** Each is uniform across 4.5 to 5.2 on the machine it came from.

- **What a physics point cache says about itself once its folder is gone.** `PointCache.info` reads `'0 frames on disk.'` on macOS and read `'60 frames on disk.'` on Linux. The macOS reading was taken twice to be sure, and both machines were asked about the same sixty-frame cache; 5.3 on the Mac reads `'0 frames on disk.'` too. That string exposed the loss on the tested Mac and did not on the tested Linux machine. Other machines are untried.
- **One thing to take from the numbers rather than the words.** The Linux write-up says in so many words that the cache-gone render is exactly the picture the file gives with no bake at all, while its own quoted figures show 4899 of 102400 channels differing. The Mac took that comparison directly and they are plainly not the same picture. **Take the numbers.**

**Where it differs, version by version.**

**A disk point cache written by 4.5 with a compression that 5.0 dropped.** Blender 4.5 wrote it and reads it. Opened in 5.0, 5.1 and 5.2 it is refused, and every one of those three prints the same warning, naming the object — that the cache cannot be read because it uses an outdated compression method and the caches must be deleted and re-baked — once when the file is opened and again while it renders. The render still finishes with success and gives a different picture from 4.5's. `is_baked` still reads true and the cache still says it has sixty frames on disk in all three. **Word for word the same on both machines.** This is the one case in the whole topic where a cache that cannot be used is announced, and it is carried by 5.0's own release note as well as by the test. **5.3 was not given such a cache**: it needs Blender 4.5 to write one, and 4.5 was not to hand when 5.3 was run.

**The Cycles texture cache exists in 5.2 and 5.3 alone.** In 4.5, 5.0 and 5.1 the setting is simply not there, so that cache cannot be absent in them at all — asked directly, all three answer that they have no such setting. In 5.2, with the cache switched on, automatic generation off and no cache file anywhere, **nothing failed**: the render finished and gave the picture it gives with the cache off. Switching generation on made the cache file, with the same name character for character on both machines. **Within 5.2 the two machines then part; the cause is unestablished and this is no version difference:** once a cache file exists, turning the cache on changes the picture slightly on the Mac — the largest single channel moving 0.09 out of 1, steady, reversible, and reappearing whenever a cache file is there to be read — while on Linux it made no difference to the picture at all. **5.3 on the Mac behaved as 5.2 did on the Mac**: with the cache on, generating off and no cache file, the same picture as with the cache off; generating made `checker.png.0-926BDA8569F1F2504902F06ABA51E46D.tx` in a `blender_tx` folder beside the image; and whenever that file existed and the cache was on, generating or not, the picture differed slightly — one channel of one pixel by one step in 255 for its picture — steadily, and went back exactly with the cache off. Nothing was printed about the cache in any run. **The 5.2.2 run of the same picture on the same Mac gave 5.3's six comparisons word for word and the same file name**, so the smaller figure belongs to the picture, not to the version.

**Verdict: it differs.** The shared cloth, geometry-nodes and light-probe tests finish with success and no missing-bake warning, with changed pictures. They establish their separate outcomes, not a general rule that every absent bake is simulated again. The ocean test is answered only in 5.3 and the 5.2.2 Mac control; the Alembic test only in 5.3, and it warns and uses the object's own mesh. Fluid-folder recreation remains unresolved. These observations establish no version change in the missing-cache response. What differs is narrower and worth having exactly. A disk point cache written by 4.5 is refused by 5.0, 5.1 and 5.2 with a warning, where 4.5 reads it — settled by the same test run in all four versions on both machines, carried by 5.0's release note, and never tried in 5.3. And 5.2 and 5.3 alone have a Cycles texture cache, so they are the only versions in which that particular cache can be missing.

**Not established.**

- **What a render does when an ocean modifier's baked files are gone, in 4.5, 5.0 and 5.1.** Attempted on both machines and unanswered on both. On Linux the bake could not be made at all — the operator reported success and wrote nothing, in every version. On the Mac, called the way the interface calls it, it does write the bake: twenty files, one per baked frame. But `is_cached` never turns true — not straight after the bake, not after the file is saved and opened again — and the render is the same picture with the files present and with them gone. Since the modifier never reports itself as using the bake, those matching pictures carry no information about the loss. **The Mac did settle one thing: the want of a window is not the reason.** Open in those three. In 5.2 the two Mac readings disagree — that run, and the 5.2.2 run that behaved as 5.3 did — and in 5.3 it is answered above.
- **Why `is_cached` never turned true in 4.5 to 5.2's Mac runs**, when it did in 5.3 and in the 5.2.2 run. Nothing records what kept it false.
- **Whether the external point cache pointing at an empty folder really gives exactly the picture the file gives with no bake at all, in 4.5 to 5.2.** That is the phrase the record uses of it, and the caution above says the same phrase used of the neighbouring comparison is contradicted by the figures written down beside it. Take the numbers where there are numbers. In 5.3 the numbers say it does.
- **Whether opening a file puts back a fluid cache folder that has gone.** 4.5 to 5.2's runs did; 5.3 and the 5.2.2 run on the Mac did not, from a bake that wrote six sub-folders rather than two.
- **Whether a 4.5-written point cache is refused by 5.3.** Not tried.
- **Whether a partly-present cache behaves differently from a wholly absent one.** Every test deleted the whole folder or began with an empty one, in all five. The ocean modifier's documented rule about frames outside a baked range is the only source statement about partial coverage, in every version that carries it, and no test reached it.
- **Whether the two machine differences above are anything more than the two file systems.** Both were seen, both were checked, and neither was explained; 5.3 was not run on Linux to add to either.
- **Whether any of this behaves the same on Windows.** No Windows machine ran this question.

## 19. What decides whether two recorded library locations are treated as the same library or as two different libraries?

**How it is known.** No source states the library-identity rule. Surrounding library and naming properties are documented; conclusions drawn from them are inferred. The counts, recorded paths and reopen results below are observed. The summary rule is inferred from those tests, and packing's addition is also stated in 5.0's release notes.

**So the whole of the answer below was settled by test rather than by reading.** Fifteen hand tests were run in all four versions, on two machines — the Creator's Mac, and the **third** rented Linux machine, which is neither of the two rented machines the earlier questions rest on — and by both ways of making a link, `bpy.ops.wm.link`, which is what the interface's File ▸ Link runs, and `bpy.data.libraries.load`, a plain Python call. **The two ways of linking gave the same answer everywhere**, in every test, in every version, on both machines. All fifteen results are labelled **observed**. **Nothing was rendered at all**: every result is a count of library entries and the text each one holds. Blender was started with no window in every run, so all of this is what happens when Blender is driven from outside its own interface; the count of libraries was read from a terminal — the number of entries, and a printed line giving each entry's name and its recorded text — rather than counted as rows on a screen. That is the same set of entries the Outliner's Blender File view shows, read a different way, and **nothing below claims to be a reading of the screen**. **Every test also saved the file and opened it again in a fresh Blender**, so that a decision made at the moment of linking and a decision made when a file is read back could be told apart.

**In 5.3 the same tests were run on the Mac alone**, by both ways of linking, with no window, saving and reopening each time — all of them except the second mount of one folder, which the Mac cannot make. **The two ways of linking gave the same counts and the same recorded text in every 5.3 test**, and every one matched 4.5 to 5.2's Mac results. So every paragraph below holds in 5.3 on the Mac unless it says otherwise.

**The same in all four versions, and the same on both machines.** Every "both machines" from here to the end of question 19 means that pair and no other.

**The count can say one and it can say two.** Linking a second object from the same file, with the path written exactly the same way, leaves one entry; linking from a genuinely different file makes a second. That control ran first, and without it none of the results below would mean anything.

**The same file recorded relative and then recorded absolute gives one library.** With the relative option on, the entry records `//lib.blend`. Linking a second object from the same file with the relative option off adds no entry and does not change the text — it still reads `//lib.blend`, before and after the file is saved and opened again. So the two forms are not two libraries, and the second link did not rewrite the first one's recording.

**A path with a step in it that goes nowhere gives one library.** The plain path, the same path with `/./` in it, and the same path with a `sub/../` detour in it all landed in one entry, and what was recorded is the plain path.

**Two names on disk for one file give a separate library each.** A symbolic link to the file, a hard link to the file, and a symbolic link to the folder each made an entry of its own alongside the real path — four entries for one file. On the rented Linux machine a fourth route was possible, the same folder mounted a second time somewhere else, and it made a fifth. The shell was asked first, and confirmed that the hard link really was the same file rather than a copy. **So Blender does not see through a link to the file underneath.** The Creator's Mac cannot mount a folder twice, so it ran four of the five steps and matched Linux on all four; the second mount is a Linux result only.

**Two entries can be made to hold identical text, and they do not survive it.** Starting from two libraries linked from two different files, writing the first one's recorded text into the second was accepted without complaint. Two entries stood in the open session, both holding the same text. After the file was saved and opened again there was **one**. So the merging happens when a file is read, not when the text is changed. **What 5.3 said when it merged them**, the only version whose record quotes it: `Library '<path>/lib1.blend', '<path>/lib1.blend' had multiple instances, save and reload!`, then `LIB: Object: 'Q1' missing from '<path>/lib1.blend'` and `0 libraries and 1 linked data-blocks are missing`. `Q1` lived in the second file; after the merge it was sought in the first, and lost.

**Rewriting all of a file's paths at once moves the text and never the count.** Make Paths Absolute and Make Paths Relative both reported success, the recorded text flipped between the full path and `//lib.blend` and back, and the number of entries never moved. The case this was built for — two entries collapsing because a rewrite made their text identical — could not arise here, because the relative-and-absolute test had already given one entry rather than two. The forced-identical-text test above covers it instead.

**The same file reached directly and reached through another library is one library.** Linking a collection out of a middle file, which itself links from the shared file, brought the shared file in; linking an object straight out of that shared file afterwards added nothing. Both objects report the same library. The control held — the shared file really was present after the first link — so the second half means something.

**Two identical recorded texts standing for two different files never arose, and the reason is worth knowing.** The test put two folders side by side, each with its own file of the same name, and arranged for the host file and a middle file each to record `//x.blend`. What actually happened is that the middle file's own recording, `//x.blend`, appears in the host file as `//../one/x.blend` — Blender rewrote it against the host as it came in. So the two texts were never the same and the two files stayed two libraries. The worked-out full paths were printed for both, and they name the two different files. In 5.3 the `Read library` lines printed on reopening differed by route while the counts and recorded texts did not: for the file built through the link operator, the middle file's neighbour was printed as `'//x.blend'` with the middle file as its parent; for the file built through the plain Python call, as `'//../one/x.blend'` with parent `'<direct>'`. The test of two files recording one library differently showed the same split.

**Two different files that share a file name give two entries. A library entry's name is the bare file name**, and where two would clash the second is given `.001`. That is what makes the naming rule quoted in all four versions' documentation usable at all.

**Two files that record one library two different ways, both linked into a third, give one entry for that shared library.** One intermediate file recorded it relative and the other absolute — both checked on their own first — and the file that links from both ends up with one entry for the shared library, recorded relative.

**Capital and small letters — and here the two machines part.** This is an operating-system fact and not a version difference: each machine gave the same result in all four versions, and the two machines are never set against one another.

- **On the rented Linux machine**, the shell was asked first and said the differently-spelled name is not a file at all. The second link was then refused, and the refusal was printed word for word — an error saying the file could not be opened through the plain Python call, and a different error saying nothing was indicated through the operator. One entry, before and after.
- **On the Creator's Mac**, the shell listed both spellings as one file of the same size. The second link succeeded and made **a second library entry**, recording the differently-spelled path, and both entries survived a save and a reopen. 5.3 did the same there, its second entry named `LIB.blend`.

So on the third rented Linux machine — the kind of machine a Smoozy render happens on, though this settles that one machine and not the kind — a wrongly capitalised library path is a link that fails outright; on the Creator's Mac it is a link that quietly succeeds and leaves the file holding two libraries where an artist meant one. Neither result says anything about the other machine, and neither says anything about Windows, which no test in this question reached.

**Where it differs, version by version.** One test of the fifteen, and one only: packing linked data into the file.

**Blender 4.5.** The three archive properties on a library — `is_archive`, `archive_parent_library` and `archive_libraries` — do not exist; asked by name, all three come back absent. Asking `bpy.data.libraries.load` to pack raises an error saying `pack` is not a keyword it accepts, and the file is left with no library at all.

**Blender 5.0, 5.1, 5.2 and 5.3.** All three properties are present. The packing call is accepted. Afterwards the file holds **two library entries whose recorded text is identical** — the same full path in both — the second named with a `.001` suffix, marked as an archive, with the first named as its archive parent; the first is not an archive and lists the second among its archives. The linked object belongs to the archive rather than to the original. Both entries survive a save and a reopen. The three versions printed the same thing as each other, and the same thing on both machines; 5.3 printed the same on the Mac. **5.3 was also asked what happens when the library itself goes**: with `lib.blend` moved away and the file opened again, the packed object was still there, marked linked-and-packed and not missing, and nothing was printed about the library. No earlier version was asked that.

Blender 5.0's own release notes record archive libraries as new in 5.0, and 5.0's findings quote them: packed linked data is stored in a new kind of archive library, owned and managed by the real library it came from, so that packed data cannot collide by name. 5.3's release notes change which packed linked items count as directly linked and are written — under question 13.

**Verdict: it differs.** How Blender decides that two recorded library locations are one library or two came back identical in all five versions — in fifteen tests on both machines for 4.5 to 5.2, and in the same tests on the Mac for 5.3. What differs is packing: 4.5 cannot pack linked data and has none of the machinery for it, while 5.0 to 5.3 can, and doing so deliberately leaves the file holding two libraries with the very same recorded location — the one arrangement that the ordinary rules never produce. **Settled by the same test run in all four versions on both machines and in 5.3 on the Mac**, which is what makes this a real difference rather than a gap in somebody's reading, **and corroborated by 5.0's own release note.**

**What the fifteen results add up to, said once.** No single test states the rule, and no version's documentation states it either, so this is a reading of the whole set rather than a quotation from any part of it — but it is the reading every one of the fifteen supports, in every version, 5.3 included, and somebody designing around it needs it in one place:

- Two recordings that name the same file and differ only in how the path is written — relative against absolute, or a detour that leads back to the same place — are **one library**. Blender tidies the writing before it decides.
- Two recordings that reach the same file by two different names on disk — a symbolic link, a hard link, a symbolic link to the folder, and the same folder mounted twice (that last on the rented Linux machine only, because the Mac cannot do it) — are **a separate library each**. The tidying stops at the text; it does not go to the disk and ask what the file really is.
- Two recordings that differ only in capitals follow the file system, not Blender — **and this was run on two machines, so it settles those two and no others**: on the rented Linux machine, whose disk minds capitals, the second is simply not a file and the link fails; on the Creator's Mac, whose disk does not, both work and you get two libraries. What a third machine, or Windows, would do is untested.
- Two different files that happen to share a file name are **two libraries**, and the second entry's name gets a numbered suffix.
- The decision is made when a file is read, not only when a link is made: two entries forced to hold identical text stand until the file is saved and opened again, and then there is one — and, in 5.3 at least, the data that came from the second file is then sought in the first and lost.
- Reaching one file directly and through another library is **one library**, and so is reaching it through two intermediate files that record it differently.
- From 5.0 onward, 5.3 included, packing is the deliberate exception: it makes a second library entry holding the same recorded location as the first.

**Not established.**

- **What happens when a library is relocated onto a file that another library in the same file already records.** This is the one thing the fifteen tests set out to settle and could not, and it is open in all four versions on both machines. The relocate operator was called with the second library named and the first library's file as the target; it reported success, two entries survived, and **the library named in the call had not moved at all** — what changed was the *other* entry's recorded text, rewritten from a full path into the `//` form. Two further tests were added on the spot. Calling it twice in one run, aimed at a third file that no library records, changed nothing either time. Calling it once per run, three separate runs, gave the same picture: with Blender started with no window this call reports success whatever it is given, does nothing at all when the target is a file no library records, and when the target is a file some existing library records, it rewrites *that* library's text into the `//` form and leaves the named one where it was. **Because the named library never moved, no collision ever arose**, so nothing about collisions was learned. Every version's findings say so, and doing it by right-clicking the entry in a window would settle it. **And the doing-nothing half does not hold everywhere: Reading a file 9** ran the same call, windowless, on a file linking one library and aimed at a file no library records, and it moved — the named library was repointed and its text recorded in the `//` form — in all four versions. The runs here were made on a file linking two libraries. **What separates the two is not established — do not read either as a general rule**, and the count of libraries is only one of the things the two set-ups differ in, the others being what was linked and the form each library's path was recorded in. **5.3 on the Mac, on a file linking two libraries, did exactly what this topic's runs did**: aimed at the file the other library records, it rewrote that library's text into the `//` form and left the named one where it was; aimed at a file no library records, it changed nothing; both answered `{'FINISHED'}`. Open in all five.
- **Whether any of this behaves differently with a window open.** Neither machine ran a window for this question — the third rented Linux machine has no display server, and none was opened on the Mac, in any of the five versions. So everything above is established for Blender driven from outside its own interface and for nothing else, in every version. Three particular things were dropped for want of a window and each has what was done instead written beside it: Blender's memory figure in the Status Bar before and after a second link, which was replaced by printing which library each object belongs to; what the Info editor shows after a relocate, replaced by keeping the operator's returned value and everything printed to the terminal; and what the File Browser does with a name typed in different capitals, replaced by handing the differently spelled path straight to the link operator. Counting rows in the Outliner's Blender File view was not dropped but replaced — the same entries read from a terminal — and how those rows are laid out and labelled on screen is untested in every version.
- **Everything about Windows.** No Windows machine ran this question; the one this topic reached ran question 20 alone. A drive letter mapped to a network folder against the server-and-share form of the same folder, back slashes against forward slashes in a recorded location, a directory junction as a second route into a folder, and the Windows arm of the capitals test all stay **untested rather than answered**, in every version. That is a silence in what could be tried and it is not a difference between versions.
- **Two different network mounts of one share.** This needs a second computer serving a share, which the project does not have. The nearest thing that could be done is the second mount of one folder on the rented Linux machine, above, and it is not the same condition.
- **The other meaning of the word "library".** An asset library is a folder registered in Preferences. Its name is not required to be unique; how two registered locations are told apart is unestablished here. No test touched this reading in any version.
- **Whether a packed linked object outlives its library in 4.5 to 5.2.** Only 5.3 was asked — and 4.5 cannot pack linked data at all.
- **What 4.5 to 5.2 print when two identical library entries are merged on reading.** Their records give the count and not the words.
- **One thing only 5.2's record raises, and it is a silence in the other four rather than a difference.** Blender's documentation has a plain "this file is already loaded, re-use what is there" option on the calls that load an image, a sound, a font or a movie clip, and no such option on the call that loads a library — and on the movie-clip loader the words quoted say that option is switched off. Blender 5.2's record sets out the contrast; no other version's mentions it at all. Nothing in any release note says the option was added to or removed from anything, and no test touched it. **Do not read it as a difference between versions.**

## 20. When a `.blend` file is opened and saved again, and none of the places it records for outside files is touched while it is open, what does the saved file record for each of those places?

**How it is known.** The sourced answer about untouched paths is inferred from documented save settings, not stated outright. The saves, path text, bytes and listings below are observed on the named machines. Blender 5.3's release notes separately add initial support for unchanged files on opening and saving and change which packed linked items are written (question 13). Their full reach was not tested.

**Everything below was settled by test, not by reading**, on three machines whose Blenders match one another build for build. Eight tests were run in all four versions on the Creator's Mac and again in all four on the fourth rented Linux machine; seven on the Mac alone, of which one is in Blender 5.2 alone and two cross a pair of versions rather than all four; one on the rented Linux machine alone, because it needed a real window; one carrying a file from the Mac to that machine, in 4.5 and 5.2; and **six on the rented Windows machine, which reported itself as Windows Server 2025 Standard** — five of them in all four versions and the crossing in 4.5 and 5.2. Nothing here was rendered; every result is text read out of Blender or out of a file's own bytes. All of it is labelled **observed**, and each answer below says which machines it rests on. **In 5.3 the Mac's tests were run again on the Mac alone**, from a file built the same way with three more kinds in it — an Alembic cache, a movie clip and a movie strip, each made for the test — one of them through a window driven from a script; nothing was run on Linux or Windows, and nothing crossed between machines.

**The same in all five.** A plain save over the same file, with nothing touched, writes every recorded place back with the text it already held. That was checked two ways at once — by asking the running Blender, and by pulling the path text straight out of the file's bytes — and the two agree. What came back character for character, in every version on the Creator's Mac and on the rented Linux machine — and on the rented Windows machine too, apart from the separator, which is the next paragraph: a plain relative place, a full path, a `..` segment that still resolves, a doubled separator, the wrong letter case, a name in characters outside the Latin alphabet, a name with a space in it, a trailing space, a place pointing at nothing, a place one folder up, a template with its braces still in it, and the places recorded for a library, a font, a sound, a volume, a text, an OSL script node, a light-profile node, the bake picture, the cloth cache, the geometry-nodes bake folder and the sequencer's proxy folder. The two settings a script can read a place through printed the same string every single time, on all three machines. **5.3 on the Mac gave the same**: between the first opening and the opening after a plain save not one printed place differed, and that held as well for the movie strip, the sound strip, the movie clip — recorded as a full path, as it was loaded — and the Alembic file and its object path.

**Two things do change at a plain save that nobody asked for, and both are the same in all five versions.**

**The first is the separator, and which way it is re-spelled follows the computer rather than the version.** On the Creator's Mac and on the rented Linux machine, a place written with a backslash comes back written with a forward slash. On the rented Windows machine it runs the other way and it is much larger: **every forward slash in a recorded place becomes a backslash**. The re-spelling happens when the file is *opened*, and the plain save then writes it into the file. Nothing else about the text moves in either direction — the leading `//` stays, a doubled separator stays doubled, a `..` step stays, letter case stays, a trailing space stays, non-Latin characters come through unharmed, a place pointing at nothing is re-spelled just the same. **All four versions do the same thing on each machine, so this is a fact about operating systems and not a difference between versions.** 5.3 on the Mac did the Mac's thing: the build's own save wrote `//assets\tex.png` and `//assets\..\assets//TEX.PNG ` into the file as typed, both found in the file's text; the first opening read them with forward slashes; and the plain save wrote the forward-slash spellings into the file.

**Seven recorded places keep their forward slashes on Windows and are the only ones that do**, in all four versions, checked by name rather than read off an absence: the compositor output node's folder, the cloth cache's folder, the geometry-nodes bake folder, the bake picture's place, the sequencer's proxy folder, the linked library's own place, and the weak reference beside it. **The last two are on the list only because both are `//lib.blend`, with no separator in them to change**, so five real places are left alone. **The render output path is not among them**, and it is also a place written to, so the rule is not "places written to are left alone".

**The second is that a data-block nobody is using is dropped at the save, taking its recorded place with it.** An image with no users and no fake user disappeared at the plain save in every version on all three machines, and the weak reference beside it, which recorded the library it had been appended from, went too. An unused image shielded with a fake user survived every save. One built with no users and no shield never reached the first reading at all, because the build's own save had already dropped it. **In 5.3 on the Mac both unused images — the appended one with its weak reference, and the unshielded one — were already gone at the first opening**, dropped by the build's own save, and the shielded one survived. The 5.2.2 run of the same build did the same, so which save drops it follows the build; that a save drops it is the same in all five.

**In the earlier 4.5 to 5.2 runs, the plain save changed both bytes and size.** That is not the result for 5.3 or its 5.2.2 Mac control below. **That is not established as a rule about plain saves**, and the reason is named in the sentence above it — the test file carried an unused data-block, which the first save drops, so a different size was certain once and could not have come out the other way. Nothing here varied whether such a data-block was present, and **Reading a file 1** records two saves of one file coming back the same size, attaching its own instability warning to compressed saves alone. **In 5.3 the unused data had already gone before the plain save, and the size came back the same** — 600,713 bytes before and after — while the bytes still differed: seven lines of the file's text changed, two of them the backslash spellings. The 5.2.2 run of the same build also kept its size. **What stands whatever the truth of that is the advice**: a check that compares whole files, or their checksums, says nothing about whether a recorded place moved — the separator re-spelling and the dropped data-block both move the bytes. **Only the path text can be compared.**

**Saving somewhere else is the other reading of the question, and it answers differently — the same way in all four versions.** Saving into a **different folder** with nothing passed for the remap setting rewrites every relative place a file is *read* from, and tidies it on the way: a `..` segment and a doubled separator are collapsed, letter case and a trailing space are kept, a place pointing at nothing is rewritten just the same, and a place written as a full path is not touched at all. **The tested write places are not touched either** — the render output path, the bake path, the compositor node's folder, the cloth cache, the geometry-nodes bake folder and the sequencer's proxy folder all still read what they read before, which after the move means a different place on disk. Turning the remap setting off leaves the text alone and the pictures then stop loading. Saving into the **same** folder under a new name changes nothing, and neither does a plain save with the remap setting deliberately switched on — so "a different directory" is a real boundary. Save Incremental writes a numbered file beside the original in the same folder and changes no recorded place. **5.3 on the Mac did all of this the same way**, with a bare geometry-nodes modifier holding a folder, not an actual bake (question 17). It also showed it for the three kinds no earlier version was given: saving into another folder rewrote the Alembic file's and the movie strip's relative places like any other, and left the movie clip's full path and the Alembic object path alone. With the remap setting off, the opened copy also printed that the library, the font and the Alembic file could not be found. And saving into a folder that does not exist failed with `Cannot open file <path>/main.blend@ for writing: No such file or directory` and wrote nothing.

**On Windows that shape is the same and one case is sharper** — for 4.5 to 5.2, as every Windows result here is. Saving into another folder on the same drive behaves exactly as it does on the Mac, written the Windows way. But **saving the file onto a second drive turns every relative place into a full path naming the old drive, and says nothing about it** — the one place already on the new drive is the only relative-or-not place left as it was. Windows cannot form a relative path across drives, and Make Paths Relative names such a place, refuses it and carries on: it prints which place failed and which data-block it belonged to, counts the failure, and **still reports itself finished**, so a caller reading only the answer will not know a place was left behind. All four versions.

**Letter case in a drive letter survives a plain save and survives Make Paths Absolute**, in all four versions, and Windows finds the file either way. Make Paths Relative removes the drive letter and with it the question. A place written as a drive letter with no root behind it is the one result here that looks wrong: Make Paths Relative treats it as an ordinary relative name and puts steps back up in front of it, producing text that can name no file on any machine, in all four versions.

**Crossing between machines rewrites a file's whole recorded text, both ways, by a save that touched nothing.** A file saved on Windows and opened on the Mac has every backslash turned into a forward slash — including the full Windows paths and the second drive's, which the Mac cannot resolve and rewrites anyway — and the same file carried back and saved once on Windows has them all turned back. The five places that keep their forward slashes on Windows keep them on the Mac too, so they are the only text that survives a round trip unchanged. Blender 4.5 and 5.2 do exactly the same thing. The Mac-to-Linux crossing, run in 4.5 and 5.2, changes nothing but the backslash entries, as above. **One thing that differs on a crossing is about finding a file rather than recording its place:** a place written `//assets/TEX.PNG` against a file named `tex.png` loads the picture on the Mac and does not load it on Linux. The recorded text is identical on both; what differs is the file system's answer, which is question 8's result.

**What changes the spelling is the reload; whether the way of asking changes it as well is not settled.** A file's recorded places can be listed through `bpy.utils.blend_paths` or through `bpy.data.file_path_map`. In the process that has just built the file and never reloaded it, both report a place written with a backslash exactly as it was set, backslash and all; in a fresh process that has opened the file from disk, both report it with forward slashes. Same in all four versions. **How well established that is, said plainly: it is a macOS result, taken three times, and one of the three does not agree with the other two.** Two of the three found the two ways agreeing in the building process, one of them comparing the strings character by character by script rather than by eye; the third found them disagreeing there, one showing the backslash and the other forward slashes. The stored output of that odd one reads the same way as the other two. Nothing settles which is right, and nothing here is settled beyond what three runs on one machine can settle. **On the rented Windows machine the two ways agree with each other too**, in the building process and after a reload, in all four versions — so on that machine both agree with each other and both disagree with any file that was written anywhere else, which moves the danger rather than removing it. **5.3's one run on the Mac agrees with the two**: both ways gave the backslash spellings in the process that built the file, and both gave forward slashes once it had been opened from disk.

**The two ways do not return the same collection of places, and that is a different thing from the spelling.** In the building process on the Mac one returns 24 strings and the other 27, in every version; the extras are repeated copies of places both report rather than places one spells differently. 5.3's file, which held more kinds, gave 27 from each in the building process and 24 against 25 once opened from disk, the extra one in `file_path_map` being `//lib.blend`; the 5.2.2 run of that file gave the same once opened. On Windows the same holds, with larger totals because that file was built with eight more spellings in it, and with the linked library's own inner picture among the extras because one route reaches through the library and the other does not.

**The two listing functions exist in 4.5 to 5.2 on the three tested machines; `bpy.data.file_path_foreach` exists in 5.0 to 5.2 and not in 4.5. In 5.3 all three exist on the Mac alone**, which is question 1's result. No 5.3 Linux or Windows run established their presence there. So Blender 5.1's record that one of them appears nowhere in 5.1's documentation is a gap in that documentation and not a difference in Blender.

**Other things a save does, and does not do, the same in all five versions.** Switching on Automatically Pack Resources and saving leaves every recorded place with exactly the text it had and only turns the packed mark on, and the file grows — in 5.3, twelve items packed, the movie clip, text, Alembic file, library and the OSL and IES nodes not among them. Setting the preference for relative paths to off and then saving changes no recorded place. Giving Blender a render output on the command line **before** the file is named is overwritten by loading the file; giving it **after** the file sticks, and a following plain save writes it into the file — so a driven run can touch a recorded place with nobody editing anything. An automatically written file, whether the timed one or the one left at quitting, records exactly the same text as the file it came from; the pictures do not load from it only because it sits in a temporary folder, so a place written relative no longer reaches them — in 4.5 to 5.2 on the rented Linux machine alone, and in 5.3 through a window on the Mac. The shipped values of both save commands match what every version's documentation says, and the four choices offered for unpacking are worded the same in all four.

**What the same command does on a file holding places that point at nothing is not settled.** In 4.5 to 5.2's runs it refused outright, naming the one it could not find, and the save never happened. In 5.3 on the Mac it printed `Unable to pack file` for each of the four places that reach nothing, raised the same error — and **wrote the file anyway**, with twelve items packed, those four not, a backup copy beside it, and no warning on reopening. **The 5.2.2 run of the same steps on the same Mac did exactly the same.** What kept the earlier runs' file from being written is not recorded, so this is not a difference between versions — but a caller that takes the error to mean nothing was saved can be wrong.

**The timed save, in 5.3.** Through a window on the Mac, with the auto-save interval set to one minute and a 75-second pause, 5.3 wrote both a timed save and a file at quitting, each recording the same text as the file it came from. The 5.2.2 run of the same steps did the same. That bears on the 4.5-against-5.x split below.

**Opening a file made by another version and saving it rewrites no recorded place.** A file made in 4.5 and saved in 5.0, 5.1 and 5.2 came through with every place unchanged but the dropped data-block, and the compositor node's single recorded place was carried straight into the newer shape with the file-name half left empty. A file made in 5.2, opened in 4.5 with no window and saved, **went through with no prompt of any kind** — it printed a warning that the file was written by a newer Blender and finished — and changed no recorded place. Both on the Creator's Mac. 5.3 was not given a file made by another version.

**Saving a file writes nothing into a library it links.** The library file's time, size and checksum were the same before and after the parent's save. Run in Blender 5.2 and 5.3 alone, on the Creator's Mac.

**Where it differs, version by version.** Not in what a save records — that came back identical in all five — but in two settings around it, each asked for by name in all five versions **on the Creator's Mac, and on no other machine**.

**Blender 4.5, 5.0 and 5.1.** There is no setting for saving pictures changed inside Blender; asking for it throws. The preference deciding whether a saved file is compressed is off in 4.5 and on in 5.0 and 5.1.

**Blender 5.2 and 5.3.** The setting exists, with three choices and "ask" as the shipped one, and the save commands carry one more setting than the other three versions' do — `show_save_modified_images_dialog`, off by default, read off 5.3 by name. With no window, "ask" behaves as "never": nothing stopped, nothing waited, and the picture's own file was left alone. Set to always save, the picture's file was rewritten; set to never, it was not. **The recorded place is the same string in all three cases**, so this setting decides whether a picture's own file is rewritten and never what the blend-file records for it. The compression preference is on, as in 5.0 and 5.1. **5.3 on the Mac did the same at all three choices**: "ask" left the picture's file alone with no window, "always save" rewrote it, "never save" did not, and the recorded place read `//assets/paint.png` every time; none left the picture packed. Its compression preference is on.

**One more thing looks like a version difference and is not established as one.** Blender 4.5 wrote an automatic timed save where 5.0, 5.1 and 5.2 wrote only a file at quitting, in three separate runs on the rented Linux machine, with the save interval left as it was. The split itself was seen every time; what is not settled is whether it is a change in Blender or a difference in when a version decides a file has been edited, so it is not listed as a difference in Blender. With the interval shortened to one minute on the Mac, 5.3 and the 5.2.2 run both wrote a timed save, which makes a change in Blender less likely and settles nothing about 5.0 and 5.1.

**And one change 5.3's release notes record, whose reach is unknown.** They give "Initial support for keeping .blend files the same when opening and saving a .blend file" as new, and do not say what it covers. Nothing in the 5.3 runs showed it: every recorded place behaved as in the 5.2.2 run, and a plain save still changed the file's bytes. The release note establishes a change. Its reach is unknown; it does not establish a different result for the path spellings tested here.

**Verdict: the same everywhere.** What a saved file records for a place nobody touched is one behaviour in 4.5, 5.0, 5.1, 5.2 and 5.3 alike: the same text, with the separator re-spelled to the one the computer uses, and with a data-block nobody is using dropped altogether. Saving into a different folder rewrites the tested relative read places and leaves the tested write places alone, in all five. In 5.3 the geometry-nodes folder belonged to a bare modifier; this does not settle saving a file with an actual bake. **Settled by test in all four versions on the Creator's Mac and again in all four on the fourth rented Linux machine; on the rented Windows machine, which reported itself as Windows Server 2025 Standard, in all four versions for the separator, the two drives, the drive letter, the two ways of asking and saving somewhere else, and in 4.5 and 5.2 for the crossing; and in 5.3 on the Mac alone.** What differs between the versions is what surrounds a save rather than what a save records: 5.2 and 5.3 alone can be told to write out pictures changed inside Blender, and the compression preference is off in 4.5 and on from 5.0, 5.3 included. **That pair was settled on the Creator's Mac alone**, with Blender 5.0's own release note behind the compression half and nothing behind the other but the test. Neither changes a recorded place.

**Not established.**

- **Whether 5.3 behaves on Linux and Windows as 4.5 to 5.2 did.** Not run — the separator going the other way on Windows, the second drive, the drive letter and every crossing among them.
- **What 5.3's "initial support for keeping .blend files the same" covers.** Set out above.
- **Whether a save with Automatically Pack Resources on, in a file holding places that reach nothing, writes the file.** Set out above: the earlier runs say no, 5.3 and the 5.2.2 run say yes.
- **Whether the two ways of asking a file for its outside places ever disagree about spelling.** Three runs on the Creator's Mac in 4.5 to 5.2: two say they agree in the process that built the file, one says they do not. 5.3's run on the Mac agrees with the two. Nothing settles what happened in the odd one, and the machines the other operating systems' runs used are gone.
- **Whether a desktop edition of Windows behaves as the Server edition did.** Every Windows result here was taken on Windows Server 2025 Standard, on a machine created from an image named for the desktop edition; a second image in the same account, also named for a desktop edition, booted Windows Server 2016. Nothing seen suggests the separator behaviour would differ, and nothing has shown it.
- **Why five recorded places keep their forward slashes on Windows while the render output path does not.** The five are known by name and behave the same in all four versions; what separates them is not.
- **What a drive letter with no root behind it is meant to mean**, and therefore whether what Make Paths Relative does with one is wrong. All four versions do the same thing, and the place did not reach its picture before the command either.
- **Why Blender 4.5 writes an automatic timed save where the newer three write only a file at quitting**, with the interval left as it was. Shortened to one minute, 5.3 and the 5.2.2 run wrote one on the Mac.
- **What a save records for a cache file, a movie clip or a movie strip, in 4.5 to 5.2.** Each needs a real file of its kind to put into a test file, so none was in the file their tests start from. 5.3 was given all three, and a plain save kept each one's text.
- **Whether saving a file leaves the library it links untouched in 4.5, 5.0 and 5.1.** Run in 5.2 and 5.3 alone.
- **Which packed linked items 5.3 writes into a saved file.** Its release notes say only directly linked ones (question 13); no test looked.
- **A place on a network share, written the way Windows writes one.** The second drive in these tests is a drive letter mapped onto a folder, which answers the two-drives question and not the share one. There is no folder on network storage that two of this project's machines can reach at the same moment.
