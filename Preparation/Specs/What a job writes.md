# What a job writes

*What a render job actually puts on disk, where it lands, and which of it Smoozy treats as the work that matters. Not one word about how it's built.*

**How firm the Blender facts here are.** The Creator has asked that every Blender fact in this document be confirmed at Blender Research, and confirmed with more rigour than anything else in the project, because a file output node's behaviour changes from version to version. Most of it has now been checked, so each fact carries its own label where it stands: **documented**, **observed** or **inferred** where the research has answered it, naming the version every time the versions differ; **Creator-stated** where the fact is still the Creator's and is expected to be checked, which never means settled; **an assumption** where something is leaned on without support; and **unresolved** where nobody has established it at all. Several things the Creator recalled have been overturned or narrowed by what the research found, and the research stands each time. See [Sources](Sources/What%20a%20job%20writes.sources.md).

**Which machines the checked answers rest on.** Nearly every one was run twice — on an Apple-silicon Mac, and on a rented Linux machine with an NVIDIA card, which is the kind of machine Smoozy renders on — and the two agreed. Where an answer rests on one machine only, it says so where it stands. Several rented machines were used over the rounds, and no figure from one is ever set against a figure from another. No Windows machine is among them, which bears only on what an artist's own file carries into a job. A Windows machine can be rented, so that gap is untried rather than out of reach.

**What Smoozy does about all this is decided, and the research has shown it can be carried out.** The two mechanisms the whole document rests on — bringing every place a job writes under one folder, and naming every file a frame owes before the render starts — were both checked and both work in every supported version. What is left open is smaller, and each open thing says so where it stands rather than only in a section further down.

## Why this is its own document

Four modules make promises about a job's outputs, and none of them owns the question. **Render Settings** reads the file and declines to offer the output path. **Queue & History** gives each job a folder and picks a picture out of it. **Download** counts a job's files, narrows an arrangement by format, and watches one folder for new arrivals. **Rendering** starts the render that writes all of it. What none of them holds is the thing they all lean on: what a `.blend` will actually write, and where.

So it is settled here, once, and those modules point at it. Settled means the product decisions are made in one place; it does not mean every fact underneath them is in.

## A render writes files in two quite separate ways

A `.blend` writes through its **regular output path**, and separately through the **file output nodes** in its **compositor**. All three names are the [Glossary](../Groundwork/Glossary.md)'s, which holds what each one is; what this document adds is what Smoozy does about them.

The two routes are set up separately and neither implies the other, but the same picture can land in both. Every file has a regular output path, and it writes unless Blender 5.2's own switch turns it off — the only version with such a switch. File output nodes are a thing the artist adds, so a file with several of them is as ordinary as a file with none. Label: **documented and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md). That split is what the rest of this document is about.

**A node writes its files as each frame finishes, not in one lot at the end of the job.** Over a four-frame animation each frame's file carried a time of its own, in Blender 4.5, 5.0, 5.1 and 5.2 alike. Two conditions travel with it: the node writes during a render only — a compositor running in a viewport writes nothing, which was tried on the Mac alone — and switching compositing off stops it writing at all. Label: **documented and observed** (the same in all four versions). See [Sources](Sources/What%20a%20job%20writes.sources.md).

**A compositor belongs to one scene in Blender 4.5, and from Blender 5.0 it is a thing the file holds.** In 4.5 a compositing tree cannot be shared — pointing a second scene at one is refused outright. From 5.0 the tree stands in its own right and a scene points at it, so two scenes can share one; where they do, the shared tree writes the picture of the scene named inside it rather than the picture of the scene being rendered. Which compositor runs is decided by which scene is rendered, in every version. Label: **documented and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md).

A job is always exactly one scene (see [Queue & History](Queue%20&%20History.md)), so from Blender 5.0 two jobs from one file can be driving the same compositor, and one of them may be writing the other's picture. **Where a job's scene shares its compositor with another scene, Smoozy says so before the job is submitted** — the pictures the job writes may belong to that other scene rather than to the one being rendered. It arises from Blender 5.0 on and never in 4.5, which cannot share a compositor at all. Label: **Creator-stated** (2026-08-03). It is the fifth of the things said before submitting — see [What the user is told before submitting](#what-the-user-is-told-before-submitting).

**A second scene's picture arrives by two routes, and they behave differently.** A scene can take in another scene's rendered result — that behaviour is [Render Settings](Render%20Settings.md)'s. Through a **Render Layers node** pointing at the other scene, that scene's compositor does no work at all and its own file output nodes stay silent, whatever its own compositing switch is set to. Through a **strip in the video sequencer**, that scene's compositor genuinely runs and its file output nodes write, whenever that scene's own compositing switch is on. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

So a job named for one scene does write another scene's outputs into its folder, by the second route and not the first. Everything this document settles covers both: the folders shown before submitting, the file count, the list of formats, the search for the main output and the re-run reckoning all take in every scene a sequencer strip reaches, and not only the job's own.

## Whether anything writes at all is not a given

Three things decide it, and each has to be read out of the file rather than assumed.

**Whether the compositor runs.** Three conditions gate it in every version and all three must hold: the **Compositing** switch is on, a compositing tree is present, and that tree holds a live final output node. With any one of them missing the raw render is written instead. The final output node is not the same node in every version — it is the **Composite** node in Blender 4.5, and the **Group Output** node in 5.0, 5.1 and 5.2, which have no Composite node at all. Muting it stops the compositor's result reaching the file in Blender 4.5 and makes no difference in the other three. Blender 4.5 also has a fourth condition the later versions do not — its old **Use Nodes** switch, which starts off in a new file and leaves the raw render in the file when it is off; from Blender 5.0 that switch decides nothing. **Of those three conditions, only the Compositing switch reaches a file output node**: with it off, a node in the tree writes nothing at all. A tree whose final output node is missing or muted still writes its file output nodes. Label: **documented, inferred and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md). So *does this file have file output nodes* is the wrong question — the question is whether they will run.

**And when the compositor does run, the regular output path holds its result rather than the raw render.** The picture that lands there is whatever reaches the final output node, in every version. Label: **documented and observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md). That matters below: the regular output path holds the beauty pass only when the artist wired the beauty to that node.

**Whether the regular output path writes.** It can be switched off entirely from **Blender 5.2** and no earlier: a **Save Output** switch, on by default, which stops the regular output path writing even when a path is handed in at the moment the render is started, while a file output node in the same file goes on writing. Blender 4.5, 5.0 and 5.1 have no such switch, and its absence was checked in each of them rather than read out of a quiet manual. Label: **documented and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**Whether an individual node writes.** Muting a whole file output node stops it — nothing appears on disk, and it does not even make its folders. There is no switch for one output on its own, but an output is silenced by cutting or muting the link that feeds it, and an output with nothing connected writes nothing at all. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**A job that writes nothing at all arises only from Blender 5.2, and it takes two shapes.** In Blender 4.5, 5.0 and 5.1 the regular output path cannot be switched off, so a job there always writes its frames somewhere unless the render fails. From Blender 5.2, with the Save Output switch off:

- **Where the compositor has a file output node Blender counts as live, the render runs** and that node's files are the only ones. That is an ordinary, working setup, not a fault.
- **Where it has none, Blender refuses the render outright** and says so, before any frame is started. Nothing is written and the output folder is not even made. Label: **documented and observed** (Blender 5.2 alone) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

So the case this document was written for — a render that runs to the end and leaves nothing — needs Blender to count a node as live while that node writes nothing, which a muted node, an output with nothing connected, or the Compositing switch being off all produce. Label: **permanently unresolved** — see [Sources](Sources/What%20a%20job%20writes.sources.md). Whether Blender counts a node that will write nothing as a live one was never asked during the Blender research, and the Creator ruled on 2026-08-31 that there will be no further research, so it will not now be asked. **Nothing waits on it.** Smoozy's warning and the Creator's ruling two paragraphs below hold whichever way it goes, and all the answer would change is how often this case comes up. What holds without it is settled at Architecture — see the [Job files and outputs architecture](../Architecture/Job%20files%20and%20outputs.md), unresolved list item 14, Row 124.

**What such a render leaves behind is nothing anyone can keep.** The finished picture stays inside Blender and dies with it when the render ends. Nothing is written to the output folder, and Blender's own temporary folder is empty before, during and after, even on a long render. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). All the user gets is what the machine says while it works, which [Queue & History](Queue%20&%20History.md) already shows them as Blender's raw output.

**Smoozy warns and lets the user go ahead anyway, with the option to stop.** Label: **Creator-stated** (2026-08-06). A job that writes nothing is not treated as a failure, and Smoozy does not refuse to run it — but it costs a rented machine real money for nothing to keep, so Smoozy says so before the job is submitted where the file has been read, and holds the job at its start where it has not (see [What the user is told before submitting](#what-the-user-is-told-before-submitting)). [Queue & History](Queue%20&%20History.md) already holds that a job producing nothing is a real thing. **That is a job that owes nothing. A job that owed files and wrote none of them is a failed render** ([Queue & History](Queue%20&%20History.md#when-a-render-fails), added 2026-11-02).

## What a file output node can do

One node is not one file — see the [Glossary](../Groundwork/Glossary.md). What follows is what the rest of this document leans on.

**A node writes whatever picture it is fed, and that picture need not have come straight from the render.** It has to be a picture: an output fed something that is not one wrote nothing at all, and said nothing about it. A picture that reached the node through other nodes is written normally. Label: **documented, inferred and observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md). So a node's existence says nothing about what is in it, which is why the main output below is found by following the beauty pass rather than by asking which kind of destination something is.

**One folder belongs to the node, and each output carries a name.** There is a single folder setting and it sits on the node; an output has a name and no folder of its own. Label: **inferred and observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**A folder can sometimes be made by putting a separator inside an output's name, and what that does differs sharply by version.** Label: **documented and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md).

- **Blender 4.5.** It works. Names are kept as typed, a separator makes folders as deep as asked, and missing folders are made. A name can also climb *upwards* and land its file outside the node's own folder.
- **Blender 5.0.** It cannot be done at all. Every separator in a name is replaced with an underscore, and every one of the node's files lands flat in the node's own folder.
- **Blender 5.1 and 5.2.** It works, but a name cannot climb out of the node's folder. The node's own base file name is joined to the front of the output's name before the split, so it becomes part of the first folder's name.

So one product rule cannot preserve the artist's arrangement everywhere: an artist who separated their passes by name gets those folders in 4.5, 5.1 and 5.2, and one flat folder in 5.0. What Smoozy redirects is the node's folder; what a name does beneath it is Blender's, and the rules below work on the folder rather than the name.

That is why the rules below are written in terms of **destinations** — one destination is one place a job writes into, whether that is the regular output path or one output inside a file output node. A node with several outputs is several destinations, and in Blender 5.0 every one of them sits in the node's own folder.

**The same picture can end up written several times over**, in several formats and several folders, because more than one node can be fed from the same place. Label: **Creator-stated** (2026-07-28). That is what makes a job's file count more than a count of frames, and what makes the main output a choice rather than a reading.

**Several outputs can be gathered into one file.** Set to write a multi-layer file, a node writes one file per frame holding every output as a layer of it, whatever the number of outputs, and each layer is named for the output it came from. The gathering is the same in all four versions; what differs is which setting switches the node into that way of writing, and how the single file is named — from the node's folder text in Blender 4.5, and from the node's own base file name from 5.0. Label: **documented, inferred and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**A file output node inside a group of nodes still writes**, once, wherever it sits, and muting the group from outside stops it. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md). Using the same group twice in one tree left one file, which is also what a collision looks like, so that case does not tell one write from two writes over the same place.

## Everything a job writes lands under the job's folder

[Queue & History](Queue%20&%20History.md) gives every job a folder of its own. This document settles what that means once file output nodes are involved: **Smoozy redirects every place the job would write so that all of it lands under that folder.** Label: **Creator-stated** as the decision (2026-07-28); the research has since shown it can be carried out — see below.

**The job's folder sits where the file's own outputs point. Added 2026-10-04.** It is made inside the deepest folder that every place the render itself writes into has in common — the regular output path and the file output nodes' folders, worked out on the server — so the job's files land beside the artist's own work rather than in a folder of Smoozy's. A file whose nodes write to `//../Render/PNG` and `//../Render/EXR` gets `Render/<the job's folder>/PNG` and `Render/<the job's folder>/EXR`, next to the folder the `.blend` sits in on the server, and its regular output lands at the top of the job's folder. The caches and bakes named in the next paragraph do not decide where it sits; they go into it. **One folder per job still holds, for the reasons it was chosen**: two jobs of the same file get two folders side by side and never write over each other, and [Download](Download.md) still has one folder to watch. Label: **Creator-stated** (2026-10-04), replacing the placing half of their rule of 2026-07-22, under which the job's folder sat in Smoozy's own area on the server.

**Two cases fall back to Smoozy's own area on the server, and the job says so.** Where the place the file points at belongs to another computer — a path from the artist's own Mac or Windows machine, which means nothing on the server — or is a folder Smoozy cannot use, the job's folder is made in Smoozy's own area instead, as it was before, and the job says which of the two it was. Nothing is held or asked for this: the files still all land in one folder and still come home. Label: **Creator-stated** (2026-10-04). *(Corrected later on 2026-10-04: the fallback is Smoozy's own area only where the user has not chosen another folder for that server — the next paragraph.)*

**The fallback folder can be chosen, once per server. Added 2026-10-04.** The user can name a folder on a server for the fallback to use instead of Smoozy's own area, set with that server's own details ([Servers](Servers.md)). Left empty, it is Smoozy's own area, exactly as above. Every job that falls back still gets its own folder inside whichever folder that is. It decides nothing else: where the place the file points at can be used on the server, the job's folder goes there as before. A chosen folder has to be one Smoozy can use, as a folder the file points at has to be; where it is not, at submission, the job's folder is made in Smoozy's own area and the job says so in the same words as any other fallback. The folder in force is the one set when the job was submitted, so changing it touches only jobs submitted afterwards. Label: **Creator-stated** (2026-10-04). *(Corrected later on 2026-10-04, ruled by the build runner under Rule 8: the user chose that folder, so the job does not change place without a word. Where the chosen folder cannot be used, the job also says, in one short sentence, that the server's fallback folder could not be used and its files are in Smoozy's own folder — beside the sentence saying why the file's own place was not used.)*

**Which places that covers is now named, because a file writes in more places than the obvious two.** The scene's own output path and each file output node's folder are the ones this document has been about. Beside them a file can record a bake output path, a point cache, a geometry-nodes bake folder and a sequencer proxy folder, and **those are redirected too**. So a bake and a cache written during the render land under the job's folder with everything else, are brought home with it, and are not left on a machine that is about to be destroyed. Label: **Creator-stated** (2026-08-18). **The geometry-nodes bake folder is narrowed: a bake uploaded beside the `.blend` is read where it is, and only a bake sent by *Check dependencies* is copied into the job's folder and read there.** Label: **Creator-stated** (2026-10-02). Nothing the job writes is left outside its folder by it: a geometry-nodes simulation set to bake to disk and never baked wrote nothing anywhere when rendered. Label: **observed** at the desk, 2026-10-02 — see [Sources](Sources/What%20a%20job%20writes.sources.md). What it costs when one of them cannot be brought under the folder is the same as for any other place: the job is held and the user is asked, as the next paragraph says.

**Every form of path a `.blend` can record is covered by the rule**, including one written relative to where the file sits and one written on another kind of computer. What each of those means on a rented Linux machine is set out under *Keeping the arrangement the artist built* below.

**Where Smoozy cannot bring a path under the job's folder, the job is held before the render starts and the user is given the choice** — stop, or carry on knowing that part of what the job writes will land somewhere Smoozy is not watching and will not bring home. Smoozy does not narrow the promise quietly and carry on: [Download](Download.md) is told it has one folder to watch, a file that escapes it never comes home, and whether that is acceptable is the user's to decide rather than Smoozy's to decide for them. Label: **Creator-stated** (2026-08-03).

The reason for the rule is not tidiness. A file output node can be pointed anywhere at all — a folder with no relation to the `.blend`, a drive that only exists on the artist's own computer, a drive reached over a network. Label: **Creator-stated** (2026-07-28). The `.blend` was made somewhere else and is rendering on a rented Linux machine, so a good number of those places do not exist there — and **Blender does not refuse a place that is not there. It makes it.** A missing folder, and a whole chain of missing folders, are made without a word, for the regular output path and for a node's folder alike. A whole folder tree shaped for the artist's own computer is built at the top of the rented machine's disk and written into, silently, and the render reports success. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). So an unredirected job does not fail loudly; it quietly fills a folder nobody will look in. Redirecting is what makes those files land where they can be found.

**What a write does when the folder cannot be written to, and when there is no room left, are two different failures and only one of them is safe.** An unwritable **regular output path** stops the render at its very first frame, leaves the folder completely empty with not even a part-written file in it, and ends with a failing exit status — the same in all four versions, on both machines. A full disk does not behave that way: the frame being written when the room runs out is written as far as it will go, Blender announces it as saved, and **a picture that does not end is left on disk**. That has now been run on a rented Linux machine as well as on the Mac — a single still and a three-frame animation in all four versions, and a four-hundred-frame animation in Blender 5.2 alone — and every run left a picture that does not end. Label: **observed** — see [Sources](Sources/What%20a%20job%20writes.sources.md). **Whether Blender says anything about the disk beside that saved line is not firm.** The run that wrote OpenEXR printed lines naming it; what the two that wrote PNG printed was not kept, so nothing says whether they mentioned the disk at all. Label: **observed** for the run that spoke, **unresolved** for the silence — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**A file output node fails differently from the regular output path, and its failure is quieter.** Where one of a frame's several writes cannot be finished — its name taken by a folder, its folder refusing writing, its path template broken, or the disk full — **the render carries on and reaches its last frame, and the process exit status is 0**. Everything else for that frame is still written: the node's other outputs, any other file output node, and the regular output path. Where the write was refused before any bytes went down, nothing is left behind — except on Linux with a full volume, where the files that could not be opened were left at zero bytes. Where the write started and then ran out of room, a part-written file is left **and Blender prints its ordinary saved line for it**, exactly as it does for a file written in full. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**Making the folder is the same story, and it splits the same way.** Where a node's folder cannot be made — the place above it refusing writing — the render does not stop, and it ends at a **successful** status. The regular output path in the same position does the opposite: the render stops at its first frame and ends at a failing status with nothing written. So one job can fail in two different ways and only one of them shows in the exit status. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). **This is the fifth thing this stage has found that Blender reports as success**, and it is written here for whoever builds the thing that reads a job's ending: a node's write is not covered by the exit status at all. That constraint is Architecture's to carry — see [Open Threads](../Groundwork/Open%20Threads.md).

**So neither the exit status nor a file's presence can be trusted on its own.** The words Blender prints for a failed write differ by version and by operating system — four wordings for one failure — so nothing here is decided by reading them. And a failure raised inside a script that catches it leaves a successful exit status behind. Label: **observed** (both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). What the user is told when a write fails is settled by *how a failure reaches the user* in [Whole app](Whole%20app.md); that a finished-looking file may not be finished reaches the re-run rule below.

**What the exit status can be trusted for is narrower than it looks, and it is worth stating exactly.** A run that could not read the `.blend` at all ends with a failing status, so Smoozy can tell *the job never started* from *the job ran*. It cannot tell *everything was written* from *a file was lost*: a job that lost one of a frame's files to a full disk ends at success, with a saved line printed for the file that is not whole. **The rule behind that is exact, and it is not what it looks like.** A part-written frame never sets the exit status; what sets it is the **next** write, the one that cannot be opened at all. So a job of one frame that runs out of room prints its ordinary saved line and ends at a **successful** status over a picture that is not whole, while a job with a frame after it ends at a failing status when that next frame cannot be opened. Format, picture size, version, and whether the disk was already full or filled part way explain none of the runs behind this; the rule explains all of them. Label: **observed** (the failing case in all four versions on both machines; the successful one in all four versions on a rented Linux machine) — see [Sources](Sources/What%20a%20job%20writes.sources.md). **The only signal a lost write leaves anywhere is a line naming the path in what the machine printed, and where the room ran out even that is not certain, as above.** Nothing on the node records it, Blender fires no hook for a failed frame write though it has one for a failed file save, and **counting the files that arrive does not catch it either** — a write that ran out of room leaves a file at the right name, and this document says plainly that Smoozy cannot tell that file from a finished one. So a program driving the render cannot be told, only read. That is what [Queue & History](Queue%20&%20History.md) already shows the user as Blender's raw output, and it is all there is.

**So the frame a full disk stopped on leaves a file Smoozy cannot vouch for.** The picture that does not end carries the name the finished frame would have carried, Blender's own announcement calls that frame saved, and the two things Smoozy could otherwise judge by — the exit status and the file being there — are the two just named as untrustworthy. So Smoozy does not tell that file from a finished one, and does not pretend to. **A file left by a write that ran out of room is one Smoozy cannot treat as finished**, which is the standing this document already gives a file caught part-written mid-render. That reaches three places: what counts as already there for a re-run below, which file the frame preview reads, and what [Download](Download.md) brings home.

Redirecting also gives **Download** one place to watch and to bring home, and it leaves one folder to get right on the machine's disk rather than many.

**Redirecting does not change the artist's `.blend`.** The file the user uploaded and can open again is left exactly as it was, so nothing about their own setup is rewritten to make the redirect work. Label: **Creator-stated** (2026-07-28). That is a promise about this redirect and not about Smoozy as a whole — whether any other part of Smoozy changes the file is that module's to say. **Dependency Upload & Remap** changes files by design, but never this one: the file the user points at for a render is read and never written to, and what that module rewrites is the files Smoozy itself put on the machine. Label: **Creator-stated** (2026-07-28).

**The redirect can be arranged, and both halves of it were checked.** The regular output path can be settled at the moment the render starts, and the `.blend` on disk is left byte for byte as it was. A file output node's own place can be settled too, though not the same way: no version has a way of doing it as the render starts, so it is done either by a script handed to Blender at launch — which reaches the node's values and the render that follows uses them — or by writing the new place into a file and saving it. Label: **documented, inferred and observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**What differs by version is what has to be written, not whether it can be.** The two values a node keeps are named one way in Blender 4.5 and another from 5.0, so whatever carries out the redirect has to know which Blender it is driving. That is Architecture's to hold; what this document settles is that the promise can be kept in every supported version. Where the route chosen writes into a file, it writes into a copy Smoozy renders from — the promise above is about the artist's own `.blend`, not about whatever Smoozy hands to Blender. One way of doing that is parked in [Open Threads](../Groundwork/Open%20Threads.md).

**One thing the redirect cannot be built on, and it is worth naming so nobody reaches for it.** Blender's own bulk commands for rewriting all of a file's recorded locations at once — the ones that make every path relative or absolute, and the list of a file's outside files — **do not reach the places a file records for writing**. They miss the regular output path, a file output node's own folder, and every kind of cache and bake folder but one — an ocean modifier's cache path is reached — in every version. So making a file's paths relative leaves its render output path exactly where it was, and asking Blender what a file points at will never name the folder it is about to write into. Each of those settings has to be reached and written on its own. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md). That constrains how Architecture carries the redirect out; it takes nothing away from the promise.

### Keeping the arrangement the artist built

The folders an artist sets up in their nodes mean something — `beauty`, `mist`, `depth` — and redirecting must not lose that separation. Label: **Creator-stated** (2026-07-28).

**Two things are promised, and they are the binding part.** Everything a job writes lands under the job's folder, and the arrangement of folders the artist built survives inside it. Label: **Creator-stated** as the decision (2026-07-28); both can be carried out, for the reason above.

The rest of this section is one way those two promises could be kept, worked through with the Creator and written down so the thinking is not lost. It is a suggestion to Architecture, not a fixed decision: **take the folder every destination writes into, throw away the run of folders they all share, and keep what is left under the job's folder.**

Four things would pin that down, because each is a place two readings could differ:

- **The shared run is measured in whole folder names, never in letters.** `/home/a/out` and `/home/a/output2` share `/home/a`, not `/home/a/out`.
- **A destination with nothing left after the shared run is taken away lands at the job's folder itself.** That covers the ordinary file with one destination and no compositor, and it covers several destinations that were the same place — either way there is nothing left to tell apart, so nothing is invented to tell them apart with.
- **A destination's folder is what the rule works on**, not the name the output carries. For a file output node the folder is the node's and the name is the output's, kept as two separate settings. The regular output path is **one single piece of text holding the folder and the front of the name together** — but Blender itself splits it at the last separator, treating everything before as the folder and whatever follows as the front of the file's name, so the rule works on the part before that separator. A path ending in a separator has no name front at all, and the file is named by its frame number alone. Label: **documented and observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md).
- **A name that climbs out of its node's folder is not carried by the rule.** In Blender 4.5 an output's name can reach above the node's folder, so moving that folder does not move the output with it. Unless the redirect accounts for the names as well, such a job is one whose paths Smoozy cannot bring under the job's folder, and it is held under the rule above.

Four cases worked through that way. They are the simple case: every path written out in full and rooted where the render runs. A file an artist made on their own Mac or Windows computer may hold neither of those things, and the two forms that follow from that — a path written relative to the `.blend`, and one carrying another operating system's way of naming a drive — are worked through after them.

- **The ordinary file.** No file output nodes, one regular output path at `/home/artist/proj/render/`. Everything is shared, so nothing is left, and the frames land at the top of the job's folder. The artist gets what they always got: a folder of frames, in a folder named for the job that made them.
- **Three nodes** writing to `/home/artist/proj/render/beauty/`, `.../mist/` and `.../depth/`. They share the run `/home/artist/proj/render/`, so the job's folder gets `beauty/`, `mist/` and `depth/` — the artist's own arrangement, and nothing else.
- **A node nested under the output path.** Regular output at `/home/a/out/`, one node at `/home/a/out/beauty/`. The shared run is `/home/a/out/`, so the frames land at the top of the job's folder and the node's files in `beauty/` beneath — exactly the nesting the artist built.
- **Two nodes sharing nothing but the root** — `/mnt/fast/beauty/` and `/home/artist/mist/`. Only that root goes, so both keep everything below it: `mnt/fast/beauty/` and `home/artist/mist/`. Deeper than the artist meant, but nothing is lost.

Worked that way, **two places that were different on the machine stay different under the job's folder**, because only what is identical is ever thrown away. Two destinations that share nothing at all keep everything, which is the fourth case above and also what a foreign path produces.

**A path written relative to the `.blend` is a real folder once the file is on the machine.** Such a path is measured from the folder the `.blend` sits in, and it may climb above that folder. It survives being carried from one kind of computer to another whole, and resolves against wherever the file now sits. Label: **documented and observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). So Smoozy resolves it against where it put the `.blend` on the rented machine, and from then on it is an ordinary path the rule works on like any other.

**A path written on another kind of computer is kept exactly as written, and means nothing.** Blender does not translate it, does not rewrite it and does not refuse it — a full path from an artist's own Mac stays a full path from an artist's own Mac, and a drive letter from a Windows machine is treated as an ordinary place name that happens to hold a colon. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). Under the rule that costs nothing: a Mac path shares only the topmost folder with anything on the rented machine, so it keeps everything below it, and a drive-lettered path shares nothing at all, so it keeps the whole of itself with the drive letter as its first folder. Deeper than the artist meant, and nothing is lost.

So there is no form of path the rule cannot bring under the job's folder. The one thing that could still defeat it is a name that climbs out of its node's folder in Blender 4.5, above — and where a job's paths cannot be brought under its folder for any reason, the job is held and the user is asked, under the rule above.

**Smoozy does not touch the output names.** The redirect moves folders and leaves the names alone, so what each output is called reaches the machine as the artist wrote it. What Blender then does with a name is its own business and is not the same everywhere — Blender 5.0 replaces every separator in a name with an underscore, as above. **A rented Linux machine refuses nothing in a name but length**, and Blender writes what it is given: a colon, an asterisk, a question mark, a pipe, a semicolon, letters outside the Latin alphabet, an emoji and a trailing space all reached disk unaltered, in all four versions. Two things are not passed through. A backslash becomes a folder separator, which is Blender's doing and not the machine's. And a name the machine will not take for its length is refused at the moment of writing — tried on the **regular output path**, where the render stops, nothing lands, and the run fails. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). No Windows machine ran it, so what a name would do there is unknown; Smoozy renders on Linux, so that gap costs nothing here.

**The answer depends on the whole set.** Add a node and the others may land at a different depth. Two different jobs never share a folder, so that harms nothing between jobs. Within one job it rests on an assumption: that **a re-run is the same file with the same set**. Label: **an assumption**. Nothing stops the user replacing the `.blend` between an interruption and the automatic re-run. Where the file did change between runs, the shared run can differ, so one job's folder ends up holding two arrangements of subfolders.

**What Smoozy does then is settled 2026-09-02.** The machine's side was already settled at Architecture: a re-run whose file has changed reads the file again, works out a fresh arrangement, keeps the earlier attempt's arrangement beside it, and records that the file changed — see the [Job files and outputs architecture](../Architecture/Job%20files%20and%20outputs.md), clauses R13, C7 and M9. So the re-run's *already there* check below is made against the arrangement this attempt is about to write into.

**Whether that arrangement moved is what decides the rest, and the two outcomes are different things to be told. Corrected 2026-09-04, out of a code round.** This paragraph used to say flatly that a frame finished under the earlier arrangement is not found there and is rendered again. **That is only true where the arrangement moved.** The arrangement is worked out from where the job's outputs point, and **an artist who changes a material, a light or the camera and saves again has moved none of them** — so the fresh reading produces the same arrangement as the one before it, every file the finished frames wrote is exactly where the check looks, and **those frames are found and reused**. That is the ordinary way a file changes between an interruption and the re-run, not a corner of it. So there are two cases and both are real:

- **The arrangement moved.** A frame finished under the earlier one is not found and is rendered again. The job's folder ends up holding two arrangements of subfolders.
- **The arrangement did not move.** The frames finished before the change are reused, and nothing is rendered twice. The job's folder ends up holding frames rendered from **two versions of the artist's file** — some of the work as it stood before the change and some as it stands after.

A change can move part of an arrangement and leave the rest, so a job can land partly in each. **What the entry says then is that frames were reused**, because some of them were, and that is the half the user needs to know about their folder.

**What is settled here is the telling.** Where a re-run finds the file changed, Smoozy says so on the job's entry, which is [Queue & History](Queue%20&%20History.md)'s: that the file changed between attempts, and **what became of the frames that were already finished — whether they were rendered again, or reused.** It is said, not asked. The re-run is automatic and follows an interruption, so the user may not be at the computer, and a question there either holds a machine that bills by the hour waiting for an answer nobody is present to give, or is answered by a default, which is silence with a prompt in front of it. Neither of the other courses is worth a tap either — writing into an arrangement the current file does not describe, or abandoning the job — and a user who wants to step in already has *submit again* and *carry on from where this stopped*.

**What it costs the user is not the same in the two cases, which is why the entry says which one happened.** Where the arrangement moved, frames they have already paid for are paid for a second time, and the job's folder holds two arrangements of subfolders. Where it did not, nothing is paid for twice, and what the folder holds instead is one set of frames rendered from two versions of the file. Whichever it was, it is said rather than found out.

**Nothing here asks Smoozy to keep the frames apart, and that is deliberate.** Replacing the file mid-job is the user's own act, and the frames already on disk are their own work, not damaged by being kept. What the third promise requires is that Smoozy not say something happened that did not — which is exactly what the entry's sentence was doing.

**The regular output path is one of the destinations, counted like any other.** It is not treated as the root of everything, and it takes part in working out the shared run alongside the nodes.

## The main output

A job can write the same picture to several places. One of them is the **main output**: the destination holding the work the artist actually cares about, and its folder is what *show outputs* opens. The frame preview does not choose which folder to read from — it reads across everything the job wrote — but it does use the main output to break a tie between two otherwise equal files, and the section after this one holds that rule.

**It is found by following the beauty pass.** Whatever destination the beauty pass is written to is the main output. Label: **Creator-stated** (2026-07-28).

**The beauty pass has one name wherever a file records it, and it is the same in every version.** Blender calls it **Combined**, and that is what it is called in a written file and in a multi-layer file's list of layers. Label: **documented and observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md). **The socket it comes out of carries a different name.** The beauty leaves the Render Layers node on a socket called `Image`, and no socket on that node is called `Combined` at all. Label: **observed in a test** (2026-09-20, the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md). So the one pass this document leans on hardest can be told apart by name wherever a file records it, with no version-by-version handling behind it — and the name to look for on the socket is not that one.

**CORRECTED 2026-09-20, out of a Build reading, and this is the third of three places rather than all three.** This paragraph said the pass is called *Combined* and that this is what it is called *"in a written file, in a multi-layer file's list of layers, **and on the socket it comes out of**"*, all three under one label of **documented and observed**. **The third is not true.** Every Render Layers node in 4.5.12, 5.0.1, 5.1.2 and 5.2.2 LTS was read at the desk, under Cycles and under the built-in engine alike: **the socket the beauty leaves on is called `Image`, and no socket on the node is called `Combined` at all.** **The other two places were not read against and stand**, and what rests on them here does not move — the picture-by-name rule further down rests on the second. **Nothing substitutes a name to make something work**: `Image` is what the four Blenders printed, and a name with no source would be written down as an absence instead.

**The render can be found where it enters the compositor, and followed forward from there.** It arrives on a **Render Layers node**, which is a node type of its own and names the scene and the view layer it reads, so the entry point can be picked out. Nothing marks the picture itself once it is travelling, in any version, so the beauty is followed by walking forward from that node rather than by recognising it further along. The walk ran to completion in every version tried, through a reroute to both its destinations and past a muted node and a muted link. Label: **documented, inferred and observed** — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**How far that walk goes is now settled, and it goes far enough.** It survives colour work — a node that changes a picture's colours takes one picture in and gives one out, so the chain does not break there — and it survives a node that takes two pictures in and gives one out, because every such node has exactly one picture output. Which of the two inputs came out the far side can be told for each of the nodes that do this: a Switch hands its chosen input through exactly, a Mix and an Alpha Over hand one input back at the ends of their factor, a muted node states which input it passes and what it states is what the render produces, and a depth-combining node chooses pixel by pixel. **The whole chain reads back out of a saved file with no window at all**, complete, in every version. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md). Which of the two came out can be told for the five kinds of two-picture node that were tried and for no others. **Most of these runs were made on one machine**, and their other half has simply not been run — so they settle Linux and are untested on macOS. So real files full of ordinary compositing are walkable, and the fallbacks below are the exception rather than the ordinary case.

**Four limits travel with that walk, and each is a place a reading could go wrong.** Nothing marks a picture with where it came from, in any version, so the beauty is only ever found by following the wiring and never by recognising a picture further along — which is what makes every one of these limits matter. **A link cannot be walked across the boundary of a node group**: nothing in the outer tree names a node inside the group, so the walk has to step into the group's own tree. **A splitting node puts its first input on the right in Blender 4.5 and on the left in 5.0, 5.1 and 5.2**, so which side of it carries the beauty is not the same in every version. **Where the factor of a two-picture node sits between its ends, both inputs contribute and nothing says which contributed what**, so the beauty can only be followed past such a node when the factor is at one end. And a freshly added mixing node starts at a different factor in Blender 5.2 from the other three. Label: **observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md). Where the walk cannot get through, the job falls to the no-main-output case below: *show outputs* opens the job's own folder and the preview is the last image and nothing better. That weakens the promise rather than breaking it, and it is why the fallbacks below are written out rather than left implied.

**Whether the beauty reaches the regular output path is not a given, and the same walk answers it.** Where the compositor is not running, the raw render lands there, so the beauty does. Where it is running, what lands there is whatever reaches the final output node — the Composite node in Blender 4.5, the Group Output node from 5.0 — so the beauty reaches the regular output path only if the artist wired it to that node. The walk from the Render Layers node settles it either way: the regular output path is a destination the beauty reaches when the walk arrives at that node, and is not one when it does not.

**Where the beauty reaches a destination inside a file output node, that destination wins**, whatever the regular output path is also writing. The reason is that nodes do not appear by themselves: a file has one because the artist put it there and pointed the beauty at it, and that is a statement about where they want their work. The regular output path is just what the file came with. **This is the Creator's decision about which output matters, not an agent's reading of what a file means.** Label: **Creator-stated** (2026-07-28).

Three arrangements cover what a file can do with its beauty:

- **No file output nodes.** Whatever the regular output path holds is all there is, so it is the main output.
- **File output nodes carrying only utility passes.** The main output is the regular output path — the nodes do not demote it merely by existing. Only a destination the beauty actually reaches wins.
- **The beauty is wired into a file output node.** The destination inside that node that the beauty reaches is the main output, whatever the regular output path is also writing.

**A node is not a single place, so a node winning does not settle it.** Where the beauty reaches several destinations inside one node, those destinations are treated exactly as destinations in different nodes are, and the tiebreakers below decide between them.

**A job can have no main output at all, and it does not take an unusual file.** Where the beauty pass is written nowhere, there is no destination for it to name, and Smoozy names **the job's own folder**. That happens whenever the compositor sends something other than the beauty to its final output node and no file output node carries the beauty either — which every version allows — as well as in Blender 5.2 with the regular output path switched off. That is not a claim about which work matters; it is Smoozy saying it does not know, and opening the whole job rather than picking a folder at random. The diffuse colour pass is not walked here, though it is the frame preview's second choice: it is a utility pass, and a utility pass's folder is not the folder holding the work the artist cares about. Label: **Creator-stated** (2026-07-28).

**Where the beauty reaches more than one destination, the working format wins** (see the [Glossary](../Groundwork/Glossary.md) for that name and its opposite). This is the tiebreaker *between destinations inside file output nodes*, not between one of those and the regular output path — that one is already settled above. A beauty written in a working format is there because the artist meant it to be the work; the same beauty alongside it in a viewing format is a check render. So the working format's destination is the main output. **This too is the Creator's decision about which output matters, not an agent's reading of what a file means.** Label: **Creator-stated** (2026-07-28). The research has since named every format each version can write, and named the two that hold more light than a screen can show — OpenEXR and Radiance HDR. Label: **documented and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**The split is settled, and it is stated as a rule rather than as a list.** Label: **Creator-stated** (2026-08-13).

- **Anything that is not PNG or JPEG is a working format.** That covers every format each version can write, including ones added after this was written, so the rule does not go stale when Blender gains a format.
- **Where the only formats present are PNG and JPEG, PNG is the working format** and JPEG is the viewing one.
- **Where only one format is present at all, it is both.** There is nothing to choose between, and the tiebreaker has nothing to do.

A rule rather than a list is deliberate: a list would have to be checked against every version and rewritten whenever Blender added a format, and the research has already shown those lists differ across the four supported versions.

**Where two or more candidates are left in the same format class, the pick is arbitrary — and it is made once.** Two working formats, or two viewing formats, give Smoozy nothing to tell them apart with, and it does not invent a rule to break the tie. Whichever it picks, it picks once for the job and keeps it: *show outputs* opens the same folder every time that job is asked, and the frame preview reads the same file every time it is opened. Smoozy says plainly that the pick was arbitrary, so a user who finds it opening one of two equal folders knows the pick was arbitrary rather than wrong. Label: **Creator-stated** (2026-07-28 for the arbitrary pick, 2026-08-03 for its being fixed once and kept).

**The main output is not something the user is asked about.** It decides where *show outputs* opens, and nothing more. Where the user is given a choice about which outputs come home, that choice is by file format — see [Download](Download.md).

## What the frame preview reads

[Queue & History](Queue%20&%20History.md) owns the frame preview. This document owns which file it reads.

**It reads across everything the job wrote**, not only the main output. The main output is picked for the working format; the preview wants the opposite, so confining it there would hand the user the one file Smoozy is least able to show.

**The pass comes first, the format second.** A beauty pass in a working format beats a utility pass in a viewing one. Format only ever chooses between files showing the same thing.

The order:

1. **The beauty pass.**
2. Failing that, the **diffuse colour pass**, which the Creator holds also shows whether the textures loaded — the thing the preview is most often being looked at for. Label: **Creator-stated** (2026-07-28), **and not confirmed by the research** — see below. Two things bear on this rung. It depends on the same assumption about tracing as the beauty pass above: if the beauty cannot be picked out of a job's files, the diffuse colour pass most likely cannot either, and both rungs fall together. And unlike the beauty, this pass is **not called the same thing in every version** — `DiffCol` in Blender 4.5, `Diffuse Color` from 5.0 — so finding it means knowing which Blender wrote the file. Label: **documented and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md).
3. Failing that, the fallback [Queue & History](Queue%20&%20History.md) already promises: the latest image, whatever pass it turns out to be.

Label: **Creator-stated** (2026-07-28).

**A file Smoozy cannot treat as finished is not a candidate, at any of the three rungs.** [Download](Download.md) already works to that standing for a file it might bring home, and the preview holds to it for the same reason: a frame caught part-written, or one left by a write that ran out of room, shows the user something that is not the render — half a picture reads as a broken job, and a nearly complete one reads as a frame that is fine and is not there. So where the newest image is one of those, the preview reads the last one it can vouch for instead; where it can vouch for none, there is no picture to show, which is the case below.

**Within one rank, prefer the viewing format.** Where the same pass exists in both, the one that opens as a picture anywhere is what the preview reads, wherever in the job's folder it sits.

**Where two files are left after that** — the same pass, the same format, in two different folders — the one in the main output's folder is read. Where the job has no main output, or neither file sits there, the pick is arbitrary and is made once for the job and kept, exactly as above, so a finished job's preview never changes from one opening to the next. Label: **Creator-stated** (2026-07-28 for the arbitrary pick, 2026-08-03 for its being fixed once and kept).

**Where only a working format exists, Smoozy reads it anyway.** A preview that shows the render is worth more than no preview, and the point of looking is to see that it rendered and the textures are there.

**Every View Layer a frame rendered gets its own picture, where the job's files hold it.** *(Added 2026-10-10, from the Creator's seventh notes, note 4.)* The rungs above choose one picture for each frame, and that picture stays what it was. The preview also reads, by the same rungs, the picture of every other View Layer that rendered at that frame, and the user can look at any of them: inside the chosen file where it is a multi-layer file holding that layer, and otherwise among the files written for that layer alone — a File Output node fed by one View Layer is the ordinary case. A file more than one View Layer feeds, other than a multi-layer file, is never read for another layer: where the frame's own picture did not come from it, a View Layer whose picture sits only there — as the first layer's does in the regular output path written in an ordinary format (see *A frame with several active view layers writes one set of files* below) — has no picture of its own. A View Layer that did not render at a frame has no picture at that frame. Label: **Creator-stated** (2026-10-10; widened 2026-10-11, the Creator's ninth notes, note 2). *(Changed 2026-10-12 from the Creator's ninth notes (2026-10-11), note 2: "the preview window doesn't show different view layers". The paragraph covered one shape of file only, and the Creator's file sends each layer to its own File Output node. It read: "Where the chosen file holds more than one View Layer's picture, the preview also reads, by the same rungs and choosing by each layer's name, the picture of every other View Layer that rendered at that frame, and the user can look at any of them. Only a multi-layer file holds more than one View Layer's picture — an ordinary picture holds one alone (see* A frame with several active view layers writes one set of files *below) — so a job written that way still has one picture per frame and nothing to choose between.")*

**Where the job has written no image at all, there is no preview**, and the entry says so rather than showing an empty space. That covers a job that writes nothing at all, and a running job before its first frame lands. [Queue & History](Queue%20&%20History.md) promises the user is never left without a picture; that promise is about choosing among the images a job wrote, not a promise that a job wrote one. Where a job wrote none, there is none to show. Label: **Creator-stated** (2026-07-28).

Two things make reading a working format harder than it sounds, and both are real:

- **A working format has no single look, and the file does not record the one it was made under.** It holds more light than a screen can show, so turning it into a picture means choosing an exposure and a colour treatment — and nothing in the written file says which the artist was working under. Three files written under plainly different treatments came back describing themselves identically, in all four versions, and a Radiance HDR records nothing at all. From Blender 5.0 an OpenEXR does name its colour space, which is not the same thing and does not narrow the choice. Label: **documented and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md). **So Smoozy always has to choose**, and the picture may look nothing like what the artist sees in Blender — a good render can come out washed out or near black.
- **A working format can hold several pictures in one file, and they can be told apart by name.** OpenEXR holds a picture per pass per view layer, and each is named for what it is — the beauty pass is `Combined` in every version, under the name of the view layer it came from. A picture written there by a file output node takes the name of the output that fed it. Label: **documented and observed; differs by version** in how the file is put together, and the same everywhere in how the pictures are named — see [Sources](Sources/What%20a%20job%20writes.sources.md). So picking the right picture inside the file is the same reading as picking the right file outside it, and no harder.

Both are why the preview's promise is a narrow one: **it says files were written, and it shows a missing texture that was feeding colour. It cannot confirm the render came out right, and it is not what the colour is judged by.** [Queue & History](Queue%20&%20History.md) owns that promise and states it in full. Label: **Creator-stated** (2026-07-28), narrowed by the research on 2026-08-09 — the narrowing is set out below.

**What a missing texture looks like is settled, and the answer is only half as useful as it once looked.** Where a missing or unreadable picture is feeding **colour**, it comes out as flat magenta in the finished picture, in every version, on both machines and on either make of graphics card. It holds for Cycles and EEVEE outright, and for Workbench only once that engine is set to draw textures with flat lighting — left as it comes, Workbench renders the same grey whether the picture is there or not. So the preview's top rung carries that much, and the second rung is not what it rests on. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**Where the missing picture is feeding anything other than colour, nothing shows at all — and that is the common case, not a corner.** The stand-in is handed over at the moment the picture is looked for, before anything knows what the value will be used for, so it reaches a bump map or a mask as a number rather than as a visible colour. A missing **bump** map gives no bump: the surface is indistinguishable from one with nothing connected. A missing **displacement** map shrinks the object, evenly, with no relief in it. A missing **normal** map leaves the whole surface shaded as though tilted. A missing **transparency** map hands the fully solid end to whatever reads it, so a cut-out would stay solid — that one is what the measured value implies, since no test rendered such a mask. In the compositor the substitute is black rather than magenta, and in a geometry node setup it is zero. A volume whose data file is gone **draws nothing at all**. Every one of those renders a plausible picture with one property silently wrong, and every one finishes at a successful exit status with the frame written. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**So the preview's promise narrows, and it narrows in the honest direction.** It shows a missing texture that was feeding colour. It does not show a missing bump, displacement, normal, mask or volume, and it cannot be relied on to show that a job's textures loaded. Three older limits stand alongside that: nothing says **which** texture is missing, nothing tells a missing texture from a surface the artist genuinely made magenta, and whether the diffuse colour pass carries the magenta as the finished picture does was never tested — so the second rung is a preference and not a promise.

**What does say so is not the picture at all, and it can be asked for.** Blender will report a file's missing references by name, with no window open, on the machine — which is the same reading [Dependency Upload & Remap](Dependency%20Upload%20&%20Remap.md)'s check is built on, and it does not need a render to have happened. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). What a render *prints* about it is thinner, and it differs by engine as well as by version. **Under Cycles, Blender 4.5 prints nothing that marks a picture as missing** — one line does name the file, but it is printed whether the file is there or not, so it marks nothing. **Under EEVEE, Blender 4.5 does print a line, and prints it only when the picture is missing**, though the line does not say which picture; that was run on a rented Linux machine, through EEVEE alone. **Under Cycles**, Blender 5.0 and 5.1 print an error naming the path, and 5.2 prints a warning and a count of what failed to load. Label: **observed; differs by version and by engine** — see [Sources](Sources/What%20a%20job%20writes.sources.md). So a job rendered on 4.5 through Cycles leaves no trace of a missing texture anywhere except in the picture, and only where it was feeding colour.

## What the user is told before submitting

Once the file has been read, Smoozy states the folders the job will write into, how many files that comes to, and whether it comes to none. **It shows the user that before the job is submitted.** Label: **Creator-stated** (2026-07-28). The folders can be stated firmly — every form of path is now covered by the rule above. The count is firm too, except for the two cases *Counting a job's files* below still marks open: a job whose regular output is one video file, and a set of outputs that changes from frame to frame.

It is offered because Smoozy is quietly reinterpreting the artist's own output paths, and because where their work is going is theirs to check. Six things it covers:

- **The folders the job's files will land in**, as they will appear under the job's folder, and where that folder sits on the server. **The folders Smoozy redirects its caches and bakes to are not listed**: they are still redirected and still come home, but they are not where the artist's work goes, and listing them on every job, whether anything wrote there or not, told the user their work was going somewhere it was not. *(Changed 2026-10-04, out of the Creator's note 14 on the test copy. This bullet read "The folders the job will write into, as they will appear under the job's folder", and every job was shown four or five cache folders whether or not anything wrote there. Where the folder sits was added the same day with the Creator's ruling above.)*
- **A job that will write nothing at all**, which otherwise costs a machine's time for no files.
- **Two destinations in different nodes aimed at the same name in the same place.** That happens in real files — it has caught the Creator more than once. Label: **Creator-stated** (2026-07-28). After redirecting they still collide, one picture survives and the other is lost, and Smoozy can see it before the render rather than after, so it says so. Two outputs on one node cannot collide: Blender adds a number to a repeated name as it is typed.
- **The same picture written to more than one place.** A beauty carried by a file output node often reaches the regular output path as well — Label: **Creator-stated** (2026-07-28), narrowed by the research to the case where the artist also wired the beauty to the compositor's final output node — so a common setup writes it twice. That is what the artist's file asks for and Smoozy leaves it as the file asks, but it doubles what comes home under an auto-download that has not been narrowed, and narrowing by format does not separate two copies in the same format. Whether it happens is read off the same walk that finds the main output, so Smoozy warns only when it really does. **Where the regular output path writes a video, the beauty reaching it is not this case**: a video is not a pass, and the two are named as what they are — frames from a file output node, and a video from the output path — rather than warned of. Only places that write images count toward this one. Label: **Creator-stated** (2026-10-12, the Creator's eighth notes, note 4, and their answer that day: *"I said that a video should not be thought of as a pass at all"*). Narrowing by format does separate a video from frames, so the reason above does not reach that case. *(Added 2026-10-12. Until then the bullet made no exception, and a job writing a video through the output path and frames through a file output node was told its beauty pass was written twice. No auditor has seen it.)*
- **A compositor shared with another scene**, which the pictures the job writes may belong to rather than to the scene being rendered. Label: **Creator-stated** (2026-08-03). It arises from Blender 5.0 on and never in 4.5, where a compositor cannot be shared at all.
- **A job whose output is a single video file**, and what an interruption costs it — the whole range rather than the frames since the last one. Label: **the decision is Smoozy's** (see *Counting a job's files* above, where it is settled and why).

Smoozy warns and changes nothing in the file. Renaming an artist's outputs, or dropping one of a colliding pair, would mean deciding what their file meant, and the only way to change what the file asks for is to fix the file in Blender and send it up again. What the user can decide is whether to run the job at all, and whether to let all of it come home.

**Where the file has not been read, all six are said later instead.** Nothing forces a user to pre-load before submitting. The file is read anyway when the job starts, and at that moment the job's queue entry carries the same six things: which folders it is writing into, that it is writing nothing where that is so, that two of its destinations collide where they do, that the same picture is being written to more than one place, that its compositor is shared with another scene, and that its output is a single video file. The duplicate-picture one is on the entry because the render having started does not settle what comes home — the user can still turn auto-download off before every frame arrives twice and fills their disk and their connection. Label: **Creator-stated** (2026-08-03). The queue entry is [Queue & History](Queue%20&%20History.md)'s; what it says here is this document's.

**Two of the six hold the job before the render starts.** Where that read finds the job will write nothing at all, or finds a colliding pair, Smoozy holds the job before any rendering is paid for and gives the user a clear choice: stop, or carry on knowing. Pre-loading stays optional, and the warning stops arriving too late to act on. Label: **Creator-stated** (2026-08-03).

## Counting a job's files

[Download](Download.md) tells the user how far a job has got against the whole, and offers to narrow an arrangement to particular formats. Both need to know what the job will write.

**The count is of the files the job is expected to leave on disk**, not of the writes it asks for. Label: **Creator-stated** (2026-08-03). Download measures what has arrived against it, so a number that can never be reached would leave a job's progress short of done for good.

**It is worked out frame by frame, never by multiplying.** That is a constraint on the count rather than the method.

**The method is now settled.** Label: **Creator-stated** (2026-08-13). For each frame the job covers, the file is asked four things: which view layers render at that frame; what the regular output path writes; which file output nodes will run and what is connected to each; and where two of those land on one name. The frame's owed files are the regular output's one file, plus what each running node owes, less what a collision swallows. The job's count is those added up over its frames.

**View layers do not multiply the count, and that is the part worth stating plainly**, because the natural reading of *frames times view layers* is wrong. A frame with several active view layers writes **one** set of files from the regular output path, never one set per view layer — the section below states it and the research carries it in all four versions. Where a view layer changes the count is only through the compositor: a view layer feeds a file output node's input, and an input with nothing connected to it writes nothing at all. So renderability across frames matters to the count **by way of what is left feeding a node**, not by way of the scene's own output.

**A view layer that does not render at a frame writes nothing at that frame**, so a file output node input fed only by it owes no file. Label: **Creator-stated** (2026-08-13). This is what the count already assumed, and it is now stated rather than assumed — it decides the count of every job whose view layers are animated.

**What one frame owes**, for each frame the job covers:

- **The regular output path**, one file, where it writes.
- **Each file output node that will run** — one file for the whole node where it is set to gather its outputs into a single multi-layer file, and otherwise one file for each of its outputs that has something connected to it.
- **Less what a collision swallows.** Two nodes aimed at the same folder and the same name leave one file between them rather than two: the picture of the node built first survives, silently, and the other is gone. A node group used twice in one tree is the same case. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

The job's count is those added up over its frames. A node's picture need not have come straight from the render, so what a node writes is not always the render's own picture — but it is still one file per frame, so the count is unchanged.

**The count assumes the set of outputs that will run is the same for every frame, and that assumption now holds everywhere but Blender 4.5.** Nothing that decides whether a file output node writes will take a keyframe or a driver in Blender 5.0, 5.1 or 5.2 — not the node's own silencing, not the silencing of the link feeding it, not a group's, and not the switch that turns compositing on. Exactly one switch accepts a keyframe in every version, the compositor's old Use Nodes switch, and from 5.0 that switch does nothing at all. In **Blender 4.5** it does work, and it is the one way an artist's own file can make a node write on some frames and not on others. Label: **observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md). So the count is firm on a file rendered by 5.0 and later, and on 4.5 it can be wrong for a file built that way — a frame that finished perfectly would then be judged permanently incomplete, which reaches the re-run below as well as the count.

**A script running inside the render is a different matter, and Smoozy meets it only where the file carries one.** In every version a script called once per frame does reach the node's silencing and does stop it writing, though the change lands one frame later than it was asked for. Smoozy sends no such script, but every render lets the file's own scripts run (the [Rendering spec](Rendering.md), changed 2026-10-08; until then Blender's starting state kept them off), so a file that carries one meets this. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**A frame with several active view layers writes one set of files, never one set per view layer.** No view layer's name goes into a file name, and for an ordinary picture format the file holds one view layer's picture alone — the first one, or whichever the compositor was set to read, which was tried on a rented Linux machine alone. Only a multi-layer file carries them all, and it carries them inside the one file as layers. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). So the count is not multiplied by view layers, and neither is what "every file that should be there" means for the re-run below. This settles the two readings that disagreed: the [Glossary](../Groundwork/Glossary.md)'s one set per frame is right about the files, and the several beauty passes [Queue & History](Queue%20&%20History.md) leaves open are real but sit inside a single multi-layer file. One thing was tried on no machine — what such a frame writes when the render is started from inside Blender's own window — and it costs nothing here, since Smoozy never starts one that way.

**Frames that produce nothing are counted as nothing.** A frame with no view layer active on it renders nothing and writes nothing at all (see the [Glossary](../Groundwork/Glossary.md), which owns that fact and its label), and a job can have a stretch of those in the middle of its range — [Render Settings](Render%20Settings.md) sets out how that happens. A count that multiplied frames by outputs would promise files that are never coming, and Download would report such a job as permanently unfinished.

**A file output node cannot write video, and one job cannot write video and separate images at once.** No version of the four lets a node write video, by any route, and an animation gives one picture per frame. Nor can a render's own output be a video and a set of images together: the setting holds one value at a time in every version, which was tried on a rented Linux machine alone. Label: **observed** (the same in all four versions) — see [Sources](Sources/What%20a%20job%20writes.sources.md). So a node's outputs are always one file per frame, and the whole-range case can only come from the regular output path — where it is the *only* thing that path writes.

**Where the regular output path writes video, three things about that one file are now known and all three are awkward.** It is named for the whole range before Blender knows the render will finish. **Its size on disk does not move while the render runs** — it appears within moments at a token size and stays there, reaching its real size only when the file is closed, which happens when the render ends or when Blender splits it. So watching that file tells the user nothing about how far the job has got. And where the artist has Blender's own splitting switched on, Blender closes the file just under a size limit and opens a second under a name of its own; a file already split away is closed, and the reader used could find its frames — so a long render interrupted late has not lost everything. Nothing here says what another program would make of any of these files. Running the job again replaces what was left rather than adding to it. Label: **observed** (the same in all four versions; the splitting on a rented Linux machine only) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**Two limits on that, and they matter more than the finding does.** It rests on **one container and one codec** — the only ones the round tried, apart from a survey of what each container leaves behind after an interruption, which came out differently for every one of them, and the splitting test, which used a container, a codec, a picture size and a render engine of its own. So none of it should be read as a fact about video output in general. And **a size that does not move is not the same as nothing being written**: what the round establishes is that the file's *reported* size waits for the close, not where the frames are meanwhile. A stop that lets Blender close the file properly gets them all back, which is the paragraph below.

**What a stopped render leaves of that file depends entirely on how it was stopped, and the difference is stark.** An **interrupt** — what pressing Ctrl-C at a terminal sends — leaves a file holding the frames that were finished, and Blender treats it as a cancelled render. A **polite request to close** and an **outright kill** each leave the file at its token size with nothing in it, and the polite request fires nothing at all inside Blender. So the gentler-sounding of the two endings is the one that loses the whole video. Label: **observed** (the same in all four versions, on both machines; what each stop fires inside Blender on a rented Linux machine alone) — see [Sources](Sources/What%20a%20job%20writes.sources.md). Which of the three Smoozy sends is [Rendering](Rendering.md)'s to settle, and this document's finding is why it matters.

**So a frame-by-frame count is wrong for that file and a frame-based re-run has nothing to look for**, and Blender's own way of skipping frames already on disk does not work on a video output either — the whole range renders again. What Smoozy does instead is settled here, in three parts.

- **It counts one file, and says the number may grow.** A video job's expected count is one, plus however many further files Blender's own splitting makes — which depends on how big the picture turns out to be and cannot be known in advance. So Smoozy states one and says plainly that a long job may leave more, rather than promising a number it will have to break.
- **A re-run renders the whole range again**, because there is no frame-shaped thing on disk to skip and a partly written video is not something a second run can carry on from. What was left is replaced rather than added to, which is Blender's own behaviour and means nothing has to be cleared first.
- **The user is told before the job is submitted**, alongside the other things said at that moment, that this job's output is a single video and that an interruption costs the whole range rather than the frames since the last one. That is the only place the warning is worth anything: once the render is under way there is nothing to be done about it.
- **Its first-frame check writes a picture, not a video.** Where the user asks for the check on such a job, the check's one frame is written as a still picture with the job's own settings, so it has a preview like any other frame; the job after it writes the video. [Rendering](Rendering.md) owns the check and says why. Label: **Creator-stated** (2026-10-27). *Added 2026-10-27. No auditor has seen it.*

Label: **the decision is Smoozy's**, taken here on the strength of the research rather than settled by the Creator — the alternative, promising nothing at all for such a job, leaves the user with a progress reading that never completes and no warning about what an interruption costs them.

The formats are a matching reckoning: **the list is every format anything in the job writes**, not the scene's own format. A file whose regular output is PNG and whose nodes write EXR offers both. Where a node gathers its outputs into a single file, the format that counts for it is that file's, not the outputs' own.

## A re-run, and what counts as already there

[Queue & History](Queue%20&%20History.md) promises that a job re-run after an interruption covers only the frames that are not already there. With a job writing into several folders, *already there* needs saying exactly.

**A frame counts as already there only when every file it should have produced is present.** Label: **Creator-stated** (2026-07-28). A folder existing is not enough — a folder can sit there with a file missing from inside it, and that frame is not done. What a frame should have produced is the per-frame reckoning the count above is made of, which is why that count is worked out frame by frame rather than multiplied.

**Naming those files before any of them exists is what makes the rule workable, and it can be done.** For the regular output path the recipe is the same in all four versions: the frame number lands wherever the artist put hash marks in the recorded name — padded to as many marks as there are, or added on the end four digits wide when there are none — and the format's own ending goes last unless the artist switched that off. The padding is a floor and not a ceiling, so a frame number too big for it is written out in full rather than cut. For a file output node the recipe **differs by version**: Blender 4.5 joins the node's folder, the output's own piece of path, the frame number and the ending, while 5.0, 5.1 and 5.2 put the node's own base file name between the folder and the output's name. Label: **documented and observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md). So Smoozy can write down every name a frame owes before the render starts, provided it knows which Blender it is driving.

**Blender can also be asked directly, and it agrees with what lands on disk — with one exception that costs nothing here.** For a frame render and for an animation, the name the file predicts and the name that appears are the same, templates and frame-number padding and all. Only a still rendered through the script route comes out differently, with the padding left in the name unsubstituted — and every job Smoozy runs is rendered as an animation, so that route is never taken. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**A path a file cannot resolve stops the job before it costs anything.** Where the **regular output path** holds a template Blender cannot work out, the render started from outside ends at once with a failing exit status and a message naming the path — for a single frame as well as for a whole animation — and asking the file where the frame would land raises the same complaint before any render begins. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). A broken template inside one *output's* own name is the quieter case: that one output is skipped, the rest of the node writes, and the render finishes at success — which is the file-output failure described above, not this one.

**A file being present is not proof it finished writing, and that is settled rather than feared.** A file can be caught part-written, because Blender writes straight to the final name rather than to a temporary one and renaming it at the end. And where the artist has Blender's placeholder setting on, an empty file sits at exactly the path the finished frame will occupy from the moment that frame's work begins, and is replaced in place when it finishes. Label: **documented, inferred and observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). That is what the highest-frame rule below exists to answer, and it also means a file arriving in the job's folder during a render is not yet a file worth bringing home — which is [Download](Download.md)'s to deal with rather than this document's.

Re-rendering a frame that was nearly complete costs one frame. A pass quietly missing from frame 60 costs a whole re-render later, or is not noticed until the work is being composited — which is worse.

**A frame that should produce nothing is already there**, since there is nothing owed and nothing to wait for.

**Where every frame of a job produces nothing, the job is complete and the re-run has nothing to do.** [Queue & History](Queue%20&%20History.md) says a job that wrote nothing before it died simply runs again; that covers the ordinary interrupted job, whose frames were owed files and had not written them yet. Where the job was never going to write anything, this document's rule takes priority — running it again would spend the machine's time producing the same nothing a second time.

**One thing makes *already there* impossible to work out at all, and it has to be said here. Added 2026-09-01, after the research was repaired.** If the scene is set to render **two views** — the two eyes of a 3D picture — Blender does not write the file under the name the reckoning predicts. It writes **two** files per frame, one per eye, under names of their own; **the predicted name is never written at all.** So every frame of a job that rendered perfectly reads as **not there**: the job is reported incomplete, and a re-run does the whole range again. **The user pays twice and is told it failed both times.**

**Where Smoozy sees a scene set to more than one view, it does not work out what the frames should be at all.** It says so plainly — the job's frames cannot be predicted, and why — and from then on **nothing reads a file's absence as evidence of anything**: no frame is called missing, no re-run is offered, and no count is shown rather than a wrong one being shown. **The render itself is untouched and still runs.**

**What is not settled, and is not being decided here.** Whether Smoozy should carry such a job at all — nothing in these specs has ever mentioned two views, so there is no promise either way — and what a stop landing between a frame's two files leaves behind, which nobody has ever tried. Label: **observed in a test** for the naming, on one rented Linux machine in all four versions — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**The last frame Smoozy asked for that counts as already there is re-rendered anyway.** The frame being written when the machine died can be complete in one folder and half-written in another, and a file existing is not proof that it finished. So the last frame that looks complete is done again regardless. One frame costs little for that.

**The order a render works through its frames is settled, and it changes how that rule is worded.** A plain range is walked forward, ascending, one frame at a time. A range with a step starts at the first frame and moves forward by the step, stopping at the last frame at or below the end rather than reaching back for it. **A typed list of frames is rendered in the order it was written, not sorted** — so for a re-run, where Smoozy hands over the frames it wants, the highest-numbered frame present need not be the last one finished. It is the last one **in the order Smoozy asked for** that is present, which Smoozy knows because it wrote the list. The order does not change with the render engine, the make of graphics card or the number of them. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**What an interruption leaves is not the same for every way of stopping a render, and this is the sharpest thing the research has said about the re-run.** An **interrupt** has never left a short image — not in one run, by anybody, in any version, on either machine, across hundreds of runs. A **polite request to close** and an **outright kill** are a different matter: in the largest set of runs — eighty of each signal in all, ten in each version on each machine — both left the last image short **every single time**, and on the Linux machine every one of those short files was exactly **zero bytes**. Two smaller earlier sets found them mostly whole. **What separates the sets is when the stop landed.** The eighty-run set aimed each signal at the moment the file appeared; the smaller sets stopped at no particular moment, against a write window about a thousandth of a second wide. A neighbouring topic that stopped eight times at no particular moment saw nothing part-written at all, which at that width is what chance predicts rather than anything Blender promises. All three sets stand, and what is settled is the one-way half: an interrupt is safe, and the other two cannot be relied on. Label: **observed; the sets differ in when the stop landed and none is preferred** — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**And it sits beside a neighbouring answer, which two things separate.** A separate question in the same topic says the frame in flight is thrown away by every means of stopping, with nothing written for it whole or partial, in every version on both machines — where the stop lands during the rendering. Those runs were about the **regular output path**'s own picture and were stopped at no particular moment; the short files above were a **file output node**'s, stopped at the moment its file appeared. So the two are a different write and a different moment rather than one answer twice, which that question now says itself. What this document holds to is the harder of the two: a short or empty file can sit at the last frame's name.

**So the last-frame rule above is the ordinary case again rather than a safety net.** A zero-byte file sitting at exactly the name the finished frame would carry is *present*, and presence is what the *already there* test reads — so without that rule an abruptly stopped job would treat a frame that was never written as finished, and the missing picture would never be rendered. The rule catches it because the short frame is the frame in flight, which is the last frame Smoozy asked for that is present. The rule is worded as the last frame asked for rather than the highest number on disk for the same reason.

**The regular output path has since been tested directly, and it behaves the way the rule assumes.** A stop aimed at the instant the frame's own file appears leaves a short file at that frame's own path for a **polite request to close** and for an **outright kill**, and leaves the frame **whole** for an **interrupt**, which finishes the write rather than cutting it. The same in all four versions on both machines. Blender writes straight to the final name and the file grows in place — no temporary name ever appears — so the file that can be caught part-written is the file itself. How many bytes are left is a race with no pattern by version or machine, running from nothing to some tens of thousands, so nothing may key on a size. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). This closes what this document previously carried as unresolved, and it settles the assumption the last-frame rule rests on rather than unsettling it.

**Two things come with it that anything checking a frame has to know.** A part-written file **opens**: a stopped TIFF, and sometimes a stopped JPEG, loads and reports the full picture size with real data in it, so *it opens* is never proof a frame finished — what separates them is size against a whole one. And a **file output node writes before the frame's own file**, every frame, so a stop landing between the two leaves the node's file short with nothing at all at the frame's own path. Label: **observed** (the first in all four versions on both machines; the order of the two writes on both machines for Blender 4.5 and on the Mac alone for the other three) — see [Sources](Sources/What%20a%20job%20writes.sources.md). That second one the *already there* rule already answers, since the frame owes a file that is not there.

**Where it does not hold is a machine going down.** With the machine reset at the kernel mid-write, no frame's contents survived at all — **including a frame reported as saved seconds earlier**. So the damage is not always confined to the frame in flight, and a zero-byte file left at a frame that is **not** the last one Smoozy asked for would pass the *already there* test and never be rendered again. Label: **observed** on one rented Linux machine; macOS untested, since the Creator's machine is not reset for a test — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**So a file of zero bytes is never a finished frame, and never counts as already there.** A frame counts as already there only when every file it should have produced is present **and none of them is empty**. This is not Smoozy judging whether a picture is whole — it is Smoozy refusing to count nothing as something, and it costs nothing: the folder is already being read to see which files are there, and how large each one is comes with that reading. Every place this document has found a lost write leaves a nought-length file, an abrupt stop and a machine going down alike, so this is the shape the loss actually takes rather than a guess at one. Label: **Creator-stated** (2026-08-12), resting on the observed findings above.

**What it does not cover is stated plainly, because the gap is real.** A file that is short but not empty still counts as already there, and Smoozy does not open frames to weigh them — it has no idea what a whole frame of a given scene should weigh, and *A file Smoozy cannot vouch for* above says outright that opening a frame proves nothing. So a machine that went down can still leave a job reporting complete with a hole in it, where the file left behind happens to hold some bytes. **That limit is stated rather than hidden**, and where it bites the same two signals do the telling as everywhere else in this document: the count coming up short, and what the machine printed. Label: **Creator-stated** (2026-08-12).

**The re-run's starting point does not move for this.** Backing off an extra frame was weighed and not taken: the loss observed reached every frame in the run rather than the last one or two, so no fixed number of frames covers it, and re-rendering a frame on every carry-on costs the user something on every job to cover nothing in particular. What [Rendering](Rendering.md) does instead is show the figure, say what it rests on, and let the user move it. Label: **Creator-stated** (2026-08-12).

**And it decides how a stop is sent.** Smoozy stops a render the way that leaves whole frames — the interrupt — and never the outright kill, because the two endings differ in what they leave rather than merely in how quickly they arrive. Label: **the decision is Smoozy's**, taken here on the strength of the finding above rather than settled by the Creator. [Rendering](Rendering.md) owns ending a render and carries the rule; this document owns why it is worded that way. Where a machine goes down of its own accord nothing is sent at all, and that case is the one the last-frame rule was always written for.

**A user who deletes a folder of passes by hand makes every frame look incomplete**, so a re-run after that redoes the job. That is rare — a re-run only follows an interruption — and it is also correct: those files were asked for.

**Smoozy does the reckoning itself and hands Blender the frames it wants.** Blender can be asked to skip frames already on disk, but its judgement is too coarse to lean on: it looks at one path only — the one the regular output path would write — and it judges by bare existence, so an empty file counts as done. It does not reach file output nodes at all, so a frame whose passes are missing but whose regular output file is there would be skipped for good. Label: **documented and observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md). Handing over a list of frames instead works in every version, and the list may mix single frames and stretches.

## Every job renders as an animation

**A job is always rendered as an animation, even when it covers a single frame.** Label: **Creator-stated** (2026-07-28).

There is more than one way to set a render going, and what gets written is not the same for all of them. Rather than carry that difference around, Smoozy uses one of them for everything. This agrees with what [Render Settings](Render%20Settings.md) already says — a range of one frame is an ordinary range, not a separate kind of thing — and it means nothing in Smoozy ever depends on telling a still from an animation.

**The difference does arise outside Blender's interface, and the rule is worth more than it looked.** Every render Smoozy starts is started from outside, over a connection to a rented machine, and from outside there are two routes. A render asked for on the command line **is always an animation render**, whatever range it covers. A render driven by a script can be asked for either way, and there a single frame writes nothing at all unless it is separately told to save. Label: **documented and observed** (the same in all four versions, on both machines) — see [Sources](Sources/What%20a%20job%20writes.sources.md).

**The sharper reason for the rule is the frame number.** From Blender 5.0 a file output node stamps the frame number onto its file only on an animation render — a single frame rendered any other way writes a name with no number in it at all, and Blender 4.5 stamps it every time. Label: **observed; differs by version** — see [Sources](Sources/What%20a%20job%20writes.sources.md). A job that rendered a single frame the other way would leave a file the re-run above could never find and the count could never match. Rendering everything as an animation makes the frame number always present, in every version, and that is what this rule now buys.

## What this document hands over, and what it does not decide

- **Queue & History** owns the job's folder, its name and the identity behind it, the frame preview and *show outputs*. This document owns none of those. It hands that module which file the preview reads, which folder *show outputs* opens, what a queue entry says about the folders a job is writing into, a job that will write nothing, two destinations colliding, the same picture written to more than one place, a compositor shared with another scene and an output that is a single video file, and what *already there* means for a re-run — a frame counts only when every file it should have produced is present, the last frame Smoozy asked for that is present is re-rendered anyway, and a job that was never going to write anything is complete rather than re-run, which overrides that spec's own rule for a job that wrote nothing before it died. It also hands that module the two things that make the re-run safe: a job whose render was ended abruptly can leave a zero-length file where its last frame should be, so the last-frame rule is what stands between an abrupt ending and a frame that is never rendered; and **a file of zero bytes never counts as already there**, wherever in the range it sits, which is what stands between a machine going down and a job reporting complete with a hole in it. The same rule reaches [Download](Download.md), which does not bring an empty file home, and [Rendering](Rendering.md), whose carry-on figure is built on what counts as already there.
- **Download** brings outputs home; this document brings nothing home. It hands Download the count of files the job is expected to leave on disk, the list of formats, the one folder to watch, and the warning that a file appearing in that folder during a render may not have finished being written.
- **Render Settings** reads the `.blend`, through Pre-load Settings; this document does not read it. It hands Render Settings what the user is shown before a job is submitted.
- **Rendering** starts the render and carries out the redirect; this document does neither. It hands Rendering the redirect, that every job is rendered as an animation, that a running render is ended the way that leaves whole frames rather than the way that leaves a short one, and the two moments a job is held before its render starts for the user to choose — a path that cannot be brought under the job's folder, and a start-of-job read that finds no output at all or a colliding pair. That the redirect belongs to Rendering waits on that spec — see [Open Threads](../Groundwork/Open%20Threads.md).
- The [Glossary](../Groundwork/Glossary.md) holds the names — regular output path, compositor, file output node, main output, working and viewing format, beauty and utility pass. This document holds what Smoozy does about each.
- **Settled here:** a job that will write nothing is warned about and not stopped. The user is told, and may go ahead or stop. Label: **Creator-stated** (2026-08-06). What such a render leaves behind — nothing anyone can keep — is what the ruling was waiting on.
- **Settled here:** what a compositor shared between two scenes means for a job, which Blender 5.0 onwards allows. Smoozy warns before submitting that the pictures the job writes may belong to the other scene — the rule sits with the other things said before submitting, and is handed to Queue & History with them for the queue entry.
- **Settled here, and decided by Smoozy rather than by the Creator:** what is counted and what a re-run does for a job whose output is a single video file — one file with the number stated as possibly growing, a re-run of the whole range, and a warning before submitting that an interruption costs the whole range. And that a render Smoozy ends is ended the gentler way that leaves whole frames rather than the abrupt way that leaves a short one. Either can be pulled.
