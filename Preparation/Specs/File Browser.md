# File Browser

*What the File Browser module does, in plain terms: how the user looks through a connected server's files, sends files up to it, and manages what is there — including choosing the `.blend` a render is built from. Not one word about how it's built.*

## Where File Browser fits

File Browser is how the user views the machine they rented. Through it the user **looks through the server's files**, **manages what is there** — deleting, renaming, moving, copying, and making folders — and **sends files up** — any files and folders the user points at. It is the one place ordinary uploading lives.

It is the counterpart of Download. Download owns everything coming **down** to the user's computer; File Browser owns everything going **up**, and the browsing that surrounds both. Nothing travels down here — the file browser is one of the places a download is *started* from, but the files themselves come back through **Download**. A picture can be looked at here, but it is read to be shown and never kept *(see* A picture can be looked at without downloading it*, below; added 2026-10-31)*.

**Connections.** The [module map](Whole%20app.md) owns how File Browser is wired to the rest of the app. It needs a connected server from **Servers** for everything it does — there is nothing to browse without one. It works within one connected server at a time — one machine is browsed at a time. Label: **Creator-stated** (2026-07-23). It provides the chosen `.blend` to **Render Settings**. It hands the user a way to start a download, but the download itself is **Download**'s. And the ordinary uploading here is distinct from **Dependency Upload & Remap**, which does its own, more careful kind of uploading — finding a `.blend`'s missing assets and remapping the file to them; File Browser sends up what the user points at and changes nothing inside the files. What it does hand that module is where on the user's computer each uploaded file came from — see *Uploading* below. And it leans on **Queue & History** to know which jobs are running or waiting, so it can warn before the user disturbs a file one of them depends on.

**It can be opened at a chosen folder rather than wherever the user last was.** *Show outputs* on a job does exactly that, landing the user at that job's main output on the machine that rendered it — see the [Queue & History spec](Queue%20&%20History.md). Nothing else about browsing changes: from that moment the user is in the ordinary file browser, on the ordinary machine. Label: **Creator-stated** (2026-07-28).

**Where that job ran on a different machine, the browser moves to it**, since only one machine is browsed at a time. That is worth the user noticing rather than not, because an upload lands where they are browsing — so the move changes where the next file they send would go. An upload already under way keeps going to the machine it was sent to and stays visible in the transfer window. Only the next upload lands where the browser now is. Smoozy never opens a connection to do it: a machine the user has not connected cannot be browsed, and the action is not offered there. Settled at Design (2026-08-23): the server's badge and name change with the browser, and one line above the list says the move happened and why, clearing when the user next changes folder by hand.

## Browsing a server

The user moves through the server's folders and sees what is in them — files and folders, in the places they actually sit on the machine. What Smoozy shows is what the login it connected with is allowed to see. Where the login is not permitted to read something, Smoozy shows what it can and says plainly what it could not — see *do what can be done, and say what can't* in [Whole app](Whole%20app.md). And where the machine allows it, Smoozy can offer to try again with **elevated access**, rather than only reporting the refusal. Label: **Creator-stated** (2026-07-23). **What that costs the user is now settled**, and it is settled once for the whole app rather than here: where elevated access needs a password, Smoozy asks for it at that moment and the user chooses whether it is kept for that action alone, for as long as the connection lasts, or until they clear it — see *Security* in [Whole app](Whole%20app.md). **Whether a given machine allows elevated access at all is now settled, and it differs by the kind of machine rented.** On a whole rented machine the login can elevate — sometimes with nothing asked of the user at all, sometimes for a password. On a machine rented as a container, where the login Smoozy connects with is not that container's own owner, there is no route to elevate by: so Smoozy makes no offer there at all, rather than asking for a password that could open nothing. And on a machine Smoozy cannot place as either kind, there is no offer either and the refusal is reported as it stands — everything else about browsing that machine is unchanged. Label: **settled at Architecture** (2026-08-23). Permission can block an action just as it blocks a view — an upload into a folder the login cannot write to, or a delete it is not allowed — and the same two responses hold: Smoozy carries out the part it can and says plainly what it could not, and can offer to retry with elevated access where the machine allows.

**What Smoozy knows about each file** is settled here; how it is laid out, sorted, and shown is Design's. For every file: its name, its size, when it was last changed, and its kind. **When it was last changed means when its content last changed, wherever that happened: an upload keeps the file's own time, and so does a download**, so a texture last touched months ago on the artist's computer reads that date on the server, and a frame brought home reads the time it was rendered. Label: **Creator-stated** (2026-10-04), the Creator's note 3 on the test copy. *(Added that day. No plan had said whether a transfer keeps a file's time, and none did, so every uploaded file read as changed at the moment it went up.)* And for a `.blend` file, one thing more — **the Blender version it was saved with**, so the user can see at a glance which Blender made it. Smoozy reads that version straight from the file, without running Blender on it or pre-loading its settings. Label: **Creator-stated** (2026-07-23). Two Blender facts sit under that reading, and both are now settled: the version is in the file's opening text, which Blender 4.5 writes one way and 5.0, 5.1 and 5.2 another — label: **observed** (the same in all four versions, on both machines); and from Blender 5.0 an ordinary save is compressed, with a common compression that tools other than Blender can undo — label: **documented**. See [Sources](Sources/File%20Browser.sources.md). Handling both is Architecture's. The browser also shows how much free disk space is left on the machine's disk. Label: **Creator-stated** (2026-07-27).

**A folder's size is shown only when the user asks for it.** Asked, Smoozy counts everything inside the folder — every file in every folder below it, to any depth — and shows the total until the folder is next listed. Label: **Creator-stated** (2026-10-30), the Creator's twenty-third note 2: *"Not just the files inside it, but recursively."* *(Added that day. No plan had promised a folder's size, and the list showed none.)*

**A picture can be looked at without downloading it.** Opening a PNG or JPEG on the server shows it over the window, as it is, read from the server to be shown and never kept on the user's computer. It works on any connected server, set up or not. **Any other picture, and any file over 100 MB, is not shown**: Smoozy says so and offers to download it. Bringing a file to the user's computer is still Download's. Label: **Creator-stated** (2026-10-30), the Creator's seventeenth note 11: *"Can we include an image viewer in the file browser? Just a viewer, nothing else. Because I feel like simply double-clicking an image and instantly seeing a preview is something people would surely expect."* Asked whether Files should have an image viewer: *"Yes to both your questions."* PNG and JPEG only, and the 100 MB cap, **ruled 2026-10-31 under the Creator's standing delegation**: showing OpenEXR and the other working formats needs a copy made by the server's Blender, and that is parked in [Open Threads](../Groundwork/Open%20Threads.md). *(Added 2026-10-31, a want entering at Specs under Rule 7. No auditor has seen it.)*

**Hidden files stay hidden until the user asks to see them.** A hidden file or folder is one whose name starts with a period. The browser has one checkbox, *Show hidden files*, and it is off until the user ticks it. Label: **Creator-stated** (2026-10-01), in their own words: *"We need a checkbox — just a simple checkbox that shows and hides these. And they should be hidden by default."*

**The choice is remembered for the whole app, not per server** — one setting, kept from one run of Smoozy to the next. **It changes only what the list shows**: downloading, deleting, moving or copying a folder still takes everything inside it, hidden or not, nothing is uploaded or skipped differently, and the already-exists question still counts a hidden file an upload would land on. Label: **ruled 2026-10-02 under the Creator's standing delegation**.

**Smoozy's own staging folders are hidden like any other.** A part-sent upload waits in a folder of Smoozy's own beside where it will land, and that folder's name starts with a period. With the box off it is not listed; with it on it is listed and marked as Smoozy's. Either way, a part-sent upload left behind is still told about in the transfer window and removed from there. Label: **ruled 2026-10-02 under the Creator's standing delegation**.

**A hidden folder still opens.** Where the browser is sent straight into one — *Show outputs* landing on a job's folder, or a part of the path along the top — it opens and lists like any other folder. The box hides names in a list; it locks nothing. Label: **ruled 2026-10-02 under the Creator's standing delegation**.

Settled at Design (2026-08-10 onward) — see [the Design document](../Design/File%20Browser.md), which carries the layout, the sorting and the navigation.

## Choosing a `.blend`

Choosing a `.blend` from the browser is how a render begins: the chosen file is handed to **Render Settings**. Choosing the file does **not** read it — reading is a separate action, **Pre-load Settings**, that belongs to Render Settings (see the [module map](Whole%20app.md)). File Browser's part is only to let the user find and pick the file; what happens to it after that is Render Settings' work.

**Another module can open the browser so the user points at a file.** When the user submits a job again from history and the `.blend` is no longer where that job found it, **Rendering** opens the browser on the machine so they can point at where it went — see the [Rendering spec](Rendering.md), which owns when that happens. The browser's part is the same as ever: the user finds a file and picks it, and the file goes back to whoever asked. This is the second way in of that kind, alongside *show outputs* opening the browser at a folder for **Queue & History**. Label: **Creator-stated** (2026-07-30).

## Uploading

The user sends files up from their own computer to the server: files and folders, any number, in any mix. To File Browser these are just files and folders — a `.blend` among them is only a file here, no different from any other until it is chosen for a render. Label: **Creator-stated** (2026-07-23).

**Uploads land where the user is browsing.** The folder the user is looking at on the server is where an upload goes. There is no separate "upload destination" to set — the user navigates to where they want the files, and sends them there. Label: **Creator-stated** (2026-07-23).

**A folder goes up as a folder.** The structure the files have on the user's computer is the structure they have when they land on the server — the mirror of how Download brings a folder back down (see [Download](Download.md)).

**An upload records where each file came from on the user's computer**, and that record is available to **Dependency Upload & Remap**. That module needs it: a `.blend` can record where it expects to find a thing in a form that only means something back on the computer the file came from, and knowing where Smoozy watched that file go up is what lets the original location be worked out again — see the [Dependency Upload & Remap spec](Dependency%20Upload%20&%20Remap.md), which owns the rule and the Blender fact under it. A file that reached the machine some other way carries no such knowledge. This is the promise and nothing about the method; how the record is held is Architecture's.

**The unit is the file, the request is still one thing.** Sending up a folder of three hundred textures is three hundred transfers, not one — the user can see exactly which file is moving, which is slow, and which failed, while still seeing how far the upload as a whole has got. A set number of transfers run at once per server and the rest wait their turn, and the user does not set that number. This is the same behaviour as a download, and for the same reasons — the [Download spec](Download.md) sets it out, and File Browser follows it. Uploads and downloads draw on that same per-server pool of slots; how they share it is Smoozy's to manage and Architecture's to tune. **The order is settled**, and it contains the pair the Download spec already fixed rather than re-deciding it: auto-download first, then manual download, then the uploads a submission is waiting on, then ordinary uploads. Downloads come before uploads because the line is far faster downwards, so a slot spent that way frees itself sooner. Nothing waiting is left waiting for ever — whatever has been passed over long enough is taken next, and where two things qualify at once the order above decides between them. Label: **settled at Architecture** (2026-08-23). Label: **Creator-stated** (2026-07-23).

## When the file is already there

Before an upload starts, Smoozy checks what it is about to land on. This covers **files, folders, and any mix of them** — whatever the user is sending up. If anything it is sending would land exactly on something already there, it stops and asks — **once for the whole upload**, not once per file. It says **how many** already exist as the headline, and the user can see which files collide before choosing. Files covered by the separate **Dependency Upload & Remap** warning are counted in this already-exists total, and that warning names them separately.

**Collisions are judged file by file, by name and place.** A folder is not one lump that either collides or does not. Smoozy looks at where each file *inside* it would land, and a collision is a single file that would land exactly on an existing one — same name, same folder. Uploading a folder into a same-named folder is a **merge**, not a clash in itself: two folders called `Textures` become one, and only the files that share a name and place inside them actually collide. A file landing on a same-named folder, or a folder landing on a same-named file, cannot merge and is treated as a collision — the same question, with **Keep both** giving the arriving one a non-colliding name. The same holds for a move and a copy. Label: **Creator-stated** (2026-07-23).

So sending a folder of ten files into a place that already holds a folder of that name with ten *different* files collides with nothing — the folder ends up holding all twenty. If instead ten of the arriving files share names with ten already there, Smoozy reports **ten already exist**, and the four answers act on those ten:

- **Replace** the existing copies with the ones being sent up. For a folder, this touches only the files that actually collide — the rest of what was already in the folder is left alone, and the non-colliding new files are added. It does **not** wipe the existing folder and drop the new one in its place. And where a file it would replace is one a running or waiting job depends on, the live-job warning fires first, the same as for a delete (see *Managing files on the server* below). Label: **Creator-stated** (2026-07-23).
- **Keep both** — renames the whole arriving top-level thing (the folder as a lump, or the loose file) with a non-colliding name. What is already on the server is left untouched. If a folder of three hundred files arrives where twelve names collide, the whole arriving folder is set aside under a new name, and the twelve are not renamed individually. Nothing inside a renamed folder is merged.
- **Skip existing** — send up only the files that are not already there.
- **Stop** the whole upload.

The one answer covers everything that collides in the upload, loose files and whole folders alike: **Replace** overwrites every colliding file across the batch, **Keep both** renames the whole arriving top-level thing (the folder as a lump, or the loose file), and **Skip existing** passes over all of them.

**One kind of collision is warned about separately**, because replacing the file would break a render silently. **Dependency Upload & Remap** puts files on a machine and rewrites some of them so they point at each other; a plain upload landing on one of those would put back a file that points at the user's own computer instead. So Smoozy says so and offers to send it through that module instead, which is where the rule lives — see the [Dependency Upload & Remap spec](Dependency%20Upload%20&%20Remap.md). File Browser's part is only to raise it before the upload lands.

Smoozy compares by **name and place only**. It does not look inside the files, and it does not compare dates or sizes to guess which the user wants. The same file-by-file logic serves a download bringing a folder home, turned around to face the user's own computer — see the [Download spec](Download.md), which states what it means coming down. Label: **Creator-stated** (2026-07-23).

This is the server side of things, and is separate from the whole-app rule that Smoozy never silently overwrites files on the *user's own computer* (see [Whole app](Whole%20app.md)) — that rule is about the local machine; this question governs the server, which is the user's machine too, reached across a connection.

## Managing files on the server

The file browser is a full file manager for the machine the user rented. Beyond browsing and uploading, the user can **delete** files and folders, **rename** them, **move** them from one place to another, **copy or duplicate** them, and **make a new folder**. Label: **Creator-stated** (2026-07-23).

This follows the whole-app principle that *the machine is the user's* (see [Whole app](Whole%20app.md)): Smoozy carries out what the user asks on their own server, the same as any file manager would.

**Deleting is permanent, and Smoozy warns before it does it.** A file deleted on the server is gone — Smoozy keeps no copy and cannot undo it, and the machine itself has no recycle bin to fall back on. Label: **an assumption** (the machine-side point) — see [Sources](Sources/File%20Browser.sources.md). So a deletion is warned about before it happens. That warning is dismissible, and like every dismissible warning it can be switched back on from Settings all at once (see *restoring suppressed warnings* in [Whole app](Whole%20app.md)).

**A move or a copy that would collide is caught the same way** a colliding upload is — landing a file or folder where one of that name already sits is caught, and Smoozy never silently writes over what is there. A colliding move gets **Replace** or **Cancel**. A colliding copy gets **Replace**, **Keep both**, or **Cancel**. A copy leaves the original in place; a move does not. Both stay within the one machine.

**A rename that would collide is not allowed in the first place.** Renaming is an in-place change to a single thing, so there is nothing to merge and no second copy to keep — if the new name is already taken in that folder, Smoozy does not accept it, and the user picks another. This follows how a file manager handles renaming, rather than the upload question. Label: **Creator-stated** (2026-07-23).

**Smoozy warns before you disturb a file a live job is using.** The warning is not dismissible. Before deleting, moving, renaming, or overwriting a file — or a folder that holds one — Smoozy checks whether any job depends on it, and warns if so, naming the job. This warning covers a job's `.blend` and the assets it reads, as well as the folder and files a running job is writing to. The trigger fires on touching a file the job depends on, or on any change inside a folder the job uses. Overwriting counts because an upload's **Replace** can land on a file a live job is reading, which disturbs that job as surely as deleting it would. This covers jobs that are **running** *and* jobs that are **waiting to run**: a file pulled out from under a queued job breaks it just as surely as one pulled from a render already going. The user can still go ahead — it is their machine (see [Whole app](Whole%20app.md)) — but never unknowingly. Label: **Creator-stated** (2026-07-23).

**What disturbing such a file actually does to a running render is now known, and it is not always a break.** A picture replaced under a job that is already rendering **reaches that render from some later frame onward** — the earlier frames hold the old one and the rest hold the new one, and no frame ever came out part old and part new. So the job does not fail: it finishes, at full price, with two different textures in it. A linked `.blend` and a movie clip behave the other way and do not reach the **next** render until they are reloaded — neither was tried under a render already running — and a picture packed inside the `.blend` ignores its file where nothing is done about it. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/File%20Browser.sources.md). That is why the warning is not dismissible: the harm it prevents is often a finished job that looks perfectly ordinary rather than a render that stops.

**Where the user goes ahead, Smoozy says so to the queue.** File Browser tells **Queue & History** which live jobs were affected, and that module marks each of them as having had a file disturbed — see the [Queue & History spec](Queue%20&%20History.md), which owns what the mark says and how the job reads afterwards. The reason is the gap in time: the warning is read now and the job fails hours later, by which point the user has no memory of the file they moved, and an unexplained failure on a machine billed by the hour is the worst way to learn it. Nothing about this stops the user — the warning is still theirs to overrule. Label: **Creator-stated** (2026-07-30).

File Browser cannot see this by itself — it is a file manager, not the render queue. It leans on **Queue & History** for which jobs are running or waiting. Knowing which files a given job depends on — its `.blend` and every asset it references, some of them put there by **Dependency Upload & Remap** — is knowledge that spans those modules; this includes anything on the machine that has been pointed at, not only what a live job is reading. The live-job warning is the stronger case that names the jobs at risk. How a `.blend`'s references are worked out, and the Blender facts under it, belong to **Dependency Upload & Remap** — see the [Dependency Upload & Remap spec](Dependency%20Upload%20&%20Remap.md). One limit there reaches this warning: where a file the job needs is itself missing, nothing below that file can be read, so the set Smoozy has may be smaller than the set the job really uses. Label: **observed** (the same in Blender 4.5, 5.0, 5.1 and 5.2) — see [Sources](Sources/File%20Browser.sources.md). Whether Smoozy can work out every file a job depends on stays **unresolved**, and where the record of it lives is for the module map and Architecture to settle. What is settled here is the promise: a live job's files are not disturbed silently, as far as Smoozy can see them.

**Narrowing the warning to the rendering scene's own files was weighed and not taken.** A render was found not to open another scene's picture — the same in all four versions on both machines — while a linked `.blend` is opened whichever scene renders. Label: **observed** — see [Sources](Sources/File%20Browser.sources.md). So the warning could in principle fire on less, and fewer warnings is worth something, since a warning the user learns to click past protects nobody. **It stays wide, on the Creator's ruling of 2026-08-12**, because the evidence reaches a scene's material picture and a linked `.blend` and nothing else. A background scene, a compositor node naming another scene and a sequencer scene strip were never tested, and those are exactly the places a narrowed warning would be silent when it should not be. Warning too often costs the user a click; warning too rarely costs them a finished render with the wrong texture in it, which the paragraph above says is the ordinary outcome. Label: **Creator-stated** (2026-08-12).

**A second warning covers a file nothing live is using**, and it fires on the same actions. Where **Dependency Upload & Remap** put a file on the machine, or fixed one to point at it, disturbing that file breaks something whether or not a job is running — an asset two projects share, or a `.blend` left pointing at nothing. So Smoozy warns there too, naming what the file is depended on by rather than naming a job. When that fires, and what counts as depended on, are that module's — see the [Dependency Upload & Remap spec](Dependency%20Upload%20&%20Remap.md). The wording and shape of the warning are this module's, like every other warning it shows, and the user can go ahead in either case.

## Stopping a transfer, losing the connection, losing the app

The user can stop an upload that is under way. Stopping an upload stops the whole request: files already finished stay on the server, files still waiting are not sent, and the one in flight is stopped.

**A part-arrived file is not left on the server looking finished.** Whatever ends a transfer before it completes — the user stopping it, a lost connection, or the app closing — Smoozy does not leave a half-sent file sitting on the server as though it were the whole thing. An upload the user deliberately stops has its leftover removed straight away. An upload cut off by a lost connection or the app closing keeps its leftover, so it can be carried on later; the user is told it is there and can remove it. In particular, it is never counted as already being there. The already-exists question compares by name and place, and a half-sent file has the same name in the same folder as a finished one, so *skip existing* would otherwise pass over it and call the upload done. A part-sent file is not something to skip; it is something to finish. Exactly how the partial is held is Architecture's; that the user is never left with a broken file that looks complete is settled here. This is the mirror of what the [Download spec](Download.md) promises for files coming down. A file that arrives whole but damaged is the same harm reached another way, and the whole-app promise that a file is either correct or plainly not there covers both — see [Whole app](Whole%20app.md).

**Closing Smoozy stops uploads**, the same as it stops downloads — a transfer runs between the user's computer and the server, so it needs Smoozy to be there. This is unlike the render queue, which lives on the server and carries on unwatched (see [Queue & History](Queue%20&%20History.md)).

**And the browser itself does not sit there pretending to be live.** A folder listing is what Smoozy saw when it last looked, and while the connection is down that is all it is. So the listing **stays on screen and says plainly that it is not live** — it is not emptied, because throwing away what the user was looking at helps nobody and they may still want to read a name off it. Everything that needs the machine is **unavailable rather than failing on a click**: opening a folder Smoozy has not already seen, uploading, downloading, deleting, renaming, moving, copying, making a folder. The free-space reading and each file's details are equally stale and read as such. When the connection comes back — by the user's own act or by the repair [Servers](Servers.md) makes on its own — the listing is read again and the controls return. Label: **Creator-stated** (2026-08-10).

Two things make that the right shape. It matches what the server itself reads as while the line is down, which is [Servers](Servers.md)', so the two parts of the app do not disagree about the same machine. And it keeps the whole-app rule that Smoozy never looks as though a click did nothing, and never claims to know more than it does (see [Whole app](Whole%20app.md)): a stale listing the user is told is stale is honest, and one they can click into as though it were current is not. How stale reads on screen, and how the controls show as unavailable, is Design's.

**A lost connection stops an upload, and Smoozy carries it on when the connection comes back.** [Servers](Servers.md) has Smoozy notice a dropped connection itself and keep repairing it, unasked, for as long as the app is open. When that repair succeeds, the uploads the drop interrupted carry on from where they stopped, and the user does not ask again. While the line is down those uploads are waiting rather than finished or failed, and the user can stop one exactly as they can stop one that is moving. Label: **Creator-stated** (2026-08-12).

**That reverses what this document used to say, and the reason it gave does not survive it.** The old rule was that an upload is a request made at a moment rather than a standing arrangement, and a moment that has passed is not one Smoozy renews on the user's behalf. What decided it the other way is the position Smoozy is actually in: it is holding a live connection it repaired on its own initiative and not using it, the user's request has not changed, and asking them to make it again charges them for a network they do not control. Label: **Creator-stated** (2026-08-12).

**It lasts as long as Smoozy is open, and no longer.** Closing Smoozy stops uploads and ends the request with them. What is left on the server stays there to be carried on by hand, as the paragraph above sets out, but no upload starts itself again on a later connection — a connection the user opens in a fresh sitting is a fresh act. So the request survives the connection dropping and does not survive the app closing.

**And it carries on only where Smoozy can tell the file has not changed** — the same condition the carry-on inside a single file rests on, below. Where the file was saved over while the line was down, the upload does not resume: Smoozy says the file changed while it was being sent and offers to send the new version, exactly as it does for a save that lands mid-upload.

**Nothing that already crossed is sent again — whole files, or part of one.** An upload Smoozy carries on picks up where it stopped, so nothing that landed goes across twice and the answers the user already gave about collisions still stand. And where the user does start the upload again themselves — after closing Smoozy, or after the file changed — they need never re-send what arrived either: Smoozy says what is already there and puts **Skip existing** forward as the answer that keeps it.

For **whole files**, an upload of many files is many transfers, and the ones that finished are finished — they sit complete on the server, not swept away with the partial one. So a folder that was half sent when the connection dropped is not started over from nothing. The already-exists check recognises everything that landed, so **Skip existing** will send only what did not — the finished files are kept and passed over, and only the remainder crosses the wire. Nothing forces the finished files back across; the user chooses skip existing to leave them be. Label: **Creator-stated** (2026-07-23).

The same holds **inside a single file**. A large `.blend` that stopped nine-tenths of the way up does not go back across the wire from the beginning — Smoozy carries on from where it stopped. This matters most for the upload the user repeats. A folder of textures is already protected by the files that arrived whole, but a packed `.blend` is one file and nothing else, so without this there is nothing to keep; and because sending only the `.blend` is how the user iterates (see the [Dependency Upload & Remap spec](Dependency%20Upload%20&%20Remap.md)), that is the upload made over and over. Label: **Creator-stated** (2026-07-26).

**But only where Smoozy can be sure the file has not changed.** Carrying on assumes the thing being sent is still the thing that was half sent. A user who edits and saves the file between the two attempts would otherwise get the first part of the old version joined to the end of the new one — a file of the right name and the right size, and worthless. That is worse than starting over, and it is exactly the broken-file-that-looks-finished the promise above exists to prevent. So Smoozy carries on only where it can tell the file is unchanged, and sends that file again from the beginning where it cannot. The promise gives way rather than handing back a broken file. How Smoozy tells, and whether a transfer can be carried on part-way at all, are Architecture's — see [Sources](Sources/File%20Browser.sources.md). Label: **unresolved**. Label: **Creator-stated** (2026-07-26).

**A file changed while it was going up is stopped, not landed.** The user can edit and save a file after its upload has started — a `.blend` tweaked once more in Blender, a texture re-exported while its folder is on the way. Smoozy does not carry on and land the first part of the old version joined to the last part of the new one. It stops that transfer and says the file changed while it was being sent, leaving nothing on the server that looks finished (see [Whole app](Whole%20app.md)). It then **offers to send the new version**, which is almost always what the user wants next — but an offer, not something done unasked. When the user accepts the offer to send the new version, Smoozy waits until the file has been left alone for a moment before starting. If it is saved again while going up, it stops and offers again, as now: a save made mid-edit can be a state the user would never render, and because the file has changed nothing already sent can be reused, so starting again costs whatever the upload had already spent. This holds for any file, not only a `.blend`. Label: **Creator-stated** (2026-07-26).

## Where transfers are watched

Uploading and downloading are watched in **one place** — a single transfer window covering ordinary uploads and downloads together. The dependency uploader has its own interface, and how its transfers share the window is settled in the paragraph below. Auto-download is shown as its own kind of thing, distinct from a plain transfer (see [Download](Download.md)). Label: **Creator-stated** (2026-07-22).

Settled at Design (2026-08-11 onward) — see [the Transfers Design document](../Design/Transfers.md), which carries one list of four kinds with a tag on each, the direction as an arrow, and how a request reads against its files.

## What File Browser does not do

- It does not bring anything **down** to the user's computer — that is **Download**. It is a place a download is started from, but the files come back through Download. Showing a picture is not bringing it down: the picture is read to be shown and is not kept *(added 2026-10-31)*.
- It does not remap a `.blend`'s references or hunt down its missing assets — that is **Dependency Upload & Remap**. The plain uploading of files the user points at is File Browser's; the careful upload-and-remap of a file's dependencies is not.
- It does not read a `.blend` or fill in its render settings — that is **Render Settings**' Pre-load Settings. File Browser only lets the user pick the file.
- It does not connect to a server. Everything here needs a connection from **Servers**, and it never reaches a server the user has not connected.
- It does not install anything on the server — that is **Server Setup**.
- It does not run, stop, or reorder any render, and it does not manage the queue — it only reads which jobs are live, to warn about a file one of them needs.
