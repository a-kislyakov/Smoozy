# Render Settings

*What the Render Settings module does, in plain terms: the settings a user fixes for a chosen `.blend` before it renders, and the routine that reads the file to fill them in. Not one word about how it's built.*

## Where Render Settings fits

Render Settings sits between picking a file and submitting a job. **File Browser** hands over a `.blend` the user chose on a connected machine; what the user settles here is what **Rendering** submits, and from that moment the settings are fixed and cannot be changed.

The module owns two things: the settings, and **Pre-load Settings** — the routine that reads the file and fills them in with what is actually in it.

**Connections.** The [module map](Whole%20app.md) owns how Render Settings is wired to the rest of the app. That covers the chosen `.blend` arriving from **File Browser**, the settled settings feeding **Rendering**, its reading of the file giving **Download** both the count of a job's expected outputs and the list of formats an auto-download arrangement can be narrowed to, and that same reading telling **Server Setup** the one add-on case a file announces — an engine the chosen Blender lacks, which is all a `.blend` can be read for. What that reading finds about a job's outputs — the count, the formats, the folders, the main output — is settled in [What a job writes](What%20a%20job%20writes.md); this module supplies the read, not the answers. It needs a connected server from **Servers**, because both the file and the Blender that reads it are on the machine, and it depends on **Server Setup** having put a Blender there. Checking a `.blend` for the assets it is missing is **not** part of this module — it is its own action and belongs to **Dependency Upload & Remap**.

## Where each setting starts

Nothing here is a Smoozy default. **Each setting read from the file opens showing the value the file itself carries**, shown as a starting value rather than something the user typed. Leave it alone and the render uses what the file says. Type over it and the user's number wins. That covers the frame range, the view layer boxes, the sample count, the resolution percentage, the engine, and the choice between the machine's GPUs and its processor.

**One thing limits that rule and cannot be worked around here.** What a setting "carries" is what the chosen Blender reported when it read the file, and for the engine those two can differ — a Blender that has not got the engine the file names hands back its own instead. That is set out under [The render engine](#the-render-engine).

**Before the file is read, those starting values are a promise rather than a display.** Picking a `.blend` does not read it (see the [File Browser spec](File%20Browser.md)), so at that moment Smoozy does not yet know the file's frame range, its scenes, its view layers or its sample count. The settings still mean "whatever the file says" — Smoozy just cannot show the user what that is yet. **Pre-load Settings** is what turns the promise into numbers.

**Three things do not start at a file value**, so the rule above is not the whole page:

- **Which scenes are ticked.** A `.blend` carries its scenes, not an answer about which of them to render, so there is no file value to show~~ or to hand back to~~. There is nothing to clear either, because handing the choice back would leave the page with no answer at all. **The one way back is the control that hands everything back**, which ticks the scene the file was saved showing (below). *Changed 2026-10-08, the Creator's fifth notes, note 4.* **Before the file has been read there is no list of scenes, so there is nothing to tick and no scene choice on the page.** A job submitted at that point carries no scene name, and renders whichever scene the file was saved showing — which is settled in the [Rendering spec](Rendering.md). One case sits outside that: a page opened from a history entry arrives carrying that job's scene, which is the user's own answer rather than anything read from the file — see [Which scenes](#which-scenes). Once the file has been read the choice appears, starting with exactly one scene ticked and never empty; which one that is falls to Design. What the job's entry shows for the scene until the read happens is the [Queue & History spec](Queue%20&%20History.md)'s.
- **The frame range with more than one scene ticked.** Each scene carries its own range and there is no one number true of all of them, so nothing is shown as a starting value. Left alone, every scene uses its own range; clearing a typed range returns to that.
- **Which Blender renders the job.** It comes from the machine rather than from the file — the versions installed there, matched against the version the file was saved with (see [Which Blender](#which-blender)). Clearing it returns to that automatic match, not to a value out of the file.

**Handing a setting back is always possible.** Every setting the user has overridden carries a way to clear it and return to the file's value — a small cross, in the Creator's picture; how it looks is Design's. This holds for every setting on the screen, including the view layer boxes below. Label: **Creator-stated** (2026-07-27).

Together that is the model, and it means the user only ever states the differences. A job submitted without touching anything renders the file exactly as the artist saved it.

**Handing everything back at once is also possible.** One control returns every setting to the file's own values in a single go, and to the automatic match for the Blender version. The individual ones stay — this is the shortcut, not a replacement for them. Label: **Creator-stated** (2026-07-27). **Once the file has been read, it also ticks the scene the file was saved showing, alone, in place of whatever is ticked.** Label: **Creator-stated** (2026-10-07): *"Reset all to file values doesn't reset the selected scene. It should revert to the file's active scene."*

**Every setting this page offers can be imposed on a render started from outside Blender**, rather than only by changing the file. Four of them — the frame range, the step, a list of frames, and the engine — are stated directly when the render is started. The other three — the sample count, the resolution percentage, and whether a view layer renders — have no route of their own, and are set instead by an instruction handed to Blender as the render starts, after the file has been named. Neither route changes the `.blend`: after a render contradicting everything the file held, the file was untouched and still carried its own values. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine). See [Sources](Sources/Render%20Settings.sources.md).

The engine carries a version catch of its own, set out under [The render engine](#the-render-engine). The choice between the machine's GPUs and its processor has its own section further down.

## What the user typed is not lost while they look elsewhere

Setting up a render is not one uninterrupted sitting. The user compares scenes, goes back to the file browser to check something, opens another `.blend`. None of that throws away what they have typed.

**Switching scenes keeps each scene's settings.** Every scene holds its own set, so moving to another scene and back finds the first scene exactly as it was left — overrides and all. Nothing is redrawn from the file because the user looked away. Label: **Creator-stated** (2026-07-27).

**Switching files keeps them too**, and so does switching servers. A `.blend` the user set up, left, and came back to still carries what they typed into it, whether they went to another file on the same machine or to a different machine entirely. Label: **Creator-stated** (2026-07-27). *(A range a history entry loaded is not something they typed: the [Rendering spec](Rendering.md), under* The setup waits while they go*. Added 2026-11-03. No auditor has seen it.)*

**A dropped connection does not take them.** What the user typed is theirs — numbers they chose, owing nothing to the machine — so a connection falling over leaves it all intact, and reconnecting finds the settings as they were. Setting up a long render can take a while, and a connection that falls over in the middle of it does not undo the work. Label: **Creator-stated** (2026-07-27).

**What the connection does take is what was read from the file.** Those values were true of the file when it was last read, and Smoozy cannot vouch for them across a gap it was not watching — the file may have been replaced or changed in the meantime. So a reconnect keeps the user's own values and drops the file's, leaving the settings meaning exactly what they meant before anything was read: whatever the file says, plus whatever the user typed. Reading the file again fills the rest back in.

That split is the whole rule: **the user's answers survive, the file's do not.**

**The scenes ticked and the view layer instructions are the user's answers, so they survive too.** Both are stated in terms of things only the read knows — a scene by name, a view layer by name — but what the user said about them is theirs, so it is held against the scene and the view layer they named and shows again as soon as the file is read. In the gap the settings still carry those answers, and the page shows them without the file's values beside them: the scenes the user ticked stay ticked, and a view layer they pinned on or off is still pinned, with no boxes for the view layers they never touched, because nothing knows what those are until the file is read again.

**A read stops being true of the file it was taken from, and of the Blender it was taken with.** Three things end a read, and all three do the same thing — the file's values are dropped and the user's own are kept, exactly as at a reconnect:

- **The connection drops**, as above.
- **The `.blend` is replaced or changed on the machine** while Smoozy stays connected — a new upload over the top, or a save the user made in Blender. The values on screen would then describe a file that no longer exists. **Smoozy notices this at moments of its own rather than by watching the file.** Nothing on a machine can tell Smoozy that a file changed, so there is no watch: the page checks at the few points where the user has just done something that could make it stale. **A change landing between two of those points is not noticed until the next one, and for that stretch what is on screen is out of date.** That costs the user a stale display and never a wrong render: every render attempt reads the file afresh on the machine as it starts, which catches anything the page missed. Label: **settled at Architecture** (2026-08-23).
- **The user changes the Blender version.** A read is taken with the version the job will render with, so changing that version afterwards leaves everything the read produced describing a version the job will not use — including whether the file names an engine that Blender lacks, since an add-on **does** belong to one Blender on the machine rather than to the machine itself: nothing is shared between versions unless somebody arranges it, because each Blender reads a folder named for its own version and nothing else keeps them apart. Label: **observed** (the same in all four versions, on both machines) — see the [Server Setup spec](Server%20Setup.md), which owns add-ons. Nothing has to notice this one: this page is where the version is changed. Reading the file again with the new version fills it back in.

**Closing Smoozy takes everything.** Settings live for as long as the app is open and no longer. Nothing here is kept on disk or carried into another sitting: this is a working state, not a saved one. Label: **Creator-stated** (2026-07-27).

That last part is deliberate rather than a shortfall. Settings are only ever a statement of how a particular file should be rendered *now*; the record of how something *was* rendered lives on its job, which **Queue & History** keeps until the user clears it.

## Pre-load Settings

**Pre-load Settings reads the `.blend` and fills the settings in with its real values.** It is a separate action the user takes, not something that happens on picking a file. That name is settled. Label: **Creator-stated** (2026-07-17). *(Withdrawn 2026-10-13: the change of 2026-10-12, that either read starts the other, was taken back the next day because the Creator deferred the request (the ninth notes, note 4). The idea is parked in Open Threads.)*

**The file is read anyway when the job starts.** If the user never clicks Pre-load, the render loads the file itself, so the file is read at that point regardless. A file's real settings are therefore known at the latest when its job begins, never later. Anything downstream that needs the file read can rely on that — the [Queue & History spec](Queue%20&%20History.md) leans on it for what a queue entry can say about a job. Label: **Creator-stated** (2026-07-24).

**One read covers the whole file.** A `.blend` holds every scene it has, so pre-loading once gives Smoozy all of them — their ranges, their view layers, their sample counts — not only the scene the user is currently looking at.

**It can be run again at any time**, and a second run replaces only the file's values. Whatever the user typed stays exactly as they left it, which is the same rule a reconnect follows. Uploading a corrected `.blend` over the top and reading it again is the ordinary way this page is used.

**A read either succeeds whole or gives nothing.** The chosen Blender may fail to open the file — some files will not open in some versions (see [Which Blender](#which-blender)) — and then nothing about the file's insides is shown: no scenes, no view layer boxes, no sample count, no statement of what the file will write. Nothing is left half-filled. What the user typed stays exactly as it was, Smoozy says the file could not be read and with which version, and the user can pick another installed Blender and run it again. Submitting is still offered, because the file is read anyway when the job starts. Label: **Creator-stated** (2026-07-29).

**Pre-load also reads what the file will write.** A `.blend` writes files in two quite separate ways — its own output path, and its compositor, which can write any number of files to anywhere on the machine. Reading that is part of the same read, and it is what gives **Download** the count and the format list, what finds the job's **main output**, and what fills in the statement below. All of it is settled in [What a job writes](What%20a%20job%20writes.md); this module only supplies the reading. Label: **Creator-stated** (2026-07-28).

**Nothing about the file's insides can be shown until it has run.** That covers the list of the file's scenes, the view layer boxes, the samples warning, what the file was going to do about stopping a render short, the warning that one scene pulls in another, whether the file names an engine this Blender lacks, and everything about where the job's outputs will go. Each is a fact about what is inside the file, and there is nothing to show before the inside has been read.

**Pre-load needs a Blender on the machine**, because reading a `.blend` means opening it. On a machine with no Blender installed, no file can be read and no job can be sent from it — what does stay available there is set out under [When the machine has no Blender](#when-the-machine-has-no-blender). Label: **Creator-stated** (2026-07-27) — a Blender fact from the Creator, who holds that it needs no confirming.

**Where the add-ons a render needs can be read out of a file, Pre-load is what reads them.** That is Smoozy's decision, and it is all this document claims. Label: **Creator-stated** (2026-07-29). **They almost never can, and this is what Pre-load honestly claims to find.** A `.blend` keeps no record of the add-ons it needs and Blender offers no way to read one out. Nor does an add-on declare whether it takes part in a render. Label: **documented and observed**, all four versions on two kinds of computer — owned and cited by the [Server Setup sources](Sources/Server%20Setup.sources.md), along with everything else about add-ons.

**One thing announces itself, and it is the only one.** A file records by name which engine renders it, and a Blender lacking that engine's add-on says so the moment the file is opened. Pre-load already reads the engine, so a job whose renderer is a missing add-on is found by the read this module already does. Nothing else is. Label: **Creator-stated** (2026-08-13).

So what Pre-load finds is that one case, never a list of what the file needs, and it says so on this page, plainly. **It offers nothing to install: Smoozy installs no add-ons.** Label: **Creator-stated** (2026-10-08) — the Creator's words are quoted in the [Server Setup spec](Server%20Setup.md#add-ons), which parks the guess, the offer and the rest of that section.

**One limit, stated rather than hidden.** Whether something outside Blender could read a `.blend` directly and work backwards to an add-on was never established: no version's sources describe the file's shape and no test tried it. Nothing here rests on it.

**What can be found is found inside this read rather than in a pass of its own**, and this module owns that choice. There was never much to find — the engine is a setting this read already takes — and a third read of the same file, beside this one and the dependency check, would cost more than it is worth. Two things follow from putting it here. The engine is read with the version the job will render with, so the answer describes that job rather than the machine; and it carries the cost Pre-load carries for everything else, that a user who never runs it learns nothing.

**Pre-load is not a dependency check.** It reads the file's settings, what it will write, and the one add-on case a file announces — an engine the chosen Blender lacks — and says nothing about the textures, caches and other pieces the file may be missing. Finding those is its own action, and it belongs to **Dependency Upload & Remap**. Label: **Creator-stated** (2026-07-27). *(Withdrawn 2026-10-13: the change of 2026-10-12, that either read starts the other, was taken back the next day because the Creator deferred the request (the ninth notes, note 4). The idea is parked in Open Threads.)*

## Which scenes

A `.blend` can hold several scenes, each with its own frame range, its own view layers and its own render settings (see the [Glossary](../Groundwork/Glossary.md)). **The user ticks the scenes they want**, and an **all scenes** option alongside ticks every one of them in a single go. One scene, three of them, or the whole file are the same act with a different number ticked. Label: **Creator-stated** (2026-07-29).

**The scene choice governs the settings that are read from a scene** — the frame range, the view layer boxes, the sample count, the resolution percentage, the engine, and the choice between the machine's **GPUs and its processor**, which is a scene's own setting like the rest: a file saved with one scene set to the graphics cards and another left alone came back exactly that way. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine), see [Sources](Sources/Render%20Settings.sources.md).

**One setting sits outside the scene choice** and stays live however many scenes are ticked: **which Blender renders the job**, which comes from the machine rather than from the file at all.

**One scene ticked leaves all of those live**, and they all belong to that scene. Ticking a different scene instead redraws them from that scene's own values — a scene's range, its view layers and its samples are its own, and nothing carries across.

**More than one ticked greys all of them but the frame range.** Each ticked scene then renders as the file specifies it, and the range stays open: the one range the user sets is imposed on every ticked scene alike, overriding each scene's own. That covers the whole of what a range is — the first and last frame, the step, or a list given in place of them (see [The frame range](#the-frame-range)).

**No other typed value is imposed across a ticked set, and the range is the exception for a reason.** A first, last and step are frame numbers, and a frame number means the same thing in every scene, so one range can be stated once and imposed on all of them. Everything else on the page describes how a single scene is rendered and is shown as the value read from the scene in hand; with more than one ticked there is no one scene to read from, and Smoozy does not put a number on the page for scenes the user has not looked at.

**An imposed range applies by frame number**, with no adjustment for where each scene's own range sat. A scene whose own range is 100–200, rendered inside a set with an imposed range of 1–10, renders frames 1 to 10. What those frames hold is the file's business; Smoozy imposes the numbers and nothing else.

**The frame count reads for the group.** With more than one scene ticked, the count beside the range is what the whole set comes to: left alone, each ticked scene's own range added up; typed into, the typed range once for every ticked scene.

**Handing everything back at once, with more than one scene ticked**, clears the range so every scene uses its own again and returns the Blender version to the automatic match. The greyed settings have nothing to hand back, never having been typed into, ~~and the scenes ticked are not touched — that control returns settings to the file's values, it does not change what the user asked to render~~ and the ticked scenes go back to the one the file was saved showing. *Changed 2026-10-08, the Creator's fifth notes, note 4 (above).*

**Either way, what reaches the queue is single-scene jobs.** Ticking several scenes does not produce one job spanning them; it submits one job per scene, each carrying its own scene's settings, shown together as a group. That is settled in the [Queue & History spec](Queue%20&%20History.md), which owns what happens to those jobs from submission onwards.

**A page opened from a history entry arrives carrying that job's scene, read or no read.** The scene the old job ran is the user's own answer rather than a value taken from the file, so it comes across with the rest of the setup and stays — the same way a ticked scene survives a reconnect, and for the same reason. It shows before the file has been read on this machine, and a job submitted at that point carries that scene name rather than none. What the read still owes is the rest: until it runs there is no list of the file's scenes, so there is nothing else to tick, and nothing here says whether the file on this machine still holds a scene of that name. Nothing checks that for the user. Where the file on this machine holds no scene of that name, the job fails when it starts and says why, and the user reads the file to pick a scene. Label: **Creator-stated** (2026-08-20).

**A submission of several scenes can be cut in half by a dropped connection**, some scenes sent and some not. What happens then belongs to **Rendering**, which owns submitting: whatever reached the machine stays, Smoozy says which scenes went and which did not, and offers to submit the remaining ones as a single action — see the [Rendering spec](Rendering.md).

## A scene that pulls in another scene

Scenes mostly stand on their own (see the [Glossary](../Groundwork/Glossary.md)), but not always: **one scene can be set up to take in another scene's rendered result.** Rendering the first then renders the second as well. There are two ways to set it up — through the compositor, and through the video sequencer — and a render started from outside honours both. Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine), see [Sources](Sources/Render%20Settings.sources.md).

That breaks two things the user would otherwise reasonably assume, so Smoozy states both before the job goes rather than leaving the user to work it out afterwards.

**A single-scene job can be much bigger than the scene it names.** The user ticked one scene and is paying for two. Nothing about the job is wrong — it is still one job, one scene, exactly as [Queue & History](Queue%20&%20History.md) has it — but its cost and its time are not what the scene alone suggests.

**Where both scenes are ticked, the same scene renders twice.** Once as its own job in the group, and again inside the job of the scene that pulls it in. The same frames, twice, on a machine billed by the hour, for one set of results.

**The pulled-in scene renders at its own engine and its own sample count**, not the ones on this page. What the user settles here describes the scene they ticked; the scene it pulls in renders as the file has it. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine).

**Smoozy says so and does nothing clever.** Pre-load reads every scene in the file, so it can see the connection; where it finds one, the user is told which scene pulls in which, and told about the doubling where both scenes are ticked. Smoozy does not rearrange the jobs, drop the duplicate, or try to share one render between two jobs. Label: **Creator-stated** (2026-07-27).

**Nothing is known about this before the file is read**, like every other fact about a file's insides. A job submitted without pre-loading carries the cost without the warning.

**A second case sits underneath this one, and it is settled.** Whether the pulled-in scene's own compositor also runs and writes files of its own depends on which of the two routes was used: through the compositor it does not run at all, and through the video sequencer it does, and its own outputs land inside this job's folder. Either way the job's file count already takes them in. That is [What a job writes](What%20a%20job%20writes.md)'s, which owns it.

## The frame range

The range opens at the file's own, exactly like every other setting, and clearing it goes back to that.

**A file's range can start at any frame number.** Not necessarily 1 — it may be 10, or 0, or a negative number, all of which Blender allows. Nothing in Smoozy assumes the first frame is frame 1, and the view layer behaviour below depends on this being right. Label: **Creator-stated** (2026-07-27) — a Blender fact from the Creator, see [Sources](Sources/Render%20Settings.sources.md).

**A range of one frame is an ordinary range**, not a separate kind of thing. Everything below reads the same whether the range covers one frame or four hundred.

**A range is three numbers, not two.** Alongside the first and last frame, a file carries a **step** — how many frames to move on by each time. A step of two renders every second frame of the range, a step of three every third. It opens at the file's own like everything else, and a file that renders every frame simply carries a step of one. Label: **documented** (Blender 4.5, 5.0, 5.1 and 5.2) — a range is a first frame, a last frame and a step, in every version, see [Sources](Sources/Render%20Settings.sources.md).

**The step counts forward from the first frame**, so the first frame always renders and the last one renders only if the step lands on it. A range of 10–50 with a step of two covers 10, 12, 14 and so on up to 50; the same range with a step of three stops at 49 and never renders 50. Nothing is added to make it land, and nothing warns that it did not — the count below is what shows the user what they actually asked for. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine).

The step is why Smoozy offers no separate way to say *odd*, *even* or *every third*: each of those is a step, and giving them their own words would add a second way to state one thing. Which frames a step lands on depends on the first frame as well, so odd or even is a first frame and a step together — a step of two from frame 10 gives even frames, and the same step from frame 11 gives odd ones.

**The user can also give a list of frames instead.** Some work needs particular frames rather than a run of them — a handful to check, or two stretches with a gap between. So the range can be replaced by a written list: single frames, runs, or a mix of the two, such as `1, 3, 7` or `1-10, 22-25`. A list is an alternative to the first, last and step, not an addition to them: using one replaces the other, so there is only ever one answer to what the job covers. Label: **Creator-stated** (2026-07-27).

**Blender can be asked for such a list.** Single frames, a run, and both mixed in one instruction all work, and a step has nothing to act on in a list. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine), see [Sources](Sources/Render%20Settings.sources.md).

**What a list means.** A run inside a list counts upward from its first frame to its last, like any run. A frame named twice, and two runs that overlap, are the same frames named more than once: every frame the list covers is rendered once, however many times it is named. The order the entries are written in decides nothing.

**That is Smoozy's rule, and Blender does not follow it on its own.** Handed a list as the user wrote it, Blender renders the frames in the order they were written rather than in numerical order, and a frame named twice is rendered a second time over the same file. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine). So the promise above holds only if Smoozy tidies the list — dropping repeats and putting the frames in order — before the render is started. That it does so is settled here; how is Architecture's.

**What is not a range at all.** A last frame before the first, a step of zero, an empty list, a stray character — none of these can be read as frames, so none of them is accepted. **Nor is a range or list covering more than a million frames**: Smoozy cannot build one that big, and a million frames is over eleven hours of finished film at twenty-four a second, so no real job asks for it. Smoozy says so where the user typed it, the setting stays on its last good value or on the file's, and nothing unreadable ever reaches a submission. How that reads on the page is Design's.

**A job whose file writes a video takes one unbroken run of frames.** A video holds frames one after another and cannot skip any, so where the scene's regular output is a video, ~~a list with gaps, or a step other than one,~~ **a list with gaps** is refused where the user typed it, the way any range that cannot be used is, with one line saying why: *A video can't skip frames. Type one unbroken range.* A list that comes to one unbroken run — `1-10, 11-20` — is that run and is accepted. **A step is not a gap and is kept**: a video job renders every step-th frame of its run, as Blender itself would, whether the step is the file's own or typed. *(Corrected the same day, 2026-10-17, after a second controlled test showed the step can be handed to Blender as asked — `Audits/Build/Step 10c/A second desk test — the step on a video and frames below zero.md`.)* **The ground is observed**: started with a list of frames, Blender leaves a video holding one frame; started with a first and last frame, a video holding exactly those frames. Label: **observed** (a controlled test, Blender 4.5, 5.0, 5.1, 5.2 and 5.3 beta, on a Mac, 2026-10-17 — `Audits/Build/Step 10c/V1's desk test — how a video is written whole.md`). The rule itself is the build runner's, 2026-10-17, under the Creator's standing delegation, on the Creator's eleventh notes, note 1. *No auditor has seen it.*

**Smoozy shows how many frames the job covers.** Whatever the user typed — a run, a run with a step, or a list — a count sits beside it saying how many frames that comes to. A step or a list makes the count much harder to do in the head than a plain run does, and it is the fastest way to catch a range that says something other than what was meant. Label: **Creator-stated** (2026-07-27).

**The count describes how much gets rendered, not how many files come back.** A frame can write several files or none at all, so a job's file count is worked out frame by frame from every destination that writes, never by multiplying the frames by anything. That count comes from reading the file, and what it is made of is settled in [What a job writes](What%20a%20job%20writes.md), which is where **Download** takes it from.

**None of this changes what the view layer boxes read from.** They show the **lowest** frame the job covers — the first frame of the run, or the lowest frame the list covers wherever in the list it was written, whatever the step is (see [View layers](#view-layers)).

**Frames are scene-local**, so a range only means anything alongside the scene it belongs to (see the [Glossary](../Groundwork/Glossary.md)). That is why every job carries exactly one scene. What a re-run treats as already there is settled by [What a job writes](What%20a%20job%20writes.md) and [Queue & History](Queue%20&%20History.md), which own it between them.

## View layers

A view layer is a slice of a scene that renders on its own, and **whether it renders can change from frame to frame** (see the [Glossary](../Groundwork/Glossary.md)). That makes this the one setting where what the user is shown and what the job does are not the same thing, so both are stated exactly.

**Each view layer is a checkbox, and the boxes only exist once the file has been read.**

**An untouched box is a look at one frame, not an instruction.** It shows whether that view layer renders on the **lowest frame the current range covers** — nothing more. Left untouched, the view layer renders across the job exactly as the file has it. That may be the same on every frame, and often is; where it does change from frame to frame, the box is showing one frame's worth of an answer that varies.

**Untouched boxes follow the range as the user types it.** Change the range and every untouched box redraws at once for the lowest frame it now covers, without waiting for anything — **with one exception**. Where the switch follows a driver rather than a keyframe, there are no keyframes for a read to reason from, and what the read brings back covers the file's own frame range and no further; type a range reaching outside that, and such a box says nothing is known there until the file is read again, rather than redrawing at once. Nothing on this page stops the user typing such a range, so the case is a real one rather than a corner.

**That rests on one read of the file answering the question for any frame later asked about, and it holds where the switch is keyframed.** It is a bigger claim than knowing which view layers a file holds, and the whole of the paragraph above depends on it: without it, a box could only be drawn for the frames already looked at. The switch that decides whether a view layer renders takes a keyframe, the animation curve that results sits on the scene and can be read out, and a render started from outside honours it frame by frame. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine), see [Sources](Sources/Render%20Settings.sources.md).

Two version differences sit behind that and neither reaches this page. The route to the animation curve is not the same in 4.5 as in 5.0, 5.1 and 5.2, which is Architecture's to deal with. And the switch's stated starting value differs — off in 4.5, on in 5.0, 5.1 and 5.2 — while in every version's tests a file's own view layers rendered without anyone turning them on.

**Two other ways the switch can be driven are not covered.** It can be made to follow a driver rather than a keyframe, and a script inside the file could change it as each frame comes round. **One shape of each has since been tried, in two versions, and the read and the render agreed both times.** Label: **settled at Architecture** (2026-08-23). What that does not cover is every other shape either can take — a driver written as a small piece of Python rather than a plain sum, and stored scripts shaped differently from the one tried — and for those it is still **unresolved**. It is a named and bounded question rather than an open one: it is **Fact 113** in the project's fact register (Row 148), and what is left of it closes at Architecture rather than here. Neither the ruling of 2026-08-31 against further Blender research nor the one against further rentals reaches it — answering it needs no rented machine and no graphics card, only a computer carrying two supported Blender versions and a file of each shape. See [Sources](Sources/Render%20Settings.sources.md). **What breaks meanwhile:** such a file would meet boxes drawn from a reading that does not describe it, so a negative answer is a hole here rather than a thinness.

**Touching a box turns it into an instruction, and the instruction covers the whole range.** A view layer the user checks renders on **every** frame of the range, whatever the file says. A view layer the user unchecks renders on **none** of them. Either way that view layer stops following the file and stops reacting to the range changing. Clearing it, as any setting can be cleared, hands it back to the file.

Label: **Creator-stated** (2026-07-27).

Take a file whose own range is 10–50, holding view layers A, B and C. A renders on every frame, B only on frames 10 to 20, C nowhere at all.

- **Nothing touched.** The boxes read from frame 10: A on, B on, C off. The job renders A across the whole range, B on frames 10 to 20 only, C never. B's box says on while B renders for about a quarter of the job — that is the model working, not a fault.
- **Range changed to 30–50.** The boxes redraw for frame 30: A on, B off, C off. Nothing is pinned, so B simply renders nowhere in this range.
- **Range changed to 15–15.** The boxes read from frame 15: A on, B on. Both render on that single frame.
- **Range replaced by the list `40, 22-25`.** The boxes read from the lowest frame the list covers, which is 22 rather than the 40 written first: A on, B off, C off. The job renders A on frames 22, 23, 24, 25 and 40.
- **C checked, range 10–50.** C is now pinned and renders on all 41 frames, though the file never renders it anywhere. A and B are untouched and still follow the file. Change the range to 30–50 and A and B redraw for frame 30 while C does not move.
- **A unchecked.** A renders nowhere, whatever the range is set to afterwards. B and C carry on following the file.
- **B clicked off and on again.** The box looks exactly as it did, but B is pinned on now, so it renders across all of 10–50 instead of only 10 to 20. The same picture means a different job — which is why the difference between a pinned box and an untouched one has to be visible. That is Design's.

**Boxes all reading off are not proof that a job renders nothing**, and that is about files in general rather than the one above, whose A renders on every frame. In another file a view layer can switch on later in the range than the frame the boxes read from — a range starting at 30, a view layer that comes on at frame 40 — and the job renders it even though its box read off. A job producing nothing is a real thing all the same (see the [Queue & History spec](Queue%20&%20History.md)); empty boxes are not proof of it either way.

## Samples

**Smoozy shows one sample count for the whole job**, and it opens at the file's own. There is no per-view-layer control here. Label: **Creator-stated** (2026-07-27).

Everything in this section is written for Cycles. Which of it applies at all depends on the engine chosen, and that is set out under [The render engine](#the-render-engine).

**A view layer can carry its own sample count, different from the scene's.** So the one number Smoozy shows can be true of most of a job and wrong about part of it. Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2), see [Sources](Sources/Render%20Settings.sources.md). Which engine obeys that override depends on the version, and is set out under [The render engine](#the-render-engine).

**Where any view layer overrides it, Smoozy says so.** The user is told that at least one view layer renders at its own count rather than the one on screen. Smoozy knows this only after the file has been read, so the warning appears with everything else pre-load fills in.

**Typing a number sets everything.** A sample count the user types applies to the whole job, per-view-layer overrides included. That is the point of typing it: the user is stating what they want rendered at, not adjusting a scene value and leaving the exceptions in place.

**A typed number is the count, not a ceiling.** A file can be set up so the number in it is not what actually gets rendered — the render can stop early once the picture is clean enough, and it can be told to stop after a length of time instead of after a count at all. Left alone, all of that stands, and the file behaves exactly as the artist set it up. **Typed into, none of it does:** the job renders the number the user typed, and anything that would have cut it short is set aside. That last part is under Cycles; under EEVEE there is nothing to set aside, which is set out under [The render engine](#the-render-engine). Label: **Creator-stated** (2026-07-27) as to what Smoozy does.

**Under EEVEE the typed number is a floor as much as a target, and that is left as it is.** Two of EEVEE's own features raise a count above what they are given: motion blur rounds it up to a multiple of its own steps — 64 came back as 65 — and jittered depth of field raises it to fit a pattern, where 16 came back as 19. Label: **observed** (all four versions) — see [Sources](Sources/Render%20Settings.sources.md). Neither is a setting Smoozy offers or touches, and the file renders as the artist saved it. **The promise above is not narrowed for it, on the Creator's ruling of 2026-08-12**: the gap is one sample or three, nothing the user sees changes, and the number Smoozy states is still the number the render is given. It is written down here so that nobody meeting a finished EEVEE job reporting 65 against a typed 64 reads it as a fault. Label: **Creator-stated** (2026-08-12).

That is the same principle as the paragraph above, carried through: a typed number is a statement about what to render, and Smoozy does not leave exceptions to it standing.

**None of that follows from the number.** Handing a render a count from outside changes the number and nothing else: the frame still stops early once its pixels are clean, a time limit still ends it wherever the count has got to, and a view layer's own count still stands in place of the one handed in. Which of those two counts wins is a scene setting of its own, with three answers — use the view layer's, cap it by the count handed in, or throw it away — and it starts on the first. So the two paragraphs above are things Smoozy switches off as it states the count, not consequences of stating it. **These three are not everything that can displace a count handed in**, so nothing here is a list of what has to be switched off. What Smoozy promises is unchanged; how it is done is Architecture's. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine, every render on the processor), see [Sources](Sources/Render%20Settings.sources.md).

**Both of those Blender behaviours are real, and one of them is on unless somebody turned it off.** Stopping early once the picture is clean is on in every version's starting state, so a great many files carry it; stopping after a length of time is off unless somebody turned it on. Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine), see [Sources](Sources/Render%20Settings.sources.md).

**It can cost more, and Smoozy says so.** A file that would have stopped part-way through now runs to the end, so the job may take longer and cost more on a machine billed by the hour than the file's own setup would have. Label: **Creator-stated** (2026-07-27).

**A time limit is spent on each frame, not on the whole job**, and a frame cut short is still written — so a file carrying one is not capped at that length overall, and a long animation costs the limit many times over. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine). Every one of those runs rendered on the processor, and whether a time limit is counted the same way on the graphics cards was tried in no version — which matters here, because Smoozy renders on machines rented for their cards. **That half is permanently unresolved**, and the marker it carried is cleared on 2026-09-02. Answering it needs a rented machine with a graphics card in it, and the Creator ruled on 2026-08-31 that there will be no further rental. There is nothing on the research side to carry across either: the project's own comparison of the four versions already lists *whether the time limit is counted the same way on a graphics card* among the things it did not establish. See [Sources](Sources/Render%20Settings.sources.md). **What breaks:** if the cards count the limit across the whole job instead, then the sentence above is wrong on exactly the machines Smoozy rents, and the page tells the user a false thing about what a job will cost. The user is told to expect the limit once per frame and to budget a long animation at the limit many times over; the render would instead stop after one limit's worth in all, and fewer frames would come back than were paid for, with nothing saying why.

**When that is said depends on whether the file has been read.** Whether a typed number sets anything aside is a fact about the file, so only a read can tell Smoozy there is a cost to warn about at all. Where the file has been read and shows an early-stop or time-stop setup, the warning appears as the number is typed. Where it has not been read, Smoozy says the same thing it says everywhere else on this page: nothing is known about the file's insides yet, so a typed count may be setting aside a setup Smoozy cannot see, and reading the file is what would show it.

**Smoozy says what the file was going to do.** Once the file has been read, its early-stop or time-stop setup is shown on the page whether or not the user touches the samples box — whether a file stops itself short changes what a job costs on a machine billed by the hour, and a user who leaves the box alone may still want to know. Where the user is considering typing a number, it is also what shows them what they would be replacing. Before the file is read there is nothing to show.

**The override warning goes when there is nothing left for it to be true about.** This is the first of the two warnings above — the one about a view layer using its own count, not the one about cost. It is only worth saying while it is true of the job in hand, so it disappears in each of the three ways that can happen:

- The user unchecks the overriding view layer, so it renders nowhere.
- The user sets a range in which that view layer never renders.
- The user types a sample count, which sets every per-view-layer count aside, so nothing renders at its own count any more. Hand the count back to the file and the warning returns.

If more than one view layer overrides, the warning stands until none of the ones still rendering does.

Label: **Creator-stated** (2026-07-27).

## Resolution percentage

**The file carries a percentage of the scene's full resolution, and the setting opens at that percentage.** What the job renders at, in pixels, is that percentage of the scene's full size — so typing 50 means half the scene's full width and height, whatever the file's own percentage was. Label: **Creator-stated** (date unrecorded) — recorded in the [Product brief](Product%20brief.md). The Creator ruled on 2026-07-30 that *what the percentage means* is settled and was deliberately not researched.

**The setting takes whole numbers from 1 to 32767, and a render bigger than the file asks for is possible.** That is the whole range, and Blender reports a second and narrower pair, 1 to 100, that governs dragging alone — so a value above 100 is one the user types rather than drags. **What a slider actually does when dragged, and what the field does when an out-of-range number is typed into it, were tried in no version**: both need somebody at a window and nobody had one this round. There is no zero, no negative number and no fraction — a decimal is refused outright rather than rounded. Blender reports the value as not animatable, and no version was tried with a driver on it. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Render%20Settings.sources.md). So the one handle this page gives on how big a render comes out really does reach upwards, which is what the section was waiting to know.

**Smoozy's own box takes exactly that and nothing else, and that is a decision rather than a reading.** A number outside the range is not refused by Blender — it is **silently pulled to the nearest allowed one**, with nothing printed on the terminal and a successful ending — whether anything appears inside Blender's own window was tried in no version, so a job asked for at 40000 per cent quietly renders at 32767 and a job asked for at 0 quietly renders at 1. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Render%20Settings.sources.md). Neither the ending status nor anything printed says the number it sent was not the number used — the correction was only ever caught by measuring the written picture — and the user pays for the wrong size. So Smoozy holds the box to whole numbers from 1 to 32767 and says so where the user types something else, rather than passing a value on to be silently changed. Label: **the decision is Smoozy's**, taken on the strength of that finding. This is Smoozy doing what it says it will do, not checking the user's judgment: what size to render at stays entirely theirs.

**A percentage inside the range can still ask for a render that cannot be made, and that one does refuse.** Where the percentage works out to less than a pixel, the render stops with a complaint and writes nothing at all. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Render%20Settings.sources.md). It is a real failure and it reaches the user the way every render failure does, through [Queue & History](Queue%20&%20History.md) and the whole-app rules in [Whole app](Whole%20app.md).

**And a percentage inside the range can ask for a render nobody would want, with nothing said at all.** A very large number is neither refused nor warned about: the render simply starts, at a size that may take a machine days. Label: **observed** (the same in all four versions, on both machines). Smoozy does not stop it and does not lecture about it — sizing a render is the user's own judgment, and this page's job is to pass on what they asked for.

**So the page shows the size the percentage works out to, in pixels, beside the box.** A percentage on its own says nothing about how big the picture will be, and this is the only handle the page gives on it — a user typing 400 should be able to read the width and height that follows without working it out. Label: **Creator-stated** (2026-08-12).

**It is a reading, not a setting.** The pixel figure cannot be typed into, dragged, or overridden: the percentage is the setting and the pixels follow from it, so the figure moves as the user changes the percentage and never the other way about. Smoozy offers no way to ask for a render by its width and height. Label: **Creator-stated** (2026-08-12).

**It needs the file to have been read, and says nothing where it has not.** The scene's full size in pixels sits inside the `.blend`, so without **Pre-load Settings** there is no number to take a percentage of. The page then shows the percentage alone and states plainly that the size in pixels is not known rather than showing a blank or a guess — the same shape every other unread value takes on this page. This is also why the figure appears at all only for the scene that was read.

What the job actually renders at — in pixels as well as the percentage — is carried on the job's queue entry too, which the [Queue & History spec](Queue%20&%20History.md) owns. That is the same figure at a later moment: this page shows it while the user is choosing, the entry keeps it after the job is fixed.

## The render engine

The user can set the engine, and it opens at the file's own. **The page offers Cycles and EEVEE.** That those two are Blender's own is recorded in the [Product brief](Product%20brief.md). Label: **Creator-stated** (date unrecorded) — and ruled on 2026-07-30 to be settled and deliberately not researched. That the page offers those two and no more is Smoozy's own decision, and the Creator's (2026-08-06).

**Blender's own list is longer than that, and it can grow.** What a file may name is decided by what is registered in the Blender that is running: three engines come built in, and more arrive as add-ons. Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on two rented Linux machines), see [Sources](Sources/Render%20Settings.sources.md). Two things follow, and the Creator ruled on both (2026-08-06).

- **The third built-in engine is not offered.** Nobody would use it for an actual render, so this page leaves it out and the choice stays Cycles and EEVEE.
- **A file can name an engine this page does not offer** — that third one, or one an add-on brought. Smoozy does not pretend otherwise: it names the engine the file carries and offers Cycles and EEVEE beside it, refusing neither the file nor the choice. Leaving the setting alone means the render uses what the file named; picking one of the two is an override like any other. How that reads on the page is Design's.

**A file's engine does not necessarily survive the render, and nothing about the job says so.** Where the Blender that renders does not have that engine, the render is not refused: Blender says the engine is not available, falls back to EEVEE, renders at EEVEE's own sample count instead of the file's, writes the image, and finishes cleanly. Worse for this page, a read of the file taken by that same Blender reports EEVEE as the file's engine, so Smoozy never learns what the file actually said. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine) — with the Cycles add-on switched off, which is the case that was tested; a missing add-on engine could not be tried. See [Sources](Sources/Render%20Settings.sources.md).

**So the engine and the sample count on this page describe the file as the chosen Blender read it, not what the render will do.** Smoozy promises no more than that, and must not: a job can finish with an image, at a sample count nobody asked for, on an engine nobody chose, and none of it looks like a failure.

**Whether Smoozy can catch that afterwards is now answered, and the answer is yes by two routes.** From **Blender 5.0 on a render names its engine in what it prints**, on an ordinary run with no switches asked for; Blender 4.5 has no such line at any setting. **That line is not there by every route**: whether a running render prints anything at all depends on how the render was started, so the printed route holds only where the render is started the way that prints. Label: **observed** — the fact is the [Rendering spec](Rendering.md)'s, which owns starting a render and what a running render prints. And in **every version a finished Cycles picture carries four fields of Cycles' own inside it** that an EEVEE picture of the same frame does not — so the engine that produced a render can be read out of the file afterwards, in all four versions. Label: **observed; the printed line differs by version, the fields do not** — see [Sources](Sources/Render%20Settings.sources.md). **The fields can only be read once the render is over, and when the printed line appears is not established**, so neither route can be counted on before the render ends — which is the limit that matters: by then the machine has been paid for. What Smoozy does with either belongs to **Rendering** and [Queue & History](Queue%20&%20History.md), which own what a running job says and what a finished entry shows.

**EEVEE does not answer to the same name in every version, and which name is taken depends on which of the two routes states it.** Blender 4.5 knows it by one name and 5.0, 5.1 and 5.2 by another. **The name a version knows as its own works by either route.** The other version's name does not: stated directly at the start of a render, the newer three do take 4.5's name, but set by an instruction handed to Blender they refuse it outright. Given the newer name, 4.5 refuses it by either route — stated at the start of a render it reports an error, writes nothing, and then ends badly, hanging on the rented Linux machines and crashing out on the Mac. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on two rented Linux machines; the newer three taking 4.5's name was seen on one rented Linux machine only). Nothing the user does here depends on it, but whatever starts the render has to use the name the chosen version knows, which is **Rendering**'s and Architecture's.

**Changing the engine can change what comes out, so it is a deliberate act.** A scene built for one engine does not simply come out the same in the other. Label: **documented** (Blender 4.5, 5.0, 5.1 and 5.2) — see [Sources](Sources/Render%20Settings.sources.md). Smoozy therefore never offers the choice as a way to save time or money, and it does not tell the user why they might want it — that is theirs.

**The engine decides what some of the other settings on this page mean.** A file carries its own settings for each engine, so the settings below follow whichever engine is chosen rather than sitting above the choice. Label: **Creator-stated** (2026-07-27) as to what Smoozy does; each Blender behaviour underneath carries its own label.

- **Samples.** A file holds a count for each engine, and holds all of them at once, so the number shown is the chosen engine's wherever the user has not typed one. **A count the user typed stays typed across an engine change** and applies to the new engine, like any other typed value; handing it back is how the user gets the new engine's own count. Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine).
- **The two things that can cut a render short** — stopping early once the picture is clean, and stopping after a length of time — belong to Cycles alone; EEVEE has neither. So under EEVEE the typed-number rule above has nothing to set aside, and nothing to warn about. Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine).
- **A view layer carrying its own sample count is not Cycles alone.** The override is one value on the view layer, and which engine obeys it depends on the version: Cycles obeys it in all four, EEVEE ignores it in 4.5 and obeys it in 5.0, 5.1 and 5.2. Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine). So the samples warning does arise under EEVEE wherever the job renders with 5.0 or later, and does not under EEVEE with 4.5.

**EEVEE renders on a rented machine with no display attached.** On a Linux machine with no display server at all, every engine each version has rendered — on the graphics cards and on the processor alike, EEVEE included — and finished cleanly. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a rented Linux machine with no display server), see [Sources](Sources/Render%20Settings.sources.md). So the choice stays. Three cases were never reached — Windows, a machine with no graphics hardware at all, and a Mac with no display server — and none of them is Smoozy's, which renders on rented Linux machines.

## What the render runs on

A scene carries whether its render uses the machine's **GPUs** or its **processor**. That setting is on this page like the others, opening at the scene's own value. It is Cycles' setting: EEVEE has nothing to choose, because it only renders on the graphics cards. Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on rented Linux machines), see [Sources](Sources/Render%20Settings.sources.md).

**A fresh scene starts at the processor**, so a scene saying processor may be saying it only because nobody ever changed it. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2).

**It is on the page because the user has to be able to see it.** A machine is rented for its GPUs, and a file saved elsewhere may well say processor — in which case the user pays by the hour for a machine whose cards are not being used. Leaving that setting invisible would let that happen without the user knowing.

**Choosing the processor is a real choice, not always a mistake.** Some work genuinely needs it, so Smoozy does not refuse it or quietly change it. Label: **Creator-stated** (2026-07-27).

**Where the scene says processor on a machine that has GPUs, Smoozy says so.** It states what will happen and leaves the choice alone — the user either meant it or did not, and only they know which. This is the same shape as everything else here: say what is true, do not decide for the artist.

**Where a Cycles job on the GPUs cannot render on this server's driver, from Blender 5.3, Smoozy says that too.** Below the driver 5.3 asks for, Cycles cannot use the cards at all. It is one line, and it stops nothing: the user may still send the job. EEVEE and the processor are not told, because both render there. On a server where Smoozy can replace the driver nothing is said here, because the job waits for the replacement instead (see the [Queue & History spec](Queue%20&%20History.md)). Label: **observed** (the 5.3.0 Beta, one driver below the bar, on one rented machine, 2026-11-02), the line the build runner's ruling of that day. *No auditor has seen this.*

**What that warning can say is bounded by two things, and both are now known.** A render started from outside can override the scene's own choice, so what this page shows is not necessarily what the render does. And a scene asking for the graphics cards is no promise that it gets them: on a rented Linux machine left as it comes, every card is switched on but no card technology is chosen, and a scene asking for the cards then renders on the processor with Blender saying nothing at all about it. Label: **observed** (Blender 4.5, 5.0, 5.1 and 5.2) — the override on a Mac and on a rented Linux machine, and the machine left as it comes on one rented Linux machine. So the warning can state the setting and what it means, and cannot promise the outcome.

**And the two are not interchangeable: the same file rendered on the cards and on the processor does not come out the same picture.** More than half the colour values differed, in all four versions, on an NVIDIA card through both of its technologies and on Apple's own graphics — and the two card technologies disagreed with each other as well. The control is what makes it mean something: each device repeats its own render to within about a millionth, which is tens of thousands of times smaller than the gap between devices. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Render%20Settings.sources.md).

**How much of that difference could ever be seen was not settled.** It was measured on a picture written at full precision, where the average difference came to about a twenty-fifth of one step of an ordinary eight-bit picture — too small to show in such a picture at all — while the largest single difference would show. Another of the research's own comparisons, on a small scene written to an ordinary eight-bit format, found the processor's render and the card's identical, and nobody has run both comparisons on one scene. Label: **observed** — the measurement sits under the same finding, the eight-bit comparison under another topic. See [Sources](Sources/Render%20Settings.sources.md).

**That stance was put back to the Creator on 2026-08-12 with the measurement above beside it, and it stands exactly as written.** Label: **Creator-stated** (2026-08-12).

**So this setting is a choice about the picture and not only about the speed, and the page treats it as one.** Nothing here presents it as a way to make a job cheaper, and Smoozy never suggests changing it. Where the note above tells the user their scene says processor on a machine with cards, it says what will happen and stops there; it does not imply the cards would give them the same render sooner, because they would not. What was measured is each device against its own machine's processor, and the two card technologies against each other on one card. **Whether two makes of card give each other's picture was never compared**, and whether a picture is reproducible across machines at all is on the research's own not-settled list — so Smoozy promises nothing about a job submitted again on a different machine coming out the same, and says nothing about it either.

**Making the machine's GPUs available to a render is not this module's**, and no user setting reaches it. Whatever makes that true belongs to **Rendering** — see [Open Threads](../Groundwork/Open%20Threads.md). This page only carries the scene's own choice between the two.

**What a render runs on is settled; how each side of it is reached is not, and is not a Blender fact.** Imposing the scene's own setting on a render, and making the machine's cards available, are both matters of how Smoozy is built. **Both now have a way chosen.** The scene's own choice is imposed as the render is started, without the file being altered, and the machine's cards are made available by that same start — which technology to name is worked out from what the cards actually are. **What is settled is which way to do it, and not that the way works.** Handing the scene's own device setting over in the material given to Blender as a render starts is not one of the ways Blender is known to take that setting, and no run has yet imposed it that way and then read back which of the two the render actually used. If it does not take, the failure is the quiet one: a user who asked for the processor gets a render on the cards, and the job finishes with nothing said. Label: **settled at Architecture** (2026-08-23) **for the choice of route; that the route works is unobserved.**

## What is deliberately not offered for making a render cheaper

The page carries three things that change what a job costs — the sample count, the resolution percentage, and the choice between the cards and the processor. Blender has many more, and the research went looking for them, though no version's own list of them claims to be complete. **None of the rest is offered, and that is a decision rather than an oversight.**

**Some of Blender's cost settings were measured and most were not, and the difference matters.** **Nine of them were compared and left the picture untouched pixel for pixel** — the thread count, the tile size, whether tiling is used at all, three settings governing how a scene is prepared for tracing and the number of time steps used for it, keeping a scene's prepared data between frames, and high-quality normals. Eleven comparisons in all, since two of the nine were tried at two values each. Each was set against an unchanged render of the same scene, in all four versions, on both machines, with two controls that did move the picture to show the comparison could see a change at all. Label: **observed** (the same in all four versions, on both machines; **on one small scene rendered on the processor, at the two values named and no others**) — see [Sources](Sources/Render%20Settings.sources.md). **A much larger group was never compared at all** — Blender's own documentation says they change the picture and no test looked. And no version's own list of these settings claims to be complete.

**Those nine are not offered because there is nothing in them for an artist.** They change how long a render takes and how much memory it wants, and nothing the user would look at. Smoozy has no basis for choosing a value for any of them — the right tile size depends on the machine and the scene, and guessing on the artist's behalf is exactly what this page is written not to do. Leaving them alone means a job renders the way the file was set up, which is the page's whole shape. Label: **the decision is Smoozy's**.

**The other group does change the picture, and it is the one worth the Creator's attention.** Blender carries a group of settings that cut what a scene loads rather than shrinking what it produces — capping how finely surfaces are subdivided, how many child particles are grown, and **how large a texture is allowed to be**. Blender's own documentation groups them among the settings that affect render speed and memory, and describes each as changing the picture. Label: **documented**. What was **observed** is narrower and is worth keeping apart: switching the group's render column on gave Cycles, EEVEE and Workbench each a different picture, and two of its settings were read back out of a file unchanged. **Imposing them on a render started from outside is observed for two and inferred for the rest.** Switching the group on, and setting the subdivision cap, were both applied by an instruction handed to Blender as the render started, and the picture changed — all four versions, both machines. The texture cap was written into a file and read back at the value set, in all four versions on both machines, and never imposed at the start of a render with the result looked at; the child-particle cap was neither imposed nor read back. Label: **observed** for the switch and the subdivision cap, **inferred** for the others. See [Sources](Sources/Render%20Settings.sources.md). *(This corrects what this section said before 2026-08-12 — that the lever was watched working for a sample count and for none of these, which walked past its own topic's hand test.)*

**How much they save is Blender's own description and the Creator's own experience, and no test has measured it.** No run in the research timed a render with them on against one with them off, or measured what either took in memory. Label: **documented; Creator-stated** (2026-08-12) **for the saving; unmeasured by this project**. *(This settles a disagreement inside this document: the sentence here used to say no Creator statement about it was on record, while this page's own [Sources](Sources/Render%20Settings.sources.md) file said the opposite. The Creator confirmed it on 2026-08-12, and the sources file was right.)*

**They are not on this page, and that is now a settled decision rather than a wait.** The Creator ruled on 2026-08-12 that they are not offered at the ordinary settings: Smoozy is a render farm, the file is the artist's to prepare in advance, and offering to cut somebody's scene down every time they submit is holding their hand at the one moment they have not asked for it. Label: **Creator-stated** (2026-08-12).

**Where they are offered instead is a job that has already failed**, under Blender's own name for them, Simplify. That belongs to [Rendering](Rendering.md), which owns the offer, which three of them it exposes and why the two culling settings and Blender 5.2's own texture-resolution setting are left out. This page keeps none of it and shows none of it.

## Which Blender

Every other setting on this page is about the file. This one is about the machine, and it is the only setting where a wrong choice can stop the job rendering at all.

**The choice is which of the Blenders installed on that server renders the job.** A machine can hold several — different versions, unstable daily builds, self-compiled ones — which is **Server Setup**'s doing.

**It matters more than a version number usually does.** Blender versions differ in what they can do, a feature a file relies on may be missing or behave differently in another version, and some files will not open in some versions at all: every version's manual says a new major version can make a file unreadable by older Blenders, which then refuse it and name the version needed. Label: **documented** (Blender 4.5, 5.0, 5.1 and 5.2), see [Sources](Sources/Render%20Settings.sources.md).

**Smoozy picks the nearest version above the one the file was saved with**, and an exact match wins over everything: a file saved in 5.0 on a machine that holds 5.0 renders with 5.0. Failing that, a file saved in 5.0 on a machine holding 4.5 and 5.2 is set to render with 5.2. Where nothing above exists, the pick falls to the nearest below and says so. The saved-with version is read straight from the file and needs no pre-load, which is why the file browser can already show it (see the [File Browser spec](File%20Browser.md)). Label: **Creator-stated** (2026-07-27).

**That rule is a decision about what to prefer, not a reading of what a mismatch costs.** Going to the nearest version above, and falling back to the nearest below where nothing above exists, is settled and stands as written. Label: **Creator-stated** (2026-07-29).

**One kind of installed Blender the rule cannot place**, handed here by name by the [Server Setup spec](Server%20Setup.md): **a build below 4.5**, which is the whole app's floor (see [Whole app](Whole%20app.md)). It appears in the list and can be picked: Smoozy neither refuses it nor pretends it is supported, which is the same stance Server Setup takes when such a build is installed. It is never the automatic pick, because nothing in Smoozy is written for those versions, and picking one is the user's own decision.

Every installed build has a version number to place it by. A build can be asked what version it is and it answers, which is **Server Setup**'s fact and stated there — so there is no such thing here as a build Smoozy holds no number for.

**Where a machine holds nothing but builds below the floor**, the automatic pick has nothing to land on. Smoozy picks no version and says why, and the user picks one themselves — a job cannot be submitted without a Blender to render it.

**The user can pick any installed version, and Smoozy warns them where the file was saved with a different one.**

**The warning is one small line beside the version choice: it names the two versions and says something may not work as expected. It opens nothing.** Label: **Creator-stated** (2026-10-02), from the Creator's notes on 0.1.7: *"Just a small indication (not a button) that something may not work as expected is enough."* ~~The warning is a small one sitting beside the version choice, and it can be opened for the whole of it — whether it expands in place or opens elsewhere is Design's. What it shows is how *this* mismatch makes *this* job worse, not the general principle that mismatches are risky. Label: **Creator-stated** (2026-08-06).~~ *Struck 2026-10-02 by the ruling above.*

**What it rests on.** Label: **documented** and **observed** (Blender 4.5, 5.0, 5.1 and 5.2, on a Mac and on a rented Linux machine), see [Sources](Sources/Render%20Settings.sources.md).

- **A newer file opened by an older Blender says so and renders anyway.** It reports that the file was written by a newer Blender and that loss of data should be expected, then renders and writes the image. It does not refuse, and the job looks like any other.
- **The other direction is silent.** An older file opened by a newer Blender says nothing at all, so no warning is not the same as no cost.
- **Each version records its own breaks.** **5.0** changed the file format itself, dropped one older class of machine's files, raised the longest name a piece of data may carry so that longer names are cut short when a 5.0 file is opened in 4.5 and cannot be linked there at all, makes data packed into a 5.0 file open in 4.5 as ordinary local data, corrected a material property whose meaning had been inverted so that 5.0 files bake lighting differently in older Blenders, and began honouring view layer overrides so that older files using them render differently. **5.1** requires node tools to carry names unique across the file, set by opening and saving in 5.1, and rebuilt Grease Pencil fills with an automatic conversion some setups need adjusting after. **5.2** converts older Cycles files to a legacy mode so they keep matching, and requires asset files holding geometry-node tools to be re-saved. **4.5** warns about that older class of machine's files and says the support is going.
- **Blender 4.5 opening a 5.2 file also prints a good deal of other noise**, and still renders.

**Two of those are why the line exists.** The corrected material property and the view layer overrides both change what a render comes out looking like while nothing fails. **The line does not name them**, on the Creator's ruling above; it says something may not work as expected, and what that is stays the artist's to judge.

## What comes from the file and is not offered here

Everything Smoozy does not put on this page comes from the file's own settings and is rendered as the artist saved it — the output format, denoising, and anything else the file carries that this page does not offer. The user is not offered them here and this module does not change them. Recorded in the [Product brief](Product%20brief.md). Where the frames are written is the one exception, and the paragraph below says what happens to it.

**Where the outputs land is a different question, and it is not settled here.** It is settled in [What a job writes](What%20a%20job%20writes.md), which owns everything about what a job puts on disk — including that Smoozy redirects every place a file would write so all of it lands under the job's own folder. This spec claims only that the user does not set the output path here. It does not claim Smoozy leaves that path alone; it does not.

**But the user is shown what the file will write, before the job goes.** Once pre-load has run, Smoozy states what the file will write. That statement belongs to [What a job writes](What%20a%20job%20writes.md), which settles what it covers, what it says and how firm each part of it is; this page carries none of that. It appears here because this is where the user is standing when the file gets read. Without a pre-load there is nothing to show, like everything else on this page.

## Submitting

Submitting is **Rendering**'s action, not this module's. What Render Settings hands over is the settled set of settings, and from that moment they are fixed: a job's settings never change after submission, and rendering the same file differently means submitting it again. That is settled in the [Queue & History spec](Queue%20&%20History.md).

**This page is also where a finished job is submitted again.** A history entry keeps the whole setup its job ran with, and submitting it again opens this page with that setup already in place rather than sending the job off as it was — see the [Rendering spec](Rendering.md), which owns that action. Nothing about the model changes: the settings mean what they always mean, the file's own values plus the overrides on top, and those overrides are the ones the job carried instead of ones the user has just typed. They can be changed or handed back like any other. The file itself still has to be read before its own values can be shown, exactly as on any other visit. Label: **Creator-stated** (2026-07-28).

**That needs a connected machine with the file on it — but not the ones the job used.** The setup comes out of Smoozy's own record and outlives the machine; the render does not, so it needs some connected machine and a `.blend` on it. Destroying the machine is the ordinary ending of a job, and an entry with no machine behind it can still be submitted again: the user points the same setup at a `.blend` on another connected machine. That is settled in the [Rendering spec](Rendering.md), which owns the action and what has to be found again, and in the [Queue & History spec](Queue%20&%20History.md), which owns the entry that outlives the machine. Neither is restated here.

**A job can be submitted without the file ever having been pre-loaded.** Nothing forces the user to read the file first. The settings still mean what they always meant — whatever the file says, plus whatever the user typed over — and the file is read when the job starts. Label: **Creator-stated** (2026-07-24).

**The submission says which checks have not run.** A pre-load stands between the user and most of what this page can tell them about the file: the warning that one scene pulls in another and what that doubles, whether any view layer renders at its own sample count, what the file was going to do about stopping a render short, which whether the file names an engine this Blender lacks, everything Smoozy would otherwise state about what the job will write (see [What a job writes](What%20a%20job%20writes.md)), and the list of formats an auto-download can be narrowed to. None of it exists without the read, so submitting without one names what has not been checked and offers to read the file first. The user can go ahead anyway: the read is not forced, and what changes is only that they are told what they are giving up at the moment they give it up. Label: **Creator-stated** (2026-07-29).

One thing follows, and it lands on **Download**. An auto-download arrangement is normally made at the moment of submission, and it can be narrowed to particular output formats — but the list of formats a job will produce comes from reading the file. Submit without pre-loading and there is no list to narrow at that moment, so the arrangement is made across everything the job produces. Narrowing stays available afterwards, from the queue, once the job has started and the file has been read. Forcing a pre-load before submission was considered and rejected; what a user gives up by going ahead without one is named at the submission, as above. See the [Download spec](Download.md).

## When the machine has no Blender

A server that has had no Blender installed can neither read a `.blend` nor render one.

**The settings still open.** The user can look at them and type into them, and nothing pretends the file cannot be worked with. But the file's own values cannot be shown, there are no scenes to choose between, no view layer boxes and no samples warning — pre-load has nothing to run.

**Submitting is not available, and Smoozy says why.** It names the reason — this machine has no Blender — and points at **Server Setup**, rather than leaving a dead control on the screen. So the page does the part it can and states the part it cannot, which is the whole-app rule the [module map](Whole%20app.md) owns.

## What Render Settings does not do

- It does not submit jobs — that is **Rendering**'s.
- It does not choose the file. **File Browser** does, and picking a file does not read it.
- It does not check the file for missing assets, find them, or upload them. That is **Dependency Upload & Remap**'s, and no part of Pre-load Settings.
- It does not install Blender, an add-on, or anything else on the machine — that is **Server Setup**'s. It only picks between the Blenders already there, and says on this page the one add-on case a file announces — an engine the chosen Blender lacks. Smoozy installs no add-ons (2026-10-08). It reads no list of the add-ons a job needs, because a `.blend` holds none.
- It does not connect to a machine. Reading the file needs a connection from **Servers**.
- It does not change the `.blend`. Everything the user sets here belongs to the job, not to the file, and the file on the server is left exactly as it was.
- It does not keep settings between jobs, or remember what the user chose last time. A finished job's entry keeps the setup it ran with, which is **Queue & History**'s.
- It does not keep what the user typed past the sitting. Settings survive moving between scenes, files and servers, and a dropped connection; they do not survive Smoozy closing.
- It does not decide what a render runs on beyond carrying the scene's own choice. Making a machine's GPUs available to a render is **Rendering**'s.
- It does not decide where a job's outputs land on disk, how many there are, or which of them matters. That is [What a job writes](What%20a%20job%20writes.md)'s. This module declines to offer the output path as a setting, and hands over what its read of the file found.
