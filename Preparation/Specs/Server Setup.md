# Server Setup

*What the Server Setup module does, in plain terms: how a bare rented machine is got to the point where it can render, how Blender gets onto it and comes off again, and why Smoozy installs no add-ons. Not one word about how it's built.*

## Where Server Setup fits

A rented machine arrives bare. Three things can stand between it and a render: whatever the machine itself needs before a render will run on it, a Blender to render with, and — for some files, though not most — an add-on the render depends on. This module owns the first two, and it is the only place in Smoozy that installs anything on a machine. The third it does not handle: Smoozy installs no add-ons, and *Add-ons* below says why. One thing it installs is not about rendering at all: the piece of **Telegram** that runs on a machine, which [Getting the machine ready](#getting-the-machine-ready) below sets out.

The first two are what every machine needs and what this module promises.

It is also the module the rest of the app waits on. **Render Settings** cannot read a `.blend` without a Blender on the machine, **Dependency Upload & Remap** cannot check one for what it is missing, and **Rendering** has nothing to render with. All three say so and send the user here.

**Connections.** The [module map](Whole%20app.md) owns how Server Setup is wired to the rest of the app. It needs a connected server from **Servers**, and it is reached two ways: from the Add Server dialog, where two setup options start this module's work, and from the server itself once connected, where the fuller choice lives. **Render Settings** picks between the Blenders this module installed, Its **Pre-load Settings** still finds the one add-on case a file announces — an engine the chosen Blender lacks — and says so on its own page; nothing about it reaches this module, which installs no add-ons. It leans on **Queue & History** for which jobs are running or waiting on a machine, so it can warn before it disturbs one.

**Making the machine's cards available to a render is not here.** Whatever that takes happens when a job is run rather than when the machine is set up, which is why the promise sits with **Rendering** (see the [Rendering spec](Rendering.md)).

## Two ways in

**The quick path** is the pair of options in the Add Server dialog — get the machine itself ready, and install the latest stable Blender. They are named by the outcome each delivers, they are ticked at the moment a server is added, and the [Servers spec](Servers.md) describes what ticking them does to the add. The work behind them is this module's.

**The full path** is Server Setup itself, opened on a connected server at any time. It is where the choice lives: which Blender to install, which to take off, and what the machine already has. Add-ons are not installed here or anywhere else (see [Add-ons](#add-ons)).

The quick path is deliberately the thin one. Someone renting their first machine should not have to know what a Blender build is to get a render going.

## Getting the machine ready

**What a bare machine needs before a render will run on it is known in part.** Blender asks for a graphics card and a driver at or above a version it states, and both floors moved between Blender versions. Label: **documented**, differing by version — see [Sources](Sources/Server%20Setup.sources.md). Beyond that it asks for very little: it carries its own Python, it needs no internet connection, and it needs no screen — every version started and rendered on rented Linux machines that had no display of any kind. Label: **observed** on rented Linux machines, all four versions.

**What is still missing is the numbers.** No figure for memory, disk, processor or operating-system version is established for any version, and the two graphics floors Blender's own pages give do not agree with each other. Label: **unresolved** — see [Sources](Sources/Server%20Setup.sources.md).

So this module promises the **outcome** — the machine made able to render — and offers a single action to reach it. The driver is the part that is established, and it is enough to keep that action whole rather than split it into choices. What a rented machine needs on top of it is a question about rented machines rather than about Blender. **It does need more, and the single action covers it as far as the machine allows.** A rented machine can arrive missing pieces of system software Blender needs to start at all, so the action finds what is missing before it installs anything, puts those pieces on explicitly rather than hoping the driver brings them, and handles the driver in its own order. What is missing is not the same list on every machine — it is a property of the image the machine was rented with rather than of rented machines in general. **Two things bound that, and where either bites, Smoozy says what it did not check rather than letting the outcome read as though it had.** The missing pieces are found by checking a Blender against the machine — one already there, or the one this run is putting there — so where there is neither, there is nothing to check against and that half does not run at all. And on a machine that will not let Smoozy install anything, none of it runs; that is the case the next paragraph describes, and it is the ordinary kind of rental rather than the odd one. Label: **settled at Architecture** (2026-08-23).

**Which Linux this module can prepare is named, and a machine outside it is refused rather than half-prepared.** Smoozy prepares **Ubuntu and Debian** machines. Every Linux family installs software its own way — a different installer, different package names, different repair steps and a different route to a graphics driver — so a preparation written for one family does not merely work less well on another, it does the wrong thing. **So the machine is asked which family it is before anything is installed**, and where the answer is not one of the two, Smoozy says so plainly, prepares nothing, and leaves the machine exactly as it found it. It is not presented as the machine being broken: it is a kind Smoozy does not prepare, said in one sentence, at the moment the user asks for the setup rather than part-way through it. The rest of the app is untouched — the machine still connects, still browses, and still renders if it already has what a render needs. Label: **Creator-stated** (2026-08-22). **The user is told which kinds to rent before they rent**, which the [module map](Whole%20app.md) owns. **How the family is asked for, and what happens where the machine will not say, is Architecture's.**

**Where the machine will not take it, Smoozy says what it could not do.** A locked container whose drivers are already in place has nothing to prepare. That rented machines can be arranged that way is **observed**, on a container rented to pose it (2026-08-15/16) — see [Sources](Sources/Server%20Setup.sources.md). *(This read **an assumption** until 2026-08-23, more than a week after the rental answered it.)* Smoozy says so plainly and moves on, and does not present it as something gone wrong: the option had nothing to do, which is not the same as failing. This is the same event the [Servers spec](Servers.md) describes for a ticked option on an add, said in the terms this module owns.

**Where a server's graphics driver is too old for a Blender to render with OptiX and Smoozy cannot replace it, Smoozy says so from the first connection, with the driver's version, and marks each Blender on that server the driver is too old for.** Label: **Creator-stated** (2026-10-11). *Added 2026-10-11, the Creator's rulings on OptiX and the driver; no auditor has seen it.* **From 5.3 it says more, because more is true: below the driver 5.3 asks for, Cycles cannot use the cards at all, by either of its two card technologies.** EEVEE and the processor still render. Label: **observed** (the 5.3.0 Beta, one driver below the bar, on one rented machine, 2026-11-02); the words are the build runner's ruling. Older versions keep their OptiX words. *No auditor has seen this.*

**Where Smoozy can replace it, it does, without asking and without a warning, so that the newest Blender on the server can render with OptiX — however that Blender got there: a setup, an install from the list, or the user's own build.** Replacing the driver restarts the machine, so while anything on that server is rendering or waiting to render, it waits, and that Blender keeps its mark until it is done. Label: **Creator-stated** (2026-10-11). *Added 2026-10-11, later the same day, the Creator's ruling that the driver follows every Blender on the server; no auditor has seen it.*

**A job sent meanwhile for a Blender the driver is too old for does not meet the old driver.** Where it renders on the cards, it is held back until the driver is replaced, and the wait does not count it as work; then it runs. Its entry in the queue says it is waiting for the driver update (see the [Queue & History spec](Queue%20&%20History.md)). Label: **Creator-stated** (2026-10-11). *Added 2026-10-11, the Creator's ruling that a job needing the newer driver is held back and the user is told; no auditor has seen it.*

**Where a server's graphics driver came without the library OptiX needs, Smoozy says so from the first connection, with the driver's version** — so a setup never ends ready with nothing said, and the first job is not where the user learns it. Without that library no job renders on that server's cards. Where Smoozy installs the driver itself it puts the library on with it; a driver that already works is not touched, so there the user is told and nothing is installed. Label: **Creator-stated** (2026-11-02). That a rented machine's driver can come without it is **observed** (2026-11-01) — see [Sources](Sources/Server%20Setup.sources.md). *Added 2026-11-02, the Creator's ruling that setup checks for it; no auditor has seen it.*

**It also says what it does not know about that machine: whether it can render on its cards.** Having nothing to prepare is not the same as being ready, and **an ordinary job will not settle it either**. With the graphics driver missing or wrong, every version rendered on the processor, wrote its picture and reported success — 4.5 saying nothing at all about it and the other three printing one warning line. Label: **observed**, on a rented Linux machine, all four versions — see [Sources](Sources/Server%20Setup.sources.md). So a finished job is not proof the cards were used, and at this moment Smoozy says only what it knows: there was nothing here for it to do.

**But a Cycles job can be made to say what did the work, and that is most of the promise this module was owed.** Every version prints a line naming the part of the computer that rendered — the model, and for a card the route taken to it and its place on the machine — and none of them prints it unless asked. **Every result behind that is Cycles' own report**, so whether an EEVEE or Workbench job names anything is not established in any version. **How you ask differs**: Blender 4.5 offers only one route and puts the line on the stream reserved for complaints, while 5.0, 5.1 and 5.2 answer to an ordinary logging switch and put it on the ordinary output. Label: **observed; it differs by version** (the route was run on both machines; the closing-report timing on one) — see [Sources](Sources/Server%20Setup.sources.md).

**Two limits travel with it and both matter here.** The line is a **closing report**, printed after the last sample and before the frame is written, so nothing says what a running job is using. **A render stopped part-way was believed never to reach it. That was wrong, and it is corrected here 2026-09-01** — two of the four versions print the whole report after a stop, one prints a cancelled line and no report, one prints nothing, and the version that prints it publishes its own note calling the figures in it wrong. **So Smoozy reads the line only from a job that finished**, and a line found on a job that did not finish is treated as nothing at all. That matters more here than anywhere else: this is the reading that can tell the user their machine is set up wrong and offer to redo it, which can restart the machine. And a machine's settings read back afterwards do not answer the question at all — they can be shown to name a card while the processor did the work. So what can be had is: *this finished job ran on these parts of this machine*, and nothing sooner. Label: **observed** (the same in all four versions) — see [Sources](Sources/Server%20Setup.sources.md).

**What Smoozy does with that belongs to [Rendering](Rendering.md)**, which owns what a job reports, and to [Queue & History](Queue%20&%20History.md), which owns what a finished entry shows. What this module now says at a machine with nothing to prepare is narrower and truer than before: there was nothing here to do, whether the cards work will be known once a job has run on them, and until then nobody can say.

**This module may read the same line for its own question, and only for that.** Reporting a job is those two modules'; asking whether this machine renders on its cards is this one's, and a finished Cycles job is the only evidence of it there is. So Server Setup may read what a finished job ran on, and what it may conclude from it is bounded:

- **A job that asked for the cards and rendered on the processor is a setup fault, and Smoozy says so and says what to do about it.** That is exactly the case a machine left as it comes produces — every card switched on, no card technology chosen, and a scene asking for the cards rendering on the processor with Blender saying nothing about it (see the [Render Settings spec](Render%20Settings.md), which owns the fact). Running the ready action again is the thing that fixes it, so this is one of the places Smoozy knows what to do and is allowed to say it — the whole-app rule in [Whole app](Whole%20app.md).
- **A job that asked for the processor and rendered on the processor says nothing about the machine.** Choosing the processor is a real choice and not always a mistake ([Render Settings](Render%20Settings.md)), so this is the artist getting what they asked for, and Smoozy neither flags it nor advises on it. Treating every job that ran on the processor as a broken driver would tell a user with a healthy machine to set it up again — and doing that can restart the machine and take a running render down.

What the scene asked for is known: it is a setting on the settings page and it goes with the job. Label: **Creator-stated** (2026-08-13). How the line reads, and where it sits, are Design's.

**Whether Smoozy can look at a machine and tell what has already been done to it is now settled, and the answer is yes on one condition**: the setup writes down each stage it passes as it passes it, and that record survives a reboot with nothing running behind it. Read afterwards, a machine names the last stage it actually got past — not the one it died inside. **What cannot be done is working it out by inspecting a machine that never recorded anything.** Label: **settled at Architecture** (2026-08-23). See [Sources](Sources/Server%20Setup.sources.md). This is about the setup state; reading which Blenders and add-ons a machine holds is a separate matter and is settled below (see [What Server Setup shows](#what-server-setup-shows)). So this module can say what a machine it has just met has already had done to it, as far as that machine's own record reaches. Where a machine recorded nothing, running the ready action again is the user's only way to be sure — which is why it must be safe to run on a machine that is already ready (see [When a setup fails, or is cut off](#when-a-setup-fails-or-is-cut-off)).

**Making a machine ready also puts Telegram's piece on it, where Telegram is switched on.** Telegram's bot runs on the machine rather than inside Smoozy, so something has to be put there, and this is the module that puts things on machines — it goes on with the rest of what the machine needs, over the connection this module already holds. That is the whole of this module's part in it. What the piece does afterwards, and everything else about the bot, belongs to the [Telegram spec](Telegram.md). Where Telegram is off, nothing of it is put on the machine. The [module map](Whole%20app.md) owns the hand-off.

**A machine set up before Telegram was switched on gets the piece by an action of its own.** It adds Telegram's piece and does nothing else: the rest of the setup is not run again, and the machine is not restarted, so a render already going on that machine is left alone. Without it the only route would be making the machine ready all over again, which may restart it and take that render down — a heavy price for a message on a phone. Label: **Creator-stated** (2026-08-03). It is offered on a connected server like everything else here, and only while Telegram is switched on. It is offered on the server's card and on Render Settings' Telegram line. *(The page added 2026-11-03: see the [Telegram spec](Telegram.md), under* A machine set up before Telegram was switched on*. No auditor has seen it.)*

## Installing Blender

**A machine can hold several Blenders side by side**, and the user picks which one renders each job in **Render Settings** (see the [Render Settings spec](Render%20Settings.md)). A Blender is a self-contained folder that can be put anywhere, and several can sit on one machine at once. Label: **documented** in all four Blender versions, and **observed** on two kinds of computer — see [Sources](Sources/Server%20Setup.sources.md).

**Installing one does not displace another's files, but two of the same version share their settings.** Blender keeps its settings — and the add-ons installed into them — in one folder named for the version counted to two numbers, so every 5.2 build on a machine uses the same one, whatever else differs between them. A build removed leaves that folder behind, so a fresh one installed afterwards lands on it rather than on a clean slate. Label: **documented**, and **observed** on two kinds of computer, all four versions. This narrows what the Creator stated, and the [Sources](Sources/Server%20Setup.sources.md) file records what was stated and what the research found.

**A Blender arrives one of two ways.** Label: **Creator-stated** (2026-07-29).

- **From a list Smoozy offers.** Smoozy shows what Blender publishes and the user picks. **One narrowing, Creator-stated: an unfinished build — a release candidate, a beta or any other — is not listed once the list holds a finished release of the same series at the same or a newer version.** A series is a version's first two numbers, so a 5.2.2 release candidate goes once 5.2.2 is released, a 4.5.0 beta goes beside a released 4.5.14, and a 5.3.0 beta stays while no 5.3 is released. In the Creator's words, on 2026-09-27: *"an actual release existing automatically means that all the previous builds with this exact version are irrelevant"*; and on 2026-09-28, asked about that 4.5.0 beta: *"Of course older unstable builds should go once a newer version arrives."* **It is compared within one series, never across the whole list**: the question put to the Creator was about a line that already has a newer finished release, and a fix release of an older long-term-support line is not made irrelevant by a newer series. That Blender publishes finished releases, long-term-support releases and unstable daily builds, and marks the unstable ones alpha or beta, is **documented** in all four versions. That a published build can be fetched with nobody at a web page is **observed**: a release folder on Blender's own download server was read as a plain listing, a build fetched from it, and it matched the checksum published beside it. **A second narrowing, for finished releases: only the newest finished release of each series is listed.** A stable 5.2.3 removes a stable 5.2.2 from the list; 4.5's newest release stays beside them, and so does an unfinished 5.3 while no 5.3 is released. It is judged from what the list offers, never from what the server holds, so installing a version never changes the list. *Added 2026-10-28, Creator-stated, the twentieth notes, note 1: "Blender 5.2.2 is still listed as an option despite 5.2.3 being the latest, which was actually already installed"; the smallest change, runner-ruled under the Creator's standing delegation. A want entering at Specs under Rule 7. No auditor has seen it.* **Finished releases and unfinished builds are listed from two different places, and that is settled rather than accidental.**
  - **Finished releases** are listed from a shop-front for Linux software — not the machine's own distribution packages. It is published by the Blender Foundation, carries every release line with a version, a date and a size, and marks the long-term-support lines. Label: **observed**, one run on one machine. They are fetched from Blender's own release folders. Label on the split: **Creator-stated** (2026-08-12).
  - **Unfinished builds — alpha, beta, release candidate — are listed and fetched from Blender's own build service, and each is named by Blender's own word for its kind.** The narrowing above applies to them as to everything else. Label: **Creator-stated** (2026-10-02), revising the list half of the 2026-08-12 ruling for unfinished builds only, out of the Creator's notes on 0.1.7: *"Experimental Blender builds don't show whether they are alpha, beta or RC"*, and *"I can't install Blender 5.3.0a"*. **The fetch half of that ruling holds**: every build still comes from Blender itself. **Why it had to move.** Blender's release folders held no unfinished build on either day they were read, so every unfinished build the shop-front named was one Smoozy could not fetch. On 2026-10-02 the shop-front named 5.3.0 and Blender's release folder for it did not exist, while the build service listed *Blender 5.3.0 Alpha* with its archive and checksum. Label: **observed** (2026-08-19 and 2026-10-02); see [Sources](Sources/Server%20Setup.sources.md).

    **A Blender newer than any whose settings Smoozy has read can be installed, but renders nothing until its settings are read; a job sent to it fails before Blender starts, saying so:** *Blender 5.4.0 is not supported yet.*, with the version as read from the build. *Words changed 2026-10-28 (was *Smoozy cannot render with Blender 5.4.0 yet.*): Creator-stated, the final words sweep. No auditor has seen it.* *Added 2026-10-18, the Creator's thirteenth notes, note 8 ("it looks like it didn't even try and immediately sent it to failed"). No auditor has seen it.*

**What that costs is one thing, and the spec says what happens then.** Nothing establishes that a listing and the place its build is fetched from agree, so the list can still name a build Smoozy then cannot fetch. Where that happens Smoozy says the build could not be fetched and names it by version and kind, rather than hiding the entry or failing silently — the user can still bring that build up themselves by the second way in below. It does not quietly substitute a different version. Label: **Creator-stated** (2026-08-12). The list holds nothing below 4.5, since that is the whole app's floor (see [Whole app](Whole%20app.md)).
- **A build the user points at on their own computer.** Smoozy sends it up and installs it. This is how a self-compiled Blender gets onto a machine, and it is why the list is not the only way in.

**What Smoozy fetches comes from Blender's own downloads, not from the machine's own software.** A Blender put there by a Linux distribution may leave out rendering on graphics cards altogether, and the one examined was more than two release series behind. Label: **documented** in all four versions, and **observed** on a rented Linux machine. Blender's own build was checked in all four versions and carries graphics-card rendering. **This is why only the list comes from the shop-front and never the build itself.** Nothing establishes that a Blender installed through it renders on graphics cards, and cards are what the user rented the machine for.

**Blender's own advice is one long-term-support version per project, and the quick path deliberately does not follow it.** Every version's own deployment page advises settling on a single long-term-support version for a given project, because a newer version may change what an existing file produces. Label: **documented**, all four versions — see [Sources](Sources/Server%20Setup.sources.md). No version names one release for everybody, which is what this spec and [Servers](Servers.md) already say. **The quick path installs the latest finished release, on the Creator's ruling of 2026-08-12**, which is the fourth time that has been settled the same way: the quick path exists to get a machine rendering with nothing to decide, the artist's own file already carries the version it was made with, and the list above is where somebody who wants a particular release picks one. **The quick path installs the newest finished release, whichever line publishes it; it never prefers an older long-term-support release.** Label: **Creator-stated** (2026-10-27), the nineteenth notes, note 1. *Changed 2026-10-27; no auditor has seen it.*

**Sending a build up is this module's own work, not the file browser's.** It is the same distinction Dependency Upload & Remap draws: sending up something the module needs is not the same act as the user putting their own files on a machine (see the [File Browser spec](File%20Browser.md)).

**A build the user brings is taken as they gave it.** Smoozy does not judge it or refuse it — a user who compiled their own Blender knows more about it than Smoozy does. That includes the case above: a build made some other way may have no graphics-card rendering in it, and Smoozy neither checks nor says so.

**A build can be asked what version it is, and it answers.** Asked from a terminal it prints its version, whether it is a long-term-support release, and whether it is a finished release or an unstable build. Label: **documented and observed**, all four versions on two kinds of computer, with the long-term-support marking **observed** only — see [Sources](Sources/Server%20Setup.sources.md). Every build tested was a finished release, so that an unstable one says so is **documented** and untested. So Smoozy says which version a build turns out to be, which is what **Render Settings** needs to match a file against what is installed.

**Where that version is below the floor, the user is warned plainly at the moment of installing.** Smoozy says the version is unsupported, that nothing in the rest of the app is written for it, and that what happens with it from there is the user's own affair. It warns and does not refuse: the user may install whatever they want, and only 4.5 and above is supported. Label: **Creator-stated** (2026-07-29).

**A build below the floor can therefore end up on a machine, and nothing downstream is written for it.** Smoozy neither refuses it nor pretends it is supported; what the rest of the app does when a job renders on such a version is **Render Settings**', which is where the version is chosen and which settles it: the build appears in the list and can be picked, and is never the automatic pick — see the [Render Settings spec](Render%20Settings.md).

**The quick path installs the latest stable release.** That Blender publishes a stable release distinct from its other builds is **documented** in all four versions; the fact is owned and cited by the [Servers sources](Sources/Servers.sources.md), where the Add Server option first leans on it. That this is the deliberate quick path is the Creator's decision and is not in question.

## Taking a Blender off

**The user can remove a Blender through Server Setup.** Label: **Creator-stated** (2026-07-29). A machine able to hold several with no way to clear one out only fills up, and the user would be left deleting files by hand through the file browser to undo something this module did.

**Removing the last Blender is not warned about, on its own account.** Label: **Creator-stated** (2026-07-29). Someone taking the only Blender off a machine is doing it on purpose, and a warning saying the machine can no longer render would only tell them what they had just decided. What they meet afterwards belongs to **Render Settings** (see the [Render Settings spec](Render%20Settings.md)).

**Work already on the machine is a separate matter, and it does carry a warning.** A job that is running is rendering with a particular Blender, and a job that is waiting was submitted with one already chosen (see the [Render Settings spec](Render%20Settings.md)). Before removing a Blender that a running or waiting job needs, Smoozy names those jobs and the user decides. It never refuses, and it never removes quietly. This is the same shape as the file browser's warning before disturbing a file a live job depends on (see the [File Browser spec](File%20Browser.md)).

**That warning holds even when the Blender being removed is the last one.** The two rules answer different questions. The first is about what the machine can do next, which the user has just chosen. The second is about work already under way, which they may well have forgotten — and on a machine holding one Blender, that is every job on it. Staying silent there would drop the warning at exactly the point where the most work is at risk.

**What removing it does to a job already rendering is nothing.** Deleting the folder a render was running from was permitted at once, the render carried on, every frame was written, and it ended normally. Label: **observed**, all four Blender versions on two kinds of computer — see [Sources](Sources/Server%20Setup.sources.md). So the warning names the jobs and tells the truth about each: a job already rendering will finish, and a job still waiting was submitted with that Blender chosen and will have nothing to render with. What becomes of the waiting one is **Queue & History**'s (see the [Queue & History spec](Queue%20&%20History.md)).

**The warning leans on Queue & History** for which jobs are live on a machine and which Blender each of them is using (see the [Queue & History spec](Queue%20&%20History.md)). Both halves are there: a job is submitted to render with one named Blender, and that choice is part of the setup its entry keeps, whether the user picked the version or took the one Smoozy picked for them. So the warning can name the jobs and say which of them was submitted to render with the Blender being removed.

## Add-ons

**Parked, 2026-10-08: Smoozy installs no add-ons.** Label: **Creator-stated**. The Creator, word for word: *"You know what? Let's ditch add-ons for now. You can put my own wording wherever the reasons for that go — I feel like this will create more problems than it will solve. Maybe someday when I have all the add-ons that fit the criteria of running at render time myself I will get back to it. But right now — we're not building it."* So nothing in this section, and no other sentence in this spec about installing, enabling, listing or offering an add-on, is a promise: none of it is built. It stays as the record of what was learned and what was planned, for the day it is taken up again — **when the Creator holds the add-ons that run at render time** and can try them. Two things stay true and are kept. **Render Settings**' Pre-load still finds a file whose engine this Blender lacks, and says so plainly on its own page, offering nothing to install. And *Where the user picks an engine themselves and the machine's Blender does not have it* (below) still holds: such a job is refused before it starts. Parked in [Open Threads](../Groundwork/Open%20Threads.md).

**Some `.blend` files need an add-on to render, and most do not.** Label: **Creator-stated** (2026-07-29) — see [Sources](Sources/Server%20Setup.sources.md). An add-on the artist used to build something leaves ordinary Blender data behind in the file, and the render wants nothing further from it. The ones that matter are the smaller set that take part in the render itself.

**Which are which cannot be told apart.** A `.blend` keeps no record of the add-ons it needs and Blender offers no way to read one out. Nor does an add-on say anything about whether it takes part in a render: everything it declares about itself is written by whoever made it and is never checked against what it does — the only kind it can call itself is add-on or theme, its tags are a fixed list holding both Render and User Interface, and the things it may ask permission for are files, network, clipboard, camera and microphone, with nothing about rendering. Label: **documented and observed**, all four Blender versions on two kinds of computer — see [Sources](Sources/Server%20Setup.sources.md).

**The one exception is the engine.** A file records by name which engine renders it, and a Blender that lacks that engine's add-on says so plainly the moment the file is opened. So a job whose renderer is a missing add-on can be found; nothing else can.

So the guess below rests on far less than a whole answer, and everything this section promises about add-ons has to be read in that light. The reading itself is **Render Settings**' — the [Render Settings spec](Render%20Settings.md) owns that half, including why it sits there rather than in a pass of its own — and **that spec now settles what the reading can honestly claim: the missing engine, and nothing else.** Label: **Creator-stated** (2026-08-13). So what reaches this module from Pre-load is that one case. The guess below is Smoozy's own, made from what the user knows about their file rather than from anything read out of it.

What follows here is what Smoozy does with what it found.

**It is a guess, and Smoozy says so.** Label: **Creator-stated** (2026-07-29). Smoozy holds no catalogue of add-ons and does not go and study them; it says what it thinks the file needs, and does not dress that up as a finding. This is about the file in front of the user and never about what they own — an artist with a fluid add-on on their computer uses it in one project and not the next.

**Smoozy offers; it does not install unasked.** Label: **Creator-stated** (2026-07-29). The whole answer is a guess, and installing on a guess without being asked would put software on a machine the user never agreed to. So the add-ons are shown where Pre-load found them — on the settings page — with the ones Smoozy can supply offered there, and the user takes the offer or does not.

**It says plainly which ones it cannot supply, and those are the user's own to sort out.** That second list is expected rather than a failure: handling every add-on an artist might own would be a product of its own, and this module does not try.

**An add-on is fetched from a repository, and Blender holds a list of them.** Where an add-on may come from is decided by that list, which sits in Blender's own settings and can be read, added to and cut down with nobody at a screen. A fresh Blender holds three: Blender's own extensions site, a folder belonging to the user, and a folder inside the Blender itself. A repository's address may be a plain folder path rather than a web address. Label: **documented** in all four Blender versions, and **observed** on two kinds of computer — see [Sources](Sources/Server%20Setup.sources.md).

**So there is one route, not two.** Blender's own site is one entry on that list, a folder on the machine is another, and a site somebody else runs is another — Blender's documentation says other sites are supported so long as they are built to the same shape. That third kind could not be tried, because no address for one appears anywhere in Blender's own documentation; label: **unresolved** for that case alone. A package can also be installed straight from a file, which is what a copy from the user's computer uses. What Blender will not take is a web address: it installs by name from a repository, or from a file, and nothing else. Label: **documented and observed**, all four versions.

**Fetching one and taking a copy from the user both count as Smoozy handling it.** The user does the pointing in the second case, but Smoozy asks for it, sends it up and installs it, so the add-on is still handled here rather than left to them. **Cannot supply** is kept for the one case Smoozy has no route to at all: a separate program with its own installer, below.

**The copy from the user's computer is what reaches a paid add-on.** It goes up exactly as it sits, already set up where the artist set it up. What Smoozy promises is what Smoozy controls: it does not ask for a licence key, does not read one, and does not check one. It never talks to whoever sold the add-on, and never decides who is entitled to what. Smoozy also does not judge whether the user may put a paid add-on on a rented machine; that is between them and whoever sold it.

**How add-ons are sold is described nowhere in Blender's own documentation** — no pricing, no purchase, no keys, no activation. Label: **unresolved**, all four versions. Whether a copy taken from the user's computer carries licence material inside it is **unresolved** with it — see [Sources](Sources/Server%20Setup.sources.md).

**A copy carried to a machine of a different kind half works, and says nothing about it.** An add-on packed up on one machine and opened by a Blender of the same version on a machine of another kind was listed as installed and was switched on, and the plain part of it worked; the part built for the first machine did not, and the failure came only when something used the add-on — with that run reporting success too. Label: **observed**, all four Blender versions, between a Mac and a rented Linux machine — see [Sources](Sources/Server%20Setup.sources.md). Every render Smoozy runs happens on a rented Linux machine, and the artist's computer is usually not one, so this is the ordinary case rather than the odd one.

**Installing means switched on, and that much Smoozy can do.** Label: **Creator-stated** (2026-07-29). An add-on that is present and switched off is worse than one that was never installed: everything reads as done and the render still does not have it. Installing an add-on, switching it on, and setting its own settings all worked on a machine with no screen and no display of any kind, in all four Blender versions. Label: **observed**, on a rented Linux machine with no display — see [Sources](Sources/Server%20Setup.sources.md).

**What Smoozy cannot promise is that the add-on will work.** An add-on may declare a part it is supposed to carry with it, install with no warning of any kind, report success, be switched on, and simply not have that part. Nothing is said until something uses it, and even that run reports success. Label: **observed**, all four Blender versions on a rented Linux machine — see [Sources](Sources/Server%20Setup.sources.md).

**So this module does not say the add-on is supplied. It says what it did.** The add-on was installed and switched on, and whether it works shows when the job renders. That is the whole of what can honestly be claimed, and it is less than an add-on being ready to work.

**A little more can be checked than that, and it is worth having exactly.** Switching an add-on on **can** give a machine-readable answer: on one of the two routes the act succeeds for a working add-on and raises for a broken one, naming the fault, so Smoozy learns at that moment whether the add-on could be loaded. **The other route swallows the failure**, and switching one on at launch prints a complaint and still ends at success — so which route is used decides whether anything is learned at all. What it does not learn is anything about whether the part the render needs will work — **nothing anywhere, documented or tested, tells you that before the add-on is used.** Every other check Blender offers is a check that something has already gone wrong. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Server%20Setup.sources.md).

**Three limits keep that from being worth more than it is.** The list of switched-on add-ons **records what was asked for rather than what loaded**, so an add-on that broke on disk after being switched on stays in the list with only a line printed at start-up to say otherwise — the answer can be trusted about a switch-on made in the same sitting and no further. Asking Blender to look again over its add-ons **reports nothing about damage**; every fault surfaces at start-up instead. And the listing of what is installed says nothing about health and nothing about whether an add-on is on or off. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Server%20Setup.sources.md).

**And one thing has to be got right or the whole offer misreports itself: one kind of refusal still ends at a successful status.** An add-on declaring it needs a Blender it is not being installed into is refused by name, nothing is installed and nothing reaches the listing — and the command reports success all the same. Another kind does report failure: a compiled part built for the wrong Python is refused at a failing status. So the ending cannot be read either way round, and Smoozy has to look at what the machine now holds rather than at what the command said. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Server%20Setup.sources.md). The same declaration is **ignored entirely for an older-style add-on**, which is listed, switched on and run whatever Blender it declares it needs — so the two kinds cannot be treated alike.

**So the wording stands and the checking behind it is now known.** Installed, switched on, and loadable at the moment it was switched on — and beyond that, whether it works shows when the job renders.

**A separate program is not an add-on, and Smoozy does not handle one.** Some of what an artist calls an add-on is a whole program of its own, with its own installer and its own licensing — an outside physics engine is the plain example. Smoozy does not install those, and it has no way to run an installer the user puts on a machine either: nothing Smoozy runs on a machine is a program the **user** supplied. So this is a **limit**, stated as one, not a route the user is quietly pointed down. Label: **Creator-stated** (2026-07-29).

**What Smoozy does run on a machine, said plainly here because this sentence is where a reader looks for it.** A render, and the piece of **Telegram** it put there itself — and, besides those, whatever this module needs to do its own work: fetching and unpacking a Blender, asking a build which version it is, searching the disk for the Blenders already on it, listing and installing add-ons and switching them on, and running whatever a machine needs before a render will work. Other modules run things too — reading a `.blend` for its settings is [Render Settings](Render%20Settings.md)', and reading one for what it is missing is [Dependency Upload & Remap](Dependency%20Upload%20&%20Remap.md)'. None of that is a route for the user's own installer, which is the only thing the limit above is about. Label: **Creator-stated** (2026-08-13).

**Blender's own rule stands behind that limit.** An add-on packaged the modern way must not depend on anything else already being on the computer — it has to bring what it needs with it — and where an add-on needs another add-on, Blender's answer is to bundle the other one inside it. Nothing an add-on declares can name another add-on. Label: **documented**, all four versions — see [Sources](Sources/Server%20Setup.sources.md). An add-on may declare that it needs the network, and Blender says plainly it cannot stop one that breaks the rule.

**So an add-on that quietly wants a separate program is against Blender's rule rather than ordinary, and the sharper hole is the one above** — an add-on that was supposed to bring its own part and did not. Both end the same way, and both get the same answer: installed and switched on, and nothing more claimed.

**The user is told where Pre-load finds one, and told what it means for the job.** Smoozy names the add-on there, says it is a separate program and cannot be installed from Smoozy, and says the plain consequence: if the render really needs it, this job cannot be made render-ready from inside Smoozy, and putting the program on the machine is not something Smoozy can do for them. The job can still be submitted, like any job whose add-ons Smoozy did not supply. **The limit is what is promised here, and there is no way through it.**

**An add-on belongs to a folder, and the folder is named for the Blender version.** An add-on installed by one Blender sits in that Blender's settings folder, which is named for the version counted to two numbers. Nothing in Blender refuses another version's add-on — one folder handed to four Blenders in turn had the add-on listed and switched on by every one of them — so what keeps versions apart is the folder's name and nothing else. Label: **documented and observed**, all four Blender versions on two kinds of computer — see [Sources](Sources/Server%20Setup.sources.md).

**So a machine holding two Blenders needs the add-on twice**, once per version, unless the two are builds of the same version, which share one folder. And a part built into an add-on is built for the Blender's own Python, which changed between 5.0 and 5.1, so an add-on installed for one of those is not usable by the other even when they share a folder. Label: **documented and observed**.

**Add-ons pile up on a machine, so nothing is installed twice.** A machine renders many jobs, and the second one often needs what the first already put there. What the guess asks for is compared against what that Blender's folder holds — the same look this module already takes for Blender versions.

**That look cannot see everything, and where it cannot tell, Smoozy leaves the machine alone.** No single route gives a complete inventory: what Smoozy itself installed is visible, and the listing says nothing about whether an add-on is on or off and nothing about its health. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Server%20Setup.sources.md). **And no route is established to cover a switched-off older-style add-on** — which is exactly the shape an artist's own hand-placed copy takes. **That is a silence, not an answer, and it read here as a settled *no* until 2026-09-02.** Nobody ever asked whether a route reaches one, so Smoozy may not claim it sees them and may not claim it cannot. Label: **unresolved, and permanently** — see [Sources](Sources/Server%20Setup.sources.md) and *What is not settled* below. **So the listing is taken as good enough and Smoozy does not install over what it cannot see, on the Creator's ruling of 2026-08-12.** The two ways were installing again to be sure, which writes over a copy the user put there and may be the copy they wanted, or trusting the listing, which can skip an install and leave the job running against the artist's own older copy. The second was taken: the machine is the user's, an add-on Smoozy overwrites is gone without being asked about, and a job running against a copy the artist put there is running against a copy the artist chose. Label: **Creator-stated** (2026-08-12).

**It follows that *nothing is installed twice* is a promise about what Smoozy can see.** This module already says it does not claim an add-on will work, only that it was installed and switched on (below) — this is the same shape one step earlier, and it is stated rather than assumed.

**The offer says what it covers.** It is met per job, on the settings page, while installing happens on the machine — so the user is told which of those they are agreeing to rather than left to assume. The offer covers the add-ons this job needs, put on this machine, for the Blender this job will render with. It does not reach the machine's other Blenders, which need their own copies.

**The answer belongs to the version it was read with.** Pre-load opens the file with the Blender the job will render with, so the add-on list describes that job on that version. The user can change the version afterwards on the same page, which leaves the list describing a version the job will not use — and leaves the add-ons already installed sitting in the old version's folder, where the new one will not find them. What Smoozy says at that moment is that the list no longer describes this job, and reading the file again with the new version is what produces one that does. Nothing here closes the wider question: what happens to everything else Pre-load found when the version changes is **Render Settings**' and is settled at Architecture — see the [Render Settings architecture](../Architecture/Render%20Settings.md), clause Q12, Row 142. Changing the version throws away the whole reading of the file, exactly as reconnecting does, so everything Pre-load found goes rather than this list alone.

**Nothing here blocks a render, and the user should know what they are risking.** A file whose add-ons Smoozy could not supply can still be submitted, and the user decides. **A render missing an add-on does not stop — it produces something else. That holds where Smoozy leaves the file's own choice alone, which is the ordinary case, and it is not the whole picture. Corrected 2026-09-01, after the research was repaired.** A file whose engine's add-on is absent prints one line saying so and then renders with Blender's own real-time engine instead, writes an image, and reports success.

**Where the user picks an engine themselves and the machine's Blender does not have it, nothing falls back.** No picture is written at all; three of the four Blender versions stop at a failure, and **the fourth never stops — on a rented machine it runs until somebody destroys it, billing all the while.** So that case is not a wrong picture, it is an open bill. **Smoozy therefore refuses such a job before it starts** rather than sending it, and says why.

**That does not contradict the promise this section opens with, and the difference is worth being clear about.** *Nothing blocks a render* is about **the file's own choice**, which Smoozy leaves alone: a file whose add-ons are missing still goes through, still renders, and the user still decides what they are risking. The refusal is about **a choice the user makes inside Smoozy** — picking an engine the machine cannot run — where the alternative is not a wrong picture but a machine billing with nothing coming. *(Decided 2026-09-01 under the Creator's standing delegation of 2026-08-31, not put to them; the app already behaves this way and this paragraph had not said so.)* An add-on that changes a render without being the engine is silent when absent: the render finishes normally and reports success. Label: **observed**, all four Blender versions on two kinds of computer — see [Sources](Sources/Server%20Setup.sources.md). So what the user is weighing is a finished job with the wrong picture, not a failure, and Smoozy says that plainly.

What they were told depends on whether they pre-loaded at all. Someone who did was shown the guess and can weigh it. Someone who did not is named the checks that have not run, add-ons among them, and offered the read before the job goes — that is **Render Settings**' rule for a submission with no pre-load behind it (see the [Render Settings spec](Render%20Settings.md)). Either way the user can go ahead.

## What Server Setup shows

**What is on the machine, read from the machine.** The server list deliberately shows no Blender versions, because the user can install or remove one without Smoozy ever knowing, so anything remembered would be a guess rather than a fact (see the [Servers spec](Servers.md)). Server Setup is where the true answer comes from, and it comes from looking.

**Add-ons can be asked for; Blenders have to be looked for.** Blender can be asked, with no screen, what add-ons a Blender holds and which of them are switched on — by three routes, no one of which is a complete list. Label: **documented and observed**, all four versions on two kinds of computer. For Blenders there is no such route: no Blender reports another, and a machine's own software lists name only what was installed their way, so a build simply put in a folder is invisible to all of them — only a search of the machine's files found every Blender on it. Label: **observed**, on a Mac and on a rented Linux machine. See [Sources](Sources/Server%20Setup.sources.md). Each build found then answers for itself when asked its version, so the version list **Render Settings** chooses from can be built by looking rather than by remembering. That the search finds every one of them on a rented machine is Architecture's to deliver.

**This is reading the software installed on a machine, which is not the same as reading the setup state it is in.** The first is what this section promises. The second is the question settled under [Getting the machine ready](#getting-the-machine-ready), and it is answered from what the setup itself wrote down as it went rather than from looking at the machine; where a machine recorded nothing, running the ready action again is what covers it. The two land differently: a machine can always be listed for what is installed on it, and a machine that recorded nothing still cannot say how far a half-finished setup got.

**So it is read afresh and never carried forward.** Nothing about what a machine holds survives from one connection to the next.

## Restarting the machine

**Where a setup step needs the machine restarted, Smoozy restarts it as part of that step, without stopping to ask.** Label: **Creator-stated** (2026-07-29). The user asked for the setup; the restart is part of carrying it out rather than a separate thing to agree to. That a driver install can require one is **observed**, on two rented machines and for two different reasons (2026-08-15/16) — on one the provider had left the card bound to another driver, on the other the install pulled a whole new kernel and demanded the restart itself. **Only the first said nothing**, which is why the rule is to restart where the card's own check fails and never on the installer's word — see [Sources](Sources/Server%20Setup.sources.md). *(This read **an assumption** until 2026-08-23.)* Restarting a rented machine over the connection Smoozy holds is **observed**: the restart command closed that connection, the same address and port answered again in about ten seconds with a new boot id, and the disk was intact. Label: **observed**, one rented Linux machine (2026-08-13) — see [Sources](Sources/Server%20Setup.sources.md).

**This is a stated exception to the whole-app boundary** that Smoozy never acts on a machine's power. Label: **Creator-stated** (2026-07-29). The [module map](Whole%20app.md) owns that boundary and carries the exception, which reaches exactly this far: a restart a setup step needs. Smoozy still never powers a machine on, and never powers one down for good.

**Smoozy still says so.** Not asking is not the same as not telling: Smoozy says the machine is being restarted, waits for it to come back, and carries on with the setup where it left off.

**It is the one time Smoozy puts a connection back that the user did not lose.** The connection goes down because Smoozy took the machine down, so it is neither the user disconnecting nor a drop to be repaired. The [Servers spec](Servers.md) owns what a connection is and when Smoozy may make one, and carries this as its own case: the connected period survives the restart, and the ordinary dropped-connection handling — trying again, then giving up and saying so — does not run. It follows that the whole-app notification for a connection Smoozy could not restore does not fire on a restart it caused.

**How long Smoozy waits is settled at Architecture.** At some point a machine that has not come back has to be treated as gone, and the user is sitting in front of a half-finished setup while that is decided. While it waits, the server reads as **restarting**. The waiting itself is the same waiting **Servers** already does for any connection that has dropped — four rounds of attempts, ten minutes in all — and when that gives up, the setup is reported cut off part-way, saying only that the connection is down and could not be restored. See the [Server Setup architecture](../Architecture/Server%20Setup.md), clause T6, and the [Servers architecture](../Architecture/Servers.md), clause M4; Row 108.

**If the machine does not come back, Smoozy says only what it knows**: the connection is down and could not be restored. It does not claim to know why, because it cannot tell a machine still starting up from one that will never answer again (see [Whole app](Whole%20app.md)). What the setup managed before the restart is reported as any part-finished setup is, below.

**Once Smoozy gives up waiting, it is a setup cut off part-way.** Nothing carries on by itself, and Smoozy does not keep trying. The way forward is the one the next section already provides: when the machine can be reached again, the user opens a connection and runs the rest from here.

**A restart stops everything else in flight on that machine** — a transfer, a dependency check, a render. Label: **observed** for a transfer (2026-08-13) and for a render (2026-08-15/16); the dependency check is **unresolved** and nothing has posed it — see [Sources](Sources/Server%20Setup.sources.md). *(Both observed halves read **an assumption** until 2026-08-23.)* Each of those already sets out what a lost connection does to it, in the module that owns it.

**And a render that was running dies.** Label: **observed**, two real machine restarts with a Cycles render in flight, restarted over the connection rather than from the provider's console (2026-08-15/16) — see [Sources](Sources/Server%20Setup.sources.md). *(This read **an assumption** until 2026-08-23.)* That is what the warning below is for. When the machine comes back it re-runs the job it was interrupted on, with nobody asking it to; what that re-run covers, and what happens if the same job is interrupted twice, is settled in the [Queue & History spec](Queue%20&%20History.md), which owns everything that happens to work when a machine goes down.

**The rest of the setup goes first, and the re-run waits for it.** Two things want the machine the moment it comes back: the setup Smoozy is part-way through, and the job the machine takes up again on its own. Smoozy finishes the setup, and the interrupted job is re-run after it. That is the order worth having — the setup is what the restart was for, and a render started while the machine is still being changed underneath it may only die again. It is a promise this spec makes and Architecture has to deliver, and not a light one, because the machine re-runs without waiting for Smoozy or anyone else. If it cannot be kept, that is a fault in this plan, to be fixed here rather than reinterpreted.

## Setting up a machine that has work on it

**Setup is never withheld while a machine is busy.** Label: **Creator-stated** (2026-07-29). Refusing would lock a user out of installing the one Blender version their next file needs, on a machine that is going to be busy for the next six hours.

**The warning depends on the step, not on the machine being busy.** Label: **Creator-stated** (2026-07-29). Not every setup step threatens a running render, and warning about all of them equally would teach the user to click through the warning that matters. So Smoozy warns where the step it is about to run **could disturb work on the machine** — saying so, and saying what happens to that job if it does — and says nothing where it could not.

Which steps fall on which side follows from what each step does, and for making a machine ready that is still open above. Three are worth stating.

- **Installing a Blender alongside the ones already there does not disturb a running render**, so it carries no warning. A whole second Blender was put in beside a render in progress and the render finished, every frame written. Label: **observed**, all four Blender versions on two kinds of computer — see [Sources](Sources/Server%20Setup.sources.md). **Alongside is the word that carries it.** Copying a Blender over the very folder a render was running from killed that render on a rented Linux machine, in all four versions, part way through — the same act was harmless on a Mac. Label: **observed**. Every render Smoozy runs happens on a rented Linux machine, so Smoozy installs into a folder of its own and never over one a job is using. That is a promise Architecture has to honour.
- **Making a machine ready may restart it**, and a restart takes a running render down (see [Restarting the machine](#restarting-the-machine)), so it warns. *One restart never warns, because it never meets a render: replacing a driver too old for OptiX waits until nothing on the server is rendering or waiting to render (see [Getting the machine ready](#getting-the-machine-ready)). Added 2026-10-11, the Creator's ruling that the driver follows every Blender on the server.* *A job held back for that driver is not one of the things it waits for, since it has not started (added 2026-10-11, the Creator's ruling that such a job is held back).*
- **Installing an add-on does not disturb a running render either, so it carries no warning.** It was tried both ways round — installs fired at a render from a second Blender, and an install made from inside the very Blender that was rendering — and in every case the render wrote all its frames, ended at success, and **every frame matched the undisturbed control picture for picture, with not one differing value**. Blender's own setting for locking the interface during a render made no difference — **that one on the Linux machine alone, with no window; the windowed form is still not established**. Label: **observed** (the same in all four versions, on both machines except where said) — see [Sources](Sources/Server%20Setup.sources.md). One limit the research states and this rule leans on: what was shown is that **these** installs, fired at **this** rate, changed no frame — not that installing is harmless in general. *(Was unresolved, and stayed on the warned side out of caution; the test moved it.)*

  **Two things sit beside that and neither changes the answer.** A Blender that is already running **does not pick up a newly installed add-on by itself** and asking it to look again does not change that, though the add-on can then be switched on inside it without a restart. And Blender keeps a lock on its own add-on store: with one Blender holding it, an install fired from another **refuses in under a second at a failing status**, naming the session that holds it, rather than waiting. **A Blender that is rendering does not hold that lock**, which is why none of the installs above disturbed anything — but a second setup running at the same moment would be refused, and Smoozy has to expect that rather than read it as a broken machine.

The rule is written by that test rather than by naming steps, so a step whose effect is settled later slots into it rather than changing it.

Where Smoozy warns, it warns and does not refuse. The user decides.

## When a setup fails, or is cut off

**A step that fails is reported here, and can be run again from here.** Servers deliberately remembers nothing about a setup once Smoozy has reached the machine (see the [Servers spec](Servers.md)), which is what makes this module the place a failed step is picked up. How the failure reaches the user is settled by the whole-app concern *how a failure reaches the user* (see [Whole app](Whole%20app.md)); only the words are Design's.

**A connection lost part-way through stops it, and nothing resumes on its own.** Label: **Creator-stated** (2026-07-29). Smoozy says what it managed and what it did not; the user runs the rest from here on a connection they open. It never carries on by itself, and it never counts a half-finished step as done. A restart Smoozy caused is the one case this does not cover, because Smoozy is expecting the machine back (see [Restarting the machine](#restarting-the-machine)).

**The user can stop a step that is under way.** A setup can take a long while, and someone who changes their mind should not have to pull the connection down to get out of it. Stopping leaves the same situation a lost connection leaves: what was already done stays on the machine, Smoozy says what it managed and what it did not, and no half-finished step counts as done. Running it again from here is how the machine is put right. One thing cannot be called back — a restart already begun. Stopping then only stops Smoozy waiting; the machine still restarts, and the user picks the setup up again once it is back.

**While a setup runs, the user can watch what the server prints**: the newest lines as they arrive, and the whole of it to read or copy. It is the server's own words, shown as printed, and Smoozy reads nothing into them. Label: **Creator-stated** (2026-10-18), the thirteenth notes, note 7: "Can we add a blender output-style window to server setup? … 3 lines with an option to open the whole thing and copy to clipboard." *No auditor has seen it.*

**Running a step again is always safe.** Whether the last attempt finished, stopped part-way, or was never started, running it again puts the machine right rather than making it worse. Two things need that. A setup cut off part-way can leave the machine in a state neither Smoozy nor the user can describe, and running it again is the only way out. And where a machine cannot be read for what has already been done to it, running the step again is the user's only way to be sure it has been.

**For installing a Blender that is settled.** An install cut off part-way was run again over the same folder with nothing deleted first, and produced a working Blender the same as a clean one. Label: **observed**, on a rented Linux machine, one Blender. For **making a machine ready** the answer came back **no** — running it again on a half-finished machine is not harmless. Label: **observed**, run last on a box being given up (2026-08-18) — see [Sources](Sources/Server%20Setup.sources.md). **The promise is kept anyway, and by construction rather than because the question came back the other way**: Architecture never re-runs the action over a half-finished machine, it clears the half-finished state first. *(This read **unresolved** until 2026-08-23, five days after the answer.)*

**One way of unpacking a Blender breaks it silently.** Blender's documentation names the one tool its archive must be unpacked with; unpacked with another, that tool reported success both times it was run and the result would not start at all. Label: **documented and observed**, on a rented Linux machine. Nothing in the outcome says it went wrong, so Architecture has to use the right tool rather than check afterwards.

That safety is about the step, not about the machine's other work. Making a machine ready may still restart it and take a render down, whether it is the first run or the fourth — which is what the warning above is for.

**Smoozy runs one setup step at a time on a machine.** Two installs going at once on one machine is a way to break both. This is per machine only — each server's setup is its own, and several machines can be set up at the same time.

**Several Blenders can be picked from the list at once, and they install one after another.** Label: **Creator-stated** (2026-10-06): *"The user should be able to install several Blender versions at the same time."* Each is its own install, so the rule above holds. A failed install stops the ones still waiting, and Smoozy names the ones it did not install.

**If Smoozy closes before every one picked has started, the ones that never started are named when it opens again.** *Added 2026-10-16, step 10c's owed piece 4, on the build runner's ruling R3 that this is a hole under Rule 8: Smoozy went quiet about installs the user asked for. No auditor has seen it.* *Widened 2026-10-27 to every act waiting its turn, below.*

**Anything the user asks for on a server while a setup runs there waits its turn, and the Set up card lists it until it starts.** Label: **Creator-stated** (2026-10-27), the nineteenth notes, note 2: *"The user has to be able to do these things simultaneously. On the server they may happen sequentially, but it mustn't be for the user to figure out that he has to wait. … he should be able to click the button to put all those actions in queue. And the UI has to reflect that, so that the user isn't left hanging."* That is every act the card offers while a setup runs: installing a Blender from the list or from the user's own computer, removing one, and installing Telegram reporting. **Setting the server up again is not offered on the card while a setup is running there**, and comes back when the run ends. Label: **Creator-stated** (2026-10-30), the twenty-fourth notes, note 1: *"Server setup. Set up again should not be available (grayed out or just non-existent) when setting up is actually happening. There's no point in this button in this scenario."* A setting up again already waiting, or asked for from another place in Smoozy that still offers it, still waits its turn the same way. *Until that day the running card offered setting the server up again as well. No auditor has seen this.* Each runs as its own setup, in the order asked, so one setup still runs at a time. Nothing is refused because another setup is running. *Until that day such a press was refused, and the refusal was wiped from the card at once, so the user saw nothing happen. No auditor has seen this.*

**What stops the rest is the same for every act as for installs.** An act that fails, or that the user stops, stops the ones behind it, and Smoozy names them. **So does a setup that restarts the server**: the ones behind it do not start and are named. Where an act carries a warning — removing a Blender a job needs, or a setup that may restart a busy server — the warning is shown when the user asks for it, not when its turn comes, and covers the work on the server at that moment. If Smoozy closes before they start, they are named when it opens again, as above. Label: the build runner's rulings of 2026-10-27, under the Creator's standing delegation. *No auditor has seen this.*

**Installing needs the machine's permission, and whether a given machine gives it is now settled — and it differs by the kind of machine rented.** Label: **settled at Architecture** (2026-08-23). This is the same thread the [File Browser spec](File%20Browser.md) already carries for elevated access. See [Sources](Sources/Server%20Setup.sources.md).

**What is settled is what asking for it costs the user, and it is settled once for the whole app.** Where a step here is refused for lack of permission, Smoozy offers to try again with elevated access; where that needs a password, it asks at that moment and the user chooses whether it is kept for that one action, for as long as the connection lasts, or until they clear it. Smoozy never asks before a step needs it, and a password that stops working is forgotten rather than retried. The rule and its three choices are *Security* in [Whole app](Whole%20app.md); this module only ever reaches it at the moment a step is refused. **It matters more here than anywhere else**, for the reason the next paragraph gives: a browse refused loses one folder, and a machine that refuses this may not be set up at all.

**A Blender needs less of that permission than the rest.** A Blender is a self-contained folder that can be put anywhere, so putting one on a machine changes nothing the whole machine shares, and an add-on goes inside that Blender's own settings. Label: **documented**, all four versions. What still leans hard on the machine's permission is making it ready: a machine that refuses it may not be set up at all.

## What Server Setup does not do

- It does not rent, bill, power on, or power off the **machine** — that boundary is the whole app's, owned by the [module map](Whole%20app.md), and restarting a machine for a setup step is its one stated exception. Nothing else here touches the machine's power.
- It does not make the machine's GPUs available to a render. That happens when a job is run, and belongs to **Rendering**.
- It does not choose which Blender renders a job — that is **Render Settings**', from what this module installed.
- It does not connect to a machine, and never reaches one the user has not connected. It works over a connection **Servers** holds.
- It does not browse a machine or send up the user's own work — that is **File Browser**'s. The only thing it sends up is a Blender build.
- It does not read a `.blend` — not for its settings and not for a missing engine, both of which are **Render Settings**' Pre-load, and not for what the file points at, which is **Dependency Upload & Remap**'s. It offers to install what that read asks for; it does not do the reading.
- It does not keep a catalogue of add-ons, study them, or judge whether the user may put one on a rented machine.
- It does not install, or run, a program the user brings that is not an add-on. An outside physics engine or anything else with its own installer is beyond what Smoozy does. The one program it puts on a machine itself is Telegram's piece, above.

## What is not settled

Each of these is an outside fact a promise above rests on. Every one is parked in [Open Threads](../Groundwork/Open%20Threads.md), and every one is cited in [Sources](Sources/Server%20Setup.sources.md), including the one this module leans on but another document owns — elevated access, owned by File Browser. What Blender Research settled is written into the body above and is not repeated here.

- **What a rented machine needs beyond a graphics driver before a render will run on it. Settled at Architecture** (2026-08-23): a machine can arrive missing pieces of system software Blender needs to start, and the ready action finds what is missing and installs it explicitly — where there is a Blender to check the machine against, and where the machine lets Smoozy install anything at all. Where either is absent that half does not run, and Smoozy says so rather than claiming the check passed. There is no one list: what is missing is a property of the image the machine was rented with. What is still not established is any figure for memory, disk or processor, which is not a Blender question either.
- **Whether a machine can be read for the setup state it is in. Settled at Architecture** (2026-08-23): yes, from what the setup itself wrote down as it went, which survives a reboot. It cannot be worked out on a machine that recorded nothing.
- **Whether blender.org publishes a list of its builds that a machine can read.** Fetching a published build is settled, and so is that a machine-readable listing exists elsewhere — a shop-front for Linux software carries one, which is not the machine's own distribution packages. **blender.org's own is settled too** (read 2026-08-19): its build service publishes a machine-readable listing and the daily builds sit on it. Label: **settled at Architecture** (2026-08-23). ~~It changes nothing here — the Creator's ruling of 2026-08-12 already fixes where the list Smoozy offers comes from, and daily builds are not on it.~~ **Corrected 2026-10-02: unfinished builds are listed and fetched from it** (*From a list Smoozy offers*, above), on the Creator's ruling of that day.
- **Whether Smoozy can restart a rented machine over the connection it holds. Answered: yes**, on one rented Linux machine; the same address and port answered again in about ten seconds with a new boot id and an intact disk.
- **Whether a restart really stops everything in flight on the machine, including a running render. Answered for a transfer and for a render** — an 8 GB write in flight died and did not come back, leaving 4.7 GB under the file's final name with nothing marking it incomplete (2026-08-13); and two real restarts with a Cycles render in flight, taken over the connection rather than from the provider's console, killed it (2026-08-15/16). **The dependency check is the one part nobody posed, and it will not now be posed.** Settling it needs a rented machine restarted with a check genuinely under way, and the Creator ruled on 2026-08-31 that there will be no further rental. Label: **permanently unresolved**. What holds without it is settled at Architecture — see the [Server Setup architecture](../Architecture/Server%20Setup.md), clause T7 and its unresolved list item 2, Row 109: a check is taken to die with the machine, the record of what it was doing ends with no outcome, and the tidy-up that runs once the setup is finished writes what became of it either way, whatever killed it. **What breaks:** that a restart stops a dependency check is worked out from what a transfer and a render do rather than seen, and that limit is written down in only that one place.
- **Whether a machine permits the elevated access making it ready needs. Settled at Architecture** (2026-08-23), and it differs by the kind of machine rented. On an ordinary rented machine the access exists, but it is held by the account the machine was handed over with rather than by the login Smoozy runs as — and putting Smoozy's own pieces on the machine needs none of it, while everything about making the machine ready needs all of it. On a container a login without that access has no route to it at all, and the fullest access inside a container still reaches only as far as the container was given, which does not include the driver. How the access is obtained is not part of this either: what the user is asked and what Smoozy keeps is settled under *Security* in [Whole app](Whole%20app.md). The narrowing above stands — a machine that refuses it may not be set up at all. This is the same thread [File Browser](File%20Browser.md) owns.

Three come from what the research found rather than from before it.

- **Whether Smoozy can tell a machine whose cards work from one whose driver is broken. Answered: a job can be made to say what did the work, in every version, and only once it has finished.** The setup still cannot show it and neither can a plain job, but a job asked the right way names the part of the machine that rendered — through one route in Blender 4.5 and another in the newer three. What Smoozy does with that is [Rendering](Rendering.md)'s and [Queue & History](Queue%20&%20History.md)'s.
- **Whether installing an add-on disturbs a render already running. Answered: it does not.** Tried both ways round in all four versions on both machines, with every frame compared picture against picture and not one value differing. A Blender that is rendering does not hold the lock an install needs, which is why. What is worth carrying instead is that a second setup fired while one holds that lock is refused at once rather than made to wait.
- **Whether anything can be checked about an installed add-on beyond installed-and-switched-on. Answered, narrowly.** Switching one on fails outright and names the fault where the add-on cannot be loaded, so that much is machine-readable at the moment of switching on. Nothing anywhere tells you beforehand whether the part a render needs will work, the list of switched-on add-ons records what was asked for rather than what loaded, and an install Blender refuses still ends at a successful status — so an install is judged by what the machine holds afterwards and never by the command.

One thing about add-ons is still owed, and it is about money rather than about Blender.

- **Whether a copy of an add-on already set up on the user's computer carries licence material inside it.** What this module says about licences has to change if it does. Neither the ruling of 2026-08-31 against further Blender research nor the one against further rentals reaches this: the way to an answer is reading a particular seller's own published material, and the project's fact register already records that neither a machine nor Blender's documentation could answer it (Fact 56, Row 98). Nobody has been asked yet, because the question was raised out of an agent's own knowledge and has to be re-worded blind first. **What breaks meanwhile: nothing Smoozy does.** The promise above holds either way — Smoozy does not ask for a licence key, does not read one, and does not check one — and what an answer would change is only what this module *says* about licences.

One more is added here because it was being stated as an answer when it is a silence.

- **Whether any route can see a switched-off older-style add-on on a machine. Never asked, and permanently unresolved. Added 2026-09-02.** Until that date this spec said flatly that such add-ons are *not covered at all*, and three further documents repeated it word for word. The research says something different: whether any route gives one complete list of everything installed, switched-off older-style add-ons included, is **not established** — nobody posed it. **A silence is not a finding**, and the wording above now says only what was established. Settling it would need Blender research, which the Creator ruled out on 2026-08-31, so it stays a silence rather than waiting for an answer. **What holds:** the ruling of 2026-08-12 stands untouched — the listing is taken as good enough and Smoozy never installs over what it cannot see — and *nothing is installed twice* remains a promise about what Smoozy can see, which is what it already said. **What breaks if the guess is wrong, both ways round.** If such an add-on really is invisible to every route, Smoozy can install over a copy the artist put on the machine by hand, without being able to warn about it — the cost the 2026-08-12 ruling knowingly accepted, and the harder of the two. If instead some route does reach one, nothing breaks at all: Smoozy would simply be more cautious than it needs to be, and would be disclosing a cost it never pays. Either way no promise here moves, which is why this is written down rather than chased.
