# Sources — Telegram

*Where the outside-world facts in the [Telegram spec](../Telegram.md) came from. The spec carries each fact's label in place; this file carries the citation behind it, and what that citation does not cover.*

*Note: most of what the Telegram spec settles is Smoozy's own decision — that the bot runs on the machine, that it does nothing the app cannot do, that the user makes one bot and Smoozy pools it across machines, the five things that can be done from a phone, and the first-frame check. Decisions have no source and earn no entry here, whoever settled them.*

**Where the Telegram facts below came from, and what changed on 2026-08-12.** All but two were raised by an agent from its own knowledge, in the conversation that settled this module (2026-07-29), with no source consulted. **Most of them have now been tested against a real bot**, on three rented Linux machines holding one token at once, and each says so where it stands. The record of that run — what was done, what came back, and what it does not cover — is `Audits/Specs/Telegram/Behaviour tests 2026-08-12/Findings.md`, with the scripts beside it. **Ruled 2026-09-01, because a sweep flagged these three pointers as possibly reaching past a door they may not.** They do not. **The rule that nothing downstream may open `Findings/` is about the Blender Research folder**, and this is a Specs-owned test record that happens to share the word in its name; Telegram is not Blender and this run was never part of that stage. **The pointers stay.** What matters more is that **every entry below states its own result in full** — the refusal's exact words, the counts, the timings — so **a reader who is forbidden `Audits/` for some other reason loses nothing but the ability to re-check it.** Telegram is not Blender, so none of this waited for the Blender Research stage: these are fast-changing outside facts of the kind Rule 2 sends to Architecture.

**The two load-bearing ones are settled, and both went the way the spec hoped.** Several holders of one token can send at once; only one can receive; and a holder that is not receiving can read the pinned message without disturbing the one that is. So the promise of **one bot for life, covering every machine at once** stands on tested ground rather than on an agent's memory.

**Telegram's own documentation settles neither, and that is worth recording.** It was read the same day (core.telegram.org/bots/api, /bots, /bots/features, /bots/faq, /bots/webhooks, /bots/api-changelog, checked 2026-08-12) and **it never addresses more than one program holding one token** — not for sending, not for receiving. The only exclusivity it states is between `getUpdates` and a webhook, which is a different question. The nearest it comes is a security warning: *"Everyone who has your token will have full control over your bot."* So documentation could not have answered this, and the test was not a shortcut past a page somebody failed to read.

**Some entries below are Blender facts rather than Telegram ones**, and those did wait for the Blender Research stage. Each names the comparison question it comes from and none carries a quote of Blender — the comparison is what a reader opens.

**The two exceptions were checked against Telegram's own documentation on 2026-08-03**, under a stated exception allowing that one check: that a bot can pin a message, and what the pinned message reported for a chat is. Both are marked **documented** below, and neither rests on an agent's memory.

- **That a bot is made by talking to Telegram's own bot-making chat, which asks for two names — one free, one that must be unique across all of Telegram — and hands back a token.** Label: **Creator-stated** (2026-08-12), from making one. It asks for exactly two names, as the spec assumed. **One detail is gentler than the spec expects**: the token arrived as its own field to copy rather than buried in a longer message, so the promise to take a whole pasted reply and find the token inside it is insurance rather than the ordinary case — worth keeping, since a phone paste may still carry surrounding text, but the walkthrough should not be written as though hunting were the norm. **A link of the form `t.me/<name>` opened a chat with the bot directly**, which the spec's last setup step needs. Label: **observed in a test** (2026-08-12). **And one thing nobody had written down: the user must press Start before the bot can be messaged at all** — the spec already has them press Start, so nothing changes, but it is a requirement rather than a courtesy. What none of this covers: what the bot-making chat does when a unique name is already taken, which was not provoked.

- **That any number of holders of one token can send messages as that bot, but only one can receive what the user sends or taps.** Label: **observed in a test** (2026-08-12, three machines, one token) — see `Audits/Specs/Telegram/Behaviour tests 2026-08-12/Findings.md`. **Both halves hold.** Sending is not exclusive in any way: two machines sent 120 messages into one conversation at the same time with no refusal, and every ordinary call behaved the same. Receiving is exclusive and says so plainly — `409 Conflict: terminated by other getUpdates request; make sure that only one bot instance is running`.

  **Two things the test found that nobody had assumed, and both matter more than the fact itself.** **The newest request always wins**, whichever machine it comes from, so a machine takes over listening simply by asking — which is a free hand-over and also a hazard. And because the newest wins, **a machine that retries beats one that asks once, so two machines that both retry destroy each other**: three machines all polling for a minute produced 61 attempts, 60 conflicts and 1 success, with nobody listening for about 92% of the time. Arbitrating which single machine listens is therefore a **requirement** on Architecture rather than a refinement, and it is parked in [Open Threads](../../Groundwork/Open%20Threads.md). Nothing in the spec's body changes: the user still meets none of it.

  What the test does not cover: more than three machines, any run longer than a minute, and webhooks, which were not exercised at all.

- **That any holder of the token can read a conversation's pinned message at any time, without receiving anything.** Label: **observed in a test** (2026-08-12) — see `Audits/Specs/Telegram/Behaviour tests 2026-08-12/Findings.md`. It holds, and the disturbance question — the one that would have killed it — was answered too: one machine polled a full 25 seconds at 200 while another read the chat three times during it, and the listener was never thrown off. Reading is cheap enough to lean on: three machines reading once a second for a minute gave 168 reads and no refusals.

  **The whole idea was then run end to end rather than assembled from parts.** With two machines: the owner of a job never called for updates, the listener held no job, and a pinned message was the only thing between them — a tap reached the right machine and it acted **1.4 seconds** later. With three machines and two jobs, each of two taps reached the machine holding that job, in **0.9 and 0.7 seconds**. The answer never goes to the machine that asked; it goes to whichever is listening, which can always tell who it was for, either from the id of the message replied to or from what the sending machine wrote into its own button.

  **One limit is sharp enough to be a design constraint rather than a caveat.** The pinned slot holds one message, and **an instruction written on it can be lost with nothing to show it existed**: two machines wrote ten milliseconds apart, Telegram told both they had succeeded, and a third machine reading every 1.5 seconds only ever saw the later one. So the noticeboard needs a protocol for writing, not just a place to write. That is Architecture's and is parked in [Open Threads](../../Groundwork/Open%20Threads.md). None of this reaches the spec's body: what Specs needs is only that **one bot can cover every machine**, and it does.

- **That the pinned message reported for a chat is the most recent one by sending date.** Label: **documented and observed in a test** — Telegram's Bot API documentation, core.telegram.org/bots/api, checked 2026-08-03 and again 2026-08-12, where `ChatFullInfo` describes `pinned_message` as *"The most recent pinned message (by sending date)"*; confirmed by test on 2026-08-12, where one machine's pin displaced another's from the reading and both machines then read the newer one.

  **The test added the part the documentation does not say, and it softens the clash.** Pinning is a **stack, not one slot**: unpinning the newest revealed the older one underneath, so an older pin is hidden rather than destroyed. Deleting a pinned message left the slot reading absent rather than falling back. So the two things that wanted this slot — the spec's body then had **each machine keeping its own pinned message current**, and the machinery above has machines **passing notes through a shared pinned note** — were in tension, but the tension was about what the single *reported* pin says rather than about anything being lost. This entry handed the clash over in those words — *"Architecture owns the resolution; nothing in the spec's body turns on it."* — and Architecture has since taken it: **the shared note keeps the pinned slot and each machine's status message is not pinned**, ruled by the Creator on 2026-08-19 out of Architecture's Round 1, and the spec's body now says so. That nothing in the spec's body turned on it is what made the hand-over safe. What this does not cover: group conversations, how deep the stack goes, and whether an older pin can be read without unpinning the newer one, which was not tried.

- **That a bot can pin a message in the conversation at all.** Label: **documented and observed in a test** — Telegram's Bot API documentation states that in a private chat all non-service messages can be pinned, and that no administrator right is needed there: core.telegram.org/bots/api, checked 2026-08-03; pinned and unpinned repeatedly from three machines on 2026-08-12. What rests on it is the shared note the machines pass their notes through, which is the one pinned message in the conversation; the message that keeps itself up to date is **not** pinned, by the Creator's ruling of 2026-08-19. **One thing the test noticed and the documentation does not say: a pin produces an update**, so the listening machine hears about every pin the others make. Whether that is noise or a useful signal is Architecture's. What this does not cover: pinning in a group conversation, and how many messages can be pinned at once.

- **That a bot can edit a message it has already sent.** Label: **observed in a test** (2026-08-12). It can, and the test went further than the assumption did: **any holder of the token can edit any message the bot sent, including one a different holder sent**, and two machines editing the *same* message at the same time had fifteen edits each accepted with no conflict. That is what makes a shared noticeboard possible at all. The one thing it does not make safe is two machines writing *different* instructions at once — see the pinned-message entry above, where an instruction was lost.

- **That Telegram allows messages at the pace this spec assumes.** Label: **observed in a test** (2026-08-12), and the answer is comfortable. Forty edits of one message in 9.3 seconds and thirty messages in 4.9 seconds both went through with **no refusals**; two machines sending sixty each into one conversation at the same time gave 120 messages and **no refusals**. The rate fell from about six a second to about three under two machines. **Corrected 2026-08-21: this said Telegram pushed back by slowing down rather than by refusing, and that nothing in any run produced a `429` or a `retry_after`.** Neither is true. This project's own record holds two `setWebhook` refusals — `{"ok":false,"error_code":429,"description":"Too Many Requests: retry after 1","parameters":{"retry_after":1}}` — and the field is documented under `ResponseParameters` on the very page these entries were read from: *"Optional. In case of exceeding flood control, the number of seconds left to wait before the request can be repeated"* (`https://core.telegram.org/bots/api`, read 2026-08-20). **And the rate is published**, on Telegram's own Bot API FAQ, `https://core.telegram.org/bots/faq`, read 2026-08-20: *"In a single chat, avoid sending more than one message per second. We may allow short bursts that go over this limit, but eventually you'll begin receiving 429 errors."* — which describes what was seen here exactly: a permitted short burst, not a ceiling. **What is true and stays true is the narrow form**: no *send* this project made was ever refused, at the depths tried. **What this costs the spec is nothing it promises** — a picture per frame, several machines in one conversation and a status message on a clock all still work — but the third is now known to be **62% of the published per-chat budget at rest and over it under load**, which `Preparation/Architecture/Telegram.md` §21 item 4 carries with the arithmetic and which is with the Creator, whose 2026-08-19 ruling set the cadence. What it does not cover: any run longer than a minute; and whether an **edit** counts against a **message** rate is published nowhere.

- **That a bot can send a short moving picture that plays in the conversation.** Label: **observed in a test** (2026-08-12), with one condition the assumption did not know about: **it must be a video file rather than a GIF.** A GIF sent as an animation was accepted but filed as a plain document; an MP4 sent the same way came back properly recognised, with duration, dimensions and a thumbnail, and the Creator confirmed on the phone that **it plays by itself without tapping**. The GIF played too, but as a document. So the feature stands, and what the machine must produce is an MP4 — which bears on the neighbouring Blender fact below, since that is what the frames have to be turned into.

- **That the machine can turn finished frames into a short moving picture.** Label: **documented** — Blender Research comparison, **Images 7**; the same in Blender 4.5, 5.0, 5.1 and 5.2, and it works with no window open. This was an open Blender question beside the Telegram one above, and it is now closed.

  **The two halves fit, and that is worth stating rather than leaving to be noticed.** The Telegram test above found that a moving picture must be a **video file** rather than an animated image, and **Images 7 records that with the MPEG-4 container and the H.264 codec Blender writes an MP4** — the run wrote `out_0001-0006.mp4`, reported as ISO Media MP4, in all four versions on both machines, and the same question records that pairing writing a playable file in all four on both. *(The container and codec are added 2026-08-30: they are a setting whatever produces the moving picture has to make, not something a headless encode does of its own accord — **Images 3** lists ten containers and **Images 4** records that the setting refuses none of them while the encoder refuses plenty. Nothing the spec promises moves; what changes is that the production must name the format rather than inherit it.)* So the format Blender produces is the format Telegram recognises, and nothing has to be converted in between. Neither topic could have said this alone: the Blender side never asked what Telegram accepts, and the Telegram side never asked what Blender writes. What it does not cover: how long "short" may be, which no version's sources put a limit on, and Windows, untested.

- **That the machine can make a small, plainly viewable copy of a rendered frame.** Label: **observed** — Blender Research comparison, **Images 8**; the same in Blender 4.5, 5.0, 5.1 and 5.2, and it works with no window open. Every preview this module sends is such a copy. What it does not cover: Windows, untested.

- **That a picture shows a missing texture only where that texture was feeding colour, and leaves no mark that reads as a failure where it was feeding anything else.** Label: **observed** — Blender Research comparison, **Images 9**; the same in Blender 4.5, 5.0, 5.1 and 5.2, on both machines. The one exception to the label is the transparency case, which is what a measured value implies rather than something any test rendered, and the spec's body says so where it stands. [Queue & History](../Queue%20&%20History.md) and [What a job writes](../What%20a%20job%20writes.md) own this promise and its limits; this module inherits both, for the frame pictures and for the first-frame check alike. What it does not cover: a picture reaching the render through Blender's older kind of texture block rather than through a shader node; roughness and metallic as such, where the conversion behind them was measured but no render was made with the value actually driving either; Windows, untested.

- **That what a job prints about a missing image texture depends on the Blender version and, in 4.5, on the render engine.** Label: **observed** — Blender Research comparison, **Images 2**. In 4.5 a Cycles render prints nothing that tells a missing picture from a present one, while an EEVEE render prints one line and prints it only when the picture is missing. [What a job writes](../What%20a%20job%20writes.md) owns this fact and its limits; this module inherits it, and nothing the phone shows turns on it. What it does not cover: what the newer three print on an EEVEE render, which is recorded nowhere — every line on record for those three is Cycles' own, which is why the spec now names Cycles there; whether Cycles ever prints the 4.5 EEVEE line, which was never asked; the EEVEE run was on the rented Linux machine alone; Windows, untested.

- **That the machine can be asked which of a file's references are missing, and that it answers by name.** Label: **observed** — Blender Research comparison, **Reading a file 6**; the same in Blender 4.5, 5.0, 5.1 and 5.2, and it works with no window open. This is the second half of the spec's missing-texture sentence, and it is a different question from the one above: what a render *prints* differs by version, what the machine can be *asked* does not. What it does not cover: Windows, untested.

- **That a bot can put several pictures into one message, and how many.** Label: **observed in a test** (2026-08-12). **Ten, and no more** — eleven was refused outright with `too many messages to send as an album`. Two albums of ten sent back to back read as **two blocks of ten rather than one of twenty**, confirmed by the Creator on the phone, so ten is the cap on what reads as one group and not merely on one call. **This is exactly the case the entry anticipated**: the contact sheet at the end of a job shows a **sample** of what came out rather than everything, since a job of two hundred frames cannot be one message. What the spec promises — one message showing what came out — has to narrow to that, and where the sample comes from is Design's and What a job writes'.

- **That there is a limit on the size of what a bot can send, small enough to rule out a full-resolution frame.** Label: **observed in a test** (2026-08-12). A photo is capped at **10,485,760 bytes exactly**, and the refusal says so in as many words. There is a **dimension limit besides the size limit** — 6000 by 6000 was refused as invalid dimensions at only 119 KB — which the assumption never contemplated and which matters more for renders, since a large frame fails on its shape before its weight. An ordinary file caps somewhere between 45 and 55 MB, not narrowed further. So the spec's *small copies only* is not a preference but the only thing that works.

- **That Telegram itself makes the small copies.** Label: **observed in a test** (2026-08-12). Every photo Telegram accepts comes back in **five sizes** — a 1920 by 1080 send returned 90×51, 320×180, 800×450, 1280×720 and the original. This does not change what the spec promises, and it is recorded because it bears on a question Architecture already holds: where a preview's small copy is made. Telegram making its own does not remove the need for the machine to make one first, since the full-size frame must be small enough to send at all.

- **That an answer from the phone reaches the machine that asked for it.** Label: **observed in a test** (2026-08-12), and **it does not.** A tap or a reply goes to whichever machine is listening, never to the machine that sent the message — which follows from receiving being exclusive. What it carries is enough to route: the id and text of the message replied to, or whatever the sending machine wrote into its own button. Nothing in the spec's body assumed otherwise, since the spec never says which machine hears what; it is recorded because every action the phone offers now has a known path, and because the routing it makes possible is parked as a want in [Open Threads](../../Groundwork/Open%20Threads.md).

- **That a bot can be limited to answering one conversation and will ignore anything from anywhere else.** Label: **partly observed in a test** (2026-08-12), and the untested half is the one that matters. **What was seen:** every update carries the conversation it came from, so a machine can tell one conversation from another and answer only the chosen one. That is the whole of what the promise needs on Smoozy's side. **What was not tested:** whether a stranger can reach the bot at all, and what the bot sees when they do — nobody else's Telegram account was available. So the filtering is known to be possible and the thing being filtered has never been produced. Confirm at Architecture with the question of how the token is kept, and with how Smoozy proves the conversation is the user's, which the spec leaves to that stage. Telegram's own documentation is blunt about the stakes and is worth quoting where this is settled: *"Everyone who has your token will have full control over your bot."*

- **That a render cannot be held part-way and picked up where it left off, so carrying on means a fresh render of the frames that are left.** Label: **documented** — Blender Research comparison, **Frames 2**; the same in Blender 4.5, 5.0, 5.1 and 5.2. This replaces what the Creator stated on 2026-07-29 — *that a render cannot be stopped part-way and picked up again*, held at about 98% rather than certain — and it is a narrowing rather than an overturning, so it is recorded here rather than left as a silent edit. What the Creator stated is right about the thing that matters: there is no pause and resume, and only whole frames reach the disk **for a stop landing at no particular moment during the rendering — which is the qualifier *Frames 2* attaches itself, and it names the other case in the sentence beside it**: a stop aimed at the moment a frame's own file appears *"does leave something at that frame's path — a short file, for a polite terminate and for an uncatchable kill, though not for an interrupt"*, and the same question says why it matters for carrying on, since a frame is skipped on the bare existence of a file at its path. *(The exception is added 2026-08-30. The two-job shape is unchanged: Smoozy ends a render with the interrupt and never with the other two — `Job files and outputs` C32 — and no run by anybody has ever caught an interrupt leaving a short image.)* What research adds is that the remaining frames can be rendered afresh, which is exactly the two-job shape the first-frame check already has. So the check is unchanged, and it is now carried by research rather than by recollection. What it does not cover: an animation written as a single video file rather than as separate frames, and Windows, untested.

- **That a render can be told to finish the frame it is working on and then stop.** Label: **unresolved** as an assumption, and now **answered no**. Blender Research comparison, **Frames 11**: no version has any such control, inside a window or outside it, in Blender 4.5, 5.0, 5.1 and 5.2 alike; **the frame in flight is discarded, with nothing written for it whole or partial, where the stop lands during the rendering** — which is the qualifier *Frames 11* carries in its own words, and it names the other case beside it: an interrupt arriving once that frame's own file has already begun to appear does not cut the write, Blender finishes it, and the frame is whole. *(The condition is added 2026-08-30; this read *always discarded*.)* **The action is removed either way**, since neither case is the frame being finished on request. The assumption was an agent's, raised on 2026-07-29 and never checked, and the entry it replaces said plainly what a negative answer costs: the action is **removed**, not weakened. That has been done in this document — the phone now offers five things instead of six, and the user's only way out of a wrong render is the one that throws the frame in hand away. **It lands on two other documents.** The same action at the desk is written into the [Rendering spec](../Rendering.md) and the [Queue & History spec](../Queue%20&%20History.md), and both rest on the same assumption; neither is this document's to change. What the citation does not cover: how long a stop takes to take effect, which differs by version on the Creator's Mac and is untested elsewhere, and Windows, untested.

## Added 2026-10-27 — a finished video sent to the chat (the Creator's nineteenth notes, note 4)

- **Telegram takes a video file of up to 50 MB from a bot.** Label: **documented**. `https://core.telegram.org/bots/api`, **read 2026-08-20** and quoted at `Preparation/Architecture/Sources/Telegram.sources.md` entry 44: `sendDocument`, *"Bots can currently send files of any type of up to 50 MB in size, this limit may be changed in the future."*, the identical sentence on `sendVideo`, and *Sending files*: *"10 MB max size for photos, 50 MB for other files."* **Not read again on 2026-10-27**: the session that wrote this could not reach `core.telegram.org`, so the figure is the 2026-08-20 reading, and the page says it *"may be changed in the future"*. Whether *50 MB* means 50,000,000 or 52,428,800 bytes is not established (`Architecture/Telegram.md` §21 item 32), so Smoozy sends nothing above 50,000,000 bytes. **Not covered:** how a phone shows a video in a container other than MP4 sent this way.

## Added 2026-10-29 — one look for every message (the Creator's twenty-first notes, note 5)

- **That a bot's message can carry bold and italic text, in its text and in a picture's caption, sent as a list of marked ranges beside the text.** Label: **documented**. `https://core.telegram.org/bots/api#formatting-options`, **read 2026-10-29** (the page then headed *Bot API 10.3*, August 24, 2026). *Formatting options*: *"The Bot API supports basic formatting for messages. You can use bold, italic, underlined, strikethrough, spoiler text, block quotations as well as inline links and pre-formatted code in your bots' messages."* `MessageEntity`'s `type` lists *"“bold” (**bold text**), “italic” (_italic text_)"* among its kinds; its `offset` is *"Offset in UTF-16 code units to the start of the entity"*. `sendMessage` takes *"entities … A JSON-serialized list of special entities that appear in message text, which can be specified instead of parse_mode"*, and `sendPhoto` the same as `caption_entities`. On nesting: *"bold, italic, underline, strikethrough, and spoiler entities can contain and can be part of any other entities, except pre and code."* **Not covered:** how each Telegram app draws them; an older app was not looked at.
- **That a bot cannot use its own small pictures inside a message unless its owner pays Telegram for it or has bought the bot a special name, so the badge's rounded shape cannot be sent as such.** Label: **documented**, the same page and reading: *"Custom emoji entities can only be used by bots that purchased additional usernames on Fragment or in the messages directly sent by the bot to private, group and supergroup chats if the owner of the bot has a Telegram Premium subscription."* **Not covered:** whether the Creator's own account would qualify; the spec does not rest on any one user's subscription.
- **That a button's words are plain text, and a button can be asked to show in red.** Label: **documented**, the same page and reading. `InlineKeyboardButton`: `text`, *"Label text on the button"*, a plain string with no entity list; `style`, *"Must be one of “danger” (red), “success” (green) or “primary” (blue). If omitted, then an app-specific style is used."* **Not covered:** how an older Telegram app draws a button with a style it does not know; nothing relies on the colour.
- **Not a Telegram fact, and labelled as what it is:** that the coloured square characters (red, orange, yellow, green, blue, purple, brown) exist and a phone draws them as coloured squares is an **assumption**, not read on any page in this pass. Nothing breaks if a phone draws one differently: the bold name still names the server.

## Added 2026-10-31 — the bot's commands (the Telegram discussion of that day)

- **That typing `/` in a chat with a bot lists the bot's commands with a line each, that picking one sends it at once, and that a menu button beside the message field lists them too.** Label: **documented**. `https://core.telegram.org/bots/features`, **read 2026-10-31**, *Commands*: *"Suggest a list of supported commands with descriptions when the user enters a / (for this to work, you need to have provided a list of commands to @BotFather or via the appropriate API method). Selecting a command from the list immediately sends it."*; *Menu Button*: *"In all bot chats, a menu button appears near the message field. By default, tapping this button opens a menu that can hold some or all of a bot's commands, including a short description for each."* **Not covered:** how any one Telegram app draws the list or the button; the drawing shows the shape, not Telegram's own look. The method the bot sets its list with is the Architecture's, and its sources file quotes it.
