# Sources — Render Settings

*Where the outside-world facts in the [Render Settings spec](../Render%20Settings.md) came from. The spec carries each fact's label in place; this file carries the citation behind it, and what that citation does not cover.*

*Note: the way settings behave — starting at the file's own value, a typed number winning, a cleared setting handing back, an untouched view layer box looking at the first frame and a touched one covering the range, a typed sample count flattening the per-layer ones — is Smoozy's own decision throughout, so none of it earns an entry here. Only the Blender behaviour those decisions are built on does.*

*Where a fact comes from Blender Research, the citation is the topic and question number of the checked comparison — the document downstream reads and stops at. The findings behind it are the paper trail and are not part of the reading.*

## Facts from Blender Research

- **Every setting this page offers can be imposed on a render started from outside Blender.** Label: **observed**. **Settings 1** — see the [comparison](../../Blender%20Research/Comparison/Settings.md). Four are stated directly at the start of a render; the sample count, the resolution percentage and whether a view layer renders have no route of their own and were watched being set by an instruction given as the render starts, in all four versions on the Creator's Mac and on the one-card rented Linux machine. That entry also carries that neither route changes the `.blend`. This closes the marker the round-1 audit added, which held that nothing in this project had established it.
- **A frame range is a first frame, a last frame and a step**, and a stepped run counts forward from the first frame, rendering the last only where the step lands on it. Label: **documented** and **observed**. **Frames 8** — see the [comparison](../../Blender%20Research/Comparison/Frames.md). Identical in Blender 4.5, 5.0, 5.1 and 5.2, on the Mac and on the one-card rented Linux machine. This replaces the earlier entry, which recorded the step as agent-raised, Creator-confirmed and awaiting research.
- **Blender can be asked for a list of frames that is not a plain run** — single frames, a run, and both mixed in one instruction — and a step has nothing to act on in a list. Label: **observed**. **Frames 7**, same comparison. The list forms — single frames, a run, and both mixed in one instruction — are identical in all four versions on both machines. **The step half is narrower and the condition travels with it (narrowed 2026-08-30, downstream citation audit, which found this entry claiming both machines for both halves):** that a step has nothing to act on in a list was run **on the one-card rented Linux machine alone**, in all four versions; the Mac was never asked, so it is not established for macOS. This closes the marker that held it unresolved.
- **Blender does not tidy such a list.** A frame named twice is rendered twice, and the frames are rendered in the order written rather than in order. Label: **observed**. **Frames 7**. This does not contradict what Smoozy promises, but it means Smoozy has to drop repeats and put the frames in order itself before the render is started; the spec now says so. Not established: nothing here says what a very long list costs beyond the point at which the machine itself refuses it.
- **One read of a `.blend` answers, for every view layer, whether it renders at any frame later asked about — where the switch is keyframed.** Label: **observed**. **Reading a file 3** — see the [comparison](../../Blender%20Research/Comparison/Reading%20a%20file.md). The switch takes a keyframe, the curve lands on the scene and can be read out, and a render started from outside honours it frame by frame, in all four versions on the Creator's Mac and on the rented Linux machine. Two version differences sit behind it, also there: the route to the curve differs between 4.5 and the newer three, and the switch's declared starting value reads off in 4.5 and on in 5.0, 5.1 and 5.2. **What it does not cover**: a driver on that switch rather than a keyframe, and a script inside the file changing it as each frame comes round — this research tested neither in any version. **One shape of each has since been tried outside this research**, in Blender 4.5 and 5.2, by this project's own test of 2026-08-19 recorded in the [Render Settings architecture](../../Architecture/Render%20Settings.md): a driver written as an expression, and one in-file script shape, that one on both sides of the machine setting that decides whether a file's stored scripts run at all. The read and the render agreed each time. Label for that much: **observed** — by this project rather than by the comparison above, on the two shapes named and no others. **The marker the spec keeps open is now the narrower one**: every other shape a driver or an in-file script can take. Nothing on Windows. This replaces the earlier entry, which recorded the claim as Creator-stated at about 95% and awaiting research; research confirmed it for the keyframed case and narrowed it to that case.
- **A view layer can carry its own sample count, different from the scene's.** Label: **documented** and **observed**. **Settings 4**. The override is one value on the view layer in all four versions. Which engine obeys it is the entry below.
- **A render can be set to stop early once the picture is clean enough, and to stop after a length of time instead of after a count.** Label: **documented** and **observed**. **Settings 2**. Both are Cycles' and neither exists under EEVEE, in all four versions; stopping early is on in every version's starting state and the time limit is off. This closes the marker that held both behaviours agent-raised and unconfirmed.
- **A time limit is spent on each frame rather than across the whole job, and a frame cut short is still written.** Label: **observed**. **Settings 2**, which now carries twenty-four further runs of a three-frame render under a ten-second limit — three per version on the Creator's Mac and three per version on an idle rented Linux machine. Every one wrote all three frames and took about three times the limit. *(Was open on Linux; answered by the round behind **Settings 16**.)* **What it does not cover**: every one of those runs was on the processor, and whether the limit is counted the same way on a graphics card was tried in no version. Smoozy renders on machines rented for their cards, so the spec keeps a marker open for that case.

- **A sample count handed to a render from outside changes the number and nothing else.** Label: **observed**. **Settings 16** — see the [comparison](../../Blender%20Research/Comparison/Settings.md). The frame still stops early once its pixels are clean, the time limit still ends it wherever the count has got to, and a view layer's own count still stands in place of the one handed in. Which of those two counts wins is a scene setting with three answers — use the view layer's, cap it by the count handed in, or throw it away — starting on the first. The step from "a view layer can carry a number of its own" to "that number beats the count the run was given" is the one every version's sources only inferred, and the test settled it. All four versions, on the Creator's Mac and on the rented Linux machine with the RTX 4060 Ti. **This corrects what the spec said** — that a typed count sets aside anything that would have cut the render short, as though imposing the number were enough. What was stated: that none of it stands once a number is typed. What was found: imposing a number does none of it. Smoozy's decision is untouched; the spec now states it as three things Smoozy switches off. Recorded in the `Audits/Specs/Render Settings/Decisions record.md`. **Those three are not the whole list.** The same question counts five things in Cycles standing between the number a run is given and the number of samples a pixel takes; a setting that fixes how many samples a frame renders in place of the maximum is another of them. The spec names the three it had already promised to set aside, and now says plainly that they are not everything, so that nothing downstream reads them as the list. **What it does not cover**: every Cycles render behind that question was on the processor, so nothing there speaks for a render on a graphics card; and the rule by which the several limits combine when more than one is in force is established nowhere, because the part of Cycles that runs a render session is absent from every version's file snapshot.
- **A file carries a separate sample count for each engine and holds them all at once.** Label: **documented** and **observed**. **Settings 4**. All four versions, on both machines. This closes half of the marker the spec carried about the engine deciding what the settings mean.
- **EEVEE takes exactly the count it is given except where two of its own features raise it.** Label: **observed** (all four versions). **Settings 16** — see the [comparison](../../Blender%20Research/Comparison/Settings.md). Motion blur rounds the count up to a multiple of its own step figure, so 64 came back as 65; jittered depth of field raises it to fit a pattern, so 16 came back as 19. In EEVEE the number given is a floor as much as a target. **Neither feature is anything Smoozy offers or touches**, and the file renders as the artist saved it. Found by the check of the comparison rather than by the comparison itself. **What the spec decides out of it** — that the promise about the typed number is not narrowed, because the gap is one sample or three and nothing the user sees changes — is Smoozy's own and earns no entry here. **Not covered:** whether other EEVEE features do the same, since only these two were met; and any figure for how much the raised count costs.

- **The two ways of cutting a render short belong to Cycles alone; a view layer's own sample count does not.** Label: **documented** and **observed**. **Settings 16**, which settled the EEVEE half by test — an override of 8 against a scene count of 256 gave 256 in 4.5 and 8 in 5.0, 5.1 and 5.2, in all four versions on both of that question's machines, and 5.0's release notes say the same in words. **Settings 4** carries the same split and points there. **This overturns what the spec said.** What was stated: that a view layer's own sample count is Cycles alone, so the samples warning does not arise under EEVEE — agent-raised and marked unresolved. What was found: it is not Cycles alone from 5.0. Research won, and the spec now states it version by version. Recorded in the `Audits/Specs/Render Settings/Decisions record.md`.
- **What decides the list of engines a file can name is what is registered in the running Blender: three come built in and more arrive as add-ons.** Label: **documented** and **observed**. **Settings 13**. Seen in all four versions on the Mac and on both rented Linux machines. **This narrows a fact the Creator had settled** — that Cycles and EEVEE are Blender's own engines. What was stated: the engines are Cycles and EEVEE. What was found: Blender itself has three built in and the list grows with add-ons. Research won as to Blender; what Smoozy offers is Smoozy's own decision, and the Creator ruled on 2026-08-06 that the third built-in engine is dismissed and the page still offers Cycles and EEVEE. Recorded in the decisions record, closing the between-rounds thread opened on 2026-08-01. **Partly covered now — corrected 2026-09-01, after the research was repaired; this read *anything about a third-party engine is untested everywhere*.** Another question ran the case: **where an engine is named on the launch line and its add-on is absent, no image is written at all**, Blender 5.0, 5.1 and 5.2 stop at a failure, and **4.5 does not stop at all** — killed by hand on the Mac, and on a rented Linux machine never ending on its own. **What is left uncovered is narrower**: when in the launch the engine has to be named for that to happen. *(The original wording follows.)* **Not covered**: anything about a third-party engine, since none could be installed on any machine — what a file naming a missing one does is untested in every version.
- **A file's engine does not necessarily survive the render.** Where the Blender doing the render does not have that engine, it is not refused: Blender reports the engine as unavailable, falls back to EEVEE, renders at EEVEE's own sample count instead of the file's, writes the image and finishes cleanly — and a read of the file taken by that Blender reports EEVEE as the file's engine. Label: **observed**. **Settings 13**. Identical in all four versions on both machines. **What it does not cover, and this is the important half — corrected 2026-09-01, after the research was repaired.** The case tested is **the Cycles add-on switched off**, which is the file's own engine going missing with nothing named on the launch line. **That is not the same case as an engine Smoozy names on the line, and the two end completely differently.** Where the engine is **named at launch** and its add-on is absent there is **no fallback and no image**: three versions stop at a failure and **4.5 never stops**, which on a rented machine means one that bills until somebody destroys it by hand. **So the graceful fallback described above is the file's-own-choice case only**, and nothing may generalise it to a choice the user makes in Smoozy. This is the finding that broke a promise rather than filling a blank — the spec had said each setting opens showing the value the file carries, which is not true of the engine on a Blender that lacks it.

- **Whether the engine a render actually used can be learned afterwards.** Label: **observed; the printed line differs by version, the written fields do not**. **What actually ran 2** — see the [comparison](../../Blender%20Research/Comparison/What%20actually%20ran.md). **Yes, by two routes.** From Blender 5.0 on, an ordinary background render with no switches asked for prints a line naming its engine; Blender 4.5 has no such line at any log setting, which is a difference between 4.5 and the other three rather than the one the documents' silence had suggested. And in **all four versions** a finished Cycles picture carries four fields of Cycles' own written into it that an EEVEE picture of the same frame does not, the same names everywhere, on both machines, whether the processor or the cards did the work — **every one of the seven findings documents had said no such trace existed**, and the test overturned them. So the engine that produced a render is readable from the file in every version. **The device line is only ever available once the render has finished**, which is the limit that matters: by then the machine has been paid for. **When the engine line is printed is not established** — nothing records its timing, and it should not be assumed to share the device line's. **Not covered:** whether a third-party engine leaves anything of its own, since none could be installed anywhere. **One limit on the printed route**: whether a running render prints anything at all depends on how the render was started, so the printed line is not available by every route. **Reports 9** — see the [comparison](../../Blender%20Research/Comparison/Reports.md). That fact is owned by the [Rendering sources](Rendering.sources.md), not here; this spec carries only the limit it puts on the printed route.
- **EEVEE's identifier is not the same in every version, and which name is taken depends on the route.** Label: **observed**. **Settings 13**, which now sets the two routes out side by side, and **Images 9** for the route that hands Blender an instruction. Blender 4.5 knows one name and 5.0, 5.1 and 5.2 know another. Stated at the start of a render, the newer three do take 4.5's name; set by an instruction handed to Blender, all three refuse it outright with an error, and 4.5 refuses the newer name the same way. Each version's own name works by both routes. How 4.5 ends when it is given the newer name at the start of a render differs by machine — hanging on both rented Linux machines, ending at a crash on the Mac — so no single symptom should be expected. The comparison used to end "the old name is safe in all four", which holds only for the name stated at the start of a render; it now states the route rule instead — the name that works by every route is the version's own. **What it does not cover:** the newer three taking 4.5's name rests on one run, on one rented Linux machine, on a 64 by 64 scene; nothing recorded whether that render really used EEVEE or whether it printed a warning, and it was never tried on the Mac.
- **EEVEE renders on a machine with no display server.** Label: **observed**. **Settings 6**. On a rented Linux machine with no display server at all, every engine each version has rendered, aimed at the graphics cards and at the processor alike, exiting cleanly, in all four versions. This closes the marker that held it able to remove the engine choice entirely. **Not covered**: Windows, a machine with no graphics hardware at all, and a Mac with no display server — none of which is Smoozy's case, since Smoozy renders on rented Linux machines.
- **A scene built for one engine does not simply come out the same in the other.** Label: **documented**. **Settings 7**, from all four versions' manuals; no test touched it in any version. The spec leans on it only for saying that changing the engine is a deliberate act.
- **Whether a render uses the machine's graphics cards or its processor is a scene's own setting, not the file's, and a fresh scene starts at the processor.** Label: **documented** and **observed**. **Settings 9**. Held one scene at a time, surviving a save and a reload, in all four versions on both machines. It is Cycles' setting: EEVEE has nothing to record because it only renders on the graphics cards. **This overturns what the spec said.** What was stated: that the file carries the choice rather than a scene, so it sits outside the scene selection and stays live however many scenes are ticked — Creator-stated (2026-07-27). What was found: it is per scene. Research won, and the spec now treats it like every other scene setting. Recorded in the decisions record.
- **A render started from outside can override the scene's own graphics-or-processor setting**, so what this page shows is not necessarily what the render does. Label: **observed**. **The machine 5** — see the [comparison](../../Blender%20Research/Comparison/The%20machine.md) — and **Settings 9**. What makes a machine's cards available sits outside this module and is owned by the [Rendering sources](Rendering.sources.md).
- **A scene asking for the graphics cards is no promise that it gets them.** On a rented Linux machine left as it comes, every card is switched on but no card technology is chosen, and the render goes to the processor with Blender saying nothing about it. Label: **observed**. **The machine 5**, in all four versions. The spec uses it only for what the processor warning can and cannot promise; acting on it belongs to Rendering.
- **One scene can be set up to take in another scene's rendered result, two ways — through the compositor and through the video sequencer — and a render started from outside honours both.** Label: **documented** and **observed**. **Settings 8**. The pulled-in scene renders with its own engine and its own sample count rather than the host scene's, in all four versions on both machines. This replaces the earlier entry, which recorded it as agent-raised, Creator-confirmed and awaiting research. Whether the pulled-in scene's own compositor also runs and writes files of its own is a different question — **The compositor 4**, which answers it for both routes — and it is owned and cited in full by the [What a job writes sources](What%20a%20job%20writes.sources.md), not here.
- **Blender versions differ in what they can do, and some files will not open in some versions at all.** Label: **documented**. **Settings 10**, which carries the manual's statement that a new major version can make a file unreadable by older Blenders. This replaces the earlier entry, which recorded it as a Creator's fact with what a mismatch costs parked for research.
- **What a version mismatch costs.** Label: **documented** and **observed**. **Settings 10**. A newer file opened by an older Blender reports the expected loss of data and renders anyway — **in Blender 4.5, 5.0 and 5.1, on both machines** (narrowed 2026-08-30, downstream citation audit: this read *in all four versions*, and the comparison records that 5.2 could not be tested this way at all, on any machine, there being no newer file to give it — which the *not covered* line below already said in its own words); the other direction is silent. Each version's own release notes record its own breaks, which is the material the spec's warning is made of. Blender 4.5 opening a 5.2 file also prints a good deal of other noise and still renders. **Not covered**: no version newer than 5.2 exists to test 5.2 against, and how many warning lines 4.5 prints is disputed between two runs of the same test and is not relied on. That the warning is a small one beside the version choice, opening for the whole of it, is the Creator's decision (2026-08-06) and earns no entry here.

## Facts owned elsewhere

- **A `.blend` file's frame range can begin at any frame number** — not necessarily 1, and Blender allows 0 and negative numbers. Label: **Creator-stated** (2026-07-27). The Creator holds that this one needs no confirming, and it was deliberately not researched.
- **Reading a `.blend` for its settings requires a Blender on the machine.** Label: **Creator-stated** (2026-07-27). The Creator holds that this one needs no confirming, and it was deliberately not researched.
- **The resolution percentage** — that the file carries a percentage of the scene's full resolution, and that a typed percentage is of that same full size. Label: **Creator-stated** (date unrecorded), named in the [Product brief](../Product%20brief.md). The Creator ruled on 2026-07-30 that *this much* is settled and is not to be researched, and it is recorded in the research's own question register among the questions deliberately not asked. *(The link was removed 2026-09-01: nothing downstream may open the question register. The ruling itself is the Creator's and is recorded above; nobody needs that file to check it.)* That ruling covers what the percentage **means** and nothing else. **What values the setting accepts was never part of it**, and is asked as **Settings 14 and 15** — see the entry below.

- **What values a resolution percentage can be set to.** Label: **observed** (the same in all four versions, on both machines). **Settings 14** — see the [comparison](../../Blender%20Research/Comparison/Settings.md). **Whole numbers from 1 to 32767 inclusive, starting at 100.** No zero, no negative number, no fraction. There are **two ranges and not one**, and Blender itself was asked for both: the outright pair is 1 and 32767, and a narrower pair, 1 and 100, governs dragging alone — which no version's documentation states anywhere and which four of the eight findings documents had guessed correctly from a picture. The setting reports itself as not animatable. The manual says in all four versions that the control both reduces and increases the size of the picture, so values above 100 are meant as well as allowed. **The Creator's recollection was right**, and the range is far wider than the yes-or-no it settled. *(Was unresolved; answered by the research on 2026-08-09.)*

  **What breaks if the range came back narrow is no longer live** — it came back wide. Kept here in one line because it is why the question was asked: the percentage is the only handle Smoozy gives on how big a render comes out, so a narrow range would have taken away the user's only route inside Smoozy to a render bigger than the file asks for.

- **What a render does when it is asked for a value outside what the setting accepts.** Label: **observed; what is printed differs by version**. **Settings 15**. **The value is corrected the instant it is assigned and nothing whatever is said about it** — below the range stores 1, above it stores 32767, with no error, no warning and no line of any kind, and a control assigning text in the same run is refused with a complaint on that same channel, so the silence is real rather than a channel nobody was watching. **Whatever started Blender is not told either**: with the switch that turns a script failure into a chosen exit status set, a run that deliberately fails comes back at that status and a run that merely had its value corrected comes back at success, in every run in all four versions on both machines. So anything judging a render by its exit status will never learn that the percentage it asked for was not the one used. **What did catch it was measuring the written picture**, which the same question did — so the correction is not undetectable, only unreported.

  **The render then goes ahead at the corrected value and the picture comes out at that size**, measured out of the written files. A fraction is refused outright rather than rounded, and so is text. **A request working out to less than one pixel is refused and no file appears.** And a wildly large request neither refuses nor warns — it simply starts a render cut into tens of thousands of tiles, none of which finished inside a four-minute limit, with nothing in the output matching any search for an error or a warning. What differs between the versions is only the shape of the printed lines, which changed at 5.0 as it did for the rest of this topic. **Not covered:** what the field does when an out-of-range number is typed into it at a window, where the slider stops when actually dragged, whether a driver could carry the value out of range, and Windows. *(Was unresolved; answered by the research on 2026-08-09.)*

- **Whether the picture is the same rendered on the machine's cards and on its processor.** Label: **observed** (the same in all four versions, on both machines). **What a render demands 2** — see the [comparison](../../Blender%20Research/Comparison/What%20a%20render%20demands.md). **It is not.** The same file rendered on the processor and on the card differed in more than half of its colour values, in all four versions, under both of an NVIDIA card's technologies and on Apple's own graphics, and the two card technologies disagreed with each other as well. The control is what makes it mean something: the processor repeats its own render exactly, and each graphics device repeats its own to within about a millionth, tens of thousands of times smaller than the gap between devices. **This is what the spec's device section now rests on**, and it is why that setting is treated as a choice about the picture rather than about speed. **How far the difference reaches is a separate matter the same question states, and the spec had dropped it:** the comparison was made on a picture written at full precision, where the average difference is about a twenty-fifth of one step of an eight-bit picture — so most of it could not appear in an eight-bit picture at all — while the largest single difference would. Another topic compared a processor render against a card render on a tiny scene written to an eight-bit format and found the two identical, recorded under **Frames**, and nobody has run both comparisons on one scene. **Not covered:** a graphics card of any third make, and Windows.

- **Which of Blender's cost settings leave the picture untouched, and which change it.** Label: **observed** (the same in all four versions, on both machines; on one small scene rendered on the processor). **What a render demands 1 and 2**. **Nine settings were compared and left it untouched pixel for pixel** — eleven comparisons in all, since the thread count and the tile size were each tried at two values: tiling switched off, three settings governing how a scene is prepared for tracing, the number of time steps used for that preparation, keeping a scene's prepared data between frames, and high-quality normals. Each was set against an unchanged render of the same scene, with two controls that did move the picture. **A much larger group was never compared at all**: the comparison splits the settings three ways, and its middle group — samples, the time limit, the noise threshold, the bounce ceilings and a dozen more — is **documented** as changing the picture and was not tested. **The group's render column does change the picture**, and reaches every engine — Cycles, EEVEE and Workbench each rendered a different picture with it on. That is one switch rather than each named setting, and of the group's settings only two were read back out of a file. **That any of them can be imposed on a render started from outside is inferred in every version**: the general lever is an instruction given as Blender starts, watched working for a sample count and for none of these. **What no test measured is what that group saves**: no run timed a render with it on against one with it off, and none measured what either took in memory. That it makes a render cheaper is Blender's own description of the group and the Creator's own experience — **confirmed by the Creator on 2026-08-12**, which settled a disagreement where the spec's body denied any such statement was on record and this file asserted one; the spec now agrees — and it is not something this project has watched — which matters, because the whole case for offering it is the size of the saving against the cost to the picture. The sweep that ran in all four versions on both machines was for **names that are not in all four versions**, and the same list came back each time, which is what makes the version differences Blender's rather than one machine's. It was not an inventory of every cost setting, and **no version's own list claims to be complete**.

  **How far that reaches, stated exactly, because the spec's decision rests on it.** All eleven were compared on **one small scene per version**, rendered **on the processor**, at one size and one sample count. Nothing was compared on a graphics device, on a heavier scene, or at other values. The controls show the comparison could see *a* change; they do not show that each of the eleven had something in that scene to bite on. **Not covered:** what the settings that need hardware this project does not have would do; whether the picture is reproducible across machines at all, which every version's sources are silent on; and Windows. **What the spec decides out of this** — that none of them is offered on the page, and that the group which caps what a scene loads waits on the Creator's ruling — is Smoozy's own and earns no entry here.

- **What a render can be told about its settings at the moment it is started from outside Blender.** Label: **documented and observed; two differences by version**. **What a render demands 3**, which extends **Settings 1** rather than repeating it. A short list of arguments settles things directly — the engine, the thread count, the graphics device, the graphics technology, and a few others — and **nothing else has an argument of its own**, in any version. The general lever is an instruction given as Blender starts, which reaches any writable setting and is used by the render that follows; that was watched working for a sample count in every version on both machines. **The graphics-device argument beats both the file and the saved preferences, in both directions, and writes nothing down.** A file asking for the cards with no card technology named in the preferences renders on the processor and never touches a card — shown three separate ways, the first of which could not have failed and was rebuilt. **Naming a technology the build accepts but has no hardware for stops the render, writes no image and returns a failing status**, which is a signal something driving Blender can actually read, unlike the device it ran on — **Linux only, on a machine whose card was working, and never run on the Mac**. And the resolution percentage does reach a render started from outside. **Not covered:** what one Windows-only argument does — no Windows machine ran it, and a Windows machine can be rented.
- **A `.blend` writes files in two separate ways — its own output path, and its compositor's file output nodes — and both can be read out of the file.** Owned and cited in full by the [What a job writes sources](What%20a%20job%20writes.sources.md). It appears here only because this module supplies the read: Pre-load Settings is what finds it.
- **Whether a view layer renders is animatable, so it can change frame by frame.** Owned by the [Glossary](../../Groundwork/Glossary.md), which carries the label and the citation. Listed here only because this spec leans on it harder than anything else does.
- **Whether a `.blend` can be read for the add-ons a render needs, and whether those can be told from the add-ons that merely helped build it.** Label: **documented and observed** — the answer is no: a `.blend` keeps no record of them and Blender offers no way to read one out. Owned and cited in full by the [Server Setup sources](Server%20Setup.sources.md), which carries the versions and machines. It appears here because this module was written to supply the read, and there is no read to supply. The label stood as **unresolved** here until 2026-08-13, after the owning document had already settled it.
- **Add-ons belong to one Blender on the machine rather than to the machine itself.** Label: **observed**. Owned and cited in full by the [Server Setup sources](Server%20Setup.sources.md), which owns add-ons. The spec carries the label in place and leans on it only for what changing the Blender version ends.
- **A `.blend` records the Blender version it was saved with, readable without opening the file.** Owned by the [File Browser sources](File%20Browser.sources.md), which carries the citation. This spec leans on it for the version Smoozy picks by default.
