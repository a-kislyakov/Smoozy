# Sources — Rendering

*Where the outside-world facts in the [Rendering spec](../Rendering.md) came from. The spec carries each fact's label in place; this file carries the citation behind it, and what that citation does not cover.*

*A Blender fact is cited by its topic and question number — "The machine 5" means question 5 of `Preparation/Blender Research/Comparison/The machine.md`. That comparison answers on its own; the findings behind it are the paper trail and are not part of the reading.*

*Note: what Smoozy does at a submission — keeping whatever part of an all-scenes submission reached the machine, warning that a file's assets may never have been looked for, opening the settings page filled in when a job is submitted again, and making a new job rather than restarting the old one — is Smoozy's own decision throughout, so none of it earns an entry here.*

- **A machine's GPUs are not necessarily used just because a file asks for them.** Label: **observed** — **The machine 5**, with the scene's own starting value from **Settings 9**. Answered the same in all four versions.
- **One instruction given to a render started from outside is enough to reach every card.** Label: **observed** — **The machine 5**. Answered the same in all four versions, on an Apple-silicon Mac and on rented Linux machines with one, two and four NVIDIA cards. That whatever it takes happens **when the job is run** rather than when the machine is set up is Label: **Creator-stated** (2026-07-27), and it is why this promise sits in this module rather than in **Server Setup**.
- **More than one card is Cycles only; EEVEE renders on one.** Label: **observed** — **The machine 5**. Answered the same in all four versions.
- **Blender can be asked which cards it can see, from outside, with no window, on a machine with no screen.** Label: **observed** — **The machine 6**. Answered the same in all four versions by the Cycles route; the newer routes differ by version and none of them is what this module needs.
- **A render asked for the cards on a machine where none is usable completes on the processor and says nothing.** Label: **observed** — **The machine 4** and **Settings 9**. Answered the same in all four versions, on the Mac and on rented Linux machines. **That is a technology left to the machine's own saved settings.** The same technology **named when the render is started** refuses loudly instead, and so does a value that is no device name at all — see the **What a render demands 3** entry below. The spec's GPU promise cannot rest on a render failing where Smoozy names nothing, because it will not.
- **What a render used is in the run's own words while it happens, and in nothing it leaves behind.** Label: **observed** — **The machine 4** and **Reports 2**. That the shape of the lines travelling through Blender's own logging changed at 5.0 is **Reports 4** — which also records that Cycles' statistics block, and the messages printed while the command line is still being read, stay plain in every version, so it is **not** every line Blender prints. And that **every version puts some of Blender's own words on the error stream** — six messages shared by all four, four more in 4.5 alone, one more in 4.5, 5.0 and 5.1, and one in 5.2 that no earlier version has — is **Reports 2**, which says in as many words that standard error is empty only on an ordinary render with nothing wrong, and is not reliably empty in any version. Answered for all four versions.
- **Still owed on the cards:** NVLink pairs, two makes together, cards of unequal speed, and which card EEVEE picks on a machine with several — **The machine 5**, not established in any version, for want of the hardware. All three rented Linux machines have been destroyed.
- **An output path can be imposed on a render at the moment it starts, without writing it into a file.** Label: **observed** — **Writing 1** for the scene's own output, **Writing 9** for a file output node's. **That it can be done** is answered the same in all four versions, on macOS and on Linux: the `.blend` came back byte for byte unchanged, its stored path still in it, and the image landed where it was told. Owned by the [What a job writes sources](What%20a%20job%20writes.sources.md); it appears here because this module is what carries the redirect out. **Three limits.** The two outputs are not reached the same way — the scene's own takes a command-line argument and a file output node's takes none in any version, so that one needs a script handed to Blender as it starts, and **Writing 9**'s verdict is that what has to be set for the node is **not** the same in all four versions, so nothing driving Blender from outside can use one wording for all four. Where the value is given on the command line the order matters, because loading the file overwrites a value set before it. And Windows is untried.
- **Frames already written survive a render being ended part-way, and where the stop lands at no particular moment nothing at all is left for the frame in flight.** Label: **observed** — **Frames 11**. Answered the same in all four versions, on macOS and on Linux. **The condition is Frames 11's own**: a stop aimed at the moment a frame's own file appears is the other case, and it is the entry below on how a stop decides what a render leaves behind. This replaces the assumption the spec carried. The [Queue & History spec](../Queue%20&%20History.md) states the same for a job given up after a second interruption.
- **No version offers a stop that waits for the current frame to finish.** Label: **observed** — **Frames 11**. Answered the same in all four versions, on macOS and on Linux, inside Blender's window and outside it; the one script route that might have arranged it was tried and did not stop the render.

  **This contradicts what the spec assumed, and research wins.** The spec offered *end after the frame it is on* resting on a fact the [Telegram spec](../Telegram.md) labelled **an assumption** — that a render might be tellable to do this. It cannot be. Dropping a promise to the user was put to the Creator rather than taken by an agent, and **they ruled on 2026-08-06 that the offer is dropped** rather than reached some other way. It is gone from this spec, from [Queue & History](../Queue%20&%20History.md) and from [Telegram](../Telegram.md), which are the three documents that stated it. Label on the ruling itself: **Creator-stated** (2026-08-06) — a decision, not a fact, so it has no source beyond this line. Recorded in the `Audits/Specs/Rendering/Decisions record.md`.
- **A render running on a rented machine can be reached over a connection and told to end.** Label: **observed in a test** — answered at the promise level on 2026-08-18, on rented machines of both kinds, against a real Blender render rather than a stand-in, under all three ways of stopping. Recorded at `Preparation/Architecture/Facts.md`, Fact 2. **Not a Blender question**, and it did not go to Blender Research. The two entries above settle Blender's side — what an ended render leaves behind, and that no version offers a stop that waits for the frame — and neither says that whatever Smoozy puts on a rented machine can be reached and told to end the render it is holding. That is the ability this answers. **What it found:** the stop reaches Blender's own workings and nothing standing in front of them; nothing restarted the render afterwards; and it is not instant — the time before anything showed the render had ended was one to three seconds on the one kind of machine and about two to fourteen on the other. **Not covered: how long a heavy frame takes to honour a stop.** Every run was a small scene, so nothing measures the slow end of it, and any limit set for waiting on a stop rests on that gap rather than on a measurement. **What rested on it, and now stands:** the user's stop from the queue, **Servers**' stop-and-clear on a removal, the group stop that [Queue & History](../Queue%20&%20History.md) offers, and **Telegram**'s stop from a phone. This entry was carried as **unresolved** from 2026-08-09, agent-raised, and parked for Architecture with the other rented-machine assumptions.
- **A render started from outside can be pointed at one named scene; told nothing, it renders the scene that was showing when the file was saved.** Label: **observed** — **Settings 12**. Answered the same in all four versions, on the Mac and on a rented Linux machine. **A name matching no scene is reported and then ignored** — the render goes ahead on the scene it would have used anyway and finishes cleanly. Same source, same versions. Not covered: every file tried was saved by a Blender with no window, so what a file saved from the interface records as its showing scene is untested.
- **What can make a render fail, and what Blender does in each case.** Label: **observed** — **Reports 1**. Answered for all four versions. It is a list of causes, not a ruling: it is what the open question about *try it again* from a phone has to be settled from, and it does not settle it. Two limits worth carrying: no version gives a failure message as a list a program can read (**Reports 2**), and the same failure is worded differently depending on whether Blender has a window (**Reports 2**), so what Smoozy shows a user is not what that user would see on their own machine.
- **A machine with no Blender has nothing on it to render with**, which is why it can be sent no job. The underlying fact — that rendering, and reading a `.blend`, both need a Blender on the machine — is owned and cited by the [Render Settings sources](../Sources/Render%20Settings.sources.md).
- **Other render farms require a `.blend` to be packed before it is sent** — everything the file needs bundled into it. Label: **Creator-stated** (2026-07-28). This is why Smoozy warns at submission that a file's assets may never have been looked for: a user who expects packing will assume Smoozy has it covered. It covers the render farms the Creator has met, not every render farm that exists.
- **There is more than one way to set a render going, and what gets written is not the same for all of them.** Label: **observed** — **Writing 6**. Answered for all four versions, on macOS and on Linux. It appears here because this module is where every job being rendered as an animation is applied; the rule itself is owned by the [What a job writes sources](What%20a%20job%20writes.sources.md).

  **This confirms what the Creator stated** (2026-07-28) and settles what that document could not: the difference is there when a render is started from outside Blender's interface, not only inside it. A single-frame render leaves the frame number out of the name and an animation puts it in, the same in all four versions. A file output node splits at a different place — the frame number every time in 4.5, and on an animation only from 5.0. Rendering every job as an animation removes both.

## Added when the second and third rounds of Blender Research were carried in (2026-08-10)

- **Whether a render can be made to name the part of the computer that did the work.** **Corrected 2026-09-01, after the research was repaired: *a stopped render never reaches it* was reasoned from the timings of a run that finished, and no stopped render was ever run for it.** One has been now. **Two of the four versions print the whole closing report after a stop, one prints a cancelled line and no report, and one prints nothing at any level** — and in the runs that printed, the frame's own sampling had finished inside the wait, so **what a frame genuinely cut short prints is recorded nowhere.** **And the version that prints it publishes its own list of faults calling that report fake, with wrong numbers**, borne out by a run whose report claimed 600 samples for a frame the line above it called 599. **So a line found on a job that did not finish is evidence of nothing, and Smoozy reads it only from a job that finished.**

   Label: **observed; how you ask differs by version**. **What actually ran 1**, with **What actually ran 6** for when the line can be read — see the [comparison](../../Blender%20Research/Comparison/What%20actually%20ran.md). Yes, in every version, and never without being asked. **Every one of these results is Cycles' own path-tracing report**, so nothing establishes that an EEVEE or Workbench job names anything at all. Blender 4.5 reaches the line only through a debugging switch and puts it on the stream reserved for complaints; 5.0, 5.1 and 5.2 answer to an ordinary logging switch on the ordinary output. **It is a closing report**, printed after the last sample and before the frame is written, so nothing says what a running job is using and a render stopped part-way never reaches it — **established on the Linux machine alone**, while the route to the line was run on both. The settings read back afterwards **do not answer it and can be shown to name a card while the processor did the work**, in every version on both machines. **Not covered:** whether a card running out of memory announces the move into the machine's own memory; Windows; a card of another make; a machine with two cards.

- **What happens when a card technology is named and there is no usable card behind it.** Label: **observed** (the same in all four versions, on a rented Linux machine with its card working). **What a render demands 3** — see the [comparison](../../Blender%20Research/Comparison/What%20a%20render%20demands.md). **The render stops, writes no image and ends at a failing status**, saying it found no device of the kind asked for — word for word the same in all four versions, on a machine whose card was working. Given each of six technology names in turn, the ones with hardware behind them rendered and the three without stopped that way. **This is what the spec's decision to name the technology rests on**: it turns a machine that cannot give what was asked for from a six-hour processor render into a refusal. **Not covered:** a **broken driver**, which is a different condition and was never run this way — the only record of one says Cycles listed no devices at all; how long the refusal takes, since no run was timed; the same run on the Mac; and which names a build will even accept is a fact about the operating system rather than about the version.

- **How the way a render is stopped decides what it leaves behind.** Label: **observed**. **Frames 12** — see the [comparison](../../Blender%20Research/Comparison/Frames.md) — as read against the rest of the research by the cross-sweep, whose correction now sits in **File output nodes 13** — see that [comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). Each of the three signals was sent eighty times in all — ten in each version on each machine — within about a thousandth of a second of the last image file appearing: **an interrupt left that image whole in all eighty of its runs, and a polite request to close and an outright kill each left it short in all eighty of theirs**, every short file on Linux being exactly zero bytes. **The earlier, smaller sets that found them whole do not disagree with that**, which is the cross-sweep's correction to what this entry used to say. The sweep read the two against each other and found the same node, the same format and the same signals behind both: what differs is when the stop landed. The earlier runs sent eight stops at no particular moment, and the topic that saw nothing short actually spent a *larger* share of each frame writing — so neither picture size nor the version is doing the work. The same reading reconciles **Frames 11**, which says the frame in flight is always discarded with nothing written for it: that is what a stop sent at no particular moment leaves, and it was answered about the scene's own output. The same choice decides a video output: an interrupt leaves a file holding the frames that were finished and fires Blender's own cancelled-render notification, while the other two leave a file with nothing in it and the polite one fires nothing at all. **That gap has since been closed by a stop aimed at the scene's own write.** It used to be the largest thing left open here, on the grounds that every short file on record was a **file output node's**. **Frames 13** — see [the comparison](../../Blender%20Research/Comparison/Frames.md) — aimed each signal at the instant the frame's own file appeared: an **interrupt** finished the write and left the frame whole, while a **polite request to close** and an **outright kill** each left a short file at the frame's own path, in all four versions on both machines. **That strengthens the decision this module already takes** — end a render with the interrupt and never the kill — since the interrupt is now the ending shown not to truncate the scene's own picture rather than merely the one nothing had been fired at. The bytes left are a race with no version or machine reading, and a part-written file can still open and report the full picture size, so nothing may treat opening or size as proof a frame finished. Also not covered: what pressing Esc inside Blender's own window leaves, which no machine on this project could reach; and Windows.

- **Whether a render survives the connection it was started from being lost.** Label: **observed** (the same in all four versions, on both machines). **The machine 7** — see the [comparison](../../Blender%20Research/Comparison/The%20machine.md). It does. The connection was cut on the Linux machine and the shell killed on the Mac, and then, in a second run, a hang-up was sent to the whole group of programs the render belonged to — which is what closing a terminal really sends. In all four versions the render was still going and frames kept appearing. **One treatment per machine rather than both on each.** **Not covered:** what a whole machine going to sleep does, and Windows.

- **Whether anything on the ordinary render path waits for a person.** Label: **observed** (the same in all four versions, on both machines). **The machine 7**. **Nothing does**, with a window or without one — not a refused script inside the file, not unsaved changes, not an output file already on disk, not a missing texture, not two Blenders sharing one output folder. **Two of those rest on one machine each**: the window cases are the Mac's alone, and the only missing-texture test that could have come out the other way is the Linux machine's and went through EEVEE alone. Blender starts with a file's own stored scripts switched off in every version, and a refused one becomes a printed line while the render carries on and writes a picture of a scene whose script did not run. **Two things do hold a render up and both are in the file's own doing**: a script hooked into the render holds it for as long as that script runs, and a script inside Blender reading from standard input waits for ever where something holds the other end open. Neither arises from anything Smoozy sends. **Not covered:** what a screen locking or a display going to sleep does, which was written out and deliberately not attempted; a whole machine going to sleep under a render; whether Cycles says anything about a texture it cannot find, since those messages all came from EEVEE; and Windows.

## Added when the carry-on figure was ruled to be read from the machine (2026-08-12)

- **A machine reset mid-write left no frame's contents at all, including a frame reported saved seconds earlier.** Label: **observed**, on **one rented Linux machine**; **macOS untested**, because the Creator's own machine is not reset for a test. **Frames 13** — see the [comparison](../../Blender%20Research/Comparison/Frames.md). Owned in full by the [What a job writes sources](What%20a%20job%20writes.sources.md), which also owns what *already there* means. It appears here because *carry on from where this stopped* starts the range after the last frame Smoozy can vouch for, and a figure remembered from the job's own ending can therefore name a frame whose file is gone. Two runs disagree about which directory entries survive — the later one left the folder present and empty in all four versions, while the earlier one left it empty in two, left no folder at all in a third and left a nought-byte file in the fourth, which the comparison says plainly reads like a version difference and is not one — and both agree no contents survived. **Not covered:** macOS, Windows, a polite shutdown rather than a reset, and **how far back the loss reaches**, which nothing measured — so no fixed number of frames could have been backed off instead of reading the machine. What the spec does about it, and that a short-but-not-empty file still passes, is Smoozy's own decision and earns no entry.

## Added when Simplify was ruled onto a failed job (2026-08-12)

*What Smoozy decides here — that the offer appears on a failed job and nowhere else, which three settings are exposed, that it is never applied unasked, and that the entry is marked — is Smoozy's own and earns no entry. What follows is the Blender side it rests on.*

- **Simplify's render half carries Max Subdivision, Child Particles and Texture Limit, in all four versions.** Label: **documented**, from every version's own manual and API pages, with the Cycles half read out of Cycles' own files because Cycles is an add-on and its settings have no page in Blender's API documentation in any version. **What a render demands 1 and 2** — see the [comparison](../../Blender%20Research/Comparison/What%20a%20render%20demands.md). Blender's own documentation groups them among the settings that affect render speed and memory, and describes each as changing the picture.

- **Blender 5.2 carries a Texture Resolution setting the other three versions have not got.** Label: **observed**, both machines. **Settings 14** — see the [comparison](../../Blender%20Research/Comparison/Settings.md), where the full account sits, with **What a render demands 6** for the same pair seen from the saved-file side. Every Python file inside every installed Blender was searched: 5.2's Cycles carries `texture_resolution` and `texture_resolution_render` and 4.5, 5.0 and 5.1 carry nothing of the kind. It is a decimal scale from 0.00001 to 1.0, starting at 1.0, announced in 5.2's release notes as a new Texture Resolution percentage in the Simplify panel — **a different setting from the render's resolution percentage**. This is why the spec leaves it out: a control that appears and disappears with the Blender chosen, for one setting.

- **Simplify's render half changes the picture under all three engines, not Cycles alone.** Label: **observed** (all four versions, both machines). **What a render demands 2 and 4** — see the [comparison](../../Blender%20Research/Comparison/What%20a%20render%20demands.md). Six renders per version of a scene carrying a subdivision modifier at render level 4: Cycles, EEVEE and Workbench each came back different with Simplify on. Blender documents Simplify on a Cycles page, so the documentation and the behaviour part here and the behaviour is what the spec rests on. **Not covered:** one small scene, one modifier, one value.

- **Switching Simplify on and setting Max Subdivision as a render starts was watched working; Texture Limit and Child Particles were not.** Labels: **observed** for the switch and Max Subdivision, **inferred** for the other two. **What a render demands 2, 4 and 6** — see the [comparison](../../Blender%20Research/Comparison/What%20a%20render%20demands.md). The six-render test above applied both by a start-up expression, from outside Blender's window, and the pictures changed. **Texture Limit** was set to 512, saved into a file and read back at 512 in all four versions on both machines — that round trip is **What a render demands 6**'s — and never imposed at the start of a render with the result looked at. That same question does record a hand test in which the Simplify **switch** alone, with a texture limit and a child-particle percentage already stored in the file, changed the picture materially in all four versions; what stays inferred is imposing those two values **as the render starts**. **Child Particles** was read in every version's documentation and neither imposed nor read back. No version offers a command-line argument for any of them — every version's whole command-line page was read — so the lever is an instruction handed to Blender as it starts, which is the same lever the two proved settings went in by. **This entry corrects what [Render Settings](../Render%20Settings.md) used to say** — that the lever "was watched working for a sample count and for none of these" — which walked past its own topic's hand test. **The Creator ruled on 2026-08-12 that the two inferred settings are promised on this ground rather than held for a further test.** **Not covered:** whether Texture Limit or Child Particles imposed this way actually reach a render; Windows; anything on a graphics device, since the comparison runs were on the processor; and how much any of the three saves in time or memory, which no test measured.

## Added when the Blender Research cross-sweep was carried in (2026-08-11)

*A sweep read the fifteen checked comparisons against each other — the check this project had never made. Nothing below is a new run: each is a reading of runs the research already held, and the entry above on what a stop leaves behind was corrected by the same sweep. What it found has since been carried into the comparisons themselves, which is what the entries below cite.*

- **Which route starts a render decides whether it reports its progress.** Label: **observed; it differs by version**. **Reports 9** — see the [comparison](../../Blender%20Research/Comparison/Reports.md). Both machines, all four versions, and **every run a Blender with no window: with a window open, no route prints any progress in any version.** Named on the command line, a render prints its progress in all four. Handed an instruction to render instead, Blender 4.5 still prints its full progress, while 5.0, 5.1 and 5.2 print **no progress line at all** — no samples, no tiles, no stages — and still print the line naming each file they saved. A first attempt lost the output to a buffer and was run again with the buffer emptied after every line; a second control shows the silence is an absence rather than a lost record, since those three versions do print their saved-file line on the same route. **Not covered:** whether the closing line naming what did the work survives the second route in those three versions. Nothing was run for it, which is why the spec marks that question pending rather than answering it.

- **A name given to a render is not accepted alike by both routes.** Label: **observed**. **Settings 13** — see the [comparison](../../Blender%20Research/Comparison/Settings.md) — for the command line, and **Images 9** — see the [comparison](../../Blender%20Research/Comparison/Images.md) — for the other route. Blender 5.0, 5.1 and 5.2 accept the older EEVEE name on the command line and refuse it outright when it is set by an instruction handed to Blender; 4.5 is the mirror image, taking only its own name by either route. **Each version's own name works both ways**, which is what the spec binds whatever starts a render to. The refusal is not a name being quietly ignored: an unrecognised name on the command line stops the run and writes nothing. **Not covered:** the command-line acceptance rests on one run, on one machine, on a 64 by 64 factory scene, and nothing recorded whether that render really used EEVEE or printed a warning. Six topics touched this and split three against three, and two of the six never tried the other name at all. **Settings 13 no longer says the old name is safe in all four**: it carries the two-route table instead, and says the name that works by every route is the version's own.

## Added 2026-10-27 — a video job's first-frame check written as a picture (the Creator's nineteenth notes, notes 3 and 9)

- **A scene set to write a video can be switched, for one render and without saving the file, to write a still picture, and it then writes one picture for the frame, named by the frame, at the job's own size and with its transparency kept.** Label: **observed in a test**, 2026-10-27, during the Build stage, in a cloud container on Linux, with no window — **not the Blender research.** Blender 4.5.15 LTS (build `5afeabba6097`) and 5.2.3 LTS (build `e13b728c6880`), the Blender Foundation's own builds of Blender as a Python module from the Python package index, because the session could not reach `download.blender.org`. A factory scene set to Cycles, 64 by 48, MPEG-4 and H.264, range 1 to 10: switched to PNG and narrowed to frame 1, it wrote `v_0001.png` and nothing else; the same file left as a video wrote `v_0001-0001.mp4`. At 50 per cent and set to carry transparency, the picture came out 32 by 24 with four channels. The saved file still read as a video afterwards. **From 5.0 the format must follow the media type**: setting the picture format alone was refused (`enum "PNG" not found in ('FFMPEG')`), and setting the media type to picture first made it PNG at once; 4.5 has no media type and takes the format straight. `Audits/Build/Step 10c/The video wants — what landed.md`, *The Blender test*. **Not covered:** 5.0, 5.1, 5.3 and 5.4 were not run; the render was started from Python and not from Smoozy's command line, so that a value set by a script after the file loads reaches a command-line render rests on the Blender research's *What can be set from outside* rather than on this test; one container and codec, and the transparent case one other.
