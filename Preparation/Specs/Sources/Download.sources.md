# Sources — Download

*Where the outside-world facts in the [Download spec](../Download.md) came from. The spec carries each fact's label in place; this file carries the citation behind it, and what that citation does not cover.*

*Note: where the spec says it follows how web browsers or the macOS Finder behave, that is where an idea came from, not a fact the spec rests on. Smoozy's behaviour in each of those places is its own settled decision and holds whether or not those applications work exactly that way, so none of them earns an entry here.*

- **How many output files a job will produce is knowable at submission** — reading the `.blend` together with the settings the job was submitted with gives the number. This is a Blender fact and comes from the Creator rather than from documentation. Label: **Creator-stated** (2026-07-22). **This is not a research question and does not close with any research topic**: the Creator holds the method for working it out, and it is Architecture's to record — see [Open Threads](../../Groundwork/Open%20Threads.md). What the count is made of is settled in [What a job writes](../What%20a%20job%20writes.md), which also carries the open questions that bend it.
- **One render can produce several files for the same frame, in different formats and in several folders at once.** A Blender fact from the Creator rather than from documentation. Label: **Creator-stated** (2026-07-22, widened 2026-07-28). Cited in full by the [What a job writes sources](What%20a%20job%20writes.sources.md), which owns it: what does the writing is the file's compositor, and the whole of that behaviour is to be confirmed at Blender Research.
- **Which output formats each version of Blender can write.** Labels: **documented and observed; differs by version** — see **Images 3** in [the checked comparison](../../Blender%20Research/Comparison/Images.md), and **Images 6** in the same comparison for what a written file records about its own colour space. The spec's body carries the answer. **This confirms an assumption the Creator raised** (2026-07-22) that the supported list is not fixed and depends on the version a job renders with; it was not confirmed against documentation then, and the research bears it out. Nothing the Creator stated was overturned, so there is no clash to record. It does not cover Windows, which the research could not test.
- **What happens when a file asks for a format the version rendering it cannot deliver.** Label: **unresolved** — see **Images 4** in [the checked comparison](../../Blender%20Research/Comparison/Images.md), which records it as not established for any version. The reason is worth keeping: every copy of Blender the project asked has every optional format built in, on both the machines it could test, so the case was never produced. **One copy was never asked.** A fifth Blender came with the rented Linux machine's own image and nothing was ever run on it, so whether it was built without a format is not known, and that machine has since been destroyed — see **Builds 7** in [the checked comparison](../../Blender%20Research/Comparison/Builds.md), which records the five Blenders that machine held and says the fifth was never asked anything. So the case was never produced rather than being impossible to produce. Settling it still needs a Blender built without one of the optional formats. Still parked — see [Open Threads](../../Groundwork/Open%20Threads.md).
- **Whether an output path can be imposed on a render without changing the `.blend`.** Labels: **documented, inferred and observed** — see **Writing 1** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md) for the regular output path, and **Writing 9** in the same comparison for a file output node's own. **Writing 9 names the routes; the `.blend` being left alone is Writing 1's half, and Writing 1 covers the regular output path only.** Cited in full by the [What a job writes sources](What%20a%20job%20writes.sources.md), which owns it and keeps the two as separate entries. It matters here because the single folder auto-download watches rests on it.

## Added when the second and third rounds of Blender Research were carried in (2026-08-10)

- **What happens when one of a frame's several files cannot be finished.** Label: **observed** (the same in all four versions, on both machines). **File output nodes 15** — see the [comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). Owned in full by the [What a job writes sources](What%20a%20job%20writes.sources.md); it appears here because of what it does to this module. **The render carries on to its last frame and ends at a successful status**, whatever the cause — a name taken by a folder, a folder refusing writing, a broken path template, or a full volume — and every other file for that frame is written normally. A write that started and ran out of room leaves a part-written file **and Blender prints its ordinary saved line for it**. Nothing on the node records the loss and Blender fires no hook for a failed frame write, so the only signal anywhere is a line naming the path in what the machine printed. **So the file count this module measures arrivals against catches only some of these**: a write refused before it started leaves nothing and the count comes up short — except on Linux with a volume that has no room left, where the file that could not be opened is left at zero bytes — while a write that ran out of room leaves a file at the right name that Smoozy cannot tell from a finished one. The line naming the path is the only signal that is always there. **Not covered:** a folder over a network taken away part-way, a file locked by another program, and Windows.

- **Nothing about a frame cut short by a full volume tells it apart from a finished one.** Label: **observed** (all four versions, both machines). **File output nodes 15**, **Frames 6** and **Frames 13** — see the [File output nodes comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md) and the [Frames comparison](../../Blender%20Research/Comparison/Frames.md). The write leaves the file at the frame's own final name, Blender prints its ordinary saved line for it, and the file opens reporting the full picture size. Owned in full by the [What a job writes sources](What%20a%20job%20writes.sources.md); it appears here because it is what narrows auto-download's promise to the same reach as the manual half's. **There is one format where a third thing does judge it** — the corrected **Writing 5** records the one full-volume picture it ran being refused outright by Blender's own image reader — but **Frames 13** shows a stopped TIFF or JPEG opening and reporting the full size, so a rule built on the reader would be right sometimes and silently wrong the rest. That is why the promise is narrowed rather than a check being added. **Not covered:** Windows, a folder over a network taken away part-way, and a file locked by another program.

- **A machine reset mid-write left no frame's contents at all, including a frame reported saved seconds earlier.** Label: **observed**, on **one rented Linux machine**; **macOS untested**, because the Creator's own machine is not reset for a test. **Frames 13** — see the [comparison](../../Blender%20Research/Comparison/Frames.md). It appears here because *a job that ends badly still gives up what it made* is a promise about what is on the server, and a server that went down may hold less than its own reports said. **What is left where those frames were is not settled, and *Frames 13* says so outright** — one run left the folder empty in 4.5 and 5.1, no folder at all in 5.0 and the first frame's file present at zero bytes in 5.2; a second run left the folder present and empty in all four; both stand, and the reading is that whichever directory entries survive is whatever the file system happened to have written down. What *is* settled is that no frame's contents survived. **A file of zero bytes is the one shape either run saw**, and [What a job writes](../What%20a%20job%20writes.md) owns it and rules it out of every count; a frame that left no entry at all is caught by the count coming up short instead. *(Corrected 2026-08-30: this said flatly that what the emptied frames look like is a file of zero bytes, which reads a question's own *not settled* as a settled answer. Nothing the module promises moves — both shapes fail the same test.)* **Not covered:** macOS, Windows, whether the same holds for a machine shut down politely rather than reset, and how much of a run is at risk — nothing measured how far back the loss reaches, so it is not a fixed number of frames.

- **What a job whose output is one video file leaves, and what its size says.** Label: **observed**. **Frames 12** — see the [comparison](../../Blender%20Research/Comparison/Frames.md). Owned by the [What a job writes sources](What%20a%20job%20writes.sources.md) and by the [Queue & History sources](Queue%20&%20History.sources.md); it appears here because the count is this module's to state. The file is created within moments of the render starting at a token size and **its reported size does not move while the render runs**, reaching its real size only when the file is closed — all four versions, both machines — so its arrival says nothing about the job's progress. Where the artist has Blender's own splitting switched on it may become more than one file; **that half ran on a rented Linux machine alone**, with a different container, codec, picture size and render engine from everything else in the question. **Not covered:** the splitting on macOS, one container and one codec and one scene at one frame rate being all that was tried, what pressing Esc inside Blender's own window leaves, and Windows.
