# Sources — What a job writes

*Where the outside-world facts in [What a job writes](../What%20a%20job%20writes.md) came from. The document carries each fact's label in place; this file carries the citation behind it, and what it does not cover.*

*Note on provenance, which is unusual for this document. Almost every Blender fact here began with the Creator, a Blender professional — but unlike the Creator's facts elsewhere in this project, the Creator asked that **all of them be confirmed at Blender Research**, and confirmed with more rigour than anything else in the project. Their reason: the file output node's behaviour changes from version to version, with features added, reworked, removed and returned. Most of them have now been checked, so most entries below are a label and a pointer at a question in a checked comparison. **Creator-stated** still means good enough to plan on and expected to be checked, never settled. Where the research and the Creator disagreed, the research wins under the project's standing rule; every such clash is written out below, saying what was stated, what was found, and which stands.*

*Note: what Smoozy does about all this — the redirect, the shared-run rule, the main output, the preview's order, what the user is told and when, and what a re-run treats as already there — is Smoozy's own, carries its label in the document, and earns no entry here.*

*Note on the machines. Nearly every checked answer below was run twice, in all four versions each time: on the Creator's Apple-silicon Mac, and on a rented Linux machine with an NVIDIA card, which is the kind of machine a Smoozy render actually happens on. The two agreed everywhere they were both asked. Where an answer rests on one machine only, its entry says so. Several different rented machines were used across the rounds, with different cards and different amounts of memory, and no figure from one is ever set against a figure from another. One gap is worth naming: **no Windows machine is among the machines behind these answers**, which bears only on what an artist's own file carries into a job rather than on what the render does. A Windows machine can be rented, so the gap is untried rather than out of reach. What the regular output path does when the disk runs out of room was recorded here as run on the Mac and deliberately not on Linux; that topic's comparison was corrected on 2026-08-12 and now carries three Linux runs of it, and the entry below sets out what they show and what they do not.*

*Note on the cross-sweep, **rewritten 2026-09-01: the pointer it describes has been removed, because nothing downstream may open anything under `Audits/`, and this note was framing a link that should not have been there.** One entry below **used to cite** a file under `Audits/Blender Research/Cross-sweep/Verified/`. That is a check the project had not made before: the fifteen checked comparisons read against each other rather than each against its own sources, with the strongest findings taken back to the hand tests and findings behind them. It read no Blender documentation and ran no test of its own, so where it is cited here it rests on the research documents named in the same entry. It was named because it is the only place that reading is written down — **and that is exactly why the citation could not stay**: a reader who may not open it cannot check it, so the entry below now states what the reading found rather than sending anyone to it. The disagreement it found between Writing's comparison and Writing's own findings is gone — that comparison was corrected on 2026-08-12 and now carries the Linux runs itself — so what the citation is still for is narrower: where two of those runs came from, and what about them cannot be repeated as written.*

## The two routes, and whether either of them writes

- **A `.blend` writes through a regular output path on the scene, and separately through the file output nodes in its compositor. Every file has the first; the second is a thing the artist adds.** Labels: **documented and observed; differs by version** — see **Writing 2** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md) for how each is recorded, **The compositor 2** in [its comparison](../../Blender%20Research/Comparison/The%20compositor.md) for one writing while the other is switched off, and **File output nodes 13** in [its comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md) for a node writing alongside the scene's own output. *(Was Creator-stated 2026-07-28; replaced by the research on 2026-08-06.)*

- **File output nodes are commonly used, not a power user's trick.** Label: **Creator-stated** (2026-07-28). This is a fact about how artists work rather than about Blender, and rests on the Creator's own professional experience. It needs no documentation, but it is what justifies treating this whole document as the ordinary case rather than an edge case.

- **What decides whether a file's compositor runs at all, which node is its final output in which version, and which of those conditions reaches a file output node.** Labels: **documented, inferred and observed; differs by version** — see **The compositor 1** in [the checked comparison](../../Blender%20Research/Comparison/The%20compositor.md), and **File output nodes 13 and 14** in [its comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md) for the Compositing switch stopping a node writing while the tree's own output node has no bearing on it. **This replaced a Creator recollection** that the compositor kept running regardless of the old Use Nodes switch as long as post-processing was on; the research found the opposite for Blender 4.5, and the research stands. *(Was Creator-stated 2026-07-28; replaced by the research on 2026-08-03.)*

- **What the regular output path holds when the compositor is running: the compositor's result, not the raw render.** Labels: **documented and observed** — see **The compositor 1** in [the checked comparison](../../Blender%20Research/Comparison/The%20compositor.md) and **Images 1** in [its comparison](../../Blender%20Research/Comparison/Images.md). **This narrows a Creator recollection.** The Creator stated that a beauty carried by a file output node usually reaches the regular output path as well, so a common setup writes it twice. The research shows that only holds when the artist wired the beauty to the compositor's final output node — otherwise the regular output path holds something else entirely. The Creator's statement is the common case and not the rule, and the document now says which. *(Narrowed 2026-08-06; the duplicate-picture warning still stands, for the case where it does happen.)*

- **Whether the regular output path can be switched off entirely.** Labels: **documented and observed; differs by version; confirms the Creator's own recollection** — see **The compositor 2** in [the checked comparison](../../Blender%20Research/Comparison/The%20compositor.md), and **Writing 7** in [its comparison](../../Blender%20Research/Comparison/Writing.md) for the same switch reached the other way.

- **What Blender does when nothing at all would be written, and what such a render leaves behind.** Labels: **documented and observed** — see **Writing 7** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md). Two halves. With the switch off and no live file output node, Blender 5.2 refuses the render outright and says so — word for word on both machines — and on the rented Linux machine the output folder was not even made, which is the half that rests on one machine. Where a render does run and write nothing, the picture stays inside Blender and dies with it, and Blender's own temporary folder is empty before, during and after. **The Creator's own expectation was recorded here and deliberately kept from the researchers** — that whatever comes of such a render would show up in what the machine says while it works rather than on disk. It is borne out in the narrowest way: what comes out is a message and nothing else. The product decision this was waiting on has since been made — Smoozy warns and lets the user proceed, with the option to stop. Label: **Creator-stated** (2026-08-06); that is a decision and not a fact, and it lives in the document.

- **Whether Blender counts a file output node that will write nothing — muted, unconnected, or sitting in a tree whose Compositing switch is off — as a live one for the purpose of that refusal.** Label: **unresolved**. Not asked at Blender Research and not answered by any comparison. It decides whether a render that runs to the end and writes nothing is reachable at all, or whether Blender always refuses first. The warning and the ruling above stand either way; what is at stake is only how often the case arises.

## What a file output node can do

- **What one File Output node can be made to write, how many outputs it can have, and what each output carries.** Labels: **documented and observed; differs by version** — see **File output nodes 1** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). Leaves the maximum open.

- **Whether an output carries a folder, and whether a folder can be expressed inside its name.** Labels: **inferred, documented and observed; the second differs by version** — see **File output nodes 3 and 4** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). The document's use of individual destinations rather than whole nodes rests on this.

- **Which folders a File Output node can be pointed at.** Labels: **documented and observed where tested; unresolved for network storage** — see **File output nodes 5** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). A folder on network storage could be tried on neither machine and stays open in every version.

- **What a File Output node can be fed, and whether it must come from the render.** Labels: **documented, inferred and observed** — see **File output nodes 12** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). The main-output rule and the file count both rest on this.

- **What happens when two outputs are aimed at the same name in the same place.** Label: **observed** — see **File output nodes 10** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). The collision warning and the count both rest on it. The same entry records that the scene's own Overwrite and Placeholders settings do not reach a file output node at all, which the re-run rule leans on below.

- **Several outputs gathered into one file; a node inside a group; switching a node or one output off.** Labels: **documented, inferred and observed; part of the first differs by version** — see **File output nodes 6, 7 and 8** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md).

- **What causes a File Output node to write, and when during a render it writes each file.** Labels: **documented and observed; the frame-number rule differs by version** — see **File output nodes 13** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). Auto-download during a render, *show outputs* on a running job, and an in-progress frame preview all depend on files being written as each frame finishes.

- **Whether a File Output node can write a video file.** Label: **observed** — see **File output nodes 11** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). The job's file count and the frame-based re-run rule depend on the answer being no.

- **Whether the set of outputs a frame writes can change from frame to frame** — whether a node's mute switch, or the switch that decides whether the compositor runs, can be made to change during one render. Label: **observed; differs by version** — see **File output nodes 14** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). The answer is no in Blender 5.0, 5.1 and 5.2 and yes in one narrow way in 4.5. Nothing that gates a node will take a keyframe or a driver in any version except the compositor's old Use Nodes switch, which works in 4.5 and does nothing from 5.0 on — Blender's own documentation for the newer three says setting it has no effect and reading it always returns on, so the documentation and the test agree. A script called once per frame does reach the node's own silencing in every version, landing one frame late, but Smoozy sends no such script, and a file's own stored scripts start switched off — see **Settings 11** in [its comparison](../../Blender%20Research/Comparison/Settings.md). So the count's assumption is firm from 5.0 and can be broken on 4.5 by a file built that way. *(Was an assumption; answered by the research on 2026-08-07.)*

- **When one of several files being written for the same frame cannot be finished.** Label: **observed** (the same in all four versions, on both machines) — see **File output nodes 15** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). This is the entry the document's whole trust-nothing paragraph now rests on. The render carries on to its last frame and the process exit status is 0, whatever the cause — a name taken by a folder, a folder refusing writing, a broken path template, or a full volume. Every other file for that frame is written: the node's other outputs, any other file output node, and the regular output path. A write refused before it starts leaves nothing, except on Linux with a full volume, where the unopenable files were left at zero bytes. **A write that starts and runs out of room leaves a part-written file and Blender prints its ordinary saved line for it** — so a saved line is not proof of a complete file, which is the most consequential thing this question settled. The only signal anywhere is a line naming the path in what the machine printed: nothing on the node records it, and Blender fires no hook for a failed frame write though it has one for a failed file save. Blender 5.2 alone exposes its own report log to a script, and with no window that log stays empty even for something that certainly errored, so it buys nothing here. **Not covered:** a folder reached over a network taken away part-way, a file locked by another program, anything on Windows, and anything needing eyes on a screen.

- **The exit status a render ends at, and the rule that decides it.** Label: **observed** — see **File output nodes 15** in [the checked comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md), and **Writing 5** in [its comparison](../../Blender%20Research/Comparison/Writing.md) for the three full-disk runs of the scene's own output. A run that could not read the `.blend` at all ends at a failing status; a run that lost one of a frame's files ends at success. So the status separates *never started* from *ran*, and never *everything written* from *a file lost*. **The rule underneath it: a part-written frame never sets the status, and what sets it is the next write, the one that cannot be opened at all.** The three runs of the scene's own output on a disk with no room came back 0, 1 and 1 — a single still in all four versions at 0, a three-frame animation in all four versions at 1, and a four-hundred-frame animation in Blender 5.2 alone at 1; the Mac's own three-frame run agrees at 1. Format, picture size, version and whether the disk was already full or filled part way each fail to separate them. Where there was a next frame the render stopped there and ended at 1; where there was none it ended at 0. **Both research documents now state the rule, and both say whose write they were testing** — Writing 5's three cases are all the scene's own output path with no node in them, and File output nodes' runs all kept the scene's own output on a roomy disk on purpose, so its "the exit status was 0 in every run" is about the node's write alone and was never a disagreement with Writing. **Not covered:** Windows, and a run where the scene's own output and a node's fail together.

## The compositor and the scenes around it

- **Whether a compositor belongs to one scene or to the whole `.blend`, and what a shared one renders.** Label: **documented and observed; differs by version** — see **The compositor 3** in [the checked comparison](../../Blender%20Research/Comparison/The%20compositor.md).

- **Whether a scene that pulls in another scene's rendered result also runs that second scene's compositor and writes its file output nodes.** Label: **observed, the same in every version** — see **The compositor 4** in [the checked comparison](../../Blender%20Research/Comparison/The%20compositor.md). **There are two routes and they answer differently** — through a Render Layers node, and through a scene strip in the video sequencer. The body carries both. Neither answer is the general one, so this entry must not be read as settling the other route. The scene-pulls-in-scene behaviour itself is owned by the [Render Settings sources](Render%20Settings.sources.md).

- **What the render arrives into the compositor as, and whether it can be told apart there.** Labels: **documented; not in the sources at the data level; inferred and observed for the forward trace** — see **The compositor 5** in [the checked comparison](../../Blender%20Research/Comparison/The%20compositor.md). The main-output rule and the frame preview both depend on it.

- **How far the beauty can be followed forward — through colour work, and through a node that takes two pictures in and gives one out.** Label: **observed** (the same in all four versions; the version-shaped parts differ) — see **The compositor 8** in [the checked comparison](../../Blender%20Research/Comparison/The%20compositor.md). The answer is the favourable one and it is now the document's rather than an assumption. A colour-changing node takes one picture in and gives one out; every two-picture node has exactly one picture output; and the whole chain reads back out of a saved file with no window at all, complete, in every version. **Which input came out can be told for five named kinds of two-picture node and for no others.** And **thirteen of the seventeen terminal tests behind this question were run on one machine only** — their other half is simply not run, so those answers settle Linux and are untested on macOS. Which input came out can be told node by node — a Switch hands its chosen input through exactly, Mix and Alpha Over hand one input back at the ends of their factor, a muted node states the input it passes and the render matches, and a depth-combining node chooses pixel by pixel.

  **Four limits travel with it and the document carries all four.** Nothing marks a picture with where it came from, in any version, so the walk is always by wiring. A link cannot be walked across a node group's boundary — the walk has to step inside. A splitting node's first input lands on the right in Blender 4.5 and on the left in the other three. And with a two-picture node's factor between its ends both inputs contribute and nothing says which contributed what, while a freshly added mixing node starts at a different factor in 5.2 from the other three. **Not covered:** what a socket's inspection panel draws, which needs a pointer held still and no machine on this project can do; whether the File Output node's own name setting can carry a token standing for the socket's name; and Windows. *(Was an assumption; answered by the research on 2026-08-07.)*

## Paths, names, and the redirect

- **Whether an output path can be imposed on a render at the moment it is started, without changing the file.** Labels: **documented and inferred for the mechanism; observed for the file being untouched** — see **Writing 1** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md). This covers the regular output path only, and the answer is yes: the `.blend` on disk came back byte for byte identical. *(Was unresolved; answered by the research on 2026-08-06.)*

- **Whether a file output node's own path can be changed for a render, by any route.** Labels: **documented, inferred and observed; the names of the two values differ by version** — see **Writing 9** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md). The answer is yes by two routes and no by a third: no version has a command-line argument for it, a script handed to Blender at launch reaches it, and a windowless Blender can write it into a file and save it. **This is the load-bearing promise of the whole document**, and it is now carried. *(Was unresolved; answered by the research on 2026-08-06.)*

- **Whether Blender's bulk path commands reach the places a file records for writing.** Label: **observed** (the same in all four versions) — see **Dependencies 17** in [the checked comparison](../../Blender%20Research/Comparison/Dependencies.md), and **Reading a file 9** in [its comparison](../../Blender%20Research/Comparison/Reading%20a%20file.md) for the fuller sweep across twenty-one kinds of recorded location. **They do not.** Of six recorded locations put side by side, the commands that make every path relative or absolute, the command that reports missing files, and Blender's own list of a file's outside paths reach only the ordinary image and one cache path — not the render output path, not a file output node's folder, not a point cache, not a geometry-nodes bake folder. The wider sweep gives the same shape: the listing means and the relative sweep reach sixteen of twenty-one kinds and miss the render output path, the bake output path, the File Output node's path, the point cache, the geometry-nodes bake folder, the sequencer's proxy folder and a path held in a custom property. Walking Blender's own marks on its settings finds nineteen of the twenty-one, so the two together cover all but the custom property. **That wider sweep rests on the rented Linux machine alone** — its nineteen tests were never run on the Mac, so they settle Linux and are untested on macOS, where the six-location comparison above was run on both. **This constrains how Architecture carries the redirect out** — each of those settings has to be reached and written on its own — and it takes nothing away from the promise. It also means asking Blender what a file points at will never name the folder it is about to write into. **Not covered:** whether the absolute sweep would reach those seven if they were recorded relative, which the run could not tell apart; and Windows.

- **Whether Blender agrees with itself about where a frame will land, and what a broken template does.** Label: **observed** (the same in all four versions, on both machines) — see **Dependencies 17** in [the checked comparison](../../Blender%20Research/Comparison/Dependencies.md). For a frame render and for an animation the name the file predicts and the name that appears are the same, templates and padding and all. Only a still driven through the script route differs, leaving the padding unsubstituted in the name — which costs nothing here, since every job Smoozy runs is an animation. A template Blender cannot work out in the **regular output path** stops the render started from outside at once, at a failing exit status, with a message naming the path, and asking the file where the frame would land raises the same complaint before anything runs. A broken template inside one output's own name is the quieter case and behaves as the file-output failure above. **Each research document now says whose write it was testing, and the two were testing different ones**, so either one read alone generalises the wrong way — Writing's broken-template test set the scene's own output path and had no node in it at all, and File output nodes' set a healthy scene path and broke the node's; see **Writing 5** in [its comparison](../../Blender%20Research/Comparison/Writing.md) and **File output nodes 15** in [its comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md). The document names the regular output path in the failing case for that reason.

- **How a path inside a `.blend` can be written, and what each form means.** Labels: **documented and observed; the list of template variables differs by version** — see **Dependencies 5** in [the checked comparison](../../Blender%20Research/Comparison/Dependencies.md) for the forms and how each is stored and resolved, and **Writing 2** in [its comparison](../../Blender%20Research/Comparison/Writing.md) for the regular output path being one single piece of text rather than a folder and a name kept apart. All three parts this entry once carried as open are now answered. *(Was unresolved; answered by the research on 2026-08-06.)*

- **What a location recorded on one kind of computer means on another.** Label: **observed, the same in every version, on both machines** — see **Dependencies 6** in [the checked comparison](../../Blender%20Research/Comparison/Dependencies.md), and **Dependencies 10** in the same comparison for what a render actually does when handed one. A relative path survives the crossing and resolves against the file's new folder; a foreign absolute path is kept exactly as written and means nothing, and a render given one silently builds the whole foreign-shaped folder tree at the top of the rented machine's disk and reports success. **Not covered:** Windows at either end, in any version — what a Windows Blender writes into a path, and what a path written there means elsewhere. And every run of the foreign-path render was made as a user who owns the top of that disk, so what happens to a render user who cannot write there is not established. *(Was unresolved; answered by the research on 2026-08-06.)*

- **What a location pointing at another computer means, at either end.** Label: **unresolved** — see **Dependencies 7** in [the checked comparison](../../Blender%20Research/Comparison/Dependencies.md). No version's documentation describes it and it could not be tested: there are two machines but no storage both can reach. The one adjacent thing settled, the same in every version on both machines, is that a path naming a volume that is not mounted is kept as written, resolved as written, and simply not found. The document does not rest on this: a network path is a path the redirect moves like any other, and where a path cannot be brought under the job's folder the job is held and the user asked.

- **Whether an output name can carry a character a rented Linux machine will not accept, and what happens if it does.** Label: **observed, the same in every version, on both machines** — see **Writing 10** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md). Neither machine refuses anything but length, and Blender writes what it is given; a backslash is turned into a folder separator by Blender rather than by the machine, and an over-long name is refused at the moment of writing. That refusal was tried on the **regular output path**, and the render stopping there is the scene's own write failing rather than a general rule about names. **Not covered:** what an over-long name in one of a node's outputs does, which was not asked; and Windows, which is the system that rejects ordinary characters, and was never tried in any version. *(Was unresolved; answered by the research on 2026-08-06.)*

- **How the name a file records for a place it writes becomes the name of a file on disk.** Labels: **documented and observed; the File Output node's recipe differs by version** — see **Writing 8** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md). This is what lets the re-run name every file a frame owes before any of them exists, and the file count and the frame preview lean on it too. *(Was unresolved; answered by the research on 2026-08-06.)*

- **What a write does when its folder is not there, when there is no room left, or when it cannot be written to.** Labels: **observed** — see **Writing 4 and 5** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md) for the regular output path, and **File output nodes 15** in [its comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md) for a file output node's own write. **Read the cases apart, because they do not behave alike.** A missing folder is made without a word. An unwritable **regular output path** stops the render at the first frame and leaves nothing at all, at a failing exit status. A full disk leaves a part-written picture that Blender announces as saved. An unwritable or full destination inside a **file output node** does not stop the render at all: that write is lost, everything else for the frame is written, the render reaches its last frame and the exit status is 0. Windows is untried in every case. *(Was unresolved; answered by the research on 2026-08-06, and the file-output half on 2026-08-09.)*

  **The folder-making case splits the same way, and it was answered separately.** See **Writing 12** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md), tested in all four versions on both machines on 2026-08-12. **A file output node whose folder cannot be made does not stop the render and exits 0**, where the regular output path in the same position stops at the first frame and exits 1 with nothing written. So one job can fail in two ways and only one shows in the exit status. The document carries this for whoever reads a job's ending, and the same constraint is parked for Architecture — see [Open Threads](../../Groundwork/Open%20Threads.md). **Not covered:** Windows, and a folder reached over a network. **One condition of the test is worth carrying**, because it is the sort of thing that silently voids a result: on the rented Linux machine the account is the machine's owner and is not stopped by an unwritable folder, so the trustworthy runs are the ones made as an ordinary account. An earlier round of the same topic recorded a way of dropping that power for a single command; **it did not work here**, and two whole passes came back as successes that should have failed before anyone noticed.

  **The Linux gap this entry carried is closed, and the comparison carries it.** **Writing 5** used to say in six places that running out of room was never run on Linux. It was corrected on 2026-08-12 and now reads "settled on macOS and on Linux, in all four versions", holding all three Linux runs: a single still, a three-frame animation and a four-hundred-frame animation, each leaving a part-written picture that Blender announced as saved. **The comparison is what the answer in the document rests on.**

  **Two things the Linux answer does not carry.** Two of the three runs are on no hand-test list and one of them has no written procedure anywhere in the project, so they cannot be repeated as written — the research's own cross-sweep record sets out where each came from — **the link was removed 2026-09-01, nothing downstream being permitted to open it; what it says is that two of the three runs are on no hand-test list and one has no written procedure anywhere, which is the whole of what this entry needs from it** — what survives that, checked twice and re-run with a corrected check, is the part the document uses, a saved line over a file that is not a whole picture. And **the silence is not established**: what Blender printed in the two runs that wrote PNG was not kept, so nothing says whether it mentioned the disk at all. The run that wrote OpenEXR printed four lines naming it.

  **What the file-output answer does establish is bad enough on its own.** That write leaves a part-written file, gets Blender's ordinary saved line, and the render carries on and finishes at success — so there is no failed job, no failure on the entry and no notification, and [Queue & History](../Queue%20&%20History.md)'s failure path genuinely does not fire. **And nothing else catches it either.** Counting the files that arrive does not: the write leaves a file at the right name, and this document says plainly that Smoozy cannot tell that file from a finished one. So the printed line naming the path is the whole of the signal.

- **Blender creates folders that do not yet exist when it writes.** Labels: **observed, the same in every version, on both machines; confirms the Creator's own recollection** — see **Writing 4** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md), and **Dependencies 10** in [its comparison](../../Blender%20Research/Comparison/Dependencies.md) for the same thing for a file output node's folder. *(Was Creator-stated 2026-07-28, given during the round-1 audit; confirmed by the research on 2026-08-06.)*

## Frames, view layers and the re-run

- **What a frame with several active view layers writes.** Label: **observed, the same in every version, on both machines** — see **Frames 9** in [the checked comparison](../../Blender%20Research/Comparison/Frames.md), and **Images 1** in [its comparison](../../Blender%20Research/Comparison/Images.md) for the same result reached another way. One set of files per frame, never one per view layer. **This settles a disagreement between two of this project's own documents**: the [Glossary](../../Groundwork/Glossary.md) reads as one set per frame and is right about the files, and the several beauty passes the [Queue & History spec](../Queue%20&%20History.md) leaves open are real but sit inside a single multi-layer file. **Not covered:** what such a frame writes when the render is started from inside Blender's own window, which was tried on no machine — and which costs nothing here, since Smoozy never starts one that way. *(Was unresolved; answered by the research on 2026-08-06.)*

- **The order a render works through the frames it was given, and what an interruption leaves behind.** Label: **observed, the same in every version, on both machines** — see **Frames 10** in [the checked comparison](../../Blender%20Research/Comparison/Frames.md). **The answer corrected the document's own rule.** A plain range and a stepped range are walked forward, but a typed list of frames is rendered in the order written and not sorted — so the highest-numbered frame present is not always the last one finished, and the rule now names the last frame in the order Smoozy asked for instead. *(Was an assumption; answered by the research on 2026-08-06.)*

- **What an interruption actually leaves of the last image, which is not the same for every way of stopping a render.** Label: **observed; three sets of runs differ in when the stop landed and none is preferred** — see **Frames 12** in [the checked comparison](../../Blender%20Research/Comparison/Frames.md). **This overturned what this file said before.** The earlier entry read that an interruption leaves whole frames only, by every way of stopping a render short, and treated the re-render-the-last-frame rule as a safety net for one untested case. The round of 2026-08-09 sent each of the three signals eighty times in all — ten in each version on each machine — within about a thousandth of a second of the image file appearing: **an interrupt left the last image whole in all eighty of its runs, and a polite request to close and an outright kill each left it short in all eighty of theirs.** On Linux every short file was exactly zero bytes. Two smaller earlier sets found them mostly whole and both stand.

  So what is settled is one-way: an interrupt has never left a short image in any run by anybody, in any version, on either machine, and the other two cannot be relied on. **The disagreement is between the runs and not between the versions** — in the largest of the three sets all four versions behaved identically, while the smallest set does split by version, which is part of why none has been preferred.

  **What separates the sets is when the stop landed.** See **Frames 13** in [the same comparison](../../Blender%20Research/Comparison/Frames.md) for a stop aimed at the write itself, and **File output nodes 13** in [its comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md) for the eight stops sent at no particular moment: the largest set aimed each signal within about a thousandth of a second of the file appearing, and the smaller ones stopped at no particular moment against a write window about that wide, so finding nothing part-written is what chance predicts rather than what Blender promises. **The same two things separate Frames 11 from Frames 12**: 11's runs were about the regular output path's own picture and were stopped at no particular moment, and 12's short files are a file output node's, stopped at the moment its file appeared. So they are a different write and a different moment rather than one answer twice — which **Frames 11** now says itself, pointing at **Frames 13** for the aimed stop.

  **That gap is now closed, and it was the largest thing this entry left open.** It used to read that nobody had ever aimed a stop at the regular output path's own write, and that the last-frame rule's assumption of damage confined to one frame leaned on it. **Frames 13** answers it directly — see [the checked comparison](../../Blender%20Research/Comparison/Frames.md). Each run was stopped at the instant the second frame's own file appeared: an **interrupt** did not cut the write at all, finishing the frame and quitting at 1 with the picture whole and openable; a **polite request to close** left a short file at that frame's own path at exit -15 with no saved line; an **outright kill** left one too, at exit -9. Neither of those opened. **The same in all four versions on both machines, with the same three exit codes.** The same question also settled that Blender writes to the final name and lets the file grow in place — a 4096 by 4096 uncompressed OpenEXR watched every two milliseconds climbed through more than a hundred sizes and only ever appeared under its final name, with nothing ending `.tmp` or `.part`. Label: **observed** (the same in all four versions, on both machines).

  **How many bytes are left is a race and carries no version or machine reading.** Ten repeats per format per version per machine, 160 runs: fifteen of the sixteen cells came back a spread of sizes and a mixture of files that opened and files that did not. The sixteenth, Blender 5.1's JPEG on the Mac, gave nought bytes ten times out of ten — and the same version's JPEG on the other machine gave 4,096 bytes three times out of ten, so it is not a version difference either. Two things held across all 160: a file of nought bytes never opened, and a file of exactly 1,306 bytes usually did. Label: **observed**. **So no size may be treated as a signature**, and the document says nothing may key on one.

  **Two further findings the document carries from the same question.** A part-written file can **open and report the full picture size** with real data — a stopped TIFF, and sometimes a stopped JPEG — where a whole TIFF of that scene is about 5.4 million bytes against a leftover of about 1,300; so opening a file is never proof its frame finished. And in a complete run a **File Output node's save is printed before the frame's own**, every frame, in all four versions; stopped between the two, the folder held the node's file short and unopenable and **nothing whatever at the Output panel's own path for that frame**. That second one was run on both machines for Blender 4.5 and on the Creator's Mac alone for the other three, where it came back the same shape. Label: **observed**.

  **And one case that comes out worse than any stop, which is what the document now leaves open.** With the machine reset at the kernel the instant the second frame's file appeared, **no frame's contents survived in any version — including the first frame, which had been reported saved seconds earlier.** Two runs of it disagree about which directory entries survive, one leaving the folder empty and the other leaving a nought-byte file, and the reading is that this is whatever the file system happened to have written down; both runs agree that no contents survived. So the last-frame rule's assumption that damage stays confined to the frame in flight does **not** hold when a machine goes down. Label: **observed**, on the Ada rented Linux machine alone — macOS is untested, because the Creator's machine is not reset for a test. This is also as close as the research got to a real power cut, which remains out of reach on both machines. **The document's marker for this is cleared**: a file of zero bytes never counts as already there, wherever in the range it sits, and a file that is short but not empty still does — which the document states as a limit rather than hiding. That ruling is Smoozy's own and earns no entry here. What this finding does **not** give it is any measure of how far back a machine going down reaches, since no run measured that, so no fixed number of frames could have been backed off instead.

  Two consequences the document carries: the last-frame rule is the ordinary case again rather than a net, because a zero-byte file sitting at the finished frame's own name is *present* and presence is what the already-there test reads; and Smoozy ends a render with the interrupt rather than the kill, which is a decision the document takes on the strength of this finding and labels as its own.

- **That a frame file existing is not proof it finished writing.** Labels: **documented, inferred and observed, the same in every version, on both machines** — see **Frames 6** in [the checked comparison](../../Blender%20Research/Comparison/Frames.md). Two separate reasons: Blender writes straight to the final name rather than renaming at the end, so a file can be caught part-written; and a placeholder file sits at the finished frame's own path from the moment that frame's work begins. **This also lands on [Download](../Download.md)**, which watches one folder for new arrivals: a file appearing there during a render is not yet a file worth bringing home. *(Was unresolved and owned by Open Threads; answered by the research on 2026-08-06.)*

- **Whether Blender can be asked for only the frames that are not already on disk, and how it judges that.** Labels: **documented and inferred for the switch, observed for the rule** — see **Frames 4** in [the checked comparison](../../Blender%20Research/Comparison/Frames.md), and **File output nodes 10** in [its comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md) for the scene's Overwrite setting not reaching a file output node. The answer is yes but too coarse to lean on: it looks at the regular output path's own file only, judges by bare existence so an empty file counts as done, and does not reach file output nodes at all. So Smoozy does the reckoning and hands over a list of frames, which **Frames 7** in [the same comparison](../../Blender%20Research/Comparison/Frames.md) shows works in every version and may mix single frames and stretches. *(Was unresolved; answered by the research on 2026-08-06.)*

- **What a job whose regular output is one video file writes, and what a stopped render leaves of it.** Labels: **observed; the file splitting, what each stop fires inside Blender, and the setting holding one value on a rented Linux machine alone** — see **Frames 5 and 12** in [the checked comparison](../../Blender%20Research/Comparison/Frames.md), **Writing 8** in [its comparison](../../Blender%20Research/Comparison/Writing.md) for how the one file is named, and **Frames 4** for Overwrite having no effect on a video output. **Question 12 added the part the document's decision now rests on.** The file appears within moments at a token size and **its reported size does not move while the render runs**, reaching its real size only when the file is closed — at the end of the render, or at a split. So watching that file says nothing about progress. **Two limits belong with that, and the spec now carries both.** It rests on **one container and one codec**; a survey of ten containers found each leaving a different amount behind after an interruption, so none of this is a fact about video output in general. And **a size that does not move is not the same as nothing being written** — what the round establishes is that the reported size waits for the close, not where the frames are meanwhile, which is why a stop that lets Blender close the file properly gets them all back. What a stop leaves depends on which stop: an interrupt leaves a file holding the frames that were finished and fires Blender's own cancelled-render notification; a polite request to close and an outright kill each leave the token size with nothing in it, and the polite one fires nothing at all. A file already split away survives whole. A second run replaces what was left rather than adding to it. And **one render's own output cannot be a video and a set of images at once** — the setting holds one value — which closes a premise two versions' earlier readings had rested on with nothing behind it. What is decided in the document out of all this — one file counted with the number stated as possibly growing, a whole-range re-run, and a warning before submitting — is Smoozy's own and earns no entry here.

- **A frame with no view layer active on it renders nothing and writes nothing.** Owned by the [Glossary](../../Groundwork/Glossary.md), which carries the label and the citation. Listed here because the file count rests on it.

## Starting a render

- **What each of the ways of starting a render writes, and what that means for a render started from outside Blender's interface.** Labels: **documented and observed; the frame-number rule differs by version** — see **Writing 6** in [the checked comparison](../../Blender%20Research/Comparison/Writing.md), and **File output nodes 13** in [its comparison](../../Blender%20Research/Comparison/File%20output%20nodes.md) for the frame number.

  **This is a clash, and the research wins.** The Creator stated (2026-07-28) that a single-frame render does not write to the regular output path at all, while file output nodes still write on one — and that the difference was seen from inside Blender's own interface, which is the one place Smoozy never stands. The research found that the difference is not between a still and an animation at all: what decides it is whether the render is **told to save**. Inside the interface the still route passes no such instruction, which is why the Creator saw what they saw. From outside, a render asked for on the command line is always an animation render and always writes; a render driven by a script writes a still only when it is separately told to. The half of the recollection about file output nodes holds — a node writes on every shape of the render call, in every version.

  **And the research made the always-an-animation rule worth more than it was.** From Blender 5.0 a file output node stamps the frame number on its file only for an animation render, so a job rendered any other way would leave files the re-run could never find. That was not the reason the rule was made, and it is now the strongest reason to keep it.

## Pictures, passes and formats

- **Telling a beauty pass from a utility pass.** Owned by the [Queue & History sources](Queue%20&%20History.sources.md), which carries the label and the citation. This document leans on it harder than anything else does: it is what finds the main output, not only what the preview shows.

- **What Blender calls the finished picture, and what it calls the diffuse colour pass.** Labels: **documented and observed; the beauty the same in every version, the diffuse colour pass differs by version** — see **Images 1** in [the checked comparison](../../Blender%20Research/Comparison/Images.md). The beauty pass is `Combined` everywhere; the diffuse colour pass is `DiffCol` in Blender 4.5 and `Diffuse Color` from 5.0.

  **CORRECTED 2026-09-20 — the document read this entry as covering three places, and the third of them is false.** Its sentence gave the name as the same *"in a written file, in a multi-layer file's list of layers, and on the socket it comes out of"*, all three under the labels above. **The socket half is not what the four Blenders say.** Every Render Layers node in **4.5.12, 5.0.1, 5.1.2 and 5.2.2 LTS** was read at the desk, under Cycles and under the built-in engine alike: **the socket the beauty leaves on is called `Image`, and no socket on the node is called `Combined` at all.** Label: **observed in a test** — `Audits/Build/Step 10c/Piece 13 — what landed.md`, finding 1, read 2026-09-20, which is the same reading the [Job files and outputs sources](../../Architecture/Sources/Job%20files%20and%20outputs.sources.md) entry 46 carries; what it found is written out here so a reader who does not open it still has the fact. **Nothing else in this entry moves:** the name in a written file and in a multi-layer file's list of layers was not read against, and neither was the diffuse colour pass. **Not covered:** no Windows machine, no version outside those four, and no engine outside Cycles and the built-in one.

- **A diffuse colour pass also shows whether the textures loaded.** Label: **Creator-stated** (2026-07-28), **and not confirmed** — see **Images 2** in [the checked comparison](../../Blender%20Research/Comparison/Images.md). What the research settles is that a missing or unreadable texture comes out flat magenta in the **finished picture**, in every render engine and every version, on both machines and either make of graphics card. Which separate passes carry that magenta was tested in no version, so the claim about the diffuse colour pass specifically is neither confirmed nor overturned — and the reason it was made the preview's second choice is weakened, because the top rung already shows the failure. Three further limits are recorded there and all narrow the preview's promise: nothing says which texture is missing, nothing tells a missing texture from a genuinely magenta surface, and a texture driving something other than colour was never tested at all. The third of those has an entry of its own below.

- **Whether a missing texture that drives something other than colour shows in the picture at all.** Label: **observed** (the same in all four versions, on both machines) — see **Images 9** in [the checked comparison](../../Blender%20Research/Comparison/Images.md). **It came back the unfavourable way this entry feared, and every promise named below is narrowed rather than broken.** The stand-in for a picture that cannot be found is handed out at the lookup itself, before anything downstream knows what the value will be used for, so it reaches a bump or a mask as a number rather than as a visible colour. A missing bump map gives no bump — indistinguishable from nothing connected. A missing displacement map shrinks the object evenly with no relief in it. A missing normal map leaves the whole surface shaded as though tilted. A missing transparency map hands the fully solid end to whatever reads it — **that one is what a measured value implies, since no test rendered such a mask**. The compositor substitutes black and a geometry node setup zero, neither of them the magenta. A volume whose data file is gone draws nothing at all and says nothing. Every one of those finishes at a successful exit status with the frame written and the error stream empty. **Two of them do leave a large measured mark on the picture** — the displacement one moves the object's outline by hundreds of pixels and the normal one shifts the shading everywhere. What none of them leaves is a mark that reads as a failure, which is the point.

  **So three promises are narrowed and each now says so where it stands.** The frame preview's claim that it says the textures loaded, which is [Queue & History](../Queue%20&%20History.md)'s and points here for its limits; the picture a finished-job notification carries; and this document's own top preview rung. All three now hold only for a texture that was feeding **colour**. **What can be asked for instead** is Blender's own report of a file's missing references, which works with no window and names each one — the same reading [Dependency Upload & Remap](../Dependency%20Upload%20&%20Remap.md)'s check is built on, and it needs no render. **Not covered:** Windows; a missing picture reached through a legacy texture data-block rather than a shader node; a render actually made with the value driving roughness or metallic, as against the conversion measured directly; and graphics cards of any other make. *(Was unresolved; answered by the research on 2026-08-09.)*

- **What a render prints about a missing picture, which differs by engine as well as by version.** Label: **observed; differs by version and by engine** — see **Images 9** in [the checked comparison](../../Blender%20Research/Comparison/Images.md) for the Cycles answers, **The machine 7** in [The machine's comparison](../../Blender%20Research/Comparison/The%20machine.md) for the EEVEE one, and **Images 2** in [the same comparison](../../Blender%20Research/Comparison/Images.md), which puts the two side by side. **This corrects what this entry said before.** Under **Cycles**, Blender 4.5 prints nothing that marks the picture as missing: a search of a whole run's output for every word that might name the failure matched only the line saying the frame was saved, and the two runs differed in nothing but the output file's own name and the time taken. One line does name the picture, the ordinary loading line, but it is printed whether the file is there or not, in every version, so it marks nothing and no watcher can use it. Under **EEVEE**, 4.5 does print a line saying a texture was not loaded, and prints it only when the picture is missing — both runs with the picture present were searched and returned nothing. It does not name the picture, and neither does what the newer three print in its place: a differently worded line about failing to make a graphics texture. **Back under Cycles**, Blender 5.0 and 5.1 print an error naming the path; 5.2 prints a warning and adds a count of what failed to load. All of them, under either engine, exit at success with the frame written. **Sharpened 2026-09-01, after the research was repaired, and the sharpening is in two directions at once.** **What the render *does* is now settled on two machines in all four versions, on a test that could have failed** — the earlier runs used a file whose image sat in a material slot no face of the cube used, so removing the picture changed nothing and the silence recorded then was silence about a texture that reached nothing; rebuilt with the texture in the slot the faces actually use, the control fires and **the run still ends by itself at exit status 0 with its frame written, in all four versions on both machines.** **What Blender *prints* is still the Linux machine alone**, and that limit is unchanged. **And the wording differs more than a line shape**: 4.5 prints `GPUTexture: Blender Texture Not Loaded!` before anything else, **with no marking of any kind and without naming the file**, while 5.0, 5.1 and 5.2 print `ERROR Failed to create GPU texture from Blender image` in a column of their own. **So a watcher written against one version's words finds nothing in the others**, and no version names which picture. **Not covered:** whether Cycles ever prints the EEVEE line, which was not asked; Windows; and what a Mac prints about a missing texture that really is in the picture. So a job rendered on 4.5 through Cycles leaves no trace of a missing texture anywhere except in the picture, and only where it was feeding colour.

## Added 2026-09-01, after the research was repaired — the condition every counting answer here was measured under

- **Every counting and already-there answer in this file was taken on a scene with one view, and none of them says so.** Label: **observed in a test** — *Frames*, resting on *Writing 8* and *Images 5*, with the multi-view half run on **one rented Linux machine and on no Mac**. In that comparison's own words: *"Every one of those answers, and every Overwrite test on this sheet, was taken on a scene with one view. With two views switched on, no file with that name is written at all — the files are `img_0001_L.png` and `img_0001_R.png`."* With the settings as they come every version writes **two** files per frame, one per eye, left then right; told to put both eyes in one file, every version writes **one**.

  **What breaks is not a frame but the whole job, and it breaks in silence.** Every predicted name is absent, so every frame counts as not there, the job reports as incomplete, and a re-run does the entire range again — over a job that rendered correctly and wrote both files for every frame.

  **What the spec does about it, and what it deliberately does not.** It stops predicting: where the scene writes more than one view, no reckoning is made, the reason is said, and no absence is read as evidence. **It does not work out the per-eye names**, and that refusal is the point — the suffix was seen for still pictures on one machine only, and for a video the name **differs between Blender versions** (`stereo_0007-0009_L.mp4` in 4.5 and 5.0, `stereo_0007-0009.mp4` in 5.1 and 5.2), so a rule built from that would be assembled out of separate answers rather than read from one.

  **Not covered:** what a stop landing between a frame's two files leaves, never tried in any version; and whether Smoozy should carry such a job at all, which nothing in these specs has ever mentioned and which is the Creator's to say.
