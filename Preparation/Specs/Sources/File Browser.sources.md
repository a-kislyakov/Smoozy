# Sources — File Browser

*Where the outside-world facts in the [File Browser spec](../File%20Browser.md) came from. The spec carries each fact's label in place; this file carries the citation behind it, and what that citation does not cover.*

- **A `.blend` file records the Blender version it was saved with, in a header Smoozy can read without opening or parsing the file.** Label: **Creator-stated** (2026-07-23) — a Blender fact the Creator supplied. Because it is header-readable, showing the saved-with version does not depend on the file having been pre-loaded.
- **The version is in the file's opening text, and Blender 4.5 writes that text differently from 5.0, 5.1 and 5.2. From Blender 5.0 an ordinary save is compressed, with a common compression that other tools can undo.** Label: **observed** for the opening text (the same in all four versions, on both machines), **documented** for the compression — Blender Research comparison, **Reading a file 1**. No version's documentation describes the file's inside, so what its opening text holds and how it differs between versions rests on the tests rather than on a manual; the compression is in every version's manual. This carries the Creator-stated fact above rather than contradicting it, and adds two things the Creator did not state: the opening text is not one shape across versions, and a plainly saved file from 5.0 onward is compressed. Neither changes what the spec promises the user. What it does not cover: how the file's inside is laid out, and Windows, which was never tested.
- **A file deleted on the server is gone for good** — there is no recycle bin, trash, or undo on the rented machine to fall back on. Label: **an assumption** — an agent's recollection of how a remote machine's filesystem behaves, not confirmed against documentation, and operating-system and filesystem behaviour is one of the outside facts Rule 2 covers. What the spec states is Smoozy's own behaviour — it keeps no copy and offers no undo, and warns before deleting — which stands on the Creator's decision; only the claim that the file is unrecoverable *on the machine* is the unconfirmed part. Confirm before anything leans harder on it than the warning does. If a rented machine turns out to offer any recovery, the warning's "is gone" wording has to soften. Parked in [Open Threads](../../Groundwork/Open%20Threads.md).

- **Whether a machine permits elevated access** is settled, and so is **how** that access is obtained. Label: **settled at Architecture** (2026-08-23), by running it on rented machines. **Corrected 2026-08-23**: this entry read **unresolved** while the body it serves said settled, so the spec pointed at its own refutation. That Smoozy *offers* to retry with elevated access where possible remains its own decision (Creator-stated, in the body); the outside fact underneath it is what moved.

  **The answer differs by machine kind and is not one answer.** [Architecture — Server Setup](../../Architecture/Server%20Setup.md) §1 carries the table and §9 the route. On a whole rented machine the login can elevate — observed with nothing asked and observed asking for a password. On a machine rented as a container the login Smoozy connects with is not that container's own owner and there is no route to elevate by, so no offer is made rather than a password being asked for that could open nothing; that is what two of three providers shipped ([The multi-provider batch](../../Architecture/The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md)). On a machine that cannot be placed as either kind there is no offer either.

  **How it is obtained** is the machine's own elevating command with the password on its standard input — `sudo -S`, documented: *"Write the prompt to the standard error and read the password from the standard input instead of using the terminal device"*, `sudo(8)` 1.9.17p2, read 2026-08-19, cited in the [Server Setup sources](Server%20Setup.sources.md). A command argument is not used, because it is readable by any other login on the machine. Label: **documented**.

  **What is not covered.** The kinds observed are the kinds this project has rented; a machine of a kind nobody here has met falls to the third branch above, which makes no offer and reports the refusal as it stands. That is the negative outcome handled rather than a gap.

  **What the user is asked for when elevating is no longer part of this, and no longer depends on that answer.** It was settled on 2026-08-10 under *Security* in the [Whole app spec](../Whole%20app.md): where elevated access needs a password, Smoozy asks at that moment and the user chooses whether it is kept for that one action, for as long as the connection lasts, or until they clear it. Label: **Creator-stated** (2026-08-10). That is a decision rather than an outside fact and earns no citation here.

- **Whether an interrupted upload can be carried on from where it stopped** is not settled. That Smoozy never re-sends what already crossed, and gives the promise up rather than joining two versions of a file together, are its own decisions (Creator-stated, in the body). How a part-sent file is carried on is an outside fact about how transfers behave. Label: **unresolved** — for Architecture. If a transfer turns out not to be continuable part-way, the promise is a hole in this spec, to be fixed here rather than quietly reinterpreted. Parked in [Open Threads](../../Groundwork/Open%20Threads.md).

- **Whether Smoozy can tell that a file changed while it was going up** is not settled. The no-corruption promise at line 94 rests entirely on it. Some programs save by writing a new file and swapping it in, which may slip past detection. Label: **unresolved**. Parked in [Open Threads](../../Groundwork/Open%20Threads.md).

- **Whether Smoozy can work out every file a job depends on** is an outside fact. Label: **unresolved** — already parked in [Open Threads](../../Groundwork/Open%20Threads.md). The Blender facts under it belong to the [Dependency Upload & Remap spec](../Dependency%20Upload%20&%20Remap.md), which owns them; this document points at that one rather than keeping its own copy. Research has since moved all three pieces of it:
  - **A file's chain of references can be read while some of the files in it are absent, but the chain stops at the first absent file — what that file points at in turn is named nowhere.** Label: **observed** — Blender Research comparison, **Reading a file 8**; the same in 4.5, 5.0, 5.1 and 5.2. This is why the spec now says the warning covers the files Smoozy can see rather than every file the job uses. What it does not cover: Windows, untested.
  - **What a file points at can be traced to the scene that uses it.** Label: **observed** (the same in all four versions, on both machines) — Blender Research comparison, **Reading a file 7**. The documentation carries the map this rests on but not the walk over it, which is why the label is observed rather than documented. Recorded here only because it bears on the same warning; the fact's home is the Dependency Upload & Remap spec, and nothing in this document leans on it directly.
  - **Rendering one scene of a file does not open the other scene's picture at all, and a `.blend` linked as a library is opened whichever scene is rendered.** Label: **observed** (the same in all four versions, on both machines) — Blender Research comparison, **Dependencies 14**. This was recorded here as unresolved and the research answered it on 2026-08-07. The old test asked whether Blender *complained* about the other scene's missing file, and Blender 4.5 never names a missing picture at all, so that test could not have come out the other way and settled nothing; it was replaced by readings that watch the computer rather than ask Blender, and every control worked. The library is opened either way because it is read when the file is loaded rather than when a scene is drawn. What it does not cover: anything beyond the two kinds tried — a picture used by a scene's material, and a `.blend` linked as a library; a scene reached *from* the rendered one, as a background scene, through a compositor node naming another scene, or through a sequencer scene strip, which no test on either machine has touched; whether naming the scene at the moment the render starts changes any of it; and Windows. **Whether the live-job warning narrows to one scene's files is a decision about what Smoozy does, and is not taken here. It was taken on 2026-08-12 and the answer is no** — the warning stays wide, because the untested cases named just above are exactly where a narrowed one would be silent when it should not be. That ruling is Smoozy's own and earns nothing further here; the spec carries it.

- **Whether the machine's free disk space can be read over a connection** is an outside fact for Architecture. Label: **unresolved** — parked in [Open Threads](../../Groundwork/Open%20Threads.md). **What breaks if it cannot be read.** This is the only place anywhere in Smoozy where the user can learn that a machine's disk is full, and the only way they can confirm that clearing space worked. A negative answer leaves a render killed by a full disk with no diagnosis available from inside the app at all — and it takes two promises made elsewhere with it, both of which rest on this reading: that such a failure names the disk as the cause and says to free space, in [Whole app](../Whole%20app.md); and that a rendering job shows how much room is left on its machine, in [Queue & History](../Queue%20&%20History.md).

The spec's other behaviours borrowed from the [Download spec](../Download.md) — the already-exists question, the set number of transfers at once, and the single file as the transfer unit — are Smoozy's own decisions, mirrored so the two directions behave alike. Where those were first drawn from how the macOS Finder or web browsers behave, that is where an idea came from rather than a fact anything rests on, so no citation is owed for it here or there.

## Added when the second and third rounds of Blender Research were carried in (2026-08-10)

- **What replacing a file a running render depends on actually does to that render.** Label: **observed** (the same in all four versions, on both machines). **Reading a file 11** — see the [comparison](../../Blender%20Research/Comparison/Reading%20a%20file.md). Owned in full by the [Dependency Upload & Remap sources](Dependency%20Upload%20&%20Remap.sources.md); it appears here because it is what this module's live-job warning is protecting against. **A picture replaced under a running render reaches it from some later frame onward** — the frames up to some point hold the old one and every frame after it the new one, and **no frame ever came out part old and part new** in any of the eight runs. Which frame the change lands on moves with the timing and is not a version difference. **A changed picture also reaches the very next render inside a running Blender with nothing done at all**, which is the opposite of what every version's documentation would lead a reader to expect. A **linked `.blend`** and a **movie clip** behave the other way and do not reach the **next** render until reloaded, neither having been tried under a render already running; a **packed** picture ignores its file on disk where nothing is done about it; and one render setting, off by default, stops a changed picture being picked up by the next render — it was measured there rather than under a render already running. **So the harm the warning prevents is usually a job that finishes and is wrong rather than one that stops** — which is why it is not dismissible. **Not covered:** what happens if a file is deleted rather than changed; **what happens when the replacement differs in size, format or colour depth from the file it replaces**, which is exactly what this module's Replace does and is on the research's own not-established list; the version split for a picture behind a sequencer strip, which reaches the next render by itself in Blender 4.5 and in none of the newer three; three results where repeated runs disagreed and every run stands; and Windows.
