# Sources — Dependency Upload & Remap

*Where the outside-world facts in the [Dependency Upload & Remap spec](../Dependency%20Upload%20&%20Remap.md) came from. The spec carries each fact's label in place; this file carries the citation behind it, and what that citation does not cover.*

*Note: what Smoozy does here — that the check is the user's own action and reads with the Blender the job will render with, where an uploaded asset lands, the states a row can be in and which of them mean Smoozy actually looked, what the user may override, telling files apart by what is inside them, keeping a record on the user's computer, never writing to the file the render is built from, preserving whatever the user sent up, never checking anything at a submission, what stops Rendering's warning and what replaces it, and never removing assets by itself — is Smoozy's own decision throughout, so none of it earns an entry here.*

## From the Creator

- **Other render farms require a `.blend` to be packed before it is sent** — everything the file needs bundled inside it. Label: **Creator-stated** (2026-07-26). Owned and cited by the [Rendering sources](../Sources/Rendering.sources.md), where the same fact carries the submission warning. It appears here because this module's founding choice is stated against it: Smoozy deliberately does not work that way, and the cost of not doing so is this whole module. It also establishes that a `.blend` can hold its dependencies inside it; that it can do so *partly* is answered below.
- **A `.blend` records a location for each thing it points at, and that location can be written relative to the file itself rather than in full — which is Blender's usual way of writing it.** Label: **Creator-stated** (2026-07-28). The spec's first search rests on this, and so does its stated limit: a relative location is of no use once the file has moved to the machine, unless Smoozy watched that file go up. The shift rests on it too. Does not cover which form Blender writes by default: the research establishes which forms exist and how each behaves (**Dependencies 5**) and says nothing about which is usual, so that word rests on the Creator alone.
- **The kinds of thing a `.blend` can point at include textures, physics caches, geometry nodes simulation bakes, volumes, linked `.blend` files and remote libraries.** Label: **Creator-stated** (2026-07-28), and stated by the Creator as a floor rather than the answer. The full list is at **Dependencies 1** and covers every kind the Creator named. The term *remote libraries* has no counterpart in the research: a file points at one kind of library, another `.blend` (**Dependencies 2**). This is not recorded as a clash — a library reached over network storage is a `.blend` at a location of that kind, and what such a location means is the part no version settles (**Dependencies 7**).
- **A linked `.blend` carries its own dependencies, and the linking can go to any depth.** Label: **Creator-stated** (2026-07-28). The spec's two-kinds-of-remap split rests on it. Corroborated by **Dependencies 13**. Does not cover a maximum: none is documented in any version, and a render stops bringing an object in at nine nested collection instances while the files themselves still record and resolve.
- **Reading a `.blend` for what it points at needs a Blender**, and is the same kind of read Pre-load Settings performs for a file's settings. Label: **Creator-stated** (2026-07-28). The underlying fact is owned and cited by the [Render Settings sources](../Sources/Render%20Settings.sources.md). That the read happens on the machine, with the Blender the job will render with, is Smoozy's decision rather than part of the fact. **Reading a file 1** neither contradicts nor confirms it: no version's documentation describes the file's layout, so nothing establishes that only Blender can read one.
- **Blender versions differ in what they can do, and some files will not open in some versions at all.** Label: **Creator-stated** (2026-07-27). Owned and cited by the [Render Settings sources](../Sources/Render%20Settings.sources.md). It appears here because the check reads with the Blender the job will render with, which may be one that cannot open the file.
- **Two files on one computer cannot sit at the same full location**, so the whole location identifies a file on the computer it came from. Label: **an assumption** — nothing in this project has established it. The spec's whole rule for where an uploaded asset lands rests on it, and the spec's body carries the same doubt. The research does not touch it. It settles one neighbouring half only: whether two names differing in capitals are one file or two is the disk's decision, not Blender's (**Dependencies 8**).

## Facts about rented machines, not about Blender

- **Whether the check's read can be carried out on a rented machine.** Label: **an assumption**. That a `.blend` can be read for what it points at is settled and cited below, on the Creator's Mac and on the rented Linux machines the research used. What has no source in this project, and did not come from the Creator, is that **Smoozy** can drive that read on a rented machine over the connection it holds, on machines it never touched. It is the same unconfirmed ability the rest of the plan leans on for a rented machine — restarting one, searching one for the Blenders it holds, reading one for the work left on it — and it is not a Blender question. It does not go to Blender Research.

  **What falls over if it cannot.** The check itself, which is the whole of this module's first job: the read happens on the machine, with the Blender the job will render with, so a machine that cannot be driven produces no rows, no found files, nothing sent and nothing remapped. A user renting a fresh machine for an old project meets it at once — they put the `.blend` up, ask what it is missing, and there is no answer. Everything downstream of the rows goes with it: what stops [Rendering](../Rendering.md)'s missing-assets warning, the record of what each reference resolved to, and the remap that makes an uploaded asset get used at all. A negative answer is a hole in this spec rather than a narrowing of it. Parked for Architecture in [Open Threads](../../Groundwork/Open%20Threads.md), with the other rented-machine assumptions.

## From Blender Research

*Each entry gives the label and points at the question in the comparison, which is what a reader opens and where the fact lives. The comparisons cited below sit in `Preparation/Blender Research/Comparison/` and are **Dependencies**, **Reading a file**, **Node setups**, **Images** and **Writing**. All cover Blender 4.5, 5.0, 5.1 and 5.2, tested on the Creator's Mac and on rented Linux machines. **Nothing in any of them was tried on Windows**, so every entry below reaches those two kinds of computer and no further — which matters, because the artist's own computer may be a Windows one.*

- **The kinds of thing a `.blend` can point at.** Label: **documented and observed**. **Dependencies 1** — the same in all four versions; what differs between them is only what exists to find and name those pointers. Does not cover whether the list is complete: no version's documentation claims it is, and a test file holds only the kinds it was built to hold.
- **What kinds of library a file can point at.** Label: **documented**, with the second kind new in Blender 5.0. **Dependencies 2**. Does not cover a library that does not sit on the same computer.
- **A font is an ordinary recorded location, with nothing family-name-shaped anywhere in any version** — no family, no style, no lookup key into the computer's own font list. Label: **documented and observed**, the same in all four versions. **Dependencies 16**. Does not cover where Windows keeps its fonts, nor **whether Blender ever resolves a font by family name rather than by path**, which that question records as not established: nothing in any version suggests it does and nothing rules it out.
- **Which of a file's recorded locations are places it writes to, and where such a write lands.** Label: **documented and observed**. **Dependencies 10**. Two writes differ by version, and Blender 5.2 has one the others do not. Does not cover what a render does when it genuinely cannot write where it points.
- **Whether a place a file writes to is later read back.** Label: **observed** (the same in all four versions, on both machines). **Dependencies 17** — and the answer is yes. A render with Overwrite switched off skips the frames that are already at the recorded output place and names each one it skips — **that Blender looks at that place to know which frames are already there is the one step every version marks inferred**, the sources stating the outcome and never the mechanism; and Cycles' own animation denoiser reads that place and stops on a frame that is not there, which is observed in all four. The same question settles two more things this module leans on: **a render makes an output folder that is not there, one level deep and two levels deep, without a word**, which no version's documentation says of the render output path; and **a zero-length file at the output place counts as a frame already done** where Overwrite is off and placeholders are on, so that arrangement rests on a name being present rather than on a picture being in it. **Does not cover** the tooltip on a red path field, whether frames are claimed the same way over a network, or Windows. *(Was unresolved; answered by the research on 2026-08-07.)*

- **Whether Blender's own bulk path commands reach the places a file records for writing.** Label: **observed** (the same in all four versions). **Dependencies 17**, with the fuller sweep at **Reading a file 9**. **They do not.** Of six recorded locations put side by side, making every path relative or absolute, reporting missing files and Blender's own list of a file's outside paths reach only an ordinary image and one cache path — not the render output path, not a File Output node's folder, not a point cache, not a geometry-nodes bake folder. So making a file's paths relative leaves its output path alone, and asking Blender what a file points at will never name a bake folder that has gone.

  **This was a hole in the spec rather than a gap in the answers**, found on 2026-08-06 by a check the Creator asked for. The module had classified all of them write-only and therefore did not send them, which loses a bake the render needed and produces a picture of something else at full price — **Dependencies 12** establishing that a render with missing pieces finishes and reports success. The classification is corrected in the body, the safe side is taken until the question is answered, and the question is parked in [Open Threads](../../Groundwork/Open%20Threads.md) for the next research round. Recorded in the `Audits/Specs/Dependency Upload & Remap/Decisions record.md`.
- **What a render does when a cache or a bake the file records is absent.** Label: **observed** (the same in all four versions, on both machines). **Dependencies 18** — and it is the unfavourable answer. The render works the simulation out again rather than skipping it, says nothing at all, finishes at success, and gives a picture that is not the baked one — **and it does not work it out from the beginning**, so a farm rendering a frame out of order gets very little of the simulation. That holds for a physics disk cache and for a geometry-nodes bake. **Corrected 2026-10-02 — the desk saw otherwise, in the next entry.** A physics cache marked baked with its files missing was not worked out again, and nor was a geometry-nodes bake or simulation. **For an EEVEE light probe volume only the outcome holds** — a different picture, silently — since what stands in for the bake is every version's reading of one manual sentence, marked **inferred**, and no test looked at what the light actually was. **Two things can be noticed from outside and only two.** An external physics point cache pointing at an empty folder reports itself as holding no valid data, readable with no window; and a physics disk cache written by Blender 4.5 is refused by 5.0, 5.1 and 5.2 with a message saying it must be deleted and re-baked, printed twice, after which the render carries on at success and gives a different picture. Everything else is silent. **A fluid cache is the worst case**: with the folder gone the file goes on reporting every part of it as baked, because those marks are held in the file rather than read off the disk, and opening the file makes the folder again and writes a frame into it. **Does not cover** what a render does when an ocean modifier's baked files are gone, which was attempted on both machines and answered on neither; whether a partly-present cache differs from a wholly absent one; or Windows. *(Was unresolved; answered by the research on 2026-08-07.)*
- **What a render does when a cache or a bake is absent, as seen at the desk — and it is not always worked out again.** Label: **observed in a test**, at the desk, 2026-10-02, during the Build stage, from the command line with no window, on copies. **Not the Blender research.** Three cases. **A geometry-nodes simulation that was never baked does not move at all**: a control scene lifting a cube each frame gave frame 1 and frame 24 pixel-identical, in Blender 4.5.12, 5.0.1, 5.1.2 and 5.2.2, with nothing printed and a success at the end, while the same file stepped frame by frame first rendered the cube risen. **A physics cache marked baked whose files are missing gives the object as it starts, unmoving**: a baked cloth with its cache folder taken away hung still at its starting height — frame 24 alone in 4.5.12 and 5.2.2, and every frame of 1 to 24 rendered in order in 4.5.12. **A geometry-nodes Bake node whose folder is missing leaves the baked object out**: in 4.5.12 and 5.2.2. Source: `Audits/Build/Step 10c/Simulation files at the desk — what was seen.md` (the control scene, *Geometry-nodes simulations*, and `bake_load`) and `Audits/Build/Step 10c/Does the redirect cut the render off from bakes — what was seen.md` (the cloth disk cache, *plain-without*, and `bake_load`). **Does not cover** a rented machine, Windows, a geometry-nodes simulation set to bake to disk and never baked, or any kind not named here; one Mac, the versions named.
- **Blender's list of a file's external references carries neither the render output path nor the File Output node's.** Label: **observed**, the same in all four versions. **Reading a file 4**, with the same result under **Dependencies 1**.
- **A file can be packed item by item; some kinds can never be packed; a partly-packed file says nothing about what it lacks when it is opened, and names it when asked.** Label: **documented and observed**, the same in all four versions. **Dependencies 3**.
- **A chain of linked files is read whole to at least nineteen levels, and a location recorded inside a library is measured from that library rather than from the file that was opened.** Label: **observed**, the same in all four versions. **Dependencies 13**.
- **The readable chain stops at the first absent file** — everything below a missing linked `.blend` is named nowhere. Label: **observed**, the same in all four versions. **Reading a file 8**. Blender 5.2 can list one level of another file's own libraries without opening it, which still needs that file to be there.
- **Something a file points at can be traced back to the scene using it**, with no window open. Label: **observed**, the same in all four versions. **Reading a file 7** — which has since answered the three awkward cases as well: a reference held only inside a node group, one that is only a driver's target, and one held only by a custom property are all reachable, in all four versions, **on the rented machine alone**. Does not cover macOS for that half, nor any kind of thing but a picture put in those three places, nor what the walk costs on a large file. *(Those three were not covered; the research has since answered them.)*
- **The ways a recorded location can be written, and the two forms Blender never works out** — a home-folder shorthand and an environment variable. Label: **documented and observed**. **Dependencies 5**. Blender 4.5 offers four curly-brace template variables; 5.0, 5.1 and 5.2 offer ten.
- **Whether capital and small letters matter is decided by the disk, not by Blender — and Blender's own search for missing files minds them too.** Label: **observed**, the same in all four versions, on a Mac disk and on a rented Linux machine. **Dependencies 8** — which also settles that names held *inside* a file are told apart exactly, on both machines and in all four versions. Does not cover Windows.
- **What a location written on the artist's computer means on the machine**: a relative one survives whole, a full one is kept, resolved as written, and simply not found, with nothing said unless Blender is asked. Label: **observed**, the same in all four versions. **Dependencies 6**. Covers a Mac carried to a rented Linux machine, and nothing about Windows at either end.
- **What a location pointing at another computer means, at either end.** Label: **unresolved**. **Dependencies 7** — no version's documentation describes one, and it could not be tested for want of storage two machines can both reach. The one adjacent result, about a volume that is not mounted, is not an answer to it.
- **Names written in non-Latin characters survive being read out, carried to the machine, and found by the render.** Label: **observed**, the same in all four versions. **Dependencies 9**. Does not cover a name the two computers would store differently, nor Windows. The same answer holds the version difference in how long a name inside the file may be — 63 bytes in 4.5, 255 in 5.0, 5.1 and 5.2.
- **One reference can mean many files, in several ways; Blender will list the real files only from version 5.2.** Label: **documented and observed**. **Dependencies 4**. Does not cover how Blender decides which files on disk belong to a sequence.
- **A reference points at a named thing inside another file, and a rename breaks it exactly as a removal does, reported in the same words.** Label: **observed**, the same in all four versions. **Dependencies 11**.

  **Widened 2026-08-23, because the body now leans on a second half of the same question that this entry did not carry.** What was cited stopped at *reported in the same words*; what the spec rests on it for is what the report contains. **Dependencies 11** also records, in all four versions, from a terminal on the Creator's Mac and again on a rented Linux machine: the reported line for the file-present-item-missing case **names the item and its library file**, with the count beside it reading `0 libraries`; and what is left in memory is an empty placeholder marked as missing that **keeps the item's name and its library**. **So the count is what separates *the whole library file is gone* from *the file is there and the item is not*, rather than being the whole of what is reported.** **Does not cover** telling a rename from a deletion, which that question records as genuinely indistinguishable, nor whether Smoozy's own reading can observe the stand-in at all, which the body carries as open.
- **What a render does when something it points at is missing, and what it says about it.** Label: **observed**. **Dependencies 12** — what it does is the same in all four: it finishes, writes the frame and reports success. What it says differs: Blender 4.5 never names a missing image, 5.0 and 5.1 print one error, 5.2 prints a warning and a separate counting error. Does not cover whether a missing dependency ever changes the exit status; every case tested came back a success.
- **A `.blend`'s recorded locations can be read out and written back, by Blender, with no window, and the change survives a save and a re-opening.** Label: **observed**, the same in all four versions. **Reading a file 5** — which also answers that half for a linked library: assigning its path changes what is recorded at once and leaves the old data in place until the library is reloaded, and the relocate command does both in one act — that half in all four versions **on the rented Linux machine alone**. For anything but a library, whether a write is enough on its own is still untried.

- **Which kinds of recorded location each way of listing or rewriting them actually reaches.** Label: **observed; differs by version**. **Reading a file 9** — the central half of that question, which every version's documentation leaves unstated. A file holding **twenty-one** kinds of recorded location was put to every route Blender offers. Every one of these tests was run **on the rented Linux machine alone**. The plain list of a file's outside paths, and the sweeps that make every path relative or absolute, reach **sixteen readings** — a count of settings read back by name rather than of the twenty-one kinds — and miss seven: the render output path, the bake output path, the File Output node's path, a physics point cache, a geometry-nodes bake folder, the sequencer's proxy folder, and a path held in a custom property. **Walking Blender's own marks on its settings finds nineteen**, including six of the seven the sweeps miss; it misses the custom property and a text file's own path. **Finding is not the same as rewriting**: the step from "this setting carries no read-only mark" to "it can be written" is marked **inferred** in every version and no test closed it, so for the six kinds only the mark walk reaches, rewriting is an inference. **The two together cover everything but the custom property, and no single means reaches everything in any version.** One of those misses is softer than it reads: the absolute sweep was run on a file the relative one had already saved, in which those seven were still written out in full, so what it shows is that it changed none of them rather than that it would pass them by. Whether it reaches them is untried. A one-pass route that visits every recorded path and can rewrite each by returning a new one exists in **5.0, 5.1 and 5.2 and not in 4.5**, with 5.2 alone telling its caller more about each path. Two further things worth having: the wider form of the missing-file search silently repoints references that are not broken, and a path holding a template is left alone by every route. **Does not cover** Windows; whether the absolute sweep would reach the seven if they were recorded relative, which the run could not tell apart; what a tool that is not Blender could do; and whether nineteen tests run on the rented machine alone come out the same on a Mac.
- **Blender can report what is missing, search a folder for it and rewrite what it finds — and the report only ever comes back as words, in every version including 5.2.** Label: **documented and observed**. **Reading a file 6**, with **Images 9** for the report working with no window and naming each missing path in what it prints. So a program driving the render can read it out of the output; it is not handed a structured answer.

- **How Blender's own search chooses when several files could serve, and what it writes back.** Label: **observed** (the same in all four versions, on both machines). **Reading a file 10** — this is what the entry above used to say it did not cover, and every part of it argues for Smoozy doing its own searching. **A file is a possible match on its name, exactly, capitals included**, and the Mac gave that answer too. **That strictness is Blender's own rule and not the disk's — settled 2026-09-01, after the research was repaired; this read *unresolved* until then.** The comparison now carries the run with the control that decides it: with only an upper-case name on disk and a lower-case one recorded **neither machine found it**, while the control with the matching name found it on both — and the Creator's own Mac gave the failing answer *"even though its own file system does not treat capital letters in a file name as significant"*, which is precisely the case that separates the two readings. **Windows is untried and will stay so**, under the Creator's ruling of 2026-08-31 that there will be no further research and no further rented machine. **Nothing here turns on it either way**, which is why the spec closed the question without it. **Where several match, the largest file on disk wins**, whatever folder it sits in and however deep, with an exact tie in one arrangement going to the folder named `aaa` rather than the one named `zzz` — one observation, and nothing in the round establishes the rule behind it. **Nothing at all is said about there having been more than one**, in any arrangement, in any version, on either machine — with a control showing the same channel does carry the "could not find" warning, so the silence is real. **The wider form of the search silently repoints references that were not broken**, to a same-named file in the search folder. **And what it writes back keeps the form it was handed, as far as anyone has looked. Corrected 2026-09-02.** This read *"what it writes back is a relative location, where every version's own manual says recoveries are made as absolute ones — a documented promise the running program does not keep"*. **That claim was withdrawn on 2026-09-01** and this entry had not caught up, so it contradicted the correction standing further down this same file. **There is no disagreement and no broken promise.** The runs recorded here repaired locations written in Blender's own shorthand and got the shorthand back; the runs under **Dependencies 8** and **Dependencies 12** repaired locations written out in full and got full ones back. **Neither ever repaired the other kind**, so on this evidence the manual's promise is neither kept nor broken. **Whether the search keeps the form it found was never asked**, and it will not now be asked — the Creator ruled on 2026-08-31 that there will be no further Blender research and no further rented machine. Label: **permanently unresolved**, filed at the [Dependency Upload & Remap architecture](../../Architecture/Dependency%20Upload%20&%20Remap.md), section 12 item 25 *(filed as item 23 on 2026-09-02 and renumbered the same day, that number being already in use)*. **Nothing breaks on it**: Smoozy does not lean on Blender's search, and where it writes a location back it writes the one it means. It also rewrites without reading the file, reaches at least eight folders deep, and reached all six kinds of reference tried in one run. **Does not cover** whether undo reverses a recovery at a window, what a panel shows when several candidates are found, or Windows.
- **A `.blend` records a location pointing into the Blender application it was saved with, and Blender does not report that one as missing.** Label: **observed**, the same in all four versions. **Dependencies 1**, with the same entry seen under **Reading a file 5**.
- **A file relies on a colour management configuration held on the computer, storing only the name of a colour space.** Label: **documented and observed**. **Dependencies 15** — where the machine's configuration does not hold the name, Blender throws it away, substitutes its own, prints that it did so and renders on. Six things about it differ between the versions, and that question is where they are set out. **Does not cover what the finished picture then looks like**: no test there rendered one and compared it, which is why the body labels that step **inferred** and not observed.
- **Whether rendering one scene of a file pulls only that scene's references.** Label: **observed** (the same in all four versions, on both machines). **Dependencies 14** — **the verdict changed**, and the reason it changed is worth keeping. The old test asked whether Blender *complained* about the other scene's missing file; in Blender 4.5 the renderer never names a missing image at all, so that test could not have come out the other way and it settled nothing. It was replaced by two readings that watch the computer rather than ask Blender: a trace of every file each render opened, on the Linux machine, and the time the disk records for when each file was last read, on the Mac. Both agree in all four versions: **rendering one scene never opens the other scene's picture, and a `.blend` linked as a library is opened whichever scene is rendered**, because it is read when the file is loaded rather than when a scene is drawn. Both controls worked. **Does not cover** anything beyond the two kinds tried — a picture used by a scene's material and a `.blend` linked as a library — since the comparison says in as many words that the tests cover those two "and nothing else a file can point at". Nor a scene reached *from* the rendered one — a background scene, a compositor node naming another scene, or a sequencer scene strip — which is exactly the case where a render genuinely reaches into another scene, and which no test on either machine has touched. *(Was unresolved; answered by the research on 2026-08-07.)*

- **What makes two recorded library locations one library or two.** Label: **observed** (the same in all four versions, on both machines). **Dependencies 19** — settled by fifteen tests and by both ways of making a link, since no version's documentation states any of it. Two recordings naming the same file that differ only in how the path is written — relative against full, or a detour that leads back — are **one** library; Blender tidies the writing before it decides. Two recordings reaching the same file by two different names on disk — a shortcut of either kind, or the same folder mounted twice, that last on the Linux machine alone since the Mac cannot do it — are **a separate library each**; the tidying stops at the text and never asks the disk what the file is. Two different files sharing a file name are two libraries, the second given a numbered ending, which also settles that a library entry's name is the bare file name. **The decision is made when a file is read**: two entries forced to hold identical text stand until the file is saved and opened again, and then there is one. **Capitals follow the disk and the two machines differ** — on the rented Linux machine a wrongly capitalised library location is not a file and the link fails outright; on the Creator's Mac it succeeds quietly and leaves two libraries where one was meant. The comparison says plainly that this settles **those two machines and not the kind**. **From Blender 5.0 packing is the deliberate exception**, making a second entry holding the same recorded location as the first. **Does not cover** what happens when a library is relocated onto a file another library already records — the one thing the round set out to settle and could not, because the relocate command never moved the library it was given — nor anything with a window open, nor Windows.

- **What a later render uses after a file it has already read is replaced on disk.** Label: **observed** (the same in all four versions, on both machines). **Reading a file 11**. **A changed picture reaches the very next render with nothing done at all** — the opposite of what every version's documentation would lead a reader to expect — and so does a replaced frame of a picture sequence. **A picture behind a sequencer strip is the exception and it differs by version**: it reaches the next render by itself in Blender 4.5, and in 5.0, 5.1 and 5.2 nothing the round tried made it reach the render at all. A picture replaced while an animation is already running takes effect from some later frame onward, and **no frame ever came out part old and part new**; which frame it lands on moves with the timing and is not a version difference. A **linked `.blend`** behaves the other way and does not reach the next render until it is reloaded, and neither does a **movie clip**. A **packed** picture ignores its file on disk where nothing is done about it; what a reload then does to one came out two ways across three runs, and none was preferred. **One render setting, off by default, stops a changed picture being picked up at all.** A freshly started Blender reads every file as it stands. And a `.blend` replaced under a running Blender is not noticed, while reverting gives back what is on disk rather than what Blender was opened from. **Does not cover** three results where repeated runs disagreed and every run stands — a packed picture after a reload, a changed external shader script, and a cache archive; what happens if a file is deleted rather than changed; whether Blender notices its own file has been replaced, which needs a window; or Windows.

- **What a geometry node setup makes a file point at, and whether those paths take part in the file's own housekeeping.** Label: **documented and observed; differs by version**. **Node setups 1 and 2**. A setup can make its file point at a model file named on one of six import nodes, at a picture, at a font, at a folder of baked data and at another `.blend` — and from Blender 5.2 at a sound file, which the other three have no node for. **The largest difference is 4.5's**: an import node's own path takes no part in the file's path housekeeping there — the relative and absolute sweeps leave it alone, the missing-files report never names it, and it is in neither of Blender's lists of the file's outside paths — while from 5.0 it takes part in all of them. A `//` inside a **linked** node group's import node is measured from the **library** file and never from the file doing the linking, in every version. Packing does not carry an imported model into the `.blend` in any version. **Does not cover** dragging a file into the node editor, anything on Windows, or anything drawn in a window on Linux.

- **Whether an instruction can be given to a render without being written into the file.** Label: **observed**. **Writing 1** — where a render writes can be settled at the moment the render starts, and the file on disk is unchanged by it: the same size, the same modification time, and the same stored value when it is opened again, in all four versions on both machines. **Writing 9** for values a script handed in at launch reaching the render that follows, in all four versions on both machines, and **Reading a file 9** for a wholesale rewrite of a file's recorded locations showing in the running Blender and never reaching the file on disk unless something saves it, in all four versions **on the rented machine alone**.
