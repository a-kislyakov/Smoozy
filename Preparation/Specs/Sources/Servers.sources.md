# Sources — Servers

*Where the outside-world facts in the [Servers spec](../Servers.md) came from. The spec carries each fact's label in place; this file carries the citation behind it, and what that citation does not cover.*

- The **default SSH port** — the port an SSH connection uses unless told otherwise — is 22, documented in the OpenSSH manual `ssh_config(5)` under the `Port` option ("The default is 22."), man.openbsd.org, retrieved 2026-07-17. Label: **documented**.
- **Host-identity checking** — that SSH records a server's identity on first connection, checks it on every later one, and warns about a changed identity rather than silently accepting it — is documented in the OpenSSH manuals `ssh(1)` ("If a host's identification ever changes, ssh warns about this…") and `ssh_config(5)` (the `StrictHostKeyChecking` option), man.openbsd.org, retrieved 2026-07-17. That same `StrictHostKeyChecking` documentation records the default as **asking** the user before a new host identity is accepted, and `accept-new` as the setting that accepts new identities without asking while still refusing changed ones. Label: **documented**. This citation covers SSH's own behaviour only. Smoozy's host-identity policy is a decision, settled in the body of the spec.
- **Several servers on one machine** — that one rented machine commonly hands out several containers, each reachable on its own port — has no source and did not come from the Creator. Label: **an assumption**. The duplicate check does not rest on it: that rule holds because the flag only ever warns and never blocks, as the spec's *Adding a server* section sets out. It resolves with the same provider check as the jump-host question, which is already parked in [Open Threads](../../Groundwork/Open%20Threads.md).
- **A "latest stable" Blender release** — that Blender publishes a stable release distinct from its other kinds of build, and that it names no single release as the one to use for ordinary work. Label: **documented**, the same in all four versions — **Builds 1 and 4**, in the [comparison](../../Blender%20Research/Comparison/Builds.md), which is where the reading stops. **This answers the claim and narrows it.** Until 2026-08-06 it was an assumption, on the strength of which the setup option promised a "latest stable" Blender. Half of it holds: a stable release is a real published kind, so there is something for the option to install. The other half does not: no version of Blender puts one release forward as the ordinary choice, so "latest stable" is Smoozy's own pick and must never be written as Blender's recommendation. That it is the deliberate quick path is the Creator's decision and is not in question.

  **What is still open is whether Smoozy can find out which release that is.** Whether **blender.org itself** publishes anything a machine can read is **not established in any version** — **Builds 2**, in the same comparison, which also carries what has since been found by other routes. That fact belongs to the [Server Setup spec](../Server%20Setup.md), which carries the marker for it.
- **A form of the provider's connection line that cannot carry files** — the *Adding a server* paragraph on the pasted line. Label: **documented**, read 2026-10-07 from the four providers' own connection pages. **Runpod's** *Connect to a Pod with SSH* (`https://docs.runpod.io/pods/configuration/use-ssh`) says of its proxied line: *"This method does not support commands like SCP (Secure Copy Protocol) or SFTP (SSH File Transfer Protocol)."* Vast's page calls its proxy *"slower for data transfer"*, and Hyperstack and Sesterce show one direct line each. The full reading, with every quotation and what it does not cover, is at [Architecture's companion](../../Architecture/Sources/Servers.sources.md), entry 10.8. It covers those four providers on that date.
- **What a bare machine needs before a render will run on it** has no entry here on purpose. It is **Server Setup**'s fact and is cited in the [Server Setup sources](Server%20Setup.sources.md); this spec names only the outcome its setup option promises, and rests on nothing the answer might turn out to be.
- **Noticing that a connection has ended** — that Smoozy learns of a dropped connection by itself, rather than finding out the next time something needs the connection. Label: **unresolved**. No source was consulted and it did not come from the Creator; it is a claim about what the end of a connection over a network looks like to the side still holding it. **What breaks if it is wrong:** the server goes on reading **connected** with nothing behind it, so the promise that the list shows the true state fails; the **reconnecting** state is never entered and the repair never starts, so a repair that is meant to carry on for as long as the app is open never begins at all; the whole-app notification for a connection Smoozy could not restore cannot fire, since nothing noticed the drop; and every module written for the moment Smoozy knows it is offline — what a disconnected server's queue is shown as, what a transfer does when the connection goes, what a setup step cut off part-way says — is written for a moment Smoozy would not have. It is not a Blender question. Parked for Architecture in [Open Threads](../../Groundwork/Open%20Threads.md), with the other connection questions. One thing was offered when this was raised and is recorded as a **guess, not an answer**: that what happens may depend on how the connection ended, a whole-network outage on the user's own side perhaps not looking the same as a machine refusing or closing. Nothing has been checked either way. **ANSWERED, 2026-08-16, and the guess was right — recorded here 2026-08-23, the entry having sat unresolved for a week after the answer landed.** Six rented machines, three ways: a machine closing politely and a machine powered off from the provider's console are both reported to the side still holding the connection **in the same second**; the user's own line pulled is **not reported at all** unless that side is asking, and with the asking on it was noticed in **56 seconds**, with it off it went unnoticed for **21 minutes 45 seconds**. **So none of the breakages above stands, on the condition that Smoozy keeps asking.** Label: **settled at Architecture** (2026-08-23). Evidence of record: `Preparation/Architecture/Six machines — the container, the webhook and the ready action.md`; the register entry is Fact 57, which also carries what is still open — everything observed ran through one provider's proxy, and a genuine power cut cannot be produced on a rented machine.
- **Reading a machine's hardware over a connection** — that Smoozy can learn how many GPUs a machine has, which they are, how much memory each holds, and how much memory the machine itself has. Label: **settled at Architecture** (2026-08-23), by running it on rented machines rather than by reading. **Corrected 2026-08-23**: this entry read **unresolved** while the spec that links to it said settled, so the spec pointed at its own refutation. **Where the answer lives:** [Architecture — Servers](../../Architecture/Servers.md) §8.2, clauses H5 to H13, on the evidence of [The rented machine](../../Architecture/The%20rented%20machine.md) (Fact 46, a two-card box with no Blender, no screen and no display server) and [The multi-provider batch](../../Architecture/The%20multi-provider%20batch%20%E2%80%94%20the%20surface%20that%20did%20not%20vary,%20the%20Debian%20route%20that%20exists,%20and%20the%20cards%20a%20slice%20cannot%20see.md) (nine rentals across three sellers, 2026-08-22, including two-card slices of four-card hosts).

  **What is established.** The cards come back over the ordinary connection from the card vendor's own driver query, with no Blender on the machine: per card its unique identifier, its bus location, its make as a keyable value and its total memory, and the count read as the number of rows of that query. **The Blender route named below was considered and declined** — `Servers` H16 — because the promise covers a server with no Blender on it, because card memory was never seen except through Blender's window and never with more than one card, and because on a rented multi-card box Blender's own device list reports every card enabled on a build that will render on the processor. **The machine's own memory is the container's allocation where there is one**, read from the newer control-group paths or the older pair, never from the whole machine's figure on a slice.

  **What the spec's own sentence about gaps rests on.** Three absences are stated rather than guessed at: per-card memory has one route and is reported missing where that route is absent (H8); a machine whose cards are plainly there but whose driver tool is absent reads as **cards present and unreadable**, never as cardless, which on two of three providers is what they shipped (H11); and where no control-group route answers, the machine's own memory says it **could not be established** rather than reporting the host's (H9a).

  **What is still open is the one half the spec's `[PENDING]` names**: telling a machine with **no graphics card at all** from one whose cards could not be read. It is unposable on the seller this project rents from — every no-GPU offer returned is a storage machine, and two attempts to rent one were refused. Carried at `Servers` §16 item 2. ~~and the spec carries the marker.~~ *(2026-10-24, the build runner, after step 12's P1: the spec now writes this half as permanently unresolved and carries no marker.)*

  **The Blender readings this entry used to rest on are kept, because they are what the declined route was judged on.** A Blender already on a machine can be asked which cards it sees and can count them, with no window and on a machine with no display server — **The machine 6**, in the [comparison](../../Blender%20Research/Comparison/The%20machine.md), the same in all four versions. The one route by which the research ever saw a card's whole memory needs Blender's window and has never been seen with more than one card — **Reports 6**, in the [comparison](../../Blender%20Research/Comparison/Reports.md).

  **The related question the [Queue & History spec](../Queue%20&%20History.md) raises — whether a GPU's live memory use can be read the same way — is answered in part and no clause rests on it.** Used memory was read three times at ten-second intervals on two two-card slices with nothing running and held steady, with the compute-application list empty (`Servers` H7a). **What that cannot establish is whether a card can ever be shared under us**, because the cards the query shows are the ones we hold; it was not posed and that test could not pose it.

  That the user needs those facts to choose a machine is the Creator's decision (2026-07-27) and was never what was unresolved here.
