# Sources — Server Setup

*Where the outside-world facts in the [Server Setup spec](../Server%20Setup.md) came from. The spec carries each fact's label in place; this file carries the citation behind it, and what that citation does not cover.*

*Note: what Smoozy itself decides to do — in this module, everything about how the two ways in are shaped, what is promised and what is offered, what is warned about and what is not, and what happens when something stops part-way — is a decision rather than a fact, so none of it earns an entry here. Only the outside behaviour those decisions are built on does.*

*Blender facts are cited by the comparison and the question number in it — **The machine 2**, **Builds 6**, **Add-ons 11**. The comparison carries every version's answer, has been checked against the findings behind it, and is where the reading stops; the per-version findings are the paper trail for anyone checking it. No words of Blender's are copied into this project.*

## Facts about Blender

See the [comparison](../../Blender%20Research/Comparison/The%20machine.md), **The machine 1 and 2**. Not covered: no figure for memory, disk, processor or operating-system version is established for any version, and the two graphics floors Blender's own pages give do not agree — that part stays **unresolved**, under the same questions. ## Where the research and the Creator disagreed

**Stated:** on 2026-07-29 the Creator stated that a machine can hold several Blenders side by side and that **installing one never displaces another**.

**Found:** **Builds 5** and **Builds 8** carry it, documented in all four Blender versions and observed on two kinds of computer — a Blender is a self-contained folder, several sit on one machine at once, and putting one in beside another leaves its files alone. But it is not the whole of it. Blender keeps its settings in one folder named for the version counted to two numbers, so **two builds of the same version share one settings folder** — and with it the add-ons installed there. A build removed leaves that folder behind for the next one. Beyond the settings, Blender's own documentation carries two further ways one installation reaches another: registering one takes over which Blender opens `.blend` files for the whole machine, and on macOS the documented way to update is to overwrite what is there.

**Which won:** the research. The spec now says installing one does not displace another's *files*, and states the shared settings folder plainly. Nothing the Creator stated is wrong; it is narrower than it read. Recorded in the `Audits/Specs/Server Setup/Decisions record.md`.

**One other thing to name, which is not a clash.** The claim that an add-on arrives by two ways, mirroring the two ways a Blender does, was not the Creator's — it was raised by an agent from its own knowledge and this spec already marked it as possibly the wrong shape. **Add-ons 5** shows it is: there is one route, and Blender's own site is a single entry on a list of repositories. The section was rewritten rather than reworded, as the spec said it would be.

## Facts about rented machines, not about Blender

- **What a rented machine needs beyond a graphics driver before a render will run on it.** Label: **settled at Architecture** (2026-08-23). Fact 47 in the Architecture fact register carries it, asked first on four freshly rented machines on 2026-08-15/16 — the question is about what a provider leaves undone, so it had to be the first thing asked on each. **There is no single answer, and that spread is the finding**: the four machines needed nothing, two things, four things and seven. What is missing is a property of the image a provider ships rather than of rented machines. **All four agree on what the blocker is**, which is what the ready action is built on: the chain of shared system pieces Blender opens as it starts, needed even for a render with no window at all, so a machine that lacks them fails at launch rather than at render. **And Blender names only the first missing piece**, so mending them one at a time takes as many rounds as there are pieces — the whole list has to be read off the build in one go. **One trap the research names and the spec's wording turns on:** on one machine the driver package incidentally brought in six of the nine missing pieces, so an action that leans on the driver to supply them is right on that machine and wrong on the next; they are installed explicitly instead. **Not covered:** the list itself, which cannot be settled for all machines because it is per image; four further images on three providers are still owed; and one of the four was asked sixth rather than first, against the question's own precondition, so a strict reading would want that one asked again.

- **That a rented machine can be a locked container, with its drivers already in place and no way for Smoozy to change them.** Label: **an assumption**. It has no source in this project and did not come from the Creator; it is inherited from the [Servers spec](../Servers.md), which describes the same case for a ticked setup option. The spec's rule that Smoozy says what it could not do, without treating it as a fault, exists for it. It sits beside the neighbouring container assumption in the [Servers sources](Servers.sources.md), that one machine commonly hands out several containers, and should be confirmed with it. **ANSWERED, 2026-08-15/16, on a container rented to pose it — recorded here 2026-08-23.** Yes, and the *cannot change* half held under every route tried. Label moves from **an assumption** to **observed**. This was one of the two facts that gated the whole Architecture spine. Register entry: `Preparation/Architecture/Facts.md` Fact 48; evidence of record `Preparation/Architecture/Six machines — the container, the webhook and the ready action.md`. **The neighbouring assumption it was to be confirmed with stays where it is** — that one wants a provider's page, not a rental, and neither closes the other.

- **Whether a rented machine can be searched for every Blender on it.** Label: **an assumption**. The Blender half is settled and sits above: a machine cannot be asked which Blenders it holds, and only a search of its files found every one — **Builds 7**, observed on a Mac and on a rented Linux machine. What has no source in this project, and did not come from the Creator, is that Smoozy can run that search on a rented machine over the connection it holds. The spec says plainly that delivering it is Architecture's; nothing anywhere says it can be delivered.

  **What falls over if it cannot.** The list of Blenders a machine offers, which this module builds by looking rather than by remembering and which is the whole of what *What Server Setup shows* promises. The version match in the [Render Settings spec](../Render%20Settings.md), which sets the version a `.blend` was saved with against the versions installed — with no list of what is installed there is nothing to match against, no automatic pick, and no list for the user to pick from either. And the mismatch warning that rests on that pick, which is what a user submitting an old job again on a fresh machine meets in place of the version they rendered with last time. A machine that cannot be searched is a machine no job can be sent from, since a job cannot be submitted without a Blender to render it. Parked for Architecture in [Open Threads](../../Groundwork/Open%20Threads.md), with the other rented-machine assumptions.

- **Whether a machine can be read for the setup state it is in.** Label: **settled at Architecture** (2026-08-23). What is *installed* can be read — see the Blender entries above — and how far a half-finished setup got is a separate question, which could not be asked until the ready action existed. Fact 49 in the Architecture fact register carries the run, made on a rented machine on 2026-08-18 against a setup deliberately cut off part-way. **The answer is yes, and it comes from what the setup wrote down as it went rather than from inspecting the machine.** Cut at a boundary it had recorded, the machine named the third of five boundaries by name, with the moment it was reached; cut hard, part-way through a step, it named the second — the last boundary it actually got past, not the one it died inside — and the record survived a reboot with nothing running behind it. **Not covered:** a machine that recorded nothing, where the state cannot be worked out at all, and where running the ready action again stays the user's only way to be sure. **And one reading is named wrong**: between a hard cut and the machine's next start, a setup that is dead reads as still running. That is about whether something is alive rather than about how far it got, so it does not touch what the spec promises here. *(Was **unresolved**, and could not be posed until the ready action existed, exactly as this entry said.)*

- **Whether making a machine ready can be run again on a half-finished machine without harm.** Label: **unresolved**. Installing a Blender again is settled — see **Builds 9** above — and this half is not. The spec promises it plainly, and that promise is the only way out of two situations the spec otherwise has no answer for: a setup cut off part-way that left the machine in a state nobody can describe, and a machine that cannot be read for what has been done to it. Parked in [Open Threads](../../Groundwork/Open%20Threads.md). **ANSWERED, 2026-08-18 — NO, and recorded here 2026-08-23.** Run last on a box being given up, against a machine an earlier run had left half-finished with two of five steps genuinely done. Label moves from **unresolved** to **observed**. The card itself was unharmed, so **the harm is the state rather than the hardware** — and clearing under the original identity worked, after which a fresh run started cleanly with a new identity. **The spec's promise is kept anyway and by construction**: Architecture clears the half-finished state before it runs the action again, rather than running it again over the top. Register entry: Fact 50; evidence of record `Preparation/Architecture/The last two boxes — the hook that cannot be read back, the full disk, and the unit that kills a render.md` §16.

- **That Smoozy can restart a rented machine over the connection it holds.** Label: **observed**, one rented Linux machine, 2026-08-13. Fact 51 in the Architecture fact register records the run: `systemctl reboot` over the held connection; the connection reported `closed by remote host`; the same address and port answered again in about ten seconds with a new boot id and the disk intact. Not covered: another provider, another kind of rental, or the separate unresolved question of whether the concrete driver work in the ready action requires a restart.

- **That a restart stops everything else in flight on the machine — a transfer, a dependency check, a render — and that a render that was running dies with it.** Label: **an assumption**, both halves. Neither has a source in this project and neither came from the Creator. What rests on them: the busy-machine warning, the [Queue & History spec](../Queue%20&%20History.md)'s re-run of the interrupted job, and the ordering promise that the rest of the setup finishes before that re-run. If work stops in some way other than plainly dying — a transfer left half-written, a render neither finished nor gone — then what each module says a lost connection does to it is not the whole story. Parked in [Open Threads](../../Groundwork/Open%20Threads.md). **ANSWERED for two of the three, and recorded here 2026-08-23.** **The transfer half, 2026-08-13:** an 8 GB write in flight died and did not come back, leaving **4.7 GB under the file's final name with nothing marking it incomplete** and an empty error stream — which is exactly the *some way other than plainly dying* this entry named, and it is what the architecture's publication rules are written against. **The render half, 2026-08-15/16:** two real restarts with a Cycles render in flight, taken over the connection as root rather than from the provider's console, killed it. Label moves from **an assumption** to **observed** for both. **The dependency check is the one part nobody has posed**, and it stays parked. Register entry: Fact 55; evidence of record `Preparation/Architecture/Six machines — the container, the webhook and the ready action.md`.

- **Installing drivers can require the machine to be restarted.** Label: **an assumption**. It has no source in this project and did not come from the Creator. The spec's restart rule exists for it. If no setup step ever needs a restart, the rule simply never fires and nothing is broken; if restarts are needed more widely, the rule already covers that, being written for a setup step needing one rather than for drivers specifically. **ANSWERED, 2026-08-15/16, on two rented machines — recorded here 2026-08-23.** Yes on both, **for two different reasons, and they disagree about the signal, which is the useful part.** On one the provider had left the card bound to another driver: the install finished at exit 0 in 85 seconds, **printed no reboot demand at all**, and left the card's own check failing. On the other the install pulled a whole new kernel and printed its own demand. Label moves from **an assumption** to **observed**. **What Architecture took from it:** restart where the card's own check fails, never on the installer's word — the machine that needed it was the machine that said nothing. Register entry: Fact 80; evidence of record `Preparation/Architecture/Six machines — the container, the webhook and the ready action.md`.

- **Whether a machine permits the elevated access making it ready needs.** Label: **settled at Architecture** (2026-08-23). Owned and cited by the [File Browser sources](File%20Browser.sources.md), which raised it for a read refused for lack of permission. It appears here because a machine that refuses it may not be set up at all — this module's weight of the question, which is the heavier one. Fact 27 in the Architecture fact register carries the answer, read across rented machines on 2026-08-15/16 and closed at this module's own weight on 2026-08-18. **It differs by the kind of machine rented, and that is the useful part.** On an ordinary rented machine the access exists and asks for no password, but it belongs to the account the machine is handed over with rather than to the login Smoozy runs as — and the two halves part cleanly: putting Smoozy's own pieces on the machine needed none of it and succeeded under the ordinary login, while everything about making the machine ready was refused to that login outright, including the driver repair the machine actually arrived needing. On a container an ordinary login has no route to it at all, and the fullest access inside a container holds thirteen of the machine's forty-one permissions — not the ones a driver needs — so a container arrangement calls for a step the arrangement itself cannot perform. **Installing a Blender leans on it far less than it did**: a Blender is a self-contained folder that can be put anywhere and an add-on goes inside that Blender's own settings — **Builds 5** — so nothing the whole machine shares is touched. What still leans on it is making the machine ready. **Not covered:** the permissions read inside the container are the ordinary ones for that kind of rental, and a provider handing out a container with more would answer differently; nothing here can rule that out.

  **The other half of this — how the access is obtained — is no longer here.** What the user is asked for, and what Smoozy keeps, was settled on 2026-08-10 under *Security* in the [Whole app spec](../Whole%20app.md): Smoozy asks for a password at the moment a step needs one and never before, and the user chooses whether it is kept for that one action, for as long as the connection lasts, or until they clear it. Label: **Creator-stated** (2026-08-10). That is a decision rather than an outside fact, so it lives in the document and earns no citation. The machine's own half above is the part that was unresolved, and it is now answered.

## The add-on questions — where they came from

**A warning worth keeping, even though the questions have been answered.** Most of the add-on questions this spec once carried were raised by an agent from its own knowledge, at the Creator's explicit request and with Rule 2's labelling deliberately set aside for that one conversation (2026-07-29). That made them the exact hypothesis a blind researcher must not be handed, and each had to be reworded blind before anyone was asked. They became **Add-ons 1 to 8, 10 and 11** in the [comparison](../../Blender%20Research/Comparison/Add-ons.md) — none of them became Add-ons 9, which was retired there on 2026-07-30 and whose number is not reused; the comparison keeps the retirement entry in place so the gap cannot be read as an omission. The two still open above carry the same hazard and the same requirement.

One claim in the spec's body is not from that conversation and is labelled differently: **that some `.blend` files need an add-on to render and most do not**. Label: **Creator-stated** (2026-07-29) — the Creator drew the line themselves between add-ons that are conveniences and add-ons that are not. Nothing in the research contradicts it; what the research does establish is that Blender gives no way to tell the two apart, which is **Add-ons 1 and 2** above.

## Added when the second and third rounds of Blender Research were carried in (2026-08-10)

- **Whether a job can be made to report which parts of the computer it actually used.** Label: **observed; how you ask differs by version**. **What actually ran 1** — see the [comparison](../../Blender%20Research/Comparison/What%20actually%20ran.md). **Yes, in every version, and every result behind it is Cycles' own report** — whether an EEVEE or Workbench job names anything is not established. A render prints a line naming the model of the part that did the work, and for a card the route taken to it and its place on the machine — and none of the four prints it unless asked. **Blender 4.5 reaches it only through a debugging switch and puts it on the stream reserved for complaints; 5.0, 5.1 and 5.2 answer to an ordinary logging switch and put it on the ordinary output.** A render with no switches at all names no device in any version.

  **Three limits, and each bears on what this module can promise.** **Corrected 2026-09-01, after the research was repaired: *a stopped render never reaches it* was reasoned from the timings of a run that finished, and no stopped render was ever run for it.** One has been now. **Two of the four versions print the whole closing report after a stop, one prints a cancelled line and no report, and one prints nothing at any level** — and in the runs that printed, the frame's own sampling had finished inside the wait, so **what a frame genuinely cut short prints is recorded nowhere.** **And the version that prints it publishes its own list of faults calling that report fake, with wrong numbers**, borne out by a run whose report claimed 600 samples for a frame the line above it called 599. **So a line found on a job that did not finish is evidence of nothing, and Smoozy reads it only from a job that finished.** **That matters most here, because this is the module that turns the line into an offer to redo a machine's setup, which can restart it.**

   The line is a **closing report**, printed after the last sample and before the frame is written, so a render stopped part-way never reaches it and nothing says what a running job is using — **that timing established on the Linux machine alone**, while the route to the line was run on both. The settings read back afterwards **do not answer it and can be shown to say the wrong thing outright** — with the preference naming a card, the scene naming a card and the work sent to the processor, both settings still named the card. And the render-time layer that exists from Blender 5.0 follows the **scene's setting** and pays no attention to what actually ran, so a file carrying it says what was asked for and nothing about what happened. **Not covered:** whether a card running out of memory announces the move into the machine's own memory, which was attempted three ways and defeated because the machine's memory gave out first; anything on Windows, on a card of another make, or on a machine with two cards. *(Was unresolved; answered by the research on 2026-08-07.)*

- **Whether installing an add-on disturbs a render already running on the same computer.** Label: **observed** (the same in all four versions, on both machines). **Add-ons 12**. **It does not.** Both readings of the question were tested: installs fired at a running render from a second Blender, and an install made from inside the very Blender that was rendering. Every run wrote all its frames and ended at success, and **every frame was compared picture against picture rather than file against file — not one value differed**, the findings recording sixty-four such comparisons for the rebuilt interface-lock run alone. Blender's own setting for locking the interface during a render made no difference — **on the Linux machine alone, with no window**, established in a form that could have come out either way after a first attempt that could not; the windowed form remains not established. **The reason is worth having**: Blender keeps a lock on its own add-on store, and a Blender that is rendering does not hold it. **Two neighbouring facts.** A Blender that is already running does not pick a newly installed add-on up by itself, and asking it to look again does not change that — though it can then be switched on without a restart. And with one Blender holding that lock, an install fired from another **refuses in under a second at a failing status**, naming the session that holds it, rather than waiting. **Not covered:** whether an install is harmless **in general** rather than at the rate and in the manner these were fired, which the research states plainly; the windowed form of the interface-lock test; and Windows. The busy-machine rule leans on this result, so the first of those is the one to watch. *(Was unresolved; answered by the research on 2026-08-07.)*

- **What more can be learned about whether an installed add-on will work.** Label: **observed** (the same in all four versions, on both machines). **Add-ons 13**. **Switching an add-on on can give a machine-readable answer, on one of the two routes** — there the act succeeds for a working add-on and raises for a broken one, naming the fault, tried against three different kinds of breakage. The other route hands back nothing rather than raising, and switching an add-on on at launch prints its complaint and still ends at success. So which route is used decides whether anything is learned. **Nothing anywhere, documented or tested, says beforehand whether the part a render needs will work**; every check Blender offers is a check that something has already gone wrong. Three limits: the list of switched-on add-ons **records what was asked for rather than what loaded**, so one that broke on disk stays in the list after a restart with only a start-up line to say otherwise; asking Blender to look again over its add-ons **reports nothing about damage**, every fault surfacing at start-up instead; and the listing of what is installed says nothing about health and nothing about on or off. Seventeen ways of asking were tried with no window open and sixteen answered in every version, so this checking is reachable from outside the interface, which is what Smoozy needs. **Not covered:** what Blender's own add-on error status actually holds, which no version documents at all; and Windows. *(Was unresolved; answered by the research on 2026-08-07.)*

- **What an add-on install's exit status can be trusted for.** Label: **observed** (the same in all four versions, on both machines). **Add-ons 14**. **One kind of refusal still ends at a successful status, and another does not.** An add-on declaring it needs a Blender version it is not being installed into is refused by name, nothing is installed, nothing reaches the listing and nothing can be switched on — and the command reports success. A compiled part built for the wrong Python is refused at a **failing** status. So the ending cannot be read either way round. So an install has to be judged by what the machine holds afterwards. **The same declaration is ignored entirely for an older-style add-on**, which is listed, switched on and run whatever Blender it declares it needs — and every version's manual says the opposite, that an older Blender will not display it. That is a documented promise the running program does not keep, in all four versions on both machines.

- **What decides whether an add-on set up for one Blender works in another on the same computer.** Label: **documented and observed; the Python version differs by version**. **Add-ons 14**. **Exactly four things**, all now observed rather than reasoned: which folders that Blender reads; the Blender version range the add-on declares, enforced for a modern add-on and ignored for an older-style one; the Python the Blender carries, for anything compiled into it; and the kind of computer the add-on was built for. **Nothing in Blender refuses another version's add-on** — five separate ways of sharing all worked, and an installed folder copied by hand from one version's folder into another's worked in both directions. What keeps versions apart is the folder's version-numbered name and nothing else, and that name carries two numbers rather than three, so patch releases share. The Python is **3.11 for Blender 4.5 and 5.0 and 3.13 for 5.1 and 5.2**, so a compiled part built for one pair will not serve the other, and that is refused at install rather than left to fail later. **Not covered by this question:** two different builds of one version sharing a folder, which **Builds 5** above settles instead — on one machine, in one run, for one pair of builds of one version from two sources; two Blenders built for different operating systems on one computer; and Windows, which leaves the Windows paths untested. The one route Blender documents for carrying an older version's add-ons into a newer one behaves differently on the two machines and not between the versions, so nothing about it is a version fact.
