# Servers

*What the Servers module does, in plain terms: how the user adds the servers Smoozy renders on, keeps track of them, connects to them, edits them, and removes them. Not one word about how it's built.*

*2026-10-27 — Removed the withdrawn paid-access text and its obsolete references under the Creator’s free-and-open-source decision of 2026-10-04 (wave 5); retained protections and evidence keep their force. No auditor has seen this removal.*

## Where Servers fits

Servers owns a server's **connection identity** — the details Smoozy needs to reach a machine over [SSH](../Groundwork/Glossary.md) — and the list of the machines the user has added. The rest of the app depends on it: every module that acts on a server — browsing its files, installing Blender, rendering — needs a connection from Servers first.

**Connections.** The [module map](Whole%20app.md) owns how Servers is wired to the rest of the app. That covers what Servers takes from **Keys**, including who holds the passphrase when a server's key is protected by one. It covers what it hands to **Server Setup**. It covers what it asks of **Rendering** and **Queue & History** when a server is removed. And it covers the rule that Smoozy knows only servers and keys, never providers. What Servers asks for on a removal is set out in [Removing a server](#removing-a-server).

## Adding a server

The user adds a server through the **Add Server dialog**. They give:

- **The connection details** — the server's host, its port, the username to log in as, and which key to connect with. The port field starts at 22, the standard SSH port. *(documented — see [Sources](Sources/Servers.sources.md))* All four must be filled in before the server can be saved, on an add and on an edit alike. The port is required like the rest: clearing it puts 22 back rather than leaving it empty. Design will decide how a blank required field looks and what message it shows.

  The key is chosen from the keys Smoozy already knows about. If the user needs a new key, or wants to point Smoozy at one kept elsewhere, they can open Keys right from the dialog, and Keys hands the key back **selected** for this server. Any key the Keys module currently marks **unusable** — what makes a key unusable is Keys' to define (see the [Keys spec](Keys.md)) — **is not offered**, so a server can never be created already needing a new key.

  The dialog checks these details against the *other* servers already saved, and flags a **possible duplicate**: an existing server with the same **host and port**. Host and port together name what Smoozy is reaching; the username and the key only settle who logs in once it is reached, so neither is compared. A different port therefore means a different server. The case that makes this matter is one rented machine handing out several containers, each on its own port. *(an assumption — see [Sources](Sources/Servers.sources.md))*

  A match on host and port is a strong hint that the machine is already in the list, not proof of it. A saved server's address can go out of date, because rented addresses rotate — so a match says the two entries point at the same address **today**, not that they are the same machine. The flag is worded as a likelihood and never as a certainty.

  The flag **warns only**. It never blocks the add, and the user can save the server anyway. That is what makes the loose comparison the right one: because nothing is ever refused, a flag raised wrongly only asks the user to read it and carry on, while one missed leaves two entries that look identical in the list they pick from. The second costs more, so Smoozy flags more rather than less. How the flag is shown, and whether it names the matching host and port, is Design's. The same check runs on edits (see [Editing a server](#editing-a-server)).

  **Host, port, username and key are enough.** Settled at Architecture on 2026-08-19: three providers' own documentation was read, and none of them puts a gateway in front of a rented machine that needs its own details — see `Preparation/Architecture/Servers.md` §13.1 C1, Fact 61, Row 24. Where a provider offers a route through another address, that route is an address and a port and not a second login. What was read is those three providers on that one date; a machine at a company or a university reached through a gateway was not read and sits outside it.

  **The provider's own connection line can be pasted to fill the details in. Added 2026-10-04.** A provider shows a ready-typed line for reaching a machine from a terminal, such as `ssh -p 1239 ubuntu@203.0.113.7`. Pasted into the dialog, the line fills the host, the port and the username, and the user sees them before anything is saved — the server is saved only when they add it, as on any add. **Smoozy reads the line and never runs it.** Label: **Creator-stated** (2026-09-21).

  - **A line with no port means the standard one**, so the port reads 22. That is what the line itself says, not a guess.
  - **A line missing a host or a username fills what it has and names what it lacks**, in one line. Nothing is guessed.
  - **What else the line carries is not used** — a key file of the user's own, forwarded ports, other options. The key is chosen in the dialog as always: a key file named in the line is a file on the user's computer that Smoozy has not been given.
  - **Smoozy does not judge which form of the line it was given.** A provider may offer more than one form, one of them through a relay of its own that may not carry files. **What Smoozy says about such a form waits on one reading of the four providers' own connection pages, dated and quoted** (see [Sources](Sources/Servers.sources.md) once it is filed). Until that reading is filed nothing is said about forms, and a line of any form fills the fields like any other. Where a provider is found to document a form that cannot carry files, a line of that form fills nothing and says so in one line, naming that provider's direct form. *Words changed 2026-11-01 (was *says so in one sentence*; the line is two short sentences, and names the direct form by its console label, not the provider): Creator-stated, the second words sweep. No auditor has seen it.* Label: **ruled 2026-10-04 under the Creator's standing delegation**; whether any provider's form cannot carry files is **unresolved** until that reading. **The reading was filed on 2026-10-07: of the four, Runpod documents one such form, its proxied line, and says it does not support file copying.** A line of that form fills nothing and the user is pointed to Runpod's direct line. The other three providers document no such form. Label: **documented** (see [Sources](Sources/Servers.sources.md)). *Added 2026-10-07 by the builder of step 10c's second notes, piece 15. No auditor has seen it.*
- **An optional name.** A free label shown in the server list — for example "RunPod 4090". It is only a label to help the user tell their servers apart; it carries no other meaning.

  If the user leaves it blank, the server shows as `username@host`. The port is shown as well wherever that is the only thing telling two unnamed entries apart, as it is when one machine runs several containers on different ports *(an assumption — see [Sources](Sources/Servers.sources.md))*.

  A name does not have to be unique. But the list is where the user picks between their servers, so two rows reading identically there is a problem whatever caused it. The rule is therefore stated by outcome: **if saving would leave two servers reading identically in the list, Smoozy points that out** — a warning only, which the user can accept and save anyway. That covers a typed name matching another server's name, a typed name matching the label another server displays for itself, a name being cleared so that the generated label collides, and two unnamed servers that would show the same label.
- **A colour, which arrives already chosen.** Every server carries one, and it means one thing only: *which server*. Smoozy picks the first of its colours that no other server is using, and the user can change it to any of them, including one already in use. Choosing for them is not deciding for them — it is offering the answer they would have given, at a moment they care least about it. Label: **Creator-stated** (2026-08-13). How many colours there are, what they are, and how the choice is shown are Design's.
- **Two optional setup options.** Smoozy can **get the machine itself ready to render** — whatever a bare machine needs before a render will run on it — and can **install the latest stable Blender**. Blender publishes a stable release as one of its kinds of build, so there is such a thing to install; it names no single release as the one to use for ordinary work, so picking the latest stable one is Smoozy's own choice rather than Blender's advice. *(documented — see [Sources](Sources/Servers.sources.md))* Whether a given machine will take either option is **Server Setup**'s to settle, and the [Server Setup spec](Server%20Setup.md) states that constraint. These name the *outcome* each option delivers, not the steps behind it. What getting a machine ready actually takes is deliberately not stated here, so that the option promises an outcome rather than a list of steps. It belongs to **Server Setup**, which carries both what the research settled and what it left open. The exact wording is Design's. Both options can also be taken later, with more choice over Blender version, from Server Setup itself.

**When adding connects.** If either setup option is ticked, adding the server **connects to the machine right away** to carry that setup out. If neither is ticked, adding simply **saves the details** — Smoozy does not reach out to the server, and it sits in the list until the user connects to it. The trade-off of a plain add is that a wrong host, port, or username isn't caught until the first time the user connects; that is accepted, in exchange for making a bare add instant. A key is different: one that cannot be used at all is caught in the dialog, since such keys are never offered there — so the only key problem that waits until the first connection is a usable key the machine refuses to accept.

**The server is always saved.** Whether the connection fails, a setup step fails, or the machine cannot take a ticked option at all, the add stands. A failed setup step is Server Setup's concern to report and retry, and does not undo the add.

**What Smoozy remembers, and what it does not.** Smoozy remembers a ticked setup option in one case only: the **connection** failed, so the setup never started. Once Smoozy has reached the machine, nothing about the setup is remembered — what happened there is reported at the time, not carried forward. A setup step that failed on a machine Smoozy reached is therefore never remembered.

A connection that drops while a setup is under way falls on the same side. Smoozy had reached the machine, so nothing is remembered and nothing resumes on its own: Smoozy says what it managed, and the user can run the rest from Server Setup itself.

That covers a connection Smoozy **lost**, not one it took down on purpose. A setup step can require the machine to be restarted, which Smoozy does itself and carries on through — it knows the machine is coming back, so the setup is not abandoned and nothing has to be picked up by hand. That is Server Setup's, and the [Server Setup spec](Server%20Setup.md) states it in full.

The same rule covers a half-finished add. If Smoozy reaches the machine and one ticked option succeeds while the other fails, neither is remembered, and a later connect repeats neither. Smoozy says what did not work, and the user can run it again from Server Setup itself.

**When a setup option cannot run.** Two things can stop a ticked setup option before it starts, and the add survives both.

- **The connection itself fails** — a wrong host or username, so the setup can't even start. Smoozy **remembers which setup options were ticked**. The server's connect action carries that remembered setup, so once the user has fixed the details and connects, the setup they originally asked for runs then. Smoozy does not reach out on its own to finish it: the user triggers it, by connecting. The action therefore says it will do both — "Connect and Set Up", or whatever Design settles on. The user can also **drop the remembered setup** without carrying it out, if they change their mind; how that is offered is Design's.
- **The connection works but the machine cannot take a ticked option** — nothing to ready because there is no GPU, or a locked container whose GPU is already prepared, so that option has nothing to do. Smoozy says plainly what it could not do — not as something gone wrong, since the option simply had nothing to act on, which the [Server Setup spec](Server%20Setup.md) states in full — and nothing is remembered, because Smoozy reached the machine. Where one option applies and the other does not, Smoozy carries out the one it can and says what it skipped. This is the whole-app rule at work: do what can be done, and say what can't (see [Whole app](Whole%20app.md)).

How these failures reach the user is settled by the whole-app concern *how a failure reaches the user* (see [Whole app](Whole%20app.md)); only the words themselves are Design's.

## The server list

Every server the user has added shows in the server list, by its name — or by its username and host if it has none (see [Adding a server](#adding-a-server)). A server stays in the list until the user removes it, including across closing and reopening the app. For each one the user can see whether Smoozy is currently **connected** to it, and act on it: connect or disconnect it, edit its details, or remove it. A connected server also offers a way into **Server Setup**, which is where the machine's software is dealt with (see the [Server Setup spec](Server%20Setup.md)) — it needs a connection, so it is not offered on a server that has none. A server whose key is gone or unusable shows as **needing a new key**, until the user gives it a working key, mends the key itself in Keys, or removes the server (see [When a server's key is gone or unusable](#when-a-servers-key-is-gone-or-unusable)). For such a server the **connect** action is unavailable until the key works again: connecting would fail, so the action is not offered. How all of this is laid out and worded is settled during Design.

**The set of per-server actions is settled: connect or disconnect, edit, and remove, and nothing else.** Ruled 2026-09-02. A reboot the user asks for by hand is **not** offered. The only restart Smoozy ever performs is the one a setup step itself needs, which is the [Server Setup spec](Server%20Setup.md)'s stated exception to the rule that Smoozy never acts on a machine's power, and that exception reaches exactly that far and no further. An action the user could reach at any time would widen that boundary for something no spec has produced a case for. If a later module produces one, it is that module's to raise.

**What the list tells the user about the machine itself.** The user picks which machine a job runs on, and no job ever moves between machines once it is submitted (see the [Queue & History spec](Queue%20&%20History.md)), so that choice is made here and cannot be undone later. Two things beyond the name and the connection state are what the choice turns on:

- **Whether the machine has work.** What it is rendering, and whether anything is waiting behind it. A machine with neither is **idle**, which the [Queue & History spec](Queue%20&%20History.md) defines.
- **What the machine has to render with.** Its GPUs — how many, which they are, and how much memory each one has — how much memory the machine itself has, and how much room is left on its disk. Label: **Creator-stated** (2026-07-27, the disk added 2026-08-13). Reading a machine's free space is the [File Browser spec](File%20Browser.md)'s to promise, and this reaches no further than that reading does; it is here because a machine with no room left is a machine a job should not be sent to, and that is a choice made in this list.

A GPU's memory is the ceiling that a running job's live memory reading is measured against. The reading belongs to [Queue & History](Queue%20&%20History.md); the capacity belongs here, because it is a fact about the machine rather than about any one render.

**The hardware is remembered, the work is not.** A machine's GPUs and memory do not change while nobody is looking, so Smoozy keeps what it read on the last connection and shows it for a server that is not connected, saying it is what was last seen. **Free disk is remembered on the same terms and is the one reading that can be wrong while nobody is looking** — a job left running writes files, so a remembered figure is only ever what was true at the last connection. It is kept anyway, because saying how much room there was an hour ago is worth more than saying nothing, and it is never shown as current: the same last-seen mark that covers the rest of the row covers it. Label: **Creator-stated** (2026-08-13). What the machine is *doing* cannot be kept that way — it changes the moment the connection ends — so it follows the rule [Queue & History](Queue%20&%20History.md) already sets: shown while connected, held as last-known only until the app closes, and absent on a fresh launch. A server that has never been connected has no hardware to show at all, and says so rather than looking empty.

**Remembered hardware is dropped when the connection details change.** Editing a server's host or port points the entry at a different machine (see [Editing a server](#editing-a-server)), and hardware read from the old one is then simply the wrong answer. So it is forgotten at that moment and read again on the next connection.

**Blender versions are not shown here.** The machine is the user's own, and they can install or remove a Blender on it without Smoozy ever knowing, so anything the list remembered would be a guess dressed up as a fact. What is actually installed belongs to **Server Setup**, which reaches the machine to find out. Label: **Creator-stated** (2026-07-27).

**A machine can be read this way.** Smoozy takes the reading over the connection it already holds, from a machine with nothing installed on it — which is what lets the list show what it found for a server the user has only just added. Where the machine answers, the reading comes back whole: its cards, what each one is, and its memory. **Where a part of it cannot be got, that part is shown as missing rather than guessed at, and the rest still counts as a reading rather than as a failure.** Three such gaps are known and are settled that way: a machine whose cards are plainly there but whose card maker's own tool is not installed reads as **cards present and unreadable** rather than as having none — which on rented machines is the ordinary case rather than a rarity, and on some of them there is no way to look for the cards at all; a card list can come back with each card named and no memory figure beside it; and a machine rented as a slice of a bigger one, where nothing on the machine says how big the slice is, says its own memory could not be established rather than reporting the whole host's. Label: **settled at Architecture** (2026-08-23). **One part of it is permanently unresolved**, settled so on 2026-10-24, and it is the part that matters when a machine has nothing to render with: telling a machine that has no graphics card at all from one whose cards could not be read. It is an outside fact, and Architecture closed with it recorded unresolved rather than answered. Settling it needs a rented machine with no graphics card, and the Creator ruled on 2026-08-31 that there will be no further rental, so it will not now be answered. What can be said is that two attempts to rent such a machine were refused, and that this project's own search of the seller it rents from could not ask for one — **not** that the seller offers none, which `Preparation/Architecture/Facts.md` struck on 2026-08-22 as a claim drawn from those two refusals. **What holds:** Smoozy never decides a machine has no card because the card maker's tool is missing, so a machine with good cards is never written off; and on a machine rented as a slice it never says *no card* at all, only that the cards could not be established — `Preparation/Architecture/Servers.md` H11, H12 and §16 item 2. **What breaks:** a slice with no card at all reads the same as one whose cards could not be established, so the list cannot say plainly that the machine has nothing to render with. ## Connecting

To do anything on a server — browse its files, set it up, render on it — the user **connects to it first**. Connecting is an explicit action the user takes, at any time, and disconnecting is too. The user is the one who starts a connection and the one who ends it.

**What this leaves to Architecture.** The user's connect action starts a **connected period** that runs until they disconnect, or until the app closes. From one end of that period to the other, holding the connection up is Smoozy's job and not the user's: nothing in between may let it lapse unremarked, and a server with no live connection does not read as connected here. Smoozy may replace the connection underneath the period in two cases, and only these two: after an unintended drop (see below), and after a restart **Server Setup** caused. **The period stands through both** — including a drop Smoozy has not managed to repair yet, so a server can sit inside a connected period without reading as connected. How the connection is held open, and what keeps it alive, is Architecture's to work out. *(This used to end "while reading as reconnecting or disconnected". The **disconnected** half belonged to the back-and-forth word retired below, and what a server reads as while Smoozy waits for one it restarted is Design's rather than settled here, so the sentence now names no state at all and says only what it is there to say. Label: **Creator-stated** (2026-08-22).)*

Smoozy opens a connection only where this spec says so, and never as an action of its own. In three cases it opens one as part of something else the user asked for:

- **Adding a server with a setup option ticked.** Smoozy connects to carry the setup out (see [Adding a server](#adding-a-server)). When the setup ends the server **stays connected**, until the user disconnects it themselves.
- **Saving an edit to a connected server's connection details.** Smoozy puts back the connection the user had already opened (see [Editing a server](#editing-a-server)).
- **A restart Server Setup needed.** A setup step can require the machine to be restarted, which Smoozy does itself (see the [Server Setup spec](Server%20Setup.md)). It takes the connection down knowingly, waits for the machine, and puts it back. This is not a drop and is not treated as one: the ordinary repair below does not run, and the whole-app notification for a connection Smoozy could not restore does not fire on it. Only if the machine never comes back does it become an ordinary failure, reported as one. What the server reads as while Smoozy waits is Design's, and how long it waits is parked with the same question for the repair below.

It also repairs a connection the user opened, when that connection drops on its own (see below). Nowhere else does Smoozy reach out to a machine — in particular, removing a disconnected server never does (see [Removing a server](#removing-a-server)).

Each server's connection is its own: connecting or disconnecting one touches no other, and several servers can be connected at once. Each time the app is opened, every server starts disconnected — reopening the app connects to nothing on its own; the user connects when they're ready.

**What "connected" means.** A server is **connected** when there is a live connection to it. The user opens it by connecting and ends it by disconnecting, and in between the connection simply stays up, so the user has nothing to do to keep it. What the list shows is the **true state**, not the user's last instruction: if the connection is down, the server does not read as connected.

**When a connection drops on its own.** A connection can end without the user asking — the internet goes, the rented machine is powered off, or the machine simply stops responding. Smoozy does not treat that as the user disconnecting.

Restoring starts the moment the connection ends, with the user doing nothing, so a server's state can change while the user is looking elsewhere — which is what the list showing the true state requires. That is Smoozy's own decision. What it rests on is not: Smoozy has to learn of the drop by itself, rather than finding out the next time something needs the connection, and whether the end of a connection is something the side still holding it learns of that way is a fact about the world outside Smoozy. **Smoozy does learn of it by itself, and this was tried three ways.** When the machine goes away — powered off, or closing politely — Smoozy is told in the same second. When it is the user's own line that fails, nothing arrives on its own and Smoozy has to be asking: with the asking turned on it noticed in under a minute, and with it off it sat for over twenty minutes believing a dead connection was a slow one. So the asking is always on. Label: **settled at Architecture** (2026-08-23) — see [Sources](Sources/Servers.sources.md). *(This carried the label **unresolved** until 2026-08-23, more than a week after the question was answered.)*

Smoozy tries to restore the connection itself: it tries again after a short pause, possibly more than once, and where a run of attempts fails it says so rather than going quiet — while the server goes on reading **reconnecting**, because Smoozy is still repairing it (see below). Restoring a connection the user opened is not Smoozy connecting on its own behalf — it is repairing the connection the user already asked for, which is why it isn't an exception to the rule above. How many attempts and how long the pause is settled at Architecture: a run is up to eight attempts with a pause of fifteen seconds between them, and after a failed run a further run begins after a standing pause of a minute, for as long as the app is open. Label: **settled at Architecture** (2026-08-20). *(The first sentence used to say that a failed run "leaves the server disconnected and says so rather than going quiet". Only the state word moved, and it moved with the correction below; the saying is untouched, and Smoozy still tells the user when a run has failed. Label: **Creator-stated** (2026-08-22).)*

**Repair does not stop for good.** A failed run of attempts is not the end of it: the connection the user opened stays repairable for as long as the app is open, Smoozy goes on trying, and the server comes back on its own when the machine is reachable again, with the user doing nothing. So an hour with the user's own line down costs them that hour, rather than putting the server out of reach for the rest of the app run. Label: **Creator-stated** (2026-08-08).

**The connected period stands throughout.** The user asked for this connection and has not disconnected, so the period is still theirs, and every attempt to repair it belongs to that period rather than starting a new one. A repair that succeeds asks nothing of the user and does not need their connect action again. What becomes of the message saying the connection could not be restored, once it is restored, is settled by the whole-app concern *how a failure reaches the user* (see [Whole app](Whole%20app.md)).

**Smoozy does not make a connection it can see cannot work.** If the key file is missing, or the key needs a passphrase Smoozy is not holding, Smoozy does not make the attempt at all. It leaves the server disconnected, marks it with what is wrong, and says so. This holds for both of the connections Smoozy makes on its own — repairing a dropped connection, and putting a connection back after an edit (see [Editing a server](#editing-a-server)) — and it matches connect being withdrawn for a server needing a new key rather than offered and certain to fail.

**A key's passphrase.** A key can be protected by one. A connect **the user starts** may ask for the passphrase when Smoozy is not holding it; who holds and supplies it is owned by the [module map](Whole%20app.md). A connection Smoozy makes on its own never asks — an automatic attempt never puts a passphrase prompt on screen. It stops instead, as above.

While Smoozy is trying to restore a dropped connection, the server reads as neither connected nor disconnected but as **reconnecting** — one instance of the whole-app rule that anything not instant shows it is underway (see [Whole app](Whole%20app.md)). The same holds while a connection is being opened or closed by hand. **It reads as reconnecting for the whole repair**: through an attempt, through the pause between one attempt and the next, and through the longer pause between one run of attempts and the next, for as long as Smoozy is still trying. It still carries what Smoozy said about the run that failed. What these in-between states are called, and how they look, is Design's. *(This used to say that between one run of attempts and the next the server reads as **disconnected**, carrying what Smoozy said about the run that failed, and reads as **reconnecting** again the next time Smoozy tries — the word changing back and forth for as long as the repair ran. With a run's attempts fifteen seconds apart, that is a word changing faster than anyone can read it, and the plan for the app already showed the steady one instead, so this sentence described something Smoozy does not do. It is the sentence that was wrong, and it is the sentence that changed. What it costs, and the cost was accepted with the change: the user can no longer tell at a glance whether an attempt is in flight at this exact second. What they gain is a word they can read. The message saying the connection could not be restored is untouched — it still arrives when a run fails. Label: **Creator-stated** (2026-08-22).)*

**The user can end a reconnection.** Disconnecting is available for as long as Smoozy is repairing a connection — at any point in it, during an attempt or in either of the pauses — and taking it stops the attempts and leaves the server disconnected. No separate action is needed for it: it is the ordinary disconnect. *(The dash used to read "whether the server reads as reconnecting or as disconnected between attempts", which named the back-and-forth word retired above. The promise itself is unchanged: disconnect is offered for the whole repair, at any point in it. Label: **Creator-stated** (2026-08-22).)*

Neither **disconnected** nor **reconnecting** carries any claim about *why* the machine cannot be reached. Smoozy cannot tell, and says only what it knows about the connection — a whole-app rule, owned by the failures concern (see [Whole app](Whole%20app.md)).

**Connected and needing a new key can both be true.** A server's key can stop being usable while the user is connected to it — they delete it in Keys, or its file moves. Smoozy does not close the connection over it: the connection is already open, and the key was only ever needed to open it. The server stays **connected** and shows **needing a new key** alongside. The mark applies to the *next* connection, not this one. It appears the next time the server list is on screen, which includes while the server is connected — nothing watches keys in the background, and the check runs when the list is shown (see [When a server's key is gone or unusable](#when-a-servers-key-is-gone-or-unusable)).

Keeping an open connection alive through this is a promise this spec makes and Architecture has to deliver. If it ever proves undeliverable, that comes back here as a fault in the plan, not something quietly reinterpreted.

**It does survive, and this was tried rather than assumed.** A connection was opened with a key, the key was then deleted, and the connection went on working, while a fresh connection with the missing key failed. The key is what opens a connection; it is not what keeps one open. Label: **settled at Architecture** (2026-08-23).

If such a connection then drops on its own while the key is still gone or unusable, Smoozy does not try to restore it — there is no usable key to connect with, so the attempt could not succeed. The server ends up **disconnected** and **needing a new key**, and Smoozy says so.

Disconnecting ends the connection the user opened, and Smoozy does not reopen it on its own. It does not stop the server's **render work**: the render in progress keeps going whether or not Smoozy is connected, and the jobs waiting behind it stay queued and run in their turn.

The queue lives on the machine (a Queue & History fact — see the [Queue & History spec](Queue%20&%20History.md)), which is why reconnecting simply resumes following work that never paused.

That promise covers the render queue only. From Servers' side a disconnect settles nothing else: what becomes of other work driven over the connection is for its owning module to state, and each of them does. The [Download spec](Download.md) settles that transfers stop when the connection goes, and that a part-arrived file is never left behind looking finished. The [File Browser spec](File%20Browser.md) settles the upload side.

**A drop Smoozy repairs is a different event from a disconnect, and transfers in both directions carry on across it.** Where the repair above succeeds, the uploads and the downloads the drop interrupted pick up where they stopped, without the user asking again — the [File Browser spec](File%20Browser.md) for uploads and the [Download spec](Download.md) for downloads, each owning its own side. The reason is this section's: the connection the user opened is still theirs, the period never ended, and Smoozy holding a repaired connection and not using it would waste the very thing the repair was for. **The user disconnecting is the opposite case** and nothing resumes on its own, because there is no connection left and none was asked for. The [Server Setup spec](Server%20Setup.md) settles an install cut off part-way: it stops, nothing resumes on its own, Smoozy says what it managed, and the user runs the rest from there.

A connection attempt that simply fails — an unreachable host, a rejected login — can happen at any time, not only during an add; the server simply stays disconnected. How that reaches the user is settled by the whole-app concern *how a failure reaches the user* (see [Whole app](Whole%20app.md)).

**A machine that is not Linux.** Smoozy renders only on Linux machines — a whole-app boundary owned by the [module map](Whole%20app.md). A plain add never reaches the machine, so the **first connection** is the earliest Smoozy can tell. When it finds a machine that is not Linux, it says so plainly and leaves the server **disconnected**: nothing Smoozy does afterwards would work there, so one clear refusal is better than every later action failing on its own. The server stays in the list like any other, to be edited or removed. How Smoozy tells is Architecture's. Label: **Creator-stated** (2026-07-27).

**Trusting a server's identity.** SSH records a server's identity the first time it connects and checks it on every later one. Left at its default it **asks** the user before recording a new identity at all, and what it does about a *changed* identity depends on how it is set — it warns rather than silently accepting, and it can be set to refuse the connection outright. *(documented — see [Sources](Sources/Servers.sources.md))* Smoozy departs from that default deliberately: the first time it connects to a server it records the machine's identity and trusts it silently, accepting that only a *change* to it can ever be caught, in exchange for a first connection that asks the user nothing. Silent first trust is Smoozy's own policy, not documented SSH behaviour. SSH's own default, and the documented setting that behaves the way Smoozy does, are both cited in [Sources](Sources/Servers.sources.md). *(Creator-stated, 2026-07-17)* The policy itself is settled here; how it is carried out is Architecture's.

Smoozy also gives no way to see or confirm the machine's remembered identity. That is deliberate, and for its own reason: the identity means nothing to a 3D artist, so showing it would add a screen nobody could act on. This policy settles ground the whole-app **security** concern also covers, and the two have to agree (see [Whole app](Whole%20app.md)).

If the machine's remembered identity later **changes** — which can mean the machine was swapped, or that someone is impersonating it — Smoozy **warns the user and does not quietly connect anyway**, the same stance Keys takes when a key's file no longer matches what it knew (see the [Keys spec](Keys.md)). The warning offers a way through as well as a way out.

**Accepting.** The user says the new identity is legitimate. Smoozy records it, starting the machine's remembered identity over as if connecting for the first time, and the connection attempt goes ahead. That covers the honest case — a machine wiped and reinstalled at the same address — without letting an unnoticed change slip by, since accepting is a deliberate act the user has to take.

Accepting is a choice to trust the machine, not a confirmation of which machine it is. Smoozy shows no fingerprint and puts up no extra screen, so there is nothing here for the user to check the machine against — that is silent first trust holding at the second connection as well as the first. Accepting must not be read as a check that has been passed.

**Declining.** The connection attempt stops there and the server is left disconnected. The old remembered identity is kept, so the same warning comes back on the next attempt until the user accepts or the machine answers with the identity Smoozy remembers.

How the warning is shown and worded is left to Design. **The remembered identity is kept with the saved server in Smoozy's own record and nowhere else** — one per server, replaced when the user accepts, started over when the address is edited, and never put in front of the user. Label: **settled at Architecture** (2026-08-23).

**What the explicit-connect model leaves to other modules.** Because the user is disconnected by default and connects by hand, no new connection and no fresh remote action starts without them. Two things do carry on without a further word from the user: work they already asked for, such as a render already queued, and repair of a connection they opened. Automatic behaviours other modules promise have to work inside that model. Download's opt-in auto-download is the settled example: the [Download spec](Download.md) states that it stops when a connection is lost and picks up on the next connection the user opens, which is work already asked for resuming on a connection the user made. Telegram is the second settled example, and it fits differently: its bot runs on the rented machine rather than inside Smoozy, so Smoozy opens no connection for it at all, and what the bot carries out is what the user asks from their phone at the moment they ask it. See the [Telegram spec](Telegram.md).

## Editing a server

A server's details are not frozen — the user can change its name, host, port, username, or key after adding. Servers change: a rented machine's address rotates, or the key it connected with is gone and a new one must take over. Editing the key is how the user re-points a server that is waiting for a new key (see [When a server's key is gone or unusable](#when-a-servers-key-is-gone-or-unusable)). Edited details go through the same duplicate check as a new add (see [Adding a server](#adding-a-server)), warning without blocking there exactly as it does on an add. Renaming a server into a name already in use gives the same warning an add does, for the same reason.

**A server also carries a fallback folder. Added 2026-10-04.** One folder on that server, typed as its full path, for the jobs whose own output folder cannot be used there; left empty, those jobs go to Smoozy's own folder, as before. What it governs, and what happens when it cannot be used, is [What a job writes](What%20a%20job%20writes.md)'s. It is set with the server's own details — where exactly is Design's — and it is not a connection detail: saving it alone leaves the connection alone and warns about nothing, as a rename does. Label: **Creator-stated** (2026-10-04). *(Added later on 2026-10-04, ruled by the build runner: a path that is not a full path is refused where it is typed, so a typo never sends jobs somewhere the user did not mean.)*

The edit dialog picks a key the same way the Add Server dialog does: from the keys Smoozy already knows about, with unusable ones left out, and with Keys openable from the dialog and the key handed back selected. One difference: if the server's **own** key is the unusable one, it stays selected rather than being cleared. Otherwise a server whose key had broken could not be renamed, or moved to a new address, without being made to pick a new key first — and the user is meant to have more than one way out (see [When a server's key is gone or unusable](#when-a-servers-key-is-gone-or-unusable)). The edit can then be saved with that unusable key left exactly as it is. No **other** unusable key can be put in its place, since none is offered, and the server goes on showing **needing a new key** with connecting unavailable until the key works again.

**What an address edit does to the machine's remembered identity.** Changing the **host or the port** starts the remembered identity over, as if connecting for the first time. Host and port together name what Smoozy is reaching, so changing either one points the entry at a different machine — and a deliberate address change is then not mistaken for an impersonation. No extra warning and no separate choice is put in front of the user for this: it is simply what an address edit does. Changing the username or the key leaves the remembered identity alone, since neither changes which machine is reached.

**Saving** changes to the **host, port, username, or key** — the connection details — disconnects a live server so the change can be applied, after which Smoozy **puts the connection back on its own**. That applies only to a server the user had connected: editing a disconnected server leaves it disconnected. Renaming leaves the connection alone. If putting the connection back fails, the server is left disconnected with the new details saved, and Smoozy says so rather than going quiet. Smoozy does not attempt the put-back at all where it can see it cannot work — a missing key file, or a passphrase Smoozy is not holding — and leaves the server disconnected and marked with what is wrong instead (see [Connecting](#connecting)). How that reaches the user is settled by the whole-app concern *how a failure reaches the user* (see [Whole app](Whole%20app.md)).

Because Smoozy puts the connection back itself, that reconnect can meet a machine whose remembered identity has changed — on a username or key edit, where the identity is kept rather than started over. The usual changed-identity warning appears and the user decides (see [Connecting](#connecting)). Declining leaves the server disconnected with the new details saved, the same outcome as any failed put-back.

**A remembered machine password is cleared here.** Where the user let Smoozy remember a password for a step the ordinary login was not permitted to carry out, that password belongs to the **server** rather than to the key — see *Security* in [Whole app](Whole%20app.md), which owns the rule and the three choices behind it. So editing a server is where the user clears it, in the same spirit as clearing a remembered key passphrase in [Keys](Keys.md). It goes on its own when the server is removed, which is below. Changing the **username** clears it too, without asking: a password belongs to a login, and the login has changed. Label: **Creator-stated** (2026-08-10).

Editing a server that carries a **remembered setup** keeps that setup. The details change, the setup stays, and it runs on the next connect that succeeds. That is what the remembered setup is for: an add whose connection failed on a wrong address is put right by editing the address and connecting.

A connection Smoozy puts back after an edit never carries a remembered setup, though. A setup is only remembered when the connection failed, so a server carrying one has never been reached and is therefore disconnected (see [Adding a server](#adding-a-server)) — and editing a disconnected server leaves it disconnected, so there is no connection to put back.

A server **may** be edited while it has jobs queued or running on it — but never quietly. Changing the **host or port** points the entry at a different machine and leaves those jobs behind on the old one, so Smoozy warns first, plainly, and the user decides. **Changing the username carries the same warning**, for a different reason: the work stays on that machine, and Smoozy stops being able to reach it. Logged in as someone else, Smoozy can see such a render but cannot stop it, and the piece of Smoozy on the machine answers only the login it was set up under — so the work is out of reach, and it is not offered back as untracked work either. Label: **Creator-stated** (2026-08-19), settled at Architecture the same day. Changing the key moves nothing and reaches nothing, and renaming changes no connection detail at all; neither carries the warning.

If the user goes ahead, the jobs left on the old machine are **abandoned**. They keep running there, and Smoozy stops tracking them. The warning is what makes that the user's choice rather than a surprise. If a later connection finds that work again, it is picked up the same way as any untracked work Smoozy meets (see [Removing a server](#removing-a-server)).

## Removing a server

Removing a server makes Smoozy **forget it** — its details, its connection, the machine's remembered identity, any setup it was still remembering, and any machine password it was holding for it (see *Security* in [Whole app](Whole%20app.md)).

**The confirmation does not list those things out.** Saying the server is removed from Smoozy covers them, and a user who has just asked to remove one is not weighing whether the port number survives. *Words changed 2026-10-28 (was *Saying Smoozy forgets the server covers them*): Creator-stated, the final words sweep. No auditor has seen it.* A list of everything that goes reads as a torrent of information about a word the user already understands. Label: **Creator-stated** (2026-08-13). Whether the confirmation is a box at all, and how it reads, is Design's.

Removal leaves the rented **machine** itself alone — it makes Smoozy forget the server, not touch the machine. That the machine is the user's — never rented, billed, powered on or off by Smoozy, and acted on only in the ways the modules set out — is a whole-app boundary owned by the [module map](Whole%20app.md), not restated here.

**Where the machine has nothing on it, that is the whole of a removal.** A connected server with no job queued and none running is forgotten with a plain confirmation and nothing else — no jobs warning, and no offer to stop or clear anything, because there is nothing to stop and nothing to clear. Label: **Creator-stated** (2026-08-10). It is said here rather than left implied because [Queue & History](Queue%20&%20History.md) points at this document for which removals get the offer at all, and a rule stated on one side only is a rule that drifts.

If the server has jobs **queued or running** on it, Smoozy **warns the user first** — that there are such jobs — and offers a choice between two outcomes (which of them are actually available depends on the server, as set out below):

- **Leave it be.** Smoozy forgets the server and its queued and running jobs, and touches nothing on the **machine**. It forgets the server either way; what it leaves alone is the machine. Whatever was running keeps running there; the pending jobs are no longer Smoozy's concern.
- **Stop and clear first.** Smoozy stops whatever is running and clears the pending jobs, then forgets the server. This is the one removal that reaches the machine, so it is also the one that takes **Telegram**'s piece off it — what happens to that piece is the [Telegram spec](Telegram.md)'s, which owns it.

**Stop and clear** only works on a server Smoozy can reach — and **Smoozy never reaches out to a disconnected server to find out**. Removing a disconnected server never starts a connection and never asks for a passphrase.

So what the user is offered depends on the server:

- **Connected.** Smoozy can see the machine through the session the user already opened. When a connected server reports queued or running jobs, Smoozy warns, offers both choices, and this warning cannot be switched off.
- **Disconnected.** Smoozy reaches out to nothing. It warns from what it last knew, and offers only *leave it be*, since it cannot stop or clear what it will not reach. Because of where the queue lives (see [Connecting](#connecting)), a disconnected server's jobs can only be remembered, never seen — which means this warning may be out of date. Because it rests on stale knowledge, the user may **turn it off** — never seeing this warning again, for any disconnected server, not only the one in front of them, until warnings are restored in Settings. That is the difference from the connected case: the disconnected warning may be turned off because it can be wrong, and the connected one may not because it is not.

  Turning it off is not permanent. The way to bring it back is a whole-app control in Settings that restores every warning the user has switched off, not a Servers control (see [Whole app](Whole%20app.md)).

  What that last-known record is, is settled by [Queue & History](Queue%20&%20History.md): only what Smoozy read while it was connected, held only while the app is open. So this warning reaches only a server Smoozy has connected to since the app was last opened. Remove a disconnected server after closing and reopening Smoozy, and **no jobs warning appears at all** — there is nothing left to warn from, and Smoozy does not reach out to the machine to find out.

Even for a connected server, being able to reach the machine now is not a promise about a moment later: it can drop out of reach, or refuse the login, between the warning and the click.

If it does, and *stop and clear* cannot begin at all, Smoozy reports that nothing on the machine was changed. It then asks whether to try again or to remove the server and leave the work running. It does not remove the server without saying so, and it does not treat a machine it could not reach as a machine it cleared.

If *stop and clear* begins and only partly succeeds, Smoozy does not decide for the user either. It says what worked and what did not, then asks whether to try the remainder again or to remove the server anyway and leave the rest alone.

**Which half can fail on its own is settled by the order the two are done in, and that order is [Queue & History](Queue%20&%20History.md)'s.** The waiting jobs are cleared first and the running render is stopped second, because stopping the render sets the machine off on the next waiting job — so clearing first leaves it nothing to start. Two things follow for the partial case. **Where the waiting jobs could not be cleared, the running render is not stopped at all**, since stopping it would hand the machine one of the very jobs that could not be cleared. And the case this document can genuinely report as half-done is the other one: the waiting jobs went and the render could not be stopped.

The stopping and clearing themselves are **Rendering**'s and **Queue & History**'s work, which Servers asks for. What each of the two choices does to the queue on the machine — and what each leaves behind in history — is settled in the [Queue & History spec](Queue%20&%20History.md).

**What removal does to the server's history.** Nothing. A machine's finished jobs are held in Smoozy's own record on the user's computer as well as on the machine, so removing the server leaves them where they are, and destroying the machine does too — a Queue & History fact, stated and labelled in the [Queue & History spec](Queue%20&%20History.md). Nothing here needs to hide them, restore them, or match a returning machine against them. What the history is, how long it is kept, and what it holds are **Queue & History**'s to state, not Servers'.

**Work Smoozy is not tracking, found on a connection.** On **any** connection that finds queued or running work Smoozy is not tracking, Smoozy says what it found and **offers to resume tracking it**. It never resumes silently: the user may have walked away from that work deliberately, so the choice is theirs.

That is how a server removed under *leave it be* gets its work back. Its queued and running jobs are still sitting on the machine, and a plain add never reaches the machine, so nothing can be found until the **first connection that succeeds** after the machine is added back — and the offer made then is the same one any connection makes.

Declining is not final. Any later connection that finds that work still sitting there makes the offer again, so a single "no" does not hide a running render for good. What accepting does — how resumed work rejoins the live queue — is settled in the [Queue & History spec](Queue%20&%20History.md), along with the rest of the offer's meaning.

**A machine can be read for the work left on it.** One request on a connection brings back everything the machine is holding — what is running and what is waiting — and it reaches work Smoozy never tracked as readily as work it did. Where the machine cannot be reached, Smoozy says it could not check rather than saying there is nothing there. The same answer serves [Queue & History](Queue%20&%20History.md)'s promise, which rests on the same reading. Label: **settled at Architecture** (2026-08-23).

## When a server's key is gone or unusable

A saved server connects with a key from Keys. If that key becomes unavailable — the user deletes it, removes it from Smoozy, or its file goes missing or no longer matches what Keys knew — the server is **not** removed with it. It stays in the list, **marked as needing a new key**.

The user has three ways out, and can take whichever suits: give the server a working key (an edit, pointing it at a different one), mend the key itself in Keys (pointing Smoozy at where the file now lives, or putting the file back), or remove the server like any other.

**All three ways out remain available.** Choosing a different key, mending the key in Keys, and removing the server have no licence gate.

The **needing a new key** mark clears once Servers learns that the server's key is **usable** again. It does not matter how that happened — a different key chosen here, or the same key mended in Keys. No edit to the server and no removal is needed. When the server list is shown, Servers asks Keys whether each key is usable, so the mark clears the next time the user looks at their servers. Smoozy does not watch keys in the background.

What counts as usable is Keys' to define (see the [Keys spec](Keys.md)). What Servers owns is what follows from it: a server whose key is unusable is marked as needing a new key, and whether a key can actually log in is only ever proven at connect time.

Each saved server remembers the **fingerprint** of the key it uses, and matches against that. This is what lets a key be recognised as the one this server wants, even after it left Smoozy entirely and was pointed at again later. The fingerprint itself — what it is, and that it identifies a key over time — belongs to Keys (see the [Keys spec](Keys.md)), as does what Keys keeps and for how long. Servers' own half is that the server holds the fingerprint it needs.

If a key goes unusable while the user is connected to that server, the connection is left alone and the mark simply shows alongside it (see [Connecting](#connecting)).

Keys warns before a relied-on key is deleted or removed from Smoozy, naming the servers that depend on it, and lets the user proceed anyway (see the [Keys spec](Keys.md)). This section is what those named servers do once the key is gone.

## What Servers does not do

- It does not install software on a server — that is **Server Setup**'s work (see [Adding a server](#adding-a-server)).
- It does not make, store, or manage keys — it only **picks** one for a server; keys belong to **Keys**.
- It does not rent, bill, power on, or power off the rented **machine** — that boundary is the whole app's, owned by the [module map](Whole%20app.md).
- It does not browse a server's files, render, or move files to and from it — browsing and moving files belong to **File Browser**, **Dependency Upload & Remap**, and **Download**; rendering is **Rendering**'s.
