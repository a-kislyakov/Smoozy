# Whole app

*The app-wide Specs: the map of Smoozy's feature modules and how they connect, plus the concerns that belong to no single module. Each module's full behaviour lives in its own Specs document; this is the skeleton they hang off.*

## The feature modules

Smoozy is built from these feature modules — the capabilities the user gets, each able to be added, changed, or removed on its own. Their canonical names are recorded in the [Glossary](../Groundwork/Glossary.md). Each entry below gives the module's connections — how it wires to the others — and links to its own spec for the full scope. Until a module's spec is written, its entry also carries the scope.

### Keys
*Connects to:* hands keys to **Servers** — the Add Server and Edit Server dialogs pick which key a server uses — and is most often opened from one of those dialogs. Also reads from **Servers** which saved servers rely on a given key, so it can name them before the user deletes or removes that key. When a server's key is protected by a passphrase, **Keys holds and supplies the passphrase while Servers makes the connection**: the passphrase stays a Keys responsibility even though the connection is Servers' work. Works only on the local machine — it never talks to a server itself.
The hand-off with the server dialogs runs both ways and is small: a dialog opens Keys to pick, make or mend a key and gets that key back **selected** for the server; unusable keys are never offered, so no server is created already needing one; the server keeps the key's **fingerprint** rather than its name or its file, which is how the same key is recognised later; and where the key has a passphrase, Keys supplies it while Servers makes the connection. Cancel-and-return, and what makes a key unusable, are the [Keys spec](Keys.md)'s. Two keys Smoozy knows can never share a fingerprint: Keys refuses a second reference to a key it already holds and keeps one entry, so the same private key pointed at twice under two names does not arise.
*(Qualified on 2026-10-16: the passphrase hand-off in both paragraphs above happens **on macOS and Linux only**. On Windows Smoozy cannot make or use a key with a passphrase, as the [Keys spec](Keys.md) says, so there is no passphrase for Keys to supply. Out of the `Keys` code round 1, which gave the Keys spec the same narrowing on 2026-09-03 and left this map without it. No auditor has seen this change.)*
*Full scope:* [Keys spec](Keys.md).

### Servers
*Connects to:* takes a key from **Keys**, on the terms recorded under Keys above; delegates all software installing to **Server Setup** (the Add Server dialog's setup options are a front door to it, not work Servers does itself); and on removal of a server **that has jobs queued or running on it**, Servers warns and offers a choice between leaving the work running and asking **Rendering** to stop the running render and **Queue & History** to clear the waiting jobs — the latter only while connected. A removal with nothing on the machine is a plain removal, with no warning and no offer, and never reaches either module. Every module that acts on a server relies on Servers for the connection. A saved server remembers the **fingerprint** of the key it uses and matches keys against it, so a returning key — even one that left Smoozy and was pointed at again later — is recognised.
*Full scope:* [Servers spec](Servers.md).

### File Browser
*Connects to:* needs a connected server from **Servers**, and provides the chosen `.blend` to **Render Settings**. **Queue & History** can open it at a chosen folder, which is what *show outputs* on a job does. User-driven uploading lives here — it is not a module of its own, and it hands **Dependency Upload & Remap** where on the user's computer each uploaded file came from, which that module needs to resolve a location written relative to the `.blend`. It leans on **Queue & History** for which jobs are running or waiting, so it can warn before the user deletes, moves, or renames a file a live job depends on — and tells that module when the user goes ahead anyway, so the job carries the mark rather than failing later unexplained. **Rendering** can open it on a machine so the user points at a `.blend` that has moved, or at the file to use when a job is submitted again on a different machine. Nothing travels *down* here: the file browser is one of the places a download is started from, but everything that comes back to the user's machine belongs to **Download**.
*Full scope:* [File Browser spec](File%20Browser.md).

### Server Setup
*Connects to:* needs a connected server from **Servers**; reached both from the Add Server dialog, whose two setup options are a front door to it, and from Server Setup itself, where the fuller choice lives. **Rendering**, **Render Settings** and **Dependency Upload & Remap** all depend on it having put a Blender on the machine, and **Render Settings** picks between the versions it installed. It installs no add-ons: the Creator parked them on 2026-10-08 (see the [Server Setup spec](Server%20Setup.md#add-ons)). **Render Settings**' Pre-load still finds the one case a file announces — an engine the chosen Blender lacks — and says so on its own page. It leans on **Queue & History** for which jobs are running or waiting on a machine and which Blender each uses, so it can warn before removing a Blender a live job needs — the same lean **File Browser** has for a file a live job needs. A restart it causes takes a running render down, which **Queue & History** owns the aftermath of. It is the only module that installs anything on a machine, and the only one that restarts a running machine — see the boundary below. **Telegram** leans on that: the piece of it that runs on a machine is put there while the machine is being made ready, rather than by Telegram itself.
*Full scope:* [Server Setup spec](Server%20Setup.md).

### Render Settings
*Connects to:* needs a `.blend` chosen in **File Browser**, which hands the file over without reading it, and a connected server from **Servers**. Depends on **Server Setup** having put a Blender on the machine: without one the file cannot be read and no job can be sent from it. The settled settings feed **Rendering**, which submits them; and its reading of the file gives **Download** both the count of a job's expected outputs and the list of formats an auto-download arrangement can be narrowed to, and finds the one add-on case a file announces — an engine the chosen Blender lacks — which is all a `.blend` can be read for. Checking a `.blend` for what it is missing is **not** here — it is its own action the user takes, and belongs to **Dependency Upload & Remap**.
*Full scope:* [Render Settings spec](Render%20Settings.md).

### Dependency Upload & Remap
*Connects to:* needs the `.blend` chosen in **File Browser**, a connected server from **Servers**, the local files, and a Blender from **Server Setup**, since reading the file for what it points at happens on the machine. It also takes from **File Browser** where on the user's computer each uploaded file came from, without which a location written relative to the `.blend` resolves to nothing usable once the file is on the machine. Leaves the `.blend` render-ready for **Rendering** — which puts the remap of the file a render is built from into effect at the moment the render starts, alongside the output redirect, since that file is read and never written to and so carries no remap of its own. **Rendering**'s warning that nobody looked for a file's missing assets stops on the strength of this module's check. It does **not** depend on **Render Settings** having read the file: checking for missing assets is not part of Pre-load Settings, and neither read waits on the other. Its own uploading is distinct from **File Browser**'s, which sends up what the user points at and changes nothing inside the files; where a plain upload would land on a file this module fixed, Smoozy says so.
*Full scope:* [Dependency Upload & Remap spec](Dependency%20Upload%20&%20Remap.md).

### Rendering
*Connects to:* needs a Blender from **Server Setup**, settings from **Render Settings**, a render-ready file (possibly via **Dependency Upload & Remap**), and a connected server from **Servers**. Hands submitted jobs to **Queue & History**, and takes from it the setup a finished job ran with when the user submits that job again — and, for the separate action that carries a job on from where it stopped, the last frame that module can vouch for as finished, which the new job's range starts after. It hands that module back the earlier job a carried-on job continues, which the new entry then marks. Submitting is also where **Download**'s auto-download is normally switched on, before the job goes, where the job's label is given, and where **Telegram**'s choice of how much a job reports is made. Asking for the first-frame check there submits two jobs rather than one, the second held by **Queue & History** until the user answers. It opens **File Browser** on a machine when a job submitted again needs its `.blend` found — including on a machine that never ran it, since a history entry's setup outlives the machine that did. Ending a render that is running is Rendering's work and is asked for by two others: **Queue & History**, when the user stops a job, and **Servers**, on the removal of a connected server. It carries out the redirect settled in [What a job writes](What%20a%20job%20writes.md) at the moment a render starts, and at that same moment puts into effect the remap that **Dependency Upload & Remap** holds for the file the render is built from.
*Full scope:* [Rendering spec](Rendering.md).

### Queue & History
*Connects to:* receives jobs from **Rendering**; tells **Download** when a job starts running and when it is over, saying which ending it was, supplies a job's identity and the folder its outputs are written into, hands it whatever happened while Smoozy was away, and is where the user reaches Download's auto-download toggle for a job already submitted. Opens **File Browser** at a job's main output, which is what *show outputs* does, and is told by that module when the user has disturbed a file a live job needs. Holds a job that is waiting on the user's yes for **Rendering**'s first-frame check, and hands **Rendering** the setup of a finished job when the user submits it again — including onto a different machine, since that setup is Smoozy's own record and outlives the machine. For the second action on such an entry, carrying a job on from where it stopped, it also hands over the last frame it can vouch for as finished, and marks the new job's entry with the earlier job it continues. Needs a connection from **Servers** for everything it reads from a machine or acts on there, since the queue lives on the servers rather than inside Smoozy. History is the exception: each machine keeps its own, and Smoozy keeps its own record of finished jobs on the user's computer, which needs no connection and outlives the machine. On a server's removal, when that server is connected, **Servers** can ask Queue & History to clear that server's waiting jobs; **Servers** also leans on what Queue & History last knew of a disconnected server's jobs when warning about a removal. **Server Setup** reads it the same way, for which jobs are live on a machine and which Blender each uses, before it removes a Blender or runs a step that could take the machine down.
*Full scope:* [Queue & History spec](Queue%20&%20History.md).

### Download
*Connects to:* needs a connected server from **Servers**. Its auto-download is normally switched on at the moment a job is submitted, which is **Rendering**'s action. It is otherwise started from **File Browser**, where the user picks what to bring down, and from the queue, where the auto-download toggle is reached, and history in **Queue & History** — which tells Download when a job starts running and when it is over, supplying a job's identity, the folder its outputs are written into, and whatever happened while Smoozy was away. Leans on **Render Settings**, whose reading of a `.blend` gives the number of output files a job will produce. Writes to the user's own machine, and changes nothing on the server.
*Full scope:* [Download spec](Download.md).

### Telegram
*Connects to:* **Server Setup**, which puts its piece on a machine while that machine is being made ready — the one thing this module needs done to a server, and it needs no connection of its own from **Servers**, because the machine speaks for itself whether or not Smoozy is running. Reads **Queue & History** for what a job is doing and how it ended, and leans on [What a job writes](What%20a%20job%20writes.md) for which picture a preview shows, rather than choosing its own. Asks **Rendering** to stop a render and to submit a failed job again, and asks **Queue & History** and **Rendering** together for the first-frame check — a job's first frame sent on its own, with the rest waiting in the queue for the user's yes. It adds no action of its own to any of them: everything it offers is something the app already does, reached from a phone.
*Full scope:* [Telegram spec](Telegram.md).

## Concerns that span the whole product

Some things belong to no single module and are settled here.

- **Platforms.** Smoozy runs on Mac, Windows, and Linux. Label: **Creator-stated** (2026-07-16).
- **Servers and keys only — never providers.** Smoozy knows only servers and SSH keys, never providers. It may speak to the user in provider terms where that helps (for example, suggesting one key per provider), but no provider exists anywhere in the app itself.
- **The machine is the user's, not Smoozy's.** Smoozy never rents, bills, powers on, or powers off the rented machine. It acts on the machine only in the ways the modules set out — installing software, running jobs, stopping work, clearing queues — never on the machine's existence or its power. **There is one exception, and it is deliberate:** where a setup step needs the machine restarted, Smoozy restarts it itself, without asking. Label: **Creator-stated** (2026-07-29). A setup that stopped and waited for the user to go and reboot the machine at their provider would leave it half-prepared until they came back, which is the opposite of what this app is for. The exception is narrow on purpose — a restart a setup step needs, and nothing else. Smoozy still never powers a machine on, and never powers one down for good. What a restart does and what it costs belongs to the [Server Setup spec](Server%20Setup.md).
- **Where Smoozy's job stops.** Smoozy promises three things, and nothing else. It **does what it says it will do**. It **never loses or damages the user's work**. And it **always tells the truth about what happened** — including when the news is bad, and including when the cause was the user's own doing. Everything else in this document, and in every module's spec, is one of those three made specific. Label: **Creator-stated** (2026-08-07).

  Past that line the user's own judgment stands. Smoozy does not check that their file is set up sensibly, or that its settings will produce anything worth having. It does not repair a folder of assets with pieces missing. It does not stop the user doing something they chose to do, and it does not fight their own computer for them — a laptop that goes to sleep with transfers running is doing what its owner set it to. The person using this app is a professional who knows their craft, and being second-guessed at every turn costs them more than the occasional consequence of their own decision.

  Two things this does **not** excuse. The third promise never bends: a sequence with frames missing is the user's own doing, and Smoozy still says plainly what it found. Telling the truth is on Smoozy's side of the line always, and it is not the same as babysitting. And a mistake Smoozy itself makes is never the user's, however small the user's part in reaching it.

  What sits past the line is Smoozy taking over the user's judgment — checking their work for them, refusing what they asked for, or nagging. Where something helpful past the line is worth doing anyway, it is a **want** under Rule 7: it gets parked and decided on its own merits, never treated as a fault the plan owes a fix.

- **The machines Smoozy renders on run Linux, and the Linux Smoozy sets up is Ubuntu or Debian.** Smoozy works with Linux servers and no other kind. This is a deliberate limit, taken to keep the project clear of the legal complications other operating systems bring, and the user is told it before they go and rent anything (see the guidance below). Smoozy cannot check it while a server is merely being added, because a plain add never reaches the machine; the first connection is the earliest it can tell, and what it does then is set out in the [Servers spec](Servers.md). Label: **Creator-stated** (2026-07-27).

  **Inside Linux there is a second, narrower boundary, and it is named rather than left to be discovered.** Preparing a machine means installing things on it, and every Linux family does that a different way. Smoozy prepares **Ubuntu and Debian** machines. On a Linux machine of another family it says so plainly and prepares nothing, rather than half-preparing it and leaving the user with a machine that looks ready and is not. **The user is told which kinds to rent in the same guidance that tells them to rent Linux at all**, so the boundary is met before the money is spent rather than after. Label: **Creator-stated** (2026-08-22). **What this costs the user is stated rather than hidden:** somebody who rents a Fedora, Rocky or Arch machine can add it, connect to it and browse it, and cannot have Smoozy set it up. **Why this and not broader:** the machines actually on offer lean heavily to Ubuntu — on 2026-08-22, 1,700 offers sampled from one provider across several orderings, which is a sample of what it rents and not the whole of it, were Ubuntu and nothing else; a second provider offered Ubuntu, Debian and one other; and a third, read the same day, offered Ubuntu and one other in every region and no Debian anywhere, which is the reminder that a family Smoozy supports is not necessarily one a given seller stocks. So the narrow promise costs almost nobody anything, while a promise of *any Linux* would be one Smoozy could not keep. Another family can be added later, and adding one is its own bounded piece of work rather than a change to anything here.
- **Smoozy works with Blender 4.5 and above.** Older versions are out of scope, and nothing in this project is written to accommodate them. Label: **Creator-stated** (2026-07-28). The floor matters more than a version floor usually would, for reasons [What a job writes](What%20a%20job%20writes.md) sets out.
- **What a job writes, and where it lands.** **Render Settings**, **Queue & History**, **Download** and **Rendering** all promise something about a job's outputs and none of them owns the question, so it is settled in its own document: [What a job writes](What%20a%20job%20writes.md). It holds the redirect that brings every output under the job's folder, the **main output** a job's important work lands in, what the frame preview reads, what a job's file count is made of, and what a re-run treats as already there.
- **Restoring suppressed warnings.** A single control in Settings restores every warning the user has switched off, all at once — the one way back for any dismissible warning, wherever in the app it was turned off.
- **Getting the app, and updates.** The user gets Smoozy by downloading a binary from its website — no email, no account, no registration. **There is a download for Macs with Apple silicon on macOS 11 or later, for Windows 10 or later on 64-bit Intel or AMD processors, and for Ubuntu 24.04 or 26.04 and Debian 13 on those same processors, and for nothing else.** *(Ruled 2026-10-24 by the build runner under the Creator's standing delegation; why each limit sits where it does is `Desktop app and delivery` E4b. No auditor has seen it.)* **After that, Smoozy keeps itself up to date.** The user is not sent back to the website to fetch a newer copy, and updating is not something they have to remember: the app does it. **They may also ask for a check themselves**, which is the same act reached a second way rather than a thing they have to do; nothing is promised differently if they never use it. Label: **Creator-stated** (2026-07-27), and the asking-for-a-check sentence **Creator-stated** (2026-08-23). How it does it — where a new version comes from, how it is checked, and how it lands — is Architecture's and Build's, and what the user sees or is asked at that moment is Design's. Label: **settled at Design** (2026-08-23) — nothing at all on Mac and Windows; on Linux one box, once per version, saying what the password the system is about to ask for is for.

  **The Windows download is signed through SignPath Foundation's free code signing for open-source projects, so Windows names SignPath Foundation, not the Creator, as its publisher; a Windows release SignPath has not signed goes out unsigned.** Label: **Creator-stated** (2026-11-01), on learning that open-source projects can be signed for free: *"Free signing for open source? I didn't know! Does it mean I don't need an expensive developer's license here?"*, and, asked whether it should become a want, *"Yes please! That's amazing news!"* *(No auditor has seen this paragraph.)*

  **A version that cannot update itself says so, and never says it tried.** A version released before self-updating was finished cannot keep itself up to date, and its users update from the website once, by hand. Where the user would see whether an update was found, that version says plainly that automatic updates aren't available in it, known from the version itself and without asking anything over the network — never that the update service could not be reached, which would be false. Label: **Creator-stated** (2026-11-01), after the update control on 0.2.0 said *Could not reach the update service*: asked whether to say so plainly, *"Yes please"*. *(No auditor has seen this paragraph.)*

  **One thing that is asked is settled, and it is settled here because it is a cost rather than a wording.** On **Linux**, and on Linux alone, an update asks the user for their own computer password — the system's own request, not Smoozy's — because on that system a new version arrives as a package the machine installs, and installing one is something only an administrator may do. **A user who declines, or who is not an administrator of their own machine, simply stays on the version they have, working**; nothing is broken and nothing nags them. Label: **Creator-stated** (2026-08-22). **The promise above is unchanged:** the user still discovers nothing, fetches nothing and remembers nothing — Smoozy does all of it and then asks once. **On Mac and Windows the password is not asked, and that is the whole of what is settled there.** Whether an update on those two systems puts anything else in front of the user is an open question rather than a promise of silence: on Mac, whether the system's own permission-to-open step comes back for each new version the app installs for itself; on Windows, whether the system's own warning about an unfamiliar program appears on a version the app fetched and started itself. Neither has been answered either way. A Windows machine can be rented, and four have been — but every one this project has read turned out to be a server edition of Windows rather than the ordinary desktop Windows a user has, and this warning is something only the desktop one shows. So the second stays open, and answering it needs a desktop Windows. **If either turns out to put something in front of the user, that is a change to what the user gets, and it comes back here to be written as a cost rather than being settled wherever it is found.** *(No auditor has seen this paragraph.)*

  **Smoozy does not update itself while jobs are running.** Label: **Creator-stated** (2026-09-28), in their own words: *"We need to have Smoozy not update on its own while jobs are running. The user should be able to override this block, but by default — updating only happens with no running jobs."* So a new version that arrives while a job is running waits, and goes in by itself once none is; the user still has nothing to remember. **A job counts as running from the moment it is sent until it has ended** — rendering, waiting in its machine's line, and waiting on the user's answer all count — **and so does any upload or download still under way.** A job on a server Smoozy is not connected to counts as it was last seen, because Smoozy cannot tell that it has ended. **The user can have the waiting version installed anyway, and is told first what that does**: Smoozy restarts, jobs go on rendering on their servers, and transfers under way stop exactly as they do when Smoozy is closed. **What this costs is stated rather than hidden:** a user whose jobs never all end — one left waiting on an answer they never give, say — stays on the version they have until they end it or install anyway. What the user is shown is Design's. *(No auditor has seen this paragraph.)*

  **Smoozy's own part on each rented server follows the app, and waits the same way.** Label: **Creator-stated** (2026-09-28), in their own words when they asked what happens to servers already set up: *"How do they know this stuff has to be updated, too?"* — and ruled that day by carrying their rule above across to servers, which is what they asked for. **A server runs the Smoozy of the app's own version.** When Smoozy connects to a server whose part is older than the app, and nothing is running there — nothing rendering, waiting in line, waiting on the user's answer, or finished and not yet collected — it updates that part by itself. **Otherwise it waits, and the server says so**; it tries again every time it connects, and while it stays connected it updates once the last job there ends. **The user can have it updated anyway, and is told first what that does**: every job on that server is stopped and cleared first, exactly as when a server is removed with *stop and clear*, because replacing that part while a job renders would end the render. **A server whose part is too old or too new for this app to work with is told as that, never as a server that is not answering**, and the user is told what to do: for one too new, update the app; for one too old with jobs still on it, those jobs cannot be stopped from the app, so it waits for them to finish. **What this costs is stated rather than hidden:** on a server too old to work with, a job left waiting on an answer holds the update until it is answered on Telegram, where Telegram is switched on, and for good where it is not. What the user is shown is Design's. *(No auditor has seen this paragraph.)*
- **Anything that isn't instant shows that it's underway.** Whenever the user triggers something that takes a noticeable moment, Smoozy shows that it is happening — it never sits there looking as though the click did nothing. This applies wherever it is true, not only where a module's spec remembers to say so. Label: **Creator-stated** (2026-07-20).
- **Do what can be done, and say what can't.** When Smoozy can carry out part of what the user asked but not all of it, it does the part it can and tells the user plainly what it could not do. It does not abandon the whole action because one piece of it failed, and it does not stay quiet about the piece that failed. Label: **Creator-stated** (2026-07-20).
- **Smoozy carries the user across the step it hands them.** Renting a machine is the user's own step, done outside the app, because Smoozy knows no providers: they rent it somewhere, give it their public key, and come back with a host, a port and a username. Smoozy does not leave them to work that out on their own. **Whenever the server list is empty**, it lays out what to do and in what order — make a key or use one already there, copy its public half, go to a provider and give it that public key where the provider's own pages ask for it, rent a Linux machine — an **Ubuntu or Debian** one, which is what Smoozy can prepare — and come back with the details the Add Server dialog asks for. The key goes to the provider **before** the machine is rented, because that is how the providers the Creator has used are arranged: the machine is handed the key as it is created. Label: **Creator-stated** (2026-07-27). The trigger is the empty list rather than a first launch, and deliberately so: the user may already have keys from something else, which would make a true first run look like a return; and the first time through is the only time all of it is new, since afterwards the provider already holds the key and renting again is just rent and add. This is a promise the whole app makes, not a module of its own — the pieces belong to **Keys** and **Servers**. Label: **Creator-stated** (2026-07-27). Label: **settled at Design** (2026-08-23) — it fills the empty server list itself, as five numbered steps, and stays reachable from the Add Server dialog, which is the one place it is wanted a second time.
- **Smoozy can tell the user something while they are not looking at it.** Every module's promises are written as *when the user next looks*, and nobody watches a six-hour render. So four things reach out through the **operating system's own notifications**, which is what can reach a user who is working in Blender: a **job finishing**, a **job failing or being abandoned**, a **connection Smoozy opened and could not restore**, and a **server idle for half an hour** — which the [Queue & History spec](Queue%20&%20History.md) owns and states in full. *Words changed 2026-10-28 (was *a job failing or being given up … a machine that has had nothing to do for half an hour*): Creator-stated, the final words sweep. No auditor has seen it.* Each kind can be switched off in Settings. Label: **Creator-stated** (2026-07-27).

  **A job the user stopped is not among them, and that is decided rather than overlooked.** All four are things that happen with nobody watching. A stop is the user's own act, made with Smoozy open in front of them and needing a live connection to send at all, so they already know it happened.

  What bounds this is the explicit-connect model (see the [Servers spec](Servers.md)): Smoozy learns what happened on a machine only while it is open and connected. A notification therefore reaches the user while Smoozy is running behind their work, and never once they have quit it or shut the laptop. That gap is not closed here — it is what **Telegram** is for, and the [Telegram spec](Telegram.md) closes it: the bot runs on the rented machine rather than inside Smoozy, so the machine reports on itself with the app closed and the laptop shut.

  Three things follow. A notification is for something happening **now**, so a connection catching up on what happened while Smoozy was away produces the catch-up notice the [Queue & History spec](Queue%20&%20History.md) already describes, not a burst of notifications about hours-old events. **A batch of scene-jobs speaks once**, when the whole batch is done, while a job that fails still speaks for itself. And a finished-job notification **carries that job's frame preview** where the job has one, since that is the picture that says the render happened — which is all the preview says, as the [Queue & History spec](Queue%20&%20History.md) owns and states in full.

  Label: **settled at Design** (2026-08-23) — each says the thing and stops, clicking one opens what it is about, and the four switches are one per kind in Settings.
- **The ordinary run through the whole product** is set out below, under [The journey, end to end](#the-journey-end-to-end).
- **A lost connection is a fact about the connection, never a verdict on the machine.** Smoozy cannot tell a network problem from a machine that was switched off from a machine that no longer exists — all three look the same to it. So it never claims to know which it is. When a connection drops and Smoozy cannot restore it, what it says is what it knows: it could not reconnect. *Words changed 2026-10-28 (was *the connection is down and could not be restored*): Creator-stated, the final words sweep. No auditor has seen it.* It does not tell the user to try again or to check their network. The user may know exactly what happened to that machine, and being pointed at their own connection would be wrong. Whatever the user can do about it stays available, and none of it is put forward as the fix.
- **How a failure reaches the user.** Things go wrong all over Smoozy — a connection drops, an upload is refused, a render dies, a file will not come home. Every module's spec says Smoozy "says so" and leaves the *how* here, so that a failure reads the same way wherever it came from. Four rules, all Creator-stated (2026-07-27):

  **It appears on the thing that failed.** The server row, the transfer, the queue entry — whatever the user was looking at when they asked for it. Smoozy does not interrupt with a box in the middle of the screen, with one exception: where the user is standing there waiting on the answer, the answer is where they are waiting. There is no separate place failures are collected instead; the thing that failed is where its failure lives.

  **One exception was granted to that on 2026-08-24, and it is the only one.** After a run of Smoozy that crashed, Smoozy says so at the next launch and offers to report it. A run that died yesterday is not a thing on any screen, so the rule above refuses it twice over — a box the user was not standing there waiting on, and a failure surfacing somewhere other than where it happened. It reaches no further than that: the previous run's crash, at the next launch, and nothing else. [Reporting a problem](Reporting%20a%20problem.md) holds the grant and what it costs. Label: **Creator-stated** (2026-08-24).

  **It stays until the user is done with it.** Nobody is watching a six-hour render, and a failure that clears itself is a failure the user never sees. So it stays on the thing that failed until they clear it, or until that thing is gone — a server removed, a history entry deleted. Nothing about knowing what went wrong depends on having been at the screen when it happened. What reaches a user who is away from Smoozy entirely is the notification settled above, and that does not replace the mark left behind. **One more thing ends it: the condition the message describes plainly ending** — the connection restored, however it came back, whether the user connected again or Smoozy's own repair succeeded (see the [Servers spec](Servers.md)); the folder that could not be written to taking files again. The message goes then, because the reason for keeping it has been served: the user has already seen it and acted on it. Leaving it would have Smoozy saying the connection is down on a server that reads as connected — the app being wrong on screen about its own state, which is never past the line. **That covers a message about a condition that is still live, and never a job's recorded ending.** A failed job stays failed however the machine's state changes afterwards: freeing the disk does not put the frames back that were never rendered, so the reason for keeping the record has not been served at all.

  **It says what to do only where Smoozy knows.** Where the cause is genuinely known — the folder files are landing in is full, or cannot be written to — Smoozy says the thing to do about it. Where it would be guessing, it says what happened and stops there. This is the general form of the connection rule below, which is the case where guessing is most tempting: three quite different things look identical to Smoozy, so it names none of them. A Blender render that dies is the same shape — Smoozy shows the reason the machine gave and does not diagnose it (see the [Queue & History spec](Queue%20&%20History.md)); what the user does next is a new job, which belongs to **Rendering**.

  **One render failure is carved out of that, because its cause is one Smoozy can read off the machine rather than guess at.** Where Smoozy can read how much room is left on the machine and there is none, the failure says the disk is full and says to free space — **alongside** the machine's own words rather than instead of them. Reading a machine's free space is the [File Browser spec](File%20Browser.md)'s to promise, and this reaches no further than that reading does. Every other render failure stays as above: the reason the machine gave, and no diagnosis.

  **And a full disk does not always come out as a failure, so it does not always reach any of this.** Where the disk fills under one of the several files a frame writes, the render carries on to its last frame and ends at a **successful** status. Where that write had already begun, a part-written file is left and Blender prints its ordinary saved line for it as though it had been written in full; where the write was refused before it started, nothing is left, or on Linux a file of zero bytes. Label: **observed** (the same in all four versions, on both machines) — see [What a job writes](What%20a%20job%20writes.md), which owns the fact. Nothing here fires, because nothing failed as far as the machine is concerned. **What shows it is a line naming the path in what the machine printed**, which the user can open under the last rule above — [Download](Download.md)'s count of arrivals catches neither shape here, since the part-written file is present and Smoozy cannot tell it from a finished one, and on Linux a refused write leaves a file of zero bytes rather than no file at all. Smoozy does not pretend to have caught it any other way.

  **Where the disk fills under the scene's own output, it can go either way.** A job with a frame still to come ends at a **failing** status, and everything above fires as written, the disk-full carve-out included. A job whose last frame is the one that ran out of room ends at a **successful** status over a picture that is not whole, left under the name a finished frame would carry — so nothing fires there either, and whether such a run says anything about the disk beside its saved line is not established, so even the printed line the case above leans on cannot be counted on here. Label: **observed** (the failing case in all four versions on both machines, the successful one in all four versions on a rented Linux machine), and **unresolved** for what such a run prints about the disk — see [What a job writes](What%20a%20job%20writes.md), which owns all of it. Smoozy does not pretend to have caught that second case.

  **It is a plain sentence first, with the machine's own words behind it.** What the user meets is one sentence in ordinary language saying what did not happen. The raw output — Blender's, or whatever the machine said — is there to open when they want it, and never the first thing in front of them.

  **And where there are no words behind it, that is said rather than shown as a blank.** A render can end having said nothing about why it ended: the machine's own memory running out kills Blender 4.5 and 5.0 outright, leaving **the error stream** empty and writing no crash file, while the ordinary stream runs on to a sampling line and then stops; 5.1 and 5.2 say so and stop. **So the user meets an entry showing the ordinary stream's words and an empty complaints panel**, which is the case this rule is for. Label: **observed** (all four versions, on one rented Linux machine) — see the [Queue & History spec](Queue%20&%20History.md), which owns the fact and the ending. So on half the supported versions the raw output this rule promises is empty, and **an empty panel is exactly what a broken Smoozy would look like**. The plain sentence therefore says the error stream is empty — and the ordinary stream's words sit beside it, saying nothing about why and never presented as if they did — rather than leaving the user to work out whether Smoozy failed to collect the words or there were none. *(Narrowed 2026-10-11, the Creator's eighth notes, note 6: it said the render ended without complaining and there is nothing further to read. That holds for the memory ending above and nowhere else — Blender 5 writes its errors to the ordinary stream, so an empty error stream does not mean the render reported none, and the sentence says only what is true of the stream it is about. Label: **observed in a test**, `Desktop app and delivery` M13.)* Smoozy does not fill the gap with a guess at the cause. **The ending itself is never read from what was printed**: a job that stops with nothing to read is failed, not still rendering. Label: **Creator-stated** (2026-08-12).

  **And a failure carries a way to tell the Creator about it.** Added 2026-08-25, after the four rules above and not one of them. Beside the machine's own words, the user can send the Creator what happened, from where the failure sits — because they are already looking at the thing that went wrong, and that is the moment they care about it. [Reporting a problem](Reporting%20a%20problem.md) owns it, including what a failure collapsed onto a single line of a list can carry. Label: **Creator-stated** (2026-08-25).

  One thing follows for a failure that will keep happening for the same reason, such as every file in a job failing to land in a folder that is full: it is said **once**, not once per file. Smoozy does not repeat one fact a hundred times. Whether the arrangement that keeps hitting it also switches itself off is the owning module's to settle, not this concern's.

  Label: **settled at Design** (2026-08-23) — one shape wherever a failure attaches, cleared only where it describes something still true, with the machine's own words behind one control that names whose words they are.
- **What the Creator learns when a user hits a bug.** Every rule above says what the *user* is told; none of them says what reaches the person who could fix it. So Smoozy keeps a running record of its own acts on the user's own computer, and the user can hand a slice of it to the Creator by attaching it to their own mail. **Smoozy never sends anything itself, and there is no telemetry in this app.** It belongs to no module and has three things to settle rather than one — what Smoozy keeps, what a report is made of, and when Smoozy offers to make one — so it is settled in its own document: [Reporting a problem](Reporting%20a%20problem.md). Label: **Creator-stated** (2026-08-24).
- **Security.** Smoozy holds a handful of things worth protecting. What it promises about them is settled here; the detail of each belongs to the module that owns it, and nothing below is a second copy of what those documents say.

  **Everything of the user’s stays with the user.** Smoozy has no account, no registration and no email anywhere in it. It keeps no record of the user away from their own computer or their rented machines. There is no trial-and-slots exception.

  **An address to write to is not a second exception, and does not touch this.** From 2026-08-24 Smoozy names a mailbox of the Creator's, on screen, for a user who wants to report a bug. It holds no mailbox of the user's, asks for none, and sends nothing there itself — the user attaches a file and writes from their own mail account, which they opened and hold, so nothing of theirs goes anywhere Smoozy put it. *No email anywhere in it* is about what Smoozy holds for the user, and an address to write to is none of those things. Label: **Creator-stated** (2026-08-24). See [Reporting a problem](Reporting%20a%20problem.md).

  **What Smoozy holds, and where each thing lives.** Five things, and each is one document’s:

  - The **private half of an SSH key** — which Smoozy never copies, never moves, and never sends anywhere. It stays where the operating system keeps keys, or where the user pointed Smoozy at it. **Keys works only on the user's own computer and never talks to a server at all**, so the private half has nowhere to go; what reaches a provider is the public half, carried there by the user's own hand. See the [Keys spec](Keys.md).
  - A **key's passphrase**. Smoozy remembers one as soon as it is entered and keeps it until the user clears it — there is no choice at the moment of entering, deliberately, which is [Keys](Keys.md)' rule and not this concern's. See the [Keys spec](Keys.md), which also owns what a remembered passphrase belongs to. **On macOS and Linux only**: on Windows Smoozy cannot use a key with a passphrase, so it has none to remember. *(Qualifier added 2026-10-16, out of the `Keys` code round 1, matching the Keys spec's own of 2026-09-03. No auditor has seen this change.)*
  - A **machine's password**, where the user let Smoozy remember one — the rule below.
  - The **Telegram bot's token**, which is the whole of what lets anything speak as that bot. See the [Telegram spec](Telegram.md).
  - Each **machine's remembered identity**. See the [Servers spec](Servers.md).

  How each of those is kept safely is **Architecture's**, and it is one question rather than five. Where the answer costs the user anything — a place to look, something to type, a thing that can be lost — that comes back to Specs. **It came back**, and what follows is the answer.

  **Every operating system charges something for remembering, and the three charge differently.** There is no arrangement on any of them where Smoozy remembers a secret and the user meets nothing, so the question was never whether to pay but what to pay with. Label: **Creator-stated** (2026-08-16). This covers all five things above, not the machine password alone.

  - **On a Mac, Smoozy remembers**, in the place the system already keeps such things. Two things follow and the user meets both. After the user updates their system, after Smoozy updates itself, or if Smoozy has been changed on the computer, the system may put up a dialog of its own asking whether Smoozy may still read what it remembered; the user says yes, and that is the system asking rather than Smoozy. It does not happen every time. Label: **documented** — those are the three occasions Apple's own page names, and the same page says the asking is sometimes rather than always. And if the user resets their login password, everything remembered is gone — Smoozy asks for it all again as though it were new, and nothing else is lost.
  - **On Windows, Smoozy remembers and the user meets nothing** — nothing to grant, nothing to type, nothing to lose. What is given up is not on the screen: any other program running as that same user can read what Smoozy remembered. That system offers no way to prevent it, and Smoozy does not claim to.
  - **On Linux, Smoozy remembers where the computer has somewhere to remember**, which depends on what the user has installed. **Where there is nowhere, Smoozy does not pretend to remember**: it asks each time it needs the secret, and it says so once, so the user knows it is not going to learn rather than thinking it keeps forgetting. On some computers the place to remember will itself ask the user for a password before it hands anything over, which is that computer's own arrangement and not Smoozy's.

  **Windows and Linux rest on those systems' own documentation rather than on anything anyone has run**, because nobody has run it on either. A Windows machine can be rented; none has been used for this. If either behaves otherwise, this promise is what has to change.

  Label: **settled at Design** (2026-08-23) — a system's own question is the system's and Smoozy draws none of it; what Smoozy draws is the answer being no, which is the ordinary ask again with a line saying why. Where the computer has nowhere to keep a password there are no choices to offer, and one sentence takes their place.

  **Smoozy asks for a machine's password only where a step actually needs one, and never before.** A connection is made with a key, so nothing about adding or connecting to a server ever asks for a password. What can ask is any step the login Smoozy connected with is not permitted to carry out — reading a folder in the [File Browser](File%20Browser.md), or writing, deleting or renaming there, or installing what a machine needs in [Server Setup](Server%20Setup.md). Smoozy offers to try again with elevated access, the user says yes, and that is the moment it asks. Label: **Creator-stated** (2026-08-10).

  **The user chooses how long Smoozy keeps it, out of three.** Label: **Creator-stated** (2026-08-10).

  - **Don't save.** Smoozy uses it for that one action and keeps nothing. The next step that needs it asks again.
  - **While connected.** Smoozy holds it until the connection to that server ends, however it ends — the user disconnecting, the connection dropping, or the app closing. A long setup asks once rather than at every step, and nothing survives the sitting.
  - **Save.** Smoozy holds it against that server the way [Keys](Keys.md) holds a passphrase against a key. *Words changed 2026-10-28 (was *Do not remember it.*, *Remember it while this connection lasts.*, *Remember it.*): Creator-stated, the final words sweep. No auditor has seen it.*

  Three things follow, and each matches how a passphrase already behaves. **A remembered password belongs to the server, not to the key** — a key used by three servers is one key with three logins behind it, so it is cleared where the server is edited rather than anywhere near Keys, and it goes when the server is removed. **A password that stops working is forgotten rather than retried**, so a machine whose login changed asks the user again instead of failing quietly against something stale. And **Smoozy never asks speculatively** to make a later step smoother: no step, no question.

  Label: **settled at Design** (2026-08-23) — one dialog naming the step that was refused, with the three choices under the field. **How a remembered one is cleared is the [Servers spec](Servers.md)'s Edit dialog** and is tracked in that screen's own Design document.

  **A machine's identity is trusted silently the first time and is never shown to the user.** That policy, what it buys, what it gives up, and what happens when an identity changes are all the [Servers spec](Servers.md)'s, and it is named here because it is the one place this concern and that one describe the same ground. The two agree: Smoozy shows no fingerprint anywhere, at a first connection or at a changed one, because the identity means nothing to a 3D artist and a screen nobody can act on is worse than no screen.

  **None of this claims to be unbreakable.** Somebody with full control of their own computer is past what an app can guarantee. Smoozy still takes the precautions above and promises no more than it can keep.

## The journey, end to end

The ordinary run through Smoozy, from downloading it to throwing the machine away. It is the fuller version of the walkthrough in the [Product brief](Product%20brief.md), and its job is the **order and the joins** — each step is settled in the module that owns it, and is linked rather than restated. Where a module has no spec yet, only what is already settled appears, and what is still owed is marked.

The shape it follows is the Creator's own way of working: a machine is rented for one project, used until that project is done, and destroyed. It is sometimes kept a day or two in case a small change needs re-rendering. Several machines at once, for several projects, happens but is rare — rendering comes at the end of a project's life, and the farm is not wanted afterwards. Label: **Creator-stated** (2026-07-21).

**1. Getting the app.** The user downloads a binary from Smoozy's website. No email, no account, no registration. From then on Smoozy keeps itself up to date, so this is the only trip to the website.

**2. First launch.** Smoozy opens on the empty server list described in step 3, with no entry screen, trial or licence key.

**3. An empty list, and what to do about it.** The server list is empty, so Smoozy lays out what to do and in what order — the promise stated above under the whole-app concerns. This is the only point in the journey where every part of it is new: afterwards the provider already holds a key, and renting again is just rent and add.

**4. A key.** The user makes an [SSH](../Groundwork/Glossary.md) key in **Keys** and copies its public half. Smoozy suggests naming it after the provider it is for, because that name is what the user later picks between in the Add Server dialog. A key can carry a passphrase or not; if the user sets one here, Smoozy remembers it from that moment and does not ask again at the first connection; a key made outside Smoozy is asked for at the first connection and remembered from then on. See the [Keys spec](Keys.md).

**5. Renting the machine.** The user leaves Smoozy and goes to a provider's own pages. They paste the public half of the key wherever that provider asks for it, and **then** rent a Linux machine — an **Ubuntu or Debian** one, which is what Smoozy can prepare — which is handed the key as it is created. This step is theirs: Smoozy knows servers and keys, never providers, and never rents, bills, or powers anything. They come back with a host, a port and a username. That the key goes in before the machine is rented is how the providers the Creator has used are arranged. Label: **Creator-stated** (2026-07-27).

**6. Adding the server.** Those details go into the Add Server dialog, along with which key to use, and optionally two setup choices — get the machine itself ready to render, and install Blender. A plain add saves the details and reaches nothing; ticking either connects straight away to carry it out. See the [Servers spec](Servers.md).

**7. The first connection.** Connecting is always something the user asks for. Smoozy records the machine's identity and trusts it silently this once, asks for the key's passphrase if there is one and Keys is not already holding it, and checks that the machine is Linux — refusing plainly if it is not, since nothing after this point would work there. Once connected, the server list shows what the machine has to render with.

**8. Making it render-ready.** **Server Setup** gets the machine to the point where it can render: Blender itself, one or more versions side by side, and whatever else a bare machine needs. What that is, and what is still owed of the answer, belongs to that module and is stated there. A Blender comes either from a list Smoozy offers of what Blender publishes, or as a build the user points at on their own computer. The two options in the Add Server dialog are a front door to this, and Server Setup itself offers the fuller choice, including taking a version off again. Where a setup step needs the machine restarted, Smoozy restarts it. See the [Server Setup spec](Server%20Setup.md).

**9. Uploading the work.** Through the **File Browser** the user sends up the `.blend` and whatever else it needs. Nothing already sent crosses the wire again, and a file arrives whole and correct or plainly not there. Sending tens of gigabytes can take a home connection over, so the user can cap how fast Smoozy uses it. See the [File Browser spec](File%20Browser.md).

**10. Settling the render.** Clicking the `.blend` opens **Render Settings**. Every setting starts at the file's own value, so the user only ever states the differences — leave it all alone and the file renders as the artist saved it. **Pre-load Settings** is the separate action that reads the file and shows what those values actually are. The user picks one scene or all of them, sets the frame range and the rest, and chooses which of the machine's Blender versions renders it. Reading the file finds one add-on case and only one — a file naming an engine the chosen Blender lacks — because a `.blend` keeps no record of the add-ons it needs. The rest is Smoozy's own guess rather than anything read out of the file, and it is met on the same page: Smoozy offers to supply the ones it can, and hands back the ones the artist has to sort out themselves. See the [Server Setup spec](Server%20Setup.md), which owns the guess. It shows them where the job's outputs will go and how many there will be — a `.blend` can write files to places of its own choosing, and Smoozy brings all of it under one folder for the job. See the [Render Settings spec](Render%20Settings.md) and [What a job writes](What%20a%20job%20writes.md).

**11. The assets that are not there.** Checking the `.blend` for what it is missing is its own action, which the user takes — separate from reading its settings, and no part of Pre-load Settings. *(Withdrawn 2026-10-13: the change of 2026-10-12, that either read starts the other, was taken back the next day because the Creator deferred the request (the ninth notes, note 4). The idea is parked in Open Threads.)* Where pieces are missing, **Dependency Upload & Remap** finds them on the user's computer, sends them up, and points the file at the copies that arrived. Smoozy proposes and the user can override every match, because a file name identifies nothing on its own. Heavy assets go up once and stay, so a later change re-renders by sending only the `.blend` again — and the artist's own file is read, never written to. See the [Dependency Upload & Remap spec](Dependency%20Upload%20&%20Remap.md).

**12. Sending it to render.** Submitting is **Rendering**'s action, and it is normally where auto-download is switched on, so the outputs come home as they are written rather than after the job ends. Smoozy warns here if nobody ever checked the file for the assets it is missing, since other render farms require a file to be packed and Smoozy deliberately does not. Asking for every scene submits several jobs in one act, and whatever reaches the machine stays even if the connection falls over part-way. See the [Rendering spec](Rendering.md).

**13. Waiting.** The job joins the queue, which lives on the machine rather than inside Smoozy, so it keeps going when the app is closed. Each machine renders one job at a time with all its GPUs on it, and every job is exactly one scene. The entry says what it is doing, how far it has got, what it is using, and shows a picture of what came out. Nobody watches a six-hour render, so the operating system's notifications carry the ending, a failure, a connection Smoozy could not restore, and a server idle for half an hour. *Words changed 2026-10-28 (was *a machine that has had nothing to do for half an hour*): Creator-stated, the final words sweep. No auditor has seen it.* Those reach the user only while Smoozy is running; once the laptop is shut, **Telegram** is what keeps them in touch — switched on once, with a bot made in about a minute and reused for every machine ever after. The machine itself sends progress, frames as they land and the ending to their phone, and takes back a handful of instructions, chief among them stopping a render that has plainly gone wrong. See the [Queue & History spec](Queue%20&%20History.md) and the [Telegram spec](Telegram.md).

**14. Bringing the work home.** Where auto-download was switched on, the outputs arrive as they are made. Anything else the user picks out by hand. Local files are never silently overwritten. See the [Download spec](Download.md).

**15. The ending.** The project is done and the machine is not wanted. The user destroys it at the provider and removes the server from Smoozy — in **either order**, and both happen. Removing while connected offers to stop and clear whatever is still on it; removing a machine that is already gone is just an entry leaving a list. What was rendered stays: history is Smoozy's own record on the user's computer, and it survives both the removal and the machine.

**16. The next time.** A week later the same client asks for a change. The provider still holds the key, so the user rents a machine, adds it, and starts again from step 6 — the files go up afresh, because Smoozy never moves files between two servers and keeps nothing of a machine but the record of what it rendered.

**Where the change is to a job that already ran, there is a shorter way through step 10.** History outlived the machine, so the user submits that job again from its entry and its whole setup comes back instead of being entered a second time. The order is the same as for any other job all the same: the `.blend` and its assets go up first, since the new machine holds nothing and submitting starts no transfer, and the settings page holds the old setup while that is done. See the [Rendering spec](Rendering.md), which owns the action.
