# Telegram

*What the Telegram module does, in plain terms: how the user follows and drives their renders from a phone. Not one word about how it's built.*

*2026-10-27 — Removed the withdrawn paid-access text and its obsolete references under the Creator’s free-and-open-source decision of 2026-10-04 (wave 5); retained protections and evidence keep their force. No auditor has seen this removal.*

## Where Telegram fits

Every other module writes its promises as *when the user next looks*, and nobody watches a six-hour render. The [module map](Whole%20app.md) settles that four things reach out through the operating system's own notifications — but those only reach somebody whose computer is on with Smoozy running. Telegram is what reaches them once Smoozy is closed.

**The bot runs on the rented machine, not inside Smoozy.** That is the whole point of the module. A bot inside the desktop app could only send messages while the app was open, which is exactly when the user does not need it. Because it sits on the machine, the render still reports and still takes instructions with Smoozy closed and the user's computer switched off.

**It is a remote control, not a second app.** Every **action** the bot offers is one the app already has: there is nothing the user can do from a phone that they cannot do at the desk. What the bot **shows** is not held to that line — it sends a few seconds of moving picture and a contact sheet at the end of a job, and the app shows neither. That is a difference in form, not in power: both are made from what the app already knows about the job, arranged for a small screen. The limit is deliberate, and it is about actions because that is where the cost is: a bot with actions of its own would be a second product to keep in step with the first, and the two would drift. A picture arranged differently adds nothing to keep in step.

**Connections.** The [module map](Whole%20app.md) owns how Telegram is wired to the app. It leans on **Queue & History** for the job’s state and ending and for when a machine has nothing to do; on **Rendering** for stopping and resubmitting jobs; on [What a job writes](What%20a%20job%20writes.md) for previews; and on **Server Setup** for putting its piece on a machine. Setup uses a connection already opened by the user; Telegram asks for none. The bot sends and receives from the machine itself, whether or not Smoozy is running.

**It fits the explicit-connect model.** The [Servers spec](Servers.md) settles that Smoozy reaches a machine only when the user asks, and that two things carry on without a further word from them: work they already asked for, and repair of a connection they opened. Nothing here breaks that. Smoozy itself still connects only when asked. What the bot does is carry out what the user asks *from their phone* — the user is the one acting, at the moment they act — and what it reports is work they already asked for. Turning Telegram on is itself the asking.

## The bot

**The user makes one bot, once, and never again.** Telegram bots are made by talking to Telegram's own bot-making chat, which asks for two names — a friendly one and a unique one — and hands back a token. Label: **Creator-stated** (2026-08-12), from making one *(see [Sources](Sources/Telegram.sources.md))*. That is a minute of work and Smoozy takes every decision out of it: it offers both names ready to copy, gives another unique name on a tap if the first is taken, takes whatever the user pastes and finds the token inside it rather than making them pick it out, and checks the bot answers before moving on. Then it shows a link to the new bot — a link of that kind does open a chat with it directly, Label: **observed in a test** (2026-08-12) — the user presses Start, which the bot needs before it can be messaged at all, and Smoozy says hello back so they know it worked.

**Smoozy tells the user to do this on the computer if it can.** The bot is made in a chat, so with Telegram open on the same computer the whole thing is copying and pasting. From a phone alone, a long token has to be carried across by hand, which is slow and easy to get wrong. Saying so at the start saves the user finding out halfway through.

**The bot belongs to Smoozy, not to a machine.** The bot itself is Smoozy's, so removing a server never costs the user the bot: it is free for the next machine, and the same one is used again. Renting a machine, using it for a project and destroying it — the ordinary way this product is used — costs nothing here, and the user is never asked to make a second bot.

**The piece on the machine is a separate thing.** Where a removal reaches the machine, Smoozy takes that piece off with it. Where it does not — the machine is not connected, or the removal was the kind that leaves the machine alone — the piece and the token stay on it, and that machine can go on sending messages until the user destroys it. Smoozy never reaches out to a machine it was not asked to reach, so there is nothing else it could do. Which of those a removal is belongs to the [Servers spec](Servers.md).

**One bot serves every machine at once.** All of them talk in the same conversation, and every one of them can be driven from it. **The two facts this rests on were tested on three machines holding one token, and both hold**: every machine can send, only one can receive at a time, and a machine that is not receiving can still read a shared note without disturbing the one that is. Label: **observed in a test** (2026-08-12) *(see [Sources](Sources/Telegram.sources.md))*. How several machines share one bot between them is still Architecture's, and it is genuinely awkward — the same tests showed that machines all listening at once knock each other off until almost nobody is listening, and that a shared note can lose an instruction. Both are recorded in [Sources](Sources/Telegram.sources.md) and parked in [Open Threads](../Groundwork/Open%20Threads.md). What matters at this stage is unchanged: the user never meets any of it, and they make one bot that covers however many machines they run.

**Every message says which machine and which job it is about.** With one machine that is a formality; with three it is what makes one conversation readable. A machine is named by the label the user gave its server, which **Servers** owns.

**The bot answers one conversation and nobody else.** Smoozy proves that the conversation belongs to the user before the bot answers anything in it, and anything arriving from any other conversation is ignored rather than answered. Whoever holds the token can act as the bot, so the token is a secret Smoozy keeps in the same spirit as an SSH key passphrase. How the proof is done, and how the token is kept, are both Architecture's, where they meet the whole-app security concern. **The proof is that the user made the bot.** The conversation the user starts the bot from during setup is the user's, because they created the bot, they hold its token, and they are the one who started it. Smoozy remembers that conversation and answers no other — anything arriving from anywhere else, or from a conversation it cannot place, is ignored rather than answered, since answering would tell a stranger the bot is alive. A replacement token for the same bot keeps that proof; a new bot needs a new one. **The token is kept as one of the secrets the whole-app concern covers**, on the user's computer and on every machine the piece was put on. The copy on the user's computer is erased when the token is replaced or a different bot is set up, and not when Telegram is switched off, so turning Telegram on again uses the same bot. *(Changed 2026-10-31; it said the copy was also erased when Telegram was switched off, so one off and on asked the user to revoke the token, paste a new one and reconnect every server. The Creator, the fifteenth notes, note 1: "when I turned it back on immediately, all the information about the old bot was lost … Needs fixing." Ruled by the build runner on 2026-10-31 under the standing delegation. No auditor has seen it.)* Neither of those reaches a machine: a machine's copy goes only with a removal that reaches that machine and takes the piece off it, and where no removal does, the token stays on the machine and it can go on sending messages until the user destroys it — which is what this section says above of the piece. Label: **settled at Architecture** (2026-08-23).

**There is a way back if the bot or its token is lost.** A token can leak or be replaced, a bot can be deleted, and a Telegram account can be lost. None of those leaves the user stuck: Smoozy can be handed a replacement token for the same bot, or pointed at a new bot made the same way as the first. A machine Smoozy is connected to gets the new one at once, and any other on the next connection to it and not before, like everything else Smoozy tells a machine — so Smoozy says which machines it has not reached yet. *(Changed 2026-10-31 with* Telegram is off until the user turns it on*, below; it said every machine waited for its next connection. No auditor has seen it.)* Making one bot and never another is the ordinary run, not a promise that a second can never be made.

**Telegram is off until the user turns it on**, and turning it off stops the machines sending messages. Smoozy stops on its side at once: it offers nothing further from the phone and asks nothing further of a machine. A machine Smoozy is connected to at that moment is told at once and falls silent; any other falls silent the next time Smoozy connects to it, and not before, because nothing can be told to a machine Smoozy is not connected to, or while Smoozy is closed. So Smoozy says which machines it has not reached since Telegram was switched off, since any of those may still be sending. **Turning Telegram on again uses the bot already set up** and asks the user for nothing, where its token is still on the computer; the machines are told the same way. Where the switch lives is Design's. *(Changed 2026-10-31. It said every machine fell silent only at its next connection, which left three connected servers sending in the live Telegram pass of 2026-10-31 (its fault 11); and turning Telegram on again walked the user through setting up a bot from the start (the fifteenth notes, note 1, above). Ruled by the build runner the same day under the standing delegation. No auditor has seen it.)*

**A machine set up before Telegram was switched on sends nothing.** Its piece was never put there, and Smoozy cannot add it without being asked to reach the machine. **Server Setup** owns both ways that piece arrives — automatically, as part of the ordinary first setup of a machine added while Telegram is on; and, for a machine that was set up before that, through a small action of its own that adds the piece and does nothing else. See the [Server Setup spec](Server%20Setup.md), which owns both and states what each costs. Nothing is lost meanwhile: the machine renders exactly as it did, and the app tells the user everything it always did. **Render Settings says so where the choice is made, with the action there.** On a connected machine that does not have the piece, the page's Telegram line reads that it is not installed and offers to install it, in place of the choices, and Queue says the same of a job on it, so no job reads as if it will report. Where Smoozy cannot tell, it says nothing. *(Added 2026-11-03, the second 5.3 live pass: Settings read that Telegram was set up, a job's page offered* Everything*, and the chat stayed silent, with the one action on a card a user has no reason to open. The build runner's ruling. It is still an action the user takes: a connection is not asking for the piece, and the piece carries the token. No auditor has seen it.)*

**And *reachable behind it* means the user asks for them, because sending them is sending the user's own text to somebody else's servers.** What a render prints when it goes wrong carries the user's folder names, file paths, scene and project names, and whatever their own add-ons and scripts printed. **A machine waiting on the user.** Where a machine has stopped because it needs an answer — the first-frame check below is the only case — it says so, because that is money being spent while nothing renders, and the user is the only one who can clear it. *(Unless the job is set to Off, whose check is answered at the desk: see* Off, for one job*, below. **A machine with nothing to do.** A machine with nothing rendering and nothing waiting is idle, and after the wait [Queue & History](Queue%20&%20History.md) sets for it, the bot says so. ## What the user can do from the phone

Six things, and no more. Four of them are a tap on the message in front of the user, so nothing has to be typed and no machine has to be named. **A tap is only ever there where it would do something** — one of the four, trying a failed job again, is offered on some failures and not on others, for the reason given under it. The other two need the user to ask for something: *status*, which answers nothing in particular, and *send a frame*, where the user has to say which frame. *Words changed 2026-10-28 (was *how is it going*): Creator-stated, the final words sweep. No auditor has seen it.* How those two are asked for is Design's. *(Seven from 2026-10-31: the seventh is* One choice for every job, from the phone*, below. No auditor has seen it.)*

**What the user asks for, they ask with the bot's commands.** Typing `/` in the conversation lists the bot's commands, each with one line saying what it does, and Telegram's *Menu* button beside the message box lists the same. Picking one sends it. Nothing else stands under the message box: when nothing is happening there is nothing to do from the phone. Label: **Creator-stated** (2026-10-31): *"I know that bots in Telegram can suggest commands if you type a slash … Maybe we should leverage that actually?"*, then *"Okay, so slash it is."* That Telegram lists a bot's commands this way, with a line each, and that picking one sends it at once, is **documented** (Telegram's bot features page, read 2026-10-31) — see [Sources](Sources/Telegram.sources.md). The commands:

- **`/status`** — *Status*, below: one message covering every server.
- **`/frame`** — *Send a frame*, below. On its own it sends the newest finished frame; with a number, `/frame 120`, that frame. Where several jobs could answer, the bot asks *Which job?* with one button per job, as it always has; where one can, it sends.
- **`/reporting`** — *One choice for every job*, below.
- **`/stop`** — *Stop it now*, below. Where more than one job is rendering or waiting, on any server, the bot asks *Which job?* with one button per job; where one is, it goes straight to the question that asks to confirm the stop; where none is, it says so.

The words the user typed before still work: *status* and *frame 120*. *Added 2026-10-31, a want entering at Specs under Rule 7 (the Telegram discussion of that day). No auditor has seen it.*

**A command sent as a reply to a job's message is about that job**, so nothing has to be chosen. Label: **Creator-stated** (2026-10-31): *"Reply is for a job, no reply asks for what exactly, and reporting is for everything if it's not a reply."* `/frame` sends that job's newest finished frame, `/frame 120` its frame 120, and a reply to a picture of a frame sends that frame; `/stop` goes straight to the question that confirms the stop; `/reporting` changes that job alone and leaves the default for new jobs as it is. A server's own message is about the job it shows at that moment. `/status` covers every server whatever it replies to. A reply to a message about no job — the shared note, the bot's own answers, the user's own messages — works as if it were not a reply. Where the bot cannot tell which job a message is about, because its server is off, gone or has an older Smoozy, `/frame` works as if it were not a reply, and `/stop` and `/reporting` change nothing and say *Could not tell which job that message is about. Nothing changed.* *Words changed 2026-11-01 (was *Couldn't tell which job that message is about. Nothing was changed.*): Creator-stated, the second words sweep. No auditor has seen it.* On an ended job's message, `/stop` and `/reporting` say the job has already ended. *Added 2026-10-31, a want entering at Specs under Rule 7 (the Telegram discussion of that day, *Later the same day: replies*). No auditor has seen it.*

**Stop it now.** The most valuable of the lot. A preview comes through, the render is plainly wrong, and the user ends it there instead of paying for five more hours of nothing. It costs the frame in hand, which may be forty minutes in: a render stops when it is asked, the frame it was on is thrown away, and there is no way to let that frame finish first. Label: **observed** (the same in Blender 4.5, 5.0, 5.1 and 5.2) *(see [Sources](Sources/Telegram.sources.md))*. Ending a render is **Rendering**'s work, asked for from here — including which way the stop is sent, and whether anything is left where that frame should be. Both are settled in [Rendering](Rendering.md), and both matter to the re-run rather than to anything the phone shows.

**Go on, or don't.** The two answers to the first-frame check below. Saying no leaves nothing running and nothing waiting.

**Status.** The current state, on request. *Words changed 2026-10-28 (was *How is it going*): Creator-stated, the final words sweep. No auditor has seen it.* The machine's own message already carries it for one machine, so this earns its place mainly where several are running: one message covering all of them, rather than hunting through a conversation for each machine's own. **A server that does not answer is named as not answering once, then left out until it is heard from again.** Smoozy cannot tell a server that is off from one that is gone. *Added 2026-10-31, Creator-stated, the twenty-sixth notes, note 2: "/status … talks about servers that do not exist. They were once in Smoozy but now they are destroyed." Naming it once is the build runner's ruling. No auditor has seen it.*

**Send a frame.** A preview of any frame the job has finished, on request — for when somebody asks how the render is going and the user is away from their computer. A frame of more than one View Layer comes as the same named group *Frames as they arrive* sends. *Added 2026-10-18, Creator-stated, the fourteenth notes, note 7. No auditor has seen it.* Small copies only; a full-size render never goes to a phone, both because a phone is not where a frame is judged and because there is a limit on what a bot can send. **There are two limits**: a picture is capped at a little over ten megabytes, and it is capped on its dimensions besides. Label: **observed in a test** (2026-08-12) *(see [Sources](Sources/Telegram.sources.md))*. **A large frame is first made smaller; only a shape past Telegram's ratio, or a copy that still cannot fit, is refused.** *Corrected 2026-11-02, the build runner's word, from the 5.3 live pass: this said a large frame is refused for its shape before its weight, and a 4K frame's copy is within the shape limits and can be over the weight. No auditor has seen it.* So sending small copies is the only thing that works rather than a preference. Bringing a real file home is **Download**'s work and needs the computer.

**On a rendering job's own message, *Send a frame* sits beside *Stop this job*.** The server's message that keeps itself up to date offers it while its job renders and has a finished frame, and one tap sends that job's newest finished frame, so nothing has to be typed or named. *Added 2026-10-31: the build runner's take in the Telegram discussion of that day, not objected to by the Creator, and drawn for their look. No auditor has seen it.*

**Retry.** Offered on the message that says a job failed — and only where the failure was the machine's own. *Words changed 2026-10-28 (was *Try it again*): Creator-stated, the final words sweep. No auditor has seen it.* Everything about the failed job is known, so no form is needed to name it again, and the tap sends exactly the same job again, unchanged. **Where the machine went, the connection dropped, or something outside the file stopped the render**, sending the job again may clear the trouble, so the message offers the tap.

**Where the file itself is what failed, the message does not offer the tap at all.** An add-on that is not on the machine, an engine the machine cannot run, a setting the render will not accept — sending the same file again buys a second identical failure and a second bill. So instead of a tap, the message says the job needs a change before it can go again, and changing a job is work for the settings page at the desk rather than for a phone. **Where Smoozy cannot tell which of the two kinds a failure was, the tap is not offered either**, because offering it would be a guess made with the user's money.

Submitting again is **Rendering**'s action and this is that action reached from a phone; which failures the tap may act on is settled there — see the [Rendering spec](Rendering.md). *(Until 2026-09-02 this paragraph said what the tap sends was not settled and pointed at that module's open question. It is settled, and the ruling is carried here in full rather than pointed at, because what changes is what the user is offered.)* Label: **ruled 2026-09-02**.

**Send the machine's own words.** Offered on any message that says something went wrong and holds words behind it. The message says what happened and does not carry the words; one tap asks the machine that has them to send them. *What a machine tells the user* above says why they wait for the tap.

**One choice for every job, from the phone.** With many messages arriving, often a little late, working out which job reports what is hard on a phone, so from the phone the user makes one choice for everything. Label: **Creator-stated** (2026-10-31): *"changing the reporting behavior should be a global setting via Telegram specifically. Because with the torrent of messages (that often come with a slight lag) figuring out which job has what reporting mechanism can be cumbersome"*, and then *"The choice … should apply to everything and be the new default."* What it does:

- **`/reporting` offers the five choices as buttons**: *Everything*, *Pictures only*, *A picture every 5 minutes*, *Alerts only*, *Off*. Other minutes are typed: `/reporting 10` sets a picture every 10 minutes, whole minutes from 1 to 60, as at the desk; any other number is refused with the range.
- **It applies at once to every job waiting, waiting on the first frame, or rendering, on every server on this bot** *(sent as a reply to a job's message, to that job alone: see* A command sent as a reply*, above; added 2026-10-31, no auditor has seen it)*, exactly as if each had been changed in the queue (*Changed while the job is in the queue*, above): it counts from the change, and a first-frame check and its range change together.
- **It becomes the default for new jobs.** Settings' default becomes this choice, minutes included, and Render Settings offers it to the next job. Smoozy on the computer learns it the next time it connects to any server that heard it, and the queue then shows each job's new choice.
- **The reply says what was set and for whom**: *Reporting set to “Alerts only” for every job and new jobs.* *Words changed 2026-11-01 (was *Reporting set to Alerts only for every job and for new jobs.*): Creator-stated, the second words sweep. No auditor has seen it.* Where a server did not answer, the reply names it, and its jobs keep what they had. Where a server's Smoozy is too old for this, the reply names it and says it needs updating.
- **A server that is off when the choice is made does not hear it**, and when it comes back its jobs keep what they had; the bot cannot name a server it has not heard from. Sending the choice again reaches it.
- **A job submitted from a computer that has not yet heard** carries the choice that computer showed; the next choice from the phone, or the queue, changes it.
- **Choosing at the desk afterwards wins**, until the next choice from the phone. The queue keeps its own control for one job, and Settings keeps the default.

Sending a preview on to somebody else needs nothing from Smoozy: it is an ordinary Telegram message, and forwarding it is the user's own business.

## The first-frame check

**The user can ask to see the first frame before the rest of a job runs.** It catches a wrong camera, or a missing texture that was feeding colour — the same promise the frame pictures above carry, with the same limits — after one frame rather than after six hours and one paid night. It is asked for at the moment the job is submitted — see the [Rendering spec](Rendering.md). One frame comes back, the user looks at it on their phone, and taps go on or stop.

**It is a picture check and stays one.** What the research narrowed is real: only a missing texture that was feeding colour shows, so a missing bump, displacement, normal, mask or volume map renders a plausible frame, exits successfully, and on Blender 4.5 under Cycles prints nothing either. **The check is not made to carry more than a picture, on the Creator's ruling of 2026-08-12.** Sending the machine's own account of what a file is missing alongside the frame would be a different feature — it is a reading of the file rather than a look at the output, it would belong to **Rendering** and **Queue & History** rather than here, and it would make a check the user asked for as a quick look into something that answers for the whole file. What this check promises is what a person can see in one frame, and that is stated rather than dressed up. Label: **Creator-stated** (2026-08-12).

**It is two jobs, not a pause.** A render cannot be held part-way and picked up where it left off; carrying on means a fresh render of the frames that are left. Label: **documented** (the same in Blender 4.5, 5.0, 5.1 and 5.2) *(see [Sources](Sources/Telegram.sources.md))*. So asking for the check submits the first frame as its own job, and the whole range, its first frame included, as a second job that waits for the user's yes. The cost is that the second job starts Blender afresh and renders the first frame again, which is nothing against the hours it protects. *Corrected 2026-10-02, Creator-stated: the second job used to be the rest of the range — see the [Rendering spec](Rendering.md).*

**The queue carries on while the user decides.** The waiting job does not hold the machine up: whatever else is queued runs, and the approved job takes the next free place in the line when the answer comes. A machine only stands still if that job was the only thing it had — which is the one case where the *needs your answer* message above is worth sending. *Words changed 2026-10-28 (was *waiting on you*): Creator-stated, the final words sweep. No auditor has seen it.*

**A first frame that never arrives ends the whole thing.** Where the first-frame job fails, or the user stops it, there is nothing to look at, so the job waiting on that look is dropped and the user is told why. That is the check doing its job, and it leaves what saying no leaves: nothing running and nothing waiting. Waiting with no time limit, and being dropped, are both **Queue & History**'s — see the [Queue & History spec](Queue%20&%20History.md).

**Asking for every scene checks every scene.** Each scene is its own job with its own camera, so each gets its own first frame and its own answer. That is **Rendering**'s, since that is where one act becomes several jobs — see the [Rendering spec](Rendering.md).

**The approval lives in the queue, not in Telegram.** The waiting job sits in the queue marked as needing the user's yes, and can be answered at the desk exactly as it can from a phone. That keeps this a feature of the product rather than a feature of the bot, which is the rule the whole module follows. The queue's side of it belongs to **Queue & History** and the submitting belongs to **Rendering**; what this module adds is only the tap.
