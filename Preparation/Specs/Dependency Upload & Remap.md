# Dependency Upload & Remap

*What the Dependency Upload & Remap module does, in plain terms: how the user finds out what a `.blend` is missing, how those pieces are found on their own computer and sent to the machine, and how the file is pointed at the copies that arrived. Not one word about how it's built.*

## Where this module fits

A `.blend` on its own is rarely enough to render. It points outward — at textures, at caches, at other `.blend` files — and those things sit on the artist's own computer. Put the file on a rented machine and every one of those references leads nowhere.

There are two ways to solve that. Other render farms require the file to be **packed**: everything it needs bundled inside the `.blend` before it is sent anywhere. Label: **Creator-stated** (2026-07-26) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). Smoozy deliberately does not work that way. The pieces go up **once and stay up**, and afterwards only the `.blend` itself is sent. That is what lets an artist change a light and re-render in a minute instead of sending every asset up again. Label: **Creator-stated** (2026-07-26). The cost of that choice is this module: the pieces have to actually be up there, and the file has to be pointed at them.

So this module owns three things end to end. **Checking** a `.blend` for what it points at and what of that is missing. **Finding** those pieces on the user's computer and sending them up. And **remapping** — pointing the file at the copies that arrived, which is the part nothing else in Smoozy does.

**Connections.** The [module map](Whole%20app.md) owns how this module is wired to the rest of the app. It needs the `.blend` chosen in **File Browser**, a connected server from **Servers**, and the files on the user's own computer. It depends on **Server Setup** having put a Blender on the machine, because reading the file happens there. It leaves the file render-ready for **Rendering**, and **Rendering**'s warning that nobody looked for a file's missing assets stops on the strength of this module's check — the rule is stated under *When the warning stops* below. It does **not** depend on **Render Settings**: checking a file for what it is missing is a separate action from reading its settings, and neither waits on the other. *(Withdrawn 2026-10-13: the change of 2026-10-12, that either read starts the other, was taken back the next day because the Creator deferred the request (the ninth notes, note 4). The idea is parked in Open Threads.)*

## Checking a file

**The check is something the user asks for.** Nothing runs it for them — not choosing the file, not reading its settings, and not submitting a render. Label: **Creator-stated** (2026-07-28). *(Withdrawn 2026-10-13: the change of 2026-10-12, that either read starts the other, was taken back the next day because the Creator deferred the request (the ninth notes, note 4). The idea is parked in Open Threads.)* **One exception: when an upload the check started ends with files arrived, the check runs again by itself**, so what the upload resolved is already shown. Label: **Creator-stated** (2026-10-17, the tenth notes, note 4). An upload the user stopped, or one a lost connection cut, does not start it, since nothing resumes on its own (below). *(That last sentence added the same day by the plan writer, from the map of the tenth notes and `Architecture/Dependency Upload & Remap` G14. No auditor has seen either.)*

The check reads the `.blend` **on the machine**, where a Blender already sits — the same *kind* of read Pre-load Settings performs for a file's settings, not the same act. Label: **Creator-stated** (2026-07-28). So it needs a connection and a Blender on the machine, exactly as reading settings does.

**It reads with the Blender the job will render with.** A machine can hold more than one Blender and the user chooses which one renders (see the [Render Settings spec](Render%20Settings.md)), so the check uses that one. A check run with a different version would describe a file the render never reads. Where that Blender cannot open the file at all, nothing is checked: no rows are shown, and Smoozy says the file could not be read and with which version, rather than showing an empty list that reads as "nothing is missing".

**What it looks for is everything the file points at outside itself.** The kinds are the same in every Blender version Smoozy supports: another `.blend` file, and the weak reference kept to one after appending; images and movies; sounds; fonts; volumes; cache archives and their extra layers; text files; OSL shader scripts; IES light profiles; the external displacement files of the Multires and Mesh Cache modifiers; physics point caches; fluid cache folders; geometry-node bake folders; ocean bake folders; dynamic-paint output folders; a sequencer image strip's folder and a movie strip's file; proxy folders for strips and for movie clips; render output; bake output; the compositor's File Output node; collection exporters; a brush icon; a node setting whose value is a location; and the record kept with a packed file. Label: **documented and observed** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**A node setup inside the file is a route of its own, and it was missing from that list until it was asked about separately.** A geometry node setup can make a file point at a model file named on an import node — six kinds of them, the same six in every version — as well as at an image, a font, a folder of baked data and another `.blend`, and from Blender 5.2 at a sound file too. Label: **documented and observed; the sound route in 5.2 alone** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**And in Blender 4.5 one of those paths is invisible to everything that looks for a file's outside files.** An import node's own path takes no part in the file's own path housekeeping there: making a file's paths relative or absolute leaves it alone, Blender's report of missing files never names it, and it appears in neither of Blender's two lists of what the file points at. From 5.0 on it does take part in all of them. Label: **observed; differs by version** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). So a file whose geometry is imported from a model file beside it is a file Blender 4.5 will not tell you is missing anything, and the check has to reach that path another way in that version or say plainly it did not.

**Whether that is the whole list is permanently unresolved**, settled so on 2026-09-02. No version of Blender's documentation claims completeness, and a test can only turn up the kinds it was built to hold — which is exactly how the node-setup routes above went unnoticed for a whole round, since the file the first tests used held seven kinds and none of them was a node. Something small whose absence changes how a render looks without stopping it belongs here as much as a heavy one, so what may be missing from the list is not only "what else is heavy". There is no source to read and no test that could close it, and the Creator ruled on 2026-08-31 that there will be no further Blender research, so it will not now be closed. **What breaks:** a kind nobody has named is not found, not sent and not shown as a row, so the file renders on the machine with something missing and nothing says so. Carried at `Preparation/Architecture/Dependency Upload & Remap.md` G7 and §12 item 13.

**A font is an ordinary recorded location like any other.** Blender does not look a font up by family name in the computer's own font list — the location in the file is the whole of it. Label: **documented and observed**. So a font installed on the artist's computer is a file this module has to find and send, like a texture.

**A file points at exactly one kind of library: another `.blend`.** Label: **documented**. From Blender 5.0 there is a second kind of library inside the file, holding linked data that was packed into it; it is owned by the real library it came from and is not another file to go and find. Label: **documented** (5.0, 5.1, 5.2). An asset library is a folder registered on the computer rather than something a file points at, and Blender 5.2's online asset libraries cannot be linked to at all. What a library that does not sit on the user's own computer would mean is **unresolved** — the same open question as the one under *Sending them up, and where they land* below.

**What makes two recorded library locations one library or two is settled, and the remap has to know it.** Two recordings naming the same file that differ only in how the path is written — one relative, one in full, or a detour that leads back to the same place — are **one** library: Blender tidies the writing before it decides. Two recordings that reach the same file by two different names on the disk — a shortcut of either kind, or the same folder reachable twice — are **a separate library each**: the tidying stops at the text and never goes to the disk to ask what the file really is. The last of those three was possible on the Linux machine alone, since the Mac cannot mount a folder twice. Two different files that happen to share a file name are two libraries, and the second gets a numbered ending. **The decision is made when the file is read**, not when the link is made: two entries forced to hold the same text stand until the file is saved and opened again, and then there is one. **From Blender 5.0 packing linked data is the deliberate exception** — it leaves the file holding two entries with the very same recorded location, and both survive a save and a reopen. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**Two things follow for this module.** A remap that gives two ordinary library entries the same location merges them the next time the file is read, which is what Smoozy wants where two references really were one file and is a silent loss of one of them where they were not — so the check's one-row-per-thing rule has to be about the file the location reaches rather than about the text. And **capitals decide it differently at the two ends**: on the rented Linux machine a wrongly capitalised library location was simply not a file and the link failed outright, while on the Creator's Mac it quietly succeeded and left the file holding two libraries where the artist meant one. Label: **observed** — the same in all four versions on each machine, and the two machines differ. **That settles those two machines and not the kind**, which the research says in as many words; a third machine, and Windows, are untested. That is the same disk-decides rule as for any other reference, and it is why the search below matches exactly.

**Some of what a file records are places it writes to, not places it reads from**, and those are not things to go and find. Render output, the compositor's File Output node, and collection exporters. Label: **documented and observed**. Blender's own list of a file's external references carries neither the render output path nor the File Output node's. Label: **observed**.

**But a place a file writes to can also be a place it reads from, and this module sends those.** Physics caches, geometry-node bakes, the ocean bake folder, the fluid cache folder, dynamic paint's output folder and proxy folders are all recorded as places written to — and every one of them is also in the list of what a file points at, above. **Bake output belongs with them**: it is a place a file writes to that is also a place a baked result already sits, so it is found and sent where one is there, and the uploaded copy is read from the job's own folder like every other cache and bake. Label: **Creator-stated** (2026-08-22). **Moved here 2026-09-05, out of round 1 of the code audit of this module**, where it sat in the write-only sentence above and among the sent kinds at the same time. Nothing here says bake output is in Blender's own list of what a file points at; nothing establishes that.

**That is now settled by test, and it settles it the way this module already guessed.** A recorded write place is genuinely read back: a render with Overwrite switched off reads the output folder to see which frames are already there, and Cycles' own animation denoiser reads it and stops on a frame that is not there. Label: **observed** (the same in all four versions) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**And what a render does when a cache or a bake is absent is the worst of the possible answers.** It works the simulation out again rather than skipping it *(not always — corrected below, 2026-10-02)*, says nothing at all, finishes with success, and gives a picture that is not the baked one. Nothing is printed, in any version. The one exception is worth having: an external physics point cache pointing at an empty folder reports itself as holding no valid data, and that report can be read with no window open — so that single case can be noticed from outside Blender. Everything else is silent. A fluid cache is worse still: with the folder taken away the file goes on saying every part of it is baked, because those marks are held inside the file rather than worked out from the disk, and opening the file simply makes the folder again. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**Not always worked out again. Corrected 2026-10-02.** A geometry-nodes simulation that was never baked is not worked out again when rendered from the command line: it does not move at all, and every frame shows it as it is on its first frame. A physics cache marked baked whose files are missing gives the object as it starts, unmoving. A geometry-nodes Bake node whose folder is missing leaves the baked object out of the picture. Each is still silent and still ends in success. Label: **observed** at the desk, 2026-10-02 — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**So they are found and sent, and now for a reason rather than out of caution.** The two mistakes were never the same size. Sending a bake the render would have made for itself costs the user some waiting and some of the machine's disk. **That phrase holds for a frame rendered in order and not otherwise**: a simulation reaches a different state where a frame is jumped to rather than arrived at, so a render that does not walk the range from the start is not making the same thing the bake holds. Label: **observed** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). Which makes the wasteful side wasteful less often than the sentence suggests, and does not change which side this module takes. **Not** sending one the render needed costs them a render that computes something different — confirmed, at full price, with nothing said anywhere and, for a fluid cache, with the file still claiming to be baked. So the safe side is the one that wastes bandwidth, and this module takes it. Where such a write should land on the machine is settled, and it is settled the way the rest of the job's writing is. **A cache or a bake the render writes falls under the job's-folder redirect like every other place the job writes**, so it lands under the job's folder rather than inside Smoozy's asset area, [Download](Download.md) sees what the render produced, and it comes home with the frames. Label: **Creator-stated** (2026-08-18). The rule itself lives in [What a job writes](What%20a%20job%20writes.md), which names the places it covers; nothing about it is decided here. **What this module sends is unchanged** — a cache or a bake that already exists is found and uploaded exactly as above, and where an uploaded one lands is the landing rule below.

**One cache does announce itself, and it announces itself as a refusal.** A physics disk cache written by Blender 4.5 is refused by 5.0, 5.1 and 5.2, which say plainly that it uses an outdated compression and must be deleted and re-baked — twice, once at opening and once while rendering — and then render anyway, at success, giving a different picture. Label: **observed; differs by version** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). So a user who baked on 4.5 and renders on a newer Blender gets a wrong picture with a warning nobody may read, and it is the only absent-cache case in the whole set that says anything at all.

**A file can hold some of what it depends on inside itself and not the rest.** Packing is item by item, and some kinds — a movie in the sequencer, a movie clip — can never be packed at all. Label: **documented and observed**. A partly-packed file says nothing about what it is missing when it is opened; it has to be asked. Label: **observed**. So what is missing for such a file is whatever was left out, and the check reports those and not the ones carried inside.

**A linked `.blend` is both a dependency and a source of more.** A file can link another `.blend`, which links another, to any depth. The check covers the whole tree, and everything below the top file is treated the same way as everything at the top. Label: **Creator-stated** (2026-07-28). A chain of nineteen linked files was read whole, every level recorded, in every version. Label: **observed**.

**A location recorded inside a linked `.blend` is measured from that file, not from the one the user opened.** Read against the wrong file it gives a location that does not exist. Label: **observed** — the same in every version. So every location the check finds below the top file is read against the file that holds it.

**The same thing reached twice is one row.** Two files can point at the same library, and one library can be reached by more than one route through the tree. What matters is the thing pointed at, not how many references lead to it, so it is found once, sent once and shown once — and where more than one reference led to it, the user is told that. This is also what keeps the check finite: a file already reached is not walked again, so a chain that comes back round to something already read stops there rather than going round for ever.

**Reaching the deeper levels can take more than one pass.** A linked `.blend` that is missing is not on the machine, so there is nothing there to read it out of — what it points at in turn cannot be seen until it is up. **Smoozy carries the check down itself as those files arrive:** when an upload puts a missing linked file on the machine, that file is read and whatever it points at appears alongside the rest. That is not Smoozy checking on its own initiative — it is finishing the check the user asked for, which is not finished while part of the tree has never been read. The user is shown that this is happening rather than left watching a check that appears to have found everything, and a deep chain plainly takes several passes to settle. **There is no way to reach them sooner.** The readable chain stops at the first absent file: a missing linked `.blend` is named, and everything below it is named nowhere at all. Label: **observed** — the same in every version.

**A linked `.blend` that was not found hides an unknown amount below it.** Its own dependencies cannot be read while it is missing, so one *not found* row can stand for one file or for a hundred, and resolving it may put many more rows on the screen. Smoozy says so on that row, so a user reading a short list of missing pieces does not take it for the whole of what is missing.

**The check covers the file, not a scene.** A `.blend` can hold several scenes and a job is always exactly one of them (see the [Queue & History spec](Queue%20&%20History.md)), but the user checks the whole file once and is done. Checking per scene would mean checking three times to submit three scenes in one act, and a user who knows part of the file is irrelevant can set those rows aside by hand. Label: **Creator-stated** (2026-07-28).

**The row does not say which scene uses it**: the Creator dropped that line as noise, so a user sets rows aside on their own knowledge of the file. Label: **Creator-stated** (2026-10-08, sixth notes, note 3). **One exception: where Smoozy's reading finished for every reference the row stands for and reached no scene, the row says *Not used by any scene*.** *Words changed 2026-10-28 (was *Smoozy found no scene that uses it*): Creator-stated, the final words sweep. No auditor has seen it.* In every other case nothing is said about scenes. The note acts on nothing: Smoozy never sets the row aside or removes it on its own, and claims nothing about whether the render needs the file. Label: **Creator-stated** (2026-10-18, answering the dependency check's fresh look, decision 1, which grew from the Creator's twelfth notes, note 5; no auditor has seen it). The tracing itself is possible: something a file points at can be traced back to the scene using it, in every version, with no window open. Label: **observed** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). **The three awkward kinds that had never been tried have since been tried, and all three can be traced** — a reference held only inside a node group, one that is only a driver's target, and one held only by a custom property. Label: **observed** — the same in every version, on the rented machine alone and untried on the Creator's Mac. Whether every kind can be reached is still not established, since only pictures were put in those three places.

## Finding the files

**Smoozy does not go hunting across the user's computer.** It looks in two places, in order.

**First, where the file says the thing is.** A `.blend` records a location for each thing it points at, and for an artist still working on the computer they authored on, that location is simply correct. There is no reason not to look there first. Label: **Creator-stated** (2026-07-28).

That has a limit worth stating plainly. A recorded location can be written **relative to the `.blend` itself** rather than in full — and that is Blender's usual way of writing it. Label: **Creator-stated** (2026-07-28) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). The file is now on the machine, so "next to the `.blend`" resolves to somewhere on the machine rather than to the folder it came from. Smoozy can still work out the original local location where it **watched that file go up**, because it knows where the upload came from. Where the file was already sitting on the machine when the user pointed at it, that knowledge does not exist, and a relative location is of no use — only one written out in full is.

**A recorded location can be written in several ways.** In full from the top of the disk; relative to the `.blend`, which may climb above its own folder; with `#` characters standing for the frame number; with a `<UDIM>` or `<UVTILE>` token standing for a tile; with a `%` standing for a view name; and, for OSL scripts only, as a bare name with no folder at all. Label: **documented and observed** — the same in every version. Two forms look like locations and are not: a `~` standing for the user's home folder, and an environment variable, are both kept exactly as written and never worked out, so they resolve to nothing anywhere. Label: **observed**. Curly-brace templates are worked out at the moment the location is used, and are allowed only in the render output path and the File Output node.

**A location that resolves on the user's computer can still fail on the machine.** Whether capital and small letters matter **when a file is loaded** is decided by the computer's own disk, not by Blender: a location written `Texture.PNG` finds a file named `texture.png` on an ordinary Mac disk and does not find it on the rented Linux machine. Label: **observed** — the same in every version. So a reference that resolves perfectly well on the user's computer still has to be pointed at the copy on the machine, spelled as that copy landed. That is the silent failure this module exists to prevent.

**Blender's own search for a missing file is stricter than that.** It matches the file name exactly, capitals included, and it gave that answer **on the Mac too** — so a wrongly-cased reference is not rescued by Blender's repair on either of the two machines it was run on. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). **That strictness is Blender's own rule and not the disk speaking — settled 2026-09-01, after the research was repaired; this used to say it was unresolved.** The run has the one comparison that decides it: the Creator's Mac does not treat capitals in a file name as significant — ask it directly for a file by the wrong case and it hands it over — and Blender on that same Mac still failed to find it, while the run with the matching name succeeded on both machines. **Windows was never tried and now never will be.** Nothing here turns on it either way, since the repair does not rescue the spelling whichever it is.

**Second, the folders the user has told Smoozy to search.** The user adds folders once and they stay: a library of HDRIs lives in one place, so pointing Smoozy at it should benefit every future job rather than being re-stated each time.

**A folder covers everything inside it.** Adding one means everything below it as well, to any depth, so the user can point at the folder holding all their work rather than at each project in turn. That is what makes a short list enough, and it is also why one folder can hold several files of the same name — pointing at everything a user has ever made will find both `project1`'s `metallic.png` and `project2`'s. The user is told when that happens, and told which one Smoozy took, exactly as for a name found in two different folders.

**That list is the user's, not a machine's.** It describes the user's own computer, so it is kept in one place for the whole app rather than per server — a new rented machine inherits it without anything being re-added. It is managed in Settings and also reachable from the check itself, since that is where a user discovers they need one. The user sets the **order**, and the first folder holding a match wins — which is how a user says "my current work beats my archive" in a way they can predict. It settles which folder is taken from, never which file inside one.

**Where one folder holds several matches, the pick between them is arbitrary.** The order says nothing about the inside of a folder, and nothing else in Smoozy tells two files of the same name apart — inventing a rule, the shortest location or the first one met, would dress an arbitrary pick up as a judgment. So Smoozy says plainly that the pick was arbitrary as well as saying which file it took, and a user who finds the wrong one reads it as a coin toss rather than as Smoozy's opinion. This is the same honesty [What a job writes](What%20a%20job%20writes.md) already shows where it is left with two equal candidates and nothing to choose between them.

**A search can be stopped, and a folder that cannot be read does not stop the rest.** A folder covers everything below it, so a large one can be searched for a long time with nothing found yet; the user can stop it at any point and keep whatever it has already turned up. Where a folder on the list has been moved, deleted, or cannot be read, Smoozy searches the others and says plainly which one it could not use — it carries out the part it can and reports the part it could not, as the whole app does (see [Whole app](Whole%20app.md)). What that looks like is Design's.

**Smoozy never treats a name as proof.** One file can point at two different `metallic.png` in different folders; three levels of linked `.blend` can each carry their own; and the user's computer can hold more with the same name that have nothing to do with any of them. So a match found by name is a **proposal**, never a fact. Where a name matched in more than one place — two searched folders, or two spots inside one — the user is told, and told which one Smoozy took.

**Two names differing only in capitals may be one file to the user's computer and two to the machine.** Whether capitals matter is decided by the disk rather than by Blender, and the disks at the two ends need not agree — the artist's own computer commonly does not mind them, and the rented machine does. Label: **observed** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

That reaches this search before Blender is involved anywhere. Asked for `METallic.png` on a disk that does not mind capitals, the computer hands back `metallic.png` as a match, and there is nothing in the answer to say it is a different file — the disk itself calls the two names the same.

**So the search matches exactly, capitals included.** A file whose name differs by so much as one letter's case is not a match. Label: **Creator-stated** (2026-08-06).

The reason is that Smoozy cannot be lenient and correct at the same time. Blender never tries the other spelling when it loads, and its own repair for missing files does not either — so a texture that loads on the artist's own computer under the wrong case is being rescued by that computer's disk, not by Blender, and nothing rescues it on the machine. Smoozy has to get the spelling right regardless. And being lenient does not fail loudly: Smoozy would send the wrong file, point the reference at where that file landed, and the render would find it and use it. A wrong picture, at full price, with nothing missing and nothing to see. A row saying *not found* is worse for nobody.

**But a name that matches except for capitals is still shown, as a proposal.** Exactness decides what counts as found; it does not decide what the user is told. Where the only candidate differs by case alone, Smoozy says so — this is what was asked for, this is what is there, is it the same file — and the user accepts it or does not. Without that, an artist who renamed a texture's case years ago, and whose computer has quietly papered over it ever since, is told their file is missing while they are looking straight at it.

That is not a new idea in this module. A match found by name is already a proposal and never a fact; a match found by name but for its capitals is simply a weaker one, and it is offered the same way. Settled at Design (2026-08-23): the proposal sits as a qualifier under what Smoozy found, saying the match differs only in capitals, with **Accept** on the qualifier rather than on the state; over a selection the control accepts each row's own candidate and names how many it will accept.

**The record Smoozy keeps of what each reference was resolved to is compared exactly too**, capitals included. Label: **Creator-stated** (2026-08-06). That record is kept against the location written inside the `.blend`, and two references reading `METallic.png` and `metallic.png` are two references with two answers. Compared any other way they collapse into one, and the second reference silently inherits the first one's file — the same wrong picture by another route.

**Locating one file teaches Smoozy where the rest are.** When the user points at a file by hand, Smoozy learns more than that one answer: it learns the **shift** between where the file said the thing was and where it actually is. If a reference reads `work/project1/assets/textures/metallic.png` and the user finds it at `Archive/project1/assets/textures/metallic.png`, then everything else recorded under the old location can be looked for under the new one — not just the neighbours in that folder, but files in sibling folders at any depth. This is the common case: things go missing mostly because a project was moved, archived, or came off another computer.

**A shift needs an old location written out in full.** There has to be something to shift *from*, and a location written relative to the `.blend` does not give one — see the limit stated above. So the shift applies where the recorded location is written in full, or where Smoozy watched that file go up and so knows where it came from. Everywhere else, locating a file by hand teaches Smoozy that one answer and nothing more.

**A shift moves what shares a root, not everything.** Where a project's references all sit under one root, the whole tree moves together and one locate covers it. A project spread over several roots takes one locate per root — an HDRI library sitting somewhere else entirely is the obvious one. So a file whose assets come from two places takes two of these, not forty.

**A shift is visible, and it can be taken back in one go.** Smoozy shows the move it worked out — the old location and the new one — and every row the shift resolved says it came from that shift rather than from a search or from the user's own hand. One action returns every row the shift produced to *not found*, so a shift that was right for the file the user located and wrong for the rest is undone at once rather than row by row.

## What the user sees

**One row for each thing the file points at.** Each row says the location the file records, what Smoozy found for it and where that was found, how big it is, and which state it is in. Five states describe what the check found:

- **Found on your computer** — Smoozy has a file it believes is the right one, and can send it up.
- **Already on the machine** — Smoozy has looked on the machine and the file it needs is there, so nothing needs sending.
- **Sent before, not confirmed** — Smoozy's own record says it sent this file to this machine for this reference, and nothing has confirmed it since.
- **Not found** — nothing in the searched places matches.
- **Set aside** — the user has told Smoozy to stop trying.

And two describe what happened after the sending started:

- **Could not be sent** — the file was found but did not arrive, or arrived and could not be put where it belongs.
- **Could not be fixed** — a linked `.blend` arrived but Smoozy could not open it, or could not point it at its own dependencies, so the render will not find them through it.

A row in either of those last two says what went wrong as far as Smoozy knows it, and can be tried again on its own — without re-running the whole check or re-sending everything that already arrived. A retry that fails again leaves the row as it was; it is never quietly turned into a success, and it never holds up the rest of the upload.

Where a match came from more than one place, the row shows that, which one was taken, and whether the pick between them was arbitrary. What the row says is settled here; how the rows are laid out, grouped, sorted and acted on in bulk is Design's.

**A reference can point at a named thing inside another file, and none of the states above covers that thing being gone.** The name is the whole identity: rename the thing inside the library and the reference breaks exactly as if it had been deleted, reported in the same words, with no way to tell the two apart. Label: **observed** — the same in every version. What is left behind is an empty stand-in, and the render finishes anyway. The file is found, so no row reads *not found*, and the user has nothing to locate — there is no file missing to go and get.

**So it is not a row at all: the check says it, and there is nothing to act on.** The panel already carries statements that are not rows — the file could not be read, this sitting was cut short, these folders were searched — and this joins them. It says a linked item was not found inside its file and names the file; **it cannot name the item**, because what Blender gives is a count of missing libraries and never a name, and the statement says so rather than leaving the user wondering what was withheld. It is not a warning, there is nothing to dismiss, nothing to switch off, and **it does not hold up the check**: a check that is otherwise complete still says the file is ready to render, because a finding nobody can act on must not be allowed to keep a file permanently unready. The point is that the user is told, and is left free to go ahead knowing it. Label: **Creator-stated** (2026-08-22). **One limit, stated rather than hidden:** whether Smoozy can spot the empty stand-in at all is not established, and no more Blender research is being commissioned. Where it can, this is said; where it cannot, nothing is said, which is what happens today — so nothing here can ever be wrong, only absent.

**A `.blend` also records a location pointing into the Blender application it was saved with.** It is not one of the user's own files, it exists nowhere on the machine, and Blender itself does not count it as missing. Label: **observed** — the same in every version. Left as an ordinary *not found* row it would never be resolved, so the check would never leave nothing unfound and Rendering's warning would never stop for any file the user made.

**So it is not shown as a row, and it does not count against the check leaving nothing unfound.** There is nothing for the user to do with it — no file to go and get, nothing to point at, and no reason to make them set aside something that was never theirs. A row that cannot be acted on is a control that does nothing, which this app leaves out rather than offers. And leaving it in would break the one signal the plan gives that a file is ready to render.

**A row may stand for more than one file.** One reference can mean many files, in several ways: an image sequence, a UDIM or UVTILE tile set, a volume sequence, a cache archive split into a series or carrying several layers, a sequencer image strip, a physics point cache, and render output. Label: **documented and observed** — the same in every version. Such a row names the folder or the set rather than one file, pointing it at a folder by hand points the whole row at that folder, and the whole of it goes up as one thing. Its size, and the total shown before an upload, cover the whole set rather than one file. Blender can be asked which files a set really means only from version 5.2; 4.5, 5.0 and 5.1 hand back the written location and nothing more, so the count comes from Smoozy in those. Label: **observed**.

**Already-on-the-machine is judged by what is inside the files, not by their names.** Two files called `metallic.png` are the same file only when they really are the same file, and Smoozy compares them accordingly. That is what stops an old job's texture being silently reused for a new one, and it also means an asset that matches something already up there **does not cross the connection**. Telling two files apart is itself work — it means reading both of them through, at both ends, which is real time on a large asset — but it is work done on each machine rather than between them. How Smoozy does the comparing is Architecture's. Label: **Creator-stated** (2026-07-28).

**Two states are kept apart because one of them was checked and the other is only remembered.** *Already on the machine* means Smoozy looked and the file is there. *Sent before, not confirmed* means Smoozy's record says it sent that file to that machine for that reference and nothing has been looked at since — the copy may have been deleted, replaced, or never have arrived. That state is what covers a file the user has moved or deleted on their own computer, where there is no local original left to compare against: the row does not read *not found*, because Smoozy has reason to think the copy on the machine is good, but it does not claim to have looked. Such a row can be confirmed against the machine at any time, which moves it either to *already on the machine* or, where nothing is there, back to *not found*.

**The user sees what an upload will cost before it starts.** Each row carries the size of what was found for it, and before anything is sent Smoozy says how much is about to go up in total, and how much is not being sent because it is already there. The whole module is argued from size, and a user deciding whether to start now or leave it overnight needs the number.

## What the user can change

**Smoozy proposes and the user decides, on every row.** The user can work through the whole file by hand if they want to, and nothing Smoozy worked out is beyond changing. Four things can be done to any row:

- **Point it at a file** — any file the user chooses, **including one with a different name**. Files get renamed, and a manual override that only accepted the original name would fail in exactly the case that most needs it. Where the row stands for a folder or a set, this means pointing it at a folder.
- **Set it aside** — Smoozy stops trying to find it and stops counting it as missing. Some references genuinely are not worth chasing, and without this the row would go on being reported as missing at every check.
- **Bring it back** — undoes setting aside. The row returns to whatever the check finds for it now, which may be a match and may be nothing. Setting aside is remembered beyond the sitting, so without a way back it would be permanent.
- **Reject match** — put the row back to not found, where the user judges the proposal wrong and has nothing better yet. *Words changed 2026-10-28 (was *Undo Smoozy's guess*): Creator-stated, the final words sweep. No auditor has seen it.* The rejection is remembered: Smoozy does not put that same match forward again by itself, the row says there is a match the user turned down, and the user can reinstate it if they change their mind.

**Rows that were set aside stay on screen after an upload**, as not-found rows do. A row nobody can see is a row nobody can bring back.

## Sending them up, and where they land

Once the user is satisfied, Smoozy sends up everything in the **found** state. Files confirmed **already on the machine** are not sent again — that is the whole point of the module. A row that is only *sent before, not confirmed* is confirmed first, and sent if it turns out not to be there.

**An asset keeps the location it had on the user's computer.** Inside an area on the machine that Smoozy uses for assets, each file sits at the whole location it came from, from the top of the user's disk downward. Label: **Creator-stated** (2026-07-28).

**Where a file is going to land may already be taken by a different file, and Smoozy warns before it writes over one.** The rule below keeps the files of one upload apart from each other. It does not keep them apart from what an earlier job left there: the user may have replaced a file on their own computer since, so the location is the same and the file is not. Smoozy reads both, sees they differ, and does not mark the row as already on the machine — so it would send it and lay it on top of the one already there. Label: **Creator-stated** (2026-08-06).

**The warning is the one this module already gives before a delete**, for the same reason and naming the same thing: a file another job depends on is about to stop being what that job expects. Until now *Cleaning up* asked before **removing** such a file and said nothing about **replacing** one, which is the same harm by a quieter route. Both now warn.

**The choice offered is replace or stop, and not the fuller set the file browser offers** for an ordinary upload — see the [File Browser spec](File%20Browser.md), which owns that set. *Keep both* cannot work here: the landing rule sends a file to the mirrored copy of its own location and nothing else, so there is no second place for it to go, and inventing one would break the very thing that keeps two same-named textures apart. *Skip existing* cannot either: the row is only being sent because Smoozy read both files and they differ, so passing over it would leave the reference pointing at a file that is not the one it means. Said plainly here so nobody later assumes either of them carries over.

Two things make that the right rule. It should **not collide**, because two files on one computer cannot sit at the same whole location — so `project1/assets/textures/metallic.png` and `project2/assets/textures/metallic.png` stay two separate files, and that is how a working artist's folders are actually laid out. That is an **assumption** rather than something established — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md) — and the whole rule rests on it: if it is wrong, two different files land on one name and the module's central promise fails silently. The rule holds so long as the whole location, disk name included, comes up with the file. Where the user's computer names its disks, the disk is part of the location and comes up with it, so the same file name on two disks stays two files. And it stays **readable**: the user browsing the machine recognises their own structure, which no scheme of Smoozy's own naming would give them.

**What a location written on the user's computer means on the machine is settled for the crossing Smoozy actually makes.** A location written relative to the `.blend` survives it whole and resolves against the file's new folder on the machine. One written in full does not: it is kept exactly as written, resolved exactly as written, and simply not found — Blender neither translates it nor complains, and says nothing at all unless it is asked. Label: **observed** — the same in every version, carrying a file from a Mac to a rented Linux machine. That silence is why the remap is needed.

**Windows is permanently unresolved**, settled so on 2026-09-02. None of this was tried on a Windows computer, so what a location written on one means on the machine, and what one naming a disk by a letter means, was never established. The machine that could have answered it was destroyed on 2026-08-26, and the Creator ruled on 2026-08-31 that there will be no further rental, so it will not now be answered. **What holds:** the Mac and Linux answers above stand whole, the machine at the far end is Linux whichever computer the file came from, and that machine treats a lettered disk as an ordinary full location and finds nothing there. Label: **observed**. **What breaks:** a location written on Windows is outside what the landing rule promises, and a Windows artist meets that with nothing said — see `Preparation/Architecture/Dependency Upload & Remap.md` A4 and §12 item 3.

**A location that is not on the user's own computer is outside this rule.** The rule keeps a location *from the user's computer* and mirrors it on the machine. It has nothing to say about a location that was never there — a network drive, a mounted share, anything that means something only where it was written. What such a location means at either end is **permanently unresolved**, settled so on 2026-09-02 — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). No version of Blender's documentation describes one, it could not be tested, and settling it needs storage two computers can both reach, which the Creator's ruling of 2026-08-31 puts out of reach. So the standing rule is the answer rather than a placeholder for one: such a reference is shown as **not found**, and only the user's own hand resolves it, by pointing the row at a file on their own computer — `Preparation/Architecture/Dependency Upload & Remap.md` §12 item 14. **What breaks:** a file leaning on a network drive or a mounted share is outside what this rule promises, and the user mends it themselves or not at all.

**A file already up there is pointed at, not sent again.** Where the same file turns up later under a different local location — a copy kept in two projects — it is not uploaded a second time. The reference points at the copy that is already there. So the layout on the machine mirrors where a file **first** came from, and any later reference to that same file is pointed at that first copy rather than given one of its own.

**What could not be found does not stop the rest.** Smoozy sends everything it has and says plainly what it could not place — it does the part it can and reports the part it could not, as the whole app does (see [Whole app](Whole%20app.md)). Holding back a whole upload because a few of its pieces are missing would waste the user's time and their machine's, and a missing piece does not necessarily break a render — it may belong to a scene that is not being rendered. Smoozy is not the judge of that. The rows that were not found stay on screen after the upload rather than disappearing with it.

**A render does not stop when something it points at is missing.** It writes the frame and finishes as a success: a missing font loses its letterforms with nothing standing in for them, and a missing linked `.blend` leaves empty stand-ins where its contents should be. Label: **observed** — the same in every version. What a missing **texture** does to the picture is settled in [What a job writes](What%20a%20job%20writes.md), which owns it and carries the limits on it; this module does not restate it. What Blender *says* differs sharply: Blender 4.5 never names a missing image at all, 5.0 and 5.1 print one error naming the file, and 5.2 prints a warning naming the file and a separate error counting the failures. Label: **observed**. So a user who submits with pieces missing is choosing a render that will finish and may be quietly wrong, and on Blender 4.5 nothing will tell them it happened. That is what the user is weighing, and it is why the check's warning is worth having even though it blocks nothing.

**A submitted job's files can change under it, and that is exactly why Smoozy warns.** A job that is running or waiting is reading a `.blend` and the assets it points at, and this module can be asked to send a file or fix one straight on top of them. What happens then is now known and it is not reassuring: **a changed picture reaches the very next render with nothing done at all** — no reload, no restart, nothing — and a picture replaced while an animation is already running takes effect from a later frame onward, so a job comes home with its first frames drawn from one texture and its last from another. **One kind of picture does not behave that way, and it differs by version**: a picture behind a strip in the video sequencer reaches the next render by itself in Blender 4.5, and in 5.0, 5.1 and 5.2 nothing the round tried made it reach the render at all. No frame ever came out part old and part new, which is the one mercy in it. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**One more kind is on a rule of its own, and it is a clock rather than a yes or no.** An imported model file is re-read only where the time recorded against it has moved by a **whole second** — a change inside that second is not noticed at all. Label: **observed** (the same in all four versions) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). So replacing one of those under a running job may or may not reach the next render depending on nothing the user can see, which is a third answer beside *reaches it* and *does not*.

**Not everything behaves that way, and the differences matter to what a warning has to cover.** A linked `.blend` replaced under a running Blender does **not** reach the next render until it is reloaded, and a movie clip does not either. A picture packed inside the `.blend` ignores its own file on disk where nothing is done about it — what a reload then does to such a picture came out two ways across three runs and none was preferred. And one render setting, off by default, stops a changed picture being picked up at all — so an artist who switched it on gets the old texture where everyone else gets the new one. Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**So before touching anything a live or waiting job depends on, Smoozy warns** — the same promise the file browser already makes before a delete, a rename, or an upload that would land on such a file, and the wording of that warning is File Browser's (see the [File Browser spec](File%20Browser.md)). The user can go ahead; they are never left to find out from a render that broke halfway, or worse, from one that finished at full price with two different textures in it.

**A lost connection behaves exactly as it does in the file browser**: the upload stops, everything that fully arrived stays, nothing resumes on its own, and running the check again sends only what is still missing — carrying on inside a part-sent file only where Smoozy can tell that file has not changed, and sending it again from the beginning where it cannot. That condition is File Browser's and is stated there in full — see the [File Browser spec](File%20Browser.md). It is the same act, so it does not behave two ways depending on which window started it.

**A connection lost during the *check* leaves the sitting standing.** The check has read part of what the file points at and not the rest, so what it found stays on screen, said plainly to be incomplete rather than presented as the answer. Every decision the user made in that sitting is kept — a file located by hand, a row set aside, a guess rejected. Nothing carries on by itself when the connection comes back: the user runs the check again, and it starts from what is already known rather than from nothing.

## Pointing the file at them

Remapping is what makes the uploaded pieces actually get used. It happens in two different ways, because two different kinds of file are involved.

**The file the user points at for a render is read and never written to.** Whatever it costs elsewhere, the `.blend` the user chose stays exactly as they uploaded it. Label: **Creator-stated** (2026-07-28). Its remap therefore lives outside it, in Smoozy's own record: what each of its references should point at is held there, and takes effect **when the render starts**.

**By what route it takes effect is not settled here, and is not this document's to settle.** [What a job writes](What%20a%20job%20writes.md) has the same problem for its output redirect, and both apply to the same file at the same moment, so whatever route serves one serves the other. **That such an instruction can be given at all, without being written into the file, is no longer open.** Where a render writes can be settled at the moment the render starts, and the file on disk is left exactly as it was — its size, its modification time and its stored value all unchanged. Label: **observed** (the same in all four versions, on both machines). And a wholesale rewrite of a file's recorded locations shows in the Blender that is running and never reaches the file on disk unless something saves it. Label: **observed** (the same in all four versions, on one machine). Which route Smoozy takes is Architecture's, and a copy Smoozy makes and renders from is one of the ways rather than the decided one — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**Everything else on the machine is Smoozy's to manage, and a linked `.blend` is remapped in place.** Label: **Creator-stated** (2026-07-28). That holds whether Smoozy sent the file up itself or found it already there — a project folder uploaded by hand through the file browser before any check was run is the ordinary way a linked file arrives, and one left unremapped would point at the user's own computer and break the render quietly. So *already on the machine* means the file does not need sending, never that it does not need fixing.

**What the user sent up survives untouched.** *In place* means the fixing is Smoozy's own business rather than something held outside the file — it does not mean the copy the user uploaded is overwritten and lost. Whatever a linked `.blend` came up as, what the user put on the machine stays there unchanged, and what a render reads is Smoozy's version rather than theirs. A user who uploaded a file by hand and later found it altered would have had something taken from them without being asked. **How that is arranged is Architecture's** — settled here is only that the file the user sent is preserved.

**All of this rests on a `.blend`'s recorded locations being readable and writable at all, and they are.** Blender itself reads them out and writes them back, with no window open, and the change survives being saved and re-opened. Label: **observed** — the same in every version. So the in-place fixing stands as written. See [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**But no single way of listing or rewriting them reaches every kind, and that is the sharpest constraint on this module.** On one machine, a file holding twenty-one different kinds of recorded location was put to every route Blender offers; the same tests were not run on the other. The plain list of a file's outside paths, and the sweeps that make every path relative or absolute, reach sixteen of its readings and miss seven — the render output path, the bake output path, the compositor's File Output node's path, a physics point cache, a geometry-node bake folder, the sequencer's proxy folder, and a path held in a custom property. Walking Blender's own marks on its settings finds nineteen of the twenty-one, including six of the seven the sweeps miss. **The two together cover everything but the custom property.** And a one-pass route that visits every recorded path and can rewrite each one exists in Blender 5.0, 5.1 and 5.2 and **not in 4.5**, with 5.2 alone telling its caller more about each path it hands over. Label: **observed; differs by version** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md).

**So the promise holds and the method is narrower than it looked.** Every kind this module cares about can be **reached**, though not by one call, and a check built on the plain list alone would silently miss whole families of location. **That they can all be rewritten is a step the research marks as inferred rather than watched** for the six kinds only the mark walk reaches, so it is an inference this module rests on rather than a settled fact. That is Architecture's to carry out; what is settled here is that it can be done, and that it takes more than one route in every version.

**Blender can also report what is missing, search a folder for it, and rewrite the locations itself — and Smoozy still does its own searching.** Label: **documented and observed**. The report does work with no window open and does name each missing path in what it prints, so a program driving the render can read it out of the output — but it comes back as printed lines rather than as an answer a program is handed, in every version including 5.2. **Blender's own search is the part Smoozy will not lean on, and there are now four reasons rather than two.** It matches capitals exactly, which is right but is not what *Finding the files* needs to be able to soften into a proposal. Where several files could serve it **takes the largest one on disk** and says nothing whatever about there having been a choice — no line about ambiguity appeared in any arrangement, in any version, on either machine. Its wider form **silently repoints references that were not broken at all**, to a same-named file in the search folder. **And what it writes back keeps the form it was given, as far as anyone has looked. Corrected 2026-09-01, after the research was repaired.** This used to say the search writes back a **relative** location while every manual promises an absolute one — a documented promise the program does not keep. **That was two different tests read as one disagreement.** One run repaired locations written out in full and got full ones back; the other repaired locations written in Blender's own shorthand and got the shorthand back. **Neither ever repaired the other kind, so whether the search keeps the form it found has never actually been asked** — and the manual's promise is neither kept nor broken on this evidence. Label: **observed, and narrower than it reads** — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). So Blender's search is not what stands behind the rows the user sees, and where Smoozy writes a location back it writes the one it means rather than trusting a repair to have written it.

Those are the files that go up once and are not sent again, so the fixing holds across every later iteration. It is also what keeps the depth manageable: nothing has to be arranged separately for each level of linked file at the moment a render starts, because everything below the top was fixed where it sits.

Two costs follow and are accepted. A `.blend` that Smoozy fixed carries locations that mean something on the machine and nothing on the user's computer, so bringing *that* version back down gives the user a file pointing at places that do not exist for them — their own copy is still up there untouched, and is the one to bring back.

And a file that went up as a dependency is still the user's to render from. They may point at it for a render, and the read-and-never-written promise holds for it, because the copy they sent was never written to. What it does not carry is the fixing: its own recorded locations still point at their computer, so it needs a check like any other file. That check should find everything already on the machine, since those assets went up when the file was a dependency — but nothing happens by itself. Submitting it unchecked gets the same warning any unchecked file gets, and a render that looks for its pieces on a computer that is not there. Smoozy says so rather than letting them find out from the render. Settled at Design (2026-08-23): it is one of the check panel's own statements, above the rows — *Uploaded before as a dependency. Its paths still point to your computer.* *Words changed 2026-10-28 (was *the file was sent up as a dependency before, its own recorded locations still point at the user's computer, and it needs a check like any other file*): Creator-stated, the final words sweep. **Whatever makes the render find its files must survive Smoozy not being there.** A machine that restarts re-runs the job it was interrupted on with nobody connected (see the [Queue & History spec](Queue%20&%20History.md)), and that re-run has to find the same files the first run did. This is the same requirement [Rendering](Rendering.md) already carries for the output redirect and the rest of what is put in place at render start, and it is Architecture's to deliver.

## What Smoozy remembers

Because the artist's own file is never written to, **Smoozy's record is the only place its remap lives**. That record holds what the check found for a file, what each reference was resolved to, and every decision the user made by hand.

**What the record holds is of two kinds, and they are not remembered the same way.**

**A located answer is keyed to the reference as the file records it** — the location written inside the `.blend`, for that file. No machine comes into it. Check the file again and a reference that still reads the same location gets the remembered answer; one that reads a different location does not, and counts as a reference Smoozy has not seen before. That is what makes a plain re-upload cost nothing and an edit that re-points something a fresh question. It is also what makes the answer travel: the same file checked on a machine it has never been on gets every match the user made by hand, because none of those answers was ever about a machine.

**What was sent where is keyed to the machine as well**, because that is what it is about. Smoozy's record that it put a particular file on a particular machine for a particular reference means nothing on a second machine, where that file has never been. This is the split the row states show: *found on your computer* describes the user's own computer and holds wherever the file is checked, while *sent before, not confirmed* and *already on the machine* describe one machine and say nothing about another.

**It is kept on the user's own computer**, not on the machine. Rent a new server, upload again, and the work of locating everything is not repeated — the files themselves must cross the wire again, because Smoozy never moves files between two servers (see [Whole app](Whole%20app.md)), but every match the user made by hand is still there.

**It outlives the machine only for the file a render is built from.** That file's remap lives in the record, so destroying the server costs none of it. The fixing inside the linked `.blend` files is a different matter: it lives in files on the machine, and it dies with the machine. Putting those files on a new server means putting them through this module again, which is where they get fixed again.

**Losing the record costs the user every decision they made by hand.** Nothing else holds a copy — not the machine, and not the artist's `.blend`. If it goes, the check still runs and still finds what it can, but every file located by hand, every row set aside and every guess rejected has to be done again. It is also **tied to the computer it was made on**: Smoozy has no account and nothing of the user's is held anywhere but their own computer (see [Whole app](Whole%20app.md)), so moving to another computer starts with an empty record.

**What it remembers can be out of date.** The user re-links a texture, adds three, removes two — so what Smoozy remembers can describe a file that no longer exists. The record answers *where did this one live* and *what did the user decide*; it never answers *what does this file need now*. Only the check answers that, and the check reads the file every time it runs.

**The record describes a file, not a scene.** The check covers the whole file, so what the record holds is that file's references and what each resolved to. Nothing in it says which scene uses which. Any other module reading this record inherits that limit: it can be asked what a file needs, and it cannot be asked what one of that file's scenes needs.

## Iterating

This is the loop the whole module exists for.

**Re-uploading the artist's `.blend` undoes nothing.** The user changes a light, saves, sends the file up over the old one, and submits — with no check at all. Nothing has to be redone, because the remap was never inside that file to be overwritten: Smoozy's record still holds it and it still applies. Label: **Creator-stated** (2026-07-28).

That covers a change to what the file already pointed at. Two other kinds of edit are not covered.

An edit that **adds** something: a texture linked for the first time is not on the machine, nothing is checked at a submission, and the render will not find it.

An edit that **re-links** an existing reference to a different file: the reference now records a different location, so the remembered answer — which is keyed to the location the file records — no longer belongs to it. Smoozy treats it as an addition: a reference it has not seen, which the next check has to resolve like any other. The old answer is not quietly reused for it.

So the promise is that re-uploading costs the user nothing they had already done — not that any edit is safe to submit unchecked. The warning at submission is what stands in for the difference.

**Changing a linked `.blend` needs no new work on the file above it.** The top file points at a location on the machine, and that location does not change. A new version of the linked file landing in the same place is picked up with nothing else done. Label: **Creator-stated** (2026-07-28). That holds only where the new version arrives **through this module** and where the edit added nothing and re-pointed nothing.

**Which is why a changed linked `.blend` is checked before it takes the place of the one on the machine.** Smoozy cannot tell from outside whether the new version added a texture or re-pointed one, so it does not assume: the new version is checked as any file is — its references read, anything missing found and sent — and it replaces the old copy after that, fixed. That is what sending it through this module means, and it is why sending one by hand is warned about.

**A plain upload landing on a file Smoozy fixed is warned about.** Nothing stops a user sending a linked `.blend` up by hand through the file browser, straight over the remapped one — which would land an unremapped file where a remapped one was and break the next render silently. So Smoozy knows which files it placed and fixed on a machine, and where a plain upload is about to land on one it says so and offers to send it through this module instead. This is the same shape as the file browser's warning before disturbing a file a live job needs (see the [File Browser spec](File%20Browser.md)).

**Nothing is checked when a render starts.** Smoozy does not look at the file at submission, and does not verify that what it remembers still holds. The user can submit a file that was never checked, or one whose assets have moved since, and Smoozy will let them. Label: **Creator-stated** (2026-07-28). What they get instead is the warning below.

## When the warning stops

[Rendering](Rendering.md) warns at submission when nobody has looked for a file's missing assets. This module owns what makes that warning stop, and the rule has two halves.

**A check that leaves nothing unfound stops it, for that file, on that machine.** Label: **Creator-stated** (2026-07-28).

**A check that left things unfound does not stop it — it replaces it.** The generic warning that nobody has looked gives way to a specific one saying how many pieces Smoozy could not place. That is worth more than either silence or the generic wording: the user is told what is actually wrong rather than that nothing is known. It blocks nothing and can be dismissed, exactly as the generic one can. Rows the user has **set aside** do not count as unfound — setting one aside is the user saying they know and do not care, and counting it would be the row asking for ever.

**A check describes one file on one machine.** The assets are on a particular machine, so a check run against one server says nothing about a newly rented one, where none of them exist. Connect a new machine and the warning is back, because for that machine nobody has looked.

Three more things follow. It does not matter whether the user **acted** on what the check found — a check that found plenty and was acted on not at all has still told them, which is what the replaced warning above carries. It is **remembered** rather than lasting only the sitting, because Smoozy keeps what it learned about the file anyway. And it **comes back when the file is replaced**, because a check describes the file it read, and a new upload is a different file.

**That last part is felt on every iteration, and the cost is accepted.** The loop this module exists for is change a light, send the `.blend` up, submit — and the upload replaces the file, so the warning is there every time. Smoozy does not try to work out whether the edit mattered: it does not read the file at a submission, and a re-upload that added a texture looks exactly like one that moved a light. So the user renders through one dismissible warning per iteration. That is what never checking behind the user's back costs, and it is a warning rather than a stop precisely because it is expected to be dismissed most times.

## Cleaning up

**Smoozy never removes assets from a machine by itself.** They are up there precisely so they persist, and anything tidying automatically would fight the reason the module exists. Smoozy also cannot know when a project is finished. The user deletes them through the file browser like anything else on their own machine. Label: **Creator-stated** (2026-07-28).

**Smoozy knows what it placed on a machine, what it fixed there, and what points at what.** It put the assets there, it fixed the linked `.blend` files, and its record holds which reference resolved to which file. So it can tell when a delete would break something that is not obviously connected to what is being deleted — an asset shared by two projects because a later reference was pointed at the copy already there, or a `.blend` that was fixed to point at assets and would be left pointing at nothing.

**So a delete of something depended on is warned about whether or not a job is live.** The file browser already warns before disturbing a file a running or waiting job needs; what this module adds is a second sense of *depended on* — not only what a live job is reading, but what anything on the machine has been pointed at. The user can still go ahead, and is never left to find out later. The wording and the shape of that warning are File Browser's, which owns every warning it shows — see the [File Browser spec](File%20Browser.md).

**Writing over such a file is warned about on the same terms.** An upload that lands where a different file already sits leaves everything pointing at it pointing at something else, which is the same harm as removing it and is easier to miss, since nothing disappears. So the same warning is given, from the same knowledge, before the file is replaced — see *Sending them up, and where they land* above, which settles what the user is offered. Label: **Creator-stated** (2026-08-06).

## What this module does not do

- It does not read a `.blend` for its **render settings** — that is **Render Settings**' Pre-load Settings. This module's read is for what the file points at, and neither read waits on the other. *(Withdrawn 2026-10-13: the change of 2026-10-12, that either read starts the other, was taken back the next day because the Creator deferred the request (the ninth notes, note 4). The idea is parked in Open Threads.)*
- It does not do **ordinary uploading**. Sending up files the user points at is **File Browser**'s, and it changes nothing inside those files.
- It does not supply **add-ons**. A `.blend` can need one to render, and that is not a file this module goes and finds: what a job needs by way of add-ons is **Render Settings**' Pre-load to work out, and Smoozy supplies none — the Creator parked add-ons on 2026-10-08 (see the [Server Setup spec](Server%20Setup.md#add-ons)). The two are kept apart deliberately — this module's check is about files it can locate on the user's computer and place on the machine, and an add-on is not one of those. **How far that working-out reaches is not this module's to state**: a `.blend` keeps no account of the add-ons it needs and no version offers a way to read one out — label: **observed**, all four versions — so whatever Pre-load produces is a reckoning rather than a list read off the file, and the [Render Settings spec](Render%20Settings.md) answers for it. This document once wrote it as though the list were simply there to be had; it is named here as a boundary and nothing more.

  **What an add-on leaves on disk is a different matter, and it is this module's.** An add-on can write out a result the render then reads back, and that result is a file on the user's computer like any other — so it belongs in the check, though Smoozy does not supply the add-on that made it. The line is between the add-on, which is not this module's, and what it left behind, which is a dependency. Whether such a thing shows up in a file's references at all is part of the unsettled list below, since the complete list of what a `.blend` can point at is not established.
- It does not supply the **colour management configuration** the computer holds. A `.blend` stores the *name* of a colour space, not a location for the profile behind it, so this is not something the file points at and not something this module can find and send. Label: **documented and observed**. Where the machine's configuration does not hold the name, Blender throws the name away, puts its own in place of it, prints that it did so, and renders anyway. Label: **observed**. That the picture then comes back in the wrong colours is **inferred** rather than watched. That makes it the same shape of quietly wrong output this module exists to prevent, reached by a route this module cannot see.

  **Which module makes the machine's configuration match the artist's is settled 2026-09-02: none does.** Nothing in Smoozy carries the artist's colour management configuration to the machine, and no module undertakes to make the two match. Supplying one is a whole feature nobody has asked for and nobody has costed, so naming an owner for it here would buy that feature by a side door. What closes the hole instead is the telling, and the material for that already exists: Blender says the substitution out loud while the render runs, Smoozy keeps everything a render prints, and it already picks particular lines out of that as they go past. So where a render's file asks for a colour space or a view the machine does not hold, **the job's entry says so** — that the machine did not have what the file named and that Blender rendered with its own in its place. Nothing new is built for it: no new module, nothing extra sent up, and nothing new done on the machine. **One limit, stated rather than hidden:** Blender prints in two places while it runs — its running commentary and its complaints — and which of the two carries this line was never recorded, so both have to be watched for it. **What breaks without the telling:** an artist working in their own colour configuration renders on a machine that quietly puts Blender's own in its place and finishes, and nothing anywhere says the frames came home in colours the file did not ask for.
- It does not **submit** anything, or decide when a render starts. That is **Rendering**'s.
- It does not **connect** to a machine, and never reaches one the user has not connected.
- It does not **block** a render. It warns, it says what it could not do, and the user decides.
- It does not **check a `.blend` by itself** — not at submission, not on a schedule, not when a file is chosen. *(One exception from 2026-10-17: the check runs again once when an upload it started ends with files arrived — [Checking a file](#checking-a-file), the Creator's tenth notes, note 4. No auditor has seen it.)* It does watch where an upload is about to land, so it can warn before a plain upload covers a file it fixed; that is a look at the upload's destination rather than a read of any file, and it warns without blocking — the user can go ahead.

## What is not settled

The Blender facts the promises above rest on are labelled where they are used, and their citations are in [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). What is still open is gathered here.

**The one the Creator called a deal-breaker is answered.** Names written in **non-Latin characters** — Chinese, Cyrillic and Hebrew among them — survive being read out of the file, carried to the machine, and found again by the render, with nothing said about them at either end. Label: **observed** — the same in every version, from a Mac to a rented Linux machine. Label: **Creator-stated** (2026-07-28) that it had to be answered, because a user whose project is named in their own language is not an edge case. So the shift, the landing rule and what a row shows all hold for that user. One version difference sits beside it: a name inside the file may be 63 bytes long in Blender 4.5 and 255 in 5.0, 5.1 and 5.2, and a character outside the Latin alphabet takes more than one byte. Label: **documented**. Two limits stay, and they are not the same kind of limit. **The Windows half is permanently unresolved**, settled so on 2026-09-02: nothing at all was tried on Windows, and the Creator's ruling of 2026-08-31 puts a Windows computer out of reach, so a name written on Windows is outside what this module promises. **The other half is open and cheap to close**: the names tried are written the same way by both computers, so a name they would write differently is untried — but ten Windows-authored `.blend` files already sit at `/Users/artist/Documents/Windows-authored files/`, one of them a case of exactly this kind, and reading them needs a Blender and nothing rented. Nobody is owed that reading and nothing waits on it. **What breaks meanwhile:** such a name is not found, not sent and not shown as a row, and the render reaches the machine missing it — `Preparation/Architecture/Dependency Upload & Remap.md` F11, §12 items 10 and 3.

The rest, each stated where it arises:

- Whether the **list of what a `.blend` can point at** is complete, and what a **library that does not sit on the user's own computer** would mean. Under *Checking a file*. The first wants no equipment, only a source that claims completeness, and there is none; the second wants storage two computers can both reach. **Both are permanently unresolved**, under the Creator's ruling of 2026-08-31 that there will be no further Blender research and no further rented machine.
- What a location **written on a Windows computer** means on the machine, and what a location **pointing at another computer** means at either end. Under *Sending them up, and where they land*. The first wants a Windows computer. One can be rented and four have been, but every one this project has read turned out to be a server edition rather than the ordinary desktop Windows an artist has — and the artist's own computer may well be one. **Both are permanently unresolved**, under the Creator's ruling of 2026-08-31 that there will be no further rented machine.
- Whether rendering **one scene** of a file pulls only that scene's references. **Answered for the two kinds that were tried, and the answer is yes.** Label: **observed** (the same in all four versions, on both machines) — see [Sources](Sources/Dependency%20Upload%20&%20Remap.sources.md). Rendering one scene opens that scene's own picture and never the other scene's, watched two different ways on two machines with a control that worked either way. A `.blend` linked as a library is opened whichever scene is rendered, because it is read when the file is loaded rather than when a scene is drawn. **What the tests cover is a picture used by a scene's material and a `.blend` linked as a library, and nothing else a file can point at** — so this is not a general answer about every kind of reference. And a scene reached *from* the one being rendered — as a background scene, through a compositor node naming it, or through a strip in the sequencer — was touched by no test, which is the case where a render genuinely does reach into another scene. This module checks the whole file by decision, so nothing here rests on either half; other modules do.

Three things the research settled were Smoozy's own to decide, and all three are now decided where they arise: what the row says when a file is present and the named thing inside it is not, where a place the file writes to should land, and which module supplies the machine's colour management configuration — the last of them settled on 2026-09-02, and the answer is that no module does.
