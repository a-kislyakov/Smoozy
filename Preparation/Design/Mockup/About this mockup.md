# About this mockup

This folder holds **`Smoozy.html`** — one file, no build step. Open it in a browser.

## What it is

**The Design stage's drawing of the app**, and the one place its values live. Colours, type, the two faces, radii, the load-bearing widths, the side gutter and the row gap are tokens at the top of the file; [Design values](../Design%20values.md) says what each one means and what may use it.

It carries every screen, and the states each screen has to be in — a server list, an empty one, adding, removing, a changed identity, a server that is connected and whose key has gone, browsing files, dragging files in, a connection down, an already-there question, deleting, the queue, history, an ending Smoozy never learned, a failure with no frame finished, transfers, setting a server up, Settings, and the rest.

## It can be walked through

**The screens are joined up, so the mockup can be used rather than only looked at.** The rail goes where it says, the menus go where they say, opening a server opens it, choosing a `.blend` brings up its settings, submitting a job says so beside Render and *Show in Queue* opens the queue, sending a file's missing pieces lands in Transfers, right-clicking a file gives that file's menu, Upload asks the already-there question, and Connect meets the changed identity.

**The state bar also carries a window width, and it is the only way to see the layout properly.** The narrowing steps answer to Smoozy's own window rather than to the screen, so the bar sets that window directly. Eight widths: two wide enough for everything, *Fit* for whatever is showing the file, then the four narrowing steps and one below the floor.

**A width wider than the thing looking at the file is drawn at that width and scaled down**, so the whole layout is visible rather than a slice of it. That matters because some viewers lay a page out at a fixed narrow width whatever the window is doing — in one of those, *Fit* is already a narrowed state and the full-width design cannot be seen at all without this.

**And every state is one click away on the state bar along the bottom**, grouped, with the one you are in marked. That is there for the states no control of the user's can bring about — a connection dropping, a catch-up notice arriving, a setup cut off part-way — so nothing is reachable only by hunting through a list. The bar is built from the **Mockup state** list in the title bar, so the two cannot drift: add one and the other follows. Both are part of the mockup and not part of Smoozy.

**Where a control has nothing drawn behind it, it says so** rather than doing nothing — a line at the bottom reading *Nothing drawn behind this yet*. That is deliberate. Walking the mockup should show where the holes are, and a button that silently does nothing looks the same as one that is broken.

**Keys is drawn in both of its shapes**: the housekeeping list, and the same list opened from a server dialog to choose a key for one.

**So are the two modules drawn rather than written.** *On the phone* holds Telegram's conversation, which is the one surface here that is not Smoozy's window. Rendering owns no screen, so its own moments sit where they belong: a queue banner for an all-scenes submission the connection broke, and the settings panel saying where its values came from when a job is submitted again.

A **Design notes** button opens what each screen decided and why, in short.

**The menu bar along the very top is drawn where a Mac does not put it.** The menus and what is in them are real and are settled in [Whole app](../Whole%20app.md); on a Mac they sit at the top of the screen rather than in the window, which no single drawing can show. The line saying so is part of the mockup and not part of Smoozy.

## What it is not

**It is not the plan.** The Design documents beside it are: [Whole app](../Whole%20app.md) and one per screen. Where the two disagree, the documents win — they hold the decisions and the reasoning, and this holds what those decisions look like.

**It is not the app.** Nothing here is code Smoozy will run. It is drawn to be looked at and argued with.

**Rendering and Telegram live here and nowhere else.** The Creator ruled on 2026-08-23 that these go through Design **drawn rather than written**, so they have no documents beside them: their screens are here and the reasoning behind each is in the Design notes. That makes this file the plan for these two. Access left with the free-and-open-source drawing pass of 2026-10-27.

**Every screen is drawn and every marker in every Design document is closed**, the whole-app pieces included: what a failure looks like, what *underway* looks like, the password prompt, the notifications and the update. **What is left for the stage is not in this file**, and where the stage stands is `Audits/Design/Progress.md`'s to say — this one describes the drawing, not the progress.

## Changing it

Change a token to change a value everywhere — the gutter moves every screen's content at once, which is what it is for. Change a screen to try something. Then check whether a Design document has been made wrong by it, and fix the document rather than leaving it stale.

**A new screen's classes take a prefix of their own, and this has gone wrong four times.** The Keys screen was drawn with names like `krow` and `gone`, both of which already existed elsewhere in the file — so its rows silently took another screen's layout and looked *slightly* wrong rather than broken, which is the hardest kind of wrong to see. Its classes are `ky-` prefixed. The second was `.steps`, declared once for Server Setup and once for the Telegram dialogs; the later rule won, so Server Setup had been rendering at the other screen's spacing and colour for as long as both existed. The dialog one is `.bsteps`. The third and fourth were found together on 2026-09-02, and neither was a whole screen taking another's layout: `.adl` was declared once as a bordered column and once as a centred row, and the two **merged** into a centred card that neither author had asked for; *underway on the control* was written twice under two names, `.uway` and `.wk`, with two spinners, two animations and a fade on one of them, so one idea had two looks.

**None of these looks broken, which is the point** — grep the file for a class name before using it, and grep for the *idea* before writing a second name for it.

**Joining a new control up takes no code.** Put `data-go` on it naming the state it leads to, and the mockup does the rest — with `data-panel` to open a panel over a server, `data-sec` to open a Settings section, or `data-modal` to raise a box in place. Anything carrying none of those falls through to the *nothing drawn behind this* line by itself.

**A change that is a decision rather than a value goes into a Design document first.** The mockup shows; the documents settle.
