# Server Setup

*What getting a server ready looks like, how the Blenders on it are shown and changed, and what the user meets when a setup restarts the server or stops part-way. The conventions it follows are the [whole-app Design](Whole%20app.md)'s and are not restated here.*

## Where it sits

**The second of a server's two tabs**, beside [File Browser](File%20Browser.md), filling the server's screen. It is reached by opening the server — never by a control in the server list, because a control saying *Set up* in a list reads as an instruction that the server needs setting up, which is usually untrue.

**Connections.** It serves the [Server Setup spec](../Specs/Server%20Setup.md). The Blenders it installs are chosen between in [Render Settings](Render%20Settings.md). Its folders link into [File Browser](File%20Browser.md). Before removing a Blender it reads live work from [Queue & History](Queue%20&%20History.md).

## Two sections, and no third

**This server**, then **Blender**. There is no add-ons section, because Smoozy installs no add-ons. The Creator, 2026-10-08: *"Let's ditch add-ons for now. […] I feel like this will create more problems than it will solve. Maybe someday when I have all the add-ons that fit the criteria of running at render time myself I will get back to it. But right now — we're not building it."* The section drawn earlier that day (the 38's P6) is taken out with it, and the matter is parked in [Open Threads](../Groundwork/Open%20Threads.md) until the Creator holds the add-ons that run at render time.

## This server

**One state line, when it was done, one action, and a list of what was done.** Nothing else.

**The list is the point.** *Ready to render* is a word the user has to take on trust unless the screen says what Smoozy actually did. So the card names it. That answers *what is this section about* without a sentence explaining anything. Label: **Creator-stated** (2026-08-11).

**The list is always the last setup's steps, each with its mark** — *done*, *nothing to do*, *not checked …* — whether that setup installed everything or found nothing to do. *Install the GPU driver — done* is what says the driver went in. **Telegram reporting's line sits under the steps**, because it is the server's own reading and not a step of the run (the [architecture](../Architecture/Server%20Setup.md) Y6b). **It is drawn only where it says something the steps do not**: where the steps already list *Install Telegram reporting — done* and the server reads it as installed, the line would say the same thing twice, and it is not drawn. It stays where the steps do not list that step — Telegram added later by *Install it*, whose run replaces nothing of the ready action's record — and wherever the server's reading differs from the step, as *Telegram reporting not installed* with its action (§ Adding Telegram to a server already set up). *(Added 2026-10-29, Creator-stated, the twenty-first notes, note 1, on the Creator's screenshot of A6000's card: "Alignment is a little strange." The card said Telegram twice, once as the step and once as the reading. Drawn as `su-done`. No auditor has seen it.)* Where no setup Smoozy can read reached its end, there are no steps to list and the card says so. *Changed 2026-10-02, the Creator's note 6 on 0.1.7: a first setup showed a short summary and Set up again showed the steps, and "it should be consistent in that regard". It was a list of what was done, the driver and Telegram.*

**Each mark is in its meaning's colour, and the step's name stays in ordinary ink.** *done* is green (`--ok`); *nothing to do* is grey (`--idle`); *not checked …* is amber (`--busy`), being something for the user's eye; a step that failed is red (`--bad`), as the stopped card already draws it. *Added 2026-10-03, the Creator's note 3 on the test copy: "nothing to do, done and whatever else there is should be color-coded to discern it from the rest." [Design values](Design%20values.md) widened `--ok` by one phrase the same day. No auditor has seen it.* **And each mark is italic and a step heavier (weight 500)**, so it stands apart from the step's name by shape as well as by colour. Italic has no other meaning on this card; it means *the file's* only on the settings page. *Added 2026-10-04, the Creator's note 1 on the test copy: "I like the subtle color coding, but it's too subtle. Maybe make it italic, too?" Settled at Design by the build runner; no auditor has seen it.*

**Just after *Add and set up*, while the connection it asked for is being made, the state line reads *Connecting…* and the action is under way on itself.** Then the run's steps take the card. *Added 2026-10-02, the Creator's note 3 on 0.1.7 ([Servers](Servers.md), Adding a server).*

**Where that connection is not made, the card says so: *Could not connect to this server.*, with the red dot, and its action is *Connect and set up***, which connects and runs the setup the add asked for (the [architecture](../Architecture/Servers.md) B1 keeps it). It claims nothing about why. Where the connection met a cause [Keys](Keys.md) has its own sentence for, the card says that sentence instead, as All servers does. It stays until the next act on that server — connecting, editing, removing it or dropping the setup — and is not kept past closing Smoozy. *Added 2026-10-03, the Creator's note 14 on the test copy: "Deliberately chose the wrong key. It didn't connect, didn't tell me that anything is wrong, nothing." The sentence was said above the All servers list, which Add and set up had just moved the user away from. A hole a fault exposed, ruled by the build runner; no auditor has seen it.*

**Where the connection is made and Smoozy's first checks then stop the add — the server is not Linux, or the connection drops — the card says that reason with the red dot, and its action is *Set up this server***, because the add's setup is no longer remembered (the [architecture](../Architecture/Servers.md) B4 and B5) and *Connect and set up* would only connect. *Added 2026-10-08, the Creator's fourth notes, piece M2: the card read* Smoozy has not read this server yet. *Design conforming to Architecture under Rule 10, ruled by the build runner. No auditor has seen it.*

**The card always shows the server's graphics driver, under the steps, beside Telegram reporting's line**: *NVIDIA driver 595.91.07 · CUDA 13.2*. It is the server's own reading, like that line, so it is there whether or not a setup ran, greyed with when it was read where Smoozy is not connected, and absent where no NVIDIA driver answers. *Added 2026-10-11, the Creator's rulings on OptiX and the driver ([architecture](../Architecture/Servers.md) H11b). Design conforming to Architecture under Rule 10. No auditor has seen it.*

**Where that driver is too old for OptiX in a Blender and Smoozy cannot replace it, the card says so in amber, from the first connection, with the amber dot**: *This server's NVIDIA driver, 550.163.01 (CUDA 12.4), is too old for OptiX in Blender 5.2 and later. It can't be updated here.* That is a container. Where a setup tried and did not get the driver there, the last sentence is *It could not be updated.* On a server Smoozy can update, nothing is said: setup does it. It names no provider and offers no control. It stays while the reading says so. *Added 2026-10-11, the Creator's rulings on OptiX and the driver ([architecture](../Architecture/Servers.md) H11b). No auditor has seen it.*

**What the last act came to stays on the card while it is true.** A line such as *Install stopped.* or *Setup stopped.* stays until the next setup act on that server replaces it. Going to *Files* and back, or to another server and back, does not take it away, and nothing takes it away on a timer. **The same holds for *Server output*: its words stay until the next act the user asks for on that server.** A run taken up again, the next act waiting in the line, or a driver update Smoozy starts by itself adds to them or keeps its own, and never empties them; an open *Server output* keeps its words as more arrive. *(Added 2026-10-30, the Creator's twenty-third notes, note 3: "Server output sometimes gets cleared for no apparent reason." No auditor has seen it.)* *Added 2026-10-03, the build runner's ruling (a), under the Creator's standing delegation of 2026-08-31: the Vast pass before 0.1.9 watched* Install stopped. *leave the card 9 seconds after the stop with nothing pressed, and nothing said how long it stays. No auditor has seen it.*

**The action is called what it does.** *Set up this server* on a server never set up, *Set up again* afterwards. It was *Run it again*, and *it* was never named anywhere on the screen.

**It is offered loudly only where Smoozy can name a reason to press it.** The question worth asking of it is: on a server that says ready, why would anyone? There are four answers and three of them are not this screen.

- **The server was never set up.** That is the whole of this case now, and it is narrower than it was written. **Architecture answered Row 90's setup-state half yes** — a machine can be read for how far a half-finished setup got, by name and with the moment (`Preparation/Architecture/Server Setup.md` Y6) — so *Smoozy cannot tell what has been done to it* is no longer a state Smoozy is ever in about a machine it is talking to. What is left is exact: **no setup record at all, or a machine that failed the identity check.** Both are the same reading, both are loud, and on both, running the action is the main thing on the card. Label: **settled at Architecture** (2026-08-23), carried into Design under [Rule 10](../Groundwork/Rules.md).
- **The setup stopped part-way.** Its own screen, and there the action is the whole point.
- **Telegram was switched on after the server was set up.** Not this action at all — the [spec](../Specs/Server%20Setup.md) gives that its own, precisely so the machine is not restarted and a render killed for a message on a phone.
- **A job that asked for the GPU rendered on the CPU.** This is the real one, and it is new: the entry now names what did the work, so Smoozy can see it. So the line says what happened and what to do about it — *Set up again to reinstall the GPU drivers* — with the control beside it. **What it does not say is what the job cost**, which is Smoozy's opinion of the user's money rather than a fact about the render. Label: **Creator-stated** (2026-08-11).

  **It is what the job asked for that makes this a fault, not the CPU on its own.** A job submitted with the scene set to the CPU and rendered on the CPU is the artist getting exactly what they asked for, and the line does not appear — the [spec](../Specs/Render%20Settings.md) is firm that choosing the CPU is a real choice and not always a mistake. Firing on every CPU render would tell somebody with a healthy server to set it up again, and pressing that can restart the server and take a six-hour render down. What the scene asked for is on the settings page and goes with the job, so Smoozy can tell the two apart. Label: **Creator-stated** (2026-08-13).

**On a healthy server with none of those, it is an ordinary control, just not the loud one.** Pressing it may restart the server and take a six-hour render down, so a control drawn loud on a machine with nothing wrong is worse than useless. **It is never greyed out.** The user may want it for a reason Smoozy cannot see — a provider rebuilding the server underneath it, leaving Smoozy's own record right about what it did and wrong about what is there. So it sits below what the card says rather than beside the state line, and it is always available. Label: **Creator-stated** (2026-08-11). This is the same reasoning the [Servers](Servers.md) screen already uses for keeping *Set up* off a server row: a control offering it reads as an instruction that it is needed. Label: **Creator-stated** (2026-08-11).

**Nothing says the action is safe to repeat, and that is deliberate.** It reads as a warning that it might not be, on a screen where nobody asked. Where repeating it genuinely matters — a setup cut off part-way, where the [spec](../Specs/Server%20Setup.md) makes running it again the way forward — that screen says so, because there the user has a problem and needs the answer. *(It is not the only way out of a stopped setup, and [that screen](#the-two-ways-out-and-the-control-the-second-one-lost) carries the second one; the spec's sentence was written before the architecture composed it.)* Label: **Creator-stated** (2026-08-11).

**The GPU question is answered where it can be answered, and the line says which case it is in.** *Ready* only means the driver went in: the [spec](../Specs/Server%20Setup.md) settles that a job with a missing or broken driver renders on the CPU, writes its picture and reports success, so nothing before a finished job can say. What the research bought is that a **Cycles** job names what did the work.

So the card has **three** lines, not two, and only one of them is a hedge.

- **A Cycles job has run.** *Last job rendered on NVIDIA GeForce RTX 4090 · OptiX.* A fact, stated flat. *(The example read *· CUDA* until 2026-10-03, when the Creator ruled that NVIDIA cards render with OptiX — `Rendering` L23.)* The device as Blender names it, then the word in brackets after it; a line in any other shape is shown as printed. *Changed 2026-10-17, the Creator's tenth notes, note 3: the whole printed line was a mouthful. A count of cards is not shown, since how the line reads with several is not on record. The example read *Last job rendered on 1 × RTX 4090 · OptiX.* No auditor has seen it.*
- **Nothing has run here yet.** Nothing confirms it renders on the GPU, said once and gone the moment a job finishes.
- **Jobs have run and none of them said.** This is the one the design missed. The [spec](../Specs/Server%20Setup.md) is exact that every result behind the line is Cycles' own report, and whether an EEVEE or Workbench job names anything is not established in any version — so a server that has only ever rendered EEVEE has finished jobs and still nothing to read. The line says that: jobs have run here, and none of them said what did the work. It does not name EEVEE as the reason, because the research does not say EEVEE is silent — it says nobody looked.

That is the difference between a fact and a permanent hedge, and the third line is what keeps the second from being told where it is not true. Label: **Creator-stated** (2026-08-11); the third line added 2026-08-13.

**Where the server is connected and Smoozy's service on it does not answer, the card's state line says the row's words, *Smoozy isn't responding.* (shortened 2026-09-27 on the Creator's word: *"The wording is too long, I think it should be shorter"*; it was *Smoozy's service on this server is not responding.*), and never that Smoozy has not read the server yet** — it has connected, and the service is what did not answer. *Added 2026-09-27, out of step 10c's seventh pass on RunPod; the words were owed from the eighth pass's fix map. The condition is the [architecture](../Architecture/Desktop%20app%20and%20delivery.md#12-the-automatic-supervisor-unavailable-repair-trigger)'s supervisor-unavailable condition (V1). As on the [row](Servers.md#a-row), the line does not say the server will or will not start the service again (`Rented-server runtime` §16 item 16). Design conforming to Architecture under Rule 10.*

**Where the row carries one of its lines about Smoozy on the server being older or newer than the app, the card's state line says the same words**, and **Update now…** stays on the row. *Added 2026-09-28; the lines are the [row](Servers.md#a-row)'s, from `Desktop app and delivery` V13. Design conforming to Architecture under Rule 10.*

## Blender

**A table of what is installed, read from the server every time.** The heading says so, because the server list deliberately shows no versions for the same reason: the user can install one without Smoozy knowing, so anything remembered would be a guess dressed as a fact.

**Three columns**: version, where it sits, and Remove.

**Nothing under the table says how the server was searched.** The [architecture](../Architecture/Server%20Setup.md) B11 keeps the count of folders the search could not read in its answer and does not draw it. *Creator-stated 2026-10-02, note 13 on 0.1.7: "All this should just go — it's unnecessary noise."*

**There is no kind column, because the version string already is one.** *4.5.9 LTS*, *5.3.0a*, *5.2.1* — an artist reads long-term support, alpha and release straight off the number, the way Blender writes them everywhere else. A column spelling that out again was a second copy of what the user had just read. Label: **Creator-stated** (2026-08-11).

**Two things the version cannot say get a small tag instead**: a build the user brought up themselves, and one below 4.5. The second is not a refusal — it can be picked for a job, and is never picked automatically.

**A third tag was owed and is added: a build Smoozy did not put there.** The [architecture](../Architecture/Server%20Setup.md) B8a reads a build's origin from the record of the act that placed it, and there are three answers rather than two — Smoozy installed it from the list, the user pointed at it, or **no install record names this path at all**, which is a build the machine's own software manager put there. That third is common on a rented machine and had no tag. It reads **not installed by Smoozy**, and it earns its place twice over: [taking it off](#removing-a-blender) goes through the machine's own software manager rather than by deleting a folder, and its folder may be one nothing can be written into.

**The tag says the origin and never the version.** Two builds answering one version are two builds with two paths (B13), so nothing here is keyed to a number.

**One more amber tag, where the server's graphics driver is too old for OptiX in that Blender: *driver too old for OptiX*.** It is drawn like *below 4.5*. Unlike the origin tags, this one follows the version, because Blender states its driver minimum per version ([architecture](../Architecture/Server%20Setup.md) B12b, with `Rendering` L23a's table). On a 570 driver it marks 5.2.1 and a 5.3 alpha, and 5.1 and 4.5 carry nothing. It refuses nothing: the build can still be picked for a job. *Added 2026-10-11, the Creator's own addition to their rulings on OptiX and the driver. No auditor has seen it.*

### The folder column stays

**It stays, and the [architecture](../Architecture/Server%20Setup.md) B12a is what settles it.** The marker asked whether it survives, no spec granting it. B12a grants it in this stage's own terms: the folder is the directory of the path the search returned for that build, derived when the table is drawn and never remembered, and the path is the only machine value this screen composes.

**Per build, never per version.** Two builds of one version have two folders, which is the same rule the tag above follows.

**The link is on every row, including the ones it cannot help with.** A build the machine's own manager placed may sit on a mount nothing can be written to; the link is offered anyway, because withholding it would be Smoozy deciding which folders the user may look at. Where the folder has gone or cannot be read, [File Browser](File%20Browser.md) says so in its own words — this screen hands over a path and claims nothing about it.

## Installing

**In Server output, Copy appears only where the open tab holds the server’s printed words.** It appears with the first words and follows tab changes; explanatory messages never count.

*Added 2026-10-23, Creator-stated, sixteenth note 2, 2026-10-21: “The copy button should not appear in the output (both server and Blender) if nothing has actually been printed yet.” No auditor has seen it.*

**The list is what Blender publishes.** Finished releases come from the shop-front and unfinished builds from Blender's own build service — the [spec](../Specs/Server%20Setup.md), Creator-stated 2026-10-02, and the [architecture](../Architecture/Server%20Setup.md) B2. *Until that day this paragraph said the list held no daily builds, and the drawing's *Daily build* entry had been taken out for want of a source.*

**What the list does carry is unfinished builds, and telling them from finished ones is this document's.** The [architecture](../Architecture/Server%20Setup.md) B2 hands that over by name: every entry carries a risk mark, and the unstable kinds are in the list marked as what they are.

**So the list is in two parts with a rule between them.** Finished releases above, named by their line — *Latest stable*, *Release*, *Long-term support*. **Latest stable names the version the quick path installs**, as chosen by the [architecture](../Architecture/Server%20Setup.md) B3; its long-term-support line is still named where present. Other rows on the shop-front's `latest` line read *Release*. *Changed 2026-10-27, the nineteenth notes, note 1; no auditor has seen it.* Below the rule, the heading *Experimental builds* and the entries under it, with nothing explaining them — Creator-stated 2026-09-27: *"everybody knows they are just called experimental builds."* Two parts rather than a tag on each, because the question a user has here is *which of these is safe to render a night's work with*, and a rule answers it before any entry is read.

**One version is one row in each part, and the row names every line that publishes it.** The shop-front publishes a finished release on each line it belongs to, so a newest release that is also a long-term-support release sits on two lines at once. Drawn one row per line, the list showed *5.2.2 Latest stable* above *5.2.2 Long-term support*, which reads as two builds. What the user picks is a version, and installing fetches that version from Blender's own downloads whichever line named it (the [architecture](../Architecture/Server%20Setup.md) B4), so the row reads *5.2.2 Latest stable · Long-term support*. **No published line is left out but one kind: an unfinished build is not shown where the list's finished releases hold the same series — a version's first two numbers — at the same or a newer version**, so a *5.2.2 Release candidate* goes beside a finished 5.2.2 and a *4.5.0 Beta* beside a finished 4.5.14, while a *5.3.0* stays until a 5.3 is released (the [architecture](../Architecture/Server%20Setup.md) B2; Creator-stated 2026-09-27 and 2026-09-28). Every other line is named, which is what B2 asks of a list whose entries are channels, and a line named twice is named once. **One kind of finished release is left out too: an older patch of a series that has a newer finished release**, so *5.2.2* goes once *5.2.3* is published, whatever this server holds, while *4.5.14* stays beside them (the [spec](../Specs/Server%20Setup.md) and the [architecture](../Architecture/Server%20Setup.md) B2; *added 2026-10-28, Creator-stated, the twentieth notes, note 1, runner-ruled; no auditor has seen it*). The row that is left names every line that published the newest version, so *5.2.3 Latest stable · Long-term support*. Settled at Build on 2026-09-27, out of the Creator's own sighting of 5.2.2 listed twice, under the Creator's standing delegation of 2026-08-31, and carried under [Rule 10](../Groundwork/Rules.md): B2 leaves how the list's entries are told apart to this document.

**An unfinished entry names its kind in Blender's own word: *Alpha*, *Beta* or *Release candidate*.** The build service marks each entry with its kind, and those are the words Blender's own pages use. *Changed 2026-10-02, the Creator's note 5 on 0.1.7: "Just 'unstable', which is not enough information." The third kind used to read **Unstable**, because the shop-front it then came from had no word an artist would recognise for it.*

**A build the server could not download is named in the failure**: *Could not download Blender 5.3.0 Alpha.* The [spec](../Specs/Server%20Setup.md) asks for the build to be named, and *the Blender build* named nothing.

**Each entry says whether that version is on this server**, which is a version comparison and nothing more: the [architecture](../Architecture/Server%20Setup.md) B6a is firm that a published entry is a channel and a machine's build is a path, so the mark can say a version is present and can never say *this build*. Nothing acts on it — installing goes ahead whatever it says.

**Each entry has a tick box, and several can be ticked at once.** The box's button counts them — *Install 5.2.2*, *Install 3 versions* — and installs them one after another in the order listed, each its own run — the [spec](../Specs/Server%20Setup.md), Creator-stated 2026-10-06 (the third notes on the test copy, note 2): *"Blender installations should be checkboxes, not radios."* The card shows the run in hand as it does for one. A failed install stops the ones still waiting, and the card's line names them: *Not installed: Blender 5.2.2, Blender 4.5.14.* *Until that day the entries were radios.*

**Where a failed install's steps stay on the card, its failure shows once, on the failed step, with the build and the versions not installed named there** — *Could not download Blender 5.3.0 Alpha. Not installed: Blender 4.5.14.* — and no line above the steps repeats it; where the card keeps no steps once the result is read, the line is the one place it shows. *(Added 2026-10-25, the build runner's ruling under the Creator's standing delegation, the small owed fixes after the eighteenth notes: a failed install drew its line above the steps as well as the failure on the step. An install's steps stay only where it left the server part-way set up, so the card reads that run. No auditor has seen it.)*

**Where Smoozy closed before the rest started, the card names them when Smoozy opens again**, in a line under the state line shaped like the failed-install line, with the words saying Smoozy closed first: *Not installed: Blender 5.2.2, Blender 4.5.14. Smoozy closed before they started.* With one: *Not installed: Blender 4.5.14. Smoozy closed before it started.* The install going in when Smoozy closed is not named, since it had started. The line stays until *Set up again*, *Set up this server* or another install is pressed on that server ([architecture](../Architecture/Server%20Setup.md) Y9a, which keeps the list and says when it goes). *Added 2026-10-16, step 10c's owed piece 4, on the build runner's ruling R3 and the [spec](../Specs/Server%20Setup.md)'s sentence of that day, under [Rule 10](../Groundwork/Rules.md). No auditor has seen it.* *Added the same day, owed piece 5:* an *Add and set up* that sets the server up ends it too, as *Set up again* does. *Widened 2026-10-27, the nineteenth notes, note 2:* where anything but installs from the list was waiting, the line names each as the card's *Queued* list did and says Smoozy closed first — *Not started: Remove Blender 5.2.2, Set up again. Smoozy closed first.* — and any act that begins a run on that server ends it.

### Asking for more while a setup runs

**Anything asked for while a setup runs waits its turn, and the card lists it.** The [spec](../Specs/Server%20Setup.md), Creator-stated 2026-10-27 (the nineteenth notes, note 2), and the [architecture](../Architecture/Server%20Setup.md) Y9a's line. Installing from the list, *Choose a build*, *Remove* and *Install Telegram reporting* all join the line when a run is going, and so does a *Set up again* asked for from a place that still offers it — the GPU-on-CPU line, the Servers row — and each runs as its own setup, in the order pressed. The running card itself does not offer *Set up again* (below). Drawn as `su-queue`. *No auditor has seen this.*

**The running card lists them under its steps**, under the server's lines where they are shown: the heading *Queued*, then one line per act in the order asked, greyed like a step not reached and with no mark, since nothing has happened to them yet. Each is named as the act it is: *Install Blender 4.5.15* (named as the list names it, *Install Blender 5.3.0 Alpha*), *Install your build blender-4.2-linux.tar.xz*, *Remove Blender 5.2.2*, *Set up again*, *Install Telegram reporting*. When an act's turn comes it leaves the list and its steps take the card. Nothing is listed where nothing waits.

**The running card offers *Install Telegram reporting* as well**, quiet, after *Cancel setup*, where Telegram reporting is owed on that server (§ Adding Telegram below), so it can be asked for without waiting. **It does not offer *Set up again*** — gone rather than greyed ([Whole app](Whole%20app.md): absent where pressing can never help), and back on the card when the run ends. Label: **Creator-stated** (2026-10-30), the twenty-fourth notes, note 1: *"Set up again should not be available (grayed out or just non-existent) when setting up is actually happening. There's no point in this button in this scenario."* *Until then the running card offered* Set up again*, quiet, after* Cancel setup *too. No auditor has seen this.* The Blender table under the card keeps its *Install Blender* and *Remove* as always.

**A press that joins the line is answered by the list**, at once: the act appears at its end. There is no other line on the card for it, and nothing is refused.

**What stops the rest is said after the ending's own sentence**, naming each act not started in the order asked: *Not started: Remove Blender 5.2.2, Install Blender 4.5.15.* Where the run in hand restarted the server, the reason follows: *Not started: Install Blender 4.5.15. The server restarted first.* *Cancel setup* stops the rest too, and the line names them the same way. Where only installs from the list were waiting behind an install, the line reads as it always has, above: *Not installed: Blender 5.2.2, Blender 4.5.14.*

**Warnings are shown at the press.** *Remove* still opens its box with the jobs named, and *Set up again* its warning where a render is running; the act joins the line only once the user goes ahead. Neither box is shown again when its turn comes ([architecture](../Architecture/Server%20Setup.md) Y9a item 9).

### Pointing at a build on your own computer

**The pick is the system's own file chooser, and Smoozy draws none of it.** That is the whole app's rule wherever a system already owns a question, the same one the password prompt follows.

**The send is an ordinary upload.** It carries its server's badge into [Transfers](Transfers.md) under the *Upload* tag like anything else going up, and the install panel shows it underway on itself. A fifth kind for one file would make the user look in two places for one answer.

### The below-4.5 warning

**It can only ever come from this route**, because the [spec](../Specs/Server%20Setup.md) keeps everything below 4.5 out of the list. A build under the floor reaches a machine one way, and it is the user pointing at one.

**It fires after the build is up and before it lands**, which is where the [architecture](../Architecture/Server%20Setup.md) B7 and B8 put the only moment Smoozy knows the version: the build is unpacked in staging, asked what it is, and renamed into place last. So the warning is not something the page could have said when the user pointed at the file — the file's name is not its version — and it is not an apology after the fact either.

**It says the three things the [spec](../Specs/Server%20Setup.md) names and then offers both ways.** The version is unsupported, nothing in the rest of the app is written for it, and Smoozy cannot help if a job on it goes wrong — with *Install anyway* and a way out. **The spec's own words are *the user's own affair*, which is a spec's way of speaking rather than a screen's**, so the line says the same thing in the plain form Rule 9 asks for. Offering the way out is not refusing: the build is still in staging, so a user who has just learnt what they fetched can still decline it, and a warning nobody can act on is a warning worth nothing.

**What it does not do is describe what will go wrong**, because nothing establishes that. The build can be picked for a job and is never picked automatically, which [Render Settings](Render%20Settings.md) already says on its own control.

### The two ways out, and the control the second one lost

**The [architecture](../Architecture/Server%20Setup.md) S6 closes the set at two runs, and for a time this screen offered a control for one of them.** The two are a setup run that reaches its end, and a recovery run the user asks to abandon the unfinished work — which still checks the machine first and says what it found. *Set up again* is the first. The second had a control called *Ignore*; it was removed on 2026-08-29 because *ignore* claimed the user could set the matter aside by hand, which is the one thing S6 says nothing does. **Nothing was put in its place, and that was this stage's own mistake rather than anything the architecture asked for**: it left a user who does not want to run the setup again with no way out at all, the row saying the setup stopped part-way on every connection from then on. The repair is below.

**The control is *Abandon setup*.** *Abandon* is the architecture's own word for the act, and it is the plain one for what the user is doing: giving up on a setup that did not finish. *Ignore* is not reused, and not only because it was rejected once: it says nothing is done, and something is. The run goes to the server, makes the setup's final check, says what that check found, and only then gives the unfinished setup up — so a label promising a silent discard would be wrong about the act as well as about the state.

**It sits in the card's control row, before *Set up again*.** Quiet, because most people here want the setup finished rather than dropped; *Set up again* stays the loud control. It is on both stopped cards — the one where the connection dropped and the one where a step failed — because the condition standing behind them is the same one. *(It sat between Close and Set up again in a box until 2026-10-02; there is no box now.)*

**It asks nothing first.** Nothing is deleted and nothing is put back as it was: what the run installed stays installed. Running the setup again is still there afterwards, so a box asking whether the user meant it would be guarding an act that can be taken back by pressing the other control.

**What it leaves the server row reading: nothing about a setup.** *Setup stopped part-way* is a reading of the machine, not a note Smoozy kept, so once the machine stops saying it the row stops showing it — and the row is then an ordinary server row, which is what every row is unless something on that server needs saying. **The card is the half that still says something, and it says *Not set up***, with the loud *Set up this server*, exactly as on a machine never prepared. The [architecture](../Architecture/Server%20Setup.md) Y6a is what settles that: a setup that happened is a run whose record reached the last step, an abandoned run never reaches it, and so nothing on the card may say the server is ready.

**What the card does not claim is that the server was doing no work until then.** Whether a stopped setup holds the server's work back depends on whether the run had reached a step that changes the machine, which the [architecture](../Architecture/Server%20Setup.md) Y1 decides run by run — so one sentence covering both cases would be wrong about one of them. The card says what the two controls do and stops there.

**Safe to run again, and not always able to start the moment it is pressed.** The [architecture](../Architecture/Server%20Setup.md) S5 refuses a recovery run while the machine still reports the run that stopped as running, so pressing either control here can be a wait before it is an act. The wait ends by itself — the [rented-server runtime](../Architecture/Rented-server%20runtime.md) X9a has the server finish with a run whose worker has gone — so there is nothing for the user to find out and nothing to ask them for. But *safe* on its own would have someone press a control on a screen they reached because something already went wrong and then meet a delay nothing mentioned, so the sentence carries the qualification, and carries it for both controls: S5 refuses either one on the same reading.

**So the stopped card's closing paragraph reads:** *Server checked just now. Set up again is safe. Abandon setup ends the setup unfinished. ## Admin access

**Asked only when a step is actually refused, and never before.** The [Whole app spec](../Specs/Whole%20app.md) owns the rule and the choices; this screen is one of the two places it is reached.

**The choices are radios, not boxes** — one decision with one answer, not a set of switches. They are: *Don't save*, *While connected* and *Save* (until cleared), with where it is cleared named.

**How many of them there are is not fixed, and [Whole app](Whole%20app.md) owns that rule.** The [architecture](../Architecture/Security%20and%20licence.md) S36 composes the offer from what the computer Smoozy runs on can do: where that computer has nowhere to keep a password, the choice to save it until cleared is absent rather than greyed, leaving two; otherwise three. So this screen offers two or three, and this document says no more than that — the rule and its reasoning belong to the document that holds them, and a fixed count here would contradict it. Carried into Design under [Rule 10](../Groundwork/Rules.md).
