## The four things settled before the plan hardened

Each of these changes the shape of the work rather than a detail of it, and each was cheap now and expensive later. All four are settled; the working out is in the Architecture documents they belong to.

**1. A value given on the launch line is in force when the launch material runs. It goes the right way, and no job was ever at risk of not rendering.** The Blender research answered this and nobody had read the answer against the three plans that were waiting on it. The arrangement that works is the file, then the setting, then the script — and that is exactly the order the launch line is already composed in. The read-back that guards the redirect therefore works. Two riders come with it and both are real: the value that comes back is the raw text handed in, template marks and all, so the comparison is against that text and never against a finished file name; and an output path given at launch reaches the active scene alone, which was tested on one file holding two scenes and so cannot say whether it turns on which scene is active. Where that second one goes badly the attempt fails safe rather than rendering somewhere wrong. Carried into `Rendering` §9 item 1, `Job files and outputs` §14 item 19 and `Rented-server runtime` §16 item 11.

**2. The desktop shell is unchosen and only Build can choose it, so it is step one.** `Desktop app and delivery` H5b is a comparison sheet with every figure deliberately blank, and it says outright that the sheet is the next Build input. Everything on the user's computer sits on the answer, and the answer also settles the language the desktop is written in. It is step one for that reason and no other.

**3. A failed read of the secret store is told apart three ways where the system allows it, and on one system it is two, and that is the honest answer.** Row 513. The three states are *the secret is gone*, *the store refused this once* and *the store is not available*, and they want different things of the user — get it wrong one way and the user retypes a secret the machine still holds, get it wrong the other and Smoozy waits for a store that is never coming back. What each system reports is already written down in `The manuals — keys, secrets, and what cannot be told apart.md`, so this needed reading and not research. macOS separates all three by result code. Linux separates all three, but the refusal is only visible if Smoozy drives the prompt itself rather than letting a helper do it — that is a build constraint and it is the whole cost of the answer. Windows has only two, because on the path Smoozy uses nothing ever prompts, so a refusal cannot arise. **The rule: the user is asked to type a secret again only where the store says the secret is gone.** Refused and unavailable both say what happened and neither is presented as a lost secret. Where a system cannot separate two of them, Smoozy says so rather than manufacturing a difference — the same answer this project has already given twice, in `File Browser` P1 and `Rendering` K11.

**4. Nothing is squeezed in transit.** Row 514. Two ways it could have been done and both are refused. Squeezing the connection is a setting OpenSSH already has and it is off by default at the client; OpenSSH's own manual says compression *"is desirable on modem lines and other slow connections, but will only slow down things on fast networks"*. **Nothing here claims to know which of those a rented machine's line is** — no line this project uses has been measured, and the source entry says so. What the decision rests on is the default and the publication's own statement, not on a speed nobody took. *(Corrected 2026-08-31: this said a fast network "is what a rented machine sits on", which is an unsourced claim about the world and a Rule 2 breach. The decision does not move.)* And it would buy little anyway, because nearly everything Smoozy moves is compressed before it starts: a Blender file saves compressed from 5.0 on — **documented**, and labelled and cited where it is owned, at `File Browser` L8 — while textures and finished frames are already-compressed picture formats. Squeezing the **file** — sending a compressed body and unpacking it at the far end — is the one that had to be refused rather than merely declined. A resume checkpoint is a byte offset into the staged file and its digest covers that file's own bytes, so compressing the body would make a resumed offset mean something different from a fresh one, which is exactly the interaction the row was filed to catch. **So the staged bytes and the bytes on the wire are the same bytes.** This costs nothing and closes the question for good.

## The order

Each step ends with something that works and can be watched working. That is the test for whether a step is a step.

### Step 0 — the ground

Nothing here behaves like the app.

- **The shell measurement.** Build the two throwaway artifacts H5b names — one for each candidate, the same window, the same page bytes, the same build settings — on each of the three systems, and fill in the sheet. Return it to Architecture. **The three sets of artifacts come from build runners rather than from hardware anybody here owns** — which is what H5b's own *one fresh runner image per operating system recorded by digest* row asks for, and it is the reproducible route rather than the cheap one. A rental is the wrong tool here whether or not one is available: a runner image has a digest and a rented box has a story. **That is enough for a size comparison and it is not enough to prove the app runs.** Proving it runs comes later and is named where it does — and it is where the hardware gap bites: **no Windows desktop edition has ever been reached**, every Windows machine this project rented reported a Server edition, and the Linux desktop questions wait on a hypervisor ruling that is the Creator's own act.
- **The language, which falls out of the shell.** The two candidates are built in two different languages — which is a property of the shells rather than a Smoozy decision, and it is `Desktop app and delivery` H1, H4 and H5b's material rather than this plan's to establish. Decide the server package's language beside it, so there is one toolchain rather than two — and remember what the server package has to be: a complete versioned thing placed on a bare rented machine that has nothing installed on it.
- **`App/` laid out** to the module set, matching how `Preparation/` is organised.
- **The code-audit briefs**, which `Auditing.md` has owed since Groundwork. **Listed here because this is where the debt is picked up, and written later**: [Method](Method.md) says they are written when the first module is ready to audit, so that they are written against real code, and the first module is step 1's. So the brief is owed from step 0 and lands at the first audit, and **nothing in step 0 waits on it**. *(Corrected 2026-09-02, where this read “written when there is real code to write them against, so not on the first day of this step” — which put them inside a step that produces no module and read as a contradiction of Method.)*

### Step 4 — the connection, and what rides on it

Three plans built together, because they are one cycle and none of them proves anything alone.

- **`Servers`** — what a connected period is, the closed list of moments a connection is opened or replaced, how a break is learned of without using the connection to learn it, and how long repair persists.
- **`Server protocol and transfers`** — the two mechanisms the pre-package surface is made of, request framing, correlation so that sending a thing twice does not do it twice, and the one staging-resume-integrity-publication contract that holds in both directions for the machine's whole life. Item 4 above lands here.
- **`Job files and outputs`** — where Smoozy's directories sit on a machine, what every path under them is called, and what the submission manifest carries.

**Two of these three are built in part rather than whole, and saying so is the point.** `Job files and outputs`' recorded reading, its expected-output inventory, its previews and its reckoning all need a Blender on a machine and land with steps 6 to 8; what comes here is the directory layout, the manifest and the publication contract. And `State, identity and recovery`'s machine-side stores land at step 6 — step 2 built its desktop half, because step 2 has nothing remote in it.

`Servers` is built first inside this step, but to the connection shape the protocol requires — one session alternating between reading and command work, extra connections for transfers only, the host key obtainable and comparable before Smoozy's credential is ever presented. Those are requirements on the connection rather than code it calls, which is why the two are built together rather than one after the other.

**This is the first step that needs a real rented machine, and Build may rent one** — ruled 2026-08-31, on the standing terms of 2026-08-17 that Architecture already ran on: cheapest thing that answers, destroyed the moment it has, account checked empty afterwards, and anything left standing between sittings on the board with the date it must go. The keys are in `~/.smoozy-keys/` and the runner points each agent at the one file its work needs. **A rental runs until somebody destroys it by hand and nothing caps it**, which makes destroying it part of the step rather than tidying afterwards.

**At the end of step 4 a file goes up, comes back whole, and resumes correctly after being interrupted.** That is the first thing worth watching.
